# 권한 설계

누가 KG를 읽고, 정의를 수정하고, 제안을 승인하고, 소스를 실행하고, 소스에 푸시할 수 있는지를 정해요. 사용자와 그룹은 사내 SSO가 관리해요. 프락시움은 거기에 **제품에 내장된 역할**을 **범위**와 함께 연결해요. 연결하는 사람은 관리자예요. 구현하는 사람이 이 문서만 보고 데이터 스키마와 경계를 알 수 있게 적어요. 결정은 ADR-0012에 있어요.

## 1. 목적과 다루는 질문

- 사용자와 그룹은 어디서 오고, 떠나면 어떻게 되나요? SSO에서 와요(3절).
- 무엇을 할 수 있는지는 어떻게 정하나요? 권한 부여 = 누구 × 역할 × 범위예요(2, 4, 5절).
- "아무개는 이 타입의 읽기만", "이 사이트의 객체만"이 가능한가요? 범위를 객체 타입과 객체 조건으로 지정하면 돼요(5절).
- 부여가 여럿이면 한 객체의 읽기 한도는요? 그 객체에 일치하는 부여들의 최댓값이에요(5-4).
- 읽을 수 없는 것은 어떻게 보이나요? 객체는 나오지 않고, 속성은 "가려짐"으로 표시되고, 건수는 가려진 것을 뺀 값이에요(7절).
- 수정은 누가 승인하나요? 그 항목을 범위에 가진 다른 `approver`예요(9절). 단독 테스트 배포는 9-4, 시크릿 복호화는 10-3이에요.
- 판정을 경로마다 다르지 않게 하는 방법, 스토리지가 중단됐을 때의 동작, 감사 로그에 기록하는 것은 각각 6절, 3-5, 12절이에요.

테라리움에서 인계받은 자료의 6절 쟁점 나(위임하는 범위와 검증한 범위가 같아야 한다)에 대한 프락시움 측 기반이에요. 위임의 수준은 엔드투엔드(E2E) 프로세스를 구체화할 때 정해요.

## 2. 개요

**권한 부여 하나 = 누구 × 역할 × 범위.** 이것이 권한의 전부예요.

| 누구 | 역할 | 범위 | 설명 (가상의 예) |
|---|---|---|---|
| 사람 한 명 | `viewer` | 객체 타입 `VirtualMachine`, `HypervisorHost` | 이 두 타입의 객체와 링크만 읽어요 |
| 사람 한 명 | `viewer` | 타입 `NetworkSwitch`, 조건 `site = site-a`, `restricted`까지 | 그 사이트의 스위치만 `restricted`까지 읽어요 |
| 그룹 `net-ops` | `editor`, `operator` | 네트워크 층의 타입과 소스 `switch_inventory`, `switch_config_pull` | 네트워크 층의 정의를 수정하고 그 두 소스를 실행해요 |
| 서비스 계정 | `ingester` | 소스 `rack_events` | 그 소스에 푸시해요. 읽기는 없어요 |
| 로그인한 모든 사용자 | `viewer` | 전체, 민감 등급 `open`까지 | 기본으로 공개된 것만 읽어요 |

```
 사내 SSO ─(사용자, 그룹)─▶ [OIDC 어댑터] ─▶ 주체 + 그룹
 관리자 ─▶ [권한 부여] ─(캐시)─▶ [권한 판정: 한 곳] ◀─(요청한 작업, 대상)─ API / MCP / 워커
                                       │ 허용·거절+이유 → [감사 로그: 추가 전용]
                                       └ 읽기 필터 → API가 질의 엔진의 응답을 필터링
```

역할은 제품에 내장된 8종이고 관리자가 수정할 수 없어요. 읽기도 권한 부여예요. 조직 단위는 권한에 쓰지 않아요. 사용자와 그룹이 어느 조직인지는 SSO가 알아요.

## 3. SSO 연결
### 3-1. 포트와 OIDC 어댑터

코어는 "로그인된 주체와 그 그룹"만 알아요. 로그인 방식은 포트 뒤의 어댑터가 맡아요. 첫 어댑터는 표준 방식(OIDC)을 지원해요. 특정 SSO 제품에 종속되지 않고, 같은 포트에 다른 어댑터를 연결할 수 있어요.

어댑터가 코어에 넘기는 것: `subject_id`(로그인 측이 정한, 바뀌지 않는 사용자 식별자. 불투명한 값으로만 다뤄요), `display_name`, `groups`(로그인 측의 그룹 이름 목록. 수정하지 않고 그대로 받아요), `issued_at`과 `expires_at`(토큰이 유효한 기간).

### 3-2. 사용자와 그룹을 가져오는 경로

- 프락시움은 사용자와 그룹을 **생성하지 않아요.** 전달받은 것에 권한 부여를 연결할 뿐이에요. 한 사람의 유효한 권한 부여는 그 사람에게 부여된 것, 그 사람의 그룹에 부여된 것, "로그인한 모든 사용자"에게 부여된 것의 합이에요.
- 그룹을 토큰에서 읽는지 사용자 정보 엔드포인트에서 읽는지는 SSO마다 달라 가정이에요. 코어는 `groups`만 받아요.

### 3-3. 그룹 변경이 반영되는 시점

로그인(SSO) 측에서 사용자가 그룹에 추가되거나 제외되면, 프락시움은 그 사용자가 **새 토큰을 발급받을 때**(다시 로그인하거나 토큰을 갱신할 때) 알아요. 반영이 지연되는 정도는 토큰의 유효 기간(`expires_at`)이 정해요. 즉시 차단하려면 SSO 측에서 토큰을 회수해야 하고, 가능한지는 SSO 방식에 달렸어요.

### 3-4. 사용자가 떠났을 때

- SSO에서 삭제되거나 그룹에서 제외되면 새 토큰부터 권한이 없어져요. 그룹에 부여된 권한은 따로 삭제할 것이 없어요.
- 그 사람에게 직접 부여한 권한 부여는 남아요. 관리자가 회수해요.
- 그 사람이 남긴 감사 로그, 브랜치, 제안은 그대로예요. 제안은 다른 `editor`가 인계받거나 닫아요. 서비스 계정에 연결된 사람(11절)이었다면 관리자가 연결을 해제해요.

### 3-5. 스토리지가 중단돼도 질의가 되게 하는 캐시

질의는 중단되면 안 돼요(ADR-0011). 그런데 권한 판정에는 "이 사람에게 부여된 권한 부여"가 필요하고 그것은 스토리지에 있어요. 그래서 API는 이렇게 해요.

- **토큰은 스토리지 없이 검증해요.** 어댑터가 검증에 필요한 것을 자기 안에 보관해요.
- **권한 부여의 캐시를 API 인스턴스마다 둬요.** 캐시에는 유효한 권한 부여, 기본 부여, 서비스 계정의 토큰 해시와 상태가 들어 있어요. 스토리지가 정상이면 주기적으로 다시 읽어요.
- **캐시에는 나이(`copied_at`)와 상한(`max_snapshot_age`)이 있어요.** 기본값(설정)은 15분이에요([기본값 표](defaults.md)). 상한 이내의 캐시로 판정해요. **상한을 넘으면** 수정 작업과 `restricted` 이상의 읽기는 거절하고, "로그인한 모든 사용자"의 기본 부여로 가능한 읽기만 계속 응답해요(헬스 상태에 알려요).
- **스토리지가 정상일 때 서비스 계정을 비활성화하거나 토큰을 회수하면 30초 이내에 전파돼요**(11절). 15분은 스토리지가 중단된 동안의 상한이에요.

## 4. 역할 8종

`ingester`를 제외한 모든 역할은 **자기 범위의 읽기를 포함**해요. 그 밖에는 서로 포함하지 않아요(`editor`가 `approver`를 포함하지 않고, `admin`이 `editor`를 포함하지 않아요). `●`는 수행할 수 있다는 의미이고, 범위가 있는 작업은 부여의 범위 안에서만 해요.

| 할 수 있는 작업 | `viewer` | `editor` | `approver` | `operator` | `model_steward` | `auditor` | `admin` | `ingester` |
|---|---|---|---|---|---|---|---|---|
| 객체 타입 범위 안의 객체와 링크를 읽고 질의한다 (속성은 등급 한도까지) | ● | ● | ● | ● | ● | ● | ● | |
| 소스 범위 안의 소스 정의(데이터셋, 정제, 피드, 일정)와 실행 이력(단계별 건수와 시간)을 읽는다 | ● | ● | ● | ● | ● | ● | ● | |
| 소스를 탐색하고 데이터셋을 미리 보고 연결을 점검한다, 폐기·격리된 레코드의 샘플을 읽는다 (7-6, 10-3) | | ● | | ● | | | ● | |
| 대량 읽기 (`viewer` 부여에 붙는 별도 허가 `bulk_read`) | 허가 | | | | | | | |
| 브랜치를 열고, 소속이 범위에 든 정의를 수정하고 제안한다 | | ● | | | | | | |
| 제안을 승인한다 (소속이 범위에 든 항목, 자기가 수정한 것은 제외) | | | ● | | | | | |
| 소스를 실행하고 중지한다, 트라이얼 수집을 한다 | | | | ● | | | | |
| 엑셀·CSV 파일을 업로드한다 (그 소스를 범위에 가진) | | ● | | ● | | | | |
| 범위에 든 소스에 데이터를 푸시하고 수집 엔벨로프를 보낸다 (서비스 계정에만 부여해요) | | | | | | | | ● |
| 타입 사용 현황 보고를 읽는다 (그 타입을 범위에 가진. `model_steward`는 자기 범위) | ● | | | | ● | | | |
| 사용자가 보고한 문제의 원인 분류(`cause_class`)를 정한다 | | | | ● | | | | |
| 안전장치 확인, 보류된 스트림의 해제와 폐기 | | | | ● | | | | |
| 질의가 읽는 KG 버전을 이전 버전에 고정한다 (`serving_pin`) | | | | ● | | | ● | |
| 조직 표준 타입의 제안을 승인하고, 타입을 조직 표준으로 승격하고 병합한다 | | | | | ● | | | |
| 감사 로그를 읽는다 | | | | | | ● | | |
| 권한 부여를 읽는다 | | | | | | ● | ● | |
| 권한을 부여하고 회수한다, 기본 부여와 서비스 계정을 설정한다 | | | | | | | ● | |
| 제품 설정을 수정한다 (SSO 연결, `solo_approval` 등), 차단된 작업을 해소한다 (10-2) | | | | | | | ● | |
| 안전장치의 값을 완화하는 제안, 민감 등급을 낮추는 제안을 승인한다 | | | | | | | ● | |

- 저장해 둔 범위를 생성하는 일과, 승인을 위해 제안의 검사 결과와 차이를 읽는 일은 읽기에 포함돼요.
- 소스 탐색, 미리 보기, 점검, 샘플은 그 소스를 범위에 가진 `editor`나 `operator`(샘플은 `admin`도)의 작업이에요. 트라이얼 수집은 `operator`예요. 시크릿 복호화 주체의 구분은 10-3에 있어요. 엑셀·CSV 업로드는 그 소스를 범위에 가진 `operator`나 `editor`예요. 고정은 전체 범위의 `operator`나 `admin`이 해요.
- `ingester`는 범위에 든 소스로 푸시하는 경로(소스 정의에서 열어 둔 것만)와 수집 엔벨로프를 보내는 작업만 해요. 읽기도, 그 밖의 어떤 작업도 없어요. 서비스 계정에만 부여하고 사람에게는 부여하지 않아요.
- 자기가 수정한 것을 자기가 승인할 수 없는 규칙은 `approver`, `model_steward`, `admin` 모두 같아요(`solo_approval`을 켠 배포만 달라요, 9-4).
- `admin`과 `auditor`의 범위는 언제나 전체예요. **`model_steward`는 층으로 범위를 좁힐 수 있어요.** 좁히지 않으면 전체예요(10-1). 정의 내보내기는 그 소속이 범위에 든 `editor`가 하고, 일정은 정의의 항목(`schedule`)이라 수정은 `editor`, 승인은 `approver`예요(ADR-0014). 소스를 지금 실행하는 작업은 `operator`예요.

## 5. 범위
### 5-1. 범위의 종류

| 종류 | 지정하는 것 | 적용 대상 |
|---|---|---|
| 전체 | 없음 | 모든 타입과 모든 소스 |
| KG | KG ID의 목록. 생략하면 `main` | KG에 속한 것(객체, 링크, 질의, 변경, 버전)을 읽는 권한. 정의, 소스, 권한 부여는 배포에 하나라 이 필드를 보지 않아요 |
| 객체 타입 | 타입의 목록(하위 타입 포함), 표준 모델의 층(`layer`. 예: 네트워크 층 전체), 네임스페이스(`std`, `org`, `ext`, 예약된 `sys`) | 그 타입의 객체와 링크를 읽는 권한은 **여기서만** 나와요. 그 타입에 딸린 정의의 소속이기도 해요 |
| 소스 | 소스의 목록 | 그 소스의 정의와 실행 이력을 읽고(`viewer`), 수정하고 탐색하는(`editor`) 권한, 소스를 실행하고 점검하고 트라이얼 수집을 하는(`operator`) 작업, 푸시하는(`ingester`) 작업. **객체를 읽는 권한은 아니에요** |
| 민감 등급의 한도 | `open`, `restricted`, `confidential` | 속성 값을 읽을 수 있는 한도. 생략하면 `open`까지예요 |
| 객체 조건 | 타입이 선언한 범위용 속성(`scope_keys`)과 값의 목록(`속성 = 값들`) | `viewer`의 읽기를 그 속성의 값이 일치하는 객체로 좁혀요(REQ-165) |

**KG는 계약의 자원이에요**(`/v1/kgs/{kg}/...`, ADR-0016). 운영 KG는 이름 `main`으로도 가리켜요. 시스템 KG(`sys` 타입을 담는, 프락시움 자신의 컴포넌트)도 KG라서 `main`의 권한으로는 읽을 수 없고 그 KG를 필드에 지정한 부여가 있어야 해요.

**객체 조건을 범위에 넣어요.** 타입만으로는 여러 조직이 함께 쓸 때 부족하고, 나중에 넣으면 질의 엔진과 프로젝션을 다시 수정해야 해서 지금 설계에 넣어요. 범위에 쓰는 속성은 타입 등록부에서 속성에 `scope_key: true`를 지정해 선언해요(사이트, 환경, 담당 조직 같은 것. 타입 하나에 4개까지, 값 타입은 짧은 문자열이나 참조이고 `volatile`은 안 돼요. 하위 타입은 상속해요). 문법은 고정되어 있어요(속성 = 값들의 목록). 프로젝션은 그 속성의 값을 객체마다 보유하고, API가 응답을 필터링할 때 써요(kg-queries.md). 범위에 쓰는 속성은 `versioned`이고 식별 키처럼 다뤄 함부로 바뀌지 않아요. 수정 권한(`editor` 등)은 지금처럼 소속(소스, 타입) 단위예요. 층은 타입 등록부의 객체 타입에 있는 필드 `layer`(표준 모델의 10개 층 중 하나. 10번째 `system`은 `sys` 타입이 놓이는 층이에요. 사용자 정의 타입은 만들 때 골라요)이고, [standard-model.md](standard-model.md)의 층 구분을 따라요. **구현 시기**: 객체 조건 필드, 필터 조건과 판정 입력의 플레이스홀더, `/v1/grants`의 스키마는 처음 계약부터 있어요. 조건이 든 부여를 판정하는 구현은 클로즈드 베타예요(13절).

### 5-2. 범위의 필드

범위는 권한 부여 안의 하나의 객체예요: `all`(참이면 전체 타입과 전체 소스, 이때 `object_types`와 `sources`는 비어 있어요), `kgs`(KG의 ID 목록, 기본 `[main]`), `object_types`(선택자의 목록. 선택자는 `kind`: `type` / `layer` / `namespace`와 `ref`), `sources`(소스 `id`의 목록), `max_sensitivity`(기본 `open`), `object_conditions`(선택. `scope_keys`의 속성 이름마다 값의 목록. 읽기에만 써요).

### 5-3. 가상의 예시

| 부여 | 누구 | 역할 | 범위 |
|---|---|---|---|
| `g-001` | 사람 `u-garam` | `viewer` | `object_types`: `type` `VirtualMachine`, `type` `HypervisorHost` |
| `g-002` | 그룹 `net-ops` | `editor` | `object_types`: `layer` 네트워크. `sources`: `switch_inventory`, `switch_config_pull` |
| `g-003` | 그룹 `net-ops` | `operator` | `g-002`와 같은 범위 |
| `g-004` | 로그인한 모든 사용자 | `viewer` | `all`, `max_sensitivity`: `open` |
| `g-005` | 사람 `u-narae` | `approver` | `sources`: `rack_sheet`, `server_list`. `object_types`: `type` `Rack` |
| `g-006` | 사람 `u-daon` | `viewer` | `object_types`: `type` `NetworkSwitch`. `object_conditions`: `site` = `site-a`. `max_sensitivity`: `restricted` |
| `g-007` | 서비스 계정 `sa-rack-feed` | `ingester` | `sources`: `rack_events` |

### 5-4. 부여가 여럿일 때

부여는 **허용만** 있어요. 거절하는 부여는 없고 여럿이면 합집합이에요. 읽기에서 부여 하나는 **(타입 선택자, 객체 조건, 민감 등급 한도)의 3요소 조합**이에요. 객체가 한 부여에 "일치한다"는 것은 타입이 선택자에 포함되고 객체의 `scope_keys` 값이 조건을 만족한다는 의미예요(조건이 없으면 타입만 봐요). **객체 하나의 한도는 그 객체에 일치하는 부여들의 한도 가운데 가장 높은 것**이에요. 일치하는 부여가 하나도 없으면 그 객체는 가려진 객체예요. 타입 단위로 따지지 않아요. 타입 단위로 따지면 조건이 붙은 부여가 그 타입 전체의 한도를 올려 버려요.

`u-daon`(`g-004`, `g-006`)의 경우: 사이트가 `site-a`인 `NetworkSwitch`는 `g-004`와 `g-006`에 일치해서 한도가 `restricted`예요. 사이트가 `site-b`인 `NetworkSwitch`는 `g-004`에만 일치해서 `open`이에요. `Rack`은 `g-004`로 `open`이에요.

## 6. 권한 부여의 필드와 권한 판정
### 6-1. 권한 부여 (`grant`)

| 필드 | 설명 |
|---|---|
| `grant_id` | 변하지 않는 식별자 |
| `subject_kind`, `subject_ref` | `person`(`subject_id`) / `group`(이름) / `system_account`(`account_id`) / `everyone`(로그인한 모든 사용자. 서비스 계정은 제외. `subject_ref`는 비어요) |
| `role`, `scope` | 8종 중 하나와 5-2의 범위. `ingester`는 `system_account`에만 줘요 |
| `status`, `reason` | `active` / `revoked`와 부여 사유(한 줄) |
| `granted_by`, `granted_at`, `revoked_by`, `revoked_at` | 부여하고 회수한 사람과 시각. 회수한 부여는 삭제하지 않고 남겨요 |
| `expires_at` | 선택. 있으면 그 시각부터 효력이 없어요 |
| `bulk_read` | `viewer` 부여에만. 참이면 대량 읽기를 할 수 있어요. `admin`이 부여하고 사용 내역이 감사 로그에 남아요 |
| `delegate` | 선택. **범위 한정 위임을 위한 필드**예요. `grantable_roles`(`viewer`, `editor` 가운데)를 적으면, 이 부여를 가진 사람이 **이 부여의 범위 안에서** 그 역할을 부여하고 회수할 수 있어요. 필드와 스키마는 처음부터 있고 구현은 클로즈드 베타예요 |

부여하고 회수하는 작업은 `admin`만 해요. 클로즈드 베타부터는 `delegate`를 가진 사람도 자기 범위 안에서 `viewer`와 `editor`를 부여하고 회수해요(자기보다 넓게는 부여할 수 없어요). 변경은 모두 감사 로그에 남아요.

### 6-2. 판정은 한 곳에서 해요

HTTP API, MCP, 워커가 모두 같은 판정을 호출해요. 판정은 코어의 한 단위가 맡고 그 단위는 기반 단위만 import해요(ADR-0006). 같은 판정이 화면을 위한 **허용 작업 힌트**(`GET /v1/me`, 응답의 `meta.allowed_actions`)도 제공해요. 힌트는 `[{action, allowed, reason_code}]`이고 차단 사유 코드는 고정 목록이에요: `forbidden.role`, `forbidden.scope`, `conflict.state`, `blocked.approval_required`, `blocked.limit`, `unavailable.degraded`([REST API 설계](rest-api.md) 4절). 힌트일 뿐이고 판정은 요청마다 다시 해요. 정책은 **제품에 내장된 데이터**예요. 규칙 테이블로 두고 한 곳에서 해석해요. 관리자는 정책을 수정할 수 없고 권한 부여만 수정해요. 허용하는 규칙이 하나도 없으면 거절해요.

규칙의 필드: `action`과 `required_role`(4절의 행과 필요한 역할), `scope_check`(범위에 포함되어야 하는 대상: `object_type`, `source`, `item`, `none`), `conditions`(추가 조건. 예: `actor_is_not_author`, `grade_within_limit`).

### 6-3. 입력과 출력

| 입력 | 설명 |
|---|---|
| `subject`, `groups`, `grants` | 사람 또는 서비스 계정, SSO에서 전달된 그룹, 캐시에서 읽은 유효한 권한 부여 |
| `action`, `target` | 요청한 작업, 대상(`kind`, `id`, `kg_id`, `object_type_id`, `layer`, `namespace`, `source_ids`, `sensitivity`) |
| `target_attributes` | 대상 객체의 `scope_keys` 값. 읽기 판정에서 객체 조건을 대조할 때 써요. 조건이 든 부여의 판정은 클로즈드 베타예요 |
| `context` | 승인이면 수정한 사람과 이미 받은 승인, 완화하는 제안인지, 정의가 읽는 소스 등 |

| 출력 | 설명 |
|---|---|
| `decision`, `reason` | `allow` / `deny`와 이유 코드. 예: `no_grant_for_role`, `target_out_of_scope`, `sensitivity_above_limit`, `self_approval_not_allowed`, `admin_approval_required`, `snapshot_too_old`, `no_rule_allows` |
| `matched_grants`, `matched_rule` | 근거가 된 부여들, 적용된 규칙 |
| `read_filter` | 읽기 판정일 때만: 7-5의 필터 조건 |

예: `u-narae`(`g-005`)가 소스 `rack_sheet`의 피드를 수정한 제안 `P-31`을 승인하려 하면, 입력은 `approve_proposal`, 대상의 `source_ids`는 `rack_sheet`, `context`의 수정한 사람은 `u-hansol`이에요. 출력은 `allow`, `matched_grants`는 `g-005`, `matched_rule`은 `approve_proposal.item_in_scope`예요. 자기가 수정한 제안을 승인하려 하면 `self_approval_not_allowed`로 거절돼요.

## 7. 읽기
### 7-1. 부여의 3요소 조합으로 정해지는 읽기, 링크가 보이는 조건

객체를 읽는 권한은 5-4의 3요소 조합으로만 정해져요(하위 타입 포함). 일치하는 부여가 없는 객체는 `find`와 `neighbors`에 나오지 않고, `get`은 없는 객체와 같은 형태("찾을 수 없음")로 응답해요. 소스 범위는 객체를 읽는 권한이 아니에요. **링크가 보이는 조건**은 양 끝 객체를 모두 읽을 수 있을 때예요. 한쪽이 가려진 객체면 `neighbors`에 나오지 않고, 영향 범위에서는 7-4처럼 가려진 항목으로 집계돼요.

### 7-2. 민감 등급

속성마다 `sensitivity`가 타입 등록부에 적혀 있고(kg-model.md의 속성 필드), 비어 있으면 `open`이에요. 한도는 **객체마다** 5-4로 정해져요.

- `open`: 기본. 그 객체를 읽을 수 있으면 값을 읽어요.
- `restricted`: 그 객체의 한도가 `restricted` 이상이어야 읽어요.
- `confidential`: 그 객체의 한도가 `confidential`이어야 읽어요. `confidential` 값은 프로젝션에 없어요.

등급은 수집할 때부터 전파돼요. 소스의 컬럼에 등급을 지정하고(프리셋이 기본값을 제공해요), 정제를 거치며 입력 중 가장 높은 등급이 이어져요. 속성의 등급은 매핑된 컬럼의 등급보다 낮을 수 없어요. 낮추려면 사유와 `admin`의 승인이 필요해요(ingestion.md).

### 7-3. 가려진 객체와 속성의 응답

읽을 수 없는 **속성**은 없는 것처럼 빠지지 않고 "가려짐"으로 표시돼요. 속성이 있다는 것은 알지만 값은 모르는 상태예요.

```
get  PhysicalServer srv-0042
  hostname:         "srv-0042"                  grade: fact
  model:            "model-x"                   grade: fact
  management_addr:  { masked: true, reason: sensitivity_above_limit }
```

가려진 속성을 **검색 조건으로 쓰면 거절**해요. 예를 들어 `find PhysicalServer where management_addr = "192.0.2.10"`에는 오류 `masked_attribute_in_condition`이 반환되어 "이 속성은 가려져 있다"고 알려요. 조용히 필터링하지 않아요. 필터링하면 결과 유무로 값이 노출되기 때문이에요. 같은 이유로 전문 검색은 호출자가 읽을 수 있는 속성만 대상으로 해요.

### 7-4. 영향 범위가 가려진 객체를 지날 때, 그리고 건수

영향 범위는 정확성을 위해 **전체 그래프에서 계산**해요. 호출자에 따라 계산이 달라지면 틀려요. 가리는 것은 응답을 만들 때예요. 가려진 객체가 경로 위에 있거나 영향받는 끝에 있으면 이름, 타입, 속성은 제공하지 않아요. **건수는 호출자의 범위에 따라 달라요.**

```
impact  of: srv-0042-pdu                  # 범위가 좁은 호출자
  affected:
    - PhysicalServer srv-0042      down          lost_channels: [power]
  hidden:
    hidden_passed:  present         # 경로에서 지나간 가려진 객체가 있음
    hidden_reached: present         # 영향받는 끝에 가려진 객체가 있음
```

- **건수를 반환하는 모든 필드는 "가려진 것을 뺀 건수"예요**(계약에 그렇게 명시해요). 대상: `impact`의 `groups_touched`(그룹의 `n`, `alive`, `min_alive`), `exposure`의 `would_die_count`, `containment`의 `subtree_size`, `get`의 `link_counts`, `neighbors`의 `groups`, `what_depends`의 `object_count`와 `unreadable`, 충족률의 분모, 변경 알림과 SSE `kg_changed`의 타입별 건수.
- **가려진 항목의 수(`hidden_*`)는 범위가 전체가 아닌 호출자에게 정확한 건수를 주지 않고 있음/없음(`present` / `none`)만 줘요.** 범위가 전체인 호출자는 가려진 것이 없어요. 설정으로 정확한 건수를 공개할 수 있어요(같은 타입을 조직별로 가려 보는 배포에서는 다른 조직의 건수가 정보가 될 수 있기 때문이에요).
- `paths`가 가려진 객체를 지나면 그 홉은 "가려진 객체"로 표시돼요. 가려진 객체를 `of`나 `dead`에 넣으면 "찾을 수 없음"과 같은 형태로 응답해요.

### 7-5. API의 질의 엔진 응답 필터링

프로젝션은 DB의 행 단위 권한을 우회해요. 그래서 필터링은 API가 해요. 호출자는 언제나 API를 거쳐요(ADR-0010).

1. API가 권한 판정을 호출해 `read_filter`를 받아요. 필터 조건은 **3요소 조합의 목록**이에요: `[{object_types(선택자), object_conditions, max_sensitivity}]`(`all`이면 모든 타입). 타입과 등급만 있던 이전 형태를 조건 필드가 들어간 이 형태가 대체해요.
2. API가 엔진에 질의하고, 엔진은 전체 그래프에서 계산해요. 프로젝션에는 객체의 이름과 타입의 작은 테이블과 객체별 `scope_keys` 값이 들어 있어서 응답의 객체마다 타입과 조건에 쓸 값을 알 수 있어요. 민감한 속성의 값은 프로젝션에 없어요.
3. API가 응답의 객체마다 3요소 조합과 대조하고 일치하는 조합의 한도 가운데 가장 높은 것을 그 객체의 한도로 삼아요. 일치하는 조합이 없는 객체는 응답에서 빼고 `hidden`으로 집계해요. `via`가 가려진 객체를 가리키면 "가려진 객체"로 바꿔요.
4. 엔벨로프의 건수(`result_complete.total` 등)는 필터링한 뒤의 값으로 수정해요(7-4). 필터링 전의 건수를 주면 가려진 항목의 수가 노출돼요.
5. 속성을 반환하는 질의(`find`, `get`, `neighbors`)는 스토리지에서 속성을 읽은 뒤 한도를 넘는 속성을 "가려짐"으로 바꿔요. 변경 알림 목록과 대량 읽기도 같은 필터 조건을 거쳐요.
6. 필터링한 뒤의 페이지는 필터링한 결과로 채워 돌려줘요. 필터링하고 남은 것이 `limit`보다 적으면 엔진에 추가로 질의해 채우고, `cursor`도 필터링한 뒤의 위치를 가리켜요(객체 ID를 써요).

스토리지가 중단됐을 때는 3번까지만 되고, 필터 조건은 캐시(3-5)에서 도출해요. 스토리지 측에서 `scope_keys` 값으로 필터링하는 필드와 인덱스는 [kg-storage.md](kg-storage.md)에 있어요.

### 7-6. 원본을 읽는 경로

소스 범위는 객체를 읽는 권한이 아니에요. 그런데 미리 보기, 샘플, 통계(`/profile`), 재실행의 샘플은 그 소스의 행을 그대로 보여 줘서, 그 경로로 객체 읽기 권한을 우회할 수 있어요. 그래서 이 경로들은 **그 데이터셋이 채우는 타입의 읽기 권한을 함께 요구해요.** 소스 범위만으로는 안 돼요. 컬럼의 민감 등급은 그대로 적용되고, `open`이 아닌 컬럼의 빈출 값은 제공하지 않아요. 이 경로의 사용 이력은 감사 로그에 남아요(12절).

### 7-7. 문제 목록과 역량 질문 목록

문제의 `detail`과 역량 질문의 미충족 객체 목록은 객체의 내용을 담아요. 이것들도 같은 필터 조건을 거쳐요.

- 가려진 객체에 관한 항목은 나오지 않고 가려진 항목으로 집계해요(7-4: 범위가 좁은 호출자에게는 있음/없음만). 항목 안의 속성은 객체의 한도를 넘으면 "가려짐"이에요.
- 충족률의 분모와 "미충족 객체 N"은 가려진 것을 뺀 건수예요(7-4).

## 8. 담당자

소스, 타입, 정의의 항목에는 **담당자**(`contacts`: 사람의 `subject_id`나 그룹의 이름 목록)가 붙어요. 담당자는 권한이 아니라 연락처예요.

- 문제와 알림이 담당자에게 전달돼요(ADR-0011, ADR-0013). 제안의 검토 요청도 그 항목의 담당자에게 전달돼요.
- 담당자라고 해서 읽거나 수정하거나 승인할 수 없어요. 그 권한은 언제나 권한 부여에서 나와요. 담당자를 수정하는 일은 정의의 변경이에요(브랜치, 제안). 담당자가 비어 있으면 알림은 `admin`에게 전달돼요.

## 9. 범위에 따른 제안의 승인 규칙

제안은 브랜치를 운영 정의에 반영해 달라는 요청이에요(ADR-0014). 승인 규칙은 다음과 같아요.

- 제안이 수정한 **항목 하나하나**에는 **소속**이 있고, 그 소속이 범위에 든 `approver`의 승인이 있어야 해요. 수정한 사람은 제외해요. 수정하는 쪽도 소속이 범위에 든 `editor`예요.
- 한 사람의 범위가 여러 항목을 덮으면 그 사람의 승인 한 번으로 충분해요.
- 승인 뒤에 내용이 바뀌면 승인은 무효예요.
- 검사가 "이 제안 때문에 깨진다"고 보고한 항목도 수정한 항목처럼 승인을 받아야 해요.
- 승인은 사람만 해요. 서비스 계정은 승인자가 될 수 없어요. 같은 주체이거나 같은 `on_behalf_of`이면 승인할 수 없어요(definitions-at-agent-scale.md).
- 조직 표준 타입은 `model_steward`가 승인해요(10-1). 안전장치를 완화하는 것과 민감 등급을 낮추는 것은 `admin`이 승인해요(10-1).

### 9-1. 항목이 범위에 드는 조건

| 항목 | 소속 |
|---|---|
| 소스 설정, 데이터셋, 정제, 일정, 기대 조건 | 그 항목이 속한 소스 |
| 타입(`ext`)과 속성, 링크 정의(**출발 타입**), 식별 규칙, 예외 목록, 역량 질문, 목표 | 그 항목이 다루는 객체 타입 |
| 피드 | 소스와 타입 둘 (아래) |
| 조직 표준 타입(`org`) | 범위로 구분하지 않아요. `model_steward`가 해요 |

**피드**는 소스의 `editor`가 수정해요. 그 피드가 객체를 생성하거나, 폐기하거나, 식별 키를 매핑하면 대상 타입을 범위에 가진 `approver`의 승인도 필요해요. 그렇지 않으면 타입의 담당자에게 알림만 전달돼요. 한 사람의 범위가 둘을 모두 덮으면 승인은 한 번이에요.

**정의가 다른 소스의 데이터셋을 읽을 때**(정제 데이터셋, 링크 정의)는 소속 외에 읽는 소스도 범위 검사 대상이에요. 정의를 작성하는 `editor`는 읽는 소스를 자기 범위에 가져야 하고(없으면 작성도 `:preview`로 결과를 보는 것도 `target_out_of_scope`예요), 승인은 읽는 소스의 범위도 따져요. 읽는 소스의 담당자에게는 알림도 전달돼요.

### 9-2. 가상의 예시 1: 한 소스의 매핑 수정

`u-hansol`(`editor`, `sources`: `rack_sheet`)이 소스 `rack_sheet`의 피드 `rack_sheet_to_rack`을 수정하는 제안 `P-31`을 올렸어요. 이 피드는 `Rack` 객체를 생성해요.

- `u-narae`(`approver`, `sources`: `rack_sheet`, `server_list`, `object_types`: `Rack`)는 **승인할 수 있어요.** 소스와 대상 타입을 모두 범위에 가졌고 수정한 사람이 아니에요. 한 번이면 충분해요.
- `u-narae`에게 `Rack`이 없었다면 `Rack`을 범위에 가진 다른 `approver`의 승인이 더 필요해요.
- `u-daon`(`approver`, 네트워크 층)은 소속이 범위 밖이라 승인할 수 없어요(`target_out_of_scope`). `u-hansol`은 `approver`도 갖고 있어도 자기가 수정한 것이라 승인할 수 없어요(`self_approval_not_allowed`).

### 9-3. 가상의 예시 2: 두 소스의 데이터셋을 읽는 링크 정의 수정

`u-hansol`이 링크 정의 `server_in_rack`의 조건을 수정하는 제안 `P-32`를 올렸어요. 이 정의는 소스 `server_list`와 `rack_sheet`의 데이터셋을 읽고, 출발 타입은 `PhysicalServer`예요. 소속은 출발 타입이에요.

- `u-hansol`이 작성하려면 `server_list`와 `rack_sheet`가 둘 다 `u-hansol`의 소스 범위에 있어야 해요.
- 승인은 출발 타입 `PhysicalServer`와 읽는 소스 `server_list`, `rack_sheet`를 모두 범위에 포함해야 해요. 한 사람이 모두 덮으면 한 번이고(`u-eun`이 `PhysicalServer`와 두 소스를 다 가졌다면 그 한 번), 나눠 덮으면 덮는 사람마다 한 번씩 필요해요.
- `u-narae`(소스 둘만 가짐)는 혼자서는 승인할 수 없어요. 출발 타입이 범위 밖이에요.
- 덮을 `approver`가 없으면 제안이 차단돼요. `admin`이 권한을 부여해 해소해요(10-2).

### 9-4. 단독 사용 초기 구축과 테스트 배포: `solo_approval`

처음 구축할 때나 혼자 테스트하는 배포에서는 자기가 수정한 것을 자기가 승인할 사람밖에 없어요. 이를 위한 **명시적인 설정 하나**(`solo_approval`)가 있어요. 기본은 꺼짐이에요. `admin`이 켜면 자기가 수정한 것을 자기가 승인할 수 있어요(`self_approval_not_allowed`가 해제돼요. `admin`에게도 같아요). 켜져 있는 동안 **모든 승인의 감사 로그에 `solo_approval` 표시가 남고 헬스 상태에 경고가 표시돼요.** 서비스 계정은 여전히 승인할 수 없어요.

## 10. 조직 표준 타입, 모델 관리, 차단 해소
### 10-1. 승인 주체

| 변경 (제품 표준 `std`는 제품이 포함해 제공하고 원본을 수정하지 않아요) | 수정하는 사람 | 승인하는 사람 |
|---|---|---|
| 조직 표준 `org`의 추가·수정·삭제, 제품 표준의 오버레이 | `editor`가 제안 | 그 타입의 층을 범위에 가진 `model_steward` |
| 사용자 정의 `ext` | `editor`가 제안 | 그 타입을 범위에 가진 `approver` (수정한 사람 제외) |
| `ext` 타입을 `org`로 승격, 타입 병합 | `editor`가 제안 | `model_steward`가 해요 |
| 안전장치의 값 완화 | `editor`가 제안 | `admin` (강화는 범위를 가진 `approver`) |
| 속성의 민감 등급 낮추기 | `editor`가 제안 | `admin` |

- **`model_steward`의 범위는 층으로 좁힐 수 있어요**(`object_types`에 `layer` 선택자). 층마다 담당자를 둘 수 있어요. 범위를 생략하면 전체예요.
- "표준 타입은 승인이 필요하다"는 요구는 `org` 층의 변경에 승인이 필요하다는 것으로 해석해요.
- 타입 사용 현황 보고는 그 타입을 범위에 가진 `viewer`가 읽고(`model_steward`는 자기 범위), `model_steward`는 겹치는 타입 쌍을 주기적으로 받아 봐요(kg-model.md의 유사 타입 방지 장치). 사용자 정의 타입은 `experimental`로 시작해 사용되면 `active`가 되고, 여럿이 사용하면 조직 표준으로 승격해요. 승격해도 `id`가 유지돼요. `experimental` 타입은 그 타입을 범위에 가진 `editor`가 아닌 모든 사용자에게 경고와 함께 표시돼요.

### 10-2. `admin`의 차단 해소

작업이 차단됐을 때 해소하는 권한은 `admin`에게 있어요.

- 범위를 가진 `approver`가 없어 제안이 차단됐을 때: 승인할 사람에게 권한 부여를 해 줘요.
- 방금 병합된 제안이 긴급하게 문제가 됐을 때: 승인 없이 리버트해요. 검사와 병합 큐는 그대로 거치고 정해진 기한 안에 사후 검토를 받아요(ADR-0014).

이 작업들은 감사 로그에 `admin_override`로 별도 표시돼요. 자기가 수정한 것을 자기가 승인할 수 없는 규칙은 `admin`에게도 같아요(`solo_approval`을 켠 배포만 달라요).

### 10-3. 시크릿 복호화 주체

소스 탐색, 점검, 미리 보기, 트라이얼 수집은 소스의 시크릿을 복호화해서 사용해요(ADR-0018). 누가 하는지는 **브랜치가 소스의 접속 주소를 바꿨는가**로 구분해요.

- 브랜치의 소스 정의가 메인 브랜치와 같으면(접속 주소가 같음) 그 소스를 범위에 가진 `editor`, `operator`가 해요.
- 브랜치가 접속 주소를 바꿨으면 그 소스를 범위에 가진 `operator`(또는 `admin`)만 해요.
- 시크릿은 `allowed_hosts` 안의 주소로만 사용돼요. 변경된 주소는 트라이얼 수집 전에 표시돼요(ADR-0018).
- 시크릿을 등록하고 변경하는 것은 그 소스를 범위에 가진 `operator`(또는 `admin`)예요. `editor`는 참조만 정의에 넣어요. 제품 범위의 시크릿(알림 채널의 키, 서명 키)은 `admin`만 등록하고 변경해요. 메타 정보는 `auditor`도 볼 수 있어요. 값은 아무도 읽을 수 없어요.
- 복호화한 사용 이력은 `secret_used`로 남아요(12절).

### 10-4. 운영 액션의 승인

프락시움 자신의 운영 액션(ADR-0017)은 요청자가 아닌 `admin`이나 범위를 가진 `operator`인 **사람**이 승인해요. 서비스 계정은 승인할 수 없어요. 승인이 필요 없는 액션은 `pause_sources_by_secret`처럼 되돌릴 수 있고 보호 목적의 액션이에요. 검증을 끄거나 암호화 없이 접속하는 소스 연결과 `rewrap_master_key`는 `admin`이 승인해요. 승인된 연결에는 기한이 있어요.

## 11. 서비스 계정

사람이 아닌 시스템(다른 조직의 도구, 에이전트)이 쓰는 계정이에요. 프락시움이 발급해요. 같은 역할과 범위를 부여받고, 권한 부여의 "누구" 필드에 `system_account`로 들어가요. 푸시하는 서비스 계정은 `ingester`를 부여받아요.

필드: `account_id`, `display_name`, `description`, `contacts`(담당자. 한도 초과나 이상 사용 시 연락할 곳), `token_hash`(토큰 값은 저장하지 않고 생성할 때 한 번만 보여 줘요), `expires_at`, `rotated_at`(새 토큰을 발급하면 이전 토큰은 짧은 중복 허용 기간 뒤에 차단돼요), `rate_limit`(호출자별 한도, ADR-0010), `bound_persons`(이 계정이 `on_behalf_of`로 지정할 수 있는 사람의 목록. 관리자가 연결해 둬요), `status`(`active` / `disabled`), `created_by`, `created_at`.

- 생성, 토큰 교체, 비활성화, 사람 연결은 `admin`이 해요. 인증은 로그인 포트 뒤에 둬요. SSO가 시스템용 자격 증명을 제공하면 그것을 쓰고, 아니면 프락시움이 발급한 토큰을 써요. 토큰의 해시와 상태는 캐시(3-5)에 들어 있어서 스토리지가 중단돼도 검증돼요.
- **`on_behalf_of`는 계정이 임의로 지정하는 값이 아니에요.** 요청에 지정한 값은 `bound_persons` 중에서만 고를 수 있고, 아니면 거절해요. "같은 위임자이면 승인할 수 없다"는 규칙의 키이기 때문이에요.
- **계정을 비활성화하거나 토큰을 회수하면 스토리지가 정상일 때 30초 이내에 전파돼요.** 스토리지가 중단된 동안은 캐시의 나이 상한(15분)까지 남을 수 있어요.
- 계정이 어느 타입과 속성을 읽었는지는 사용 통계로 남아요. 수정하거나 폐기하기 전에 "영향받는 항목"을 확인하는 데 써요(ADR-0014). `bulk_read` 허가는 `admin`이 부여하고, 그 사용 이력은 감사 로그에 남아요.
- 서비스 계정이 운영 액션을 요청할 때는 근거가 된 진단의 ID(`diagnosis_id`)가 있어야 해요(ADR-0017).

## 12. 감사 로그
### 12-1. 기록하는 것과 기록하지 않는 것

기록하는 것: 정의를 수정한 것(누가, 어느 항목, 어느 제안) / 승인과 거절, 병합과 리버트 / 정의나 KG의 범위를 내보낸 것 / 권한 부여를 부여하고 회수한 것(위임한 부여 포함), 기본 부여와 서비스 계정을 변경한 것 / `admin`이 차단된 작업을 해소한 것 / 민감한 속성(`restricted`, `confidential`)을 읽은 것과 대량 읽기 / **원본을 읽는 경로**(7-6)의 사용 / **모든 운영 액션**(요청, 승인, 실행. 운영 역할의 안전장치 확인, 스트림 해제, 버전 고정 포함) / 시크릿을 등록·변경·삭제한 것과 복호화해서 사용한 것, `allowed_hosts`를 변경한 것 / 이 가운데 수정 작업과 민감한 속성·대량 읽기의 거절된 시도.

기록하지 않는 것: 일반 읽기와 그 거절(양이 감당되지 않아요. 사용 통계로만 남아요, ADR-0013), 민감한 속성의 값, 시크릿, 행의 내용.

### 12-2. 로그 레코드의 필드

- `audit_id`, `occurred_at`, `kg_id`(KG에 속한 것을 읽거나 수정한 로그면): 로그의 식별자와 시각
- `actor_kind`(`person` / `system_account` / `role_instance`), `actor_id`(`subject_id`, `account_id` 또는 역할 실행). `role_instance`(시크릿을 복호화해서 사용한 실행)는 요청한 쪽을 `on_behalf_of`에 적어요
- 정의의 변경이면 `authored_by`(주체와 `actor_kind`), `on_behalf_of`, `agent_run_id`, `agent_build`, 승인 경로(`approval_path`: 사람 또는 정책 버전. 정책이면 버전 번호). 승인은 사람만 하고 같은 주체나 같은 `on_behalf_of`는 승인할 수 없어요(definitions-at-agent-scale.md)
- 승인이면 `solo_approval`(참이면 9-4를 켠 채 한 승인)
- 운영 액션이면 `action`에 그 액션의 이름을 그대로 적고(예: `rewrap_master_key`, `pause_sources_by_secret`), 요청자, 승인한 사람, 서비스 계정의 요청이면 `diagnosis_id`. 스토리지가 중단돼 역할의 디스크에 먼저 기록했다가 옮긴 레코드는 `written_late`가 참이에요(kg-operations.md)
- `action`: 고정 목록의 작업 이름. 예: `edit_definition`, `approve_proposal`, `merge_proposal`, `revert_proposal`, `export_definition`, `grant_created`, `grant_revoked`, `read_sensitive`, `bulk_read`, `read_raw_data`, `admin_resolve`, `secret_used`, `secret_changed`, `secret_hosts_changed`와 운영 액션의 이름
- `target_kind`, `target_id`(작업 대상), `grant_ids_used`(어느 권한 부여가 허용했나), `outcome`(`allowed` / `denied`), `admin_override`(`admin`이 차단된 작업을 해소한 것인가)
- `proposal_id`, `definition_bundle`(정의를 수정한 경우 어느 제안과 정의 세트, `D-142` 같은 번호), `detail`(건수 같은 요약. 값은 넣지 않아요), `request_id`(요청 하나의 식별자)

감사 로그는 추가만 하고 수정하거나 삭제하지 않아요. 잃으면 안 되는 등급이에요(ADR-0011). 보존 기한은 설정 값이고 기본값은 3년이에요([기본값 표](defaults.md) 4절). `auditor`가 읽어요. 스토리지가 중단됐을 때 상태를 바꾸는 운영 액션은 거절하고, 스토리지 없이 수행할 수 있는 긴급 액션만 디스크에 먼저 기록해요(kg-operations.md).

## 13. 단계별 구현 시기

- **알파**: 백엔드의 권한 모델을 모두 구현해요. 역할 8종, 권한 부여와 범위(타입, 소스, 민감 등급, KG), 권한 판정, 읽기의 필터링과 가림, OIDC 어댑터, 캐시, 서비스 계정(`bound_persons`와 30초 이내의 회수 전파 포함), 감사 로그, `solo_approval`. 스키마상의 **플레이스홀더**도 지금 만들어 둬요: 객체 조건 필드와 3요소 조합의 필터 조건, `target_attributes`, `delegate`, `/v1/grants`의 스키마. 알파의 기준은 이 모두가 API와 CLI로 동작하는 거예요(화면은 ADR-0016).
- **클로즈드 베타**: 객체 조건을 판정하는 구현(프로젝션의 `scope_keys`, 필터 조건의 조건 대조, 스토리지 측 필터링), 범위 한정 위임(`delegate`).

## 14. 알려진 한계

- **캐시가 회수한 권한을 늦게 반영해요.** 서비스 계정의 비활성화와 토큰 회수는 스토리지가 정상이면 30초지만, 권한 부여의 회수는 캐시를 새로 읽는 주기와 토큰의 유효 기간만큼 남을 수 있어요. 쓰기 작업(수정, 승인)은 스토리지가 정상일 때만 하게 해서 지연 구간을 줄이고, 읽기에서는 이를 감수해요.
- **가려진 항목의 수도 정보가 될 수 있어요.** 범위가 좁은 호출자에게는 있음/없음만 주지만, 있음 자체와 가려진 홉의 위치(`paths`), 호출자가 고르는 `dead`를 바꿔 가며 질의하는 방법으로 가려진 쪽의 구조를 추측할 수는 있어요. 설정으로 건수를 공개하면 더 커져요. 일반 읽기를 기록하지 않아서, `open` 등급 값을 누가 읽었는지는 사고 뒤에도 알 수 없어요.
- **범위를 가진 `approver`가 한 명뿐이면** 그 사람이 수정한 제안은 `admin`의 개입이 있어야 병합돼요(`solo_approval`은 단독으로 쓰는 배포를 위한 것이에요). `admin`의 권한이 커서 감사 로그의 표시와 사후 검토로 감시해요.
- **필터링한 뒤 채우느라 엔진에 추가로 질의해요.** 가려진 것이 많은 호출자는 계산 예산에 먼저 도달할 수 있어요. 객체 조건이 도입되면 더 심해져요.
- **알파에서 객체 조건은 필드만 있어요.** 그 전에는 "이 사이트의 객체만"을 타입으로 구분해야 해요.

## 15. 미결 사항

- `delegate`를 어느 역할의 부여에 붙일 수 있는지, 위임받은 사람이 다시 위임할 수 있는지.
- 객체 조건이 든 부여를 클로즈드 베타 전에 생성하면 거절할지(넓게 읽히는 것을 막으려면 거절해야 해요), 조건이 선택자 안 타입에 없는 속성을 가리킬 때의 처리.
- 범위가 좁은 호출자에게 충족률의 비율을 가려진 것을 뺀 객체 기준으로 다시 계산해 줄지.
- `solo_approval`이 켜져 있을 때 같은 `on_behalf_of` 규칙도 해제할지. 소스 탐색도 7-6의 읽기 권한을 요구할지. KG 필드가 `auditor`, `admin`에도 적용될지.
