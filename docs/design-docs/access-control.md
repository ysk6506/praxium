# 권한 설계

누가 KG를 읽고, 정의를 고치고, 제안을 승인하고, 소스를 돌리고, 소스에 밀어 넣을 수 있는지를 정해요. 사람과 무리는 사내 SSO가 알고 있어요. 프락시움은 거기에 **제품에 든 역할**을 **범위**와 함께 붙여요. 붙이는 사람은 관리자예요. 구현하는 사람이 이 문서만 보고 데이터의 모양과 경계를 알 수 있게 적어요. 결정은 ADR-0012에 있어요.

## 1. 무엇에 답하나

- 사람과 무리는 어디서 오고, 떠나면 어떻게 되나요? SSO에서 와요(3절).
- 무엇을 할 수 있는지는 어떻게 정하나요? 권한 부여 = 누구 × 역할 × 범위예요(2, 4, 5절).
- "아무개는 이 타입의 읽기만", "이 자리의 객체만"이 되나요? 범위를 객체 타입과 객체의 조건으로 주면 돼요(5절).
- 부여가 여럿이면 한 객체의 읽기 한도는요? 그 객체에 맞는 부여들의 최댓값이에요(5-4).
- 읽을 수 없는 것은 어떻게 보이나요? 객체는 안 나오고, 속성은 "가려짐", 수는 가려진 것을 빼요(7절).
- 고치는 일은 누가 승인하나요? 그 항목을 범위에 가진 다른 `approver`예요(9절). 혼자 시험하는 배포는 9-4, 비밀 값을 푸는 일은 10-3이에요.
- 판단이 길마다 달라지지 않으려면, 저장소가 멈추면, 무엇을 기록하나요? 6절, 3-5, 12절이에요.

넘겨받은 것 문서 6절의 쟁점 나(맡기는 범위와 검증한 범위가 같아야 한다)의 프락시움 쪽 바탕이에요. 맡김의 수준은 E2E 프로세스를 구체화할 때 정해요.

## 2. 한눈에

**권한 부여 하나 = 누구 × 역할 × 범위.** 이것이 권한의 전부예요.

| 누구 | 역할 | 범위 | 뜻 (지어낸 예) |
|---|---|---|---|
| 사람 한 명 | `viewer` | 객체 타입 `VirtualMachine`, `HypervisorHost` | 이 두 타입의 객체와 링크만 읽어요 |
| 사람 한 명 | `viewer` | 타입 `NetworkSwitch`, 조건 `site = site-a`, `restricted`까지 | 그 자리의 스위치만 `restricted`까지 읽어요 |
| 무리 `net-ops` | `editor`, `operator` | 네트워크 층의 타입과 소스 `switch_inventory`, `switch_config_pull` | 네트워크 층의 정의를 고치고 그 두 소스를 돌려요 |
| 시스템 계정 | `ingester` | 소스 `rack_events` | 그 소스에 밀어 넣어요. 읽기는 없어요 |
| 로그인한 모두 | `viewer` | 전체, 민감 등급 `open`까지 | 기본으로 열린 것만 읽어요 |

```
 사내 SSO ─(사람, 무리)─▶ [OIDC 어댑터] ─▶ 주체 + 무리
 관리자 ─▶ [권한 부여] ─(사본)─▶ [권한의 판단: 한 곳] ◀─(하려는 일, 대상)─ API / MCP / 일꾼
                                       │ 허용·거절+까닭 → [감사 기록: 추가만]
                                       └ 읽기 거름표 → API가 질의 엔진의 답을 거름
```

역할은 제품에 든 여덟이고 관리자가 고치지 못해요. 읽기도 권한 부여예요. 조직의 단위는 권한에 쓰지 않아요. 사람과 무리가 어느 조직인지는 SSO가 알아요.

## 3. SSO 연결
### 3-1. 포트와 OIDC 어댑터

코어는 "로그인된 주체와 그 무리"만 알아요. 로그인 방식은 포트 뒤의 어댑터가 맡아요. 첫 어댑터는 표준 방식(OIDC)을 말해요. 특정 SSO 제품에 묶이지 않고, 같은 포트에 다른 어댑터를 꽂을 수 있어요.

어댑터가 코어에 넘기는 것: `subject_id`(로그인 쪽이 정한, 바뀌지 않는 사람의 식별자. 불투명한 값으로만 다뤄요), `display_name`, `groups`(로그인 쪽의 무리 이름 목록. 고치지 않고 그대로 받아요), `issued_at`과 `expires_at`(증표가 유효한 시간).

### 3-2. 사람과 무리가 오는 길

- 프락시움은 사람과 무리를 **만들지 않아요.** 받은 것에 권한 부여를 붙일 뿐이에요. 한 사람의 효력 있는 권한 부여는 그 사람에게 걸린 것, 그 사람의 무리에 걸린 것, "로그인한 모두"에 걸린 것의 합이에요.
- 무리를 증표에서 읽는지 사용자 정보 길에서 읽는지는 SSO마다 달라 가정이에요. 코어는 `groups`만 받아요.

### 3-3. 무리의 바뀜이 반영되는 때

로그인 쪽에서 사람이 무리에 들거나 빠지면, 프락시움은 그 사람이 **새 증표를 받을 때**(다시 로그인하거나 증표를 갱신할 때) 알아요. 반영이 늦는 정도는 증표의 유효 시간(`expires_at`)이 정해요. 즉시 끊으려면 SSO 쪽에서 증표를 거둬야 하고, 되는지는 SSO의 방식에 달렸어요.

### 3-4. 사람이 떠났을 때

- SSO에서 사라지거나 무리에서 빠지면 새 증표부터 권한이 없어져요. 무리에 걸린 권한은 따로 지울 것이 없어요.
- 그 사람 이름으로 직접 건 권한 부여는 남아요. 관리자가 거둬요.
- 그 사람이 남긴 감사 기록, 브랜치, 제안은 그대로예요. 제안은 다른 `editor`가 이어받거나 닫아요. 시스템 계정에 묶인 사람(11절)이었다면 관리자가 묶음을 풀어요.

### 3-5. 저장소가 멈춰도 묻기가 되게 하는 사본

묻기는 멈추면 안 돼요(ADR-0011). 그런데 권한의 판단에는 "이 사람에게 걸린 권한 부여"가 필요하고 그것은 저장소에 있어요. 그래서 API는 이렇게 해요.

- **증표는 저장소 없이 확인해요.** 어댑터가 확인에 필요한 것을 자기 곁에 둬요.
- **권한 부여의 사본을 API 벌마다 둬요.** 사본에는 효력 있는 권한 부여, 기본 부여, 시스템 계정의 토큰 해시와 상태가 들어요. 저장소가 살아 있으면 주기로 새로 읽어요.
- **사본에는 나이(`copied_at`)가 있고 상한(`max_snapshot_age`)이 있어요.** 기본값(설정)은 15분이에요([기본값 표](defaults.md)). 상한 안의 사본으로 판단해요. **상한을 넘으면** 고치는 일과 `restricted` 이상의 읽기는 거절하고, "로그인한 모두"의 기본 부여로 되는 읽기만 계속 답해요(건강에 알려요).
- **저장소가 살아 있을 때 시스템 계정을 끄거나 토큰을 거두는 것은 30초 안에 퍼져요**(11절). 15분은 저장소가 멈춘 동안의 상한이에요.

## 4. 역할 여덟

모든 역할은 `ingester`를 뺀 나머지가 **자기 범위의 읽기를 포함**해요. 그 밖에는 서로 포함하지 않아요(`editor`가 `approver`를 포함하지 않고, `admin`이 `editor`를 포함하지 않아요). `●`는 할 수 있다는 뜻이고, 범위가 있는 일은 부여의 범위 안에서만이에요.

| 할 수 있는 일 | `viewer` | `editor` | `approver` | `operator` | `model_steward` | `auditor` | `admin` | `ingester` |
|---|---|---|---|---|---|---|---|---|
| 객체 타입 범위 안의 객체와 링크를 읽고 묻는다 (속성은 등급 한도까지) | ● | ● | ● | ● | ● | ● | ● | |
| 소스 범위 안의 소스의 정의(데이터셋, 정제, 공급, 일정)와 실행 기록(단계별 수와 시간)을 읽는다 | ● | ● | ● | ● | ● | ● | ● | |
| 소스를 들여다보고 데이터셋을 미리 보고 연결을 점검한다, 떨어진·떼어 둔 기록의 견본을 읽는다 (7-6, 10-3) | | ● | | ● | | | ● | |
| 대량 읽기 (`viewer` 부여에 붙는 따로 된 허가 `bulk_read`) | 허가 | | | | | | | |
| 브랜치를 열고, 자리를 범위에 가진 정의를 고치고 제안한다 | | ● | | | | | | |
| 제안을 승인한다 (자리를 범위에 가진 항목, 자기가 고친 것은 제외) | | | ● | | | | | |
| 소스를 돌리고 멈춘다, 시험 수집을 한다 | | | | ● | | | | |
| 엑셀·CSV 파일을 올린다 (그 소스를 범위에 가진) | | ● | | ● | | | | |
| 범위에 든 소스에 데이터를 밀어 넣고 수집 봉투를 보낸다 (시스템 계정에만 줘요) | | | | | | | | ● |
| 타입의 쓰임 보고를 읽는다 (그 타입을 범위에 가진. `model_steward`는 자기 범위) | ● | | | | ● | | | |
| 사용자가 알린 문제의 까닭 분류(`cause_class`)를 정한다 | | | | ● | | | | |
| 안전장치의 확인, 붙잡힌 흐름의 풀기와 버리기 | | | | ● | | | | |
| 묻는 쪽을 옛 KG 버전에 고정한다 (`serving_pin`) | | | | ● | | | ● | |
| 조직 표준 타입의 제안을 승인하고, 타입을 조직 표준으로 올리고 합친다 | | | | | ● | | | |
| 감사 기록을 읽는다 | | | | | | ● | | |
| 권한 부여를 읽는다 | | | | | | ● | ● | |
| 권한을 주고 거둔다, 기본 부여와 시스템 계정을 정한다 | | | | | | | ● | |
| 제품의 설정을 고친다 (SSO 연결, `solo_approval` 등), 막힌 일을 푼다 (10-2) | | | | | | | ● | |
| 안전장치의 값을 느슨하게 하는 제안, 민감 등급을 낮추는 제안을 승인한다 | | | | | | | ● | |

- 저장해 둔 범위를 만드는 일과, 승인하려고 제안의 검사와 차이를 읽는 일은 읽기에 포함돼요.
- 들여다보기, 미리보기, 점검, 견본은 그 소스를 범위에 가진 `editor`나 `operator`(견본은 `admin`도)의 일이에요. 시험 수집은 `operator`예요. 비밀 값을 푸는 일의 가름은 10-3이에요. 엑셀·CSV 올리기는 그 소스를 범위에 가진 `operator`나 `editor`예요. 고정은 전체 범위의 `operator`나 `admin`이 해요.
- `ingester`는 범위에 든 소스에 밀어 넣는 길(소스의 정의가 열어 둔 것만)과 수집 봉투를 보내는 일만 해요. 읽기도, 그 밖의 어떤 일도 없어요. 시스템 계정에 줘요. 사람에게는 주지 않아요.
- 자기가 고친 것을 자기가 승인하지 못하는 규칙은 `approver`, `model_steward`, `admin` 모두에 같아요(`solo_approval`을 켠 배포만 달라요, 9-4).
- `admin`과 `auditor`의 범위는 언제나 전체예요. **`model_steward`는 층으로 범위를 좁힐 수 있어요.** 안 좁히면 전체예요(10-1). 정의 내보내기는 그 자리를 범위에 가진 `editor`가 하고, 일정은 정의의 항목(`schedule`)이라 고치는 일은 `editor`, 승인은 `approver`예요(ADR-0014). 소스를 지금 돌리는 일은 `operator`예요.

## 5. 범위
### 5-1. 범위의 종류

| 종류 | 고르는 것 | 무엇에 걸리나 |
|---|---|---|
| 전체 | 없음 | 모든 타입과 모든 소스 |
| KG | KG의 ID의 목록. 안 적으면 `main` | KG에 든 것(객체, 링크, 질의, 변경, 버전)을 읽는 권한. 정의, 소스, 권한 부여는 배포에 하나라 이 칸을 보지 않아요 |
| 객체 타입 | 타입의 목록(하위 타입 포함), 표준 모델의 층(`layer`. 예: 네트워크 층 전체), 이름 공간(`std`, `org`, `ext`, 예약된 `sys`) | 그 타입의 객체와 링크를 읽는 권한은 **여기서만** 와요. 그 타입에 딸린 정의의 자리이기도 해요 |
| 소스 | 소스의 목록 | 그 소스의 정의와 실행 기록을 읽고(`viewer`), 고치고 들여다보는(`editor`) 권한, 소스를 돌리고 점검하고 시험 수집을 하는(`operator`) 일, 밀어 넣는(`ingester`) 일. **객체를 읽는 권한은 아니에요** |
| 민감 등급의 한도 | `open`, `restricted`, `confidential` | 속성 값을 어디까지 읽나. 안 적으면 `open`까지예요 |
| 객체의 조건 | 타입이 선언한 범위에 쓰는 속성(`scope_keys`)과 값의 목록(`속성 = 값들`) | `viewer`의 읽기를 그 속성의 값이 맞는 객체로 좁혀요(REQ-165) |

**KG는 계약의 자원이에요**(`/v1/kgs/{kg}/...`, ADR-0016). 운영 KG는 이름 `main`으로도 가리켜요. 시스템 KG(`sys` 타입을 담는, 프락시움 자신의 부품)도 KG라서 `main`의 권한으로는 읽지 못하고 그 KG를 칸에 적은 부여가 있어야 해요.

**객체의 조건을 범위에 넣어요.** 타입만으로는 여러 조직이 함께 쓸 때 모자라고, 나중에 넣으면 질의 엔진과 투영을 다시 고쳐야 해서 지금 설계에 넣어요. 범위에 쓰는 속성은 타입 등록부에서 속성에 `scope_key: true`를 적어 선언해요(자리, 환경, 맡은 조직 같은 것. 타입 하나에 넷까지, 값 타입은 짧은 글이나 참조이고 `volatile`은 안 돼요. 하위 타입은 물려받아요). 문법은 닫혀 있어요(속성 = 값들의 목록). 투영은 그 속성의 값을 객체마다 갖고, API가 답을 거를 때 써요(kg-queries.md). 범위에 쓰는 속성은 `versioned`이고 식별 키처럼 다뤄 함부로 바뀌지 않아요. 고치는 권한(`editor` 등)은 지금처럼 자리(소스, 타입) 단위예요. 층은 타입 등록부의 객체 타입에 있는 칸 `layer`(표준 모델의 층 열 가지 중 하나. 열째 `system`은 `sys` 타입이 놓이는 층이에요. 사용자 정의 타입은 만들 때 골라요)이고, [standard-model.md](standard-model.md)의 층 구분을 따라요. **언제 만드나**: 객체 조건의 칸, 거름표와 판단의 입력의 자리, `/v1/grants`의 모양은 처음 계약부터 있어요. 조건이 든 부여를 판단하는 구현은 클로즈 베타예요(13절).

### 5-2. 범위의 칸

범위는 권한 부여 안의 한 덩어리예요: `all`(참이면 전체 타입과 전체 소스, 이때 `object_types`와 `sources`는 비어 있어요), `kgs`(KG의 ID 목록, 기본 `[main]`), `object_types`(선택자의 목록. 선택자는 `kind`: `type` / `layer` / `namespace`와 `ref`), `sources`(소스 `id`의 목록), `max_sensitivity`(기본 `open`), `object_conditions`(선택. `scope_keys`의 속성 이름마다 값의 목록. 읽기에만 써요).

### 5-3. 지어낸 예시

| 부여 | 누구 | 역할 | 범위 |
|---|---|---|---|
| `g-001` | 사람 `u-garam` | `viewer` | `object_types`: `type` `VirtualMachine`, `type` `HypervisorHost` |
| `g-002` | 무리 `net-ops` | `editor` | `object_types`: `layer` 네트워크. `sources`: `switch_inventory`, `switch_config_pull` |
| `g-003` | 무리 `net-ops` | `operator` | `g-002`와 같은 범위 |
| `g-004` | 로그인한 모두 | `viewer` | `all`, `max_sensitivity`: `open` |
| `g-005` | 사람 `u-narae` | `approver` | `sources`: `rack_sheet`, `server_list`. `object_types`: `type` `Rack` |
| `g-006` | 사람 `u-daon` | `viewer` | `object_types`: `type` `NetworkSwitch`. `object_conditions`: `site` = `site-a`. `max_sensitivity`: `restricted` |
| `g-007` | 시스템 계정 `sa-rack-feed` | `ingester` | `sources`: `rack_events` |

### 5-4. 부여가 여럿일 때

부여는 **허용만** 있어요. 거절하는 부여는 없고 여럿이면 합집합이에요. 읽기에서 부여 하나는 **(타입 고르기, 객체 조건, 민감 등급의 한도) 세 짝**이에요. 객체가 한 부여에 "맞는다"는 것은 타입이 선택자에 들고 객체의 `scope_keys` 값이 조건을 만족한다는 뜻이에요(조건이 없으면 타입만 봐요). **객체 하나의 한도는 그 객체에 맞는 부여들의 한도 가운데 가장 높은 것**이에요. 맞는 부여가 하나도 없으면 그 객체는 가려진 객체예요. 타입마다 따지지 않아요. 타입마다 따지면 조건이 붙은 부여가 그 타입 전체의 한도를 올려 버려요.

`u-daon`(`g-004`, `g-006`)의 경우: 자리가 `site-a`인 `NetworkSwitch`는 `g-004`와 `g-006`에 맞아서 한도가 `restricted`예요. 자리가 `site-b`인 `NetworkSwitch`는 `g-004`에만 맞아서 `open`이에요. `Rack`은 `g-004`로 `open`이에요.

## 6. 권한 부여의 칸과 권한의 판단
### 6-1. 권한 부여 (`grant`)

| 칸 | 뜻 |
|---|---|
| `grant_id` | 바뀌지 않는 식별자 |
| `subject_kind`, `subject_ref` | `person`(`subject_id`) / `group`(이름) / `system_account`(`account_id`) / `everyone`(로그인한 모든 사람. 시스템 계정은 제외. `subject_ref`는 비어요) |
| `role`, `scope` | 여덟 중 하나와 5-2의 범위. `ingester`는 `system_account`에만 줘요 |
| `status`, `reason` | `active` / `revoked`와 왜 주었나 한 줄 |
| `granted_by`, `granted_at`, `revoked_by`, `revoked_at` | 주고 거둔 사람과 때. 거둔 부여는 지우지 않고 남겨요 |
| `expires_at` | 선택. 있으면 그때부터 효력이 없어요 |
| `bulk_read` | `viewer` 부여에만. 참이면 대량 읽기를 해요. `admin`이 주고 쓰임이 감사 기록에 남아요 |
| `delegate` | 선택. **범위 있는 관리의 자리**예요. `grantable_roles`(`viewer`, `editor` 가운데)를 적으면, 이 부여를 가진 사람이 **이 부여의 범위 안에서** 그 역할을 주고 거둘 수 있어요. 칸과 모양은 처음부터 있고 구현은 클로즈 베타예요 |

주고 거두는 일은 `admin`만 해요. 클로즈 베타부터는 `delegate`를 가진 사람도 자기 범위 안에서 `viewer`와 `editor`를 주고 거둬요(자기보다 넓게는 못 줘요). 바뀜은 모두 감사 기록에 남아요.

### 6-2. 한 곳에서 판단해요

HTTP API, MCP, 일꾼이 모두 같은 판단을 불러요. 판단은 코어의 한 단위가 맡고 그 단위는 기반만 읽어요(ADR-0006). 같은 판단이 화면을 위한 **할 수 있는 일의 귀띔**(`GET /v1/me`, 응답의 `meta.allowed_actions`)도 줘요. 귀띔은 `[{action, allowed, reason_code}]`이고 막힌 까닭의 코드는 닫힌 목록이에요: `forbidden.role`, `forbidden.scope`, `conflict.state`, `blocked.approval_required`, `blocked.limit`, `unavailable.degraded`([REST API 설계](rest-api.md) 4절). 귀띔일 뿐이고 판단은 요청마다 다시 해요. 정책은 **제품에 든 데이터**예요. 규칙의 표로 두고 한 곳에서 풀어요. 관리자는 정책을 고치지 못하고 권한 부여만 고쳐요. 허용하는 규칙이 하나도 없으면 거절해요.

규칙의 칸: `action`과 `required_role`(4절의 행과 필요한 역할), `scope_check`(무엇이 범위에 들어야 하나: `object_type`, `source`, `item`, `none`), `conditions`(덧붙는 조건. 예: `actor_is_not_author`, `grade_within_limit`).

### 6-3. 입력과 출력

| 입력 | 뜻 |
|---|---|
| `subject`, `groups`, `grants` | 사람 또는 시스템 계정, 로그인 쪽에서 온 무리, 사본에서 푼 효력 있는 권한 부여 |
| `action`, `target` | 하려는 일, 대상(`kind`, `id`, `kg_id`, `object_type_id`, `layer`, `namespace`, `source_ids`, `sensitivity`) |
| `target_attributes` | 대상 객체의 `scope_keys` 값. 읽기 판단에서 객체의 조건을 맞춰 볼 때 써요. 조건이 든 부여의 판단은 클로즈 베타예요 |
| `context` | 승인이면 고친 사람과 이미 받은 승인, 느슨하게 하는 제안인지, 정의가 읽는 소스 등 |

| 출력 | 뜻 |
|---|---|
| `decision`, `reason` | `allow` / `deny`와 까닭의 코드. 예: `no_grant_for_role`, `target_out_of_scope`, `sensitivity_above_limit`, `self_approval_not_allowed`, `admin_approval_required`, `snapshot_too_old`, `no_rule_allows` |
| `matched_grants`, `matched_rule` | 어느 부여들이 받쳤나, 어느 규칙이 걸렸나 |
| `read_filter` | 읽기 판단일 때만: 7-5의 거름표 |

예: `u-narae`(`g-005`)가 소스 `rack_sheet`의 공급을 고친 제안 `P-31`을 승인하려 하면, 입력은 `approve_proposal`, 대상의 `source_ids`는 `rack_sheet`, `context`의 고친 사람은 `u-hansol`이에요. 출력은 `allow`, `matched_grants`는 `g-005`, `matched_rule`은 `approve_proposal.item_in_scope`예요. 자기가 고친 제안을 승인하려 하면 `self_approval_not_allowed`로 거절돼요.

## 7. 읽기
### 7-1. 읽기는 부여의 세 짝으로 정해져요, 링크가 보이는 조건

객체를 읽는 일은 5-4의 세 짝으로만 정해져요(하위 타입 포함). 맞는 부여가 없는 객체는 `find`와 `neighbors`에 나오지 않고, `get`은 없는 객체와 같은 모양("찾을 수 없음")으로 답해요. 소스 범위는 객체를 읽는 권한이 아니에요. **링크가 보이는 조건**은 양 끝의 객체를 모두 읽을 수 있을 때예요. 한쪽이 가려진 객체면 `neighbors`에 나오지 않고, 영향 범위에서는 7-4처럼 가려진 것으로 잡혀요.

### 7-2. 민감 등급

속성마다 `sensitivity`가 타입 등록부에 적혀 있고(kg-model.md의 속성 칸), 비어 있으면 `open`이에요. 한도는 **객체마다** 5-4로 정해져요.

- `open`: 기본. 그 객체를 읽을 수 있으면 값을 읽어요.
- `restricted`: 그 객체의 한도가 `restricted` 이상이어야 읽어요.
- `confidential`: 그 객체의 한도가 `confidential`이어야 읽어요. `confidential` 값은 투영에 없어요.

등급은 받을 때부터 따라 흘러요. 소스의 컬럼에 등급을 적고(프리셋이 기본값을 줘요), 정제를 지나며 입력 가운데 가장 높은 등급이 따라가요. 속성의 등급은 매핑된 컬럼의 등급보다 낮을 수 없어요. 낮추려면 까닭과 `admin`의 승인이 필요해요(ingestion.md).

### 7-3. 가려진 객체와 속성의 답

읽을 수 없는 **속성**은 없는 것처럼 빠지지 않고 "가려짐"으로 보여요. 속성이 있다는 것은 알지만 값은 모르는 모양이에요.

```
get  PhysicalServer srv-0042
  hostname:         "srv-0042"                  grade: fact
  model:            "model-x"                   grade: fact
  management_addr:  { masked: true, reason: sensitivity_above_limit }
```

가려진 속성을 **찾는 조건으로 쓰면 거절**해요. 예를 들어 `find PhysicalServer where management_addr = "192.0.2.10"`에는 오류 `masked_attribute_in_condition`이 와서 "이 속성은 가려져 있다"고 말해요. 조용히 걸러 주지 않아요. 걸러 주면 결과가 있고 없음으로 값이 새기 때문이에요. 같은 까닭으로 글로 찾기는 부르는 쪽이 읽을 수 있는 속성만 훑어요.

### 7-4. 영향 범위가 가려진 객체를 지날 때, 그리고 수

영향 범위는 정확성을 위해 **전체 그래프에서 계산**해요. 부르는 쪽에 따라 계산이 달라지면 틀려요. 가리는 것은 답을 낼 때예요. 가려진 객체가 길에 있거나 영향받는 끝에 있으면 이름, 타입, 속성은 주지 않아요. **수는 부르는 쪽의 범위에 따라 달라요.**

```
impact  of: srv-0042-pdu                  # 범위가 좁은 부르는 쪽
  affected:
    - PhysicalServer srv-0042      down          lost_channels: [power]
  hidden:
    hidden_passed:  present         # 길에서 지난 가려진 객체가 있음
    hidden_reached: present         # 영향받는 끝에 가려진 객체가 있음
```

- **수를 내는 모든 칸은 "가려진 것을 뺀 수"예요**(계약에 그렇게 적어요). 대상: `impact`의 `groups_touched`(묶음의 `n`, `alive`, `min_alive`), `exposure`의 `would_die_count`, `containment`의 `subtree_size`, `get`의 `link_counts`, `neighbors`의 `groups`, `what_depends`의 `object_count`와 `unreadable`, 충족률의 분모, 변경 알림과 SSE `kg_changed`의 타입별 수.
- **가려진 것의 수(`hidden_*`)는 범위가 전체가 아닌 부르는 쪽에게 정확한 수를 주지 않고 있음/없음(`present` / `none`)만 줘요.** 범위가 전체인 부르는 쪽은 가려진 것이 없어요. 설정으로 정확한 수를 열 수 있어요(같은 타입을 조직별로 가려 보는 배포에서 남의 수가 정보가 될 수 있기 때문이에요).
- `paths`가 가려진 객체를 지나면 그 걸음은 "가려진 객체"로 보여요. 가려진 객체를 `of`나 `dead`에 넣으면 "찾을 수 없음"과 같은 모양으로 답해요.

### 7-5. 질의 엔진의 답을 API가 거르는 법

투영은 DB의 행 단위 권한을 지나쳐요. 그래서 거르는 일은 API가 해요. 부르는 쪽은 언제나 API를 거쳐요(ADR-0010).

1. API가 권한의 판단을 불러 `read_filter`를 받아요. 거름표는 **세 짝의 목록**이에요: `[{object_types(선택자), object_conditions, max_sensitivity}]`(`all`이면 모든 타입). 타입과 등급만 있던 옛 모양을 조건의 칸이 들어간 이 모양이 대신해요.
2. API가 엔진에 묻고, 엔진은 전체 그래프에서 계산해요. 투영에는 객체의 이름과 타입의 작은 표와 객체마다의 `scope_keys` 값이 들어 있어서 답의 객체마다 타입과 조건에 쓸 값을 알아요. 민감한 속성의 값은 투영에 없어요.
3. API가 답의 객체마다 세 짝에 맞춰 보고 맞는 짝의 한도 가운데 가장 높은 것을 그 객체의 한도로 삼아요. 맞는 짝이 없는 객체는 답에서 빼고 `hidden`으로 세요. `via`가 가려진 객체를 가리키면 "가려진 객체"로 바꿔요.
4. 봉투의 수(`result_complete.total` 등)는 거른 뒤의 값으로 고쳐요(7-4). 거르기 전의 수를 주면 가려진 것의 수가 새요.
5. 속성을 주는 질의(`find`, `get`, `neighbors`)는 저장소에서 속성을 읽은 뒤 한도를 넘는 속성을 "가려짐"으로 바꿔요. 변경 알림의 목록과 대량 읽기도 같은 거름표를 지나요.
6. 거른 뒤의 쪽은 거른 수로 채워 돌려줘요. 거르고 남은 것이 `limit`보다 적으면 엔진에 더 물어 채우고, `cursor`도 거른 뒤의 자리를 가리켜요(객체 ID를 써요).

저장소가 멈췄을 때는 3번까지만 되고, 거름표는 사본(3-5)에서 풀어요. 저장소 쪽에서 `scope_keys` 값으로 거르는 칸과 색인의 자리는 [kg-storage.md](kg-storage.md)에 있어요.

### 7-6. 원본을 보는 길

소스 범위는 객체를 읽는 권한이 아니에요. 그런데 미리 보기, 견본, 통계(`/profile`), 다시 돌리기의 견본은 그 소스의 행을 그대로 보여 줘서, 그 길로 객체 읽기를 돌아갈 수 있어요. 그래서 이 길들은 **그 데이터셋이 대는 타입의 읽기 권한을 함께 요구해요.** 소스 범위만으로는 안 돼요. 컬럼의 민감 등급은 그대로 걸리고, `open`이 아닌 컬럼의 흔한 값은 주지 않아요. 이 길의 쓰임은 감사 기록에 남아요(12절).

### 7-7. 문제 목록과 역량 질문의 목록

문제의 `detail`과 역량 질문이 못 채운 객체의 목록은 객체의 내용을 담아요. 이것들도 같은 거름표를 지나요.

- 가려진 객체에 관한 항목은 나오지 않고 가려진 것으로 세요(7-4: 좁은 부르는 쪽에는 있음/없음만). 항목 안의 속성은 객체의 한도를 넘으면 "가려짐"이에요.
- 충족률의 분모와 "못 채운 객체 N"은 가려진 것을 뺀 수예요(7-4).

## 8. 담당자

소스, 타입, 정의의 항목에는 **담당자**(`contacts`: 사람의 `subject_id`나 무리의 이름 목록)가 붙어요. 담당자는 권한이 아니라 연락처예요.

- 문제와 알림이 담당자에게 가요(ADR-0011, ADR-0013). 제안의 검토 요청도 그 항목의 담당자에게 가요.
- 담당자라고 읽거나 고치거나 승인하지 못해요. 그것은 언제나 권한 부여에서 와요. 담당자를 고치는 일은 정의의 변경이에요(브랜치, 제안). 담당자가 비어 있으면 알림은 `admin`에게 가요.

## 9. 제안의 승인 규칙을 범위로

제안은 브랜치를 운영의 정의에 들여 달라는 요청이에요(ADR-0014). 승인의 규칙은 이래요.

- 제안이 고친 **항목 하나하나**에는 **자리**가 있고, 그 자리를 범위에 가진 `approver`의 승인이 있어야 해요. 고친 사람은 제외해요. 고치는 쪽도 자리를 범위에 가진 `editor`예요.
- 한 사람의 범위가 여러 항목을 덮으면 그 사람의 한 번의 승인으로 돼요.
- 승인 뒤에 내용이 바뀌면 승인은 무효예요.
- 검사가 "이 제안 때문에 깨진다"고 말한 항목도 고친 항목처럼 승인을 받아요.
- 승인은 사람만 해요. 시스템 계정은 승인자가 못 돼요. 같은 주체이거나 같은 `on_behalf_of`이면 승인하지 못해요(definitions-at-agent-scale.md).
- 조직 표준 타입은 `model_steward`예요(10-1). 안전장치를 느슨하게 하는 것과 민감 등급을 낮추는 것은 `admin`이에요(10-1).

### 9-1. 항목이 범위에 드는 조건

| 항목 | 자리 |
|---|---|
| 소스 설정, 데이터셋, 정제, 일정, 기대 조건 | 그 항목이 딸린 소스 |
| 타입(`ext`)과 속성, 링크 정의(**출발 타입**), 식별 규칙, 예외 목록, 역량 질문, 목표 | 그 항목이 다루는 객체 타입 |
| 공급 | 소스와 타입 둘 (아래) |
| 조직 표준 타입(`org`) | 범위로 가르지 않아요. `model_steward`가 해요 |

**공급**은 소스의 `editor`가 고쳐요. 그 공급이 객체를 만들거나, 물러나게 하거나, 식별 키를 매핑하면 대상 타입을 범위에 가진 `approver`의 승인도 필요해요. 그렇지 않으면 타입의 담당자에게 알림만 가요. 한 사람의 범위가 둘을 다 덮으면 한 번의 승인이에요.

**정의가 다른 소스의 데이터셋을 읽을 때**(정제 데이터셋, 링크 정의)는 자리 말고도 읽는 소스가 걸려요. 쓰는 `editor`는 읽는 소스를 자기 범위에 가져야 하고(없으면 쓰는 것도 `:preview`로 결과를 보는 것도 `target_out_of_scope`예요), 승인은 읽는 소스의 범위도 따져요. 읽는 소스의 담당자에게는 알림도 가요.

### 9-2. 지어낸 예시 하나: 한 소스의 매핑을 고침

`u-hansol`(`editor`, `sources`: `rack_sheet`)이 소스 `rack_sheet`의 공급 `rack_sheet_to_rack`을 고치는 제안 `P-31`을 올렸어요. 이 공급은 `Rack` 객체를 만들어요.

- `u-narae`(`approver`, `sources`: `rack_sheet`, `server_list`, `object_types`: `Rack`)는 **승인할 수 있어요.** 소스와 대상 타입을 모두 범위에 가졌고 고친 사람이 아니에요. 한 번으로 돼요.
- `u-narae`에게 `Rack`이 없었다면 `Rack`을 범위에 가진 다른 `approver`의 승인이 더 필요해요.
- `u-daon`(`approver`, 네트워크 층)은 자리가 범위 밖이라 못 해요(`target_out_of_scope`). `u-hansol`은 `approver`도 갖고 있어도 자기가 고친 것이라 못 해요(`self_approval_not_allowed`).

### 9-3. 지어낸 예시 둘: 두 소스의 데이터셋을 읽는 링크 정의를 고침

`u-hansol`이 링크 정의 `server_in_rack`의 조건을 고치는 제안 `P-32`를 올렸어요. 이 정의는 소스 `server_list`와 `rack_sheet`의 데이터셋을 읽고, 출발 타입은 `PhysicalServer`예요. 자리는 출발 타입이에요.

- `u-hansol`이 쓰려면 `server_list`와 `rack_sheet`가 둘 다 `u-hansol`의 소스 범위에 있어야 해요.
- 승인은 출발 타입 `PhysicalServer`와 읽는 소스 `server_list`, `rack_sheet`를 모두 범위로 덮어야 해요. 한 사람이 다 덮으면 한 번이고(`u-eun`이 `PhysicalServer`와 두 소스를 다 가졌다면 그 한 번), 나눠 덮으면 덮는 사람마다 한 번씩이에요.
- `u-narae`(소스 둘만 가짐)는 혼자서는 못 해요. 출발 타입이 범위 밖이에요.
- 덮을 `approver`가 없으면 제안이 막혀요. `admin`이 권한을 줘서 풀어요(10-2).

### 9-4. 혼자 쓰는 처음 세우기와 시험 배포: `solo_approval`

처음 세울 때나 혼자 시험하는 배포에서는 자기가 고친 것을 자기가 승인할 사람밖에 없어요. 이를 위한 **드러난 설정 하나**(`solo_approval`)가 있어요. 기본은 꺼짐이에요. `admin`이 켜면 자기가 고친 것을 자기가 승인할 수 있어요(`self_approval_not_allowed`가 풀려요. `admin`에게도 같아요). 켜 있는 동안 **모든 승인의 감사 기록에 `solo_approval` 표시가 남고 건강에 경고가 떠요.** 시스템 계정은 여전히 승인하지 못해요.

## 10. 조직 표준 타입, 모델 관리, 막힌 일 풀기
### 10-1. 누가 승인하나

| 변경 (제품 표준 `std`는 제품이 싣고 원본을 고치지 않아요) | 고치는 사람 | 승인하는 사람 |
|---|---|---|
| 조직 표준 `org`의 추가·수정·삭제, 제품 표준의 덧씌움 | `editor`가 제안 | 그 타입의 층을 범위에 가진 `model_steward` |
| 사용자 정의 `ext` | `editor`가 제안 | 그 타입을 범위에 가진 `approver` (고친 사람 제외) |
| `ext` 타입을 `org`로 올리기, 타입 합치기 | `editor`가 제안 | `model_steward`가 맡아요 |
| 안전장치의 값을 느슨하게 하기 | `editor`가 제안 | `admin` (조이는 것은 범위를 가진 `approver`) |
| 속성의 민감 등급을 낮추기 | `editor`가 제안 | `admin` |

- **`model_steward`의 범위는 층으로 좁힐 수 있어요**(`object_types`에 `layer` 선택자). 층마다 맡는 사람을 둘 수 있어요. 범위를 안 적으면 전체예요.
- "표준 타입은 승인이 필요하다"는 요구는 `org` 층의 변경에 승인이 필요하다는 것으로 받아요.
- 타입의 쓰임 보고는 그 타입을 범위에 가진 `viewer`가 읽고(`model_steward`는 자기 범위), `model_steward`는 겹치는 타입의 짝을 주기로 받아 봐요(kg-model.md의 비슷한 타입을 막는 장치). 사용자 정의 타입은 `experimental`로 시작해 쓰이면 `active`가 되고, 여럿이 쓰면 조직 표준으로 올려요. 올려도 `id`가 이어져요. `experimental` 타입은 그 타입을 범위에 가진 `editor`가 아닌 모두에게 경고와 함께 보여요.

### 10-2. `admin`이 막힌 일을 풀 때

일이 막혔을 때 푸는 길은 `admin`에게 있어요.

- 범위를 가진 `approver`가 없어 제안이 막혔을 때: 승인할 사람에게 권한 부여를 줘요.
- 방금 병합된 제안이 급하게 문제가 됐을 때: 승인 없이 되돌려요. 검사와 줄은 그대로 거치고 정해진 기한 안에 사후 검토를 받아요(ADR-0014).

이 일들은 감사 기록에 `admin_override`로 따로 표시돼요. 자기가 고친 것을 자기가 승인하지 못하는 규칙은 `admin`에게도 같아요(`solo_approval`을 켠 배포만 달라요).

### 10-3. 비밀 값을 푸는 일은 누가 하나

들여다보기, 점검, 미리 보기, 시험 수집은 소스의 비밀 값을 풀어 써요(ADR-0018). 누가 하는지는 **브랜치가 소스의 닿는 주소를 바꿨는가**로 갈라요.

- 브랜치의 소스 정의가 본줄기 그대로(닿는 주소가 같음)이면 그 소스를 범위에 가진 `editor`, `operator`가 해요.
- 브랜치가 닿는 주소를 바꿨으면 그 소스를 범위에 가진 `operator`(또는 `admin`)만 해요.
- 비밀 값은 `allowed_hosts` 안의 주소로만 쓰여요. 바꾼 주소는 시험 수집 앞에 보여요(ADR-0018).
- 비밀 값을 넣고 바꾸는 것은 그 소스를 범위에 가진 `operator`(또는 `admin`)예요. `editor`는 참조만 정의에 넣어요. 제품 범위의 비밀 값(알림 길의 열쇠, 서명 열쇠)은 `admin`만 넣고 바꿔요. 메타 정보는 `auditor`도 봐요. 값은 아무도 읽지 못해요.
- 푼 쓰임은 `secret_used`로 남아요(12절).

### 10-4. 운영 행위의 승인

프락시움 자신의 운영 행위(ADR-0017)는 요청한 쪽이 아닌 `admin`이나 범위를 가진 `operator`인 **사람**이 승인해요. 시스템 계정은 승인하지 못해요. 승인이 필요 없는 행위는 `pause_sources_by_secret`처럼 되돌릴 수 있고 지키는 행위예요. 확인을 끄거나 암호화 없이 닿는 소스 연결과 `rewrap_master_key`는 `admin`이 승인해요. 승인된 연결에는 기한이 있어요.

## 11. 시스템 계정

사람이 아닌 시스템(다른 조직의 도구, 에이전트)이 쓰는 계정이에요. 프락시움이 내요. 같은 역할과 범위를 받고, 권한 부여의 누구 칸에 `system_account`로 들어가요. 밀어 넣는 시스템 계정은 `ingester`를 받아요.

칸: `account_id`, `display_name`, `description`, `contacts`(담당자. 한도에 걸리거나 쓰임이 이상할 때 연락할 곳), `token_hash`(토큰 값은 저장하지 않고 만들 때 한 번만 보여 줘요), `expires_at`, `rotated_at`(새 토큰을 내면 옛 토큰은 짧은 겹침 뒤에 막혀요), `rate_limit`(부르는 쪽마다의 한도, ADR-0010), `bound_persons`(이 계정이 `on_behalf_of`로 적을 수 있는 사람의 목록. 관리자가 묶어 둬요), `status`(`active` / `disabled`), `created_by`, `created_at`.

- 만들고, 토큰을 바꾸고, 끄고, 사람을 묶는 것은 `admin`이에요. 인증은 로그인 포트 뒤에 둬요. SSO가 시스템용 자격을 주면 그것을 쓰고, 아니면 프락시움이 낸 토큰을 써요. 토큰의 해시와 상태는 사본(3-5)에 들어서 저장소가 멈춰도 확인돼요.
- **`on_behalf_of`는 계정이 스스로 적는 값이 아니에요.** 요청에 적은 값은 `bound_persons` 가운데서만 고를 수 있고, 아니면 거절해요. "같은 맡긴 사람이면 승인하지 못한다"는 규칙의 열쇠이기 때문이에요.
- **계정을 끄거나 토큰을 거두는 것은 저장소가 살아 있으면 30초 안에 퍼져요.** 저장소가 멈춘 동안은 사본의 나이 상한(15분)까지 남을 수 있어요.
- 계정이 어느 타입과 속성을 읽었는지는 쓰임의 통계로 남아요. 고치거나 물러나게 하기 전에 "무엇이 걸리나"를 답하는 데 써요(ADR-0014). `bulk_read` 허가는 `admin`이 주고, 그 쓰임은 감사 기록에 남아요.
- 시스템 계정이 운영 행위를 요청할 때는 근거가 된 진단의 ID(`diagnosis_id`)가 있어야 해요(ADR-0017).

## 12. 감사 기록
### 12-1. 적는 것과 적지 않는 것

적는 것: 정의를 고친 것(누가, 어느 항목, 어느 제안) / 승인과 거절, 병합과 되돌리기 / 정의나 KG의 범위를 내보낸 것 / 권한 부여를 주고 거둔 것(위임한 부여 포함), 기본 부여와 시스템 계정을 바꾼 것 / `admin`이 막힌 일을 푼 것 / 민감한 속성(`restricted`, `confidential`)을 읽은 것과 대량 읽기 / **원본을 보는 길**(7-6)의 쓰임 / **모든 운영 행위**(요청, 승인, 실행. 운영 역할의 안전장치의 확인, 흐름 풀기, 버전 고정 포함) / 비밀 값을 넣고 바꾸고 지운 것과 풀어 쓴 것, `allowed_hosts`를 바꾼 것 / 이 가운데 고치는 일과 민감한 속성·대량 읽기의 거절된 시도.

적지 않는 것: 보통의 읽기와 그 거절(양이 감당되지 않아요. 쓰임의 통계로만 남아요, ADR-0013), 민감한 속성의 값, 비밀 값, 행의 내용.

### 12-2. 기록의 칸

- `audit_id`, `occurred_at`, `kg_id`(KG에 든 것을 읽거나 고친 기록이면): 기록의 식별자와 때
- `actor_kind`(`person` / `system_account` / `role_instance`), `actor_id`(`subject_id`, `account_id` 또는 역할의 실행). `role_instance`(비밀 값을 풀어 쓴 실행)는 시킨 쪽을 `on_behalf_of`에 적어요
- 정의의 변경이면 `authored_by`(주체와 `actor_kind`), `on_behalf_of`, `agent_run_id`, `agent_build`, 승인의 길(`approval_path`: 사람 또는 정책의 판. 정책이면 판의 번호). 승인은 사람만 하고 같은 주체나 같은 `on_behalf_of`는 승인하지 못해요(definitions-at-agent-scale.md)
- 승인이면 `solo_approval`(참이면 9-4를 켠 채 한 승인)
- 운영 행위면 `action`에 그 행위의 이름을 그대로 적고(예: `rewrap_master_key`, `pause_sources_by_secret`), 요청한 쪽, 승인한 사람, 시스템 계정의 요청이면 `diagnosis_id`. 저장소가 멈춰 역할의 디스크에 먼저 적었다가 옮긴 기록은 `written_late`가 참이에요(kg-operations.md)
- `action`: 닫힌 목록의 일 이름. 예: `edit_definition`, `approve_proposal`, `merge_proposal`, `revert_proposal`, `export_definition`, `grant_created`, `grant_revoked`, `read_sensitive`, `bulk_read`, `read_raw_data`, `admin_resolve`, `secret_used`, `secret_changed`, `secret_hosts_changed`와 운영 행위의 이름
- `target_kind`, `target_id`(무엇에 한 일인가), `grant_ids_used`, `outcome`(`allowed` / `denied`. 어느 권한 부여가 허락했나), `admin_override`(`admin`이 막힌 일을 푼 것인가)
- `proposal_id`, `definition_bundle`(정의를 고친 일이면 어느 제안과 정의 묶음, `D-142` 같은 번호), `detail`(건수 같은 요약. 값은 넣지 않아요), `request_id`(한 요청의 이름표)

기록은 더하기만 하고 고치거나 지우지 않아요. 잃으면 안 되는 것의 등급이에요(ADR-0011). 보관 기한은 설정 값이고 기본값은 3년이에요([기본값 표](defaults.md) 4절). `auditor`가 읽어요. 저장소가 멈췄을 때 바꾸는 운영 행위는 거절하고, 저장소 없이 되는 급한 행위만 디스크에 먼저 적어요(kg-operations.md).

## 13. 단계별로 언제 만드나

- **알파**: 백엔드의 권한 모델을 다 만들어요. 여덟 역할, 권한 부여와 범위(타입, 소스, 민감 등급, KG), 권한의 판단, 읽기의 거름과 가림, OIDC 어댑터, 사본, 시스템 계정(`bound_persons`와 30초의 거둠 포함), 감사 기록, `solo_approval`. 모양의 **자리**도 지금 둬요: 객체 조건의 칸과 세 짝의 거름표, `target_attributes`, `delegate`, `/v1/grants`의 모양. 알파의 기준은 이 모두가 API와 명령줄 클라이언트로 되는 거예요(화면은 ADR-0016).
- **클로즈 베타**: 객체 조건을 판단하는 구현(투영의 `scope_keys`, 거름표의 조건 맞춤, 저장소 쪽의 거르기), 범위 있는 관리(`delegate`).

## 14. 알고 가는 한계

- **사본이 거둔 권한을 늦게 반영해요.** 시스템 계정의 끔과 토큰은 저장소가 살아 있으면 30초지만, 권한 부여의 거둠은 사본을 새로 읽는 주기와 증표의 유효 시간만큼 남을 수 있어요. 쓰는 일(고치기, 승인)은 저장소가 살아 있을 때만 하게 해서 틈을 줄이고, 읽기에서는 받아들여요.
- **가려진 것의 수는 정보일 수 있어요.** 범위가 좁은 부르는 쪽에는 있음/없음만 주지만, 있음 자체와 가려진 걸음의 위치(`paths`), 부르는 쪽이 고르는 `dead`를 바꿔 가며 묻는 길로 가려진 쪽의 구조를 짐작할 수는 있어요. 설정으로 수를 열면 더해요. 보통의 읽기를 안 적어서, 열린 값을 누가 읽었는지는 사고 뒤에도 알 수 없어요.
- **범위를 가진 `approver`가 한 명뿐이면** 그 사람이 고친 제안은 `admin`의 도움이 있어야 병합돼요(`solo_approval`은 혼자 쓰는 배포를 위한 것이에요). `admin`의 힘이 커서 감사 기록의 표시와 사후 검토로 지켜봐요.
- **거른 뒤 채우느라 엔진에 더 물어요.** 가려진 것이 많은 부르는 쪽은 계산 예산에 먼저 닿을 수 있어요. 객체 조건이 들어오면 더해요.
- **알파에서 객체 조건은 자리만 있어요.** 그 전에는 "이 자리의 객체만"을 타입으로 갈라야 해요.

## 15. 아직 정하지 않은 것

- `delegate`를 어느 역할의 부여에 붙일 수 있는지, 위임받은 사람이 다시 위임할 수 있는지.
- 객체 조건이 든 부여를 클로즈 베타 전에 만들면 거절하는지(넓게 읽히는 것을 막으려면 거절해야 해요), 조건이 선택자 안 타입에 없는 속성을 가리킬 때.
- 범위가 좁은 부르는 쪽에게 충족률의 비율을 가려진 것을 뺀 객체로 다시 따져 줄지.
- `solo_approval`을 켠 때 같은 `on_behalf_of` 규칙도 푸는지. 들여다보기도 7-6의 읽기 권한을 요구하는지. KG 칸이 `auditor`, `admin`에도 걸리는지.
