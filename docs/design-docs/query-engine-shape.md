# 질의 엔진의 언어와 구조

[KG 질의](kg-queries.md)의 프로젝션과 엔진을 확정하는 문서예요(ADR-0006, ADR-0010). 공개 출처와 측정은 [설계 조사](../references/design-research.md)에 있어요. 모든 수는 지어낸 그래프의 프로토타입에서 측정한 것이고, 이 문서에서는 모두 가정이에요. 약속이 아니라 목표의 근거예요.

## 1. 목적과 다루는 질문

- 엔진을 어떤 언어로, 어떤 구조로 만들까요? 기성 그래프 엔진을 쓸까요?
- 규모가 커지면 어디가 먼저 병목이 되나요? 병목이 되는 곳을 지금 설계에 어떻게 반영하나요?
- 측정한 수가 무엇을 말하고 무엇을 말하지 않나요? 테스트 환경 없이 규모를 어떻게 확인하나요?

## 2. 결정

1. **질의 엔진은 Go로 직접 구현해요. 확정이에요.** 같은 엔진을 Go와 Rust로 구현해서 노드와 엣지를 합쳐 100만, 1천만, 3천만, 1억 개에서 나란히 측정했더니 결과가 같았고(모든 규모에서 모든 루트 집합의 체크섬이 일치), Rust는 질의와 빌드가 10~30% 빨랐을 뿐이에요. Go는 질의 중 GC가 한 번도 실행되지 않았고(포인터 없는 배열) 가장 긴 정지가 1ms 미만이었어요. 한계는 언어가 아니라 재빌드와 병합의 순간 메모리였고 두 언어에서 같았어요. 한 언어로 가는 이득(도구와 검사 한 벌, 같은 프로세스 안의 경계)이 더 커요. 운영 중에 언어를 바꿔 다시 구현하는 위험을 지지 않으려고 지금 정해요.
2. **기성 그래프 엔진은 쓰지 않아요.** 허용 라이선스, 임베디드 사용, 메모리 상주, 증분 갱신, 과거 버전, 우리 모델의 의미(이중화, 채널, 3값 논리)를 모두 충족하는 것이 없었어요. 의존성을 늘리지 않는다는 방침과도 맞아요. 엔진의 핵심은 표준 라이브러리로만 구현해요.

## 3. 엔진의 구조

측정한 프로토타입의 구조를 설계로 삼아요.

| 항목 | 구조 | 이유 |
|---|---|---|
| 노드 | 32비트 정수 ID. 노드마다 포인터 없음 | 포인터가 없어서 GC가 스캔할 것이 없어요 |
| 이웃 | 정방향과 역방향의 압축 이웃 배열(CSR) | 장애는 의존하는 쪽 방향(역방향)으로 전파돼요 |
| 엣지 | 엣지별 링크 의미와 채널은 나란한 바이트 배열 | 필터가 1바이트 비교예요 |
| 계산 | 작업 큐 기반의 최소 고정점 계산. 노드마다 "마지막으로 전파한 상태"를 두어 같은 상태를 두 번 전파하지 않아요 | 처리 횟수에 상한이 있고 순환이 자동으로 끝나요 |
| 변경 | 베이스 위의 오버레이에 쌓고 주기적으로 병합해요 | 4.2절, 4.5절 |
| 동시 질의 | 워커마다 별도의 작업 공간. 질의 중 할당이 없어요 | 락이 없고 GC가 개입하지 않아요 |

프로토타입의 상태는 4개(`ok < exposed < degraded < down`, 여기의 `exposed`는 프로토타입의 한 값이고 설계의 `exposed_direct`·`exposed_inherited` 2개로 나뉜 것이 아니다)라서 노드당 처리가 3번 이내였어요(측정한 최댓값은 노드당 1.85번). 설계의 결과 종류와 채널은 더 많아서 이 상한은 그대로 옮기지 못해요. 기준 구현으로 다시 계산해요(8절).

## 4. 측정이 드러낸 것과 설계에 반영한 것

### 4.1 노드 ID는 32비트예요

프로토타입은 간선 하나를 64비트 키 하나에 묶었고 노드 ID가 26비트(약 6,700만 노드)라서 노드와 엣지 합계 약 2.4억에서 한계에 부딪혔어요(노드 대 엣지가 1 대 2.8일 때). 그래서 ID는 32비트로 두고 **엣지의 키에 ID를 좁게 묶지 않아요.** 프로토타입의 이웃 오프셋이 32비트라 엣지 약 43억이 상한이었어요. 청크로 나누면 오프셋은 청크 안의 값이에요. 객체 ID(16바이트)와 내부 번호의 매핑은 프로젝션에 있고, 내부 번호는 빌드마다 달라서 외부(응답, 커서)에 노출하지 않아요. 외부에는 객체 ID를 써요.

### 4.2 통째로 다시 병합하지 않아요: 컨테인먼트 단위의 청크

오버레이를 병합하려면 키 배열, 새 구조, 이전 구조가 함께 있어야 해서 병합하는 순간의 메모리가 평소의 약 2.4배였어요(1억에서 평소 1.2GB, 병합 피크 2.85GB, 병합 시간 약 7.6초). 이 8GB 기계에서 가장 먼저 도달하는 한계가 이것이고, Rust에서도 같았어요(구조의 바이트 수와 병합 방식이 같아서예요).

- **베이스를 청크로 나눠 청크마다 병합해요.** 버전 교체도 청크 단위로 해요.
- **청크의 단위는 컨테인먼트(위치 포함 관계)예요.** 해시로 나누지 않아요. 영향 범위가 컨테인먼트 안에서 대부분 끝나서 청크 안에서 계산이 닫혀요.
- **청크를 건너는 엣지는 두 청크의 경계 테이블에 둬요.** 청크마다 해시가 있고 경계 테이블도 프로젝션 파일의 한 섹션이에요([KG 질의](kg-queries.md) 8절).
- **엔진의 메모리 예산은 "평소 + 가장 큰 청크의 병합"이에요.** 통째로 병합할 때의 2.4배가 아니에요.
- [알파: 청크의 구조, 클로즈드 베타: 청크의 크기와 개수의 값]

```
 컨테인먼트 A(청크 A) ──경계 테이블 A↔B──  컨테인먼트 B(청크 B)
   병합: A를 병합하는 동안 B는 그대로 읽혀요(순간 메모리는 A의 몫만 늘어요)
```

### 4.3 응답 시간은 KG의 크기가 아니라 도달하는 노드의 수를 따라요

질의 하나는 도달한 노드당 약 20~35ns였어요. 규모를 키우는 것이 사이트를 더 붙이는 것이라서 최악 질의가 규모와 거의 무관하게 사이트 하나의 크기(약 24만 노드)로 제한됐어요. 사이트를 넘나드는 의존을 넣으면 달라져요. 의존 확률 3%에서 데이터홀 하나에 장애가 났을 때의 질의가 도달하는 노드가 6.2만에서 14.7만으로, 중앙값이 2.3ms에서 9.1ms로 늘었고, 60%에서는 약 61만 노드에 34~43ms였어요. 전역 서비스로 사이트가 연결된 실제 구조에서는 최악이 규모에 비례해 커질 수 있어요(추정).

그래서 **질의의 한도와 응답의 요약은 도달한 노드 수를 기준으로 적용해요.** 경로 열거는 한도 없이는 쓸 수 없어요. 큰 객체를 루트로 하면 22~107ms 안에 100만 경로의 한도에 도달해 잘렸고 영향 노드는 25만~66만 개였어요. `paths`가 `top_k`와 시간 예산을 가지는 이유예요.

### 4.4 노출됨은 끝까지 전파돼요

노출됨(이중화를 잃었으나 아직 동작해요)은 그 아래 의존하는 것들에 **전파돼요.** 이중화를 잃은 랙 위의 VM은 노출됨이에요. 프로토타입은 랙에서 멈췄어요(`contained_in`과 그룹이 노출됨을 상속하지 않았어요). 그것은 프로토타입의 규칙이지 설계가 아니에요.

- **전파 깊이의 설정은 없어요.** 깊이가 설정이면 같은 KG의 같은 질의가 배포마다 다른 결과를 내고, 기준 구현과 골든 값이 깊이마다 따로 필요해요. 깊이는 값이 아니라 결과의 의미예요.
- 결과는 `exposed_direct`(자기의 이중화를 잃음)와 `exposed_inherited`(의존하는 것이 노출됨)를 구분해요([KG 질의](kg-queries.md) 5.4절).
- 전파되는 만큼 도달하는 노드가 늘어요. 프로토타입에서 데이터홀 하나의 장애는 노드 약 6만~12만 개였는데 노출됨이 VM까지 내려가면 그 수준(수만~수십만)으로 늘 것으로 봐요(추정). 이 비용은 측정하지 않았어요.

### 4.5 오버레이가 쌓이면 느려져요: 병합 주기의 예산

1억 단위에서 오버레이 100만 연산(간선의 약 1.3%)이 쌓이자 데이터홀 하나에 장애가 났을 때의 질의 중앙값이 3.1ms에서 14.0ms로 올랐어요(약 4.5배). 병합하면 돌아와요. 오버레이는 연산당 약 156바이트의 포인터 있는 힙이라 수천만 연산이 되면 GC 부담도 커질 것으로 봐요(추정). 그래서 **병합 주기의 예산**을 둬요. 오버레이가 얼마나 쌓이면 병합하는지의 값은 기본값 표에 가정으로 두고 측정해서 정해요(8절).

## 5. 측정한 수와 이 수에 포함되지 않은 것

조건: 지어낸 구조(시드 하나), 2코어 8GB 한 대, 설정마다 1회씩 실행(실행 간 편차 10~40%), 입출력 없음. 규모는 노드와 엣지의 합계이고 1억 개는 노드 약 2,630만, 엣지 약 7,400만이에요.

| 항목 | 값 |
|---|---|
| 노드와 엣지 하나의 크기(구조만) | 약 12바이트 |
| 1억 개의 상주 메모리 | 약 1.2GB |
| 빌드(정렬과 정방향·역방향 구조) | 1억 개에서 4~8초 |
| 데이터홀 하나에 장애가 나는 경우(VM 약 3.4만) | 중앙값 약 2ms |
| 사이트의 전원 2개가 모두 장애인 경우(VM 약 20만) | 중앙값 5~7ms, 최대 약 46ms |
| 영향이 가장 큰 루트 100개 | 중앙값 약 9ms, p99 약 33ms |
| 병합 피크 메모리 | 평소의 약 2.4배 |

정확성은 느리지만 단순해서 명백히 정확한 기준 구현과 전 노드의 상태를 비교해서 확인했어요(1,367개 질의에서 불일치 0, 갱신 뒤 병합한 구조도 150개 질의에서 0).

**이 수에 포함되지 않은 것.** 아래는 프로토타입에 없어서 이 수가 말하지 않는 것이에요.

| 빠진 것 | 프로토타입에서는 |
|---|---|
| 3값(알 수 없음)과 2가지 결과(사실만, 가정 포함), `min_alive`를 모를 때 가능한 값을 모두 평가하기 | 없음. 모두 안다고 가정했어요 |
| 앵커까지의 연결성과 의존을 번갈아 실행하기 | `connected_to`는 "대상에 장애가 나면 `degraded`"일 뿐이에요 |
| 채널 6종의 동시 상태 | 원인 채널 하나만. 전력과 냉방이 함께 장애인 경우가 없어요 |
| 노출됨의 전파 | 랙에서 멈춤(4.4) |
| 링크별 근거 등급과 종류와 관측 시각, `delay_class` | 없음 |
| 조회 관점(`as_designed`, `as_observed`)과 `max_staleness`, `volatile`의 경량 변경 레코드 | 없음 |
| 객체 ID(16바이트)와 내부 번호의 매핑, 이름과 타입 테이블, 객체별 `scope_keys` 값, 그룹 테이블 | 없음 |
| 속성 필터링, 과거 버전 | 없음 |
| 읽기와 쓰기의 동시 실행 | 쓰는 동안 읽기를 멈췄어요 |
| 입출력(스토리지, 파일 보관, 재시작) | 없음 |

- **12바이트는 구조만의 값이에요.** 위의 테이블이 추가되면 메모리는 12바이트의 몇 배가 될 거예요. 배수는 측정해야 알 수 있어요.
- **"1초"는 아직 근거가 없는 목표예요.** 스위치의 ECMP·BGP·LACP를 모두 고려한 영향 범위가 바로 연결성 계산인데, 그것을 측정하지 않았어요. 2가지 결과와 번갈아 실행하기가 계산 시간에 곱해져요. 자릿수로는 수 초 이내이지만(가정) 1초는 모르는 숫자예요.
- 엔진을 Go로 선택한 결론은 이 빠진 것들에 의존하지 않아요. 병목이 메모리 접근과 병합의 순간 메모리라는 측정은 구조가 달라져도 유효해요.
- 노드와 엣지 합계 1억까지 측정했고 그 위는 추정이에요. 병합 피크 기준으로 이 기계의 실용 상한은 약 2.2억~2.4억 단위(선형 외삽한 추정)이고, 청크마다 병합하는 것이 이 상한을 올리는 방법이에요. 규모의 요구는 한 KG에 수천만 개, 설계의 여유는 수억까지예요(REQ-134).

## 6. 규모를 검증하는 방법

제품 책임자가 테스트 환경을 제공할 수 없어서 이렇게 해요.

- **합성 세계 생성기**를 제품의 일부로 둬요(층별 분기 수와 깊이와 사이트 간 교차의 비율이 인자).
- **기준 구현**과 결과를 비교하는 테스트를 상시 실행해요. **영향 범위 단계의 첫 작업이 설계의 의미를 모두 반영한 기준 구현이에요**(5절 표의 빠진 것을 모두). 생성기의 정답을 이것으로 만들어요.
- 규모를 바꿔 가며 측정하는 벤치마크를 정해진 장비의 CI에서 실행해 성능 회귀를 잡아요.
- 실제 소스를 연결하면 제품이 KG의 **분포 프로파일**(연결 수의 분포, 깊이, 그룹의 크기, 사이트 간 교차의 비율)을 산출하고 그 값으로 생성기를 다시 보정해요.

"클로즈드 베타에서 환경으로 측정한다"는 문장은 이것으로 바뀌었어요. 클로즈드 베타에서는 이 방법으로 수천만 개를 측정해요. 엔진 측은 위의 방법으로 되지만 **스토리지 측**(프로젝션 빌드, 적용, WAL, 정리)의 수천만 측정은 2코어 8GB로는 부족해서 클로즈드 베타 전에 빈 장비 하나가 필요해요(설계의 질문이 아니라 준비의 일이에요).

## 7. 알려진 한계와 가정

- 모든 수는 합성 구조, 1회씩, 한 대에서 측정한 가정이에요. 규모 사이의 비교보다 자릿수와 경향을 신뢰해요.
- 실제 구조(전역 서비스, 허브)는 4.3절처럼 최악을 크게 바꿀 수 있어요. 실제 소스를 연결한 뒤 분포 프로파일로 다시 보정해요.
- 비슷한 공개 사례는 우리와 가장 가까운 분야(자산과 서비스 맵의 영향 분석)에서 공개된 수를 찾지 못했어요. 찾은 사례는 설계 조사에 있고 요약 도구로 읽은 것이라 원문 그대로의 인용이 아니에요.

## 8. 미결 사항

- 청크의 크기와 개수의 기준, 병합 주기의 예산 값(가정으로 [기본값 표](defaults.md)에 둬요).
- 청크 단위의 교체와 "응답은 이전 버전이거나 이후 버전이다"(섞이지 않음)를 함께 지키는 방법. 한 질의가 여러 청크를 지날 때예요.
- 노출됨을 상속하는 링크 의미의 목록. 노출됨이 끝까지 전파될 때 처리 횟수의 상한.
- "정해진 장비의 CI"를 누가 마련하나.
