# 질의 엔진의 언어와 모양

[KG에 묻기](kg-queries.md)의 투영과 엔진을 굳히는 덧붙임이에요(ADR-0006, ADR-0010). 공개 출처와 측정은 [설계 조사](../references/design-research.md)에 있어요.

## 1. 결정
1. **질의 엔진은 Go로 직접 만들어요. 확정이에요.** 같은 엔진을 Go와 Rust로 짜서 노드와 엣지 100만, 1천만, 3천만, 1억 개에서 나란히 쟀더니 답이 같았고 Rust는 질의와 짓기가 10~30% 빨랐을 뿐이며, Go는 질의 중 GC가 한 번도 돌지 않았고(포인터 없는 배열) 가장 긴 멈춤이 1ms 아래였어요. 한계는 언어가 아니라 다시 짓기와 합치기의 순간 메모리였고 Rust에서도 같았어요. 한 언어로 가는 이득(도구와 검사 한 벌, 같은 프로세스 안의 경계)이 더 커요.
2. **기성 그래프 엔진은 쓰지 않아요.** 허용 라이선스, 넣어 쓸 수 있음, 메모리 상주, 증분 갱신, 과거 버전, 우리 뜻(이중화와 채널과 세 값)을 함께 채우는 것이 없었어요. 의존성을 늘리지 않는다는 방침과도 맞아요. 엔진의 핵심은 표준 라이브러리로만 짜요.

## 2. 엔진의 모양(측정한 시제품의 모양을 설계로 삼아요)
정수 ID, 앞방향과 뒷방향의 눌러 담은 이웃 배열, 엣지마다의 뜻과 채널은 나란한 바이트 배열, 노드마다 포인터 없음이에요. 영향 범위는 일감 목록으로 도는 가장 작은 고정점이고 노드마다 처리 횟수에 상한이 있어요. 변경은 바탕 위의 덧씌움에 쌓고 때때로 합쳐요.

## 3. 측정이 드러낸 것
- **노드 ID는 32비트로 둬요.** 시제품의 26비트 묶음은 약 2.4억에서 막혀요. 엣지의 열쇠에 ID를 좁게 묶지 않아요.
- **통째로 다시 합치지 않아요.** 합치기의 순간 메모리가 평소의 약 2.4배였어요. 바탕을 조각으로 나눠 조각마다 합치고 버전의 바꿈도 조각 단위로 해요. 엔진의 메모리 예산은 "평소 + 가장 큰 조각의 합치기"로 잡아요. [알파: 조각의 구조, 클베: 값]
- 응답 시간은 KG의 크기가 아니라 **질의가 닿는 노드의 수**를 따라요(닿는 노드 하나에 수십 나노초). 그래서 질의의 한도와 답의 요약은 닿은 수로 걸어요. 사이트를 건너는 의존이 많으면 닿는 수가 늘어요.
- **노출됨**(이중화를 잃었으나 아직 서요)은 그 아래 기대는 것들에 **번져요**(이중화를 잃은 랙의 VM은 노출됨이에요). 시제품은 랙에서 멈췄고 그것은 시제품의 규칙이지 설계가 아니에요. 번지는 깊이의 값은 [기본값 표](defaults.md)에 둬요(값은 아직 정해지지 않았어요).

## 4. 잰 수(가정이에요. 약속이 아니고 목표의 근거예요)
조건: 지어낸 모양, 2코어 8GB, 한 번씩 돌림, 입출력 없음, 속성 거르기와 과거 버전 없음.

| 무엇 | 값 |
|---|---|
| 노드와 엣지 하나의 크기 | 약 12바이트 |
| 1억 개의 상주 메모리 | 약 1.2GB |
| 홀 하나가 서는 경우 | 가운데값 약 2ms |
| 사이트의 전원 둘이 다 서는 경우(VM 약 20만) | 가운데값 5~7ms, 최대 약 46ms |

## 5. 규모를 검증하는 길
제품 책임자가 시험 환경을 줄 수 없어서 이렇게 해요.
- 지어낸 세계 생성기를 제품의 부분으로 둬요(층의 갈래 수와 깊이와 사이트 건넘의 비율이 인자).
- 느리지만 뻔히 옳은 기준 구현과 답을 견주는 시험을 늘 돌려요.
- 규모를 바꿔 가며 재는 벤치를 정해진 장비의 CI에서 돌려 뒷걸음을 잡아요.
- 실제 소스를 붙이면 제품이 KG의 **모양 카드**(연결 수의 분포, 깊이, 묶음의 크기, 사이트 건넘의 비율)를 내고 그 값으로 생성기를 다시 맞춰요.

"클로즈 베타에서 환경으로 잰다"는 문장은 이것으로 바뀌었어요. 클로즈 베타에서는 이 길로 수천만 개를 재요.

## 6. 설계 담당에게 묻는 것
- 노출됨이 번지는 깊이의 기본값.
- 조각의 크기와 개수의 기준.

## 7. 관련
