# 데이터 관측성

소스에서 데이터가 잘 들어오는지, 들어온 데이터가 유효한지, 파이프라인이 실행되는지, 객체가 잘 만들어지는지, 객체·액션·링크가 얼마나 바뀌는지를 보는 설계예요. 신호가 생겨서 저장되고, 헬스 상태가 되고, 알림과 응답이 되기까지를 다뤄요. 문제 목록의 처리 절차는 [KG 운영](kg-operations.md)(ADR-0011)이 정해요. 지표와 헬스 상태와 알림은 이 문서가 맡아요. 숫자는 제품에 포함된 기본값(설정)이거나 측정하지 않은 가정이고, 클로즈드 베타에서 측정해서 수정해요(16절). 알파는 100만 개 규모의 합성 세계로 기능을 테스트해요.

## 1. 목적과 다루는 질문

| 쟁점 | 답 |
|---|---|
| 소스에서 데이터가 잘 들어오는가, 들어온 데이터가 유효한가 | 연결·수집·유효성의 신호(3절), 기대 조건과 컬럼 통계, 이상 탐지(7절) |
| 파이프라인이 잘 실행되고 객체가 잘 만들어지는가 | 단계별 건수 대조와 소요 시간, 객체의 신호, 실행 소스 탐색(3절, 9절) |
| 객체·액션·링크가 얼마나 바뀌는가 | 변경 신호, 플래핑, 타임라인(3절, 9절) |
| 소스 하나가 이상 상태이면 무엇이 영향받는가 | 정의의 계보를 따른 헬스 상태 전파와 근본 원인(5절, 10절) |
| 사람과 에이전트가 "믿어도 되는가"를 어떻게 질의하는가 | `health`와 `quality` 질의, 응답의 헬스 힌트(11절) |
| 제품 자신과 알림에 장애가 나면 | 같은 구조로 측정하고 하트비트를 둠(13절) |

## 2. 개요

**핵심 원칙 3가지.** 첫째, 관측은 나중에 붙이는 화면이 아니라 실행기가 산출하는 정식 결과물이에요. 둘째, 헬스 상태는 정의의 계보를 따라 전파돼요. 셋째, 사람만 질의하는 것이 아니라 에이전트와 다른 시스템도 API와 MCP로 질의해요.

```
 실행기(워커, 질의 엔진, API): 단계별 건수와 통계, 증분 갱신
   │ 신호
   ▼
 지표 테이블 · 실행 이력 · 타임라인 · 사용 이력 ── 검사: 기대 조건 · 내장 검사 · 목표 · 이상 탐지
   ▼
 자원별 헬스 상태 ◀── 정의의 계보(소스 → 데이터셋 → 피드 → 타입·속성 → 링크 정의 → 읽는 계정)
   ├─▶ 알림(근본 원인별 그룹) ─▶ 문제 목록 ─▶ 담당자(발송 경로 포트)
   ├─▶ `health`·`quality` 질의 ─▶ 모든 응답 엔벨로프에 헬스 힌트(API, MCP)
   └─▶ 개방형 형식(OpenTelemetry)의 지표·로그·트레이스, 변경 알림 경로
```

헬스 상태 계산, 집계, 알림 평가는 일정에 따라 워커가 실행해요. 같은 일정이 중복 실행되지 않게 키로 차단해요(ADR-0011의 6번).

## 3. 신호: 8개 영역

자원은 소스, 데이터셋, 피드, 파이프라인(소스 하나가 수집부터 적용까지 거치는 단계 전체), 타입(객체 타입), 속성, 링크 타입, 역량 질문, KG, 서비스 계정이에요. `detail_key`는 지표 안의 세부 구분이에요. 지표 이름은 제품에 포함된 고정 목록이에요. 스트림의 "구간"은 짧은 시간(기본 1분, 가정) 동안 수집한 변경 배치예요.

|---|---|---|---|---|---|
| 연결 | `connection_ok`, `auth_ok`, `read_only_verified` | 접속됐는가, 인증이 통과했는가, 소스 쪽 계정이 읽기 전용으로 확인됐는가(어댑터가 확인하지 못하면 값이 없고 `unknown`) | 0/1 | 소스 | 배치는 수집 때와 주기 점검 때, 스트림은 구독이 유지되는 내내 |
| 연결 | `response_time_ms`, `request_error_ratio`, `rate_limited_count` | 요청 응답 시간(분포), 요청 오류 비율, 속도 제한에 걸린 횟수 | ms, 비율, 회 | 소스 | 같음 |
| 연결 | `circuit_open` | 연속 실패해서 차단했는가(인증 실패는 즉시 차단) | 0/1 | 소스 | 배치는 일정이 중단됨, 스트림은 구독을 끊음 |

| 유효성 | `quarantined_records` | 위반해서 격리한 레코드 | 건 | 피드 | 스트림만. 배치는 `fail`이면 적용을 중단 |

| 사용 | `query_count`, `query_errors`, `query_latency_ms`, `answer_staleness` | 질의 종류(`detail_key`)별 건수, 오류, 응답 시간(분포), 응답에 붙은 신선도(분포) | 건, ms, 초 | KG, 서비스 계정 | 같음 |
| 사용 | `rate_limited_calls`, `bulk_reads` | 한도에 걸린 호출, 대량 읽기 | 회 | 서비스 계정 | 같음 |
| 사용 | `unread_days` | **읽히지 않는 항목**: 마지막으로 읽힌 뒤 경과한 일수 | 일 | 타입, 속성, 피드 | 같음 |
| 충족 | `competency_fill_rate`, `competency_not_evaluated` | 역량 질문의 충족률(필요한 것을 모두 채운 대상 객체 ÷ 대상 객체. 필드 `reading`이 `fact_only`와 `with_assumed`로 두 값을 구분하고, `step_key`가 필요 항목의 단계, `group_key`가 `tracked_groupings`의 그룹), 한도 때문에 계산하지 못한 객체 수. 자세한 것은 ADR-0015 | 비율, 개 | 역량 질문 | 증분 갱신이라 배치든 스트림이든 같음. 속성으로 필터링한 값은 지표로 쌓지 않고 질의할 때 계산 |

- 액션은 지금 타입의 목록뿐이라 정의의 변경(`definition_merges`와 타입의 상태 변경)으로 측정해요. 액션 실행을 측정하는 부분은 엔드투엔드(E2E) 프로세스를 구체화할 때 같은 구조에 채워요.
- 이중화 현황은 `exposure` 질의와 같은 계산이에요(ADR-0010). 질의 엔진이 자기 프로젝션에서 집계해 지표 엔드포인트로 노출하고, 워커가 수집해 지표 테이블에 쌓아요(엔진은 스토리지에 쓰지 않아요). 가장 많이 바뀌는 객체는 지표가 아니라 `churn_top` 테이블(4.3절)에 값으로 남아요.

## 4. 지표의 저장

### 4.1 `metric_point`

데이터의 지표는 제품 안에 저장해요. API가 과거 추이를 보여 줘야 하고, 확정한 시점의 값을 KG 버전과 함께 남겨야 해서예요(`kg_version` 필드. 스트림에서 1시간마다 확정하면 버전이 빠르게 늘어요). ADR-0011의 `quality_metric` 테이블은 이 테이블이 이어받아요.

| 필드 | 의미 |
|---|---|
| `kg_id` | 해당 KG. 제품 컴포넌트의 지표는 비어 있어요 |
| `resource_kind` | `source` / `dataset` / `feed` / `pipeline` / `object_type` / `attribute` / `link_type` / `competency_question` / `kg` / `system_account` / `component`(제품 컴포넌트, 13절) |
| `resource_id` | 정의 항목의 바뀌지 않는 `id`(이름이 아니에요. 이름을 바꿔도 이어져요) |
| `detail_key` | 세부 구분. 고정 목록이나 정의 항목의 `id`예요(컬럼, 단계, 질의 이름, 기대 조건, 오류 코드, 이유). 행의 값은 쓸 수 없어요 |
| `step_key`, `group_key` | 역량 질문의 지표만 써요. 몇 번째 단계(`need_id`)인지와 미리 정의해 둔 그룹의 값(`grouping_id`와 그룹 키). `detail_key`와 따로 있어서 단계와 그룹을 함께 구분할 수 있어요. 나머지 지표에는 비어 있어요 |
| `reading` | `competency_fill_rate`만 써요. `fact_only`(사실만으로 채움)와 `with_assumed`(가정을 포함해 채움)로 두 값을 구분하고, 나머지 지표에는 비어 있어요 |
| `metric`, `window`, `window_start` | 3절의 이름, 구간 길이(`run`, `1m`, `1h`, `1d`)와 시작 시각 |
| `value`, `numerator`, `denominator` | 값. 비율은 분자와 분모도 남겨요(분모가 바뀐 것을 알 수 있게) |
| `buckets` | 분포 지표의 버킷별 건수(고정된 경계) |
| `definition_set` | 이 값을 산출한 정의 세트(`D-142` 같은 번호) |
| `kg_version`, `change_seq` | 확정 버전의 ID와 이 구간이 반영한 마지막 `change_seq`. 없을 수 있어요 |

키는 (`kg_id`, `resource_kind`, `resource_id`, `detail_key`, `step_key`, `group_key`, `reading`, `metric`, `window`, `window_start`)예요. 지표별 종류, 단위, 대상 자원은 지표 목록(`metric_def`)에 제품이 포함해요.

원본은 PostgreSQL에 둬요. 지표, 사용 이력, 컬럼 통계를 PostgreSQL로 감당할 수 없으면 분석용 스토리지(컬럼형)를 포트 뒤에 둬요. 그것은 파생 데이터이고, 오래된 값은 콜드 스토리지로 옮길 수 있어요(ADR-0009). 어느 제품을 쓸지는 구현하는 변경에서 측정해서 정해요.

### 4.2 다운샘플링

구간을 합치는 방법은 종류마다 달라요. `counter`(예: `records_received`)는 합산해요. `gauge`(`connection_ok`)는 마지막 값, 최솟값, 최댓값을 남겨요. `ratio`(`attribute_fill`)는 분자끼리 분모끼리 합산해요. `distribution`(`response_time_ms`)은 버킷별 건수를 합산하고, 분위수는 버킷에서 추정해서 읽어요(결정적이에요). 구간은 `run`과 `1m`을 짧게, `1h`를 중간, `1d`를 길게 둬요(보존 기한은 가정, 16절). 굵은 구간으로 넘기면 세밀한 구간은 삭제해요. 정의 세트가 바뀐 구간은 합치지 않고 `definition_set`마다 따로 둬서 병합 전후를 구분할 수 있게 해요.

### 4.3 카디널리티를 제한하는 규칙

- **객체 하나하나를 레이블로 붙이지 않아요.** 레이블(필드)이 될 수 있는 것은 4.1의 자원 종류와 정의 항목의 `id`, 고정된 `detail_key`뿐이에요.
- 행 수는 (자원 수 × 지표 수 × 세부 구분 수 × 구간 수)로 상한이 정해져요. 자원은 정의 항목이라 객체 수에 비례해서 늘어나지 않아요. 예: 합성 데이터셋 1,000개에 컬럼 20개면 컬럼 통계만 구간마다 수만 행이에요. 그래서 컬럼 통계는 `1m` 없이 `run`이나 `1h`부터 남겨요(가정, 측정해서 정해요).
- 값으로 남기는 상위 목록은 `churn_top`(자원, 구간, 순위 20까지, 객체 참조, 횟수)이에요. 크기가 고정이라 레이블이 아니에요.
- 사용 이력은 지표 테이블이 아니라 일 단위 집계 테이블 `usage_record`(서비스 계정, 타입, 속성, 날짜, 횟수)예요. 계정 수 × 읽은 속성 수로 상한이 정해져요. 10절에서 "누가 읽는가"에 답해요.

### 4.4 통계를 증분으로 갱신하는 방법

실행기는 변경(추가, 수정, 삭제)을 처리하면서 컬럼 통계 상태(`column_stat_state`: 데이터셋, 컬럼, 종류, 상태)를 갱신해요. 전체를 다시 읽지 않아요.

- 건수와 빈 값의 수는 정확히 세요(추가 +1, 삭제 -1).
- 고유 값의 수는 고정된 해시와 고정된 크기로 세는 추정값이고, 가장 흔한 값은 고정된 크기의 빈도 추정값이에요(비율만 지표로 남겨요). 범위는 최솟값과 최댓값이에요. 이 셋은 삭제를 반영할 수 없어서 구간 안에 들어온 레코드로 세고, 전체는 온전한 수집이나 정합성 대조 때 처음부터 다시 세요.
- 추정값도 같은 입력과 같은 순서면 같은 결과예요(해시와 크기가 고정이고, 처리 순서는 `change_seq`로 고정돼요). 학습이나 무작위 표본을 쓰지 않아요.
- **내용이 지표로 유출되지 않게 해요.** 흔한 값 자체와 범위는 행의 내용이라서, 민감 등급이 `open`이 아닌 컬럼은 건수·빈 값·고유 값 추정 개수만 남기고 범위와 흔한 값은 저장하지 않아요. 흔한 값의 실제 값은 9.2절의 샘플 경로로만 권한에 따라 보여 줘요.

## 5. 헬스 상태

### 5.1 상태 6종

| 상태 | 의미 |
|---|---|
| `healthy` | 검사가 모두 통과했고 상위 자원도 정상이에요 |
| `degraded` | 일부가 기준에서 벗어났어요(`warn`, 목표 미달). 사용은 할 수 있어요 |
| `failing` | 사용할 수 없는 상태예요(`fail`, 안전장치로 인한 중단, 인증 실패, 일정 자동 중단) |
| `paused` | 사람이 의도적으로 중단했어요(운영 역할의 일시 정지). 검사는 남기되 상태는 이것이에요 |
| `unknown` | 측정할 신호가 없어요(처음 수집 전, 검사를 실행하지 못함). `healthy`로 해석하지 않아요 |
| `affected_upstream` | 자기 검사는 모두 통과했는데 상위 자원이 `degraded`나 `failing`이에요 |

헬스 상태 행(`health_state` 테이블)의 필드: `resource_kind`, `resource_id`, `health_state`, `own_state`(자기 검사만으로 정한 5종), `cause_refs`(근본 원인의 목록), `since`, `evaluated_at`, `definition_set`, `kg_version`. 헬스 상태를 계산하는 자원은 소스, 데이터셋, 피드, 파이프라인, 타입, 속성, 링크 타입, 역량 질문, KG예요. 역량 질문의 헬스 상태는 충족률 목표에서 나오고, 못 채우는 이유가 소스나 피드이면 계보를 따라 근본 원인이 거기로 올라가요. 서비스 계정은 헬스 상태가 아니라 영향받는 쪽으로만 나와요.

### 5.2 검사의 종류

- **기대 조건**(ADR-0008): 정의로 선언하는 고정 종류예요(비어 있지 않음, 중복 없음, 값의 목록, 범위, 값 타입, 참조, 행 수, 스키마). `fail`이면 `failing`, `warn`이면 `degraded`이고 문제 목록에도 올라요.
- **목표**(6절): 목표 미달 비율이 허용치를 넘으면 `degraded`, 빠르게 악화되면 `failing`.
- **내장 검사**: 정의 없이 항상 실행돼요. 기본값은 가정이에요.

| 내장 검사 | 자원 | 발생 조건 | 상태 |
|---|---|---|---|
| `connection_failed`, `auth_failed` | 소스 | 접속하지 못함, 인증 실패(즉시 차단) | `failing` |
| `schedule_missed` | 소스, 데이터셋 | 일정을 건너뜀 / 일정이 자동으로 중단됨(연속 5회 실패, ADR-0011) | `degraded` / `failing` |
| `no_data` | 데이터셋 | 온전한 수집인데 수집 건수가 0, 또는 스트림이 기대 간격 동안 이벤트가 없음 | `degraded` |
| `schema_changed`, `guard_blocked` | 데이터셋, 파이프라인 | 수신한 스키마가 바뀜, 안전장치가 적용을 중단함(스트림은 `held`) | `failing` |
| `stale`, `lagging` | 소스, 속성 | 주기의 2배를 넘음(ADR-0011), 스트림의 지연이 기대치를 넘음 | `degraded` |
| `unbalanced` | 파이프라인 | 단계별 건수 대조가 일치하지 않음 | `degraded` |

### 5.3 자원 하나의 헬스 상태를 정하는 규칙

위에서부터 처음 해당하는 규칙을 적용해요.

1. 운영 역할이 의도적으로 중단한 소스와 그 파이프라인은 `paused`.
2. 자기 검사 중 `failing`을 반환하는 것이 있으면 `failing`.
3. `degraded`를 반환하는 것이 있으면 `degraded`.
4. 실행해야 할 검사가 하나도 실행되지 않았거나 신호가 없으면 `unknown`.
5. 자기 검사는 모두 통과했는데 계보의 상위에 `failing`이나 `degraded`가 있으면 `affected_upstream`.
6. 그 밖에는 `healthy`.

집계 자원은 하위 자원의 상태도 반영해요. **타입**은 객체를 만드는 피드(`creates_objects`)의 헬스 상태를, **속성**은 그 속성을 소유한 피드의 헬스 상태를 반영해요. 속성을 피드 2개가 제공하는데 우선순위가 첫째인 피드가 이상 상태여도 다음 피드가 값을 대신 제공하므로 `degraded`예요(둘 다 이상 상태면 `failing`). **KG**는 자기 검사와 소스 수를 집계해(`failing` 몇 개, `degraded` 몇 개) 보여 줘요. 소스 하나가 이상 상태라고 KG 전체가 `failing`이 되지는 않아요.

### 5.4 계보를 따른 전파와 근본 원인

전파 경로는 정의의 계보예요(ADR-0014): 소스 → 데이터셋 → 정제 → 피드 → 타입·속성 → 링크 정의 → 파생 그룹 → 읽는 서비스 계정. 컬럼과 속성 단위까지 따라가므로, 컬럼 하나의 스키마가 바뀌면 그 컬럼이 연결된 속성만 이상 상태가 돼요.

- **하위로 전파돼요.** 자기 검사가 기준을 벗어난 자원에서 출발해 하위 자원(후손)에게 `affected_upstream`과 `cause_refs`를 붙여요.
- **상위로 거슬러 올라가요(근본 원인).** 기준을 벗어난 자원이 의존하는 상위에도 기준을 벗어난 자원이 있으면, 더 위에 없는 자원까지 올라가 그것을 근본 원인으로 적어요. 근본 원인이 여럿이면 모두 적어요.
- **원인이 상위에 있는 이상은 자기 알림을 만들지 않고 근본 원인의 알림에 묶여요.** 신선도·채움·수집량 목표를 어긴 속성의 피드가 이상 상태인 소스에 의존하는 경우가 그래요.

가상의 예시예요. 스위치 재고 소스 `switch_inventory`의 인증이 만료돼요.

```
소스 switch_inventory       auth_failed → failing   ◀── 근본 원인(마지막 온전한 수집 27시간 전)
 ├ 데이터셋 switch_devices ─ 피드 feed_devices ─────▶ 타입 NetworkDevice        affected_upstream
 └ 데이터셋 switch_ports ─┬─ 피드 feed_ports ───────▶ 타입 Interface            affected_upstream
                          └─ 피드 feed_lag_links ───▶ 파생 Lag 그룹              affected_upstream
                                      └──────────────▶ 읽는 계정 acct_capacity_report, acct_netops_agent
```

소스는 인증 실패로 즉시 `failing`이 되고 일정이 중단돼요. 데이터셋 2개, 피드 3개, `NetworkDevice`·`Interface`, `Lag` 그룹이 `affected_upstream`이에요. 몇 주기 뒤 `Interface`의 `oper_status`(`dynamic`)가 신선도 목표를 지키지 못해 자기 검사로도 `degraded`가 되지만, 원인이 상위에 있어서 알림은 소스의 알림 하나에 묶여요. 계정 2개는 10절의 "누가 읽는가"로 나오고, 알림의 수신자는 소스의 담당자예요. 반대로 `NetworkDevice`의 값이 오래된 이유를 질의하면(11절) 소스의 인증 실패 하나가 나와요.

## 6. 목표

목표는 정의의 항목이에요(버전이 있고 제안과 승인을 거쳐요). 필드: `objective_id`(바뀌지 않는 `id`), `target`(대상 자원: 피드, 타입, 속성, 역량 질문), `kind`(`freshness` 정해진 시간 이내 / `fill_rate` 채워진 비율 이상 / `validity` 위반 비율 이하 / `volume` 수집량이 최소~최대 범위 안 / `competency_fill` 충족률 이상. 프락시움 자신의 목표를 위해 `latency` 응답 시간, `lag` 지연, `on_time_ratio` 제때 실행 비율, `error_ratio` 오류 비율을 추가해요. ADR-0013, ADR-0017), `threshold`(종류에 맞는 값), `period`(목표 미달 비율을 집계하는 기간, 기본 28일), `allowed_miss`(기간 중 미달이 허용되는 비율), `severity`.

**목표 미달 비율의 계산.** 판정 간격마다(배치는 실행마다, 스트림과 신선도는 기본 5분, 가정) 목표를 "달성 / 미달 / 알 수 없음"으로 판정해요. 미달 비율 = 미달 횟수 ÷ (달성 횟수 + 미달 횟수). 알 수 없음은 분모에서 빼고 `unknown_share`로 따로 보여 줘요(알 수 없음이 많으면 목표는 `unknown`). 남은 허용치 = `allowed_miss` − 미달 비율.

**빠른 악화의 판정.** 소진율 = (짧은 창의 미달 비율) ÷ `allowed_miss`예요. 짧은 창(기본 1시간)과 긴 창(기본 6시간)의 소진율이 둘 다 기준(기본 6, 가정)을 넘을 때만 "빠른 악화"예요. 일시적인 튐과 느린 악화를 모두 걸러 내려는 거예요. 이때 헬스 상태는 `failing`이고, 미달 비율만 넘었으면 `degraded`예요. 소진율과 「빠른 악화」의 구현은 클로즈드 베타예요(15절).

**속성의 변경 빈도에 따른 기본값.** 표준 모델이 속성마다 적은 `change_class`(ADR-0007)가 기본 목표를 정해요. 목표를 적지 않아도 아래 기본값이 적용돼요. 값은 가정이에요.

| `change_class` | 신선도 | 온전함 | 변경 빈도 |
|---|---|---|---|
| `static` | 목표 없음(바뀌지 않는 값은 오래돼도 괜찮아요) | `required`면 99% 이상 | 바뀐 비율이 아주 낮아야 하고, 넘으면 "식별이 불안정해요" |
| `slow` | 피드 주기의 2배 이내 | `required`면 95% 이상 | 목표 없음 |
| `dynamic` | 피드 주기의 2배(스트림은 지연 1분 이내) | 목표 없음 | 플래핑(`flapping_count`)을 확인해요 |

## 7. 이상 탐지

방법은 정해진 통계 하나예요. 학습 모델을 쓰지 않아서 같은 입력이면 같은 판정이 나오고 이유를 설명할 수 있어요.

- **대상**: `records_received`, `objects_created`·`objects_retired`, `links_created`·`links_removed`, `change_rate`, `run_duration_s`, `column_null_ratio`, `column_distinct_est`, `column_top_share`.
- **평소 값(기준선)**: 같은 요일, 같은 시간대의 과거 값 여러 개(기본 4주, 가정)의 중앙값과 산포(중앙값에서의 절대 편차의 중앙값).
- **점수** = |현재 값 − 중앙값| ÷ max(산포 × 1.4826, 하한). 하한은 0으로 나누지 않게 하는 최소 폭(중앙값의 5%와 1건 중 큰 것, 가정)이에요.
- **판정**: 점수가 임계값(경고 4, 심각 6, 가정) 이상이고 차이가 최소 크기 이상일 때만 "이상 탐지"예요(작은 수에서 생기는 오탐을 막으려는 거예요). 현재 값, 중앙값, 산포, 점수, 기준선 표본 수를 함께 남겨서 "왜"를 설명해요.
- **처음이라 과거 값이 없을 때**: 기준선 표본이 최소 개수(기본 3, 가정)보다 적으면 판정은 `insufficient_history`이고 헬스 상태에 영향이 없어요. 응답에는 `insufficient_history`로 나오고 화면이 "기준선을 쌓는 중"이라고 표시해요.
- **정의나 일정이 바뀐 직후**의 구간은 기준선을 끊지 않고 판정에 `definition_changed`를 붙여요. 알림 메시지에 "`D-142` 병합 뒤"가 함께 나와요.
- **임계값의 기본값은 가정이에요.** 규칙마다 수정할 수 있고, 클로즈드 베타에서 오탐과 미탐을 집계해 조정해요(구현도 클로즈드 베타. 15절).

## 8. 알림

### 8.1 규칙

규칙 종류는 고정된 9종이에요: `threshold`(임계값), `anomaly`(이상 탐지), `no_data`, `schedule_missed`, `schema_changed`, `expectation_violated`, `lagging`, `objective_burning`(목표가 빠르게 악화), `health_changed`. 필드: `rule_id`, `kind`, `target`(자원이나 조건), `condition`(종류에 맞는 필드), `severity`(`info` / `warning` / `critical`), `recipients`(비워 두면 자원의 담당자(ADR-0012). 담당자가 없는 자원과 제품 자신은 `admin`), `for`(이 시간 동안 지속돼야 알려요), `group_by`(기본 `root_cause`), `working_hours`(수신자의 근무 시간대. 밖이면 `critical`만 바로 보내고 나머지는 근무 시간대가 시작될 때 한 번에 보내요), `escalation`(확인 기한과 다음 담당자). **규칙도 정의의 항목이에요**(버전, 브랜치, 제안을 거쳐요. ADR-0014). 제품이 기본 규칙을 포함하고, 규칙 수정은 그 자원(소스나 객체 타입)을 범위로 가진 `editor`가 제안하고 `approver`가 승인해요. 알림을 확인하고, 스누즈하고, 에스컬레이션하는 것은 정의가 아니라 운영 업무라서 `operator`가 해요. `paused` 자원에는 `no_data`와 `schedule_missed`를 적용하지 않아요.

### 8.2 근본 원인으로 묶기

알림 하나(`alert`)는 `group_key` = (근본 원인 자원, 근본 원인 검사)마다 하나예요. 소스 하나에 장애가 나도 타입 100개의 알림이 가지 않아요. 알림에는 영향받는 자원의 **수와 종류별 개수**가 붙고, 자세한 목록은 열면 10절의 계산으로 나와요. 근본 원인이 바뀌거나 심각도가 오르면 같은 알림이 갱신되어 다시 알려요.

### 8.3 상태 전이

```
open ──확인──▶ acknowledged ──스누즈(시간)──▶ snoozed ──시간 경과, 조건 지속──▶ open
 └─기한 안에 확인 없음─▶ escalated(다음 담당자, 새 기한)
(어느 상태에서든) 조건 해소(연속 3회, 가정) ─▶ resolved ─같은 근본 원인이 다시 발생─▶ open(같은 `issue_id`, 재발)
```

확인, 스누즈, 에스컬레이션은 자원의 범위를 가진 `operator`가 해요(에스컬레이션은 클로즈드 베타). 확인하지 않은 알림은 `escalation`의 다음 담당자에게 가고, 끝까지 없으면 `admin`이에요.

### 8.4 알림은 문제 목록의 항목이에요

수신함은 하나예요. 알림은 문제 종류 `data_alert`의 항목(ADR-0011의 `issue`)이 되고 `cause_key`는 `group_key`예요. 문제의 상태 3종과는 이렇게 대응해요: `open` ↔ `open`, `acknowledged`·`snoozed`·`escalated` ↔ `in_progress`, `resolved` ↔ `resolved`. 해결 절차는 문제 목록과 같아서, 원인이 규칙(기대 조건, 목표, 매핑)에 있으면 브랜치를 열어 수정해요. 알림이 KG를 직접 수정하지 않아요.

### 8.5 발송 경로

발송 경로는 포트 뒤의 어댑터예요(메신저, 메일, 변경 알림 경로). 포트의 입력은 알림 엔벨로프(`alert_id`, 심각도, 제목, 근본 원인, 영향 건수, 수신자, 확인용 링크)이고 출력은 전달됨 / 실패 / 재시도예요. 메시지는 템플릿에서 만들어서 행의 내용과 시크릿이 없어요. 전달에 실패하면 다음 경로로 전환하고 `notify_delivery_failures`로 집계해요(13절).

## 9. 실행 소스 탐색과 타임라인

### 9.1 실행 이력

동기화 1회(`sync_run`, ADR-0011)와 스트림의 구간 1개가 이력 하나예요. 단계마다 행(`run_stage`)을 하나 추가해요.

| 필드 | 의미 |
|---|---|
| `run_id`, `stage`, `attempt` | 실행, 단계, 리스 번호 |
| `started_at`, `ended_at`, `status` | 시각과 결과 |
| `in_count`, `out_count`, `dropped_count` | 입력·출력·제외 건수. 입력 = 출력 + 제외가 성립해야 해요 |
| `dropped_by_reason` | 이유별 제외 건수(단계마다 고정 목록: `filtered_by_rule`, `invalid_value`, `quarantined`, `duplicate`, `unreadable`, `excluded_by_exception` 등) |
| `capture_range` | 사용한 원본 레코드의 구간(스트림은 `change_seq`의 처음~끝) |
| `definition_set`, `executor_version` | 사용한 정의 세트, 실행기의 의미 버전 |
| `diff_summary`, `guard_verdict`, `trace_id` | 타입별 추가·수정·폐기(retired) 건수, 안전장치의 판정과 이유, 트레이스 ID |

한 동기화의 건수 대조는 원본 레코드 하나가 최종적으로 4종(사용, 규칙이 걸러 냄, 문제, 미사용) 중 하나가 되어 합이 수집한 건수와 같아야 해요(ADR-0008).

### 9.2 제외·격리된 레코드의 샘플과 권한

샘플은 `rejected_sample`(`run_id`, 단계, 이유, 원본 레코드 참조)로 이유마다 몇 건(기본 20, 가정)만 남겨요. 내용은 복사하지 않고 읽을 때 원본 레코드에서 가져와요. 그러면 보존 기한이 지난 내용은 "삭제됨"으로 보여요. 샘플은 행의 내용이라서 일반적인 읽기와 달라요. 그 소스를 범위로 가진 `operator`·`editor`·`admin`만 읽고, 컬럼마다 민감 등급 한도에 따라 "마스킹됨"으로 표시돼요. 샘플은 사람이 사용하는 HTTP 경로에서만 나오고 MCP와 개방형 형식 내보내기에는 나가지 않아요.

### 9.3 트레이스 ID와 리플레이

- 동기화 1회(또는 스트림의 구간 1개)가 트레이스 하나예요. 단계와 소스 요청이 각각 스팬(span)이고, 같은 `trace_id`가 로그와 실행 이력에 남아요. 레이블과 건수만 있어요.
- **리플레이**는 수집해 둔 원본 레코드의 해당 구간을 같은 정의 세트와 같은 실행기 버전으로 뒤쪽 단계(정제부터 차이 계산까지)만 다시 실행해 단계별 건수와 제외된 레코드를 확인하는 드라이 런이에요. 소스에 다시 접속하지 않고 KG를 바꾸지 않아요. 결정성 덕에 원래 결과와 같은지 비교할 수 있고, 브랜치의 정의로 실행하면 "수정하면 이 레코드들이 정상 처리되는가"를 확인할 수 있어요. 운영 역할이 해요.

### 9.4 자원의 타임라인

`timeline_event`의 필드: `at`, `kg_version`/`change_seq`, `resource_kind`, `resource_id`, `event_kind`, `severity`, `ref`(실행, 알림, 제안, `D-N`), `summary`(템플릿으로 만든 짧은 문장), `definition_set`. 이벤트의 종류는 고정 목록이에요.

- 실행: `sync_succeeded`, `sync_failed`, `sync_waiting_confirmation`, `stream_held`, `stream_released`, `schedule_paused`, `schedule_resumed`, `schema_changed`, `guard_blocked`, `guard_confirmed`
- 헬스 상태와 알림: `health_changed`, `alert_opened`, `alert_acknowledged`, `alert_snoozed`, `alert_escalated`, `alert_resolved`
- 정의와 KG: `proposal_opened`, `definition_merged`, `definition_reverted`, `emergency_revert`, `type_status_changed`, `kg_version_sealed`, `serving_pinned`, `serving_unpinned`

자원의 타임라인은 그 자원의 이벤트에 계보 상·하위 자원의 이벤트를 선택해서 합칠 수 있어요. 지표 선을 겹쳐 놓으면 "`D-142`가 들어간 뒤 `Interface`의 객체 수가 줄었다"를 눈으로 확인할 수 있어요.

## 10. 데이터 인시던트의 영향

피드나 소스가 이상 상태일 때 무엇이 영향받는지를 두 가지로 응답해요. (1) **정의의 계보**에서 하위 자원(후손)을 모아요: 데이터셋, 피드, 컬럼 단위로 연결된 타입과 속성, 링크 정의, 파생 그룹, 저장해 둔 범위. (2) **사용 이력**(`usage_record`)에서 그 타입·속성을 최근 N일(기본 30일, 가정) 안에 읽은 서비스 계정을 사용량이 많은 순으로 모아요. 같은 계산이 수정 전의 "무엇이 영향받는가"(ADR-0014의 정의의 계보)와 같은 경로예요. 응답은 "이 소스가 이상 상태라서 타입 2개, 속성 11개, 파생 그룹 1개, 계정 2개가 영향받아요"처럼 종류별 건수를 먼저 주고, 열면 목록이에요.

**영향 범위 질의 응답에 붙는 표시.** `impact`, `exposure`, `paths`의 응답에 사용된 객체 타입, 링크 타입, 속성(채널의 입력)의 피드 중에 `failing`·`degraded`·`stale`이 있으면 응답에 `data_health_notes`가 붙어요. 예: "이 응답에 사용된 링크 타입 `MEMBER_OF`의 피드 `feed_lag_links`가 소스 `switch_inventory`의 인증 실패로 27시간 동안 갱신되지 않았어요". 표시는 타입·링크 타입 단위예요. 어느 객체가 오래됐는지까지는 알 수 없어요(값마다 출처를 저장하지 않아서예요, 17절). 관측을 사용한 응답(`as_observed`)에는 관측 시점의 경과 시간도 함께 붙어요.

## 11. 질의 방법

`health`와 `quality`는 사전 정의 질의(ADR-0010)이고 HTTP API와 읽기 전용 MCP에 똑같이 제공돼요.

| 질의 | 입력 | 출력 |
|---|---|---|
| `health` | `resource`(`{kind, id}`) 또는 `scope`(자원 종류, 상태 목록, 담당자, 소스), `include`(`checks`, `cause`, `downstream`, `impact`, `timeline`), `as_of`(현재가 기본, 또는 확정한 KG 버전), `limit`, `cursor` | `health_state`, `own_state`, `since`, `checks`(`{check, kind, state, observed, threshold, since}`), `cause`(근본 원인 자원과 그 검사, 거기까지의 경로), `affected`(종류별 개수와 목록, 잘렸는지), `readers`(읽는 계정과 마지막으로 읽은 시각), `timeline` |
| `quality` | `resource`나 `scope`, `metrics`(이름 목록), 기간(`from`, `to`) 또는 `kg_versions`, `window`, `compare`(`previous_version` / `same_weekday`), `include`(`objectives`, `anomalies`) | 지표 시계열 `{resource, metric, detail_key, points:[{at, value, numerator, denominator, kg_version}]}`, 목표의 `{miss_ratio, budget_left, state}`, 이상 탐지의 `{score, median, spread}` |

**응답 엔벨로프에 붙는 헬스 힌트.** 모든 응답 엔벨로프(KG 버전, 신선도, 근거 등급, 잘렸는지, ADR-0010)에 `health_hint`가 붙어요: `has_unhealthy_inputs`, `worst_state`, `total`, 그리고 상세(`full`)를 고르면 `items`(자원, 상태, 근본 원인)를 상한 개수까지 포함해요. 간략(`brief`)을 고르면 앞의 3개만 가요. 힌트는 읽을 수 있는 범위만 보여 줘요. 수를 반환하는 모든 필드는 숨겨진 것을 뺀 수예요. 읽을 수 없는 것의 수는 범위가 전체가 아닌 주체에게 정확한 수 대신 있음/없음만 줘요(설정으로 수를 공개할 수 있어요. ADR-0012). 경로는 KG에 속해서 `/v1/kgs/{kg}/health`예요(`main`이 기본).

**MCP 사용 예.** 에이전트가 "이 스위치에 장애가 나면 어디까지 전파되는가, 이 결과를 믿어도 되는가"를 질의해요.

```
impact(objects=[sw-0417], view=as_observed)
  → 응답 … , health_hint: {has_unhealthy_inputs: true, worst_state: "affected_upstream",
      total: 3, items: [{resource: "Interface", state: "affected_upstream", cause: "switch_inventory"}]}
health(resource={kind: "object_type", id: "Interface"}, include=["cause", "readers"])
  → health_state: "affected_upstream", cause: [{resource: "switch_inventory", check: "auth_failed", since: "27h"}]
```

에이전트는 응답을 "오래된 구성 기준"이라고 표시해서 넘기고 소스의 담당자에게 알리는 방법을 선택해요. MCP 응답은 크기에 상한이 있고 오류가 다음에 할 일을 알려 줘요(ADR-0010). 두 질의 모두 서비스 계정별 호출 한도가 적용돼요.

## 12. 내보내기

- **개방형 형식으로 지표·로그·트레이스를 내보내요.** 조직이 이미 가진 관측 도구가 가져가요. 개방형 관측 형식(OpenTelemetry가 정한 지표·로그·트레이스의 3가지 신호와 전송 규약)을 쓰고 특정 도구에 종속되지 않아요. 지표는 제품 안과 같은 이름과 레이블(자원 종류, `resource_id`, `detail_key`)을 써요. 컬럼과 속성 단위의 지표는 카디널리티 때문에 기본으로 꺼 두고 켠 것만 내보내요. 트레이스는 동기화 1회가 하나이고 단계가 스팬이에요.
- **데이터 헬스 상태의 이벤트는 변경 알림 경로(ADR-0010)로도 나가요.** 같은 경로에서 이벤트의 `kind`로 KG의 변경과 구분해요: `health_changed`, `alert_opened`, `alert_resolved`, `guard_blocked`, `stream_held`. 가져가기(pull) 방식이 기본이고 푸시 방식은 나중에 제공해요.
- **내용과 시크릿이 없어요.** 내보내는 것은 지표 목록과 이벤트 목록에 있는 필드뿐이고 자유 서식 텍스트 필드가 없어요. 로그에는 레이블과 건수만 남기고(ADR-0008) 샘플은 9.2절의 경로로만 나가요. 이 성질은 테스트가 보장해요(내보내는 모든 필드가 목록에 있는지).

## 13. 제품 자신의 헬스 상태와 하트비트

제품 컴포넌트(`component`)도 같은 구조(지표 테이블, 헬스 상태, 알림)로 측정해요. 수신자는 `admin`이에요. 지표: `worker_alive`와 `lease_takeovers`(워커가 정상 동작 중인가, 장애가 난 워커의 작업을 이어받은 횟수), `queue_depth`와 `oldest_job_age_s`(대기 중인 작업 수, 가장 오래된 작업의 경과 시간), `db_unavailable_count`와 `db_replication_lag_s`(DB에 접속하지 못한 횟수, 복제 지연), `engine_memory_bytes`와 `engine_loaded_version_age_s`와 `projection_lag_seq`(질의 엔진의 메모리, 로드된 버전의 경과 시간, 반영하지 못한 `change_seq`의 수), `api_error_ratio`, `notify_delivery_failures`(알림 전달에 실패한 횟수).

**알림 시스템 자체의 장애를 감지하는 방법.** 알림이 오지 않으면 문제가 없어서인지 알림 시스템에 장애가 나서인지 구분할 수 없어요. 그래서 (1) 발송 경로마다 주기적으로 하트비트(`heartbeat`)를 어댑터 끝까지 보내고, (2) 마지막 하트비트의 경과 시간(`alert_heartbeat_age_s`)과 헬스 상태 계산이 마지막으로 실행된 뒤의 경과 시간(`health_evaluator_age_s`)을 개방형 형식으로 내보내요. 조직의 외부 관측 도구가 이 경과 시간이 길어지는 것을 보고 제품과 별개로 알려요. 스토리지가 중단돼도 질의 엔진은 응답하므로(ADR-0011) 엔진의 지표는 엔진 자신이 개방형 형식으로 계속 내보내요.

## 14. 정의 변경과 타입 관리 관측

- `proposals_open`, `proposal_oldest_open_age_s`: 열린 제안의 수와 가장 오래된 것의 나이(KG).
- `merge_check_failures`: 병합 검사의 실패 수. `detail_key`가 검사(유효성, 정의의 테스트, 드라이 런, 안전장치)예요(KG).
- `reverts`, `emergency_reverts`, `post_review_overdue`: 리버트, 긴급 리버트, 사후 검토 기한을 넘긴 건수. `breaking_changes`: 호환성을 깨는 변경의 수(KG).
- `retired_type_in_use`: 폐기(retired)됐는데 매핑이나 객체가 아직 사용하는 타입(타입). `experimental_type_age_days`: `experimental` 상태로 오래 머문 타입의 경과 일수(타입).
- `similar_type_pairs`: 이름·속성·식별 키가 겹쳐 비슷해 보이는 타입 쌍의 수. 비슷한 타입 찾기(ADR-0007)와 같은 계산이에요(KG).
- `serving_pin_age_s`: 질의 대상을 이전 버전에 고정(`serving_pin`)해 둔 시간(KG).

`unread_days`(3절)와 함께 모델 관리 역할(`model_steward`)에게 주기적으로 보여 줘요. 병합 직전·직후의 지표를 `definition_set`으로 비교해 "정의 변경의 효과"를 확인해요.

## 15. 알파의 범위

화면은 다른 리포지토리의 일이고(ADR-0016), 이 리포지토리의 알파는 모든 것이 API와 CLI로 되는 거예요. 알파 2(넓히기)에서 API가 제공하는 조회: 자원의 헬스 상태 목록(상태, 자원 종류, 담당자로 필터링) / 자원 하나의 헬스 상태(검사, 근본 원인, 하위로 전파된 것, 타임라인) / 실행 목록과 상세(단계별 건수, 샘플) / 타입의 피드 목록(헬스 상태 필드 포함) / 문제 목록(알림 포함, 확인·스누즈). 알림 규칙과 목표의 편집은 정의의 변경이라 제안을 거쳐요. 충족률은 `competency` 질의(ADR-0015)가 줘요. 계보 그림과 지표 차트는 프런트엔드 리포지토리가 클로즈드 베타 때 설계해요.

**계약만 알파에 두고 구현은 클로즈드 베타로 미루는 것**: 목표의 소진율과 「빠른 악화」(6절), 이상 탐지의 통계(7절), 알림의 에스컬레이션과 나머지 상태 전이(8.3절). 필드, 경로, 코드의 목록은 알파부터 있고 값은 `unknown`이거나 비어 있어요. 이것들의 수치(임계값, 창)는 클로즈드 베타에서 오탐과 미탐을 집계해 정해요.

## 17. 알려진 한계

- 헬스 상태는 **수집한 데이터**의 헬스 상태예요. 소스가 틀린 값을 온전하게 제공하면 기대 조건으로 선언한 만큼만 잡아내요. 완전성 선언이 없는 곳은 "누락됐다"를 알 수 없고 "모른다"로 처리해요(ADR-0011).
- 응답에 붙는 헬스 상태 표시는 타입·링크 타입 단위예요. 값마다 출처를 저장하지 않기 때문이에요(ADR-0008).
- 평소 값은 같은 요일·시간대만 봐요. 월말, 연휴, 분기말의 패턴은 반영하지 못해서 그때는 오탐이 나요(스누즈로 처리해요).
- 고유 값·흔한 값·범위는 삭제를 반영할 수 없어서 구간 기준이에요(4.4절).
- 이중화 현황은 질의 엔진의 계산에 의존해서, 엔진의 지표가 워커에 도달하는 경로가 차단되면 그동안 값이 비어요.
- 스트리밍의 처리량과 지연은 조사에서 측정하지 못했어요. 지표의 이름과 의미는 정했고 기대 값은 측정해서 정해요. 액션 실행을 측정하는 부분은 비어 있어요(E2E 프로세스 때).

## 18. 미결 사항

- 헬스 상태 이력과 해결된 알림의 보존 기한(지표는 기본값 표가 정해요).
- 헬스 상태 계산과 집계를 맡는 워커의 일정 간격과 부하 상한. 계보 전파를 변경마다 증분으로 다시 계산할지, 일정마다 전부 다시 계산할지.
- 첫 번째 발송 경로의 어댑터 종류.
