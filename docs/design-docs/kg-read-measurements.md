# KG 읽기의 측정

개발용 적재기(`adapter.devload`)가 생성기의 정답을 메모리 저장소(`adapter.memstore`)에 넣는 데 드는 시간과 메모리, 그리고 그 위에서 첫 셋의 질의(`find`, `get`, `neighbors`)가 걸리는 시간이에요. ADR-0026이 "느리다: 스캔이다. 측정은 4부에 있다"고 미뤄 둔 몫이에요(ADR-0027).

**이 숫자는 모두 가정 아래의 것이에요.** 한 대의 기계에서 한 번씩 측정했고, 세계는 생성기가 지어낸 합성 모양이고, 기본 인자다. 운영 저장소(PostgreSQL)와 프로젝션이 서면 다르고, 현실의 데이터센터와도 다르다. 영향 범위의 목표(1초, 수 초)와는 상관이 없다(질의 엔진 단계에서 따로 측정한다).

## 조건

| 항목 | 값 |
|---|---|
| 기계 | 가상 기계. Intel Xeon 2.30GHz 2코어, 메모리 8GB, Linux 6.18, Go 1.24.7 |
| 저장소 | `adapter.memstore`(기준 구현, 모든 변경 번호의 행을 쥔다). 질의는 `core.query`를 프로세스 안에서 바로 부른다(HTTP를 지나지 않는다) |
| 읽기 권한 필터링 | `query.AllowAll()`. 가려진 객체가 없다 |
| 적재 | 한 묶음에 5,000개(객체 묶음 다음에 링크 묶음), 단일 리스자, 시계는 실제 시계 |
| 세계 | 시드 7. 작은 것은 `-scale 500`, 큰 것은 `-scale 280000`(객체와 링크를 합친 수에 맞추므로 객체는 그 3분의 1쯤) |
| 되풀이 | 적재는 3번의 평균, 질의는 30번의 평균. 재는 동안 다른 일을 돌리지 않았다 |

| 세계 | 객체 | 링크 | `volatile` 값 | 식별자 | 정답 파일 |
|---|---|---|---|---|---|
| 작은 것 | 522 | 932 | 865 | 237 | 0.37MB |
| 큰 것 | 100,150 | 178,973 | 174,281 | 64,645 | 72.5MB |

## 적재

| 세계 | 시간(평균) | 메모리 | 변경 배치 |
|---|---|---|---|
| 작은 것 | 55ms | 프로세스 최대 상주 약 32MB | 2 |
| 큰 것 | 15.3초(벤치마크), 16.5초(명령줄, 세 번 16.5~16.8초) | 프로세스 최대 상주 약 1.5~1.6GB, 적재가 끝난 저장소가 쥔 힙은 약 0.9GiB | 57 |

- 명령줄은 `praxium dev load-truth <파일>`이다. 파일을 읽어 해석하는 시간과 정답 전체를 메모리에 두는 몫이 든다(적재기는 키를 만들려고 링크 전체를 먼저 읽는다). 벤치마크는 파일을 메모리에서 읽는다.
- 객체당 약 9KB 안팎(링크와 `volatile` 값을 포함해 저장소가 쥔 것. 벤치마크의 힙에는 정답 바이트도 든다)이다. 객체 3천만 개의 규모는 이 저장소로 못 한다(운영 저장소의 일, TD-0011).
- 첫 측정은 이보다 한참 느리고 컸다. 3만 5천 객체의 세계에서 24초와 상주 3.0GB였다. 이유는 셋이었고 모두 고쳤다: 링크마다 등록부가 링크 타입 전체를 복사하던 것(적용기와 적재기에 기억을 두었다), 값마다 JSON 파서를 새로 만들던 것, 메모리 저장소의 식별자 찾기가 전부를 훑던 것(색인을 두었다). 큰 세계는 앞의 둘을 고친 뒤에도 식별자 색인이 없어서 44초였다.

## 질의

작은 세계와 큰 세계에서 한 번 부르는 데 걸린 평균이다. `get`은 `attributes`, `identifiers`, `link_counts`를 포함한다. `find`는 쪽 50개(`shape: items`)이고, `neighbors`는 한 걸음, 쪽 50개다.

| 질의 | 작은 세계 | 큰 세계 | 이유 |
|---|---|---|---|
| `find`, 타입(`PhysicalServer`) | 0.88ms | 307ms | 스냅숏 전체를 훑는다. 객체 수에 비례한다 |
| `find`, 글(`rack-0-0-0`) | 1.4ms | 540ms | 모든 객체의 읽을 수 있는 문자열 속성을 훑는다 |
| `get`, 랙 하나 | 0.06ms | 0.06ms | 객체 ID로 바로 간다. 크기와 상관없다 |
| `neighbors`, 랙(링크 16~19개) | 0.06ms | 0.08ms | 객체의 링크 색인으로 간다 |
| `neighbors`, 잎(팬, 링크 2개) | 0.014ms | 0.024ms | 같다 |
| `neighbors`, 허브(가상화 관리자, 링크 45개 / 12,538개) | 0.14ms | 114ms | 링크 수에 비례한다. 묶음(`groups`)을 세려고 객체의 링크를 모두 읽는다 |

읽을 수 있는 것:
- `get`과 평범한 `neighbors`는 크기를 타지 않는다. 화면 한 장에 필요한 만큼은 아무 문제가 없다.
- `find`는 객체 수에 선형이다(3백만 객체면 약 10초). 인덱스가 없어서이고 기준 구현의 몫이다(ADR-0026). 질의 엔진 단계가 색인을 가진다.
- 허브의 `neighbors`는 링크 수에 선형이다. 허브에 쪽을 넘기는 것은 항목뿐이고 묶음의 수는 매번 전부를 센다.

## 다시 재는 법

```
cd backend
go test ./internal/readcheck -run '^$' -bench Load    -benchtime 3x  -benchmem
go test ./internal/readcheck -run '^$' -bench Queries -benchtime 30x -benchmem
go run ./cmd/praxium worldgen -scale 280000 -seed 7 -out /tmp/large && go run ./cmd/praxium dev load-truth /tmp/large/truth.jsonl
```

벤치마크는 `go test`의 기본 실행에 들지 않는다. 큰 세계를 짓는 데 한 번에 약 20초, 질의 벤치마크는 합쳐 1분쯤 든다.
