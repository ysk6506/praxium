# KG 읽기 성능 측정

개발용 적재기(`adapter.devload`)가 생성기의 정답을 메모리 스토리지(`adapter.memstore`)에 적재하는 데 드는 시간과 메모리, 그리고 그 위에서 첫 3개 질의(`find`, `get`, `neighbors`)의 소요 시간이에요. ADR-0026이 "느리다: 스캔이다. 측정은 4부에 있다"며 미뤄 둔 측정이에요(ADR-0027).

**이 숫자는 모두 특정 가정 아래의 값이에요.** 기계 한 대에서 한 번씩 측정했고, 세계는 생성기가 만든 합성 데이터이며, 인자는 기본값이에요. 운영 스토리지(PostgreSQL)와 프로젝션이 도입되면 결과가 달라지고, 현실의 데이터센터와도 달라요. 영향 범위의 목표(1초, 수 초)와는 무관해요(질의 엔진 단계에서 따로 측정해요).

## 조건

| 항목 | 값 |
|---|---|
| 기계 | 가상 머신. Intel Xeon 2.30GHz 2코어, 메모리 8GB, Linux 6.18, Go 1.24.7 |
| 스토리지 | `adapter.memstore`(기준 구현, 모든 변경 번호의 행을 보유해요). 질의는 `core.query`를 프로세스 안에서 직접 호출해요(HTTP를 거치지 않아요) |
| 읽기 권한 필터링 | `query.AllowAll()`. 숨겨진 객체가 없어요 |
| 적재 | 배치당 5,000개(객체 배치 다음에 링크 배치), 단일 리스 보유자, 시계는 실제 시계 |
| 세계 | 시드 7. 작은 세계는 `-scale 500`, 큰 세계는 `-scale 280000`(객체와 링크를 합친 수에 맞추므로 객체는 그 3분의 1 정도) |
| 반복 | 적재는 3회 평균, 질의는 30회 평균. 측정하는 동안 다른 작업을 실행하지 않았어요 |

| 세계 | 객체 | 링크 | `volatile` 값 | 식별자 | 정답 파일 |
|---|---|---|---|---|---|
| 작은 세계 | 522 | 932 | 865 | 237 | 0.37MB |
| 큰 세계 | 100,150 | 178,973 | 174,281 | 64,645 | 72.5MB |

## 적재

| 세계 | 시간(평균) | 메모리 | 변경 배치 |
|---|---|---|---|
| 작은 세계 | 55ms | 프로세스 최대 상주 약 32MB | 2 |
| 큰 세계 | 15.3초(벤치마크), 16.5초(명령줄, 3회 16.5~16.8초) | 프로세스 최대 상주 약 1.5~1.6GB, 적재가 끝난 스토리지가 보유한 힙은 약 0.9GiB | 57 |

- 명령줄은 `praxium dev load-truth <파일>`이에요. 파일을 읽어 파싱하는 시간과 정답 전체를 메모리에 올리는 비용이 포함돼요(적재기는 키를 만들려고 링크 전체를 먼저 읽어요). 벤치마크는 파일을 메모리에서 읽어요.
- 객체당 약 9KB 안팎이에요(링크와 `volatile` 값을 포함해 스토리지가 보유한 크기이고, 벤치마크의 힙에는 정답 바이트도 포함돼요). 객체 3천만 개 규모는 이 스토리지로 처리할 수 없어요(운영 스토리지의 과제, TD-0011).
- 첫 측정은 이보다 훨씬 느리고 메모리도 많이 썼어요. 객체 3만 5천 개의 세계에서 24초와 상주 3.0GB였어요. 원인은 3가지였고 모두 수정했어요. 링크마다 등록부가 링크 타입 전체를 복사하던 것(적용기와 적재기에 캐시를 두었어요), 값마다 JSON 파서를 새로 만들던 것, 메모리 스토리지의 식별자 조회가 전체를 순회하던 것(색인을 두었어요)이에요. 큰 세계는 앞의 두 가지를 수정한 뒤에도 식별자 색인이 없어서 44초였어요.

## 질의

작은 세계와 큰 세계에서 1회 호출에 걸린 평균 시간이에요. `get`은 `attributes`, `identifiers`, `link_counts`를 포함해요. `find`는 페이지당 50개(`shape: items`)이고, `neighbors`는 1홉, 페이지당 50개예요.

| 질의 | 작은 세계 | 큰 세계 | 원인 |
|---|---|---|---|
| `find`, 타입(`PhysicalServer`) | 0.88ms | 307ms | 스냅숏 전체를 순회해요. 객체 수에 비례해요 |
| `find`, 텍스트(`rack-0-0-0`) | 1.4ms | 540ms | 모든 객체의 읽을 수 있는 문자열 속성을 순회해요 |
| `get`, 랙 하나 | 0.06ms | 0.06ms | 객체 ID로 바로 조회해요. 크기와 무관해요 |
| `neighbors`, 랙(링크 16~19개) | 0.06ms | 0.08ms | 객체의 링크 색인으로 조회해요 |
| `neighbors`, 잎(팬, 링크 2개) | 0.014ms | 0.024ms | 위와 같아요 |
| `neighbors`, 허브(가상화 관리자, 링크 45개 / 12,538개) | 0.14ms | 114ms | 링크 수에 비례해요. 그룹(`groups`)을 집계하려고 객체의 링크를 모두 읽어요 |

측정에서 알 수 있는 점:
- `get`과 일반적인 `neighbors`는 크기의 영향을 받지 않아요. 화면 하나에 필요한 만큼은 문제가 없어요.
- `find`는 객체 수에 선형이에요(객체 3백만 개면 약 10초). 인덱스가 없기 때문이며 기준 구현의 한계예요(ADR-0026). 질의 엔진 단계에서 색인을 도입해요.
- 허브의 `neighbors`는 링크 수에 선형이에요. 허브에서 페이지로 나누는 것은 항목뿐이고 그룹 수는 매번 전체를 집계해요.

## 재측정 방법

```
cd backend
go test ./internal/readcheck -run '^$' -bench Load    -benchtime 3x  -benchmem
go test ./internal/readcheck -run '^$' -bench Queries -benchtime 30x -benchmem
go run ./cmd/praxium worldgen -scale 280000 -seed 7 -out /tmp/large && go run ./cmd/praxium dev load-truth /tmp/large/truth.jsonl
```

벤치마크는 `go test`의 기본 실행에 포함되지 않아요. 큰 세계를 생성하는 데 1회 약 20초, 질의 벤치마크는 합쳐서 1분 정도 걸려요.
