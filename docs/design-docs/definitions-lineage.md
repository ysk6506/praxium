# 정의의 계보

[정의의 버전과 브랜치](definitions.md) 12절에서 나눈 문서예요(그 문서가 400줄을 넘지 않게 나눴어요). 아래 번호는 본문과 같은 12-1~12-4예요.

## 12-1. 그래프
항목 사이의 기댐을 그래프로 가져요. 정의 묶음마다 하나이고, 브랜치의 덧씌움 위에서도 계산해요.

| 노드 | 뜻 |
|---|---|
| 항목 | 소스, 데이터셋, 정제, 공급, 타입, 링크 정의, 끌어낸 묶음, 기대 조건, 목표, 알림의 규칙, 역량 질문 |
| 컬럼 | (데이터셋, 컬럼) |
| 속성 | (타입, 속성) |
| 읽는 쪽 | 저장해 둔 범위, 시스템 계정 |

| 간선 | 뜻 |
|---|---|
| `reads` | 정제가 입력 데이터셋을 읽어요. 데이터셋이 소스에 딸려요 |
| `column_from` | 출력 컬럼이 어느 입력 컬럼들에서 왔나. 정제 연산이 하나 붙어요 |
| `maps_to` | 공급이 컬럼을 속성에 잇거나 식별 키에 잇는다 |
| `defines_link` | 링크 정의가 컬럼이나 속성을 읽어 링크 타입을 만들어요. 끌어낸 링크와 묶음 만들기도요 |
| `checks` | 기대 조건, 목표, 역량 질문이 컬럼이나 속성이나 링크 타입에 걸려요 |
| `extends`, `supersedes` | 하위 타입, 물러난 타입과 후속 |
| `read_by` | 저장해 둔 범위나 시스템 계정이 타입이나 속성을 읽어요 |

## 12-2. 컬럼과 속성 단위로 따라가기
정제의 연산이 닫힌 목록(열넷)이라서 어느 컬럼이 어느 컬럼에서 왔는지를 코드가 알아요. 사용자 코드를 받는 제품은 이걸 하기 어려워요. 그래서 "컬럼 `hostname`이 바뀌면 속성 `PhysicalServer.name`과 링크 정의 둘이 걸린다"까지 가요. 합친 결과의 검사(7-3)와 데이터 건강의 번짐(ADR-0013)이 같은 그래프를 써요. 간선은 항목의 판마다 계산해서 묶음에 이어 붙이는 방식으로 두려고 해요(저장 방식은 재서 정해요).

## 12-3. 누가 쓰나
밖에서 쓰는 쪽도 세요. 저장해 둔 범위(ADR-0010의 `scopes`)는 이미 정의로 저장돼 있어요. 시스템 계정은 쓰임의 통계(`usage_record`: 계정, 타입, 속성, 날, 횟수. 하루 집계이고 읽기 하나하나를 적지 않아요. ADR-0013)가 있어요.

## 12-4. "무엇이 걸리나"의 답
입력은 대상(항목, 컬럼, 속성, 타입)과 하려는 일(고침, 물러남, 지움). 답은 이렇게 와요.

| 칸 | 뜻 |
|---|---|
| `depends` | 걸리는 정의의 항목들. 항목, 갈래(`will_break`/`may_change`/`reference_only`), 닿는 길(컬럼 단위로 어느 간선), 담당자 |
| `readers` | 걸리는 저장해 둔 범위(만든 무리)와 시스템 계정(마지막으로 읽은 때와 횟수) |
| `open_proposals` | 같은 대상을 건드리는 다른 열린 제안 |
| `object_count` | 지금 KG에서 그 타입의 객체 수 |
| `unreadable` | 읽을 권한이 없어 못 보인 항목의 수. 정의와 계보는 그 자리(소스나 타입)를 범위에 가진 `viewer`가 읽어요 |

- **두 축.** 이 계보는 정의 쪽이에요(항목에서 항목으로). ADR-0008의 출처 따라가기는 데이터 쪽이에요(객체에서 원본 기록으로). 객체와 링크는 원본 기록의 참조와 규칙의 버전(정의 묶음)을 가지고 있어서, 값 하나에서 "어느 기록에서, 어느 규칙의 어느 판으로"를 따라가고, 거기서 이 그래프로 올라가 "그 규칙이 어디에 기대나"를 봐요.
- 제안에는 "무엇이 걸리나"가 붙고 에이전트도 읽기 전용 MCP로 물을 수 있어요(MCP는 읽기만 해요).
