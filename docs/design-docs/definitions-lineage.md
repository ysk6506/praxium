# 정의의 계보

[정의의 버전과 브랜치](definitions.md) 12절에서 분리한 문서예요(그 문서가 400줄을 넘지 않게 분리했어요). 아래 번호는 본문과 같은 12-1~12-4예요.

## 12-1. 그래프
항목 사이의 의존을 그래프로 관리해요. 정의 세트마다 하나이고, 브랜치의 오버레이 위에서도 계산해요.

| 노드 | 설명 |
|---|---|
| 항목 | 소스, 데이터셋, 정제, 피드, 타입, 링크 정의, 도출한 그룹, 기대 조건, 목표, 알림의 규칙, 역량 질문 |
| 컬럼 | (데이터셋, 컬럼) |
| 속성 | (타입, 속성) |
| 소비자 | 저장해 둔 범위, 서비스 계정 |

| 간선 | 설명 |
|---|---|
| `reads` | 정제가 입력 데이터셋을 읽어요. 데이터셋은 소스에 속해요 |
| `column_from` | 출력 컬럼이 어느 입력 컬럼들에서 왔나. 정제 연산이 하나 연결돼요 |
| `maps_to` | 피드가 컬럼을 속성이나 식별 키에 연결해요 |
| `defines_link` | 링크 정의가 컬럼이나 속성을 읽어 링크 타입을 만들어요. 도출한 링크와 그룹 생성도 포함해요 |
| `checks` | 기대 조건, 목표, 역량 질문이 컬럼이나 속성이나 링크 타입에 적용돼요 |
| `extends`, `supersedes` | 하위 타입, 폐기된 타입과 후속 타입 |
| `read_by` | 저장해 둔 범위나 서비스 계정이 타입이나 속성을 읽어요 |

## 12-2. 컬럼과 속성 단위의 추적
정제의 연산이 고정 목록(14개)이라서 어느 컬럼이 어느 컬럼에서 왔는지를 코드가 알아요. 사용자 코드를 받는 제품은 이것을 하기 어려워요. 그래서 "컬럼 `hostname`이 바뀌면 속성 `PhysicalServer.name`과 링크 정의 2개가 영향받는다"까지 알 수 있어요. 병합 결과의 검사(7-3)와 데이터 헬스 상태의 전파(ADR-0013)가 같은 그래프를 써요. 간선은 항목의 버전마다 계산해서 정의 세트에 이어 붙이는 방식으로 저장하려고 해요(저장 방식은 측정해서 정해요).

## 12-3. 사용처 집계
외부 소비자도 집계해요. 저장해 둔 범위(ADR-0010의 `scopes`)는 이미 정의로 저장돼 있어요. 서비스 계정은 사용 통계(`usage_record`: 계정, 타입, 속성, 날짜, 횟수. 하루 집계이고 읽기 하나하나를 기록하지 않아요. ADR-0013)가 있어요.

## 12-4. 영향 분석 결과
입력은 대상(항목, 컬럼, 속성, 타입)과 수행할 작업(수정, 폐기, 삭제)이에요. 응답은 다음과 같아요.

| 필드 | 설명 |
|---|---|
| `depends` | 영향받는 정의의 항목들. 항목, 분류(`will_break`/`may_change`/`reference_only`), 도달 경로(컬럼 단위로 어느 간선), 담당자 |
| `readers` | 영향받는 저장된 범위(생성한 그룹)와 서비스 계정(마지막 읽기 시각과 횟수) |
| `open_proposals` | 같은 대상을 건드리는 다른 열린 제안 |
| `object_count` | 현재 KG에서 그 타입의 객체 수 |
| `unreadable` | 읽을 권한이 없어 보이지 않는 항목의 수. 정의와 계보는 그 소속(소스나 타입)을 범위에 가진 `viewer`가 읽어요 |

- **두 축.** 이 계보는 정의 측이에요(항목에서 항목으로). ADR-0008의 출처 추적은 데이터 측이에요(객체에서 원본 레코드로). 객체와 링크는 원본 레코드의 참조와 규칙의 버전(정의 세트)을 가지고 있어서, 값 하나에서 "어느 레코드에서 어느 규칙의 어느 버전으로 만들어졌는지"를 추적하고, 거기서 이 그래프로 올라가 "그 규칙이 무엇에 의존하는지"를 확인해요.
- 제안에는 영향 분석 결과가 첨부되고 에이전트도 읽기 전용 MCP로 조회할 수 있어요(MCP는 읽기만 해요).
