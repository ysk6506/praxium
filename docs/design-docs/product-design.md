# 제품 설계 한 장

새 요구사항을 설계하기 전에, 그리고 구현을 맡기기 전에 이 문서부터 읽어요. 지금은 KG를 짓고 운영하는 기반의 설계가 끝난 단계예요(ADR-0005~0018). 코드는 아직 없어요. 단계는 알파 1, 알파 2, 클로즈 베타, 오픈 베타, 정식이에요(5절).

## 1. 프락시움의 값

제품 목표(ADR-0001, ADR-0004, ADR-0005): 현실의 IT 인프라를 데이터로 받아 운영 세계를 짓고, 그 위에서 에이전트가 맡는 E2E 프로세스를 정하고 맡기고 재는 사내 운영 관리 플랫폼.

사용자가 사는 것은 한 문장이에요: **"이 일을 에이전트에게 맡겨도 되고, 맡긴 뒤에 무슨 일이 있었는지 안다."**

| 기둥 | 뜻 | 지금 |
|---|---|---|
| 현실을 받아 KG를 짓고 운영한다 | 구성 데이터를 읽어 객체와 링크로 맞추고, 읽은 것과 가정한 것을 밝힌다. 읽기만 한다 | **지금 구체화한다.** 설계 끝(ADR-0007~0016), 코드 없음 |
| 일을 E2E 프로세스 단위로 정하고 맡긴다 | 누가 무엇을 어디까지, 누가 승인하는지, 무슨 일이 있었는지 | 방향만 있다([방향 메모](process-direction.md)). 요구사항과 결정은 아직 없다 |
| 맡긴 뒤에 잰다 | 단계·사람·시간으로 잰다 | 뒤. 맡기기 전의 검증은 제품 밖의 일이다 |

## 2. 원칙

제품 책임자가 못 박은 전제와 그동안의 결정이에요. 모든 요구사항을 여기에 대 봐요. 어긋나면 덧붙이지 않고 먼저 말해요.

| # | 원칙 | 어기면 생기는 일 |
|---|---|---|
| 1 | **현실에는 읽기만 한다.** 현실 시스템을 바꾸는 길이 프락시움 안에 없다(ADR-0008의 세 겹) | 관리 도구가 사고의 원인이 된다 |
| 2 | **실제 툴은 부르지 않는다.** 부르는 것은 에이전트이고 MCP 게이트웨이를 거친다. 인증과 인가는 게이트웨이의 일이다 | 권한이 두 곳에서 따로 정해지고, 누가 한 일인지 흐려진다 |
| 3 | **모델은 프락시움이 쥔다.** 이름은 영어, 뼈대는 공개 표준에서 빌린다(ADR-0005, ADR-0007) | 남의 제품의 말과 한계에 묶인다 |
| 4 | **같은 입력이면 같은 결과.** 다음 상태는 앞 상태, 받은 원본 변경, 정의, 실행기의 뜻에서만 나온다(ADR-0009) | 무엇이 왜 바뀌었는지 말할 수 없다 |
| 5 | **모르는 것은 모른다고 말하고, 고칠 길을 준다.** 보고로 끝내지 않는다 | 정직하지만 쓸모없는 기능 |
| 6 | **사람은 규칙을 정하고, 건별로 손대지 않는다**(ADR-0011) | 수천 건을 아무도 검증하지 못한다 |
| 7 | **맡기기 전의 검증은 제품 밖의 일이다.** 프락시움은 실험장을 모른다(ADR-0005) | 한쪽이 멈추면 다른 쪽도 멈춘다 |
| 8 | **정의 하나가 배치와 흐름에 똑같이 돈다**(ADR-0008) | 스트리밍이라서 못 쓰는 연산이 생긴다 |
| 9 | **자리에 맞는 것을 쓴다. 진실의 자리는 하나, 뜻의 구현은 하나**(ADR-0006) | 같은 사실이 두 곳에서 따로 고쳐지고 같은 뜻이 둘이 된다 |
| 10 | **계약이 먼저다.** 화면은 다른 저장소이고 REST API의 계약으로만 대화한다(ADR-0016) | 백엔드와 화면이 서로를 기다린다 |
| 11 | **모든 변경은 정의의 변경이고 브랜치와 제안을 탄다**(ADR-0014) | 누가 왜 바꿨는지 모르는 상태가 숨는다 |
| 12 | **프락시움도 에이전트가 운영할 수 있게 만든다.** 볼 것(신호), 진단, 정해진 운영 행위, 권한과 기록을 갖춘다(ADR-0017) | 지표는 보이는데 무엇을 해도 되는지 몰라 사람이 셸로 들어간다 |
| 13 | **연동 정보는 쓰기만 되고, 쓰는 자리에서만 풀린다.** 평문으로 저장하지 않고 다시 나오지 않으며 쓴 기록이 남는다(ADR-0018) | 읽기 전용이어도 열쇠 묶음이 새면 조직 전체의 구성이 샌다 |

## 3. 쟁점마다 어디서 답했나

[테라리움에서 넘겨받은 것](../references/from-terrarium.md) 6절의 쟁점이에요. 그 문서는 출발 자료이고 답은 여기서 찾아요.

| 쟁점 | 답이 있는 곳 |
|---|---|
| 가. 시나리오와 프로세스가 맞물리지 않는다 | E2E 프로세스를 구체화할 때 정해요. 방향은 [방향 메모](process-direction.md) 2절 |
| 나. 맡기는 범위와 검증한 범위가 같아야 한다 | 검증이 제품 밖으로 나가 전제가 빠졌어요(ADR-0005). 구체화할 때 물음부터 다시 세워요(방향 메모 3절). 권한의 바탕은 ADR-0012 |
| 다. 두 가지 "맡김"은 다른 능력이다 | E2E 프로세스를 구체화할 때. 방향 메모 3절 |
| 라. 일 전체를 맡은 에이전트를 어떻게 돌리나 | E2E 프로세스를 구체화할 때. 방향 메모 4절 |
| 마. 실제 툴은 실험장에 없다 | 같은 까닭으로 전제가 빠졌어요(ADR-0005). 방향은 방향 메모 5절 |
| 바. 운영 경로가 되면 멈추면 안 된다 | 묻기는 멈추지 않는다: ADR-0011. 질의 엔진 여러 벌과 저장소가 멈춰도 답하기: ADR-0010. 역할 넷: ADR-0006. 맡김과 조치의 등급은 E2E 때 |
| 사. 이음매의 형식이 아직 없다 | 테라리움과의 이음매를 없앴어요(ADR-0005). KG의 한 범위를 내보내는 일은 계획의 뒤 순서이고, 재료는 ADR-0010의 저장해 둔 범위와 ADR-0014의 정의 내보내기 |
| 아. 말이 겹친다 | 두 제품이 이어지지 않아 프락시움 안에서는 생기지 않아요(ADR-0005). 말은 [용어집](glossary.md) |

## 4. 요구사항을 받았을 때

1. 그 요구가 **어느 기둥과 어느 원칙**에 닿는지 적어요.
2. **기존 자산에 걸리는 것**을 전부 찾아요.
3. **같은 문제가 다른 곳에도 있는지** 봐요. 한 곳만 고치지 않아요.
4. 뒤집는 결정이 있으면 **한 번에** 뒤집어요.
5. 범위를 넘거나 원칙과 부딪치면 맞춰 덧붙이지 않고 **먼저 말해요**.
6. 같은 주제의 결정 기록을 하루에 둘 넘게 쓰게 되면 **멈추고 전체를 다시 봐요**.

## 5. 순서

날짜는 두지 않아요. 위에서 아래가 순서예요. 자세한 것은 [계획](../exec-plans/active/plan.md)에 있어요.

| 순서 | 무엇 | 끝났다는 증거 |
|---|---|---|
| 1~3 | 구조 세우기, 저장소 설정, 제품 목표 굳히기 | 구조 검사와 시험이 CI에서 통과한다. 목표가 결정 기록에 있다 |
| 4 | KG 기반의 설계 (ADR-0005~0018) | 결정 기록과 설계 문서, 예정 요구사항 |
| 5 | 뼈대와 지어낸 세계 | 표준 모델이 스스로 맞는지 보는 시험, 같은 씨앗이면 같은 세계 |
| 6 | 계약 | OpenAPI 문서와 계약의 검사, 명령줄 클라이언트의 뼈대 |
| 7 | 얇게 끝까지 한 줄(알파 1: 제품 책임자가 여기서부터 눌러 봐요) | 파일 소스 하나에서 KG 버전이 나오고 `find`/`get`/`neighbors`가 API와 명령줄로 답한다 |
| 8 | 받기를 넓힌다 | 지어낸 세계의 정답 KG와 맞고, 흩뜨린 입력에서 안전장치가 멈춘다 |
| 9 | 정의의 브랜치와 제안과 되돌리기, 권한 | 병합과 되돌리기가 검사를 거쳐 들어간다 |
| 10 | 영향 범위 | 지어낸 100만 객체에서 기능과 결정성이 시험된다. 제품 책임자의 숫자와 견주는 재기는 클로즈 베타에서 한다 |
| 11 | 관측성과 역량 질문, 프락시움 자신의 관측성과 운영 행위 | 건강과 충족률이 API로 나오고, `diagnose`와 운영 행위가 API로 된다 |
| 12 | 알파 2 | 객체와 링크 100만 개 수준에서 모든 기능이 API와 명령줄 클라이언트와 임시 콘솔로 돈다 |
| 13 | 클로즈 베타 | 수천만 개로 재서 숫자가 문서에 있다 |
| 14 | 오픈 베타 | 프로덕션에 나갈 수 있는 수준: 비밀 값과 암호화, 자신의 운영, 에이전트 시대의 정의 버전, 저장소의 운영 수준이 구현돼 있다 |
| 정식, 그 뒤 | 프런트엔드 저장소(아직 없다), E2E 프로세스의 구체화 | |
