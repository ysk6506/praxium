# 게이트웨이 설계

에이전트가 현실의 툴을 부를 때 지나가는 문을 프락시움의 구성요소로 만드는 설계예요. 결정은 ADR-0061에 있어요. 이 문서는 구성과 책임, 실행의 계약, 호출의 순서, 분류와 연결, 확인을 다뤄요. 신뢰의 경계, 보안 원칙, 가용성과 긴급, 정의의 통제, 단계와 여는 조건, 장애 표는 [게이트웨이의 안전](gateway-safety.md)에, 액션 타입 표는 [게이트웨이의 액션 타입 표](gateway-actions.md)에, 보장하는 것과 하지 않는 것은 [안내서](../guides/what-praxium-guarantees.md)에 있어요.

**아직 구현하지 않았어요.** 현재 코드는 현실 시스템을 읽기만 해요. 이 문서의 모든 내용은 예정이고 요구사항은 REQ-450부터 REQ-469까지예요([요구사항](../product-specs/requirements-gateway.md)). 구현은 클로즈드 베타 뒤예요.

## 1. 목적과 다루는 질문

| 쟁점 | 답 |
|---|---|
| 게이트웨이는 무엇인가 | 같은 릴리스, 같은 실행 파일의 별도 기동 모드예요. 코어가 판단하고 기록하고, 게이트웨이가 집행하고 업스트림 MCP 서버의 자격 증명을 가져요(2절) |
| 에이전트는 무엇을 보는가 | 프락시움의 액션 타입을 툴로 봐요. 업스트림 툴의 설명은 에이전트에게 가지 않아요(3절) |
| 어떤 툴이 열리는가 | 등록하면 꺼져 있고, 승인한 뒤에만 켜져요. 정의의 해시를 고정해요(4절) |
| 업무 권한은 언제 주는가 | 업무를 요청할 때 한꺼번에 주고, 조건이 충족될 때 집행해요(5절) |
| 호출은 어떤 순서인가 | 준비, 실행, 조회의 세 번의 호출이에요(6절) |
| 중간에 끊기면 | 실행 대장가 남고, 이어받는 에이전트는 맥락 읽기 툴로 이어 가요(7절) |
| 읽기, 진단, 바꾸기는 어떻게 다른가 | 프락시움이 분류하고 연결마다 신뢰 단계를 둬요(8절) |
| 성공했는지 어떻게 아는가 | 툴의 성공 응답을 믿지 않고 수집 쪽이 다시 읽어서 확인해요(9절) |

## 2. 구성과 책임

```
에이전트 하네스 ── MCP ──> 게이트웨이 ── MCP ──> 업스트림 MCP 서버 ──> 현실 시스템
                             │  ▲
                        판단 요청 │ │ 판단 결과
                             ▼  │
                            코어 (레지스트리, 판단, 기록, 승인)
```

| 구성요소 | 하는 일 | 하지 않는 일 |
|---|---|---|
| 코어 | 정의, 레지스트리, 조건 판단, 승인, 실행 대장, 기록 | 업스트림 자격 증명을 갖는 일, 업스트림을 부르는 일 |
| 게이트웨이 | 집행, 업스트림 호출, 업스트림 자격 증명 보관, 결과 필터링 | 판단을 스스로 바꾸는 일, 바꾸는 호출을 스스로 만드는 일 |
| 하네스, 업스트림 MCP 서버 | 프락시움 밖에 있어요 | |

- 코어와 게이트웨이를 나누는 것은 자격 증명이 코어 밖으로 나가지 않게 하는 효과만 있어요. 코어는 가장 믿어야 하는 구성요소이고, 코어의 보호가 여는 조건의 첫째예요([안전](gateway-safety.md) 2절).
- 게이트웨이는 상태를 갖지 않고 둘 이상을 띄워요. 파일 스토어는 단일 인스턴스 전용이라, 게이트웨이를 쓰는 운영 구성은 동기 복제와 장애 전환이 있는 PostgreSQL이 필요해요.
- 쓰려는 조직들은 이미 MCP 서버를 갖고 있는 경우가 많아요. 프락시움은 그것을 업스트림으로 연결하고 새로 만들게 하지 않아요.
- KG를 조회하는 MCP 인터페이스은 영구히 읽기 전용이고 그대로예요. 게이트웨이는 다른 주소의 다른 구성요소예요([REST API](rest-api.md), [질의](kg-queries.md)).

## 3. 에이전트가 보는 것

- 에이전트는 액션 타입(예: `set_cooling_setpoint`)을 툴로 봐요. 게이트웨이가 그것을 업스트림 툴의 호출로 바꿔요.
- 업스트림 툴의 설명은 에이전트에게 가지 않아요. 설명에 숨은 지시가 들어올 길을 막기 위해서예요.
- 읽기와 진단 툴은 승인한 정의의 사본으로 넘겨요.
- 툴 목록은 실행마다 고정이에요(토큰에 묶여요). 통제는 호출할 때 거절하는 것으로 해요. 2026-07-28판 MCP 명세는 상태가 없고 목록 캐시 범위가 비공개라서 이 방식과 맞아요.
- 업스트림 응답은 필터링해서 넘겨요. 리소스 링크를 지우고, 크기를 제한하고, 시크릿을 가려요.

## 4. 툴의 등록과 분류

- 업스트림 툴은 등록하면 꺼져 있어요. 승인한 뒤에만 켜지고, 승인한 정의의 해시를 고정해요. 정의가 바뀌면 끄고 다시 승인을 받아요.
- 분류는 툴이 스스로 붙인 표시(`readOnlyHint` 같은 주석)가 아니라 프락시움이 정해요. 셋이에요.

| 종류 | 설명 | 통제 |
|---|---|---|
| 읽기 | 부작용이 없는 조회 | 묶음에는 부작용 없는 읽기만 넣어요. 자유 형식 인자가 있는 툴은 읽기로 분류하지 않아요 |
| 진단 | 부작용이 있을 수 있는 확인(점검, 재탐색, 연결 테스트) | 업스트림 서버와 대상별 호출 한도, 실행에 묶고 기록해요 |
| 바꾸기 | 현실을 바꿔요 | 실행의 계약과 승인, 확인을 거쳐요 |

- 실행 중에 툴을 더하는 일은 이미 등록하고 승인한 액션만 되고, 정의 승인자 수준의 승인을 받고, 실행마다 개수 한도가 있어요.

## 5. 실행의 계약

"단계"로 열리는 툴은 없어요. 대신 실행이 계약을 가져요. 업무를 요청하면 계약이 만들어지고, 거기서 권한이 한꺼번에 부여돼요.

| 항목 | 내용 |
|---|---|
| 실행 ID | 실행을 가리켜요 |
| 프로세스 정의 | 시작할 때의 버전을 고정해요 |
| 허용 액션 집합 | 시작할 때 한꺼번에 부여해요 |
| 대상 객체 집합 | 시작할 때 풀어서 고정해요. 늘리려면 승인이 필요해요 |
| 한도 | 호출 수, 객체 수, 시간 |
| 승인 규칙 | 어느 호출에 누구의 승인이 필요한지 |
| 상태 | 열림, 대기, 끝남, 돌려줌, 중단 |
| 하네스 세션 임대 | 세대 번호를 가져요(7절) |

- 실행을 시작하는 것 자체가 권한이에요. 사람이 시작해요.
- 이벤트로 자동 시작하는 것은 읽기만 하는 프로세스에만 허용해요.
- 티켓 시스템의 요청은 만든 사람이 시작 권한이 있는 프락시움 계정에 대응하면 사람의 시작으로 봐요. 기계가 만든 티켓은 이벤트로 봐요.
- "조건이 충족될 때 실행"은 프락시움이 스스로 실행하지 않는다는 뜻이에요. 조건이 안 맞으면 실행 호출이 "아직"과 맞지 않은 조건의 목록을 돌려주고, 에이전트가 다시 불러요.
- 의도는 토큰과 독립으로 남아요. 하네스는 실행이 열려 있는 동안 새 실행 토큰을 받을 수 있고(갱신은 실행에 묶여요), 승인을 기다리는 동안 살아 있는 토큰이 필요하지 않아요.
- 토큰 형식, 수명, 소지 증명 방식은 아직 정하지 않았어요([안전](gateway-safety.md) 9절).

## 6. 호출의 순서

바꾸는 호출은 세 번의 호출이에요.

| 호출 | 입력 | 하는 일 |
|---|---|---|
| 준비 | 액션, 대상, 인자 | 의도 ID와 전달할 호출의 요약, 조건 평가, 영향 범위, 승인 필요 여부를 돌려줘요. 기록해요 |
| 실행 | 의도 ID | 한 번만 실행하고 멱등이에요. 조건을 실행 직전에 다시 확인해요 |
| 조회 | 의도 ID | 상태를 돌려주고 조건을 다시 평가해요 |

- 준비는 내용으로 멱등이에요. 같은 실행에서 같은 (액션, 대상, 인자)로 열린 의도가 있으면 새로 만들지 않고 그것을 돌려줘요. 같은 것이 이미 끝났으면 "이미 했음(확인 결과)"을 돌려줘요. 다시 하려면 이유를 적어 명시적으로 요청해야 하고 한도에 세요.
- 인자는 대상의 관측된 식별자, 액션이 선언한 인자, 고정값만 지나갈 수 있어요. 자유 문장 인자는 승인 화면에 그대로 보여요. 액션 타입에 인자의 정의를 더하는 일은 [할 일](gateway-actions.md)이에요.
- 게이트웨이는 바꾸는 업스트림 호출을 스스로 다시 보내지 않아요. 에이전트와의 연결이 끊겨도 업스트림 호출은 끝까지 기록해요. 대상이 여럿이면 대상마다 기록해요.
- 승인은 의도의 내용 해시와 조건의 증거에 묶여요. 실행 직전에 조건을 다시 확인하고, 승인은 폴링으로 기다려요(MCP의 요청 도중 질의(elicitation)를 쓰지 않아요).
- 승인 시간이 지나면 거절로 처리해요. 자동 승인은 없어요.

## 7. 실행 대장와 이어 가기

실행 대장는 코어가 영속적으로 가져요. 의도의 상태는 준비됨, 승인 대기, 실행 중, 끝남, 확인 결과, 모름이에요. 결과를 모르는 호출은 확인으로 풀릴 때까지 "모름"으로 남아요.

이어 가기 맥락은 읽기 툴 하나가 돌려줘요: 이 실행이 무엇인지, 끝난 것(확인 결과 포함), 진행 중이거나 모르는 것, 남은 것이에요.

- 에이전트가 "이어받겠다"고 맥락 읽기를 부르면 실행의 세대 번호가 하나 올라요. 준비와 실행은 세대 번호를 툴 인자로 받고 낡은 세대는 거절해요. 같은 세션의 하위 에이전트는 세대를 공유해요.
- 표준 MCP 클라이언트만으로 동작해요.

## 8. 연결과 신뢰 단계

연결은 액션 타입과 업스트림 툴의 짝이에요. 하나의 액션은 하나의 업스트림 호출이고, 인자는 식별자와 고정값뿐이에요. 업스트림 툴이 대상 밖의 것도 바꾸면 그렇게 선언하고 가장 위험한 액션의 위험을 따라요.

연결마다 신뢰 단계를 둬요.

| 단계 | 동작 |
|---|---|
| 그림자 | 전달했을 호출을 기록만 해요 |
| 호출마다 승인 | 모든 바꾸는 호출에 사람의 승인이 필요해요 |
| 자율 | 조건이 충족되면 승인 없이 집행해요 |

- 단계는 사람이 확인 기록을 보고 올려요.
- 툴의 정의가 바뀌거나 확인 결과가 어긋나면 자동으로 내려가요.
- 실험 환경으로 보내는 경로는 두지 않아요. 프락시움은 실험 환경을 모른다는 원칙은 그대로예요(ADR-0005).

## 9. KG를 믿는 규칙과 확인

### 9.1 KG를 믿는 규칙

- 업스트림 호출에 넣는 식별자는 그 툴이 다루는 시스템에서 직접 읽은 `observed` 식별자이고, 정한 나이 안이어야 하고, 그 객체에 열린 식별 후보나 충돌이 없어야 해요. "사실" 등급만으로는 모자라요. 사람이 쓴 값(엑셀의 `declared`)도 기본 등급이 사실이기 때문이에요.
- 영향 범위를 쓰는 조건은 관련 링크 타입에 완전성 선언이 있어야 통과하고, 없으면 "확인 못 함"이에요. 모르는 것은 영향을 받는 것으로 세요. 중복 상실 가능과 모름(부분 상실)도 영향으로 세요.
- 자료의 나이는 읽은 때가 아니라 값 자체의 시각으로 재요(관리 툴은 저장된 값을 돌려줘요).
- 조건마다 허용 나이가 있고 속성의 변화 속도에서 와요. 낡았으면 "확인 못 함"이고 통과가 아니에요.
- 잠금은 대상과 그것이 직접 속한 중복 그룹, 그 그룹이 속한 그룹까지 걸어요. 깊이 한도와 임대 기간이 있어요. 진행 중인 의도는 다른 실행의 조건 평가에서 이미 일어난 것으로 세요.

### 9.2 확인

- 툴의 "성공"을 믿지 않아요. 읽기는 코어가 요청하고 수집 쪽이 하고, 기존의 지정 재수집(REQ-225)과 기대와 대조(REQ-226)를 재사용해요.
- 1차에서는 다시 읽을 수 있는 소스의 속성만 조건에 써요. 읽기 툴로 확인하는 것은 나중에 하고, 그때는 바뀐 서버와 같은 경로임을 낮은 신뢰로 표시해요.
- 결과는 기존 넷이에요: `confirmed`, `not_yet`, `contradicted`, `unverifiable`.
- KG는 관측만 믿어요. 어긋나면 자동으로 되돌리지 않고 멈춰서 상태 요약과 함께 사람에게 넘겨요.
- 밀어 넣은 값은 `declared`이고 증거가 될 수 없어요.
- 시계 어긋남이 한도를 넘으면 헬스 상태로 올려요.

## 10. 하네스와 다른 게이트웨이

- 표준 MCP 클라이언트로 연결해요. 하네스에 맞춘 것은 만들지 않아요.
- 하네스와 게이트웨이 사이를 상호 TLS로 묶는 것은 선택 강화예요. 없으면 수명을 짧게 하고 한도를 낮춰요.
- 하위 에이전트는 실행의 한도를 공유해요.
- 이미 게이트웨이가 있는 조직은 프락시움 게이트웨이를 그 뒤의 MCP 서버로 둘 수 있게 지원해요. 코어와 게이트웨이 사이의 판단 계약은 버전을 가져요.
