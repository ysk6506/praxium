# 질의 스키마

사용자가 KG를 SQL로 물을 때 보는 것의 설계예요. 타입 이름의 뷰와 링크 뷰, 객체를 타입 없이 읽는 뷰, 과거 시점 함수, 모델을 설명하는 테이블과 주석, 민감 등급이 가리는 것, 본보기 질의를 정해요. 결정은 ADR-0080에 있어요. **이 문서는 아직 구현하지 않은 설계(예정)예요.** 제품은 영향 범위나 이중화 같은 도메인의 뜻을 계산하지 않아요(ADR-0077, ADR-0078). 사용자가 이 스키마 위에서 질의를 써서 직접 구해요. 예시의 이름과 값은 지어낸 것이에요. 뷰 밑의 테이블은 [새 저장의 모양](storage-shape.md)에, 질의를 돌리는 방어는 [질의 실행기와 읽기의 세 경로](query-execution.md)에 있어요.

## 1. 목적과 다루는 질문

- 사용자와 LLM이 SQL을 처음 쓰면서도 틀리지 않으려면 스키마가 어떤 모양이어야 하나.
- 같은 질의를 호출자의 KG와 민감 등급에 따라 다른 데이터에 어떻게 안전하게 돌리나.
- 모델이 바뀌면(타입, 속성, 링크 타입) 사용자가 보는 것은 어떻게 따라가나.
- 여러 단계를 따라가는 질의와 폭발적으로 느는 범위는 어떻게 감당하나(그래프 함수, 4절).

## 2. 스키마의 구성

- **KG마다, 민감 등급마다 질의 스키마**를 둬요. 이름은 `q_<kg_no>_<등급>`(`open`, `restricted`, `confidential`)이에요. 서버가 호출자의 KG와 등급에 맞춰 검색 경로(`search_path`)를 정하므로 사용자는 스키마 이름을 쓰지 않고 `SELECT name FROM physical_server WHERE …`처럼 써요.
- **높은 등급의 스키마에는 낮은 등급과 달라지는 뷰만** 둬요. 표준 속성은 모두 `open`이라, 달라지는 것은 조직의 커스텀 속성을 가진 타입의 뷰와 그것을 쓰는 뷰뿐이에요. 검색 경로를 높은 것부터 겹쳐요(`q_1_confidential, q_1_restricted, q_1_open`). 낮은 등급의 호출자는 `q_1_open`만 쓸 수 있어요. 전체를 등급마다 두면 3배가 되는 것을 줄여 KG마다 뷰가 약 230개예요(원형에서는 타입 뷰 168, 링크 타입 뷰 55, 공통 뷰 몇 개).
- **큰 적용 중용 스키마**를 따로 한 벌 더 둬요. 지금 테이블에서 읽기 워터마크 이하인 행과 이력에서 그 번호를 덮는 행을 합친 뷰예요([새 저장의 모양](storage-shape.md) 9절). 어느 쪽을 쓸지는 질의 실행기가 질의마다 KG의 머리 행을 보고 골라요. 이름은 구현할 때 정한다.
- **역할은 (KG, 민감 등급)마다 하나**예요. 질의 실행기가 질의마다 트랜잭션 안에서 그 역할로 바꿔요(`SET LOCAL ROLE`). 그 역할은 자기 질의 스키마의 `USAGE`, 뷰의 `SELECT`, 제품 함수의 `EXECUTE`만 가져요. KG의 격리는 행 조건(`WHERE kg_no = …`)이 아니라 **KG마다의 저장 스키마와 역할**로 해요. 행 조건은 값이 새지 않는다는 보장이 아니라 비용 순서의 결과일 뿐이라서예요(원형에서 확인).
- 뷰는 모두 `SELECT`만이에요. 사용자가 객체를 만들 수 없어요(스키마와 임시 테이블의 권한을 거둬요).

## 3. 타입 뷰

타입마다 뷰 하나예요. 이름은 타입 이름이고(`physical_server`) 사용자는 이것을 일반 테이블처럼 써요.

| 컬럼 | 뜻 |
|---|---|
| `id` | 조인 키(`obj_no`). DB 전체에서 하나뿐이고 다시 쓰지 않는 번호예요 |
| `ref` | 밖에서 기억하는 참조(해시 id). 에이전트는 이 값을 메모리에 둬요 |
| `name` | 객체의 이름 |
| 표준 속성의 컬럼 | 모델의 속성 이름. 형은 [새 저장의 모양](storage-shape.md) 6절의 표를 따라요 |
| 상태의 컬럼 | `lifecycle_state`, `oper_state`와 그 시각, 그 타입의 변동 속성 |
| 커스텀 속성의 컬럼 | 조직이 더한 속성. 이름은 아래 규칙을 따라요 |
| `min_grade` | 그 객체의 속성들 가운데 가장 약한 근거 등급 |
| `provenance` | 속성마다의 출처(근거 등급, 근거 종류, 시각, 소스 참조)를 담은 `jsonb`. 속성 번호가 아니라 이름이 키예요 |

- **부모 타입의 뷰는 자식 뷰의 합집합**(`UNION ALL`)이에요. 부모의 속성을 자식이 모두 물려받으므로 부모 뷰의 컬럼은 부모의 속성이고 자식 뷰에는 그것이 모두 있어요. 이 규칙은 [모델](kg-model.md)에도 적어요.
- **컬럼 이름의 규칙(커스텀 속성)**: 조직 속성의 이름은 `org.snake_case`처럼 점이 있어요(ADR-0050, ADR-0053). 뷰의 컬럼 이름은 **속성의 이름 그대로**이고 점이 있어서 큰따옴표로 감싸요(`"org.rack_owner"`). 표준 속성은 점이 없어서 겹치지 않아요. `SELECT s.name, s."org.rack_owner" FROM physical_server s`처럼 써요. 이 규칙은 이 문서가 정한 것이고 구현할 때 다듬어요.
- **이름을 바꾼 속성**: 질의 스키마에는 옛 이름의 별칭을 두지 않아요. 옛 이름을 쓰던 저장한 질의는 올릴 때의 재검사에서 깨진 것으로 드러나요([저장한 질의와 간선 정의](saved-queries.md) 3절). 별칭을 둘지는 정하지 않았어요.
- 값의 형이 모델과 다르게 들어가는 일은 쓰기 전의 모델 검사가 막아서, 뷰는 읽을 때 형 오류를 내지 않아요.

## 4. 링크 뷰

- **`link(type, src, dst, grade, basis, props)`**: 링크 전체. `type`은 링크 타입 이름, `src`와 `dst`는 `id`, `grade`는 근거 등급(`fact`, `assumed`, `unknown`), `basis`는 근거 종류, `props`는 링크 속성(`jsonb`)이에요.
- **링크 타입마다의 뷰**(`mounted_in`, `runs_on` 같은 이름): `src`, `dst`, `grade`, `basis`와 그 링크 타입의 속성 컬럼(링크 타입 55개 가운데 속성을 가진 것은 11개)이에요. 방향이 있고, 반대 방향은 `src`와 `dst`를 바꿔 쓰거나 `direction`을 받는 함수로 해요.
- 간선에 속성 조건이 필요하면(예: "주 경로만") **간선 정의**를 써서 사용자가 만든 뷰를 이 스키마에 더해요([저장한 질의와 간선 정의](saved-queries.md) 5절). 제품은 무엇이 의존이고 무엇이 이중화인지 전제하지 않아요.

## 5. 타입을 가리지 않는 뷰

| 뷰 | 컬럼 | 쓰임 |
|---|---|---|
| `object` | `id`, `ref`, `type`(타입 이름), `name`, 상태 둘 | 타입 없이 이름이나 참조로 찾기, 이웃의 이름 읽기 |
| `object_detail` | `id`, 속성을 이름 키의 `jsonb`로 편 문서(출처 포함) | 한 객체를 모든 속성과 함께 읽기. 문서의 번호 키를 이름으로 바꾼 것이에요 |
| `attribute` | `id`, `name`, `value`, 근거 등급, 시각 | 속성을 한 줄씩 편 것. **느린 길**이에요(훑는 데 쓰지 않아요) |

- `object`의 `type` 컬럼은 `model_type`을 조인해서 얻어요. 행마다 부분 질의로 이름을 찾으면 규모에 비례해 느려요(원형: 116만 객체에서 타입별 개수가 6.8초, 3천만에서 100~170초로 추정).
- `object_detail`이 쓰는 함수의 권한(질의 역할의 실행 권한과 등급 인자의 처리)은 구현할 때 정한다. 원형에서는 이 함수에 질의 역할의 실행 권한이 없으면 뷰가 안 읽혔고, 등급을 인자로 두면 스키마의 사용 권한이 막아 주는 깨지기 쉬운 구조가 됐어요. 등급을 뷰가 정하는 상수로 두거나 등급마다 함수를 두는 쪽이 안전해요.

## 6. 과거 시점

타입마다 **`<타입 이름>_at(시점)`** 함수가 있어요(예: `physical_server_at(1200)`). 시점은 변경 번호이고, 지금 테이블과 이력 테이블을 합쳐 그 번호의 모습을 줘요. 변동 속성은 이력이 없으므로 이 결과에 없어요. 이 길은 **느려요**: 원형에서 가상 머신 12.7만 행의 개수를 구하는 데 약 0.39초였어요. 한 객체의 이력만 읽는 것은 이력 테이블에서 직접 읽어 0.1ms였어요. 과거 시점과 변경 기록도 민감 등급이 같은 집합으로 걸러요(8절).

## 7. 모델 설명

LLM이 타입 뷰 168개에서 맞는 질의를 쓰려면 스키마가 스스로를 설명해야 해요(원형의 모형 스키마는 컬럼 이름과 형만으로 3,361줄, 70kB예요).

- **모든 뷰와 컬럼에 `COMMENT`**를 달아요. 열거 값과 단위는 컬럼 설명에 실어요.
- **테이블 4개**(질의 스키마에 읽기 전용):

| 테이블 | 내용 |
|---|---|
| `model_type` | 타입 이름, 부모, 설명, 층 |
| `model_attribute` | 타입, 속성 이름, 값 형, 단위, 열거 값, "검색에 쓴다" 표시, 설명 |
| `model_link_type` | 링크 타입 이름, 속성, 설명 |
| `model_link_rule` | **어느 타입을 어느 링크 타입이 잇는가**(출발 타입, 링크 타입, 도착 타입, 개수 제약) |

- **스키마 설명은 걸러서 나눠 줘요.** `kg_schema`(MCP 툴)와 스키마 설명 REST 경로는 통째로 주지 않고 낱말로 찾기와 타입 하나 보기를 줘요. 호출자의 민감 등급으로 거르고, 링크 규칙에서 **조인의 본보기 문장**을 함께 줘요(`physical_server.id = mounted_in.src AND mounted_in.dst = rack.id`). 그래프를 SQL로 쓸 때 틀리는 자리가 조인의 방향이라서예요(추측).
- 완전성 선언("모른다"와 "없다"의 구분)은 모델 설명에 싣고 안내서에 적어요. 반조인("VM이 없는 호스트")은 SQL에서 "없다"로 답하는데, 소스가 그 데이터를 다 주었는지는 피드의 완전성 선언에 있어요([모델](kg-model.md) 9.3절).
- 표준 모델에 남기는 뜻은 구조(타입, 속성, 링크 타입, 잇는 규칙, 개수 제약)예요. 계산을 위한 뜻(전파, 채널, 인자)은 모델에서 빼요(ADR-0080의 순서에서 둘째 걷어내기).

## 8. 민감 등급이 가리는 것

- **가리는 것은 값이에요.** 낮은 등급의 스키마에는 그 속성의 컬럼이 없어요. `provenance`, `attribute`, `object_detail`, 과거 시점 함수, 변경 기록도 같은 속성 번호의 집합으로 걸러요. 뷰와 함수를 만드는 코드 한 곳이 "이 등급에서 보이는 속성 번호의 집합"으로 전부를 거르고, 테스트가 그것을 잠가요(한 곳에서 필터링).
- **카탈로그로 보이는 것을 받아들여요**(제품 책임자가 받아들였어요). 높은 등급 속성의 이름이 DB의 카탈로그로 보일 수 있어요. 원형에서 낮은 등급의 역할이 볼 수 있었던 것: 역할 이름 22개, 함수의 본문, 다른 KG의 테이블 개수(`pg_class`의 추정), 통계 객체 정의, `version()`, `pg_settings`예요. 높은 등급 뷰의 정의와 열 이름은 스키마 `USAGE`가 없어서 거절됐어요. **카탈로그에 비밀을 두지 않아요**(함수 본문, 주석, 뷰의 정의, 속성 설명에 값이나 키를 넣지 않아요).
- **행 단위의 범위 제한은 클로즈드 베타에 없어요.** 읽기 권한은 KG와 민감 등급의 단위예요. 원형에서 장벽 뷰(`security_barrier`)로 행을 제한하면 7단계 패턴이 0.54초에서 53초로 약 100배 느려졌고(누출 방지 표시가 없는 연산의 조건이 인덱스로 내려가지 않아요. `LIKE`, 정규식, `numeric` 비교, 열거형 비교, `jsonb` 연산이 그래요), 그래서 **장벽 뷰로 하지 않아요.** 방법은 미결이에요(행 단위 보안 정책에 누출 방지 표시를 두는 설계, 스키마를 나누는 방식을 따로 재야 해요). 범위 키의 값은 진짜 컬럼이어야 하고 서버가 트랜잭션에 거는 값을 사용자가 못 바꿔야 한다는 전제는 질의 실행기의 방어가 지켜요.
- **조인 순서 탐색의 한도**는 PostgreSQL의 기본값을 유지해요. 올리면 계획 시간이 87~125ms로 늘어요(원형의 7단계 패턴).

## 9. 본보기 질의

이름과 값은 지어낸 것이에요(`example.test`). 안내서와 `kg_schema`의 예시 질의로 같이 줘요.

```sql
-- 1) 속성 검색: 메모리가 64GiB를 넘는 리눅스 가상 머신
SELECT id, name, oper_state FROM virtual_machine
WHERE guest_os_family = 'linux' AND memory_gib > 64 ORDER BY name LIMIT 100;

-- 2) 조인: 랙 rack-a-01에 장착된 서버 (링크 규칙의 본보기 문장대로)
SELECT s.name FROM physical_server s
JOIN mounted_in m ON m.src = s.id JOIN rack r ON r.id = m.dst
WHERE r.name = 'rack-a-01';

-- 3) 이웃: 참조로 찾은 객체에 이어진 모든 객체(방향 무관)
WITH me AS (SELECT id FROM object WHERE ref = $1)
SELECT l.type, o.name FROM link l JOIN me ON l.src = me.id JOIN object o ON o.id = l.dst
UNION ALL
SELECT l.type, o.name FROM link l JOIN me ON l.dst = me.id JOIN object o ON o.id = l.src;

-- 4) 집계: 랙마다 서버 수
SELECT r.name, count(*) AS servers FROM rack r
JOIN mounted_in m ON m.dst = r.id GROUP BY r.name ORDER BY servers DESC LIMIT 20;

-- 5) 도달 집합: 호스트 하나가 멈추면 영향받는 객체를 사용자가 정의한 간선으로 구한다
SELECT o.name, r.depth
FROM reachable(start => (SELECT id FROM object WHERE ref = $1),
               edges => ARRAY['runs_on', 'mounted_in'], direction => 'in',
               max_depth => 6, max_nodes => 50000) r
JOIN object o ON o.id = r.id;

-- 6) 과거 시점: 변경 번호 1200 때의 내려가 있던 서버
SELECT name FROM physical_server_at(1200) WHERE oper_state = 'down';

-- 7) 반조인: 가상 머신이 하나도 없는 호스트
SELECT h.name FROM physical_server h
WHERE NOT EXISTS (SELECT 1 FROM runs_on e WHERE e.dst = h.id);
```

- 5번의 "영향받는 객체"가 무엇인지(`runs_on`만 볼지, 전원 의존도 볼지)는 사용자가 정해요. 제품은 의미를 전제하지 않아요. 함수의 인자와 돌려주는 열은 [질의 실행기와 읽기의 세 경로](query-execution.md) 3절에 있어요.
- 이웃 펼치기나 도달 집합의 결과를 사람이 읽는 이름으로 바꾸는 것은 `object`와의 조인이에요.
- 7번은 "없다"가 "모른다"일 수 있어요. 소스의 완전성 선언을 모델 설명에서 확인해요(7절).

## 10. 재귀 SQL의 올바른 꼴과 터지는 꼴

그래프 함수 대신 재귀 SQL을 직접 쓰는 것을 막지 않아요. 재귀 SQL은 함수보다 빠를 때가 많아요(원형: 사이트 아래 전체 0.44초 대 함수 1.29초). 대신 예산이 없어요. 안내서에 올바른 꼴과 터지는 꼴을 적어요.

```sql
-- 올바른 꼴: id만 UNION으로 모아 방문 집합을 만든다. 순환과 중복에 안전하다
WITH RECURSIVE reach(id) AS (
  SELECT dst FROM runs_on WHERE src = $1
  UNION
  SELECT e.dst FROM reach r JOIN runs_on e ON e.src = r.id
)
SELECT id FROM reach LIMIT 10000;
```

```sql
-- 터지는 꼴: 깊이 열이 있어 UNION의 중복 제거가 듣지 않고, 양방향이라 되돌아간다
WITH RECURSIVE walk(id, depth) AS (
  SELECT $1::bigint, 0
  UNION
  SELECT CASE WHEN l.src = w.id THEN l.dst ELSE l.src END, w.depth + 1
  FROM walk w JOIN link l ON l.src = w.id OR l.dst = w.id
)
SELECT * FROM walk;
```

- 규칙: (가) 재귀 안에서는 id만 모으고 깊이는 열로 넣지 않아요(깊이가 필요하면 그래프 함수). (나) 방향을 하나로 해요. (다) 바깥에 `LIMIT`을 걸어요(재귀 질의는 바깥이 100행만 받으면 몇 번 돌고 멈춰요). (라) 경로를 세거나 나열하는 재귀는 쓰지 않아요(모든 규모에서 한도에 걸려요).
- **터지는 꼴은 한도가 끊어요.** 원형에서 위와 같은 재귀 SQL 8개를 30초 동안 함께 돌렸을 때 서버 프로세스의 개인 메모리가 최고 1.86GB(기계 8GB의 23%)였고 서버는 살아 있었으며 끝나자 곧 평소로 돌아왔어요. 세션당 초당 약 20MB로 자라요. 시한과 임시 파일 한도와 풀 크기가 이 값을 정해요([질의 실행기와 읽기의 세 경로](query-execution.md) 2절).

## 11. 알려진 한계와 가정

- 카탈로그로 보이는 이름이 있어요(8절). 행 단위 범위 제한이 없어요.
- 뷰의 수가 많아서(KG마다 약 230, 큰 적용용 한 벌 더) 질의를 처음 돌리는 연결이 카탈로그를 읽는 데 메모리를 써요(원형: 뷰 232개를 읽은 뒤 연결 메모리 14MB).
- 이름 변경의 별칭이 없어요. 사용자 질의가 모델 변경에 깨질 수 있어요. 저장한 질의는 올릴 때와 정의 변경 때 다시 검사해요.

## 12. 미결 사항

- 행 단위의 범위 제한의 방법.
- 이름을 바꾼 속성의 옛 이름 별칭.
- `object_detail`이 쓰는 함수의 권한, 큰 적용 중용 스키마의 이름.
- 도달 집합의 시작점이 여럿일 때의 모양, 한도가 있는 경로 함수(`paths`)를 셋째 그래프 함수로 둘지(원형 뒤에 정해요).
