# E2E 프로세스의 방향

> **제품 책임자가 지금은 E2E 프로세스의 요구사항을 구체화하지 않기로 했어요. KG를 구축하고 운영하는 기반이 먼저예요.**
> 이 문서는 인계받은 쟁점 가~마([테라리움에서 인계받은 것](../references/from-terrarium.md) 6절)를 조사하며 정리한 방향을, 다음에 다시 조사하지 않도록 남긴 거예요. **여기 적힌 것으로 요구사항이나 코드를 만들지 않아요.** 구체화할 때 결정 기록으로 다시 정해요.

## 1. 읽는 법

- **방향이지 결정이 아니에요.** "~로 정리했다", "~가 방향이다"라고 적었어요. 결정 기록도 요구사항 번호도 없어요. 구체화할 때 이 문서를 출발점으로 삼되, 약한 근거(쟁점마다 네 번째 항목)부터 다시 따져요.
- **근거의 표시.** 조사 보고서가 원문을 직접 읽어 확인한 것만 사실로 적었어요. 블로그, 벤더 글, 프리프린트, 단일 사례는 그렇다고 밝혔어요. 확인하지 못한 것은 가정이에요.
- **숫자는 모두 가정이에요.** 측정하지 않았어요.
- **쟁점별 절.** 가는 업무의 단위(2절), 나와 다는 위임(3절), 라는 에이전트 실행(4절), 마는 실제 툴(5절), 바는 중단되면 안 되는 것(6절)이에요. 사와 아는 ADR-0005가 이미 답했어요(7절). KG 기반이 이 방향을 위해 남겨 둔 확장 지점은 8절에 있어요.
- **제품 책임자가 정한 전제.** 실제 툴은 에이전트가 MCP 게이트웨이로만 호출하고 그 인증과 인가는 게이트웨이의 몫이에요. 현실 시스템은 읽기만 해요. 위임 전의 검증은 프락시움의 일이 아니에요.
- **이 메모 안에서만 쓰는 용어.** 용어집에 없어요. 구체화할 때 용어부터 다시 정해요.

| 용어 | 의미 |
|---|---|
| 업무 정의, 업무 | 에이전트에게 위임하는 E2E 프로세스 하나의 정의. 목표, 규칙, 범위 |
| 케이스, 케이스 이력 | 업무 정의에 따라 열린 작업 하나. 케이스에서 일어난 일을 추가 전용으로 적은 나열 |
| 규칙, 범위 | 지켜야 하는 것(고정 목록의 템플릿에서 선택). 케이스가 읽을 수 있는 객체와 변경할 수 있는 객체 |
| 액션, 툴 매핑 | 객체 타입마다의 동사. 객체 타입, 액션, 조건에서 게이트웨이의 서버, 툴, 인자로 가는 규칙 |
| 허가 토큰 | 준비된 조치 한 번, 그 인자에만 유효한, 프락시움이 서명한 토큰 |
| 위임 | 에이전트 버전에게 케이스 하나를 끝까지(업무 위임) 또는 당직을 일정 시간 동안(당직 위임) 위임하는 설정 |
| 조건 조합, 적용 단계, 실적 | 실적과 적용 단계를 따로 갖는 위임의 단위 하나. 초안, 그림자, 승인 적용, 자율 적용. 운영에서 쌓인 이력 |
| 에이전트 핑거프린트 | 모델, 프롬프트, 하네스 버전, 사용하는 툴 세트를 식별하는 값 |
| 배정, 리스, 대기, 브리핑 | 케이스를 세션이 지금 보유하고 있다는 기록. 그 유효 시간. 케이스가 기다리는 것의 기록. 새 세션을 위해 이력에서 만드는 요약 |
| 반환 | 케이스 전체를 사람 절차로 넘기는 것 |

## 2. 쟁점 가: 시나리오와 프로세스의 불일치

**인계받은 질문.** 업무를 플로차트로 그리면 분기가 곱으로 늘어요. 검증되지 않은 분기를 사람에게 넘기면 위임의 의미가 줄어요. 업무를 어떤 단위로 정해야 하나요?

**정리한 방향.** 업무는 플로차트가 아니라 **목표, 규칙, 범위**로 정하고, 진행 과정은 케이스 이력에서 읽어요.

| 업무 정의의 항목 | 담는 것 |
|---|---|
| 목표 | KG나 이력에서 확인할 수 있는 종료 조건, 반환 조건 |
| 범위 | 시작 객체에서 규칙(링크 타입, 방향, 홉 수, 영향 범위)으로 확장함. 읽기 범위와 변경 범위를 따로 둠 |
| 사용할 수 있는 액션 | 모델의 액션 중에서 선택함 |
| 규칙 | 아래 고정 목록의 템플릿에서 선택함 |
| 마일스톤 | 확인할 수 있는 중간 목표. 순서를 강제하지 않음(순서가 필요하면 규칙으로 적음) |
| 사람 작업 | 승인, 현장 작업. 담당(사람, 그룹, 그 객체를 담당하는 조직의 당직), 기한, 기한 초과 시 에스컬레이션 대상 |
| 출력 필드 | 에이전트의 판단을 받는 선택지 목록. 규칙의 조건은 텍스트를 읽지 않고 출력 필드의 값만 읽음 |
| 한도, 시작 조건 | 시간과 조치 수. 이벤트, 상태 변화, 스케줄, 사람의 요청(영향 범위가 겹치는 알람은 케이스 하나로 그룹화) |
| 현행 방식 표 | 누가, 무엇을, 얼마나, 유형(확인, 승인, 물리, 에스컬레이션). 측정의 베이스라인 |

규칙 템플릿은 처음 10종이에요. 새 템플릿은 결정 기록으로만 추가해요.

| 템플릿 | 의미 |
|---|---|
| 선행 / 후행 | B 전에 A가 있어야 해요 / A 뒤에 기한 안에 B가 있어야 해요 |
| 금지 / 후행 금지 | 하지 않아요 / A 뒤에는 B를 하지 않아요 |
| 횟수 한도 / 합계 한도 | 횟수 상한 / 동시에 내려가 있는 수나 영향 범위의 크기 상한 |
| 시간 윈도 | 정해진 시간 안에서만 해요 |
| 승인 필요 | 액션의 위험(4축)과 범위의 조건에서 승인자 수와 대상을 정해요 |
| 객체 잠금 | 같은 객체에는 케이스 하나만 변경해요 |
| 신선도 | 오래 관측하지 못한 객체에는 조치하지 않아요 |

- 규칙마다 강도(필수, 권고), 강제 지점(조치를 준비할 때 프락시움이 차단, 게이트웨이의 정책, 이력 감시), 위반 시 동작(차단, 승인 요구로 강등, 반환, 케이스 중단)을 적어요.
- 규칙 하나에서 강제하는 검사, 이력 감시, 에이전트에게 주는 안내 문장이 나와요. 손으로 따로 적지 않아요.
- 케이스는 열 때 업무 정의 버전, 규칙 버전, 에이전트 핑거프린트를 고정해요. 실행 중에 정의가 바뀌어도 그 케이스는 고정된 버전으로 끝나요.
- 케이스 이력은 이벤트마다 주체(사람 역할, 에이전트 핑거프린트, 프락시움), 내용, 이유, 관련 객체 여러 개, 두 시각(발생 시각, 기록 시각)을 담아요. 객체 중심 이벤트 로그(OCEL 2.0)로 내보낼 수 있는 구조예요.
- 진행 과정은 마일스톤에 도달한 순서와 시간이에요. 단계 수는 툴 호출이 아니라 마일스톤으로 세고, 단일 값이 아니라 분포로 보여요.
- 측정하는 것은 사람이 개입한 횟수, 소요 시간, 대기 시간(누구를 기다렸는지로 구분), 롤백, 반환, **위임 비율**이에요. 범위 밖이라 반환한 케이스도 분모에 넣어요. 적은 값(현행 방식 표)과 측정한 값은 따로 보여요.
- 긴급할 때 규칙을 끄는 방법은 없어요. 긴급 상황용 업무 정의를 따로 두고, 사용하면 사후 검토 케이스가 자동으로 열려요.
- 유지하는 것은 현행 방식 표, 조건의 고정 목록, 출력 필드, 위험의 축에 따른 승인 기본값, 범위 규칙, 시작 조건과 그룹화예요. 제외하는 것은 블록(분기, 반복, 병렬), 분기별 검증, 단계 완료 툴이에요.

**근거(조사에서 확인된 것).**
- 선언형 프로세스 모델(Declare, DCR)과 정책 언어(Cedar)는 모두 닫힌 템플릿과 기계 검사가 핵심이에요. 어휘를 열면 규칙이 분기 폭발의 새 이름이 돼요.
- 미완료 케이스도 감시할 수 있어요. Declare 계열 모니터링은 제약마다 "지금은 괜찮지만 나중에 위반할 수 있음"까지 구분해요.
- 객체 중심 이벤트 로그(OCEL 2.0)는 이벤트 하나가 서버, 랙, 티켓을 함께 가리키는 구조를 평탄화하지 않고 담아요. 객체와 링크로 된 KG와 구조가 비슷해요.
- 테라리움의 공개 리포지토리에는 "현행 방식" 표가 이미 코드로 있어요. 컬럼은 순번, 담당, 작업, 소요 시간, 유형이에요.

**약한 근거와 위험한 가정.**
- **가장 위험한 가정: 매번 다른 경로를 가는 에이전트의 이력에서 프로세스를 읽어 낸 선행 사례를 찾지 못했어요.** 프로세스 마이닝 기법은 성숙했지만 비결정적 경로에 적용한 증거는 없어요. 단계를 마일스톤으로 세는 것도 이 가정 위에 있어요. 구체화하면 합성한 이력으로 먼저 확인해요.
- 규칙 3개 이상이 얽힌 효과는 도구도 사람도 잡기 어려워요. Declare 계열은 제약 쌍까지만 신뢰할 수 있다고 저자가 밝혔어요. 저장할 때 서로 모순인 규칙을 검사하고 규칙별 위반 수를 보는 것으로 줄이려 했지만 충분한지 몰라요.
- 선언형 모델은 읽기 어렵다는 실험이 있어요(텍스트 표기가 오히려 나빴음). 학습 실험은 학생 20명 규모예요.
- 규칙을 언어 모델에게 작성시키면 누락이 남아요(한 연구에서 규칙 생성의 재현율이 70.96%, 프리프린트의 자기 보고). 규칙은 사람이 쓰고 모델은 초안 보조로만 써요.
- 선언된 베이스라인("A 업무는 몇 단계")이 실제보다 이상적이라는 것은 통념이고 정량 근거를 확인하지 못했어요.

**구체화할 때 정해야 할 것.** 마일스톤의 추상화 기준. 사람과 에이전트가 번갈아 하는 작업의 순서를 어디까지 규칙으로 적을지. 규칙 수의 상한. 템플릿 10종으로 충분한지. 출력 필드의 형식. 업무 정의를 어디에 저장하고 누가 검토하는지.

## 3. 쟁점 나와 다: 위임하는 범위와 위임의 종류

**인계받은 질문(나).** "실험장이 검증한 범위와 위임하는 범위가 같아야 한다." **질문이 바뀌었어요.** 제품 책임자가 위임 전의 검증을 프락시움의 일에서 뺐어요(ADR-0005). 검증은 사용자가 테라리움 같은 실험장에서 제품 밖에서 독립적으로 해요. 그래서 질문은 **"프락시움은 무엇을 보고 어디까지 위임하나"**가 됐어요. 답은 사람이 정한 범위와 운영에서 쌓은 실적이에요. 프락시움이 "위임해도 된다"를 아는 방법은 이 하나예요.

**인계받은 질문(다).** 케이스 하나를 끝까지 처리하는 것과 며칠 당직을 서며 들어오는 작업을 처리하는 것은 다른 능력이에요.

**정리한 방향.**
- **위임의 단위는 조건 조합이에요.** 업무 정의 버전, 객체 타입 그룹(범위), 권한 수준(보기만, 승인받고 조치, 스스로 조치), 액션 세트, 에이전트 핑거프린트의 조합이에요. 당직 위임은 동시에 보유하는 케이스 수가 더해져요. 실적과 적용 단계는 조합마다 따로 있어요.
- **위임 범위는 사람이 정하고 프락시움이 그 안에서만 위임해요.** 범위 밖의 객체에는 조치가 준비되지 않아요.
- **범위 밖의 케이스는 케이스 전체를 반환해요.** 폴백하는 단위가 분기에서 케이스로 올라가요. 판정은 케이스가 열릴 때 조건 조합이 실적을 가졌는지를 묻는 일이라 분기 수와 상관없어요.

| 적용 단계 | 하는 일 |
|---|---|
| 초안 | 정의만 있어요 |
| 그림자 | 실제 케이스에서 읽기만 해요. 하려던 조치를 기록해 사람이 실제로 한 것과 비교해요 |
| 승인 적용 | 조치마다 사람이 승인해요 |
| 자율 적용 | 스스로 조치해요 |

- **승격은 사람이 정해요.** 프락시움은 조합마다 실적을 보여 주고 승격할 수 있는 최소 조건을 강제해요. 그림자에서 비교한 케이스 수와 일치 비율, 승인 적용에서 연속으로 성공한 조치 수, 사후 확인 실패와 롤백과 규칙 위반이 한도 안일 것. 숫자는 업무 정의의 소유자가 정하고 기본값은 측정해서 정해요.
- **강등은 자동으로 돼요.** 조합마다 따로 강등돼요.
- **실적이 무효가 되는 경우.** 에이전트 핑거프린트가 바뀜, 업무 정의나 규칙이 바뀜, 롤백과 사후 확인 실패와 사람의 개입이 한도를 넘음, 오래 사용되지 않음. 무효가 되면 승인 적용으로 강등되어 실적을 새로 쌓아요. 한도를 넘어 강등되면 그림자까지 내려가요.
- 케이스가 진행되는 중에 핑거프린트가 바뀌면 케이스는 열 때의 핑거프린트를 고정해요. 새 핑거프린트의 조합이 자율 적용 실적이 없으면 남은 조치는 승인 적용으로 실행해요.
- **위임은 2종이에요.** 업무 위임은 케이스 하나를 끝까지예요. 당직 위임은 대상 업무 정의 목록과 객체 범위, 동시 케이스 상한, 우선순위, 초과 시 덜어 내는 규칙(load shedding), 응답 목표, 인수인계 메모를 가져요. 당직은 다른 능력이라 실적도 따로 쌓아요. 포함된 업무마다 업무 위임의 실적이 먼저 있어야 하고, 동시 케이스 상한은 1에서 시작해 실적에 따라 사람이 올려요. 객체 잠금과 동시 상한은 어느 쪽이든 프락시움이 강제해요.
- 당직을 측정하는 것은 응답 목표를 지킨 비율, 대기 중인 케이스의 경과 시간, 우선순위가 역전된 횟수, 인수인계 메모가 빠진 케이스예요.
- **승인.** 기본값은 액션의 위험에서 가져오는 것으로 정리했어요(조사 때의 예: 읽기 0명, 롤백할 수 있음 1명, 롤백할 수 없음 2명. 4축에 어떻게 대응시킬지는 구체화할 때 정해요). 승인은 그 조치 한 번, 그 인자에만 유효해요. 자기가 수정한 업무 정의 버전의 배포는 스스로 승인하지 못해요. 업무마다 6가지 역할이 있어요: 소유자, 편집, 배포 승인, 시작, 조치 승인, 보기.
- 사용자가 밖에서 한 검증의 근거는 배포를 승인하는 사람이 케이스에 첨부할 수 있어요. 이력으로 남을 뿐 프락시움이 읽어 계산하지 않아요.

**근거(조사에서 확인된 것).**
- 자율성 수준 체계들이 수준과 범위를 나눠요. 한 체계(AWS의 범위 구분표)는 할 수 있는 것(agency)과 얼마나 독립적으로 정하는지(autonomy)를 별개 축으로 두고, 다른 체계(Knight 연구소 제안)는 수준만 있고 범위 차원이 없어요. 한 클라우드 SRE 에이전트 제품은 검토와 자율 모드를 대응 계획 단위로 정하고, 2~4주 검토로 관찰한 뒤 반복 승인되는 패턴만 자율로 승격하라고 안내해요.
- 강등을 소급하지 않고 에이전트 단위로 추적한 오픈소스 사례가 있어요(문서 1건).
- 당직은 케이스 능력과 달리 응답 시간 목표, 부하 상한, 과소 부하의 문제라고 Google SRE 책이 말해요. 과소 부하도 숙련을 해쳐요. 에이전트가 거의 쓰이지 않는 조합은 실적이 낡기 쉬워요.
- 요청자와 승인자를 분리하는 것(four-eyes), 시간 제한 승인은 AWS 범위 구분표가 통제로 열거해요.

**약한 근거와 위험한 가정.**
- 승격과 강등의 기준은 제품마다 사람의 판단이거나(검토 모드), 수치를 공개하지 않은 프리프린트예요. 정량 기준의 증거는 약해요.
- 실적은 드문 상황을 말해 주지 못해요. 한 번도 일어나지 않은 분기는 실적에 없어요. 그래서 롤백할 수 없는 액션의 자율 적용에는 게이트웨이의 단계 2가 필요하고(5절), 규칙은 경로가 아니라 결과를 차단해요. 드문 상황의 검증은 사용자가 제품 밖에서 해요.
- 표본이 적으면 말할 수 있는 것이 적어요. 실패 0건이어도 30건이면 실패율 10% 이내라고밖에 말할 수 없다는 것은 일반 통계 상식이고, 별도 출처를 확인하지 못했어요.
- 호출마다 승인하면 사람이 훑고 누르게 돼요(승인 피로). 이를 줄이려고 계획 단위로 승인하는 방식을 생각했지만 실증 연구를 찾지 못했어요. 인자에 묶은 승인 토큰은 개발자 블로그 2건 수준이에요.
- 업무 정의, 규칙, 환경이 바뀌는 속도는 모델이 바뀌는 속도와 달라요. 모델 호스팅이 고정된 버전을 제공하는지는 확인하지 못했어요.

**구체화할 때 정해야 할 것.**
- 승격 최소 조건의 기본값(케이스 수, 일치 비율, 연속 성공 수, 한도).
- 케이스가 진행되는 중 에이전트 핑거프린트가 바뀔 때의 처리(위의 방향이 맞는지 제품 책임자에게 확인).
- 버전이 섞인 케이스를 누구의 실적으로 셀지.
- 표본이 적은 드문 액션을 어떻게 다룰지(조사 보고서에서는 승인 적용에 머무르게 두자는 의견이 나왔어요).
- 액션의 위험은 KG의 모델에서 등급 하나가 아니라 4축이에요(8절). 승인 기본값을 축에 어떻게 대응시킬지.
- 당직의 부하 연동 강등을 둘지.

## 4. 쟁점 라: 업무 전체를 위임받은 에이전트의 실행 방식

**인계받은 질문.** 며칠 걸리는 케이스에는 대기와 중단이 있어요. 에이전트가 어떻게 재개하나요?

**정리한 방향.** 프락시움은 하네스가 아니에요. 에이전트를 실행하지 않아요. 팀이 자기 에이전트와 하네스를 가져오고, 세션은 쓰고 버려도 돼요. 기준 데이터는 케이스 이력에 있어요. 세션을 저장했다가 복원하는 방식(체크포인트)에는 의존하지 않아요.

| 인터페이스 | 내용 | 특징 |
|---|---|---|
| 작업 인터페이스 | 프락시움의 MCP 서버. 에이전트가 호출해요 | 상태를 보유하지 않아요. 인가는 MCP 규격(OAuth 2.1)을 따라요 |
| 풀 인터페이스 | HTTPS와 JSON. 하네스 측의 얇은 실행기가 롱 폴링으로 배정을 가져가요 | 하트비트를 보내고 완료를 보고해요. "깨운다"는 가져갈 배정을 만든다는 의미예요 |

작업 인터페이스의 툴은 조사 때 이렇게 정리했어요: `get_briefing`, `get_events`, `find_objects`, `get_object`, `get_neighbors`, `get_impact`, `get_changes`, `list_actions`, `prepare_action`, `get_action`, `report_action`, `set_output`, `request_wait`, `hand_over`, `return_case`. 이름은 구체화할 때 정해요.

- **리스와 순번.** 배정은 리스 시간 동안 유효하고 하트비트로 연장해요. 끊기면 다른 세션이 가져가요. 가져갈 때마다 순번이 오르고, 상태를 변경하는 모든 요청은 (배정, 순번)을 확인받아요. 늦게 깨어난 옛 세션은 기록하지 못해요.
- **조치는 먼저 기록해요.** `prepare_action`이 의도, 조치 번호, 기준이 된 KG 버전을 이력에 남긴 뒤에 에이전트가 게이트웨이로 호출하고 `report_action`으로 보고해요. 보고가 없는 조치는 **알 수 없음** 상태로 남고, 재시도하기 전에 관측(읽기 툴, 다음 동기화)으로 확인해요. 조치 번호는 멱등 키예요.
- **대기는 이력의 정식 항목이에요.** 타이머, 승인, 외부 이벤트(기대 효과가 다음 동기화에서 보임), 사람 작업(현장 작업). 마감과 에스컬레이션 규칙이 있고, 대기하는 동안 세션은 종료돼도 돼요.
- **브리핑은 코드가 만들어요.** 목표, 규칙, 범위, 수행한 일, 열린 조치(알 수 없음 포함), 대기, KG의 신선도를 고정된 형식으로 줘요. 원문은 `get_events`로 따로 읽어요. 알람과 티켓의 텍스트처럼 외부에서 온 텍스트는 출처와 신뢰 등급을 붙여 데이터로만 실어요. 요약을 언어 모델에 위임하지 않아요. 같은 이력이면 같은 브리핑이에요.
- **재개를 전제로 두지 않아요.** 승인 적용에서 세션이 교체된 뒤에도 문제없이 끝난 케이스의 실적이 있는 조건 조합만, 여러 세션에 걸친 케이스를 자율 적용으로 실행해요. 그 실적이 쌓이기 전에는 세션이 교체된 뒤의 첫 변경 조치가 승인을 받아요.
- 상태. 케이스: 열림, (진행 중 ⇄ 대기), 종료 또는 반환 또는 중단. 배정: 가져갈 수 있음, 보유 중, 종료 또는 리스 만료.
- 푸시(웹훅, A2A)는 힌트이거나 선택 어댑터로만 두고, 정확성은 풀에 의존해요. 하네스가 내부망에 있어도 되고 누락된 깨우기가 없어요.

**근거(조사에서 확인된 것).**
- 하네스는 소모품이고 기준 데이터는 하네스 밖의 추가 전용 이력이라는 방향이 여러 1차 자료에서 같아요(장기 작업 하네스 글, 관리형 에이전트 글, 이슈 트래커를 이력으로 삼는 오케스트레이터 사양).
- MCP 최신 규격(2026-07-28)은 프로토콜 세션, 서버가 먼저 보내는 요청, 연결 재개를 제거했어요. 구독은 활성 상태인 클라이언트 연결이 전제라 깨어 있지 않은 에이전트를 깨우지 못해요. 작업 확장(tasks)은 방향이 반대(에이전트가 서버의 긴 작업을 기다림)이고 유효 시간이 있어요. 그래서 깨우기는 MCP 밖에 둬요.
- 리스만으로는 안전하지 않아요. 만료를 모르고 기록하는 옛 세션은 단조 증가하는 순번(fencing token)으로 차단해야 해요(Kleppmann).
- 체크포인트 재개는 도구가 한 번 이상 실행될 수 있다고 ADK 문서가 직접 경고해요. 그래서 의도를 먼저 기록해요.

**약한 근거와 위험한 가정.**
- **"로그만 보고 안정적으로 재개한다"는 주장에 강한 증거가 없어요.** 합의의 근거 대부분은 코딩 에이전트 사례이고, 며칠짜리 운영 케이스(물리 작업 대기, 변경 윈도)에서 검증된 공개 사례를 찾지 못했어요.
- 한 워크숍 초록은 중단이 평균 성공률을 41.7%에서 28.0%로 낮췄고, 18개 설정 중 11곳에서 구조화 요약이 전체 이력보다 나았다고 해요. 초록만 확인했고 표본과 모델이 적어요. 되감기 연구는 자기 보고이고 외부 서비스에 미친 효과는 되돌리지 못한다고 스스로 밝혔어요.
- 단일 세션이 수 시간 작업한다는 근거(METR 시간 지평)는 코딩, ML, 보안 과제 위주예요. 며칠짜리 대기와 중단이 낀 운영 케이스의 증거가 아니에요.
- 리스 시간과 하트비트 간격의 예(90초, 30초)는 조사 보고서의 예시이고 측정하지 않았어요.
- 게이트웨이가 허가 토큰이나 멱등 키를 검증할 수 있는지, 하네스 측이 실행기를 붙일 수 있는지, 아웃바운드 폴링이 허용되는지는 확인하지 못했어요.
- 알람과 티켓 텍스트가 이력에 섞여 다음 세션에 다시 들어가는 경로(기억 오염)가 있어요. 방어의 효과는 확인하지 못했어요. 최종 방어선은 게이트웨이의 최소 권한이에요.

**구체화할 때 정해야 할 것.** 리스 시간과 하트비트 간격, 같은 배정이 거듭 끊길 때 사람에게 에스컬레이션하는 기준. 푸시 어댑터를 둘지. 브리핑의 필드와 길이. 세션을 임의 시점에 중단하고 재개하는 성공률을 어떻게 측정할지. 케이스 이력의 신뢰 등급 이름. 케이스 하나를 병렬로 나눠 보유할지(처음에는 케이스당 배정 하나로 단순하게 시작하자는 의견이 있었어요).

## 5. 쟁점 마: 실제 툴은 실험장에 없다

**인계받은 질문.** 툴은 에이전트가 MCP 게이트웨이로만 호출해요. 게이트웨이가 검증 호출을 실험장으로 보내는 경로가 제품이 분리된 뒤에도 성립하나요?

**정리한 방향.** **실제 툴이 제대로 동작하는지는 운영의 단계와 이력으로 확인해요.** 게이트웨이가 검증 호출을 실험장으로 보내는 경로는 포기해요. 그림자와 승인 적용 단계, 사후 확인이 실제 툴의 검증이에요.

- **툴 매핑은 프락시움의 몫이에요.** 객체 타입, 액션, 조건에서 서버, 툴, 인자 규칙으로 매핑해요. 객체를 하나씩 연결하지 않아요. `prepare_action`이 호출할 서버, 툴, 채워진 인자를 줘요. 에이전트는 변경 조치의 인자를 스스로 구성하지 않아요(알람 텍스트에 속아도 인자가 바뀌지 않아요).
- **읽기만 하는 액션(`mutates`가 아님)은 준비 없이 호출해요.** 진단이 프락시움에 의해 차단되지 않아요.
- **액션의 위험은 프락시움의 모델이 정해요.** MCP 툴의 주석(`readOnlyHint` 등)은 신뢰하지 않고 대조하는 데만 써요.
- 매핑은 선언형으로 두고(액션에서 서버, 툴, 인자 템플릿), 조건은 모델의 속성만 읽게 해요.

| 단계 | 게이트웨이가 제공하는 것 | 올라갈 수 있는 적용 단계 |
|---|---|---|
| 0 | 툴 목록을 읽게 해 줘요 | 그림자까지 |
| 1 | 에이전트 신원을 전달하고 호출 이력(인자 포함)을 읽게 해 줘요 | 승인 적용까지. 롤백할 수 있는 액션은 자율 적용까지 |
| 2 | 외부 인가 연동으로 허가 토큰을 확인해요(호출의 툴과 인자를 토큰과 대조) | 롤백할 수 없는 액션도 자율 적용까지 |
| 3 | 툴 정의가 바뀌면 알려 주거나 고정해 줘요 | 단계는 그대로. 없으면 프락시움이 툴 목록의 핑거프린트를 주기적으로 읽어 비교해요 |

- 단계 1에서는 차단하지 못하고 탐지할 뿐이에요(이력의 호출과 준비한 인자를 사후에 대조). 그래서 롤백할 수 없는 액션은 자율 적용으로 두지 않아요.
- 허가 토큰은 프락시움이 서명하고 수명이 짧아요. 조치 번호, 서버와 툴, 인자의 해시, 에이전트 신원을 담아요. 특정 표준 초안에 묶지 않아요.
- 툴 매핑마다 그림자, 승인 적용, 자율 적용 순으로 신뢰를 쌓고 변경 범위도 객체 하나에서 그룹으로 넓혀요.
- **사후 확인.** 조치의 기대 효과가 독립된 관측(다음 동기화)에서 보이는지 확인해요. 안 보이면 실패예요.
- **자동으로 강등되는 경우.** 툴의 입력 스키마 핑거프린트가 바뀜, 사후 확인 실패, 이력의 호출이 준비한 인자와 다름, 이력에 호출이 없음, 실패 한도 초과.
- 조치마다 적는 것: 조치 번호, 케이스, 액션, 객체, 기준 KG 버전, 준비한 서버, 툴, 인자의 해시, 승인, 허가 토큰, 게이트웨이 이력과 대조한 결과, 보고, 사후 확인. 프락시움의 추적 키(케이스 번호, 조치 번호)를 MCP 요청의 `_meta`에 실어 게이트웨이 이력과 연결하고, 개발 중인 관측 규약의 이름에는 의존하지 않아요.

**근거(조사에서 확인된 것).**
- 확인한 범위에서 게이트웨이가 흔히 제공하는 것은 서버와 툴 단위 접근 제어, 호출자 식별(JWT 클레임), 호출 로그예요. 인자 수준 정책은 제품마다 편차가 커요. 정의 고정(핀닝)과 서명된 허가의 오프라인 검증은 드물고, 한 제품은 자동 핀닝이 아직 없다고 밝혔어요.
- 검증 호출을 환경에 따라 다른 곳으로 라우팅한다고 문서로 밝힌 게이트웨이를 찾지 못했어요. 헤더 기반 라우팅을 지원하는 곳도 확인되지 않았어요.
- MCP 툴 주석은 힌트일 뿐 보장이 아니고, 신뢰할 수 없는 서버의 주석은 무시해야 해요(MCP 블로그).
- 인자에 묶는 허가의 표준은 아직 없어요. 가장 가까운 두 개인 초안(트랜잭션 토큰, 축소 가능한 토큰)은 만료됐거나 채택 전이에요. 관례를 차용해요.
- 액션을 사전에 정의한 카탈로그에서 호출하는 방식은 오래된 패턴이에요. 한 데이터 플랫폼의 액션 타입 문서가 비슷한 구조예요(객체 변경 배치, 파라미터, 권한 검증).

**약한 근거와 위험한 가정.**
- **게이트웨이 여러 개와 일반 운영 관행은 출처를 직접 대조하지 못했어요.** 표의 "없음"은 "확인한 문서에 없음"이지 "기능 없음"이 아니에요. 단계 표는 흔한 것, 일부, 드문 것으로 확인된 범위에서 구성했어요.
- `prepare_action`의 출력은 권고가 아니라 허가 토큰 발급과 짝일 때만 통제예요. 게이트웨이가 허가 토큰 없는 쓰기를 거부하지 못하면 편의 기능에 그쳐요. 그 환경에서는 허용 목록, 로그, 사후 탐지로 솔직하게 적어야 해요.
- 에이전트가 `prepare_action`을 건너뛰고 직접 호출하는 경로를 게이트웨이가 차단하지 못하면 인자를 채우는 이득이 사라져요.
- 사후 확인은 동기화 주기만큼 늦고, 일시적이거나 늦게 나타나는 효과는 판정이 모호해요. 도구가 거짓 성공을 반환할 때를 잡으려면 독립된 읽기 경로가 있어야 해요.
- 드라이 런(서버 측 사전 점검)은 도구마다 편차가 커서 일반화하지 못해요. 부작용이 없다는 보장도 도구별로 확인해야 해요.
- 매핑 규칙이 조건 로직을 쌓아 작은 프로그래밍 언어가 될 위험이 있어요.

**구체화할 때 정해야 할 것.** 게이트웨이가 제공할 수 있는 단계(소유자에게 확인). 허가 토큰의 형식과 수명. 툴 목록 핑거프린트의 주기. 액션 타입에 사전 점검 지원 여부를 둘지(조사에서는 있으면 승인 화면에 결과를 붙이고, 없으면 위험 등급을 한 단계 올리자는 제안이 있었어요). 이력의 변조 방지를 요구할지(확인한 게이트웨이 중 제공하는 곳이 없었어요). 툴 매핑의 입력 스키마 핑거프린트가 바뀐 뒤 재승격 방법.

## 6. 쟁점 바: 운영 경로가 되면 중단되면 안 된다

**인계받은 질문.** 어디까지를 중단해도 되는 것으로 두고 어디부터 고가용으로 만드나요?

**정리한 방향.** 이 쟁점의 KG 측(질의, 동기화, 이력, 스토리지)은 ADR-0011과 ADR-0009가 정해요. 위임과 조치에 관련된 부분은 이렇게 정리했어요.

- **배정, 조치 준비, 승인은 잃으면 안 되는 것이에요.** 중단되면 새 조치가 준비되지 않아 에이전트가 멈추고, 사람은 사람 절차로 처리해요. **자율 적용인 업무가 생기기 전에 "중단되면 안 됨"으로 올려요.**
- 케이스 이력, 승인, 조치 결과, 대기와 타이머도 잃으면 안 돼요. 기록하지 못한 결과는 에이전트 측에 쌓였다가 다시 전달돼요.
- 측정과 업무 정의 편집은 중단돼도 돼요.
- 작업 큐, 타이머, 리스는 단일 진실 공급원(KG 기반과 같은 스토리지) 위에 두는 것으로 정리했어요. 별도 브로커나 내구 실행 엔진이 필요한지는 구체화할 때 측정해서 정해요(ADR-0006의 원칙: 단일 진실 공급원은 하나, 나머지는 용도에 맞게). 리스와 타이머는 케이스 이력 스키마에 둬요. 깨우기는 주기적인 폴링이 기본이고 알림은 속도를 높이는 선택지예요.

**중단됐을 때의 약속** (프락시움은 툴 호출 경로 밖에 있어요).
- 이미 허가받은 호출 한 건은 끝내요. 새로 변경하는 조치는 시작하지 않아요. 허가 토큰의 짧은 수명이 이것을 강제해요(게이트웨이 단계 2). 단계 0과 1에서는 에이전트의 약속과 사후 대조에 의존해요.
- 승인은 fail-closed로 동작해요. "전에 허용했으니 허용"하는 캐시를 두지 않아요.
- 결과 보고는 거절하지 않아요. 부하를 줄일 때도 가장 마지막에 차단하고, 조치 번호로 멱등이에요.
- 읽기 툴은 프락시움을 거치지 않아서 진단은 계속돼요.
- 복구된 뒤에는 게이트웨이의 호출 이력을 두 번째 기준 데이터로 삼아 케이스 이력과 대조해요.
- 동기화가 실패하면 마지막 정상 KG 버전에 머물고 신선도가 나빠져요. 오래 관측하지 못한 객체에는 조치를 준비하지 않아요(신선도 규칙). 이 KG 측 동작은 ADR-0011이 정해요.

**고가용을 나중에 추가할 수 있게 처음부터 지키는 것.** 서버는 상태를 보유하지 않아요. 모든 상태는 스토리지 한 곳이에요. 처리기는 멱등이에요. 케이스 이력은 추가 전용이에요. KG 버전은 바뀌지 않아요. 프로세스 안의 단일 인스턴스에 의존하지 않아요. 같은 스케줄이 두 번 실행되지 않게 키로 차단해요. 이것들은 KG 기반 설계에도 같은 것이 적용돼요(ADR-0011).

**근거와 약한 근거.**
- 근거: 잃으면 안 되는 것과 중단돼도 되는 것을 나눈 점은 테라리움의 설계에서 이어졌어요. 현실 시스템을 변경하는 경로가 프락시움에 없으므로 중단돼도 현실에 아무 일이 없다는 전제가 있었고, E2E 프로세스가 들어오면 이 전제가 깨져요.
- 약한 근거: 허용 가능한 데이터 손실 시간과 복구 시간의 숫자는 측정하지 않았어요. 모두 가정이에요. 합성한 규모로 측정해서 정해요.
- 약한 근거: 허용 결정을 캐시하지 않는 약속은 게이트웨이 단계가 낮으면 에이전트의 약속에 의존하는 정도에 그쳐요.

**구체화할 때 정해야 할 것.** 허용 가능한 데이터 손실 시간과 복구 시간. 승인과 조치 준비를 "중단되면 안 됨"으로 올리는 시점과 방법. 결과 보고를 가장 마지막에 차단하는 순서의 구현. 허용 결정을 캐시하지 않을 때의 지연이 괜찮은지.

## 7. 쟁점 사와 아

- **사(경계의 형식).** 경계가 없어졌어요. 프락시움과 테라리움은 서로를 몰라요(ADR-0005). KG의 한 범위를 공개된 형식의 파일로 내보내는 일반 기능은 우선순위가 낮은 후순위예요.
- **아(용어 겹침).** 두 제품이 이어지지 않으니 프락시움 안에서는 생기지 않아요. 테라리움 문서를 읽을 때만 조심해요. 거기서 "운영"은 실험 유형이고 "승인"은 가상의 상대가 규칙대로 응답하는 것이에요.

## 8. KG 기반이 이 방향을 위해 남겨 둔 확장 지점

KG 기반이 이 방향의 요구사항을 미리 만들지 않아요. 다만 나중에 전면 재작업하지 않도록 아래 확장 지점을 일부러 남겨 뒀어요.

| 확장 지점 | KG 기반의 결정 | 이 방향이 나중에 쓰는 곳 |
|---|---|---|
| 액션 타입의 목록과 위험의 축 | 타입 등록부에 액션 타입(이름, 대상 타입, 위험의 4축, 선언한 효과, 롤백 액션)을 둬요. 지금은 목록과 의미만 두고 실행과 툴 매핑은 두지 않아요. 축은 `mutates`, `reversibility`, `disruption`, `physical`이에요(ADR-0007, REQ-100) | 사용할 수 있는 액션, 승인 기본값, 툴 매핑의 키, 사후 확인이 읽는 기대 효과 |
| 범위 계산에 쓰일 링크 의미 | 링크 타입마다 고정된 11종 중 하나의 의미를 가져요. 영향 범위가 이 의미로 계산돼요(ADR-0007, ADR-0010, REQ-101, REQ-141) | 업무의 범위 규칙(링크 타입, 방향, 홉 수, 영향 범위), 합계 한도와 객체 잠금 |
| 이중화 그룹과 하나 더 | `exposure` 질의가 하나만 더 장애 나면 장애가 되는 객체를 답해요(ADR-0010, REQ-102) | 조치 전에 영향 범위를 확인하는 규칙, 동시에 내려가 있는 수의 한도 |
| 신선도 | 신선도는 객체가 아니라 소스의 수집과 속성(그것을 소유한 피드)에 걸려요. 모든 질의 응답에 붙어요(ADR-0009, ADR-0011, REQ-108, REQ-152) | 신선도 규칙(오래 관측하지 못한 객체에는 조치하지 않음), 브리핑의 신선도 |
| 근거 등급 | 모든 값과 링크와 응답에 사실, 가정, 알 수 없음이 붙어요(ADR-0007, REQ-103) | 브리핑과 사후 확인이 읽는 값의 신뢰도, 모르는 것을 안전하다고 읽지 않기 |
| 읽기 전용 MCP | KG를 읽는 MCP 서버가 사전 정의 질의를 제공해요. 응답에 KG 버전이 붙어요(ADR-0010, ADR-0016, REQ-149) | 작업 인터페이스의 읽기 툴(이웃, 영향 범위, 변경). 이름은 구체화할 때 정해요 |
| KG 버전과 변경 사항 | 바뀌지 않는 KG 버전과 `changes` 질의, 변경 알림(ADR-0009, ADR-0010, REQ-130, REQ-135, REQ-144) | 조치의 기준 KG 버전, 사후 확인(기대 효과가 다음 동기화에서 보임), 시작 조건의 상태 변화 |
| 권한과 담당자 | 사람과 그룹은 SSO에서 오고, 권한 부여는 누구 × 역할 × 범위, 소스와 타입과 정의의 항목마다 담당자(연락처), 서비스 계정(ADR-0012, REQ-160, REQ-161, REQ-163) | 사람 작업에서 "그 객체를 담당하는 조직의 당직", 업무마다 6가지 역할, 에이전트의 신원 |
| 가용성 등급 | KG 질의는 중단되면 안 되고 이력은 잃으면 안 돼요(ADR-0011, REQ-154) | 6절의 등급 확장. 배정과 조치 준비가 같은 스토리지와 같은 약속 위에 얹혀요 |
| 구조 | E2E 프로세스의 단위(업무, 케이스, 위임)는 그 작업을 구체화할 때 추가해요(ADR-0006) | 유닛 방향과 계약 유닛에 추가하는 지점 |

## 9. 관련 결정과 요구사항
