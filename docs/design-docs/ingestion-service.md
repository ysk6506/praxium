# 수집 서비스와 실행

[ADR-0058](adr/0058-sources-from-db-and-api-worker-ingestion-and-editing-screens.md)의 자세한 내용 가운데 수집을 돌리는 쪽이에요. **이 문서는 아직 구현하지 않은 설계(예정)예요.** 지금은 명령줄(`ingest run`)만 수집하고, 계획은 소스 하나를 읽고, 실행 기록이 남지 않아요. 소스 정의와 어댑터는 [소스와 어댑터](sources-and-adapters.md)에, 정의를 쓰는 경로와 화면은 [정의의 쓰기, 시크릿, 경로, 화면](source-editing.md)에 있어요. 정의 오류의 구조화와 쓰지 않고 차이를 내는 길은 별도의 변경이 구현하고 있어요. 예시의 이름과 숫자는 지어낸 것이에요.

## 1. 목적과 범위
- 여러 소스의 자료가 하나의 KG로 이어지게 해요(3절). 소스가 다르면 링크도 값 붙이기도 안 되던 한계를 풀어요.
- 수집을 서버가 돌려요. 워커의 수집 부분이 **받기**(소스에서 읽어 오는 일)와 **적용**(KG에 반영하는 일)을 나눠서 해요(5절). 배치와 스트림이 갈리는 자리가 여기예요.
- 정의를 바꾸면 소스를 다시 읽지 않고 **다시 계산**해요(6절). 확인을 기다리는 적용과 안전장치를 둬요(7절).
- 이번 구현은 배치(전체 읽기)뿐이에요. 스트림과 증분 수집, 스케줄, 원격 수집기, PostgreSQL 저장소에서의 수집은 이름과 자리만 둬요(12절).

## 2. 개요
```
소스 A ─받기(소스마다 나란히, 4개까지)─┐
소스 B ─받기─────────────────────────┼─▶ 받은 것(레코드의 묶음, 완전성, 소스, 데이터셋)
                                       │        │ (함수 호출이 아니라 자료 모양으로 끊어요)
                                       │        ▼
                                       └─▶ 적용(KG마다 차례로): 원본 레코드에 반영 → KG 전체를 다시 계산
                                                    → 차이 → 안전장치 → (확인 대기) → 변경 배치
```
받기는 소스를 읽기만 하고 KG를 몰라요. 적용은 소스를 몰라요. 둘 사이의 자료 모양이 [수집 설계](ingestion.md) 7.2의 "수집 변경 로그" 자리예요.

## 3. KG 단위의 계획과 상태 2판

### 3.1 지금과 바뀌는 것
| 기제 | 지금 | 바뀌는 것 |
|---|---|---|
| 계획 | 소스 하나와 매핑 하나 | KG의 모든 소스 정의와 모든 매핑 정의에서 만들어요 |
| 데이터셋의 이름 | 매핑 안의 이름 | 피드와 정제가 `<소스 id>.<데이터셋 id>`로 가리켜요 |
| id의 범위 | 문서 안 | 피드, 정제, 링크 정의의 id는 KG 안에서 겹치지 않아요. 링크 정의는 어느 매핑 문서의 피드든 id로 가리켜요 |
| 상태 | 소스별 한 파일(1판) | 소스별(실행 번호, 데이터셋의 원본 레코드와 안 보인 횟수)과 KG 단위(식별 색인, 만든 객체와 링크, 키, KG 순번)로 갈라요(2판) |
| 입력 | 상태에 열려 있는 원본 레코드 | 같아요. 모든 소스의 열려 있는 원본 레코드를 읽어요 |
| 닫는 판단 | 데이터셋의 원본 레코드마다(완전한 수집 3회와 24시간) | 같아요. 객체는 그것을 받치는 행이 어느 소스에도 없을 때 닫혀요 |
| 근거 참조 | `소스/데이터셋/키`라는 글자 | **글자를 그대로 유지해요.** 바뀌면 모든 객체가 "바뀜"이 돼요 |

한 소스를 새로 받으면 그 소스의 원본 레코드만 바뀌어요. 그래도 KG 전체를 다시 계산하는 것이 맞아요. 지금도 파이프라인의 입력은 캡처가 아니라 상태의 원본 레코드라서 식별, 값 붙이기, 폐기, 닫힘의 유예가 코드 그대로 성립해요(코드를 따라가 확인했어요).

- **아직 한 번도 받지 않은 소스**의 피드를 가리키는 링크와 값은 문제가 아니라 "그 소스를 아직 받지 않음"으로 따로 세요.
- 받지 않은 데이터셋의 걸러진 행은 붙든 채로 둬요. 다른 소스의 실행이 유예를 앞당기지 않아요.
- 메모리: 실행마다 모든 소스의 원본 레코드가 메모리에 올라요. 지금의 한계([ADR-0041](adr/0041-cli-usability-local-mode-and-keeping-ingestion-results.md))가 소스 수만큼 커져요. 한도와 권장 크기는 [기본값 표](defaults.md)에 "예정"으로 있고 서버 모드의 권장 메모리를 안내서에 적어요.

### 3.2 KG 순번과 차례
값이 겹칠 때의 우선순위는 순위, 나중에 받은 것, 피드의 차례예요([파이프라인 설계](pipeline.md) 3.2). 소스별 실행 번호는 소스 사이에서 견줄 수 없어요(50번 돌린 소스의 옛 값이 2번 돌린 소스의 새 값을 이겨요). 그래서:

- "나중"은 **KG 단위의 순번**이에요. 적용마다 하나 오르고([수집 설계](ingestion.md) 7.2의 `ingest_seq`의 자리) 원본 레코드가 열릴 때 찍혀요. 옛 레코드는 옛 차례대로 번호를 받아요. 소스가 하나인 옛 폴더에서는 소스 안의 차례가 유지돼요.
- 피드의 차례는 문서가 여럿이면 정해지지 않으므로 **피드 id의 글자순**으로 정해요. 피드를 도는 차례(식별의 결과에 닿아요. 먼저 돈 피드의 키가 새 객체의 ID가 돼요)도 같은 순서로 고정하고 테스트로 잠가요.
- 값의 시각: 값이 다른 소스에서 이번 계산으로 새로 이기면 그 행의 데이터셋을 마지막으로 받은 시각을 써요. 그래서 상태 2판의 데이터셋마다 받은 시각이 있어요.

### 3.3 알려진 한계
- 병합이 없어서 **소스를 받은 순서에 따라 같은 것이 두 객체가 될 수 있어요.** 새 객체의 ID는 처음 본 키에서 나와요. 소스 A가 약한 키만, 소스 B가 강한 키만 주고 둘을 잇는 행이 나중에 오면 "키가 이미 다른 객체의 것"이라고 알리고 그대로 둬요.
- 소스 사이에서 링크가 차수를 넘칠 때 남는 쪽은 정해진 순서이지 뜻이 있는 순서가 아니에요. 문제 문장에 그렇게 적어요.
- 그 문제들을 보이는 검증은 받는 순서를 바꾼 두 소스로 해요(10절).

## 4. 실행의 종류
| 종류 | 받는 것 | 하는 일 |
|---|---|---|
| 전체 읽기 | 소스의 데이터셋 전부(지금은 언제나 전부) | 받고 적용해요 |
| 다시 계산 | 없음 | 저장된 원본 레코드와 머리 정의로 계산해 차이를 적용해요 |

**다시 계산**은 매핑만 고친 사람이 KG에 반영하려고 실제 소스를 다시 읽지 않게 해요. 같은 길에서 적용을 빼면 정의 변경의 **정확한 미리 보기**(표본이 아니라 전부, 기존 KG와의 차이까지)가 돼요. 이것은 지금 머리 정의로 보는 것이라 브랜치의 정의로 후보 KG를 만드는 드라이 런([정의 설계](definitions.md))과 정의의 출처가 달라요. 이 설계는 "미리 보기"라는 낱말을 쓰고 브랜치와 관계없어요.

### 4.1 정의를 바꾼 뒤의 규칙
정의를 바꾸면 KG 전체에, 어느 소스든 다음에 돌 때 반영돼요. 그래서 세 가지를 정해요.

- **받은 때의 선언.** 원본 레코드의 데이터셋 상태에 받은 때의 소스 정의 리비전을 적어요. 그 뒤 컬럼이나 자연 키가 바뀐 데이터셋은 "다시 받아야 함"이 돼요. 그 소스를 다시 읽기 전의 계산은 그 데이터셋을 **받은 때의 선언**으로 읽어요(리비전은 지워지지 않으니 읽어 올 수 있어요). 그렇지 않으면 바뀐 컬럼이 비어서 그 소스의 객체가 유예 없이 닫혀요.
- **피드를 지우거나 깨뜨림.** 유예는 행이 사라지거나 걸러질 때만 있어서, 매핑을 저장한 사람과 다른 소스를 돌린 사람이 다르면 객체가 곧바로 닫혀요. 안전장치가 잡아요(7.3). 저장할 때 다시 계산의 미리 보기가 "이 저장으로 객체 N개가 닫힌다"를 보여요.
- **정의는 뒤로 가지 않아요.** 전체를 다시 계산하므로 마지막으로 적용한 정의 세트보다 옛 세트로 적용하면 그 사이의 변경이 KG에서 되돌려져요. KG 단위의 상태에 마지막으로 적용한 세트 번호를 두고 그보다 옛 세트의 적용을 거절해요.

실행은 시작할 때의 정의 세트를 실행 기록에 남기고, **받기**는 그 소스의 정의 리비전을 고정해서 끝까지 돌아요. **적용**은 그때의 머리 정의로 해요. 받은 소스의 리비전이 그 사이에 바뀌었으면 받은 것을 버리고 실패로 끝내요.

## 5. 받기와 적용

### 5.1 유닛과 포트
새 코어 유닛이에요(작업 이름 `core.ingestrun`). "API 역할이 수집을 한다"가 아니라 "한 프로세스에 함께 뜬 **워커의 수집 부분**"이에요([ADR-0008](adr/0008-ingestion.md) 결정 24, [ADR-0018](adr/0018-secrets-and-encryption.md) 결정 4 그대로). 조립에서 워커 부분으로 따로 묶어요. 시크릿을 복호화하는 것은 이 부분의 어댑터뿐이에요.

- **받기**: 소스마다 하나이고 서로 나란히 돌아요(동시에 도는 받기는 4개까지). 한 소스의 받기는 겹치지 않아요(이미 돌고 있으면 409). 배치는 한 번 읽고 끝나요. 스트림은 뒤에 이 길에 "붙어 있는 받기"로 들어와요.
- **적용**: KG마다 하나씩 차례로 해요. 받은 것을 받아 원본 레코드에 반영하고 KG 전체를 다시 계산하고 차이를 적용해요. 줄에 선 받은 것 여럿을 **한 번의 계산으로 묶어** 적용할 수 있어요(소스 다섯을 한꺼번에 누르면 계산이 다섯 번이 되지 않게 해요). 그래도 실행 기록은 각각 남아요. 적용 ID와 실행 기록은 1:N이에요.
- 서비스의 포트: (가) 전체 읽기를 한 번 요청한다 (나) 실행 기록을 읽는다 (다) 취소, 확인, 버리기 (라) 점검, 소스 탐색, 미리 보기. 스트림의 "받기 상태를 묻고 바꾼다"는 이름만 정하고 뒤에 더해요.
- 포트는 `core.ingest`의 타입을 드러내지 않아요. 정의는 JSON 바이트로, 실행 기록은 이 유닛의 타입으로 주고받아요.
- 스트림과의 이음: 스트림에서는 이 자리가 "보류"와 "해제·폐기"가 돼요([수집 설계](ingestion.md) 9.2). 같은 낱말(확인, 버리기)과 같은 역할(`run_sources`)을 써요.

### 5.2 PostgreSQL 저장소와 여러 인스턴스로 갈 때 바뀌는 것
다시 쓰지 않도록 포트 둘로 끊어 둬요. 이번 구현은 파일과 메모리예요.

| 포트 | 하는 일 | 바뀌는 것 |
|---|---|---|
| 실행 기록 저장소 | 실행 기록을 읽고 써요 | 파일에서 PostgreSQL로 |
| 실행의 조정 | 차지하기, 살아 있음 알리기, 취소 요청 읽기 | 프로세스 안에서 작업 리스(ADR-0011)로. 늦게 깨어난 쪽의 쓰기는 번호로 막아요 |

PostgreSQL 저장소에서는 수집을 쓸 수 없어요(상태의 저장이 파일뿐이에요). 쓸 수 없는 서버는 "쓸 수 없음"과 이유를 코드로 답해요(9절).

## 6. 반쯤 된 적용의 정리와 취소

**문제.** 적용은 조각 단위로 쓰여서 중간에 끊기면 머리에 반쯤 된 적용이 남고 다른 적용을 모두 막아요.

- 실행이 취소나 실패로 끝나면 서비스가 그 적용을 **버려요**(`Abandon`). 서버가 뜰 때 남아 있으면 먼저 버려요. 적용 ID는 시도마다 달라요(실행 자원의 id). 큰 적용에서는 임대를 갱신해요.
- **예정 상태.** 적용하기 전에 새 상태를 적용 ID와 함께 "예정"으로 먼저 써요. 뜰 때 머리의 마지막 적용 ID와 견줘 같으면 예정을 올리고 다르면 버려요. 이렇게 안 하면 적용 뒤 상태를 저장하기 전에 죽었을 때 KG에는 있고 상태에는 없는 객체가 생기고, 폐기는 상태의 목록만 보므로 아무도 닫지 않아요.
- 취소가 닿는 자리는 받기 중(컨텍스트)과 적용의 조각 사이예요. 마지막 조각 뒤 상태를 저장하기 전에 죽은 경우는 위 예정 상태가 정리해요.
- 테스트: 조각이 둘 이상인 적용을 중간에 끊고 다시 띄워 다른 소스가 곧바로 도는지, 같은 소스가 바뀐 내용으로 다시 돌 때 KG가 한 실행의 내용만 가지는지, 마지막 조각 뒤에 죽이고 소스에서 행을 빼고 세 번 돌린 뒤 객체가 닫히는지 봐요.

## 7. 확인 뒤 적용과 안전장치

### 7.1 적용 방식 둘
- `auto`: 받고 곧바로 적용해요.
- `after_review`: 받고, 계산하고, **차이를 요약해 보이고 멈춰요.** 확인하면 적용하고, 버리면 원본 레코드도 바뀌지 않아요.

차이의 요약은 새로 생길 객체와 링크의 수, 바뀔 수, 닫힐 수, 닫히기를 기다리는 수, 타입별 표본, 문제 목록이에요. 이것을 내려면 `core.graph`에 쓰지 않고 차이만 세는 길이 필요하고 별도의 변경이 만들고 있어요.

### 7.2 확인할 때 다시 계산해요
기다리는 사이에 다른 소스의 적용이 지나가면 요약한 차이가 낡아요. 계산한 배치와 상태를 들고 기다리면 확인한 순간 옛 값이 새 값을 덮어요. 그래서:

- **들고 있는 것은 받은 레코드의 묶음과 완전성뿐이에요.** 메모리에만 둬요. 디스크에 두면 소스의 자료가 평문으로 한 벌 더 생겨요.
- 확인하면 그때의 상태와 머리 정의로 **다시 계산해요.** 바뀌는 것의 목록(종류, ID, 옛 해시, 새 해시)의 해시가 보였던 것과 다르면 적용하지 않고 다시 보여요. 저장소의 배치 다이제스트는 값의 시각이 들어 있어 실행마다 달라서 쓰지 않아요.
- 서버가 다시 시작하면 실행은 실패로 닫혀요. 한도 시간(기본 1시간)이 지나면 `canceled`와 이유가 남아요.
- 기다리는 실행이 있는 소스의 새 실행 요청은 409예요. **다른 소스의 적용은 막히지 않아요.**
- 확인과 버리기의 능력은 이미 있는 `confirm_guards`를 써요.

### 7.3 안전장치
소스의 첫 적용, 정의 세트가 바뀐 뒤의 첫 적용, 불완전한 수집(지금도 닫지 않아요), 대량 소실에서는 `auto`로 요청해도 `after_review`가 돼요([ADR-0008](adr/0008-ingestion.md) 결정 20의 일부를 지금 구현해요. REQ-118). 수신한 스키마의 변경은 뒤의 일이에요.

- 대량 소실의 분모는 KG 전체가 아니라 **객체 타입**이에요. KG 전체이면 작은 피드 하나가 통째로 사라져도 걸리지 않아요. 기준은 [기본값 표](defaults.md)의 것(10%이면서 5건, 또는 500건)이에요.
- 첫 적용과 대량 소실의 판단은 쓰지 않고 세는 길 없이 돼요(닫을 수는 배치에 있어요). 서비스 단계에 넣어요.

### 7.4 명령줄의 규칙
`ingest run`은 요청한 사람이 그 자리에서 결과를 보는 경로예요. 그래서 **차이의 요약을 출력하고 그대로 적용해요**(지금의 동작). 멈추려면 플래그를 줘요(이름은 구현할 때 정해요). 대량 소실만은 명령줄에서도 멈추고 플래그로 넘어가요. 소스의 첫 적용과 `-times N`이 지금처럼 한 번에 되도록 하는 것이 목적이에요.

## 8. 실행 기록
자원 `sync-run`은 **전체 읽기 한 번(또는 다시 계산 한 번)의 기록**이에요. 스트림의 상태는 여기에 섞지 않아요(계획된 `feed-flows`의 자리). 계약의 모양을 먼저 정하고, Go 구조체의 JSON 태그를 계약으로 삼지 않아요. 계약의 모양에서 `ingest.Report`로 옮겨요.

**상태**는 작업의 낱말을 써요.

| 상태 | 뜻 |
|---|---|
| `queued`, `running` | 줄에 섰어요 / 돌고 있어요 |
| `awaiting_confirmation` | 차이를 보이고 확인을 기다려요 |
| `succeeded`, `failed` | 끝났어요. "문제가 있었다"는 상태가 아니라 건수 필드예요. 중단은 `failed`와 오류 코드예요 |
| `cancel_requested`, `canceled` | 취소를 요청했어요 / 취소됐어요 |

**필드.** `id`, `kg`, `source_id`, `dataset_ids`(지금은 언제나 전부), `receive_mode`(`full`), `apply`(`auto`, `after_review`), `definition_set`, 시작한 사람과 시각, `stage`(받기, 계산, 확인 대기, 적용), 데이터셋별 건수(받음, 읽음, 쓰임, 걸러짐, 문제), 문제 종류별 개수, `diff_summary`, `guard_verdict`, KG의 새 버전, 닫히기를 기다리는 객체 수, 경고(POST로 읽음, TLS 확인 끔).

**문제를 둘로 갈라요.** 전체를 다시 계산하면 식별 충돌, 붙을 대상이 없는 값, 소스 간 충돌, 링크의 대상 없음, 차수 위반이 모든 소스의 모든 행에 대해 매번 나와요. 한 실행 기록에 섞으면 안 돼요.

| | 뜻 | 쓰임 |
|---|---|---|
| 실행의 문제 | 이번에 받은 데이터셋의 행에서 난 것 | 행 수의 대조(받음 = 읽음 + 못 읽음, 읽음 = 쓰임 + 걸러짐 + 문제 + 안 쓰임)와 짝이 맞아요. 표본의 한도는 여기에만 써요 |
| KG의 문제 | 지금 열려 있는 모든 것 | 계획된 `issues`의 자리. 이번에 열지 않아도 실행 기록에 섞지 않아요 |

다른 소스의 행에서 **이번 적용으로 새로 생긴** 문제(A를 받았더니 B의 링크가 끊겼다)는 따로 세어 건수로 내요.

- 문제 표본은 하위 자원 `/samples`로 떼고 권한을 따로 걸어요. 실행마다 파일 하나, 소스마다 최근 50개를 보관해요. 값이 든 문장이 자료 폴더에 평문으로 남으므로 폴더를 넘길 때 함께 간다는 것을 안내서에 적어요.
- 소스의 읽기 응답에는 마지막 실행의 참조(`last_sync_run`)를 둬요. 소스의 `status`는 다른 것이고 뒤의 일이에요.
- 확인을 기다리는 상태와 필드는 REST 읽기를 열 때부터 계약에 있어요(나중에 더하지 않아요).
- 값이 많은 실행이 API의 응답과 메모리를 나눠 써요(12절).

## 9. 수집을 쓸 수 있는 서버, KG 만들기, 해시 키
- **쓸 수 있는 서버**는 파일 저장소로 뜬 서버예요. `local`이 첫 대상이에요. 기능 전체가 플래그 하나로 잠겨요([정의의 쓰기, 시크릿, 경로, 화면](source-editing.md) 5절). 메모리 저장소, PostgreSQL 저장소, 데모 폴더에서는 수집 경로가 "이 서버에서는 수집을 쓸 수 없다"와 이유를 코드로 답해요.
- **KG 만들기.** 서비스가 뜰 때 폴더에 KG가 없으면 `main`을 만들고 상태 파일과 짝지어요(지금 명령줄의 판정 표 그대로). `local`은 빈 폴더(없으면 만든다)에서 뜰 수 있어요. 실행 자원에 `kg`를 둬요(지금은 `main`만).
- **KG별 해시 키.** 기밀 등급 값의 키 기반 해시는 지금 공개된 고정 키를 써요. 서비스가 새로 만드는 KG는 KG를 만들 때 무작위 키를 만들어 **자료 폴더 안**에 둬요(자료와 같은 등급. 폴더와 함께 움직이고 명령줄이 그냥 읽어요). 시크릿 저장소와 마스터 키에 묶지 않아요. 마스터 키가 없는 기계로 폴더를 옮겨도 KG가 굳지 않게 하려는 거예요. 옛 폴더는 옛 키를 쓴다고 폴더에 적어 둬요. 이 일은 서비스 단계의 일이에요. [시크릿과 암호화](secrets-and-encryption.md) 12.3을 이 설계가 고쳐요.
- 명령줄의 `ingest run`도 같은 서비스를 지나요(서버가 폴더를 쥐고 있지 않을 때). 실행 기록이 같은 자리에 같은 모양으로 남아요. 데이터 폴더가 있으면 정의 파일을 저장소에 직접 적용한 뒤 그 소스를 받아요. 데이터 폴더가 없는 메모리 실행은 지금 그대로예요.

## 10. 옛 폴더 옮기기
상태 1판의 폴더를 새 서버가 열 때예요.

- **정의를 가져오기 전에는 실행을 받지 않아요**(소스가 하나여도). 옛 폴더에는 정의가 저장소에 없어요(지금까지 저장한 적이 없어요). 원본 레코드는 있는데 정의가 없는 소스가 있으면 실행을 거절하고 그 소스들의 정의를 가져오라고 안내해요. 정의 없이 다시 계산하면 그 객체들이 닫혀요.
- 소스가 하나면 식별 색인, 객체, 링크, 키를 KG 단위로 그대로 옮겨요.
- **소스가 여럿인 옛 폴더**의 식별 색인을 합칠 때 같은 키가 서로 다른 객체에 묶여 있으면 소스 id의 글자순으로 앞의 것을 남기고 몇 개였는지 보고해요. 진 쪽의 객체는 다음 계산에서 행을 잃어 닫혀요.
- **옮긴 뒤의 첫 적용은 언제나 확인 대기**예요. 소스 정의는 가져왔는데 그 소스를 읽던 매핑이 없으면 객체가 유예 없이 닫히기 때문이에요.
- 1판 파일은 지우지 않고 다른 이름으로 남겨요.
- 피드, 정제, 링크 정의의 id는 상태에 들어 있지 않아서(색인의 키, 근거 참조, 걸러진 행의 키 어디에도 없어요) id를 바꿔도 상태는 이어져요. 따로 쓴 옛 매핑 파일 둘의 피드 id가 겹치면 어느 문서의 무엇과 겹치는지를 말해요.

## 11. 검증
단계마다 그 단계가 연 길의 끝에서 끝까지를 넣어요(서비스는 취소와 다시 시작). 여러 소스는 아래를 봐요.

- 소스 둘이 같은 객체를 채울 때, 한쪽에서 사라질 때, 한쪽을 아직 받지 않았을 때, 받는 순서를 바꿨을 때.
- 소스 정의의 컬럼을 바꾸고 다른 소스를 돌렸을 때(받은 때의 선언).
- 확인을 기다리는 사이에 다른 소스가 적용됐을 때(다시 계산해 다시 보여요).
- 적용한 뒤 상태를 저장하기 전에 죽고 그 사이에 소스가 바뀐 경우.
- 소스가 여럿인 옛 폴더, 폴더를 옮겨 마스터 키가 없는 경우에도 수집이 되는지.
- 20만 행 실행 중에 API의 응답 시간과 프로세스의 메모리. 실행 중에 정의를 저장했을 때 실행이 시작할 때의 리비전으로 끝나는지.

## 12. 알려진 한계와 미결
- 수집과 API가 한 프로세스라서 큰 실행은 API와 메모리를 나눠 써요. 한도와 권장 크기는 측정해서 정해요.
- 스케줄, 스트림, 증분 수집, 원격 수집기가 없어요. 실행은 사람이 눌러요. 일정은 정의이므로 따로 설계해요.
- PostgreSQL 저장소와 여러 인스턴스에서는 수집을 쓸 수 없어요(5.2).
- 미결: 여러 받은 것을 묶는 적용의 세부(몇 개까지 묶는지), 명령줄에서 멈추는 플래그의 이름.
