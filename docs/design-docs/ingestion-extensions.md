# 받기를 넓히는 길

[현실 데이터 받기](ingestion.md)와 [파이프라인](pipeline.md)에 이어지는 덧붙임이에요(ADR-0008, ADR-0010). 여기서 더한 기능은 모두 `/v1`의 자원으로 내요([자원 (3)](rest-api-resources-additions.md)).

## 1. 밀어 넣기
- **가져오기가 기본이고 밀어 넣기는 받는 방식 `stream`의 한 꼴이에요**(이미 있어요).
- 밀어 넣는 길은 소스마다 정의로 열어요(기본은 닫힘). 시스템 계정으로 인증하고, 같은 것을 여러 번 보내도 한 번만 반영돼요(보낸 쪽의 사건 ID). 차례는 `source_time`으로 가려요.
- 밀어 넣은 것도 같은 실행기와 안전장치와 행 셈을 지나요.
- 밀어 넣기만 하는 소스는 빠진 것을 알 수 없어요. 맞춰 보기(스냅샷)를 함께 두기를 권하고, 없으면 완전함을 선언하지 못해요.
- 단계: 받기를 넓히는 단계, 알파 안.

## 2. 지정해서 다시 받기(targeted refresh)
객체 하나나 몇 개를 지정하면 그 객체에 값을 대는 공급들의 소스에서 **그 객체의 것만** 지금 다시 읽어 같은 길로 적용해요. 작업(operation)으로 돌고, 답에 무엇이 바뀌었는지와 속성마다의 `source_time`과 적용된 변경 번호가 실려요.
- 프리셋이 "열쇠로 하나 읽기"를 할 수 있는지 선언해요(`keyed_read`). 못 하는 소스는 가장 좁은 범위의 읽기로 대신하거나 "이 소스는 못 한다"고 답해요. 속성마다 어느 소스가 다시 읽혔고 어느 것이 못 읽혔는지 적혀요.
- 소스 보호의 한도 안에서 돌아요. 주체마다 한도가 있고 일정의 실행보다 앞선 차례를 가져요.
- **지움을 만들지 않아요.** 그 객체가 소스에 없다는 답은 "없음을 봄"으로 적고, 물러나게 하는 것은 보통의 규칙이 해요.
- 이어서 받는 소스의 속성은 다시 읽을 것이 없어서 "이 시각 뒤의 값이 올 때까지 기다리기"로 답해요.
- **열쇠로 하나 읽기는 되도록 저절로 얻어요**(사용자가 소스마다 따로 등록하지 않아요). 프리셋에 들어 있고, SQL 어댑터는 데이터셋의 열쇠 칸(식별에 이미 선언돼 있어요)에 조건을 붙여 저절로 만들어요. 파일 소스는 그 파일을 다시 읽어 그 줄만 써요. HTTP JSON 어댑터는 목록 요청에 거르는 인자가 선언돼 있으면 그것을 쓰고, 한 건의 길이 따로 있으면 사용자가 길의 틀 한 줄을 더할 수 있어요(없어도 돼요). 어느 것도 없으면 가장 좁은 범위의 읽기로 대신하고 그 비용을 소스의 화면과 답에 보여요. 소스를 만들 때 "한 건 다시 받기가 되나"를 지어낸 열쇠가 아닌 실제 한 건으로 시험해 보는 길이 있어요.
- 단계: 알파(HTTP JSON과 SQL 어댑터의 열쇠 읽기부터). MCP의 읽는 면에도 내요.

## 3. 기대와 견주기
묻는 쪽이 "이 객체의 이 속성이 이 값이어야 한다"와 기준 시각(액션을 한 시각)을 주면, 답은 속성마다 이 넷 중 하나예요(ADR-0010, `kg-queries.md`).

| 값 | 뜻 |
|---|---|
| `confirmed` | 기준 시각 뒤에 소스에서 본 값이 기대와 같아요 |
| `not_yet` | 기준 시각 뒤에 본 값이 아직 없어요 |
| `contradicted` | 뒤에 본 값이 기대와 달라요 |
| `unverifiable` | 다시 읽을 수 없는 소스예요 |

기다릴 한도를 줄 수 있어요. 영향 범위처럼 이웃에 번지는 것의 확인은 같은 변경 번호를 `min_seq`로 주고 물으면 돼요.

**확인의 근거는 소스에서 본 것이어야 해요.** 액션을 한 쪽이 "내가 이렇게 바꿨다"고 밀어 넣은 값은 근거의 종류가 `declared`이고 `observed`가 아니에요. 견주기는 `observed`만으로 `confirmed`를 내요. 한 쪽의 말로 스스로를 확인하지 못해요.

프락시움은 실제 시스템에 쓰지 않아요(ADR-0001). 다시 받기는 읽기예요. 액션의 실행은 프락시움 밖의 일이고, 이 결정은 그 뒤의 확인에 필요한 KG 쪽 기반만 정해요(E2E 프로세스는 구체화하지 않아요).

## 4. 매핑을 만드는 사람을 돕는 길
화면의 모양은 클로즈 베타의 일이고 여기서는 화면이 기댈 API만 정해요.
1. **스키마만 보고 매핑하지 않아요.** 데이터셋을 볼 때 컬럼의 이름과 값 타입과 함께 견본 줄, 컬럼마다의 통계(빈 값의 비율, 서로 다른 값의 수, 흔한 값, 값의 꼴)를 줘요. 견본과 통계는 민감 등급과 읽기 권한을 따라요.
2. **매핑의 제안(`suggest`).** 데이터셋과 객체 타입을 주면 컬럼과 속성의 짝을 까닭과 함께 내놔요: 이름의 비슷함, 값 타입이 맞는지, 값의 꼴(식별자의 꼴, 단위), 같은 프리셋이나 같은 타입의 다른 공급이 쓴 짝. 식별에 쓸 컬럼의 후보도 내요(값이 서로 다르고 비지 않은 것, 이미 있는 식별자와 겹치는 비율). 제안은 정해진 규칙으로만 만들고(같은 입력이면 같은 답) 저절로 적용하지 않아요. 사람이 받아들인 것만 브랜치에 적혀요.
3. **타입 쪽에서 보기.** 객체 타입 하나에서 속성마다 "어느 공급이 대나, 비어 있나, 얼마나 채워졌나, 배치인가 실시간인가"를 봐요(타입의 공급 표, 이미 있어요). 비어 있는 속성에서 시작해 댈 수 있는 데이터셋의 후보를 찾는 길을 더해요.
4. **미리 보기.** 저장하기 앞에 견본 줄 몇 개가 어떤 객체와 링크가 되는지(식별이 기존 객체에 붙는지 새로 만드는지, 타입이 안 맞아 떨어지는 값)를 보여요. 전체에 돌린 결과의 차이는 브랜치의 후보 실행이 보여요.
5. 프리셋이 있는 소스는 기본 공급이 들어 있어 매핑 없이 시작해요.

## 5. 표로 저절로 떨어지지 않는 소스 데이터: 문서, 나무, 줄
1. 원본 데이터셋에 **읽어 들이기** 단계를 둬요. 어댑터가 받은 것은 줄의 묶음이 아닐 수 있어요(문서 하나, 글 덩어리). (가) **해석기**가 문서를 **나무**(이름 붙은 가지와 값, 차례 있는 목록)로 만들고, (나) **줄 고르기**가 나무에서 "무엇이 한 줄인가"와 "그 줄의 컬럼은 어느 가지인가"를 길(경로)로 골라 표를 만들어요. 위쪽 가지의 값을 아래 줄에 내려 붙일 수 있어요(장비의 이름을 그 아래 인터페이스 줄마다). 그 뒤는 여느 표와 같아요.
2. **해석기는 제품에 든 닫힌 목록이에요**(사용자 코드는 없어요): JSON과 줄마다 JSON, XML, CSV와 구분자 글, 너비가 정해진 글, 열쇠=값과 구획이 있는 설정 글, YAML, **들여쓰기로 층을 이루는 설정 글**(네트워크 장비의 설정처럼 줄과 들여쓰기로 된 것을 층 그대로 나무로 만들어요), **줄 틀로 읽기**(정렬된 글 표나 명령의 출력처럼 꼴이 정해진 글을 이름 붙은 잡기와 상태의 옮김으로 된 틀로 읽어요). 새 해석기는 결정 기록으로 더해요.
3. **줄 틀은 데이터예요.** 프리셋처럼 판이 있고 지어낸 견본으로 도는 시험이 있어야 실려요. 조직이 자기 틀을 `org` 이름 공간에 만들 수 있고 브랜치와 제안을 거쳐요. 틀의 말은 닫혀 있어요(정규식의 잡기, 상태, 줄을 내는 때, 위 값을 채워 넣기). 돌고 도는 일이 없게 줄마다 한 번 읽고 정규식은 물러서기가 폭발하지 않는 것만 써요.
4. **맞지 않은 것을 숨기지 않아요.** 해석기가 못 읽은 줄과 틀에 안 맞은 줄은 버리지 않고 세요(행 셈의 "읽지 못함" 칸). 그 비율에 기대 조건을 걸 수 있고 견본을 볼 수 있어요. 나무의 모양이 바뀌면(없던 가지, 사라진 가지) 받은 모양이 바뀐 것으로 다뤄요.
5. **만드는 사람을 돕는 길.** 견본 문서를 올리면 해석기의 후보와 나무를 보이고, 나무에서 가지를 고르면 길이 만들어져요. 줄 틀은 견본 줄에서 잡을 곳을 고르면 초안이 나와요. 결과의 표를 그 자리에서 미리 봐요(4절과 같은 길).
6. **범위 밖**: 사람이 쓴 자유로운 글, 그림, 스캔 문서에서 뜻을 뽑는 일은 제품이 하지 않아요. 밖의 에이전트가 뽑아 밀어 넣을 수 있고 그 값의 근거는 `declared`예요.
7. **의존성**: 해석기는 표준 라이브러리로 짜요. YAML만 표준 라이브러리에 없으므로 쓰는 부분 집합을 직접 읽거나 허용 라이선스의 라이브러리 하나를 까닭과 함께 들여요(구현하는 변경이 정하고 결정 기록에 남겨요).
8. 단계: JSON, XML, CSV, 열쇠=값, 들여쓰기 설정 글은 알파의 얇은 한 줄 다음(받기를 넓히는 단계). 줄 틀과 YAML도 알파 안이에요.
9. **정제한 데이터셋을 타입에 매핑하는 것은 이미 돼요.** 정제 데이터셋은 여러 원본이나 다른 정제 데이터셋을 입력으로 받아(소스가 달라도 돼요) 조인, 유니언, 고르기, 모으기, 겹친 것 없애기를 한 결과이고, 공급은 원본이든 정제든 데이터셋에 붙어요. 정제를 여러 겹으로 이을 수 있고 고리는 막아요. 계보는 속성, 공급, 정제의 연산, 원본 컬럼, 소스까지 이어져요.

## 6. 설계 담당에게 묻는 것
- 밀어 넣기의 한 번 보내는 양과 사건 ID를 기억하는 기간.
- 매핑의 제안에서 이름의 비슷함을 어떤 규칙으로 재는지(정해진 규칙이라는 것만 정해졌어요).
- 지정해서 다시 받기의 주체마다 한도 값.

## 7. 관련
ADR-0008, ADR-0010. 요구사항: REQ-224(밀어 넣기), REQ-225(지정해서 다시 받기), REQ-226(기대와 견주기), REQ-227(매핑을 돕는 길), REQ-228(문서, 나무, 줄).
