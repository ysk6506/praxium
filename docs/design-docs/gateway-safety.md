# 게이트웨이의 안전

[게이트웨이 설계](gateway.md)가 구성과 흐름을 다루고, 이 문서는 그것이 안전하려면 무엇을 지켜야 하는지를 다뤄요(ADR-0061). 아직 구현하지 않았어요. 숫자는 모두 측정하지 않은 가정이에요.

## 1. 목적과 다루는 질문

| 쟁점 | 답 |
|---|---|
| 무엇을 믿고 무엇을 믿지 않는가 | 코어가 가장 믿는 구성요소이고, 에이전트와 툴의 결과는 믿지 않아요(2, 3절) |
| 정의를 누가 바꿀 수 있는가 | 게이트웨이 정의는 R3 이상이고 자동 병합이 없어요(4절) |
| 프락시움이 멈추면 | 에이전트는 아무것도 바꾸지 못해요(5절, 장애 표) |
| 긴급하면 | 사람이 시작하는 긴급 프로세스뿐이고 규칙을 끄는 길은 없어요(5절) |
| 언제 여는가 | 확인할 수 있는 증거가 모이면 열어요(7절) |
| 미결 사항 | 9절 |

## 2. 신뢰의 경계

- 코어와 게이트웨이를 나누는 것은 자격 증명이 코어 밖으로 나가지 않게 할 뿐이에요. 코어가 뚫리면 판단이 뚫려요. 그래서 코어의 보호(접근 통제, 관리자 인증, 기록의 변조 방지)가 여는 조건의 첫째예요.
- 게이트웨이가 스스로 갖는 것은 셋이에요.
  1. 업스트림 주소와 자격 증명은 게이트웨이 쪽 설정에 있고, 코어의 레지스트리는 이름만 가리켜요.
  2. 허용하는 바꾸기 업스트림 툴과 호출 한도(업스트림 서버별, 실행별)의 두 번째 사본.
  3. 호출 이력을 코어가 아닌 곳(조직의 로그 수집)으로 직접 내보내요.
- 위험이 큰 액션은 승인자의 서명을 게이트웨이에서 확인하고 업스트림 서버가 권한을 직접 검사하는 것을 목표로 해요. 목표일 뿐 지금 약속하지 않아요.
- 세 겹의 안전은 권한(누가 어느 액션을 하는가), 상태(지금 해도 되는 상태인가), 결과(했더니 맞는가)예요. 한 겹이 뚫려도 다음 겹이 막게 해요.

## 3. 보안 원칙

1. 에이전트와 툴의 결과를 믿지 않아요.
2. 기본은 거절이에요. 판단할 수 없으면 막아요.
3. 프락시움이 죽어도 사람의 길은 열려 있어요. 프락시움은 에이전트의 문이고 사람의 문이 아니에요.
4. 권한의 실체는 정의예요. 정의를 통제하는 것이 권한을 통제하는 것이에요.
5. 자격 증명을 나눠요. 받은 토큰을 업스트림에 넘기지 않아요.
6. 기록 없이 바꾸지 않아요. 추가 전용 스토어, 해시 체인, 조직 보안 도구로 내보내기가 있고, 기록을 쓸 수 없으면 변경을 거절해요. 인자는 해시와 가린 요약으로 기록해요.
7. 사람의 인증은 조직의 SSO(OIDC)를 쓰고, 첫 설치, 서비스 계정, 긴급용으로 내장 인증을 둬요.
8. 폭주를 통제해요. 실행별 호출, 객체, 시간 한도, 영향이 큰 일의 사람 승인, 전체와 실행 하나와 업스트림 서버 하나에 대한 정지 스위치가 있고, 판단 지점에 기대지 않고 동작해요.
9. 정책은 포트 뒤에서 직접 구현해요. OPA나 Cedar는 필요할 때 선택 어댑터로만 둬요. 판단 코드는 입력 묶음의 순수 함수이고 입력을 기록해 재현하며, 판단 테스트 모음이 여는 조건에 들어가요.

## 4. 정의의 통제

- 게이트웨이 정의의 종류는 프로세스, 액션과 툴의 연결, 툴 승인, 조건 제거, 한도 완화, 업스트림 서버 등록이에요.
- 위험 등급의 하한이 R3이고 자동 병합과 자동 첫 적용에서 빠져요([에이전트 시대의 정의](definitions-at-agent-scale.md)).
- 권한을 넓히는 리버트는 긴급 경로를 쓸 수 없어요.
- 이 종류의 승인자는 관리자 두 명이 지정해요.
- 바꾸는 툴을 켠 설치는 셀프 승인(`solo_approval`)을 거절해요. 승인자가 한 명뿐인 조직은 바꾸는 툴을 쓸 수 없어요.
- 특정 시점 복구 뒤에는 바꾸는 툴이 닫힌 채 시작하고 툴 승인을 다시 확인해요.
- 직무 분리는 작성자, 승인자, 툴 승인자가 서로 달라야 해요. 승인은 내용 해시에 묶여요.

## 5. 가용성과 긴급

**프락시움이 멈추면 에이전트는 아무것도 바꾸지 못해요.** 이것을 숨기지 않아요.

- 1차에서는 "코어가 멈추면 게이트웨이도 전부 막는다"예요. 읽기도 막아요. 읽기를 계속하는 것은 측정한 뒤에 더해요.
- 게이트웨이는 버릴 수 없는 것(호출 전 기록, 정지 상태)을 작은 로컬 저널에 둬요. 그러려면 게이트웨이마다 내구성 있는 디스크가 필요해요. 죽은 게이트웨이의 저널에만 있는 결과는 대장에서 "모름"으로 남아요.
- 정지 신호는 코어의 것과 다른 관리자 긴급 키로도 낼 수 있어요.
- 바꾸는 툴을 켠 설치는 에이전트가 바꿀 수 있는 인프라와 분리된 기반이 필요해요. 프락시움이 의존하는 객체는 자동 변경에서 빼요.
- 게이트웨이는 상태가 없고 둘 이상이에요. 멱등 키로 장애 전환 중 같은 호출이 두 번 가지 않게 하고, 결과를 모르는 호출은 확인이 풀 때까지 "모름"이에요.
- 긴급 프로세스는 정식 종류예요. 사람이 시작하고, 호출마다 승인하고, "확인 못 함" 조건은 승인 화면에 보이고, 사후 검토가 자동으로 열려요. 긴급하다고 규칙을 끄는 길은 없어요. 1차에서는 열지 않고 방향만이며 2차 안에서 열어요.

### 장애 종류별 동작 (1차)

| 장애 | 읽기 | 변경 | 진행 중인 실행 | 기록 | 정지 신호 |
|---|---|---|---|---|---|
| 코어 정지 | 막아요 | 막아요 | 의도는 대장에 남아요. 새 호출은 막아요. 이미 나간 호출의 결과는 게이트웨이 저널에 있고 대장에서는 "모름" | 저널과 조직 로그로 내보낸 것에 남아요 | 게이트웨이가 직접 받아요(긴급 키) |
| DB 정지 | 막아요 | 막아요 | 코어 정지와 같아요 | 쓸 수 없으니 변경을 거절해요 | 게이트웨이가 직접 받아요 |
| 소스 정지 | 값이 낡으면 "확인 못 함"으로 보여요 | 조건이 "확인 못 함"이면 "아직"이고 승인 화면에 보여요 | 확인이 `unverifiable`로 남고 사람에게 넘겨요 | 정상 | 정상 |
| 게이트웨이 일부 정지 | 남은 게이트웨이가 받아요 | 남은 게이트웨이가 받아요. 멱등 키로 이중 전송을 막아요 | 정지한 쪽의 결과를 모르면 "모름" | 정상. 정지한 쪽의 저널은 복구 때 합쳐요 | 남은 게이트웨이가 받아요 |
| DB 복제본 하나 정지 | 정상 | 동기 복제와 "기록 없이 변경 없음" 때문에 전체 변경이 멈출 수 있어요 | 변경이 멈추면 대기 | 쓸 수 없는 동안 변경 거절 | 정상 |
| 프락시움이 올라간 기반의 장애 | 코어 정지와 같아요 | 막아요 | 코어 정지와 같아요 | 조직 로그로 내보낸 것에 남아요 | 긴급 키 |

DB 정지 행은 "판단할 수 없으면 막는다"에서 이어 낸 판단이에요. 측정하고 훈련한 뒤에 다시 봐요.

## 6. 승인 피로

- 승인 시간이 지나면 거절이에요. 자동 승인은 없어요.
- 승인 화면에 조건의 증거, 영향 요약, 평소와 다른 점을 보여요.
- 승인자별 건수, 걸린 시간, 거절률을 지표로 봐요.
- 업그레이드할 때 진행 중인 실행은 시작할 때의 정의 집합을 유지해요.

## 7. 단계와 여는 조건

순서는 KG 쪽 선행 조건(읽기 전용 MCP 인터페이스, API와 DB 소스와 지정 재수집, 범위가 있는 권한, 감사 로그 저장) → 게이트웨이의 읽기 툴 → 바꾸는 툴 1차 → 2차예요. 릴리스 서명과 출처 증명은 읽기 툴 단계로 앞당겨요. 이미 한 것은 `SECURITY.md`, 워크플로 액션 고정, DB TLS 확인이에요(ADR-0064). 키 교체, 민감 열 암호화, 릴리스 서명과 SBOM과 출처 증명, 다중 사이트, 공개 위협 모델은 오픈 베타 전에 해요.

바꾸는 툴 1차는 "실험 기능, 기본 꺼짐"으로 내고, 켤 때 조건 점검 화면을 보여요.

### 7.1 1차(승인 전용)를 여는 조건

범위는 모든 바꾸는 호출에 사람의 승인이 필요하고, 액션은 되돌릴 수 있고 지장이 없고 객체 하나에 곧바로 관측되는 속성 하나예요([액션 타입 표](gateway-actions.md)). 증거로 적어요.

| 조건 | 확인할 증거 |
|---|---|
| 코어의 보호 | 코어의 접근 통제와 관리자 인증 테스트의 통과 기록 |
| 실행 모델과 토큰 | 실행의 계약과 토큰의 수명 테스트, 정해진 토큰 형식과 수명의 결정 기록 |
| 판단할 수 없으면 막기 | 진행 중인 의도, 멱등 키, "모름" 상태를 다루는 테스트의 통과 |
| 직무 분리와 내용 해시 승인 | 작성자, 승인자, 툴 승인자가 같으면 거절하는 테스트과 해시가 다르면 거절하는 테스트 |
| 변환과 대상 고정 | 대상 객체를 시작할 때 고정하고 실행 직전에 조건을 다시 확인하는 테스트 |
| 변조 방지 기록과 "기록 없이 변경 없음" | 기록을 쓸 수 없을 때 변경이 거절되는 테스트, 해시 체인 검증 |
| 한도와 정지 | 한도 초과, 실행 하나 정지, 전체 정지 스위치를 테스트한 기록 |
| 서명 키와 업스트림 권한 | 키 보관과 교체 절차의 문서, 최소 권한 업스트림 자격 증명, 일괄 차단 절차 |
| KG를 믿는 규칙 | 게이트웨이 설계 9.1절의 규칙을 판단 테스트 모음이 확인한 기록 |
| 장애 대비 | 게이트웨이 둘 이상, 동기 복제와 장애 전환의 훈련 기록 |
| 관리자 인증 | 관리 경로와 데이터 경로의 분리, 강한 관리자 인증 테스트 |
| 사후 확인과 리버트 | 확인 결과 네 가지를 내는 테스트, 선언한 리버트 액션이 있는지 점검 |
| 설계 검토 | 이 1차 조건 목록에 대한 설계 검토 기록(v2가 병합 전 검토를 요구해요) |

### 7.2 2차(자율)를 여는 조건

| 조건 | 확인할 증거 |
|---|---|
| 연결별 신뢰의 이력 | 그림자와 호출마다 승인 단계의 연결별 기록 |
| 장애 훈련 | 5절의 장애 표의 각 행을 훈련한 기록 |
| 잘못된 확인의 비율 | 그림자 운전에서 확인이 틀린 비율의 측정값 |
| 외부 보안 검토 | 외부 검토의 보고와 조치 기록 |
| 판단 테스트 모음 | 판단 테스트 모음의 통과와 입력 재현 기록 |
| 긴급 프로세스 | 긴급 훈련의 기록과 사후 검토 |

API를 직접 부르는 툴 출처("선언한 API 동작 하나가 툴 하나")은 프락시움이 현실 시스템의 자격 증명을 갖게 되므로 1차가 끝난 뒤에 다시 정해요.

## 8. 보장의 범위

우회가 열려 있으면 그 길에는 게이트웨이의 거절, 잠금, 한도, 정지 스위치가 적용되지 않아요. 정지 스위치는 "게이트웨이를 지나는 호출의 정지"를 뜻해요. 자세한 목록은 [안내서](../guides/what-praxium-guarantees.md)에 있어요.

## 9. 미결 사항

- 지원하는 MCP 명세의 판(세션 방식의 옛 판 포함).
- 토큰 형식과 수명, 소지 증명 방식.
- 실행의 권한과 시작한 사람의 역할의 관계(조사는 교집합을 권했지만 설계는 정하지 않았어요).
- 새 역할(툴 승인자, 프로세스 작성자)이 필요한지. 새 역할은 결정 기록으로만 더해요(ADR-0012).
- 운영 액션의 위임(`delegation`)과 실행의 계약을 합치는 방법.
- 조건과 기대 효과의 문법, 조직이 조건을 더하고 빼는 규칙.
- 여러 KG, 여러 사이트, 망 분리의 배치.
- 수치(토큰 수명, 한도, 복구 목표). 모두 측정할 가정이에요.
- 작은 조직의 직무 분리.
- "분리된 기반"을 어떻게 확인하는가.
- 2차에서 되돌릴 수 없는 액션과 지장을 주는 액션의 조건.
- 업그레이드 중 진행 중인 실행의 자세한 규칙.
- 잘못된 확인의 비율을 재는 방법.
- 신원을 업스트림에 넘기는 방법(현실 시스템의 기록에는 누가 했는지 나오지 않아요).
- 프로세스 정의의 형태와 시작 방법(사람, 일정, 이벤트).
- 액션 타입의 인자와 효과 선언([할 일](gateway-actions.md)).
