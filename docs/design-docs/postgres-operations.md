# 저장소의 운영 수준

[KG의 저장과 버전](kg-storage.md)을 프로덕션에 나갈 수 있는 수준으로 잇는 보충 문서예요(ADR-0009, ADR-0006). 단계 표시는 [알파] [클로즈드 베타] [오픈 베타]예요.

> **조사의 한계.** 조사에는 요약 도구를 썼어요. 그래서 인용 원문은 확인하지 못했어요. WAL이 3~4배라는 것은 추정이에요. 이 문서의 숫자는 가정이에요([설계 조사](../references/design-research.md)).

## 1. 쓰기 경로
1. **초기 적재는 한 트랜잭션으로 하지 않아요** [알파]. 구축 중(`building`)인 KG에 크기 한도가 있는 청크(chunk)로 나눠 재개할 수 있게 적재하고, 끝나면 한 번의 쓰기로 서비스 중인 KG(`serving`)로 전환해요. 큰 적용은 청크마다 `change_seq`를 하나 사용하고 읽기 워터마크(`readable_through`)를 배치가 끝날 때만 올려요([KG의 적용](kg-storage-apply.md) 4절). 수천만 개로 테스트하는 것은 [클로즈드 베타]예요.
2. **헤드 행은 적용기만 수정해요** [알파]. 확정과 정리가 수정하는 필드는 다른 행(`kg_maintenance`)에 둬요. 변경 번호는 헤드 행의 카운터로 매기고 시퀀스를 사용하지 않아요(커밋 순서와 번호 순서가 같아야 해요).
3. **`volatile`의 쓰기 감소** [알파]. 한 배치 안의 같은 키는 마지막 값만 기록해요. 값이 같으면 `seen_at`은 오래됨(stale) 판정 간격의 절반이 지났을 때만 기록해요(같은 값이면 경량 변경 레코드도 없어요). 그만큼 신선도의 정밀도를 포기해요. 스트림의 `volatile`만 보내는 데이터셋의 원본 레코드는 구간이 아니라 추가 전용의 짧은 로그(`raw_log`)예요.

## 2. 읽기와 복제
4. **복제본 읽기의 계약** [알파]. 질의하는 쪽이 `min_seq`(적어도 이 변경 번호까지 반영된 응답)를 지정할 수 있고, 응답에는 그 번호가 포함돼요. 복제본의 `readable_through`가 거기에 못 미치면 주 저장소로 보내거나 `wait_timeout` 안에서 기다리거나 거절해요(`max_staleness`는 소스에서 관측한 값이 얼마나 오래돼도 되는지만 의미해요). 번호는 세대와 함께 전달되고 세대가 다르면 `conflict.generation_changed`예요. 에이전트가 쓰기 직후 읽을 때 오래된 응답을 근거로 삼지 않게 해요. 대량 읽기용과 API 읽기용 복제본을 분리하는 것은 [클로즈드 베타]예요(kg-queries.md).
5. **동기 복제는 정족수 방식** [알파: 결정, 클로즈드 베타: 커밋 지연 측정]. 후보 2개 이상 중 하나가 수신하면 커밋해요. 동기 대상이 하나뿐이라 그것이 장애가 나면 쓰기가 멈추는 구성은 사용하지 않아요.

## 3. 연결, 잠금, 스키마 [알파]
6. 트랜잭션 단위 풀에서 동작하지 않는 기능(세션 잠금, LISTEN)을 사용하지 않아요. 병합의 직렬화와 적용기 단일화는 행 잠금과 트랜잭션 범위의 잠금으로 해요. NOTIFY는 사용하지 않고 폴링으로 해요. LISTEN이 꼭 필요한 역할은 풀 밖의 전용 연결을 사용해요.
7. 구문 실행, 잠금 대기, 트랜잭션 내 유휴 시간의 한도를 역할(적용, API 읽기, 대량, 드라이 런, 마이그레이션)마다 둬요. 스키마 변경은 짧은 잠금 대기 한도로 하고 테이블을 다시 쓰는 변경을 하지 않으며 인덱스는 잠금 없이(CONCURRENTLY) 만들어요. 인접한 두 버전의 역할이 함께 실행될 수 있어야 해서, 마이그레이션은 확장(새 것 추가) → 이전 → 축소(옛 것 삭제) 순서로 하고 축소는 다음 버전에서 해요. 스키마 마이그레이션의 잠금 대기 한도는 첫 마이그레이션부터 적용해요. 표준 모델과 `sys` 타입은 마이그레이션의 한 단계로 저장소에 적재하고, 실행 파일은 저장소의 것을 읽어요.
8. **테이블의 설계 항목** [알파: 틀, 클로즈드 베타: 값]. 테이블마다 쓰기 부하, 보관, 파티션 키, 인덱스 예산, 채움 비율(fillfactor), 제자리 갱신(HOT update)의 규칙을 적어요. 모든 기본 키와 인덱스의 선두 컬럼은 `kg_id`예요(닫힌 예외: 감사 로그, 시크릿, 권한 부여, 설정). 추가 전용 테이블은 구간으로 파티셔닝하고 `live`는 `kg_id`와 해시로 파티셔닝해요. 테이블별 청소(vacuum) 설정은 측정해서 정해요.

| 테이블 | 쓰기 부하 | 보관 | 파티셔닝 | 인덱스·갱신 규칙 |
|---|---|---|---|---|
| `raw_record` | 배치는 높다. 스트림은 `raw_log`로 분리한다 | 닫힌 구간만 | `source_id` | 열린 구간 인덱스만 |
| `raw_log` | 높다(추가 전용) | 짧게 | `ingest_seq` 구간 | 기본 키만 |
| `object_live`, `link_live` | 중간 | 현재 버전 | `kg_id`와 해시 | 인덱스 예산을 둔다. 채움 비율은 측정해서 |
| `object_hist`, `link_hist`, `change_entry` | 중간(추가 전용) | 1년(가정) | `seq_to`나 `change_seq` 구간 | 기본 키만 |
| `attr_volatile` | 높다(제자리 갱신) | 현재 값 | 정하지 않음 | 보조 인덱스 없음. 채움 비율을 낮춘다 |
| `light_change` | 높다(추가 전용) | 짧게 | `change_seq` 구간 | 기본 키만 |
| `kg_head` | 적용마다 한 행 | 한 행 | 없음 | 적용기만 수정한다 |
| `stage_*`, `plan_change` | 적용 중에만 | 적용마다 삭제 | `apply_id` | 로그 비활성(UNLOGGED) |

## 4. 신호와 운영 액션
9. **저장소의 신호** [알파: 이름과 단위, 구현은 단계별]. dead tuple과 bloat, 트랜잭션 ID의 나이(age), WAL의 양과 LSN 위치, 복제 지연, 긴 트랜잭션, 슬롯이 보존하는 WAL의 양, 보관 지연, 마이그레이션의 잠금 대기를 자기 관측성의 신호와 이벤트 코드(`storage.*`)에 추가해요. 한도까지 남은 시간의 예측은 [오픈 베타]예요. 저장소를 다루는 운영 액션(수집 속도 감소, 보류, 백필 중지, 긴 트랜잭션 종료, 질의 패턴 차단, 테이블 청소)은 [클로즈드 베타→오픈 베타]예요.
10. **저장소 신호에 따른 백프레셔** [클로즈드 베타]. 복제 지연, dead tuple, 적용 지연에 따라 수집 속도를 줄였다 늘려요. 우선순위는 읽기 > 적용 > 드라이 런과 백필이에요. 재시도에는 지터(jitter)를 넣어요.

## 5. 드라이 런과 분리
11. **드라이 런을 주 저장소의 부하에서 분리해요** [클로즈드 베타: 설계, 오픈 베타: 구현]. 드라이 런의 스테이징 영역과 결과는 정본이 아니므로 별도의 임시 저장소(복제와 백업이 없는 것)에 두거나 영향 범위만의 오버레이로 실행해요. 통째로 복사한 후보 KG를 기본값으로 삼지 않아요.
12. **임계값의 단위를 3가지로 적어요** [알파: 문서, 클로즈드 베타: 측정]. "초당 2만~3만 행"은 논리 변경 수예요. 물리적으로 쓰는 행 수와 WAL 바이트를 따로 측정하고, 전환 판단은 3가지를 함께 봐요.
13. **이전 경로를 미리 마련해요** [알파: 라우팅 계층, 오픈 베타: 이전 절차]. 모든 저장소 접근이 `kg_id`로 대상 저장소를 찾는 계층을 거쳐요(알파에서는 답이 언제나 하나예요). 이 계층은 **KG를 저장소 사이에서 이전하는 데** 사용해요. KG를 분할하는 것은 쓰기 한계를 해결하는 수단이 아니에요. 영향 범위가 KG 하나 안에서만 계산되는데 분할하면 계층을 가로지르는 영향 범위가 끊기기 때문이에요. 서로 의존하지 않는 자산 그룹(따로 운영되는 환경)만 다른 KG가 될 수 있어요. KG 사이를 가로지르는 트랜잭션은 만들지 않아요.
14. **백업과 복원의 훈련, 메이저 버전 업그레이드 절차, 슬롯 방침**(외부 소비자에게 논리 슬롯을 제공하지 않아요) [오픈 베타]. 작업 테이블은 작게 유지하고 긴 트랜잭션을 감시해요 [클로즈드 베타].

## 6. 메시지 로그 저장소(Kafka 규약)의 운영 부담
1. **프락시움은 메시지 로그 저장소를 직접 기동하거나 운영하지 않아요.** 어댑터는 조직이 이미 운영하는 것에 연결해요. 그런 것이 없는 배포는 PostgreSQL 어댑터를 사용해요. 그 저장소의 고가용성 구성과 관리는 제품의 범위 밖이고, 제품은 연결에 필요한 조건(토픽, 보관, 권한, 최소 복제 수)을 문서로 제공해요.
2. **전환 순서**: 임계값(12)을 넘으면 먼저 쓰기 감소 조치(3, 10)를 적용하고, 그래도 부족하면 메시지 로그 저장소로 이전해요. KG 분할은 이 순서에 없어요(13). 처리량 외의 이유(외부 소비자가 많아 같은 로그를 되감아 읽어요)라면 바로 이전할 수 있어요.
3. **연결이 끊겼을 때**: KG와 질의는 그대로 동작해요(적용된 변경의 기록은 언제나 PostgreSQL에 있어요). 수집이 지연돼요. 수집기는 한도까지 버퍼링하고 넘치면 소스를 중지하고 문제로 보고해요. 보관 기간이 지나 되감을 수 없으면 그 소스를 전체 스냅샷 대조로 다시 동기화해요. 중복 수신분은 (소스, 오프셋)으로 걸러져요.
4. **연결된 메시지 로그 저장소도 관측해요**: 접속 가능 여부, 지연, 쓰기 실패, 보관까지 남은 여유를 자기 관측성의 신호와 진단에 넣어요.
5. 단계는 그대로예요: 어댑터는 클로즈드 베타, 알파는 PostgreSQL이에요.

## 7. 측정 계획 [클로즈드 베타]
저장소 쪽만 측정해요(질의 엔진은 [kg-queries.md](kg-queries.md)가 다뤄요). 합성 데이터로 측정한 값은 환경, 규모, 한계와 함께 적고, 불합격 기준은 미리 적어요(가정). 수천만 객체의 측정은 작은 장비로는 부족해서 전용 장비 하나가 필요해요.

| 순서 | 측정 항목 | 정하려는 것 |
|---|---|---|
| 1 | 청크로 나눈 초기 적재: 청크 크기 한도별 시간, 인덱스를 먼저·나중에 만들 때의 차이, 디스크 크기 | 청크 크기 한도, 인덱스 생성 시점 |
| 2 | 적용: 0.1%와 1%가 바뀐 적용의 단계별 시간, WAL의 양, dead tuple의 누적. 스트림의 작은 배치 처리량, `volatile` 갱신량, 경량 변경 레코드의 양. **큰 적용 중 스트림의 적용 지연** | 한 트랜잭션이 짧은지, 파티셔닝과 인덱스, 청소 설정 |
| 3 | SQL만으로 답하는 질의의 기준선(얕은 이웃, 계층의 상위·하위, 도달 집합, `scope_v*` 필터링) | 어디까지 SQL로 답하나, 범위 색인 |
| 4 | 프로젝션 구축과 변경 추적 갱신(경량 변경 레코드 포함) | 프로젝션의 파티셔닝, 레이어 적용과 컴팩션의 주기 |
| 5 | 결정성: 입력 순서, 워커 수, 청크 크기 한도, 로케일을 바꿔 가며 그래프 해시 | kg-storage.md 7.5의 테스트 |
| 부가 | 복제본 읽기와 커밋 방식별 쓰기 지연, 쓰기 감소의 효과, 링크가 `volatile`이 아닐 때 `runs_on`의 쓰기량 | kg-storage.md 11절의 선택, 임계값의 3가지 단위 |

## 8. 설계 담당에게 확인할 사항
- 3절 구문 실행·잠금 대기·유휴 시간의 한도, 5절 정족수의 값, `wait_timeout`의 기본값, 수집기 버퍼 한도의 기본값.
