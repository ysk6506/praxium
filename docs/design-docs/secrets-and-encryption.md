# 비밀 값과 암호화

프락시움은 조직의 거의 모든 인프라 시스템을 읽는 열쇠 묶음을 쥐어요. 읽기 전용 계정이어도 그 묶음이 새면 조직 전체의 구성이 새요. 이 문서는 그 열쇠(비밀 값)를 어떻게 넣고, 어디에 두고, 누가 언제 풀어 쓰고, 어떻게 돌려 쓰고, 샜을 때 어떻게 하는지를 적어요. 제품 책임자의 요구는 이래요. 소스 시스템의 연동 정보를 암호화해서 관리하는 것이 중요해요. 프로덕션에 나가려면 요구되는 수준이고, 오픈 베타 때는 구현돼 있어야 해요.

> **길과 칸은 다음 변경의 OpenAPI 문서에서 굳어요. 그때 바뀔 수 있어요.** 길은 `/v1/...`이고 이름은 이 문서가 정한 가정이에요. 예시의 값은 모두 지어낸 거예요.

## 1. 무엇에 답하나
- 어디에 두나요(3, 4절)? API로 넣은 값을 다시 볼 수 있나요(5절)? 누가 풀 수 있나요(6절)?
- 떨어진 망의 소스는요(7절)? 바꾸다 실패하면요(8절)? 누가 언제 썼는지는요(9절)?
- 값이 정의, 로그, 수집한 데이터로 새지 않나요(10, 6, 13절)? 샌 것으로 의심되면(14절), 으뜸 열쇠를 잃으면(4.6)? 언제 만드나요(15절)?

비밀 값 제공자가 멈춰도 API와 질의 엔진은 비밀 값을 풀지 않아서 KG와 질의는 그대로 답해요. 멈추는 것은 수집뿐이에요.

## 2. 한눈에
### 2.1 비밀 값의 종류와 원칙
| 종류 `kind` | 담는 칸 `field_names` | 쓰는 곳 |
|---|---|---|
| `password` | `username`, `password` | 세션 로그인이나 SQL 계정으로 닿는 소스 |
| `token` | `token` | 토큰으로 닿는 HTTP 소스 |
| `certificate` | `certificate_pem`, `private_key_pem` | 소스가 클라이언트 인증서를 요구할 때 |
| `connection_string` | `dsn` | 연결 문자열 하나로 닿는 소스 |
| `notifier_key` | `key` | 알림을 보내는 길(ADR-0013) |
| `signing_key` | `private_key_pem` | 프락시움이 서명하는 열쇠 |

시스템 계정의 토큰(ADR-0012)은 프락시움이 낸 것이라 해시만 저장하고, 이 저장소에 넣지 않아요. 그 토큰을 쥐고 쓰는 쪽(수집기, 다른 시스템)이 자기 쪽에서 `token`으로 다뤄요.

**원칙은 넷이에요.** (1) 평문으로 저장하지 않아요. (2) 쓰는 순간에만, 쓰는 역할에서만 풀어요. (3) API와 로그와 내보내기로 다시 나오지 않아요. (4) 누가 언제 썼는지가 남아요.

### 2.2 넣어져서 쓰이기까지
```
 사람·시스템 ─(1) 값 넣기: POST /v1/secrets ─▶ [API 역할]
                 (값은 본문에만)                │ 데이터 열쇠를 만들어 값을 암호화(묶음 정보 = secret_id, 판)
                                                │ 데이터 열쇠를 으뜸 열쇠로 "감싸기"만 해요(풀 수 없어요)
                                                │ 값과 데이터 열쇠는 메모리에서 지워요
                                                ▼
     [저장소 PostgreSQL]  secret, secret_version = 암호문 + 감싼 데이터 열쇠 + 메타 정보
     [정의] source.credential_ref = { secret_id }  ← 참조만. 브랜치·제안·내보내기에도 참조만
                                                │
 [일꾼의 수집 부분] ─(2) 소스 하나의 일을 받아요 ─┤ 그 소스의 참조인지 확인
        │ (3) 감싼 데이터 열쇠를 풀어 달라고 ──▶ [으뜸 열쇠: 열쇠 관리 서비스 / 하드웨어 보안 모듈 / 열쇠 파일]
        │◀(4) 데이터 열쇠 ── 값을 풀어 메모리에만 두어요
        │ (5) 요청 틀의 자리 표시에 값을 넣어 읽기 전용 요청 ─TLS(인증서 확인)─▶ [소스]
        │ (6) 연결이 끝나면 값을 지워요. "풀어 쓴 기록"을 감사 기록에 남겨요
 [질의 엔진] ✕ 으뜸 열쇠에 닿는 권한이 없어요      [API 역할] ✕ 풀기 메서드가 없어요
```
바깥 비밀 저장소 어댑터를 쓰면 저장소 칸이 바깥 저장소로 바뀌고 프락시움에는 참조와 메타 정보만 남아요(3절).

## 3. 제공자 포트
비밀 값은 포트 하나(`SecretProvider`) 뒤에서 다뤄요. 포트의 쓰임이 셋이라 인터페이스도 셋으로 나눠 조립해요(ADR-0006의 방식. 구조 계약에 등록하는 변경에서 건다).

| 쓰임 | 메서드(뜻) | 하는 일 | 어느 역할의 조립이 받나 |
|---|---|---|---|
| 쓰기 | 넣기(`put`) | 새 비밀 값과 첫 판을 넣어요. 값은 입력에만 있어요 | API |
| | 바꾸기(`add_version`) | 새 판을 더해요(8절의 흐름을 시작해요) | API |
| | 물리기(`retire`) | 판을 쓰지 않게 하고 암호문을 지워요 | API, 일꾼 |
| 풀기 | 쓰려고 풀기(`open`) | 값(또는 짧게 사는 자격)을 메모리로 가져와요. 호출한 역할과 실행의 이름표를 받아 풀어 쓴 기록을 남겨요. 끝나면 `close`로 덮어써요 | **일꾼의 수집 부분, 수집기만** |
| 메타 | 메타 정보 읽기(`describe`) | 이름, 판, 때, 만료, 지문의 앞자리 | 모든 역할 |

**값을 읽어 돌려주는 메서드가 API 쪽에 없어요.** 어댑터 포트에 쓰는 메서드가 없다는 읽기 전용의 셋째 겹(ADR-0008)과 같은 방식이에요. `open`은 소스에 닿는 역할의 조립에만 이어져요. API 역할의 조립은 `open`이 있는 인터페이스를 받지 못해요. 구조 검사가 봐요.

### 3.1 어댑터 둘
| | 바깥 비밀 저장소 어댑터 | 제품에 든 봉투 암호화 어댑터 |
|---|---|---|
| 값이 있는 곳 | 그 저장소 | 프락시움의 저장소에 든 암호문 |
| 프락시움이 쥐는 것 | 참조(`external_ref`), 메타 정보 | 암호문, 감싼 데이터 열쇠, 메타 정보 |
| 권한, 돌려 쓰기, 감사 | 그 저장소가 맡아요(프락시움도 풀어 쓴 기록은 남겨요) | 프락시움이 해요(4~9절) |
| 어댑터의 모양 | 널리 쓰이는 규약마다 하나. 저장소가 내는 면(값 저장 / 짧게 사는 자격 / 암호화 대행) 가운데 쓰는 면을 `capabilities`로 선언해요 | 으뜸 열쇠의 어댑터 셋(열쇠 관리 서비스, 하드웨어 보안 모듈, 열쇠 파일) |

공개된 비밀 저장소의 문서는 면을 셋으로 가르는 것으로 확인했어요: 넣은 값을 돌려주는 저장, 요청에 따라 자격을 만들어 주고 임대 기간이 지나면 거두는 동적 비밀 값, 데이터를 저장하지 않고 암호화만 해 주는 암호화 대행. 프락시움은 앞의 둘을 바깥 저장소 어댑터의 `capabilities`(`versions`, `short_lived`, `expiry_metadata`)로, 셋째를 으뜸 열쇠 어댑터(감싸기와 풀기)에 써요.

### 3.2 고르는 기준
비밀 값마다 어댑터를 골라요(`secret.provider`: `builtin`, `external`, `remote`).
1. 조직이 이미 가진 바깥 비밀 저장소가 있고 일꾼이 닿을 수 있어요 → **바깥 저장소**를 권해요. 권한과 돌려 쓰기를 이미 하고 있어요.
2. 바깥 저장소가 없는 배포 → **제품에 든 저장소**예요. 이것이 있어서 비밀 저장소가 없는 배포가 평문으로 물러나지 않아요.
3. 소스가 짧게 사는 자격을 주는 방식을 지원해요 → 그 면이 있는 바깥 저장소예요. 제품에 든 저장소는 보관만 해요.
4. 소스가 떨어진 망에 있어요 → 그 망 안의 제공자예요(7절).

## 4. 제품에 든 저장소
### 4.1 열쇠의 위아래
```
 으뜸 열쇠(key_id)        저장소 밖. 열쇠 관리 서비스 / 하드웨어 보안 모듈 / 열쇠 파일
   │  감싸기(wrap)·풀기(unwrap)
   ▼
 데이터 열쇠              비밀 값의 판마다 새로 만들고 한 번만 써요. 감싼 모양(wrapped_key)만 저장소에 있어요
   │  인증을 겸하는 암호(AEAD)
   ▼
 값(ciphertext)           칸 이름과 값을 묶은 글 하나를 암호화한 것
```
으뜸 열쇠는 데이터 열쇠를 감싸는 열쇠(key-encrypting key)이고 데이터 열쇠는 값을 암호화하는 열쇠예요. 공개된 열쇠 관리 서비스의 문서도 최상위 열쇠가 데이터 열쇠를 보호하는 같은 구조를 설명해요.

### 4.2 암호의 요구
- **인증을 겸하는 표준 암호(AEAD)**를 써요(RFC 5116의 틀. 예: SP 800-38D의 GCM 모드의 AES-256, 또는 ChaCha20-Poly1305. 비밀 값 관리의 지침(OWASP)이 두 가지를 예로 들어요). 암호문이 바뀌었거나 묶음 정보가 다르면 풀기가 실패해요.
- **덧붙이는 묶음 정보(AAD)**에 `secret_id`, `version`, `aad_format`을 넣어요. 묶음 정보는 암호화하지 않지만 인증돼요(RFC 5116). 그래서 DB를 고칠 수 있는 사람이 암호문을 다른 비밀 값이나 다른 판의 자리로 옮겨 붙여도 풀리지 않아요. 데이터 열쇠를 감쌀 때도 같은 묶음 정보를 쓰기를 권해요(구현에서 확인).
- **묶음 정보는 비밀이 아니에요.** 열쇠 관리 서비스의 문서도 묶음 정보(encryption context)가 비밀이 아니고 로그에 평문으로 남는다고 해요. 그래서 `secret_id`와 판 번호만 넣고 이름이나 주소 같은 것을 넣지 않아요.
- **nonce는 열쇠마다 겹치면 안 돼요**(RFC 5116은 같은 열쇠에서 nonce를 다시 쓰면 GCM의 기밀성과 무결성이 모두 깨진다고 해요). 데이터 열쇠를 판마다 새로 만들고 한 번만 쓰므로 열쇠 하나에서 암호화가 한 번뿐이에요. nonce는 무작위로 내요.
- **임시 값의 규칙.** 평문의 값과 데이터 열쇠는 메모리에만 있어요. 덮어쓸 수 있는 바이트 조각에 담고 쓴 뒤 곧 덮어써요. 디스크, 임시 표, 로그, 추적, 오류 글에 쓰지 않아요. 코어 덤프와 스왑을 막는 배포 설정을 권해요. 완전한 지움은 보장하지 못해요(16절).
- **지문(`fingerprint_prefix`)은 값의 해시가 아니에요.** 값의 해시 앞자리는 짧은 비밀번호를 DB를 읽는 사람이 맞춰 볼 수 있게 해요. 그래서 넣을 때 데이터 열쇠로 키를 단 해시(HMAC)의 앞자리를 계산해요. API가 그때 데이터 열쇠를 쥐고 있어서 풀지 않고도 돼요. 방법은 구현에서 확인해요.

### 4.3 저장하는 칸
모든 표에 `kg_id`가 있는 규칙(ADR-0009)은 KG에 딸린 표의 규칙이에요. 비밀 값은 배포 하나의 것이라 `kg_id`가 없어요.

| 표 | 칸 | 뜻 |
|---|---|---|
| `secret` | `secret_id`, `name`, `kind`, `field_names`, `provider`, `external_ref`, `scope_kind`(`source` / `product`), `source_id`, `allowed_hosts`, `current_version`, `suspected_at`, `created_by`, `created_at`, `deleted_at` | 비밀 값 하나. 값은 없어요. `external_ref`는 바깥 저장소 안의 이름이고 값이 아니에요. `allowed_hosts`는 이 값이 닿아도 되는 주소의 목록이에요(6절) |
| `secret_version` | `secret_id`, `version`, `state`, `ciphertext`, `nonce`, `wrapped_key`, `key_id`, `aad_format`, `external_version`, `fingerprint_prefix`, `created_by`, `created_at`, `activated_at`, `retired_at`, `expires_at`, `last_opened_at`, `failure_code` | 판 하나. 바깥 저장소 어댑터면 `ciphertext`, `nonce`, `wrapped_key`는 비어 있고 `external_version`이 있어요. 물린 판은 암호문을 지우고 메타 정보만 남겨요 |
| `master_key` | `key_id`, `kind`(`kms` / `hsm` / `key_file`), `purpose`(`secret_value` / `column`), `location_ref`, `state`(`active` / `decrypt_only` / `retired`), `created_at`, `retired_at` | 으뜸 열쇠의 목록. 열쇠 재료가 아니라 어디에 있는지의 참조(`location_ref`)만 담아요 |

`secret_version.state`는 `staged`, `trying`, `current`, `retired`, `failed`예요(8절).
### 4.4 으뜸 열쇠의 자리 셋
| 자리 | 어떻게 | 알아 둘 것 |
|---|---|---|
| 열쇠 관리 서비스 | 감싸기와 풀기를 서비스에 맡겨요. 열쇠 재료가 서비스 밖으로 나오지 않아요 | 서비스가 재료를 스스로 돌려도 옛 재료는 풀기용으로 남아요. `key_id`가 그대로면 다시 감쌀 필요가 없어요 |
| 하드웨어 보안 모듈 | 같아요 | 지연과 호출 한도를 재야 해요 |
| 열쇠 파일 | 배포가 읽기 전용 파일로 줘요(환경 변수가 아니에요) | 알파와 닫힌 망의 길이에요. 프로세스가 파일을 읽을 수 있어서 서비스보다 약해요 |

**API 역할은 감싸기만 하고 풀 수 없어요.** 값을 넣으려면 데이터 열쇠를 감싸야 해서 감싸기 권한이 필요하고, 풀기 권한은 수집 부분에만 있어야 해요. 열쇠 관리 서비스와 하드웨어 보안 모듈은 두 권한을 따로 줘요. 열쇠 파일은 으뜸 열쇠를 열쇠 쌍으로 두고, 감싸기에 쓰는 공개 쪽을 API에 주고 풀기에 쓰는 개인 쪽을 소스를 향하는 역할(수집 부분)에만 줘요.

**저장소(PostgreSQL)에 두지 않는 까닭.** 열쇠를 그것이 감싼 값 옆에 두지 말라는 지침(OWASP)이에요. 같은 DB나 DB와 같이 백업되는 설정 파일에 으뜸 열쇠가 있으면 백업 하나로 모든 값이 풀려요. 열쇠 파일은 DB 백업과 다른 곳에 두고 접근을 따로 지켜요.

### 4.5 으뜸 열쇠를 돌려 쓸 때
```
 1 새 으뜸 열쇠를 등록     master_key: 새 것 active, 옛 것 decrypt_only   (새로 넣는 값은 바로 새 열쇠로 감싸요)
 2 다시 감싸기(작업)       각 secret_version(과 칸 열쇠)마다: 옛 열쇠로 풀기 → 새 열쇠로 감싸기 → wrapped_key, key_id 갱신
                           값(ciphertext)은 건드리지 않아요. 갱신은 판 번호를 조건으로 걸어 겹쳐도 안전해요
 3 옛 열쇠를 참조하는 행이 0   → 옛 것을 retired로 하고 배포가 열쇠를 없애요
```
2번은 풀기와 감싸기를 모두 가진 수집 부분이 하고, 운영 행위 `rewrap_master_key`(self-observability 7.1)로 시켜요. `admin`의 승인이 들어요. 진행 수가 작업 자원에 보여요. 3 전에는 옛 열쇠로 되돌릴 수 있어요(`decrypt_only`).

### 4.6 으뜸 열쇠를 잃으면
제품에 든 저장소의 값은 되살릴 수 없어요. 암호문은 쓸모가 없어지고 비밀 값을 새 으뜸 열쇠로 다시 넣어야 해요(소스 쪽 자격을 새로 받아야 할 수 있어요). 수집이 멈추고 KG와 질의는 그대로 답해요. 그래서 배포 안내에 으뜸 열쇠를 DB 백업과 다른 곳에 둘 이상 보관하고 되살리기를 연습하는 절차를 적어요. 건강은 `secret_master_key_reachable`로 "으뜸 열쇠에 닿는가"를 보고, 닿지 못하면 `secret.master_key_unreachable`을 내요(자신의 관측성 설계).

## 5. 쓰기만 되는 값
### 5.1 API에서의 모양
| 길 | 메서드 | 하는 일 | 역할 | 작업 |
|---|---|---|---|---|
| `/v1/secrets` | GET, POST | 목록(메타 정보만) / 넣기. `Idempotency-Key` 필요 | 읽기: 그 소스를 범위에 가진 `viewer` 이상, 제품 범위의 것은 `admin`, `auditor`. 쓰기: 아래 9절 | - |
| `/v1/secrets/{secret_id}` | GET, PATCH, DELETE | 메타 정보 / 이름, 담당자, 만료를 고치기(값은 못 고쳐요. `If-Match` 필요) / 지우기(참조하는 소스가 없을 때만) | 같아요 | - |
| `/v1/secrets/{secret_id}/versions` | POST | 바꾸기: 새 판 | 같아요 | - |
| `/v1/secrets/{secret_id}/versions/{version}:check` | POST | 새 판으로 시험 연결 | 그 소스의 `operator` | 작업 |
| `/v1/secrets/{secret_id}/versions/{version}:retire` | POST | 판 물리기 | 같아요 | - |
| `/v1/master-keys` | GET | 으뜸 열쇠의 목록과 상태(재료는 없어요) | `admin` | - |
| `/v1/master-keys/{key_id}:rewrap`, `:retire` | POST | 다시 감싸기(4.5. 운영 행위와 같은 일), 옛 열쇠 물리기 | `admin`(승인 필요) | 작업 |

풀어 쓴 기록은 `GET /v1/audit-records`를 `action`과 `target_id`로 걸러 읽어요(9절). **값을 읽는 길은 없어요.** `GET`은 어느 길에서도 값을 돌려주지 않아요.

**넣는 요청과 돌아오는 메타 정보**(값은 본문에만 있고, 주소와 머리말에는 없어요):
```json
POST /v1/secrets    Idempotency-Key: 8b0c...
{"name": "inventory-reader-login", "kind": "password", "provider": "builtin",
 "scope": {"kind": "source", "source_id": "src_inventory"},
 "fields": {"username": "svc-read", "password": "(쓰기만 되는 값)"}, "expires_at": null}

→ 201 ETag: "sec-1"
{"data": {"secret_id": "sec_41", "name": "inventory-reader-login", "kind": "password",
          "field_names": ["username", "password"], "provider": "builtin",
          "scope": {"kind": "source", "source_id": "src_inventory"}, "current_version": null,
          "versions": [{"version": 1, "state": "staged", "created_by": "sub_21", "created_at": "2031-04-02T09:30:00Z",
                        "last_opened_at": null, "expires_at": null, "fingerprint_prefix": "a3f9"}],
          "suspected": false}, "meta": {}}
```
**새 판을 넣은 뒤 읽으면**(값은 없어요):
```json
GET /v1/secrets/sec_41   → {"data": {"secret_id": "sec_41", "current_version": 2, "suspected": false, "used_by": [{"kind": "source", "id": "src_inventory"}],
  "versions": [{"version": 2, "state": "current", "last_opened_at": "2031-05-01T08:00:00Z", "fingerprint_prefix": "7c21"},
               {"version": 1, "state": "retired", "retired_at": "2031-05-01T02:00:00Z", "fingerprint_prefix": "a3f9"}]}, "meta": {}}
```
- **값이 들어가는 곳은 본문 하나예요.** 주소(경로, 검색어), 머리말, `cursor`에는 없어요. 어디서나 찍히는 곳이라서요.
- **오류도 값을 되풀이하지 않아요.** 틀린 칸은 `errors`에 `pointer`와 `code`만 주고 `params`에 보낸 값을 싣지 않아요.
- **겹침 방지 기록도 본문을 쓰지 않아요.** 다른 본문인지 가리려고 본문의 키를 단 해시만 쥐고, 다시 보내면 처음 응답(메타 정보)만 줘요.
- **요청 본문을 찍지 않아요.** 접근 기록에도 추적에도 없어요. API 앞의 중계 장치가 찍지 않게 하는 것은 배포의 몫이에요. **명령줄 클라이언트는 값을 인자로 받지 않고** 표준 입력이나 파일에서 읽어요. 인자는 셸 이력에 남아요.
- 새 오류 코드(가정): `invalid_input.secret_like_value`(10.2), `invalid_input.secret_field_unknown`, `conflict.secret_in_use`.

### 5.2 정의에는 참조만
소스의 정의 항목에는 비밀 값의 `secret_id`만 들어가요. 브랜치, 제안, 정의의 차이, 후보 실행, 내보낸 파일(`/v1/definition-sets/{set_no}/exports`) 어디에도 값이 없어요. 낱개의 유효성 검사(`item_valid`, 정의 설계)는 이것을 봐요.
```json
{"kind": "source", "name": "inventory",
 "body": {"adapter": "http_json", "preset": "inventory-basic@3",
          "endpoints": ["https://inventory.example.internal"],
          "credential_ref": {"secret_id": "sec_41"},
          "tls": {"verify": true}}}
```
- 참조는 **그 소스에 딸린 비밀 값**이나 제품 범위의 것만 가리킬 수 있어요. `editor`가 남의 소스의 `secret_id`를 자기 소스에 걸어 그 값을 쓰게 하는 길을 막으려는 거예요. 풀 때도 비밀 값의 `source_id`와 실행의 소스가 같은지 다시 봐요(6절).
- 비밀 값을 바꾸어도 참조가 같아서 정의의 판은 안 바뀌어요. 바뀜은 정의의 이력이 아니라 감사 기록에 남아요.

## 6. 푸는 자리
| 역할 | 풀 수 있나 | 으뜸 열쇠 | 값에 닿는 때 |
|---|---|---|---|
| API | 아니요. `open`이 없어요 | 감싸기만 | 넣는 요청의 본문이 지나가는 동안 메모리에 잠깐 있어요(암호화하고 곧 덮어써요) |
| 일꾼(수집 부분) | **예** | 풀기와 감싸기 | 수집, 시험 수집, 들여다보기, 점검의 연결을 맺는 동안 |
| 일꾼(나머지)과 질의 엔진 | 아니요 | 비밀 값의 으뜸 열쇠에 없음(칸 열쇠는 12.2) | 닿지 않아요 |
| 수집기 | **예**(자기 망의 제공자에서만) | 본체의 으뜸 열쇠에는 닿지 않아요 | 연결을 맺는 동안 |

한 프로세스에 역할을 다 띄우는 알파에서는 이 나눔이 코드의 길과 권한의 구분으로 서요. 배포에서는 수집을 맡는 일꾼 벌만 풀기 권한을 받게 해서 나눠요.

**`open`이 확인하는 것.** (1) 부른 쪽이 수집 부분인가, (2) 비밀 값의 소스가 실행의 소스와 같은가, (3) 그 판이 풀어도 되는 상태(`current`, `trying`)인가, (4) 샌 것으로 의심된 때(`suspected_at`)보다 앞에 만든 판이 아닌가, (5) 소스가 `paused`가 아닌가(시험 연결은 예외), (6) 연결하려는 주소가 비밀 값의 `allowed_hosts` 안인가. 시험 수집과 들여다보기를 포함해 어느 길로도 그 밖의 주소로는 쓰이지 않아요. `allowed_hosts`를 바꾸는 것은 그 소스를 범위에 가진 `operator`나 `admin`이고 감사에 남아요(`secret_hosts_changed`). 브랜치가 주소를 바꾸면 시험 수집 앞에 바뀐 주소를 보여 줘요. 실패하면 `secret_open_denied`를 남겨요.

**메모리에 있는 시간.** 연결을 맺는 동안만이에요. 연결 하나에 한 번 풀고 끝나면 덮어써요. 오래 두는 흐름 소스의 연결은 사는 동안 쥐고, 끊겨 다시 맺을 때 다시 풀어요(그때마다 기록이 남아요). 풀어 둔 값을 캐시하지 않아요.

**남지 않아야 하는 곳.**
| 곳 | 규칙 |
|---|---|
| 로그 | 값이 없어요. 이름표(`secret_id`, 판, 역할)와 수만 찍어요. 사건 코드의 `params`에도 값이 없어요 |
| 추적 | 요청과 연결의 속성에 값, 머리말, 본문이 없어요. 소스로 가는 요청의 계측은 값이 든 머리말과 본문을 기록하지 않아요 |
| 오류 글 | 아래 규칙. 값을 되풀이하지 않아요 |
| 덤프 | 코어 덤프를 막아요. 값은 바이트 조각에만 둬요 |
| 지표, 작업 자원, 운영 행위의 결과 | 이름표, `params`, `result`에 값이 없어요. `detail_key`는 `secret_id`예요 |
| 요청의 견본 | 자리 표시는 가려진 채로 보여요(10절) |
| 감사 기록, 내보낸 정의, 차이, 제안 | `detail`에 값이 없어요(9절). 정의에는 참조만 있어요(5.2) |

**소스가 돌려준 오류 글을 그대로 싣지 않아요.** 소스와 드라이버의 오류 글에는 연결 문자열, 계정 이름, 주소, 쿼리가 섞여 나오는 일이 흔해요(공개된 약점 목록 CWE-209, CWE-532가 오류 글과 로그로 정보가 새는 길을 들어요). 그래서 어댑터는 소스의 오류를 닫힌 목록의 분류로 바꿔요: `auth_failed`, `permission_denied`, `tls_verify_failed`, `connect_timeout`, `protocol_error`, `rate_limited`, `source_error`. 로그와 오류에는 분류, 상태 코드, 걸린 시간만 실어요. 원인은 소스 쪽의 기록에서 찾아요(16절).

## 7. 떨어진 망
```
   [본체: API · 일꾼 · 질의 엔진 · 저장소]                   [떨어진 망]
    secret 행: provider = remote, 참조와 메타 정보만            수집기(제품이 싣는 것)
    source.credential_ref = { secret_id }  ─(2) 소스 하나의 일 ─▶  │ (3) 참조 이름으로 자기 망의 제공자에서 값을 얻어요
                                                                    ▼
                                                      [그 망의 비밀 저장소] 또는 [수집기 쪽 암호화 저장소]
                                                                    │ (4) 읽기 전용 요청 ──▶ [소스]
    ◀─(5) 수집 봉투(원본 기록)와 사용 보고(참조, 판, 때, 결과) ─────┘   값은 이 망을 떠나지 않아요
```
- **본체가 아는 것.** 참조, 이름, 종류, 칸 이름, 만료(그 제공자가 알려 주면), 사용 보고, 점검의 결과예요.
- **본체가 모르는 것.** 값, 데이터 열쇠, 그 망의 으뜸 열쇠예요. 본체가 뚫려도 그 망의 열쇠는 나오지 않아요.
- **넣는 길.** 그 망의 제공자에 그 망의 관리자가 직접 넣어요. 본체의 `POST /v1/secrets`로는 값을 넣지 않아요(값이 본체를 지나기 때문이에요). 본체에는 `provider: remote`로 참조만 등록해요(값이 없는 요청).
- **풀어 쓴 기록.** 수집기가 사용 보고를 보내면 본체가 감사 기록에 적어요. 본체가 확인하지는 못해요(16절). 담당자가 만든 수집기(수집 봉투만 쓰는 것)의 비밀 값은 그 소스의 담당자의 몫이에요(ingestion 6.2). 수집기 쪽 암호화 저장소의 모양은 정하지 않았어요(16절).

## 8. 판과 돌려 쓰기
### 8.1 판의 상태 흐름
```
 put / add_version
       │
    staged ──(다음 연결 또는 checks)──▶ trying ──연결 돼요──▶ current ──(다음 판이 current가 되면)──▶ retired
                                          │
                                          └─연결 안 돼요──▶ failed ──(retire)──▶ retired
```
- `put`과 `add_version`은 새 판을 `staged`로 만들어요. 옛 `current`는 그대로예요.
- 다음 연결(또는 `checks`)이 새 판으로 연결을 한 번 시도해요(`trying`). **한 번만 시도하고 다시 하지 않아요.** 인증 실패를 다시 하지 않는 기본값(소스를 지키는 값)과 같은 까닭으로, 소스의 계정이 잠기지 않게 해요.
- 연결이 되면 새 판이 `current`가 되고 옛 판을 물려요(`retired`: 암호문과 감싼 열쇠를 지우고 메타 정보만 남겨요). 비밀 값의 `current_version`이 올라요.
- 연결이 안 되면 새 판은 `failed`예요. 같은 실행은 옛 `current`로 돌아가 이어 가고, 그 소스의 담당자에게 사건 코드 `secret.version_check_failed`로 알려요. 판의 시험 연결 실패는 그 소스의 연속 실패(잇달아 5번)에 세지 않아요. 옛 판은 `current`로 그대로 남아요.
- 바깥 비밀 저장소 어댑터는 새 판을 그 저장소가 만들어요. 프락시움은 `describe`로 `external_version`이 바뀐 것을 보면 같은 흐름(`trying`)으로 확인해요. 저장소가 옛 판을 내주지 못하면 되돌릴 수 없어요(`capabilities.versions`).
- 지우기(`DELETE /v1/secrets/{secret_id}`)는 참조하는 소스가 없을 때만 돼요.

### 8.2 만료 알림
- `expires_at`을 가진 값은 만료 전에 알려요. 인증서는 넣을 때 인증서의 만료 시각을 읽어 적고, 사람이 아는 토큰의 만료는 `PATCH`로 적고, 바깥 저장소가 알려 주면(`expiry_metadata`) 그것을 써요.
- 알리는 때는 만료 30일 전, 7일 전, 1일 전이에요(**가정**. 기본값 표에 아직 없어요). 지표는 `secret_expires_in_s`, 사건 코드는 `secret.expiring`이에요. 알림은 소스의 담당자에게 가고 문제 목록의 항목이 돼요(ADR-0013).

**짧게 사는 자격을 주는 소스.** 소스가 그 방식을 지원하고 바깥 저장소 어댑터의 `capabilities`에 `short_lived`가 있으면 먼저 써요. `open`이 임대 기간이 있는 자격(`lease_expires_at`)을 주고, 프락시움은 저장하지 않고 임대 기간 안에서만 쓰고 연결이 끝나면 버려요. 돌려 쓸 판이 사라지고 오래 사는 값은 저장소가 돌려요. 값의 수명이 짧을수록 훔친 값의 쓸모가 짧아서, 비밀 값 관리의 지침(OWASP)도 가능하면 동적 비밀 값을 쓰라고 해요.

## 9. 권한과 감사
### 9.1 누가 무엇을 하나
| 일 | 누가 |
|---|---|
| 소스에 딸린 비밀 값을 넣고, 바꾸고, 물리고, 지우기 | 그 소스를 범위에 가진 `operator`, `admin` |
| 제품 범위의 비밀 값(알림 길의 열쇠, 서명 열쇠) | 넣고 바꾸기는 `admin`만. 메타 정보는 `auditor`도 봐요. 값은 아무도 못 읽어요 |
| 메타 정보 읽기 | 그 소스를 범위에 가진 `viewer` 이상. 제품 범위의 것은 `admin`, `auditor` |
| 정의에 참조를 넣기 | `editor`(그 소스에 딸린 비밀 값의 참조만) |
| 시험 연결(`checks`) | 그 소스의 `operator` |
| 풀어 쓴 기록 읽기, 으뜸 열쇠의 다시 감싸기와 물리기 | `auditor`, `admin` 읽기 / `admin`(다시 감싸기는 승인 필요) |
| `allowed_hosts` 바꾸기 | 그 소스를 범위에 가진 `operator`, `admin` |
| 샌 것으로 의심될 때 소스를 한 번에 멈추기(`pause_sources_by_secret`) | 그 소스들을 모두 범위에 가진 `operator`, 넓으면 `admin` |

**`editor`가 할 수 있는 것과 없는 것.** 있어요: 참조를 정의에 더하고 고치고, 메타 정보를 읽어요. 없어요: 값을 보거나 넣거나 바꾸는 것, 판을 물리는 것, 비밀 값을 지우는 것, 새 판의 시험 연결(`:check`).

**비밀 값을 푸는 일(들여다보기, 점검, 미리 보기, 시험 수집)의 권한.** 본줄기의 소스 정의 그대로이면 그 소스를 범위에 가진 `editor`도 해요. 브랜치가 닿는 주소(`endpoints`)를 바꿨으면 그 소스의 `operator`여야 해요. 제안을 만들 수 있다는 것만으로 바뀐 주소에 남의 소스의 열쇠를 쓰지 못해요. 그때도 주소는 `allowed_hosts` 안이어야 해요(6절). 비밀 값은 정의가 아니라서 제안과 승인을 거치지 않고 넣어요.

### 9.2 감사 기록에 남는 것
ADR-0012의 감사 기록 칸(`audit_id`, `occurred_at`, `actor_kind`, `actor_id`, `action`, `target_kind`, `target_id`, `outcome`, `request_id`, `detail`)을 그대로 써요. `target_kind`는 `secret`, `target_id`는 `secret_id`예요. 값은 어디에도 없어요.

| `action`(닫힌 목록에 더해요) | 언제 | `detail`의 칸 |
|---|---|---|
| `secret_created`, `secret_deleted` | 넣었어요 / 지웠어요 | `kind`, `provider`, `scope` |
| `secret_version_added`, `secret_version_activated` | 새 판을 넣었어요 / `current`가 됐어요 | `version`, `fingerprint_prefix`, `previous_version` |
| `secret_version_retired` | 판을 물렸어요 | `version`, `reason`(`replaced`, `failed`, `manual`, `suspected`) |
| **`secret_opened`** | **풀어 썼어요** | `version`, `role`, `instance_id`, `run_id`, `purpose`(`sync`, `check`, `introspect`, `trial_ingest`, `rewrap`) |
| `secret_open_denied` | 풀기가 거절됐어요 | 위와 같고 `reason` |
| `master_key_rewrapped` | 다시 감쌌어요 | `from_key_id`, `to_key_id`, `count` |
| `secret_hosts_changed` | `allowed_hosts`를 바꿨어요 | `before`, `after` |

- **풀어 쓴 기록은 "언제 어느 역할의 어느 실행이 풀어 썼나"예요.** 행위자는 사람이 아니라 역할의 벌이라서 `actor_kind`에 `role_instance`(`actor_id`는 `instance_id`)를 더하고, 그 일을 시킨 사람이나 일정은 `detail.on_behalf_of`에 적어요. 
- 기록은 **연결 하나에 한 줄**이에요. 보통의 읽기를 적지 않는다는 규칙은 값을 푸는 일에 걸리지 않아요. 거절된 시도도 적고, 보관 기한은 감사 기록과 같아요(기본값 3년).
- 샌 것으로 의심될 때는 `GET /v1/audit-records`를 `filter[action][equals]=secret_opened`, `filter[target_id][equals]=sec_41`, `occurred_at`의 구간으로 걸러 뽑아요(14절).

## 10. 프리셋의 요청 틀과 정의 안의 값 막기
### 10.1 자리 표시와 가리기
프리셋의 허용된 요청(`allowed_requests`, ingestion 3.1)에 **비밀 값이 들어갈 자리**(`secret_slot`)를 따로 표시해요. 틀의 그 자리에만 값이 들어가요.
```yaml
allowed_requests:
  - {name: login, method: POST, path_template: /session,      # 지어낸 소스의 길
     body_shape: {user: {secret_slot: username}, pass: {secret_slot: password}}}
  - {name: list_servers, method: GET, path_template: /servers,
     headers: {authorization: {secret_slot: token, prefix: "Bearer "}}}
```
- 자리 표시의 이름은 소스의 `credential_ref`가 가리키는 비밀 값의 `field_names` 안에 있어야 해요. 아니면 프리셋을 싣거나 정의를 저장할 때 거절해요.
- 자리 표시는 **머리말과 본문에만** 둘 수 있어요. 주소(경로, 검색어)는 중계 장치와 접근 기록이 어디서나 찍어서 둘 수 없어요. 값을 주소에 넣어야만 하는 소스의 프리셋은 싣지 못해요(16절).
- 자리 표시는 **로그, 추적, 요청의 견본에서 저절로 가려져요**(`***`). 요청을 만드는 한 곳(어댑터 앞단, 읽기 허용 목록과 같은 자리)에서 가려서 프리셋이 우회하지 못해요.

### 10.2 자유로운 검색 안의 값 검사
쿼리 말을 받는 소스의 검색은 관리자가 자유롭게 적어요(ingestion 8.2). 이 글 안에 값을 적으면 정의로 퍼져요. 그래서 **저장할 때** 값처럼 보이는 것을 찾아 막아요(허용된 명령으로 검사하는 것에 더하는 안전망이에요). 검사는 자유로운 검색만이 아니라 **정의의 모든 글 칸**에 걸리고 제안의 검사에서 해요. 확실한 꼴은 막고 애매한 것은 경고해요.
- 찾는 모양: `password=`, `token=`, `api_key=` 같은 이름 뒤의 값 / 주소 속 계정(`scheme://user:값@host`) / 인증서와 개인 키의 머리(`-----BEGIN ...`) / `Authorization:`, `Bearer ` 뒤의 글자열 / 길고 무작위로 보이는 글자열(길이와 엔트로피의 문턱은 **가정**이고 지어낸 견본으로 재서 정해요).
- 확실한 꼴이 걸리면 저장을 거절하고(`invalid_input.secret_like_value`) 애매한 것은 경고만 해요. 오류와 경고는 어느 칸의 어느 위치인지와 어느 규칙인지만 말하고 **걸린 글을 되풀이하지 않아요**. 고치는 길은 값을 비밀 값에 넣고 자리 표시를 쓰는 것이에요. 탐지는 경계가 아니에요(16절).

## 11. 지나가는 길
### 11.1 소스로 가는 연결
- 암호화가 기본이고 소스의 인증서와 이름을 확인해요. 믿는 인증 기관은 **조직의 인증 기관을 설정으로 받아요**(배포가 줘요).
- 소스마다 `tls`가 있어요: `verify`(기본 `true`)와 예외의 `verify_off`(`reason`, `approved_by`, `approved_at`, `expires_at`). **확인을 끄는 것은 소스마다의 드러난 예외예요.** 정의의 변경이라 이력이 남고, 건강에 경고로 보이고, `tls_verify_disabled_sources`가 수를 세요. 승인은 `admin`이 하고 기한이 있어요(기한이 지나면 확인이 다시 켜져요). 암호화 없이 닿는 소스도 같은 예외예요.
- 소스가 클라이언트 인증서를 요구하면 `certificate` 비밀 값을 써요.

### 11.2 프락시움 안
- **역할 사이와 수집기와 본체 사이**는 서로를 확인하는 암호화 연결이에요(수집기와 본체 사이는 실제 소스를 붙이는 클로즈 베타부터, 역할 사이는 오픈 베타). 양쪽이 인증서를 내보여요. 인증서는 배포의 인증 기관이 내고 돌려 써요. 프락시움이 발급자가 되지 않아요. 수집기는 인증서에 더해 수집기용 시스템 계정의 토큰을 써요(ingestion 6.1). 토큰만 훔쳐서는 수집기인 척할 수 없어요.
- **저장소 연결**은 암호화하고 서버의 인증서를 확인해요(PostgreSQL 공식 문서: SSL 연결은 암호와 질의와 반환 데이터를 모두 암호화하고, 양쪽이 인증서를 내밀 수 있어요).

## 12. 쉬는 데이터
### 12.1 저장소, 백업, 내려 둔 파일
PostgreSQL 공식 문서가 드는 암호화 선택지는 비밀번호의 해시, 특정 칸을 암호화하는 확장, 파티션이나 파일 시스템의 암호화, 네트워크의 SSL, 클라이언트 쪽 암호화예요. 본체에 투명한 데이터 암호화는 그 목록에 없어요. 그래서 **저장소의 디스크 암호화와 백업의 암호화는 배포가 켜요**(공식 문서는 파일 시스템이나 블록 수준의 암호화가 도둑맞은 디스크를 막지만 마운트된 동안의 공격은 막지 못한다고 해요). 내려 둔 파일은 객체 저장소의 암호화 기능을 배포가 켜요.

**제품은 켜져 있는지를 점검해 건강에 보여요**(`at_rest_encryption_enabled`: 0/1/모름). 객체 저장소는 설정을 물어 확인해요. 디스크와 백업은 제품이 직접 볼 수 없는 경우가 많아서 배포가 선언한 값을 `declared`로 보이고, 선언이 없으면 모름이에요. 모름을 켜짐으로 읽지 않아요.

### 12.2 `confidential` 칸의 칸 단위 암호화
민감 등급이 `confidential`인 속성과 원본 기록의 그 컬럼은 제품이 칸 단위로 암호화해요(같은 봉투 암호화). DB를 읽을 수 있는 사람도 그 값은 못 봐요. PostgreSQL의 칸 암호화 확장은 쓰지 않아요. 공식 문서가 밝히듯 복호화 열쇠와 평문이 서버에 잠깐 있어 서버 관리자가 가로챌 수 있어요. 공식 문서도 서버를 믿을 수 없으면 클라이언트가 암호화하라고 해요. 프락시움에서는 앱(API와 일꾼)이 암호화하고, 속성 값(JSONB)에는 평문 대신 `{"enc": {"key_id": "ck_7", "nonce": "...", "ct": "..."}}` 모양이 들어가요.

- **열쇠.** `purpose: column`의 으뜸 열쇠가 **칸 열쇠**를 감싸요. 칸 열쇠는 `kg_id`와 객체 타입마다 하나예요(가정. 재서 정해요). 한 열쇠로 낼 수 있는 암호화의 횟수에는 표준의 한도가 있어요(무작위 nonce를 쓸 때. 숫자는 이 조사에서 확인하지 못했어요). 그래서 열쇠를 일정한 수마다 새로 내요.
- **묶음 정보.** `kg_id`, 표, 행의 ID(`object_id`나 `natural_key`), 칸 이름, `aad_format`이에요. 암호문을 다른 행이나 칸으로 옮겨 붙여도 풀리지 않아요.
- **푸는 역할.** 그 칸을 읽고 쓰는 API와 일꾼이 칸 열쇠를 풀어요. 질의 엔진은 못 풀어요(`confidential` 값은 투영에 없어요). 비밀 값의 으뜸 열쇠(`purpose: secret_value`)와 다른 열쇠예요. API가 칸 열쇠를 풀 수 있어도 소스의 비밀 값은 풀지 못해요.
- 읽기는 권한도 따라요. `confidential`을 읽으려면 부여의 `max_sensitivity`가 `confidential`이어야 해요(ADR-0012). 암호화는 그 위의 한 겹이에요.

**숨기지 않고 적는 영향.** 암호화한 칸으로는 **찾거나 정렬하지 못해요.**
| 하고 싶은 일 | 어떻게 되나 |
|---|---|
| `filter[<속성>]`으로 거르기, 정렬, 범위 | 안 돼요. `invalid_input.filter_on_encrypted_attribute`(가정)로 거절해요. 가려진 속성으로 거를 때와 같은 길이에요 |
| 색인, 겹친 객체 찾기, 고르기 값의 집계 | 안 돼요. 암호화한 칸에는 색인을 두지 않아요 |
| 식별 키로 쓰는 속성 | `confidential`은 식별 키가 될 수 없어요. 같은 것 알아보기가 찾기에 기대기 때문이에요 |
| 컬럼 통계, 읽기 | `open`이 아닌 컬럼은 범위와 흔한 값을 지표에 저장하지 않아요(ADR-0013). 읽을 때마다 푸는 비용이 드는데 큰 읽기에서 얼마인지는 재서 정해요 |

이것은 `confidential`로 표시한 칸에만 걸려요. 표시하지 않은 속성은 DB를 읽는 사람에게 보여요. 어느 속성을 `confidential`로 두는지는 관리자의 몫이고 등급은 컬럼에서 속성으로 따라 흘러요(ingestion 8.5).

### 12.3 내용 해시에 드는 `confidential` 값: 열쇠를 단 해시(알파부터)
객체와 원본 기록의 내용 해시(ADR-0009, kg-storage 7.3)에 드는 `confidential` 값은 값 자체가 아니라 **열쇠를 단 해시**(HMAC)로 들어가요. 그냥 해시면 짧거나 추측하기 쉬운 값을 DB를 읽는 사람이 맞춰 볼 수 있어서예요. 해시 열쇠는 KG마다 하나이고 으뜸 열쇠로 감싸 저장소에 두어요(열쇠 재료는 평문으로 저장소에 없어요). 칸 암호화는 오픈 베타지만 이것은 **알파부터** 해요. 뒤에 바꾸면 내용 해시, 그래프 해시, `kg_version_id`가 모두 바뀌기 때문이에요. 해시에는 타입과 속성의 이름이 아니라 바뀌지 않는 ID가 들어요. 암호화한 값의 봉투 모양(`{"enc": ...}`)은 알파에 읽을 줄 아는 코드의 자리를 두어 오픈 베타에 해시가 바뀌지 않게 해요.

## 13. 수집한 데이터에 섞여 온 비밀 값
받을 때 지워요(ingestion 7.3의 `redact`를 넓혀요).
1. 프리셋과 데이터셋이 선언한 칸(`redact`: `drop`, `mask`)을 지워요.
2. 선언하지 않은 문자열 칸에서 값처럼 보이는 것을 찾아 지워요(10.2의 모양. 돌리는 칸과 비용은 재서 정해요. 가정).
3. 수집 봉투로 온 기록은 받는 쪽이 다시 지워요(`redacted_again`).

해시는 지운 뒤 내용으로 구하고 지운 규칙의 버전과 경로를 남겨요. **지운 수가 지표로 남아요**(`secret_scrubbed_fields`, 데이터셋마다. ADR-0013). 선언하지 않았는데 탐지가 지운 것은 문제 목록에 올려 프리셋이 칸을 선언하게 해요. 이미 쌓인 원본 기록에서 나중에 발견한 값은 **내용을 걷어 내요**: 내용은 지우고 해시와 자리와 까닭만 남기는 표시예요(`admin`의 운영 행위 `redact_raw_record`, 감사에 남아요). 걷어 낸 기록을 다시 돌릴 때는 남은 해시로 「같은 입력」임을 보이고 값은 걷어 낸 것으로 다뤄요. 표시는 원본 기록의 모양에 처음부터 있어요(ADR-0009). 로그, 추적, 내려 둔 파일에 남은 값은 같은 길로 치워요(14절 6).

## 14. 급할 때
비밀 값이 샌 것으로 의심될 때의 차례예요. 값을 화면에서 다시 보려고 하지 않아요. 읽는 길이 없어요.
| 차례 | 하는 일 | 어떻게 |
|---|---|---|
| 1 | 그 값을 쓰는 소스를 한 번에 멈춰요 | 운영 행위 `pause_sources_by_secret`. 새 연결이 없어지고 값에 `suspected`가 표시돼요. 되돌리는 행위는 소스마다 `resume_source`예요. 승인은 기본으로 필요 없고(되돌릴 수 있고 지키는 행위예요) 설정으로 켤 수 있어요 |
| 2 | 소스 쪽에서 옛 자격을 거두고 새 자격을 받아요 | 소스를 맡은 쪽의 일이에요(프락시움은 소스에 쓰지 않아요) |
| 3 | 새 값을 넣고 확인해요 | `POST /v1/secrets/{secret_id}/versions`, 그리고 `:check`(멈춘 소스에도 시험 연결은 돌아요) |
| 4 | 옛 판을 물려요 | `:retire`(`reason: suspected`). 암호문이 지워져요 |
| 5 | 풀어 쓴 기록을 뽑아요 | `GET /v1/audit-records`를 `secret_opened`와 그 `secret_id`로 걸러 의심되는 때부터 봐요. 일정에 없던 풀기가 있는지 봐요 |
| 6 | 소스를 이어요, 샌 곳을 치워요 | 소스마다 `resume_source`. 값이 로그, 정의, 견본에 남았는지 찾아 지워요 |

**으뜸 열쇠가 샜다고 의심되면** 그 열쇠로 감싼 모든 값이 의심돼요. 새 으뜸 열쇠를 세우고(4.5) 모든 비밀 값을 새 값으로 바꿔요. 다시 감싸기만으로는 모자라요. 이미 가져간 암호문을 옛 열쇠로 풀 수 있어서요.

[운영 행위의 목록](self-observability.md)에 있는 것은 `pause_sources_by_secret`, `rewrap_master_key`(`admin`의 승인), `redact_raw_record`이고, 나머지는 위 API의 길이에요.

## 15. 단계
| | 알파 | 클로즈 베타 | 오픈 베타 |
|---|---|---|---|
| 포트와 어댑터 | 포트, 제품에 든 저장소(열쇠 파일) | 바깥 비밀 저장소의 어댑터 | 열쇠 관리 서비스의 어댑터(하드웨어 보안 모듈은 필요가 있을 때) |
| 값 | 쓰기만 되는 값, 가리기, 참조만 정의에, 수집할 때 지우기 | 판과 돌려 쓰기, 만료 알림, 짧게 사는 자격 | 으뜸 열쇠의 돌려 쓰기, 다시 감싸기 |
| 기록과 점검 | 넣고 바꾼 기록 | 풀어 쓴 기록 | 으뜸 열쇠의 건강 점검, 쉬는 데이터 암호화 점검 |
| 칸 단위 암호화 | 열쇠를 단 해시(12.3), 봉투 모양을 읽는 자리 | - | `confidential` 칸의 암호화 |
| 길과 떨어진 망 | 소스로 가는 TLS 확인 | 수집기와 본체 사이의 서로 확인하는 연결 | 역할 사이의 서로 확인하는 연결, 떨어진 망의 비밀 값 |
| 급할 때 | - | `:retire`, 풀어 쓴 기록 뽑기 | 운영 행위 `pause_sources_by_secret`, `rewrap_master_key`, `redact_raw_record`, 으뜸 열쇠 절차 |

오픈 베타에 나가려면 위가 모두 구현돼 있어야 해요. 알파의 임시 콘솔은 비밀 값의 메타 정보만 보이고 값을 입력받지 않아요([임시 콘솔](temporary-console.md)).

## 16. 알고 가는 한계와 아직 정하지 않은 것
**알고 가는 한계**
- **메모리에서 값을 완전히 지운다고 보장하지 못해요.** 가비지 수집, 스왑, 덤프가 있어요. 바이트 조각에 담고 덮어쓰고 덤프와 스왑을 막는 설정으로 줄이는 데 그쳐요.
- **풀기 권한은 소스가 아니라 역할에 있어요.** 수집 부분이 뚫리면 그 부분이 풀 수 있는 모든 비밀 값이 노출돼요. 으뜸 열쇠를 나눠 줄일 수 있지만 지금은 정하지 않았어요. 알파는 한 프로세스라 분리가 코드의 길 수준이에요.
- **값 탐지는 안전망이에요.** 못 찾는 값이 있고 정상 글을 막기도 해요.
- **소스의 오류 글을 안 싣는 대가로 원인 찾기가 불편해요.** 분류와 상태 코드와 시간뿐이에요.
- **수집기가 보고한 풀어 쓴 기록을 본체는 확인하지 못해요.** 디스크와 백업의 암호화도 배포가 켜고 제품은 점검만 해요.
- **주소에 값을 넣어야 하는 소스는 프리셋을 싣지 못해요.** `confidential`이 아닌 속성은 DB를 읽는 사람에게 보여요.
- **`confidential`이 아닌 값은 해시로 맞춰 볼 수 있어요.** 열쇠를 단 해시는 `confidential` 값에만 걸려요(12.3).

**아직 정하지 않은 것**
- 수집기 쪽 암호화 저장소의 모양과 값을 넣는 명령.
- 해시 열쇠를 감싸는 으뜸 열쇠의 쓰임(`purpose`)을 어떻게 가르는지.
- 만료 알림의 때와 값 탐지의 문턱을 기본값 표에 더하는 것.
