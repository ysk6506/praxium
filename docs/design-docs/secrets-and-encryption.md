# 시크릿과 암호화

프락시움은 조직의 거의 모든 인프라 시스템을 읽는 자격 증명(키 모음)을 보유해요. 읽기 전용 계정이어도 그 모음이 유출되면 조직 전체의 구성이 유출돼요. 이 문서는 그 키(시크릿)를 어떻게 입력하고, 어디에 저장하고, 누가 언제 복호화해서 쓰고, 어떻게 로테이션하고, 유출됐을 때 어떻게 대응하는지를 적어요. 제품 책임자의 요구는 이래요. 소스 시스템의 연동 정보를 암호화해서 관리하는 것이 중요해요. 프로덕션에 나가려면 요구되는 수준이고, 오픈 베타 때는 구현돼 있어야 해요.

> **경로와 필드는 다음 변경의 OpenAPI 문서에서 확정돼요. 그때 바뀔 수 있어요.** 경로는 `/v1/...`이고 이름은 이 문서가 정한 가정이에요. 예시의 값은 모두 지어낸 거예요.

## 1. 목적과 다루는 질문
- 어디에 저장하나요(3, 4절)? API로 입력한 값을 다시 볼 수 있나요(5절)? 누가 복호화할 수 있나요(6절)?
- 분리망의 소스는요(7절)? 로테이션에 실패하면요(8절)? 누가 언제 사용했는지는요(9절)?
- 값이 정의, 로그, 수집한 데이터로 유출되지 않나요(10, 6, 13절)? 유출이 의심되면(14절), 마스터 키를 잃으면(4.6)? 언제 구현하나요(15절)?

시크릿 제공자가 멈춰도 API와 질의 엔진은 시크릿을 복호화하지 않아서 KG와 질의는 그대로 응답해요. 멈추는 것은 수집뿐이에요.

## 2. 개요
### 2.1 시크릿의 종류와 원칙
| 종류 `kind` | 담는 필드 `field_names` | 사용처 |
|---|---|---|
| `password` | `username`, `password` | 세션 로그인이나 SQL 계정으로 접속하는 소스 |
| `token` | `token` | 토큰으로 접속하는 HTTP 소스 |
| `certificate` | `certificate_pem`, `private_key_pem` | 소스가 클라이언트 인증서를 요구할 때 |
| `connection_string` | `dsn` | 연결 문자열 하나로 접속하는 소스 |
| `notifier_key` | `key` | 알림을 보내는 채널(ADR-0013) |
| `signing_key` | `private_key_pem` | 프락시움이 서명하는 키 |

서비스 계정의 토큰(ADR-0012)은 프락시움이 발급한 것이라 해시만 저장하고, 이 스토리지에 넣지 않아요. 그 토큰을 보유하고 사용하는 호출자(수집기, 다른 시스템)가 자기 쪽에서 `token`으로 다뤄요.

**원칙은 4가지예요.** (1) 평문으로 저장하지 않아요. (2) 사용하는 순간에만, 사용하는 역할에서만 복호화해요. (3) API와 로그와 내보내기로 다시 나오지 않아요. (4) 누가 언제 사용했는지가 남아요.

### 2.2 입력부터 사용까지
```
 사람·시스템 ─(1) 값 입력: POST /v1/secrets ─▶ [API 역할]
                 (값은 본문에만)                │ 데이터 키를 만들어 값을 암호화(AAD = secret_id, 버전)
                                                │ 데이터 키를 마스터 키로 "래핑"만 해요(복호화할 수 없어요)
                                                │ 값과 데이터 키는 메모리에서 지워요
                                                ▼
     [스토리지 PostgreSQL]  secret, secret_version = 암호문 + 래핑한 데이터 키 + 메타 정보
     [정의] source.credential_ref = { secret_id }  ← 참조만. 브랜치·제안·내보내기에도 참조만
                                                │
 [워커의 수집 부분] ─(2) 소스 하나의 수집 작업을 받아요 ─┤ 그 소스의 참조인지 확인
        │ (3) 래핑한 데이터 키를 언래핑해 달라고 ──▶ [마스터 키: 키 관리 서비스 / 하드웨어 보안 모듈 / 키 파일]
        │◀(4) 데이터 키 ── 값을 복호화해 메모리에만 보관해요
        │ (5) 요청 템플릿의 플레이스홀더에 값을 넣어 읽기 전용 요청 ─TLS(인증서 확인)─▶ [소스]
        │ (6) 연결이 끝나면 값을 지워요. "복호화 사용 기록"을 감사 로그에 남겨요
 [질의 엔진] ✕ 마스터 키에 접근할 권한이 없어요      [API 역할] ✕ 복호화 메서드가 없어요
```
외부 시크릿 스토리지 어댑터를 쓰면 스토리지 부분이 외부 스토리지로 바뀌고 프락시움에는 참조와 메타 정보만 남아요(3절).

## 3. 제공자 포트
시크릿은 포트 하나(`SecretProvider`) 뒤에서 다뤄요. 포트의 용도가 3가지라 인터페이스도 3개로 나눠 조립해요(ADR-0006의 방식. 구조 계약에 등록하는 변경에서 적용해요).

| 용도 | 메서드(의미) | 하는 일 | 어느 역할의 조립이 사용하나 |
|---|---|---|---|
| 쓰기 | 입력(`put`) | 새 시크릿과 첫 버전을 입력해요. 값은 입력에만 있어요 | API |
| | 교체(`add_version`) | 새 버전을 추가해요(8절의 절차를 시작해요) | API |
| | 폐기(`retire`) | 버전을 사용 중단하고 암호문을 삭제해요 | API, 워커 |
| 복호화 | 사용 시점 복호화(`open`) | 값(또는 수명이 짧은 자격 증명)을 메모리로 가져와요. 호출한 역할과 실행의 식별자를 받아 복호화 사용 기록을 남겨요. 끝나면 `close`로 덮어써요 | **워커의 수집 부분, 수집기만** |
| 메타 | 메타 정보 읽기(`describe`) | 이름, 버전, 시각, 만료, 지문 앞부분 | 모든 역할 |

**값을 읽어 반환하는 메서드가 API 측에 없어요.** 어댑터 포트에 쓰기 메서드가 없다는 읽기 전용의 세 번째 방어선(ADR-0008)과 같은 방식이에요. `open`은 소스에 접속하는 역할의 조립에만 연결돼요. API 역할의 조립은 `open`이 있는 인터페이스를 받지 못해요. 구조 검사가 확인해요.

### 3.1 어댑터 2종
| | 외부 시크릿 스토리지 어댑터 | 제품 내장 엔벨로프 암호화 어댑터 |
|---|---|---|
| 값이 있는 곳 | 그 스토리지 | 프락시움 스토리지에 있는 암호문 |
| 프락시움이 보유하는 것 | 참조(`external_ref`), 메타 정보 | 암호문, 래핑한 데이터 키, 메타 정보 |
| 권한, 로테이션, 감사 | 그 스토리지가 담당해요(프락시움도 복호화 사용 기록은 남겨요) | 프락시움이 해요(4~9절) |
| 어댑터의 형태 | 널리 쓰이는 규약마다 하나. 스토리지가 제공하는 기능(값 저장 / 수명이 짧은 자격 증명 / 암호화 대행) 가운데 쓰는 것을 `capabilities`로 선언해요 | 마스터 키 어댑터 3종(키 관리 서비스, 하드웨어 보안 모듈, 키 파일) |

공개된 시크릿 스토리지의 문서는 기능을 3가지로 나눈다고 확인했어요: 입력한 값을 반환하는 저장, 요청에 따라 자격 증명을 발급하고 임대 기간이 지나면 회수하는 동적 시크릿, 데이터를 저장하지 않고 암호화만 해 주는 암호화 대행. 프락시움은 앞의 둘을 외부 스토리지 어댑터의 `capabilities`(`versions`, `short_lived`, `expiry_metadata`)로, 셋째를 마스터 키 어댑터(래핑과 언래핑)에 사용해요.

### 3.2 선택 기준
시크릿마다 어댑터를 선택해요(`secret.provider`: `builtin`, `external`, `remote`).
1. 조직이 이미 가진 외부 시크릿 스토리지가 있고 워커가 접속할 수 있어요 → **외부 스토리지**를 권해요. 권한과 로테이션을 이미 운영하고 있어요.
2. 외부 스토리지가 없는 배포 → **제품 내장 스토리지**예요. 이것이 있어서 시크릿 스토리지가 없는 배포가 평문으로 폴백하지 않아요.
3. 소스가 수명이 짧은 자격 증명 발급을 지원해요 → 그 기능이 있는 외부 스토리지예요. 제품 내장 스토리지는 보관만 해요.
4. 소스가 분리망에 있어요 → 그 망 안의 제공자예요(7절).

## 4. 제품 내장 스토리지
### 4.1 키 계층
```
 마스터 키(key_id)        스토리지 밖. 키 관리 서비스 / 하드웨어 보안 모듈 / 키 파일
   │  래핑(wrap)·언래핑(unwrap)
   ▼
 데이터 키                시크릿 버전마다 새로 만들고 한 번만 사용해요. 래핑한 형태(wrapped_key)만 스토리지에 있어요
   │  인증 암호화(AEAD)
   ▼
 값(ciphertext)           필드 이름과 값을 묶은 문자열 하나를 암호화한 것
```
마스터 키는 데이터 키를 래핑하는 키(key-encrypting key)이고 데이터 키는 값을 암호화하는 키예요. 공개된 키 관리 서비스의 문서도 최상위 키가 데이터 키를 보호하는 같은 구조를 설명해요.

### 4.2 암호 요구사항
- **인증 암호화(AEAD)**를 사용해요(RFC 5116의 프레임워크. 예: SP 800-38D의 GCM 모드의 AES-256, 또는 ChaCha20-Poly1305. 시크릿 관리 지침(OWASP)이 두 가지를 예로 들어요). 암호문이 변조됐거나 AAD가 다르면 복호화가 실패해요.
- **추가 인증 데이터(AAD)**에 `secret_id`, `version`, `aad_format`을 넣어요. AAD는 암호화하지 않지만 인증돼요(RFC 5116). 그래서 DB를 수정할 수 있는 사람이 암호문을 다른 시크릿이나 다른 버전의 위치로 옮겨 붙여도 복호화되지 않아요. 데이터 키를 래핑할 때도 같은 AAD를 쓰기를 권해요(구현에서 확인).
- **AAD는 비밀이 아니에요.** 키 관리 서비스의 문서도 AAD(encryption context)가 비밀이 아니고 로그에 평문으로 남는다고 해요. 그래서 `secret_id`와 버전 번호만 넣고 이름이나 주소 같은 것을 넣지 않아요.
- **nonce는 키마다 중복되면 안 돼요**(RFC 5116은 같은 키에서 nonce를 다시 쓰면 GCM의 기밀성과 무결성이 모두 깨진다고 해요). 데이터 키를 버전마다 새로 만들고 한 번만 사용하므로 키 하나에서 암호화가 한 번뿐이에요. nonce는 무작위로 생성해요.
- **임시 값의 규칙.** 평문 값과 데이터 키는 메모리에만 있어요. 덮어쓸 수 있는 바이트 배열에 담고 사용한 뒤 곧바로 덮어써요. 디스크, 임시 테이블, 로그, 트레이스, 오류 메시지에 기록하지 않아요. 코어 덤프와 스왑을 차단하는 배포 설정을 권해요. 완전한 삭제는 보장하지 못해요(16절).
- **지문(`fingerprint_prefix`)은 값의 해시가 아니에요.** 값의 해시 앞부분은 짧은 비밀번호를 DB를 읽는 사람이 대조해 볼 수 있게 해요. 그래서 입력할 때 데이터 키로 만든 키 기반 해시(HMAC)의 앞부분을 계산해요. API가 그때 데이터 키를 보유하고 있어서 복호화하지 않고도 계산할 수 있어요. 방법은 구현에서 확인해요.

### 4.3 저장하는 필드
모든 테이블에 `kg_id`가 있는 규칙(ADR-0009)은 KG에 속한 테이블의 규칙이에요. 시크릿은 배포 하나의 것이라 `kg_id`가 없어요.

| 테이블 | 컬럼 | 설명 |
|---|---|---|
| `secret` | `secret_id`, `name`, `kind`, `field_names`, `provider`, `external_ref`, `scope_kind`(`source` / `product`), `source_id`, `allowed_hosts`, `current_version`, `suspected_at`, `created_by`, `created_at`, `deleted_at` | 시크릿 하나. 값은 없어요. `external_ref`는 외부 스토리지 안의 이름이고 값이 아니에요. `allowed_hosts`는 이 값을 사용해도 되는 주소 목록이에요(6절) |
| `secret_version` | `secret_id`, `version`, `state`, `ciphertext`, `nonce`, `wrapped_key`, `key_id`, `aad_format`, `external_version`, `fingerprint_prefix`, `created_by`, `created_at`, `activated_at`, `retired_at`, `expires_at`, `last_opened_at`, `failure_code` | 버전 하나. 외부 스토리지 어댑터면 `ciphertext`, `nonce`, `wrapped_key`는 비어 있고 `external_version`이 있어요. 폐기한 버전은 암호문을 삭제하고 메타 정보만 남겨요 |
| `master_key` | `key_id`, `kind`(`kms` / `hsm` / `key_file`), `purpose`(`secret_value` / `column`), `location_ref`, `state`(`active` / `decrypt_only` / `retired`), `created_at`, `retired_at` | 마스터 키 목록. 키 재료가 아니라 위치 참조(`location_ref`)만 담아요 |

`secret_version.state`는 `staged`, `trying`, `current`, `retired`, `failed`예요(8절).
### 4.4 마스터 키 보관 위치 3종
| 위치 | 방식 | 알아 둘 것 |
|---|---|---|
| 키 관리 서비스 | 래핑과 언래핑을 서비스에 위임해요. 키 재료가 서비스 밖으로 나오지 않아요 | 서비스가 재료를 자체 로테이션해도 옛 재료는 복호화용으로 남아요. `key_id`가 그대로면 다시 래핑할 필요가 없어요 |
| 하드웨어 보안 모듈 | 같아요 | 지연 시간과 호출 한도를 측정해야 해요 |
| 키 파일 | 배포가 읽기 전용 파일로 제공해요(환경 변수가 아니에요) | 알파와 폐쇄망용이에요. 프로세스가 파일을 읽을 수 있어서 서비스보다 약해요 |

**API 역할은 래핑만 하고 복호화할 수 없어요.** 값을 입력하려면 데이터 키를 래핑해야 해서 래핑 권한이 필요하고, 언래핑 권한은 수집 부분에만 있어야 해요. 키 관리 서비스와 하드웨어 보안 모듈은 두 권한을 따로 부여해요. 키 파일은 마스터 키를 키 쌍으로 두고, 래핑에 쓰는 공개 키를 API에 주고 언래핑에 쓰는 개인 키를 소스에 접속하는 역할(수집 부분)에만 줘요.

**스토리지(PostgreSQL)에 두지 않는 이유.** 키를 그 키가 래핑한 값 옆에 두지 말라는 지침(OWASP)이에요. 같은 DB나 DB와 함께 백업되는 설정 파일에 마스터 키가 있으면 백업 하나로 모든 값이 복호화돼요. 키 파일은 DB 백업과 다른 곳에 두고 접근 권한을 따로 관리해요.

### 4.5 마스터 키 로테이션
```
 1 새 마스터 키를 등록    master_key: 새 것 active, 옛 것 decrypt_only   (새로 입력하는 값은 바로 새 키로 래핑해요)
 2 다시 래핑(작업)        각 secret_version(과 컬럼 키)마다: 옛 키로 언래핑 → 새 키로 래핑 → wrapped_key, key_id 갱신
                          값(ciphertext)은 건드리지 않아요. 갱신은 버전 번호를 조건으로 걸어 중복 실행해도 안전해요
 3 옛 키를 참조하는 행이 0   → 옛 것을 retired로 하고 배포가 키를 삭제해요
```
2번은 언래핑과 래핑을 모두 가진 수집 부분이 수행하고, 운영 액션 `rewrap_master_key`(self-observability 7.1)로 요청해요. `admin`의 승인이 필요해요. 진행 수가 작업 리소스에 표시돼요. 3 전에는 옛 키로 되돌릴 수 있어요(`decrypt_only`).

### 4.6 마스터 키를 잃으면
제품 내장 스토리지의 값은 복구할 수 없어요. 암호문은 쓸모가 없어지고 시크릿을 새 마스터 키로 다시 입력해야 해요(소스 측 자격 증명을 새로 발급받아야 할 수 있어요). 수집이 멈추고 KG와 질의는 그대로 응답해요. 그래서 배포 안내에 마스터 키를 DB 백업과 다른 곳에 둘 이상 보관하고 복원을 연습하는 절차를 적어요. 헬스 상태는 `secret_master_key_reachable`로 "마스터 키에 접속할 수 있는가"를 확인하고, 접속하지 못하면 `secret.master_key_unreachable`을 발행해요(자기 관측성 설계).

## 5. 쓰기 전용 값
### 5.1 API 형태
| 경로 | 메서드 | 하는 일 | 역할 | 작업 |
|---|---|---|---|---|
| `/v1/secrets` | GET, POST | 목록(메타 정보만) / 입력. `Idempotency-Key` 필요 | 읽기: 그 소스를 범위에 가진 `viewer` 이상, 제품 범위의 것은 `admin`, `auditor`. 쓰기: 아래 9절 | - |
| `/v1/secrets/{secret_id}` | GET, PATCH, DELETE | 메타 정보 / 이름, 담당자, 만료 수정(값은 수정할 수 없어요. `If-Match` 필요) / 삭제(참조하는 소스가 없을 때만) | 같아요 | - |
| `/v1/secrets/{secret_id}/versions` | POST | 교체: 새 버전 | 같아요 | - |
| `/v1/secrets/{secret_id}/versions/{version}:check` | POST | 새 버전으로 테스트 연결 | 그 소스의 `operator` | 작업 |
| `/v1/secrets/{secret_id}/versions/{version}:retire` | POST | 버전 폐기 | 같아요 | - |

| `/v1/master-keys/{key_id}:rewrap`, `:retire` | POST | 다시 래핑(4.5. 운영 액션과 같은 일), 옛 키 폐기 | `admin`(승인 필요) | 작업 |

복호화 사용 기록은 `GET /v1/audit-records`를 `action`과 `target_id`로 필터링해 읽어요(9절). **값을 읽는 경로는 없어요.** `GET`은 어느 경로에서도 값을 반환하지 않아요.

**입력 요청과 반환되는 메타 정보**(값은 본문에만 있고, 주소와 헤더에는 없어요):
```json
POST /v1/secrets    Idempotency-Key: 8b0c...
{"name": "inventory-reader-login", "kind": "password", "provider": "builtin",
 "scope": {"kind": "source", "source_id": "src_inventory"},
 "fields": {"username": "svc-read", "password": "(쓰기 전용 값)"}, "expires_at": null}

→ 201 ETag: "sec-1"
{"data": {"secret_id": "sec_41", "name": "inventory-reader-login", "kind": "password",
          "field_names": ["username", "password"], "provider": "builtin",
          "scope": {"kind": "source", "source_id": "src_inventory"}, "current_version": null,
          "versions": [{"version": 1, "state": "staged", "created_by": "sub_21", "created_at": "2031-04-02T09:30:00Z",
                        "last_opened_at": null, "expires_at": null, "fingerprint_prefix": "a3f9"}],
          "suspected": false}, "meta": {}}
```
**새 버전을 입력한 뒤 읽으면**(값은 없어요):
```json
GET /v1/secrets/sec_41   → {"data": {"secret_id": "sec_41", "current_version": 2, "suspected": false, "used_by": [{"kind": "source", "id": "src_inventory"}],
  "versions": [{"version": 2, "state": "current", "last_opened_at": "2031-05-01T08:00:00Z", "fingerprint_prefix": "7c21"},
               {"version": 1, "state": "retired", "retired_at": "2031-05-01T02:00:00Z", "fingerprint_prefix": "a3f9"}]}, "meta": {}}
```
- **값이 들어가는 곳은 본문 하나예요.** 주소(경로, 검색어), 헤더, `cursor`에는 없어요. 어디서나 기록되는 곳이라서요.
- **오류도 값을 반복하지 않아요.** 잘못된 필드는 `errors`에 `pointer`와 `code`만 주고 `params`에 보낸 값을 싣지 않아요.
- **멱등성 보장 기록도 본문을 저장하지 않아요.** 다른 본문인지 구분하려고 본문의 키 기반 해시만 보유하고, 다시 보내면 처음 응답(메타 정보)만 반환해요.
- **요청 본문을 로그로 남기지 않아요.** 접근 로그에도 트레이스에도 없어요. API 앞의 프록시가 기록하지 않게 하는 것은 배포의 몫이에요. **CLI는 값을 인자로 받지 않고** 표준 입력이나 파일에서 읽어요. 인자는 셸 이력에 남아요.
- 새 오류 코드(가정): `invalid_input.secret_like_value`(10.2), `invalid_input.secret_field_unknown`, `conflict.secret_in_use`.

### 5.2 정의에는 참조만
소스의 정의 항목에는 시크릿의 `secret_id`만 들어가요. 브랜치, 제안, 정의의 차이, 드라이 런, 내보낸 파일(`/v1/definition-sets/{set_no}/exports`) 어디에도 값이 없어요. 개별 항목의 유효성 검사(`item_valid`, 정의 설계)는 이것을 확인해요.
```json
{"kind": "source", "name": "inventory",
 "body": {"adapter": "http_json", "preset": "inventory-basic@3",
          "endpoints": ["https://inventory.example.internal"],
          "credential_ref": {"secret_id": "sec_41"},
          "tls": {"verify": true}}}
```
- 참조는 **그 소스에 속한 시크릿**이나 제품 범위의 것만 가리킬 수 있어요. `editor`가 다른 소스의 `secret_id`를 자기 소스에 연결해 그 값을 사용하는 경로를 차단하려는 거예요. 복호화할 때도 시크릿의 `source_id`와 실행의 소스가 같은지 다시 확인해요(6절).
- 시크릿을 교체해도 참조가 같아서 정의의 버전은 바뀌지 않아요. 변경은 정의의 이력이 아니라 감사 로그에 남아요.

## 6. 복호화 지점
| 역할 | 복호화할 수 있나 | 마스터 키 | 값에 접근하는 때 |
|---|---|---|---|
| API | 아니요. `open`이 없어요 | 래핑만 | 입력 요청의 본문이 지나가는 동안 메모리에 잠깐 있어요(암호화하고 곧바로 덮어써요) |
| 워커(수집 부분) | **예** | 언래핑과 래핑 | 수집, 트라이얼 수집, 소스 탐색, 점검의 연결을 맺는 동안 |
| 워커(나머지)와 질의 엔진 | 아니요 | 시크릿의 마스터 키에 접근할 수 없음(컬럼 키는 12.2) | 접근하지 않아요 |
| 수집기 | **예**(자기 망의 제공자에서만) | 본체의 마스터 키에는 접근할 수 없어요 | 연결을 맺는 동안 |

한 프로세스에 역할을 모두 기동하는 알파에서는 이 구분이 코드 경로와 권한 구분으로 성립해요. 배포에서는 수집을 담당하는 워커 인스턴스만 언래핑 권한을 받게 해서 분리해요.

**`open`이 확인하는 것.** (1) 호출자가 수집 부분인가, (2) 시크릿의 소스가 실행의 소스와 같은가, (3) 그 버전이 복호화해도 되는 상태(`current`, `trying`)인가, (4) 유출이 의심된 시각(`suspected_at`)보다 앞서 만든 버전이 아닌가, (5) 소스가 `paused`가 아닌가(테스트 연결은 예외), (6) 연결하려는 주소가 시크릿의 `allowed_hosts` 안인가. 트라이얼 수집과 소스 탐색을 포함해 어느 경로로도 그 밖의 주소에는 사용되지 않아요. `allowed_hosts`를 변경하는 것은 그 소스를 범위에 가진 `operator`나 `admin`이고 감사에 남아요(`secret_hosts_changed`). 브랜치가 주소를 바꾸면 트라이얼 수집 전에 바뀐 주소를 보여 줘요. 실패하면 `secret_open_denied`를 남겨요.

**메모리에 있는 시간.** 연결을 맺는 동안만이에요. 연결 하나에 한 번 복호화하고 끝나면 덮어써요. 오래 유지하는 스트림 소스의 연결은 유지되는 동안 보유하고, 끊겨 다시 맺을 때 다시 복호화해요(그때마다 기록이 남아요). 복호화한 값을 캐시하지 않아요.

**남지 않아야 하는 곳.**
| 곳 | 규칙 |
|---|---|
| 로그 | 값이 없어요. 식별자(`secret_id`, 버전, 역할)와 개수만 기록해요. 이벤트 코드의 `params`에도 값이 없어요 |
| 트레이스 | 요청과 연결의 속성에 값, 헤더, 본문이 없어요. 소스로 가는 요청의 계측은 값이 든 헤더와 본문을 기록하지 않아요 |
| 오류 메시지 | 아래 규칙. 값을 반복하지 않아요 |
| 덤프 | 코어 덤프를 차단해요. 값은 바이트 배열에만 둬요 |
| 지표, 작업 리소스, 운영 액션의 결과 | 식별자, `params`, `result`에 값이 없어요. `detail_key`는 `secret_id`예요 |
| 요청 샘플 | 플레이스홀더는 마스킹된 채로 보여요(10절) |
| 감사 로그, 내보낸 정의, 차이, 제안 | `detail`에 값이 없어요(9절). 정의에는 참조만 있어요(5.2) |

**소스가 반환한 오류 메시지를 그대로 싣지 않아요.** 소스와 드라이버의 오류 메시지에는 연결 문자열, 계정 이름, 주소, 쿼리가 섞여 나오는 일이 흔해요(공개된 약점 목록 CWE-209, CWE-532가 오류 메시지와 로그로 정보가 유출되는 경로를 들어요). 그래서 어댑터는 소스의 오류를 고정 목록의 분류로 변환해요: `auth_failed`, `permission_denied`, `tls_verify_failed`, `connect_timeout`, `protocol_error`, `rate_limited`, `source_error`. 로그와 오류에는 분류, 상태 코드, 소요 시간만 실어요. 원인은 소스 측 로그에서 찾아요(16절).

## 7. 분리망
```
   [본체: API · 워커 · 질의 엔진 · 스토리지]                 [분리망]
    secret 행: provider = remote, 참조와 메타 정보만            수집기(제품이 제공하는 것)
    source.credential_ref = { secret_id }  ─(2) 소스 하나의 수집 작업 ─▶  │ (3) 참조 이름으로 자기 망의 제공자에서 값을 가져와요
                                                                    ▼
                                                      [그 망의 시크릿 스토리지] 또는 [수집기 측 암호화 스토리지]
                                                                    │ (4) 읽기 전용 요청 ──▶ [소스]
    ◀─(5) 수집 엔벨로프(원본 레코드)와 사용 보고(참조, 버전, 시각, 결과) ─┘   값은 이 망을 떠나지 않아요
```
- **본체가 아는 것.** 참조, 이름, 종류, 필드 이름, 만료(그 제공자가 알려 주면), 사용 보고, 점검 결과예요.
- **본체가 모르는 것.** 값, 데이터 키, 그 망의 마스터 키예요. 본체가 침해돼도 그 망의 키는 노출되지 않아요.
- **입력 경로.** 그 망의 제공자에 그 망의 관리자가 직접 입력해요. 본체의 `POST /v1/secrets`로는 값을 입력하지 않아요(값이 본체를 거치기 때문이에요). 본체에는 `provider: remote`로 참조만 등록해요(값이 없는 요청).
- **복호화 사용 기록.** 수집기가 사용 보고를 보내면 본체가 감사 로그에 기록해요. 본체가 검증하지는 못해요(16절). 담당자가 만든 수집기(수집 엔벨로프만 쓰는 것)의 시크릿은 그 소스의 담당자의 몫이에요(ingestion 6.2). 수집기 측 암호화 스토리지의 형태는 정하지 않았어요(16절).

## 8. 버전과 로테이션
### 8.1 버전의 상태 전이
```
 put / add_version
       │
    staged ──(다음 연결 또는 checks)──▶ trying ──연결 성공──▶ current ──(다음 버전이 current가 되면)──▶ retired
                                          │
                                          └─연결 실패──▶ failed ──(retire)──▶ retired
```
- `put`과 `add_version`은 새 버전을 `staged`로 만들어요. 옛 `current`는 그대로예요.
- 다음 연결(또는 `checks`)이 새 버전으로 연결을 한 번 시도해요(`trying`). **한 번만 시도하고 재시도하지 않아요.** 인증 실패를 재시도하지 않는 기본값(소스 보호 값)과 같은 이유로, 소스의 계정이 잠기지 않게 해요.
- 연결에 성공하면 새 버전이 `current`가 되고 옛 버전을 폐기해요(`retired`: 암호문과 래핑한 키를 삭제하고 메타 정보만 남겨요). 시크릿의 `current_version`이 올라가요.
- 연결에 실패하면 새 버전은 `failed`예요. 같은 실행은 옛 `current`로 복귀해 이어 가고, 그 소스의 담당자에게 이벤트 코드 `secret.version_check_failed`로 알려요. 버전의 테스트 연결 실패는 그 소스의 연속 실패(연속 5번)에 세지 않아요. 옛 버전은 `current`로 그대로 남아요.
- 외부 시크릿 스토리지 어댑터는 새 버전을 그 스토리지가 만들어요. 프락시움은 `describe`로 `external_version`이 바뀐 것을 확인하면 같은 절차(`trying`)로 검증해요. 스토리지가 옛 버전을 제공하지 못하면 되돌릴 수 없어요(`capabilities.versions`).
- 삭제(`DELETE /v1/secrets/{secret_id}`)는 참조하는 소스가 없을 때만 돼요.

### 8.2 만료 알림
- `expires_at`을 가진 값은 만료 전에 알려요. 인증서는 입력할 때 인증서의 만료 시각을 읽어 기록하고, 사람이 아는 토큰의 만료는 `PATCH`로 기록하고, 외부 스토리지가 알려 주면(`expiry_metadata`) 그것을 써요.
- 알리는 시점은 만료 30일 전, 7일 전, 1일 전이에요(**가정**. 기본값 표에 아직 없어요). 지표는 `secret_expires_in_s`, 이벤트 코드는 `secret.expiring`이에요. 알림은 소스의 담당자에게 가고 문제 목록의 항목이 돼요(ADR-0013).

**수명이 짧은 자격 증명을 발급하는 소스.** 소스가 그 방식을 지원하고 외부 스토리지 어댑터의 `capabilities`에 `short_lived`가 있으면 먼저 써요. `open`이 임대 기간이 있는 자격 증명(`lease_expires_at`)을 주고, 프락시움은 저장하지 않고 임대 기간 안에서만 사용하고 연결이 끝나면 버려요. 로테이션할 버전이 사라지고 수명이 긴 값은 스토리지가 로테이션해요. 값의 수명이 짧을수록 탈취한 값의 쓸모가 짧아서, 시크릿 관리 지침(OWASP)도 가능하면 동적 시크릿을 쓰라고 해요.

| 작업 | 권한자 |
|---|---|
| 소스에 속한 시크릿을 입력, 교체, 폐기, 삭제 | 그 소스를 범위에 가진 `operator`, `admin` |
| 제품 범위의 시크릿(알림 채널의 키, 서명 키) | 입력과 교체는 `admin`만. 메타 정보는 `auditor`도 볼 수 있어요. 값은 아무도 읽을 수 없어요 |
| 메타 정보 읽기 | 그 소스를 범위에 가진 `viewer` 이상. 제품 범위의 것은 `admin`, `auditor` |
| 정의에 참조 추가 | `editor`(그 소스에 속한 시크릿의 참조만) |
| 테스트 연결(`checks`) | 그 소스의 `operator` |
| 복호화 사용 기록 읽기, 마스터 키의 다시 래핑과 폐기 | `auditor`, `admin` 읽기 / `admin`(다시 래핑은 승인 필요) |
| `allowed_hosts` 변경 | 그 소스를 범위에 가진 `operator`, `admin` |
| 유출이 의심될 때 소스를 일괄 중단(`pause_sources_by_secret`) | 그 소스들을 모두 범위에 가진 `operator`, 범위가 넓으면 `admin` |

**`editor`가 할 수 있는 것과 없는 것.** 가능: 참조를 정의에 추가하고 수정하고, 메타 정보를 읽어요. 불가: 값을 보거나 입력하거나 교체하는 것, 버전을 폐기하는 것, 시크릿을 삭제하는 것, 새 버전의 테스트 연결(`:check`).

**시크릿을 복호화하는 작업(소스 탐색, 점검, 미리 보기, 트라이얼 수집)의 권한.** 메인 브랜치의 소스 정의 그대로이면 그 소스를 범위에 가진 `editor`도 수행해요. 브랜치가 접속하는 주소(`endpoints`)를 바꿨으면 그 소스의 `operator`여야 해요. 제안을 만들 수 있다는 것만으로 바뀐 주소에 다른 소스의 키를 쓰지 못해요. 그때도 주소는 `allowed_hosts` 안이어야 해요(6절). 시크릿은 정의가 아니라서 제안과 승인을 거치지 않고 입력해요.

### 9.2 감사 로그에 남는 것
ADR-0012의 감사 로그 필드(`audit_id`, `occurred_at`, `actor_kind`, `actor_id`, `action`, `target_kind`, `target_id`, `outcome`, `request_id`, `detail`)를 그대로 써요. `target_kind`는 `secret`, `target_id`는 `secret_id`예요. 값은 어디에도 없어요.

| `action`(고정 목록에 추가해요) | 언제 | `detail`의 필드 |
|---|---|---|
| `secret_created`, `secret_deleted` | 입력했어요 / 삭제했어요 | `kind`, `provider`, `scope` |
| `secret_version_added`, `secret_version_activated` | 새 버전을 입력했어요 / `current`가 됐어요 | `version`, `fingerprint_prefix`, `previous_version` |
| `secret_version_retired` | 버전을 폐기했어요 | `version`, `reason`(`replaced`, `failed`, `manual`, `suspected`) |
| **`secret_opened`** | **복호화해서 사용했어요** | `version`, `role`, `instance_id`, `run_id`, `purpose`(`sync`, `check`, `introspect`, `trial_ingest`, `rewrap`) |
| `secret_open_denied` | 복호화가 거절됐어요 | 위와 같고 `reason` |
| `master_key_rewrapped` | 다시 래핑했어요 | `from_key_id`, `to_key_id`, `count` |
| `secret_hosts_changed` | `allowed_hosts`를 변경했어요 | `before`, `after` |

- **복호화 사용 기록은 "언제 어느 역할의 어느 실행이 복호화해서 사용했나"예요.** 행위자는 사람이 아니라 역할 인스턴스라서 `actor_kind`에 `role_instance`(`actor_id`는 `instance_id`)를 추가하고, 그 작업을 요청한 사람이나 일정은 `detail.on_behalf_of`에 적어요.
- 기록은 **연결 하나에 한 건**이에요. 일반적인 읽기를 기록하지 않는다는 규칙은 값을 복호화하는 작업에 적용되지 않아요. 거절된 시도도 기록하고, 보존 기한은 감사 로그와 같아요(기본값 3년).
- 유출이 의심될 때는 `GET /v1/audit-records`를 `filter[action][equals]=secret_opened`, `filter[target_id][equals]=sec_41`, `occurred_at`의 구간으로 필터링해 조회해요(14절).

## 10. 프리셋의 요청 템플릿과 정의 안의 값 차단
### 10.1 플레이스홀더와 마스킹
프리셋의 허용된 요청(`allowed_requests`, ingestion 3.1)에 **시크릿이 들어갈 위치**(`secret_slot`)를 따로 표시해요. 템플릿의 그 위치에만 값이 들어가요.
```yaml
allowed_requests:
  - {name: login, method: POST, path_template: /session,      # 지어낸 소스의 경로
     body_shape: {user: {secret_slot: username}, pass: {secret_slot: password}}}
  - {name: list_servers, method: GET, path_template: /servers,
     headers: {authorization: {secret_slot: token, prefix: "Bearer "}}}
```
- 플레이스홀더의 이름은 소스의 `credential_ref`가 가리키는 시크릿의 `field_names` 안에 있어야 해요. 아니면 프리셋을 적재하거나 정의를 저장할 때 거절해요.
- 플레이스홀더는 **헤더와 본문에만** 둘 수 있어요. 주소(경로, 검색어)는 프록시와 접근 로그가 어디서나 기록해서 둘 수 없어요. 값을 주소에 넣어야만 하는 소스의 프리셋은 적재하지 못해요(16절).
- 플레이스홀더는 **로그, 트레이스, 요청 샘플에서 자동으로 마스킹돼요**(`***`). 요청을 만드는 한 곳(어댑터 앞단, 읽기 허용 목록과 같은 위치)에서 마스킹해서 프리셋이 우회하지 못해요.

### 10.2 자유 검색 안의 값 검사
쿼리 언어를 지원하는 소스의 검색은 관리자가 자유롭게 작성해요(ingestion 8.2). 이 문자열 안에 값을 적으면 정의로 퍼져요. 그래서 **저장할 때** 값처럼 보이는 것을 찾아 차단해요(허용된 명령으로 검사하는 것에 더하는 안전망이에요). 검사는 자유 검색만이 아니라 **정의의 모든 문자열 필드**에 적용되고 제안의 검사에서 수행해요. 확실한 패턴은 차단하고 애매한 것은 경고해요.
- 탐지 패턴: `password=`, `token=`, `api_key=` 같은 이름 뒤의 값 / 주소 속 계정(`scheme://user:값@host`) / 인증서와 개인 키의 헤더(`-----BEGIN ...`) / `Authorization:`, `Bearer ` 뒤의 문자열 / 길고 무작위로 보이는 문자열(길이와 엔트로피의 임계값은 **가정**이고 합성 샘플로 측정해서 정해요).
- 확실한 패턴이 탐지되면 저장을 거절하고(`invalid_input.secret_like_value`) 애매한 것은 경고만 해요. 오류와 경고는 어느 필드의 어느 위치인지와 어느 규칙인지만 알리고 **탐지된 문자열을 반복하지 않아요**. 수정 방법은 값을 시크릿에 입력하고 플레이스홀더를 쓰는 것이에요. 탐지는 보안 경계가 아니에요(16절).

## 11. 전송 구간
### 11.1 소스로 가는 연결
- 암호화가 기본이고 소스의 인증서와 이름을 확인해요. 신뢰하는 인증 기관은 **조직의 인증 기관을 설정으로 받아요**(배포가 제공해요).
- 소스마다 `tls`가 있어요: `verify`(기본 `true`)와 예외인 `verify_off`(`reason`, `approved_by`, `approved_at`, `expires_at`). **검증을 끄는 것은 소스별로 명시하는 예외예요.** 정의의 변경이라 이력이 남고, 헬스 상태에 경고로 표시되고, `tls_verify_disabled_sources`가 개수를 세요. 승인은 `admin`이 하고 기한이 있어요(기한이 지나면 검증이 다시 켜져요). 암호화 없이 접속하는 소스도 같은 예외예요.
- 소스가 클라이언트 인증서를 요구하면 `certificate` 시크릿을 써요.

### 11.2 프락시움 내부
- **역할 사이와 수집기와 본체 사이**는 서로를 검증하는 암호화 연결(mTLS)이에요(수집기와 본체 사이는 실제 소스를 연결하는 클로즈드 베타부터, 역할 사이는 오픈 베타). 양쪽이 인증서를 제시해요. 인증서는 배포의 인증 기관이 발급하고 로테이션해요. 프락시움이 발급자가 되지 않아요. 수집기는 인증서에 더해 수집기용 서비스 계정의 토큰을 써요(ingestion 6.1). 토큰만 탈취해서는 수집기로 가장할 수 없어요.
- **스토리지 연결**은 암호화하고 서버의 인증서를 확인해요(PostgreSQL 공식 문서: SSL 연결은 암호와 질의와 반환 데이터를 모두 암호화하고, 양쪽이 인증서를 제시할 수 있어요).

## 12. 저장 데이터
### 12.1 스토리지, 백업, 아카이브 파일
PostgreSQL 공식 문서가 드는 암호화 선택지는 비밀번호 해시, 특정 컬럼을 암호화하는 확장, 파티션이나 파일 시스템의 암호화, 네트워크의 SSL, 클라이언트 측 암호화예요. 서버 내장 투명 데이터 암호화(TDE)는 그 목록에 없어요. 그래서 **스토리지의 디스크 암호화와 백업 암호화는 배포가 켜요**(공식 문서는 파일 시스템이나 블록 수준의 암호화가 디스크 도난은 막지만 마운트된 동안의 공격은 막지 못한다고 해요). 아카이브 파일은 오브젝트 스토리지의 암호화 기능을 배포가 켜요.

**제품은 켜져 있는지를 점검해 헬스 상태에 표시해요**(`at_rest_encryption_enabled`: 0/1/알 수 없음). 오브젝트 스토리지는 설정을 조회해 확인해요. 디스크와 백업은 제품이 직접 볼 수 없는 경우가 많아서 배포가 선언한 값을 `declared`로 표시하고, 선언이 없으면 알 수 없음이에요. 알 수 없음을 켜짐으로 해석하지 않아요.

### 12.2 `confidential` 컬럼의 컬럼 단위 암호화
민감 등급이 `confidential`인 속성과 원본 레코드의 그 컬럼은 제품이 컬럼 단위로 암호화해요(같은 엔벨로프 암호화). DB를 읽을 수 있는 사람도 그 값은 볼 수 없어요. PostgreSQL의 컬럼 암호화 확장은 쓰지 않아요. 공식 문서가 밝히듯 복호화 키와 평문이 서버에 잠깐 있어 서버 관리자가 가로챌 수 있어요. 공식 문서도 서버를 신뢰할 수 없으면 클라이언트가 암호화하라고 해요. 프락시움에서는 앱(API와 워커)이 암호화하고, 속성 값(JSONB)에는 평문 대신 `{"enc": {"key_id": "ck_7", "nonce": "...", "ct": "..."}}` 형태가 들어가요.

- **키.** `purpose: column`의 마스터 키가 **컬럼 키**를 래핑해요. 컬럼 키는 `kg_id`와 객체 타입마다 하나예요(가정. 측정해서 정해요). 한 키로 수행할 수 있는 암호화 횟수에는 표준의 한도가 있어요(무작위 nonce를 쓸 때. 숫자는 이 조사에서 확인하지 못했어요). 그래서 일정 횟수마다 키를 새로 발급해요.
- **AAD.** `kg_id`, 테이블, 행의 ID(`object_id`나 `natural_key`), 컬럼 이름, `aad_format`이에요. 암호문을 다른 행이나 컬럼으로 옮겨 붙여도 복호화되지 않아요.
- **복호화하는 역할.** 그 컬럼을 읽고 쓰는 API와 워커가 컬럼 키를 언래핑해요. 질의 엔진은 언래핑할 수 없어요(`confidential` 값은 프로젝션에 없어요). 시크릿의 마스터 키(`purpose: secret_value`)와 다른 키예요. API가 컬럼 키를 언래핑할 수 있어도 소스의 시크릿은 복호화하지 못해요.
- 읽기는 권한도 따라요. `confidential`을 읽으려면 부여의 `max_sensitivity`가 `confidential`이어야 해요(ADR-0012). 암호화는 그 위의 한 겹이에요.

**숨기지 않고 적는 영향.** 암호화한 컬럼으로는 **검색이나 정렬을 할 수 없어요.**
| 하고 싶은 작업 | 결과 |
|---|---|
| `filter[<속성>]`으로 필터링, 정렬, 범위 | 안 돼요. `invalid_input.filter_on_encrypted_attribute`(가정)로 거절해요. 마스킹된 속성으로 필터링할 때와 같은 처리예요 |
| 인덱스, 중복 객체 탐지, 선택값 집계 | 안 돼요. 암호화한 컬럼에는 인덱스를 두지 않아요 |
| 식별 키로 쓰는 속성 | `confidential`은 식별 키가 될 수 없어요. 동일 객체 식별이 검색에 의존하기 때문이에요 |
| 컬럼 통계, 읽기 | `open`이 아닌 컬럼은 범위와 빈출 값을 지표에 저장하지 않아요(ADR-0013). 읽을 때마다 복호화 비용이 드는데 큰 읽기에서 얼마인지는 측정해서 정해요 |

이것은 `confidential`로 표시한 컬럼에만 적용돼요. 표시하지 않은 속성은 DB를 읽는 사람에게 보여요. 어느 속성을 `confidential`로 두는지는 관리자의 몫이고 등급은 컬럼에서 속성으로 전파돼요(ingestion 8.5).

### 12.3 내용 해시에 포함되는 `confidential` 값: 키 기반 해시(알파부터)
객체와 원본 레코드의 내용 해시(ADR-0009, kg-storage 7.3)에 포함되는 `confidential` 값은 값 자체가 아니라 **키 기반 해시**(HMAC)로 들어가요. 그냥 해시면 짧거나 추측하기 쉬운 값을 DB를 읽는 사람이 대조해 볼 수 있어서예요. 해시 키는 KG마다 하나이고 마스터 키로 래핑해 스토리지에 두어요(키 재료는 평문으로 스토리지에 없어요). 컬럼 암호화는 오픈 베타지만 이것은 **알파부터** 해요. 나중에 바꾸면 내용 해시, 그래프 해시, `kg_version_id`가 모두 바뀌기 때문이에요. 해시에는 타입과 속성의 이름이 아니라 변하지 않는 ID가 들어가요. 암호화한 값의 엔벨로프 형태(`{"enc": ...}`)는 알파에서 읽을 수 있는 코드를 자리로 확보해 오픈 베타에서 해시가 바뀌지 않게 해요.

## 13. 수집한 데이터에 섞여 온 시크릿
수집할 때 삭제해요(ingestion 7.3의 `redact`를 확장해요).
1. 프리셋과 데이터셋이 선언한 필드(`redact`: `drop`, `mask`)를 삭제해요.
2. 선언하지 않은 문자열 필드에서 값처럼 보이는 것을 찾아 삭제해요(10.2의 패턴. 적용할 필드와 비용은 측정해서 정해요. 가정).
3. 수집 엔벨로프로 들어온 레코드는 수신 측이 다시 삭제해요(`redacted_again`).

해시는 삭제한 뒤 내용으로 구하고 삭제한 규칙의 버전과 경로를 남겨요. **삭제한 개수가 지표로 남아요**(`secret_scrubbed_fields`, 데이터셋별. ADR-0013). 선언하지 않았는데 탐지가 삭제한 것은 문제 목록에 올려 프리셋이 필드를 선언하게 해요. 이미 쌓인 원본 레코드에서 나중에 발견한 값은 **내용을 삭제(redact)해요**: 내용은 지우고 해시와 위치와 이유만 남기는 표시예요(`admin`의 운영 액션 `redact_raw_record`, 감사에 남아요). 삭제한 레코드를 다시 실행할 때는 남은 해시로 「같은 입력」임을 보이고 값은 삭제된 것으로 다뤄요. 표시는 원본 레코드의 스키마에 처음부터 있어요(ADR-0009). 로그, 트레이스, 아카이브 파일에 남은 값은 같은 절차로 정리해요(14절 6).

## 14. 긴급 대응
시크릿 유출이 의심될 때의 절차예요. 값을 화면에서 다시 보려고 하지 않아요. 읽는 경로가 없어요.
| 순서 | 하는 일 | 방법 |
|---|---|---|
| 1 | 그 값을 쓰는 소스를 일괄 중단해요 | 운영 액션 `pause_sources_by_secret`. 새 연결이 없어지고 값에 `suspected`가 표시돼요. 롤백 액션은 소스마다 `resume_source`예요. 승인은 기본으로 필요 없고(롤백할 수 있고 보호하는 액션이에요) 설정으로 켤 수 있어요 |
| 2 | 소스 측에서 옛 자격 증명을 회수하고 새 자격 증명을 발급받아요 | 소스를 담당하는 쪽의 일이에요(프락시움은 소스에 쓰지 않아요) |
| 3 | 새 값을 입력하고 확인해요 | `POST /v1/secrets/{secret_id}/versions`, 그리고 `:check`(중단된 소스에도 테스트 연결은 실행돼요) |
| 4 | 옛 버전을 폐기해요 | `:retire`(`reason: suspected`). 암호문이 삭제돼요 |
| 5 | 복호화 사용 기록을 조회해요 | `GET /v1/audit-records`를 `secret_opened`와 그 `secret_id`로 필터링해 의심되는 시점부터 확인해요. 일정에 없던 복호화가 있는지 확인해요 |
| 6 | 소스를 재개하고, 유출된 곳을 정리해요 | 소스마다 `resume_source`. 값이 로그, 정의, 샘플에 남았는지 찾아 삭제해요 |

**마스터 키 유출이 의심되면** 그 키로 래핑한 모든 값이 의심돼요. 새 마스터 키를 발급하고(4.5) 모든 시크릿을 새 값으로 교체해요. 다시 래핑하는 것만으로는 부족해요. 이미 가져간 암호문을 옛 키로 복호화할 수 있어서요.

[운영 액션의 목록](self-observability.md)에 있는 것은 `pause_sources_by_secret`, `rewrap_master_key`(`admin`의 승인), `redact_raw_record`이고, 나머지는 위 API의 경로예요.

## 15. 단계
| | 알파 | 클로즈드 베타 | 오픈 베타 |
|---|---|---|---|
| 포트와 어댑터 | 포트, 제품 내장 스토리지(키 파일) | 외부 시크릿 스토리지의 어댑터 | 키 관리 서비스의 어댑터(하드웨어 보안 모듈은 필요가 있을 때) |
| 값 | 쓰기 전용 값, 마스킹, 정의에는 참조만, 수집할 때 삭제 | 버전과 로테이션, 만료 알림, 수명이 짧은 자격 증명 | 마스터 키의 로테이션, 다시 래핑 |
| 기록과 점검 | 입력과 교체 기록 | 복호화 사용 기록 | 마스터 키의 헬스 상태 점검, 저장 데이터 암호화 점검 |
| 컬럼 단위 암호화 | 키 기반 해시(12.3), 엔벨로프 형태를 읽는 코드 확보 | - | `confidential` 컬럼의 암호화 |
| 경로와 분리망 | 소스로 가는 TLS 확인 | 수집기와 본체 사이의 mTLS | 역할 사이의 mTLS, 분리망의 시크릿 |
| 긴급 대응 | - | `:retire`, 복호화 사용 기록 조회 | 운영 액션 `pause_sources_by_secret`, `rewrap_master_key`, `redact_raw_record`, 마스터 키 절차 |

오픈 베타에 나가려면 위가 모두 구현돼 있어야 해요. 알파의 임시 콘솔은 시크릿의 메타 정보만 표시하고 값을 입력받지 않아요([임시 콘솔](temporary-console.md)).

## 16. 알려진 한계와 미결 사항
**알려진 한계**
- **메모리에서 값을 완전히 지운다고 보장하지 못해요.** 가비지 컬렉션, 스왑, 덤프가 있어요. 바이트 배열에 담고 덮어쓰고 덤프와 스왑을 차단하는 설정으로 줄이는 데 그쳐요.
- **복호화 권한은 소스가 아니라 역할에 있어요.** 수집 부분이 침해되면 그 부분이 복호화할 수 있는 모든 시크릿이 노출돼요. 마스터 키를 나눠 줄일 수 있지만 지금은 정하지 않았어요. 알파는 한 프로세스라 분리가 코드 경로 수준이에요.
- **값 탐지는 안전망이에요.** 탐지하지 못하는 값이 있고 정상 문자열을 차단하기도 해요.
- **소스의 오류 메시지를 싣지 않는 대가로 원인 파악이 불편해요.** 분류와 상태 코드와 시간뿐이에요.
- **수집기가 보고한 복호화 사용 기록을 본체는 검증하지 못해요.** 디스크와 백업의 암호화도 배포가 켜고 제품은 점검만 해요.
- **주소에 값을 넣어야 하는 소스는 프리셋을 적재하지 못해요.** `confidential`이 아닌 속성은 DB를 읽는 사람에게 보여요.
- **`confidential`이 아닌 값은 해시로 대조해 볼 수 있어요.** 키 기반 해시는 `confidential` 값에만 적용돼요(12.3).

**미결 사항**
- 수집기 측 암호화 스토리지의 형태와 값을 입력하는 명령.
- 해시 키를 래핑하는 마스터 키의 용도(`purpose`)를 어떻게 구분하는지.
- 만료 알림의 시점과 값 탐지의 임계값을 기본값 표에 추가하는 것.
