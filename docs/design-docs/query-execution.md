# 질의 실행기와 읽기의 세 경로

사용자의 SQL을 DB에 안전하게 돌리는 질의 실행기, 여러 단계를 따라가는 그래프 함수, 서버가 SQL을 만들어 주는 내장 읽기, 응답이 싣는 것과 한도의 기본값을 정한 설계예요. 결정은 ADR-0080에 있어요. **이 문서는 아직 구현하지 않은 설계(예정)예요.** 지금의 읽기는 SQL을 쓰지 않고 스냅샷을 훑어요([KG 질의](kg-queries.md), [질의 엔진의 언어와 구조](query-engine-shape.md)). 숫자는 모두 합성 데이터로 잰 원형의 값이고 조건은 [새 저장의 모양](storage-shape.md) 4절에 있어요. 예시의 이름은 지어낸 것이에요.

## 1. 목적과 다루는 질문

- 사용자가 쓴 SQL이 데이터를 바꾸거나, 다른 KG나 높은 민감 등급을 읽거나, 서버를 멈추지 못하게 하려면 무엇을 막아야 하나.
- 읽기 경로는 몇 가지이고, 각각 누가 쓰나.
- 한 번에 몇 단계를 따라가는 질의가 폭발적으로 늘 때 어떻게 끊나.
- 응답은 무엇을 싣고, 예전 약속(REQ-250~256) 가운데 무엇이 바뀌나.

**읽기 경로는 셋**이에요.

| 경로 | 무엇 | 누가 | SQL |
|---|---|---|---|
| **내장 읽기** | 찾기, 객체 읽기, 이웃, 도달 집합, 스키마 설명 | 화면, 에이전트(MCP), REST | 서버 코드가 만들어요 |
| **저장한 질의** | 파라미터가 있는 SQL을 정의로 저장해 REST와 MCP 툴로 내보낸 것([저장한 질의와 간선 정의](saved-queries.md)) | 화면, 에이전트, 시스템 | 사람이 써서 저장했어요 |
| **사람의 임의 질의** | 질의를 만들고 테스트하는 경로. 화면과 REST, 그 능력이 있는 역할만 | 사람 | 호출마다 써요 |

**에이전트(MCP)에는 임의 SQL이 없어요.** 임의 SQL 툴을 기본으로 닫는 것은 에이전트가 틀린 SQL을 쓸 수 있고(큰 스키마에서 텍스트-SQL의 정확도는 낮아요) 사고가 날 수 있어서예요. 에이전트가 틀리기 어려운 호출은 내장 읽기와 저장한 질의예요. DB에 직접 붙는 길(BI 도구)은 제품이 안내하는 길이 아니에요(동시 실행과 행 수의 상한이 없는 길이 생겨요).

## 2. 질의 실행기

**모든 사용자 질의는 질의 실행기를 지나요.** 세 경로 모두예요. 실행기는 다음 순서로 한 질의를 돌려요.

1. 호출자의 KG, 민감 등급, 능력(임의 질의를 쓸 수 있는 역할인지)을 확인해요.
2. 사용자의 문장이면 끝의 세미콜론을 떼고, 첫 낱말이 조회가 아니면 친절한 오류로 거절해요(이 검사는 방어의 근거가 아니고 안내예요).
3. 경로에 맞는 풀(8)에서 연결을 얻어요. 읽기 복제본을 가리키는 풀일 수 있어요([PostgreSQL의 HA](postgres-ha.md) 3절).
4. 트랜잭션을 **명시적으로 읽기 전용, 반복 읽기**로 열고, 그 안에서 `SET LOCAL ROLE`로 (KG, 민감 등급)의 역할로 바꾸고, 시한과 메모리 한도를 `SET LOCAL`로 걸어요.
5. **같은 트랜잭션의 첫 문장으로 KG의 머리 행을 읽어** 세대와 변경 번호와 어느 질의 스키마(평소용인지 큰 적용 중용인지)를 정해요. 사용자 질의와 같은 순간을 보고, 실행 중에는 DDL을 하지 않아요.
6. 감싼 문장을 확장 프로토콜로 돌리고 행과 바이트의 상한을 지켜요.
7. 트랜잭션을 끝내고(되돌려요), 연결을 정리해요(아래 표의 "실행 뒤").
8. 감사에 남겨요.

### 2.1 방어

| 방어 | 내용과 이유 |
|---|---|
| **조회문으로 감싸기** | 사용자의 문장을 `SELECT * FROM (` 줄바꿈 문장 줄바꿈 `) q LIMIT $n`으로 감싸요(끝의 세미콜론은 뗘요). 조회가 아닌 문장(`SET`, `COPY`, `LISTEN`, `EXPLAIN`, `BEGIN`, `DISCARD`, `DECLARE`, `PREPARE`, `DO`, `INSERT`)은 문법 오류이고, 데이터를 바꾸는 CTE는 "최상위여야 한다"는 오류로 거절돼요. 줄바꿈은 줄 끝 주석이 닫는 괄호를 지우지 못하게 해요. `LIMIT`을 바인딩 인자로 주면 인자가 언제나 하나 이상이라 드라이버가 단순 프로토콜로 내려가는 길도 막혀요. 값은 바인딩으로만 보내요. **감싸기가 기본 방어예요.** 준비한 문장은 문장의 수만 막고 종류는 막지 않아서(원형: `SET`, `COPY`, `LISTEN`, `EXPLAIN ANALYZE`, `BEGIN`, `COMMIT`, `DISCARD ALL`, `DECLARE … WITH HOLD`가 모두 통과했어요) "계획을 받아 데이터를 바꾸는 계획이면 거절"은 쓰지 않아요 |
| **역할** | (KG, 민감 등급)마다 하나. 질의마다 트랜잭션 안에서 그 역할로 바꿔요. 로그인 역할은 그 권한을 물려받지 않고 바꾸기만 해요. 역할은 질의 스키마의 `USAGE`, 뷰의 `SELECT`, 제품 함수의 `EXECUTE`만 가져요. 사용자가 되돌릴 길(`RESET ROLE`, `set_config('role', …)`)은 문장과 함수 두 곳에서 막혀요 |
| **읽기 전용** | 질의마다 읽기 전용·반복 읽기 트랜잭션을 **명시적으로** 열어요. 역할의 기본값(`default_transaction_read_only`)은 덧대는 것이지 근거가 아니에요. 원형에서 `set_config`로 그 기본값을 끄면 다음 트랜잭션에서 큰 객체가 만들어졌고 연결 초기화 뒤에도 남았어요 |
| **회수하는 함수** | `PUBLIC`의 실행 권한을 회수하는 목록이에요(2.2절) |
| **시간** | 서버가 자기 시한으로 취소해요. 동시에 DB의 `statement_timeout`과 `transaction_timeout`을 `SET LOCAL`로 걸어요(사용자가 못 바꿀 때만 믿을 수 있어요). 취소 요청은 새 연결을 여는 방식이라 연결이 가득 차면 못 가므로 취소용 연결을 남겨 둬요. 유휴 트랜잭션 시한을 모든 역할에 걸어요 |
| **디스크와 메모리** | 임시 파일 한도(`temp_file_limit`) 2GB를 역할에 걸어요(사용자가 못 바꿔요. **`풀 × 한도`가 디스크 여유보다 작아야 해요**). 작업 메모리(`work_mem`)와 병렬 수는 사용자가 `set_config`나 문장으로 바꿀 수 있는 값이라 그 길 셋(문장, 함수, 함수 안의 동적 문장)을 모두 막아요 |
| **동시 실행** | 풀을 나눠요: 내장 읽기와 저장한 질의 8, 사람의 임의 질의 4(기본값). 계정마다의 동시 수도 정해요. 꽉 차면 "바쁨"과 다시 시도할 때의 힌트를 줘요(서버가 스스로 다시 시도해 장애를 가리지 않아요) |
| **결과** | 행 수와 바이트의 상한(MCP 200행과 약 8천 토큰, REST 1만 행). 한 행이 지나치게 큰 것(`repeat('x', 100MB)`는 통과했어요)도 바이트로 끊고, 닿으면 연결을 닫아요. 잘리면 표시해요 |
| **실행 뒤** | 임의 SQL을 돌린 연결은 초기화하지 않고 **닫아요**(연결을 여는 값이 싸고 카탈로그 캐시 문제도 함께 사라져요. `DISCARD ALL`은 설정과 세션 잠금과 준비한 문장과 `LISTEN`을 지우지만 큰 객체와 캐시 56MB는 남겨요). 저장한 질의와 내장 읽기의 풀은 초기화하고 연결에 수명을 둬요. 취소되거나 오류가 난 연결은 버려요 |
| **끄기** | 저장한 질의는 id로, 임의 질의는 문장의 해시로 끄는 운영 액션이에요. 끈 질의는 실행기가 거절해요(조인이 많은 질의의 격리와 같은 쓰임이에요) |
| **감사** | 누가, 어느 KG에, 어느 질의를, 몇 행, 얼마나 걸렸는지. 에이전트가 KG 전체를 걸어 읽는 것의 상한은 감사의 행 수로 세어요 |

- **오류**는 SQLSTATE와 고정된 글로 답해요. PostgreSQL의 원래 오류 글에는 데이터의 값이 실리므로(형 변환 실패, 제약 위반) 값으로 취급해 길이를 제한하고 문자를 정리해 따로 싣고, 제품의 말과 구조에서 갈라요([MCP](kg-mcp.md) 4.3절).
- **서버 쪽 시한의 값**: 내장 읽기와 저장한 질의는 REST 30초, MCP 10초. 사람의 임의 질의는 10초에서 시작해 최대 30초예요. 트랜잭션 시한은 60초예요.
- **복제본**: 사용자 질의의 풀은 읽기 복제본을 가리킬 수 있어요. 질의 스키마 전체가 쓰기, 임시 테이블, 시퀀스 없이 돌아야 해요. 직렬화 가능 격리는 쓰지 않아요. 복제본의 충돌 취소(`canceling statement due to conflict with recovery`)는 한 번만 다시 시도해요([PostgreSQL의 HA](postgres-ha.md)).

### 2.2 실행 권한을 회수하는 목록

`PUBLIC`에서 실행 권한을 회수하고 질의 역할에 주지 않는 함수예요. 제품 스키마에는 기본 권한으로 `PUBLIC` 실행이 붙지 않게 해요.

- 설정: `set_config`.
- 다른 세션: `pg_terminate_backend`, `pg_cancel_backend`, `pg_stat_activity`의 읽기 권한(같은 역할의 세션은 질의의 글도 서로 보여서, 다른 사용자가 쓴 조건의 값이 새요).
- 잠금과 알림: 어드바이저리 잠금 함수 전부, `pg_notify`, `pg_logical_emit_message`(WAL에 써요).
- 시간과 번호: `pg_sleep` 계열, `pg_current_xact_id`와 `txid_current` 계열(번호를 소모해요), `pg_export_snapshot`.
- 파일과 큰 객체: 큰 객체 함수 전부(`lo_*`), `pg_read_file`, `pg_ls_dir`, 설정 다시 읽기(`pg_reload_conf`), `pg_log_backend_memory_contexts`.
- 언어: `plpgsql`의 사용 권한(`DO`).
- **이 회수는 방어의 필수 부분이에요.** 스키마 관리기의 설치 역할이 회수하고(역할 만들기와 카탈로그 함수의 권한 바꾸기가 필요해요. 필요한 권한은 배포 안내서에 적어요), 점검 명령이 회수되어 있는지 확인해요.
- 내장 함수는 수천 개라서 허용 목록으로 갈 수 없어요. 대신 **전용 데이터베이스를 전제로** 하고, 시작할 때 설치된 확장을 점검하고(`dblink` 같은 것이 있으면 막아요), **주 버전이 오를 때 새로 생긴 함수 가운데 부작용이 있는 것을 보는 점검**을 업그레이드 절차에 넣어요.

## 3. 그래프 함수

**그래프 함수는 둘**이에요. 뜻 없는 일반 연산이고, 무엇이 의존이고 무엇이 이중화인지 제품은 전제하지 않아요.

```sql
reachable(start, edges, direction, max_depth, max_nodes)
    -> (id, depth)
shortest_path(from_id, to_id, edges, direction, max_depth, max_nodes)
    -> (step, id, via)
```

| 인자 | 뜻 |
|---|---|
| `start`, `from_id`, `to_id` | 객체 번호(`id`). 시작점이 여럿일 때의 모양은 구현할 때 정해요 |
| `edges` | **링크 타입 이름의 목록**(`ARRAY['runs_on','mounted_in']`)이나 **뷰 이름**(간선 정의가 만든 뷰). 문장 글자를 받지 않아요. 이름을 관계로 풀어 받으므로 글자가 문장에 끼지 않아요 |
| `direction` | `out`, `in`, `both` |
| `max_depth` | **물음의 일부**예요. 거기서 멈추고 정상 결과를 줘요(이웃 펼치기에 써요) |
| `max_nodes` | **예산**이에요. 넘으면 **오류**예요. 조용히 자르지 않아요 |

- `reachable`은 닿은 노드와 깊이(`id`, `depth`)만 돌려줘요. 앞 노드와 지나온 링크는 내지 않고, 길이 필요하면 `shortest_path`가 줘요. 이웃 펼치기(깊이 1~3)는 이 열로 돼요.
- **기본값과 한도**: 깊이 12, 방문 20만. 사용자가 올려도 **넘을 수 없는 한도**는 방문 100만이에요. 예산 오류는 고정된 코드로 답하고 방문 수와 닿은 깊이를 싣고, 글에 값을 싣지 않아요.
- **구현의 조건**(원형에서 나온 것):
  1. **간선 전체를 읽어 두지 않아요.** 한 번 읽어 재귀 질의 하나로 도는 꼴은 닿는 것이 30개인 흔한 질의에서도 링크 전체를 읽고, 예산이 메모리를 막지 못했어요(예산 1만에도 255MB. 한 단계의 후보를 다 만든 뒤에 잘랐어요. 노드당 약 0.55KB). **단계 안에서 먼저 자르고 링크의 인덱스로 넓혀요.** 방문 집합의 크기를 단계 도중에 검사해요.
  2. **최단 경로는 양쪽에서 함께 넓혀요.** 한쪽만 넓히면 116만 노드 그래프에서 3.8~6.6초였어요. 양방향이 방문 수를 크게 줄일 것으로 추측하고, 구현해서 재요.
  3. **호출자의 권한으로 돌아요**(`SECURITY INVOKER`). 저장 스키마의 모델 테이블이 아니라 질의 스키마의 뷰를 읽어요(원형에서 저장 스키마를 읽으면 질의 역할로는 안 돌았어요).
  4. **쓰기, 임시 테이블, 시퀀스 없이 순수 SQL로**(재귀 CTE, 방문 집합은 CTE 안에서) 돌려서 복제본에서 돌아요.
  5. **질의 역할로 테스트해요.** 슈퍼유저로만 테스트하면 권한 결함이 안 드러나요.
- **원형의 값**(117만 객체): 작은 도달(닿는 것 약 30개) 1.4ms. 사이트 아래 전체(27.2만 노드, 방향 `in`) 1.3초. 양방향 전체는 예산 100만에서 4.9초에 오류로 끝나고 연결 메모리가 651MB였어요. 예산 10만은 0.44초, 예산 1만은 0.12초에 오류로 끝나요(예산에 비례하고 규모와 무관해요). 3천만에서 예산 없이 양방향으로 전체를 훑으면 약 210초와 메모리 수십 GB로 한도를 넘는다고 추정해서 **예산은 필수**예요.
- **메모리의 식**: 풀 크기 × 시간 한도 × 초당 증가량 ≤ 질의에 내줄 메모리여야 해요. 사용자가 쓴 터지는 재귀 SQL은 세션당 초당 약 20MB로 자라요(원형). 풀 8과 시한 30초에서 최고 1.86GB, 풀 4와 시한 10초에서 0.64GB였어요. 그래서 임의 질의의 시한은 10초에서 시작해요.
- 재귀 SQL을 직접 쓰는 것은 막지 않아요. 올바른 꼴과 터지는 꼴은 [질의 스키마](query-schema.md) 10절에 있고, 터지는 꼴은 위의 한도가 끊어요.

## 4. 내장 읽기

서버 코드가 SQL을 만들어 질의 실행기에 맡겨요. 타입과 속성의 이름은 모델 설명 테이블로 검증한 뒤 식별자로 인용하고, 값은 바인딩으로만 보내요. MCP 툴과 REST 경로가 같은 읽기를 불러요(ADR-0016, ADR-0062의 "같은 유스케이스 위의 두 어댑터"). 인자의 이름은 지금의 MCP와 REST의 이름을 그대로 쓰고, 아래는 뼈대예요. 새 REST 경로의 이름은 [REST API](rest-api.md)에 구현할 때 정한다(찾기, 객체 읽기, 이웃의 지금 경로는 유지해요).

| 읽기 | 인자(뼈대) | 응답의 `data`(뼈대) |
|---|---|---|
| **찾기**(`find`) | `object_type`, `include_subtypes`, `trait`, `attributes`(`name`, `op`, `values`), `identifier`(`scheme`, `value`), `text`, `limit`, `cursor` | 항목(`id`, `ref`, `type`, `name`, 상태, `min_grade`)의 목록, `next_cursor` |
| **객체 읽기**(`get`) | `object_id`나 `ref`나 `identifier`, `include`(`attributes`, `identifiers`, `link_counts`, `provenance`) | 속성마다 값과 근거 등급과 근거 종류와 시각(행에서 그대로), 링크 개수 |
| **이웃**(`neighbors`) | `object_id`, `link_types`, `direction`, `max_steps`(기본 1, 상한 3), `peer_types`, `limit`, `cursor` | 링크 타입별 그룹과 항목, 그룹 개수 |
| **도달 집합**(`reachable`) | `object_id`, `link_types`나 간선 정의 이름, `direction`, `max_depth`, `max_nodes` | `id`, `ref`, `type`, `name`, `depth`, 잘렸는지 |
| **스키마 설명**(`schema`) | `name`(낱말로 찾기), 타입 하나 보기 | 호출자의 민감 등급으로 거른 타입, 속성, 링크 타입, 잇는 규칙, 조인의 본보기 |

- **MCP 툴**: `kg_schema`, `kg_find`, `kg_get`, `kg_neighbors`, `kg_reachable`, `kg_whoami`가 기본으로 있어요(지금의 `kg_catalog`는 `kg_schema`로 대체돼요). 저장한 질의마다 툴이 더해져요. 임의 SQL 툴은 없어요([저장한 질의와 간선 정의](saved-queries.md) 4절).
- **화면**: 객체 목록, 객체 상세, 이웃은 남고 내부가 내장 읽기가 돼요.
- 기본 응답은 지금처럼 간략(`brief`)과 상세(`full`)를 가르고, 값은 구조의 값 자리에만 실어요([MCP](kg-mcp.md) 4.3절).

## 5. 응답의 세대와 변경 번호, 한도의 기본값

- **응답에는 그 질의가 본 KG의 세대와 변경 번호, 잘렸는지를 실어요.** 같은 트랜잭션의 첫 문장으로 머리 행을 읽기 때문에 질의가 본 순간과 일치해요. 변경 번호는 머리 행의 값이라 복제본에서도 읽혀요.
- 요청이 **"이 번호 이후"**(`min_seq`)를 요구하면 복제본의 머리 행이 그 번호에 닿을 때까지 `wait_timeout` 안에서 기다려요. 못 닿으면 주 서버로 보내거나 거절해요(REQ-222). 장애 조치로 커밋을 잃었을 수 있으므로 `min_seq`가 새 주의 현재 번호보다 크면 "미래 번호" 오류로 알려요. 세대가 다르면 `conflict.generation_changed`예요.

| 한도 | 기본값 | 비고 |
|---|---|---|
| 시한(내장 읽기, 저장한 질의) | REST 30초, MCP 10초 | 서버 취소와 DB 시한을 함께 걸어요 |
| 시한(사람의 임의 질의) | 10초에서 시작, 최대 30초 | |
| 트랜잭션 시한, 유휴 트랜잭션 시한 | 60초, 모든 역할에 걸어요 | 청소를 막는 긴 트랜잭션을 만들지 않아요 |
| 임시 파일 | 2GB(역할) | `풀 × 한도 < 디스크 여유` |
| 풀 | 내장 읽기와 저장한 질의 8, 사람의 임의 질의 4 | CPU 2개 기계의 원형에서. 더 늘려도 처리량이 안 늘 것으로 추측해요 |
| 결과 | MCP 200행과 약 8천 토큰, REST 1만 행 | 한 행의 바이트도 상한이 있어요 |
| 그래프 함수 | 깊이 12, 방문 20만. 넘을 수 없는 한도는 방문 100만 | 예산을 넘으면 오류 |
| 조인 순서 탐색 | PostgreSQL의 기본값 | 올리면 계획 시간이 87~125ms |

값은 원형에서 정한 시작값이고, 구현 뒤 실제 부하에서 다시 재요.

질의 화면은 사람의 임의 질의의 실행 계획(읽기 전용)을 보여 줘요([저장한 질의](saved-queries.md) 8절).

## 6. 적대적 테스트

적대적 테스트 묶음을 잠가요(원형은 74건이에요). 질의 역할의 연결에서 실행기를 흉내 내(확장 프로토콜, 감싸기, 읽기 전용·반복 읽기, `SET LOCAL ROLE`, 시한 10초, 실행 뒤 초기화) 돌렸고, **데이터 접근과 설정 변경의 시도는 모두 막혔어요**(한 건은 결함 둘을 고친 뒤의 결과예요). 목록:

- **문장**: 문장 이어 붙이기, 감싼 틀을 닫고 둘째 문장, 감싼 틀을 닫고 `UNION`으로 `LIMIT` 우회(통과하지만 행이 여전히 한도 안), `SET`, `SHOW`, `COPY TO STDOUT`, `LISTEN`, `EXPLAIN ANALYZE`, `BEGIN`/`COMMIT`, `DISCARD ALL`, `DECLARE … WITH HOLD`, `PREPARE`, `DO`, `INSERT`, 데이터를 바꾸는 CTE, `SELECT INTO`, `SELECT … FOR UPDATE`, `CREATE TEMP TABLE AS`.
- **함수**: `set_config`로 작업 메모리, 읽기 전용 기본값, 검색 경로, 역할 리버트. `pg_sleep`, `pg_sleep_for`, 어드바이저리 잠금(세션, 트랜잭션, try), `pg_notify`, `pg_logical_emit_message`, `pg_current_xact_id`, `txid_current`, `pg_export_snapshot`, 큰 객체(`lo_creat`, `lo_import`, `lo_export`), `pg_read_file`, `pg_ls_dir`, `pg_reload_conf`, `pg_log_backend_memory_contexts`.
- **격리**: 다른 KG의 질의 스키마, 저장 스키마의 테이블, 높은 등급의 뷰와 열, 검색 경로를 높은 스키마로 바꾸기(`SET LOCAL`), `SET ROLE`과 `RESET ROLE`, 상세 함수를 등급 인자로 직접 부르기, 그래프 함수에 다른 KG의 뷰 이름과 저장 테이블 이름, 타입 목록과 방향 인자에 문장 끼우기.
- **세션**: `pg_stat_activity` 읽기, 같은 역할의 다른 세션에 `pg_terminate_backend`와 `pg_cancel_backend`, 읽기 전용을 푼 뒤 다음 트랜잭션의 큰 객체.
- **카탈로그**: 높은 등급 뷰의 정의, `pg_attribute`의 높은 등급 열, 다른 KG의 테이블 크기와 행 수 추정(거절), 그리고 보이는 것을 기록하는 항목들(`pg_class`의 테이블 개수, `pg_proc`의 함수 본문, `pg_roles`, `pg_settings`, 열 설명, `version()`).
- **확장**: `dblink`.
- **자원**: 시한을 넘는 계산(2초 시한에서 취소됨), 임시 파일 폭주(윈도 함수의 전체 정렬이 2GB 한도에서 10.3초에 오류), 100MB의 큰 행 하나(통과하므로 바이트 상한이 막아야 해요).
- **감싸기가 정당한 질의를 깨지 않는가**: 끝의 세미콜론(깨지므로 실행기가 떼요), 줄 끝 주석, 블록 주석, `WITH`로 시작, 자체 `ORDER BY`와 `LIMIT`, 재귀 CTE, `VALUES`, `TABLE`, `UNION` 뒤 `ORDER BY`, 열 이름이 겹치는 `SELECT`, 따옴표와 달러 따옴표 안의 세미콜론, 파라미터 `$1`을 쓰는 질의(제한 인자의 번호는 사용자 인자 뒤에 이어 붙여요).
- **새로 더하는 것**: 복제본에서 질의 스키마 전체를 실행하는 테스트, 큰 적용 중용 스키마를 고르는 테스트, 민감 등급이 가리는 것(뷰, `provenance`, `attribute`, 과거 시점, 변경 기록) 테스트, 질의 역할로 그래프 함수를 도는 테스트.

남은 것은 카탈로그로 보이는 것(역할 이름, 함수 본문, 다른 KG의 테이블 개수)이에요([질의 스키마](query-schema.md) 8절).

## 7. 약속이 바뀌는 것(REQ-250~256)

| 지금의 약속 | 새 설계 |
|---|---|
| 응답마다 가려진 것의 수(`hidden`) | **주지 않아요.** 낮은 등급에서는 가려진 컬럼이 없고, 행 단위의 범위 제한이 없어 가릴 객체도 없어요 |
| 페이지 도중에 KG가 바뀌어도 처음 읽은 변경 번호에서 이어지는 커서 | **주지 않아요.** 커서는 "지금 모습"의 키(객체 번호) 뒤부터예요. 시점 고정은 과거 읽기가 느린 길이라서 포기해요 |
| 속성마다 값, 근거 등급, 근거 종류, 관측 시각 | 행에서 그대로 줘요(타입 뷰의 컬럼과 `provenance`) |
| 응답 전체의 신선도와 근거 등급 자동 계산, `view`, `max_staleness` | 이 설계가 정하지 않았어요. 내장 읽기가 이것을 받을지는 REQ-250~256을 고치는 구현에서 정한다 |
| 응답에 세대와 변경 번호, "이 번호 이후"를 기다리기 | 지켜요 |

사용자의 SQL에서는 응답 전체의 신선도와 가려진 것의 수가 없어요(값마다의 근거 등급과 시각은 컬럼으로 보여요). 고치는 요구는 REQ-250부터 REQ-256까지 가운데 약속이 바뀌는 것이고, 지우지 않고 "예정에서 바뀐다"로 표시해요(구현하는 변경이 고쳐요).

## 8. 알려진 한계와 가정

- 방어의 효과는 원형(PostgreSQL 19.0, 합성 데이터)의 74건이에요. 실제 복제본과 수천 개의 내장 함수 전체는 점검하지 못했어요.
- 드라이버(`lib/pq`)의 취소와 큰 행의 동작은 소스로만 확인했고 실험하지 않았어요.
- 풀의 크기와 시한은 CPU 2개, 메모리 8GB의 기계에서 정한 시작값이에요.

## 9. 미결 사항

- 내장 읽기가 `view`, `max_staleness`, 응답 전체의 신선도를 받을지.
- 그래프 함수의 시작점이 여럿일 때의 모양, 경로 함수(`paths`)를 둘지.
- 새 REST 경로의 이름, 큰 적용 중용 스키마의 이름.
- 행 단위의 범위 제한의 방법.
- 에이전트의 질의 한도(주체별 읽은 객체 수)의 값.
