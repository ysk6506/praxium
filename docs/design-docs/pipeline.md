# 파이프라인 설계

[ADR-0008](adr/0008-ingestion.md)의 결정을 풀어 쓴 문서 두 개 중 뒤 문서예요. 원본 레코드의 변경이 정제, 피드, 식별과 병합, 링크와 그룹을 거쳐 KG의 변경 배치가 되는 경로를 다뤄요. 소스와 수집과 원본 레코드와 안전장치는 [수집 설계](ingestion.md)에 있어요. 테이블 필드는 **스케치**이고 이름은 영어 snake_case예요. 예시는 모두 지어낸 것이고 숫자는 "가정"이거나 "측정해서 정한다"예요.

## 1. 목적과 다루는 질문
- 배치와 스트리밍을 한 정의로 처리하면서 스트리밍에서 사용할 수 없는 연산이 없게 하려면요?
- 한 객체 타입에 배치로 들어오는 속성과 실시간으로 들어오는 속성이 섞이면 어떻게 구축하고, 사용자는 어떻게 관리하나요?
- 같은 대상(ECMP 등)을 설정에서도 테이블에서도 문서에서도 수집하려면요?
- 수집한 행이 어디로 갔는지 어떻게 세어 대조하나요?
- 문서에서 행을 읽는 단계, 매핑을 만드는 사람을 돕는 경로, 지정 재수집과 푸시 수집은 이 경로의 어디에 연결되나요?

정의의 버전·브랜치·제안·병합·리버트는 ADR-0014의 절차를 거쳐요. 관측은 ADR-0013, 권한은 ADR-0012([권한 설계](access-control.md)), 저장은 ADR-0009([저장 설계](kg-storage.md)), 모델은 ADR-0007([모델 설계](kg-model.md))이 정해요.

## 2. 변경을 입력받아 변경을 산출하는 실행기
### 2.1 변경의 형태
변경 레코드 하나는 `(row_key, weight, row, ingest_seq, source_time)`이에요. 추가는 +1, 삭제는 −1이고, 수정은 "−이전 값 +새 값" 한 쌍이에요. 모든 연산이 +와 −를 같은 경로로 처리해서 삭제와 수정이 값으로 전달돼요. 배치의 크기는 [기본값 표](defaults.md)가 1만 행 또는 2초 가운데 먼저 도달하는 쪽으로 정해요(너무 작으면 트랜잭션 비용이 지배해요. 클로즈드 베타에서 측정해서 조정해요).

### 2.2 연산을 3가지로 분류
연산 등록부의 필수 필드 `class`예요. 증분 갱신으로 다시 계산해요.

| 분류 | 필요한 것 | 연산 |
|---|---|---|
| 가. 레코드 하나만 봐요 | 상태 없음. 변경이 그대로 전달돼요 | 행 펼치기, 컬럼 나누기, 필터링, 빈 값 채우기, 값 변환, 컬럼 선택과 이름 변경, 자료형 변환, 정규식 추출, 연결(concat), 유니언 |
| 나. 키별 상태 | 키마다 스토리지에 상태를 둬요 | 조인, 컬럼으로 모으기(피벗), 중복 제거, 조회 테이블로 값 치환 |
| 다. 전체를 봐야 해요 | — | 14개 연산 가운데는 없어요 |

- **조인**: 양쪽 인덱스를 보유하고 Δa⋈b + a⋈Δb + Δa⋈Δb로 갱신해요. 삭제(−)도 같은 식을 거쳐서 한쪽 행이 삭제되면 연결된 결과 행에 −가 전달돼요.
- **컬럼으로 모으기**: 키마다 행의 그룹을 보유해요. 만들 컬럼의 목록은 정의에 적어요(값에서 컬럼이 자동으로 생기지 않아요). 목록에 없는 값이 들어오면 수집한 스키마가 바뀐 것으로 다뤄요([수집 설계](ingestion.md) 9절).
- **중복 제거**: 키마다 후보를 **모두** 보유해요. 남은 행이 삭제되면 다음 후보가 올라와요(`−r2 +r1`). "가장 최근 값 하나만" 두면 삭제에서 틀려요.
- **조회 테이블로 값 치환**: 조회 테이블이 조인의 한쪽 인덱스예요. 조회 테이블이 바뀌면 그 키의 행을 다시 산출해요.
- **유니언**: 입력의 변경을 그대로 합쳐요. 입력 스키마가 일치하는지만 검사해요.
- **다**: 14개 연산 가운데 전체를 봐야 하는 것은 없어요(그렇게 선정한 고정 목록이에요). 새 연산이 전체를 봐야 하면 스트리밍에서 실행할 수 있는 방법(키를 정해 키마다 다시 계산하거나 큰 배치에서만 실행하는 방법)과 함께 결정 기록으로만 추가해요. 스트리밍이라서 사용할 수 없는 연산이 없게 하려는 거예요.
- "값 변환"의 함수는 제품에 내장된 순수 함수 목록에서 선택해요. 입력 순서에 의존하지 않고 시계와 난수를 사용하지 않아요.

피드, 식별과 병합, 링크 정의의 조건도 같은 구조예요. 링크 조건은 정규화한 키의 인덱스 위에서 증분 갱신으로만 평가해요.

### 2.3 키 상태 포트
메서드: `load(op_id, keys)`(상태 읽기), `store(op_id, changes)`(적용 트랜잭션 안에서 수정), `scan(op_id, key_range)`(범위 스캔), `fork(base)`(드라이 런용 복제본. 운영 상태에서 출발해 운영에 영향이 없고 폐기돼요). 복제본의 위치는 **주 스토리지가 아니에요.** 드라이 런의 스테이징 영역과 결과는 진실이 아니므로 복제와 백업이 없는 별도의 임시 스토리지에 두거나 영향 범위 전용 오버레이로 실행해요(통째로 복사한 후보 KG를 기본으로 삼지 않아요. 클로즈드 베타에서 설계하고 오픈 베타에서 구현해요). 정의가 바뀐 연산의 키 상태는 드라이 런이 수집해 둔 원본 레코드로 새로 구축하고, 적용할 때 그것으로 교체해요(바뀌지 않은 연산의 상태는 그대로 사용해요). 어느 쪽이든 같은 실행기가 실행돼요([저장 설계](kg-storage.md) 12절).

기본 어댑터는 PostgreSQL이고 메모리에 write-through 캐시를 둬요. 캐시에 내용 해시를 두면 내용이 같은 변경(노옵)을 스토리지에 접근하기 전에 걸러내요. 키 1천만 개를 한 프로세스에 두는 것은 작은 프로토타입에서 감당됐지만(정지 시간이 밀리초 미만) 스토리지 입출력이 빠진 측정이에요.

### 2.4 늦게 도착했거나 순서가 바뀐 이벤트
- **수집 순서**의 기준은 `ingest_seq`예요. 소스의 시각이나 버전으로 수집 순서를 정하지 않아요.
- 중복은 이렇게 걸러서 세어요: 수집 엔벨로프는 `capture_id`와 `seq`, 푸시 수집은 보낸 쪽의 이벤트 ID, 둘 다 내용 해시. 이벤트 ID와 `capture_id`의 기억은 **중복 제거 기간**(기본 7일, 소스별 설정) 안에서만 유효해요. 그 이후의 재전송은 키와 해시로 차단해요.
- `source_time`은 수집 순서가 아니라 **값의 우선순위를 판정할 때만** 사용해요. 같은 피드가 같은 속성에 대해 보유한 값의 시각보다 이른 값은 덮어쓰지 못하고 `late_events`로 세어요(3.3). 푸시 수집의 "순서는 `source_time`으로 판정한다"도 이 지연 도착 값 처리 규칙 하나예요.
- 시간 윈도우가 없으니 워터마크도 없어요. 시간이 필요한 작업은 `tick` 단위로 측정해요([수집 설계](ingestion.md) 7.2).

**"한 번에 입력한 결과 = 나눠서 스트리밍한 결과"의 테스트.** 속성 테스트로 적용해요: (1) 같은 원본 변경을 한 배치로 입력한 결과와 임의로 나눠서 스트리밍한 결과가 같은 KG 내용을 산출해요. (2) 중복을 섞어도 같아요. (3) 원본 레코드에서 처음부터 다시 실행해도 내용(타입, 속성, 링크의 스키마)이 같아요. ID까지 같다고는 약속하지 않아요(ADR-0007). (4) 전부 수집을 지난번과의 차이로 바꾼 것과 같은 변경을 이어서 수집한 결과가 같아요. 입력은 [수집 설계](ingestion.md) 11절의 생성기가 만들어요.

### 2.5 파싱의 위치
원본 레코드 앞에 파싱 단계가 있어요([수집 설계](ingestion.md) 3.4). 파서가 문서를 트리로, 행 선택이 테이블로 바꾸고, 그 행이 원본 레코드의 변경이 되면 이후는 일반 테이블과 같아요. 파서는 제품에 내장된 고정 목록이고 사용자 코드는 없어요(자세한 내용은 [수집 확장](ingestion-extensions.md) 5절). 파싱 결과도 결정적이에요: 같은 문서와 같은 라인 템플릿이면 같은 행이 나와요. 라인 템플릿은 데이터라서 정의의 변경(ADR-0014)을 거쳐요.

| 유입 경로 | 이 파이프라인과 만나는 곳 | 달라지는 것 |
|---|---|---|
| 가져오기(전부, 증분 수집, 재개) | 원본 레코드의 변경 | 기본이에요 |
| 푸시 수집 | 같아요(`stream`의 한 형태) | `ingester` 계정이 보내고, 이벤트 ID로 중복을 차단해요 |
| 지정 재수집 | 같아요. 그 객체의 행만 | 작업으로 실행되고 삭제를 만들지 않아요. 소스 보호의 한도 안에서 실행돼요 |
| 사람이 업로드한 파일(엑셀) | 같아요 | 파일 하나가 전부 수집 하나예요 |

**지정 재수집이 일정 실행을 기아 상태로 만들지 않아요.** 주체마다 한도가 있고 일정 실행보다 앞선 순서를 가지지만, 소스의 속도 상한 안에서 일정 실행에 할당량을 남겨요(할당량과 한도의 값은 기본값 표에 가정으로 둬요). 다시 수집한 행은 일반 변경이라 키 상태와 안전장치를 그대로 거쳐요.

## 3. 피드
### 3.1 필드
피드(`feed`)는 데이터셋 하나에서 객체 타입 하나로 가는 매핑 하나예요. 피드는 자기가 매핑한 속성만 **소유해요.**

| 필드 | 설명 |
|---|---|
| `dataset_id`, `object_type` | 어느 데이터셋에서 어느 타입으로 |
| `attributes` | 속성 매핑: `attribute`, `column`, `rank`(우선순위, 낮을수록 먼저), `history_kind`(기본은 `change_class`에서) |
| `identity` | 식별 키 매핑: `key_name`, `columns`, `priority`. 소속 객체는 부모의 문맥을 함께 적어요 |
| `creates_objects`, `retires_objects` | 객체를 생성할 수 있나, 폐기할 수 있나 |
| `basis` | 근거의 종류: `configured` / `observed` / `declared` / `derived` |
| `approximate` | 근사값 표시. `declared`의 기본 등급은 `fact`이고 근사값이면 `assumed`예요 |
| `completeness_declaration` | 완전성 선언: 이 피드가 타입이나 링크 타입을 전부 제공하는가(범위를 지정할 수 있고, 선택 필드 `expected_count`가 있어요). 소스가 아니라 **피드의 필드**예요 |
| `wait_deadline` | 속성만 붙이는 피드의 대기 기한(`tick` 단위) |
| `expectations`, `contacts` | 기대 조건, 담당자 |

### 3.2 속성 단위의 적용
- 객체의 값은 피드마다 제공한 값을 따로 보유하다가 **속성마다** 우선하는 값을 선택해요. 배치 피드의 전부 수집이 스트림 피드가 소유한 속성을 삭제하거나 덮어쓰지 않아요.
- 우선하는 값: `rank`가 낮은 것. 같은 순위 안에서는 이벤트 시각(`source_time`)이 늦은 것. 그것도 같으면 `ingest_seq`가 늦은 것.
- 우선하지 못한 값은 버리지 않고 문제 목록에 소스 간 충돌로 보여요.
- 피드가 더는 값을 제공하지 않으면(컬럼이 비었거나 레코드가 삭제됨) 그 피드가 소유한 속성만 비워져요. 다른 피드가 있으면 그 값이 우선하고, 없으면 값은 `unknown`이에요. 모르는 것을 가정으로 채우지 않아요. 기본값 규칙이 만든 값만 `assumed`예요.
- 저장은 구분해요. `versioned` 속성은 객체의 행과 이력에, `volatile`은 현재 값만 두는 별도 영역에 둬요(ADR-0009). 스트림이 초 단위로 상태를 바꿔도 객체의 행과 이력은 늘지 않고 배치의 적용과 서로 대기하지 않아요.
- **`volatile`의 변경도 전달돼요.** `volatile` 속성이 바뀌면 이력 없는 **경량 변경 레코드**(객체, 속성, 새 값의 표지, `change_seq`)를 만들어요. 프로젝션, 충족 표시, 변경 알림, SSE가 적용된 변경의 기록과 함께 이 레코드를 따라가요. 경량 레코드는 짧게 보관하고 `hist`와 버전의 해시에는 포함되지 않아요. 그래서 "그 버전 시점"의 응답에는 `volatile` 값을 주지 않아요(엔벨로프의 `volatile_as_of`).
- **쓰기 감소.** 한 배치 안의 같은 키는 마지막 값만 기록해요. 값이 같으면 경량 레코드도 없고, `seen_at`은 낡음을 판단하는 간격의 절반이 지났을 때만 새로 기록해요(그만큼 신선도의 정밀도를 포기해요).
- **링크는 `volatile`이 될 수 없어요.** 속성만 `volatile`이에요. 영향 범위가 읽는 링크는 일반 변경이에요(3.4).

### 3.3 객체를 생성하는 피드와 속성만 붙이는 피드
- 객체는 `creates_objects`인 피드의 행에서 식별 키가 모두 채워졌을 때 생성돼요. 내부 ID는 처음 관측한 식별 키에서 결정적으로 산출돼요(ADR-0007). 보통 구성 소스의 배치 피드가 생성하고 폐기도 해요. 상태를 제공하는 스트림 피드는 둘 다 할 수 없어요.
- 속성만 붙이는 피드는 자기 식별 키로 기존 객체를 찾아요(식별 규칙은 결정적이에요). 있으면 붙어요. 둘 이상이 일치하면 붙이지 않고 식별 후보로 문제 목록에 올려요.
- 없으면 객체를 만들어 내지 않고 **기한이 있는 대기**에 둬요. 기한 안에 객체가 생성되면 붙고, 아니면 문제 목록에 "붙을 곳이 없는 값"으로 올라가요. 대기 건수는 피드의 헬스 상태에 보여요.
- 객체는 폐기할 수 있는 피드(`retires_objects`) 가운데 그 객체를 **관측하고 있는** 피드가 하나라도 남아 있는 동안 유지돼요. 한 피드의 삭제([수집 설계](ingestion.md) 4.3)는 그 피드의 "관측 중" 표시만 해제해요(관측하지 못한 횟수는 (피드, 객체)마다 `unseen_object`에서만 세요. 폐기 임계값은 횟수와 최소 기간을 함께 보고 피드마다 조정할 수 있어요). 관측 중인 피드가 하나도 없으면 폐기되고, 이력에 남아요. **복원에는 조건이 있어요.** 폐기된 객체가 같은 식별 키로 다시 관측될 때 이전 ID로 복원되는 것은 (가) 강한 키로 일치했거나 (나) 정해진 기간 안일 때뿐이에요(기간은 기본값 표에 가정으로 둬요). 이름, 주소, 포트 이름 같은 약한 키는 다른 장비에 재사용되므로 기간이 지난 뒤에는 이전 ID와 이력을 승계하지 않아요. 아니면 새 ID를 부여하고 식별 후보로 문제 목록에 올려요.

**이벤트 시각 기준의 지연 도착 값 처리**(2.4의 규칙 하나). 피드가 속성마다 마지막으로 제공한 값의 `source_time`을 보유해요. 그보다 이른 값이 늦게 도착하면 덮어쓰지 않고 `late_events`로 세요. 소스가 시각을 주지 않으면(`event_time`이 없으면) 수집 순서(`ingest_seq`)로만 판정해요.

### 3.4 예: `VirtualMachine`에 피드 3개가 붙을 때
지어낸 예예요. 타입 `VirtualMachine`의 속성 가운데 구성은 하루에 한 번 전부 수집하고, 상태는 이어서 수집하고, 담당 서비스는 엑셀로 수집해요.

| 피드 | 데이터셋 · 수집 방식 | 생성 / 폐기 | 소유하는 속성 (`rank`) | `basis` |
|---|---|---|---|---|
| `vm_config_daily` | `vm_inventory` · `snapshot`, 하루 한 번 새벽 | 예 / 예 | `name`, `cpu_count`, `memory_mb`, `guest_os` (1) | `observed` |
| `vm_runtime` | `vm_runtime_events` · `stream` + 정합성 대조(6시간마다, 가정) | 아니요 / 아니요 | `power_state`, `host_name` (1) | `observed` |
| `vm_service_sheet` | `vm_service_sheet` · 파일, `manual_only`(기대 주기 한 달, 가정) | 아니요 / 아니요 | `owner_service` (1), `memory_mb` (2, 근사값) | `declared` |

식별은 `vm_config_daily`가 `instance_id`(`priority` 1)와 `name`(2)을 가져요. 시트는 `name`만 가져서 2순위 키로 붙어요.

| 속성 | `change_class` → 이력 | 소유한 피드 | 비고 |
|---|---|---|---|
| `name`, `cpu_count`, `guest_os` | `slow` → `versioned` | `vm_config_daily` | 바뀔 때마다 이력에 남아요 |
| `memory_mb` | `slow` → `versioned` | `vm_config_daily`(1), 시트(2) | 두 값이 다르면 1이 우선하고 시트 값은 불일치로 보여요. 시트 값은 근사값이라 `assumed` |
| `power_state`, `host_name` | `dynamic` → `volatile` | `vm_runtime` | 현재 값과 관측 시각만 둬요 |
| `owner_service` | `slow` → `versioned` | `vm_service_sheet` | 사람이 적은 것(`declared`) |

링크 `RUNS_ON`(`VirtualMachine` → `HypervisorHost`)은 링크 정의가 `host_name`과 호스트의 이름이 같다는 조건(정규화한 키가 같다)으로 만들어요. 링크는 `volatile`이 될 수 없어요. VM이 호스트를 자주 옮겨도 `RUNS_ON`은 일반 변경이고 이력과 영향 범위에 그대로 반영돼요(그 쓰기의 양은 측정해서 확인해요). 호스트 구성(배치)이나 `host_name`(스트림) 어느 쪽이 바뀌어도 실행기가 증분 갱신으로 다시 평가해서 사용자가 따로 할 일은 없어요.

1. **새벽의 전부 수집(정상)**: VM `vm-a`, `vm-b`, `vm-c`가 생성돼요. `power_state`는 아직 소유한 피드의 값이 없어 `unknown`이에요.
2. **이어서 수집**: `vm-a`의 `power_state=off`가 들어와서 `volatile` 영역만 바뀌어요(객체의 행과 이력은 그대로). 아직 없는 `vm-z`의 상태는 객체를 만들어 내지 않고 기한이 있는 대기에 둬요.
3. **늦은 이벤트**: `vm-a`에 `source_time`이 더 이른 `power_state=on`이 늦게 도착하면 덮어쓰지 못하고 `late_events`가 하나 늘어요.
4. **다음 날의 전부 수집**: `vm-b`의 `guest_os` 컬럼이 비면 `vm_config_daily`가 소유한 그 속성만 비워져요. `power_state`와 `owner_service`는 그대로예요. `vm-c`가 관측되지 않으면 미관측 횟수(`unseen_object`)가 1이 될 뿐 폐기되지 않아요.
5. **엑셀 업로드**: `vm-a`에 `owner_service`가 붙어요. 시트에만 있는 `vm-q`의 행은 대기에 두고, 기한 안에 `vm_config_daily`가 `vm-q`를 생성하지 않으면 "붙을 곳이 없는 값"이에요.

## 4. 타입별 피드 현황
객체 타입마다 테이블 하나가 위 예시처럼 모든 것을 보여 줘요. **API가 제공하는 리소스**이고(화면은 다른 리포지토리가 그것을 읽어 렌더링해요) CLI로도 볼 수 있어요. 피드를 추가하고 순서를 바꾸는 것은 정의의 변경이에요(ADR-0014의 절차).

필드: `attribute`, `feeds`(어느 피드: 소스 · 데이터셋 · 컬럼), `receive_mode`와 `schedule`, `rank`, `history_kind`, `staleness`와 `expected_staleness`(속성별. 응답에는 요청한 속성마다 관측 시각이 붙어요), `fill_rate`(`required`가 분모), `conflicts`(불일치).

피드별 헬스 상태도 같은 위치에서 보여요: 마지막 수집, 지연, 보류(`held`), 붙을 곳 없는 값의 건수. 질의에 `max_staleness`를 지정하면 그보다 오래된 속성이 응답에서 표시돼요(ADR-0010).

**매핑을 만드는 사람을 돕는 경로.** 매핑은 스키마만 보고 하지 않아요. API가 이런 것을 제공해요(화면의 형태는 클로즈드 베타의 일이고, 자세한 내용은 [수집 확장](ingestion-extensions.md) 4절).

| 경로 | 제공하는 것 | 규칙 |
|---|---|---|
| 데이터셋 조회 | 컬럼의 이름과 값 타입, 샘플 행, 컬럼별 통계(빈 값의 비율, 서로 다른 값의 수, 빈출 값, 값의 형태) | 샘플과 통계는 민감 등급과 읽기 권한을 따르고, 그 데이터셋이 채우는 타입의 읽기 권한을 함께 요구하며 감사에 남아요. `open`이 아닌 컬럼의 빈출 값은 제공하지 않아요 |
| 매핑 제안(`suggest`) | 컬럼과 속성의 조합과 이유, 식별 컬럼의 후보 | 정해진 규칙으로만 만들어요(같은 입력이면 같은 응답). 자동으로 적용하지 않고 사람이 수락한 것만 브랜치에 기록돼요 |
| 타입 기준 조회 | 속성마다 어느 피드가 채우나, 비었나, 채움률, 배치인가 실시간인가. 비어 있는 속성에서 시작해 채울 수 있는 데이터셋의 후보 | 위의 피드 현황이에요 |
| 미리 보기 | 샘플 행 몇 개가 어떤 객체와 링크가 되는지(기존 객체에 붙나, 새로 만드나, 타입이 맞지 않아 탈락하는 값) | 저장하기 전에 해요. 전체의 차이는 브랜치의 드라이 런이 보여요 |

프리셋이 있는 소스는 기본 피드가 들어 있어 매핑 없이 시작해요.

**맞지 않는 매핑을 알려요(차단하지는 않아요. 선택은 사용자의 몫이에요).** 표준 모델이 속성마다 `change_class`(`static` / `slow` / `dynamic`)를 적어 두고, 그것이 이력의 종류와 기대 신선도의 기본값을 정해요(`static`·`slow`는 `versioned`, `dynamic`은 `volatile`. 숫자는 가정).

| 매핑 | 알림 |
|---|---|
| `dynamic` 속성을 하루에 한 번 수집하는 배치에 매핑 | "최대 하루 오래된 값이 돼요" |
| 식별 키를 속성만 붙이는 스트림에만 매핑 | "객체가 생성되지 않아요" |
| `static` 속성이 자주 바뀜 | "식별이 불안정해져요" |

## 5. 식별과 병합, 링크 정의, 그룹 생성
### 5.1 식별과 병합
순서만 적어요. 규칙은 ADR-0007이 정해요. (1) 피드가 제공한 행의 식별 키를 값 타입의 정규화로 정리해요. (2) 우선순위대로 기존 식별자와 일치시켜요(결정적 규칙만. 확률은 후보를 제안할 뿐 자동으로 합치지 않아요). (3) 있으면 붙고, 없으면 `creates_objects`일 때만 생성해요. (4) 속성마다 우선하는 값을 선택해요(3.2). 병합과 분리는 이력에 남아요. 식별의 이력은 파생물이 아니라 진실의 일부이고 잃으면 안 돼요. **객체가 병합될 때 흡수된 쪽의 링크는 ID를 연결해요.** 이전 링크 ID와 새 링크 ID의 연결을 `identity_event`에 남기고, 변경 알림과 충족률은 그것을 "폐기와 추가"가 아니라 연결로 다뤄서 병합 하나가 알림을 요동치게 하지 않아요. 병합을 리버트하는 것도 같은 연결을 따라가요.

### 5.2 링크 정의
링크 타입마다 조건을 적어요. 사람이 선을 긋지 않아요. 승인 단위는 출발 타입 하나예요(ADR-0012). 한 정의(링크 정의와 정제 데이터셋)가 다른 소스의 데이터셋을 읽을 수 있는데, 읽는 소스는 **작성자의 범위 안**이어야 하고 승인은 읽는 소스의 범위도 확인해요. 읽는 소스의 담당자에게는 알림이 가요([권한 설계](access-control.md) 9-3). 작성자가 범위 밖의 소스를 읽는 정의는 `:preview`로 결과를 보는 것도 차단돼요.

링크 정의(`link_def`)의 필드: `link_type`과 `binding`(개수는 바인딩에 붙어요), `from`과 `to`(양 끝 타입과 사용하는 속성), `condition`(아래 6가지 중 하나와 인자), `creates`(`link` 또는 `group`), `reads`(읽는 데이터셋 목록), `basis`(`derived`)와 `history_kind`.

| 조건 | 의미 | 예 |
|---|---|---|
| `same_key` | 정규화한 키가 같다 | VM의 `host_name` = 호스트의 이름 |
| `in_list` | 목록에 들어 있다 | 점검 대상 목록의 장비 |
| `in_range` | 범위에 속한다 | 주소가 대역에 속한다 |
| `slot_matches` | 슬롯 위치가 일치한다 | 랙과 슬롯이 일치한다 |
| `same_parent` | 부모가 같다 | 같은 섀시의 부품들 |
| `follow_link` | 다른 링크를 따라간 끝이 같다 | 위치를 따라 냉방을 상속받는다 |

### 5.3 그룹 생성과 도출 링크
도출한 링크와 그룹은 질의할 때 계산하지 않고 **수집할 때 만들어 저장해요.**
1. 구성원 후보를 `group_by` 키로 그룹으로 묶어요. 그룹 객체의 내부 ID는 그룹 키에서 결정적으로 산출돼요.
2. 구성원은 `member_of`로 연결하고 가중치와 역할을 링크의 속성 값으로 가질 수 있어요.
3. 임계값(`min_alive`)의 근거: 소스가 말하면 `fact`, 종류 기본값(기본값 규칙)이면 `assumed`, 기본값이 없으면 `unknown`이에요.
4. `basis`는 `derived`이고 입력의 종류를 함께 적어요. 등급은 사용된 입력 중 가장 낮은 등급이에요. 구성에서 도출한 그룹은 설정을 온전히 읽었으면 `fact`예요.
5. 한쪽 설정만 있거나 일치하지 않으면 그룹을 만들지 않고 문제 목록에 올려요([모델 설계](kg-model.md)의 ECMP 예).

### 5.4 예: 같은 ECMP 그룹을 3개 경로로 수집
지어낸 스위치 `leaf-1`이에요. 모두 `EcmpGroup`을 가리키고, 경로마다 같은 그룹 키 필드(장비, 라우팅 문맥)에 매핑해서 같은 그룹이 돼요.

| 경로 | 데이터셋 | 수집하는 타입 · 속성 | `basis` |
|---|---|---|---|
| 설정 | 장비 설정(`snapshot`) | `RoutingProcess`의 `maximum_paths`, `RoutingSession`의 `multipath_eligible` → 링크 정의가 그룹과 구성원을 도출해요 | `configured`(그룹은 `derived`) |
| 운영 상태 테이블 | 라우팅 테이블, 이웃 테이블(`stream`이나 `snapshot`) | `RoutingSession`의 `session_state`, `EcmpGroup`의 구성원 | `observed` |
| 문서 | 설계 엑셀 | `EcmpGroup`과 구성원 | `declared` |

경로가 여럿이면 종류별로 모두 수집해 둬요. 설정이 4개를 쓰게 돼 있는데 라우팅 테이블에 2개만 보이면 버릴 충돌이 아니라 **의도와 관측의 불일치**예요. 문제 목록에 올라가고, 질의는 `as_designed`나 `as_observed`를 선택해요(ADR-0010). KG는 구조와 상태를 수집하고, 수치 시계열(온도, 전력, 사용률)은 저장하지 않고 참조만 둬요. LACP, BGP 세션, 전원 A·B, 클러스터 구성도 같은 방식이에요.

## 6. 기대 조건
데이터셋과 피드에 붙이는 선언형 검사예요(`expectation`: `target`, `kind`, `params`, `severity`, `contacts`). 정의라서 버전이 있어요.

종류는 8가지 고정 목록이에요: `not_empty`(비어 있지 않다), `unique`(중복이 없다), `in_values`(값 목록 안이다), `in_range`(범위 안이다), `matches_value_type`(값 타입에 맞다), `references`(다른 데이터셋에 있다), `row_count_range`(행 수의 범위), `shape`(컬럼과 자료형).

| | 배치 | 스트림 |
|---|---|---|
| 적용 단위 | 수집 한 번의 배치 | 레코드마다. 배치 단위로만 적용할 수 있는 `row_count_range`는 정합성 대조의 전부 수집에 적용해요 |
| `warn` | 문제 목록에 올려요 | 위반한 레코드를 격리하고 문제 목록에 올려요 |
| `fail` | 그 피드의 적용을 멈춰요 | 위반한 레코드를 격리하고 그 피드의 적용을 보류해요(`held`) |

파서가 읽지 못한 행의 비율에도 기대 조건을 적용할 수 있어요([수집 설계](ingestion.md) 3.4).

**격리한 레코드**는 이유와 함께 보관돼요. 원본 레코드에는 남아 있고 건수 대조에서 "문제"로 분류돼요. 샘플은 민감 등급과 읽기 권한에 따라 보여요. 정의의 새 버전이 병합되면 보류된 위치부터 다시 실행해요.

## 7. 건수 대조
"한 번"은 배치에서는 수집 한 번, 스트림에서는 확정한 KG 버전 사이의 구간이에요. 파싱을 거치는 소스는 그 단계에서 먼저 세어요: 수집한 것 = 읽은 행 + **읽지 못함**(파서가 읽지 못한 행, 라인 템플릿에 맞지 않은 행. 버리지 않고 세요. 샘플을 볼 수 있어요). 읽은 행이 원본 레코드가 되고, 그 원본 레코드 하나는 마지막에 4가지 중 하나로 분류돼요(여러 분류에 해당하면 앞선 것이 우선해요: 사용됨 > 문제 > 규칙이 걸러냄 > 사용되지 않음. 행 하나라도 객체나 링크에 기여하면 사용됨이에요. "사용됐지만 문제도 있는 레코드"의 수는 합에 넣지 않고 별도로 함께 산출해요): **사용됨**(객체나 링크 하나 이상에 기여) / **규칙이 걸러냄**(어느 규칙인지) / **문제**(어느 문제인지) / **사용되지 않음**. 4가지의 합은 읽은 행의 수와 같고(파싱이 없는 소스는 수집한 수와 같아요), 단계마다 입력 건수는 출력 건수와 탈락 건수(이유와 함께)의 합이에요. 한 행이 객체도 링크도 되어도 한 번만 세요. 객체나 링크는 원본 레코드의 참조와 규칙의 버전을 가져서, 값 하나의 근거는 같은 규칙을 다시 실행해 보여요(같은 입력이면 같은 결과). 값마다 출처를 저장하지는 않아요.

가상의 예: 엑셀 120행을 수집했어요. 정제(필터링: 계획 중인 장비 제외)에서 120 = 116 + 4(규칙이 걸러냄). 피드에서 116 = 108 + 8(식별 키가 빈 6행은 문제, 매핑되지 않은 2행은 사용되지 않음). 마지막 분류는 사용됨 108 + 걸러냄 4 + 문제 6 + 사용되지 않음 2 = 120이에요. 일치하지 않으면 그 동기화는 대조 실패로 문제 목록에 올라요(ADR-0013이 관측해요).

## 8. 알려진 한계
- 읽지 못함을 4가지 분류에 다섯 번째로 넣을지, 원본 레코드가 되기 전의 탈락으로 따로 셀지는 정해지지 않았어요. 위 7절은 후자로 적었고, 설계 담당의 답을 기다려요.
- 14개 연산의 수는 추정이에요. 샘플 테스트와 알파에서 조정해요. 값마다의 출처는 저장하지 않고 같은 규칙을 다시 실행해 보여요.
- 스트림에서 `row_count_range`는 정합성 대조의 전부 수집에 적용해요.
