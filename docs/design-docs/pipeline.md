# 파이프라인 설계

[ADR-0008](adr/0008-ingestion.md)의 결정을 풀어 쓴 문서 둘 중 뒤 문서예요. 원본 기록의 변경이 정제, 공급, 식별과 병합, 링크와 묶음을 거쳐 KG의 변경 묶음이 되는 길을 다뤄요. 소스와 수집과 원본 기록과 안전장치는 [받기 설계](ingestion.md)에 있어요. 표의 칸은 **스케치**이고 이름은 영어 snake_case예요. 예시는 모두 지어낸 것이고 숫자는 "가정"이거나 "재서 정한다"예요.

## 1. 무엇에 답하나
- 배치와 스트리밍을 한 정의로 받으면서 흐름에서 못 쓰는 연산이 없게 하려면요?
- 한 객체 타입에 배치로 오는 속성과 실시간으로 오는 속성이 섞이면 어떻게 짓고, 사용자는 어떻게 관리하나요?
- 같은 것(ECMP 등)을 설정에서도 표에서도 문서에서도 받으려면요?
- 받은 행이 어디로 갔는지 어떻게 세어 맞추나요?

정의의 버전·브랜치·제안·병합·되돌리기는 ADR-0014의 길을 타요. 관측은 ADR-0013, 권한은 ADR-0012([권한 설계](access-control.md)), 저장은 ADR-0009([저장 설계](kg-storage.md)), 모델은 ADR-0007([모델 설계](kg-model.md))이 정해요.

## 2. 변경을 받아 변경을 내는 실행기
### 2.1 변경의 모양
변경 한 줄은 `(row_key, weight, row, ingest_seq, source_time)`이에요. 더함은 +1, 지움은 −1이고, 고침은 "−옛 +새" 한 쌍이에요. 모든 연산이 +와 −를 같은 길로 받아서 지움과 고침이 값으로 흘러요. 묶음의 크기와 간격은 너무 작으면 트랜잭션 비용이 지배하므로 적응형으로 두고 재서 정해요.

### 2.2 연산을 셋으로 가름
연산 등록부의 필수 칸 `class`예요. 늘어난 만큼만 다시 계산해요.

| 부류 | 필요한 것 | 연산 |
|---|---|---|
| 가. 기록 하나만 봐요 | 상태 없음. 변경이 그대로 흘러요 | 행으로 펼치기, 컬럼 나누기, 고르기, 빈 값 채우기, 값 바꾸기, 컬럼 고르기와 이름 바꾸기, 자료형으로 읽기, 정규식으로 뽑기, 이어 붙이기, 유니언 |
| 나. 열쇠마다의 상태 | 열쇠마다 저장소에 상태를 둬요 | 조인, 컬럼으로 모으기(피벗), 겹친 행 없애기, 표에서 찾아 바꾸기 |
| 다. 전체를 봐야 해요 | — | 열넷 가운데는 없어요 |

- **조인**: 양쪽 색인을 쥐고 Δa⋈b + a⋈Δb + Δa⋈Δb로 갱신해요. 지움(−)도 같은 식을 타서 한쪽 행이 지워지면 이어진 결과 행에 −가 나가요.
- **컬럼으로 모으기**: 열쇠마다 행의 묶음을 쥐어요. 만들 컬럼의 목록은 정의에 적어요(값에서 컬럼이 저절로 생기지 않아요). 목록에 없는 값이 오면 받은 모양이 바뀐 것으로 다뤄요([받기 설계](ingestion.md) 9절).
- **겹친 행 없애기**: 열쇠마다 후보를 **모두** 쥐어요. 남은 행이 지워지면 다음 후보가 올라와요(`−r2 +r1`). "가장 최근 값 하나만" 두면 지움에서 틀려요.
- **표에서 찾아 바꾸기**: 조회표가 조인의 한쪽 색인이에요. 조회표가 바뀌면 그 열쇠의 행을 다시 내요.
- **유니언**: 입력의 변경을 그대로 합쳐요. 입력 모양이 맞는지만 검사해요.
- **다**: 열네 연산 가운데 전체를 봐야 하는 것은 없어요(그렇게 고른 닫힌 목록이에요). 새 연산이 전체를 봐야 하면 흐름에서 도는 길(열쇠를 정해 열쇠마다 다시 계산하거나 큰 묶음에서만 돌리는 길)과 함께 결정 기록으로만 더해요. 흐름이라서 못 쓰는 연산이 없게 하려는 거예요.
- "값 바꾸기"의 함수는 제품에 든 순수 함수의 목록에서 골라요. 입력 순서에 기대지 않고 시계와 난수를 쓰지 않아요.

공급, 식별과 병합, 링크 정의의 조건도 같은 틀이에요. 링크 조건은 다듬은 열쇠의 색인 위에서 늘어난 만큼만 따져요.

### 2.3 열쇠 상태의 자리(포트)
메서드: `load(op_id, keys)`(상태 읽기), `store(op_id, changes)`(적용 트랜잭션 안에서 고치기), `scan(op_id, key_range)`(범위 훑기), `fork(base)`(후보 실행용 사본. 운영 상태에서 출발해 운영에 영향이 없고 버려져요). 정의가 바뀐 연산의 열쇠 상태는 후보 실행이 받아 둔 원본 기록으로 새로 짓고, 적용 때 그것으로 갈아 끼워요(바뀌지 않은 연산의 상태는 그대로 써요). 후보 실행은 차이만 내는 것과 통째로 만든 후보 KG 둘이 있고 어느 쪽이든 같은 실행기가 돌아요([저장 설계](kg-storage.md) 12절).

기본 어댑터는 PostgreSQL이고 메모리에 쓰기 통과 캐시를 둬요. 캐시에 내용 해시를 두면 같은 사건(노옵)을 저장소에 닿기 전에 걸러요. 천만 개의 열쇠를 한 프로세스에 두는 것은 작은 시제품에서 감당됐지만(정지가 밀리초 아래) 저장소 입출력이 빠진 측정이에요.

### 2.4 늦게 오거나 순서가 바뀐 사건
- 순서의 기준은 `ingest_seq`예요. 소스의 시각이나 버전으로 정하지 않아요.
- 같은 `capture_id`, `seq`, 해시의 중복은 무시하고 세어요.
- `source_time`은 값을 가릴 때만 써요. 같은 공급이 같은 속성에 쥔 값의 때보다 이른 값은 덮지 못하고 `late_events`로 세어요(3.3).
- 시간 창이 없으니 워터마크도 없어요. 시간이 드는 일은 `tick`으로 세요([받기 설계](ingestion.md) 7.2).

**"한 번에 넣은 결과 = 나눠 흘린 결과"의 시험.** 속성 시험으로 건다: (1) 같은 원본 변경을 한 묶음으로 넣은 결과와 임의로 나눠 흘린 결과가 같은 KG 내용을 내요. (2) 중복을 섞어도 같아요. (3) 원본 기록에서 처음부터 다시 돌려도 내용(타입, 속성, 링크의 모양)이 같아요. ID까지 같다고는 약속하지 않아요(ADR-0007). (4) 전부 받기를 지난번과의 차이로 바꾼 것과 같은 변경을 이어서 받은 결과가 같아요. 입력은 [받기 설계](ingestion.md) 11절의 생성기가 내요.

## 3. 공급
### 3.1 칸
공급(`feed`)은 데이터셋 하나에서 객체 타입 하나로 가는 매핑 하나예요. 공급은 자기가 매핑한 속성만 **쥐어요.**

| 칸 | 뜻 |
|---|---|
| `dataset_id`, `object_type` | 어느 데이터셋에서 어느 타입으로 |
| `attributes` | 속성의 매핑: `attribute`, `column`, `rank`(이기는 순서, 낮을수록 먼저), `history_kind`(기본은 `change_class`에서) |
| `identity` | 식별 키의 매핑: `key_name`, `columns`, `priority`. 딸린 객체는 부모의 문맥을 함께 적어요 |
| `creates_objects`, `retires_objects` | 객체를 만들 수 있나, 물러나게 할 수 있나 |
| `basis` | 근거의 종류: `configured` / `observed` / `declared` / `derived` |
| `approximate` | 어림 표시. `declared`의 기본 등급은 `fact`이고 어림이면 `assumed`예요 |
| `completeness_declaration` | 완전성 선언: 이 공급이 타입이나 링크 타입을 전부 주는가(범위를 붙일 수 있고, 선택 칸 `expected_count`가 있어요). 소스가 아니라 **공급의 칸**이에요 |
| `wait_deadline` | 살만 붙이는 공급의 대기 기한(`tick`으로 세요) |
| `expectations`, `contacts` | 기대 조건, 담당자 |

### 3.2 속성 단위의 적용
- 객체의 값은 공급마다 낸 값을 따로 쥐고 있다가 **속성마다** 이기는 값을 골라요. 배치 공급의 전부 받기가 흐름 공급이 쥔 속성을 지우거나 덮지 않아요.
- 이기는 값: `rank`가 낮은 것. 같은 순위 안에서는 사건의 때(`source_time`)가 늦은 것. 그것도 같으면 `ingest_seq`가 늦은 것.
- 진 값은 버리지 않고 문제 목록에 소스 사이의 충돌로 보여요.
- 공급이 더는 값을 주지 않으면(컬럼이 비었거나 기록이 지워짐) 그 공급이 쥔 속성만 비워져요. 다른 공급이 있으면 그 값이 이기고, 없으면 값은 `unknown`이에요. 모르는 것을 가정으로 메우지 않아요. 기본값 규칙이 만든 값만 `assumed`예요.
- 저장은 갈라요. `versioned` 속성은 객체의 행과 이력에, `volatile`은 지금 값만 두는 따로 된 자리에 둬요(ADR-0009). 흐름이 초마다 상태를 바꿔도 객체의 행과 이력은 늘지 않고 배치의 적용과 서로 기다리지 않아요.

### 3.3 객체를 있게 하는 공급과 살만 붙이는 공급
- 객체는 `creates_objects`인 공급의 행에서 식별 키가 모두 채워졌을 때 생겨요. 내부 ID는 처음 본 식별 키에서 결정적으로 나와요(ADR-0007). 보통 구성 소스의 배치 공급이 만들고 물러나게도 해요. 상태를 주는 흐름 공급은 둘 다 못 해요.
- 살만 붙이는 공급은 자기 식별 키로 있는 객체를 찾아요(식별 규칙은 결정적이에요). 있으면 붙어요. 둘 이상이 맞으면 붙이지 않고 식별 후보로 문제 목록에 올려요.
- 없으면 객체를 지어내지 않고 **기한이 있는 대기**에 둬요. 기한 안에 객체가 생기면 붙고, 아니면 문제 목록에 "붙을 곳이 없는 값"으로 올라가요. 대기의 수는 공급의 건강에 보여요.
- 객체는 물러나게 할 수 있는 공급(`retires_objects`) 가운데 그 객체를 **보고 있는** 공급이 하나라도 남아 있는 동안 살아요. 한 공급의 지움([받기 설계](ingestion.md) 4.3)은 그 공급의 "보고 있음"만 거둬요(안 보인 번수는 (공급, 객체)마다 `unseen_object`에서만 세요. 물러나는 문턱은 번수와 최소 기간을 함께 보고 공급마다 고칠 수 있어요). 보고 있는 공급이 하나도 없으면 물러나고, 이력에 남아요. 같은 식별 키로 다시 보이면 옛 ID로 되살아나요.

**사건의 때로 늦은 값 막기.** 공급이 속성마다 마지막으로 낸 값의 `source_time`을 쥐어요. 그보다 이른 값이 늦게 오면 덮지 않고 `late_events`로 세요. 소스가 때를 안 주면(`event_time`이 없으면) 받은 순서(`ingest_seq`)로만 가려요.

### 3.4 예: `VirtualMachine`에 세 공급이 붙을 때
지어낸 예예요. 타입 `VirtualMachine`의 속성 가운데 구성은 하루에 한 번 전부 받고, 상태는 이어서 받고, 담당 서비스는 엑셀로 받아요.

| 공급 | 데이터셋 · 받는 방식 | 만듦 / 물러남 | 쥐는 속성 (`rank`) | `basis` |
|---|---|---|---|---|
| `vm_config_daily` | `vm_inventory` · `snapshot`, 하루 한 번 새벽 | 예 / 예 | `name`, `cpu_count`, `memory_mb`, `guest_os` (1) | `observed` |
| `vm_runtime` | `vm_runtime_events` · `stream` + 맞추기(6시간마다, 가정) | 아니요 / 아니요 | `power_state`, `host_name` (1) | `observed` |
| `vm_service_sheet` | `vm_service_sheet` · 파일, `manual_only`(기대 주기 한 달, 가정) | 아니요 / 아니요 | `owner_service` (1), `memory_mb` (2, 어림) | `declared` |

식별은 `vm_config_daily`가 `instance_id`(`priority` 1)와 `name`(2)을 가져요. 시트는 `name`만 가져서 2순위 키로 붙어요.

| 속성 | `change_class` → 이력 | 쥔 공급 | 비고 |
|---|---|---|---|
| `name`, `cpu_count`, `guest_os` | `slow` → `versioned` | `vm_config_daily` | 바뀔 때마다 이력에 남아요 |
| `memory_mb` | `slow` → `versioned` | `vm_config_daily`(1), 시트(2) | 두 값이 다르면 1이 이기고 시트 값은 어긋남으로 보여요. 시트 값은 어림이라 `assumed` |
| `power_state`, `host_name` | `dynamic` → `volatile` | `vm_runtime` | 지금 값과 본 때만 둬요 |
| `owner_service` | `slow` → `versioned` | `vm_service_sheet` | 사람이 적은 것(`declared`) |

링크 `RUNS_ON`(`VirtualMachine` → `HypervisorHost`)은 링크 정의가 `host_name`과 호스트의 이름이 같다는 조건(다듬은 키가 같다)으로 만들어요. 링크는 기본 `versioned`이고 옮겨 다님이 잦으면 `volatile`로 내릴 수 있어요. 호스트 구성(배치)이나 `host_name`(흐름) 어느 쪽이 바뀌어도 실행기가 늘어난 만큼만 다시 따져서 사용자가 따로 할 일은 없어요.

1. **새벽의 전부 받기(온전)**: VM `vm-a`, `vm-b`, `vm-c`가 생겨요. `power_state`는 아직 쥔 공급의 값이 없어 `unknown`이에요.
2. **이어서 받기**: `vm-a`의 `power_state=off`가 와서 `volatile` 자리만 바뀌어요(객체의 행과 이력은 그대로). 아직 없는 `vm-z`의 상태는 객체를 지어내지 않고 기한이 있는 대기에 둬요.
3. **늦은 사건**: `vm-a`에 `source_time`이 더 이른 `power_state=on`이 늦게 오면 덮지 못하고 `late_events`가 하나 늘어요.
4. **다음 날의 전부 받기**: `vm-b`의 `guest_os` 컬럼이 비면 `vm_config_daily`가 쥔 그 속성만 비워져요. `power_state`와 `owner_service`는 그대로예요. `vm-c`가 안 보이면 안 보인 번수(`unseen_object`)가 1이 될 뿐 물러나지 않아요.
5. **엑셀 올리기**: `vm-a`에 `owner_service`가 붙어요. 시트에만 있는 `vm-q`의 행은 대기에 두고, 기한 안에 `vm_config_daily`가 `vm-q`를 만들지 않으면 "붙을 곳이 없는 값"이에요.

## 4. 타입의 공급 표
객체 타입마다 표 하나가 위 예시처럼 모든 것을 보여 줘요. **API가 주는 자원**이고(화면은 다른 저장소가 그것을 읽어 그려요) 명령줄 클라이언트로도 볼 수 있어요. 공급을 더하고 순서를 바꾸는 것은 정의의 변경이에요(ADR-0014의 길).

칸: `attribute`, `feeds`(어느 공급: 소스 · 데이터셋 · 컬럼), `receive_mode`와 `schedule`, `rank`, `history_kind`, `staleness`와 `expected_staleness`(속성마다. 답에는 요청한 속성마다 본 때가 붙어요), `fill_rate`(`required`가 분모), `conflicts`(어긋남).

공급마다의 건강도 같은 자리에서 보여요: 마지막 수집, 밀림, 붙잡힘(`held`), 붙을 곳 없는 값의 수. 물음에 `max_staleness`를 주면 그보다 묵은 속성이 답에서 표시돼요(ADR-0010).

**맞지 않는 매핑을 알려요(막지는 않아요. 고르는 것은 사용자예요).** 표준 모델이 속성마다 `change_class`(`static` / `slow` / `dynamic`)를 적어 두고, 그것이 이력의 종류와 기대 신선도의 기본값을 정해요(`static`·`slow`는 `versioned`, `dynamic`은 `volatile`. 숫자는 가정).

| 매핑 | 알림 |
|---|---|
| `dynamic` 속성을 하루에 한 번 받는 배치에 매핑 | "최대 하루 묵은 값이 돼요" |
| 식별 키를 살만 붙이는 흐름에만 매핑 | "객체가 만들어지지 않아요" |
| `static` 속성이 자주 바뀜 | "식별이 흔들려요" |

## 5. 식별과 병합, 링크 정의, 묶음
### 5.1 식별과 병합
순서만 적어요. 규칙은 ADR-0007이 정해요. (1) 공급이 낸 행의 식별 키를 값 타입의 다듬기로 다듬어요. (2) 우선순위대로 기존 식별자와 맞춰요(결정적 규칙만. 확률은 후보를 제안할 뿐 저절로 합치지 않아요). (3) 있으면 붙고, 없으면 `creates_objects`일 때만 만들어요. (4) 속성마다 이기는 값을 골라요(3.2). 합침과 가름은 이력에 남아요. 식별의 이력은 파생물이 아니라 진실의 일부이고 잃으면 안 돼요.

### 5.2 링크 정의
링크 타입마다 조건을 적어요. 사람이 선을 긋지 않아요. 한 정의가 여러 소스의 데이터셋을 읽으면 그 소스들을 범위에 가진 `approver`의 승인이 필요해요.

링크 정의(`link_def`)의 칸: `link_type`과 `binding`(개수는 바인딩에 붙어요), `from`과 `to`(양 끝 타입과 쓰는 속성), `condition`(아래 여섯 중 하나와 인자), `creates`(`link` 또는 `group`), `reads`(읽는 데이터셋들), `basis`(`derived`)와 `history_kind`.

| 조건 | 뜻 | 예 |
|---|---|---|
| `same_key` | 다듬은 키가 같다 | VM의 `host_name` = 호스트의 이름 |
| `in_list` | 목록에 들어 있다 | 점검 대상 목록의 장비 |
| `in_range` | 범위에 든다 | 주소가 대역에 든다 |
| `slot_matches` | 자리가 맞는다 | 랙과 칸이 맞는다 |
| `same_parent` | 부모가 같다 | 같은 섀시의 부품들 |
| `follow_link` | 다른 링크를 따라간 끝이 같다 | 자리를 따라 냉방을 물려받는다 |

### 5.3 묶음 만들기와 끌어낸 링크
끌어낸 링크와 묶음은 질의할 때 계산하지 않고 **받을 때 만들어 저장해요.**
1. 구성원 후보를 `group_by` 키로 묶어요. 묶음 객체의 내부 ID는 묶음 키에서 결정적으로 나와요.
2. 구성원은 `member_of`로 들고 무게와 역할을 매개 값으로 가질 수 있어요.
3. 문턱(`min_alive`)의 근거: 소스가 말하면 `fact`, 종류 기본값(기본값 규칙)이면 `assumed`, 기본값이 없으면 `unknown`이에요.
4. `basis`는 `derived`이고 입력의 종류를 함께 적어요. 등급은 쓰인 입력 중 가장 낮은 등급이에요. 구성에서 끌어낸 묶음은 설정을 온전히 읽었으면 `fact`예요.
5. 한쪽 설정만 있거나 맞지 않으면 묶음을 만들지 않고 문제 목록에 올려요([모델 설계](kg-model.md)의 ECMP 예).

### 5.4 예: 같은 ECMP 묶음을 세 길로 받기
지어낸 스위치 `leaf-1`이에요. 모두 `EcmpGroup`을 가리키고, 길마다 같은 묶음 키 칸(장비, 라우팅 문맥)에 매핑해서 같은 묶음이 돼요.

| 길 | 데이터셋 | 받는 타입 · 속성 | `basis` |
|---|---|---|---|
| 설정 | 장비 설정(`snapshot`) | `RoutingProcess`의 `maximum_paths`, `RoutingSession`의 `multipath_eligible` → 링크 정의가 묶음과 구성원을 끌어내요 | `configured`(묶음은 `derived`) |
| 표 | 경로표, 이웃 표(`stream`이나 `snapshot`) | `RoutingSession`의 `session_state`, `EcmpGroup`의 구성원 | `observed` |
| 문서 | 설계 엑셀 | `EcmpGroup`과 구성원 | `declared` |

길이 여럿이면 종류별로 다 받아 둬요. 설정이 4개를 쓰게 돼 있는데 경로표에 둘만 보이면 버릴 충돌이 아니라 **의도와 관측의 어긋남**이에요. 문제 목록에 올라가고, 질의는 `as_designed`나 `as_observed`를 골라요(ADR-0010). KG는 구조와 상태를 받고, 수치의 시계열(온도, 전력, 사용률)은 쌓지 않고 가리키기만 해요. LACP, BGP 세션, 전원 A·B, 클러스터 구성도 같은 방식이에요.

## 6. 기대 조건
데이터셋과 공급에 붙이는 선언하는 검사예요(`expectation`: `target`, `kind`, `params`, `severity`, `contacts`). 정의라서 버전이 있어요.

종류는 닫힌 여덟이에요: `not_empty`(비어 있지 않다), `unique`(겹치지 않는다), `in_values`(값의 목록 안이다), `in_range`(범위 안이다), `matches_value_type`(값 타입에 맞다), `references`(다른 데이터셋에 있다), `row_count_range`(행 수의 범위), `shape`(컬럼과 자료형).

| | 배치 | 흐름 |
|---|---|---|
| 거는 곳 | 수집 한 번의 묶음 | 기록마다. 묶음에 걸 수밖에 없는 `row_count_range`는 맞추기의 전부 받기에 걸어요 |
| `warn` | 문제 목록에 올려요 | 어긴 기록을 떼어 두고 문제 목록에 올려요 |
| `fail` | 그 공급의 적용을 멈춰요 | 어긴 기록을 떼어 두고 그 공급의 적용을 붙잡아요(`held`) |

**떼어 둔 기록**은 까닭과 함께 보관돼요. 원본 기록에는 남아 있고 수 맞춤에서 "문제"로 분류돼요. 견본은 민감 등급과 읽기 권한을 따라 보여요. 정의의 새 판이 병합되면 붙잡힌 자리부터 다시 돌려요.

## 7. 수 맞춤
"한 번"은 배치에서는 수집 한 번, 흐름에서는 봉한 KG 버전 사이의 구간이에요. 원본 기록 하나는 끝에 넷 중 하나로 분류돼요(갈리면 앞선 것이 이겨요: 쓰임 > 문제 > 규칙이 걸러 냄 > 안 쓰임. 행 하나라도 객체나 링크에 기여하면 쓰임이에요. "쓰였지만 문제도 있는 기록"의 수는 합에 넣지 않고 따로 함께 내요): **쓰임**(객체나 링크 하나 이상에 기여) / **규칙이 걸러 냄**(어느 규칙인지) / **문제**(어느 문제인지) / **안 쓰임**. 넷의 합은 받은 수와 같고, 단계마다 들어온 수는 나간 수와 떨어진 수(이유와 함께)의 합이에요. 한 행이 객체도 링크도 되어도 한 번만 세요. 객체나 링크는 원본 기록의 참조와 규칙의 버전을 가져서, 값 하나의 근거는 같은 규칙을 다시 돌려 보여요(같은 입력이면 같은 결과). 값마다 출처를 저장하지는 않아요.

지어낸 예: 엑셀 120행을 받았어요. 정제(고르기: 계획 중인 장비 제외)에서 120 = 116 + 4(규칙이 걸러 냄). 공급에서 116 = 108 + 8(식별 키가 빈 6행은 문제, 매핑 안 된 2행은 안 쓰임). 끝의 분류는 쓰임 108 + 걸러 냄 4 + 문제 6 + 안 쓰임 2 = 120이에요. 맞지 않으면 그 동기화는 맞춤 실패로 문제 목록에 올라요(ADR-0013이 관측해요).

## 8. 알고 가는 한계
- 열네 연산의 수는 추정이에요. 견본 시험과 알파에서 고쳐요. 값마다의 출처는 저장하지 않고 같은 규칙을 다시 돌려 보여요.
- 흐름에서 `row_count_range`는 맞추기의 전부 받기에 걸어요.
