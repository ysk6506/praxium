# 게이트웨이의 액션 타입 표

표준 모델의 액션 타입 112개를 읽고, 게이트웨이가 처음 열 때(1차) 어느 것을 대상으로 삼을 수 있는지 가렸어요. 구조와 책임은 [게이트웨이 설계](gateway.md), 안전과 여는 조건은 [게이트웨이의 안전](gateway-safety.md)에 있어요(ADR-0061). 이 표는 표준 모델 파일을 고치지 않고, 파일의 `reversibility`, `disruption`, `physical`, `mutates`와 효과 문장(`declared_effects`)을 읽고, 효과가 가리키는 속성이 대상 타입에 있는지를 모델과 대조해서 만들었어요.

**한계.** 이 표는 사람이 효과의 글을 읽고 판단한 거예요. 같은 형태의 액션에 근거 낱말이 고르게 적용되지 않은 곳이 있어요(예: `enable_interface`와 `exit_ups_bypass`는 "안정된 뒤", 비슷한 속성 설정인 `cordon_node`는 "곧바로"). 표준 모델의 `disruption` 표시도 믿기 어려운 곳이 있어요(`open_breaker`, `scale_workload`, `migrate_virtual_machine`, `run_ups_self_test`가 지장 없음이에요). 그래서 이 표는 열어도 된다는 증명이 아니라, 검토할 순서를 정하는 자료예요.

## 1. 판단 규칙

1차(승인 전용)에서는 사람이 호출마다 승인하므로, 지장이 있을 수 있어도 승인 화면에 드러나면 들 수 있어요. 들 수 있는 액션의 조건은 넷이에요.

1. 되돌릴 수 있어요(`reversibility`가 `reversible`).
2. 대상이 객체 하나예요.
3. 무엇이 바뀌고 어떤 지장이 있을 수 있는지가 승인 화면에 드러나요. "지장 없음"은 조건이 아니고, 지장의 종류를 승인 화면에 보여요.
4. 효과가 가리키는 속성이 대상 타입 모두의 표준 모델에 있고, 그 속성을 다시 읽을 수 있는 소스가 있어요.

액션은 한꺼번에 열리지 않아요. 액션 타입마다 **인자, 실행 조건, 기대 효과(어느 속성이 어떤 값이 되는가), 가운데에 멈출 수 있는지, 되돌릴 때 필요한 것(이전 값)**의 선언이 갖춰지고 검토된 것만 1차의 **확정 대상**이 돼요. 선언이 갖춰지면 들 수 있는 것은 **후보**예요. 선언은 아직 하나도 없어서(아래 4절의 할 일), 지금 확정 대상은 조건 4까지 모델과 대조해서 맞는 것을 가리켜요.

물리 작업(`physical`)은 사람이 현장에서 하므로 1차에서 뺐어요. 업스트림 툴의 대상이 아닌 액션(KG 안의 일, 현장 관찰)과, 현실 시스템의 값인지 프락시움 안의 기록인지 불분명한 액션은 비고에 표시했어요.

관측 시점은 효과 문장만 보고 갈랐어요. 문장에 근거가 없으면 추측하지 않고 "판단 못 함"으로 셌어요.

| 관측 시점 | 의미 | 근거 낱말 |
|---|---|---|
| 곧바로 | 쓴 값이 다음 읽기에 보여요 | 설정값, 표시 |
| 안정된 뒤 | 상태가 바뀌는 데 시간이 걸려요 | 상태 전환, 재시작·단절 |
| 다음 동기화 | 대상 시스템이 아니라 모델의 링크나 객체가 바뀌거나, 현장 작업이라 다음 수집이 돼야 알아요 | 링크·객체, 현장 작업 |
| 판단 못 함 | 효과 문장이 없거나 모호해요 | 글 없음 |

종류 열은 `가역`/`불가역`, `무지장`/`지장`(서비스에 영향 또는 데이터 손실), 물리 작업이면 `물리`를 이어 적었어요.

## 2. 집계

| 거르는 단계 | 수 |
|---|---|
| 액션 타입 전체 | 112 |
| 읽기 액션(바꾸지 않음) | 17 |
| 바꾸는 액션 | 95 |
| 그중 되돌릴 수 있음 | 71 |
| 그중 지장 없음(물리 포함) | 43 |
| 그중 물리 작업이 아님 | 37 |
| 효과 형태와 관측 시점까지 통과(처음 걸러 낸 12개) | 12 |
| 그 12개를 모델의 속성과 대조한 결과: **확정 대상** | **2** |
| 그 12개 중 **후보**(선언이 갖춰지거나 모델을 보강하면 들 수 있음) | 10 |

위 집계의 "지장 없음" 단계는 처음 걸러 내는 데 쓴 것이고 1차의 조건이 아니에요. 같은 잣대로 후보를 더 찾는 일은 선언이 생긴 뒤 액션마다 해요. 이 문서가 든 12개 밖에 들 수 있는 액션이 더 있을 수 있어요.

바꾸는 액션 95개의 효과 형태는 속성 34, 링크 13, 객체 15, 복합 22, 판단 못 함 11이에요. 관측 시점은 곧바로 14, 안정된 뒤 32, 다음 동기화 43, 판단 못 함 6이에요(`backup_database`는 효과 글이 "백업 부하"뿐이라 판단 못 함으로 고쳤어요). 둘 다 판단 못 함인 것이 6개이고, 둘 중 하나라도 판단 못 함인 것은 11개예요. 이런 액션은 인자의 정의(4절)가 생길 때까지 들이지 않아요.

읽기 17개 가운데 4개(`run_diagnostics`, `rescan_storage`, `test_connectivity`, `run_health_check`)는 부작용이 있을 수 있는 진단이에요. 이 구분은 이름과 모델의 표시로 한 것이라, 인자의 정의가 생기면 다시 가려요.

## 3. 확정 대상과 후보

**확정 대상 2개**: `set_locator_led`(표시등 속성이 있는 섀시부터), `cordon_node`(남는 노드 수를 조건으로).

**후보 10개**: 같은 잣대로 모델과 대조한 결과예요.

| 후보 | 선언이 갖춰져도 남는 것 |
|---|---|
| `uncordon_node` | 이 실행이 막은 노드만 풀 수 있게 하고, 아니면 승인 화면에 경고해요. `drain_node`의 반대 액션이에요 |
| `set_cooling_setpoint` | 허용 범위가 있는 인자 정의가 필요해요. 속성이 CRAH와 CRAC에만 있어요. 칠러와 CDU는 하류 전체에 미쳐요 |
| `set_power_cap` | 효과 글의 "성능 저하 가능"이 승인 화면에 드러나야 해요 |
| `clear_power_cap` | `power_limit_w`가 대상 타입에 없어서 모델 보강이 필요해요. 풀면 과부하 위험이 있고 되돌리는 `set_power_cap`이 필요해요 |
| `set_fan_mode` | 팬 속성이 모델에 없어서 모델 보강이 필요해요 |
| `set_maintenance_mode` | 알림 억제가 대상 밖에 미치는 것이 승인 화면에 드러나야 해요 |
| `exit_maintenance_mode` | 작업 중인 호스트에 부하가 다시 실리고 알림 억제가 풀려요. `set_maintenance_mode`와 같은 잣대를 써요 |
| `cancel_maintenance` | 되돌리는 `schedule_maintenance`가 객체 생성이라 1차 밖이에요. 취소한 창의 승인은 돌아오지 않아요 |
| `acknowledge_alarm` | 경보 타입과 어느 경보인지 가리키는 인자가 없어요 |
| `set_label` | 레이블을 셀렉터와 정책이 읽어요. 허용 키 목록이 필요해요 |

같은 잣대를 양쪽에 써요. 예를 들어 `set_power_cap`과 `clear_power_cap`은 같은 후보이고, `set_maintenance_mode`와 `exit_maintenance_mode`도 같아요.

**대상이 불분명한 액션**: `set_label`, `acknowledge_alarm`, `cancel_maintenance`는 현실 시스템의 값인지 프락시움 안의 기록인지 효과 글만으로 알 수 없어요. 프락시움 안의 기록이면 게이트웨이의 일이 아니에요. **업스트림 툴의 대상이 아닌 액션**: `register_unknown_resolution`(KG 안의 병합), `inspect_on_site`(현장 관찰).

켜는 계열(`power_on`, `turn_on_outlet`, `enable_interface`, `start_*`, `enable_pool_member`)은 효과가 상태 전환이라 곧바로 관측되지 않아서 지금은 들이지 않아요. 링크나 객체를 만드는 액션은 조건 2와 4에서 빠져요.

1차를 이 목록만으로 열면 쓸모는 작아요. 1차의 값은 "준비, 승인, 실행, 확인"과 기록이 실제 환경에서 도는지 보고 신뢰 이력을 쌓는 데 있어요. 후보에 드는 액션을 늘리는 일은 선언을 갖추는 일이에요.

## 4. 할 일

- 액션 타입에 인자의 정의(이름, 종류, 허용값)를 더해요. 표준 모델을 고치는 일이라 이 문서의 범위 밖이에요.
- 효과 문장 대신 기계가 읽는 효과 선언(어느 속성이 어떤 값이 되는가, 관측 시점), 실행 조건, 가운데에 멈출 수 있는지, 되돌릴 때 필요한 것(이전 값)을 더해요. 그러면 표의 "판단 못 함"이 줄어요.
- 대상 타입에 효과 속성이 없는 액션(`clear_power_cap`, `set_fan_mode`)은 모델에 속성을 더해요.
- 반대 액션이 없는 `set_*`는 준비 때 이전 값을 기록해야 되돌릴 수 있어요.
- 표준 모델의 `disruption` 표시를 믿을 수 있게 고치는 결정이 2차 전에 필요해요.
- 표는 사람이 읽고 만든 거예요. 선언이 생기면 검사로 대체해요.
