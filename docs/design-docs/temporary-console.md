# 임시 콘솔

화면은 다른 저장소가 만들어요(ADR-0016). 그런데 제품 책임자는 프런트엔드 저장소를 당장 만들지 않기로 했어요. 클로즈드 베타까지만 기능을 간단히 눌러 테스트해 볼 수 있게, **나중에 없애기 쉽고 가벼운 임시 화면**을 이 저장소에 둬요. 이 문서는 그 화면이 무엇이고, 어떻게 만들어야 삭제 쉬운지, 무엇을 보이고, 언제 어떻게 지우는지를 적어요.

> **길과 화면의 이름은 구현하는 변경에서 굳어요.** 화면이 부르는 길은 [REST API의 자원 문서](rest-api-resources-data.md)의 이름이고, 그 문서의 길이 OpenAPI 문서에서 바뀌면 이 문서의 표도 맞춰요.

## 1. 목적과 다루는 질문
- 이것은 제품의 화면인가요? 아니에요. 임시예요(2절).
- 어떻게 만들어야 삭제 쉬운가요? 규칙 여섯이에요(3절).
- 어디에 두고 어떻게 내주나요(4절)? 무엇을 보이나요(5절)? 로그인은요(6절)?
- 무엇을 하지 않나요(7절)? 언제 어떤 차례로 지우나요(8절)? 알파의 기준과는 어떤 관계인가요(9절)?

## 2. 무엇이고 무엇이 아닌가
| 임시 콘솔은 | 임시 콘솔은 아니에요 |
|---|---|
| 제품 책임자가 기능을 눌러 보는 **임시** 화면이에요 | 제품의 화면이 아니에요. UX와 UI는 클로즈드 베타에서 프런트엔드 저장소가 제대로 설계해요 |
| 공개된 `/v1` API의 사용자 하나예요 | 백엔드의 일부가 아니에요. 단위(구조 계약)에 들지 않아요 |
| API를 쓰는 본보기예요(화면마다 "이 화면이 부른 API"를 보여요) | API를 화면에 맞추는 이유가 아니에요 |
| 알파의 테스트를 편하게 해요 | 알파의 기준이 아니에요. 기준은 "모든 기능이 API와 CLI로 된다"예요 |

ADR-0016의 "화면의 코드는 이 저장소에 두지 않는다"에 **예외 하나**예요. 프런트엔드 저장소가 서거나 클로즈드 베타가 끝나면 지워요(부채 TD-0007).

```
 브라우저 ──(1) 정적 파일(HTML, JS 모듈, CSS)──▶ [API 역할] ── 설정이 켜진 배포에서만, 디스크의 폴더를 읽어 내줘요
    │                                              │
    └──(2) 로그인: SSO에서 증표 ───────────────────┤   콘솔을 위한 길은 없어요
       (3) 공개된 /v1 만 부르기(Authorization: Bearer) ─▶ 일반 API 길
```

## 3. 없애기 쉽게 만드는 규칙 여섯
이 규칙이 설계예요. 규칙마다 "어긋나면 삭제가 어려워지는 이유"을 적었어요.

| # | 규칙 | 이유 |
|---|---|---|
| 1 | **저장소의 따로 된 폴더 하나에만 있어요.** 제품의 단위(구조 계약)에 들지 않고 백엔드의 어떤 코드도 그것을 import하지 않아요. 폴더를 지우고 켜는 설정 하나를 지우면 끝나요 | 백엔드 코드가 콘솔을 참조하면 지울 때 백엔드를 고쳐야 해요. 구조 검사도 콘솔을 단위로 받아들여야 하고, 그러면 지운 뒤에 구조 계약도 고쳐야 해요 |
| 2 | **공개된 REST API(`/v1`)만 써요.** 콘솔을 위한 길, 콘솔만 아는 응답, 서버 쪽의 화면 처리를 만들지 않아요. 불편해도 API를 콘솔에 맞추지 않아요 | 콘솔 전용 길이 하나라도 생기면 콘솔을 지울 때 그 길이 남아 계약을 어지럽혀요. 화면 전용의 묶음 길을 두지 않는다는 ADR-0016의 원칙 그대로예요. 콘솔이 불편하면 그 불편이 프런트엔드 저장소가 겪을 불편이라는 신호예요 |
| 3 | **빌드가 없어요.** 묶는 도구, 화면 프레임워크, 패키지 설치 없이 도는 정적 파일(HTML, 표준 JavaScript 모듈, CSS)이에요. 바깥 라이브러리는 꼭 필요한 것만 파일로 함께 싣고 라이선스를 봐요(그래프를 그리는 것 하나 정도) | 빌드 도구와 패키지 설정이 들어오면 백엔드의 검사, 의존성 점검, 라이선스 점검이 그것을 떠안고, 지울 때 흔적이 남아요. 파일을 그대로 싣는 라이브러리는 폴더와 함께 지워져요 |
| 4 | **API 역할이 정적 파일로 내줘요.** 기본은 꺼져 있고 설정으로 켜요. 프로덕션 배포에서는 켜지 않아요 | 별도의 서버를 두면 띄울 것과 지울 것이 늘어요. 기본이 꺼져 있어야 실수로 켜진 채 나가지 않아요 |
| 5 | **로그인은 제품과 같은 길이에요.** SSO에서 토큰을 받아 API에 실어요. 콘솔용 뒷문을 두지 않아요 | 뒷문은 지운 뒤에도 남기 쉽고, 삭제 전에는 제품보다 약한 길이 돼요. 같은 길이면 권한의 판단도 같은 곳에서 해요(ADR-0012) |
| 6 | **화면의 말, UX 측정, 접근성, 디자인을 다듬지 않아요.** 한국어 조사 처리도 하지 않아요. 코드와 값을 그대로 보여요 | 다듬는 일은 버려질 일이에요. 프런트엔드 저장소가 서면 처음부터 다시 해요. 임시 화면에 들인 공은 지울 때 아깝고, 아까우면 삭제 어려워요 |

### 3.1 규칙이 지켜지는지 보는 경로
구현하는 변경에서 걸 수 있는 테스트예요(제안).
- **규칙 1:** 구조 검사가 구조 계약 밖의 폴더를 import하는 백엔드 코드를 잡아요.
- **규칙 2:** 콘솔이 "이 화면이 부른 API"로 기록하는 길이 모두 계약(OpenAPI)에 있어야 해요. 없는 길을 부르면 테스트가 실패해요.
- **규칙 3:** 콘솔 폴더에 패키지 설정 파일이나 묶는 도구의 설정이 없어야 해요.
- **규칙 4:** 배포 정의의 기본값에서 콘솔이 꺼져 있고, 프로덕션 배포의 정의에는 켜는 설정이 없어야 해요.

## 4. 어디에 두고 어떻게 내주나
- **폴더의 자리는 구현하는 변경에서 정해요.** 정해진 것은 "저장소의 따로 된 폴더 하나"라는 규칙뿐이에요.
- **내주는 쪽은 API 역할이에요.** 켜는 설정은 시작할 때 읽는 배포의 값이에요(가정. 이 설정은 저장소가 뜨기 전에도 필요해서 ADR-0017의 "API로 바꾸는 설정"이 아니에요). 켜지면 API 역할이 설정이 가리키는 **디스크의 폴더**를 읽어 정적 파일로 내줘요.
- **실행 파일에 넣지 않아요.** 넣으면 빌드가 콘솔 폴더에 기대게 돼 규칙 1이 깨져요. 그래서 콘솔은 실행 파일 옆의 폴더로 배포돼요. "실행 파일 하나로 배포된다"(ADR-0006)는 알파의 이 한 곳에서 예외예요. 폴더는 디스크로 내줘요(정해진 것).
- **같은 출처에서 내줘요.** 콘솔과 API가 같은 주소에서 나오므로 교차 출처 허용이 필요 없고, API의 허용할 출처의 목록은 기본(막힘) 그대로예요.
- **정적 파일에도 보안 머리를 달아요.** 틀 안에 넣기를 막고, 스크립트를 같은 출처의 파일로만 받게 하는 머리예요(6절의 이유).
- **`GET /v1/capabilities`의 `features`에 콘솔이 켜져 있다고 보이게 하는 것**을 권해요. 오픈 베타 전에 "프로덕션에 켜져 있지 않다"를 점검하려는 거예요(10절).

## 5. 화면의 목록
기능을 테스트할 만큼만이에요. **모든 화면 아래에 "이 화면이 부른 API"** 칸이 있어요: 부른 메서드와 길, 상태 코드, 걸린 시간, 응답의 JSON. 토큰(`Authorization` 머리)는 보이지 않아요.

| 화면 | 보이는 것과 단추 | 부르는 API |
|---|---|---|
| 계약 탐색기 | 계약 문서(OpenAPI)에서 저절로 나오는 길의 목록과 칸. 길을 골라 보내 봐요. 보내는 것은 읽기와 `x-safe`로 표시된 물음뿐이에요 | `GET /v1/contract`, `GET /v1/capabilities`, `GET /v1/me`, `GET /v1/problems/{code}` |
| 소스와 일정과 실행 | 소스 목록과 상세, 일정, 실행 목록과 단계별 수, 흐름과 수집기. 단추: 지금 한 번, 일시 정지와 다시 켜기 | `GET /v1/sources`, `GET /v1/sources/{source_id}`, `GET /v1/schedules`, `POST /v1/schedules/{schedule_id}:run-now`, `POST /v1/sources/{source_id}:pause`, `POST /v1/sources/{source_id}:resume`, `GET /v1/sync-runs`, `GET /v1/sync-runs/{run_id}`, `GET /v1/sync-runs/{run_id}/stages`, `GET /v1/feed-flows`, `GET /v1/collectors`, `GET /v1/jobs/{job_id}` |
| 시크릿(메타 정보만) | 이름, 종류, 판의 상태, 만료, 마지막으로 쓴 때. 값을 넣는 칸이 없어요([시크릿과 암호화](secrets-and-encryption.md)) | `GET /v1/secrets`, `GET /v1/secrets/{secret_id}` |
| 브랜치와 제안과 드라이 런의 차이 | 열린 브랜치와 제안, 차단 사유, 검사, 정의의 차이와 KG의 차이, 병합 큐. 단추: 드라이 런 | `GET /v1/definitions-overview`, `GET /v1/branches`, `GET /v1/branches/{branch_id}/items`, `GET /v1/proposals`, `GET /v1/proposals/{proposal_id}`, `GET /v1/proposals/{proposal_id}/checks`, `POST /v1/proposals/{proposal_id}/candidate-runs`, `GET /v1/candidate-runs/{run_id}/diff`, `GET /v1/merge-queue` |
| 객체 찾기와 이웃과 영향 범위 | 객체를 찾아 상세를 보고, 이웃과 영향 범위를 작은 그래프와 표로 | `POST /v1/kgs/{kg}/queries:find`, `GET /v1/kgs/{kg}/objects/{object_id}`, `POST /v1/kgs/{kg}/queries:neighbors`, `POST /v1/kgs/{kg}/questions/impact`, `GET /v1/kgs/{kg}/graph-versions` |
| 헬스 상태와 문제 목록 | 자원의 헬스 상태와 이유, 문제 목록, 알림, 자원의 타임라인 | `GET /v1/kgs/{kg}/health`, `GET /v1/kgs/{kg}/health/{resource_kind}/{resource_id}`, `GET /v1/issues`, `GET /v1/issues/{issue_id}`, `GET /v1/alerts`, `GET /v1/resources/{resource_kind}/{resource_id}/timeline` |
| 역량 질문과 충족률 | 역량 질문의 목록과 충족률, 속성으로 거른 충족률 | `GET /v1/competency-questions`, `POST /v1/kgs/{kg}/queries:competency` |
| 권한 부여의 표 | 권한 부여의 표, 역할 여덟, 감사 로그. 단추: 부여를 주고 거두기 | `GET /v1/grants`, `POST /v1/grants`, `POST /v1/grants/{grant_id}:revoke`, `GET /v1/roles`, `GET /v1/directory/subjects`, `GET /v1/audit-records` |
| 프락시움 자신의 진단 | 지금 이상 상태인 부품과 이유, 이벤트 코드, 운영 액션의 목록과 미리 실행, 올리는 중의 상태. 운영 액션을 실행하는 단추는 없어요(명령줄로 해요) | `POST /v1/ops/diagnose`, `GET /v1/ops/event-codes`, `GET /v1/ops/actions`, `POST /v1/ops/actions/{action}:dry-run`, `GET /v1/ops/rollout` |

- 보내는 경로는 정해진 단추의 것과 `x-safe`(안전하다고 표시된 길)뿐이에요. 길의 `{kg}`는 기본 `main`이에요.
- 권한이 없는 화면은 API가 `permission.*`나 `not_found.resource`로 답하고, 콘솔은 그것을 그대로 보여요. 단추를 켜고 끄는 데는 응답의 `meta.allowed_actions`를 써요(판단은 서버가 해요).
- 화면의 목록은 상한이에요. 새 API가 생겼다고 화면을 더해야 하는 것은 아니에요(9절).

## 6. 로그인
제품과 같은 길이에요([REST API 설계](rest-api.md) 4절). 콘솔은 SSO의 한 클라이언트로 등록돼요(등록은 배포의 일).
1. 콘솔의 JS 모듈이 SSO로 인증 요청을 보내요(인증 코드 흐름과 PKCE).
2. 사용자가 SSO에서 로그인하고 인증 코드를 들고 돌아와요.
3. 콘솔이 코드와 PKCE의 verifier로 토큰을 받아 `Authorization: Bearer`로 `/v1`에 실어요.
4. 서버가 토큰을 확인하고 권한을 판단해요. 콘솔은 세션을 만들지 않아요.

임시여도 지키는 것이 있어요. 콘솔은 토큰을 들고 있어서, 뚫리면 그 사람의 권한이 그대로 쓰이기 때문이에요.
- **토큰은 메모리에만 둬요.** 브라우저의 저장소에 쓰지 않아요. 새로 고치면 다시 받아요.
- **API가 준 값은 글로만 그려요.** HTML로 해석해 그리지 않아요. 소스에서 받은 글이 객체의 이름으로 올 수 있어요.
- **바깥에서 스크립트를 받지 않아요.** 라이브러리는 폴더 안의 파일이고, 보안 머리가 그것만 허용해요.

## 7. 하지 않는 것
- 화면의 말을 다듬지 않아요. UX 측정, 접근성, 디자인, 한국어 조사 처리를 하지 않아요(규칙 6).
- 콘솔 전용 길, 묶음 길, 서버 쪽의 화면 처리를 만들지 않아요(규칙 2).
- 묶는 도구, 화면 프레임워크, 패키지 설치를 쓰지 않아요(규칙 3).
- 콘솔용 로그인이나 뒷문을 두지 않아요. 토큰을 손으로 붙여 넣는 칸도 두지 않아요(규칙 5).
- **시크릿을 입력받지 않아요.** 값을 넣고 바꾸는 것은 CLI나 API로 해요. 콘솔은 메타 정보만 보여요.
- 정의의 항목을 고치는 편집기를 만들지 않아요. 브랜치에서 고치는 일은 CLI나 API로 해요.
- 상태를 브라우저에 쌓지 않아요(토큰도, 화면의 설정도). 서버에 세션을 두지 않아요.
- 프로덕션 배포에서 켜지 않아요(규칙 4).
- 계약 탐색기에서 `x-safe`가 아닌 길을 보내지 않아요. 그런 일은 위 표의 정해진 단추나 CLI가 해요.

## 8. 지우는 조건과 차례 (TD-0007)
**지우는 조건.** 둘 가운데 먼저 오는 쪽이에요.
1. 프런트엔드 저장소가 서서 알파의 테스트 화면이 거기에 생겼을 때.
2. 클로즈드 베타가 끝났을 때.

조건이 되면 지워요. 더 쓸 만하다는 이유로 미루지 않아요. 미루려면 조건을 바꾸는 결정 기록이 있어야 해요.

**지우는 차례.** 한 변경에서 해요.
| 차례 | 하는 일 | 확인 |
|---|---|---|

**지워도 남는 것.** 콘솔이 부르던 API는 그대로예요. 계약이기 때문이에요. 콘솔이 보여 주던 "이 화면이 부른 API"의 기록은 프런트엔드 저장소가 같은 일을 할 때 참고할 수 있는 예시로 남겨도 돼요(저장소 밖으로).

## 9. 알파의 기준과의 관계
- 콘솔은 알파 1(뼈대와 한 줄)에 서고 제품 책임자가 거기서부터 눌러 봐요. 알파의 기준은 그대로예요. **모든 기능이 API와 CLI로 돼요**(ADR-0016, REQ-147). 콘솔은 그 위의 편의예요.
- **콘솔에 없다고 기능이 없는 것이 아니에요.** 제품 책임자가 알파를 테스트할 때 어떤 기능의 화면이 없으면 CLI로 테스트해요. 화면이 없다는 것이 그 기능의 알파 완료를 막지 않아요.
- 거꾸로 콘솔에 있다고 기능이 끝난 것도 아니에요. 기능의 완료는 API의 계약과 테스트가 정해요.
- 알파가 끝난 뒤 클로즈드 베타에서 프런트엔드 저장소가 UX와 UI를 설계하고, 콘솔의 화면 목록은 그때 요구의 출발 자료로만 쓰여요.

## 10. 알려진 한계와 미결 사항
**알려진 한계**
- **보안 검토를 깊이 하지 않아요.** 임시라서요. 그래서 프로덕션에 켜지 않는다는 규칙 4가 보안의 경계예요. 켜진 채 나가면 토큰을 다루는 검토 안 된 화면이 나가요.
- **알파의 "실행 파일 하나" 배포에 폴더가 하나 따라와요**(4절).
- **한 프로세스에 역할을 다 띄우는 알파에서는 콘솔을 내주는 코드가 같은 프로세스에 있어요.** 코드는 규칙 1대로 떨어져 있어요.
- **화면의 목록은 기능을 테스트할 만큼이에요.** 쓰기 쪽(정의의 편집, 승인)의 테스트는 CLI로 해야 해요.

**미결 사항**
- 폴더의 자리와 켜는 설정의 이름. 구현하는 변경에서 정해요.
- 계약 탐색기가 계약의 `x-safe` 표시를 어디까지 믿는지(표시가 틀리면 상태를 바꾸는 경로가 나갈 수 있어요).
- 콘솔이 켜져 있다고 `features`에 보이게 할지, 오픈 베타의 점검에 쓸지(4절의 권고).
- 그래프를 그리는 라이브러리. 구현하는 변경에서 허용된 라이선스의 것을 골라요.
