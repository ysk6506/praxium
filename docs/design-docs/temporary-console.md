# 임시 콘솔

화면은 다른 리포지토리가 만들어요(ADR-0016). 그런데 제품 책임자는 프런트엔드 리포지토리를 당장 만들지 않기로 했어요. 클로즈드 베타까지만 기능을 간단히 눌러 테스트해 볼 수 있게, **나중에 삭제하기 쉽고 가벼운 임시 화면**을 이 리포지토리에 둬요. 이 문서는 그 화면이 무엇이고, 어떻게 만들어야 삭제하기 쉬운지, 무엇을 보여 주고, 언제 어떻게 삭제하는지를 적어요.

> **경로와 화면의 이름은 구현하는 변경에서 확정돼요.** 화면이 호출하는 경로는 [REST API의 자원 문서](rest-api-resources-data.md)의 이름이고, 그 문서의 경로가 OpenAPI 문서에서 바뀌면 이 문서의 표도 맞춰요.

## 1. 목적과 다루는 질문
- 임시 콘솔의 성격: 제품 화면이 아니라 임시 화면(2절).
- 삭제하기 쉽게 만드는 규칙 6가지(3절).
- 배치와 제공 방식(4절), 화면 목록(5절), 로그인(6절).
- 하지 않는 것(7절), 삭제 조건과 순서(8절), 알파의 기준과의 관계(9절).

## 2. 임시 콘솔의 성격과 범위
| 임시 콘솔은 | 임시 콘솔이 아닌 것 |
|---|---|
| 제품 책임자가 기능을 눌러 보는 **임시** 화면이에요 | 제품의 화면이 아니에요. UX와 UI는 클로즈드 베타에서 프런트엔드 리포지토리가 제대로 설계해요 |
| 공개된 `/v1` API의 사용자 하나예요 | 백엔드의 일부가 아니에요. 유닛(구조 계약)에 포함되지 않아요 |
| API를 사용하는 예시예요(화면마다 "이 화면이 호출한 API"를 보여 줘요) | API를 화면에 맞추는 이유가 아니에요 |
| 알파의 테스트를 편하게 해요 | 알파의 기준이 아니에요. 기준은 "모든 기능이 API와 CLI로 된다"예요 |

ADR-0016의 "화면 코드는 이 리포지토리에 두지 않는다"에 **예외 하나**예요. 프런트엔드 리포지토리가 구축되거나 클로즈드 베타가 끝나면 삭제해요(부채 TD-0007).

```
 브라우저 ──(1) 정적 파일(HTML, JS 모듈, CSS)──▶ [API 역할] ── 설정이 켜진 배포에서만, 디스크의 폴더를 읽어 제공해요
    │                                              │
    └──(2) 로그인: SSO에서 토큰 발급 ──────────────┤   콘솔 전용 경로는 없어요
       (3) 공개된 /v1 만 호출(Authorization: Bearer) ─▶ 일반 API 경로
```

## 3. 삭제하기 쉽게 만드는 규칙 6가지
이 규칙이 설계예요. 규칙마다 "어긋나면 삭제가 어려워지는 이유"를 적었어요.

| # | 규칙 | 이유 |
|---|---|---|
| 1 | **리포지토리의 별도 폴더 하나에만 있어요.** 제품의 유닛(구조 계약)에 포함되지 않고 백엔드의 어떤 코드도 그것을 import하지 않아요. 폴더를 삭제하고 콘솔을 켜는 설정 하나를 삭제하면 끝나요 | 백엔드 코드가 콘솔을 참조하면 삭제할 때 백엔드를 수정해야 해요. 구조 검사도 콘솔을 유닛으로 받아들여야 하고, 그러면 삭제한 뒤에 구조 계약도 수정해야 해요 |
| 2 | **공개된 REST API(`/v1`)만 사용해요.** 콘솔 전용 경로, 콘솔만 아는 응답, 서버 측의 화면 처리를 만들지 않아요. 불편해도 API를 콘솔에 맞추지 않아요 | 콘솔 전용 경로가 하나라도 생기면 콘솔을 삭제할 때 그 경로가 남아 계약을 어지럽혀요. 화면 전용 집계 경로를 두지 않는다는 ADR-0016의 원칙 그대로예요. 콘솔이 불편하면 그 불편은 프런트엔드 리포지토리도 겪을 불편이라는 신호예요 |
| 3 | **빌드가 없어요.** 번들러, 화면 프레임워크, 패키지 설치 없이 동작하는 정적 파일(HTML, 표준 JavaScript 모듈, CSS)이에요. 외부 라이브러리는 꼭 필요한 것만 파일로 함께 포함하고 라이선스를 확인해요(그래프 렌더링용 하나 정도) | 빌드 도구와 패키지 설정이 들어오면 백엔드의 검사, 의존성 점검, 라이선스 점검이 그것까지 대상으로 삼고, 삭제할 때 흔적이 남아요. 파일을 그대로 포함하는 라이브러리는 폴더와 함께 삭제돼요 |
| 4 | **API 역할이 정적 파일로 제공해요.** 기본은 꺼져 있고 설정으로 켜요. 프로덕션 배포에서는 켜지 않아요 | 별도의 서버를 두면 기동할 것과 삭제할 것이 늘어요. 기본이 꺼져 있어야 실수로 켜진 채 배포되지 않아요 |
| 5 | **로그인은 제품과 같은 방식이에요.** SSO에서 토큰을 받아 API에 실어요. 콘솔용 우회 경로를 두지 않아요 | 우회 경로는 삭제한 뒤에도 남기 쉽고, 삭제 전에는 제품보다 약한 경로가 돼요. 같은 방식이면 권한 판단도 같은 곳에서 해요(ADR-0012) |
| 6 | **화면의 문구, UX 측정, 접근성, 디자인을 다듬지 않아요.** 한국어 조사 처리도 하지 않아요. 코드와 값을 그대로 보여 줘요 | 다듬는 일은 버려질 일이에요. 프런트엔드 리포지토리가 구축되면 처음부터 다시 해요. 임시 화면에 들인 노력은 삭제할 때 아깝고, 아까우면 삭제를 미루게 돼요 |

### 3.1 규칙 준수 확인 방법
구현하는 변경에서 적용할 수 있는 테스트예요(제안).
- **규칙 1:** 구조 검사가 구조 계약 밖의 폴더를 import하는 백엔드 코드를 잡아요.
- **규칙 2:** 콘솔이 "이 화면이 호출한 API"로 기록하는 경로가 모두 계약(OpenAPI)에 있어야 해요. 없는 경로를 호출하면 테스트가 실패해요.
- **규칙 3:** 콘솔 폴더에 패키지 설정 파일이나 번들러 설정이 없어야 해요.
- **규칙 4:** 배포 정의의 기본값에서 콘솔이 꺼져 있고, 프로덕션 배포의 정의에는 켜는 설정이 없어야 해요.

## 4. 배치와 제공 방식
- **폴더 위치는 구현하는 변경에서 정해요.** 정해진 것은 "리포지토리의 별도 폴더 하나"라는 규칙뿐이에요.
- **제공하는 쪽은 API 역할이에요.** 켜는 설정은 시작할 때 읽는 배포 값이에요(가정. 이 설정은 스토리지가 기동되기 전에도 필요해서 ADR-0017의 "API로 바꾸는 설정"이 아니에요). 켜지면 API 역할이 설정이 가리키는 **디스크의 폴더**를 읽어 정적 파일로 제공해요.
- **실행 파일에 넣지 않아요.** 넣으면 빌드가 콘솔 폴더에 의존하게 돼 규칙 1이 깨져요. 그래서 콘솔은 실행 파일 옆의 폴더로 배포돼요. "실행 파일 하나로 배포된다"(ADR-0006)는 알파의 이 한 곳에서 예외예요. 폴더는 디스크에서 제공해요(확정).
- **같은 출처에서 제공해요.** 콘솔과 API가 같은 주소에서 나오므로 CORS 허용이 필요 없고, API의 허용 출처 목록은 기본값(전부 차단) 그대로예요.
- **정적 파일에도 보안 헤더를 설정해요.** iframe 삽입을 차단하고, 스크립트를 같은 출처의 파일로만 로드하게 하는 헤더예요(6절의 이유).
- **`GET /v1/capabilities`의 `features`에 콘솔이 켜져 있다고 표시하는 것**을 권장해요. 오픈 베타 전에 "프로덕션에 켜져 있지 않다"를 점검하려는 거예요(10절).

## 5. 화면 목록
기능을 테스트할 만큼만이에요. **모든 화면 아래에 "이 화면이 호출한 API"** 영역이 있어요: 호출한 메서드와 경로, 상태 코드, 소요 시간, 응답의 JSON. 토큰(`Authorization` 헤더)은 보이지 않아요.

| 화면 | 보이는 것과 버튼 | 호출하는 API |
|---|---|---|
| 계약 탐색기 | 계약 문서(OpenAPI)에서 자동으로 생성되는 경로 목록과 필드. 경로를 골라 요청을 보내 볼 수 있어요. 보내는 것은 읽기와 `x-safe`로 표시된 질의뿐이에요 | `GET /v1/contract`, `GET /v1/capabilities`, `GET /v1/me`, `GET /v1/problems/{code}` |
| 소스와 일정과 실행 | 소스 목록과 상세, 일정, 실행 목록과 단계별 건수, 스트림과 수집기. 버튼: 즉시 실행, 일시 정지와 재개 | `GET /v1/sources`, `GET /v1/sources/{source_id}`, `GET /v1/schedules`, `POST /v1/schedules/{schedule_id}:run-now`, `POST /v1/sources/{source_id}:pause`, `POST /v1/sources/{source_id}:resume`, `GET /v1/sync-runs`, `GET /v1/sync-runs/{run_id}`, `GET /v1/sync-runs/{run_id}/stages`, `GET /v1/feed-flows`, `GET /v1/collectors`, `GET /v1/jobs/{job_id}` |
| 시크릿(메타 정보만) | 이름, 종류, 버전 상태, 만료, 마지막으로 기록한 시각. 값을 입력하는 필드가 없어요([시크릿과 암호화](secrets-and-encryption.md)) | `GET /v1/secrets`, `GET /v1/secrets/{secret_id}` |
| 브랜치와 제안과 드라이 런의 차이 | 열린 브랜치와 제안, 차단 사유, 검사, 정의의 차이와 KG의 차이, 병합 큐. 버튼: 드라이 런 | `GET /v1/definitions-overview`, `GET /v1/branches`, `GET /v1/branches/{branch_id}/items`, `GET /v1/proposals`, `GET /v1/proposals/{proposal_id}`, `GET /v1/proposals/{proposal_id}/checks`, `POST /v1/proposals/{proposal_id}/candidate-runs`, `GET /v1/candidate-runs/{run_id}/diff`, `GET /v1/merge-queue` |
| 객체 찾기와 이웃과 영향 범위 | 객체를 찾아 상세를 보고, 이웃과 영향 범위를 작은 그래프와 테이블로 | `POST /v1/kgs/{kg}/queries:find`, `GET /v1/kgs/{kg}/objects/{object_id}`, `POST /v1/kgs/{kg}/queries:neighbors`, `POST /v1/kgs/{kg}/questions/impact`, `GET /v1/kgs/{kg}/graph-versions` |
| 헬스 상태와 문제 목록 | 자원의 헬스 상태와 이유, 문제 목록, 알림, 자원의 타임라인 | `GET /v1/kgs/{kg}/health`, `GET /v1/kgs/{kg}/health/{resource_kind}/{resource_id}`, `GET /v1/issues`, `GET /v1/issues/{issue_id}`, `GET /v1/alerts`, `GET /v1/resources/{resource_kind}/{resource_id}/timeline` |
| 역량 질문과 충족률 | 역량 질문의 목록과 충족률, 속성으로 필터링한 충족률 | `GET /v1/competency-questions`, `POST /v1/kgs/{kg}/queries:competency` |
| 권한 부여 목록 | 권한 부여 목록, 역할 8종, 감사 로그. 버튼: 권한 부여와 회수 | `GET /v1/grants`, `POST /v1/grants`, `POST /v1/grants/{grant_id}:revoke`, `GET /v1/roles`, `GET /v1/directory/subjects`, `GET /v1/audit-records` |
| 프락시움 자신의 진단 | 지금 이상 상태인 컴포넌트와 이유, 이벤트 코드, 운영 액션의 목록과 미리 실행, 롤아웃 상태. 운영 액션을 실행하는 버튼은 없어요(CLI로 해요) | `POST /v1/ops/diagnose`, `GET /v1/ops/event-codes`, `GET /v1/ops/actions`, `POST /v1/ops/actions/{action}:dry-run`, `GET /v1/ops/rollout` |

- 요청을 보내는 경로는 정해진 버튼의 것과 `x-safe`(안전하다고 표시된 경로)뿐이에요. 경로의 `{kg}`는 기본 `main`이에요.
- 권한이 없는 화면은 API가 `permission.*`나 `not_found.resource`로 응답하고, 콘솔은 그것을 그대로 보여 줘요. 버튼을 활성화하거나 비활성화하는 데는 응답의 `meta.allowed_actions`를 써요(판단은 서버가 해요).
- 화면 목록은 상한이에요. 새 API가 생겼다고 화면을 추가해야 하는 것은 아니에요(9절).

## 6. 로그인
제품과 같은 방식이에요([REST API 설계](rest-api.md) 4절). 콘솔은 SSO의 클라이언트 하나로 등록돼요(등록은 배포의 일).
1. 콘솔의 JS 모듈이 SSO로 인증 요청을 보내요(인가 코드 플로우와 PKCE).
2. 사용자가 SSO에서 로그인하고 인증 코드를 가지고 돌아와요.
3. 콘솔이 코드와 PKCE의 verifier로 토큰을 받아 `Authorization: Bearer`로 `/v1`에 실어요.
4. 서버가 토큰을 검증하고 권한을 판단해요. 콘솔은 세션을 만들지 않아요.

임시여도 지키는 것이 있어요. 콘솔은 토큰을 가지고 있어서, 탈취되면 그 사용자의 권한이 그대로 악용되기 때문이에요.
- **토큰은 메모리에만 둬요.** 브라우저 스토리지에 쓰지 않아요. 페이지를 다시 불러오면 다시 받아요.
- **API가 준 값은 텍스트로만 렌더링해요.** HTML로 해석해 그리지 않아요. 소스에서 수집한 문자열이 객체의 이름으로 올 수 있어요.
- **외부에서 스크립트를 로드하지 않아요.** 라이브러리는 폴더 안의 파일이고, 보안 헤더가 그것만 허용해요.

## 7. 하지 않는 것
- 화면의 문구를 다듬지 않아요. UX 측정, 접근성, 디자인, 한국어 조사 처리를 하지 않아요(규칙 6).
- 콘솔 전용 경로, 집계 경로, 서버 측의 화면 처리를 만들지 않아요(규칙 2).
- 번들러, 화면 프레임워크, 패키지 설치를 쓰지 않아요(규칙 3).
- 콘솔용 로그인이나 우회 경로를 두지 않아요. 토큰을 직접 붙여 넣는 입력란도 두지 않아요(규칙 5).
- **시크릿을 입력받지 않아요.** 값을 넣고 바꾸는 것은 CLI나 API로 해요. 콘솔은 메타 정보만 보여 줘요.
- 정의의 항목을 수정하는 편집기를 만들지 않아요. 브랜치에서 수정하는 일은 CLI나 API로 해요.
- 상태를 브라우저에 저장하지 않아요(토큰도, 화면의 설정도). 서버에 세션을 두지 않아요.
- 프로덕션 배포에서 켜지 않아요(규칙 4).
- 계약 탐색기에서 `x-safe`가 아닌 경로를 호출하지 않아요. 그런 일은 위 표의 정해진 버튼이나 CLI가 해요.

## 8. 삭제 조건과 순서 (TD-0007)
**삭제 조건.** 둘 중 먼저 충족되는 쪽이에요.
1. 프런트엔드 리포지토리가 구축되어 알파의 테스트 화면이 거기에 생겼을 때.
2. 클로즈드 베타가 끝났을 때.

조건이 충족되면 삭제해요. 더 쓸 만하다는 이유로 미루지 않아요. 미루려면 조건을 바꾸는 결정 기록이 있어야 해요.

**삭제 순서.** 한 변경에서 해요.
| 순서 | 하는 일 | 확인 |
|---|---|---|
| 1 | 켜는 설정이 모든 배포 정의에서 꺼져 있는지 확인해요 | 켜져 있던 곳이 있으면 먼저 끄고 사용하던 사람에게 알려요 |
| 2 | API 역할의 정적 파일 제공 코드와 켜는 설정을 삭제해요 | 이 코드는 한 곳에 있어요(규칙 1, 4) |
| 3 | 콘솔 폴더를 삭제해요. 함께 포함했던 외부 라이브러리도 같이 삭제돼요 | 폴더 밖에 콘솔의 파일이 없어요 |
| 4 | 구조 검사와 계약의 테스트가 그대로 통과하는지 확인해요 | 콘솔이 없어도 계약과 서버가 그대로 동작한다는 증거예요(규칙 1, 2) |
| 5 | 문서와 대장을 정리해요 | 아래 |

문서와 대장에서는 ARCHITECTURE.md와 AGENTS.md의 예외 문장을 삭제하고, 이 문서와 REQ-209를 폐기(retired) 처리하고, TD-0007을 닫고, 라이선스 고지에서 콘솔이 포함한 라이브러리를 빼요.

**삭제해도 남는 것.** 콘솔이 호출하던 API는 그대로예요. 계약이기 때문이에요. 콘솔이 보여 주던 "이 화면이 호출한 API"의 기록은 프런트엔드 리포지토리가 같은 일을 할 때 참고할 수 있는 예시로 남겨도 돼요(리포지토리 밖에).

## 9. 알파의 기준과의 관계
- 콘솔은 알파 1(뼈대와 한 줄)에 구축하고 제품 책임자가 거기서부터 눌러 봐요. 알파의 기준은 그대로예요. **모든 기능이 API와 CLI로 돼요**(ADR-0016, REQ-147). 콘솔은 그 위의 편의 기능이에요.
- **콘솔에 없다고 기능이 없는 것이 아니에요.** 제품 책임자가 알파를 테스트할 때 어떤 기능의 화면이 없으면 CLI로 테스트해요. 화면이 없다는 것이 그 기능의 알파 완료를 막지 않아요.
- 반대로 콘솔에 있다고 기능이 완료된 것도 아니에요. 기능의 완료는 API의 계약과 테스트가 정해요.
- 알파가 끝난 뒤 클로즈드 베타에서 프런트엔드 리포지토리가 UX와 UI를 설계하고, 콘솔의 화면 목록은 그때 요구사항의 출발 자료로만 쓰여요.

## 10. 알려진 한계와 미결 사항
**알려진 한계**
- **보안 검토를 깊이 하지 않아요.** 임시라서요. 그래서 프로덕션에 켜지 않는다는 규칙 4가 보안의 경계예요. 켜진 채 배포되면 토큰을 다루는, 검토되지 않은 화면이 나가요.
- **알파의 "실행 파일 하나" 배포에 폴더가 하나 따라와요**(4절).
- **한 프로세스에 역할을 모두 기동하는 알파에서는 콘솔을 제공하는 코드가 같은 프로세스에 있어요.** 코드는 규칙 1대로 분리돼 있어요.
- **화면 목록은 기능을 테스트할 만큼이에요.** 쓰기 쪽(정의의 편집, 승인)의 테스트는 CLI로 해야 해요.

**미결 사항**
- 폴더 위치와 켜는 설정의 이름. 구현하는 변경에서 정해요.
- 계약 탐색기가 계약의 `x-safe` 표시를 어디까지 신뢰하는지(표시가 틀리면 상태를 바꾸는 경로가 호출될 수 있어요).
- 콘솔이 켜져 있다고 `features`에 표시할지, 오픈 베타의 점검에 쓸지(4절의 권장 사항).
- 그래프를 렌더링하는 라이브러리. 구현하는 변경에서 허용된 라이선스의 것을 골라요.
