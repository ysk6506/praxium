# PostgreSQL의 HA와 쉬운 구성

PostgreSQL이 고장 났을 때 제품이 어떻게 버티는지, 배포마다 어떤 구성을 권하는지, 그 상태를 어떻게 점검하는지의 설계예요. 결정은 ADR-0081에 있어요. **이 문서는 아직 구현하지 않은 설계(예정)예요.** 배포는 로컬 한 대, 가상 기계의 작은 운영, 쿠버네티스 셋이고 **클라우드의 관리형 PostgreSQL은 지원 대상이 아니에요.** 지금 구현은 풀 하나와 DSN 하나이고, 운영 규칙은 [PostgreSQL 운영](postgres-operations.md)에 있어요. 예시의 주소와 이름은 지어낸 것(`example.test`)이에요.

## 1. 목적과 다루는 질문

- 장애 조치(주 서버가 죽어 대기 서버가 주가 되는 일)를 누가 하고, 제품은 무엇을 지키나.
- 배포 세 가지에서 가장 쉬운 HA 구성은 무엇이고, 제품이 무엇을 내주면 쉬워지나.
- 설정이 잘못된 것(대기 하나의 동기 복제, 연결 한도 초과, 쓸 데 없는 슬롯)을 어떻게 미리 알아내나.

기준 버전은 **PostgreSQL 18**이에요. 19에만 있는 기능(예: `WAIT FOR LSN`)은 있으면 쓰는 빠른 길일 뿐이고 전제하지 않아요.

## 2. 원칙

1. **제품은 장애 조치를 구현하지 않아요.** 주 서버의 선출, 승격, 옛 주 서버의 격리는 PostgreSQL이 주지 않는 영역이고, 틀리면 분할 뇌(주가 둘이 되는 일)로 데이터를 잃어요. Patroni와 CloudNativePG가 이미 해요.
2. **제품은 그 위에서 틀리지 않는 규칙을 지켜요.** 아래 3~5절의 16가지 규칙이에요. 규칙은 코드와 검사 규칙과 테스트으로 지켜요.
3. **테스트하지 않은 HA는 약속하지 않아요.** 본보기 구성은 CI에서 장애 조치를 테스트한 것과 테스트하지 않은 것을 구분해 적어요(12절의 미결 참고).
4. **GPL과 AGPL 도구를 제품과 함께 배포하지 않아요.** 문서로 안내만 해요.
5. 근거는 공개된 운영 사례예요. OpenAI의 글 "Scaling PostgreSQL to power 800 million ChatGPT users"(https://openai.com/index/scaling-postgresql/)는 주 하나와 읽기 복제본 다수로 읽기를 넓히고, 쓰기를 줄이고, 무거운 질의와 재연결 폭풍을 막은 사례를 설명해요. 이 문서는 그 교훈을 우리 설계(KG마다 하나의 쓰기 순서, 읽기 중심)에 옮겨 적었어요. 규모와 조건이 달라서 수치를 그대로 쓰지 않아요.

## 3. 연결과 풀

**규칙 1. 쓰기는 주 서버로만.**
- 쓰기용 DSN은 여러 호스트를 받고 `target_session_attrs=read-write`로 주 서버만 골라요. 읽기용 DSN은 `prefer-standby`와 `load_balance_hosts=random`이에요.
- **풀을 역할마다 나눠요**: 쓰기(적용과 정의의 쓰기), API 읽기(내장 읽기와 저장한 질의), 대량 읽기(내보내기, 사람의 임의 질의). 사용자 질의의 풀은 읽기 복제본을 가리킬 수 있어요([질의 실행기와 읽기의 세 경로](query-execution.md) 2절).

**규칙 2. 역할이 바뀌는 오류에서 풀을 버려요.** SQLSTATE 25006, 57P01, 57P02, 57P03과 클래스 08을 만나면 그 풀의 연결을 모두 닫고 새로 열어요. 연결의 최대 수명은 5분에서 10분으로 낮춰요(지금 30분).

**규칙 3. 죽은 연결을 알아채요.** TCP keepalive(유휴 10초, 간격 5초, 3회)와 `TCP_USER_TIMEOUT`(30초)를 쓰고, 연결 시한(`connect_timeout`)은 기본 5초예요. 모든 DB 호출에 시한(`context`)을 걸어요. 값은 시작점이고 구현할 때 테스트으로 정한다.

**규칙 10. 재연결 폭풍을 막아요.** 연결을 만들 때 지터를 넣고 속도를 제한해서, 서버가 한꺼번에 뜨거나 장애 조치가 끝났을 때 모든 인스턴스가 동시에 연결하지 않게 해요. 서버가 장애를 자동 재시도로 가리지 않아요. 다시 시도해도 되는 오류는 힌트만 주고 호출자가 지터를 두고 다시 해요. **점검**: `인스턴스 수 × 풀의 최대 연결 수 ≤ max_connections − 예약(복제와 관리용)`. 지금 풀의 기본 최대 연결은 16이에요.

**읽기 복제본의 규칙**
- **규칙 7. 복제본에서 돌 수 있는 읽기**: 그래프 함수와 내장 읽기는 쓰기, 임시 테이블, 시퀀스 없이 순수 SQL이어야 해요. 읽기 트랜잭션은 읽기 전용 repeatable read예요. 직렬화 가능 격리는 쓰지 않아요. **CI에 복제본 테스트**을 둬서 대기 서버에서 질의 스키마 전체(뷰와 함수)를 실행해 봐요.
- **규칙 8. 복구 충돌**: 복제본 읽기가 복구와 충돌해 취소되면(40001) **한 번만** 다시 시도하거나 주 서버로 보내요. 서버 설정 점검: `max_standby_streaming_delay ≥ API 읽기의 시한 + 여유`(지금 API 읽기 30초와 기본값 30초가 같아 경계예요). 대량 읽기 복제본은 `hot_standby_feedback=on`과 긴 지연을 써요.
- **규칙 11. 읽기 경로는 주 서버에 쓰지 않아요.** 토큰 확인, 목록, 질의는 모두 읽기 전용 트랜잭션이고 복제본에서 돌 수 있어요. "마지막 접속 시각 갱신" 같은 쓰기를 읽기 경로에서 하지 않아요. 그래야 주 서버가 장애인 동안에도 읽기가 살아요. 지금 토큰 확인 경로가 쓰는지는 확인하지 못했고 구현할 때 확인한다.
- **규칙 12. 복제본 하나가 빠지는 테스트**: 읽기 복제본이 둘 이상인 구성에서 하나가 빠질 때 남은 복제본이 버티는지, 주 서버로 넘기는 읽기의 양에 **상한**이 있는지 테스트해요.

## 4. 장애 조치 때의 쓰기

**규칙 4. 커밋됐는지 모르는 경우.** 커밋 중에 연결이 끊기면 "모름"으로 분류해요. 다시 쓰기 전에 머리 행의 적용 번호와 **변경 배치의 id**로 결과를 판정해요(이미 있는 멱등 규칙과 같은 도구예요). 소스의 소스 커서를 확인하는 것과 응답의 변경 번호는 **내구화된 뒤에만** 내요.

**규칙 5. 내구성 정책.**
- 적용 트랜잭션은 `synchronous_commit=on`이에요. 대기가 둘 이상이면 서버는 `synchronous_standby_names='ANY 1 (…)'`처럼 후보가 둘 이상인 쿼럼이어야 해요.
- **대기 하나의 동기 복제로 "잃는 데이터 0"을 약속하지 않아요.** 그 대기가 죽으면 쓰기가 멈춰요. `remote_apply`는 비싸서 기본이 아니에요.
- 중요하지 않은 쓰기(하트비트, 지표, 임대 연장)는 트랜잭션마다 `SET LOCAL synchronous_commit=local`로 커밋 지연을 줄일 수 있어요(구현할 때 정한다).

**규칙 6. 세션에 남는 것을 쓰지 않아요.** 세션 advisory lock, `LISTEN`과 `NOTIFY`, 임시 테이블, `LOCAL`이 아닌 `SET`, 이름이 있는 준비된 문장을 쓰지 않아요. 검사 규칙으로 코드와 SQL에서 막아요(지금도 지켜져요). **큰 적용의 계획과 스테이징 데이터는 로그가 있는 테이블에 두고** 적용이 끝나면 지워요. UNLOGGED는 쓰지 않아요. 그래서 **장애 조치 뒤에도 큰 적용은 남은 조각부터 이어서 해요.** 파티션을 쓸지는 구현할 때 정해요. 쓰기 경로에 트랜잭션 모드의 풀러를 두지 않아요(읽기 경로에만 둘 수 있어요).

**규칙 9. "이 번호 이후" 읽기는 머리 행으로.** 복제본에서 읽을 때 `min_seq`는 그 복제본의 머리 행(`applied_seq`)이 `min_seq` 이상일 때만 읽어요. 기다릴 한도 안에서 다시 확인하고, 넘으면 주 서버로 보내거나 `stale`로 알려요. 19 이상에서만 `WAIT FOR LSN`을 빠른 길로 써요. **장애 조치로 커밋을 잃었을 수 있어요.** 그래서 `min_seq`가 새 주 서버의 `applied_seq`보다 크면 "미래 번호" 오류로 알려요(세대 규칙과 함께).

**규칙 14. 임대는 DB의 시각으로.** 임대의 만료는 앱 서버의 시계가 아니라 DB의 시각으로 판정해요. 점검 명령이 앱과 DB의 시계 차이를 보여요. 지금은 앱 시계이고 바꾸는 것은 구현할 때 정한다. 쓰기를 막는 `attempt` 규칙은 이미 있어요.

## 5. 스키마 변경, 슬롯, KG 이동

**규칙 13. 마이그레이션과 HA.**
1. 파일마다 한 트랜잭션과 트랜잭션 advisory lock(이미 있어요).
2. 인덱스는 온라인(`CREATE INDEX CONCURRENTLY`)으로 별도 단계에서 만들고, 시작할 때 **무효 인덱스를 찾아 정리**해요.
3. 대기 서버가 있을 때 DDL 전에 사전 점검(대상 테이블의 긴 질의, 복제 지연)을 해요.
4. 새 컬럼은 NULL을 허용하고, **테이블을 다시 쓰는 변경은 하지 않아요**(컬럼 타입 변경, 기본값 있는 NOT NULL 추가 등). 잠금 시한과 재시도를 둬요. 이 규칙이 새 저장의 구성 C의 이유 가운데 하나예요([새 저장의 모양](storage-shape.md) 4절).

**규칙 15. KG 이동의 경계.** 런타임 질의에 KG 사이의 조인이 없어요(이미 그래요). 장애 조치와 별개로, KG를 다른 클러스터로 옮길 수 있는 단위가 되어서 샤딩의 도피처가 돼요.

**규칙 16. 복제 슬롯은 없어야 정상이에요.** 논리 슬롯을 외부 소비자에게 내주지 않아요. 점검 명령은 슬롯이 있으면 경고하고, `wal_status`, 보유한 바이트, `max_slot_wal_keep_size`, 18의 `idle_replication_slot_timeout`을 보여요.

**OpenAI 사례에서 옮긴 운영 규칙**
- 조인이 많은 질의는 저장한 질의의 "끄기"로 바로 막아요([저장한 질의와 간선 정의](saved-queries.md) 9절).
- 긴 트랜잭션을 금지해요(유휴 트랜잭션 시한을 모든 역할에 걸어요).
- 인덱스는 표시한 속성에만 둬요.

## 6. 점검 명령 `praxium db check`

읽기 전용이고, 종료 코드와 JSON 출력이 있어요(에이전트도 읽어요). 새 기능이 아니라 [PostgreSQL 운영](postgres-operations.md)의 신호를 한 번에 보는 것이에요. 항목(괄호는 보는 곳):

1. 서버 버전(18 이상), 어느 쪽에 붙었는지(`in_hot_standby`), `transaction_read_only`, `data_checksums`, `wal_level`, `full_page_writes`.
2. 복제: `pg_stat_replication`(상태, 동기 상태, 쓰기와 반영 지연), 복제본 수와 정상 수, 타임라인, `synchronous_standby_names`와 `synchronous_commit`. **대기 하나의 동기 구성은 경고**예요.
3. 대기 서버: `max_connections` 등이 주보다 작지 않은지, `hot_standby_feedback`, `max_standby_streaming_delay`와 API 읽기 시한의 관계, 복구 충돌 횟수.
4. 슬롯(규칙 16).
5. WAL과 보관: `archive_mode`, `pg_stat_archiver`(마지막 보관 시각, 실패 횟수), `pg_wal`의 여유.
6. 백업의 나이와 마지막 복원 연습의 날짜.
7. 연결: 사용 수와 최대 수, `인스턴스 수 × 풀 크기`(규칙 10), 유휴 트랜잭션 시한, 가장 오래된 트랜잭션.
8. 위험: 트랜잭션 ID의 나이, **무효 인덱스**, **안 쓰는 인덱스**(주 서버와 복제본의 사용을 합쳐서 봐요. 쓰기 비용만 늘리는 인덱스를 찾아요), UNLOGGED 테이블의 존재(있으면 경고), 오래된 autovacuum.
9. 호스트: DSN의 호스트를 모두 접속해 보고 각각의 역할(주 또는 대기)을 보여요.
10. 서버 시계의 차이(규칙 14).
11. TLS: `sslmode`와 서버 인증서의 만료.
12. 권한: 질의 역할에서 위험한 내장 함수의 실행 권한이 거둬져 있는지(질의 실행기의 방어의 필수 부분이에요, [질의 실행기](query-execution.md) 2.2절), 역할의 권한이 설계와 같은지. 마스터 키 파일은 시크릿 저장소를 다루는 단계에서 정해요.

## 7. 배포마다 권하는 구성

| 배포 | 권하는 구성 | 제품이 내줄 것 |
|---|---|---|
| 로컬 한 대 | 제품과 PostgreSQL을 함께 띄우는 구성 파일. **HA를 약속하지 않아요.** 대기를 자동으로 띄우지 않아요. DSN은 여러 호스트를 받아요 | 점검 명령이 "단일 서버, 복제 없음"을 알려요. 시작할 때 버전과 체크섬을 확인해요. `pg_dump` 같은 논리 백업 안내 |
| 작은 운영(가상 기계) | 주와 대기와 **셋째 투표 노드**(Patroni와 etcd, 앞에 HAProxy나 VIP). **노드가 둘뿐이면 자동 장애 조치를 약속하지 않아요.** 비동기 복제와 수동 승격 절차서, `pg_rewind` 절차를 줘요. 서버 둘의 동기 복제는 "자동 강등" 또는 "비동기와 유실 수용" 가운데 고객이 골라요 | 본보기(`patroni.yml`, `haproxy.cfg`, etcd, `pg_hba.conf`), 셋째 노드의 최소 사양, 수동 승격과 옛 주 격리의 절차서 |
| 쿠버네티스 | CloudNativePG, 인스턴스 3개, 가용 영역 셋에 하나씩. 동기 복제는 `ANY 1`이고 "필수"(유실 0 우선)와 "선호"(가용성 우선)를 고객이 골라요. 읽기 풀러는 선택 | Helm 값의 예(쓰기 주소와 읽기 주소), `Cluster` 본보기(PG 18 이미지, 파라미터 프로파일), 모니터링 본보기, 복원 테스트 절차. 연산자가 관리하는 값을 제품이 덮어쓰지 않아요 |

- 배포마다 **구성도, 노드 수, 파라미터 프로파일, 장애 조치 때 사용자가 보는 증상과 시간**을 한 장에 적어요. 시간은 우리 테스트의 값으로 채우고. 공개 자료의 수치는 참고로만 적어요.
- 실제 파일은 구현할 때 만들어요. 세 배포의 본보기를 모두 내고, **각 본보기에 "CI에서 장애 조치를 테스트함"인지 "테스트하지 않음"인지 적어요.** 테스트하지 않은 것을 테스트한 것처럼 적지 않아요.

## 8. 백업과 시점 복구

- 백업과 WAL 보관은 도구가 해요. pgBackRest(MIT)를 문서에서 기본으로 안내하고, WAL-G를 대안으로 안내해요. Barman은 GPL이라 안내만 해요. CloudNativePG는 연산자의 방식을 따라요.
- 제품이 내주는 것: (1) 점검 명령이 백업의 나이와 WAL 보관의 헬스 상태을 보여요. (2) **복구 연습의 절차서와 스크립트**: 새 DB에 복원한 뒤 정의 세트의 해시와 샘플 질의의 일치를 확인해요(이름 `praxium verify-restore`는 가칭이고 구현할 때 정한다). (3) 시점 복구 뒤에 수집의 소스 커서가 뒤로 가는 일의 처리를 문서에 적어요. 첫 기본 백업 전에 복원을 테스트하라는 PostgreSQL 문서의 권고를 따라요.

## 9. 하지 않는 것

| 하지 않는 것 | 이유 |
|---|---|
| 제품이 선출과 승격과 옛 주 격리를 구현 | 분할 뇌의 위험. 도구가 해요 |
| GPL과 AGPL 도구를 함께 배포 | 라이선스 부담 |
| 19 전용 기능을 전제 | 도구 생태계가 18까지 명시해요 |
| 읽기 복제본에 임시 테이블, 시퀀스, 쓰기가 필요한 함수를 올림 | 대기 서버에서 못 돌아요 |
| 대기 하나의 동기 복제로 유실 0을 약속 | 대기가 죽으면 쓰기가 멈춰요 |
| `remote_apply`를 기본으로 | 비싸요 |
| 서버의 자동 재시도로 장애를 가림 | 재시도 폭풍 |
| 읽기 경로에서 주 서버에 씀 | 주 장애 때 읽기도 죽어요 |
| 테스트 없이 HA를 약속 | 테스트한 본보기만 내요 |
| UNLOGGED 테이블을 씀 | 장애 조치 때 사라지고 큰 적용을 이어 갈 수 없어요 |
| 쓰기 경로에 트랜잭션 모드의 풀러를 둠 | 세션 기능이 깨져요 |

## 10. 테스트

- 주 서버를 죽이고 쓰기가 새 주 서버로 이어지는지, 진행 중이던 적용이 멱등으로 끝나는지(규칙 2, 4).
- 복제본 하나를 죽이고 남은 복제본과 주 서버의 부하(규칙 12).
- 대기 서버에서 질의 스키마 전체를 실행하는 CI 테스트(규칙 7).
- 큰 적용 도중의 장애 조치: 남은 조각부터 적용이 이어지는지(규칙 6).
- 시점 복구 뒤 복원 연습(8절).
- 이 테스트들은 구성 파일 본보기와 같은 단계에서 만들어요([ADR-0080의 순서](adr/0080-redesign-storage-and-queries-on-one-postgresql.md)의 6단계).

## 11. 알려진 한계

- 드라이버(`lib/pq`)가 장애 조치 때 실제로 어떻게 움직이는지는 소스로만 확인했고 테스트하지 않았어요. 풀 폐기(규칙 2)의 오류 목록은 테스트으로 확정해요.
- 규칙 3의 값(keepalive, 시한)은 시작점이에요.
- CloudNativePG와 Patroni가 PostgreSQL 19를 명시하는지 확인하지 못했어요. 그래서 기준을 18로 해요.

## 12. 미결 사항

- 규칙 5의 `SET LOCAL synchronous_commit=local` 적용 대상.
- 규칙 14: 임대 만료의 시계를 DB 시각으로 옮길지.
- `praxium verify-restore`의 이름과 범위.
- 본보기 구성을 CI에서 띄우는 방법(쿠버네티스는 kind로 가능한지 확인한다).
- 규칙 11: 토큰 확인 경로의 쓰기 여부.
- 시점 복구 뒤 수집의 소스 커서 처리.
