# 기본값 표

이 문서는 설계 문서들이 "가정"이라고만 적던 숫자를 제품에 포함되는 **기본값**으로 정해 한곳에 둔 거예요. 모두 설정이에요(버전 관리되는 설정, ADR-0017). 클로즈드 베타에서 합성 세계와 실제 소스로 측정해서 수정해요. 다른 문서는 값을 반복해서 적을 수 있지만 이 문서를 가리켜요. 표에 없는 숫자는 그대로 "가정"이에요.

## 1. 단계와 규모

단계는 알파 1(뼈대와 최소 E2E 경로, 임시 콘솔), 알파 2(범위 확장), 클로즈드 베타, 오픈 베타(프로덕션에 나갈 수 있는 수준), 정식이에요. 설계 문서의 "언제 만드나"는 이 단계로 표현해요.

| 단계 | 규모와 구성 |
|---|---|
| 알파 1, 알파 2 | 객체와 링크 100만 개 수준에서 모든 기능이 실행돼요. PostgreSQL 하나와 실행 파일 하나(역할 4종을 한 프로세스에)로 충분해요 |
| 클로즈드 베타 | 한 KG에 수천만 개(설계의 여유는 수억, 엔진은 1억까지 측정했어요). 이때 측정해요(가상의 3천만 객체와 분포 프로파일로 조정한 생성기, 영향 범위의 응답, 적용 속도, 프로젝션의 메모리, 저장 용량 증가) |
| 오픈 베타 | 프로덕션에 나갈 수 있는 수준: 시크릿과 암호화, 자신의 관측성과 운영, 에이전트 규모의 정의 버전 관리, 스토리지의 운영 수준이 구현돼 있어요 |

구조는 처음부터 수천만 개를 고려해 설계해요(변경 시퀀스, 현재 상태와 이력의 분리, 프로젝션과 질의 엔진의 경계, 포트). 알파에서 줄이는 것은 구조가 아니라 어댑터의 수와 배포 형태예요. 요구사항의 숫자(영향 범위 1초와 수 초, 수천만 개)는 그대로 요구이고 클로즈드 베타에서 측정해서 확인해요.

## 2. 스토리지와 로그: 무엇을 언제 만드나

| 구성 요소 | 알파 | 클로즈드 베타 | 방식 |
|---|---|---|---|
| 단일 진실 공급원(정의, KG, 적용된 변경 로그) | PostgreSQL | PostgreSQL | |
| 수집 변경 로그 | PostgreSQL 어댑터 | 메시지 로그 스토리지 어댑터를 추가해요 | Kafka 프로토콜을 지원하는 것. 프로토콜에 맞추고 특정 배포판에 종속되지 않아요. 라이선스는 허용 목록 |
| 스트림 소스로서의 메시지 토픽 | 만들어요(스트림의 첫 어댑터) | | 같은 프로토콜 |
| 콜드 스토리지 | 없음(보존 기한 안에서 PostgreSQL에) | 만들어요 | S3 프로토콜을 지원하는 오브젝트 스토리지와 컬럼형 오픈 파일 형식 |
| 분석용 스토리지 | 없음 | 측정해서 필요하면 | 그때 정해요 |
| 외부로 보내는 변경 알림 | 번호로 조회하는 API와 이벤트 경로 | 메시지 토픽으로 내보내기를 추가해요 | 같은 프로토콜 |

결정은 "프로토콜에 맞춘다"예요. 제품 이름을 고르는 것이 아니라 어느 프로토콜의 어댑터를 만드는지를 정해요.

## 3. 수집

| 항목 | 기본값 |
|---|---|
| 소스당 동시 요청 | 1 |
| 소스당 요청 속도 | 초당 5 |
| 재시도 | 3회, 백오프 간격을 늘려 가며 |
| 인증 실패 | 즉시 중단하고 알려요(재시도하지 않아요) |
| 연속 실패하면 일정을 중단 | 5회 |
| 배치: 한 번에 사라지면 중단 | (10% 이상이면서 5건 이상) 또는 500건 이상 |
| 배치: 수집한 레코드 수가 지난번보다 줄면 누락으로 간주 | 30% 이상 |
| 관측되지 않아 폐기 처리 | 온전한 수집 3회 연속, 그리고 처음 관측되지 않은 시점부터 24시간 이상 |
| 스트림: 보류 임계값 | 5분 동안 그 피드의 객체의 5% 이상(그리고 50건 이상)이 삭제되거나, 수신한 스키마가 바뀜 |
| 오래됨 판정 | 기대 주기의 2배. 스트림은 지연 5분 |
| 연결 대상이 없는 값의 대기 | 24시간 |
| 시계 이벤트의 간격 | 1분 |
| 스트림에서 KG 버전을 확정하는 주기 | 1시간(변경이 있을 때) |
| 변경 배치의 크기 | 1만 행 또는 2초 가운데 먼저 도달한 쪽 |
| 푸시 수집의 "한 번만 반영"(멱등성 보장)이 유지되는 중복 제거 기간 | 7일(소스마다 설정) |
| 지정 재수집 | 주체마다 분당 60건. 일정에는 소스 속도 상한의 절반 이상을 남겨요 |
| 완전성 선언이 자동으로 중단되는 임계값 | 기대 수와 수집한 수가 1% 넘게 불일치한 수집이 연속 2회 |

## 4. 보관

| 항목 | 기본값 |
|---|---|
| 원본 레코드의 보관 | 90일(종료된 구간에만 적용해요. 그 이후는 콜드 스토리지로. 없으면 삭제) |
| `volatile` 값만 제공하는 스트림의 원본 라인 보관 | 3일 |
| 경량 변경 레코드 보관 | 7일 |
| 폐기된 객체가 옛 ID로 복원되는 기간(강한 키로 일치하지 않았을 때) | 30일 |
| 과거 KG 이력의 보관 | 1년. 고정된 버전은 삭제하지 않아요 |
| 지표의 보관 | 고해상도 값 30일, 다운샘플링한 값 13개월 |
| 감사 로그의 보관 | 3년 |

## 5. 질의, 권한, 정의

| 항목 | 기본값 |
|---|---|
| 권한 정보 캐시의 나이 상한 / 계정을 비활성화하거나 토큰을 회수한 것이 전파되는 시간 | 15분 / 30초 |
| `query_answers`(질의 응답에 의존하는 질의)를 다시 평가하는 주기 | 15분 |
| 프로젝션을 통째로 다시 구축하는 임계값 | 바뀐 객체와 링크가 KG의 20% |
| 청크(프로젝션과 엔진)의 단위와 크기 | 위치의 하위 트리, 노드 100만까지 |
| 오버레이를 컴팩션하는 시점 | 청크의 5%를 넘거나 10분 |
| 영향 범위의 최소 절단 크기 | 2 |
| 역량 질문 패턴의 깊이 / 홉당 분기 수(fan-out) | 8홉 / 1천 |
| 사전 정의 질의의 페이지 크기 | 100(최대 1천) |
| 긴급 리버트를 할 수 있는 기간 / 사후 검토의 기한 | 7일 / 3일 |
| 메이저 버전(API)의 지원 중단 기간 | 12개월 |

## 6. 값이 아직 정해지지 않은 항목
아래는 설계는 정해졌지만 값은 정해지지 않은 것이에요. 값을 지어내지 않아요. 구현하는 변경이 측정해서 정하고 이 표를 수정해요(가정). 노출이 전파되는 깊이는 설정이 없어요(끝까지 전파돼요).

| 항목 | 위치 |
|---|---|
| 주체당 열린 브랜치 수, 큐에 대기 중인 제안 수, 하루 제안 수, 드라이 런의 계산 예산, 트라이얼 수집의 저장량, 활동 없는 초안의 자동 종료 기한 | definitions-at-agent-scale.md 9절 |
| 자동 병합의 "차이가 작은 한도", 최근 리버트 비율의 기준 | 같은 문서 6절 |
| 쿼리(statement) 타임아웃, 잠금 대기, 유휴 시간의 한도(역할마다), 쿼럼, `max_staleness`(소스에서 관측한 값이 얼마나 오래돼도 되는지) | postgres-operations.md |
| 연결된 메시지 로그 스토리지가 끊겼을 때 수집기가 버퍼링하는 한도 | postgres-operations.md |
| 푸시 수집의 1회 전송량 | ingestion-extensions.md |
| 구조 질의의 인덱스 크기 추정(가상의 100만 객체에서 측정할 것) | competency-questions.md |

## 7. 사용 방법

- 문서에서는 "기본값(설정)"이라고 적고, 클로즈드 베타에서 측정해서 수정한다고 밝혀요.
- 이 표의 값을 바꾸면 이 문서를 먼저 수정하고, 값을 반복해서 적은 문서를 일치시켜요.
