# 수집의 규모 설계

수집을 한 KG에 객체와 링크가 수천만 개인 규모로 다시 설계해요. 결정은 [ADR-0086](adr/0086-redesign-ingestion-for-tens-of-millions-of-objects.md)에 있어요. **이 문서는 대부분 아직 구현하지 않은 설계(예정)예요. 5절의 테이블은 스키마 계획에 들어갔어요([ADR-0095](adr/0095-ingestion-tables-in-the-schema-plan.md)). 1단계(수신)와 실행 기록의 최소한, 소스를 KG에 붙이고 떼는 일은 구현했어요([ADR-0098](adr/0098-receiving-step-and-run-ledger-in-adapter-pgingest.md)). 2단계부터는 아직 없어요.** 지금 구현은 [수집 설계](ingestion.md)와 [파이프라인 설계](pipeline.md)가 설명하는 코드이고, 새 흐름은 그 옆에 지어요. 식별과 영향 집합, 적용, 유닛, 범위, 원형 측정은 [식별과 영향 집합, 적용, 범위](ingestion-at-scale-identity.md)에 있어요. 예시의 이름과 숫자는 지어낸 것이에요. **시작 값**은 원형이나 어림에서 정한 값이고 측정으로 고쳐요.

## 1. 목적과 다루는 질문

- 수집의 메모리를 배치의 크기와 무관하게 만들려면 단계를 어떻게 나누나.
- 영향받은 것만 다시 계산해도 전체를 다시 계산한 결과와 같다고 어떻게 보장하나.
- 서버가 단계 중간에 죽어도 다른 서버가 어디서 이어 가나.
- 영구 테이블에 무엇을 두고 무엇을 준비 테이블에 두나.

조건은 이래요. 한 KG에 객체와 링크 수천만 개(구조는 처음부터), HA(상태는 모두 DB에 있고 서버가 여럿이며 어느 서버든 이어 가요), 관리형 DB 없음, 새 의존성 없음, 뜻의 구현은 한 곳, 검사를 통과시키려고 규칙을 고치지 않아요.

## 2. 지금 무엇이 문제인가

지금 코드와 문서를 읽어 확인한 사실이에요.

| 자리 | 지금 |
|---|---|
| 읽기와 계산 | 한 배치 전체가 메모리에 올라요. 파일 전체, 소스의 상태 전체, 열려 있는 모든 레코드를 실행마다 다시 매핑한 결과예요. 천장은 파일 20MB, 데이터셋 20만 행이에요 |
| 적용 | 후보 전체를 정렬하고, 청크마다 전체 맵을 다시 만들고, 행을 하나씩 읽어요. 변동 값, 식별자, 식별 이벤트가 마지막 청크에 몰려요. 관계 검사가 한 건 어긋나면 배치 전체를 거절해요 |
| 식별 | 수집은 문맥(부모) 식별 키를 만들지 못해요. 표준 타입 168개 가운데 115개가 들어오지 못해요(문맥 키만 가진 타입 72개, 문맥 키를 다른 키와 함께 가진 타입 43개) |
| 상태 | 적용과 상태 저장이 따로 쓰여요 |
| 문서 | 수집 서비스, 실행 기록, 안전장치, 여러 소스의 합침은 문서에만 있어요 |

## 3. 원칙과 불변식

| 번호 | 내용 |
|---|---|
| P1 경로는 하나 | 수백 행도 3천만 행도 새 흐름의 같은 코드로 가요. 옛 경로(파일 상태 저장소 위의 `ingest run -data-dir`와 `local`의 수집)는 새 흐름의 상태 기계와 정리를 짓는 변경에서 함께 지워요(5단계를 기다리지 않아요). 그때부터 수집은 PostgreSQL이 있어야 돌고, 그 전까지는 이 원칙이 새 흐름 안에서만 참이에요 |
| P2 메모리는 크기와 무관 | 서버는 페이지 하나만 들어요. 페이지는 행 1만 개 또는 8MB 가운데 먼저 닿는 쪽이에요(시작 값). 다시 계산의 페이지는 객체 수가 아니라 **기여 레코드의 줄 수**로 잘라요. 한 객체에 기여가 아주 많을 수 있어서예요 |
| P3 행은 Go, 집합은 SQL | Go: 파싱, 정제, 자연 키, 식별 키와 끝 키 만들기, 값의 변환과 검사, 이긴 값 고르기, 내용 해시와 HMAC, 객체와 링크의 id, 행 합. SQL: 배치 안의 중복, 원본의 차이, 식별(찾기와 묶기), 끝 풀기, 차수, 차이, 적용. 정규 인코딩을 SQL로 다시 만들지 않아요. 문맥이 없는 키의 후보 id는 수신할 때 Go가 키마다 미리 계산해 싣고, 돌려 넣는 것은 문맥 키의 자식과 링크 id와 행 합뿐이에요 |
| P4 고칠 경로가 있다 | 전체 계산(영향 집합 = 그 KG의 모든 열린 레코드)은 같은 코드의 한 모드예요. 평소의 실행은 영향받은 것만 견주므로 상태의 어긋남을 스스로 찾지 못해요. 맞추는 것은 레코드 참조의 미해결 목록이고, 점검하는 것은 "전체 계산을 쓰지 않고 돌려 차이가 0줄인가"예요 |
| P5 원자성은 머리 행 | 적용이 끝났다는 표시는 KG의 머리 행의 마지막 적용 id예요. 따로 싣는 완료 행은 두지 않아요. 큰 상태는 그 뒤에 멱등으로 조각내어 반영해요(정리) |
| I1 | 결과(KG와 레코드의 문제)는 (실행 전의 식별 색인, 이번 계산이 보는 열린 레코드의 집합, 정의)의 함수예요. 레코드의 순서, 페이지의 경계, 피드와 데이터셋의 순서는 결과에 들지 않아요. 실행을 어떻게 나눴는가는 들 수 있어요(식별 색인이 이력이에요. [KG 모델](kg-model.md) 10.5절). 내용까지 달라지는 것은 "지난 실행들이 따로 만든 두 객체를 나중의 행이 잇는" 경우뿐이고 병합이 있어야 풀려요 |
| I2 | 영향받은 것만 다시 계산한 결과는 같은 상태에서 전체 계산한 결과와 같아요 |
| I3 | 준비 테이블은 넣기만 해요(`UPDATE` 없음). 비우기는 `TRUNCATE`예요 |
| I4 | 한 트랜잭션은 페이지 하나, 구간 하나, 청크 하나를 넘지 않아요. 3천만 행을 한 문장으로 돌리지 않아요 |

테스트로 고정하는 것은 이래요. I2는 "무작위의 변경 열 뒤 전체 계산의 차이가 0줄이고 문제도 같다", I1은 "행, 페이지 크기, 데이터셋의 순서를 뒤섞어도 그래프 해시와 객체 id가 같다", 그리고 "한 번에 넣은 것과 나눠 넣은 것의 내용이 같다"예요. 마지막의 한 경우(I1의 예외)는 알려진 한계로 따로 고정해요.

## 4. 흐름

실행 하나는 소스 하나의 수집이고 계산의 범위는 KG예요. 단계는 `receiving`, `computing`, (`awaiting_confirmation`), `applying`, `volatile`, `settling`이고 끝은 `succeeded`, `failed`, `canceled`, `discarded`예요. 실행 기록 `sync_run`의 한 행이 단계와 이어 갈 자리를 가져요.

**관문은 DB의 부분 유일 인덱스 둘이에요.** 같은 소스에 끝나지 않은 실행은 하나예요. 같은 KG에 `computing`, `applying`, `volatile`, `settling`인 실행은 하나예요. 리스는 DB의 시각으로 판단하고, 그 실행을 어느 서버가 하는지만 정해요. 수신은 소스끼리 나란히 돌아요.

| 단계 | 누가 무엇을 해요 | 한 트랜잭션 | 죽으면 |
|---|---|---|---|
| 1 수신 | 어댑터가 페이지의 흐름을 줘요. 페이지마다 Go가 파싱하고, 뿌리 데이터셋에서 걸러졌는지 표시하고, 자연 키와 원본 해시를 만들어요. 그 페이지의 키로 `raw_record`의 해시와 운명을 배치로 찾아(인덱스만 읽어요) 견줘요. `stage_record`에 **모든 행**의 (페이지, 번호, 키, 자리, 변화)를, **새로 왔거나 바뀐 행**만 필드를 `COPY`해요. 바뀐 행은 식별 키(후보 id 포함), 끝 키, 식별자의 주장도 함께 싣고요 | 페이지 하나(와 페이지 번호) | 어댑터가 토큰으로 이어 줄 수 있으면 다음 페이지부터, 아니면 그 데이터셋의 파티션을 비우고 0페이지부터. 처음 구현은 언제나 0페이지부터예요. **구현했어요**: `adapter.pgingest`의 `Receive`가 소스의 파티션을 `TRUNCATE`하고 페이지마다 트랜잭션 하나로 넣어요. 걸러진 행의 키·끝 키·주장은 `held` 열이 가려내고, 페이지의 문제는 행 번호 -1의 행에 둬요(ADR-0098 결정 5) |
| 2 원본 차이 | SQL이 배치 안의 중복(나중 행이 이기고 앞 행은 `duplicate_key`), 새로 옴, 바뀜, 그대로, 안 보임, 돌아옴, **기다림이 끝남**(안 보임과 걸러짐 각각)을 구해요. 안 보임은 완전한 전체 수집에서만 세요. **새 횟수와 처음 시각을 여기서 계산해 `calc_wait`에 적어요**(정리는 옮기기만 해요). 불완전한 수집의 데이터셋은 통째로 빼요(바뀐 행도 반영하지 않아요) | 구간 하나(키 해시의 앞자리로 버킷을 나눠요. 같은 키는 같은 버킷이에요) | 그 구간부터 |
| 3 영향 집합의 출발과 식별 | 출발 레코드([식별과 영향 집합](ingestion-at-scale-identity.md) 3절)를 `calc_record`에 넣어요. 미해결 레코드는 그대로인 레코드이므로 Go가 `raw_record`의 필드에서 키를 다시 만들어 실어요. 식별은 [같은 문서](ingestion-at-scale-identity.md) 2절 | 구간, 라운드, 회 하나 | 그 라운드의 처음부터(결과 테이블을 그 라운드만 비우고) |
| 4 다시 계산 | 영향받은 객체의 번호 순으로 페이지마다, 그 객체들에 기여하는 **모든 열린 레코드**(영구 테이블과 이번 준비 테이블. 다른 소스의 레코드는 그 소스의 매핑으로)를 읽어 Go가 값을 매핑하고, 이긴 값을 고르고(순위, 나중, 피드 순), 검사하고, 문서와 내용 해시와 행 합을 만들어 `stage_object`에 넣어요. 기여하는 살아 있는 레코드가 없고 폐기할 수 있는 객체는 폐기 후보예요. 링크는 끝 풀기와 차수를 SQL이, 링크 id와 속성과 해시를 Go가 해서 `stage_link`에 넣어요. 변동 값, 식별자의 주장, 레코드의 문제도 계산용 테이블에 넣어요 | 페이지 하나 | 그 페이지부터 |
| 5 차이 | `stage_object`, `stage_link`와 타입 테이블, `link`를 번호와 해시로 견줘 `ingest_diff`를 만들어요. 격리([식별과 영향 집합](ingestion-at-scale-identity.md) 4절)가 어긋난 행을 빼고 문제로 적어요. 순서와 청크 번호를 **저장해요**. 타입별 집계(대량 소실의 판단)와 변경 지문도 내요 | 구간 하나 | 그 구간부터 |
| 6 확인 뒤 적용 | **자리만 둬요(구현은 뒤).** 여기서 KG의 관문(계산과 적용 단계의 실행 하나)을 놓고 멈춰요(준비 행은 한도 1시간). 확인하면 KG의 관문을 다시 얻고 3단계(식별)부터 다시 계산해 지문이 같을 때만 적용해요 | | 시한 뒤 버려요 |
| 7 적용 | `ingest_diff`의 청크 번호 하나씩 변경 번호 하나로 적용해요. 첫 청크가 커밋되면 차이를 얼려서, 이어받은 서버는 다시 계산하지 않아요. 바뀌는 것이 없으면 적용을 건너뛰어요. 저장의 규칙은 새 KG 저장의 다음 결정 기록이 정해요([식별과 영향 집합](ingestion-at-scale-identity.md) 5절) | 청크 하나 | 머리 행의 적용 id와 다음 청크 번호로 남은 청크부터. 머리가 닫혀 있고 마지막 적용 id가 이 실행의 것이면 다음 단계로 |
| 8 변동 값 | 읽기 워터마크가 오른 뒤, 계산용 테이블의 변동 값을 구간으로 나눠 제자리에 써요. 값, 등급, 근거가 같으면 쓰지 않아서 멱등이에요. 이 단계부터는 포기도 취소도 없어요 | 구간 하나 | 그 구간부터 |
| 9 정리 | ① 확정(멱등) ② `raw_record` ③ `record_wait` ④ `record_ref`와 `record_problem` ⑤ `source_state`(캡처 해시, 선언의 리비전) ⑥ 준비 테이블 `TRUNCATE` ⑦ 통계 갱신 ⑧ 실행 기록을 끝으로. ②~④는 구간마다 "준비 테이블의 값으로 덮어쓰기"라서 같은 값을 다시 써도 같아요 | 구간 하나 | 그 일의 그 구간부터. 끝나기 전에는 그 KG의 계산이 막혀요 |

- **포기**(적용 전이나 청크 사이): KG는 지금의 포기(읽기 워터마크 뒤를 변경 번호마다 거꾸로)로 되돌리고, 영구 상태는 손대지 않았으므로 준비 테이블만 비워요.
- **정리를 버림**은 운영 액션이고 처음부터 있어야 해요. 정리가 막힌 실행 하나가 그 KG의 모든 수집을 막기 때문이에요. 실행을 `discarded`로 두고, 준비 테이블을 비우고, 그 소스에 **"전체 다시 수신"** 표시를 해요. 다음 실행은 그 소스의 모든 행을 필드와 함께 수신하고 그 KG를 전체 계산해요. 준비 테이블만 버리고 다시 계산하면 옛 원본 레코드로 계산해 방금 적용한 변화를 되돌리므로, 둘은 언제나 함께 해요.
- KG를 과거로 복원하면(세대가 올라요) 그 KG의 소스들에 "전체 계산" 표시를 해요. 매핑이나 소스 정의가 바뀌어도 그 KG의 계산 전체가 "전체"예요([수집 서비스](ingestion-service.md) 4.1절의 규칙과 이어져요).
- **취소**가 닿는 자리는 수신의 페이지 사이, 계산의 구간 사이, 청크 사이예요(청크 사이는 포기로 가요). `volatile`과 `settling`에서는 끝까지 가요.
- **리스**(시작 값): 실행의 리스는 60초이고 페이지, 구간, 청크 사이마다 갱신해요. 구간 하나가 리스의 3분의 1(20초)을 넘지 않게 구간의 크기를 잡아요. 넘겨받는 것은 만료 뒤(최대 60초)예요. 늦게 깬 서버의 쓰기는 시도 번호가 막아요(KG 쪽은 지금의 `guard`, 수집 쪽은 `sync_run`의 시도 번호를 조건으로 건 갱신).

## 5. 테이블

이름의 접두어 `stage_`, `calc_`와 `ingest_diff`는 스키마 관리기가 아는 이름으로 예약돼 있어요([ADR-0085](adr/0085-new-kg-storage-implementation-decisions-and-the-schema-plan-unit.md) 결정 17). 원본 레코드와 수집 상태를 KG의 저장 스키마에 두는 것은 [새 저장의 모양](storage-shape.md) 3.2절의 "수집 상태는 공용"이라는 문장과 달라요. 같은 문장의 원칙(행 수에 비례하는 테이블은 KG의 스키마에)을 따른 것이고 ADR-0086이 고쳐요.

### 5.1 KG의 저장 스키마: 영구

| 테이블 | 컬럼 | 키와 인덱스 | 누가 언제 써요 |
|---|---|---|---|
| `object_key` (식별 색인) | `type_no`, `ctx_no`(부모의 `obj_no`. 없으면 0), `sig_hash`(16바이트), `obj_no`, `bound_seq`(묶인 변경 번호), `sig`(원문. 진단용이고 크면 빼요) | 기본키 (`type_no`, `ctx_no`, `sig_hash`). 인덱스 (`obj_no`) | 적용의 청크. 한 번 묶인 키는 다른 객체로 옮기지 않아요. **포기는 읽기 워터마크 뒤의 줄을 지우고 과거로의 복원은 지우지 않아요**(식별 이력은 되감지 않아요) |
| 등록부 `object`의 `first_key` | 처음 본 키(id를 낳은 키) | | 적용의 청크. 이름의 대비값에 써요 |
| `raw_record` | `src_no`, `dataset_no`, `key`, `raw_hash`(32바이트), `fields`(선언한 컬럼의 순서. 이름을 줄마다 되풀이하지 않아요), `decl_rev`, `opened_seq`(열린 실행의 번호. KG 안에서 하나로 오르는 번호이고 이긴 값의 "나중"이에요), `fate`(쓰임, 문제, 걸러짐, 안 쓰임) | 기본키 (`src_no`, `dataset_no`, `key`). 해시와 운명을 인덱스에 얹어요 | 정리 ②. 닫힌 구간의 이력은 두지 않아요(뒤로). 원본의 평문이라서 질의 스키마와 질의 역할에 보이지 않아요 |
| `record_wait` | `src_no`, `dataset_no`, `key`, `kind`(안 보임, 걸러짐), `runs`, `first_at` | 기본키에 `kind`를 넣어요(한 레코드가 둘 다일 수 있어요) | 정리 ③. 보이는 행에는 줄이 없어요 |
| `record_ref` (**레코드가 낸 찾기 키**) | `src_no`, `dataset_no`, `key`, `role`, `def_no`, `sub`, `lookup_hash`, `target_no`(NULL이면 미해결), `state`(해결, 미해결, 진 주장, 걸러짐), `retirable` | 기본키 (`src_no`, `dataset_no`, `key`, `role`, `def_no`, `sub`). 인덱스 ① (`target_no`) `role`이 식별인 줄만: 객체에서 기여 레코드로 ② (`role`, `def_no`, `lookup_hash`): 끝 키와 주장으로 찾기 ③ `state`가 해결이 아닌 줄의 부분 인덱스: 미해결 목록 | 정리 ④ |
| `record_problem` | `src_no`, `dataset_no`, `key`, `def_no`, `field`, `kind`, `reason` | 인덱스 (`src_no`, `dataset_no`, `key`) | 정리 ④: 다시 계산한 레코드의 문제를 갈아 끼워요. 줄과 셀의 자리는 두지 않아요. 파일 맨 위에 한 줄이 끼면 모든 자리가 바뀌므로 이번 준비 행에서 읽어요 |

`record_problem`의 `field`는 어느 필드가 문제인지예요. 매핑을 고치는 사람이 보는 것이 이것이고, `kind`는 고정 목록이에요.

`record_ref`의 역할은 이래요.

| `role` | `def_no` | `lookup_hash` | `target_no` | 미해결과 진 주장이 뜻하는 것 |
|---|---|---|---|---|
| 식별 | 피드 | 쓰지 않아요(키는 다시 볼 때 필드에서 다시 만들어요) | 그 행의 객체 | 고아 값, 부모 없음, 식별 충돌로 격리, 걸러졌으나 객체 없음 |
| 링크의 From 끝 | 링크 정의(문맥의 선언이 만든 링크는 그 피드의 선언) | 끝 키의 해시 | 만든 링크의 `link_no` | 대상 없음, 대상 모호, 차수에서 지연(진 주장), 끝이 폐기됨 |
| 링크의 To 끝 | 링크 정의 | 끝 키의 해시 | 그 행의 객체 | 식별의 줄을 따라요 |
| 식별자의 주장 | 체계(`sub`은 피드) | 값의 해시 | 주장하는 객체 | 진 주장 |

크기는 어림이에요. 3천만 객체와 5천만 링크에서 `record_ref`가 1.2억~1.5억 줄, 10GB 남짓에 인덱스가 더해져요. 원형은 7.5만 대에서 `record_ref` 91.5MB, `link` 73.6MB, `object_key` 49.7MB, `raw_record` 47.9MB를 쟀고(객체 약 15만 개) 객체당 `object_key`가 약 320바이트였어요. 이 값으로 규모의 크기를 정하지는 못했어요.

### 5.2 KG의 저장 스키마: 준비(로그 있는 테이블)

- **수신용: 소스마다의 파티션.** 소스를 KG에 붙일 때 만들어요(실행 중에 DDL을 하지 않아요). 소스의 끝나지 않은 실행은 하나뿐이라서 파티션을 통째로 `TRUNCATE`해요. `stage_record`(데이터셋, 페이지, 번호, 키, 걸러졌는지, 변화, 원본 해시, 필드, 문제)는 "그대로"인 행의 해시와 필드가 NULL이에요. `stage_key`(피드, 키 순서, 타입, 서명 해시, 후보 참조, 부모를 찾는 키), `stage_end`(링크 정의, 방향, 끝 키의 해시), `stage_claim`(체계, 피드, 값의 해시, 값)이 따라와요. 세 테이블은 걸러진 행의 것을 가려내는 `held`(참이면 걸러진 행)를 가져요(생성기 버전 4, ADR-0098).
- **계산용: KG마다 한 벌.** 한 번에 한 실행이므로 `run_id`가 없어요. 계산을 시작할 때 `TRUNCATE`해요. `calc_record`(이번에 다시 보는 레코드), `calc_wait`, `calc_key`와 `calc_end`와 `calc_claim`(그대로인 레코드에서 다시 만든 키), `calc_bind`(행에서 객체 번호, 새것인가, 라운드), `calc_newkey`(새로 묶을 키), `stage_object`(번호, `ref`, 타입, 이름, 문서, 내용 해시, 행 합, `first_key`), `stage_link`, `stage_volatile`, `stage_ident`, `calc_problem`, `calc_ref`(새 `record_ref`의 줄), `ingest_diff`예요.
- `ingest_diff`(순서, 청크 번호, 종류, 타입 번호, 번호, `ref`, 변화, 옛 해시, 새 해시)의 종류는 객체, 키, 링크, 식별자예요(적용이 쓰는 순서이고 종류의 번호가 그 순서예요). 순서는 (종류, 타입 번호, id)이고 청크 번호는 저장된 컬럼이에요. 키 줄은 묶는 키의 `ctx_no`와 `sig_hash`를 함께 가져요. 이것이 미리 보기의 목록, 변경 지문, 대량 소실의 판단, 청크의 목록이에요.
- 이 테이블들의 이름과 컬럼, 소스의 파티션을 만들고 떼는 문장, 입력 다이제스트의 줄의 바이트 배치는 `adapter.pgschema`가 한 곳에서 줘요(ADR-0095). 준비 테이블은 로그 있는 테이블이고 `calc_dropped`(한 실행에서 충돌로 버린 키)와 `calc_object`(다시 계산할 객체의 목록)가 위의 목록에 더 있어요.

### 5.3 공용 스키마

- `sync_run`: `run_no`(시퀀스. `opened_seq`로 써요), KG, 소스, 종류(전체 수집과 뒤의 증분과 스트림의 자리), 방아쇠, 적용 방식, 단계, 이어 갈 자리(데이터셋과 페이지와 토큰, 계산의 일과 구간, 변동 값의 구간, 정리의 일과 구간), 건수, 적용 id, 정의 세트, 소유자와 시도 번호와 리스, 시각, 끝난 이유(설정의 문제, 일시적인 문제, 제품의 문제 세 분류예요). 부분 유일 인덱스가 둘이에요(4절: `sync_run_one_open_per_source`, `sync_run_one_working_per_kg`). 공용 테이블은 마이그레이션 `0006`이 만들어요.
- `source_state`: 소스의 `src_no`(DB 전체에서 하나뿐인 번호), KG, "전체 다시 수신"과 "전체 계산" 표시(새 소스는 둘 다 켜져 있어요), 마지막으로 적용한 정의 세트. `source_dataset`: `dataset_no`, 마지막 완전한 수집의 **캡처 해시**와 선언의 리비전(같은 바이트의 지름길의 자리), 커서(증분과 스트림의 자리).
- 옮기지 않는 것은 `Closed`, `IngestSeq`, `ObjectInfo.Type`이에요(읽는 곳이 없어요).

## 6. 알려진 한계와 가정

- 원형은 7.5만 대까지 쟀고 더 큰 규모는 재지 못했어요. 3천만의 수치는 어림이에요([식별과 영향 집합, 적용, 범위](ingestion-at-scale-identity.md) 8절).
- 한 KG에 소스가 수백 개까지를 가정해요(소스마다의 파티션). 그보다 많은 경우는 뒤로 둬요. 소스마다 파티션이 다섯이라, KG를 지울 때 소스가 붙은 채로 한 트랜잭션에 지우면 소스 하나에 잠금이 약 68개 들어요. 그래서 소스를 하나씩 먼저 떼고 지워요(ADR-0095의 측정). `DeleteKG`가 그렇게 해요(ADR-0098, 소스 30개의 KG 삭제를 테스트가 지켜요).
- 자식의 소스를 부모의 소스보다 먼저 넣으면 다음 실행이 커요(미해결 참조 전부가 출발 레코드예요). 받아들여요.
