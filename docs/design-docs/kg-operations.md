# KG 운영

KG를 짓는 것(받기)과 쓰는 것(묻기) 사이에서 날마다 일어나는 일을 다뤄요. 얼마나 믿을 만한지 보이고, 풀지 못한 것을 규칙으로 풀고, 낡은 것을 숨기지 않고, 무엇이 죽어도 묻기는 멈추지 않게 하는 설계예요. 숫자는 모두 재지 않은 가정이에요(11절).

## 1. 무엇에 답하나

| 쟁점 | 답 |
|---|---|
| 이 KG를 믿어도 되나 | 품질 지표를 버전마다 남겨 숫자로 보여요(3절) |
| 풀지 못한 것은 어디로 가나 | 문제 목록으로 가고, 맡은 도메인이 규칙을 고쳐 풀어요(4절) |
| 이 답은 얼마나 낡았나 | 소스의 마지막 온전한 수집에서 재서 답에 붙여요(5절) |
| 무엇이 죽으면 무엇이 멈추나 | 기능마다 등급을 정했어요. 묻기는 멈추지 않아요(6절) |
| 동기화가 실패하면 | 마지막 정상 버전을 지키고 일정을 쉬게 하고 알려요(7절) |
| 넘겨받은 쟁점 "운영 경로가 되면 멈추면 안 된다" | 현실을 바꾸는 길이 프락시움에 없으니 멈추면 안 되는 것은 묻기예요. 맡김과 조치의 등급은 E2E 프로세스를 구체화할 때 다시 매겨요 |

## 2. 한눈에: 운영하는 사람이 날마다 보는 것

백엔드의 API가 먼저이고, 화면은 같은 계약을 읽는 얇은 층이에요(알파는 기능을 시험하는 수준만).

| 보는 것 | 어디서 오나 | 이런 때 움직여요 |
|---|---|---|
| 소스 줄: 마지막 온전한 수집, 상태(`fresh` / `stale` / `failed`), 일정이 멈췄는지 | 소스, 실행 기록 | 낡은 소스를 먼저 봐요 |
| 안전장치에 걸려 기다리는 적용 | 동기화 실행 | 차이를 보고 확인하거나 막아요 |
| 최근 동기화 실행: 단계별 수와 시간, 수 맞춤 | 실행 기록 | 맞지 않는 실행이 있으면 원인을 봐요 |
| 품질 지표의 흐름(버전 사이) | 품질 지표 | 떨어진 지표를 따라 문제 그룹으로 가요 |
| 문제 그룹: 건수 순, 주인 도메인, 연결된 브랜치 | 문제 목록 | 가장 많이 막는 까닭부터 규칙을 고쳐요 |
| 사용자가 알린 것 중 새 것 | 문제 목록 | 원인을 나눠요(4.6절) |
| 질의 엔진이 올려 둔 버전과 그 나이 | 엔진의 지표 | 오래 갈아 끼우지 못한 벌을 봐요 |

## 3. 품질 지표

### 3.1 지표의 정의

모두 "무엇을 무엇으로 나누나"를 정해 두고, 분자와 분모를 함께 남겨요. 비율만 남기면 분모가 바뀐 것을 알 수 없어요.

| 지표(`metric`) | 분자 | 분모 | 읽는 법 |
|---|---|---|---|
| `attribute_fill` | 그 속성에 값이 있는 객체(값의 근거 등급이 `fact` 또는 `assumed`) | 그 타입의 객체. 분모에 드는 속성은 타입 등록부에서 `required`로 표시한 것뿐이에요 | 속성마다 하나. 낮으면 소스가 안 주거나 매핑이 빠진 거예요 |
| `grade_fact`, `grade_assumed`, `grade_unknown` | 그 등급의 속성 값(링크는 따로 센다) | 속성 값 전체 | 셋의 합은 1. 가정과 모름이 늘면 답이 약해져요 |
| `orphan_objects` | 링크가 하나도 없는 객체 | 그 타입의 객체 | 타입이 원래 홀로 서는 것이면 높아도 정상이에요. 흐름을 봐요 |
| `duplicate_suspects` | 식별 후보 문제에 든 객체 | 그 타입의 객체 | 합치기를 기다리는 겹침 |
| `source_conflicts` | 소스 사이에 값이 다른 속성 값(풀리지 않은 것) | 둘 이상의 소스가 댄 속성 값 | 이기는 소스 규칙이 빠진 곳을 보여요 |
| `freshness_age` | 지금 − 마지막 온전한 수집의 시각 | 그 소스의 주기 | 1을 넘으면 주기를 한 번 놓친 거예요. 2를 넘으면 낡음(5절) |
| `reconciliation_balanced` | 수 맞춤이 맞은 동기화 | 그 기간의 동기화 | 맞지 않은 실행은 원인을 찾을 때까지 목록에 남아요 |
| `record_outcome` | 쓰임, 규칙이 걸러 냄, 문제, 안 쓰임 각각 | 받은 원본 기록 | 넷의 합이 분모와 같아요(ADR-0008 수 맞춤) |

링크의 등급 비율도 `grade_*`로 내고 `detail_key`에 `link`를 적어요.
### 3.2 어느 단위로 내나

| 지표 | KG 전체 | 도메인 | 소스 | 타입 |
|---|---|---|---|---|
| `attribute_fill` | ○ | ○ | ○ (그 소스가 맡은 속성) | ○ |
| `grade_*` | ○ | ○ | ○ | ○ |
| `orphan_objects` | ○ | ○ | ○ (그 소스의 매핑이 만든 객체) | ○ |
| `duplicate_suspects` | ○ | ○ | | ○ |
| `source_conflicts` | ○ | ○ | ○ (진 쪽 소스) | ○ |
| `freshness_age` | | | ○ | ○ (그 타입에 대는 소스 중 가장 낡은 것) |
| `reconciliation_balanced`, `record_outcome` | ○ | ○ | ○ | |

도메인 단위의 객체는 그 객체를 만든 매핑의 도메인(ADR-0012)으로 세요. 속성 하나를 여러 도메인이 댄 값은 속성마다 댄 도메인으로 세요.

### 3.3 KG 버전마다 남기는 것

지표는 KG 버전을 새로 공개할 때 그 버전에 대해 계산해 같은 트랜잭션 가까이에서 남겨요. 그래야 버전 사이의 차이로 추세를 봐요. 표 `quality_metric`의 칸은 이래요.

| 칸 | 뜻 |
|---|---|
| `kg_id`, `kg_version` | 어느 KG의 어느 버전인가 |
| `metric` | 3.1의 이름 |
| `scope_kind`, `scope_id` | `kg` / `domain` / `source` / `type`과 그 ID |
| `detail_key` | 속성 이름, 등급, 분류 이름처럼 지표 안의 갈래. 없으면 비어 있어요 |
| `numerator`, `denominator` | 분자와 분모(정수) |
| `computed_at` | 계산한 때 |

신선도는 읽는 순간의 나이가 값이고 버전이 만들어진 때의 나이는 참고로 남겨요. 같으면 새 버전을 만들지 않으므로(ADR-0008), 버전이 없는 사이의 신선도 흐름은 실행 기록에서 읽어요.

지어낸 예시예요. 서버 교체 뒤 첫 동기화 버전 `v42`에서:

| scope | metric | detail_key | numerator | denominator | 비율 |
|---|---|---|---|---|---|
| type `PhysicalServer` | `attribute_fill` | `rack_position` | 1,180 | 1,250 | 94.4% |
| type `PhysicalServer` | `orphan_objects` | | 12 | 1,250 | 1.0% |
| source `asset_sheet` | `freshness_age` | | 26시간 | 24시간 | 1.08 |

`v41`에서 `rack_position`이 97.0%였다면 서버 교체 때 들어온 서버 일부에 자리가 안 적힌 거예요. 다음 절의 문제 그룹으로 이어져요.

## 4. 문제 목록

### 4.1 문제의 종류

| 종류(`issue_kind`) | 뜻 | 만드는 단계 |
|---|---|---|
| `dangling_link` | 링크 정의가 이으려 했는데 끝점이 없다(못 이은 링크) | 링크 |
| `attribute_conflict` | 둘 이상의 소스가 같은 속성에 다른 값을 댔고 진 값이 있다 | 식별과 병합 |
| `invalid_value` | 틀린 값. 자료형, 단위, 고르기 값, 범위에 어긋난다 | 정제, 매핑 |
| `identity_candidate` | 같은 것일 수 있는 객체 둘. 확률로 맞춘 제안이라 저절로 합치지 않는다 | 식별과 병합 |
| `completeness_mismatch` | 소스가 "이 타입을 전부 준다"고 선언했는데 다른 소스나 링크가 그 타입의 객체를 가리킨다, 또는 선언한 수와 받은 수가 다르다 | 링크, 안전장치 |
| `retired_type_in_use` | 표준 모델에서 물러난 타입을 쓰는 매핑이 있다(8절) | 제품 업그레이드 뒤 |
| `user_report` | 사용자가 KG가 틀렸다고 알렸다 | 사람 |

종류는 닫힌 목록이고, 새 종류는 결정 기록으로 더해요.

### 4.2 문제 하나의 칸

표 `issue`예요. 이름은 영어 snake_case예요.

| 칸 | 뜻 |
|---|---|
| `issue_id` | 문제의 ID. 같은 까닭에서 같은 대상이면 같은 ID가 나와요(결정적). 동기화마다 새로 생기지 않아요 |
| `kg_id` | 어느 KG |
| `kind` | 4.1의 종류 |
| `status` | `open` / `in_progress` / `resolved` (4.4절) |
| `subject_ref` | 대상. 객체 ID, 링크 ID, 원본 기록의 참조 중 하나 이상 |
| `rule_ref` | 이 문제를 낸 정의의 항목과 버전(매핑, 링크 정의, 식별 규칙, 안전장치) |
| `source_id` | 관련한 소스. 없을 수도 있어요 |
| `owner_domain_ids` | 주인 도메인. 하나, 또는 둘(4.5절) |
| `cause_key` | 같은 까닭을 알아보는 열쇠(4.3절) |
| `first_seen_version`, `last_seen_version` | 처음과 마지막으로 나온 KG 버전 |
| `detail` | 문제의 자세한 내용. 값은 민감 등급을 따르고, 비밀 값은 없어요 |
| `branch_ref` | 이 문제를 풀려고 연 브랜치. 없을 수 있어요 |
| `report` | `user_report`만. 보고한 KG 버전, 대상, 무엇이 어떻게 틀렸다는 주장, 증거 글, 보고자 |
| `cause_class` | `user_report`만. 원인 분류(4.6절). 처음엔 비어 있어요 |

### 4.3 같은 까닭으로 묶기

수천 건을 하나씩 보지 않아요. 문제를 `cause_key`로 묶은 것이 문제 그룹(`issue_group`)이에요.

`cause_key` = (`kind`, 소스, 타입, `rule_ref`, 시그니처). 시그니처는 같은 까닭이면 같게 나오는 짧은 모양이에요. 예를 들면 `dangling_link`는 "찾는 키의 값이 이런 모양"이고, `attribute_conflict`는 "진 소스와 이긴 소스의 쌍과 속성 이름"이에요.

| 칸 | 뜻 |
|---|---|
| `group_id`, `kind`, `cause_key` | 그룹의 ID, 종류, 열쇠 |
| `owner_domain_ids` | 그룹에 든 문제의 주인 도메인의 합 |
| `open_count` | 풀리지 않은 문제 수. 이 순서로 정렬해요 |
| `sample_issue_ids` | 눈으로 확인할 견본 몇 건 |
| `first_seen_version` | 그룹이 처음 나온 KG 버전 |

예: 서버 교체 뒤 `asset_sheet`의 랙 이름이 `R-07`에서 `R07`로 바뀌어 `dangling_link` 312건이 한 그룹으로 보여요. 원인 후보는 "랙 이름의 표기"이고 고칠 곳은 다듬기 규칙이에요.

### 4.4 푸는 길은 규칙을 고치는 것이다

낱개를 손으로 고쳐 KG에 넣는 길은 없어요. 문제 그룹에서 푸는 흐름은 이래요.

```
문제 그룹(open)
  → 브랜치를 연다. 그룹이 in_progress로 바뀐다(브랜치와 연결)
  → 매핑, 다듬기, 이기는 소스, 예외 목록 중 까닭이 있는 규칙을 고친다
  → 후보 실행: 받아 둔 원본 기록으로 후보 KG를 만든다. 소스에 다시 가지 않는다
       그룹의 문제가 몇 건 사라지고, 새로 생기는 문제가 없는지, 품질 지표가 어떻게 변하는지를 본다
  → 병합: 고친 사람이 아닌 사람이 주인 도메인에서 승인한다. 병합 직전에 최신 정의 위에서 후보 실행을 다시 하고 안전장치를 거친다
  → 다음 동기화에서 그 문제가 더는 나오지 않으면 resolved
```

문제는 풀렸다고 지우지 않아요. 같은 까닭이 다시 나오면 같은 `issue_id`가 `open`으로 돌아와요(재발이 보여요).

**낱개 예외는 정의에 남아요.** 사람이 낱개로 정한 "같다 / 다르다"(식별 후보에 대한 답)는 식별 규칙의 예외 목록에 한 줄로 더해져요. 예외 목록은 정의의 항목이라 버전이 있고, 브랜치와 병합을 거치고, 내보내고 들일 수 있어요. 낱개 손질이 숨은 상태가 되지 않아요(ADR-0007). 낱개 예외는 둘뿐이에요: 식별의 예외(같다 / 다르다)와 원본 기록 제외(이 기록은 쓰지 않는다). 값을 낱개로 덮어쓰는 예외는 없어요. 값은 소스에서 고치거나 규칙으로 고쳐요.

### 4.5 주인 도메인에게 보내기와 도메인 둘에 걸친 문제

- 문제의 주인은 그 소스나 그 정의 항목의 주인 도메인이에요. 소스가 낸 틀린 값은 소스의 도메인이고, 매핑이 낸 문제는 매핑의 도메인이에요.
- 한쪽 소스의 장비가 다른 쪽 소스의 랙을 가리키는데 없으면 `owner_domain_ids`에 둘이 들어가고 양쪽 화면에 보여요. 도메인을 가로지르는 링크 정의는 플랫폼의 정의이거나 양쪽이 함께 승인하는 정의라서(ADR-0012), 이 문제를 푸는 병합도 그 정의의 승인 규칙을 따라요.
- 가려진 도메인의 문제는 그 도메인에 보이는 사람만 봐요. 다른 사람에게는 "가려진 문제 몇 건"으로만 보여요(ADR-0012).

### 4.6 사용자가 알린 것

- 사용자나 시스템 계정이 "이 객체의 이 값이 틀렸다"고 알려요. 알린 것은 `user_report` 문제가 되어 KG를 직접 고치지 않아요(같은 입력이면 같은 KG가 나온다는 성질을 지켜요).
- 원인을 `cause_class`로 나눠요: `source_error`(소스가 틀림) / `rule_error`(규칙이 틀림) / `model_limit`(모델이 못 담음) / `stale`(최신이 아님). 나눈 뒤는 다른 문제와 같은 길이에요. `stale`이면 소스의 신선도를 보고, `rule_error`면 규칙을 고쳐요. `source_error`는 소스의 주인 도메인에 알리는 것으로 끝나고 KG는 고치지 않아요.

## 5. 신선도

### 5.1 무엇에 거나

신선도는 **소스의 마지막 온전한 수집**에서 재요. 객체마다 "마지막으로 본 때"를 쓰지 않아요(동기화마다 모든 행이 바뀌므로, ADR-0009).

- "온전한 수집"은 안전장치의 덜 받은 수집 검사를 통과한 것이에요: 쪽 넘김이 끝까지 갔고, 소스가 알려 준 수와 맞고, 지난번보다 기록 수가 크게 줄지 않았어요.
- 온전히 받았는데 바뀐 것이 없어 새 KG 버전이 안 생겨도 그 시각은 갱신돼요. 아니면 안정한 소스가 낡아 보여요.
- 중간에 끊긴 수집은 시각을 갱신하지 않아요.

소스 신선도의 칸이에요.

| 칸 | 뜻 |
|---|---|
| `source_id` | 소스 |
| `last_complete_capture_at` | 마지막 온전한 수집이 끝난 때 |
| `expected_interval` | 소스의 주기. 손으로만 받는 소스는 관리자가 적은 기대 갱신 주기예요. 적지 않으면 비어 있어요 |
| `freshness_state` | `fresh` / `stale` / `failed` (5.3절) |
| `consecutive_failures` | 잇달아 실패한 동기화 수(7절) |

### 5.2 답과 화면에 어떻게 붙나

- 소스 목록에는 마지막 온전한 수집과 상태가 보여요.
- 모든 답에 붙는 신선도(ADR-0010)는 두 가지예요: 답이 쓴 소스들의 신선도 중 가장 나쁜 것, 그리고 소스별 목록이에요. 가장 나쁜 쪽에 맞추는 것은 근거 등급이 가장 낮은 입력을 따르는 것과 같은 생각이에요.
- 짧게는 "이 데이터는 26시간 전 것"처럼 사람이 읽는 말로 보이고, 자세히 보면 소스마다 시각이 나와요.
- 영향 범위처럼 투영에서 답할 때는 투영을 만든 KG 버전과 그때의 신선도를 쓰고, 지금 신선도와 다르면 둘 다 보여요.

### 5.3 낡음의 판정

| 상태 | 조건 | 기본값 |
|---|---|---|
| `fresh` | 마지막 온전한 수집이 주기의 2배 안 | 2배는 가정 |
| `stale` | 주기의 2배를 넘음 | |
| `failed` | 일정이 멈춤(7절) | |

**기본값은 가정이에요.** 주기가 있는 소스는 이 규칙을 따라요. 손으로만 받는 소스도 관리자가 기대하는 갱신 주기를 적으면 그것에 대어 판정해요. 적지 않은 소스는 나이만 보이고 "기대 주기 없음"으로 표시돼요.

## 6. 가용성

현실을 바꾸는 길이 프락시움에 없으므로, 프락시움이 멈춰도 현실에는 아무 일이 없어요. 멈추면 안 되는 것은 **묻기**뿐이에요. 장애 중에 가장 많이 묻기 때문에 질의는 처음부터 이 등급으로 설계해요.

### 6.1 기능의 등급

| 기능 | 등급 | 어떻게 | 멈추면 |
|---|---|---|---|
| KG에 묻기(질의, 영향 범위, MCP) | **멈추면 안 됨** | 질의 엔진과 API가 여러 벌. 엔진은 올려 둔 투영으로 저장소 없이도 답해요 | 한 벌이 죽어도 답해요. 저장소가 죽으면 마지막 버전으로 답해요 |
| 원본 기록, 정의, KG 버전과 이력, 실행 기록, 감사 기록 | 잃으면 안 됨 | 저장소가 복제돼 있고 백업과 시점 복구가 있어요 | |
| 동기화 | 잃으면 안 됨 | 일꾼이 여러 벌이고 죽은 일은 다른 일꾼이 이어받아요 | 마지막 버전에 머물고 신선도가 나빠져요 |
| 정의 고치기, 브랜치, 품질 보기 | 멈춰도 됨 | | 고치지 못해요. KG와 질의는 그대로예요 |

"여러 벌"은 여러 구역에 걸쳐 띄울 수 있어야 한다는 요구예요. 구역의 수와 배포 방법은 구현할 때 정해요.

### 6.2 역할 셋이 죽었을 때

서버는 같은 코드에서 시작점만 다른 세 역할로 떠요(ADR-0006).

| 역할 | 하는 일 | 한 벌이 죽으면 | 전부 죽으면 |
|---|---|---|---|
| API | 계약의 길과 MCP. 상태를 쥐지 않아요 | 나머지가 받아요. 진행 중이던 요청은 다시 보내면 돼요(읽기는 멱등) | 밖에서 묻는 길이 끊겨요. 그래서 여러 구역에 걸쳐 여러 벌을 띄울 수 있어야 해요. 저장소가 멈춰도 묻기의 길은 답해요(로그인 증표는 저장소 없이 확인하고, 무리와 역할의 짝은 나이에 상한이 있는 사본을 써요) |
| 일꾼 | 수집부터 적용까지와 일정 | 하던 동기화를 다른 일꾼이 이어받아요(7.3절). 소스마다 동시 상한은 그대로예요 | 동기화와 일정이 멈추고 신선도가 나빠져요. 묻기는 그대로예요 |
| 질의 엔진 | 투영을 메모리에 올려 영향 범위와 길을 답해요. 부르는 쪽은 엔진을 직접 부르지 않고 언제나 API를 거쳐요 | 나머지가 답해요. 새 버전은 한 벌씩 갈아 끼우므로 갈아 끼우는 동안에도 한 벌 이상은 답해요 | 영향 범위와 길의 답이 멈춰요. 얕은 이웃은 SQL로 답할 수 있으니 저장소가 살아 있으면 이어져요 |

### 6.3 저장소가 죽었을 때

| 무엇 | 어떻게 되나 |
|---|---|
| 묻기 | 이미 올려 둔 투영으로 마지막 KG 버전을 답해요. 답에 버전과 신선도가 적혀 있어요 |
| 동기화, 정의 고치기, 브랜치, 품질 보기 | 멈춰요. 일꾼은 소스에 가지 않고 기다려요 |
| 복구 뒤 | 점유 기한이 지난 일은 다른 일꾼이 이어받고, 멈춘 사이 밀린 일정은 소스마다 하나로 합쳐 한 번만 돌려요. 엔진은 가장 새 버전의 투영을 다시 올려요. 투영 파일은 저장소가 아니라 파일 보관 포트 뒤에 있고 엔진은 받은 파일을 자기 디스크에 두므로, 저장소가 죽어도 새로 뜨는 벌이 올릴 것이 있어요 |

### 6.4 처음부터 지키는 것 여덟

나중에 고가용을 붙이려고 다시 쓰지 않게, 첫 코드부터 아래를 지켜요.

| # | 지키는 것 | 왜 필요한가 |
|---|---|---|
| 1 | 서버는 상태를 쥐지 않는다 | 어느 벌이 죽어도 다른 벌이 이어요. 벌을 늘리고 줄이는 일이 안전해요 |
| 2 | 모든 상태는 저장소 한 곳 | 백업과 복구의 대상이 한 곳이라 빠뜨릴 수 없어요 |
| 3 | 처리기는 멱등 | 죽은 일을 이어받거나 요청을 다시 보내도 같은 결과예요. 두 번 처리해서 두 번 적용되지 않아요 |
| 4 | 기록은 추가만 | 감사와 이력이 변조되지 않고, 복구 때 어디까지 갔는지 알 수 있어요 |
| 5 | KG 버전은 바뀌지 않는다 | 읽는 쪽이 한 버전만 보고, 엔진 벌들이 서로 같은 버전으로 답해요 |
| 6 | 프로세스 안의 단 하나뿐인 것에 기대지 않는다 | 일정표와 캐시가 한 프로세스에만 있으면 그 프로세스가 죽을 때 같이 사라져요. 파생물은 다시 만들 수 있어야 해요 |
| 7 | 같은 일정이 두 번 걸리지 않게 키로 막는다 | 벌이 여럿이면 일정 확인도 여럿이 해요. 키가 없으면 같은 동기화가 두 번 걸려요 |
| 8 | 서버 여럿이 함께 떠도 동기화 하나는 한 곳에서만 돈다 | 같은 소스를 둘이 동시에 읽으면 소스에 부하가 두 배이고, 적용이 부딪쳐요 |

## 7. 동기화의 실패 처리

### 7.1 다시 하기와 일정 멈춤

| 일 | 규칙 | 기본값(모두 가정) |
|---|---|---|
| 한 동기화 안의 요청이나 단계가 실패 | 물러났다 다시 해요(기다리는 시간을 늘려요) | 3번 |
| 그래도 실패 | 그 동기화는 실패로 기록하고, 새 KG 버전을 만들지 않아요. 마지막 정상 버전이 그대로예요 | |
| 동기화가 잇달아 실패 | 그 소스의 일정을 멈추고 알려요. 상태는 `failed` | 잇달아 5번 |
| 인증 실패 | 다시 하지 않고 바로 끊어요(소스 쪽 계정이 잠기지 않게, ADR-0008) | 즉시 |
| 안전장치가 막음(모양 바뀜, 대량 사라짐, 덜 받음) | 적용하지 않고 확인을 기다려요. 실패로 세지 않고 "기다림"으로 따로 세요 | |

일정이 멈춘 소스는 운영 역할이 손으로 켜요. 소스 하나가 실패해도 다른 소스는 진행해요. 실패한 소스의 객체가 사라졌다고 보지 않아요(마지막 정상 수집을 유지하고 신선도만 나빠져요).

### 7.2 알림

알릴 때는 다섯이에요: 일정이 멈출 때(잇달아 실패, 인증 실패로 끊음), 안전장치가 막아 적용이 확인을 기다릴 때, 받은 컬럼이나 자료형이 바뀌어 멈출 때, 소스가 `fresh`에서 `stale`이 될 때, 단계의 들어온 수와 나간 수가 안 맞을 때.

같은 알림은 풀릴 때까지 한 번만 보내요(중복 억제). 알림은 포트 뒤에 두고, 보내는 길(메신저, 메일 등)은 어댑터예요. 받는 쪽은 문제나 소스의 주인 도메인의 운영 역할이고, 플랫폼의 것은 플랫폼 관리자예요.

### 7.3 일꾼이 죽은 일을 이어받기

한 동기화는 한 곳에서만 돌아야 해요(6.4의 8번). 아래 장치 셋이 함께 지켜요. 모두 저장소 안에서 하고 따로 도는 조율 서비스를 두지 않아요(ADR-0009).

| 장치 | 어떻게 |
|---|---|
| 소스당 하나만 | 같은 소스의 `queued` 또는 `running` 실행은 하나만 있을 수 있어요. 저장소의 유일 제약이 막아요 |
| 일정의 키 | 일정이 만드는 실행에는 (소스, 시각 칸)으로 낸 키가 있어요. 일꾼 여럿이 같은 칸을 만들려 해도 하나만 들어가요 |
| 점유와 점유 기한 | 일꾼이 실행을 집으면 `claimed_by`와 `lease_expires_at`을 써요. 일하는 동안 `lease_expires_at`을 계속 미뤄요. 일꾼이 죽으면 미뤄지지 않아 기한이 지나요 |

`sync_run`의 칸이에요.

| 칸 | 뜻 |
|---|---|
| `run_id`, `source_id` | 실행과 소스 |
| `schedule_key` | 일정의 키. 손으로 돌린 것은 비어 있어요 |
| `status` | `queued` / `running` / `waiting_confirmation` / `succeeded` / `failed` / `abandoned` |
| `attempt` | 이어받을 때마다 오르는 번호(점유 번호) |
| `claimed_by`, `lease_expires_at` | 점유한 일꾼과 기한 |
| `stage`, `stage_counts` | 지금 단계와 단계마다 들어온 수·나간 수·떨어진 수·시간 |
| `guard_verdict` | 안전장치의 판정과 이유 |
| `kg_version` | 만들어진 KG 버전. 없으면 비어 있어요 |
| `error_code` | 오류 코드. 비밀 값과 행의 내용 없이 |

**이어받는 규칙**
- 점유 기한이 지난 `running` 실행은 다른 일꾼이 `attempt`를 올리며 집어요.
- 모든 쓰기는 자기 `attempt`가 지금 번호와 같을 때만 받아들여져요. 죽은 줄 알았던 일꾼이 늦게 깨어나 쓰려 해도 거절돼요(두 곳에서 도는 일을 막는 마지막 장치).
- 수집 단계에서 죽었으면 수집을 처음부터 다시 해요. 같은 기록은 복제되지 않으므로(ADR-0008) 안전하고, 중간에 끊긴 수집은 온전한 수집이 아니라 신선도를 올리지 않아요.
- 수집이 끝난 뒤에 죽었으면 받아 둔 원본 기록으로 다음 단계부터 이어 돌려요. 소스에 다시 가지 않아요.
- 적용은 짧은 트랜잭션 하나라서(ADR-0009) 반쯤 적용된 상태가 없어요. 죽었으면 적용은 안 된 거예요.
- 이어받기를 되풀이해도 끝나지 않으면 `abandoned`로 두고 실패로 세요.

## 8. 표준 모델과 제품의 업그레이드

제품이 오르면 표준 모델도 올라요(ADR-0007).

- **덮어쓰지 않아요.** 표준 타입의 이름은 예약돼 있고, 관리자가 더한 타입은 이름 공간이 따로예요. 업그레이드가 관리자의 타입과 매핑을 바꾸지 않아요.
- **타입은 지우지 않고 물러나요.** 물러난 타입은 이력에 남고 기존 객체도 지워지지 않아요.
- **알려요, 저절로 고치지 않아요.** 물러난 타입을 쓰는 매핑이 있으면 `retired_type_in_use` 문제가 그 매핑의 주인 도메인에 올라요. 같은 물러난 타입 하나에서 온 문제는 한 그룹으로 묶여요.
- **정의를 옮기는 것은 규칙을 고치는 일과 같은 길이에요.** 주인 도메인이 브랜치에서 매핑을 새 타입으로 옮기고, 후보 실행으로 차이를 보고, 승인을 받아 병합해요. 옮기기 전에도 받는 데이터는 그대로 받아져요. 물러난 타입에는 후속 타입을 가리키는 칸(`superseded_by`)이 있어 알림에 함께 보여요. 표준 모델이 오른 뒤의 첫 적용은 정의를 고친 뒤의 첫 적용과 같아서, 사람이 차이를 보고 확인해요.

## 9. 지표와 로그

### 9.1 지표(수를 밖에서 읽는 길)

지표는 흔히 쓰는 형식의 주소로 내요. 모니터링하는 쪽이 그대로 가져가요. 이름표는 **소스까지만** 붙여요.

| 이름표 | 값의 범위 |
|---|---|
| `role` | `api` / `worker` / `query_engine` |
| `source` | 소스의 ID. 이름표 중 가장 좁은 것이에요 |
| `stage` | 동기화의 단계 이름 여덟 |
| `result` | `succeeded` / `failed` / `waiting_confirmation` |

타입, 속성, 도메인, 객체 ID는 이름표로 붙이지 않아요. 이름표의 조합이 많아지면 시계열이 수없이 늘어요. 타입이나 도메인 단위의 숫자는 지표 주소가 아니라 품질 지표(3절)로 읽어요.

내는 것은 이래요.
- 동기화: 실행 수(소스, 결과별), 단계별 시간과 들어온 수·나간 수·떨어진 수, 소스의 응답 수와 오류, 점유를 이어받은 수.
- 신선도: 소스별 `freshness_age`와 `consecutive_failures`, 일정이 멈춘 소스 수.
- 질의: 질의 이름별 응답 시간과 오류 수, 엔진이 올려 둔 KG 버전과 올린 뒤 지난 시간.
- 저장소: 연결 실패와 쓰기 불가를 만난 수.

### 9.2 로그

| 찍는 것 | 찍지 않는 것 |
|---|---|
| 실행·소스·단계의 이름표 | 비밀 값, 토큰, 헤더 |
| 수(들어온, 나간, 떨어진), 시간 | 응답 본문, 원본 기록의 내용 |
| 오류 코드, 경로, 행 번호 | 행의 내용, 속성 값, 식별자의 값 |
| 안전장치의 판정과 이유(수와 이름) | URL의 쿼리 문자열 |

"찍지 않는 것"은 어떤 로그 수준에서도 찍지 않아요. 행의 내용이 필요하면 권한이 있는 사람이 원본 기록을 읽어요.

## 10. 백업과 복구: 진실과 파생물

저장과 백업의 방법은 [KG의 저장과 버전](kg-storage.md)에 있어요. 여기서는 운영의 눈으로 무엇이 진실이고 무엇이 다시 만들 수 있는 것인지만 나눠요.

| 구분 | 무엇 | 복구 뒤 |
|---|---|---|
| 진실(잃으면 안 됨) | 원본 기록, 정의와 버전과 브랜치, KG 버전과 이력, 실행 기록, 감사 기록, 사람이 알린 `user_report`와 문제 상태의 바뀜 | 백업과 시점 복구에서 되살려요 |
| 파생물(다시 만들 수 있음) | 투영, 품질 지표, 규칙이 낸 문제 항목, 문제 그룹 | KG 버전과 정의에서 다시 만들어요 |

- 시점 복구로 돌아가면 그 뒤의 KG 버전이 사라져요. 소스를 다시 읽으면 같은 입력에서 같은 버전이 나와요(ADR-0009).
- **소스에서 다시 받을 수 없는 것**이 있어요. 올린 엑셀 파일과 수집 봉투로 받은 기록이에요. 이것의 원본 기록은 백업이 유일한 사본이라 복구 훈련에 반드시 넣어요.

## 11. 숫자는 가정이고 재서 정한다

| 숫자 | 지금 쥔 값 | 어떻게 재서 정하나 |
|---|---|---|
| 낡음의 기준 | 주기의 2배 | 알파에서 소스마다 주기와 실제 지연을 보고 |
| 다시 하기 횟수 | 3번 | 소스의 오류 모양별로 일시 오류가 몇 번 안에 풀리는지 |
| 일정 멈춤의 연속 실패 수 | 5번 | 거짓 멈춤(알림 피로)과 늦은 멈춤(소스 부하)의 균형 |
| 대량 사라짐의 기준 | ADR-0008의 기본값 | 견본 시험 |
| 점유 기한, 점유 연장 간격 | 정하지 않음 | 가장 긴 단계의 시간과 일꾼 장애 주입 |
| 잃어도 되는 시간(RPO) | 커밋된 기록은 0을 목표 가정 | 복제 방식별 쓰기 지연과 복구 훈련 |
| 복구 시간(RTO) | 한 벌의 장애는 수십 초에서 2분, 저장소 전체의 상실은 수 시간(둘 다 가정) | 장애 주입(구역 격리, 주 저장소 강제 종료, 백업 저장 위치 단절, 비밀 저장소 단절) |
| 투영을 올리는 시간, 품질 지표 계산 시간 | 정하지 않음 | 지어낸 3천만 객체로(ADR-0009의 재는 순서) |

## 12. 알고 가는 한계와 가정

- 조사에서 확인하지 못한 것(여러 제품의 안쪽 동작, 페일오버 시간, 큐의 실제 지연)이 있어 위 숫자는 모두 가정이에요.
- 품질 지표는 "있어야 할 것이 없다"를 직접 알 수 없어요. 완전성 선언이 있는 소스와 타입에서만 `completeness_mismatch`가 나오고, 선언이 없는 곳은 "모른다"예요.
- 문제 그룹의 시그니처가 너무 넓으면 다른 까닭이 섞이고, 너무 좁으면 잘게 쪼개져요. 알파에서 고쳐요.

## 13. 아직 정하지 않은 것

- 품질 지표와 해결된 문제 항목의 보관 기한.
