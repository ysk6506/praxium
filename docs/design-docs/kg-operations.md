# KG 운영

KG를 짓는 것(수집)과 쓰는 것(묻기) 사이에서 날마다 일어나는 일을 다뤄요. 풀지 못한 것을 규칙으로 풀고, 무엇이 죽어도 묻기는 멈추지 않게 하고, 받는 길이 멈춰도 잃지 않게 하는 설계예요. 숫자는 제품이 싣는 기본값(설정)이거나 측정하지 않은 가정이에요(8절). 측정해서 고치는 일은 클로즈드 베타에서 해요.

데이터가 잘 들어오는지 재고 보이는 일은 이 문서의 것이 아니에요. 품질 지표, 신선도, 헬스 상태, 목표, 이상 탐지, 알림의 규칙, 실행 소스 탐색, 지표와 로그의 내보내기는 [데이터 관측성](data-observability.md)(ADR-0013)이 정해요. 정의를 고치는 경로(브랜치, 제안, 검사, 병합, 리버트)은 [정의의 버전과 브랜치](definitions.md)(ADR-0014)가, 권한과 감사는 [접근 제어](access-control.md)(ADR-0012)가 정해요. 이 문서는 그 지표들이 가리키는 문제를 어떻게 풀고, 그 데이터가 멈추지 않고 흐르게 하는 일을 다뤄요.

## 1. 목적과 다루는 질문

| 쟁점 | 답 |
|---|---|
| 풀지 못한 것은 어디로 가나 | 문제 목록으로 가고, 담당자가 규칙을 고쳐 풀어요(2절) |
| 무엇이 죽으면 무엇이 멈추나 | 기능마다 등급을 정했어요. 묻기는 멈추지 않아요(3절) |
| 동기화와 흐름이 실패하면 | 마지막 정상 버전을 지키고, 일정을 쉬게 하고, 흐름은 붙잡되 받는 것은 이어요(4절) |
| 제품이 오르면 | 물러난 타입을 알리고 저절로 고치지 않아요(5절) |
| 복구하면 무엇이 돌아오나 | 진실은 되살리고 파생물은 다시 만들어요(6절) |
| 넘겨받은 쟁점 "운영 경로가 되면 멈추면 안 된다" | 현실을 바꾸는 경로가 프락시움에 없으니 멈추면 안 되는 것은 묻기예요. 맡김과 조치의 등급은 E2E 프로세스를 구체화할 때 다시 매겨요 |

운영하는 사람이 날마다 보는 것 가운데 이 문서의 것은 넷이에요. 헬스 상태와 지표는 데이터 관측성 문서에서 봐요. 모두 API로 읽고 조작해요(화면은 다른 저장소가 같은 API로 만들어요. ADR-0016).

| 보는 것 | 어디서 오나 | 이런 때 움직여요 |
|---|---|---|
| 문제 그룹: 건수 순, 담당자, 연결된 제안 | 문제 목록 | 가장 많이 차단 사유부터 규칙을 고쳐요 |
| 보류된 스트림과 안전장치가 멈춘 적용 | 동기화 실행, 흐름 | 쌓인 변경을 보고 풀거나 버려요 |
| 일정이 멈춘 소스 | 소스의 일정 | 원인을 고치고 다시 켜요 |
| 사용자가 알린 것 중 새 것 | 문제 목록 | 원인을 나눠요(2.6절) |

## 2. 문제 목록

### 2.1 문제의 종류

| 종류(`issue_kind`) | 뜻 | 만드는 단계 |
|---|---|---|
| `dangling_link` | 링크 정의가 이으려 했는데 끝점이 없다(못 이은 링크) | 링크 |
| `attribute_conflict` | 둘 이상의 소스가 같은 속성에 다른 값을 댔고 진 값이 있다 | 식별과 병합 |
| `invalid_value` | 틀린 값. 자료형, 단위, 고르기 값, 범위에 어긋난다 | 정제, 매핑 |
| `identity_candidate` | 같은 것일 수 있는 객체 둘. 확률로 맞춘 제안이라 저절로 합치지 않는다 | 식별과 병합 |
| `completeness_mismatch` | 공급이 "이 타입을 전부 준다"고 선언(`completeness_declaration`)했는데 다른 소스나 링크가 그 타입의 객체를 가리킨다, 또는 선언한 수와 받은 수가 다르다 | 링크, 안전장치 |
| `unattached_value` | 살만 붙이는 공급이 준 값인데, 기한 안에 붙을 객체가 생기지 않았다(붙을 곳이 없는 값) | 매핑 |
| `intent_observation_mismatch` | 설정(의도)과 관측이 어긋난다. 예: 경로 넷을 쓰게 설정됐는데 둘만 보인다. 버릴 충돌이 아니라 값진 정보다 | 식별과 병합 |
| `expectation_violation` | 기대 조건을 어겼고 강도가 `warn`이다(`fail`은 적용을 멈춘다) | 정제, 안전장치 |
| `retired_type_in_use` | 표준 모델에서 물러난 타입을 쓰는 매핑이 있다(5절) | 제품 업그레이드 뒤 |
| `user_report` | 사용자가 KG가 틀렸다고 알렸다 | 사람 |
| `data_alert` | 데이터 헬스 상태의 알림(근본 원인 하나에 묶인 것). 규칙은 ADR-0013이 정한다 | 관측 |

종류는 고정 목록이고, 새 종류는 결정 기록으로 더해요. 알림도 문제 목록의 항목이 돼요. 받은 편지함은 하나예요(ADR-0013).

### 2.2 문제 하나의 칸

표 `issue`예요. 이름은 영어 snake_case예요.

| 칸 | 뜻 |
|---|---|
| `issue_id` | 문제의 ID. 같은 이유에서 같은 대상이면 같은 ID가 나와요(결정적). 동기화마다 새로 생기지 않아요 |
| `kg_id` | 어느 KG |
| `kind` | 2.1의 종류 |
| `status` | `open` / `in_progress` / `resolved` (2.4절) |
| `subject_ref` | 대상. 객체 ID, 링크 ID, 원본 레코드의 참조 중 하나 이상 |
| `rule_ref` | 이 문제를 낸 정의의 항목과 판(매핑, 링크 정의, 식별 규칙, 기대 조건, 안전장치) |
| `source_ids` | 관련한 소스. 하나, 또는 둘 이상(2.5절) |
| `type_ref` | 관련한 객체 타입이나 링크 타입. 없을 수도 있어요 |
| `contact_refs` | 담당자. 소스, 타입, 정의 항목에 붙은 담당자를 모아요 |
| `cause_key` | 같은 이유를 알아보는 키(2.3절) |
| `first_seen_version`, `last_seen_version` | 처음과 마지막으로 나온 KG 버전 |
| `detail` | 문제의 자세한 내용. 값은 민감 등급을 따르고, 비밀 값은 없어요 |
| `proposal_ref` | 이 문제를 풀려고 연 제안. 없을 수 있어요 |
| `report` | `user_report`만. 보고한 KG 버전, 대상, 무엇이 어떻게 틀렸다는 주장, 증거 글, 보고자 |
| `cause_class` | `user_report`만. 원인 분류(2.6절). 처음엔 비어 있고, 알린 것을 받아 살핀 `operator`가 정해요 |

### 2.3 같은 이유로 묶기

수천 건을 하나씩 보지 않아요. 문제를 `cause_key`로 묶은 것이 문제 그룹(`issue_group`)이에요.

`cause_key` = (`kind`, 소스, 타입, `rule_ref`, 시그니처). 시그니처는 같은 이유이면 같게 나오는 짧은 모양이에요. `dangling_link`는 "찾는 키의 값이 이런 모양"이고, `attribute_conflict`는 "진 소스와 이긴 소스의 쌍과 속성 이름"이에요.

| 칸 | 뜻 |
|---|---|
| `group_id`, `kind`, `cause_key` | 그룹의 ID, 종류, 키 |
| `contact_refs` | 그룹에 든 문제의 담당자의 합 |
| `open_count` | 풀리지 않은 문제 수. 이 순서로 정렬해요 |
| `sample_issue_ids` | 눈으로 확인할 샘플 몇 건 |
| `first_seen_version` | 그룹이 처음 나온 KG 버전 |

예: 서버 교체 뒤 `asset_sheet`의 랙 이름이 `R-07`에서 `R07`로 바뀌어 `dangling_link` 312건이 한 그룹으로 보여요. 원인 후보는 "랙 이름의 표기"이고 고칠 곳은 다듬기 규칙이에요.

### 2.4 푸는 경로는 규칙을 고치는 것이다

낱개를 손으로 고쳐 KG에 넣는 경로는 없어요. 문제 그룹에서 푸는 흐름은 이래요. 고치는 경로 자체는 ADR-0014가 정해요.

```
문제 그룹(open)
  → 브랜치를 열고 제안을 만든다. 그룹이 in_progress로 바뀐다(제안과 연결)
  → 매핑, 다듬기, 이기는 소스, 예외 목록 중 까닭이 있는 규칙을 고친다
  → 검사와 후보 실행: 받아 둔 원본 기록으로 후보 KG를 만든다. 소스에 다시 가지 않는다
       그룹의 문제가 몇 건 사라지고 새로 생기는 문제가 없는지를 본다
  → 병합: 범위를 가진 다른 `approver`가 승인한다. 병합 직전에 최신 정의 위에서 다시 검사한다
  → 다음 동기화(흐름은 다음 변경)에서 그 문제가 더는 나오지 않으면 resolved
```

문제는 풀렸다고 지우지 않아요. 같은 이유가 다시 나오면 같은 `issue_id`가 `open`으로 돌아와요(재발이 보여요). 급할 때의 리버트와 묻는 쪽을 옛 KG 버전에 고정하는 길은 ADR-0014에 있어요.

**낱개 예외는 둘뿐이고 정의에 남아요.** 식별의 예외(같다 / 다르다)와 원본 레코드 제외(이 기록은 쓰지 않는다)예요. 둘 다 예외 목록의 한 줄이고, 정의의 항목이라 버전이 있고, 제안과 병합을 거치고, 내보내고 들일 수 있어요. 낱개 손질이 숨은 상태가 되지 않아요(ADR-0007). **값을 낱개로 덮어쓰는 예외는 없어요.** 값은 소스에서 고치거나 규칙으로 고쳐요.

### 2.5 담당자에게 보내기와 두 소스에 걸친 문제

- 문제는 관련한 소스, 타입, 정의 항목의 담당자에게 가요. 담당자는 사람이나 무리의 목록이고 연락처예요. 문제를 보고 푸는 권한은 담당자라서 생기지 않고 권한 부여에서 와요(ADR-0012).
- 한쪽 소스의 장비가 다른 쪽 소스의 랙을 가리키는데 없으면 `source_ids`에 둘이 들어가고 양쪽의 담당자에게 보여요. 여러 소스의 데이터셋을 읽는 링크 정의를 고쳐도 승인은 그 정의의 출발 타입을 범위에 가진 `approver`가 하고, 읽는 소스의 담당자에게는 알림만 가요(ADR-0012). 문제를 푸는 병합도 그 규칙을 따라요.
- 문제를 보는 것도 읽기 범위를 따라요. 범위 밖의 소스나 타입의 문제는 내용을 보이지 않아요.

### 2.6 사용자가 알린 것

- 사용자나 서비스 계정이 "이 객체의 이 값이 틀렸다"고 알려요. 알린 것은 `user_report` 문제가 되어 KG를 직접 고치지 않아요(같은 입력이면 같은 KG가 나온다는 성질을 지켜요).
- 원인은 그것을 받아 살핀 `operator`가 `cause_class`로 정해요(알린 사람이 정하지 않아요): `source_error`(소스가 틀림) / `rule_error`(규칙이 틀림) / `model_limit`(모델이 못 담음) / `stale`(최신이 아님). 나눈 뒤는 다른 문제와 같은 길이에요. `stale`이면 데이터 관측성 문서의 헬스 상태를 보고, `rule_error`면 규칙을 고쳐요. `source_error`는 소스의 담당자에게 알리는 것으로 끝나고 KG는 고치지 않아요.

## 3. 가용성

현실을 바꾸는 경로가 프락시움에 없으므로, 프락시움이 멈춰도 현실에는 아무 일이 없어요. 멈추면 안 되는 것은 **묻기**뿐이에요. 장애 중에 가장 많이 묻기 때문에 질의는 처음부터 이 등급으로 설계해요.

### 3.1 기능의 등급

| 기능 | 등급 | 어떻게 | 멈추면 |
|---|---|---|---|
| KG에 묻기(질의, 영향 범위, MCP) | **멈추면 안 됨** | 부르는 쪽은 언제나 API를 거쳐요. API와 질의 엔진이 여러 벌. 엔진은 올려 둔 투영으로 저장소 없이도 답해요 | 한 벌이 죽어도 답해요. 저장소가 죽으면 마지막 버전으로 답해요 |
| 원본 레코드, 정의, KG의 변경과 버전, 실행 기록, 감사 로그 | 잃으면 안 됨 | 저장소가 복제돼 있고 백업과 시점 복구가 있어요 | |
| 동기화와 흐름 | 잃으면 안 됨 | 워커가 여러 벌이고 죽은 일은 다른 워커가 이어받아요. 흐름은 붙잡혀도 받아서 쌓아요 | 마지막 버전에 머물고 신선도가 나빠져요 |
| 정의 고치기, 브랜치, 품질 보기 | 멈춰도 됨 | | 고치지 못해요. KG와 질의는 그대로예요 |

"여러 벌"은 여러 구역에 걸쳐 띄울 수 있어야 한다는 요구예요. 구역의 수와 배포 방법은 구현할 때 정해요.

### 3.2 역할 넷이 죽었을 때

실행 파일 하나가 역할을 골라 떠요(ADR-0006). 개발과 알파에서는 한 프로세스에 여럿을 함께 띄울 수 있어요.

| 역할 | 하는 일 | 한 벌이 죽으면 | 전부 죽으면 |
|---|---|---|---|
| API | 계약의 길과 MCP. 상태를 쥐지 않아요. 부르는 쪽은 엔진을 직접 부르지 않고 이것을 거쳐요 | 나머지가 받아요. 진행 중이던 요청은 다시 보내면 돼요(읽기는 멱등) | 밖에서 묻는 길이 끊겨요. 그래서 여러 구역에 걸쳐 여러 벌을 띄울 수 있어야 해요. 저장소가 멈춰도 묻기의 길은 답해요(로그인 토큰은 저장소 없이 확인하고, 무리와 역할의 짝은 나이 상한 15분의 사본을 써요. 3.3절) |
| 워커 | 수집부터 적용까지와 일정, 흐름의 실행기 | 하던 동기화나 흐름을 다른 워커가 이어받아요(4.4절). 소스마다 동시 상한은 그대로예요 | 동기화와 흐름이 멈추고 신선도가 나빠져요. 묻기는 그대로예요 |
| 질의 엔진 | 투영을 메모리에 올려 영향 범위와 길을 답해요 | 나머지가 답해요. 새 버전은 한 벌씩 갈아 끼우므로 갈아 끼우는 동안에도 한 벌 이상은 답해요 | 영향 범위와 길의 답이 멈춰요. 얕은 이웃은 SQL로 답할 수 있으니 저장소가 살아 있으면 이어져요 |
| 수집기 | 소스가 있는 분리망에서 받아 수집 엔벨로프로 보내요. 밖으로 나가는 연결만 써요. **소스 커서를 본체에 둬요** | 다른 벌이나 새로 띄운 벌이 본체에 있는 소스 커서부터 이어받아요. 한 벌뿐이면 그동안 그 망의 일이 기다리고 헬스 상태에 보여요. 두 벌 이상을 권해요 | 그 망의 소스에서 받기가 멈추고 신선도가 나빠져요. 다른 소스와 묻기는 그대로예요 |

### 3.3 저장소가 죽었을 때

| 무엇 | 어떻게 되나 |
|---|---|
| 묻기 | 이미 올려 둔 투영으로 마지막 KG 버전을 답해요. 답에 버전과 신선도가 적혀 있어요 |
| 수집 | 저장소에 쓸 수 없으니 새 수집과 적용이 멈춰요. 워커는 소스에 가지 않고 기다려요 |
| 정의 고치기, 브랜치, 품질 보기 | 멈춰요 |
| 운영 액션 | 감사 로그를 못 쓰므로 바꾸는 행위는 거절해요. 예외는 저장소 없이도 되는 급한 행위 셋(소스 멈추기, 비밀 값으로 소스 멈추기, 점검 모드 켜기)이에요. 역할의 디스크에 먼저 적어 두었다가 저장소가 돌아오면 감사 로그로 옮겨요. 디스크에도 못 적으면 거절해요(self-observability 5.4절) |
| 복구 뒤 | 리스 기한이 지난 일은 다른 워커가 이어받고, 멈춘 사이 밀린 일정은 소스마다 하나로 합쳐 한 번만 돌려요. 엔진은 가장 새 버전의 투영을 다시 올려요 |

**새로 뜨는 엔진.** 프로젝션 파일은 파일 보관 포트 뒤에 있고 엔진이 자기 디스크에 둬요. 그러나 새로 뜬 벌의 디스크는 비어 있어요. 올릴 투영이 없으면 엔진은 저장소에서 직접 지어 올려요. 파일 보관은 빨리 뜨기 위한 것이지 없으면 안 되는 것이 아니에요. 저장소도 파일 보관도 없으면 새 벌은 올릴 것이 없고, 이미 뜬 벌만 답해요.

**장애가 길어질 때.** 저장소 없이 답하는 동안 권한 캐시는 새로 읽지 못해서 나이가 늘어요. 나이 상한(15분)을 넘으면 `restricted` 이상은 거절하고 기본 부여의 읽기만 답해요. 그래서 장애가 길면 「묻기는 멈추지 않는다」가 기본 부여의 읽기로 줄어요(REQ-154). 정의 고치기와 받기는 계속 멈춰 있어요.

**쓰기가 감당되지 않을 때(갈아타는 차례).** 변경 속도의 임계값은 단위 셋(논리 변경 수, 물리적으로 쓰는 행 수, WAL의 바이트)을 함께 봐요(ADR-0009). 임계값을 넘으면 차례는 이래요. (1) 쓰기를 줄이는 손질(`volatile`의 같은 키는 마지막만 쓰기, 저장소 신호가 이끄는 되밀기). (2) 그래도 안 되면 메시지 기록 저장소 어댑터(클로즈드 베타)로 옮겨요. **KG 나누기는 쓰기 한계를 푸는 수단이 아니에요.** 영향 범위가 KG 하나 안에서만 돌아서, 서로 기대지 않는 환경만 다른 KG가 될 수 있어요. 처리량이 아닌 이유(밖의 소비자가 같은 기록을 되감아 읽음)이면 바로 옮길 수 있어요.

**메시지 기록 저장소는 제품이 띄우지 않아요.** 조직이 이미 운영하는 것에 붙고, 없는 배포는 PostgreSQL 어댑터로 가요. 제품은 붙는 데 필요한 조건(주제, 보관, 권한, 복제의 최소)을 문서로 내요. 그 저장소가 끊기면 KG와 묻기는 그대로예요(적용된 변경의 기록은 언제나 PostgreSQL). 받기가 밀려요. 수집기는 한도까지 쌓고 넘치면 소스를 멈추고 문제로 올려요. 보관 기간이 지나 되감지 못하면 그 소스를 전체 스냅샷 대조(스냅샷)로 다시 맞추고, 겹쳐 받은 것은 (소스, 자리)로 걸러져요. 붙은 저장소의 닿음, 지연, 쓰기 실패, 보관까지 남은 여유는 자기 관측성의 신호와 진단에 들어가요.

### 3.4 처음부터 지키는 것 여덟

나중에 고가용을 붙이려고 다시 쓰지 않게, 첫 코드부터 아래를 지켜요.

| # | 지키는 것 | 왜 필요한가 |
|---|---|---|
| 1 | 서버는 상태를 쥐지 않는다 | 어느 벌이 죽어도 다른 벌이 이어요. 벌을 늘리고 줄이는 일이 안전해요 |
| 2 | 모든 상태는 저장소 한 곳 | 백업과 복구의 대상이 한 곳이라 빠뜨릴 수 없어요 |
| 3 | 처리기는 멱등 | 죽은 일을 이어받거나 요청을 다시 보내도 같은 결과예요. 두 번 처리해서 두 번 적용되지 않아요 |
| 4 | 기록은 추가만 | 감사와 이력이 변조되지 않고, 복구 때 어디까지 갔는지 알 수 있어요 |
| 5 | KG 버전은 바뀌지 않는다 | 읽는 쪽이 한 버전만 보고, 엔진 벌들이 서로 같은 버전으로 답해요 |
| 6 | 프로세스 안의 단 하나뿐인 것에 기대지 않는다 | 일정표와 캐시가 한 프로세스에만 있으면 그 프로세스가 죽을 때 같이 사라져요. 파생물은 다시 만들 수 있어야 해요 |
| 7 | 같은 일정이 두 번 걸리지 않게 키로 막는다 | 벌이 여럿이면 일정 확인도 여럿이 해요. 키가 없으면 같은 동기화가 두 번 걸려요 |
| 8 | 서버 여럿이 함께 떠도 동기화나 흐름 하나는 한 곳에서만 돈다 | 같은 소스를 둘이 동시에 읽으면 소스에 부하가 두 배이고, 적용이 부딪쳐요 |

## 4. 동기화와 흐름의 실패 처리

### 4.1 다시 하기와 일정 멈춤

소스는 `snapshot`, `incremental`, `stream`, `stream` + 맞추기 가운데 받는 방식을 골라요(ADR-0008). 아래 규칙은 일정으로 도는 방식(`snapshot`, `incremental`, 맞추기)의 것이고, 흐름의 연결이 끊길 때도 다시 하기와 멈춤은 같아요.

| 일 | 규칙 | 기본값(설정, [기본값 표](defaults.md)) |
|---|---|---|
| 한 동기화 안의 요청이나 단계가 실패 | 물러났다 다시 해요(기다리는 시간을 늘려요) | 3번 |
| 그래도 실패 | 그 동기화는 실패로 기록하고, 새 KG 버전을 만들지 않아요. 마지막 정상 버전이 그대로예요 | |
| 동기화가 잇달아 실패 | 그 소스의 일정을 멈추고 알려요. 상태는 `failed` | 잇달아 5번 |
| 인증 실패 | 다시 하지 않고 바로 끊어요(소스 쪽 계정이 잠기지 않게, ADR-0008) | 즉시 |
| 안전장치가 막음(모양 바뀜, 대량 사라짐, 덜 받음) | 적용하지 않고 확인을 기다려요. 실패로 세지 않고 "기다림"으로 따로 세요 | |

일정이 멈춘 소스는 `operator`가 손으로 켜요. 소스 하나가 실패해도 다른 소스는 진행해요. 실패한 소스의 객체가 사라졌다고 보지 않아요(마지막 정상 수집을 유지하고 신선도만 나빠져요). 일정 멈춤과 안전장치의 멈춤은 알림 사건으로 나가고, 규칙과 받는 쪽은 ADR-0013이 정해요.

### 4.2 보류된 스트림

흐름에는 "온전한 수집"이 없어서 안 보인다고 물러나게 할 수 없어요. 삭제 사건과 맞추기만 물러나게 해요. 흐름의 안전장치는 비율을 봐요.

| 걸리는 때 | 어떻게 되나 |
|---|---|
| 짧은 시간에 너무 많이 사라지거나 바뀜 | 그 소스의 적용을 붙잡아요(`held`) |
| 받은 모양(컬럼, 자료형)이 바뀜 | 그 소스의 적용을 붙잡아요(`held`) |

**붙잡혀도 받는 것은 멈추지 않아요.** 받은 변경은 원본 레코드에 쌓여요. 잃지 않아요. 붙잡히지 않은 다른 소스의 적용도 그대로예요. 임계값의 숫자는 가정이고 소스마다 고칠 수 있어요.

흐름 하나(`feed_flow`)의 상태예요.

| 칸 | 뜻 |
|---|---|
| `source_id`, `dataset_id` | 어느 소스의 어느 데이터셋의 흐름인가 |
| `flow_state` | `running` / `held` / `paused` / `failed` |
| `held_reason` | 붙잡은 이유(어느 검사가 얼마나 넘었나). 비밀 값과 행의 내용은 없어요 |
| `held_since_seq` | 붙잡은 때까지 적용한 `change_seq`. 이 뒤로 쌓여요 |
| `queued_changes` | 붙잡힌 뒤 쌓인 변경 수 |
| `source_cursor` | 소스에서 어디까지 읽었는지 |

`operator`가 쌓인 것을 보고 둘 중 하나를 골라요.

| 고르기 | 하는 일 |
|---|---|
| 풀기(`release`) | 쌓인 변경을 받은 순서대로 적용해요. 한도가 있는 묶음으로 나눠 적용해요(오래 쌓였다 풀려도 한 번에 몰리지 않아요). 붙잡힌 변경은 풀릴 때 수집 순서(`ingest_seq`)를 받아요. 풀기 전에 드라이 런으로 차이를 보고, 안전장치가 걸린 이유를 확인한 것으로 기록해요 |
| 버리기(`discard`) | 쌓인 변경을 적용하지 않고 지나가요. 쌓인 원본 레코드는 지우지 않아요. 버린 뒤에는 전부 받아 맞춰서 어긋난 것을 바로잡아요. **맞추기를 할 수 있는 소스에서만 돼요.** 전부 받을 길이 없는 흐름은 버릴 수 없고 풀거나 붙잡아 둘 뿐이에요 |

붙잡힌 이유가 정의 탓이면(받은 모양이 바뀌어 매핑이 안 맞음) 풀기 전에 정의를 고쳐 병합해요. 병합된 자리부터 새 정의로 흐르고, 쌓인 변경은 새 정의로 적용돼요.

**쌓이는 양의 한도.** 붙잡힌 동안 쌓이는 변경은 조용히 버려지지 않아요. 쌓인 양이 보관의 한도에 가까워지면 알림이 올라가요. 한도를 넘으면 오래된 것부터 콜드 스토리지(ADR-0009)로 내려가요. 내려 둘 자리가 없으면, 소스가 소스 커서부터 다시 줄 수 있을 때는 그 소스의 수집을 멈추고 알려요. 다시 줄 수 없을 때는 계속 받아 쌓되 가장 높은 심각도로 알려요. 어느 쪽이든 조용히 버리지 않아요. 한도의 숫자는 가정이고 측정해서 정해요. 풀거나 버리는 일, 안전장치의 확인은 결과를 바꾸므로 수집 순서에 드는 사건이에요(kg-storage의 고정 목록).

### 4.3 알림과 문제 목록

붙잡힘, 일정 멈춤, 안전장치의 멈춤은 사건으로 나가요. 알림의 규칙과 묶기와 받는 쪽은 ADR-0013이 정해요. 같은 근본 원인의 알림은 하나로 묶여요. 알림은 문제 목록의 항목이 되므로 담당자의 받은 편지함은 하나예요.

### 4.4 워커가 죽은 일을 이어받기

한 동기화나 흐름은 한 곳에서만 돌아야 해요(3.4의 8번). 아래 장치 셋이 함께 지켜요. 모두 저장소 안에서 하고 따로 도는 조율 서비스를 두지 않아요(ADR-0009).

| 장치 | 어떻게 |
|---|---|
| 소스당 하나만 | 같은 소스(흐름은 데이터셋)의 `queued` 또는 `running` 실행은 하나만 있을 수 있어요. 저장소의 유일 제약이 막아요 |
| 일정의 키 | 일정이 만드는 실행에는 (소스, 시각 칸)으로 낸 키가 있어요. 워커 여럿이 같은 칸을 만들려 해도 하나만 들어가요 |
| 점유와 리스 기한 | 워커가 실행을 집으면 `lease_owner`와 `lease_until`을 써요. 일하는 동안 `lease_until`을 계속 미뤄요. 워커가 죽으면 미뤄지지 않아 기한이 지나요. 점유에는 실행기의 의미 버전이 들어서, 올리는 중에 낮은 버전의 워커가 적용을 쥐지 못해요 |

`sync_run`의 칸이에요.

| 칸 | 뜻 |
|---|---|
| `sync_id`, `source_id` | 실행과 소스 |
| `schedule_key` | 일정의 키. 손으로 돌린 것은 비어 있어요 |
| `state` | `queued` / `running` / `waiting_confirmation` / `succeeded` / `failed` / `abandoned` |
| `attempt` | 워커가 일을 쥘 때마다 오르는 번호 |
| `lease_owner`, `lease_until` | 점유한 워커와 기한 |
| `stage`, `stage_counts` | 지금 단계와 단계마다 들어온 수·나간 수·떨어진 수·시간 |
| `guard_verdict` | 안전장치의 판정과 이유 |
| `kg_version` | 만들어진 KG 버전. 없으면 비어 있어요 |
| `error_code` | 오류 코드. 비밀 값과 행의 내용 없이 |

**이어받는 규칙**
- 리스 기한이 지난 `running` 실행은 다른 워커가 `attempt`를 올리며 집어요.
- 모든 쓰기는 자기 `attempt`가 지금 번호와 같을 때만 받아들여져요. 죽은 줄 알았던 워커가 늦게 깨어나 쓰려 해도 번호로 거절돼요(두 곳에서 도는 일을 막는 마지막 장치).
- 수집 단계에서 죽었으면 수집을 처음부터 다시 해요. 같은 기록은 복제되지 않으므로(ADR-0008) 안전하고, 중간에 끊긴 수집은 온전한 수집이 아니에요.
- 수집이 끝난 뒤에 죽었으면 받아 둔 원본 레코드로 다음 단계부터 이어 돌려요. 소스에 다시 가지 않아요.
- 흐름은 소스에서 소스 커서와 그 적용을 한 트랜잭션에 묶고 번호로 겹침을 막아요(ADR-0006). 이어받은 워커는 저장된 `source_cursor`부터 읽으므로 같은 변경이 두 번 적용되지 않고 빠지지도 않아요.
- 적용은 짧은 트랜잭션 하나라서(ADR-0009) 반쯤 적용된 상태가 없어요. 죽었으면 적용은 안 된 거예요. 큰 적용은 `change_seq` 여러 개로 쪼개요. 읽는 쪽이 반쯤 든 배치를 보지 않게 읽기 워터마크(`readable_through`)는 배치가 끝날 때만 올라요(`min_seq`와 `serving_pin`이 이것을 봐요). 큰 적용 중 흐름의 적용 지연은 클로즈드 베타에서 재요.
- 이어받기를 되풀이해도 끝나지 않으면 `abandoned`로 두고 실패로 세요.

## 5. 표준 모델과 제품의 업그레이드

제품이 오르면 표준 모델도 올라요(ADR-0007).

- **덮어쓰지 않아요.** 제품 표준 타입(`std`)은 제품이 싣고 배포 안에서는 고치지 않아요. 조직이 표준 타입을 맞춘 것은 `org` 층의 오버레이이고, 사용자 정의 타입은 `ext` 층이에요. 업그레이드가 오버레이와 사용자 정의 타입과 매핑을 바꾸지 않아요.
- **타입은 지우지 않고 물러나요.** 물러난 타입은 이력에 남고 기존 객체도 지워지지 않아요.
- **알려요, 저절로 고치지 않아요.** 물러난 타입을 쓰는 매핑이 있으면 `retired_type_in_use` 문제가 그 매핑의 담당자에게 올라요. 물러난 타입의 `superseded_by`가 후속 타입을 가리키면 알림에 함께 보여요. 같은 물러난 타입 하나에서 온 문제는 한 그룹으로 묶여요.
- **정의를 옮기는 것은 규칙을 고치는 일과 같은 길이에요.** 매핑을 새 타입으로 옮기는 변경은 호환성을 깨는 변경이라서 옮김을 함께 적어요(ADR-0014). 브랜치에서 옮기고, 드라이 런으로 차이를 보고, 승인을 받아 병합해요. 옮기기 전에도 받는 데이터는 그대로 받아져요.
- **표준 모델이 오른 뒤의 첫 적용은 정의를 고친 뒤의 첫 적용과 같은 규칙이에요.** 위험의 등급 R2부터 사람이 차이를 보고 확인하고, 낮은 등급은 저절로 적용하고 알려요(definitions). 표준 모델과 `sys` 타입은 옮김의 한 걸음으로 저장소에 실려요.

## 6. 백업과 복구: 진실과 파생물

저장과 백업의 방법은 [KG의 저장과 버전](kg-storage.md)에 있어요. 여기서는 운영의 눈으로 무엇이 진실이고 무엇이 다시 만들 수 있는 것인지만 나눠요.

| 구분 | 무엇 | 복구 뒤 |
|---|---|---|
| 진실(잃으면 안 됨) | 원본 레코드(내용을 걷어 낸 표시를 포함해요. 샌 값은 해시와 자리만 남기고 지워요), 정의와 판과 브랜치와 제안, KG의 변경(`change_seq`)과 버전, 소스에서 소스 커서, 실행 기록, 감사 로그, 사람이 알린 `user_report`와 문제 상태의 바뀜 | 백업과 시점 복구에서 되살려요 |
| 파생물(다시 만들 수 있음) | 프로젝션, 규칙이 낸 문제 항목, 문제 그룹 | KG와 정의에서 다시 만들어요. 지표의 복구는 [데이터 관측성](data-observability.md)을 따라요 |

- 시점 복구로 돌아가면 그 뒤의 KG 변경과 버전이 사라져요. 소스를 다시 읽으면 같은 입력에서 같은 버전이 나와요(ADR-0009). 복구할 때마다 KG의 **세대** 번호가 올라가요. 세대는 `as_of`, 커서, 이벤트 ID, `min_seq`에 실려서 복구 전의 것을 쥔 밖의 소비자와 에이전트는 `conflict.generation_changed`를 받고 처음부터 다시 맞춰요. 메시지 기록 저장소를 쓸 때 복구 뒤 수집 순서가 다시 굳으면 처음과 다를 수 있어서 같은 규칙이 걸려요.
- **소스에서 다시 받을 수 없는 것**이 있어요. 올린 엑셀 파일, 수집 엔벨로프로 받은 기록, 흐름으로만 오는 사건이에요(맞추기는 지금 상태만 주므로, 지나간 사건을 다시 주는지는 소스에 달렸어요, 가정). 이것의 원본 레코드는 백업이 유일한 사본이라 복구 훈련에 반드시 넣어요.
- 복구 뒤 흐름은 저장된 `source_cursor`부터 이어 읽고, 소스가 그 자리를 더는 주지 못하면 맞추기로 바탕을 다시 만들어요.

## 7. 알려진 한계

- 조사에서 확인하지 못한 것(여러 제품의 안쪽 동작, 페일오버 시간, 큐의 실제 지연, 이어서 받는 소스의 부하)이 있어 8절의 가정 표시가 붙은 숫자는 측정해서 고쳐요.
- 문제 그룹의 시그니처가 너무 넓으면 다른 이유가 섞이고, 너무 좁으면 잘게 쪼개져요. 클로즈드 베타에서 고쳐요.
- 흐름의 붙잡는 임계값이 낮으면 `operator`에게 확인할 일이 몰리고, 높으면 오염이 들어가요. 소스마다 고치는 경로가 있지만 클로즈드 베타에서 측정해서 기본값을 고쳐요.
- 보류된 스트림이 오래 쌓이면 풀 때 적용할 양이 커져요(묶음으로 나눠 적용해요). 한도의 숫자는 아직 측정하지 않았어요. 병합 줄이 막혔을 때 쌓이는 에이전트의 제안은 한도(설정)가 막아요.
- 프로토타입의 숫자(저장소 입출력 없이 측정한 것)는 한계가 있어요. 메시지 기록 저장소로 갈아타는 임계값은 추정이에요(ADR-0009).

## 8. 기본값이고 클로즈드 베타에서 측정해서 정한다

| 숫자 | 지금 쥔 값 | 어떻게 측정해서 정하나 |
|---|---|---|
| 다시 하기 횟수 | 3번(기본값) | 소스의 오류 모양별로 일시 오류가 몇 번 안에 풀리는지 |
| 일정 멈춤의 연속 실패 수 | 5번(기본값) | 거짓 멈춤(알림 피로)과 늦은 멈춤(소스 부하)의 균형 |
| 대량 사라짐의 기준(배치) | ADR-0008의 기본값 | 샘플 테스트 |
| 흐름을 붙잡는 비율과 시간 | 5분 동안 5% 이상(그리고 50건 이상)(기본값) | 지어낸 흐름에 흩뜨린 입력을 넣어 |
| 리스 기한, 리스 연장 간격 | 정하지 않음 | 가장 긴 단계의 시간과 워커 장애 주입 |
| 메시지 기록 저장소로 갈아타는 임계값 | 논리 변경 수, 물리적으로 쓰는 행 수, WAL의 바이트 셋을 함께 봐요. 초당 2~3만은 논리 변경 수의 추정이에요(WAL이 3~4배라는 것도 추정) | 클로즈드 베타에서 저장소 입출력을 넣어 셋을 따로 측정해서 |
| 잃어도 되는 시간(RPO) | 정족수 방식의 동기 복제(후보 둘 이상 중 하나가 받으면 커밋)로 커밋된 기록은 0을 목표 가정 | 커밋 지연과 복구 훈련 |
| 복구 시간(RTO) | 한 벌의 장애는 수십 초에서 2분, 저장소 전체의 상실은 수 시간(둘 다 가정) | 장애 주입(구역 격리, 주 저장소 강제 종료, 백업 저장 위치 단절, 비밀 저장소 단절) |
| 투영을 올리는 시간 | 정하지 않음 | 지어낸 3천만 객체로(ADR-0009의 재는 순서) |

## 10. 관련 결정과 요구사항

- 결정: [ADR-0011](adr/0011-kg-operations.md). 이어진 것은 ADR-0006(역할 넷, 언어), ADR-0007(근거 등급, 식별, 표준 모델), ADR-0008(받는 방식, 안전장치), ADR-0009(버전, 저장소), ADR-0010(답에 붙는 것), ADR-0012(권한, 담당자, 감사), ADR-0013(데이터 관측성), ADR-0014(정의의 버전과 브랜치).
- 요구사항: REQ-151(문제 목록은 규칙으로 푼다), REQ-154(가용성의 등급). 품질 지표와 신선도(REQ-150, REQ-152)와 관측성(REQ-180~189)은 ADR-0013, 감사 로그(REQ-164)은 ADR-0012의 것이에요.
