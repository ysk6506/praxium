# KG 운영

KG를 구축하는 일(수집)과 사용하는 일(질의) 사이에서 날마다 일어나는 일을 다뤄요. 해결하지 못한 문제를 규칙으로 해결하고, 어떤 구성 요소에 장애가 나도 질의는 멈추지 않게 하고, 수집 경로가 멈춰도 데이터를 잃지 않게 하는 설계예요. 숫자는 제품에 내장되는 기본값(설정)이거나 측정하지 않은 가정이에요(8절). 측정해서 조정하는 일은 클로즈드 베타에서 해요.

데이터가 잘 들어오는지 측정하고 보여 주는 일은 이 문서의 범위가 아니에요. 품질 지표, 신선도, 헬스 상태, 목표, 이상 탐지, 알림 규칙, 실행 소스 탐색, 지표와 로그 내보내기는 [데이터 관측성](data-observability.md)(ADR-0013)이 정해요. 정의를 수정하는 경로(브랜치, 제안, 검사, 병합, 리버트)는 [정의의 버전과 브랜치](definitions.md)(ADR-0014)가, 권한과 감사는 [접근 제어](access-control.md)(ADR-0012)가 정해요. 이 문서는 그 지표가 가리키는 문제를 어떻게 해결하고, 데이터가 멈추지 않고 흐르게 하는 일을 다뤄요.

## 1. 목적과 다루는 질문

| 쟁점 | 답 |
|---|---|
| 해결하지 못한 것은 어디로 가는가 | 문제 목록으로 가고, 담당자가 규칙을 수정해 해결해요(2절) |
| 어떤 구성 요소에 장애가 나면 무엇이 멈추는가 | 기능마다 등급을 정했어요. 질의는 멈추지 않아요(3절) |
| 동기화와 스트림이 실패하면 | 마지막 정상 버전을 지키고, 스케줄을 중지하고, 스트림은 적용을 보류하되 수집은 계속해요(4절) |
| 제품을 업그레이드하면 | 폐기된 타입을 알리고 자동으로 수정하지 않아요(5절) |
| 복구하면 무엇이 돌아오는가 | 진실은 복원하고 파생 데이터는 다시 만들어요(6절) |
| 넘겨받은 쟁점 "운영 경로가 되면 멈추면 안 된다" | 현실을 바꾸는 경로가 프락시움에 없으니 멈추면 안 되는 것은 질의예요. 위임과 조치의 등급은 엔드투엔드(E2E) 프로세스를 구체화할 때 다시 매겨요 |

운영하는 사람이 날마다 보는 것 중 이 문서의 것은 4가지예요. 헬스 상태와 지표는 데이터 관측성 문서에서 봐요. 모두 API로 읽고 조작해요(화면은 다른 리포지토리가 같은 API로 만들어요. ADR-0016).

| 보는 것 | 출처 | 조치하는 때 |
|---|---|---|
| 문제 그룹: 건수 순, 담당자, 연결된 제안 | 문제 목록 | 차단 사유가 가장 많은 것부터 규칙을 수정해요 |
| 보류된 스트림과 안전장치가 멈춘 적용 | 동기화 실행, 스트림 | 쌓인 변경을 확인하고 해제하거나 버려요 |
| 스케줄이 중지된 소스 | 소스의 스케줄 | 원인을 수정하고 다시 켜요 |
| 사용자가 신고한 것 중 새 것 | 문제 목록 | 원인을 분류해요(2.6절) |

## 2. 문제 목록

### 2.1 문제의 종류

| 종류(`issue_kind`) | 설명 | 생성 단계 |
|---|---|---|
| `dangling_link` | 링크 정의가 연결하려 했는데 끝점이 없다(연결하지 못한 링크) | 링크 |
| `attribute_conflict` | 둘 이상의 소스가 같은 속성에 다른 값을 제공했고 채택되지 않은 값이 있다 | 식별과 병합 |
| `invalid_value` | 틀린 값. 데이터 타입, 단위, 열거값, 범위에 어긋난다 | 정제, 매핑 |
| `identity_candidate` | 같은 것일 수 있는 객체 둘. 확률로 만든 제안이라 자동으로 합치지 않는다 | 식별과 병합 |
| `completeness_mismatch` | 피드가 "이 타입을 전부 준다"고 선언(`completeness_declaration`)했는데 다른 소스나 링크가 그 타입의 객체를 가리킨다, 또는 선언한 수와 수신한 수가 다르다 | 링크, 안전장치 |
| `unattached_value` | 속성만 덧붙이는 피드가 준 값인데, 기한 안에 붙을 객체가 생기지 않았다(붙을 대상이 없는 값) | 매핑 |
| `intent_observation_mismatch` | 설정(의도)과 관측이 어긋난다. 예: 경로 4개를 쓰도록 설정됐는데 2개만 보인다. 버릴 충돌이 아니라 가치 있는 정보다 | 식별과 병합 |
| `expectation_violation` | 기대 조건을 위반했고 강도가 `warn`이다(`fail`은 적용을 중단한다) | 정제, 안전장치 |
| `retired_type_in_use` | 표준 모델에서 폐기된 타입을 쓰는 매핑이 있다(5절) | 제품 업그레이드 뒤 |
| `user_report` | 사용자가 KG가 틀렸다고 신고했다 | 사람 |
| `data_alert` | 데이터 헬스 상태의 알림(근본 원인 하나에 묶인 것). 규칙은 ADR-0013이 정한다 | 관측 |

종류는 고정 목록이고, 새 종류는 결정 기록으로 추가해요. 알림도 문제 목록의 항목이 돼요. 수신함은 하나예요(ADR-0013).

### 2.2 문제 하나의 필드

테이블 `issue`예요. 이름은 영어 snake_case예요.

| 필드 | 설명 |
|---|---|
| `issue_id` | 문제의 ID. 같은 원인에서 같은 대상이면 같은 ID가 나와요(결정적). 동기화마다 새로 생기지 않아요 |
| `kg_id` | 어느 KG인지 |
| `kind` | 2.1의 종류 |
| `status` | `open` / `in_progress` / `resolved` (2.4절) |
| `subject_ref` | 대상. 객체 ID, 링크 ID, 원본 레코드의 참조 중 하나 이상 |
| `rule_ref` | 이 문제를 발생시킨 정의 항목과 버전(매핑, 링크 정의, 식별 규칙, 기대 조건, 안전장치) |
| `source_ids` | 관련된 소스. 하나이거나 둘 이상(2.5절) |
| `type_ref` | 관련된 객체 타입이나 링크 타입. 없을 수도 있어요 |
| `contact_refs` | 담당자. 소스, 타입, 정의 항목에 지정된 담당자를 모아요 |
| `cause_key` | 같은 원인을 식별하는 키(2.3절) |
| `first_seen_version`, `last_seen_version` | 처음과 마지막으로 나타난 KG 버전 |
| `detail` | 문제의 자세한 내용. 값은 민감 등급을 따르고, 시크릿은 없어요 |
| `proposal_ref` | 이 문제를 해결하려고 연 제안. 없을 수 있어요 |
| `report` | `user_report`만. 신고한 KG 버전, 대상, 무엇이 어떻게 틀렸다는 주장, 증거 텍스트, 신고자 |
| `cause_class` | `user_report`만. 원인 분류(2.6절). 처음에는 비어 있고, 신고를 받아 검토한 `operator`가 정해요 |

### 2.3 같은 원인으로 묶기

수천 건을 하나씩 보지 않아요. 문제를 `cause_key`로 묶은 것이 문제 그룹(`issue_group`)이에요.

`cause_key` = (`kind`, 소스, 타입, `rule_ref`, 시그니처). 시그니처는 같은 원인이면 같게 나오는 짧은 형태예요. `dangling_link`는 "찾는 키의 값이 이런 형태"이고, `attribute_conflict`는 "채택되지 않은 소스와 채택된 소스의 쌍과 속성 이름"이에요.

| 필드 | 설명 |
|---|---|
| `group_id`, `kind`, `cause_key` | 그룹의 ID, 종류, 키 |
| `contact_refs` | 그룹에 속한 문제의 담당자를 합친 것 |
| `open_count` | 해결되지 않은 문제 수. 이 순서로 정렬해요 |
| `sample_issue_ids` | 눈으로 확인할 샘플 몇 건 |
| `first_seen_version` | 그룹이 처음 나온 KG 버전 |

예: 서버 교체 뒤 `asset_sheet`의 랙 이름이 `R-07`에서 `R07`로 바뀌어 `dangling_link` 312건이 한 그룹으로 보여요. 원인 후보는 "랙 이름의 표기"이고 수정할 곳은 정제 규칙이에요.

### 2.4 해결 경로는 규칙을 수정하는 것이다

개별 항목을 손으로 수정해 KG에 넣는 경로는 없어요. 문제 그룹을 해결하는 흐름은 다음과 같아요. 수정 경로 자체는 ADR-0014가 정해요.

```
문제 그룹(open)
  → 브랜치를 열고 제안을 만든다. 그룹이 in_progress로 바뀐다(제안과 연결)
  → 매핑, 정제, 우선 소스, 예외 목록 중 원인이 되는 규칙을 수정한다
  → 검사와 드라이 런: 수집해 둔 원본 레코드로 후보 KG를 만든다. 소스에 다시 접속하지 않는다
       그룹의 문제가 몇 건 줄었는지, 새로 생기는 문제가 없는지를 확인한다
  → 병합: 범위를 가진 다른 `approver`가 승인한다. 병합 직전에 최신 정의 위에서 다시 검사한다
  → 다음 동기화(스트림은 다음 변경)에서 그 문제가 더는 나오지 않으면 resolved
```

문제는 해결됐다고 삭제하지 않아요. 같은 원인이 다시 나타나면 같은 `issue_id`가 `open`으로 돌아와요(재발이 보여요). 긴급 리버트와 질의를 이전 KG 버전에 고정하는 방법은 ADR-0014에 있어요.

**개별 예외는 2가지뿐이고 정의에 남아요.** 식별 예외(같다 / 다르다)와 원본 레코드 제외(이 레코드는 쓰지 않는다)예요. 둘 다 예외 목록의 항목이고, 정의 항목이라 버전이 있고, 제안과 병합을 거치고, 내보내고 가져올 수 있어요. 개별 수동 조정이 숨은 상태가 되지 않아요(ADR-0007). **값을 개별로 덮어쓰는 예외는 없어요.** 값은 소스에서 수정하거나 규칙으로 수정해요.

### 2.5 담당자에게 전달하기와 두 소스에 걸친 문제

- 문제는 관련된 소스, 타입, 정의 항목의 담당자에게 전달돼요. 담당자는 사람이나 그룹의 목록이고 연락처예요. 문제를 보고 해결하는 권한은 담당자라서 생기는 것이 아니라 권한 부여에서 와요(ADR-0012).
- 한쪽 소스의 장비가 다른 쪽 소스의 랙을 가리키는데 그 랙이 없으면 `source_ids`에 두 소스가 들어가고 양쪽 담당자에게 보여요. 여러 소스의 데이터셋을 읽는 링크 정의를 수정해도 승인은 그 정의의 출발 타입을 범위에 가진 `approver`가 하고, 읽는 소스의 담당자에게는 알림만 가요(ADR-0012). 문제를 해결하는 병합도 같은 규칙을 따라요.
- 문제를 보는 것도 읽기 범위를 따라요. 범위 밖의 소스나 타입의 문제는 내용을 보여 주지 않아요.

### 2.6 사용자 신고

- 사용자나 서비스 계정이 "이 객체의 이 값이 틀렸다"고 신고해요. 신고는 `user_report` 문제가 되고 KG를 직접 수정하지 않아요(같은 입력이면 같은 KG가 나온다는 성질을 지켜요).
- 원인은 신고를 받아 검토한 `operator`가 `cause_class`로 정해요(신고한 사람이 정하지 않아요): `source_error`(소스가 틀림) / `rule_error`(규칙이 틀림) / `model_limit`(모델이 표현하지 못함) / `stale`(최신이 아님). 분류한 뒤는 다른 문제와 같은 경로예요. `stale`이면 데이터 관측성 문서의 헬스 상태를 보고, `rule_error`면 규칙을 수정해요. `source_error`는 소스의 담당자에게 알리는 것으로 끝나고 KG는 수정하지 않아요.

## 3. 가용성

현실을 바꾸는 경로가 프락시움에 없으므로, 프락시움이 멈춰도 현실에는 아무 일이 없어요. 멈추면 안 되는 것은 **질의**뿐이에요. 장애 중에 질의가 가장 많이 몰리기 때문에 질의는 처음부터 이 등급으로 설계해요.

### 3.1 기능의 등급

| 기능 | 등급 | 방법 | 멈추면 |
|---|---|---|---|
| KG 질의(질의, 영향 범위, MCP) | **멈추면 안 됨** | 호출하는 쪽은 항상 API를 거쳐요. API와 질의 엔진을 여러 인스턴스로 운영해요. 엔진은 로드해 둔 프로젝션으로 스토리지 없이도 답해요 | 인스턴스 하나에 장애가 나도 답해요. 스토리지에 장애가 나면 마지막 버전으로 답해요 |
| 원본 레코드, 정의, KG의 변경과 버전, 실행 이력, 감사 로그 | 잃으면 안 됨 | 스토리지를 복제하고 백업과 시점 복구가 있어요 | |
| 동기화와 스트림 | 잃으면 안 됨 | 워커를 여러 인스턴스로 운영하고 장애 난 작업은 다른 워커가 이어받아요. 스트림은 적용이 보류돼도 수집해서 쌓아요 | 마지막 버전에 머물고 신선도가 나빠져요 |
| 정의 수정, 브랜치, 품질 조회 | 멈춰도 됨 | | 수정할 수 없어요. KG와 질의는 그대로예요 |

"여러 인스턴스"는 여러 가용 영역에 걸쳐 띄울 수 있어야 한다는 요구예요. 가용 영역의 수와 배포 방법은 구현할 때 정해요.

### 3.2 역할 4종에 장애가 났을 때

실행 파일 하나가 역할을 골라 기동해요(ADR-0006). 개발과 알파에서는 한 프로세스에 여러 역할을 함께 띄울 수 있어요.

| 역할 | 하는 일 | 인스턴스 하나에 장애가 나면 | 전부 장애가 나면 |
|---|---|---|---|
| API | 계약의 경로와 MCP. 상태를 보유하지 않아요. 호출하는 쪽은 엔진을 직접 부르지 않고 이것을 거쳐요 | 나머지가 받아요. 진행 중이던 요청은 다시 보내면 돼요(읽기는 멱등) | 외부에서 질의하는 경로가 끊겨요. 그래서 여러 가용 영역에 걸쳐 여러 인스턴스를 띄울 수 있어야 해요. 스토리지가 멈춰도 질의 경로는 답해요(로그인 토큰은 스토리지 없이 검증하고, 그룹과 역할의 조합은 경과 시간 상한 15분의 사본을 써요. 3.3절) |
| 워커 | 수집부터 적용까지와 스케줄, 스트림의 실행기 | 하던 동기화나 스트림을 다른 워커가 이어받아요(4.4절). 소스별 동시 실행 상한은 그대로예요 | 동기화와 스트림이 멈추고 신선도가 나빠져요. 질의는 그대로예요 |
| 질의 엔진 | 프로젝션을 메모리에 로드해 영향 범위와 경로를 답해요 | 나머지가 답해요. 새 버전은 한 인스턴스씩 교체하므로 교체하는 동안에도 한 인스턴스 이상은 답해요 | 영향 범위와 경로 질의의 응답이 멈춰요. 얕은 이웃 조회는 SQL로 답할 수 있으니 스토리지가 정상이면 이어져요 |
| 수집기 | 소스가 있는 분리망에서 데이터를 수집해 수집 엔벨로프로 보내요. 외부로 나가는 연결만 써요. **소스 커서를 본체에 둬요** | 다른 인스턴스나 새로 띄운 인스턴스가 본체에 있는 소스 커서부터 이어받아요. 인스턴스가 하나뿐이면 그동안 그 망의 작업이 대기하고 헬스 상태에 표시돼요. 2개 이상을 권장해요 | 그 망의 소스에서 수집이 멈추고 신선도가 나빠져요. 다른 소스와 질의는 그대로예요 |

### 3.3 스토리지에 장애가 났을 때

| 대상 | 어떻게 되나 |
|---|---|
| 질의 | 이미 로드된 프로젝션으로 마지막 KG 버전을 답해요. 응답에 버전과 신선도가 적혀 있어요 |
| 수집 | 스토리지에 쓸 수 없으니 새 수집과 적용이 멈춰요. 워커는 소스에 접속하지 않고 대기해요 |
| 정의 수정, 브랜치, 품질 조회 | 멈춰요 |
| 운영 액션 | 감사 로그를 쓸 수 없으므로 상태를 바꾸는 액션은 거절해요. 예외는 스토리지 없이도 가능한 긴급 액션 3종(소스 중지, 시크릿 기준 소스 중지, 점검 모드 켜기)이에요. 역할의 디스크에 먼저 기록해 두었다가 스토리지가 복구되면 감사 로그로 옮겨요. 디스크에도 기록하지 못하면 거절해요(self-observability 5.4절) |
| 복구 뒤 | 리스 기한이 지난 작업은 다른 워커가 이어받고, 멈춘 사이 밀린 스케줄은 소스마다 하나로 합쳐 한 번만 실행해요. 엔진은 가장 최신 버전의 프로젝션을 다시 로드해요 |

**새로 기동하는 엔진.** 프로젝션 파일은 파일 스토어 포트 뒤에 있고 엔진이 자기 디스크에 둬요. 그러나 새로 기동한 인스턴스의 디스크는 비어 있어요. 로드할 프로젝션이 없으면 엔진은 스토리지에서 직접 구축해 로드해요. 파일 스토어는 빠른 기동을 위한 것이지 필수가 아니에요. 스토리지에도 파일 스토어에도 없으면 새 인스턴스는 로드할 것이 없고, 이미 기동한 인스턴스만 답해요.

**장애가 길어질 때.** 스토리지 없이 답하는 동안 권한 캐시를 새로 읽지 못해서 경과 시간이 늘어나요. 경과 시간 상한(15분)을 넘으면 `restricted` 이상은 거절하고 기본 부여된 읽기만 답해요. 그래서 장애가 길어지면 「질의는 멈추지 않는다」가 기본 부여된 읽기로 줄어요(REQ-154). 정의 수정과 수집은 계속 멈춰 있어요.

**쓰기가 감당되지 않을 때(전환 순서).** 변경 속도의 임계값은 지표 3가지(논리 변경 수, 물리적으로 쓰는 행 수, WAL 바이트)를 함께 봐요(ADR-0009). 임계값을 넘으면 순서는 다음과 같아요. (1) 쓰기를 줄이는 조치(`volatile`의 같은 키는 마지막 값만 쓰기, 스토리지 신호에 따른 백프레셔). (2) 그래도 안 되면 메시지 로그 스토리지 어댑터(클로즈드 베타)로 전환해요. **KG 분할은 쓰기 한계를 푸는 수단이 아니에요.** 영향 범위가 KG 하나 안에서만 계산되므로, 서로 의존하지 않는 환경만 별도 KG가 될 수 있어요. 처리량이 아닌 이유(외부 소비자가 같은 로그를 되감아 읽음)이면 바로 전환할 수 있어요.

**메시지 로그 스토리지는 제품이 기동하지 않아요.** 조직이 이미 운영하는 것에 연결하고, 없는 배포는 PostgreSQL 어댑터를 써요. 제품은 연결에 필요한 조건(토픽, 보존, 권한, 최소 복제본 수)을 문서로 제공해요. 그 스토리지가 끊겨도 KG와 질의는 그대로예요(적용된 변경의 기록은 언제나 PostgreSQL). 수집이 밀려요. 수집기는 한도까지 쌓고 넘치면 소스를 중지하고 문제로 올려요. 보존 기간이 지나 되감지 못하면 그 소스는 전체 스냅샷으로 정합성 대조를 다시 하고, 중복 수신한 것은 (소스, 커서)로 걸러져요. 연결된 스토리지의 접속 가능 여부, 지연, 쓰기 실패, 보존 기한까지 남은 여유는 자기 관측성의 신호와 진단에 포함돼요.

### 3.4 처음부터 지키는 것 8가지

나중에 고가용성을 붙이려고 다시 쓰지 않게, 첫 코드부터 아래를 지켜요.

| # | 지키는 것 | 이유 |
|---|---|---|
| 1 | 서버는 상태를 보유하지 않는다 | 어느 인스턴스에 장애가 나도 다른 인스턴스가 이어받아요. 인스턴스를 늘리고 줄이는 일이 안전해요 |
| 2 | 모든 상태는 스토리지 한 곳 | 백업과 복구의 대상이 한 곳이라 빠뜨릴 수 없어요 |
| 3 | 처리기는 멱등 | 장애 난 작업을 이어받거나 요청을 다시 보내도 같은 결과예요. 두 번 처리해서 두 번 적용되지 않아요 |
| 4 | 기록은 추가만 | 감사 로그와 이력이 변조되지 않고, 복구 때 어디까지 처리했는지 알 수 있어요 |
| 5 | KG 버전은 바뀌지 않는다 | 읽는 쪽이 한 버전만 보고, 엔진 인스턴스들이 서로 같은 버전으로 답해요 |
| 6 | 프로세스 안의 단일 항목에 의존하지 않는다 | 스케줄과 캐시가 한 프로세스에만 있으면 그 프로세스에 장애가 날 때 함께 사라져요. 파생 데이터는 다시 만들 수 있어야 해요 |
| 7 | 같은 스케줄이 두 번 실행되지 않게 키로 막는다 | 인스턴스가 여럿이면 스케줄 확인도 여럿이 해요. 키가 없으면 같은 동기화가 두 번 실행돼요 |
| 8 | 서버 여러 대가 함께 기동해도 동기화나 스트림 하나는 한 곳에서만 실행한다 | 같은 소스를 둘이 동시에 읽으면 소스 부하가 2배이고, 적용이 충돌해요 |

## 4. 동기화와 스트림의 실패 처리

### 4.1 재시도와 스케줄 중지

소스는 `snapshot`, `incremental`, `stream`, `stream` + 정합성 대조 중에서 수집 방식을 골라요(ADR-0008). 아래 규칙은 스케줄로 실행되는 방식(`snapshot`, `incremental`, 정합성 대조)의 것이고, 스트림 연결이 끊길 때도 재시도와 중지는 같아요.

| 상황 | 규칙 | 기본값(설정, [기본값 표](defaults.md)) |
|---|---|---|
| 한 동기화 안의 요청이나 단계가 실패 | 백오프하며 재시도해요(대기 시간을 늘려요) | 3회 |
| 그래도 실패 | 그 동기화는 실패로 기록하고, 새 KG 버전을 만들지 않아요. 마지막 정상 버전이 그대로예요 | |
| 동기화가 연속으로 실패 | 그 소스의 스케줄을 중지하고 알려요. 상태는 `failed` | 연속 5회 |
| 인증 실패 | 재시도하지 않고 바로 연결을 끊어요(소스 쪽 계정이 잠기지 않게, ADR-0008) | 즉시 |
| 안전장치가 차단함(스키마 변경, 대량 사라짐, 수집량 부족) | 적용하지 않고 확인을 기다려요. 실패로 세지 않고 "대기"로 따로 세요 | |

스케줄이 중지된 소스는 `operator`가 수동으로 켜요. 소스 하나가 실패해도 다른 소스는 계속 진행해요. 실패한 소스의 객체가 사라졌다고 보지 않아요(마지막 정상 수집을 유지하고 신선도만 나빠져요). 스케줄 중지와 안전장치 중지는 알림 이벤트로 나가고, 규칙과 수신 대상은 ADR-0013이 정해요.

### 4.2 보류된 스트림

스트림에는 "온전한 수집"이 없어서 보이지 않는다고 사라진 것으로 처리할 수 없어요. 삭제 이벤트와 정합성 대조에서만 사라진 것으로 처리해요. 스트림의 안전장치는 비율을 봐요.

| 발동 조건 | 어떻게 되나 |
|---|---|
| 짧은 시간에 너무 많이 사라지거나 바뀜 | 그 소스의 적용을 보류해요(`held`) |
| 수신한 스키마(컬럼, 데이터 타입)가 바뀜 | 그 소스의 적용을 보류해요(`held`) |

**적용이 보류돼도 수집은 멈추지 않아요.** 수신한 변경은 원본 레코드에 쌓여요. 잃지 않아요. 보류되지 않은 다른 소스의 적용도 그대로예요. 임계값의 숫자는 가정이고 소스마다 조정할 수 있어요.

스트림 하나(`feed_flow`)의 상태예요.

| 필드 | 설명 |
|---|---|
| `source_id`, `dataset_id` | 어느 소스의 어느 데이터셋의 스트림인지 |
| `flow_state` | `running` / `held` / `paused` / `failed` |
| `held_reason` | 보류한 이유(어느 검사가 얼마나 넘었는지). 시크릿과 행의 내용은 없어요 |
| `held_since_seq` | 보류한 시점까지 적용한 `change_seq`. 이후 변경이 쌓여요 |
| `queued_changes` | 보류된 뒤 쌓인 변경 수 |
| `source_cursor` | 소스에서 어디까지 읽었는지 |

`operator`가 쌓인 변경을 확인하고 둘 중 하나를 선택해요.

| 선택 | 동작 |
|---|---|
| 해제(`release`) | 쌓인 변경을 수신 순서대로 적용해요. 한도가 있는 배치로 나눠 적용해요(오래 쌓였다 해제돼도 한 번에 몰리지 않아요). 보류됐던 변경은 해제될 때 수집 순서(`ingest_seq`)를 부여받아요. 해제하기 전에 드라이 런으로 차이를 확인하고, 안전장치가 발동한 이유를 확인한 것으로 기록해요 |
| 버리기(`discard`) | 쌓인 변경을 적용하지 않고 건너뛰어요. 쌓인 원본 레코드는 삭제하지 않아요. 버린 뒤에는 전체를 다시 수집해 정합성 대조를 하여 어긋난 것을 바로잡아요. **정합성 대조를 할 수 있는 소스에서만 가능해요.** 전체를 다시 받을 방법이 없는 스트림은 버릴 수 없고 해제하거나 보류해 둘 수 있을 뿐이에요 |

보류된 이유가 정의 때문이면(수신한 스키마가 바뀌어 매핑이 맞지 않음) 해제하기 전에 정의를 수정해 병합해요. 병합된 시점부터 새 정의로 처리하고, 쌓인 변경은 새 정의로 적용돼요.

**쌓이는 양의 한도.** 보류된 동안 쌓이는 변경은 조용히 버려지지 않아요. 쌓인 양이 보관 한도에 가까워지면 알림이 올라가요. 한도를 넘으면 오래된 것부터 콜드 스토리지(ADR-0009)로 옮겨져요. 옮길 곳이 없으면, 소스가 소스 커서부터 다시 보낼 수 있을 때는 그 소스의 수집을 중지하고 알려요. 다시 보낼 수 없을 때는 계속 수집해 쌓되 가장 높은 심각도로 알려요. 어느 쪽이든 조용히 버리지 않아요. 한도의 숫자는 가정이고 측정해서 정해요. 해제하거나 버리는 일, 안전장치 확인은 결과를 바꾸므로 수집 순서에 들어가는 이벤트예요(kg-storage의 고정 목록).

### 4.3 알림과 문제 목록

보류, 스케줄 중지, 안전장치 중지는 이벤트로 나가요. 알림 규칙과 그룹화와 수신 대상은 ADR-0013이 정해요. 같은 근본 원인의 알림은 하나로 묶여요. 알림은 문제 목록의 항목이 되므로 담당자의 수신함은 하나예요.

### 4.4 워커의 작업 인계

한 동기화나 스트림은 한 곳에서만 실행돼야 해요(3.4의 8번). 아래 3가지 장치가 함께 지켜요. 모두 스토리지 안에서 처리하고 별도의 조율 서비스를 두지 않아요(ADR-0009).

| 장치 | 방법 |
|---|---|
| 소스당 하나만 | 같은 소스(스트림은 데이터셋)의 `queued` 또는 `running` 실행은 하나만 있을 수 있어요. 스토리지의 유일 제약이 막아요 |
| 스케줄 키 | 스케줄이 만드는 실행에는 (소스, 시각 슬롯)으로 만든 키가 있어요. 워커 여러 대가 같은 슬롯을 만들려 해도 하나만 들어가요 |
| 리스와 리스 기한 | 워커가 실행을 가져가면 `lease_owner`와 `lease_until`을 기록해요. 작업하는 동안 `lease_until`을 계속 연장해요. 워커에 장애가 나면 연장되지 않아 기한이 지나요. 리스에는 실행기의 의미 버전이 들어 있어서, 롤아웃 중에 낮은 버전의 워커가 적용 리스를 획득하지 못해요 |

`sync_run`의 필드예요.

| 필드 | 설명 |
|---|---|
| `sync_id`, `source_id` | 실행과 소스 |
| `schedule_key` | 스케줄 키. 수동으로 실행한 것은 비어 있어요 |
| `state` | `queued` / `running` / `waiting_confirmation` / `succeeded` / `failed` / `abandoned` |
| `attempt` | 워커가 작업을 가져갈 때마다 올라가는 번호 |
| `lease_owner`, `lease_until` | 리스를 가진 워커와 기한 |
| `stage`, `stage_counts` | 현재 단계와 단계별로 들어온 수·나간 수·탈락한 수·소요 시간 |
| `guard_verdict` | 안전장치의 판정과 이유 |
| `kg_version` | 만들어진 KG 버전. 없으면 비어 있어요 |
| `error_code` | 오류 코드. 시크릿과 행의 내용은 포함하지 않아요 |

**인계 규칙**
- 리스 기한이 지난 `running` 실행은 다른 워커가 `attempt`를 올리며 가져가요.
- 모든 쓰기는 자기 `attempt`가 현재 번호와 같을 때만 받아들여져요. 장애가 난 줄 알았던 워커가 늦게 깨어나 쓰려 해도 번호로 거절돼요(두 곳에서 실행되는 것을 막는 마지막 장치).
- 수집 단계에서 장애가 났으면 수집을 처음부터 다시 해요. 같은 레코드는 중복 저장되지 않으므로(ADR-0008) 안전하고, 중간에 끊긴 수집은 온전한 수집이 아니에요.
- 수집이 끝난 뒤에 장애가 났으면 수집해 둔 원본 레코드로 다음 단계부터 이어서 실행해요. 소스에 다시 접속하지 않아요.
- 스트림은 소스 커서와 그 적용을 한 트랜잭션으로 묶고 번호로 중복을 막아요(ADR-0006). 이어받은 워커는 저장된 `source_cursor`부터 읽으므로 같은 변경이 두 번 적용되지 않고 빠지지도 않아요.
- 적용은 짧은 트랜잭션 하나라서(ADR-0009) 반쯤 적용된 상태가 없어요. 장애가 났으면 적용은 안 된 거예요. 큰 적용은 `change_seq` 여러 개로 나눠요. 읽는 쪽이 일부만 들어간 배치를 보지 않게 읽기 워터마크(`readable_through`)는 배치가 끝날 때만 올라가요(`min_seq`와 `serving_pin`이 이것을 봐요). 큰 적용 중 스트림의 적용 지연은 클로즈드 베타에서 측정해요.
- 인계를 반복해도 끝나지 않으면 `abandoned`로 두고 실패로 세요.

## 5. 표준 모델과 제품 업그레이드

제품이 업그레이드되면 표준 모델도 올라가요(ADR-0007).

- **덮어쓰지 않아요.** 제품 표준 타입(`std`)은 제품에 내장돼 있고 배포 안에서는 수정하지 않아요. 조직이 표준 타입을 조정한 것은 `org` 층의 오버레이이고, 사용자 정의 타입은 `ext` 층이에요. 업그레이드가 오버레이와 사용자 정의 타입과 매핑을 바꾸지 않아요.
- **타입은 삭제하지 않고 폐기해요.** 폐기된 타입은 이력에 남고 기존 객체도 삭제되지 않아요.
- **알리기만 하고 자동으로 수정하지 않아요.** 폐기된 타입을 쓰는 매핑이 있으면 `retired_type_in_use` 문제가 그 매핑의 담당자에게 올라가요. 폐기된 타입의 `superseded_by`가 후속 타입을 가리키면 알림에 함께 표시돼요. 같은 폐기 타입 하나에서 비롯된 문제는 한 그룹으로 묶여요.
- **정의를 이전하는 것은 규칙을 수정하는 일과 같은 경로예요.** 매핑을 새 타입으로 이전하는 변경은 호환성을 깨는 변경이라서 마이그레이션을 함께 적어요(ADR-0014). 브랜치에서 이전하고, 드라이 런으로 차이를 확인하고, 승인을 받아 병합해요. 이전하기 전에도 수집하는 데이터는 그대로 수집돼요.
- **표준 모델이 올라간 뒤의 첫 적용은 정의를 수정한 뒤의 첫 적용과 같은 규칙이에요.** 위험 등급 R2부터 사람이 차이를 확인하고, 낮은 등급은 자동으로 적용하고 알려요(definitions). 표준 모델과 `sys` 타입은 마이그레이션 단계의 하나로 스토리지에 적재돼요.

## 6. 백업과 복구: 진실과 파생 데이터

저장과 백업 방법은 [KG의 저장과 버전](kg-storage.md)에 있어요. 여기서는 운영 관점에서 무엇이 진실이고 무엇이 다시 만들 수 있는 것인지만 구분해요.

| 구분 | 대상 | 복구 뒤 |
|---|---|---|
| 진실(잃으면 안 됨) | 원본 레코드(내용을 제거했다는 표시를 포함해요. 유출된 값은 해시와 위치만 남기고 삭제해요), 정의와 버전과 브랜치와 제안, KG의 변경(`change_seq`)과 버전, 소스별 소스 커서, 실행 이력, 감사 로그, 사람이 신고한 `user_report`와 문제 상태 변경 | 백업과 시점 복구에서 복원해요 |
| 파생 데이터(다시 만들 수 있음) | 프로젝션, 규칙이 만든 문제 항목, 문제 그룹 | KG와 정의에서 다시 만들어요. 지표 복구는 [데이터 관측성](data-observability.md)을 따라요 |

- 시점 복구로 돌아가면 그 뒤의 KG 변경과 버전이 사라져요. 소스를 다시 읽으면 같은 입력에서 같은 버전이 나와요(ADR-0009). 복구할 때마다 KG의 **세대** 번호가 올라가요. 세대는 `as_of`, 커서, 이벤트 ID, `min_seq`에 포함돼서, 복구 전의 값을 보유한 외부 소비자와 에이전트는 `conflict.generation_changed`를 받고 처음부터 다시 정합성 대조를 해요. 메시지 로그 스토리지를 쓸 때 복구 뒤 수집 순서가 다시 정해지면 처음과 다를 수 있어서 같은 규칙이 적용돼요.
- **소스에서 다시 가져올 수 없는 것**이 있어요. 업로드한 엑셀 파일, 수집 엔벨로프로 받은 레코드, 스트림으로만 오는 이벤트예요(정합성 대조는 현재 상태만 주므로, 지나간 이벤트를 다시 주는지는 소스에 달렸어요, 가정). 이것의 원본 레코드는 백업이 유일한 사본이라 복구 훈련에 반드시 넣어요.
- 복구 뒤 스트림은 저장된 `source_cursor`부터 이어서 읽고, 소스가 그 위치를 더는 제공하지 못하면 정합성 대조로 기준 상태를 다시 만들어요.

## 7. 알려진 한계

- 조사에서 확인하지 못한 것(여러 제품의 내부 동작, 페일오버 시간, 큐의 실제 지연, 이어서 받는 소스의 부하)이 있어 8절에서 가정으로 표시한 숫자는 측정해서 조정해요.
- 문제 그룹의 시그니처가 너무 넓으면 다른 원인이 섞이고, 너무 좁으면 잘게 쪼개져요. 클로즈드 베타에서 조정해요.
- 스트림의 보류 임계값이 낮으면 `operator`에게 확인할 일이 몰리고, 높으면 오염된 데이터가 들어와요. 소스마다 조정하는 경로가 있지만 클로즈드 베타에서 측정해서 기본값을 조정해요.
- 보류된 스트림이 오래 쌓이면 해제할 때 적용할 양이 커져요(배치로 나눠 적용해요). 한도의 숫자는 아직 측정하지 않았어요. 병합 큐가 막혔을 때 쌓이는 에이전트의 제안은 한도(설정)가 막아요.
- 프로토타입의 숫자(스토리지 입출력 없이 측정한 것)는 한계가 있어요. 메시지 로그 스토리지로 전환하는 임계값은 추정이에요(ADR-0009).

## 8. 기본값이며 클로즈드 베타에서 측정해서 정한다

| 항목 | 현재 값 | 측정해서 정하는 방법 |
|---|---|---|
| 재시도 횟수 | 3회(기본값) | 소스의 오류 유형별로 일시 오류가 몇 번 안에 해소되는지 |
| 스케줄 중지를 일으키는 연속 실패 수 | 5회(기본값) | 오탐 중지(알림 피로)와 늦은 중지(소스 부하)의 균형 |
| 대량 사라짐의 기준(배치) | ADR-0008의 기본값 | 샘플 테스트 |
| 스트림을 보류하는 비율과 시간 | 5분 동안 5% 이상(그리고 50건 이상)(기본값) | 가상의 스트림에 변형한 입력을 넣어서 |
| 리스 기한, 리스 연장 간격 | 정하지 않음 | 가장 긴 단계의 소요 시간과 워커 장애 주입 |
| 메시지 로그 스토리지로 전환하는 임계값 | 논리 변경 수, 물리적으로 쓰는 행 수, WAL 바이트 3가지를 함께 봐요. 초당 2~3만은 논리 변경 수의 추정이에요(WAL이 3~4배라는 것도 추정) | 클로즈드 베타에서 스토리지 입출력을 넣어 3가지를 따로 측정해서 |
| 허용 데이터 손실 시간(RPO) | 쿼럼 방식의 동기 복제(후보 2개 이상 중 하나가 받으면 커밋)로 커밋된 기록은 0을 목표 가정 | 커밋 지연과 복구 훈련 |
| 복구 시간(RTO) | 인스턴스 하나의 장애는 수십 초에서 2분, 스토리지 전체 유실은 수 시간(둘 다 가정) | 장애 주입(가용 영역 격리, 주 스토리지 강제 종료, 백업 저장 위치 단절, 시크릿 스토리지 단절) |
| 프로젝션을 로드하는 시간 | 정하지 않음 | 가상의 3천만 객체로(ADR-0009의 측정 순서) |

## 9. 미결 사항

- 문제 항목과 해결된 문제 그룹의 보존 기한.

## 10. 관련 결정과 요구사항

- 결정: [ADR-0011](adr/0011-kg-operations.md). 관련 결정은 ADR-0006(역할 4종, 언어), ADR-0007(근거 등급, 식별, 표준 모델), ADR-0008(수집 방식, 안전장치), ADR-0009(버전, 스토리지), ADR-0010(응답에 붙는 것), ADR-0012(권한, 담당자, 감사), ADR-0013(데이터 관측성), ADR-0014(정의의 버전과 브랜치).
- 요구사항: REQ-151(문제 목록은 규칙으로 해결한다), REQ-154(가용성의 등급). 품질 지표와 신선도(REQ-150, REQ-152)와 관측성(REQ-180~189)은 ADR-0013, 감사 로그(REQ-164)는 ADR-0012의 것이에요.
- 같이 읽을 문서: [데이터 관측성](data-observability.md), [정의의 버전과 브랜치](definitions.md), [접근 제어](access-control.md), [KG의 저장과 버전](kg-storage.md), [KG에 묻기](kg-queries.md), [현실 데이터 수집](ingestion.md), [KG의 모델](kg-model.md).
