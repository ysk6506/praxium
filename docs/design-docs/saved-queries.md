# 저장한 질의와 간선 정의

사용자가 쓴 SQL을 정의로 저장해 REST 경로와 MCP 툴로 내보내는 설계예요. 그래프 함수에 줄 간선을 정의하는 **간선 정의**와, 질의를 만들고 테스트하는 질의 화면도 여기에서 정해요. 결정은 ADR-0080에 있어요. **이 문서는 아직 구현하지 않은 설계(예정)예요.** 예시의 이름과 값은 지어낸 것이에요. 제품은 영향 범위나 이중화를 계산하지 않고(ADR-0077, ADR-0078), 사람들이 이 질의로 자기 조직에 맞는 MCP 툴을 만들어요. 그래서 질의는 쉬워야 해요.

## 1. 목적과 다루는 질문

- 사람이 쓴 SQL을 에이전트가 틀리지 않고 부를 수 있는 툴로 바꾸려면 무엇을 저장하고 무엇을 검사해야 하나.
- 호출자마다 민감 등급이 달라서 실패하는 질의는 어떻게 다루나. 권한은 누구의 것인가.
- 모델이 바뀌어 깨지는 질의를 언제 알아차리나.
- 속성 조건이 있는 간선을 어떻게 정의하고, 그래프 함수가 어떻게 쓰나.

## 2. 정의의 모양

**저장한 질의와 간선 정의는 정의의 종류예요**(같은 저장소, 같은 id 문법, 같은 변경 절차. [정의의 버전과 브랜치](definitions.md) 3-1절의 표에 두 종류가 더해져요). id는 `[a-z][a-z0-9_-]{0,63}`이에요(ADR-0075). 종류의 이름(`saved_query`, `edge_definition`)은 가칭이고 구현할 때 정한다.

```yaml
# 저장한 질의(가상의 예)
id: servers-in-rack
title: 랙에 장착된 서버
description: >
  랙 이름을 받아 그 랙에 장착된 물리 서버의 이름과 운영 상태를 낸다.
  영향 범위를 뜻하지 않는다.
sql: |
  SELECT s.name, s.oper_state
  FROM physical_server s
  JOIN mounted_in m ON m.src = s.id
  JOIN rack r ON r.id = m.dst
  WHERE r.name = :rack_name
  ORDER BY s.name
params:
  - {name: rack_name, type: string, required: true, description: "랙의 이름. 예 rack-a-01"}
  - {name: min_state, type: string, required: false, default: "down",
     values: [up, down, unknown], description: "이 상태 이상만 낸다"}
limits: {timeout_ms: 10000, max_rows: 200}
expose: [rest, mcp]
engine: sql
```

| 필드 | 뜻 |
|---|---|
| `id` | 정의의 id. REST 경로와 MCP 툴 이름의 바탕이에요 |
| `title` | 사람이 읽는 제목 |
| `description` | **LLM이 읽는 설명**이에요. 툴의 설명문이 돼요. 누가 고칠 수 있는가가 권한 설계에 들어가요(설명에 지시를 심는 길이라서). 변경은 정의의 변경 절차(제안과 승인)를 지나요 |
| `sql` | **SELECT 한 문장**. 파라미터는 **값의 자리에만** 올 수 있어요. 자리의 표기는 `:이름`이고(`::` 형 변환과 구분해요) 서버가 바인딩 인자로 바꿔요. 표기는 구현할 때 다듬어요. `SELECT *`는 금지예요(모델이 바뀌면 결과의 모양이 바뀌어요). 타입 이름이나 컬럼 이름은 파라미터가 될 수 없어요 |
| `params` | 이름, 타입, 설명, 기본값, 필수, 값 목록. 타입은 `string`, `integer`, `number`, `boolean`, `timestamp`(UTC, 끝이 `Z`)예요. 목록 형은 구현할 때 정한다. `kg`(기본 `main`)는 모든 질의가 받는 암묵 파라미터예요 |
| `limits` | 시한과 최대 행 수. 상한은 실행기의 한도(MCP 10초와 200행, REST 30초와 1만 행)를 넘을 수 없어요 |
| `expose` | 내보내는 곳(`rest`, `mcp`) |
| `engine` | `sql`. 뒤의 선택 사항(외부 그래프 DB)을 위한 자리예요 |
| 결과 열 | 저장할 때 DB에서 받아 적는 열의 이름과 타입(3절). 직접 쓰지 않아요 |

**화면이 쓰는 읽기를 저장한 질의로만 할 수는 없어요.** 객체 목록은 타입이 인자인데 타입은 뷰의 이름이고 파라미터는 값의 자리에만 오기 때문이에요(타입마다 질의를 두면 168개예요). 그래서 목록, 상세, 이웃, 찾기는 내장 읽기가 맡아요([질의 실행기와 읽기의 세 경로](query-execution.md) 4절). 저장한 질의는 조직이 정한 물음을 위한 것이에요.

소속(수정 권한과 승인의 범위를 가르는 기준)은 구현할 때 정한다. 정의는 KG가 아니라 배포에 하나이고, 질의가 어느 KG에 도는지는 부를 때 `kg`로 정해요.

## 3. 저장할 때의 검사

저장(제안과 미리 보기 포함)할 때 서버가 해요.

1. **준비해 보아** 문법과 권한을 확인해요. 질의 실행기와 같은 감싸기와 같은 역할로 해요.
2. **민감 등급마다** 준비해 봐요. 호출자의 등급에 따라 어떤 컬럼이 없어서 실패하는 질의가 생기므로, "이 질의를 부를 수 있는 가장 낮은 민감 등급"을 계산해 적어 둬요.
3. **결과 열의 이름과 타입을 DB에서 받아 적어요**(감싼 문장을 `LIMIT 0`으로 한 번 돌려서 얻어요. 추측이고 구현할 때 확인해요). 이것이 MCP 툴의 출력 스키마가 돼요.
4. `SELECT *`와 값 자리 밖의 파라미터를 거절해요. 파라미터 이름이 문장에 쓰였는지, 필수와 기본값이 맞는지, 한도가 실행기의 한도 안인지 검사해요.
5. 오류는 정의 오류의 규칙대로 장소와 코드와 함께 한 번에 여럿을 알려요(ADR-0070).
6. 변경은 정의의 변경 절차를 지나요. 제안의 미리 보기에 **이 변경으로 깨지는 저장한 질의**를 보여 줘요. 조직 속성(커스텀 속성)을 빼거나 이름을 바꾸는 제안이 대상이에요.

## 4. 권한

- **권한은 부르는 사람의 것이에요.** 질의는 부르는 사람의 (KG, 민감 등급)의 역할로 돌아요. 저장한 사람의 권한을 빌리지 않아요. 높은 등급 속성을 쓰는 질의를 낮은 등급의 호출자가 부르면 컬럼이 없어서 오류예요.
- 저장하고 바꾸는 것은 그 소속의 `editor`예요. 승인은 `approver`예요. 부르는 것은 `viewer`부터이고, 에이전트는 서비스 계정의 토큰으로 불러요([접근 제어](access-control.md)).
- **MCP의 툴 목록은 호출자의 민감 등급으로 걸러요.** 계정의 등급은 잘 바뀌지 않아서 목록이 실행마다 고정이라는 원칙(ADR-0074)과 부딪히지 않아요.
- 임의 SQL 툴은 MCP에 없어요. 화면과 REST의 임의 질의는 그 능력이 있는 역할만 써요.

## 5. 올릴 때의 재검사

- **제품을 올릴 때 저장한 질의를 모두 다시 검사해요**(준비, 등급마다, 결과 열). 깨진 것은 **문제 목록**에 올려요.
- **조직의 속성 정의가 바뀔 때도** 다시 검사해요. 커스텀 속성이 빠지면 뷰의 컬럼이 사라져서 질의가 깨져요. 이것은 제안의 미리 보기에서 먼저 알려요(3절의 6번).
- 깨진 질의를 부르면 고정된 오류 코드로 답해요. 툴 목록에서 빼는지는 구현할 때 정한다. 질의 스키마에는 옛 이름의 별칭이 없어요([질의 스키마](query-schema.md) 3절).

## 6. REST와 MCP 툴이 되는 규칙

**REST**: 스키마 설명, 내장 읽기(찾기, 객체 읽기, 이웃, 도달 집합), 저장한 질의의 실행, 임의 질의(그 능력이 있는 역할만)가 있어요. 경로의 이름은 [REST API](rest-api.md)에 구현할 때 정한다. 응답은 결과 열과 행과 세대와 변경 번호와 잘렸는지를 싣고, 같은 질의 실행기를 지나요.

**MCP**: 기본 툴 여섯 개(`kg_schema`, `kg_find`, `kg_get`, `kg_neighbors`, `kg_reachable`, `kg_whoami`)가 있고, **`expose`에 `mcp`가 있는 저장한 질의마다 툴이 하나 더해져요.**

| 툴의 요소 | 어디에서 오나 |
|---|---|
| 이름 | 정의의 id에서 만들어요. 기본 툴과 겹치지 않아야 하고 `-`는 밑줄로 바꿔요. 접두어와 최대 길이는 구현할 때 정한다(예: `q_servers_in_rack`) |
| 설명문 | 정의의 `description`(고정된 글이에요. KG의 값이 들어가지 않아요) |
| 입력 스키마 | `params`에서. 이름, 타입, 설명, 기본값, 필수, 값 목록이 JSON Schema가 돼요. `kg`와 `detail`은 기본 툴처럼 받아요 |
| 출력 스키마 | 저장할 때 받아 적은 결과 열 |
| 읽기 전용 주석 | 모든 툴에 달아요 |

- **툴 목록은 정의가 바뀔 때만 바뀌어요**(ADR-0074의 원칙). 같은 서버 버전에서 정의가 그대로면 툴 정의의 정규 직렬화가 바이트까지 같아요(프롬프트 캐시를 위해서예요). 호출마다 달라지는 값(시각, 건수, KG의 값)은 정의에 넣지 않아요.
- **목록이 바뀌는 것의 알림**: 정의의 병합 이벤트가 나가고(이벤트 스트림), 클라이언트는 `tools/list`를 다시 가져와요. 지금 MCP는 `listChanged`가 거짓이에요(서버가 먼저 보내는 연결이 없어서예요, [MCP](kg-mcp.md) 2.2절). 켜는 때는 구현할 때 정한다.
- 결과는 지금의 MCP처럼 `{meta, next, data}`의 순서이고, 응답 크기에 상한이 있어서 항목 수를 줄이고 잘렸다는 표시와 다음 할 일을 줘요. 값은 구조의 값 자리에만 있고 설명이나 오류 글에 섞지 않아요([MCP](kg-mcp.md) 4.3절).
- 에이전트가 틀리기 어렵게: 오류는 고칠 단서를 줘요(없는 컬럼이면 그 뷰의 컬럼 목록). 예시 질의는 `kg_schema`로 찾아볼 수 있어요.

## 7. 간선 정의

**간선 정의**는 `src`와 `dst`(객체 번호)를 내는 SELECT예요. 저장하면 **질의 스키마의 뷰**가 돼요. 그래프 함수의 `edges`가 그 뷰 이름을 받아요([질의 실행기와 읽기의 세 경로](query-execution.md) 3절). 속성 조건이 있는 간선을 만드는 방법이에요. 제품은 무엇이 의존이고 무엇이 이중화인지 전제하지 않고, 조직이 정해요.

```yaml
# 간선 정의(가상의 예)
id: primary-power-edges
title: 확인된 전원 링크
description: 전원 링크 가운데 근거 등급이 fact인 것만 간선으로 본다.
sql: |
  SELECT src, dst FROM powered_by WHERE grade = 'fact'
```

- 뷰의 이름은 id에서 만들어요(`primary-power-edges`의 `-`를 밑줄로 바꿔 `primary_power_edges`). 타입 뷰나 링크 뷰와 이름이 겹치면 저장할 때 거절해요.
- 열은 `src`, `dst`가 필수이고 `bigint`예요. 더 있는 열은 그대로 보여요.
- 저장할 때의 검사(3절)는 같아요. 민감 등급마다 준비해 보고, 만들 수 있는 가장 낮은 등급의 질의 스키마에만 뷰를 더해요(스키마 관리기가 만들어요).
- 쓰기가 아니라 뷰예요. 사용자는 뷰를 만들 수 없으므로 이 정의가 "속성 조건을 건 자기 간선"의 통로예요.
- 쓰는 예: `reachable(start => …, edges => 'primary_power_edges', direction => 'in', max_depth => 6, max_nodes => 50000)`.

## 8. 질의 화면의 흐름

화면은 `apps/web`에 있고 지금 모양은 임시예요. 여기서는 동작의 흐름만 정해요.

1. **스키마 보기**: 모델 설명으로 타입과 속성과 링크 규칙을 낱말로 찾고, 조인의 본보기 문장을 봐요.
2. **SQL 쓰기와 실행**: 사람의 임의 질의 경로(풀 4, 시한 10초에서 30초)로 돌려서 행과 결과 열을 봐요. 잘렸으면 표시해요. 한도에 걸리면 이유와 좁히는 방법을 알려요.
3. **저장**: 제목, 설명, 파라미터, 한도, 내보내는 곳을 적어요. 서버의 검사 결과(결과 열, 가장 낮은 민감 등급, 오류의 장소)를 보여요.
4. **내보내기**: REST와 MCP를 골라요. 정의의 제안과 승인을 거쳐요.
5. 객체 목록, 객체 상세, 이웃은 남고 내부가 내장 읽기가 돼요. **영향 화면은 없앴어요**(ADR-0077).

## 9. 끄는 운영 액션

- **저장한 질의는 id로, 임의 질의는 문장의 해시로** 끌 수 있어요. 끈 질의는 실행기가 거절하고 감사에 남겨요. 운영 중 DB를 무겁게 만드는 질의를 바로 막는 장치예요(조인이 많은 질의의 격리와 같은 쓰임이에요).
- 운영 액션의 이름과 권한(`operator`)은 구현할 때 정한다.

## 10. 알려진 한계와 가정

- 결과 열의 이름과 타입을 받는 방법, 파라미터의 표기, 이름의 규칙은 원형에서 측정하지 않았고 구현할 때 확인해요.
- LLM의 정확도: 열 설명이 있으면 올라가요(공개된 벤치마크에서 6.7점). 큰 스키마의 날 텍스트-SQL은 낮아요(다른 벤치마크에서 21%). 조건이 달라 직접 비교할 수 없어요. 제품은 이 한계를 설명, 본보기, 오류의 단서로 줄여요.

## 11. 미결 사항

- 종류의 이름, 소속, 툴 이름의 접두어와 길이, 파라미터의 목록 형, `:이름` 표기.
- 깨진 저장한 질의를 툴 목록에서 빼는지, `listChanged`를 켜는 때.
- 끄는 운영 액션의 이름과 권한.

## 12. 관련
