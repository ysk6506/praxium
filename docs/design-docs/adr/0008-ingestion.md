# ADR-0008 현실 데이터 수집: 어댑터와 프리셋, 수집 방식 4가지, 변경을 입력받아 변경을 출력하는 실행기 하나, 속성 단위로 객체를 구축하는 피드, 읽기 전용 3중 장치, 안전장치

## 맥락
KG는 현실의 IT 인프라를 수집해 구축한다(ADR-0005). 제품 책임자의 요구는 다음과 같다. 소스는 여럿이고 읽기만 한다. 소스마다 동기화 주기를 관리한다. 배치로도 스트리밍으로도 수집하고, 둘을 잘 처리하는 것이 이 제품의 차별점이다(다른 제품은 스트림에서 쓰지 못하는 연산과 기능이 많다는 사용자 의견). 한 객체 타입에 배치로 오는 속성과 실시간으로 오는 속성이 섞이고, 사용자가 그것을 쉽게 관리해야 한다. 같은 정보(ECMP 등)를 설정에서도 테이블에서도 수집할 수 있어야 한다. 엑셀이 위치·전원·냉방 정보의 주된 수집 경로다. 쿼리 언어를 받는 소스에서는 검색을 자유롭게 작성한다.

[테라리움에서 넘겨받은 것](../../references/from-terrarium.md) 6절의 쟁점 가~아는 엔드투엔드(E2E) 프로세스와 경계에 관한 질문이라 이 결정이 직접 답하는 것은 없다. 가장 가까운 것은 바(운영 경로가 되면 멈추면 안 된다)다. 수집이 멈추거나 낡아도 KG와 질의는 마지막 정상 버전으로 그대로 답한다(ADR-0011).

넘겨받은 설계(T0144, T0149~T0152, T0161, T0164, T0165)는 요구가 올 때마다 수정하며 쓰였고 실제 소스와 대조된 적이 없다. 소스의 역할은 현재 구성 하나다. 실시간 상태의 수치(온도, 전력, 알람의 현재 값)는 미룬다. 구조와 상태(존재 여부, 설치 위치, 기동 여부, 이웃)는 수집한다. 여러 조직이 함께 쓰므로 소스도, 소스를 아는 담당자도 많다고 가정한다.

## 결정
1. **어댑터와 프리셋.** 프로토콜 하나를 다루는 **어댑터**는 제품에 포함된 소수의 코드이고, 소스 제품 하나에 맞춘 **프리셋**은 데이터다(허용된 요청, 데이터셋, 기본 매핑, 테스트). 첫 어댑터는 파일(엑셀, CSV), HTTP JSON, 읽기 전용 SQL 3종이다. 스트림 어댑터(메시지 로그 스토리지의 토픽, 폴링 방식의 API, 변경 데이터 캡처, 푸시 수집)는 결정 기록과 함께 하나씩 추가한다. "모든 소스가 선언만으로 된다"고 약속하지 않는다. 사용자 코드를 넣는 경로는 없다. 프리셋은 합성 샘플로 실행되는 테스트가 있어야 탑재된다.
2. **어댑터의 포트**는 메서드 6개다: 소스 탐색, 미리보기, 전체 수집, 증분 수집, 이어서 수집, 점검. 쓰기 메서드는 없다.
3. **수집 방식은 소스의 데이터셋마다 4가지 중에서 고른다**: `snapshot`(전체 수집) / `incremental`(증분 수집) / `stream`(이어서 수집) / `stream` + 정합성 대조(처음에 전체 수집, 이어서 수집, 가끔 전체 수집으로 정합성 대조). 삭제를 파악하는 방법은 방식마다 다르고, 소스마다 선언한다.
4. **스케줄이 정의다.** 소스와 데이터셋마다 스케줄을 두고(주기, 수집을 허용하는 시간대, 일시 정지, 즉시 1회 실행, 건너뛴 실행의 처리, 겹치는 실행 금지, 스트림의 켜고 끔과 정합성 대조 주기) 버전을 둔다. 수동으로만 수집하는 소스에도 기대하는 갱신 주기를 적고, 낡음은 그것을 기준으로 판단한다.
5. **수집한 것은 모두 원본 레코드의 변경이 된다.** 전체 수집한 것은 지난번과 비교해 추가·수정·삭제로 바꾸고, 이어서 수집한 것은 그대로 변경이다. 그 뒤의 단계는 수집 방식을 모른다. KG마다 하나뿐인 적용기가 수집 변경 로그에서 배치를 읽으며 순서를 확정하고 단조 증가하는 `ingest_seq`를 부여해 수집 순서를 고정한다. 소스가 준 시각이나 버전으로 수집 순서를 정하지 않는다(소스의 시각은 값을 가릴 때만 쓴다. 결정 10의 지연 도착 값 처리와 이어서 정한 것의 푸시 수집). 보류된 변경은 보류되기 전이 아니라 해제될 때 `ingest_seq`를 부여받는다.
6. **원본 레코드**는 레코드 단위로 수집한 형태 그대로 보관하고 수정하지 않는다. 같으면 중복 저장하지 않고 구간을 늘리며, 끝을 열어 둘 수 있다. 수집할 때 시크릿과 가릴 필드를 제거하고(프리셋이 선언), 보존 기한은 닫힌 구간에만 적용한다(열려 있는 구간은 경과 시간으로 삭제하지 않는다. 고침 8-34). `volatile` 속성만 제공하는 스트림의 데이터셋은 구간이 아니라 추가 전용의 짧은 보관 큐로 둔다. 이미 쌓인 레코드에서 유출된 값을 제거하는 **내용 제거 표시**(내용은 삭제하고 해시와 위치와 이유만 남긴다)를 처음부터 스키마에 둔다. 로그는 둘이고 섞지 않는다: 수집 변경 로그(포트)와 KG에 적용된 변경의 기록(언제나 PostgreSQL). 소스 커서도 둘이다: `source_cursor`는 수집 변경 로그 쓰기와 함께 진행하고, `applied_through`는 적용 트랜잭션에 묶여 "정확히 한 번"을 보장한다. 시계도 이벤트로 기록에 넣어 다시 실행해도 같은 결과가 나온다.
7. **한 번 수집해 KG까지 가는 단계**: 수집 → 정제 → 피드(매핑) → 식별과 병합 → 링크와 그룹 → 차이 → 안전장치 → 적용. 연결 점검은 단계가 아니라 필요할 때 하는 점검이다. 연동(수집)과 모델 동기화(그 뒤)의 경계를 지킨다.
8. **정제·피드·식별·링크는 변경을 입력받아 변경을 출력하는 실행기 하나가 실행한다.** 연산마다 입력 변경을 출력 변경으로 바꾼다. 정의 하나가 배치와 스트림에서 똑같이 실행되고, 배치용과 스트림용 정의나 연산을 따로 두지 않는다. 배치는 큰 변경 배치이고 스트림은 작은 변경 배치이다. 삭제와 수정이 값으로 전달된다(수정은 "−이전 값 +새 값"). 연산은 레코드 하나만 보는 것, 키별 상태가 필요한 것, 전체를 봐야 하는 것 3가지로 구분하고 등록부에 적는다. 키 상태는 포트 뒤에 둔다. **같은 원본을 한 번에 넣은 결과와 잘게 나눠 흘린 결과는 같아야 하고** 테스트로 검증한다.
9. **정제의 연산은 고정된 14종이다**: 행으로 펼치기 / 컬럼으로 모으기(피벗) / 컬럼 나누기 / 조인 / 유니언 / 고르기(필터) / 빈 값 채우기 / 값 바꾸기 / 컬럼 선택과 이름 바꾸기 / 데이터 타입으로 변환 / 중복 행 제거 / 테이블에서 찾아 바꾸기 / 정규식으로 추출 / 이어 붙이기. "값 바꾸기"의 함수는 검토를 거쳐 제품에 포함된 순수 함수 목록에서 고른다. 새 연산은 스트림에서 실행되는 방법과 함께 결정 기록으로만 추가한다.
10. **객체는 여러 피드가 속성 단위로 구축한다.** 피드는 데이터셋 하나에서 객체 타입 하나로 가는 매핑 하나이고, 자기가 매핑한 속성만 소유한다. 적용은 속성 단위다. 배치 피드의 전체 수집이 스트림 피드의 속성을 지우거나 덮어쓰지 않는다. 피드가 값을 주지 않으면 그 피드의 속성만 비워진다. 같은 속성은 속성마다 우선순위로 값을 고르고, 채택되지 않은 값은 충돌로 표시한다. 같은 순위에서는 이벤트 시각이 늦은 것이 채택되고, 늦게 도착한 옛 이벤트는 새 값을 덮어쓰지 못한다.
11. **객체를 생성하는 피드와 속성을 덧붙이는 피드를 구분한다**(`creates_objects`, `retires_objects`). 속성만 덧붙이는 피드가 아직 없는 객체의 값을 주면 객체를 만들지 않고 기한이 있는 대기에 둔다. 기한 안에 객체가 생기면 붙고, 아니면 문제 목록에 "붙을 대상이 없는 값"으로 올린다.
12. **타입의 피드 테이블을 API가 제공한다.** 속성마다 어느 피드가 소유하는지, 수집 방식과 주기, 우선순위, 이력의 종류, 신선도, 채움, 충돌을 한곳에서 본다. 속성의 변경 속도(`change_class`)가 이력의 종류와 신선도의 기본값을 정하고, 맞지 않는 매핑은 알리되 막지 않는다. 프리셋은 전체 수집 데이터셋과 증분 수집 데이터셋과 둘의 매핑을 한 세트로 포함한다.
13. **링크 정의**는 링크 타입마다 조건을 적는다. 조건은 고정된 6종이다: 정제한 키가 같다 / 목록에 들어 있다 / 범위에 속한다 / 위치가 일치한다 / 부모가 같다 / 다른 링크를 따라간 끝이 같다. 그룹 객체도 만든다. 도출한 링크와 그룹은 수집할 때 만들어 저장한다. 같은 그룹을 설정·테이블·문서 어디서든 수집하고, 근거 종류(`configured`, `observed`, `declared`, `derived`)를 붙여 모두 보관한다. 설정과 관측이 어긋나면 문제 목록의 "의도와 관측의 어긋남"이다.
14. **기대 조건**을 데이터셋과 피드에 붙인다(고정된 8종, 강도 `fail`과 `warn`). 배치에서는 배치 단위로, 스트림에서는 레코드마다 적용한다. 위반한 레코드는 따로 격리한다.
15. **읽기 전용은 3중 장치다.** 첫째 프리셋의 요청 허용 목록(메서드, 경로 패턴, 본문 형식). 둘째 소스 쪽 계정이 읽기 전용이다(연결할 때 확인). 셋째 어댑터에 쓰기 경로가 없다(구조 검사가 확인한다). 쿼리 언어 소스의 검색은 관리자가 자유롭게 작성하되, 저장할 때 허용된 명령 목록으로 검사한다.
16. **소스를 보호하고 연결을 제한한다.** 소스마다 동시 요청 상한(기본 1), 속도 상한, 백오프 재시도, 연속 실패 시 연결 차단(인증 실패는 즉시), 수집을 허용하는 시간대를 둔다. 워커가 접속할 수 있는 곳은 소스마다 적은 주소뿐이고 기본은 차단이다. 소스마다 주기적으로 가볍게 접속해 인증과 읽기 전용 권한을 점검한다. 시크릿은 참조로만 정의에 들어가고 값은 시크릿 제공자 포트 뒤에 있다(제공자 2종이 정식. ADR-0018. 고침 8-34).
17. **소스를 탐색한다.** 읽기 전용으로 무엇이 있는지와 몇 행의 미리보기를 제공하고, 양에 상한이 있고 소스 보호를 거친다. 매핑을 만들 때 쓴다.
18. **민감 등급이 컬럼에서 속성으로 전파된다.** 소스의 컬럼에 등급을 적고(프리셋이 기본값), 정제를 거치며 입력 중 가장 높은 등급이 따라간다. 속성의 등급은 매핑된 컬럼의 등급보다 낮을 수 없다. 낮추려면 이유와 승인이 필요하다(ADR-0012의 속성 등급과 같은 체계).
19. **수집 엔벨로프가 정식 확장 지점이다.** 소스를 아는 담당자가 익숙한 언어로 자기 수집기를 만들어(수집 엔벨로프의 클라이언트 라이브러리는 Go, Python, TypeScript부터 여러 언어로 제공한다) 공개된 수집 엔벨로프(무엇을, 언제, 온전한지, 레코드마다의 종류와 순번)로 보낸다. 수신한 뒤는 다른 소스와 같다. 워커의 수집 역할을 소스가 있는 망에 **수집기**로 따로 띄울 수 있고, 외부로 나가는 연결만 쓴다. 제품에 포함된 어댑터가 실행되므로 읽기 전용 3중 장치가 그대로 적용된다. 담당자가 직접 만든 수집기는 읽기 전용을 그 소스의 담당자가 책임진다고 문서와 API 응답에 밝힌다.
20. **안전장치는 배치와 스트림 모두에 적용한다.** 배치는 덜 수집한 결과를 다음 단계로 보내지 않고, 같으면 새 버전을 만들지 않고, 처음 적용·정의 수정 뒤 첫 적용·표준 모델 업그레이드 뒤 첫 적용·수신한 스키마 변경·대량 사라짐에서 멈춘다. 보이지 않는 것은 바로 삭제하지 않고 온전한 수집에서 연속으로 보이지 않고 최소 기간도 지나면(피드마다 조정할 수 있고 기본 3회, 가정) 폐기(retired)로 표시한다. 객체는 폐기할 수 있는 피드 중 보고 있는 것이 하나라도 남아 있는 동안 유지된다. 스트림에는 온전한 수집이 없으므로 보이지 않는다고 폐기하지 않고(삭제 이벤트와 정합성 대조에서만), 비율을 보아 그 소스의 **적용을 보류한다**(`held`). 보류된 동안에도 수집은 멈추지 않는다. 해제(`release`, 드라이 런으로 차이를 확인한 뒤. 한도가 있는 배치로 나눠 적용한다)와 버리기(`discard`, 정합성 대조를 할 수 있는 소스에서만, 버린 뒤 전체를 다시 수집해 정합성 대조를 한다)가 있고, 쌓인 변경은 한도에 가까워지면 알리고 넘으면 오래된 것부터 콜드 스토리지로 옮기며, 옮길 곳이 없으면 수집을 중지한다. 수집기는 소스 커서를 본체에 둬서 장애가 나도 다른 인스턴스가 이어받는다. 완전성 선언은 기대 수와 수신한 수의 불일치가 임계값을 넘으면 자동으로 중단된다(`expected_count`를 제공할 수 있는 소스에서). 숫자는 모두 측정하지 않은 가정이다.
21. **건수 정합성.** 원본 레코드 하나는 마지막에 4가지 중 하나로 분류된다: 사용됨 / 규칙이 걸러 냄 / 문제 / 사용되지 않음. 4가지의 합은 수집한 수와 같고, 단계마다 들어온 수는 나간 수와 탈락한 수(이유와 함께)의 합이다. 객체와 링크는 원본 레코드 참조와 규칙 버전을 가지고, 값 하나의 근거는 같은 규칙을 다시 실행해 보여 준다.
22. **엑셀**은 위치·전원·냉방 정보의 주된 수집 경로다. 양식을 제공하고 양식대로면 매핑 없이 수집한다. 한 행에 장비 하나인 목록 형식을 받고 격자 형식은 읽지 않는다. 파서는 포트 뒤에 두고 파일 크기와 압축 해제 후 크기에 상한을 두며 수식은 값으로만 읽는다.
23. **담당자와 역할.** 소스, 데이터셋, 피드, 정의 항목에는 담당자(사람이나 그룹)가 지정된다. 담당자는 연락처이고 권한은 권한 부여에서만 온다(ADR-0012). 소스를 실행하고 중지하고 보류된 스트림을 해제하는 일은 범위를 가진 `operator`가 한다. 다른 소스의 데이터셋을 읽는 정의는 읽는 소스가 작성자의 범위 안이어야 하고, 승인은 승인 지점(출발 타입 하나, ADR-0012)에서 읽는 소스의 범위도 확인하며 읽는 소스의 담당자에게 알린다(고침 8-34).
24. **역할은 4종으로 기동한다**: API, 워커, 질의 엔진, 수집기(ADR-0006). 워커가 수집부터 적용까지와 스케줄을 맡는다. 수집 변경 로그는 포트이고 어댑터 2종(PostgreSQL, 메시지 로그 스토리지)이 정식이다. 알파는 PostgreSQL이고 메시지 로그 스토리지 어댑터는 클로즈드 베타이며 제품은 그 스토리지를 직접 띄우거나 운영하지 않는다(고침 8-34). 원본 레코드의 오래된 구간과 키 상태도 포트 뒤에 둔다(ADR-0009). 화면은 다른 리포지토리가 만들고 이 리포지토리는 REST API와 CLI를 제공한다. 소스·피드·스케줄·타입의 피드 테이블은 API의 자원이다.
25. **테스트 자료**는 합성 세계 하나에서 배치와 스트림 형태를 함께 만드는 생성기와 정답 KG, 그리고 입력을 변형하는 장치(스키마 변경, 수집량 부족, 대량 사라짐, 중복, 순서 뒤바뀜, 병합 셀, 수식)다. 실제 데이터는 리포지토리에 두지 않는다.
26. **정의의 변경은 ADR-0014의 경로를 따른다.** 소스, 스케줄, 정제, 피드, 링크 정의, 기대 조건, 안전장치 값의 버전, 브랜치, 제안, 드라이 런, 병합, 리버트는 ADR-0014가 정한다. 관측은 ADR-0013, 권한은 ADR-0012, 저장은 ADR-0009가 정한다.

**스트림에서 "더 낫다"의 의미.** 공개 문서에서 확인한 범위에서 Palantir Foundry의 스트림은 쓰지 못하는 연산의 목록보다 구조의 제약이 컸다(조인은 배치 쪽이 추가만 가능하고 키마다 가장 최근 값 하나만 둔다, 순서는 사용자가 키로 설계한다, 정의를 바꾸면 스트림을 재설정하고 재생한다, 객체로 가는 경로는 가장 최근 갱신이 채택된다). 그래서 5가지로 정의한다.
1. **같은 정의가 두 방식에서 실행된다.** 스트림이라서 쓰지 못하는 연산이 없다.
2. **수집 순서대로의 결정성.** 전체 순서는 제품이 번호로 부여하고, 같은 입력은 같은 결과다.
3. **삭제하지 않고 다시 실행하기.** 정의를 바꿔도 원본 레코드에서 새 정의로 되감아 다시 실행한다.
4. **삭제와 수정을 아는 조인과 집계.** 키마다 후보를 모두 보유하므로 삭제가 와도 다음 후보가 올라온다.
5. **스트림에서도 드라이 런.** 미리보기와 드라이 런이 같은 실행기를 쓴다.

- 배치와 스트림을 한 실행기에 두면 정제·매핑의 의미가 한 구현에만 있고, 드라이 런과 미리보기가 같은 경로를 탄다. 스트림 처리 엔진을 도입하면 수집 순서대로의 결정성과 이 일치를 지키기 어렵고 폐쇄망에 무겁다(ADR-0006).
- 객체를 행째 교체하면 배치 한 번이 스트림의 속성을 덮어쓴다. 속성 단위가 아니면 한 타입에 섞인 피드를 쓸 수 없다.
- 덜 수집한 결과가 대량 삭제의 흔한 원인이다. 스트림에서는 같은 일이 "스트림이 끊긴 채 보이지 않음"으로 나타난다.

## 버린 대안
- **소스 제품마다 전용 커넥터 코드**: 소스가 늘 때마다 코드가 는다. 프리셋은 데이터로 둔다.
- **사용자 코드(스크립트) 허용**: 결정성, 샌드박스, 감사를 해친다.
- **기존 수집 엔진이나 스트림 처리 엔진 도입**: 조사한 것들은 라이선스가 허용 목록 밖이거나, 드라이 런과 결정성을 지키기 어렵다.
- **질의할 때 소스에 직접 조회하기(연합)**: 소스에 부하를 주고 버전을 고정할 수 없다.
- **이번에 보지 못한 것을 일괄 삭제**: 덜 수집한 결과에서 오삭제가 난다.
- **값마다 출처를 저장하기**: 수천만 규모에서 감당할 수 없다. 원본 레코드 참조와 규칙 버전으로 다시 실행해 보여 준다.
- **배치용과 스트림용 정의를 따로 두기**: 차별점이 사라지고 의미가 두 곳에 생긴다.
- **객체를 한 소스가 통째로 소유하기**: 타입 하나에 배치와 스트림이 섞이는 것이 보통이다.
- **라우팅 테이블을 수집하지 않기, KG에는 구성만 기록하기**: 경로를 한 가지 형태에 묶는 일이라 버린다.
- **수치의 시계열을 KG에 쌓기**: 미루고 참조만 한다.
- **객체를 사용자가 직접 수정해 소스에 되써 넣기, 내보내기와 웹훅으로 외부를 바꾸기**: 현실에는 읽기만 한다.

## 조사의 한계
- 여러 제품의 내부 동작과 부하 특성은 확인하지 못했다. 비교는 공개 문서에서 확인한 범위이고, 문서는 요약 도구로 읽어 숫자와 인용을 원문과 한 글자씩 대조하지 못했다.
- 정제 연산의 수, 안전장치의 숫자, 보존 기한, 스트림 처리 속도는 추정이다. 합성 샘플 테스트와 알파에서 조정한다.
- 처리 속도를 측정한 작은 프로토타입은 스토리지 입출력이 없고 데이터가 합성이다. 실제 연산의 조합은 들어 있지 않다.
- 스트림 소스의 전달 보장과 순서는 일부만 확인했다. 모든 소스가 중복과 순서 불일치를 낼 수 있다고 전제한다.

## 이어서 정한 것: 푸시 수집, 지정 재수집, 매핑 지원, 문서에서 행까지
자세한 것은 [수집 확장](../ingestion-extensions.md)에 있다. 위 결정의 본문을 수정한 것(5, 6, 16, 20, 23, 24번)은 거기서 다시 적지 않는다.
- **푸시 수집**은 수집 방식 `stream`의 한 형태다. 소스마다 정의로 열고(기본은 닫힘) 서비스 계정으로 인증한다. 그 계정의 역할은 8번째 역할 `ingester`이고, 범위에 속한 소스에 푸시하고 수집 엔벨로프를 보내는 것만 하며 읽기도 없다(ADR-0012). 같은 것을 여러 번 보내도 한 번만 반영되는 것은 **중복 제거 기간 안에서** 성립한다(기본 7일, 소스마다 설정, 계약에 적는다). 푸시 수집의 "순서는 `source_time`으로 가린다"는 수집 순서가 아니라 지연 도착 값 처리 규칙이다. 푸시 수집만 하는 소스는 전체 스냅샷 정합성 대조를 함께 두지 않으면 완전함을 선언하지 못한다.
- **지정 재수집.** 객체를 지정하면 그 객체에 값을 제공하는 피드의 소스에서 그 객체의 것만 다시 읽어 같은 경로로 적용한다. 프리셋이 `keyed_read`를 선언하고, 지원하지 못하면 가장 좁은 범위의 읽기로 대신한다. 소스 보호의 한도 안에서 실행되고 삭제를 만들지 않으며 **스케줄을 기아 상태로 만들지 않는다**(소스의 속도 상한에서 스케줄용 할당량을 남긴다).
- **확인의 근거는 소스에서 관측한 것이다.** 푸시된 값은 `declared`이고 `observed`가 아니다. 프락시움은 실제 시스템에 쓰지 않는다(ADR-0001).
- **매핑 지원 방법.** 샘플과 컬럼 통계, 정해진 규칙으로 만든 매핑과 식별 후보의 제안(자동으로 적용하지 않는다), 타입 기준 보기, 저장 전 미리 보기. 원본을 보여 주는 경로(소스 탐색, 미리 보기, 샘플, 통계)는 그 데이터셋이 채우는 타입의 읽기 권한도 함께 요구하고 감사 로그에 남기며, `open`이 아닌 컬럼의 흔한 값은 제공하지 않는다. 시크릿을 복호화하는 일(소스 탐색, 점검, 미리 보기, 트라이얼 수집)은 메인 브랜치의 소스 정의 그대로이면 그 소스를 범위에 가진 `editor`도 할 수 있고, 브랜치가 접속 주소를 바꿨으면 그 소스의 `operator`여야 한다. 브랜치에만 있는 소스에는 `branch_id`를 받는다.
- **문서, 트리, 행.** 원본 데이터셋에 파싱 단계(파서가 트리를 만들고 행 선택이 테이블을 만든다)를 둔다. 파서는 제품에 포함된 고정 목록이고 라인 템플릿은 데이터다. 읽지 못한 행은 버리지 않고 건수 집계의 "읽지 못함" 필드로 센다. 자유 서술 텍스트에서 의미를 추출하는 일은 제품이 하지 않는다.
- **`volatile`.** 스트림이 `volatile` 속성을 바꾸면 이력 없는 경량 변경 레코드가 프로젝션과 알림에 전달된다. 값이 같으면 레코드가 없다. 링크는 `volatile`이 될 수 없다(ADR-0009).
- **식별.** 폐기된 객체가 이전 ID로 되살아나는 것은 강한 키로 일치했거나 정해진 기간 안일 때뿐이다. 합칠 때 흡수된 쪽의 링크 ID는 `identity_event`의 연결 정보로 잇는다.
- **보류된 스트림이 해제될 때**는 한도가 있는 배치로 나눠 적용하고, 배치마다 `ingest_seq`를 부여받는다.
- **시크릿**은 ADR-0018이 정한다. 프리셋의 요청 템플릿에 시크릿이 들어갈 위치를 따로 표시하고, 수집하는 데이터 안의 시크릿은 수집할 때 제거한다(`redact`).
