# ADR-0085 새 KG 저장의 구현 결정과 스키마 계획의 유닛 `adapter.pgschema`

## 맥락

ADR-0080이 저장을 타입마다 테이블로 다시 설계했고 ADR-0083이 PostgreSQL 어댑터를 나눴다. 이제 새 KG 저장을 구현한다. 설계를 구현으로 옮기면서 정해야 할 것이 남았다. 포트가 나르는 필드 가운데 설계의 테이블에 자리가 없던 것, 등록부의 불변식, 포기와 복원의 트랜잭션 경계, 스키마 관리기의 규칙, 테스트 기반을 바꾸는 순서다. 독립 검토가 빠진 결정과 함정을 짚었고 그 결과를 여기에 모은다.

이 변경은 그 가운데 순수한 부분(모델에서 DDL 계획을 만드는 유닛)만 구현한다. 나머지는 뒤의 변경들이 구현하고, 각 변경이 자기 테스트를 붙인다.

## 결정

1. **스키마 계획은 새 유닛 `adapter.pgschema`다.** 순수하고(입출력도 `database/sql`도 `lib/pq`도 없다) `core.kernel`과 `core.model`만 import한다. 실행은 `adapter.pgstore`가 한다(다음 변경). ADR-0083의 공용 부품 규칙에 `pgschema`를 더한다. `pgstore`의 `may_import`에 더하는 것은 실행기를 만드는 변경이 한다.
2. **행 수에 비례하는 테이블은 KG의 저장 스키마에 둔다**(ADR-0080 결정 2). 변경 배치와 항목, 가벼운 변경, 식별자, 식별 이벤트, 수집의 순서 사건은 객체를 `obj_no`로 가리킨다. 공용에는 KG마다 몇 줄인 것만 남는다.
3. **포트에 있는데 테이블에 자리가 없던 것**을 둔다. 링크의 `discriminator`(진짜 컬럼), 객체와 링크의 행 단위 출처 `source_refs`(jsonb), 변동 값의 등급과 근거와 출처(상태 테이블의 `prov jsonb` 한 컬럼. 키는 속성 번호).
4. **등록부의 불변식.** `(KG, ref)`의 `obj_no`와 `type_no`는 영원히 같고 등록부의 행은 KG를 지울 때 말고는 지우지 않는다. 살아 있음의 컬럼(`retired_seq`. 살아 있으면 NULL)과 살아 있는 행만의 부분 인덱스를 둔다. 진실은 타입 테이블이고 등록부는 찾기용이다. 처음 본 키 `first_key`를 등록부에 두고, 식별 색인 `object_key`(`bound_seq` 포함)를 둔다. 포기는 그 변경 번호가 묶은 `object_key`의 줄을 지우고 복원은 지우지 않는다(식별의 이력은 되감지 않는다).
5. **포기와 복원.** 변경 번호 하나씩 거꾸로, 번호마다 트랜잭션 하나로 변경 항목으로 그 번호의 행만 찾아 제자리에서 되돌린다. 머리 행에 진행의 표시("포기하는 중", "복원하는 중과 어디까지")를 두어 도중에 죽으면 어느 서버든 이어서 끝낸다. 복원은 첫 트랜잭션에서 세대를 올리고 그 KG의 읽기와 쓰기를 "복원하는 중"으로 거절하다가 마지막 트랜잭션에서 연다. 그림자 스키마는 전체 다시 만들기에만 쓴다.
6. **스키마 관리기의 규칙.** 더하는 변경만 받는다. 저장 스키마마다 매니페스트(생성기 버전, 모델과 번호와 검색 집합의 해시, 타입마다의 요약)와 상태(`ok`, `index_pending`, `stats_pending`)를 공용에 적고, 상태는 해시에 들지 않는다. 서버의 매니페스트와 어긋나면 그 KG의 적용과 질의를 거절한다. 실행기는 한 트랜잭션 안의 어드바이저리 잠금과 `lock_timeout`으로 안의 단계를 돌리고, 데이터가 있는 테이블의 인덱스만 트랜잭션 밖에서 `CONCURRENTLY`로 하나씩 만들며, 무효 인덱스를 정리하고, 매니페스트를 마지막에 쓴다(되풀이해도 같다). 공용의 저장 형식 번호가 서버가 아는 것보다 크면 서버는 시작하지 않는다. `kg_no`는 시퀀스에서 받는다.
7. **저장소가 모델을 얻는 길**은 `pgstore.Open`의 설정에 모델 제공자(정의 집합의 해시에서 등록부)를 받는 것이다. 포트의 `CreateKG`는 그대로다. `NewTestStore`는 표준 모델이 기본이다.
8. **임대의 만료는 DB의 시각으로 판단한다.** 설정 `LeaseClock`의 기본이 DB의 시각이고 호출자의 시각은 테스트만 쓴다.
9. **"검색에 쓴다"의 집합은 계획의 입력이다.** 모델의 해시 밖에 있다. 처음 집합은 식별 키를 이루는 속성이고 모델에서 계산해 낸다(`DefaultSearchSet`). 손으로 더하는 목록 파일은 필요해질 때 만든다. 인덱스는 이 집합과 상태 테이블의 공통 상태 컬럼에만 둔다.
10. **식 통계는 표준 속성 전부에 건다.** 한 객체에 식 여덟까지 묶는다. 만드는 때는 측정으로 정한다. KG 하나를 만드는 시간이 1초를 넘으면 통계 객체를 첫 적재 뒤에 만들고, 그동안 매니페스트의 상태는 `stats_pending`이다. 큰 적용의 마지막 청크 뒤에는 바뀐 행이 임계값을 넘은 테이블에 `ANALYZE`를 부른다(트랜잭션 밖. 실패해도 적용은 성공).
11. **한 트랜잭션의 상한은 새 옵션이다.** 청크의 크기와 따로 둔다. 0은 끔이고 지금과 같은 동작(언제나 청크의 크기로 자른다)이다. 값은 조립부가 준다. 옵션이 다른 서버가 이어받아도 이어 가기의 판단이 같아야 한다.
12. **묶음 읽기는 선택 능력 인터페이스다.** 여러 id의 객체와 여러 객체의 링크를 읽는 인터페이스를 `graph`에 더하고 적용자가 있으면 쓴다. `scratch.go`와 메모리 저장소는 고치지 않는다.
13. **해시 키.** 어댑터가 KG마다 키를 갖는다(마스터 키로 감싸 공용에 둔다. 키 버전이 있다). 후보 KG는 기준 KG의 키를 물려받는다. 적용과 확정과 검증을 하는 모든 서버가 마스터 키를 가져야 하고, 마스터 키를 바꾸면 감싼 키를 다시 감싼다. 마스터 키 파일 없이 DB의 백업만 있으면 기밀 값이 있는 KG는 해시를 다시 계산하지 못하므로 백업의 안내에 적는다.
14. **테스트 기반.** 기존의 잠긴 테스트를 옮기지 않는다. 새 저장의 합격선은 지금의 적합성 사례를 그대로 돌리는 것이고, 새 저장만의 확인은 새 테스트 파일에 둔다. 테스트 전용 유닛 `adapter.pgcheck`가 수집의 끝에서 끝까지가 두 저장에서 같은 해시를 내는지 등 다섯 안팎을 확인하고, 바꿔 다는 변경의 합격선이 된다.
15. **바꿔 다는 방식.** 새 구현을 새 이름으로 더해 적합성을 통과시킨 뒤 한 변경에서 `Open`과 `NewTestStore`가 새 구현을 주게 바꾸고 옛 테이블의 코드를 지운다. 옛 테이블을 지우는 마이그레이션도 그 변경에 넣는다. 알파 릴리스가 이미 나갔으므로 ADR-0032 결정 4의 "좁히는 변경은 한 판 뒤"의 **한 번뿐인 예외**다. 이유는 옛 데이터를 새 테이블로 옮기지 않기로 해서 옛 판과 새 판이 함께 도는 것이 뜻이 없기 때문이다. 그 마이그레이션은 KG에 딸린 공용 테이블의 행도 비운다(인증 기록은 남긴다). 알파 사용자는 PostgreSQL에 둔 KG를 다시 수집한다(릴리스 노트에 안내한다. 이미 나간 알파의 실행 파일은 새 DB에서 모든 연산이 오류가 난다는 것을 함께 적는다).
16. **바꿔 단 직후의 읽기.** 새 저장이 지금의 `Reader`와 `Snapshot`을 그대로 구현하므로 읽기 쪽 코드는 바뀌지 않고 제품이 돈다. 질의 스키마와 내장 읽기는 뒤의 단계가 바꾼다.
17. **계획이 정한 테이블의 모양**(이 변경). 물리 이름은 번호로만 짓는다(`t_<type_no>`, `s_<type_no>`, 컬럼 `a<attr_no>`). 값을 문서에서 꺼내는 식은 한 곳에서 만들어 인덱스, 통계, 뒤의 뷰가 같은 글자를 쓴다. 상태 테이블(`object_state`)의 컬럼은 모든 타입이 가진 변동 속성(표준 모델에서는 `lifecycle_state`와 `oper_state`)이고, 이 집합이 바뀌거나 값 형이나 번호가 바뀌거나 타입이나 속성이 모델에서 사라지면 더하는 변경이 아니라서 거절한다. 채움 비율은 타입 테이블 85, 상태 테이블 70이고 큰 테이블과 상태 테이블에는 자동 청소의 설정을 건다. 준비 테이블의 접두어 `stage_`, `calc_`와 `ingest_diff`는 이름만 예약하고 테이블은 만들지 않는다. 컬럼과 키의 정확한 모양은 저장소의 구현이 쓰면서 고칠 수 있고 고치면 생성기 버전을 올린다.
18. **준비 테이블에서의 적용**(`StagedApplier`, 입력 다이제스트의 새 규칙, 변동 값의 단계)은 이 기록이 정하지 않는다. 수집의 규모 설계의 원형 측정 뒤 뒤의 결정 기록이 정한다.

## 이유

- 순수한 계획은 DB 없이 테스트할 수 있고 3단계의 뷰와 함수의 계획을 같은 유닛에 더할 수 있다. 실행기가 계획을 모르는 DB 쪽 일(잠금, 재시도, 무효 인덱스)만 맡는다.
- 포트가 나르는 필드가 테이블에 없으면 해시와 이력이 깨진다. 설계의 표를 구현 전에 고치는 것이 가장 싸다.
- 포기와 복원을 변경 번호 하나씩 하면 트랜잭션이 짧고(청소를 막지 않는다) 도중에 죽어도 어느 서버든 이어서 끝낸다.
- 행 수에 비례하는 테이블을 KG의 스키마에 두면 KG를 지우는 일이 스키마를 지우는 일이고 한 KG의 청소가 다른 KG에 닿지 않는다. 옛 데이터를 버리는 지금이 옮기기 가장 싸다.
- 매니페스트의 상태를 해시 밖에 두면 통계를 나중에 만드는 KG가 정상 상태로 남고 어긋남의 판단이 흔들리지 않는다.

## 대안과 기각 사유

- **스키마 계획을 `pgstore` 안에 둔다.** 3단계의 뷰와 함수가 쌓이면 한 유닛이 너무 커지고 순수한 부분의 커버리지를 따로 지키기 어렵다.
- **스키마 계획을 코어에 둔다.** 코어에 SQL 문자열이 들어간다.
- **복원 뒤에 같은 `ref`가 오면 새 `obj_no`를 준다**(복원이 등록부 행을 지운다). 이력과 과거 시점 함수에서 `id`로 잇는 것이 복원을 넘어서 깨진다. 규칙 하나가 낫다.
- **옛 테이블을 한 릴리스 뒤에 지운다.** 옮기지 않는 데이터를 위해 옛 판과 새 판을 함께 돌려야 한다.
- **"검색에 쓴다"를 모델의 필드로 둔다.** 모델의 해시와 잠긴 모델 테스트에 번진다. 표시는 모델의 뜻이 아니라 인덱스다.
- **통계 객체를 항상 KG를 만들 때 만든다.** 만드는 시간을 재기 전에는 정할 수 없다. 상태를 두면 어느 쪽도 고를 수 있다.

## 결과

- 새 유닛 `adapter.pgschema`가 있다. `Build`(계획과 매니페스트), `Diff`(더하는 변경의 단계), `DefaultSearchSet`, 이름과 식의 함수를 내보낸다. 구조 계약, `ARCHITECTURE.md`, 커버리지 하한을 같은 변경에서 더한다.
- 표준 모델의 계획은 테이블 215개(타입 168, 변동 속성이 있는 타입 35, 고정 12), 문장 833개를 낸다.
- 새 요구사항은 없다. 이미 있는 예정 요구사항(REQ-551부터 REQ-632)이 이 결정을 구현하는 변경에서 강제 장치를 얻는다.
- 문서 `storage-shape.md`의 테이블 절과 스키마 관리기 절이 이 결정의 새 내용(컬럼, 매니페스트의 상태)으로 고쳐진다.
