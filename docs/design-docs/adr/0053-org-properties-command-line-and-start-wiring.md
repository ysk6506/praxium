# ADR-0053 조직 속성의 명령줄과 시작 배선

## 맥락

ADR-0050이 조직 속성의 모델(오버레이, 이름과 번호 공간, 합치기, 변경 분류)을, ADR-0049가 정의 저장소(불변 리비전, 정의 세트, 머리, 번호 원장, 데이터 폴더의 `definitions.json`)를 만들었다. 둘은 서로를 모르고 아무도 부르지 않는다. 사용자는 자기 컬럼("관리 부서", "도입 연도")을 표준 타입의 속성으로 받아 화면과 조회에서 표준 속성처럼 보고 싶은데, 파일을 검사해 저장하는 길도, 저장된 정의로 수집과 서버가 시작하는 길도 없다. 조회에는 두 가지 문제도 있었다. 명령줄의 `--attr 이름.연산=값`이 첫 점에서 잘라 `org.x.equals=A`를 깨뜨렸고, 레지스트리가 행보다 옛것일 때(정의를 바꾸기 전에 시작한 서버) 모르는 속성 번호의 값이 이름 없는 속성으로 응답에 나왔다.

## 결정

1. **명령.** `praxium model check|apply|show|export|history`. 조직 속성 파일(ADR-0050의 `praxium-org-model`)을 읽어 검사하고 데이터 폴더의 정의 저장소에 쓴다.
   - `check`는 저장하지 않는다. 오류를 모아 한 번에 보이고, 경고와, 저장된 정의와의 차이(추가, 호환되는 변경, 호환성을 깨는 변경)를 보인다. `-data-dir`이 없으면 표준 모델에 대해서만 검사한다. 잠금을 잡지 않으므로 서버가 폴더를 열고 있어도 된다.
   - `apply`는 검사에 통과하면 항목 하나가 대상(표준 객체 타입이나 특성) 하나인 `type_overlay`로 정의 저장소에 직접 적용한다(`Service.Apply`). 새 속성의 번호는 저장소의 번호 원장(`next_attr_no`, 시작 값 `model.OrgNumberBase`)에서 받고, 번호 올리기와 리비전, 세트, 머리 쓰기는 **한 번의 원자적 쓰기**다. 바뀐 것이 없으면 아무것도 쓰지 않고 그렇다고 말한다. 호환성을 깨는 변경은 거절하고 무엇이 깨는지와 가야 할 길을 말한다. 강제 플래그는 없다. 정의 세트의 해시는 `definitions.SetHash`에 표준 레지스트리의 해시를 기준으로 넘겨 계산한다.
   - 이름을 바꾸면(`id`를 그대로 두고 `name`을 고침) 옛 이름은 파일에 적지 않아도 별칭으로 남는다. 파일은 완전한 상태라서 파일에 없는 저장된 속성은 호환성을 깨는 변경이다. 물러나게 하려면 `status: deprecated`로 바꾼다.
   - `show`, `export`(번호와 ID가 채워진 파일. 다시 `apply`하면 "바뀐 것 없음"), `history`(세트마다 시각, 해시 앞 8자, 추가·바뀐 속성 수, 메시지)는 읽기라서 잠금 없이 된다. `-set N`으로 지난 세트를 읽는다. 쓰는 중인 파일을 읽지 않는 것은 정의 파일의 원자적 교체가 보장한다. 읽는 쪽은 앞선 쓰기가 남긴 임시 파일도 지우지 않는다(지금 쓰는 중일 수 있다).
   - 모든 명령에 `--help`와 `--json`이 있고 종료 코드는 기존 규칙(0, 1 실패, 2 명령줄 오류)을 따른다. `-store postgres`는 "정의의 PostgreSQL 저장은 아직 없다"고 말하고 종료 코드 2다.
2. **데이터 폴더의 잠금.** `apply`는 폴더의 잠금(`LOCK`)을 잡고 쓴다. 서버나 수집이 폴더를 열고 있으면 이유를 말하고 거절한다. 서버는 시작할 때 정의를 읽으므로, 도는 중에 정의를 바꾸면 서버가 모르는 번호의 값이 들어올 수 있다.
3. **시작 배선.** `ingest run -data-dir`, `local`, `demo`, `api serve -store file`이 시작할 때 데이터 폴더의 정의를 읽어 표준 모델과 합친 레지스트리를 쓴다(`loadModel`). 서버는 저장소를 열어 폴더를 잡은 뒤에 읽는다. 정의가 없으면(`definitions.json`이 없거나 항목이 없으면) 지금과 똑같이 표준만 쓰고 아무것도 만들지 않는다. 합칠 수 없는 정의(대상 없음, 번호 겹침, 깨진 파일)면 **시작을 거절**하고 이유와 해결 방법을 한두 줄로 말한다. 데이터 폴더가 없는 실행(메모리 스토어)과 PostgreSQL 스토어의 서버는 표준만 쓴다(PostgreSQL의 정의 저장이 없다).
4. **수집.** 매핑의 `attribute`에 `org.<이름>`을 쓰면 된다(컴파일이 레지스트리를 쓴다). 물러난(`deprecated`) 속성에 잇는 매핑은 정의 오류로 거절하고 후속 속성이 있으면 이름을 알려 준다(표준 속성만 후속을 가질 수 있다. 조직 속성은 후속 없이 물러난다). 타입에 없는 속성의 오류는 `org.`을 붙이면 있는 이름이면 그렇게 알려 준다. 이름을 바꾼 속성의 옛 이름(별칭)은 매핑에서 그대로 통한다. 조직 속성은 식별 키에 쓸 수 없다. 이유를 말하고 거절한다(이미 저장된 객체의 식별을 바꾸면 이력을 잃는다).
5. **조회.** 명령줄의 `--attr 이름.연산=값`과 `--filter 이름.연산=값`은 **마지막** 점에서 잘라 이름이 점을 가질 수 있다. 서버의 속성 필터는 이름으로 찾으므로 조직 속성 이름을 그대로 받는다(끝에서 끝까지 테스트한다).
6. **안전장치.** 조회가 레지스트리에 없는 속성 번호의 값을 만나면(정의를 바꾸기 전에 시작한 서버가 새 번호의 값을 읽을 때) 그 값을 건너뛴다. 이름 없는 속성을 만들거나 죽지 않는다. 값이 건너뛰어지는 것을 알리는 응답의 경고 필드는 계약 변경이라서 이번에는 하지 않는다. 이 변경 전에는 이름 없는 속성이 응답에 나왔고 값이 텍스트 검색에도 걸렸다(민감 등급을 모르는 채로).

### 잠긴 테스트의 변경

없다. 새 테스트만 더한다.

## 이유

- **직접 적용은 얇은 껍질로 바뀐다.** 브랜치와 제안을 거치는 흐름(ADR-0049에 있다)은 승인할 사람과 화면이 있어야 쓸모가 있다. 지금 사용자는 파일과 데이터 폴더를 가진 한 사람이다. `apply`가 저장소의 직접 적용을 쓰면 나중에 제안 경로가 와도 `apply`는 "브랜치를 만들고 제안하고 승인하고 병합"하는 얇은 껍질로 바뀌고, 파일 형식과 검사, 분류, 번호 규칙은 그대로다.
- **폴더의 잠금은 서버를 지킨다.** 서버가 시작할 때 읽은 정의가 도는 중에 바뀌면 서버가 모르는 번호의 값이 들어올 수 있다. 읽기만 하는 명령은 잠금을 잡지 않아 서버가 도는 중에도 검사하고 볼 수 있다.
- **시작을 거절한다.** 합칠 수 없는 정의로 조용히 표준만 쓰면 수집이 조직 속성을 빼고 값을 쓰고, 서버는 있는 값을 안 보여 준다. 시작하지 않는 것이 한두 줄의 이유로 고치게 하는 가장 싼 방법이다.
- **옛 이름이 매핑에서 통한다.** 이름 바꾸기가 호환되는 변경이려면 이름을 바꾼 뒤에도 옛 이름으로 쓴 매핑과 질의가 통해야 한다. 질의는 이미 별칭을 쓴다.
- **마지막 점.** 표준 속성 이름은 점이 없고 연산은 점이 없으므로 마지막 점이 이름과 연산의 경계다. 첫 점으로 자르면 조직 이름을 쓸 수 없다.
- **건너뛰는 안전장치는 정의 적용의 한계를 줄인다.** 재시작해야 반영되는 한계는 두고, 한계에서 응답이 틀리거나 서버가 죽는 일을 막는다.

## 대안과 기각 사유

- **`apply`가 서버 실행 중에도 쓰고 서버가 정의를 다시 읽는다.** 서버가 레지스트리를 바꾸는 일(타입 색인, 필터, 응답 캐시, 계약 생성)이 크고, 읽는 중에 모델이 바뀌는 일관성을 설계해야 한다. 재시작 한 번이 훨씬 싸다.
- **합칠 수 없으면 경고하고 표준만 쓴다.** 위 이유대로 조용히 틀린 결과를 만든다.
- **호환성을 깨는 변경을 `-force`로 허용한다.** 쓰이는 번호의 값이 다른 뜻이 된다. 새 속성을 더하고 채우고 옛것을 물러나게 하는 길이 있다.
- **`--attr`에 이름과 연산을 따로 받는 플래그.** 기존 사용법과 이미 쓰는 도움말이 깨진다. 마지막 점 규칙은 점 없는 이름에서 지금과 같은 결과를 낸다.

## 결과

- 사용자는 파일 하나로 표준 타입에 속성을 더해 수집하고, 표준 속성과 똑같이 타입 화면, 객체 상세, `find`의 필터에서 본다. 안내서는 [조직 속성 안내서](../../guides/org-model.md)다.
- **재시작해야 반영된다.** `apply`한 뒤에 서버(`local`, `demo`, `api serve`)를 다시 시작해야 새 속성을 안다. 그 전에 새 번호의 값이 들어오면 서버는 그 값을 건너뛴다. 헬스 상태에 정의 세트가 서버와 저장소가 다른 것을 보이는 일은 뒤의 변경이다.
- PostgreSQL 스토어의 서버는 이번에는 표준 모델만 쓴다. 정의의 PostgreSQL 저장이 생기면 같은 `loadModel`이 그것을 읽는다.
- 하지 않은 것(뒤의 변경): 계약의 `Property`에 `namespace`와 `display_names`, 웹의 표시 이름과 배지, KG의 정의 세트 포인터, PostgreSQL 정의 저장, API 쓰기 경로, 브랜치와 제안을 거치는 흐름(그때 `apply`는 얇은 껍질이 된다), 응답의 "건너뛴 값" 경고.
