# ADR-0081 PostgreSQL의 HA

## 맥락

제품 책임자가 정했다. HA를 고려하고 HA 구성을 쉽게 한다. 저장은 PostgreSQL 하나가 되었고([ADR-0080](0080-redesign-storage-and-queries-on-one-postgresql.md)) 정의와 수집 상태까지 DB에 있으므로, DB의 장애는 곧 제품의 장애다. 지금 코드는 풀 하나와 연결 문자열 하나이고, 장애 조치를 만나면 어떻게 되는지 규칙이 없다.

OpenAI는 글 "Scaling PostgreSQL to power 800 million ChatGPT users"(<https://openai.com/index/scaling-postgresql/>)에서 주 서버 하나와 읽기 복제본 여럿으로 읽기를 넓히고, 쓰기를 줄이며, 무거운 질의와 재연결 폭풍을 막은 운영을 밝혔다. 우리 제품은 규모와 조건이 다르다. KG마다 쓰기 순서가 하나이고 읽기가 대부분이며 사용자 질의가 무거워질 수 있다. 그래서 교훈을 옮기되 수치는 그대로 쓰지 않는다. 근거 조사의 자세한 내용은 [PostgreSQL의 HA와 쉬운 구성](../postgres-ha.md)에 있다. 조건: 이 결정은 설계와 문헌 조사로 정했고, 장애 조치와 복제본은 직접 테스트하지 않았다(아래 결과).

## 결정

1. **장애 조치(선출, 승격, 옛 주 서버의 격리)를 제품이 구현하지 않는다.** Patroni와 CloudNativePG가 한다. 기준 버전은 PostgreSQL 18이고 19에만 있는 기능에 기대지 않는다.
2. **제품이 코드와 검사와 테스트로 지키는 규칙은 열여섯 가지다.**
   1. 쓰기는 주 서버로만 간다. 연결 문자열은 여러 호스트를 받고 쓰기 풀은 `target_session_attrs=read-write`로 주 서버만 고른다. 풀을 쓰기, API 읽기, 대량 읽기로 나눈다. 사용자 질의의 풀은 읽기 복제본을 가리킬 수 있다.
   2. 역할이 바뀌는 오류(SQLSTATE 25006, 57P01, 57P02, 57P03, 클래스 08)를 만나면 그 풀의 연결을 모두 버리고 다시 연다. 연결의 최대 수명은 5분에서 10분이다.
   3. 죽은 연결을 알아챈다. TCP keepalive, `TCP_USER_TIMEOUT`, 연결 시한 5초, 모든 DB 호출의 `context` 시한이다. 값은 테스트로 정한다.
   4. 커밋됐는지 모르는 쓰기는 "모름"으로 분류하고, 머리 행의 적용 번호와 변경 배치 id로 확인한 뒤에만 다시 쓴다. 소스의 소스 커서와 응답의 변경 번호는 내구화된 뒤에만 낸다.
   5. 적용 트랜잭션은 `synchronous_commit=on`이다. 대기가 둘 이상이면 후보가 둘 이상인 쿼럼(`ANY 1`)을 권한다. 동기 대기 하나로 "잃는 데이터 0"을 약속하지 않는다. `remote_apply`는 기본이 아니다.
   6. 세션에 남는 것(세션 advisory lock, `LISTEN`과 `NOTIFY`, 임시 테이블, `LOCAL`이 아닌 `SET`, 이름 있는 준비된 문장)을 쓰지 않고 검사 규칙으로 막는다. 큰 적용의 계획과 스테이징 데이터는 로그가 있는 테이블에 두고 적용이 끝나면 지운다. UNLOGGED는 쓰지 않는다. 장애 조치 뒤에도 큰 적용은 남은 조각부터 이어서 한다. 파티션은 구현할 때 정한다.
   7. 읽기는 복제본에서 돌 수 있다. 그래프 함수와 내장 읽기는 쓰기, 임시 테이블, 시퀀스 없는 순수 SQL이다. CI가 대기 서버에서 질의 스키마 전체를 실행해 본다.
   8. 복제본 읽기의 복구 충돌(40001)은 한 번만 다시 시도하거나 주 서버로 보낸다. `max_standby_streaming_delay`가 API 읽기 시한보다 작으면 점검이 경고한다.
   9. "이 번호 이후" 읽기는 복제본의 머리 행의 적용 번호로 판정한다. 장애 조치로 커밋을 잃었을 수 있어서, 새 주 서버의 적용 번호보다 큰 번호는 "미래 번호" 오류다.
   10. 재연결 폭풍을 막는다. 연결을 만들 때 지터와 속도 제한을 두고, 서버는 장애를 자동 재시도로 가리지 않는다. 점검은 `인스턴스 수 × 풀의 최대 연결 수 ≤ max_connections − 예약`을 확인한다.
   11. 읽기 경로(토큰 확인, 목록, 질의)는 주 서버에 쓰지 않는다. 주 서버가 장애인 동안에도 읽기가 산다.
   12. 읽기 복제본 하나가 빠지는 테스트를 한다. 주 서버로 넘어가는 읽기의 양에 상한이 있다.
   13. 마이그레이션은 파일마다 한 트랜잭션이고, 인덱스는 온라인으로 별도 단계에서 만들며 무효 인덱스를 시작할 때 정리한다. 새 컬럼은 NULL을 허용하고 테이블을 다시 쓰는 변경은 하지 않는다. 잠금 시한이 있다.
   14. 리스의 만료는 앱 서버의 시계가 아니라 DB의 시각으로 판정한다. 점검이 시계의 어긋남을 보여 준다.
   15. KG 사이의 조인이 없으므로 KG를 다른 클러스터로 옮길 수 있다. 샤딩의 도피처다.
   16. 복제 슬롯은 없어야 정상이다. 있으면 점검이 경고하고 상태와 보유한 바이트를 보여 준다.
3. **배포마다 가장 쉬운 구성을 권하고 본보기와 절차서를 준다.** 로컬 한 대는 제품과 PostgreSQL을 함께 띄우는 구성 파일이고 HA를 약속하지 않는다. 가상 기계의 작은 운영은 주, 대기, 셋째 투표 노드(Patroni와 etcd)이고, **노드가 둘뿐이면 자동 장애 조치를 약속하지 않고** 수동 승격의 절차서와 `pg_rewind` 절차를 준다. 쿠버네티스는 CloudNativePG 인스턴스 3개다. **클라우드의 관리형 PostgreSQL은 지원 대상이 아니다(본보기도 테스트도 없다).** 세 배포의 본보기를 모두 내고 각각 CI에서 장애 조치를 테스트했는지 적는다.
4. **점검 명령 `praxium db check`를 둔다.** 읽기 전용이고 JSON과 종료 코드가 있다. 버전, 주 서버인지 대기 서버인지, 복제 상태와 지연, 동기 설정(대기 하나의 동기 구성은 경고), 연결 한도와 풀, 긴 트랜잭션, 복제 슬롯, 무효 인덱스와 안 쓰는 인덱스, 백업의 나이, 시계의 어긋남, 권한(위험한 내장 함수의 실행 권한이 거둬져 있는지 포함)을 본다.
5. **하지 않는 것.** 제품이 선출을 구현하기, GPL과 AGPL 도구를 함께 배포하기, 19 전용 기능을 전제하기, 복제본에 쓰기나 임시 테이블이 필요한 함수를 올리기, 동기 대기 하나로 유실 0을 약속하기, 서버의 자동 재시도로 장애를 가리기, 읽기 경로에서 주 서버에 쓰기, 테스트하지 않은 HA를 약속하기, UNLOGGED 테이블을 쓰기, 쓰기 경로에 트랜잭션 모드의 풀러를 두기.
6. **서버는 상태를 DB에 두고 여러 개 띄울 수 있다.** 마스터 키 파일의 일은 시크릿 저장소를 다루는 단계에서 정한다(ADR-0076).

## 이유

- 장애 조치의 선출과 옛 주 서버 격리는 PostgreSQL 자체가 주지 않는 영역이다. 틀리면 주가 둘이 되어 데이터를 잃는다. 검증된 도구가 이미 하고 있다.
- 제품이 약속할 수 있는 것은 그 위에서 틀리지 않는 일이다. 풀이 옛 주 서버를 붙잡고, 죽은 연결을 오래 쓰고, 커밋됐는지 모르는 쓰기를 다시 쓰고, 장애 직후 모든 서버가 한꺼번에 연결하는 일은 도구가 막아 주지 않는다.
- OpenAI 사례에서 옮긴 것: 쓰기는 주 서버 하나로 두고 읽기를 복제본으로 넓힌다(규칙 1, 7, 11), 무거운 질의의 격리와 끄기(ADR-0080의 질의 실행기), 긴 트랜잭션 금지, 재연결 폭풍과 재시도 폭풍의 방지(규칙 10), 복제본 하나 손실의 테스트(규칙 12), 스키마 변경 때 테이블을 다시 쓰지 않기(규칙 13), 복제 지연의 경보(점검 명령), 인덱스를 필요한 곳에만. 우리와 다른 점은 KG마다 쓰기 순서가 하나라는 것과 사용자가 SQL을 쓴다는 것이다.
- 노드가 둘뿐이면 자동 장애 조치의 투표가 성립하지 않는다(Patroni는 과반이 서는 합의 저장소가 필요하다). 동기 대기 하나는 그것이 죽을 때 쓰기가 멈춘다. 그래서 둘짜리 구성에서 약속할 수 있는 것을 줄여 적는다.
- 읽을거리: Rick Branson의 글 "10 Things I Hate About PostgreSQL"(https://rbranson.medium.com/10-things-i-hate-about-postgresql-20dbab8c2791). 글의 약점 가운데 청소, 트랜잭션 ID의 나이, 통계, 복제본과 백업의 구분을 점검 항목으로 옮겼다.
- 점검 명령은 새 기능이 아니라 운영 문서의 신호를 한 번에 보는 것이어서 구현이 작고, 잘못된 설정(연결 한도 초과, 대기 하나의 동기, 슬롯 방치)을 장애 전에 찾는다.

## 대안과 기각 사유

- **제품이 주 서버 선출을 직접 구현.** 분할 뇌의 위험을 제품이 떠안고, 검증된 도구보다 늦고 틀리기 쉽다.
- **노드 둘의 자동 장애 조치를 약속.** 투표가 성립하지 않아 분할 뇌나 쓰기 중단이 생긴다. 수동 승격의 절차서가 정직하다.
- **PostgreSQL 19 전용 기능을 전제.** CloudNativePG와 Patroni 같은 도구가 19를 명시하는지 확인하지 못했다. 19의 `WAIT FOR LSN`은 있으면 쓰는 빠른 길로만 둔다.
- **캐스케이딩 복제를 기본 구성으로.** 복제본이 많아질 때의 선택이고 우리 규모에서 구성이 복잡해진다. 필요해지면 구현 때 정한다.
- **관리형 DB의 HA를 그대로 쓰기.** 제품이 DB의 설정과 권한을 스스로 잡아야 해서 기각한다(역할 만들기, 위험한 내장 함수의 실행 권한 거두기, 체크섬, 복제 설정의 점검). 제품 책임자가 지원하지 않기로 했다.
- **서버의 자동 재시도로 장애를 가리기.** 재시도 폭풍을 만든다. 힌트만 주고 호출자가 지터를 두고 다시 한다.
- **읽기 경로에서 주 서버에 쓰기(마지막 접속 시각 갱신 같은).** 주 서버가 장애일 때 읽기도 죽는다.
- **GPL과 AGPL 도구(repmgr, Barman 등)를 함께 배포.** 라이선스 부담이 커진다. 문서로 안내만 한다.

## 결과

- 구현은 [ADR-0080](0080-redesign-storage-and-queries-on-one-postgresql.md)의 1단계(연결 규칙과 CI의 PostgreSQL 18)와 6단계(본보기 구성, 점검 명령, 장애 조치의 테스트)에 나뉜다. 요구사항 REQ-553~559, REQ-602~617, REQ-620, REQ-621, REQ-628은 예정이다.
- **측정과 한도**: 드라이버(`lib/pq`)의 장애 조치 때 동작은 소스로만 확인했고 테스트하지 않았다. 규칙 3의 값은 시작점이다. 실제 복제본으로는 테스트하지 않았다.
- **미결**: 규칙 5의 `SET LOCAL synchronous_commit=local` 적용 대상, 리스 만료를 DB 시각으로 옮기는 방법(규칙 14), 복구 연습 스크립트의 이름과 범위, 쿠버네티스 본보기를 CI에서 띄우는 방법, 토큰 확인 경로가 지금 쓰는지(규칙 11), 시점 복구 뒤 수집의 소스 커서 처리.
- 1단계의 변경이 고칠 곳: `README.md`와 `harness-guide.md`의 "PostgreSQL 16".
- 지금 문서의 "파티션 + UNLOGGED" 준비 테이블 행은 로그 있는 테이블로 고치고(PostgreSQL 운영), 기준 버전과 연결 규칙도 맞춘다.
