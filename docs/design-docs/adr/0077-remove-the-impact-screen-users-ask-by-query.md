# ADR-0077 영향 범위 화면을 삭제한다

## 맥락

제품 책임자가 정했다. **영향 범위 계산은 제품이 하지 않는다. 사용자가 질의를 써서 직접 한다. 제품은 그것이 가능하게 만든다.** 제품이 대신 풀어 주는 계산(`impact` 질의)과 그 결과를 그리는 화면은 이 방향과 맞지 않는다.

웹 화면에는 영향 범위를 그리는 화면이 있다. 원인 트리의 계산, 묶음, 퍼짐 재생, 그래프와 목록 부품([ADR-0051](0051-impact-view-parts-svg-without-new-dependencies.md))과, 그것을 주소와 읽기 훅과 객체 상세의 입구에 이은 연결([ADR-0054](0054-impact-screen-wired-to-the-api.md))이다. 요구사항은 REQ-350~357과 REQ-374~380이다.

## 결정

1. **웹의 영향 범위 화면을 지운다.** 화면, 읽기 훅, 순수 계산(원인 트리, 배치, 묶음, 재생 상태, 주소 상태, 목록 행, 알림 문구), 그래프·목록·재생 부품과 그것만 쓰던 등급 표지, 알림 부품을 지운다. 객체 상세의 입구 셋("이 객체가 멈추면", "안에 든 것까지 멈추면", "이 객체가 의존하는 것")과 주소(`#/kg/{kg}/impact`)와 메뉴 연결도 지운다. 지운 주소는 "페이지를 찾을 수 없습니다"가 된다. 다른 화면이 쓰는 부품(근거 등급의 이름과 톤, 결과 알림, 표, 탭 등)은 남긴다.
2. **계약은 이 변경에서 바꾸지 않는다.** 서버의 `queries:impact` 경로, 계약 조각, 생성한 API 코드는 그대로다. 서버와 CLI와 계약은 뒤의 변경이 지운다.
3. **요구사항을 삭제한다.** REQ-350~357과 REQ-374~380의 행을 지우고 그 번호는 다시 쓰지 않는다(요구사항 입구의 번호 문단에 적었다). 요구사항을 삭제하는 정해진 절차는 리포지토리에 없다. 그래서 행을 그것을 테스트하던 테스트와 같은 변경에서 지우고(TRACE001), 번호를 쓰지 않는다고 입구 문서에 남긴다.
4. **REQ-381은 삭제하지 않는다.** 접속 설정 화면의 문구(`접근 토큰`, 접속 방식 넷의 안내)에 관한 요구사항이고 영향 범위와 무관하다. 영향 범위의 요구사항 문서에서 [웹 UI, 명령줄, 릴리스](../../product-specs/requirements-web-cli-release.md)로 옮기고 번호는 그대로 둔다. 테스트는 `apps/web/src/impact-screen.test.tsx`에 하나 남는다(아래 5).
5. **`apps/web/src/impact-screen.test.tsx`는 지우지 않는다.** 대체된 결정 기록도 문서 검사의 경로 확인(`DOC031`)을 받고, 확정된 ADR-0054의 본문이 이 파일을 적고 있다. 확정된 본문은 고칠 수 없으므로(`DOC070`) 파일이 없으면 검사가 실패한다. 규칙을 바꾸지 않고, 파일을 남기되 REQ-381의 테스트 하나만 두도록 다시 쓴다. 파일 이름이 내용과 맞지 않는 것은 알고 있고, 이름을 바꾸는 일은 이 결정의 범위 밖이다.
6. **ADR-0051과 ADR-0054를 대체한다.** 두 결정이 정한 것은 모두 위 1로 지워진다. 두 기록의 `status`를 `superseded`로, `superseded_by`를 이 ADR로 고친다(앞부분만 고치고 본문은 그대로다). `enforced_by`가 가리키던 테스트가 모두 사라지므로 이렇게 해야 `DOC080`을 어기지 않는다.
7. **잠긴 테스트.** 지우는 테스트와 지원 코드의 잠금 항목(테스트 122개, 지원 191개)과 고쳐서 남기는 항목 하나(`impact-screen.test.tsx`의 `beforeEach` 준비 코드)를 `amends_tests`에 적는다. 남는 REQ-381 테스트는 이름을 바꿨으므로 새 항목으로 잠근다. 옛 항목은 지우는 목록에 있다.
8. **문서.** 용어집의 "영향 범위" 항목과 "직접 노출 / 상속된 노출" 항목, 웹 화면 설계의 화면 목록과 영향 범위 화면 절, 구조 문서의 `web.ui`와 `web.data` 설명에서 영향 화면에 관한 부분을 고친다.

## 이유

- 제품이 계산해 보여 주는 화면은 사용자가 질의로 직접 구한다는 방향과 맞지 않고, 남겨 두면 읽기 질의와 모델의 설계가 이 화면에 맞춰진다.
- 화면과 서버를 한 번에 지우면 변경이 커진다. 화면을 먼저 지우면 계약은 그대로여서 생성한 API 코드가 달라지지 않고, 서버의 삭제가 화면에 영향을 주지 않는다.
- 번들이 줄어든다. 화면을 지운 뒤의 번들은 gzip으로 JS 146159바이트, CSS 6205바이트이다(삭제하기 전에는 JS 163098, CSS 6588).

## 대안과 기각 사유

- **화면을 두고 서버만 지운다.** 화면이 서버 경로를 부르므로 깨진 화면이 남는다.
- **서버와 화면을 한 변경으로 지운다.** 잠긴 항목과 요구사항과 계약 변경이 한꺼번에 모여 검토가 어렵다. 둘로 나누고 웹을 먼저 한다.
- **영향 화면을 숨기기만 한다(입구만 지운다).** 쓰지 않는 코드와 테스트와 요구사항이 남아 부채가 된다.
- **REQ-381을 함께 삭제한다.** 접속 설정 화면의 문구는 영향 범위와 무관하게 필요하다.
- **`impact-screen.test.tsx`를 지우고 ADR-0054의 본문을 고친다.** 확정된 본문은 고칠 수 없다.

## 결과

- 영향 범위 화면과 입구가 사라지고, 관련 요구사항 행(REQ-350~357, 374~380)이 사라진다. 요구사항 문서 `requirements-impact.md`에는 서버 계산의 요구사항(300번대, 425~437)만 남는다.
- 커버리지 바닥은 낮추지 않는다. 지운 뒤의 웹 유닛의 값은 바닥 이상이다.
- 이 결정은 새 의존성도 새 설정도 더하지 않는다.

## 뒤의 변경

서버의 `impact` 질의(풀이기, 서비스, REST 경로, CLI), 계약 조각과 `openapi.json`, 생성한 API 코드, 서버 쪽 요구사항(REQ-300~306 등), 관련 결정 기록과 문서는 뒤의 변경(ADR-0078)이 지운다. 표준 모델의 계산용 필드는 그 뒤의 별도 단계에서 다룬다.
