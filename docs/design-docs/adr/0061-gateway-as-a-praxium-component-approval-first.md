# ADR-0061 MCP 게이트웨이는 프락시움의 구성요소다

## 맥락

지금까지의 전제는 "프락시움은 현실에 읽기만 하고, 실제 툴은 에이전트가 프락시움 밖의 MCP 게이트웨이로 호출한다"였다(ADR-0001, ADR-0008, 방향 메모). 이 전제에서는 권한 판단이 프락시움 안과 밖 두 곳에서 따로 이뤄지고, 호출이 지나간 뒤 현실이 맞게 바뀌었는지를 아는 쪽이 없다. 프락시움이 가진 것(객체와 링크, 영향 범위, 근거 등급, 승인, 감사)이 바로 바꾸기 전의 판단과 바꾼 뒤의 확인에 필요한 것이다. 조직마다 이미 MCP 서버를 갖고 있는 경우가 많아서 새 툴을 만들게 하지 않고 그것을 업스트림으로 연결하는 길이 필요하다.

제품 책임자가 방향을 정했다. 이 결정은 그 방향을 설계 책임자가 구체화한 것이다. 상세 설계는 [게이트웨이 설계](../gateway.md), [게이트웨이의 안전](../gateway-safety.md), [액션 타입 표](../gateway-actions.md)에 있다. 구현은 하지 않았고 클로즈드 베타 뒤다.

## 결정

### 1. 누가 무엇을 정했는가

| 정한 쪽 | 내용 |
|---|---|
| 제품 책임자 | 게이트웨이를 프락시움의 구성요소로 둔다. 우회를 막는 것은 조직의 책임이다. 권한은 업무 요청 때 한꺼번에 부여하고 조건이 충족될 때 실행한다. 지속성 있게 관리하고 이어 갈 맥락을 준다 |
| 설계 책임자 | 아래 2~15항. 신뢰의 경계, 실행의 계약, 호출의 순서, 분류, 확인, 가용성, 정의의 통제, 단계와 여는 조건 |

### 2. 구성과 보장의 범위

- 게이트웨이는 같은 릴리스, 같은 실행 파일의 별도 기동 모드다. 코어가 판단하고 레지스트리와 기록을 가지며, 게이트웨이가 집행하고 업스트림 MCP 서버의 자격 증명을 가진다. 하네스와 업스트림 MCP 서버는 프락시움 밖에 있다.
- KG 조회의 MCP 인터페이스은 영구히 읽기 전용이다. 게이트웨이는 다른 주소의 다른 구성요소다. "MCP는 읽기만 한다"는 앞 면에 대한 말로 남는다.
- 보장은 **게이트웨이를 지나는 호출**에 한한다. 우회가 열려 있으면 그 길에는 게이트웨이의 거절, 잠금, 한도, 정지 스위치가 적용되지 않는다. 정지 스위치는 "게이트웨이를 지나는 호출의 정지"를 뜻한다. 우회를 막는 일은 조직의 책임이고, 보장하지 않는 것은 [안내서](../../guides/what-praxium-guarantees.md)에 목록으로 둔다.
- 게이트웨이를 우회 차단의 선행 조건으로 삼지 않는다.

### 3. 신뢰의 경계

- 코어와 게이트웨이를 나누는 효과는 자격 증명이 코어 밖으로 나가지 않는 것뿐이다. 코어가 가장 믿어야 하는 구성요소이고 코어의 보호가 여는 조건의 첫째다.
- 게이트웨이가 스스로 가지는 것: 업스트림 주소와 자격 증명(코어의 레지스트리는 이름만 가리킨다), 허용하는 바꾸기 업스트림 툴과 호출 한도의 두 번째 사본, 코어 밖으로 직접 내보내는 호출 이력.
- 위험이 큰 액션에서 승인자의 서명을 게이트웨이가 확인하고 업스트림 서버가 권한을 직접 검사하는 것은 목표로만 둔다.

### 4. 실행의 계약

"단계"로 툴을 여는 방식을 쓰지 않는다. 실행은 계약을 가진다: 실행 ID, 고정한 프로세스 정의 버전, 시작할 때 한꺼번에 부여한 허용 액션 집합, 시작할 때 풀어 고정한 대상 객체 집합(늘리려면 승인), 호출과 객체와 시간의 한도, 승인 규칙, 상태, 세대 번호가 있는 하네스 세션 임대.

- 실행의 시작이 곧 권한이다. 사람이 시작하고, 이벤트로 시작하는 것은 읽기만 하는 프로세스에 한한다. 만든 사람이 시작 권한이 있는 계정에 대응하는 티켓은 사람의 시작이고 기계가 만든 티켓은 이벤트다.
- "조건이 충족될 때 실행"은 프락시움이 스스로 실행하지 않는다는 뜻이다. 조건이 안 맞으면 실행 호출이 "아직"과 맞지 않은 조건을 돌려주고 에이전트가 다시 부른다.
- 툴 목록은 실행마다 고정이고 통제는 호출할 때의 거절이다. 실행 중에 더하는 툴은 이미 등록하고 승인한 액션만이고 정의 승인자 수준의 승인과 개수 한도가 있다.
- 토큰이 없어도 의도는 남는다. 하네스는 실행이 열려 있는 동안 새 토큰을 받고, 승인을 기다리는 동안 살아 있는 토큰이 필요 없다.

### 5. 호출의 모양, 실행 대장, 이어 가기

- 바꾸는 호출은 준비, 실행, 조회의 세 번의 호출이다. 준비는 (액션, 대상, 인자)가 같으면 멱등이고, 이미 끝났으면 "이미 했음"을 돌려주며 다시 하려면 이유를 적어 명시적으로 요청하고 한도에 센다. 실행은 한 번만 실행한다.
- 게이트웨이는 바꾸는 업스트림 호출을 스스로 다시 보내지 않는다. 에이전트 연결이 끊겨도 업스트림 호출은 끝까지 기록한다. 대상이 여럿이면 대상마다 기록한다.
- 코어는 의도의 상태(준비됨, 승인 대기, 실행 중, 끝남, 확인 결과, 모름)를 실행 대장에 영속적으로 가진다. 읽기 툴 하나가 이어 가기 맥락(무엇인지, 끝난 것과 확인 결과, 진행 중이거나 모르는 것, 남은 것)을 준다. 이어받겠다고 부르면 세대 번호가 올라 낡은 세대의 호출은 거절된다. 표준 클라이언트만으로 동작한다.
- 승인은 내용 해시와 조건의 증거에 묶이고 실행 직전에 조건을 다시 확인한다. 승인은 폴링으로 기다린다.

### 6. 읽기, 진단, 바꾸기

분류는 툴의 표시가 아니라 프락시움이 정한다. 읽기(부작용 없음), 진단(부작용이 있을 수 있음: 업스트림 서버와 대상별 한도, 실행에 묶고 기록), 바꾸기(계약과 승인과 확인)다. 자유 형식 인자의 툴은 읽기가 될 수 없다. 업스트림 툴은 꺼진 채 등록하고 승인한 뒤에만 켜며 정의의 해시를 고정한다. 정의가 바뀌면 끄고 다시 승인받는다. 에이전트에게는 업스트림 툴의 설명을 전하지 않고, 응답은 필터링해서(리소스 링크 제거, 크기 제한, 시크릿 가리기) 넘긴다.

### 7. 연결별 신뢰 단계

연결은 액션 타입과 업스트림 툴의 짝이고 한 액션이 한 업스트림 호출이다. 단계는 그림자(보낼 호출을 기록만) → 호출마다 승인 → 자율이고 사람이 확인 기록을 보고 올린다. 툴의 정의가 바뀌거나 확인 결과가 어긋나면 자동으로 내려간다. 실험 환경으로 보내는 경로는 두지 않는다(ADR-0005, 프락시움은 실험 환경을 모른다).

### 8. KG를 믿는 규칙과 확인

- 업스트림 호출에 넣는 식별자는 그 툴이 다루는 시스템에서 직접 읽은 `observed` 식별자이고 정한 나이 안이며 열린 식별 후보나 충돌이 없어야 한다. 사실 등급만으로는 모자라다(사람이 쓴 `declared` 값도 기본이 사실이다).
- 영향 범위를 쓰는 조건은 관련 링크 타입에 완전성 선언이 있어야 통과하고 없으면 "확인 못 함"이다. 모르는 것은 영향으로 센다. 자료의 나이는 값 자체의 시각으로 재고, 조건마다 허용 나이가 있어 낡으면 통과가 아니다.
- 잠금은 대상과 직접 속한 중복 그룹과 그 그룹이 속한 그룹까지 걸고 깊이 한도와 임대가 있다. 진행 중인 의도는 다른 실행의 평가에서 이미 일어난 것으로 센다.
- 툴의 성공 응답을 믿지 않는다. 읽기는 코어가 요청하고 수집 쪽이 한다. **소스의 세 능력 가운데 이미 있는 지정 재수집(REQ-225)과 기대와 대조(REQ-226)를 재사용하고 새 읽기 경로를 만들지 않는다.** 1차에서는 다시 읽을 수 있는 소스의 속성만 조건에 쓴다.
- 결과는 기존의 넷, `confirmed`, `not_yet`, `contradicted`, `unverifiable`이다. KG는 관측만 믿고, 어긋나면 자동으로 되돌리지 않고 멈춰서 사람에게 넘긴다. 밀어 넣은 값은 `declared`라 증거가 되지 못한다.
- 안전은 세 겹이다: 권한(누가 어느 액션을 하는가), 상태(지금 해도 되는 상태인가), 결과(했더니 맞는가).

### 9. 보안 원칙

에이전트와 툴의 결과를 믿지 않는다. 기본은 거절이고 판단할 수 없으면 막는다. 프락시움이 죽어도 사람의 길은 열려 있다. 권한의 실체는 정의다. 자격 증명을 나누고 받은 토큰을 업스트림에 넘기지 않는다. 기록 없이 바꾸지 않는다(추가 전용, 해시 체인, 조직 보안 도구로 내보내기, 기록을 쓸 수 없으면 거절). 사람의 인증은 조직의 SSO(OIDC)를 쓰고 첫 설치와 서비스 계정과 긴급용으로 내장 인증을 둔다. 폭주를 통제한다(실행별 한도, 큰 영향의 사람 승인, 정지 스위치). 정책은 포트 뒤에서 직접 구현하고 OPA나 Cedar는 필요할 때 선택 어댑터로만 둔다. 판단 코드는 입력의 순수 함수이고 입력을 기록해 재현한다.

### 10. 가용성과 긴급

- 프락시움이 멈추면 에이전트는 아무것도 바꾸지 못한다. 1차는 "코어가 멈추면 게이트웨이도 전부 막는다"이고 읽기도 막는다. 읽기를 계속하는 것은 측정한 뒤에 더한다. 장애 종류별 동작은 [안전](../gateway-safety.md) 5절의 표가 정한다.
- 게이트웨이는 상태가 없고 둘 이상이다. 파일 스토어는 단일 인스턴스 전용이라, 게이트웨이를 쓰는 운영 구성은 동기 복제와 장애 전환이 있는 PostgreSQL이다. 멱등 키로 장애 전환 중 이중 전송을 막고, 결과를 모르는 호출은 확인이 풀 때까지 "모름"이다.
- 게이트웨이는 버릴 수 없는 기록(호출 전 기록, 정지 상태)을 로컬 저널에 둔다. 죽은 게이트웨이의 저널에만 있는 결과는 "모름"으로 남는다. 정지 신호는 코어와 다른 관리자 긴급 키로도 낼 수 있다.
- 바꾸는 툴을 켠 설치는 에이전트가 바꿀 수 있는 인프라와 분리된 기반이 필요하고, 프락시움이 의존하는 객체는 자동 변경에서 뺀다.
- 긴급 프로세스는 정식 종류다(사람이 시작, 호출마다 승인, "확인 못 함" 조건을 승인 화면에 표시, 사후 검토 자동 개시). 규칙을 끄는 길은 없다. 1차에서는 열지 않고 2차 안에서 연다.

### 11. 정의의 통제

게이트웨이 정의의 종류(프로세스, 액션과 툴의 연결, 툴 승인, 조건 제거, 한도 완화, 업스트림 서버 등록)는 위험 등급 하한이 R3이고 자동 병합과 자동 첫 적용에서 빠진다. 권한을 넓히는 리버트는 긴급 경로를 쓸 수 없다. 이 종류의 승인자 지정은 관리자 두 명이 한다. 바꾸는 툴을 켠 설치는 셀프 승인(`solo_approval`)을 거절하고, 승인자가 한 명뿐인 조직은 바꾸는 툴을 쓸 수 없다. 특정 시점 복구 뒤에는 바꾸는 툴이 닫힌 채 시작하고 툴 승인을 다시 확인한다. 작성자, 승인자, 툴 승인자는 서로 달라야 하고 승인은 내용 해시에 묶인다.

### 12. 승인 피로

승인 시간이 지나면 거절이고 자동 승인은 없다. 승인 화면은 조건의 증거, 영향 요약, 평소와 다른 점을 보여 준다. 승인자별 건수, 걸린 시간, 거절률을 지표로 둔다. 인자는 해시와 가린 요약으로 기록한다. 업그레이드할 때 진행 중인 실행은 시작할 때의 정의 집합을 유지한다. 시계 어긋남이 한도를 넘으면 헬스 상태로 올린다.

### 13. 하네스와 다른 게이트웨이

표준 MCP 클라이언트로만 연결한다. 하네스와 게이트웨이 사이의 상호 TLS 결속은 선택 강화이고, 없으면 토큰 수명을 짧게 하고 한도를 낮춘다. 하위 에이전트는 실행의 한도와 세대를 공유한다. 이미 게이트웨이가 있는 조직은 프락시움 게이트웨이를 그 뒤의 MCP 서버로 둘 수 있게 지원하고, 코어와 게이트웨이의 판단 계약은 버전을 가진다.

### 14. 단계와 여는 조건

순서는 KG 쪽 선행 조건(읽기 전용 MCP 인터페이스, API와 DB 소스와 지정 재수집, 범위가 있는 권한, 감사 로그 저장) → 게이트웨이의 읽기 툴 → 바꾸는 툴 1차 → 2차다. 릴리스 서명과 출처 증명은 읽기 툴 단계로 앞당긴다.

- **1차(승인 전용)**: 모든 바꾸는 호출에 사람의 승인이 필요하고, 액션은 되돌릴 수 있고 지장이 없고 객체 하나에 곧바로 관측되는 속성 하나다. 액션 타입 표(95개의 바꾸는 액션 중 10개가 대상, 2개는 설계 검토까지 보류)가 대상을 정한다. "실험 기능, 기본 꺼짐"으로 내고 켤 때 조건 점검을 보여 준다.
- **2차(자율)**: 연결별 신뢰 이력, 장애 훈련 기록, 그림자 운전에서 잘못된 확인의 비율의 측정값, 외부 보안 검토, 판단 테스트 모음의 통과 같은 증거가 모인 뒤에 연다.
- 여는 조건은 기능의 이름이 아니라 확인할 수 있는 증거로 [안전](../gateway-safety.md) 7절에 적는다. 1차의 조건 목록은 새 설계이므로 병합 전에 설계 검토를 받는다.
- API를 직접 부르는 툴 출처은 프락시움이 현실 시스템의 자격 증명을 갖게 되므로 1차 뒤에 다시 정한다.

### 15. 요구사항과 고치는 문서

요구사항 REQ-450~469를 예정으로 [requirements-gateway.md](../../product-specs/requirements-gateway.md)에 둔다. 전제가 바뀐 문서(`updates_docs`)는 "현재 코드는 읽기만 한다"와 "KG 조회의 MCP 인터페이스은 영구히 읽기 전용이다"를 구분해 고친다. 요구사항 REQ-111(소스는 읽기 전용)은 그대로 유효하다.

## 이유

- 판단하는 쪽과 집행하는 쪽이 한 제품이면 권한이 두 곳에서 따로 정해지는 문제와 "누가 한 일인지 불분명하다"는 문제가 줄고, 바꾼 뒤의 확인을 같은 KG가 한다.
- 에이전트의 한 번 호출이 여러 번의 판단을 필요로 하지 않도록 권한을 시작할 때 한꺼번에 주고, 조건은 집행 직전에 다시 본다. 단계로 툴을 열면 목록이 호출마다 변해 표준 클라이언트와 맞지 않는다.
- 툴의 성공 응답과 표시는 믿을 수 없고, 사람이 쓴 값도 사실 등급일 수 있다. 그래서 관측과 나이와 완전성 선언으로 판단한다.
- 코어와 게이트웨이를 나눠도 코어가 뚫리면 판단이 뚫리고, 우회가 열리면 게이트웨이가 힘을 잃는다. 그래서 가능한 것과 불가능한 것을 숨기지 않고 쓴다.
- 처음에는 승인 전용으로 좁혀서 증거(그림자 운전의 측정, 훈련의 기록)를 모은 뒤에 넓히는 것이 안전하다.

## 대안과 기각 사유

- 게이트웨이를 프락시움 밖에 두는 지금의 전제: 판단이 두 곳에 나뉘고 확인하는 쪽이 없어 기각했다.
- 단계마다 툴을 여는 실행 모델(v1): 툴 목록이 호출마다 변하고, 한꺼번에 부여하는 권한이라는 제품 책임자의 방향과 맞지 않아 실행의 계약으로 바꿨다.
- 읽기는 서명한 승인 묶음으로 코어 없이 계속하는 방안(v1): 1차에서는 코어가 멈추면 읽기도 막는다. 측정 뒤에 다시 본다.
- 업스트림 툴의 주석(`readOnlyHint` 같은 표시)으로 분류하는 안: 툴이 스스로 붙인 표시를 믿을 수 없어 기각했다.
- 사실 등급이면 식별자로 쓰는 안: 사람이 쓴 값도 사실이라 기각했다.
- MCP의 요청 도중 질의(elicitation)로 승인을 받는 안: 승인은 오래 걸리고 토큰이 없어도 남아야 해서 폴링으로 했다.
- 실험 환경으로 검증 호출을 보내는 경로: 프락시움은 실험 환경을 모른다는 원칙(ADR-0005)을 지킨다.

## 하지 않는 것

- 구현하지 않는다. 표준 모델(`actions.json`)을 고치지 않는다. 액션 타입에 인자의 정의와 효과 선언을 더하는 일은 할 일이다(REQ-468).
- 게이트웨이를 우회하는 길을 막는 일은 프락시움이 하지 않는다.
- 프락시움이 바꾸는 호출을 스스로 만들거나 스스로 실행하지 않는다.
- API를 직접 부르는 툴 출처, 읽기 툴로 하는 확인, 업스트림 서버의 권한 검사와 승인자 서명의 확인은 이 결정에서 열지 않는다.
- 1차에서는 긴급 프로세스, 읽기의 계속, 자율 실행을 열지 않는다.

## 미결 사항

[안전](../gateway-safety.md) 9절에 목록으로 둔다. 지원할 MCP 명세의 판, 토큰의 형식과 수명과 소지 증명, 실행의 권한과 시작한 사람의 역할의 관계, 새 역할의 필요, 운영 액션의 위임과의 통합, 조건과 효과의 문법, 여러 KG와 사이트와 망 분리, 수치 전부, 작은 조직의 직무 분리, 분리된 기반의 확인 방법, 2차의 되돌릴 수 없는 액션, 업그레이드 중 진행 중인 실행, 잘못된 확인의 비율의 측정 방법, 신원을 업스트림에 넘기는 방법, 프로세스 정의의 형태와 시작 방법.

## 검토에서 받아들이지 않은 것

- 실험 환경으로 경로를 두는 것: 위에서 기각했다.
- 업스트림 서버의 권한 검사와 승인자 서명의 확인을 지금 요구하는 것: 목표로만 둔다. 업스트림 서버가 같이 바뀌어야 하는 일이라 이 제품이 보장할 수 없다.
- 게이트웨이를 우회 차단의 선행 조건으로 삼는 것: 제품 책임자가 우회를 조직의 책임으로 정했다.
- API 직접 호출 툴 출처을 지금 정하는 것: 1차 뒤에 다시 정한다.

## 결과

- 문서가 "현재 코드는 읽기만 한다"와 "게이트웨이는 방향이다"를 구분한다. 코드는 바뀌지 않는다.
- 수정한 ADR(0001, 0006, 0008, 0011, 0012, 0014, 0017, 0018)은 front matter에 `amended_by`만 더해진다. 본문은 그대로다. ADR-0005는 원칙 7을 그대로 지키므로 고치지 않는다.
- 역할 4종의 표와 구조 계약은 구현할 때 결정 기록으로 고친다.
