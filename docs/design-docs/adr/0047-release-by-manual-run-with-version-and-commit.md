# ADR-0047 릴리스를 수동 실행으로도 낸다 — 버전과 커밋을 입력받아 태그와 릴리스를 함께 만든다

## 맥락

ADR-0039는 `v*` 태그를 푸시해야만 릴리스가 만들어지게 했다. 수동 실행은 아티팩트만 남겼다. 그런데 태그를 푸시할 수 없는 환경이 있고, 터미널 없이 GitHub 화면에서만 릴리스를 내야 할 때도 있다. 첫 릴리스(`v0.1.0-alpha.1`)는 이미 검증을 마친 커밋을 그대로 내보내야 하는데, 그 커밋에는 이번 변경의 스크립트가 없다. 릴리스 노트도 지금은 GitHub가 만드는 것뿐이라 어떤 내용이 나가는지 검토할 수 없다.

## 결정

1. **수동 실행에 입력 두 개를 더한다.** `version`이 비면 지금처럼 스냅숏 빌드만 하고 릴리스는 만들지 않는다. 채우면(`0.1.0-alpha.1` 또는 `v0.1.0-alpha.1`) 그 버전으로 빌드하고 태그와 릴리스를 함께 만든다. `commit`은 릴리스할 커밋의 40자리 SHA이고, 비우면 실행한 브랜치의 끝 커밋이다. 실행할 수 있는 사람은 저장소에 쓰기 권한이 있는 사람이다(GitHub가 정한다).
2. **작업을 셋으로 나눈다.**
   - `plan`(읽기 권한): 실행한 ref를 모든 이력과 태그와 함께 체크아웃하고 `scripts/release-plan.sh`로 입력을 검증해 `mode`(`tag-push`, `manual`, `snapshot`), `tag`, `sha`, `publish`를 낸다.
   - `build`(읽기 권한): `plan`이 정한 `sha`를 체크아웃해 지금과 같은 단계로 빌드한다. 빌드 스크립트와 설정 액션은 **릴리스할 커밋의 것**이다.
   - `release`(`contents: write`, `publish`가 `true`일 때만): **실행한 ref**를 체크아웃하고 아티팩트를 내려받아 `scripts/release-publish.sh`로 게시한다.
3. **검증(`release-plan.sh`).** 버전은 시맨틱 버저닝이고(앞의 `v`는 있어도 없어도 되며 태그는 항상 `v`로 시작한다), 커밋은 40자리 16진수이고 저장소에 있어야 한다. 수동 릴리스(버전이 있는 실행)는 워크플로를 **메인 브랜치(`refs/heads/main`)에서 실행했을 때만** 받아들이고(스냅숏은 어느 ref에서나 된다), 커밋이 메인 브랜치의 조상(끝 커밋 포함)이어야 하고, 그 태그가 아직 없어야 한다. 어긋나면 이유를 말하고 실패한다. 태그 푸시는 지금과 같다(태그는 푸시된 태그, `sha`는 그 커밋, `publish`는 `true`). 값은 모두 환경 변수로 받고 검증한 뒤에만 쓴다.
4. **게시(`release-publish.sh`).** `sha256sum -c SHA256SUMS`로 파일을 확인하고, 릴리스 노트를 정하고, `gh release create`를 부른다. 태그 푸시는 `--verify-tag`, 수동 실행은 `--target <sha>`(GitHub가 그 커밋에 태그를 만든다)를 쓴다. 태그에 `-`가 있으면 `--prerelease`이고 제목은 태그다. 수동 실행에서는 게시 직전에 태그가 그사이 생기지 않았는지 `gh api`로 한 번 더 본다. 응답이 404일 때만 "없다"로 보고, 성공이면 "있다"로, 그 밖의 실패(네트워크 오류, 5xx, 권한)는 "확인하지 못했다"로 실패한다. 게시한 뒤에는 새 태그가 가리키는 커밋을 읽어 빌드한 `sha`와 같은지 확인하고, 다르면 지우고 다시 실행하라는 말과 함께 실패한다(스크립트가 스스로 지우지는 않는다).
5. **릴리스 노트는 리포지토리 파일이다.** 실행한 ref의 `docs/releases/<태그>.md`가 있으면 프런트매터를 뺀 본문을 쓰고, 없으면 GitHub가 만드는 노트(`--generate-notes`)를 쓴다. 어느 쪽이든 `SHA256SUMS`를 코드 블록으로 붙여, 다운로드하기 전에 화면에서 체크섬을 볼 수 있게 한다.
6. **스크립트에 로직을 두고 테스트로 묶는다.** 워크플로는 스크립트를 부르기만 한다. 두 스크립트는 임시 git 저장소와 가짜 `gh`로 테스트한다(`release_plan_test.go`, `release_publish_test.go`).
7. **동시 실행.** `release` 작업에 태그별 `concurrency` 그룹을 둔다. 같은 버전의 게시가 겹치지 않고, 서로 다른 버전은 서로를 기다리거나 취소하지 않는다. 워크플로 전체에는 그룹을 두지 않는다(대기 중인 실행이 새 실행에 밀려 취소될 수 있어서다).

## 이유

- **수동 실행.** 릴리스는 태그를 푸시할 수 있는 환경에 묶이지 않아야 하고, 버튼 하나와 입력 두 개로 끝나야 실수가 준다. 태그와 릴리스를 한 번에 만들면 "태그는 있는데 릴리스가 없는" 상태가 생기지 않는다.
- **세 작업으로 나눈 이유.** 같은 커밋이면 같은 바이트가 나와야 한다(ADR-0039). 그래서 빌드는 릴리스할 커밋의 스크립트와 설정 액션만 쓰고, 다른 것을 섞지 않는다. 한편 이미 검증을 마친 옛 커밋에는 게시 스크립트가 없다. 게시는 빌드가 아니므로 실행한 ref의 스크립트로 하고, 그 작업만 쓰기 권한을 갖는다. 읽기만 하는 `plan`과 `build`가 탈취돼도 저장소에 쓸 수 없다는 ADR-0039의 권한 분리는 그대로다.
- **메인 브랜치에서 실행한 것만 릴리스한다.** 게시 스크립트와 릴리스 노트는 실행한 ref의 것이므로, 검토를 거쳐 메인에 들어온 것이어야 한다. 쓰기 권한자가 다른 브랜치에서 바꾼 스크립트로 릴리스하는 것을 막는다.
- **메인의 조상만 릴리스한다.** 검토와 CI를 거쳐 메인에 들어간 커밋만 공개 릴리스가 된다. 검토를 받지 않은 브랜치의 커밋이나 임의의 SHA가 쓰기 권한자의 실수로 나가는 것을 막는다.
- **릴리스 노트를 파일로 둔다.** 노트가 끌어오기 요청으로 검토를 거치고, 저장소 이력에 남아 공개 기록이 된다. 릴리스 페이지에서 손으로 고치는 것은 기록이 남지 않는다. 파일이 없으면 지금처럼 GitHub가 만든다.
- **게시 직전에 태그를 다시 본다.** `plan`의 확인과 게시 사이에 빌드 시간이 있다. 그 사이 같은 이름의 태그가 푸시되면 GitHub는 `--target`을 무시하고 기존 태그에 릴리스를 만들어, 태그가 가리키는 커밋과 올라간 파일이 어긋난다.
- **게시 뒤에 태그의 커밋을 확인한다.** 직전 확인과 게시 사이의 아주 짧은 틈에 태그가 생기는 경우까지 잡는다. 이미 게시된 뒤라 막을 수는 없고, 잘못된 릴리스를 곧바로 알리는 것이 목적이다.
- **`GITHUB_TOKEN`이 만든 태그는 태그 푸시 워크플로를 다시 일으키지 않는다.** 수동 실행이 GitHub API로 만든 태그가 `release` 워크플로를 한 번 더 시작하는 일은 없다. 이것이 `plan`이 `manual` 모드를 따로 두고 한 실행 안에서 빌드와 게시를 모두 끝내는 이유다. 태그 푸시 실행과 수동 실행이 서로를 부르지 않으므로 같은 릴리스가 두 번 만들어지지 않는다.

## 버린 대안

- **수동 실행이 태그를 푸시한 뒤 태그 워크플로에 맡기기.** `GITHUB_TOKEN`으로 만든 태그는 워크플로를 일으키지 않아서 안 되고, 개인 토큰을 쓰면 시크릿이 늘어난다.
- **현재 ref의 스크립트로 빌드하기.** 이미 검증한 커밋과 다른 스크립트가 섞여 같은 커밋이 같은 바이트를 내지 못하고, 옛 커밋은 스크립트가 없어 빌드할 수 없다.
- **릴리스할 커밋의 스크립트로 게시하기.** 첫 릴리스 대상 커밋에는 게시 스크립트가 없다.
- **메인이 아닌 커밋도 허용하기.** 검토를 거치지 않은 코드가 공개 릴리스가 될 수 있다.
- **릴리스 노트를 워크플로 입력으로 넘기기.** 검토도 이력도 없다.

## 결과

- 릴리스를 내는 방법이 둘이다: 태그 푸시, Actions 화면의 수동 실행. 절차는 [릴리스 만들기](../../guides/release.md)에 있다.
- ADR-0039의 6번(워크플로)과 9번(릴리스 노트)이 바뀐다. 나머지는 그대로다.
- 새 파일은 `scripts/release-plan.sh`, `scripts/release-publish.sh`, 테스트 두 개, 첫 릴리스 노트(`docs/releases/v0.1.0-alpha.1.md`)다.
- 아래는 실제 GitHub에서만 확인되는 가정이다. 첫 릴리스 실행에서 확인한다: `gh release create --target <sha>`가 없는 태그를 그 커밋에 만든다는 것, `--notes-file`과 `--generate-notes`를 함께 쓰면 파일의 내용이 생성된 노트 앞에 붙는다는 것(그러면 파일이 없는 경우 체크섬 블록이 생성된 노트 앞에 온다), 읽기 권한의 `GITHUB_TOKEN`으로 `gh api repos/.../git/ref/tags/<태그>`를 부를 수 있다는 것.
