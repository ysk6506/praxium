# ADR-0034 내장 파일 스토어

## 맥락

스토리지 포트의 구현은 둘이다. 인메모리 어댑터(`adapter.memstore`)는 프로세스가 끝나면 KG가 사라지고, PostgreSQL 어댑터(`adapter.pgstore`, ADR-0032)는 운영 수준이지만 서버를 먼저 준비해야 한다. 제품을 처음 써 보는 사람, 작은 규모, 서버 한 대에서는 그 임계값이 크다. 실행 파일 하나와 데이터 폴더 하나로 KG가 남는 길이 필요하다. 운영, 이중화, 대규모는 계속 PostgreSQL 어댑터의 몫이다.

KG는 "적용된 변경의 순서"다(ADR-0025). 그러니 저장도 그 순서를 그대로 쓰면 된다. 쓰기마다 한 레코드를 로그에 덧붙이고, 가끔 상태 전체를 스냅샷으로 쓴다. 읽기는 모두 메모리에서 한다.

## 결정

1. **구조.** 인메모리 스토어(`adapter.memstore`)가 상태 기계로 남고, 그 안에 **저널 포트**(`memstore.Journal`: 복구, 레코드 덧붙이기, 스냅샷 쓰기, 닫기)를 둔다. 저널이 없는 스토어(`memstore.New`)는 지금과 똑같이 동작하고, 기존 코드와 테스트는 바뀌지 않았다. 저널이 있는 스토어(`memstore.Open`)는 상태를 바꾸는 쓰기 다섯 가지(`CreateKG`, `ApplyChunk`, `AbandonApply`, `Seal`, `Restore`)마다 **검사가 끝난 뒤, 메모리를 바꾸기 전에** 레코드 하나를 덧붙이고 동기화가 끝나야 적용해서 응답한다. 리스(lease)는 실행 중인 프로세스의 상태라서 저장하지 않는다. 다시 시작하면 리스는 없고 `attempt`는 저장된 변경 배치의 최댓값부터 이어서 오른다.
2. **새 단위 `adapter.filejournal`**(`backend/internal/filejournal`, `may_import: [core.kernel]`)이 저널의 파일 구현이다. 레코드는 바이트일 뿐이고 그래프를 모른다. `memstore`를 import하지 않고, 만나는 곳은 메서드 시그니처뿐이다(어댑터끼리 import하지 않는다). 둘을 잇는 것은 조립 루트(`cmd.praxium`)다. 테스트 파일만 `core.graph`, `adapter.graphcheck`, `adapter.memstore`를 쓴다(`test_may_import`).
3. **디스크는 작은 인터페이스(`filejournal.Disk`)로 추상화한다**: 잠금, 목록, 읽기용 열기, 새 파일 만들기, 덧붙이기용 열기, 원자적 이름 바꾸기, 폴더 동기화, 삭제, 그리고 파일의 쓰기와 동기화. `os`는 `restricted_stdlib` 때문에 조립 루트만 쓸 수 있으므로 실제 디스크(`backend/cmd/praxium/filedisk.go`)는 `cmd.praxium`이 구현해 넘긴다(파일 소스 어댑터가 오프너를 받는 것과 같은 방식). 테스트는 메모리 위의 가짜 디스크로 어느 연산에서든 끊고, 어느 바이트에서든 쓰기를 자르고, 동기화하지 않은 바이트를 잃게 한다. 규칙(`restricted_stdlib` 등)은 바꾸지 않았고, 이 구조가 규칙과 맞았다.
4. **서드파티 의존은 0이다.** 표준 라이브러리만 쓴다(`hash/crc32`의 Castagnoli, `encoding/gob`, `encoding/binary`).
5. **파일.** 데이터 폴더에는 `LOCK`, 로그 세그먼트 `log-<첫 레코드 번호 20자리>.log`, 스냅샷 `snap-<마지막 레코드 번호 20자리>.snap`(쓰는 중에는 `.tmp`)만 있다. 그 밖의 파일은 건드리지 않는다.
   - **머리(20바이트)**: 형식 이름 6바이트(`PRXLOG`, 스냅샷은 `PRXSNP`), 형식 버전 2바이트, 번호 8바이트(세그먼트는 첫 레코드, 스냅샷은 마지막 레코드), 앞 16바이트의 CRC-32C 4바이트. 머리의 배치는 어느 버전에서도 바뀌지 않는다. 읽는 쪽은 먼저 체크섬을 보고(틀리면 손상) 그다음 버전을 본다(체크섬이 맞는데 버전이 다르면 다른 버전이 쓴 파일).
   - **레코드(프레임)**: 페이로드 길이 4바이트, CRC-32C 4바이트(길이, 레코드 번호, 페이로드에 대한), 레코드 번호 8바이트, 페이로드. 적용된 쓰기 하나가 레코드 하나이고 번호는 1부터 빈틈없이 오른다. 페이로드는 형식 버전 1바이트, 종류 1바이트, 그 뒤 `encoding/gob`로 만든 전송용 타입(`wChunk` 등)이다. 속성 값은 gob이 nil과 빈 목록을 구분하지 못하므로 값만 따로 만든 작은 형식(태그 바이트와 가변 길이 정수)으로 쓴다. ID는 문자열로 쓴다. **파일 형식은 이 전송용 타입들이 정의한다**(`memstore/codec*.go`): 필드를 더하는 것은 호환되고, 빼거나 이름을 바꾸는 것은 호환되지 않는다.
   - **스냅샷**: 머리, 청크(길이 4바이트 + 바이트, 최대 1 MiB)들, 길이 0의 끝 청크, 앞 전체의 CRC-32C. 본문은 gob 부분(`snapPart`)의 연속이고 한 부분은 한 종류의 행을 최대 2048개 담아, 수백만 행도 전체 복사 없이 쓰고 읽는다.
6. **쓰기.** 레코드 하나는 한 번의 `Write`로 쓰고 응답하기 **전에** `Sync`한다. 새 세그먼트의 첫 레코드는 폴더도 동기화한다. 같은 시점의 쓰기를 묶는 동기화(그룹 커밋)는 하지 않는다. 적용기가 KG마다 하나뿐이고 쓰기는 스토어 잠금 안에서 직렬이기 때문이다. 쓰기나 동기화가 한 번 실패하면 저널과 스토어는 이후의 쓰기를 모두 거절하고(`fsync` 실패 뒤 다시 시도하지 않는다) 읽기는 계속된다. 다시 시작하면 폴더를 읽어 진실을 찾는다. 메모리는 저널보다 앞서지 않는다(저널이 먼저다).
7. **스냅샷.** 로그가 마지막 스냅샷 이후 128 MiB(`memstore.DefaultCheckpointBytes`)가 되면 스토어가 쓰는 도중에, 그리고 닫을 때(`Store.Close`) 스냅샷을 쓴다. 쓰기 순서는 임시 파일 쓰기, 파일 동기화, 이름 바꾸기, 폴더 동기화다. 그 뒤 세그먼트를 닫아 다음 레코드가 새 세그먼트에서 시작하게 하고, **스냅샷 두 세대(최신과 직전)와 직전 스냅샷 이후의 로그를 남기고** 나머지(더 오래된 스냅샷, 직전 스냅샷에 모두 담긴 세그먼트)를 지운다. 스냅샷을 쓰는 동안 쓰기는 기다리고(읽기는 일부가 기다린다) 스냅샷이 실패해도 로그는 온전하며 스토어는 계속 쓴다(`CheckpointError`로 본다).
8. **복구.** 시작할 때: (a) 임시 파일을 지운다. (b) 스냅샷을 새것부터 하나씩 **끝까지 읽어 체크섬을 확인한** 뒤에야 적재한다. 손상됐으면 다음으로 오래된 스냅샷으로 넘어가고 보고에 남긴다. (c) 그 뒤의 로그 레코드를 번호 순서대로 재생한다(스냅샷에 이미 든 레코드는 건너뛴다). 레코드는 재생할 때도 쓰기와 같은 검사를 거친다.
   - **끝의 깨진 레코드는 잘라 내고 계속한다.** 마지막 좋은 레코드 뒤에서 읽을 수 없는 바이트가 시작하고 **그 뒤에 온전한 레코드가 하나도 없으면** 중단된 쓰기로 본다(응답하지 않은 쓰기이므로 잃어도 된다). 그 세그먼트에는 더 덧붙이지 않고 새 세그먼트에서 이어 가므로 파일을 자르는 연산이 필요 없다(`Disk`에 `Truncate`가 없다). 앞 세그먼트의 끝에 남은 쓰레기는 다음 세그먼트가 정확히 이어질 때만 받아들이고 그렇지 않으면 아래 오류다.
   - **중간의 손상은 오류로 멈춘다.** 깨진 레코드 뒤에 온전한 레코드가 있거나, 체크섬은 맞는데 번호가 다르거나, 레코드나 세그먼트가 빠졌거나(재생할 첫 번호와 세그먼트의 첫 번호가 맞지 않거나), 스냅샷이 모두 손상됐는데 로그가 처음부터가 아니면 `filejournal_corrupt`이고 아무것도 열지 않는다. 조용히 건너뛰지 않는다.
   - 모든 스냅샷이 없는 폴더는 로그 1번부터 재생한다.
9. **잠금.** 폴더를 여는 쪽은 `LOCK` 파일에 배타적 잠금을 시스템 호출(`flock`, 기다리지 않는다)로 건다. 이 잠금은 파일을 연 프로세스가 가진 것이고 **프로세스가 끝나면(죽거나 강제 종료돼도) 운영체제가 회수한다.** 그래서 죽은 프로세스가 남긴 잠금은 없다. `LOCK` 파일 자체는 남아 있어도 잠금이 아니다(안에는 사람이 볼 프로세스 번호가 있다). 두 번째로 여는 쪽은 `filejournal_locked`로 곧바로 거절된다. 잠금이 믿을 수 없는 파일 시스템(네트워크 파일 시스템)에서는 쓰지 않는다. `flock`이 없는 시스템(`!unix`)은 파일에 프로세스 번호가 든 것을 잠금으로 보는 어림 구현이고, 죽은 프로세스가 남기면 사람이 `LOCK`을 지워야 한다(메시지가 파일 이름을 말한다).
10. **형식 버전.** 머리의 버전이 이 빌드가 아는 값(1)이 아니면 열지 않고 `filejournal_unsupported_format`으로 어느 파일이 어느 버전인지 말한다(스냅샷은 손상으로 보고 이전 스냅샷으로 넘어가지 않는다). 페이로드와 스냅샷 본문에도 버전이 있고 같게 처리한다(`unsupported`). 버전을 올릴 때는 새 ADR에서 읽는 쪽의 이행을 정한다.
11. **기동.** `praxium api serve -store file -store-data-dir <폴더>`(기본 `-store`는 계속 `memory`). 폴더가 없으면 만든다. `-dev-truth`는 다른 스토리지와 같게 동작하고, 같은 폴더로 다시 시작하면 KG가 남아 있다(`dev`라는 KG가 이미 있으면 `-dev-truth`는 거부된다). 서버가 멈추면 마지막 스냅샷을 쓴다. `-store-data-dir`은 `-store file`에만, `-store-dsn-file`은 `-store postgres`에만 쓸 수 있다.

### 바뀐 설정과 보호 경로

| 경로 | 바뀐 것 | 이유 |
|---|---|---|
| `harness/config/architecture.yaml` | 단위 `adapter.filejournal` 등록 (`may_import: [core.kernel]`, `test_may_import: [core.graph, adapter.graphcheck, adapter.memstore]`) | 새 단위의 등록. 다른 단위의 `may_import`는 넓히지 않았다 |
| `harness/config/coverage-floor.json` | `go:adapter.filejournal`의 하한 추가(`pnpm ratchet`이 쓴다) | 새 단위의 하한. 내린 하한은 없다 |
| `harness/config/test-lock.json` | 새 테스트의 지문(`pnpm lock-tests`가 쓴다) | 새 테스트의 잠금. 기존 항목은 바뀌지 않았다 |
| `docs/product-specs/requirements.md` | REQ-271~274 추가 | 요구사항 표의 변화 |

규칙, 한도, 허용 목록, 잠긴 테스트는 느슨하게 하지 않았다(`restricted_stdlib`도 그대로다).

## 이유

- KG가 이미 "적용된 변경의 순서"이고 쓰는 쪽이 하나라서, 로그와 스냅샷이면 충분하고 가장 단순하다. 읽기는 모두 메모리라서 인메모리 어댑터의 의미(적합성 31사례를 통과한 기준 구현)를 그대로 쓴다. 영속성은 그 아래에 덧붙은 것이라 의미가 둘로 갈라지지 않는다.
- "저널이 먼저, 메모리는 그 뒤"이면 응답한 쓰기는 반드시 로그에 있고, 로그에 있으나 응답하지 않은 쓰기는 최대 하나(중단된 쓰기)뿐이다. 이것이 복구의 약속이고, 장애 주입 테스트가 모든 연산과 모든 바이트 위치에서 확인한다.
- 이름 바꾸기와 폴더 동기화를 쓰는 스냅샷 순서와 직전 세대의 보존은 스냅샷 파일이 손상돼도 쓰기를 잃지 않게 한다(로그를 직전 스냅샷부터 남기므로).
- 끝의 손상과 중간의 손상을 가르는 기준(그 뒤에 온전한 레코드가 있는가)은 전원 차단은 한 번에 하나의 동기화하지 않은 레코드만 남길 수 있다는 점에 기댄다. 중간의 손상을 조용히 건너뛰면 KG가 틀려도 모르게 된다.
- `flock`은 운영체제가 프로세스의 끝에 거두므로 "죽은 프로세스의 잠금"을 판단할 필요가 없다(프로세스 번호를 읽어 살아 있는지 보는 방식은 번호 재사용과 경합으로 틀린다).

## 대안과 버린 이유

| 대안 | 버린 이유 |
|---|---|
| SQLite(또는 임베디드 DB 라이브러리) | 서드파티 의존이 생기고(순수 Go 이식은 크고 C 라이브러리는 빌드가 복잡하다), 읽기는 어차피 메모리라서 두 번째 질의 엔진과 스키마를 유지하게 된다. 인메모리 의미와 DB 의미가 갈라지면 적합성 31사례를 두 곳에서 지켜야 한다 |
| 로그 없이 주기적 스냅샷만 | 응답한 쓰기가 다음 스냅샷 전에 사라진다 |
| 매 쓰기마다 전체를 다시 쓰기 | 쓰기 비용이 KG 크기에 비례한다 |
| 로그의 끝을 잘라 내는 `Truncate` | 디스크 인터페이스가 커지고 잘라 내는 도중의 중단이 또 하나의 경우가 된다. 새 세그먼트로 이어 가면 쓰레기가 남을 뿐이다 |
| 프로세스 번호를 쓴 잠금 파일(`O_EXCL`) | 죽은 프로세스의 잠금을 따로 판단해야 하고 번호 재사용과 경합이 있다. `flock`은 운영체제가 회수한다 |
| 그룹 커밋 | 쓰는 쪽이 하나라서 이득이 없고 응답의 약속이 복잡해진다. 측정에서 필요하면 후속으로 한다 |

## 결과

- 처음 써 보는 사람은 실행 파일과 폴더만으로 KG를 남긴다. PostgreSQL을 준비하지 않는다.
- **한계.** (1) **단일 프로세스**: 한 폴더는 한 프로세스만 연다. (2) **이중화가 없다**: 폴더가 있는 디스크가 곧 단일 장애점이고 복제나 자동 장애 조치가 없다. 백업은 서버를 멈추고 폴더를 복사하는 것이다. (3) **메모리에 들어가는 규모**: 전체 상태가 메모리에 있고 시작할 때 모두 읽는다(아래 측정). (4) 스냅샷을 쓰는 동안 쓰기가 기다린다. (5) 레코드는 하나씩 동기화하므로 쓰기 처리량은 디스크의 동기화 속도가 정한다. (6) 마지막 레코드의 비트 부패(전원 차단이 아닌 매체 손상)는 중단된 쓰기와 구별할 수 없어 잘려 나간다. 복구 보고(`Report.DroppedTail`, `DroppedBytes`)에 남고 서버가 시작할 때 경고로 로그에 적는다(응답을 돌려주지 않은 마지막 기록을 몇 바이트 버렸는지). 이전 세대 스냅샷으로 되돌아가 복구한 경우도 경고로 적는다. (7) 파일 형식은 Go의 gob에 기대므로 다른 언어의 도구가 읽지 못한다. (8) 리스는 저장하지 않으므로 다시 시작하면 적용기는 리스를 새로 얻어야 한다. (9) 값에 `int`나 부동소수점을 쓰면 저널이 거절한다(모델의 값은 문자열, `int64`, 불리언, 목록, 맵과 nil뿐이다).
- **PostgreSQL로 옮기는 경로는 후속 작업이다.** 두 어댑터는 같은 포트를 구현하므로 내보내기와 불러오기(포트로 한 스토어의 변경 시퀀스를 다른 스토어에 순서대로 적용)가 이행의 길이다. 이 결정은 그것을 만들지 않았다. 지금은 `-store file`로 시작한 데이터를 `-store postgres`로 옮기는 도구가 없다.
- 측정과 권장 범위. 아래는 `praxium worldgen`의 합성 세계를 개발용 적재기로 넣은 **이 환경(메모리 8GB) 한 번의 측정이고 기준선이 아니다.**
  - 객체 약 24.7만(247,168), 링크 약 44.1만(441,300), 청크 139개에서 적재 시간은 저널 없이 55.8초, 저널 있이 73.3초(약 1.3배)였고 해시는 같았다. 적재 뒤 힙은 약 985MB였다.
  - 종료할 때 마지막 스냅샷에 6.0초가 걸렸다. 데이터 폴더는 종료 전 828MB, 종료 뒤 874MB(스냅샷 2세대와 로그)였다.
  - 재시작 복구는 스냅샷만 읽을 때 11.7초, 스냅샷 이후 로그 28건을 재생할 때 22.8초였고 해시가 같았다.
  - 객체 약 53만 규모는 이 환경에서 인메모리 스토어가 메모리 부족으로 실패했다. 그래서 측정값이 없다.
  - **권장 범위는 객체 수십만 개 이하, 서버 한 대다.** 그 이상은 PostgreSQL을 쓴다. 한계의 원인은 저널이 아니라 인메모리 스토어의 메모리 사용량이고, 이를 줄이는 것은 후속 작업이다.
