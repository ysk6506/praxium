# ADR-0062 KG의 읽기 전용 MCP 인터페이스

## 맥락

쓰려는 조직의 에이전트는 이미 읽기와 진단의 MCP 툴을 쓴다. KG 조회(객체 찾기, 이웃, 영향 범위)를 MCP 툴로 내주면 클로즈드 베타에서 바로 쓸모가 있다. 지금까지의 결정은 방향만 정했다. KG의 MCP는 읽기만 하고(ADR-0010), REST와 같은 유스케이스 위의 두 어댑터이며(ADR-0016), 운영 MCP는 따로 둔다(ADR-0017). 툴의 이름과 목록, 인가, 규격의 판, 한도는 정하지 않았고 문서마다 이름이 어긋나 있었다(`find`와 `find_objects`). 인가는 "MCP 규격(OAuth 2.1)을 따른다"고만 적혀 있었다.

설계 검토와 사전 확인에서 다음이 드러났다.

- MCP 규격은 16개월 사이에 판이 네 번 바뀌었다. 지원하는 판이 셋이면 판마다 헤더, 메서드, 오류의 응답이 다르고, 규격이 말하지 않는 곳이 있다.
- 지금 서버는 모르는 경로에 웹 화면(HTML 200)을 돌려준다. `/mcp`를 같은 포트에 올리려면 이 충돌과 브라우저 출처 검증을 정해야 한다.
- 인증, 읽기 필터, 오류 코드의 대응, 응답 엔벨로프의 변환이 모두 `httpapi` 안에 있고 구조 계약은 어댑터끼리의 import를 막는다. 사본을 만들면 "REST와 같은 판단"이 코드로 보장되지 않는다.
- 하네스의 자동 승인은 주소나 툴 이름 단위로 걸린다. 읽기 전용이라 믿고 건 승인이 나중에 쓰기 툴까지 넓어지면 안 된다.
- 공식 Go SDK를 쓸지 직접 구현할지는 SDK를 받아 재 봐야 정할 수 있었다. 사전 확인 환경은 새 Go 모듈을 받을 수 없었다(정책으로 거부).

게이트웨이(ADR-0061, 예정)는 따로 정한다. 이 결정은 KG를 읽는 인터페이스만 다룬다.

## 결정

1. **문을 나눈다.** 코어의 `POST /mcp`는 **영구히 KG 읽기 전용**이다. 현실을 바꾸는 툴도, 조직의 MCP 서버를 거치는 툴도, 운영 MCP(`ops_*`)도 얹지 않고 이것을 툴 정의의 계약 파일에 적는다. 게이트웨이는 다른 주소의 다른 구성요소이고, 같은 툴 등록부로 KG 읽기 툴도 함께 내줄 수 있다. `kg_` 접두어는 KG 읽기 툴에만 쓴다.
2. **툴 여섯 개.** `kg_whoami`, `kg_catalog`, `kg_find`, `kg_get`, `kg_neighbors`, `kg_impact`. 사전 정의 질의와 1:1이고 범용 질의 툴은 만들지 않는다. 모든 툴이 `kg`(기본 `main`)와 `detail`(`brief` 기본, `full`)을 받는다. 설명문과 인자 이름은 영어이고 설명문은 KG의 값이 없는 고정된 글이며 인자 이름은 REST의 본문 필드와 같다. 읽기 전용 주석을 달되 우리 쪽 통제의 근거로 삼지 않는다. 재수집(`refresh`), 값 확인(`check_values`), 대량 읽기, 나머지 사전 정의 질의는 첫 묶음에 넣지 않고 구현되는 대로 더한다. 이로써 ADR-0010의 툴 이름과 "기대와 대조를 MCP에도 제공한다"는 범위를 고친다.
3. **켜고 끄기와 받는 토큰.** 운영 모드는 기본으로 꺼 두고 명시적으로 켠다. `local`과 `demo`는 기본으로 켠다. 읽기 역할의 서비스 계정 토큰만 받고, 관리자나 쓰기 역할의 토큰은 이유를 말하며 거절한다. MCP로 나가는 민감 등급의 상한을 설정으로 두고 기본은 `open`이다. 지금은 등급을 정하지 않은 속성이 모두 `open`이라 토큰 하나로 KG 전체가 읽힌다는 사실을 문서에 적는다. 인가는 1단계에서 내장 토큰이고(ADR-0044) OIDC는 그다음이다(ADR-0012). 인가 메타데이터는 OIDC를 붙일 때 낸다.
4. **판을 요청마다 가른다.** 지원하는 판은 2026-07-28(주), 2025-11-25, 2025-06-18이다. 서버는 판을 기억하지 않고 요청마다 판을 정해 그 판의 규칙으로 답한다. 순서는 (가) 본문의 `_meta`에 판이 있으면 새 판(헤더와 `_meta`를 대조), (나) 메서드가 `initialize`면 옛 판의 협상, (다) 헤더가 옛 판 둘 중 하나면 옛 판의 모양, (라) 그 밖에는 거절이다. 옛 판에는 세션 ID를 주지 않고 `GET`과 `DELETE`는 405이며, 일괄 요청과 2024-11-05는 받지 않는다. 헤더가 없는 요청은 `initialize`가 아니면 거절한다(2025-03-26을 지원하지 않기 때문이다). 판 처리 표는 [설계 문서](../kg-mcp.md) 2.1절이고, 규격의 문장을 직접 읽은 칸과 읽지 못한 칸을 나눠 적었다. 읽지 못한 칸은 추측으로 채우지 않고 구현 전에 확인한다. 판별 요청 수를 세고, 옛 판을 뺄 때는 한 릴리스 전에 알린다.
5. **같은 포트의 충돌과 출처 검증.** `/mcp`와 `/.well-known/oauth-protected-resource`(와 그 아래)는 웹 화면보다 먼저 처리하고, 인가 메타데이터를 내지 않는 동안 JSON 404로 답한다. `Origin`이 있으면 허용 목록(기본은 비어 있다)에 있을 때만 받고 아니면 403이다. `Content-Type`은 `application/json`만, 로컬 모드는 루프백 `Host`만 받는다. 인증은 본문을 해석하기 전에 한다. 401은 지금의 REST와 같이 `WWW-Authenticate: Bearer`와 문제 상세 본문으로 답하고 `resource_metadata`는 싣지 않는다. 규격은 인가를 쓰지 않는 서버가 401에 무엇을 실어야 하는지 말하지 않는다.
6. **결과와 오류의 모양.** 결과는 `{meta, next, data}`의 순서다. `meta`는 줄인 봉투, `next`는 고정된 글의 다음 할 일이다. 이로써 ADR-0016의 "응답 엔벨로프가 같다"를 "권한 판단과 오류 코드가 같고 봉투는 MCP가 줄인 형태를 쓴다"로 고친다. 크기 상한은 바이트로 자르지 않고 항목 수를 줄여 유스케이스에 다시 요청한다. 오류는 층으로 나눈다. 토큰, 판, 출처는 HTTP 상태, 툴 호출의 오류(인자, 객체 없음, 역할 부족, 민감 등급 상한, 한도, 동시 계산 상한, 시간 예산)는 `isError: true`의 결과이고 오류 결과에는 `structuredContent`를 싣지 않는다. 한도를 HTTP 429로 내면 에이전트가 전송 오류로 읽으므로 429는 인증 실패의 제한기에만 남긴다.
7. **KG의 값은 믿을 수 없는 입력이다.** 값은 `data`의 값 자리에만 싣고 "말"(설명, `next`, 오류 안내)은 고정된 글로만 쓴다. 길이를 제한하고 제어 문자, 보이지 않는 문자, 방향 제어 문자를 지운다. `kg_catalog`의 타입과 속성의 설명은 모델의 글이라 이 규칙의 예외이고 `data`에만 싣는다. 완전한 방어는 없다고 문서에 밝히고, 자료가 "프락시움, 하네스, 모델 제공자"의 길로 나간다는 것을 연결 안내의 한 절로 알린다.
8. **영향 범위의 큰 결과.** 요약을 먼저, 항목은 상위 20개, `path`는 `detail=full`일 때만 준다. 순서는 결과 등급의 심각한 순, 장애 지점에서 가까운 순, 타입, 이름이다. 지금 코드의 순서(ID의 글자순)를 유스케이스에서 바꾸므로 REST와 CLI의 순서도 바뀐다. 잠긴 테스트가 걸리면 건별로 보고하고 풀며 테스트를 조용히 바꾸지 않는다. 결과 등급, 객체 타입, 상위 객체로 걸러내는 인자를 유스케이스에 더한다. MCP 호출의 시간 예산은 기본 10초이다.
9. **코드의 자리.** 인증(토큰에서 주체까지), 읽기 필터, 오류 코드의 대응, 응답 엔벨로프의 변환, 입력의 해석을 두 어댑터가 함께 쓰는 코어의 유닛으로 옮긴다. REST의 동작은 바뀌지 않고 기존 테스트가 그대로 통과한다. 새 어댑터 `mcpapi`는 전송과 판 처리만 맡고, 툴 등록부(이름, 설명, 입력과 출력 스키마, 실행 함수)는 전송을 모른다. 새 유닛의 이름과 구조 계약의 변경은 설계 문서 8절에 있고, 구조 계약은 구현하는 변경이 이 ADR을 `touches_protected`에 적어 바꾼다.
10. **한도와 기록.** 호출자별 한도에 더해 영향 범위 계산의 프로세스 전체 동시 상한을 두고, 넘으면 기다리게 하지 않고 "지금 바쁨"으로 답한다. 읽기 기록은 첫 릴리스에서 호출마다 한 줄이다(토큰 ID, 추적 ID, KG, 툴, 건드린 객체 타입, 이름으로 댄 객체 ID, 결과 수, 잘림 여부, 판, `clientInfo`, 시간). 기존 설계의 타입·속성별 사용 이력보다 약하고, 그 저장은 감사 로그의 저장과 함께 온다.
11. **직접 구현하고, 그 근거를 정직하게 적는다.** 표준 라이브러리로 직접 구현한다. **이 결정은 SDK와 견준 실측 없이 내렸다.** 사전 확인 환경이 새 Go 모듈을 받지 못해 SDK를 넣었을 때의 실제 크기와 판 호환을 측정하지 못했다. 안전장치는 보안 테스트의 목록(JSON 키의 대소문자·널 문자·중복, `Content-Type`, `Origin`, `Host` 등 15가지)과 본문 파서의 퍼징 테스트다. 공식 적합성 테스트를 릴리스 전에 돌릴 수 있게 하되, 저장소의 검사에 넣으면 개발 의존성이 하나 늘므로 그 판단은 구현하는 변경이 따로 한다. **SDK로 넘어가는 조건**은 (가) 규격의 다음 판이 스트림이나 작업 확장을 읽기 전용 서버에도 요구할 때, (나) 우리 구현에서 전송 층의 보안 결함이 두 번 나올 때, (다) 적합성 테스트의 실패를 한 릴리스 안에 고치지 못할 때다. ADR-0006의 "MCP의 공식 SDK가 Go에도 있다"는 이 길로 남는다(그 결정은 바꾸지 않는다).
12. **계약과 검사.** 툴의 정의를 계약 파일로 두고 코드의 등록부와 어긋나면 검사가 실패한다(OpenAPI 대조와 같은 방식). 출력 스키마는 REST 응답의 스키마와 같은 원본에서 나온다. `/mcp`는 OpenAPI 밖이다.
13. **운영 MCP와의 구분.** ADR-0017의 운영 MCP(`ops_*`)는 `/mcp`에 얹지 않는다. 그 주소와 인증은 이 결정이 정하지 않는다(ADR-0017의 "읽기 전용 MCP(KG)와 별도"를 "다른 주소의 별도 면"으로 고친다).

## 이유

- **문을 나누는 이유.** 승인은 주소와 툴 이름 단위로 걸린다. 코어의 `/mcp`가 읽기 전용임을 계약으로 못 박아야 읽기 전용이라 믿고 건 승인이 넓어지지 않는다. "나중에 같은 문으로 게이트웨이의 툴을"이라는 초안의 방향은 버린다.
- **토큰의 조건.** 관리자 토큰이 하네스의 설정 파일에 놓이면 셸을 쓸 수 있는 에이전트가 읽어 REST 관리 경로를 직접 부를 수 있다. 읽기 역할만 받으면 이 길이 막힌다. 운영 모드를 기본으로 끄는 것은 ADR-0044의 "확신이 없으면 보수적인 쪽"을 따른다. 업그레이드한 배포에서 자료가 모델 제공자로 나가는 길이 묻지 않고 열리지 않게 한다.
- **판을 요청마다 가르는 이유.** 규격의 호환성 표에 따르면 옛 판의 클라이언트는 새 판만 받는 서버에 붙지 못하고, 현장의 하네스가 어느 판을 말하는지 다 확인하지 못했다. 새 판은 세션과 `initialize`가 없어 서버가 기억하지 않아도 되므로 같은 엔드포인트가 두 시대를 함께 받을 수 있다(규격이 허용한다). 판 처리 표는 이 판단을 문장에 묶어 두려고 만들었다.
- **직접 구현의 근거.** (가) 읽기 전용, 툴 여섯, 무상태, JSON 응답만이라 필요한 범위가 작다. (나) 공식 SDK의 2026년 심각도 높은 보안 권고 4건 가운데 둘은 JSON 라이브러리를 바꾸며 생겼고 둘은 출처 검증이었다. 우리는 표준 라이브러리의 JSON을 쓰고 출처 검증을 5번에 명시한다. (다) 폐쇄망에 들일 것이 늘지 않는다. 다만 이 근거는 SDK를 재 보지 않고 세운 것이다. 직접 구현하면 규격의 새 판을 우리가 따라가야 하고(16개월에 네 판), 전송 층의 결함도 우리 몫이다. 그래서 안전장치와 넘어가는 조건을 약속으로 적는다.
- **오류의 층.** 토큰·판·출처의 오류는 에이전트가 고칠 수 없는 연결의 문제라 HTTP 상태가 맞다. 툴 호출의 오류는 에이전트가 읽고 고칠 수 있어야 하므로 결과로 준다. `isError`는 세 판 모두에서 통한다(2025-06-18은 잘못된 인자를 프로토콜 오류로 분류하지만).
- **큰 결과를 바이트로 자르지 않는 이유.** 바이트로 자르면 커서가 항목을 건너뛴다. 항목 수를 줄여 다시 요청하면 커서가 이어진다.

## 대안과 기각 사유

| 대안 | 기각 사유 |
|---|---|
| 공식 Go SDK를 쓴다 | 재 보지 못했다(실측 없음). 조건이 맞으면 넘어간다(11번). 지금은 필요한 범위가 작고 폐쇄망에 들일 것이 늘지 않는 쪽을 고른다 |
| 새 판 하나만 받는다 | 옛 판의 클라이언트가 붙지 못한다. 현장의 하네스가 어느 판을 말하는지 확인하지 못했다 |
| 헤더 없는 요청을 2025-03-26으로 보고 받는다 | 지원하는 판에 없는 판을 만들어 표가 늘고 테스트할 것이 늘어난다. 거절을 택하고 판단이 필요한 곳으로 표시한다 |
| 게이트웨이의 툴을 같은 `/mcp`에 얹는다 | 주소 단위의 승인이 넓어진다(1번) |
| MCP를 `adapter.http` 안에 둔다 | 빠르지만 유닛의 경계가 흐려지고 전송과 툴 등록부를 나눌 수 없어 SDK로 바꿀 길이 좁아진다 |
| 인증과 필터의 사본을 `mcpapi`에 둔다 | REST와 같은 판단이 코드로 보장되지 않는다(REQ-149) |
| 한도 초과를 HTTP 429로 낸다 | 에이전트가 전송 오류로 읽어 "기다렸다 다시"를 받지 못한다 |
| 기본으로 켠다 | 업그레이드한 배포에서 묻지 않고 열린다. `local`과 `demo`만 기본으로 켠다 |
| 지금 OAuth 자원 서버가 된다 | 인가 서버가 조직의 것이어야 하고 OIDC가 먼저다(ADR-0012). 메타데이터는 그때 낸다 |

## 결과

- **고치는 결정**: ADR-0010(툴 이름과 첫 묶음의 범위), ADR-0016(봉투), ADR-0017(운영 MCP의 주소). `amends`와 `link-amends`로 잇는다. ADR-0006(SDK는 되돌아갈 길로 남음), ADR-0044(토큰의 조건), ADR-0012(OIDC가 먼저인 순서)는 바꾸지 않는다.
- **고치는 문서**: front matter의 `updates_docs`에 적은 문서다. 툴 이름과 목록을 `kg_` 이름으로, "MCP 인가는 OAuth 2.1"을 "1단계는 내장 토큰, OIDC는 다음"으로, 한도와 크기 상한의 문장, 운영 MCP와의 구분, "KG의 MCP 인터페이스는 영구히 읽기 전용이고 게이트웨이는 다른 주소의 다른 구성요소"로 고쳤다. 구조 계약과 `ARCHITECTURE.md`는 구현하는 변경이 고친다(설계 문서 8.3절).
- **요구사항**: REQ-500부터 REQ-517까지를 "예정"으로 `requirements-query-api.md`에 더했다. REQ-149와 REQ-207의 문장을 고쳤다.
- **구현 순서**: (1) 공통 유닛으로 옮기기와 한도, (2) `mcpapi`의 전송과 판 처리, 출처 검증, 보안 테스트, 툴 등록부와 계약 파일과 검사, `kg_whoami`와 `kg_catalog`(여기서 실제 클라이언트 둘을 붙여 본다), (3) `kg_find`, `kg_get`, `kg_neighbors`, (4) `kg_impact`, (5) 연결 안내의 하네스별 예와 독립 검증.
- **미결 사항**(설계 문서 7절): 모르는 툴 이름을 규격대로 프로토콜 오류로 줄지 `isError`로 줄지(규격은 프로토콜 오류로 분류하는데 검토의 설계는 `isError`로 적었다), 저장소 장애의 층, `content`에 JSON을 한 번 더 실을지, 결과 크기와 한도와 `ttlMs`의 값, `brief`와 `full`의 필드, 판 처리 표의 미확인 칸, 공통 유닛의 이름, 토큰 만료를 미리 알리는 방법, 이 면을 알파와 베타의 어느 차수에 넣을지(`plan.md`).
- **위험**: 판 처리 표의 미확인 칸은 구현 전에 규격과 적합성 테스트으로 확인해야 한다. 직접 구현의 크기와 부담은 측정하지 않았다. 영향 범위의 순서를 바꾸면 REST와 CLI의 응답 순서가 바뀐다.
