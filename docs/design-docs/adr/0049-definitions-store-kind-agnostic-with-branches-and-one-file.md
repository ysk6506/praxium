# ADR-0049 정의 저장소 — 종류를 모르는 저장, 브랜치와 제안, 파일 하나로 보관

## 맥락

[정의의 버전과 브랜치](../definitions.md)(ADR-0014)는 정의를 불변 리비전과 정의 세트로 쌓고, 브랜치와 제안으로 고치고, 검사를 거쳐 한 번에 병합하는 설계를 정했다. 코드는 아직 없었다. 곧 만들 것 둘이 같은 자리를 필요로 한다. 하나는 소스와 매핑(피드, 링크 정의)을 화면과 서버에서 고치고 되돌리는 일이고, 다른 하나는 표준 모델에 조직이 속성을 더하는 일이다. 둘 다 "정의를 보관하고, 고치기 전에 초안으로 두고, 확정하면 번호가 붙고, 지난 번호로 돌아갈 수 있다"를 원하고, 둘이 따로 저장소를 만들면 버전과 승인 규칙이 둘이 된다. 둘 다 처음에는 PostgreSQL 없이 내장 파일 스토어(ADR-0034)로 돌아야 한다.

## 결정

**1. 정의의 의미를 모르는 저장소 하나를 만든다.** 새 유닛 `core.definitions`(`backend/internal/definitions`). 항목에는 바뀌지 않는 `item_id`, `kind`(뜻을 모르는 문자열), 이름, 그리고 리비전마다 정규화한 JSON 본문과 스키마 버전만 있다. 본문의 뜻과 검사는 쓰는 쪽 유닛이 안다. 이 유닛은 `core.model`과 `core.ingest`를 import하지 않는다(`core.kernel`만).

**2. 설계 문서의 부분집합만 만든다.**

| 만든 것 | 이름과 규칙 |
|---|---|
| 항목과 리비전 | 리비전은 쓰기만 한다(`rev_no`, 내용 해시, `schema_version`, 본문, 만든 사람, 메시지, 시각). 내용 해시는 `kind`, 스키마 버전, 정규화한 본문의 해시다. 이름은 바뀌지 않는다(이름 변경은 하지 않는다). 지금과 같은 내용은 새 리비전이 아니고, 지난 내용으로 되돌리면 번호는 새로 오른다 |
| 정의 세트 `D-n` | `set_no`, 내용 해시, `parent_set_no`, `origin`, 항목 목록(전체), 기준 해시, 제안 ID. 해시는 기준 해시와 정렬한 (항목 ID, 내용 해시) 목록으로 계산하고 부모와 리비전 번호는 넣지 않는다. 항목이 없으면 해시는 기준 해시 그대로다(기준만 있던 기존 데이터 폴더와 같은 값) |
| 머리 | 메인 브랜치의 끝 세트 번호 하나. 기대한 값일 때만 옮겨진다(compare-and-swap) |
| 번호 원장 | 이름 붙은 카운터. 시작 값은 호출자가 주고, 세트를 만드는 같은 쓰기에서 오르며, 내려가지 않는다 |
| 브랜치 | `base_set_no`와 바뀐 항목(`add`, `modify`, `remove`)만. 고칠 때마다 저장되고 `version`으로 동시 수정을 막는다. 기준과 같아진 항목은 빠진다 |
| 제안 | 브랜치와 일대일. `draft → in_review → approved → merged`, 병합 전 어느 때나 `closed`. 승인은 내용 해시에 묶인다 |
| 병합 | 승인된 제안을 머리에 얹는다. 기준 이후 머리에서 같은 항목이 바뀌었으면 `stale`로 거절한다. 병합 직전에 호출자가 준 검사 함수가 합쳐진 세트 전체를 받는다 |
| 직접 적용 | 기대한 머리와 변경 목록을 받아 한 번에 쓰는 기본 동작. 병합도 같은 코드를 쓴다. 바뀐 것이 없으면 쓰지 않는다 |
| 복원 | 지난 세트의 내용으로 새 브랜치와 제안(`origin: restore`)을 만든다. 세트는 지우거나 고치지 않는다 |

`origin`은 설계 문서의 이름(`change`, `import`, `bootstrap`, `restore`)을 쓴다. 직접 적용과 병합은 따로 값을 두지 않고 병합으로 만든 세트에는 `proposal_id`가 있다.

**3. 승인은 정책을 받는다.** 작성자(브랜치를 고친 모든 주체와, 그들 또는 그들이 위임한 사람을 대신하는 주체)는 자기 제안을 승인하지 못한다. 호출자가 넘기는 정책이 단독 승인(`solo_approval`)을 허용하면 할 수 있고, 승인 기록에 `solo`가 남는다. 누가 어떤 역할이고 범위가 무엇인지는 이 유닛이 모른다. 호출자(접근 제어)가 주체와 정책을 넘긴다. 필요한 승인이 몇 개인지도 호출자의 일이고, 이 유닛은 승인 하나로 `approved`가 된다.

**4. 저장 포트는 "원자적 쓰기 한 번"이다.** `Store.Commit(Write)`는 새 항목, 리비전 여러 개, 세트, 원장, 머리, 브랜치와 제안의 새 상태를 전부 쓰거나 전혀 쓰지 않는다. 쓰기의 기대(머리, 원장의 값, 브랜치와 제안의 버전)가 맞지 않으면 `conflict`이고 아무것도 쓰지 않는다. 저장소는 호출자와 무관하게 자료가 올바르도록 규칙을 지킨다(리비전 번호에 빈틈 없음, 세트의 해시와 항목이 맞음, 원장은 내려가지 않음). 데이터베이스 어댑터는 같은 포트를 머리 행을 잠그는 한 트랜잭션으로 구현할 수 있다.

**5. 어댑터 둘과 적합성 사례.**

- 메모리(기준 구현): `definitions.MemoryStore`. 쓰기 규칙이 한 곳에 있고, 파일 어댑터가 이것을 바탕으로 한다.
- 파일: `adapter.definitionsfile`. 데이터 폴더의 `definitions.json` 하나(형식 `praxium-definitions`, 버전 1)를 임시 파일에 쓰고 동기화한 뒤 이름을 바꿔 교체하고 폴더를 동기화한다(`ingest-state.json`과 같은 방식, ADR-0041). 레코드 하나가 한 줄이라 읽고 비교하기 좋고, 세트의 항목은 `[항목 ID, 리비전 번호]` 쌍으로 적어 크기를 줄인다. 열 때 모든 해시를 다시 계산해 바뀐 본문이나 어긋난 세트를 찾는다. 파일이 없으면 정의 없음이고, 알 수 없는 형식 이름·버전·깨진 파일은 이유를 말하고 거절하며 덮어쓰지 않는다. 운영체제는 `Disk` 인터페이스로만 만나고 시작점이 구현한다(`os`는 시작점만 import한다). 내장 파일 스토어의 저널과 스냅샷 형식은 건드리지 않는다. 쓰기는 데이터 폴더를 독점해서 연 프로세스만 한다.
- 적합성 사례(`adapter.definitionscheck`, 14개)를 두 어댑터가 모두 통과한다. 결함이 있는 저장소(머리 확인을 건너뜀, 원장을 쓰지 않음, 브랜치 버전을 무시함, 실패한 쓰기가 일부를 남김, 재시작에 잊음)를 사례가 잡는지도 시험한다. 사례 표는 테스트 잠금에 포함한다(`go.locked_support`).
- 시각과 ID는 주입한다(`kernel.Clock`, `kernel.IDGenerator`). 같은 입력이면 같은 결과다. 생성기가 다시 시작해 이미 쓴 ID를 다시 내면 건너뛴다. 오류는 `kernel`의 코드를 따른다. 한도 위반은 `invalid_value`이고 어느 한도인지(`LimitError.Limit`) 말한다.

**6. 한도.** 생성할 때 주는 설정이고 기본값이 있다: 본문 1 MiB, 세트의 항목 20000개, 브랜치의 바뀐 항목 2000개, 열린 브랜치 100개, 이름 200바이트, 메시지 4000바이트. 근거 없는 가정이라 측정으로 바꾼다.

## 이유

- 두 첫 사용자가 같은 저장소를 쓰면 승인, 되돌리기, 번호 부여를 한 번만 만든다. 종류를 모르게 하면 모델 유닛과의 순환 의존이 없고 새 종류가 생겨도 이 유닛은 바뀌지 않는다.
- 원자적 쓰기 한 번을 포트로 삼으면 "리비전은 있는데 세트가 없다", "원장만 올랐다" 같은 반쪽 상태가 포트 수준에서 불가능하고 PostgreSQL로 옮겨도 의미가 같다.
- 병합을 겹침 검사(`stale`)로 줄이면 3-way 병합과 충돌 풀기 없이도 "먼저 병합한 쪽이 이긴다"가 안전하다. 항목은 통째로 하나로 보므로 필드 단위 병합은 어차피 하지 않는 설계다.
- 파일 하나를 통째로 교체하는 방식은 정의 변경이 드문 사람이 쓰는 내장 스토어에서 가장 단순하고, 쓰기 도중 실패해도 옛 파일이 남는다는 것을 증명하기 쉽다.

## 파일 하나의 쓰기 비용 (측정)

정의 변경은 드물다는 가정(ADR-0014)에서 출발한 선택이라, 항목이 수천 개일 때의 비용을 쟀다. 항목마다 본문 약 1 KB(컬럼 27개짜리 데이터셋 3개)의 정의를 한 번에 적용한 뒤 한 항목을 10번 고쳤다(세트 11개). 실제 디스크(`fsync` 포함)에서 쟀고, 측정할 때 컴퓨터에 다른 작업이 몰려 있어(CPU 2개에 부하 약 16) 걸린 시간은 CPU 시간의 약 4배다. 그래서 CPU 시간을 함께 적는다.

| 항목 수 | 파일 크기 | 한 항목 쓰기: CPU 시간 | 한 항목 쓰기: 걸린 시간(중앙값) | 파일 열기(걸린 시간) |
|---|---|---|---|---|
| 1000 | 2.1 MB | 약 22 ms | 약 56~100 ms | 약 0.5~0.7 초 |
| 5000 | 10.3 MB | 약 95 ms | 약 380 ms | 약 3.3~4.7 초 |
| 10000 | 20.6 MB | (측정 안 함) | 약 930 ms | 약 7 초 |

- 쓰기는 파일 전체를 다시 쓰므로 비용이 항목 수와 세트 수에 비례한다. 세트마다 항목 목록 전체를 두는 방식(ADR-0014의 가정)이라 세트가 하나 늘 때마다 파일은 항목당 약 20바이트씩 커진다. 항목 1만 개면 세트 하나에 약 200 KB라서 세트 천 개에 약 200 MB이고, 읽는 한도(512 MiB)에 가까워진다.
- 열 때가 가장 비싸다. 모든 본문과 세트의 해시를 다시 계산해 확인하기 때문이다(손상을 찾는 값이다). 서버가 오래 떠 있으면 한 번이다.
- 시간의 대부분은 JSON 만들기와 본문 정규화다. 쓰기 경로에서 쓸데없는 복사를 없앴고(처음 측정에서 항목 5000개 쓰기가 약 775 ms였다) 더 줄이려면 파일 형식을 바꿔야 한다.
- 결론: 항목 수천 개와 세트 수백 개까지는 쓸 만하고(변경 하나에 CPU 0.1초 안팎), 그 이상이거나 변경이 잦으면 PostgreSQL 어댑터로 간다. 부모 대비 차이와 주기적 전체 저장으로 바꾸는 것(ADR-0014의 대안)은 이 한계에 닿을 때 정한다.

## 대안과 기각 사유

- **소스·매핑과 조직 속성이 각자 저장소를 둔다.** 승인, 번호, 되돌리기가 둘이 된다. 기각.
- **정의 종류를 이 유닛이 안다(타입 검사, 참조 검사를 안에서).** `core.model`·`core.ingest`와 순환하거나 의존이 커진다. 종류별 검사는 호출자가 주는 검사 함수로 한다. 기각.
- **내장 파일 스토어의 저널에 정의를 함께 싣는다.** KG의 변경 순서와 정의의 번호 체계가 섞이고, 저널·스냅샷 형식이 바뀐다. 기각.
- **3-way 병합과 충돌 해결을 처음부터 만든다.** 쓰는 쪽이 아직 화면에 보일 충돌 종류를 정하지 못했다. `stale` 거절은 나중에 3-way를 얹어도 호환된다(거절하던 것을 병합할 뿐이다). 이번에는 하지 않는다.
- **파일 한 줄씩 덧붙이는 로그로 정의를 쓴다.** 쓰기 비용은 낮지만 세트 번호, 원장, 머리를 일관되게 복구하는 장치(체크섬, 끝이 잘린 줄 처리)가 필요하다. 정의 변경이 드물다는 전제에서 통째 교체가 더 단순하다. 기각(비용 표의 한계에 닿으면 다시 본다).

## 결과

- 새 유닛 셋: `core.definitions`, `adapter.definitionsfile`, `adapter.definitionscheck`. 구조 계약과 커버리지 하한에 등록했다.
- 새 서드파티 의존성은 없다(표준 라이브러리).
- 하지 않은 것: 3-way 병합과 충돌 해결, 병합 큐(`queued`), 제안 단위 리버트(`origin: revert`)와 긴급 리버트, 가져오기와 내보내기, 계보, 읽기 고정, 이름 변경, 위험 등급, `namespace`·`contacts` 컬럼, 종류별 변환과 검사, PostgreSQL 어댑터, HTTP 경로, 명령줄. 시작점에서 `Disk`를 실제 폴더에 연결하는 일도 이 변경에 없다(`ingest-state.json`용 구현과 같은 모양의 구현을 시작점에 더하면 된다).
- 요구사항 REQ-332 ~ REQ-341. 설계 문서에는 "지금 구현된 범위" 표를 더했다.
