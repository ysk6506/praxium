# ADR-0014 정의의 버전과 브랜치: 바뀌지 않는 정의 묶음, 제안과 검사, 한 줄로 들이는 병합, 앞으로 나아가는 되돌리기, 정의의 계보

## 맥락
제품 책임자의 요구는 넷이다. 파이프라인과 모델의 모든 것에 버전과 브랜치가 있어야 한다. 큰 기술 회사들이 만든 버전 관리의 사례를 참고한다. 변경은 잦지 않을 것이므로 동시 수정의 충돌 풀기와 되돌리기가 잘 돼야 한다. 데이터 계보를 관리한다.

ADR-0008은 정의의 버전과 브랜치를 한 줄로만 정했다. 조사(r14)는 그 줄이 틀리거나 모자란 곳을 찾았다. 정의의 항목이 따로 놓여 있어도 서로 가리키므로 충돌은 항목 단위로 좁지 않다. "정의의 버전"이 항목의 판인지 전체의 모습인지 적혀 있지 않았다(ADR-0009의 KG 버전 ID가 그것을 입력으로 쓴다). 병합 직렬화, 되돌리기의 단위, 급할 때의 길, KG에 미치는 효과가 없었다. 이 결정이 그것을 메운다. 파운드리와의 견줌(제품 책임자의 길잡이)에서는 정의의 시험, 깨는 변경과 옮김, 정의의 계보를 가져온다.

넘겨받은 것 문서 6절의 쟁점 가~아는 E2E 프로세스의 것이라 직접 답하지 않는다. 가까운 것은 둘이다. 바(운영 경로에서 멈춰도 되는 것의 경계): 정의 고치기는 멈춰도 되는 쪽에 두되, 되돌리기의 급한 길과 묻는 쪽의 고정은 묻기의 길을 지키는 데 쓴다. 사(이음매의 파일 형식): 정의를 글 파일로 내보내고 들이는 형식을 정한다.

## 결정
1. **정의는 항목, 판, 정의 묶음으로 저장한다.** 정의의 항목(타입(제품 표준 타입도 판이 있는 항목이다)과 덧씌움, 소스, 데이터셋, 정제, 공급, 식별 규칙, 예외 목록, 링크 정의, 기대 조건, 목표, 알림의 규칙, 역량 질문, 일정, 안전장치의 값)은 바뀌지 않는 `id`와, 내용으로 주소를 매긴 바뀌지 않는 판들을 가진다. **정의 묶음**은 어느 항목이 어느 판인가의 전체 목록이고 내용 해시를 가진다. 표준 모델의 버전도 이 해시에 반영된다. 이 해시가 KG 버전 ID의 입력인 "정의의 버전"이다(ADR-0009). 사용자에게는 `D-142` 같은 번호로 보인다. 본줄기는 정의 묶음의 한 줄 이어짐이고 끝은 행 하나이며, 견줘서 바꾸기(앞의 값이 그대로일 때만 바꾼다)로만 옮긴다. 실제 Git은 진실의 자리가 아니다. 정의는 정해진 순서의 글 파일로 내보내고 들일 수 있고, **들이면 언제나 브랜치가 생긴다**. 들이는 파일의 바탕이 본줄기에 없으면 본줄기의 지금 끝을 바탕으로 브랜치를 만들고 바탕을 몰랐다고 경고한다. 정의와 계보는 자리를 범위에 가진 `viewer`가 읽고 내보내기는 자리를 범위에 가진 `editor`가 한다. 바깥의 Git은 거울이다.
2. **브랜치는 본줄기의 한 정의 묶음을 바탕으로 한 바뀐 항목만의 덧씌움이다.** 여럿이 동시에 열 수 있고 가볍다. 한 브랜치가 타입, 소스, 정제, 공급, 링크 정의를 함께 덮는다. 타입의 변경(만들기, 고치기, 지우기)과 흐름으로 받는 소스의 정의 변경도 같은 길이다. 브랜치에서 후보 실행으로 받아 둔 원본 기록에서 후보 KG를 만들고 지금 버전과의 차이를 본다.
3. **제안은 브랜치를 본줄기에 들여 달라는 정식 객체다.** 상태는 `draft`, `in_review`, `approved`, `queued`, `merged`와 끝 하나 `closed`(까닭과 함께)다. 검사 결과, 낡음, 충돌, 모자란 승인은 상태가 아니라 **막는 까닭**으로 끌어낸다. 검사(낱개의 유효성, 합친 결과의 유효성, 정의의 시험, 후보 실행과 차이, 안전장치, 역량 질문의 충족률이 어떻게 바뀌나)는 브랜치의 내용 해시에 묶인다. 지키던 목표 충족률을 깨뜨리면 막는 까닭이 된다(ADR-0015). 모든 항목에는 **자리**가 있다(소스에 딸린 것은 그 소스, 타입에 딸린 것은 그 객체 타입, 링크 정의는 출발 타입). 고치려면 자리를 범위에 가진 `editor`가 필요하고, **승인**은 제안이 고친 항목 하나하나에 그 자리를 범위에 가진 `approver`(고친 사람 말고)가 한다(ADR-0012). 공급은 소스의 `editor`가 고치고, 객체를 만들거나 물러나게 하거나 식별 키를 매핑하면 대상 타입의 `approver`의 승인도 필요하다. 조직 표준 타입은 `model_steward`, 안전장치를 느슨하게 하는 것은 `admin`이다. 후보 실행에서 안전장치에 걸린 제안은 자리를 범위에 가진 `operator`의 확인으로 풀리고 확인은 내용 해시에 묶인다. `closed`한 제안은 다시 열지 않고 같은 브랜치로 새 제안을 만든다. 검사가 깨진다고 말한 항목과 후보 실행에서 객체가 바뀌는 타입의 범위도 승인이 필요하고, 가리키기만 하면 담당자에게 알림만 간다. 승인 뒤에 내용이 바뀌면 승인은 무효다.
4. **병합은 줄 하나로 세워 하나씩 한다.** 줄 맨 앞에서 본줄기의 지금 끝 위에 브랜치를 얹어 검사를 다시 하고, 통과하면 트랜잭션 하나로 들인다(여러 항목이 한꺼번에, 반쯤 들어간 병합은 없다). 멀쩡한 두 변경이 합쳐서 깨지는 일을 이것이 막는다. 병합과 KG에의 적용은 따로다. 병합은 정의를 한꺼번에 들이고 "새 정의를 적용하라"는 일을 건다. 적용이 끝나 KG 버전이 봉해지면 "KG가 쓰는 정의 묶음"이 옮겨 가고, 적용이 안전장치에 걸리면 KG는 앞의 묶음에 머물며 본줄기의 끝과의 어긋남이 한눈에 보이는 상태에 드러난다. 흐름은 그 자리부터 새 정의로 흐른다. 정의를 고친 뒤 첫 적용은 사람이 차이를 본다(ADR-0008).
5. **충돌은 넷으로 가르고 병합 전에 잡는다.** 같은 항목을 둘이 고침(세 쪽 견주기, 뒤에 온 브랜치의 `editor`가 고른다) / 목록 항목의 다른 줄(열쇠가 있는 목록은 저절로 합친다) / 뜻의 충돌(항목은 다르다. 합친 결과의 검사가 가리킴, 고리, 타입 맞음, 물러난 것을 씀, 식별 키의 바뀜으로 잡는다) / 결과의 충돌(후보 실행과 안전장치가 잡는다). 낡은 브랜치는 "본줄기에 맞추기"로 얹고, 충돌은 브랜치 안에 상태로 남아 나중에 풀어도 된다.
6. **되돌리기는 지우거나 되감지 않고 앞으로 나아가는 새 제안이다.** 병합된 제안 되돌리기, 일부만, 정의 묶음 `D-N`으로 돌리기(범위를 골라), 되돌린 것을 되돌리기가 있다. 뒤의 변경이 같은 항목을 고쳤으면 충돌이고, 되돌릴 것을 가리키면 검사가 실패해 막히며 함께 되돌릴 것을 미리보기로 제안한다(저절로 줄줄이 되돌리지 않는다). **급할 때** `admin`, 또는 그 제안이 고친 자리 전부를 범위에 가진 `approver`는 방금 병합된 제안(병합된 지 정해진 기간 안이고 뒤의 제안이 기대지 않을 때)을 승인 없이 되돌릴 수 있다. `operator`는 못 한다. 검사와 줄은 그대로 거치고, 감사 기록에 따로 남고, 다른 `approver`나 `admin`의 사후 검토를 정해진 기한 안에 받는다(기간과 기한의 기본값은 설정이고 재지 않은 가정이다). **KG와의 경계**: KG는 되감기지 않고 새 버전이 나온다. 식별의 이력은 되감지 않는다. 이미 합친 ID는 규칙을 되돌려도 저절로 갈라지지 않고(예외 목록으로 가른다), 예외 목록으로 가르면 남은 쪽은 ID를 그대로 갖고 흡수됐던 쪽은 옛 ID로 되살아난다. 물러났던 객체가 같은 식별 키로 다시 보이면 옛 ID로 되살아난다. 범위가 전체인 `operator`나 `admin`은 묻는 쪽을 옛 KG 버전에 고정할 수 있다(데이터는 그대로이고 답에 고정 표시가 붙는다).
7. **새 소스를 더하는 브랜치**에는 후보 실행에 쓸 원본 기록이 없으므로 브랜치에서 **시험 수집**을 할 수 있다(`operator`. 같은 읽기 전용과 소스 지키기를 거친다. 브랜치에 딸린 자리에 담긴다). 병합되면 첫 수집으로 쓸 수 있다.
8. **한눈에 보이게 한다.** 본줄기의 이어짐, 열린 브랜치와 제안, 줄, 막는 까닭을 API 하나(`definitions_overview`)가 준다(화면은 다른 저장소의 일이다. 이 저장소의 알파는 API와 명령줄 클라이언트로 된다). 한 일이 모두 기록되고 되돌릴 수 있다는 것이 보여야 사람이 겁내지 않고 고친다.
9. **정의의 시험.** 정의의 항목에 견본(지어낸 입력 행 → 기대하는 객체와 링크)을 붙이고 병합 검사로 돌린다. 프리셋은 견본이 있어야 실린다(ADR-0008을 모든 정의로 넓힌다).
10. **깨는 변경은 옮김과 함께여야 저장된다.** 변경을 더하기, 맞는 변경, 깨는 변경(속성의 이름·자료형, 식별 키, 타입을 물러나게 함, 링크의 뜻)으로 가른다. 옮김은 어느 속성이 어느 속성으로, 어떤 바꾸기로, 식별 이력은 어떻게를 적고 후보 실행에서 확인한다. 타입 합치기와 올리기도 옮김으로 적는다.
11. **정의의 계보와 누가 쓰나.** 항목 사이의 기댐(소스, 데이터셋, 정제, 공급, 타입·속성, 링크 정의, 끌어낸 묶음)을 그래프로 갖고 컬럼과 속성 단위까지 따라간다(정제 연산이 닫힌 목록이라 가능하다). 밖에서 쓰는 쪽(저장해 둔 범위, 시스템 계정의 쓰임 기록)도 센다. 고치거나 물러나게 하기 전에 "무엇이 걸리나"로 답한다. ADR-0008의 출처 따라가기(객체에서 원본 기록으로)와 함께 계보의 두 축이다.

## 이유
조사(r14, r13)는 이번 세션에 출처를 열어 읽은 것만 근거로 썼다. 한 회사의 글(원문을 열지 못한 것)은 근거로 적지 않았다. 아래는 [확인]된 것에서 무엇을 가져오고 무엇을 뒤집었는지다.

| 사례(확인한 것) | 가져온 것 | 바꾸거나 뒤집은 것 |
|---|---|---|
| 한 회사의 소스 컨트롤 재설계 글: 변경은 부모와의 차이만 담고 내용 주소의 blob을 가리킨다 | 판은 내용 해시로 주소를 매기고 브랜치는 바뀐 항목만의 덧씌움이다(결정 1, 2) | 파일 트리가 아니라 항목과 묶음의 전체 목록이다 |
| 같은 글: 줄기의 끝(ref)은 한 행에 대한 compare-and-swap | 본줄기의 끝은 행 하나이고 견줘서 바꾼다(1, 4) | |
| Sapling의 스마트로그, undo 문서: 상태를 한곳에 보이고, 머릿속 모델이 없으면 실수에서 회복하지 못한다 | 한눈에 보이는 상태와 "되돌릴 수 있다"는 믿음(8) | |
| Sapling의 hide: 숨길 뿐 지우지 않고, 서버의 공개된 커밋은 숨길 수 없다 | 닫은 제안은 숨기고, 병합된 묶음은 고치지 못한다(3, 6) | |
| jj의 일급 충돌, Dolt의 충돌 표: 충돌을 상태로 저장하고 나중에 푼다. Dolt는 기본 키로 행을 맞춰 셀 단위로 합친다 | 충돌은 브랜치 안에 상태로 남는다. 열쇠가 있는 목록만 열쇠로 맞춰 저절로 합친다(5) | 항목 안의 칸 단위 자동 병합을 기본으로 하지 않는다 |
| GitHub의 병합 큐, Bors, Zuul: 따로는 초록인 변경 둘이 합쳐서 깨질 수 있어 합친 결과를 검사한다. Dolt는 외래키 위반을 병합 뒤 막는다 | 줄 맨 앞에서 합친 결과를 다시 검사한다(4, 5) | |
| Git의 3-way 병합 문서: 겹치지 않는 변경은 그냥 합쳐서 뜻을 모른다. revert는 새 변경이다 | 뜻의 충돌은 검사로 잡고, 되돌리기는 새 제안이다(5, 6) | 줄 단위 병합을 진실로 쓰지 않는다 |
| Liquibase: 롤백은 지워진 데이터를 되살리지 않는다 | KG를 되감지 않는다고 사용자에게 알린다(6) | |
| Kubernetes server-side apply: 남이 가진 필드를 바꾸는 것은 충돌이고 소유를 옮기는 것은 이름 붙은 행위다 | 남의 항목은 힘이 아니라 범위를 가진 승인으로만 고친다(3) | 필드 단위 소유 기록은 두지 않는다 |
| 한 회사의 설정 관리 논문: 검증기, 카나리, 직렬 착륙. 진짜 충돌은 거절 | 합친 결과의 검사와 후보 실행과 안전장치의 두 문(4) | 설정이 평생 수십 번 바뀐다는 그 회사의 통계는 우리에게 맞는지 재지 않았다 |
| 소스 컨트롤 재설계 글: 하루 수만 건 병합에서는 전역 락 병합 큐가 맞지 않는다고 보고 줄 없이 병합 뒤 시험에 기댄다 | | **뒤집었다.** 변경이 잦지 않은 우리에게는 줄 하나가 단순함이고, 병합 전 합친 결과 검사에 병합 뒤 적용 안전장치가 두 번째 문으로 붙는다 |
| 파운드리의 공개 문서(우리가 열어 본 범위): 충돌은 리소스 단위로 손으로 고르고, 병합의 통합된 되돌리기 길은 문서에 없다 | 충돌 풀기와 되돌리기를 처음부터 구체적으로 정한다. 단위 시험이 병합 전에 돈다는 점은 정의의 시험으로 받는다(9) | 한 번에 고르는 충돌이 아니라 세 쪽 견주기와 합친 결과를 검사한다 |

이 결정의 이유는 셋이다. 정의는 구조가 있어서 줄 단위나 항목 단위의 병합이 뜻을 보장하지 못하므로 합친 결과를 검사해야 한다. 변경이 잦지 않으니 직렬화의 비용이 거의 없고 얻는 것(검사한 그 상태로 들어간다)이 크다. 되돌리기를 따로 만들지 않고 같은 제안과 같은 검사와 같은 줄에 태우면 만들 것이 적고 되돌리기도 검사를 받는다.

## 버린 길
- **실제 Git을 진실의 자리로**: 글자 단위 병합이 구조를 몰라 조용히 깨뜨릴 수 있고, 범위를 가진 승인이 Git에 없고, 저장소가 둘이 된다(ADR-0009와 어긋난다).
- **항목마다의 판만 두고 묶음을 두지 않기**: 여러 항목을 함께 들이거나 되돌릴 수 없고 KG 버전 ID에 넣을 정의의 버전이 없다.
- **조각(패치) 이론이나 저절로 합쳐지는 자료 구조(CRDT)**: 검토를 거치는 정의와 가리킴의 온전함을 지켜 주지 않는다. 우리는 서버가 있고 거절과 사람의 결정이 목적이다.
- **모든 조작의 기록으로 되돌리기**: 변경이 잦지 않은 곳에 과하다. 바뀌지 않는 묶음이 곧 기록이다.
- **항목 안의 칸 단위 자동 병합을 기본으로**: 한 항목의 칸들은 서로 맞아야 해서(컬럼, 속성, 식별 키) 독립이 아니다.
- **줄줄이 저절로 되돌리기**: 다른 사람의 멀쩡한 변경이 말없이 사라진다.
- **환경마다 오래 사는 브랜치**: 오래될수록 충돌이 쌓인다. 후보 실행이 이미 운영에 영향 없는 시험을 준다.
- **병합을 줄 없이 동시에**: 위에서 뒤집은 사례의 길이다. 변경이 잦아져 줄이 병목이 되면 그때 다시 정한다.

## 결과
- REQ-119를 고친다: 정의는 바뀌지 않는 정의 묶음으로 쌓이고, 브랜치와 제안으로 고치며, 병합은 검사를 거쳐 한꺼번에 들어간다. 더한다: REQ-128(충돌: 같은 항목, 뜻의 충돌, 결과의 충돌을 병합 전에 잡는다), REQ-129(되돌리기: 앞으로 나아가는 새 변경, 걸리는 것이 있으면 막고 보인다, 급할 때의 길, 묻는 쪽을 옛 버전에 고정), REQ-109(깨는 변경과 옮김), REQ-171(정의의 시험), REQ-172(정의의 계보와 누가 쓰나). 후보 실행의 검사에 충족률과 목표를 넣는 REQ-194는 ADR-0015가 더한다.
- 설계 문서 `docs/design-docs/definitions.md`가 칸, 상태, 줄, 충돌, 되돌리기, 계보의 모양을 정한다.
- 용어집에 정의 묶음, 제안, 막는 까닭, 옮김을 더한다. "변경 묶음"은 KG 데이터의 변경을 가리키는 말이라 정의 쪽에서 쓰지 않는다.
