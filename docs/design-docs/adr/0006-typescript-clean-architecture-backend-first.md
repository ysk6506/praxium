# ADR-0006 언어와 구조 — TypeScript, 클린 아키텍처, 영향 범위 엔진은 갈아 끼울 수 있게, 알파는 백엔드부터

## 맥락
지금까지 "TypeScript 하나로 만든다"는 AGENTS.md의 한 문장뿐이었다. 언어를 요구사항에서 도출한 결정 기록은 없었다. 제품 책임자가 둘을 정했다. 언어는 정해진 것이 아니라 요구사항을 분석해 정한다(P4). 클린 아키텍처를 적용한다(P5). 또 백엔드를 제품 수준으로 설계하고 구현하되 화면은 기능을 시험할 수 있는 만큼만 만든다(P10). 쓰는 조직은 작은 팀이 아니므로 규모를 작게 잡은 판단은 다시 정한다(P13).

테라리움은 단위(폴더)와 의존 규칙을 기계가 강제하는 방식으로 클린 아키텍처를 적용했다. 프락시움의 하네스는 그 검사기를 이미 갖고 있다. 이 결정은 언어, 영향 범위 엔진의 자리, 서버의 모양, 단위의 방향, 알파의 범위를 정한다. 근거는 언어 검토와 테라리움의 구조 조사다. 메모리와 시간의 수치는 모두 추정이고 재서 확인한다.

## 결정
1. **TypeScript(Node.js LTS)로 만든다.** 요구를 대 보고 정했다.

   | 요구 | 판단 |
   |---|---|
   | 에이전트용 MCP 서버 | 공식 SDK의 첫 등급(TypeScript, Python, C#, Go, Rust)에 든다 |
   | 화면과 서버가 같은 계약을 읽는다 | 한 언어면 계약 단위 하나로 된다 |
   | 같은 입력이면 같은 결과 | 어느 언어든 된다. 시계와 난수의 주입, 정해진 순서, 내용 해시로 지킨다 |
   | 코딩 에이전트가 유지보수한다 | 언어별 증거가 약하고 서로 엇갈린다. 근거로 쓰지 않는다 |
   | 구조를 기계가 강제한다 | 하네스의 30%쯤이 TypeScript 컴파일러에 묶여 있고 바로 쓸 수 있다. 다른 언어면 그만큼 다시 만든다(추정) |
   | 수천만 객체의 영향 범위 | 언어가 실제로 갈리는 유일한 곳이다. 아래 2 |
   | 외부 망이 막힌 곳에 배포 | 단일 실행 파일이 유리하지만 지금 필수 요구가 아니다. 필수가 되면 다시 본다 |

2. **영향 범위 엔진은 처음부터 갈아 끼울 수 있게 둔다.** 엔진은 포트(쓰는 쪽 코어 단위의 인터페이스) 뒤에 있고, 읽는 입력은 언어에 묶이지 않는 투영 파일(이웃 배열과 내용 해시)이다. 먼저 TypeScript의 타입 배열로 만들어 잰다. 객체 3천만, 링크 1억을 이웃 배열로 두면 어느 언어든 1.5~2GB쯤이라는 것은 추정이다.
   - **다시 보는 조건**(재서 넘으면 엔진만 다른 언어로 바꾼다. 첫 후보는 Go): 영향 범위 응답이 정한 목표를 넘고 다른 언어의 시제품이 절반 이하로 답할 때 / 메모리가 다른 언어의 두 배를 넘거나 투영을 올리는 데 10분을 넘길 때 / 엔진의 가비지 수집 때문에 서버 응답이 눈에 띄게 늦어질 때. 이때는 먼저 엔진을 다른 역할로 뺀다(결정 3은 이미 그렇게 뜬다). 조건의 숫자는 가정이다.
   - 이 경계가 곧 갈아 끼우는 경계다. 엔진은 투영 파일을 읽고 정해진 계약으로 답한다.
3. **서버는 역할 셋으로 뜬다.** 같은 코드에서 시작점만 다르다.
   - **API**: 계약의 길과 MCP. 상태를 쥐지 않고 여러 벌 뜬다.
   - **일꾼**: 수집부터 적용까지와 일정. 소스마다의 동시 상한을 지키며 여러 벌 뜬다.
   - **질의 엔진**: 투영을 메모리에 올려 영향 범위와 길을 답한다. 여러 벌 뜬다.

   개발과 알파에서는 한 프로세스에 셋을 함께 띄울 수 있다. 넘겨받은 조사는 프로세스를 나누지 말자고 했지만 작은 규모를 전제한 판단이라 바꾼다. 질의의 부하와 수집의 부하를 따로 늘릴 수 있어야 하고, 저장소가 멈춰도 질의 엔진은 올려 둔 투영으로 답을 이어 가야 한다(ADR-0011).
4. **클린 아키텍처의 원칙**은 테라리움에서 쓴 것을 그대로 쓰되, 단위는 프락시움의 영역으로 정한다.
   - 의존은 안쪽으로만 향한다. 단위는 폴더 하나이고 다른 단위는 `index.ts`로만 닿는다. 무엇을 import해도 되는지와 어떤 외부 패키지를 쓰는지는 단위마다 구조 계약에 적고 검사가 강제한다.
   - 포트는 쓰는 쪽 코어 단위에 둔다. 어댑터는 서버에 둔다. 조립은 서버의 한 곳에서만 한다.
   - 코어는 Node를 모른다. 시계와 난수는 주입받는다.
   - 계약 단위가 길 목록, 요청 스키마, 응답 모양, 오류 모양, MCP 툴의 모양, 파일 형식(투영, 수집 봉투, 정의 내보내기)을 쥔다. **화면은 계약으로만 서버와 대화하고, 이것을 구조 계약으로 강제한다.** 문서의 그림과 실제 계약이 어긋나지 않게 한다.
   - 단위 하나가 커지면 나눈다. 서버의 실행 단위 하나에 다 몰지 않는다.
5. **단위의 방향**은 아래로 정한다. 코드가 생기는 변경에서 `harness/config/architecture.yaml`에 등록한다. 이 변경에서는 구조 계약을 고치지 않는다.

   ```
   core.kernel
     └─ core.model        타입 등록부(객체·링크·액션 타입), 링크의 뜻, 근거 등급, 식별 키, 표준 모델
          ├─ core.ingest      소스 설정, 프리셋, 원본 기록, 정제, 매핑, 식별과 병합, 링크 정의, 수 맞춤 (어댑터 포트)
          ├─ core.graph       KG 버전, 후보와 차이, 적용과 안전장치 (저장소 포트)
          │    └─ core.query       닫힌 질의, 영향 범위의 뜻과 기준 구현 (엔진 포트, 투영 형식)
          └─ core.ops         동기화 실행과 일정, 품질 지표, 문제 목록, 신선도
   core.access     도메인, 역할, 권한의 판단, 감사 (kernel과 model만 읽는다. 다른 단위가 이것을 읽는다)
   core.contract   밖으로 내는 모양: HTTP 길과 스키마, MCP 툴의 모양, 파일 형식(투영, 수집 봉투, 정의 내보내기)
   server.adapters (프로토콜 어댑터, PostgreSQL 저장소, 비밀 값 제공자, 로그인, 영향 범위 엔진) / server.http / server.mcp / server.main(조립. 역할 셋: API, 일꾼, 질의 엔진)
   web             core.contract만 읽는다
   ```

   E2E 프로세스의 단위(업무, 건, 맡김)는 그 일을 구체화할 때 더한다.
6. **알파의 범위**: 백엔드의 모든 기능은 화면 없이 쓸 수 있게 계약(HTTP API)을 먼저 완성한다. 알파의 화면은 계약만 읽는 얇은 층이고 기능을 시험하는 용도다. UX와 UI의 설계와 UX 측정 하네스(TD-0002)는 클로즈 베타로 옮기고, TD-0002의 문장을 그렇게 고친다.
7. **저장되는 해시**: 자주 도는 길(객체와 링크의 내용 해시)은 프락시움이 정한 정규 바이너리 인코딩 위의 SHA-256을 쓴다. 정규 JSON(RFC 8785)은 내보내는 파일에만 쓴다. RFC 8785는 2^53을 넘는 정수와 키 정렬(UTF-16 단위)에서 다른 언어와 어긋날 수 있다. 지금 kernel의 `hash.ts`의 `hash53`은 JavaScript의 문자열 표현에 기대므로 저장되는 값이나 다른 언어와 나누는 값에 쓰지 않는다. 부채로 적는다(TD-0004).

## 이유
- 언어를 가르는 것은 수천만 객체의 영향 범위 하나인데, 그 숫자는 아직 재지 않았다. 재기 전에 전부를 다른 언어로 옮기면 화면과 계약이 두 언어가 되고 구조 검사를 다시 만든다. 엔진만 경계 뒤에 두면 재서 넘을 때 엔진만 옮기면 된다.
- 제품 코드가 아직 거의 없어서 지금 바꾸는 비용이 가장 싸다. 그런데도 TypeScript가 남는 것은 하네스가 아니라 요구의 대부분이 언어에 중립이거나 TypeScript가 조금 유리해서다.
- 조회가 많은 조직이다. 질의, 수집, 접속하는 쪽의 부하는 모양이 다르므로 같은 코드에서 따로 늘릴 수 있어야 하고, 처음 설계를 한 프로세스로 잡고 나중에 나누면 상태를 쥔 곳을 다 고쳐야 한다.
- 화면이 계약만 읽게 강제하면 알파의 얇은 화면과 클로즈 베타의 제대로 된 화면이 같은 백엔드를 쓴다.
- 저장되는 해시가 언어와 정렬 규칙에 기대면, 엔진이나 수집기를 다른 언어로 만드는 날 모든 값이 달라진다. 저장하기 전에 정하는 것이 공짜다.

## 버린 길
- **Go로 전부(차점)**: 엔진에는 맞지만 화면과 계약이 두 언어가 되고 구조 검사를 다시 만든다. 영향 범위를 재서 넘으면 엔진만 옮긴다.
- **Rust로 전부**: 엔진 밖에서는 얻는 것이 없다.
- **JVM**: 공식 MCP SDK의 등급이 낮다.
- **Python 백엔드**: 타입과 구조의 강제가 약하다.
- **Bun이나 Deno**: 얻는 것보다 바뀌는 것이 많다.
- **처음부터 엔진을 다른 언어로**: 재기 전에 복잡도를 산다.
- **한 프로세스, 한 벌을 전제로 설계하고 나중에 나누기**: 위 이유.
- **저장 해시를 정규 JSON 위에 두기**: 위 이유.

## 결과
- 새 요구사항 번호는 없다. 결정 6의 알파 범위는 ADR-0007~0012의 요구사항 구현 순서에 반영한다.
- `ARCHITECTURE.md`의 "앞으로의 층" 절을 결정 5의 방향으로 다시 쓰고, 규칙에 결정 4의 원칙을 더한다.
- 부채 장부에서 TD-0002를 고치고 TD-0004(저장되는 해시)를 더한다. 계획에 뼈대, 영향 범위의 측정, 알파의 순서를 적는다.
- 영향 범위를 재는 도구(지어낸 3천만 객체의 생성기)는 ADR-0009, ADR-0010이 정한 순서로 만든다.
