# ADR-0074 상시 가동 에이전트가 붙는 위치를 정한다

## 맥락

글 "Building always-on agents"(2026-11-13, <https://claude.com/ko/resources/articles/building-always-on-agents>)는 상시 가동 에이전트의 구조를 이렇게 그린다. 에이전트는 대부분 잠들어 있다가 이벤트가 오면 깨어 짧게 일하고, 다음 작업으로 이어질 상태를 저장하고 다시 잠든다. 구조는 다섯 요소(이벤트 수신함, 타이머, 메모리, 권한, 발신함)로 이뤄진다. 글의 "run"은 이 문서에서 "하네스 세션"으로 적는다. "실행"은 저장소의 뜻(게이트웨이의 실행 계약, 동기화 실행)으로만 쓴다.

프락시움은 에이전트를 실행하지 않는다([게이트웨이 설계](../gateway.md) 11절). 팀이 자기 에이전트와 하네스를 가져온다. 그래서 다섯 요소 가운데 에이전트 측의 스토리지(수신함, 타이머, 메모리, 발신함)는 프락시움이 만들지 않는다. 그러나 이 구조가 에이전트의 표준 형태가 되면 프락시움은 그 구조의 바깥 조각 4개가 된다.

1. 에이전트를 깨우는 이벤트를 발행하는 측(이벤트 스트림).
2. 에이전트가 메모리에 베끼지 않고 찾아보는 곳(KG와 실행 대장).
3. 자격 증명 프록시와 승인 대기(게이트웨이).
4. 프락시움이 사람과 시스템에 내보내는 것(알림 발송, 변경 알림).

프락시움 안의 늘 도는 부분(수집 서비스, 워커)도 글의 수신함과 타이머와 같은 문제를 푼다. 그래서 이 결정은 "에이전트 실행기를 만든다"가 아니라 상시 가동 에이전트가 연동하기 쉽도록 프락시움의 계약을 다듬고, 프락시움 안의 늘 도는 부분이 따를 원칙을 정한다. 조사(글의 항목 56개와 설계의 견줌)와 독립 검토를 거쳐 범위를 줄였다. 이 결정은 설계의 결정이고 코드와 하네스의 설정은 바꾸지 않는다. 프락시움이 돕는 수준은 끊긴 프로세스를 다시 불렀을 때 이어 갈 맥락을 잘 주는 것이고, 에이전트의 기억이나 작업 노트를 대신 맡지 않는다. 자세한 형식과 권고는 [상시 가동 에이전트와 프락시움](../agent-integration.md)에 있다.

## 결정

### 1. 서 있는 위치

- **유지한다.** (가) 바꾸는 호출을 스스로 다시 보내지 않는다. 글의 "죽으면 다시 처리"는 읽기와 멱등한 일에 맞고, 현실을 바꾸는 호출은 결과를 모르면 "모름"이고 사람에게 넘긴다. (나) 하네스의 세션 저장과 재개에 기대지 않는다. 에이전트가 세션을 재개하든 새로 열든 프락시움에서는 같은 일이다(이어가기 번호와 맥락 읽기 툴). (다) 분류기에 의한 자동 승인을 두지 않는다. 결정적 조건 판단과 사람의 승인이다. (라) 에이전트의 스토리지(수신함, 타이머, 메모리, 사용자 지시, 보고한 것의 기록, 메모리 정리)를 만들지 않는다. 예외는 하나다. 프락시움의 대장에 있는 것(의도, 실행)의 기한은 프락시움이 재고, 기한이 지나면 사람에게 넘긴다(3항).
- **새로 정한다.** 별도의 조율 서비스나 내구 실행 엔진을 들이지 않는다. 이벤트의 순번, 일정, 기한, 전달 상태는 스토리지 안의 기록과 워커의 한 부분으로 처리한다(ADR-0011의 원칙 2). ADR-0009가 버린 대안 "별도로 실행되는 브로커 금지"는 스토리지 어댑터의 선택에 관한 것이고 그 선택은 바뀌지 않는다. 이 결정은 조율의 용도에만 범위를 정한다. 스토리지 안의 처리로 모자라다고 측정되면 새 결정 기록으로 다시 연다.

### 2. 이벤트의 계약

1. 같은 사건은 어느 경로(스트림, `since` 조회)로 받아도 같은 `event_id`를 가진다. 받는 측은 이것으로 중복을 거른다.
2. 이벤트는 목록에 정한 필드만 싣는다. 소스에서 온 값과 자유 글은 싣지 않는다. 고정된 낱말의 상태, 진행률, 건수, 사람이 지은 id는 싣는다. 새 규칙이 아니라 이미 있는 규칙([데이터 관측성](../data-observability.md) 12절)을 이벤트의 계약으로 올린다. 프롬프트 인젝션의 통로를 줄일 뿐 없애지는 못한다.
3. KG마다 오르는 이벤트 순번이 있고 `since`는 그 순번을 받는다. 읽는 측은 커밋된 순서까지만 읽으므로 건너뛴 것이 없음을 알 수 있다. 배포에 하나인 이벤트(작업, 제안, 정의)의 순번은 미결이다.
4. 보존 기한이 지나 `since`가 가리킬 수 없으면 그 사실을 코드로 답하고(`stale.since_too_old`), 읽는 측은 현재 상태를 다시 읽는다. 보존 기한은 승인의 유효 시간보다 길다.
5. 정확성은 당겨 가기(pull)에 둔다. 진실은 자원(대장, 실행 기록, 변경 시퀀스, 문제 목록)이고 이벤트는 알림이다. 이벤트 로그는 놓친 것을 다시 읽게 해 주는, 보존 기한이 있는 기록이다. 밀어 주기(푸시)는 깨우는 신호이고 정확성을 보장하지 않는다.
6. 종류에 에이전트가 기다리는 것을 더한다. 의도(승인 대기가 됨, 승인됨, 거절됨, 만료됨, 끝남, 모름이 됨), 실행(시작됨, 닫힘), 동기화 실행(확인 대기가 됨, 끝남, 실패)이다. 종류의 이름은 각 구현 단계가 표에 정한다.
7. 구독의 권한은 계정이 읽을 수 있는 것에 관한 이벤트로 한정한다. 계정의 상태를 읽을 때마다 확인하고, 비활성화하거나 회수한 계정에는 나가지 않는다. 이벤트 스트림의 연결은 계정마다 따로 센다. 계정이 자기 의도와 자기 실행에 관한 이벤트를 받는 것은 소유에 따른 읽기 규칙이므로 게이트웨이의 결정이 권한 설계에 더한다. 여기서는 조건만 적는다.
8. **웹훅은 지금 설계하지 않는다.** 당겨 가기로 충분하고 ADR-0010이 "푸시를 먼저"를 버렸다. 나중에 변경 알림의 포트(ADR-0010) 뒤의 어댑터로 붙을 수 있고, 그때 지킬 조건은 이렇다. 구독은 서비스 계정 하나에 묶고 전달할 때마다 읽기 필터와 계정 상태를 확인한다. 서명에 보낸 시각과 이벤트 ID를 넣고 허용 시차 밖은 받는 측이 거절하며, 키를 교체하는 동안 두 키가 유효하다. POST를 보내므로 소스 읽기의 바깥 요청 묶기(ADR-0058 결정 9, 사설 주소와 루프백을 허용한다)보다 엄격한 주소 정책을 쓴다. 서명 키는 제품 범위의 시크릿이라 `admin`이 등록한다. 웹훅은 알림이고 현실을 바꾸는 호출이 아니다. 웹훅으로 깬 에이전트가 게이트웨이 밖에서 현실을 바꾸면 우회이고 조직의 책임이다.

### 3. 승인을 기다리는 동안 하네스 세션을 닫아도 된다

1. 승인이 필요한 바꾸는 호출의 응답은 "승인 대기"와 의도 ID이고, 오류가 아니라 정상 결과다. MCP의 툴 결과에서는 `isError`가 아닌 구조화된 결과다. 에이전트는 하네스 세션을 닫아도 되고 실행은 대기 상태로 남는다. 가르는 기준은 이렇다. 호출이 받아들여져 프락시움에 상태가 생긴 것("아직", 승인 대기)은 성공 결과이고 출력 스키마의 상태 필드로 알린다. 호출이 처리되지 못한 것(한도 초과, 서버를 쓸 수 없음)은 `isError`다.
2. 승인, 거절, 만료는 이벤트로 나간다(2항의 6). 이벤트로 깬 새 하네스 세션은 "이어받겠다"고 표시한 맥락 읽기로 이어가기 번호를 새로 받고 상태를 읽어 이어간다. 같은 서비스 계정의 새 세션만 이어받을 수 있고 감사에 남는다. 겹쳐 깨어도 의도마다 실행은 한 번이다(대장).
3. 폴링은 남는다. 이벤트를 받을 수 없는 단순한 에이전트와 이벤트를 놓쳤을 때를 위해서다. 승인 대기와 "아직"의 응답에는 다시 확인할 때의 힌트 `poll_after_ms`와 승인의 만료 시각을 싣는다. 의무가 아니라 힌트이고 한도 초과의 `Retry-After`와 다르다.
4. 승인된 뒤에도 프락시움은 스스로 실행하지 않는다(ADR-0061). 에이전트가 실행 호출을 다시 불러야 실행되므로 승인과 실행 사이가 길어질 수 있다. 그래서 (가) 승인에 유효 시간을 두고 지나면 만료로 닫는다. (나) 실행 호출 때 조건을 다시 판단하고, 승인에 묶인 내용 해시와 조건의 증거가 달라졌으면 거절하고 다시 승인을 받게 한다. (다) 승인 대기와 승인됨 상태의 의도가 잡은 잠금은 만료와 함께 풀린다. (라) 승인됐는데 정해진 시간 안에 실행 호출이 없으면 사람에게 알린다(깨어나지 않는 에이전트의 감지).
5. 승인자에게 알리는 경로는 운영 액션과 정의 제안에 이미 있는 승인 요청의 전달과 같은 것을 게이트웨이의 의도도 쓴다. 글은 템플릿과 링크뿐이고 인자와 KG의 값을 넣지 않는다. 알림 발송 포트의 입력을 넓히는 일은 알림 발송의 설계가 정한다.
6. **승인을 MCP Apps의 카드로 받지 않는다.** ADR-0061이 요청 도중 질의(elicitation)를 기각한 이유와 같다. 카드는 에이전트를 쓰는 사람의 화면에 뜨는데 승인자는 프락시움의 다른 사람이고, 승인은 프락시움의 인증과 감사 로그 안에서 이뤄져야 하며 서비스 계정은 승인할 수 없다. 더해서 상시 가동에서는 호스트 앞에 사람이 없을 수 있고, 게이트웨이는 응답에서 리소스 링크를 지우며 KG 읽기 MCP는 자원을 내지 않아서 `ui://` 리소스는 지금 설계와 방향이 반대다. 메신저 안의 승인 버튼도 같은 이유로 두지 않는다. 읽기 전용의 상태 카드로 쓰는 것은 막지 않지만 만들지 않는다.

### 4. 참조의 계약

1. 에이전트는 값을 베끼지 않고 참조(KG, 세대, 종류, ID, 버전)를 메모리에 둔다. 프락시움이 지키는 계약은 이렇다.
   - ID는 다른 것을 가리키게 되지 않는다.
   - 객체가 병합되면 흡수된 측의 ID는 폐기된다. 링크 ID는 병합하면 바뀌고 옛 ID와 새 ID의 대응은 식별 이벤트에 남는다.
   - 세대가 바뀌거나 KG를 처음부터 다시 구축하면 이전 세대의 ID와 버전은 무효이다. 에이전트는 식별 키로 다시 찾는다.
   - 알림의 ID(`issue_id`)는 같은 근본 원인이 재발하면 다시 열린다. 참조에는 (알림 ID, 재발 번호)를 쓴다.
   - 이 원칙을 KG를 읽는 툴과 질의의 응답으로 어떻게 나타낼지(읽기 조건 인자, `kg_version_id`의 노출, 폐기된 ID에 대한 응답, 결과의 형식)는 정하지 않는다. 그 설계가 정한다.
2. **현실에 한 일의 진행은 프락시움의 대장이 진실이다. 이것이 이 결정의 중심이다.** 에이전트의 진행 기록에는 의도 ID와 실행 ID만 두면 되고, 나머지는 맥락 읽기 툴이 답한다(REQ-455, 게이트웨이 설계 7절). 지금 설계에 이미 있는 것은 읽기 툴 하나가 무엇인지, 끝난 것(확인 결과 포함), 진행 중이거나 모르는 것, 남은 것을 돌려주는 것과 "이어받겠다"고 표시할 때만 오르는 이어가기 번호다. 이어 가기 맥락이 갖출 성질은 이렇고, 아래 (가)(나)(다)(라)(마)는 새로 더한다(REQ-550). (가) 한 번의 읽기로 이어 갈 수 있고, 왜 멈춰 있는지(승인 대기, 조건이 아직 안 맞음, 한도, 오류)와 다음에 할 수 있는 것을 싣는다. (나) 대장에서 나온 사실만 싣고 에이전트의 말이나 추론은 싣지 않는다. 소스에서 온 값은 구조에서 갈라 싣거나 참조로 가리킨다. (다) 요약이 먼저이고 크기에 상한이 있고 자세한 것은 참조로 따로 읽는다. (라) 같은 상태면 같은 차례와 같은 형식으로 나온다. (마) 세션을 재개했든 새로 열었든, 같은 서비스 계정의 다른 세션이든 같은 맥락을 받는다. 실행 ID를 잃어도 5항의 읽기로 다시 찾아 이 맥락에 이른다.
3. KG의 값은 믿을 수 없는 입력이다. 에이전트가 소스에서 온 문자열을 자기 지시 메모리에 옮겨 적으면 한 번의 인젝션이 모든 하네스 세션에 실린다. 프락시움은 값과 자기 글(툴 설명, 오류 문장)을 구조에서 가르고(KG 읽기 MCP 설계 4.3절) 이벤트에 값을 싣지 않는다. 에이전트가 무엇을 메모리에 쓰는지는 프락시움이 막을 수 없으므로 "KG의 값은 지시 메모리에 옮겨 적지 말고 ID로 가리킨다"를 권고로 적는다. 이 권고는 글에 없고 프락시움이 더하는 것이다.
4. 게이트웨이가 내는 툴 정의의 정규 직렬화(이름, 설명, 입력과 출력 스키마, 순서)를 바이트까지 고정한다. 목적은 모델의 프롬프트 캐시다. 같은 계정과 같은 서버 버전에서 두 번 읽은 정의가 같다. 호출마다 달라지는 값(시각, 건수, KG의 값, 요청 ID)은 정의에 넣지 않는다. 고정하는 대상은 HTTP 응답 전체가 아니다. `tools/list`의 `ttlMs`와 `cacheScope`는 클라이언트가 목록을 다시 가져오는 때에 관한 것이고 다른 층이다. 성질 테스트로 둔다. 이것은 MCP 전송의 일반 원칙이고, KG를 읽는 툴의 정의에 적용하는 일은 그 설계가 정한다.
5. 에이전트가 실행 ID나 `since`를 잃어도 자기에게 열린 실행과 의도를 다시 찾는 읽기(서비스 계정 기준의 목록)를 게이트웨이의 읽기 툴에 둔다. 시작된 실행을 에이전트가 처음 아는 방법은 프로세스 정의의 설계가 정한다(미결).

### 5. 자격 증명

1. 게이트웨이가 글이 말하는 자격 증명 프록시의 위치다. 에이전트는 업스트림의 자격 증명을 보지 못하고, 게이트웨이가 허용한 툴과 주소만 부르고, 모든 호출이 기록되고, 자격 증명은 시크릿 스토리지 한 곳에 있다. 설계는 그대로이고 [게이트웨이의 안전](../gateway-safety.md)에 그 이름으로 적는다.
2. 프락시움의 토큰도 에이전트의 실행 환경 밖에서 붙일 수 있게 지킨다. 조직이 헤더를 붙여 주는 프록시를 두면 에이전트는 토큰 없이 요청한다. 프락시움이 지키는 조건은 이렇다. 토큰은 `Authorization` 헤더로만 받는다(주소, 본문, 툴 인자로 받지 않는다). 요청에 실린 토큰을 응답과 로그에 되비추지 않는다(REQ-313. 발급 응답이 값을 한 번 보이는 것은 예외다). 에이전트가 토큰의 값을 알아야만 되는 기능(본문을 토큰에서 만든 시크릿으로 서명하기 등)을 만들지 않는다. 프락시움의 주소는 하나가 아니다(코어의 REST와 `/mcp`, 게이트웨이, 쓴다면 운영 MCP). 주소마다 프록시의 허용 목록에 한 줄을 둔다.
3. 게이트웨이의 실행 토큰(REQ-528)은 이 배치와 부딪친다. 하네스가 새 실행 토큰을 받고 툴 목록이 토큰에 묶이기 때문이다. 게이트웨이의 토큰 미결(형식, 수명, 소지 증명)을 정할 때의 조건을 적는다. 인증은 프록시가 붙일 수 있는 서비스 계정의 자격(헤더, 또는 상호 TLS)으로 하고, 어느 실행인지는 에이전트가 알아도 되는 식별자(경로나 헤더의 실행 ID)로 가린다. 응용 계층의 본문 서명처럼 에이전트가 시크릿을 알아야 하는 소지 증명은 쓰지 않는다. 상호 TLS 결속을 먼저 본다. REQ-528과 ADR-0061 4항은 지금 고치지 않고 게이트웨이의 결정이 고친다.

### 6. 원칙으로만 적고 각 영역의 결정에 넘긴다

- **내보내기**(알림 발송의 설계가 정한다). 보낼 것의 사본을 따로 쓰지 않는다. 추가 전용인 진실 기록(이벤트 로그, 문제 목록의 변화)을 읽고, 받는 곳마다 어디까지 전달했는지와 시도의 결과만 적는다. 스토리지가 멈췄을 때의 알림과 하트비트, 게이트웨이의 로컬 일지는 이 경로 밖이다. 처음에는 조용하게 시작하고 양의 적절함은 클로즈드 베타에서 잰다.
- **일정과 기한**(일정의 설계가 정한다). 반복 규칙은 정의에 있고 기록에는 다음 기한만 둔다(정의가 바뀌면 다시 계산한다). 스케줄러(워커의 한 부분)가 기한이 된 것을 찾아 실행 기록에 넣고, 넣는 것은 스케줄 키로 멱등하다. 실행 중에 새로 온 것의 처리는 누가 냈는지에 따라 정한다. 사람이 누른 요청은 409와 지금 도는 실행의 ID이고, 일정이 낸 것은 미룸과 합침이다. KG의 결과를 바꾸는 기한(닫힘의 유예 등)은 벽시계가 아니라 `tick`으로 센다(ADR-0009 결정 25). 타이머 기록에 두는 것은 운영의 기한뿐이고 같은 스토리지의 다른 기록이다. 리스의 만료는 인계의 조건이지 기한이 되면 실행을 넣는 타이머가 아니다.

### 7. 방향

이벤트로 시작한 읽기 전용 실행이 "이 실행을 시작해 달라"는 요청을 남기고 끝내는 경로는 결정으로 올리지 않는다. [게이트웨이의 안전](../gateway-safety.md) 9절의 미결("프로세스 정의의 형태와 시작 방법")에 후보로 한 줄 더한다. 흔한 흐름은 REQ-527의 티켓 규칙으로 이미 이어진다.

## 이유

- 에이전트를 실행하지 않는다는 위치를 지키면서도, 글의 구조가 표준이 되면 막히는 곳은 프락시움의 계약에 있다. 시작된 실행을 에이전트가 아는 경로, 승인된 뒤 깨어나지 않는 에이전트가 잠금을 잡는 일, 실행 ID나 `since`를 잃은 에이전트가 다시 찾을 방법이 없는 일이다.
- 이벤트의 계약은 새 규칙을 만들지 않고 이미 있는 규칙을 올린다. 당겨 가기가 정확하려면 순서가 필요하다. 이벤트는 여러 주체가 동시에 쓰므로 번호를 먼저 받은 쓰기가 나중에 커밋되면 읽는 측이 건너뛴다. 그래서 커밋된 순서까지만 읽는다.
- 승인 대기를 정상 결과로 하고 세션을 닫아도 된다고 적으면, 폴링하는 동안 하네스 세션을 붙들지 않아도 된다. 의도는 토큰과 독립으로 대장에 남아서(REQ-528) 설계가 이미 허용하던 것이다. 승인된 뒤의 유효 시간이 없으면 잠든 에이전트의 의도가 잠금을 잡고 다른 실행의 조건 평가에서 "이미 일어난 것"으로 세어진다.
- ID가 영원히 같은 것을 가리킨다는 약속은 병합, 세대, 재구축에서 거짓이 된다. 지킬 수 있는 약속만 적어야 에이전트가 참조를 믿고 쓴다.
- 툴 정의의 정규 직렬화는 매 하네스 세션에 실리는 고정 오버헤드를 캐시에 맞게 한다. 이미 설계가 대체로 그렇지만 이유와 테스트가 없었다.
- 자격 증명을 에이전트가 만지지 않는 배치를 막지 않으면, 셸을 쓸 수 있는 에이전트가 토큰을 읽는 위험을 조직이 줄일 길이 있다.
- 조율 서비스를 들이지 않는 이유는 ADR-0011의 원칙 2(모든 상태는 스토리지 한 곳)이다. 새로 정하는 것이므로 모자라다고 측정되면 다시 연다.

## 대안과 기각 사유

| 대안 | 기각 사유 |
|---|---|
| 에이전트 실행기나 메모리 스토리지를 프락시움이 만든다 | 프락시움은 에이전트를 실행하지 않는다(게이트웨이 설계 11절). 에이전트의 일이다 |
| 웹훅을 지금 넣는다 | 당겨 가기로 충분하다. 시크릿의 범위, 주소 정책, 구독의 권한 주체가 정해지지 않았다(2항의 8). 조건을 적어 두고 포트 뒤의 어댑터로 미룬다 |
| 승인을 MCP Apps나 요청 도중 질의로 받는다 | 3항의 6 |
| 승인되면 프락시움이 스스로 실행한다 | 프락시움은 바꾸는 호출을 스스로 만들거나 실행하지 않는다(ADR-0061). 승인과 실행 사이에 증거가 달라질 수 있다 |
| 하네스의 호출 보류(defer)와 세션 재개를 계약으로 삼는다 | 하네스에 따라 다르고 재개한 호출은 한 번 이상 실행될 수 있다. 의도마다 한 번만 내주는 대장이 있어서 하네스가 defer로 미뤘다가 재개해도 안전하지만, 계약은 하네스의 기능에 기대지 않는다 |
| MCP의 작업 확장으로 대기를 나타낸다 | 방향이 반대(에이전트가 서버의 긴 작업을 기다린다)이고 유효 시간이 있다(E2E 프로세스의 방향 4절) |
| 보낼 것의 사본을 쓰는 발신 기록을 일의 트랜잭션과 같은 쓰기로 둔다 | 파일 스토리지는 파일을 둘로 나누면 둘 사이에서 장애가 났을 때 어긋나 성립하지 않는다. 스토리지가 멈췄을 때 알려야 할 것을 쓸 수 없다. 진실과 파생 데이터의 구분에도 어긋난다 |
| 이벤트 로그를 진실의 원천으로 한다 | 진실은 자원이고 이벤트는 알림이다(REST API 3-10) |
| ID가 영원히 같은 것을 가리킨다고 약속한다 | 4항의 1에서 보듯 거짓이 된다 |
| 분류기로 자동 승인한다 | 글도 가장 중요한 결정은 사람이 본다고 한다. 결정적 조건 판단과 사람의 승인으로 한다(게이트웨이 설계 6절) |

## 결과

- **알려진 한계.** 이 결정은 설계이고 구현이 없다. 웹훅이 없으므로 길게 떠 있는 연결을 둘 수 없는 환경의 에이전트는 폴링에 기댄다. 에이전트가 메모리에 무엇을 쓰는지는 막지 못한다. 보존 기한과 승인의 유효 시간과 `poll_after_ms`의 값은 측정할 가정이다.
- **하지 않는 것.** 에이전트의 수신함, 타이머, 메모리 스토리지, 발신함, 메모리 정리. 분류기에 의한 자동 승인. 하네스의 세션 재개에 기대기. MCP Apps의 승인 카드. 별도의 조율 서비스와 내구 실행 엔진. 웹훅의 순서 보장과 정확히 한 번 전달.
- **어느 구현 단계에서 하나.** 이벤트 스트림과 동기화 실행의 이벤트(REQ-535부터 REQ-538까지)는 이벤트 스트림을 만드는 변경이 한다. 게이트웨이에 관한 것(REQ-539부터 REQ-542까지, REQ-544부터 REQ-546까지, REQ-549, REQ-550)은 게이트웨이의 구현이 한다(클로즈드 베타 뒤). 툴 정의의 고정(REQ-549)은 게이트웨이의 구현이 한다. 참조의 계약은 원칙만 적고 요구사항을 두지 않는다(REQ-547은 쓰지 않는다). 알림의 재발 구분(REQ-548)은 알림을 구현하는 변경이, 토큰의 헤더 규칙(REQ-543)은 인증을 점검하는 변경이 한다. 내보내기와 일정은 각 설계의 결정 기록이 정한다.
- **지금의 수집 설계(ADR-0058)에 이미 반영한 것.** 동기화 실행의 시작한 원인(`trigger`)과 상태 전이의 순번, 이미 돌고 있는 소스의 409에 지금 있는 실행의 `id`, 실행 `id`를 다시 쓰지 않는 것, 바깥 요청의 묶기 코드를 어댑터 밖 한 곳에 두고 정책을 인자로 받는 것. 시크릿의 범위에 종류를 둘 자리는 저장 형식을 바꾸지 않고, 제품 범위의 시크릿이 필요해질 때 형식 버전을 올려 더한다.
- **같이 더하는 것.** 게이트웨이에 실행마다 연속 거절 수와 누적 거절 수의 한도를 둔다(REQ-546). 넘으면 실행을 멈추고 사람에게 넘긴다. 값은 측정할 가정이다. REST의 `Idempotency-Key`를 기억하는 기간(구현은 10분)을 에이전트를 만드는 사람에게 알린다.
- **미결.** KG를 읽는 툴과 질의의 계약에 닿는 것(읽기 조건 인자, `kg_version_id`의 노출, 폐기된 ID에 대한 응답, 결과의 형식)은 그 설계가 정한다. 배포에 하나인 이벤트의 순번, 실행의 시간 한도가 승인 대기 중에도 흐르는지, 승인 대기 결과에 승인 화면의 주소를 실을지, 시작된 실행을 에이전트가 처음 아는 방법(프로세스 정의의 설계), 소유에 따른 읽기 규칙(게이트웨이의 결정), 토큰의 형식과 수명과 소지 증명(게이트웨이의 결정).
