# ADR-0051 영향 범위 화면의 계산과 그래프·목록 부품 (SVG 직접, 새 의존성 없음)

## 맥락

영향 범위 질의(`POST /v1/kgs/{kg}/queries:impact`)의 답을 사람이 볼 화면이 필요하다. 화면은 질문 하나를 보는 곳이다: 시작 객체들(또는 대상 객체)과 방향과 한도가 질문이고, 답은 등급별 개수와 항목(원인 경로 포함)이다. 사람이 하고 싶은 일은 "무엇이 어떤 순서로 어떻게 영향받는가"를 한눈에 보고, 모든 항목을 표로 확인하는 것이다.

엔진의 API가 아직 병합되지 않았다. 그 전에 할 수 있는 일은 응답의 모양에서 시작하는 순수 계산과, 계산 결과를 그리는 부품이다. 화면에 연결하는 일(라우트, 데이터 조회, 객체 상세의 진입 버튼)은 엔진 병합 뒤로 미룬다. 지금 화면의 모양은 임시다(디자인 콘셉트가 정해지지 않았다). 이 결정이 남기는 것은 동작, `data` 계층의 계산, 부품의 구조, 접근성 규칙이다.

## 결정

1. **그리는 기술은 SVG를 직접 쓴다. 새 의존성은 없다**(런타임도 개발용도). 그래프 라이브러리, Canvas, WebGL은 쓰지 않는다.
2. **재생은 단계마다 층 하나(`<g>`)의 투명도 전환이다.** 요소마다 애니메이션을 두지 않는다. 층의 안쪽은 단계가 바뀌어도 다시 그리지 않고(메모), 바뀌는 것은 층을 감싼 `<g>`의 클래스뿐이다. 시간은 순수 함수의 상태(정수 단계 하나)와 박자(250~700ms, 전체 4초 이하)로 정하고, 시계는 `requestAnimationFrame`의 시각을 밖에서 받는다. 프레임마다 상태를 바꾸지 않고 박자가 찰 때만 바꾼다.
3. **움직임은 `prefers-reduced-motion: no-preference`일 때만 켠다.** 전환은 `motion-safe:` 클래스(`transition-[opacity,visibility]`와 `duration-(--step-ms)`)로 걸고, 전환 길이는 인라인 `style`의 변수(`--step-ms`)로만 준다. 움직임을 줄인 설정에서는 길이를 읽는 클래스가 꺼지므로 전환이 없다(측정: 켠 설정의 층이 `opacity, visibility 0.7s`, 줄인 설정이 `0s`). 이 설정에서는 처음 열 때 재생하지 않고 끝 단계로 열리며, 슬라이더와 재생·멈춤·다시 보기는 그대로 동작한다.
4. **목록이 정답이고 그래프는 같은 데이터의 다른 보기다.** 목록은 받은 항목 전부를 등급별 구역(심각한 순)과 정렬과 쪽(50개)으로 보인다. 그래프는 접근성의 대체 수단이 아니라 퍼지는 순서를 보이는 보기이고, 그래프를 읽지 못하는 사람은 같은 내용을 목록에서 모두 본다.
5. **등급은 모양, 글자, 색을 함께 쓴다**(색만으로 구분하지 않기). 색은 테마의 토큰(`danger`, `warn`, `accent`, `muted`)만 쓴다. 근거 등급은 간선의 선 모양으로 나타낸다(사실 실선, 가정과 알 수 없음 점선). 화면과 용어집의 등급 이름은 "이중화 상실(직접)", "이중화 상실(상속)"이다(용어집의 표는 "직접 노출 / 상속된 노출"을 그대로 두고 화면의 이름을 함께 적는다).

   | 등급 | 이름 | 모양 | 색 |
   |---|---|---|---|
   | 시작 객체 | 시작 | 이중 원 | accent |
   | `down` | 중단 | 꽉 찬 사각형 | danger |
   | `interrupted` | 일시 중단(페일오버) | 속이 빈 사각형 + 점 | danger |
   | `unknown` | 알 수 없음 | 점선 원 + 물음표 | muted |
   | `exposed_direct` | 이중화 상실(직접) | 꽉 찬 삼각형 | warn |
   | `exposed_inherited` | 이중화 상실(상속) | 속이 빈 삼각형 | warn |
   | `degraded` | 저하 | 마름모 | warn |
   | `unmanageable` | 관리 불가 | 둥근 사각형 + 가로선 | accent |

6. **접근성.** 그래프 영역은 이름 있는 `section`(스크롤해서 키보드로 닿는다)이고 안의 `<svg>`는 요약 이름을 가진 `group`이다. 노드는 `<g role="button">`이고 이름은 "이름, 타입, 층, 등급, N단계"이며 탭 정지는 하나(움직이는 `tabindex`)이다. 방향키는 오른쪽이 첫 자식, 왼쪽이 부모, 위아래가 같은 열의 이웃, Home과 End가 열의 처음과 끝이고, 아직 닿지 않은 층의 노드로는 가지 않는다. Enter와 Space로 고르고 Esc로 푼다. 고른 노드는 재생 중이 아닐 때 알림 영역(`<output>`)이 읽는다. 첫 요소는 "목록으로 건너뛰기" 단추다. 노드의 줄 높이는 24px이라 누르는 영역이 24px 이상이다(WCAG 2.5.8). Biome의 `useSemanticElements`는 SVG의 `<g>`와 `<svg>`에 맞는 요소를 모르므로 역할과 상태를 속성 묶음으로 펼쳐 준다(무시 주석을 더하지 않았다).
7. **계산은 `data`에 순수 함수로 둔다.**
   - `impact-input.ts`: 응답의 모양을 아는 유일한 곳. 응답을 시작에서 각 항목까지의 사슬을 가진 기록으로 바꾼다. 나중에 `shape=graph`가 생기면 이 파일만 바뀐다. 입력 타입은 계약에서 읽는 최소한이고 생성된 `ImpactData`가 대입된다(생성된 타입 그대로 대입되는지는 `impact-input.test.ts`가 컴파일로 확인한다).
   - `impact-tree.ts`: 원인 트리. 부모는 항목 자신의 바로 앞 원인이다. 경로에만 있는 객체는 경유 노드, 읽을 수 없는 객체는 이름 없는 숨김 노드이고, 위쪽 방향은 대상이 뿌리인 같은 트리다. 두 경로가 다른 부모를 말하면 작은 ID가 이기고 자식과 뿌리는 정렬해서, 항목의 도착 순서가 달라도 같은 트리다. 원인이 고리를 이루면 끊어 숲으로 만든다.
   - `impact-layout.ts`: 층이 열(공급하는 쪽이 왼쪽: 설비, 네트워크, 스토리지, 하드웨어, 가상화, 컨테이너, 플랫폼, 서비스, 공통, 시스템, 모르는 층은 마지막)이고 줄은 `max(그 열의 다음 빈 줄, 부모의 줄)`이다. 트리를 깊이 먼저 도는 순서로 쌓으므로 반복 계산이 없고 같은 입력이 같은 좌표다.
   - `impact-group.ts`: 노드가 300개를 넘으면 같은 부모 묶음 아래의 같은 타입을 한 묶음으로 본다(재귀). 모든 노드는 묶음 하나에 들어가고, 묶음은 개수와 등급 구성과 구성원(심각한 순)을 가진다.
   - `impact-spread.ts`, `useSpread.ts`: 재생 상태와 전이, 시계.
   - `impact-stats.ts`, `impact-rows.ts`, `impact-view.ts`, `impact-picture.ts`, `impact-grades.ts`: 개수, 목록의 행·구역·정렬·쪽, 주소 상태와 요청, 그래프에 넘길 노드·간선·열, 등급의 이름과 모양.
8. **주소는 질문 중심이다**: `#/kg/{kg}/impact?...`. 쿼리는 `dead`, `site`, `cut`, `target`(각각 형식을 검사하고 20개까지, `target`이 우선), `reading`, `hops`, `max`(500, 2000, 5000, 20000, 기본 2000), `view`, `focus`, `sel`, `step`, `all`, `sort`, `dir`, `page`, `grade`이고 기본값은 쓰지 않는다. 라우터 수정은 화면을 연결할 때(다음 단계) 한다.
9. **견본 데이터는 생성 함수다**(`test-support/impact-world.ts`). 시드가 있는 난수로 지어낸 응답(작은 것, 300·2,000·5,000 항목, 한도에 걸린 것, 이중화 그룹과 알 수 없음과 숨김 객체를 가진 것)을 만든다. 큰 견본을 파일로 커밋하지 않는다.
10. **부품은 `ui`에 있고 `data`를 import하지 않는다.** 그래프는 일반 구조(열, 줄, 단계, 모양, 낭독 이름)를 받고, `data`의 `nodePicture`와 `overviewPicture`가 같은 모양을 만들어 화면이 이어 준다. 새 유닛과 새 의존성이 없다.

## 이유

- **측정**(이 기계: CPU 2개에 다른 작업이 겹친 부하 평균 약 4.5(2회차 재측정. 처음 측정은 15~23), GPU 없는 소프트웨어 렌더링의 헤드리스 크롬, 개발 서버. 절대값은 비관적이고 비교만 믿을 만하다). 그래프 부품만 띄운 견본 페이지에서 자동 재생 한 번(박자 7번, 약 4초) 동안 `requestAnimationFrame` 간격을 쟀다.

  | 견본 | 그려진 SVG 요소 | 재생 중 프레임 수 | 33ms를 넘은 프레임 | 중앙값 | 95번째 백분위 | JS 힙 |
  |---|---|---|---|---|---|---|
  | 300 항목, 노드 전부 | 1,619 | 197 | 2 (1%) | 16.7ms | 16.8ms | 17MB |
  | 2,000 항목, 노드 전부(노드 2,002), 3번 | 10,489 | 196~201 | 0~2 (0~1%) | 16.7ms | 16.7~16.8ms | 26~27MB |
  | 2,000 항목, 개요(묶음 7개) | 69 | 201 | 0 | 16.7ms | 16.8ms | 15MB |
  | 5,000 항목, 개요 | 69 | 201 | 0 | 16.7ms | 16.8ms | 16MB |

  기준은 "33ms를 넘는 프레임 5% 이하"였고 2,000 노드를 전부 그릴 때 3번 모두 1% 이하로 안이다(처음 측정은 7번 합계 4.4%였고 한 번은 14%였다. 부하가 높았던 때). 부하가 낮을 때와 높을 때의 차이가 크므로 이 숫자는 방식의 비교로만 읽는다. 처음에는 같은 페이지가 프레임마다 상태를 바꿔 요소 10,489개를 다시 만들었고 박자마다 1초가 넘게 걸렸다. 박자가 찰 때만 상태를 바꾸고 층의 안쪽을 메모하자 위의 값이 됐다(이 변경 전에는 같은 견본의 중앙값이 183ms였다).
- 계산 시간(같은 기계, 부하 포함, 5,000 항목): 트리 280~323ms, 개요 48~173ms, 그래프 노드 89~222ms, 목록 행 21~196ms. 2만 항목은 트리 840ms다. 시간은 부하에 크게 따라 변하므로 시험은 시간이 아니라 방문 수를 센다(5,000 항목의 트리가 항목 수와 경로 단계 수의 상수 배 안에서 끝남).
- **번들**(추정, 실제 화면이 붙기 전): 새 `data` 코드는 최소화해서 gzip 약 7.2KB, 새 `ui` 부품은 약 3.8KB로 합계 약 11KB이다. CSS는 새 클래스로 약 0.4KB 늘 것으로 본다(견본 페이지의 CSS 6.5KB 대 제품의 6.2KB). 예산(JS 170,000, CSS 10,000바이트)과 이 화면이 늘리는 양의 상한(JS 20KB, CSS 2KB) 안이다. 제품의 번들은 이 부품을 아직 import하지 않아 변하지 않는다(JS 143,583바이트, CSS 6,201바이트).
- **강제 색상 모드.** 등급은 모양(채움, 속 빈, 점선, 도형 종류)과 낱말로도 구분되고 색은 거들 뿐이라서 색이 시스템 색으로 바뀌어도 구분이 남는다. 헤드리스 크롬은 `forced-colors: active`에서 미디어 쿼리만 켜고 색을 바꾸지 않아 실제 시스템 색의 모습은 확인하지 못했다(Windows 고대비에서 사람이 볼 항목으로 남긴다).
- **의존성을 쓰지 않은 이유.** `@xyflow/react`는 확대·이동을 주지만 배치를 주지 않아 층 배치와 재생과 묶음은 어차피 직접 만들어야 하고, gzip 약 59KB(예산의 여유 27KB를 넘는다)와 직접 의존 셋이 는다. 노드가 React 요소라 5천 노드는 느리다. `elkjs`는 허용 라이선스 목록에 없다(EPL-2.0 또는 GPL-3.0). `dagre`와 `d3-force`는 층이 정해진 배치에서 얻는 것이 없거나 결정적이지 않다. Canvas와 WebGL은 접근성 트리, 포커스, 한글 글자, 다크 모드와 강제 색상 모드를 모두 직접 짜야 하고 5천 노드에서도 SVG보다 느렸다. 확대·이동·작은 지도가 부족하다는 증거가 나오면 그때 `@xyflow/react`를 따로 결정한다(배치 함수는 렌더러와 분리돼 있어 그대로 넘겨줄 수 있다).
- **결정적인 배치**는 같은 질문이 같은 그림이어야 링크로 공유한 화면과 스크린샷과 시험이 일치하기 때문이다. 힘 기반 배치는 이를 못 한다.
- **줄 높이 24px.** 설계 때의 16px은 노드를 24px 이상 누르게 하는 규칙(WCAG 2.5.8)과 맞지 않아 24px로 정했다. 300개를 모두 그려도 높이는 7,200px 안이다. 그 이상은 개요로 연다.

## 대안과 기각 사유

- 요소마다 SVG 애니메이션: 요소가 2,000개를 넘으면 프레임의 대부분이 느려진다(설계 때 측정: 2,043요소에서 100%).
- HTML 요소마다 애니메이션: 같은 이유로 2,049요소에서 64%.
- 프레임마다 상태를 바꾸는 시계: 위 측정대로 박자마다 1초가 넘게 걸렸다.
- 간선을 `stroke-dashoffset`으로 그려 넣는 전환: 점선(가정의 간선)과 겹치고 요소마다 전환이라 비싸다. 간선도 층의 투명도로 나타난다.
- 시작 객체의 한 번 커졌다 돌아오는 강조: 요소 하나라도 변환이 필요하고 모양이 임시라서 만들지 않았다. 열 머리는 닿을 때 글자가 굵어지고 배경띠가 켜진다(색만이 아니다).
- 목록을 화면 낭독기의 대체 수단으로만 두기: 목록이 모든 항목을 가진 정답이므로 같은 비중으로 만들었다.

## 결과

- 새 요구사항 REQ-350~357이 추가되고 테스트가 각각 `[REQ-NNN]`으로 가리킨다.
- `web.data`, `web.ui`, `web.testsupport`에 파일이 늘고 새 유닛과 의존성이 없다. 화면에 연결하지 않았으므로 제품의 번들과 동작은 변하지 않는다.
- **하지 못한 것과 다음에 할 것**: 화면 연결, 실제 API 호출, 객체 상세의 입구, 라우트와 `isKnownPath`(다음 단계). 화면 낭독기(NVDA, VoiceOver)에서 SVG 안의 `role="button"`이 어떻게 읽히는지와 강제 색상 모드는 확인하지 못했다(Playwright의 크롬 스크린샷만). 파이어폭스와 사파리의 측정이 없다. 큰 결과의 확대(`focus`)와 쪽 도착마다 나눠 처리, 표본 안내는 뒤의 단계다. 두 경로가 같은 객체에 다른 부모를 주는 경우의 보조 간선은 만들지 않았다(작은 ID의 부모만 쓴다).
- 이 화면의 모양(색, 배치, 구성)은 임시다. 디자인이 정해지면 `ui`의 부품과 CSS를 다시 만들고, `data`의 계산과 접근성 규칙은 남는다.
