# ADR-0124 테스트 잠금의 지문 계산에서 같은 일을 되풀이하지 않는다

## 맥락

테스트 변조 방지 검사(`testguard.ts`)의 테스트 `the real repository's tests are intact`는 실제 리포지토리 전체를 검사한다. CI에서 이 테스트의 시간이 8.6초(#109), 9.3초(#112), 15.5초(#114)로 늘다가 #115에서 20.5초가 되어 vitest 시간 제한(20초)을 넘었다. ADR-0120이 많은 잠긴 테스트를 한 결정으로 고치고 테스트 도우미와 테스트 파일을 더한 뒤 두 배 가까이 됐다.

로컬에서 한 번 돌린 시간(CPU 프로파일, 고치기 전 약 5.8초)은 다음과 같이 나뉘었다.

| 단계 | 시간 | 되풀이한 일 |
|---|---|---|
| 수정 결정 확인(`lockViolations`의 TLOCK004) | 약 2.7초 | 잠금 파일의 수정 기록 1,028건마다 그 결정 기록을 다시 읽고 front matter(YAML)를 다시 파싱하고 본문 해시를 다시 계산했다. 결정 기록은 34개뿐이고, 300건 안팎을 고친 결정 기록(ADR-0077, ADR-0120)은 front matter가 커서 비용이 (건수 × 크기)로 늘었다. |
| Go 파일 읽기와 토큰 분해 | 약 0.9초 | 테스트 파일과 잠금에 포함하는 지원 코드만 필요한데 모듈의 모든 Go 파일을, 그것도 두 번 읽었다. |
| Go 테스트의 지문(`describe`) | 약 1.2초 | 테스트마다 도달 범위의 선언 하나하나에서 이름 찾기, 지원 패키지 이름 찾기, 실패·건너뛰기 호출 세기, 리터럴 모으기, 파일 이름 찾기를 처음부터 다시 했다. 테스트 2,165개가 같은 도우미에 닿는다. |
| TypeScript 테스트의 정적 규칙 | 약 0.5초 | (이 결정에서는 손대지 않는다) |

## 결정

결과(지문, 오류 목록, 잠금 파일)를 바이트 단위로 같게 두고 같은 계산을 한 번만 한다. 무엇을 따라가는지는 바꾸지 않는다.

1. **수정 결정 기록은 검사 한 번에 한 번만 읽는다**(`test-lock.ts`의 `adrChecker`). 결정 기록마다 "없음/확정되지 않음", `amends_tests` 목록, 이유가 40자 이상인지를 한 번 구해 두고, 각 수정 기록에는 예전과 같은 순서(없음 → 확정 → 목록에 있음 → 이유)로 답한다.
2. **필요한 Go 파일만, 한 번 읽는다**(`go-config.ts`의 `goFiles`에 경로 조건 `keep`). 테스트 지문은 `_test.go` 파일과 `go.locked_support`의 파일만 읽는다. 조건은 경로만 보고, 고른 파일과 순서는 예전에 읽은 뒤 거른 것과 같다.
3. **선언 하나의 사실은 선언에 붙인다**(새 파일 `go-test-entry.ts`). 언급하는 이름, 테스트 핸들, 실패 호출 수, 건너뛰기 수(`testing.Short` 포함), 리터럴 목록을 선언을 만들 때 한 번 구한다. 테스트의 값은 예전처럼 도달 범위 전체에서 모으므로(리터럴은 정렬, 수는 합) 같다. 실패하는 도우미의 고정점 계산도 같은 조건을 미리 구한 이름 집합으로 판단한다.
4. **한 단계의 도달은 선언마다 한 번 구한다**(`go-test-units.ts`의 `Pool.stepsOf`, `Pool.methodsOf`). 이름·멤버·지원 패키지로 닿는 선언 목록과, 타입이 데려오는 메서드 목록을 예전의 방문 순서 그대로 저장해 두고, 테스트마다의 탐색은 그 목록을 예전 순서로 걷는다. 순환은 예전처럼 방문 집합이 끊는다. 저장은 패키지(Pool)마다 따로이므로 다른 패키지의 이름 색인이 섞이지 않는다.
5. **선언이 가리키는 파일은 (패키지 폴더, 선언)마다 한 번 찾는다**(`go-test-files.ts`의 `Files.readsOf`). 파일의 해시는 예전에도 한 번만 계산했다.

## 결과가 같음을 지킨 방법

- 고치기 전과 뒤에 실제 리포지토리에서 모든 단위(TypeScript·Go·데이터 4,323개)의 모든 필드, Go 테스트 정보 2,165개, 요구사항 인용, `GOTEST003`·`TRACE007`, `run()`의 결과를 JSON으로 덤프해 바이트 단위로 같음을 확인했다. `pnpm lock-tests`가 쓰는 잠금 파일도 고치기 전과 같다(새 테스트 파일의 항목만 더해진다).
- 하네스의 기존 테스트(잠금의 위반·수정·약화, 지원 코드, 순서 무관)가 모두 그대로 통과한다.
- 새 테스트 `go-reach.test.ts`가 메모가 틀리기 쉬운 경우를 고정한다: 서로 부르는 도우미의 순환에 다른 테스트로 들어가는 경우, 같은 이름의 메서드와 함수, 여러 파일과 선언 순서, 한 테스트의 지문이 같은 도우미를 쓰는 다른 테스트의 유무에 따라 달라지지 않음, 결정 기록 하나에 여러 수정 기록이 있을 때 각각의 답.

## 결과

- 로컬에서 그 테스트 하나가 약 7.1초에서 약 2.1초가 됐다(같은 기계, 다른 작업이 없을 때). 남은 시간의 대부분은 Go 파일의 토큰 분해와 TypeScript 파싱, 테스트마다 도달 범위의 글을 정렬해 해시하는 일이고, 테스트 수에 비례한다.
- 시간 제한, 규칙, 잠금 형식은 바뀌지 않는다.

## 대안과 기각 사유

- **시간 제한을 늘린다**: 원인(되풀이한 계산)이 그대로라 테스트와 수정 기록이 늘면 다시 넘는다. 기각.
- **식별자마다 전체 도달 범위를 메모(강한 연결 요소로 묶어 순환을 처리)**: 테스트마다 도달 범위의 글을 정렬하고 해시하는 일은 남으므로 얻는 것이 적고, 순환 처리의 코드가 늘어 결과가 같음을 지키기 어렵다. 한 단계 도달의 메모로 충분했다.
- **결과를 디스크에 캐시한다**: 캐시가 낡으면 잠금이 느슨해질 수 있다. 기각.
