# ADR-0052 수집에서 조용히 틀리거나 한 실수가 크게 번지는 동작을 고친다

## 맥락

독립 검증과 문서 작업에서, 처음 쓰는 사람이 자기 엑셀을 넣을 때 **조용히 틀리거나 한 가지 실수가 크게 번지는** 동작이 나왔다. 메시지를 고치는 일이 아니라 동작을 고치는 일이다(ADR-0046은 메시지였다).

1. 식별 키가 아닌 속성 하나의 값이 틀리면(열거에 없는 상태 "점검") 그 행이 피드에서 통째로 빠져 객체가 만들어지지 않았다. 그 객체를 가리키는 링크는 줄줄이 `link_target_missing`이 되었다. 칸 하나의 실수가 행과 링크 여럿을 지웠다.
2. 실행 안에서 객체를 맞추는 서명에 `key_name`이 들어 있었다(`identify.go`의 `sigParts`). 같은 객체를 가리키는 두 피드 중 한쪽에만 `key_name`을 주면 서로 다른 객체가 되고, 값만 더하는 피드는 오류 없이 `value_without_object`가 되었다.
3. `filter`로 걸러진 행의 객체는 그 피드가 `retires_objects`이면 다음 실행에서 바로 닫혔다. 파일에서 사라진 행은 완전한 수집에서 연속 3번과 24시간을 기다린다. 필터의 오타 하나가 객체를 바로 닫았다.
4. 엑셀에는 시트당 행 한도가 있지만 CSV와 JSON Lines에는 파일 크기 한도(20MB)뿐이었다. 큰 파일(70만 행, 16MB)에서 프로세스가 메모리 부족으로 죽은 일이 있다.
5. `filter`의 `in`과 `not_in`은 글자 그대로 비교해서 칸의 앞뒤 공백이 있으면 맞지 않았다(`not_empty`와 자연 키는 이미 공백을 무시한다).
6. 피드에 `approximate`가 있어도 링크의 근거 등급은 언제나 `fact`였다.

## 결정

**1. 한 칸의 값이 틀려도 행을 버리지 않는다 (REQ-358).**
- 식별 키의 구성 요소가 아닌 속성의 값이 틀리면 객체는 만들고 그 속성만 쓰지 않는다. 값이 없는 것(`unknown`)과 같게 다룬다. 그 칸은 지금처럼 `invalid_value`(행의 칸 범위인 셀 주소를 포함)로 보고하고, 이유 문장 끝에 "객체는 이 값 없이 만들었다"를 덧붙인다. 그 객체를 가리키는 링크는 정상으로 만들어진다.
- 전에 맞던 값이 이번에 틀린 값으로 바뀌면 빈 칸이 된 것과 같게 다룬다. 옛 값을 붙들지 않는다. 소스가 더는 그 값을 말하지 않기 때문이다.
- 식별 키의 구성 요소(속성 조합의 속성, 식별자 스킴의 값)가 틀리거나 비면 지금처럼 그 행에서 객체를 만들 수 없다(`missing_identity`). 문제 메시지는 틀린 컬럼과 값을 말하고 "식별 키의 일부라서 이 행의 객체를 만들지 못했다"고 덧붙인다. 식별을 먼저 판정하므로 이런 행은 칸의 오류를 따로 보고하지 않고 한 줄로만 보고한다.
- **필수 속성이 이렇게 비는 경우**는 지금 필수 속성의 칸이 비었을 때와 같게 다룬다. 확인한 현재 동작: 파이프라인은 빈 칸을 값 없음으로 건너뛰고 필수 여부를 검사하지 않으며(그래프도 필수 속성을 강제하지 않는다), 객체는 그 속성 없이 만들어지고 문제도 없다. 틀린 칸도 이제 객체를 만들고 그 속성이 비며, 다른 점은 `invalid_value`가 보고되는 것뿐이다. 새 규칙을 만들지 않았다.
- 행 수 식은 그대로다: `read = used + filtered + problem + unused`. 속성만 빠진 행은 `used`이다. 요약 줄의 데이터셋 줄에 `used_with_problem`(문제가 있었던 `used`의 행 수, 합에 넣지 않는다)과 `cells_left_out`(비운 칸의 수)을 더해 행이 빠진 `problem`과 구분한다. 기존 항목의 이름과 순서는 그대로 두고 `unused` 뒤에 둔다.

**2. `key_name`은 이름표일 뿐이다 (REQ-359).** 식별 키의 동일성은 **타입 + 구성 요소의 (종류, 참조, 값)의 순서 있는 목록**에서만 나온다. 참조는 속성 ID나 스킴 ID이다. `key_name`은 메시지에만 쓴다. 저장되는 키(`graph.KeyPart`)에는 처음부터 이름이 없었고 객체 ID는 타입과 그 키에서 나오므로 객체 ID와 `graph_hash`는 바뀌지 않는다. 바뀌는 것은 수집 상태 파일의 식별 색인 서명뿐이다(알파 2의 데이터 폴더는 다시 수집한다. 아래 결과).

**3. 걸러진 행의 객체를 바로 닫지 않는다 (REQ-360).** 걸러진 행도 파일에서 사라진 행과 같은 규칙으로 닫는다. 데이터셋의 상태에 걸러진 행마다 (연속으로 걸러진 횟수, 처음 걸러진 때)를 두고(`filtered`), 완전한 수집(그 실행에서 읽은 데이터셋)에서 횟수가 3 이상이고 처음부터 24시간이 지나면 그 행을 놓아 준다. `deletion: none`인 데이터셋은 사라진 행을 닫지 않으므로 걸러진 행도 닫지 않는다. 기다리는 동안에는 이미 객체가 있는 행에 한해 행이 걸러지지 않은 것처럼 먹이므로 객체와 링크가 그대로 남는다(사라진 행이 닫히기 전까지 먹이는 것과 같다). 걸러진 행으로 새 객체가 만들어지지는 않는다. 기다리는 동안 문제는 보고하지 않는다(규칙이 걸러낸 행은 문제가 아니다). 필터를 고치면 센 횟수는 지워진다. 요약 줄에 `waiting_objects`(사라졌거나 걸러져서 닫히기를 기다리는 객체 수)를 더한다. 이번 실행이 닫은 객체 수는 이미 있는 `retired_objects`이다.

**4. CSV와 JSON Lines의 행 수 한도 (REQ-361).** 소스 정의의 `limits.max_rows_per_dataset`을 더한다. 기본은 엑셀의 시트와 같은 200,000이고 0보다 작으면 정의를 거절한다. 읽는 쪽(`ParseLimited`)이 한도를 한 행 넘으면 멈추므로 파일 전체를 메모리에 올리지 않는다. 읽을 수 없는 줄도 행으로 센다. 넘으면 파일 크기 한도를 넘었을 때와 같이 그 데이터셋은 불완전한 수집(`incomplete_capture`)이고, 이유에 한도의 값과 필드 이름을 말한다. 그 데이터셋의 어떤 행도 쓰지 않고 사라진 행으로도 세지 않는다. 엑셀의 `max_rows_per_sheet`(넘으면 실행이 멈춘다)는 그대로다.

**5. `in`과 `not_in`의 공백 (REQ-362).** 칸과 목록의 값 모두 앞뒤 공백을 없애고 비교한다. 대소문자와 가운데 공백은 그대로 비교한다.

**6. 링크의 근거 등급 (REQ-363).** 설계 문서가 이미 정하고 있었다. 파이프라인 설계 5.3의 4항이 "도출한 링크와 그룹의 등급은 사용된 입력 중 가장 낮은 등급"이라고 하고, `declared`의 기본 등급이 `fact`이고 근사값이면 `assumed`라고 한다(3.1). 코드가 어긋나 있었으므로 문서가 정한 대로 맞췄다. `same_key` 링크의 입력은 두 피드의 행이므로 링크의 등급은 읽은 두 피드 가운데 낮은 쪽이다. 한쪽 피드에 `approximate`가 있으면 `assumed`, 아니면 `fact`이다. 링크 정의의 `basis`를 `derived`가 아닌 값으로 주어도 같은 규칙이다(링크가 입력보다 확실할 수는 없다). 설계 문장은 5.3의 4항에 `same_key`의 경우를 한 구절 덧붙였다. 예제와 합격 테스트는 `approximate`를 쓰지 않아 `graph_hash`가 달라지지 않는다.

**문서 (REQ-364).** 설계 문서의 바뀐 문장: 수집 설계 4.3에 걸러진 행의 규칙(문단 하나), 같은 문서 10절의 안전 한도에 CSV와 JSON Lines의 행 수 한도, 파이프라인 설계 3.1의 `identity` 행에 `key_name`의 뜻, 3.3에 틀린 칸의 처리와 걸러진 행의 기다림, 5.3의 4항에 링크 등급, 7절에 속성만 빠진 행의 분류. 형식 안내서(docs/guides/ingest-definitions.md)와 실행 파일에 담는 사본을 새 동작에 맞췄다. 7절의 예시 출력은 빌드한 실행 파일로 돌려 실제 출력으로 고쳤고(`invalid_value:` 중복, 빠진 "The result was not kept" 줄), 4.3의 "`--include`가 없으면 공통 속성이 빠진다"는 표 출력에서 사실이 아니어서(표에는 나오고 `--json`의 `properties`에만 없다) 고쳤다.

## 이유

- **조용히 틀리지 않는다.** 칸 하나의 실수가 행을 지우고 링크를 줄줄이 끊으면 사용자는 링크 문제를 고치다가 원인(상태 값 하나)을 놓친다. 문제는 하나로 보고되고 나머지는 맞게 만들어져야 한다.
- **한 실수가 번지지 않는다.** 필터의 오타 하나, 한쪽 피드의 `key_name` 하나, 70만 행 파일 하나가 객체 전체를 닫거나 프로세스를 죽이면 안 된다. 사라진 행에 이미 있는 기다림의 규칙은 걸러진 행에도 같은 이유로 맞는다.
- 사라진 행과 걸러진 행을 같은 규칙에 두면 설명이 하나다. 두 번째 규칙을 만들지 않았다.

## 대안과 기각 사유

- **틀린 값을 그대로 저장하고 `unknown` 등급으로 표시하기.** 그래프가 타입에 맞지 않는 값을 받지 않는다. 비우는 편이 "모르는 것을 가정으로 채우지 않는다"(파이프라인 설계 3.2)와 맞다.
- **걸러진 행을 새 규칙(예: 7일)으로 닫기.** 사라진 행과 규칙이 둘이 된다. 같은 N과 T를 쓰고 필요하면 한 곳에서 조정한다.
- **걸러진 행의 객체를 먹이지 않고 닫기만 늦추기.** 객체는 남지만 링크는 `st.Links`에서 빠져 바로 닫힌다. 행을 그대로 먹여야 링크도 사라진 행처럼 유지된다.
- **행 수 한도를 크기 한도(20MB)에만 맡기기.** 열이 적은 큰 파일은 20MB 안에 수십만 행이 들어간다. 행 수와 메모리가 비례하므로 행 수에 한도를 둔다.
- **`key_name`을 필수로 만들어 두 피드가 맞추게 하기.** 사용자가 맞춰야 하는 규칙이 하나 더 생기고, 틀리면 조용히 다른 객체가 된다. 값으로 알아보는 편이 틀릴 곳이 없다.

## 결과

- **알파 2의 데이터 폴더는 다시 수집한다.** 수집 상태 파일의 식별 색인 서명이 바뀌고 걸러진 행의 횟수(`filtered`)가 상태에 늘었다. 호환을 요구하지 않는다(알파 단계). 옛 폴더를 그대로 쓰면 옛 서명이 쓰이지 않을 뿐 객체 ID는 같아 같은 객체로 다시 만들어진다. 상태 파일의 버전은 올리지 않았다.
- 객체 ID와 `graph_hash`는 달라지지 않는다(저장되는 키에 이름이 없고, 예제와 합격 테스트에 `approximate`가 없다). 잠긴 테스트의 고정 해시는 바꾸지 않았다.
- 바꾼 잠긴 테스트는 하나다. `TestBadRowsAreQuarantined`는 틀린 칸의 행의 객체가 없어야 한다고 단언했고, 이제 그 객체가 있어야 한다고 단언한다(문제 수는 그대로 1).
- 알려진 한계. 걸러진 행의 기다림은 이미 객체가 있는 행에만 적용한다. 정제가 컬럼 값을 바꿔 식별 키가 달라진 행은 새 키의 객체가 없으므로 기다리지 않고 옛 키의 객체는 사라진 행처럼 닫힌다.
- 알려진 한계. 기다리는 동안 걸러진 행의 새 값이 객체에 반영된다. 규칙이 행을 걸러낸 이유(예: 상태가 제외로 바뀜)가 값에 있으면 기다림이 끝날 때까지 그 값이 객체에 들어간다.
- 알려진 한계. 행 수 한도의 기본값(20만)에서도 메모리는 큰 편이다(아래 표). 한도를 올리기 전에 메모리를 본다.

**메모리 측정**(컬럼 10개의 합성 CSV, 한 행에 객체 하나, `praxium ingest run`을 `-data-dir` 없이 실행. 개발 기계, 최대 상주 메모리는 `getrusage`의 `ru_maxrss`로 쟀다. `/usr/bin/time`이 없는 기계라서 `-v`의 Maximum resident set size와 같은 값을 파이썬에서 쟀다):

| 행 수 | 파일 크기 | 최대 메모리 | 시간 |
|---|---|---|---|
| 50,000 | 4.1MB | 586MB | 5.2초 |
| 100,000 | 8.3MB | 1,178MB | 11.3초 |
| 200,000 | 16.9MB | 2,637MB | 29.4초 |

행 수에 거의 비례한다(행당 약 13KB). 그보다 큰 파일은 돌리지 않았다.

**기본값을 20만으로 둔 이유.** 엑셀의 시트 한도(`max_rows_per_sheet`)와 같게 두어, 같은 데이터를 엑셀로 올리든 CSV로 올리든 한도가 같다. 위 표처럼 20만 행은 메모리를 2.6GB가량 쓰므로 놀랄 수 있다. 그래서 가이드(2.7)에 이 표와 "메모리가 모자라면 `limits.max_rows_per_dataset`을 낮추거나 파일을 나눈다"를 적었다. 읽은 행을 메모리에 쌓지 않고 흘려 보내 메모리를 줄이는 일은 이 변경의 범위가 아니고 다음 일이다.

새 서드파티 의존성이 없다. `harness/config`의 규칙, 한도, 허용 목록은 바꾸지 않았다. 바뀐 보호 경로는 요구사항 표(REQ-358~365 추가)와 잠긴 테스트(`test-lock.json`: 바꾼 테스트 하나의 해시와 새 테스트의 잠금)다.
