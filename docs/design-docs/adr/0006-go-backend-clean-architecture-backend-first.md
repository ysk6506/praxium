# ADR-0006 백엔드는 Go, 용도에 맞는 언어와 스토리지 — 클린 아키텍처, 역할 4종, 알파는 백엔드부터

## 맥락
제품 책임자는 언어를 TypeScript로 고정하지 않았다. 요구사항을 분석해 정하고, 클린 아키텍처를 적용하고, 백엔드를 제품 수준으로 만들며 화면은 기능을 테스트할 만큼만 만들라고 했다. 이후 스트리밍이 차별점으로 추가되었다. 소스마다 배치와 스트리밍을 고르고, 둘을 백엔드에서 한 정의로 잘 처리하는 것이다. 제품 책임자는 이후 이 프로젝트에 꼭 한 언어나 한 제품(DB, 스트림 처리)을 써야 한다는 제약은 없다고 밝혔다. 스트리밍 때문에 제품의 비중이 장시간 실행되고 메모리를 많이 쓰는 데이터 처리 쪽으로 옮겨 갔고, 언어와 스토리지의 선택을 다시 열었다. 또 화면을 다른 리포지토리로 분리하기로 해서([ADR-0016](0016-frontend-separate-rest-api-contract.md)) 이 리포지토리는 백엔드다. 아래의 "화면"은 그 다른 리포지토리를 말한다.

이 결정은 [테라리움에서 넘겨받은 것](../../references/from-terrarium.md) 6절의 가~아에 직접 답하는 것이 아니다. 쟁점 바(멈추면 안 되는 것)에는 역할을 분리하는 구조로 뒷받침한다. 무엇을 멈추면 안 되는 것으로 둘지는 ADR-0011이 정한다.

## 결정
1. **원칙은 "하나만 쓴다"가 아니라 "용도에 맞는 것을 쓴다"다.** 지킬 것은 둘뿐이다. **단일 진실 공급원은 하나**다. 같은 사실이 두 스토리지에서 따로 수정되지 않고, 나머지는 거기서 파생한 것이라 다시 만들 수 있다. **의미의 구현은 하나**다. 정제·매핑·식별·링크·영향 범위의 의미는 각각 한 곳에서만 구현된다. 새 언어나 제품을 도입할 때는 결정 기록에 이유, 라이선스(허용 목록), 정본인지 파생한 것인지, 없을 때의 폴백 방법을 적는다.
2. **언어.** 백엔드의 중심(정의, 실행기, API)은 Go, 구조 검사(하네스)는 TypeScript 도구다. 화면은 다른 리포지토리에서 TypeScript로 만든다(ADR-0016). 질의 엔진도 Go로 직접 구현한다(확정). 같은 엔진을 Go와 Rust로 작성해 노드와 엣지 100만, 1천만, 3천만, 1억 개에서 나란히 측정했더니 답이 같았고 Rust는 질의와 구축이 10~30% 빨랐을 뿐이며, Go는 질의 중 GC가 발생하지 않았고(포인터 없는 배열) 가장 긴 정지가 1ms 미만이었다(가정: 합성 그래프, 2코어 8GB, 각 1회 실행). 한계는 언어가 아니라 재구축과 병합 순간의 메모리였다(평소의 약 2.4배. 청크 단위로 병합해서 해소한다). 한 언어로 가는 이득(도구와 검사 한 벌, 같은 프로세스 안의 경계)이 더 크고, 운영 중에 언어를 바꿔 다시 작성하는 위험을 지지 않으려고 지금 정한다. 프로젝션 파일과 변경 시퀀스는 엔진의 경계로 남는다(ADR-0010). 기존 그래프 엔진은 쓰지 않는다. 수집 엔벨로프의 클라이언트 라이브러리는 여러 언어(우선 Go, Python, TypeScript)로 제공한다. 소스 담당자가 익숙한 언어로 수집기를 만들게 하려는 것이다. 정의·실행기·API를 TypeScript와 Go로 나누지는 않는다. 근거는 둘로 나눈다.
   - **측정으로 확인한 것.** 작은 프로토타입으로 측정했다. 코어 2개, 메모리 약 8GB의 머신 한 대, 합성 데이터, 스토리지 I/O 없음.
     - 변경 하나를 처리하는 속도(JSON 파싱, 정제 5개, 키 정규화, 상태 조회, SHA-256)는 언어 간 차이를 만들지 못했다. 200만 건에서 한 스레드로 Node 22가 초당 21만~22만 건, Go 표준 JSON이 19만 건이었다. 직접 구현한 파서를 쓴 Go는 48만 건이었지만 이스케이프를 지원하지 않아 쓸 수 없다.
     - 메모리 안의 그래프(객체 502만, 링크 2,090만, 이중화 그룹 약 50만)에서 영향 범위 한 번은 한 스레드로 두 언어 모두 p99가 6.1밀리초 이내였다. 추가분 10만 개를 적용한 뒤에도 같은 자릿수였다. 그래프도 언어 간 차이를 만들지 못했다.
     - **차이를 만든 것은 키별 상태다.** 문자열 키 1천만 개를 한 프로세스의 맵에 두면 Node는 가비지 컬렉션이 최대 706밀리초 정지했고 최대 메모리가 1,782MB였다. Go는 최대 0.23밀리초, 824MB였다. Node의 맵은 항목 16,777,216개에서 실패했다. 변경 단위의 실행기(조인, 중복 행 제거, 식별)는 이런 상태를 많이 보유한다.
   - **이 수치에 포함되지 않은 것.** 엔진 프로토타입에는 3값(알 수 없음 포함), 2가지 응답(사실만과 가정 포함), 연결성과 의존의 교대 실행(`connected_to`는 "대상에 장애가 나면 `degraded`"일 뿐이다), 채널 6종의 동시 상태(원인 채널 하나만), 링크별 근거와 관측 시각, 객체 ID와 내부 번호의 대응, `scope_keys`, 속성 필터링, 과거 버전, 읽기와 쓰기의 동시 실행, I/O가 없다. 노드와 엣지 하나에 약 12바이트라는 값은 구조만의 값이라 이것들이 들어오면 메모리는 몇 배가 되고 배수는 측정해야 안다. 스위치의 영향 범위 "1초"는 바로 그 연결성 계산을 측정하지 않아서 아직 근거가 없는 목표다. 목록과 이유는 [질의 엔진의 언어와 구조](../query-engine-shape.md)에 있다. 언어를 고른 결론은 이것들에 의존하지 않는다(병목이 메모리 접근이라는 측정은 구조가 달라져도 성립한다).
   - **측정하지 않고 판단한 것.**
     - 이어서 수집하는 소스의 클라이언트 생태계의 중심이 Go다(쿠버네티스의 watch, 가상화 관리 API, 네트워크 장비의 스트리밍 텔레메트리, 메시지 로그 스토리지). 차별점이 스트림인 제품에서 이 점의 비중이 크다.
     - 정제·매핑·식별·링크 의미는 한 구현에만 있어야 한다. 드라이 런, 미리보기, 정의의 검사가 같은 실행기를 쓴다. 백엔드를 TypeScript(정의, API)와 Go(실행기)로 나누면 TypeScript에는 껍데기만 남고 구조 검사가 둘로 갈라진다. 그래서 그 방안은 버린다. 이유는 언어가 둘이어서가 아니라 의미의 구현이 둘이 되기 때문이다.
     - 실행 파일 하나로 배포되어 인터넷에 연결되지 않은 환경에 옮기기 쉽다. 에이전트용 MCP의 공식 SDK가 Go에도 있다.
     - 코딩 에이전트가 어느 언어를 더 잘 유지보수하는지는 증거가 약해 근거로 쓰지 않는다.
3. **감수하는 비용.**
   - 구조 검사(하네스)의 30% 정도가 TypeScript 컴파일러에 종속되어 있다. Go용 검사(의존 방향, 공개 인터페이스, 복잡도와 크기, 테스트 잠금과 커버리지, 라이선스, 검사 무시 주석)를 만든다. 하네스 자체는 TypeScript 도구로 남고 Go 코드를 읽는 모듈을 추가한다. 첫 Go 제품 코드가 들어가는 변경에서 함께 한다(부채 TD-0005). 그 전에는 Go 제품 코드를 병합하지 않는다.
   - 지금의 `core.kernel`(TypeScript, 300줄쯤)은 화면 쪽의 공통 기반 코드(한국어 조사, 시간 표기)이므로 프런트엔드 리포지토리가 생기면 그쪽으로 옮긴다(부채 TD-0006). 그때까지 이 리포지토리에 남고 새 코드가 의존하지 않는다. 백엔드는 자기 공통 기반 코드(ID, 오류, 시계와 난수의 주입, 해시)를 Go로 가진다. REQ-001은 백엔드에 적용된다.
   - 화면과 백엔드가 계약을 코드로 함께 쓰지 못한다. 계약은 이 리포지토리가 소유하고 개방형 형식(OpenAPI, JSON Schema)으로 공개한다. 프런트엔드 리포지토리가 그것에서 클라이언트를 생성해 쓴다. 서버가 계약에 맞는지는 이 리포지토리의 검사가 확인한다(ADR-0016).
4. **클린 아키텍처는 Go의 관례로 지킨다.** 단위는 패키지 하나이고, 다른 단위는 그 패키지의 공개 인터페이스로만 접근한다. 단위마다 무엇을 import해도 되는지와 어떤 외부 모듈을 쓰는지를 구조 계약에 적고 검사가 강제한다. 포트는 사용하는 쪽 코어 단위에 두고 어댑터는 바깥 층에 둔다. 조립은 시작점 한 곳에서만 한다. 코어는 운영체제와 네트워크를 모르고 시계와 난수를 주입받는다.
5. **단위의 방향은 아래와 같다.** 코드가 생기는 변경에서 구조 계약에 등록한다.

   ```
   core.kernel
     └─ core.model        타입 등록부, 링크 의미, 근거 등급, 식별 키, 표준 모델
          ├─ core.definitions  정의의 저장, 브랜치, 제안, 병합 (ADR-0014)
          ├─ core.ingest       소스 설정, 프리셋, 원본 레코드, 정제, 매핑, 식별, 링크 정의 (어댑터 포트)
          ├─ core.graph        KG 버전, 후보와 차이, 적용과 안전장치 (스토리지 포트)
          │    └─ core.query       사전 정의 질의, 영향 범위의 의미와 기준 구현 (엔진 포트, 프로젝션 형식)
          ├─ core.observe      품질, 헬스 상태, 목표, 알림 (ADR-0013)
          ├─ core.competency   역량 질문과 충족률 (ADR-0015)
          └─ core.schedule     동기화 실행과 일정
   core.access     SSO와 권한 부여, 감사 (kernel과 model만 import한다. 다른 단위가 이것을 import한다)
   core.contract   외부에 공개하는 계약: HTTP 경로와 스키마, MCP 툴의 스키마, 파일 형식
   바깥 층         어댑터들 / HTTP / MCP / 조립(역할을 골라 기동하는 시작점)
   ```
   화면 단위는 없다. 화면은 다른 리포지토리에서 계약(OpenAPI)으로만 통신한다(ADR-0016). 엔드투엔드(E2E) 프로세스의 단위는 그 일을 구체화할 때 더한다.
6. **서버는 역할 4종으로 기동한다.** 실행 파일 하나가 역할을 선택해 기동한다. **API**(계약의 경로와 MCP. 상태를 보유하지 않고 복수 인스턴스) / **워커**(수집부터 적용까지와 일정. 소스별 동시 실행 상한을 지키며 복수 인스턴스) / **질의 엔진**(프로젝션을 메모리에 올려 영향 범위와 경로를 응답한다. 복수 인스턴스) / **수집기**(워커의 수집 역할을 소스가 있는 망에 별도로 기동한 것). 개발과 알파에서는 한 프로세스에 함께 기동할 수 있다. 질의의 부하와 수집의 부하를 따로 확장하고, 스토리지가 중단돼도 질의 엔진이 메모리에 올려 둔 프로젝션으로 계속 응답하려는 것이다. 이 경계는 엔진을 따로 테스트하고 따로 확장하려는 것이고 언어를 바꾸려는 것이 아니다(2번). 엔진은 프로젝션 파일과 변경 시퀀스(경량 변경 레코드 포함)만 읽는다.
7. **알파의 범위.** 백엔드의 모든 기능은 화면 없이 쓸 수 있도록 계약(REST API)을 먼저 완성하고 제품 수준으로 만든다. 이 리포지토리의 알파 기준은 "모든 기능이 API와 CLI로 된다"이다(ADR-0016). 알파의 화면(기능을 테스트하는 얇은 층)과 클로즈드 베타의 UX·UI 설계는 프런트엔드 리포지토리의 일이다. UX 측정 하네스(TD-0002)도 클로즈드 베타로 옮긴다. 알파는 객체와 링크 100만 개 수준에서 모든 기능이 동작한다. 이 규모에서는 PostgreSQL 하나와 실행 파일 하나(역할 4종을 한 프로세스에)로 충분하다. 수천만 개 규모의 측정은 클로즈드 베타에서 한다. 규모 요구는 한 KG에 수천만 개이고 설계 여유는 수억 개까지다(REQ-134). 엔진은 노드와 엣지 합계 1억 개까지 측정했고 그 이상은 추정이다. 구조는 처음부터 수천만 개를 전제로 구축하고, 알파에서 줄이는 것은 어댑터의 수와 배포 형태다.
8. **저장되는 해시.** 자주 실행되는 경로(객체와 링크의 내용 해시)는 프락시움이 정한 정규 바이너리 인코딩 기반의 UTF-8 SHA-256을 쓴다. 정규 JSON(RFC 8785)은 내보내는 파일에만 쓴다. RFC 8785는 2^53을 넘는 정수와 키 정렬(UTF-16 단위)에서 언어마다 결과가 달라질 수 있다. 이 문제는 TD-0004로 등록한다.
9. **스토리지.** 정본은 PostgreSQL에 둔다. 정의, 최근 원본 레코드, KG의 live와 hist, 변경 로그, 자주 바뀌는 값의 현재 값, 실행기의 키 상태, 소스 커서(소스에서 어디까지 읽었는지), 지표다. 5가지는 포트 뒤에 둔다: 변경 로그 / 원본 레코드의 보관 / 외부로 내보내는 변경 알림 / 실행기의 상태 / 프로젝션으로 전달하는 변경.
   - **내부 변경 로그**(수신한 변경을 적용 전에 쌓는 곳, 외부로 내보내는 변경 알림)는 어댑터 2개를 모두 정식으로 만든다. PostgreSQL(작은 배포와 알파)과 메시지 로그 스토리지(조직이 이미 운영하는 경우가 많은 것. 라이선스가 허용 목록에 포함되는 것)다. 메시지 로그 스토리지 어댑터는 클로즈드 베타에서 추가한다. 알파에서는 메시지 토픽을 이어서 수집하는 소스로 먼저 만든다. 스트림이 차별점이라 어댑터를 어느 규약에 맞추는지를 정하고(Kafka 규약, 특정 배포판에 종속되지 않는다), 시기와 값은 [기본값 표](../defaults.md)에 있다.
   - **오래된 데이터**(원본 레코드의 오래된 구간, 과거 이력, 지표의 오래된 값)는 개방형 형식의 파일(컬럼형)로 오브젝트 스토리지에 아카이브할 수 있다(포트). PostgreSQL에는 핫 데이터만 둔다. 재실행(replay)과 감사는 아카이브한 데이터로도 할 수 있다.
   - **분석용 스토리지**(컬럼형)는 지표, 사용 이력, 컬럼 통계를 PostgreSQL로 감당할 수 없을 때 둔다. 파생한 것이다.
   - 어느 제품을 고를지는 구현하는 변경의 결정 기록에서 비교 검토해 정한다. 지금 정하는 것은 포트와 단일 진실 공급원이다.
   - 프로토타입(PostgreSQL 16, 연결 1개, 같은 머신, 복제 없음)에서 변경 배치를 적용하는 속도는 배치 1천 행에서 초당 약 7.5만 행, 10만 행에서 약 13만 행이었다. 모든 행이 바뀌는 최악이다. 지속되는 변경이 초당 2만~3만 행(논리 변경 수. 물리 행 수와 WAL 바이트를 따로 측정하고 셋을 함께 본다)을 넘으면(추정) 먼저 쓰기 감소 조치를 하고 그래도 안 되면 메시지 로그 스토리지 어댑터를 쓴다. KG 분할은 쓰기 한계를 해소하는 수단이 아니다. 영향 범위가 KG 하나 안에서만 계산되기 때문이다.
   - 지킬 것(측정으로 확인한 것): 자주 바뀌는 값의 테이블에는 보조 인덱스를 두지 않는다. 두면 제자리 갱신(in-place update)이 안 되고 속도가 절반 정도로 떨어졌다. 변경 번호는 KG마다 쓰기 주체를 하나로 두어 부여한다. 번호의 순서와 반영의 순서가 어긋나지 않게 하려는 것이다.
   - 소스 커서와 그 적용을 한 트랜잭션에 묶고 번호로 중복을 막아 "정확히 한 번(exactly-once)"을 구현한다. 시계도 이벤트로 로그에 넣어 재실행해도 같은 결과가 나오게 한다.
10. **재검토 조건.** 위 9번의 지속 변경 속도를 넘으면 먼저 쓰기 감소 조치를 하고, 그래도 안 될 때 이벤트 로그를 메시지 로그 스토리지 어댑터로 옮긴다. 서로 의존하지 않는 자산 그룹(따로 운영되는 환경)만 다른 KG가 될 수 있고, KG를 스토리지 사이에서 옮기는 데는 `kg_id` 라우팅 계층을 쓴다. 메시지 로그 스토리지는 프락시움이 직접 기동하거나 운영하지 않는다. 어댑터는 조직이 이미 운영하는 것에 연결하고, 그런 것이 없는 배포는 PostgreSQL 어댑터를 쓴다. 그 스토리지의 고가용 구성과 관리는 제품의 범위 밖이고, 제품은 연결하는 데 필요한 조건(토픽, 보관, 권한, 복제의 최소)을 문서로 제공한다([스토리지 운영](../postgres-operations.md)). 질의 엔진의 언어는 재검토 조건이 아니라 확정이다(2번).

## 이유
- 제품의 차별점은 배치와 스트림을 한 정의로 실행하는 백엔드다. 프로토타입에서 속도는 언어 간 차이를 만들지 못했고, 큰 상태를 오래 보유하는 일과 소스 생태계에서 차이가 났다. 후자는 이 제품이 가장 많이 하는 일이다.
- 지금은 제품 코드가 300줄쯤이라 언어를 바꾸는 비용이 가장 낮다.
- 계약을 개방형 형식으로 공개하고 프로젝션 파일로 엔진을 분리하면 엔진의 경계가 분명하다. 언어를 바꿀 일은 없다(2번).
- **알려진 한계.** 프로토타입은 합성 데이터이고 스토리지 I/O가 없다(엔진 프로토타입에서 빠진 것은 결정 2번). 정의의 연산 14개, 조인 인덱스, 근거 등급, 건수 대조가 들어 있지 않다. 그래프는 단순한 임계값 개수 세기이고 연결성(ECMP, BGP, LACP) 계산이 없으며 동시 질의를 측정하지 않았다. PostgreSQL은 연결 1개로만 측정했다. 그래서 "Go가 몇 배 빠르다"로 해석하지 않는다. 증거의 강도는 중간이다.

## 버린 대안
- **언어 하나로 고정하기**: 제약이 없으므로 용도에 맞게 쓴다. 다만 의미의 구현은 하나로 둔다.
- **TypeScript 하나(차선)**: 키 상태를 전부 스토리지에 두면 되지만 스트림 소스의 클라이언트를 직접 만들어야 하고, 큰 상태에서 정지가 길다.
- **정의, 권한, API는 TypeScript이고 실행기와 질의 엔진은 Go**: 정제와 매핑의 의미가 한 구현에만 있어야 하는데 경계가 그 한가운데를 지난다. 구조 검사도 둘로 갈린다.
- **Rust로 전부**: 얻는 것에 비해 개발 속도와 소스 클라이언트 면에서 잃는다.
- **질의 엔진만 Rust로**: 측정에서 10~30% 빨랐을 뿐이고 도구와 검사 한 벌과 한 프로세스 안의 경계를 잃는다.
- **스트림 처리 엔진을 도입해 실행기를 대체하기**: 제품이 하나 더 늘어서가 아니다. 의미의 구현이 둘이 되고 수집한 순서대로의 결정성과 "드라이 런도 같은 실행기"를 지키기 어렵기 때문이다. 배포도 무겁다.
