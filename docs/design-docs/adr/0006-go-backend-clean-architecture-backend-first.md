# ADR-0006 백엔드는 Go, 자리에 맞는 언어와 저장소 — 클린 아키텍처, 역할 넷, 알파는 백엔드부터

## 맥락
제품 책임자는 언어를 TypeScript로 못 박지 않았다. 요구사항을 분석해 정하고, 클린 아키텍처를 적용하고, 백엔드를 제품 수준으로 만들며 화면은 기능을 테스트할 만큼만 만들라고 했다. 뒤에 스트리밍이 차별점으로 더해졌다. 소스마다 배치와 스트리밍을 고르고, 둘을 백엔드에서 한 정의로 잘 처리하는 것이다. 제품 책임자는 뒤에 이 프로젝트에 꼭 한 언어나 한 제품(DB, 흐름 처리)을 써야 한다는 제약은 없다고 밝혔다. 스트리밍 때문에 제품의 무게가 오래 돌고 메모리를 많이 쓰는 데이터 쪽 일로 옮겨 갔고, 언어와 저장소의 선택을 다시 열었다. 또 화면을 다른 저장소로 나누기로 해서([ADR-0016](0016-frontend-separate-rest-api-contract.md)) 이 저장소는 백엔드다. 아래의 "화면"은 그 다른 저장소를 말한다.

이 결정은 [테라리움에서 넘겨받은 것](../../references/from-terrarium.md) 6절의 가~아에 직접 답하는 것이 아니다. 쟁점 바(멈추면 안 되는 것)에는 역할을 나누는 구조로 거든다. 무엇을 멈추면 안 되는 것으로 둘지는 ADR-0011이 정한다.

## 결정
1. **원칙은 "하나만 쓴다"가 아니라 "자리에 맞는 것을 쓴다"다.** 지킬 것은 둘뿐이다. **단일 진실 공급원은 하나**다. 같은 사실이 두 저장소에서 따로 고쳐지지 않고, 나머지는 거기서 끌어낸 것이라 다시 만들 수 있다. **뜻의 구현은 하나**다. 정제·매핑·식별·링크·영향 범위의 뜻은 각각 한 곳에서만 구현된다. 새 언어나 제품을 들일 때는 결정 기록에 이유, 라이선스(허용 목록), 진실인지 끌어낸 것인지, 없을 때 물러나는 길을 적는다.
2. **언어.** 백엔드의 중심(정의, 실행기, API)은 Go, 구조 검사(하네스)는 TypeScript 도구다. 화면은 다른 저장소에서 TypeScript로 만든다(ADR-0016). 질의 엔진도 Go로 직접 만든다(확정). 같은 엔진을 Go와 Rust로 짜서 노드와 엣지 100만, 1천만, 3천만, 1억 개에서 나란히 측정했더니 답이 같았고 Rust는 질의와 짓기가 10~30% 빨랐을 뿐이며, Go는 질의 중 GC가 돌지 않았고(포인터 없는 배열) 가장 긴 멈춤이 1ms 아래였다(가정: 지어낸 모양, 2코어 8GB, 한 번씩 돌림). 한계는 언어가 아니라 다시 짓기와 합치기의 순간 메모리였다(평소의 약 2.4배. 조각마다 합쳐서 푼다). 한 언어로 가는 이득(도구와 검사 한 벌, 같은 프로세스 안의 경계)이 더 크고, 운영 중에 언어를 바꿔 다시 쓰는 위험을 지지 않으려고 지금 정한다. 프로젝션 파일과 변경 시퀀스는 엔진의 경계로 남는다(ADR-0010). 기성 그래프 엔진은 쓰지 않는다. 수집 엔벨로프의 클라이언트 라이브러리는 여러 언어(Go, Python, TypeScript부터)로 낸다. 소스의 담당자가 익숙한 언어로 수집기를 만들게 하려는 것이다. 정의·실행기·API를 TypeScript와 Go로 가르지는 않는다. 근거를 둘로 가른다.
   - **측정해서 안 것.** 작은 프로토타입으로 측정했다. 코어 둘, 메모리 약 8GB의 기계 한 대, 합성 데이터, 저장소 입출력 없음.
     - 변경 하나를 처리하는 속도(JSON 해석, 정제 다섯 개, 키 다듬기, 상태 조회, SHA-256)는 언어를 가르지 못했다. 200만 건에서 한 스레드로 Node 22가 초당 21만~22만 건, Go 표준 JSON이 19만 건이었다. 손으로 짠 파서를 쓴 Go는 48만 건이었지만 이스케이프를 지원하지 않아 쓸 수 없다.
     - 메모리 안의 그래프(객체 502만, 링크 2,090만, 이중화 그룹 약 50만)에서 영향 범위 한 번은 한 스레드로 두 언어 모두 p99가 6.1밀리초 안이었다. 덧붙임 10만 개를 얹은 뒤에도 같은 자릿수였다. 그래프도 언어를 가르지 못했다.
     - **가른 것은 키마다의 상태다.** 문자열 키 1천만 개를 한 프로세스의 맵에 두면 Node는 가비지 수집이 최대 706밀리초 멈췄고 최대 메모리가 1,782MB였다. Go는 최대 0.23밀리초, 824MB였다. Node의 맵은 항목 16,777,216개에서 실패했다. 변경 단위의 실행기(조인, 겹친 행 없애기, 식별)는 이런 상태를 많이 쥔다.
   - **이 수에 들지 않은 것.** 엔진 프로토타입에는 세 값(알 수 없음), 두 답(사실만과 가정 포함), 이어짐의 번갈아 돌리기(`connected_to`는 "대상이 죽으면 `degraded`"일 뿐이다), 채널 여섯의 동시 상태(원인 채널 하나만), 링크마다의 근거와 본 때, 객체 ID와 내부 번호의 대응, `scope_keys`, 속성 필터링, 과거 버전, 읽기와 쓰기의 동시, 입출력이 없다. 노드와 엣지 하나에 약 12바이트라는 값은 구조만의 값이라 이것들이 들어오면 메모리는 몇 배가 되고 배수는 재야 안다. 스위치의 영향 범위 "1초"는 바로 그 이어짐 계산을 측정하지 않아서 아직 근거가 없는 목표다. 목록과 이유는 [엔진의 모양](../query-engine-shape.md)에 있다. 언어를 고른 결론은 이것들에 기대지 않는다(병목이 메모리 접근이라는 측정은 모양이 달라져도 선다).
   - **측정하지 않고 판단한 것.**
     - 이어서 받는 소스의 클라이언트 생태계의 본고장이 Go다(쿠버네티스의 지켜보기, 가상화 관리 API, 네트워크 장비의 스트리밍 텔레메트리, 메시지 기록 저장소). 차별점이 흐름인 제품에서 이것이 무겁다.
     - 정제·매핑·식별·링크 의미는 한 구현에만 있어야 한다. 드라이 런, 미리보기, 정의의 검사가 같은 실행기를 쓴다. 백엔드를 TypeScript(정의, API)와 Go(실행기)로 가르면 TypeScript에는 껍데기만 남고 구조 검사가 둘로 갈린다. 그래서 그 길은 버린다. 이유는 언어가 둘이어서가 아니라 뜻의 구현이 둘이 되기 때문이다.
     - 실행 파일 하나로 배포되어 인터넷이 닿지 않는 환경에 옮기기 쉽다. 에이전트용 MCP의 공식 SDK가 Go에도 있다.
     - 코딩 에이전트가 어느 언어를 더 잘 유지보수하는지는 증거가 약해 근거로 쓰지 않는다.
3. **치르는 값.**
   - 구조 검사(하네스)의 30%쯤이 TypeScript 컴파일러에 묶여 있다. Go용 검사(의존 방향, 공개 면, 복잡도와 크기, 테스트 잠금과 커버리지, 라이선스, 검사 무시 주석)를 만든다. 하네스 자체는 TypeScript 도구로 남고 Go 코드를 읽는 조각을 더한다. 첫 Go 제품 코드가 들어가는 변경에서 함께 한다(부채 TD-0005). 그 전에는 Go 제품 코드를 합치지 않는다.
   - 지금의 `core.kernel`(TypeScript, 300줄쯤)은 화면 쪽의 공통 기반 코드(한국어 조사, 시간 표기)이라 프런트엔드 저장소가 서면 그쪽으로 옮긴다(부채 TD-0006). 그때까지 이 저장소에 남고 새 코드가 기대지 않는다. 백엔드는 자기 공통 기반 코드(ID, 오류, 시계와 난수의 주입, 해시)을 Go로 갖는다. REQ-001은 백엔드에 선다.
   - 화면과 백엔드가 계약을 코드로 함께 쓰지 못한다. 계약은 이 저장소가 쥐고 열린 형식(OpenAPI, JSON Schema)으로 낸다. 프런트엔드 저장소가 그것에서 클라이언트를 만들어 쓴다. 서버가 계약에 맞는지는 이 저장소의 검사가 본다(ADR-0016).
4. **클린 아키텍처는 Go의 관례로 지킨다.** 단위는 패키지 하나이고, 다른 단위는 그 패키지의 공개 면으로만 닿는다. 단위마다 무엇을 import해도 되는지와 어떤 바깥 모듈을 쓰는지를 구조 계약에 적고 검사가 강제한다. 포트는 쓰는 쪽 코어 단위에 두고 어댑터는 바깥 층에 둔다. 조립은 시작점 한 곳에서만 한다. 코어는 운영체제와 네트워크를 모르고 시계와 난수를 주입받는다.
5. **단위의 방향은 아래와 같다.** 코드가 생기는 변경에서 구조 계약에 등록한다.

   ```
   core.kernel
     └─ core.model        타입 등록부, 링크의 뜻, 근거 등급, 식별 키, 표준 모델
          ├─ core.definitions  정의의 저장, 브랜치, 제안, 병합 (ADR-0014)
          ├─ core.ingest       소스 설정, 프리셋, 원본 기록, 정제, 매핑, 식별, 링크 정의 (어댑터 포트)
          ├─ core.graph        KG 버전, 후보와 차이, 적용과 안전장치 (저장소 포트)
          │    └─ core.query       닫힌 질의, 영향 범위의 뜻과 기준 구현 (엔진 포트, 투영 형식)
          ├─ core.observe      품질, 건강, 목표, 알림 (ADR-0013)
          ├─ core.competency   역량 질문과 충족률 (ADR-0015)
          └─ core.schedule     동기화 실행과 일정
   core.access     SSO와 권한 부여, 감사 (kernel과 model만 읽는다. 다른 단위가 이것을 읽는다)
   core.contract   밖으로 내는 모양: HTTP 길과 스키마, MCP 툴의 모양, 파일 형식
   바깥 층         어댑터들 / HTTP / MCP / 조립(역할을 골라 뜨는 시작점)
   ```
   화면 단위는 없다. 화면은 다른 저장소에서 계약(OpenAPI)으로만 대화한다(ADR-0016). E2E 프로세스의 단위는 그 일을 구체화할 때 더한다.
6. **서버는 역할 넷으로 뜬다.** 실행 파일 하나가 역할을 골라 뜬다. **API**(계약의 길과 MCP. 상태를 쥐지 않고 여러 벌) / **워커**(수집부터 적용까지와 일정. 소스마다의 동시 상한을 지키며 여러 벌) / **질의 엔진**(프로젝션을 메모리에 올려 영향 범위와 길을 답한다. 여러 벌) / **수집기**(워커의 수집 역할을 소스가 있는 망에 따로 띄운 것). 개발과 알파에서는 한 프로세스에 함께 띄울 수 있다. 질의의 부하와 수집의 부하를 따로 늘리고, 저장소가 멈춰도 질의 엔진이 올려 둔 프로젝션으로 답을 이어 가려는 것이다. 이 경계는 엔진을 따로 테스트하고 따로 늘리려는 것이고 언어를 바꾸려는 것이 아니다(2번). 엔진은 프로젝션 파일과 변경 시퀀스(경량 변경 레코드 포함)만 읽는다.
7. **알파의 범위.** 백엔드의 모든 기능은 화면 없이 쓸 수 있도록 계약(REST API)을 먼저 완성하고 제품 수준으로 만든다. 이 저장소의 알파 기준은 "모든 기능이 API와 CLI로 된다"이다(ADR-0016). 알파의 화면(기능을 테스트하는 얇은 층)과 클로즈드 베타의 UX·UI 설계는 프런트엔드 저장소의 일이다. UX 측정 하네스(TD-0002)도 클로즈드 베타로 옮긴다. 알파는 객체와 링크 100만 개 수준에서 모든 기능이 돈다. 이 규모에서는 PostgreSQL 하나와 실행 파일 하나(역할 넷을 한 프로세스에)로 충분하다. 수천만 개로 재는 일은 클로즈드 베타에서 한다. 규모의 요구는 한 KG에 수천만 개이고 설계의 여유는 수억까지다(REQ-134). 엔진은 노드와 엣지 합계 1억까지 측정했고 그 위는 추정이다. 구조는 처음부터 수천만 개를 보고 짓고, 알파에서 줄이는 것은 어댑터의 수와 배포의 모양이다.
8. **저장되는 해시.** 자주 도는 길(객체와 링크의 내용 해시)은 프락시움이 정한 정규 바이너리 인코딩 위의 UTF-8 SHA-256을 쓴다. 정규 JSON(RFC 8785)은 내보내는 파일에만 쓴다. RFC 8785는 2^53을 넘는 정수와 키 정렬(UTF-16 단위)에서 언어마다 어긋날 수 있다. 이 일은 TD-0004로 적는다.
9. **저장소.** 진실은 PostgreSQL에 둔다. 정의, 최근 원본 레코드, KG의 live와 hist, 변경의 기록, 자주 바뀌는 값의 지금 값, 실행기의 키 상태, 소스에서 어디까지 읽었는지, 지표다. 다섯은 포트 뒤에 둔다: 변경의 기록 / 원본 레코드의 보관 / 밖으로 내는 변경 알림 / 실행기의 상태 / 프로젝션으로 가는 변경.
   - **안쪽의 변경 기록**(받은 변경을 적용 전에 쌓는 곳, 밖으로 내는 변경 알림)은 어댑터 둘을 둘 다 정식으로 만든다. PostgreSQL(작은 배포와 알파)과 메시지 기록 저장소(조직이 이미 쓰고 있는 경우가 많은 것. 라이선스가 허용 목록에 드는 것)다. 메시지 기록 저장소 어댑터는 클로즈드 베타에서 더한다. 알파에서는 메시지 주제를 이어서 받는 소스로 먼저 만든다. 흐름이 차별점이라 어댑터를 어느 규약에 맞추는지를 정하고(Kafka 규약, 특정 배포판에 묶이지 않는다), 시기와 값은 [기본값 표](../defaults.md)에 있다.
   - **오래된 것**(원본 레코드의 오래된 구간, 지나간 이력, 지표의 오래된 값)은 열린 형식의 파일(열 단위)로 객체 저장소에 내려 둘 수 있다(포트). PostgreSQL에는 뜨거운 것만 둔다. 다시 돌리기와 감사는 내려 둔 것에서도 된다.
   - **분석용 저장소**(열 단위)는 지표, 쓰임 기록, 컬럼 통계가 PostgreSQL로 감당되지 않을 때 둔다. 끌어낸 것이다.
   - 어느 제품을 고를지는 구현하는 변경의 결정 기록에서 재고 견줘 정한다. 지금 정하는 것은 포트와 단일 진실 공급원다.
   - 프로토타입(PostgreSQL 16, 한 연결, 같은 기계, 복제 없음)에서 변경 배치를 적용하는 속도는 묶음 1천 행에서 초당 약 7.5만 행, 10만 행에서 약 13만 행이었다. 모든 행이 바뀌는 최악이다. 이어지는 변경이 초당 2만~3만 행(논리 변경 수. 물리 행 수와 WAL 바이트를 따로 재고 셋을 함께 본다)을 넘으면(추정) 먼저 쓰기를 줄이는 손질을 하고 그래도 안 되면 메시지 기록 저장소 어댑터를 쓴다. KG 나누기는 쓰기 한계를 푸는 수단이 아니다. 영향 범위가 KG 하나 안에서만 돌기 때문이다.
   - 지킬 것(측정해서 안 것): 자주 바뀌는 값의 표에는 보조 색인을 두지 않는다. 두면 제자리 갱신이 안 되고 속도가 절반쯤으로 떨어졌다. 변경의 번호는 KG마다 쓰는 쪽을 하나로 두어 매긴다. 번호의 순서와 반영의 순서가 어긋나지 않게 하려는 것이다.
   - 소스에서 소스 커서와 그 적용을 한 트랜잭션에 묶고 번호로 겹침을 막아 "정확히 한 번"을 만든다. 시계도 사건으로 기록에 넣어 다시 돌려도 같은 결과가 나오게 한다.
10. **다시 보는 조건.** 위 9번의 지속 변경 속도를 넘으면 먼저 쓰기를 줄이는 손질을 하고, 그래도 안 될 때 사건 기록을 메시지 기록 저장소 어댑터로 옮긴다. 서로 기대지 않는 자산 그룹(따로 운영되는 환경)만 다른 KG가 될 수 있고, KG를 저장소 사이에서 옮기는 데는 `kg_id` 길잡이 층을 쓴다. 메시지 기록 저장소는 프락시움이 직접 띄우거나 운영하지 않는다. 어댑터는 조직이 이미 운영하는 것에 붙고, 그런 것이 없는 배포는 PostgreSQL 어댑터로 간다. 그 저장소의 고가용 구성과 관리는 제품의 범위 밖이고, 제품은 붙는 데 필요한 조건(주제, 보관, 권한, 복제의 최소)을 문서로 낸다([저장소의 운영](../postgres-operations.md)). 질의 엔진의 언어는 다시 보는 조건이 아니라 확정이다(2번).

## 이유
- 제품의 차별점은 배치와 흐름을 한 정의로 돌리는 백엔드다. 프로토타입에서 속도는 언어를 가르지 못했고, 큰 상태를 오래 쥐는 일과 소스 생태계에서 갈렸다. 후자는 이 제품이 가장 많이 쓰는 일이다.
- 지금은 제품 코드가 300줄쯤이라 언어를 바꾸는 값이 가장 싸다.
- 계약을 열린 형식으로 내고 프로젝션 파일로 엔진을 가르면 엔진의 경계가 분명하다. 언어를 바꿀 일은 없다(2번).
- **알려진 한계.** 프로토타입은 합성 데이터이고 저장소 입출력이 없다(엔진 프로토타입의 빠진 것은 결정 2번). 정의의 연산 열네 개, 조인 색인, 근거 등급, 수 맞춤이 들어 있지 않다. 그래프는 단순한 임계값 세기이고 이어짐(ECMP, BGP, LACP) 계산이 없으며 동시 질의를 측정하지 않았다. PostgreSQL은 한 연결로만 측정했다. 그래서 "Go가 몇 배 빠르다"로 읽지 않는다. 증거의 강도는 중간이다.

## 버린 대안
- **언어 하나를 못 박기**: 제약이 없으므로 자리에 맞게 쓴다. 다만 뜻의 구현은 하나로 둔다.
- **TypeScript 하나(차점)**: 키 상태를 전부 저장소에 두면 되지만 흐름의 소스 클라이언트를 직접 만들어야 하고, 큰 상태에서 멈춤이 길다.
- **정의, 권한, API는 TypeScript이고 실행기와 질의 엔진은 Go**: 정제와 매핑의 뜻이 한 구현에만 있어야 하는데 경계가 그 한가운데를 지난다. 구조 검사도 둘로 갈린다.
- **Rust로 전부**: 얻는 것에 비해 만드는 속도와 소스 클라이언트에서 잃는다.
- **질의 엔진만 Rust로**: 측정에서 10~30% 빨랐을 뿐이고 도구와 검사 한 벌과 한 프로세스 안의 경계를 잃는다.
- **흐름 처리 엔진을 들여 실행기를 대신하기**: 제품이 하나 더 늘어서가 아니다. 뜻의 구현이 둘이 되고 받은 순서대로의 결정성과 "드라이 런도 같은 실행기"를 지키기 어렵기 때문이다. 배포도 무겁다.
