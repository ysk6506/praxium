# ADR-0097 HTTP 소스 어댑터의 보안 검토 반영

## 맥락

`adapter.httpsource`(ADR-0092)를 보안 관점에서 검토했다. 공격자는 소스 정의를 편집할 수 있는 사용자이거나 악의적인 API 서버이고, 지킬 것은 서버가 닿는 내부망, 서버 자신, 다른 사용자의 시크릿이다. 검토에서 다음이 확인됐다(재현 실험이 있다).

- 서버가 요청에서 받은 인증 값을 되돌려 주면(되돌려 주는 엔드포인트, 요청을 그대로 보여 주는 오류 응답) 그 값이 사건의 경로, 미리 보기의 교환 기록, 실행의 행에 그대로 나온다. 정의를 편집할 수 있는 사람이 자기가 읽을 수 없는 시크릿을 꺼내는 길이다. 가리기는 미리 보기의 행과 오류 글에만 걸려 있었고, 그것도 시크릿 값 그대로의 글만 가렸다.
- `X-HTTP-Method-Override` 같은 헤더로 POST를 다른 메서드로 읽게 할 수 있어 "GET과 POST만"(REQ-411)의 뜻을 우회한다.
- 응답 하나를 통째로 해석해서 크기 한도가 메모리 한도가 아니었다. 15 MiB의 빈 배열 본문이 힙을 1,333 MiB까지 올렸다(약 90배).
- 서버가 준 cursor를 레코드마다 토큰으로 복사해서, 1 MiB의 cursor와 레코드 2만 개가 22.9초를 썼다.
- `Retry-After`에 `9223372037`을 주면 곱셈이 넘쳐 음수가 되고 곧바로 다시 보냈다.

## 결정

1. **시크릿 값은 어댑터가 내보내는 모든 것에서 가린다.** 읽기마다 가릴 글의 집합을 만든다.
   - 값: 어댑터가 꺼낸 시크릿 값 각각(bearer와 header의 `token`, basic과 `token_request`의 `username`과 `password`), 보낸 인증 값(basic의 `base64(user:pass)`와 `Basic `이 붙은 값, `Bearer `나 정의의 `prefix`가 붙은 값, `send_prefix`가 붙은 받은 토큰), `token_request`로 받은 토큰.
   - 꼴: 각 값을 그대로, `url.QueryEscape`, `url.PathEscape`, 표준 base64(패딩 있음과 없음), URL용 base64(패딩 있음과 없음).
   - 4바이트보다 짧은 값은 넣지 않는다. 흔한 글자(세 글자 이하의 사용자 이름이나 비밀번호)를 넣으면 모든 글에서 그 글자가 사라져 아무것도 읽을 수 없게 된다. 이것은 짧은 시크릿이 가려지지 않는다는 뜻이고, 시크릿은 길게 만드는 것이 맞다.
   - 건 곳: 사건(`Event`)의 경로와 이유, 미리 보기의 교환 기록의 경로, 질의의 이름과 값, 헤더의 이름과 값, 오류의 글(이미 있었다), 이어 읽기 토큰, 그리고 **실행과 미리 보기의 행**. 행은 행을 만들기 전에 레코드의 글과 숫자를 깊이에 상관없이 가린다(자연 키가 시크릿으로 만들어지지 않게 한다). 숫자가 가릴 글을 담으면 그 값은 글이 된다. 미리 보기는 하나라도 가렸으면 `Masked`를 켠다.
   - 요청 자체는 진짜 값을 쓴다(같은 출처라 서버는 그 값을 이미 안다). 가리는 것은 기록뿐이다.
   - 서버가 cursor에 시크릿을 담아 이어 읽기 토큰에 가릴 글이 들어가게 되면 그 페이지는 **토큰 없이** 낸다(이어 읽으면 처음부터 읽는다). 저장소에 시크릿이 남지 않는 것이 이어 읽기보다 먼저다. 그런 페이지마다 사건 하나(`token_left`)가 알리고 사건의 글에도 가릴 글이 없다. cursor를 토큰에 쓰인 모양과 원래 모양 둘 다 본다(JSON의 이스케이프가 글을 바꾸기 때문이다).
2. **메서드를 바꾸는 헤더를 정의 검사가 막는다.** `core.ingest`의 헤더 금지 목록에 `x-http-method-override`, `x-http-method`, `x-method-override`를 더한다. 오류 코드는 다른 금지 헤더와 같다(`source.connection.header_not_allowed`). 인증의 헤더 이름에도 같은 검사가 걸린다.
3. **응답 하나의 메모리를 응답 크기와 뗀다.** 본문을 JSON 토큰 단위로 흘려 읽는다. `records_path`를 찾아 레코드를 하나씩 풀어 페이지 쓰는 쪽에 넘기고, 페이지 넘김이 읽는 값(`total_path`, `next_cursor_path`, `next_path`)은 레코드 배열의 앞에 있든 뒤에 있든 잡아 둔다. 그 값들은 응답 끝까지 읽은 뒤에 쓴다.
   - 디코더에 주는 읽기 창이 디코더가 쥐는 바이트를 "레코드 하나 + 64 KiB"로 묶는다. 읽기를 16 KiB씩 끊어 줘서 앞서 읽는 양도 작다. 레코드가 **2 MiB**(쓴 그대로의 바이트. 정의의 필드가 아닌 고정 값)를 넘거나, 레코드가 아닌 값이 그만큼 크면 `response_format`이다. 레코드가 아닌 부분이 깊게 중첩된 것은 512단계까지다(스택을 쓰지 않으려고 반복으로 걷는다). 레코드 안의 깊이는 JSON 파서의 한도를 따른다.
   - `max_response_bytes`는 같은 창이 센다(압축을 푼 뒤). 정의 검사의 상한을 1 GiB에서 **256 MiB**로 낮춘다. 메모리와는 떨어졌지만 응답 하나가 연결을 붙잡는 시간과 받는 양은 이 상한이 묶는다.
   - `records_path`의 위치가 둘이면(키가 두 번 나오면) 응답 형식 오류다. 페이지 넘김이 읽는 경로가 레코드 안을 지나면(드문 정의) 그 레코드에서 읽는다.
   - 응답이 같은지는 본문 전체의 해시로 알아보므로 이제 본문을 다 읽은 뒤에야 안다. 같은 응답이 연달아 오면 둘째 응답의 레코드는 이미 페이지에 넘어간 뒤이고 읽기는 불완전로 끝난다(ADR-0092 결정 5와 남는 위험 6이 이렇게 바뀐다).
   - 본문이 읽는 도중 끊기면(GET) 요청을 다시 보내고 이미 준 레코드를 새 응답에서 건너뛴다. 이어 읽기 토큰이 쓰는 건너뛰기와 같은 방식이다. 시도 횟수는 상태 오류의 재시도와 합쳐 셋이다. POST는 다시 보내지 않는다.
   - 토큰 발급 응답은 통째로 읽되 1 MiB까지다(고정 값).
   - 사건 `response`는 본문을 다 읽은 뒤에 나오고 `Bytes`는 읽은 크기다. 그 사이에 페이지 사건이 나올 수 있다.
4. **페이지 넘김 값의 길이와 토큰 만들기.** 응답에서 가져오는 cursor, 다음 주소, `Link`의 대상은 **8 KiB**까지이고 넘으면 `response_format`이다. 토큰은 페이지를 자를 때만 만든다: `core.ingest`의 `PageWriter`에 `AddLazy(ctx, rec Table, after func() []byte, yield func(Page, error) bool) bool`을 더했다(`Add`와 `Finish`의 글자는 바꾸지 않았다). `after`는 그 레코드 바로 뒤 위치의 토큰을 만드는 함수이고 그 레코드로 끝나는 페이지를 자를 때 한 번 불린다. `nil`이면 토큰이 없다. 한 `PageWriter`는 `Add`나 `AddLazy` 가운데 하나만 쓴다. 응답의 마지막 레코드의 토큰은 응답 끝에서야 알 수 있는 다음 위치를 쓰는데, 함수라서 그때까지 기다린다.
5. **`Retry-After`.** 시간이 담을 수 있는 초보다 큰 수와 정수에 들어가지 않는 숫자는 곱하기 전에 "한도보다 길다"로 다룬다. 그러면 ADR-0092 결정 6대로 기다리지 않고 일시적 오류로 끝난다. 음수는 지금처럼 값이 없는 것이다.

## 이유

- 시크릿 가리기는 한 곳(내보내는 곳)에서 거는 것이 빠뜨리지 않는 길이다. 가린 글의 꼴을 늘린 이유는, 서버가 값을 되돌릴 때 그대로 주는 일이 드물고 인코딩해 주는 것이 흔하기 때문이다. 행을 만들기 전에 가리는 이유는 가린 뒤에 만든 키가 시크릿으로 만들어지지 않게 하려는 것이다.
- 흘려 읽기는 크기 한도 하나가 메모리 한도가 되지 못한다는 검토의 결론에 대한 답이다. 한도를 낮추는 것만으로는 90배를 못 줄이고, 한도를 더 낮추면 정직한 큰 응답이 못 읽힌다.
- 토큰을 페이지마다 만드는 것은 값이 큰 cursor에서 비용이 레코드 수에 곱으로 늘어나는 길을 끊는다.

측정(힙의 최고치. 15 MiB의 빈 배열 본문, 레코드 약 520만 개, 가비지 컬렉터를 `GOGC=25`로 자주 돌게 하고 2 ms마다 표본을 잰다. 세 번 재고 가운데 값을 한도 64 MiB와 견준다. 같은 방법으로 전과 후를 쟀다):

| | 응답 하나의 최고 힙(시작보다 늘어난 양) |
|---|---|
| 전(통째로 해석) | 346, 347, 353 MiB(검토가 기본 수집기에서 측정한 값은 1,333 MiB) |
| 후(흘려 읽기) | 8, 8, 8 MiB |

## 대안과 기각 사유

- **레코드 수에 상한을 두고 `max_response_bytes`만 낮춘다.** 정직한 큰 응답이 못 읽히고 메모리가 응답 크기에 따르는 구조는 그대로다. 기각.
- **본문을 임시 파일로 받는다.** 파일 쓰기가 필요하고 어댑터는 파일을 쓰지 않는다. 기각.
- **가릴 글을 비밀번호 하나로 한정한다.** 사용자 이름과 인증 값의 글이 지나간다. 짧은 값만 넣지 않기로 했다.
- **토큰을 레코드마다 만들고 길이만 줄인다.** 8 KiB cursor와 레코드 수백만 개에서도 비용이 곱으로 남는다. 기각.
- **같은 응답의 되풀이를 레코드를 넘기기 전에 알아낸다.** 본문 전체를 쥐어야 한다. 흘려 읽기와 양립하지 않는다. 불완전로 끝나고 중복 레코드가 이미 넘어간 것을 받아들였다.

## 남는 위험

1. **가릴 글의 꼴 밖의 변형은 지나간다.** 16진수, 값의 일부만 되돌린 것, 쪼갠 것, 압축한 것, 퍼센트 인코딩의 소문자 16진, base64가 다른 위치에서 시작한 것은 못 잡는다. 4바이트보다 짧은 시크릿은 가리지 않는다.
2. **정의를 편집할 수 있는 사람은 그 소스에 묶인 시크릿을 같은 출처 안에서 쓸 수 있다.** `token_request`의 경로와 본문, 사용자 지정 헤더, 요청 경로를 정의가 고르므로, 같은 출처에 값을 받아 적는 엔드포인트가 있으면 시크릿을 보낼 수 있다. 시크릿의 범위가 소스 id와 주소에 묶이는 것(ADR-0092)은 다른 출처로 가는 것을 막을 뿐이다. 시크릿 주인의 다시 승인(인증 설정, 요청 경로, 헤더가 바뀔 때)과 `token_request`의 경로를 시크릿 쪽에 두는 것은 조립과 권한 설계에서 정한다.
3. **이어 읽기 토큰은 인증되지 않는다.** 지문이 정의의 공개된 값의 해시라 누구나 `{"e":true}`인 토큰을 만들 수 있고, 그러면 읽지 않고 완전한 수집으로 끝난다. 토큰은 서버의 저장소에서만 온다는 규칙을 조립에서 지키고, API로 받게 되면 서버 키로 HMAC을 건다. 이번에 고치지 않았다.
4. **같은 응답이 A, B, A, B로 번갈아 오면** `max_pages`까지 돈다. 연달아 같은 응답만 알아본다. 이번에 고치지 않았다.
5. **같은 응답이 연달아 올 때 중복 레코드가 이미 페이지에 넘어간다**(위 결정 3). 읽기는 불완전로 끝나므로 사라진 행으로 세지 않지만, 한 실행 안에서 같은 키가 두 번 보일 수 있다.
6. **응답을 흘려 읽어도 한 응답의 시간은 `max_response_bytes`와 `timeout_seconds`로 묶인다.** 느린 서버는 연결을 그만큼 붙잡는다.
7. **응답 끝에서야 아는 오류가 레코드를 넘긴 뒤에 난다.** 레코드 위치가 없거나 JSON이 끝에서 깨진 응답은 앞의 레코드가 이미 페이지에 들어간 뒤에 오류가 된다. 읽기는 오류로 끝나고 이어 읽기 토큰이 앞에 낸 페이지의 위치를 가리킨다.

## 결과

- 잠긴 테스트 둘의 지문을 다시 기록한다(`amends_tests`). 둘은 패키지의 모든 `.go` 파일을 `go:embed`로 읽어 제품 코드를 스캔하므로(Reveal은 `auth.go` 한 곳, 요청은 `request.go` 한 곳, 금지한 글자와 import가 없음) 이 패키지의 제품 코드가 바뀌면 지문이 바뀐다. 테스트의 단언은 그대로다.
- `core.ingest`: 헤더 금지 목록 셋, `MaxResponseBytesLimit`(256 MiB), `PageWriter.AddLazy`. `Add`와 `Finish`와 `NewPageWriter`의 글자는 그대로이고 기존 잠긴 테스트는 바뀌지 않았다.
- `adapter.httpsource`: 흘려 읽는 `stream.go`와 `answer.go`, 가리는 `mask.go`. 새 테스트는 `[REQ-690]`부터 `[REQ-694]`까지다.
- 이어 읽기 토큰의 `e`(끝) 표시를 내보내던 `tokenEnd`는 그것을 쓰는 페이지가 없어서 지웠다. 토큰을 읽는 쪽은 그대로다.
- 이 ADR이 다루지 않은 검토 항목(H7, H8의 A, B 번갈이)은 위 "남는 위험"에 있다.
