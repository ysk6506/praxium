# 현실 데이터 수집 설계

[ADR-0008](adr/0008-ingestion.md)의 결정을 풀어 쓴 문서 둘 중 앞 문서예요. 이 문서는 소스에서 원본 레코드까지와 안전장치를, 뒤 문서인 [파이프라인 설계](pipeline.md)는 정제·피드·식별·링크를 다뤄요. 구현하는 사람이 이 문서만 보고 데이터의 형식, 상태, 경계를 알 수 있게 썼어요. 표의 필드는 **스케치**이고 이름은 영어 snake_case예요. 예시의 소스, 이름, 숫자는 모두 지어낸 것이고, 숫자는 "가정"이거나 "측정해서 정한다"예요.

## 1. 목적과 다루는 질문
- 여러 소스를 읽기만 하면서, 소스마다 수집 시점과 수집 방식을 관리하는 방법
- 배치와 스트리밍을 한 정의로 수집하면서 스트림에서 쓸 수 없는 연산이 없게 하는 방법
- 한 객체 타입에 배치로 오는 속성과 실시간으로 오는 속성이 섞일 때의 구성과 사용자의 관리 방법
- 같은 것(ECMP 등)을 설정, 테이블, 문서의 어디에서든 수집하는 방법
- 소스가 틀리거나 일부만 와도 KG가 망가지지 않게 하는 장치, 그리고 제품이 모르는 소스와 접속할 수 없는 망의 소스를 수집하는 경로
- 소스가 보내 주는 경로(푸시 수집)와, 액션 뒤에 그 객체만 다시 수집해 확인하는 경로의 위치 (자세한 것은 [수집 확장](ingestion-extensions.md))
- 테이블로 바로 변환되지 않는 소스(문서, 설정 텍스트, 명령의 출력)가 행이 되는 과정

이 문서가 정하지 않는 것: 푸시 수집, 지정 재수집, 기대 조건과의 대조, 매핑을 돕는 경로, 파서와 라인 템플릿의 자세한 내용은 [수집 확장](ingestion-extensions.md)이 정해요. 원본 레코드 뒤의 정제, 피드, 링크 정의, 기대 조건, 건수 대조는 [파이프라인 설계](pipeline.md)가 정해요. 정의의 버전·브랜치·제안·병합·리버트는 ADR-0014의 절차를 따라요. 관측은 ADR-0013, 권한은 ADR-0012([권한 설계](access-control.md)), 저장은 ADR-0009([KG의 저장과 버전](kg-storage.md)), 모델은 ADR-0007([KG의 모델](kg-model.md))이 정해요.

## 2. 개요
```
소스 ─수집─▶ 읽어 들이기 ─▶ 원본 레코드의 변경 ─정제─▶ 데이터셋 ─공급(매핑)─▶ 속성 값
(읽기만,    (파서, 행 선택)  (적용기가 ingest_seq)(사전 정의 연산 14종)               │
 가져오기나 푸시)
   ┌────────── 식별과 병합 ◀────────────────────────────────────┘
   └─▶ 링크와 그룹 ─▶ 차이 ─▶ 안전장치 ─▶ KG의 변경 배치(change_seq) ─▶ 봉인한 KG 버전
```
| 단계 | 하는 일 | 아는 것 | 모르는 것 |
|---|---|---|---|
| 수집 | 소스에서 가져오거나(기본) 소스가 푸시한 것을 수신해요(`stream`의 한 형태) | 소스 접속, 프리셋의 요청, 가릴 필드 | 모델, 매핑 |
| 파싱 | 수집한 것이 행이 아닌 문서이면 파서가 트리로, 행 선택이 테이블로 변환해요(3.4). 행이면 건너뛰어요 | 파서, 라인 템플릿 | 모델, 수집 방식 |
| 원본 레코드의 변경 | 읽은 행을 추가·수정·삭제 변경으로 바꾸고 번호를 매겨요. 수정하지 않고 보존해요 | 키, 내용 해시 | 소스의 의미, 수집 방식 |
| 정제 | 사전 정의 연산 14종으로 데이터셋을 가공해요 | 데이터셋 | 접속, 모델, 수집 방식 |
| 피드(매핑) | 컬럼을 객체 타입의 속성과 식별 키에 연결해요 | 모델 | 접속, 수집 방식 |
| 식별과 병합 | 같은 것을 식별하고 속성마다 우선하는 값을 골라요 | 모델, 식별 이력 | 소스의 프로토콜 |
| 링크와 그룹 | 링크 정의로 객체를 연결하고 그룹을 만들어요 | 모델, 링크 정의 | 접속 |
| 차이, 안전장치, 적용 | 현재 KG와 비교하고 중단할지 판단한 뒤 변경 배치로 적용해요 | KG, 규칙 | 소스 |

연결 점검은 단계가 아니라 필요할 때 하는 점검이에요. 연동(수집까지)과 모델 동기화(그 뒤)의 경계는 원본 레코드의 변경이에요. 지정 재수집도 같은 경로를 거치고 읽기만 해요([수집 확장](ingestion-extensions.md) 2절).

## 3. 소스, 어댑터, 프리셋, 데이터셋
### 3.1 필드
| 이름 | 필드 |
|---|---|
| 소스 `source` | `id`, `name`, `adapter`, `preset`(id와 버전), `collector`(`in_product` / `remote` / `envelope_only`), `endpoints`(나가는 연결의 허용 목록), `credential_ref`, `contacts`(담당자), `protection`(8.4), `expected_interval`, `status`(`active` / `paused` / `breaker_open`), `push`(푸시 경로: `enabled`(기본 꺼짐), `dedupe_window`(기본 7일, 소스마다 설정)) |
| 데이터셋 `dataset` | `id`, `source_id`, `name`, `kind`(`raw` / `refined`), `request`(프리셋의 허용된 요청 이름), `receive_mode`, `schedule_id`, `parser`와 `row_select`(문서를 행으로 바꾸는 규칙, 3.4), `natural_key`(소스가 키를 주지 않으면 구성 규칙), `event_time`(이벤트 시각 컬럼), `marker`(증분 수집의 표시), `deletion`(`absent_in_full` / `delete_event` / `delete_flag` / `none`), `columns`(이름, 값 타입, `sensitivity`), `redact`(`drop`, `mask`), `expectations`. `refined`는 `inputs`와 `ops`를 가져요 |
| 프리셋 `preset` | `id`, `version`, `adapter`, `allowed_requests`(메서드, 경로 템플릿, 본문의 형식), `pagination`, `auth_kind`, `keyed_read`(키로 단건 읽기를 지원하는지 선언), `datasets`(전체 수집과 증분 수집의 세트), `default_feeds`, `default_sensitivity`, `default_schedule`, `redact`, `tests`(합성 샘플) |

`natural_key`가 없으면 행의 순서에 의존하게 되어 결과가 정해지지 않아요. 프리셋은 키 구성 규칙을 선언해야 해요. 키가 겹치면 수집을 거절하지 않고 문제 목록에 올리고, 어느 행을 쓸지는 정제의 "중복 행 제거"가 정해요. 소스와 데이터셋에는 담당자가 붙어요. 담당자는 연락처이고, 문제와 알림과 검토 요청이 담당자에게 전달돼요. 권한은 권한 부여에서만 나와요(ADR-0012).

### 3.2 어댑터의 포트
어댑터는 프로토콜 하나를 다루는 제품 안의 코드이고 소스의 의미와 KG 모델을 몰라요. 쓰기 메서드는 없어요(구조 검사가 확인해요). 어댑터는 자기가 지원하는 메서드를 선언해요.

| 메서드 | 의미 |
|---|---|
| `inspect` 소스 탐색 | 무엇이 있는지(테이블, 엔드포인트, 컬럼)를 읽기 전용으로 반환해요. 양에 상한이 있고 소스 보호를 거쳐요. 매핑을 만들 때 써요 |
| `preview` 미리 보기 | 데이터셋의 일부 행을 반환해요 |
| `fetch_all` 전체 수집 | 레코드를 스트리밍으로 전달하고 완전성을 알려요(끝까지 갔는지, 소스가 알린 건수와 일치하는지) |
| `fetch_since` 증분 수집 | `marker` 뒤로 바뀐 것을 수집하고 다음 `marker`를 반환해요 |
| `follow` 연속 수집 | 소스 커서(`source_cursor`)부터 이벤트를 스트리밍으로 전달해요. 커서가 이어지지 않으면 `resume_lost`로 알려요 |
| `check` 점검 | 접속, 인증, 소스 쪽 계정이 읽기 전용인지 확인해요(8.1) |
| `keyed_read` 키로 단건 읽기 | 객체 하나의 키로 그 레코드만 읽어요. 지정 재수집이 써요. 선언하지 못하면 가장 좁은 범위의 읽기로 대신해요 |

`source_cursor`에 담기는 위치는 소스가 준 불투명한 표지예요. 저장하고 되돌려 보낼 뿐 크기를 비교하지 않아요(7.2). `inspect`, `preview`, `check`, 트라이얼 수집은 모두 소스 보호를 거치고, 브랜치에만 있는 새 소스에도 쓰도록 `branch_id`를 받아요. 누가 호출하는지는 **시크릿을 복호화하는 주체**로 구분해요.

| 호출하는 작업 | 주체 |
|---|---|
| 메인 브랜치의 소스 정의 그대로 시크릿을 복호화해 접속하는 작업 | 그 소스를 범위에 가진 `editor`나 `operator` |
| 브랜치가 접속 주소(`endpoints`)나 연결을 바꿨을 때 | 그 소스의 `operator`(ADR-0018) |
| 새 소스를 브랜치에서 처음 접속할 때 | 같아요. 주소를 바꾼 것이므로 `operator` |

원본을 보는 경로(`preview`, 샘플, 컬럼 통계)는 읽기 권한도 따져요. 그 데이터셋이 채우는 타입의 읽기 권한을 함께 요구하고 감사 로그에 남기며, 컬럼의 민감 등급이 `open`이 아니면 "빈출 값"을 제공하지 않아요. 다른 소스의 데이터셋을 읽는 정의는 작성자가 그 소스를 범위에 가져야 해요([파이프라인 설계](pipeline.md) 5.2).

### 3.3 첫 어댑터와 스트림 어댑터 후보
| 어댑터 | 수집 방식 | 특징 |
|---|---|---|
| 파일(엑셀, CSV) | `snapshot` | 업로드한 파일 하나가 전체 수집 한 번이에요(10절) |
| HTTP JSON | `snapshot`, `incremental` | 세션 인증, 페이지네이션, 선언한 요청 템플릿. 로그인과 검색 실행처럼 읽기인 POST는 허용 목록에 적어요 |
| 읽기 전용 SQL | `snapshot`, `incremental` | 조회만 가능한 역할로 접속해요 |

스트림 어댑터는 결정 기록과 함께 하나씩 추가해요. 전달 보장과 순서는 일부만 확인했으므로 **모든 소스가 중복과 순서 뒤바뀜을 일으킬 수 있다고 전제해요.**

| 후보 | 소스 커서 | 삭제를 아는 방법 | 정합성 대조가 필요한 이유 |
|---|---|---|---|
| 메시지 로그 스토리지의 토픽 | 파티션별 오프셋 | 값 없는 레코드나 삭제 표시 레코드 | 보존 기간이 지나면 되감을 수 없어요 |
| 워치 방식의 API | 불투명한 재개 토큰 | 삭제 이벤트 | 이어지지 않으면(너무 늦음) 처음부터 다시 수집해요 |
| CDC(변경 데이터 캡처) | 변경 로그의 위치 | 삭제 레코드. DB가 로그에 남기지 않는 삭제는 잡지 못해요 | 처음에 일관된 스냅샷, 그 뒤 로그. 최소 1회 전달돼요 |
| 푸시 수집 | 없음(소스가 보내요) | 이벤트의 종류 | 순서 보장이 없고 소스가 재시도해요. 수집 엔벨로프의 한 형태예요 |

가져오기가 기본이에요. **푸시 수집**은 소스마다 정의로 열어요(기본은 닫힘). 보내는 쪽은 서비스 계정이고 역할은 8번째 역할인 `ingester`예요. `ingester`는 범위에 든 소스에 푸시하고 수집 엔벨로프를 보내는 것만 하고 읽기도 못 해요(ADR-0012). 같은 것을 여러 번 보내도 한 번만 반영돼요. 보낸 쪽의 이벤트 ID를 **중복 제거 기간**(`dedupe_window`, 기본 7일, 소스마다 설정) 동안 기억하고, 기간이 지난 뒤의 재전송은 걸러 내지 못해요. 그 역할은 키와 내용 해시가 맡고 늦게 도착한 값은 이벤트 시각이 막아요([파이프라인 설계](pipeline.md) 2.4). 푸시한 것도 같은 실행기, 안전장치, 행 집계를 거쳐요. 푸시 수집만 하는 소스는 누락을 알 수 없으므로 정합성 대조(스냅샷)를 함께 두기를 권하고, 없으면 완전성을 선언하지 못해요.

"처음에 전체, 이어서 연속, 이어지지 않으면 다시 전체"는 워치 방식의 표준 패턴이고, 어댑터 포트가 이 패턴으로 일반화돼 있어요(4.2).

### 3.4 파싱: 문서에서 트리로, 행으로
어댑터가 수집한 것이 행의 모음이 아닐 수 있어요(문서 하나, 텍스트 덩어리). 원본 데이터셋은 수집과 원본 레코드 사이에 파싱을 둬요.

| 단계 | 내용 | 필드 |
|---|---|---|
| 파서 | 문서를 **트리**(이름 붙은 노드와 값, 순서 있는 목록)로 변환해요 | `parser`(제품에 포함된 고정 목록의 이름과 버전) |
| 행 선택 | 트리에서 "무엇이 한 행인가"와 "컬럼은 어느 노드인가"를 경로로 지정해 테이블로 변환해요. 상위 노드의 값을 하위 행에 복사할 수 있어요 | `row_select`(행의 경로, 컬럼별 경로, 복사할 노드) |

행이 이미 행인 소스(SQL, 엑셀, CSV)는 이 단계를 건너뛰어요. 파서가 읽지 못한 행과 라인 템플릿에 맞지 않은 행은 버리지 않고 행 집계의 "읽지 못함" 필드로 세어요([파이프라인 설계](pipeline.md) 7절). 트리의 구조가 바뀌면(없던 노드, 사라진 노드) 수집한 데이터의 스키마가 바뀐 것으로 다뤄서 9.1의 "스키마 변경"을 거쳐요. 파서의 목록, 라인 템플릿, 작성자를 돕는 경로는 [수집 확장](ingestion-extensions.md) 5절에 있어요.

## 4. 수집 방식
### 4.1 4종과 선택 기준
| 방식 | 내용 | 삭제를 아는 방법 | 선택 기준 |
|---|---|---|---|
| `snapshot` | 주기마다 전체를 수집해요 | 완전한 수집에서 보이지 않음 | 구성 데이터의 기본. 작고 "사라짐"이 중요하고 전체를 수집해도 소스가 견뎌요 |
| `incremental` | 주기마다 지난번 이후 바뀐 것만 수집해요 | 소스가 삭제를 알리거나, 가끔 전체를 수집해 대조해요 | 전체 수집이 비싸고 소스가 바뀐 것을 구분해 줘요 |
| `stream` | 연속으로 수집해요(구독, 워치, CDC, 푸시 수집) | 삭제 이벤트 | 몇 초 안의 반영이 필요하고 소스가 변경을 알려 줘요 |
| `stream` + 정합성 대조 | 처음에 전체, 이어서 연속, 가끔 전체로 대조해요 | 둘 다 | 삭제 이벤트가 없거나 손실이 있는 소스. 삭제를 아는 방법이 약할수록 대조를 자주 해요 |

수집 방식은 소스가 아니라 **데이터셋**의 필드(`receive_mode`)예요. 한 소스가 구성은 `snapshot`으로, 상태는 `stream`으로 제공할 수 있어요. 어느 방식이든 수집한 것은 원본 레코드의 변경이 되고, 그 뒤 단계는 수집 방식을 몰라요.

### 4.2 `stream` + 정합성 대조의 상태 전이
```
paused ─(켜기)─▶ seeding(처음에 전체 수집) ─(완전히 끝)─▶ following(연속 수집)
following ─(대조 주기)──────────▶ reconciling(전체 수집, 차이를 변경으로) ─▶ following
following ─(follow가 resume_lost)─▶ resyncing(전체 수집, 차이를 변경으로) ─▶ following
following/seeding ─(안전장치, 기대 조건 fail)─▶ held(수집은 계속, 적용만 보류)
held ─(release)─▶ 쌓인 것을 한도 있는 배치로 나눠 순서대로 적용 / ─(discard)─▶ 폐기한 뒤 전체 수집으로 대조
```
스트림의 상태는 `running` / `held` / `paused` / `failed`예요. 해제(`release`)는 `operator`가 드라이 런으로 차이를 본 뒤에 해요. **보류된 변경은 해제될 때 `ingest_seq`를 받아요**(보류되기 전에 받지 않아요). 그래서 해제와 폐기도 수집 순서에 포함되는 이벤트예요(7.2). 오래 쌓였다가 해제될 때 한 번에 적용하는 양은 기본값 표의 배치 크기(1만 행 또는 2초)로 나눠, 한 소스가 적용기를 오래 독점해 다른 소스의 스트림이 지연되지 않게 해요. 큰 적용은 `change_seq` 여러 개로 나뉘고 읽는 쪽에는 배치가 끝날 때만 보여요([KG의 저장과 버전](kg-storage.md)). 보류된 이유가 정의 때문이면 정의를 수정해 병합하고, 쌓인 변경이 새 정의로 적용돼요. **폐기(`discard`)는 정합성 대조가 가능한 소스에서만 돼요.** 전체 수집이 불가능한 스트림은 폐기할 수 없고 해제하거나 보류 상태로 둘 수만 있어요.
`incremental`도 같은 틀이에요. `fetch_since`가 `following` 상태에서 실행되고, 대조 주기마다 전체를 수집해요.

### 4.3 삭제를 아는 방법
| 방법 | 동작 | 원본 레코드에서 |
|---|---|---|
| 완전한 전체 수집(`snapshot`, 정합성 대조, `resyncing`)에서 보이지 않음 | 바로 삭제하지 않고 연속으로 보이지 않은 횟수를 (피드, 객체)마다 한 곳에서만 세요(저장 설계의 `unseen_object`. 원본 레코드 행에는 횟수를 두지 않아요) | 횟수 N과 처음 보이지 않은 때부터의 최소 기간 T를 둘 다 넘으면 구간을 닫고 `deleted`. 피드마다 수정할 수 있고 기본은 N=3(가정)이에요 |
| 소스가 알림(삭제 이벤트, 삭제 표시 컬럼) | 소스가 알린 삭제예요 | 바로 구간을 닫고 `deleted` |
| 불완전한 수집 | 보이지 않음으로 세지 않아요 | 아무것도 삭제하지 않아요 |
| 방법 없음(`deletion: none`) | 삭제를 알 수 없어요 | 피드의 완전성 선언(`completeness_declaration`)이 없으므로 "없다"가 아니라 "모른다"예요(ADR-0007) |

원본 레코드의 `deleted`가 객체를 폐기시키는 것은 아니에요. 그 피드가 `retires_objects`일 때만 폐기돼요([파이프라인 설계](pipeline.md) 3.3). 스트림에서는 삭제 이벤트와 정합성 대조만 폐기시켜요.

## 5. 일정
일정이 정의예요. 값(주기, 시간대, 대조 주기 등)을 수정하는 것은 정의의 변경이라 ADR-0014의 절차를 따라요. 일시 정지와 즉시 1회 실행은 정의를 바꾸지 않는 운영 조작이고 `operator`가 하며 감사 로그에 남아요.

| 필드 (`schedule`) | 의미 |
|---|---|
| `target` | 소스 하나 또는 데이터셋 하나. 데이터셋마다 다르게 둘 수 있어요 |
| `every` / `at` / `manual_only` | 간격 / 정해진 시각들(`timezone` 포함) / 수동으로만. `snapshot`과 `incremental`에 써요 |
| `windows` | 수집해도 되는 시간대. 밖이면 건너뛰고 기록해요 |
| `stream_enabled`, `reconcile_every` | `stream`의 켜고 끔, 정합성 대조의 주기. `incremental`도 `reconcile_every`를 가져요 |
| `misfire_policy` | 건너뛴 실행의 처리: `skip`(건너뛰고 기록) / `run_once`(한 번만 따라잡기). 기본 `run_once`(가정) |
| `expected_interval` | 기대하는 갱신 주기. 수동으로만 수집하는 소스도 적어요. 신선도 저하는 이 값을 기준으로 판단해요. 적지 않으면 경과 시간만 보이고 "기대 주기 없음"이에요 |

- **일시 정지**는 사유와 함께 중지하고 헬스 상태에 표시해요. **즉시 1회 실행**은 같은 경로, 같은 소스 보호, 같은 안전장치를 거쳐요.
- **중복 실행 금지**: 같은 데이터셋의 실행은 한 곳에서만 해요. 서버가 여럿이어도 일정의 키로 막아요(ADR-0011). 워커가 작업 리스를 획득할 때마다 `attempt`가 오르고 늦게 깨어난 워커의 쓰기는 번호로 차단해요.
- **실패**: 재시도 3회, 연속 5회 실패하면 그 소스의 일정을 중지하고 알려요(기본값(설정). 클로즈드 베타에서 측정해서 수정해요). 운영 역할이 수동으로 다시 켜요. 마지막 정상 버전은 그대로예요.
- **스트림**: 켜고 끔과 정합성 대조의 주기가 일정이에요. 스트림의 신선도는 지연(마지막으로 적용한 이벤트의 시각과 현재의 차이)과 마지막 대조의 시각이에요.

## 6. 수집 엔벨로프와 분리망의 수집기
### 6.1 수집 엔벨로프의 필드
제품 밖의 수집기가 원본 레코드를 보낼 때 쓰는 공개된 형식이에요. 형식은 계약 단위가 보유하고 버전이 있어요(ADR-0006). 보내는 쪽은 `ingester` 역할을 가진 서비스 계정이고(3.3), 범위에 든 소스에만 보낼 수 있어요.

| 필드 (`envelope`) | 의미 |
|---|---|
| `envelope_version` | 엔벨로프 형식의 버전 |
| `source_id`, `dataset_id`, `preset` | 무엇을 수집했는지 |
| `capture_id` | 수집 한 번의 키. 다시 보내도 한 번만 수신해요(멱등) |
| `mode` | `full` / `delta` / `stream` |
| `collector_id`, `collector_version` | 누가 수집했는지 |
| `started_at`, `finished_at` | 언제 |
| `capture_complete` | 수집의 완전성(이번 수집이 끝까지 갔는지): `complete`, `expected_count`, `received_count`, `pages`, `errors`. 정직하게 적어야 해요. 무조건 신뢰하지는 않아요(9.3) |
| `redaction` | 제거한 규칙의 버전과 제거한 필드의 경로 목록 |
| `body_hash` | 제거한 뒤 내용의 해시 |
| `records` | 레코드들: `kind`(`added` / `modified` / `deleted`), `natural_key`, `source_time`(선택), `position`(선택), `seq`(수집기가 매긴 순서 번호), `body` |

- 수신하는 쪽은 인증(토큰은 해시로만 저장하고 만료와 교체가 있어요), 크기 상한, `capture_id`와 `seq`로 중복을 막아요. 중복을 막는 기록은 소스의 `dedupe_window`(기본 7일) 안에서 유지돼요. 그리고 데이터셋의 `redact` 선언대로 시크릿을 다시 제거해요.
- 수신 순서는 수집기의 `seq`가 아니라 적용기가 확정하며 매기는 `ingest_seq`가 정해요. `seq`는 한 수집기 안에서 누락을 찾는 데 써요.
- 소스가 추가와 수정을 구분하지 못하면 둘 다 `added`로 보내도 돼요. 실행기는 키 상태를 보고 정해요.

### 6.2 분리망의 수집기
| | 제품이 제공하는 수집기 | 담당자가 만든 수집기 |
|---|---|---|
| 내용 | 워커의 수집 역할을 소스가 있는 망에 별도로 기동한 것(4번째 역할) | 수집 엔벨로프만 쓰는, 소스의 담당자가 구현한 것 |
| 연결 | 밖으로 나가는 연결만 써요. 본체에 문의해 작업을 받고 수집 엔벨로프로 보내요 | 같아요 |
| 읽기 전용 | 같은 어댑터가 실행되므로 3중 보장이 그대로 유지돼요 | **그 소스의 담당자가 책임져요.** 문서와 API의 응답에 명시해요(화면에 표시돼요) |
| 시크릿 | 그 망의 시크릿 제공자를 가리켜요. 본체는 참조와 메타 정보만 알아요([시크릿과 암호화](secrets-and-encryption.md)) | 담당자의 몫이에요 |

본체가 그 망에 들어가지 않아도 돼요. 수집기는 소스 커서(`source_cursor`)를 본체에 보관하므로 장애가 나도 다른 인스턴스나 새로 기동한 것이 이어받아요. 인스턴스가 하나뿐이면 그동안 작업이 대기하고 헬스 상태에 표시되므로 2개 이상을 권해요. 수집 엔벨로프의 클라이언트 라이브러리는 여러 언어로 제공해요(Go, Python, TypeScript부터). 담당자가 익숙한 언어로 수집기를 구현해요. 수집기와 본체가 서로 확인하는 연결은 클로즈드 베타에 갖춰요(실제 소스를 연결하는 시점이에요). 그 전의 수집기는 토큰 하나로 본체에 보내요. 수집기에 장애가 나면 소스의 헬스 상태에 하트비트가 끊긴 것으로 표시돼요(ADR-0013). 담당자가 만든 수집기가 지켜야 할 것은 읽기 전용, 정직한 `capture_complete`, 시크릿 제거, 그리고 합성 샘플 엔벨로프로 테스트한 것이에요.

## 7. 원본 레코드
### 7.1 구간 모델과 변경으로 바꾸기
수집한 형식 그대로(JSON) 레코드 단위로 보관하고 수정하지 않아요. 같은 레코드가 다음 수집에서도 그대로면 복제하지 않아요. 구간의 끝이 열려 있어서 행을 수정하지 않고도 "계속 보인다"가 돼요(그렇지 않으면 수집마다 모든 행이 바뀌어요). 마지막으로 완전히 수집한 시각은 레코드가 아니라 소스의 수집에서 읽어요(신선도, ADR-0009). **`volatile` 속성만 채우는 스트림의 데이터셋**은 구간을 쓰지 않아요. 이벤트마다 이전 행을 닫고 새 행을 넣으면 초당 수만 건에서 원본 레코드가 가장 큰 쓰기가 되기 때문에, 추가만 하는 단기 보관 로그로 둬요(보존 기한은 [기본값 표](defaults.md)).

| 필드 (`raw_record`) | 의미 |
|---|---|
| `source_id`, `dataset_id`, `natural_key` | 어느 소스의 어느 데이터셋의 어느 레코드인지(저장 설계 3.2의 `raw_record`는 `natural_key`를 씀) |
| `content_hash` | 시크릿을 제거한 뒤 내용의 해시 |
| `from_ingest_seq`, `to_ingest_seq` | 처음 본 `ingest_seq`, 닫힌 `ingest_seq`(비어 있으면 열려 있어요) |
| `source_time` | 소스가 알린 시각(없으면 비어 있어요). 재실행해도 늦게 도착한 값의 처리가 같은 결과가 되도록 저장해요 |
| `body`, `redaction_version` | 내용(JSON), 제거한 규칙의 버전 |
| `excluded` | 이 레코드는 사용하지 않는다는 예외(7.3) |
| `scrubbed_at`, `scrub_reason` | 내용을 삭제했다는 표시(7.3). 비어 있으면 삭제하지 않은 레코드예요 |

| 상황 | 구간 | 변경 |
|---|---|---|
| 새 키 | 새 행이 열려요 | `added` |
| 같은 키, 같은 해시 | 그대로(끝이 열려 있어요) | 없음 |
| 같은 키, 다른 해시 | 이전 구간을 닫고 새 행이 열려요 | `modified`(실행기에서 −이전 +새) |
| 완전한 전체 수집에서 보이지 않음 | 행은 그대로. `unseen_object`의 횟수가 늘고, N과 T를 넘으면 닫아요 | `deleted` |
| 다시 보임 | `unseen_object`의 횟수가 0으로 | 없음 |
| 불완전한 수집 | 건드리지 않아요 | 없음 |

어느 `ingest_seq` N 시점의 상태는 "`from_ingest_seq` ≤ N 이고 닫히지 않았거나 N < `to_ingest_seq`"인 행으로 읽어요. 그래서 보관해 둔 원본 레코드만으로 이후 단계를 언제든 재실행할 수 있어요.

### 7.2 기록 2종, 소스 커서 2종, 수집 순서의 번호
- **기록은 2종이고 섞지 않아요**(ADR-0009). 수집 변경 로그는 소스에서 수집한 변경을 적용 전에 쌓는 곳이에요. 포트이고 어댑터가 2개이며 둘 다 정식이에요(PostgreSQL은 작은 배포와 알파, 메시지 로그 스토리지는 조직이 이미 쓰고 있는 경우가 많은 것. 메시지 로그 스토리지 어댑터는 클로즈드 베타예요. 제품은 그 스토리지를 직접 기동하거나 운영하지 않고 연결에 필요한 조건(토픽, 보존, 권한, 복제의 최소)만 문서로 제공해요). KG에 적용된 변경의 기록(`change_seq`)은 언제나 PostgreSQL이에요.
- **소스 커서도 2종이에요.** `source_cursor`는 소스에서 어디까지 읽었는지예요. 수집 변경 로그에 쓰는 것과 함께 전진해요. 로그가 PostgreSQL이면 한 트랜잭션이고, 메시지 로그 스토리지면 쓴 뒤에 전진해서 겹쳐 수집한 것을 (소스, 오프셋)로 걸러 내요. `applied_through`는 수집 변경 로그에서 어디까지 적용했는지예요. 키 상태, 변경 배치와 한 트랜잭션이라 정확히 한 번 적용돼요.
- **`ingest_seq`는 KG마다 하나뿐인 적용기가 "순서를 확정하는 단계"에서 매겨요.** 수집 변경 로그에서 배치를 읽을 때 어느 레코드의 어느 위치를 어떤 순서로 읽었는지를 목록(`ingest_order`, 저장 설계 3.2)으로 적고 번호를 매겨요. 이 단계는 [KG의 저장과 버전](kg-storage.md) 5절의 적용 3단계 앞에 있어요. 순서에 포함되는 이벤트는 고정 목록이에요(원본 변경, 시계 이벤트, 확정, 보류된 스트림의 해제와 폐기, 안전장치의 확인, 원본 레코드 제외, 정의 세트의 교체. 목록은 저장 설계에 있어요). 재실행할 때는 이 목록을 따르므로 로그가 어느 어댑터든 순서가 같아요. 여러 소스의 변경이 섞이는 순서도 이 번호로 고정돼요. `change_seq`도 같은 적용기가 매기고 둘은 다른 번호예요.
- **시계도 이벤트**예요. 일정한 간격(기본값(설정) 1분)의 `tick`을 이벤트로 로그에 넣어 순서를 받게 해요. 시간에 의존하는 일(대기의 기한, 보류된 시간)은 벽시계가 아니라 `tick`으로 세므로 재실행해도 같은 결과예요.

### 7.3 시크릿 삭제와 보관
- 프리셋과 데이터셋이 `redact`(`drop`, `mask`)를 선언해요. 수집할 때 제거하고, 해시는 제거한 뒤 내용으로 구해서 시크릿이 해시에 새지 않아요. 제거한 규칙의 버전과 경로를 남겨요.
- 보존 기한은 [기본값 표](defaults.md)가 정해요(원본 90일). **기한은 닫힌 구간에만 적용해요.** 열려 있는 구간은 경과 시간으로 삭제하지 않아요(2년째 바뀌지 않은 배치의 행이 삭제되면 재실행과 값의 출처가 깨져요). KG 버전이 사용한 레코드는 기한이 지나도 참조가 고정돼요. 파티션 단위로 삭제해요.
- **내용 삭제 표시.** 유출된 시크릿이나 삭제해야 할 값이 이미 쌓인 원본 레코드에 있으면 `admin`의 운영 액션으로 그 레코드의 내용을 삭제하고 해시와 위치와 이유만 남겨요(`scrubbed_at`, `scrub_reason`). 감사 로그에 남아요. 내용을 삭제한 레코드를 재실행할 때는 남은 해시로 "같은 입력"임을 보이고 값은 삭제된 것으로 다뤄요(값이 있는 것처럼 계산하지 않아요). 이 필드는 알파부터 원본 레코드의 스키마에 있어요. 로그와 추적과 내보낸 파일에 남은 값은 같은 절차로 따로 삭제해요.

개별 예외는 2종뿐이에요. 식별의 예외(같다 / 다르다)와 원본 레코드 제외(이 레코드는 사용하지 않는다)예요. 값을 개별로 덮어쓰는 예외는 없고, 값은 소스나 규칙에서 수정해요. 둘 다 정의라서 버전이 있어요.

## 8. 읽기 전용, 소스 보호, 시크릿, 민감 등급
### 8.1 읽기 전용은 3중이에요
"읽기 메서드만"은 지킬 수 없어요(로그인, 검색 실행, GraphQL은 읽기인데도 POST를 써요).
| 단계 | 내용 | 확인 |
|---|---|---|
| 첫째, 요청 허용 목록 | 프리셋의 (메서드, 경로 템플릿, 본문의 형식). 목록 밖의 요청은 만들어지지 않아요 | 프리셋을 포함하거나 정의를 저장할 때 정적 검사 |
| 둘째, 소스 쪽 계정이 읽기 전용 | SQL은 조회만 가능한 역할. 읽기 전용 트랜잭션 설정은 경계가 아니에요 | 연결할 때 관리자가 확인하고 `check`가 가능한 소스는 권한을 점검해 헬스 상태에 표시해요 |
| 셋째, 어댑터에 쓰기 경로가 없음 | 포트에 쓰기 메서드가 없어요 | 구조 검사 |

브랜치에서 새 소스를 테스트하는 **트라이얼 수집**(`operator`, [정의 설계](definitions.md) 9절)도 같은 3중 보장과 소스 보호를 거쳐요. 수집한 레코드는 브랜치 소속 영역에 담기고 운영의 원본 레코드에 섞이지 않아요.

### 8.2 쿼리 언어를 쓰는 소스
검색은 관리자가 자유롭게 작성해요(검색 하나가 데이터셋 하나). 저장할 때 **허용된 명령의 목록**으로 검사해요. 차단 목록이 아니에요.
- 검색을 명령으로 분해해 모든 명령이 허용 목록(프리셋이 소스 제품마다 갖고 있어요) 안에 있어야 저장돼요. 목록에 없는 명령과 해석하지 못한 검색은 거절해요. 부작용이 있는 명령(저장, 삭제, 내보내기, 실행)은 허용 목록에 넣지 않아요.
- 소스 쪽 계정이 읽기 전용이라는 둘째 단계가 본선이에요. 검사는 첫째 단계예요.
- 검색마다 시간 범위와 행 수 한도를 둬요. 한도에 도달하면 잘린 채 적용하지 않고 불완전한 수집으로 중단해요. "기대하는 컬럼"은 `shape` 기대 조건으로 적어요.

### 8.3 나가는 연결의 허용 목록과 시크릿
워커와 수집기가 접속할 수 있는 곳은 소스의 `endpoints`에 적은 주소뿐이고 기본은 차단이에요(주소를 추가하는 것은 정의의 변경). 소스에는 시크릿 스토리지의 참조(`credential_ref`)만 저장하고, 값은 시크릿 제공자 포트 뒤에서만 읽어요. 로그와 지표에는 레이블과 건수만 있어요.

### 8.4 소스를 보호하는 값
완화하는 것은 `admin`의 승인이 필요해요.
소스마다 `protection`이 있고 값은 제품이 포함해 제공하는 **기본값(설정)**이에요([기본값 표](defaults.md)). 클로즈드 베타에서 측정해서 수정해요. 어댑터 앞단에서 강제해서 프리셋이 우회하지 못해요.

| 값 | 기본 | 비고 |
|---|---|---|
| `max_concurrency` | 1 | 소스의 세션과 작업 한도가 낮은 경우가 많아요 |
| `rate_limit` | 초당 5(프리셋이 수정해 선언) | 요청 수 상한 |
| `retry` | 최대 3회, 백오프 후 재시도 | 소스가 알려 준 대기 시간을 지켜요 |
| `breaker` | 연속 5회 실패하면 차단 | 인증 실패는 바로 차단해요(계정이 잠기지 않게). 테스트 요청 한 번으로 해제해요 |
| `windows` | 수집해도 되는 시간대 | 밖이면 건너뛰고 기록 |
| 예산 | 실행 하나의 요청 수·바이트·시간 상한 | 도달하면 불완전한 수집 |

### 8.5 민감 등급이 컬럼에서 속성으로 전파돼요
소스의 컬럼에 `sensitivity`(`open` / `restricted` / `confidential`)를 적어요. 프리셋이 기본값을 주고 관리자가 수정해요. 정제를 거치며 출력 컬럼의 등급은 입력 가운데 가장 높은 것이 돼요. 속성의 등급은 매핑된 컬럼의 등급보다 낮을 수 없어요. 낮추려면 이유를 적고 `admin`의 승인을 받아요. ADR-0012의 속성 등급과 한 체계예요. 원본 레코드와 격리한 레코드를 읽는 것도 등급과 권한을 따라요.

### 8.6 시크릿은 참조로만 들어와요
소스의 연동 정보는 정의에 참조(`secret_ref`)로만 들어가고 값은 쓰기만 되는 스토리지에 있어요(ADR-0018). 프리셋의 요청 템플릿은 시크릿이 들어갈 위치를 따로 표시하고, 그 위치는 로그와 추적과 요청의 샘플에서 가려져요. 관리자가 작성하는 검색 안에 시크릿을 텍스트로 적지 못하게 저장할 때 검사해요. 시크릿은 접속해도 되는 주소(`allowed_hosts`)에 묶여요. 수집한 데이터에 시크릿이 섞여 오면 수집할 때 제거해요(`redact`: `drop`, `mask`). 제거한 건수는 관측의 지표로 남아요(ADR-0013). 이 문서의 `redact`를 [시크릿과 암호화](secrets-and-encryption.md)가 확장해요.

## 9. 안전장치
자동으로 적용하기 전에 중단시키는 검사예요. 숫자는 [기본값 표](defaults.md)의 기본값(설정)이고 클로즈드 베타에서 측정해서 수정해요.

### 9.1 배치
| 장치 | 확인하는 것 | 중단되면 | 담당과 조치 |
|---|---|---|---|
| 불완전한 수집 | 페이지네이션이 끝까지 갔는지, 소스가 알린 건수와 일치하는지, 지난번보다 레코드 수가 크게 줄었는지(30% 이상) | 다음 단계로 가지 않고 원본 레코드에 "불완전"으로 남아요. 보이지 않음으로 세지 않아요 | `operator`가 원인을 확인하고 다시 수집해요 |
| 동일 | 입력이 같은지 | 새 KG 버전을 만들지 않아요 | 없음 |
| 사람의 확인 | 처음 적용, 정의를 수정한 뒤 첫 적용, 표준 모델이 올라간 뒤 첫 적용, 실행기의 의미 버전이 올라간 뒤 첫 적용 | 후보와 차이를 보여 주고 기다려요 | `operator`가 차이를 보고 확인 |
| 스키마 변경 | 컬럼과 자료형 | 중단해요 | 정의를 수정하거나 `operator`가 확인 |
| 대량 사라짐 | 객체가 10% 이상이면서 5건 이상, 또는 500건 이상 사라짐 | 중단해요 | `operator`가 확인 후 적용하거나 폐기해요 |
| 보이지 않음 | 완전한 수집에서 연속 3회 | 그제야 폐기로 표시해요 | 없음. 이력에 남아요 |
| 기대 조건 `fail` | [파이프라인 설계](pipeline.md) 6절 | 그 피드의 적용을 중단해요 | 담당자에게 알려요 |
| 읽지 못함의 비율 | 파서가 읽지 못한 행의 비율(3.4) | 기대 조건을 설정했으면 그 규칙대로 | 담당자에게 알려요 |

### 9.2 스트림
스트림에는 완전한 수집이 없으므로 **보이지 않는다고 폐기하지 않아요.** 삭제 이벤트와 정합성 대조만 폐기시켜요.

| 장치 | 확인하는 것 | 중단되면 | 담당과 조치 |
|---|---|---|---|
| 보류 `held`: 비율 | 짧은 시간에 너무 많이 사라지거나 바뀌었는지(비율과 윈도우는 측정해서 정해요) | 그 소스의 **적용**을 보류해요. 수집은 중단하지 않고 수집 변경 로그에 쌓여요(유실되지 않아요) | `operator`가 `release`나 `discard`(4.2) |
| 보류: 스키마 | 수집한 데이터의 스키마가 바뀌었는지 | 같아요 | 정의의 새 버전을 병합하면 보류된 위치부터 다시 실행해요 |
| 보류: 기대 조건 | `fail`을 위반한 레코드 | 레코드를 격리하고 보류해요 | 같아요 |
| 정합성 대조 | 전체를 수집해 어긋난 것을 바로잡아요 | 삭제는 4.3의 보이지 않음 규칙을 따라요 | 없음 |

**푸시한 것도 같아요.** 푸시 수집만 하는 소스에서 보류된 동안 수신한 것은 쌓이고, 해제될 때 `ingest_seq`를 받고 한도 있는 배치로 적용돼요.

보류된 동안 쌓이는 변경은 조용히 버려지지 않아요. 쌓인 양이 보관의 한도에 가까워지면 알림이 올라가고, 한도를 넘으면 오래된 것부터 콜드 스토리지(컬럼형 파일을 오브젝트 스토리지에 내려 두는 포트)로 이동해요. 이동할 공간이 없으면, 소스가 소스 커서부터 다시 줄 수 있을 때는 그 소스의 수집을 중지하고 알려요. 다시 줄 수 없으면 계속 수집해 쌓되 가장 높은 심각도로 알려요. 조용히 버리지 않아요. 지연은 신선도에 표시돼요(ADR-0013). 정의를 수정하는 것은 스트림에서도 브랜치와 드라이 런을 거쳐요. 병합되면 그 위치부터 새 정의로 처리돼요.

### 9.3 소스가 거짓으로 알릴 때
수집의 완전성은 수집기가 정직하게 적어야 성립해요. 완전하다고 거짓으로 알리는 소스와 완전성 선언이 만나면 "모른다"가 "없다"로 읽혀요. 대량 사라짐의 안전장치는 일부를 잡지만 조금씩 사라지는 것은 잡지 못해요. 그래서 `expected_count`를 제공할 수 있는 소스에서는 **기대 건수와 수집한 건수의 차이가 임계값을 넘으면 그 피드의 완전성 선언이 자동으로 중지돼요.** 중지된 피드는 "없다"를 말하지 못하고 "모른다"로 돌아가며, 헬스 상태에 표시되고 담당자에게 알려요. 임계값은 기본값 표에 가정으로 둬요. 다시 켜는 것은 `operator`가 차이를 확인한 뒤에 해요.

## 10. 엑셀
위치·전원·냉방을 수집하는 주된 경로예요. 양식(랙 위치, 전원 계통, 냉방 계통)을 내려받아 채우면 매핑 없이 수집해요. 한 행에 장비 하나인 목록 형식을 받고, 격자 형태의 실장도는 읽지 않고 목록 양식을 안내해요.

- **양식**: 시트 하나 = 테이블 하나, 헤더 한 행. 고정 시트 이름과 양식 버전 필드. 숨은 행에 안정 컬럼 ID를 두어 표시 이름을 바꿔도 매핑이 유지돼요. 지어낸 위치 양식의 컬럼: `rack_id`, `u_start`, `u_height`, `device_name`.
- **업로드**는 그 소스를 범위에 가진 `operator`나 `editor`가 해요. `manual_only` 소스의 전체 수집 한 번이에요. 파일의 해시가 같으면 다시 올려도 한 번만 수집하고, 지난 파일과의 차이가 변경으로 보여요. 같은 안전장치를 거쳐요.
- **행의 문제**는 문제로 분류되고 나머지는 진행돼요([파이프라인 설계](pipeline.md) 7절). 파일이 열리지 않거나 상한을 넘거나 압축 검사에 걸리면 불완전한 수집이에요.
- **안전 한도**: 파일 20MB는 파일 소스 어댑터가, 나머지는 소스 정의의 `limits`로 바꿀 수 있는 기본값이에요(압축 해제 256 MiB, 시트당 행 200,000과 열 1,024, 셀 한 칸 32,767자, 공유 문자열 2,000,000개). 넘으면 수집이 실패하고 어느 한도인지 알려요. 시트 수와 압축비의 한도는 두지 않았어요. 수식은 계산하지 않고 저장된 값으로만 읽어요. 매크로 파일(.xlsm)은 데이터만 읽고 매크로는 열지 않으며, 외부 링크는 따라가지 않아요. 옛 .xls, 암호가 걸린 파일, .xlsb, .ods, 깨진 파일은 이유를 밝혀 거절해요.
- **구현(ADR-0040)**: 파서는 라이브러리 없이 표준 라이브러리의 ZIP과 XML로 읽어요. 읽기 어댑터(`adapter.xlsx`)가 워크북을 시트와 셀의 모델로 바꾸고, 시트를 행으로 만드는 일은 `core.ingest`가 해요. 데이터셋의 `sheet` 옵션은 시트(이름 또는 순번), 머리글 행과 머리글 행 수(여러 줄 머리글은 공백으로 이어 컬럼 이름 하나), 데이터 범위, 병합 셀(`first_only`, `fill`), 빈 행의 끝(`stop_after_blank_rows`), 숨긴 행의 제외(`skip_hidden_rows`)예요. 머리글은 앞뒤 공백과 줄바꿈을 정규화해서 비교해요. 행 집계는 CSV와 같고, 문제에는 시트 이름과 셀 주소(`'서버 목록'!F6`)가 붙어요. 오류 셀과 계산된 적 없는 수식은 읽는 컬럼에서만 문제로 보고해요. 날짜 셀은 숫자 서식으로 알아보고 1900과 1904 날짜 체계를 처리해 ISO 8601 글로 바꿔요.
- **양식 이외의 파일도 읽어요**: 제목 줄, 병합 셀, 두 줄 머리글, 빈 행과 소계 행(정제의 `filter`로 제외)이 있는 파일을 위 옵션으로 읽어요. 격자 형태의 실장도는 여전히 읽지 않아요.
- **파일을 먼저 살펴보기**: `praxium ingest inspect -input <파일>`이 CSV, JSON Lines, 엑셀의 프로파일(시트 목록, 추정한 머리글 행, 컬럼별 값의 형태와 빈 값 비율과 고유 값 수와 빈출 값, 처음 몇 행)을 내요. 4절의 "매핑을 만드는 사람을 돕는 API"의 첫 구현이에요([수집 확장](ingestion-extensions.md) 4절). 매핑 제안은 아직 없어요.
- 엑셀의 값은 `declared`이고 등급은 기본 `fact`, 추정 표시가 있으면 `assumed`예요.

## 11. 테스트 자료
- **합성 세계 생성기**: 시드가 같으면 같은 세계가 나와요. 세계를 먼저 만들고 **정답 KG**를 보유하며, 같은 세계에서 **배치 형식**(엑셀 양식, HTTP JSON, SQL 덤프)과 **스트림 형식**(같은 세계의 변화를 이벤트 열로: 교체, 이동, 상태 변화)을 함께 생성해요. 소스 사이의 키가 맞물려 식별과 병합을 테스트할 수 있어요. 시각, ID, 정렬은 주입해서 같은 입력이면 같은 결과예요.
- **결함 주입**: 배치는 스키마 변경, 불완전한 수집, 대량 사라짐, 키 중복, 병합된 셀, 격자 엑셀, 수식 셀, 작은 합성 압축 폭탄, 느린 응답과 오류. 스트림은 중복 전달, 순서 뒤바뀜, 늦게 도착한 이벤트, 재개 실패, 삭제 이벤트 누락, 폭주, 스트림 끊김.
- 프리셋마다 합성 입력 행 → 기대 객체와 링크의 샘플 테스트가 있어야 포함돼요. 이름과 주소는 예시용으로 예약된 것만 쓰고, 실제 데이터는 리포지토리에 두지 않아요.


## 12. 알려진 한계, 미결 사항
- 여러 제품의 내부 동작과 부하 특성, 스트림 소스의 전달 보장은 일부만 확인했어요. 모든 소스가 중복과 순서 뒤바뀜을 일으킨다고 전제해요.
- [기본값 표](defaults.md)에 있는 숫자는 기본값(설정)이고 클로즈드 베타에서 측정해서 수정해요. 표에 없는 숫자(압축비, 시트 수 같은 안전 한도)는 가정이에요.
- 선언만으로 되는 것은 단순한 요청까지예요. 까다로운 소스는 어댑터가 별도로 필요해요.
- 처리 속도는 스토리지 입출력 없이 측정한 작은 프로토타입의 값이에요(합성 데이터, 연결 하나, 복제 없음). PostgreSQL에 변경 배치를 적용하는 속도는 배치 크기에 따라 초당 수만~십만 행이었고 보장하는 값이 아니에요. "초당 2~3만 행"은 논리 변경 수이고(추정), 물리적으로 쓰는 행 수와 WAL의 바이트를 따로 측정해서 셋을 함께 보고 전환해요. 임계값을 넘으면 순서는 이래요. 먼저 쓰기를 줄이는 최적화(`volatile`의 쓰기 감소와 역압)를 하고, 그래도 안 되면 수집 변경 로그를 메시지 로그 스토리지 어댑터로 바꿔요. KG 분할은 쓰기 한계를 푸는 수단이 아니에요(영향 범위는 KG 하나 안에서만 계산해요). 어디서 전환하는지는 측정해서 정해요. 스트림이 보류된 뒤 해제될 때의 적용 지연과, 큰 적용 중 다른 스트림의 적용 지연도 클로즈드 베타에서 측정해요.
- 미결 사항: 수집 엔벨로프의 서명과 파일 드롭이 남아요. 스트림 안전장치의 비율과 윈도우, 배치 크기, `tick`의 간격은 [기본값 표](defaults.md)가 정했어요. 완전성 선언을 자동으로 중지하는 임계값과 주체별 재수집 한도는 기본값 표에 가정으로 둬요.
- 푸시 수집의 보낸 쪽 이벤트 ID는 `dedupe_window`(기본 7일) 안에서만 중복을 막아요. 그보다 늦은 재전송은 키와 내용 해시, 이벤트 시각이 막아요.
