# 현실 데이터 받기 설계

[ADR-0008](adr/0008-ingestion.md)의 결정을 풀어 쓴 문서예요. 데이터의 칸, 상태, 규칙, 지어낸 예시를 담아요. 예시의 서버, 랙, 포트, 주소, 숫자는 모두 지어낸 것이고, 칸의 이름은 예시예요. 객체 타입과 속성의 이름은 표준 모델이 정해요([KG의 모델](kg-model.md)).

## 1. 무엇에 답하나

- 소스가 여럿이고 읽기만 해야 할 때, 무엇을 어떻게 받아야 소스가 다치지 않나요?
- 받은 것을 어떻게 남기면 규칙을 고쳐도 소스에 다시 가지 않고, 같은 입력이면 같은 결과가 나오나요?
- 엑셀 한 장도, 가상화 관리 API도, 읽기 전용 DB도 같은 길로 KG까지 가게 하려면 어디서 모양을 맞추나요?
- 덜 받거나 모양이 바뀐 데이터가 KG를 망가뜨리지 못하게 어디서 막나요?
- 여러 조직이 동시에 규칙을 고칠 때 운영을 어떻게 지키나요?

이 문서가 정하지 않는 것: 식별 규칙 자체([ADR-0007](adr/0007-kg-model.md)), 저장과 적용의 구현([ADR-0009](adr/0009-kg-storage-and-versions.md)), 품질 지표와 신선도([ADR-0011](adr/0011-kg-operations.md)), 도메인과 권한([ADR-0012](adr/0012-domains-and-access.md)). 여기서는 가리키기만 해요.

## 2. 한눈에 보는 흐름

동기화 한 번은 여덟 단계예요. 단계마다 아는 것과 모르는 것이 달라서, 한 단계를 고쳐도 다른 단계가 흔들리지 않아요.

| # | 단계 | 하는 일 | 아는 것 | 모르는 것 |
|---|---|---|---|---|
| 1 | 수집 | 소스에서 받아 원본 기록으로 남겨요. 고치지 않아요 | 소스 접속 | 모델 |
| 2 | 정제 | 닫힌 연산으로 데이터셋을 다듬어요 | 데이터셋 | 접속, 모델 |
| 3 | 매핑 | 컬럼을 객체 타입의 속성에 이어요 | 모델 | 접속 |
| 4 | 식별과 병합 | 같은 것을 알아보고 속성마다 이기는 값을 골라요 | 모델, 식별 이력 | 접속 |
| 5 | 링크 | 링크 정의로 객체를 이어요 | 모델 | 접속 |
| 6 | 차이 | 후보 KG와 지금 버전의 차이를 내요 | KG 버전 | 소스, 정제 |
| 7 | 안전장치 | 멈출지 봐요 | 차이, 규칙 | 소스 |
| 8 | 적용 | 새 버전으로 공개해요 | 저장소 | 소스, 매핑 |

연결 확인(닿는지, 읽기 전용 계정인지, 무엇이 있는지)은 단계가 아니라 필요할 때 하는 점검이에요. "연동과 모델 동기화를 나눈다"는 요구는 1단계와 2~8단계의 경계로 지켜요.

```
 소스(파일, HTTP JSON, SQL)         제품 밖의 수집기
        │ 어댑터 + 프리셋                 │ 수집 봉투
        ▼                                 ▼
 ┌──────────────── 1 수집 ────────────────┐   온전한가? ─ 아니오 ─► 덜 받음, 여기서 멈춤
 │  원본 기록 (고치지 않음, 구간으로 보관)   │
 └───────────────────┬────────────────────┘
                     │ 데이터셋 (행과 컬럼)
   2 정제 ─► 3 매핑 ─► 4 식별과 병합 ─► 5 링크 ─► 6 차이 ─► 7 안전장치 ─► 8 적용 ─► KG의 새 버전
                                                                  │
                                                                  └─ 멈춤 ─► 사람이 본다

 후보 실행 = 받아 둔 원본 기록에서 2~7단계만 돌려요. 소스에도 운영에도 영향이 없어요.
```

## 3. 소스, 어댑터, 프리셋

### 3.1 소스

소스의 역할은 지금 구성 하나라서 역할 칸이 없어요. 소스는 정의의 한 항목이고 주인 도메인이 있어요.

| 칸 | 뜻 |
|---|---|
| source_id | 소스의 바뀌지 않는 이름 |
| domain | 주인 도메인 ([ADR-0012](adr/0012-domains-and-access.md)) |
| adapter | 쓰는 어댑터 (`file`, `http_json`, `sql`, `envelope`) |
| preset | 쓰는 프리셋과 그 버전 (없으면 비워요) |
| connection | 주소 같은, 비밀이 아닌 접속 정보 |
| secret_ref | 비밀 값을 가리키는 참조. 값은 저장하지 않아요 |
| schedule | 주기 (15절) |
| protection | 소스를 지키는 값 (11절) |
| completeness_claims | 타입마다 "이 소스는 이 타입을 전부 준다"는 선언. 선언이 있어야 "링크가 없다"가 "없다"로 읽혀요 ([ADR-0007](adr/0007-kg-model.md)) |
| query | 쿼리 말을 받는 소스의 검색 문장. 소스 항목의 일부라서 버전이 있어요 |

### 3.2 프리셋

프리셋은 소스 제품 하나에 맞춘 순수한 데이터예요. 코드를 실행하지 못해요. 지어낸 가상화 관리 API의 프리셋은 이런 모양이에요.

```
preset_id: virt_manager_demo        version: 3
adapter: http_json
request_template:
  - {id: login,     method: POST, path_template: "/session",          body_shape: {user: ref, password: ref}}
  - {id: list_hosts, method: GET, path_template: "/hosts?page={page}", body_shape: none}
  - {id: list_vms,   method: GET, path_template: "/vms?page={page}",   body_shape: none}
pagination: {kind: page_number, size: 200}
redaction: {drop_fields: [password, token], mask_pattern: [secret, community]}
expected_columns: {hosts: [id, name, cluster, state], vms: [id, name, host_id]}
record_key: {hosts: id, vms: id}
default_mapping: [...]
sample_tests: [cases/normal, cases/missing_page]
```

| 칸 | 뜻 |
|---|---|
| request_template | 허용된 요청의 목록. (메서드, 경로의 틀, 본문의 모양) 단위예요. 읽는 POST도 여기에 있어야만 나가요 |
| pagination | 쪽 넘김 방식 (쪽 번호, 커서, 링크 머리글, 오프셋) |
| redaction | 받을 때 지울 필드와 가릴 필드의 선언 |
| expected_columns | 받은 모양의 기대. 어긋나면 멈춰요 (12절) |
| record_key | 기록 하나를 가리키는 소스 쪽 키. 소스가 키를 안 주면(엑셀) 프리셋이 키를 만드는 규칙을 선언해요. 키가 없으면 행 순서에 기대서 결과가 흔들려요 |
| default_mapping | 기본 매핑 |
| sample_tests | 지어낸 견본으로 도는 시험. 없으면 프리셋을 실을 수 없어요 |

`expected_columns`와 `record_key`는 이 문서가 구체화한 칸이에요. 조사에서 나온 제안을 따랐어요.

### 3.3 어댑터 포트의 메서드

어댑터는 프로토콜을 말하는 코드이고, 코어는 포트로만 어댑터를 불러요. 포트의 메서드는 읽는 것뿐이에요.

| 메서드 | 뜻 |
|---|---|
| check_connection | 닿는지, 계정의 권한이 읽기 전용인지(확인할 수 있는 소스에서만), 무엇이 있는지를 점검해요 |
| list_datasets | 프리셋이 선언한 데이터셋 중 소스에 실제로 있는 것을 알려 줘요 |
| read_dataset | 한 데이터셋을 요청 허용 목록 안에서 읽어 기록을 흘려 주고, 끝에 온전함의 증거(쪽 수, 소스가 알려 준 수, 오류)를 줘요 |

쓰기, 지우기, 고치기는 포트에 없어요. 어댑터 코드가 쓰는 길을 가질 수 없게 구조 검사가 포트의 모양을 지켜요. 수집 봉투를 받는 입구(`envelope`)는 소스를 부르지 않고 받기만 해서 `read_dataset` 대신 봉투를 받아 같은 모양으로 넘겨요.

## 4. 수집의 온전함과 수집 봉투

### 4.1 capture (수집 한 번)

| 칸 | 뜻 |
|---|---|
| capture_id | 수집 한 번의 이름. 봉투를 다시 보내도 같은 것으로 알아봐요 (멱등) |
| source_id, dataset_name | 어느 소스의 어느 데이터셋인지 |
| preset | 쓴 프리셋과 버전 |
| collector | 어댑터와 그 버전, 또는 제품 밖 수집기의 이름과 버전 |
| started_at, finished_at | 받기 시작과 끝 |
| completeness | 온전함의 판정 (4.2) |
| record_count | 받은 기록 수 |
| schema_signature | 필드 경로와 자료형의 묶음. 지난 온전한 수집과 견줘요 |
| redaction | 쓴 가림 규칙의 버전, 지운 필드의 경로 목록 (값은 적지 않아요) |

### 4.2 온전함의 판정

수집 단계가 다음을 보고, 하나라도 어기면 `partial`(덜 받음)이에요. 모두 통과하면 `complete`예요. 덜 받은 수집은 뒤 단계로 가지 않아요.

| 검사 | 어기는 예 |
|---|---|
| 쪽 넘김이 끝까지 갔다 | 7쪽 중 5쪽에서 오류로 끊김 |
| 소스가 알려 준 수와 받은 수가 맞는다 | 소스는 총 1,200건이라는데 1,150건 받음 |
| 지난 온전한 수집보다 기록 수가 크게 줄지 않았다 (가정: 30% 이상 줄면 덜 받음) | 지난번 1,200건, 이번 800건 |
| 요청 수, 바이트, 시간의 예산 안에서 끝났다 | 예산을 넘겨 중단 |
| 검색 결과가 행 수 상한에 닿지 않았다 (쿼리 말 소스) | 상한 5,000행에 정확히 닿음, 잘렸을 수 있음 |

오류를 삼켜 "빈 목록"으로 돌려주는 소스가 있어서 쪽 넘김의 끝과 소스가 알려 준 수를 같이 봐요. 대량 삭제의 실제 원인은 대개 덜 받은 수집이에요.

### 4.3 수집 봉투

제품 밖의 수집기가 보내는 공개된 모양이에요. 형식은 계약 단위가 쥐고 버전이 있어요. 받은 뒤는 다른 소스와 똑같아요.

| 칸 | 뜻 |
|---|---|
| envelope_version | 봉투 형식의 버전 |
| source_id | 보내는 소스. 소스는 미리 등록돼 있어야 해요 |
| capture_id | 수집 한 번의 이름. 같은 것을 다시 보내면 한 번으로 쳐요 |
| dataset_name | 어느 데이터셋인지 |
| collected_at | 수집한 때 |
| collector | 수집기의 이름과 버전 |
| completeness | 수집기가 말하는 온전함: 쪽 수, 소스가 알려 준 총수, 끝까지 갔는지, 오류 |
| redaction | 수집기가 지운 필드의 목록 |
| records | 기록들. 기록마다 natural_key(있으면)와 body(JSON) |
| body_hash | records 전체의 내용 해시. 받는 쪽이 다시 세어 견줘요 |

보내는 쪽은 시스템 계정이고 권한은 [ADR-0012](adr/0012-domains-and-access.md)가 정해요. 받는 쪽도 온전함을 스스로 한 번 더 봐요(기록 수가 지난번보다 크게 줄었는지). 봉투를 보내는 수집기 안의 코드는 정의 밖에 있어서, "같은 입력이면 같은 결과"는 봉투를 받은 뒤부터 성립해요.

## 5. 원본 기록과 구간 모델

원본 기록은 raw_record 한 줄이 기록 하나예요. 소스의 자연 단위(API 객체 하나, SQL 행 하나, 시트의 행 하나)로 쪼개 JSON 그대로 두고, 겹친 구조는 수집 때 펴지 않아요(펴는 일은 정제가 해요).

| 칸 | 뜻 |
|---|---|
| raw_record_id | 기록 줄의 이름 |
| source_id, dataset_name | 어느 소스의 어느 데이터셋인지 |
| natural_key | 소스 쪽 키 |
| content_hash | 가림을 마친 뒤 body의 해시. 비밀 값이 해시에 새지 않아요 |
| first_seen, last_seen | 처음 본 수집 ~ 마지막으로 본 수집 (구간) |
| body | 받은 모양 그대로의 JSON |

내용이 같으면 새 줄을 만들지 않고 last_seen만 늘려요. 내용이 바뀌면 새 줄이에요. 구간의 끝은 온전한 수집의 번호이고, 덜 받은 수집의 번호는 건너뛰어요(가정, 19절).

지어낸 예시예요. 수집 1~6번 중 4번만 쪽 넘김이 끊겨 덜 받음이에요.

| natural_key | content_hash | first_seen | last_seen | body (줄임) |
|---|---|---|---|---|
| srv-001 | h1 | 1 | 3 | 랙 R01 |
| srv-001 | h2 | 5 | 6 | 랙 R02 (랙을 옮김) |
| srv-002 | h3 | 1 | 2 | 랙 R01 |
| srv-003 | h4 | 3 | 6 | 랙 R03 (3번 수집부터 보임) |

- 수집 2번 때의 모습 = first_seen ≤ 2 ≤ last_seen인 줄: srv-001(h1), srv-002(h3).
- 수집 5번 때의 모습: srv-001(h2), srv-003(h4). srv-002는 없어요.
- srv-002는 온전한 수집 3, 5, 6번에서 안 보여요. 4번은 덜 받음이라 세지 않아요. 6번에서 잇달아 3번째라서 물러난 것으로 표시돼요(12절). 4번 때문에 srv-002가 사라진 것으로 읽히지 않아요.
- srv-001의 랙이 R01에서 R02로 바뀐 이력이 두 줄로 남아요. 사라졌다 같은 내용으로 다시 나타나면 새 구간이에요.

원본 기록에는 보관 기한이 있고(값은 [ADR-0009](adr/0009-kg-storage-and-versions.md)), 기한이 지나면 그 수집으로는 다시 돌릴 수 없어요. 한 수집을 한 데이터셋으로 보는 것은 "그 수집 때의 모습의 줄들을 행으로, 최상위 필드를 컬럼으로" 읽는 것이에요.

## 6. 정제의 열네 연산

정제는 데이터셋을 받아 데이터셋을 내요. 연산은 이 열넷이 전부이고, 모두 순수해요(같은 입력이면 같은 출력, 순서에 기대는 곳은 정렬 키를 적어요). 사용자 코드는 없어요. 걸러 낸 행은 사라지지 않고 "규칙이 걸러 냄"으로 세어져요(13절).

| # | 연산 | 입력 | 출력 | 한 줄 예시 |
|---|---|---|---|---|
| 1 | 행으로 펼치기 | 배열이나 맵이 든 컬럼 | 원소마다 한 행 | 서버 한 행의 nics 배열 2개 → 2행 |
| 2 | 컬럼으로 모으기 (피벗) | 키 컬럼과 값 컬럼 | 키마다 한 컬럼 | (서버, 항목, 값) 세 컬럼 → 서버 한 행에 항목별 컬럼 |
| 3 | 컬럼 나누기 | 컬럼 하나, 구분자나 자리나 패턴 | 컬럼 여럿 | "R01-U12" → rack_code "R01", u_start 12 |
| 4 | 조인 | 데이터셋 둘, 키 | 한 데이터셋 | 서버 NIC 행에 케이블 목록의 상대 포트를 붙임 |
| 5 | 유니언 | 모양이 같은 데이터셋들 | 아래로 쌓은 데이터셋 | 엑셀 시트 둘의 서버 목록을 한 표로 |
| 6 | 고르기 (필터) | 데이터셋, 조건 | 조건에 맞는 행 | state가 "폐기"인 행을 뺌 |
| 7 | 빈 값 채우기 | 컬럼 | 빈 칸을 바로 위 행의 값으로 채운 컬럼 | 합친 셀에서 비어 내려온 rack_code를 채움 |
| 8 | 값 바꾸기 | 컬럼, 순수 함수의 이름 | 바꾼 컬럼 | 소비전력 "1.2 kW" → 1200 W (단위 바꾸기 함수) |
| 9 | 컬럼 고르기와 이름 바꾸기 | 컬럼 목록과 새 이름 | 줄인 데이터셋 | name만 남기고 hostname으로 이름 바꿈 |
| 10 | 자료형으로 읽기 | 글자 컬럼, 자료형과 단위 | 날짜, 수 컬럼 | "2026-03-01" → 날짜 / "1,200W" → 수 1200, 단위 W |
| 11 | 겹친 행 없애기 | 키 컬럼 | 키마다 한 행 | 같은 일련번호가 두 번 나온 행을 하나로 |
| 12 | 표에서 찾아 바꾸기 | 컬럼, 코드표 데이터셋 | 찾아 바꾼 컬럼 | 제조사 코드 "A1" → "Acme" |
| 13 | 정규식으로 뽑기 | 컬럼, 정규식 | 뽑은 컬럼 | "srv-001.example.test" → "srv-001" |
| 14 | 이어 붙이기 | 컬럼 여럿, 구분 글자 | 한 컬럼 | rack_code "R01" + u_start 12 → "R01-12" |

- 5번(유니언)은 행을 쌓고, 14번(이어 붙이기)은 한 행 안의 값들을 한 글로 이어요. 둘은 다른 일이에요.
- 8번이 쓰는 함수는 검토를 거쳐 제품에 들어 있는 목록에서만 골라요. 시간, 난수처럼 결과가 흔들리는 함수는 목록에 없어요.
- 집계(합, 평균)와 식을 쓰는 파생 컬럼은 없어요. 필요하면 소스 쪽에서 하거나 새 연산을 결정 기록으로 더해요.
- 정제의 결과도 데이터셋이라서, 정제는 여러 단으로 이어질 수 있어요.

## 7. 매핑과 식별 키 잇기

### 7.1 매핑의 칸

| 칸 | 뜻 |
|---|---|
| mapping_id, domain | 매핑의 이름과 주인 도메인 |
| dataset | 읽는 데이터셋 (하나 이상) |
| object_type | 만들 객체 타입 |
| identity_keys | 식별 키에 쓰는 컬럼들. 우선순위와 다듬기 규칙을 같이 적어요 |
| parent | 딸린 객체(포트, 부품)의 부모 객체와 그것을 가리키는 컬럼. 딸린 객체는 부모의 문맥 안에서 식별해요 |
| attributes | 컬럼 → 속성. 단위와 자료형을 같이 적고, 쓰지 않는 컬럼은 "버림"이라고 적어요 |

행마다 객체 후보가 하나 나와요. 같은 식별 키의 후보는 4단계에서 한 객체가 돼요.

### 7.2 식별 키 잇기의 예

엑셀 위치 대장(소스 A)과 가상화 관리 API(소스 B)가 같은 서버를 서로 다르게 적어요.

| 소스 | 컬럼 | 받은 값 | 다듬은 값 |
|---|---|---|---|
| A (위치 대장) | serial_no, hostname, rack_code | "SN-0042", "SRV-001", "R01" | 일련번호 "sn-0042", 이름 "srv-001" |
| B (관리 API) | serial, name, cluster | "sn-0042", "srv-001.example.test", "c1" | 일련번호 "sn-0042", 이름 "srv-001" |

`PhysicalServer`의 식별 키는 일련번호(1순위)와 이름(2순위)이에요. 다듬기는 대소문자, 공백, 도메인 꼬리를 정해진 대로 다듬는 것뿐이고, 받은 값은 지우지 않아요. 두 행은 일련번호가 같아서 한 객체가 돼요. 이름도 같게 다듬어져서 확인이 겹쳐요.

속성 `rack_code`는 소스 A가 "R01", 소스 B가 "R02"라면 충돌이에요. 속성마다 이기는 소스가 정해져 있으면(위치는 A) A의 값이 이기고, 진 값은 버리지 않고 충돌로 문제 목록에 보여요.

딸린 객체의 예: 스위치 `sw-01`의 포트는 "Ethernet1/1", "Eth1/1", "Et1/1" 같은 표기로 와요. 포트 이름의 표기를 다듬은 값과 부모 `sw-01`이 식별 키예요. 다른 스위치에도 같은 이름의 포트가 있지만 부모가 달라서 섞이지 않아요.

## 8. 링크 정의

링크 정의는 링크 타입마다 하나 이상이고, 칸은 이렇게 있어요.

| 칸 | 뜻 |
|---|---|
| link_def_id, domain | 링크 정의의 이름과 주인 도메인. 도메인을 가로지르면 플랫폼의 정의이거나 양쪽이 승인해요 ([ADR-0012](adr/0012-domains-and-access.md)) |
| link_type | 만들 링크 타입 (그 링크의 뜻은 타입이 가져요) |
| from_type, to_type | 양 끝의 객체 타입 |
| condition | 조건의 종류 여섯 중 하나와 그 매개 값 |

만든 링크의 근거 등급과 근거의 종류는 [ADR-0007](adr/0007-kg-model.md)을 따라요. 한 끝에 맞는 상대가 둘 이상이면 잇지 않고 못 이은 링크로 문제 목록에 보내요. 아래 타입 이름은 예시예요.

| 조건 | 지어낸 예 | 결과 |
|---|---|---|
| 다듬은 키가 같다 | VM 행의 host_name "SRV-001"과 서버의 이름 "srv-001"이 다듬으면 같다 | `vm-9` HOSTED_ON `srv-001` (뜻: `runs_on`) |
| 목록에 들어 있다 | 케이블 목록의 한 행에 (srv-001의 eth0, sw-01의 Ethernet1/1)이 같이 있다 | `srv-001:eth0` CONNECTED_TO `sw-01:Ethernet1/1` (뜻: `connected_to`) |
| 범위에 든다 | 서버의 관리 주소 192.0.2.17이 대역 192.0.2.0/24에 든다 | `srv-001` ADDRESSED_IN `net-mgmt` (뜻: `contained_in`) |
| 자리가 맞는다 | 서버 srv-001은 랙 R01의 U12부터 2칸. R01은 42칸이고 U12~13은 비어 있다 | `srv-001` LOCATED_IN `R01` (뜻: `contained_in`). U44라면 안 이어지고 문제 목록에 가요 |
| 부모가 같다 | 전원공급장치 `psu-1`, `psu-2`와 전원 묶음 `srv-001-power`가 모두 부모 `srv-001`을 갖는다 | `psu-1`, `psu-2` MEMBER_OF `srv-001-power` (뜻: `member_of`) |
| 다른 링크를 따라간 끝이 같다 | `srv-001:eth0`도 `sw-01:Ethernet1/1`도 각자의 케이블 행으로 같은 패널 배선 `pp-07`에 닿는다. 둘의 직접 선은 소스에 없다 | `srv-001:eth0` CONNECTED_TO `sw-01:Ethernet1/1` |

"자리가 맞는다"에서 두 장비가 같은 U를 차지하면 둘 다 한 칸에 맞는 것이라 잇지 않고 문제 목록에 둬요. 5번째 줄의 전원 묶음은 `min_alive`를 소스가 말하면 `fact`, 소스에 없으면 `unknown`이에요. 소스에 없는 값을 가정으로 메우지 않아요.

링크 정의가 가져오는 이웃이 모델에 없는 타입이면(예: 등록하지 않은 장비) 객체를 새로 만들지 않고 숫자로만 세요.

## 9. 식별과 병합 단계가 하는 일

식별 규칙 자체는 [ADR-0007](adr/0007-kg-model.md)이 정했어요. 여기서는 단계가 하는 일의 순서만 적어요.

1. 매핑이 낸 객체 후보(타입, 식별 키들, 속성 값, 소스, 도메인)를 받아요.
2. 정해진 다듬기로 식별 키 값을 다듬어요. 받은 값은 지우지 않아요.
3. 파이프라인 정의의 예외 목록을 먼저 적용해요(사람이 정한 "같다"와 "다르다").
4. 타입의 식별 키를 우선순위 순서로 견줘 식별 이력에서 기존 객체를 찾아요. 있으면 그 내부 ID를 쓰고, 없으면 처음 본 식별 키에서 결정적으로 새 ID를 내요.
5. 후보 하나가 기존 객체 둘 이상에 맞거나 반대면 합치지 않고 식별 후보로 문제 목록에 보내요. 확률로 맞춘 후보는 제안일 뿐 저절로 합치지 않아요.
6. 같은 내부 ID로 모인 후보들의 속성마다 이기는 소스의 값을 골라요. 진 값은 충돌로 문제 목록에 보여요.
7. 합치기와 가르기는 이력에 남기고, 합쳐서 물러난 ID는 남은 ID를 가리키게 해요.
8. 물러남을 표시해요. 온전한 수집에서 잇달아 안 보이면(가정: 3번) 물러난 것으로 표시하고, 덜 받은 수집의 번호는 세지 않아요. 소스에서 안 보이는 것과 물러난 것은 달라요.
9. 객체(내부 ID, 속성, 근거 등급, 원본 기록 참조, 규칙 버전)를 다음 단계로 넘겨요.

## 10. 읽기 전용 세 겹

| 겹 | 무엇 | 누가 지키나 | 뚫리면 |
|---|---|---|---|
| 첫째 | 프리셋의 요청 허용 목록: (메서드, 경로의 틀, 본문의 모양) | 제품의 코드. 프리셋을 실을 때와 요청을 만들 때 | 목록 밖의 요청은 만들어지지 않아서 여기서는 뚫리지 않아요 |
| 둘째 | 소스 쪽 계정이 읽기 전용 | 소스를 쥔 쪽. 연결할 때 관리자가 확인하고, 어댑터가 확인할 수 있으면 권한도 점검해요 | 첫째만 남아요. 첫째의 목록에 읽는 요청만 있게 검토해요 |
| 셋째 | 어댑터 포트에 쓰는 메서드가 없음 | 구조 검사 | 코드가 쓰는 길을 가지려 하면 검사가 실패해요 |

- 메서드만 보는 방식(GET만)은 로그인, 검색 작업 만들기, GraphQL 같은 읽는 POST를 막거나, 허용하면 무방비가 돼서 쓰지 않아요.
- SQL은 조회만 되는 역할을 써요. 읽기 전용 트랜잭션 설정은 되돌릴 수 있어서 경계가 아니에요. 가능하면 읽기용 복제본에 연결해요.
- 어댑터가 권한을 확인하지 못하는 소스는 관리자의 확인에 기대요. 읽기 전용 계정을 만들 수 없는 소스는 수집 봉투로 받는 길이 있어요(넘겨받은 설계의 방향이고, 이 문서가 새로 정한 것은 아니에요).

### 쿼리 말 소스의 허용 명령 검사

검색은 관리자가 자유롭게 적고, **저장할 때** 이렇게 검사해요. 후보 실행과 병합 직전에도 같은 검사를 다시 해요.

1. 검색 문장을 명령 단위로 나눠요.
2. 모든 명령이 어댑터가 가진 **허용된 명령의 목록**에 있어야 해요. 목록에 없는 명령, 해석하지 못한 명령은 거절해요(차단 목록이 아니에요).
3. 하위 검색, 매크로, 저장된 검색의 호출처럼 문장 밖의 내용을 끌어오는 것은 목록에 명시한 것만 허용해요.
4. 시간 범위와 결과 행 수 상한이 있어야 하고, 기대하는 컬럼을 같이 선언해요(빈 컬럼은 결과에서 빠지는 소스가 있어요).

지어낸 검색의 예예요: `search index=hw status=down | table host, rack`은 통과해요. `... | outputlookup hosts.csv`나 `... | delete`는 명령이 허용 목록에 없어서 저장되지 않아요. 한 검색 제품은 `collect`, `delete`, `outputlookup`, `run`, `script`, `sendalert`, `sendemail` 같은 14개를 위험 명령으로 분류하지만([출처](https://help.splunk.com/en/splunk-enterprise/administer/manage-users-and-security/10.4/best-practices-for-splunk-platform-security/spl-safeguards-for-risky-commands/commands-that-trigger-spl-safeguards)), 이것은 차단 목록이라서 모르는 명령을 막지 못해요. 허용 목록의 내용은 이 어댑터를 더하는 결정 기록에서 정해요. 이 검사가 안 막는 것은 소스 쪽 계정으로 막아요(둘째 겹이 본선이에요).

## 11. 소스를 지키는 값

소스마다 정의의 항목으로 있고, 아래 기본값은 모두 **가정**이에요(재지 않았어요). 프리셋과 관리자는 기본값보다 낮게만 덮어쓸 수 있다고 보지만 이것도 가정이에요. 일꾼이 여러 벌이어도 소스마다의 상한은 지켜요.

| 값 | 뜻 | 기본값 (가정) |
|---|---|---|
| max_concurrency | 소스마다 동시 요청 상한 | 1 |
| rate_limit | 초당 요청 수 상한 | 5 이하 |
| retry | 물러났다 다시 하기: 간격을 늘려 가며, 소스가 말한 대기 시간은 존중해요 | 3번 |
| timeouts | 접속, 읽기 제한 시간 | 10초, 60초 |
| breaker | 잇달아 실패하면 끊기. 끊은 뒤 일정 시간 지나면 한 건만 시험해요 | 잇달아 5번 실패, 5분 뒤 시험 |
| auth_failure | 인증 실패(401, 403)는 다시 하지 않고 바로 끊어요. 계정이 잠기지 않게요 | 바로 끊기 |
| allowed_window | 받아도 되는 시간대. 밖이면 건너뛰고 기록해요 | 항상 |
| budget | 동기화 한 번의 요청 수, 바이트, 시간 상한. 넘기면 중단하고 덜 받음으로 표시해요 | 정하지 않음 |
| secret_ref | 비밀 값을 가리키는 참조. 값은 저장하지 않고 되돌려 주지 않고 로그에 찍지 않아요 | 필수 |

## 12. 안전장치

숫자는 모두 기본값이고 가정이에요. 멈추면 새 KG 버전이 안 만들어지고 마지막 정상 버전이 그대로 남아요. 사람의 역할(운영, 편집, 승인)은 [ADR-0012](adr/0012-domains-and-access.md)가 정해요.

| 장치 | 무엇을 보나 | 멈추면 생기는 일 | 사람이 하는 일 |
|---|---|---|---|
| 덜 받음 | 4.2의 검사 | 그 수집은 뒤로 가지 않고, 신선도가 나빠져요 | 소스 상태와 예산을 보고 다시 돌려요 |
| 같음 | 입력이 지난번과 같은가 (원본 기록과 정의가 같음) | 멈추는 것이 아니라 새 버전을 안 만들어요 | 없음 |
| 첫 적용 | 처음이거나 정의를 고친 뒤 첫 적용인가 | 동기화가 "사람 확인 기다림"에 들어요 | 차이를 보고 적용을 확인해요 (운영 역할) |
| 받은 모양 바뀜 | 컬럼 빠짐, 자료형 바뀜 (expected_columns, schema_signature) | 수집은 되고 매핑에서 멈춰요. KG는 그대로예요 | 소스가 바뀐 것이면 정의를 브랜치에서 고쳐 후보 실행으로 확인해요 |
| 대량 사라짐 | 소스와 타입마다 사라진 객체 수. 10% 이상이면서 5건 이상이거나, 500건 이상 (가정) | 멈춰요 | 차이에서 무엇이 사라졌는지 보고, 원인(소스, 정의)을 고쳐요 |
| 안 보임 | 온전한 수집에서 잇달아 안 보임 (3번, 가정) | 멈추지 않고 물러난 것으로 표시해요. 이력에 남아요 | 없음. 되살아나면 표시가 풀려요 |
| 연속 실패 | 잇달아 실패한 수 | 그 소스의 일정을 멈추고 알려요 (ADR-0011: 다시 하기 3번, 잇달아 5번, 가정) | 접속 정보, 소스 상태를 보고 일정을 다시 켜요 |
| 인증 실패 | 401, 403 | 다시 하지 않고 소스를 끊어요 | 자격 증명을 바꾸고 다시 이어요 |

분모는 소스와 타입마다 따로 세는 것으로 가정해요(조사 보고서의 제안이고 19절에 열려 있어요). 하루에 조금씩(예: 9%씩) 사라지는 것은 이 장치로는 안 걸려요. 품질 지표와 신선도가 그 몫을 해요([ADR-0011](adr/0011-kg-operations.md)).

## 13. 수 맞춤

원본 기록 하나는 끝에 넷 중 하나로 분류돼요. 넷의 합은 받은 수와 같아요.

| 분류 | 뜻 |
|---|---|
| 쓰임 | 객체나 링크 하나 이상에 기여했어요 |
| 규칙이 걸러 냄 | 고르기 같은 규칙이 뺐어요. 어느 규칙인지 적어요 |
| 문제 | 풀지 못한 일이 있어요. 어느 문제인지 적어요 |
| 안 쓰임 | 어느 매핑과 링크 정의도 쓰지 않았어요 |

한 기록이 여러 분류에 걸리면 이 순서로 하나에 넣어요(구체화한 것이고 19절에 열려 있어요): 쓰임, 문제, 규칙이 걸러 냄, 안 쓰임. 그래서 문제 목록의 항목 수와 "문제"로 분류된 기록 수는 다를 수 있어요. 기록이 쓰이면서 문제 항목(못 이은 링크)을 낼 수 있어요.

단계 사이의 계산은 **원본 기록 단위**로 세요. 행이 펼치기로 늘어나도, 조인으로 합쳐져도 행마다 어느 원본 기록에서 나왔는지의 참조를 들고 다니기 때문이에요. 단계마다 "들어온 원본 기록 수 = 나간 원본 기록 수 + 떨어진 수(이유와 함께)"가 맞아야 해요.

**예 1. 한 행이 객체도 링크도 되는 경우.** 서버 목록 120행을 받았어요.

| 분류 | 건수 | 내용 |
|---|---|---|
| 쓰임 | 100 | 100행 모두 서버 객체가 되고, 그중 96행은 랙에 이어지는 링크도 만들었어요. 한 행은 한 번만 세요 |
| 규칙이 걸러 냄 | 8 | "폐기"를 빼는 고르기 |
| 문제 | 7 | 식별 키가 빈 행 4, 자료형이 틀린 행 3 |
| 안 쓰임 | 5 | 메모만 있는 행 |

100 + 8 + 7 + 5 = 120이에요. 랙을 못 찾은 4행은 서버로는 쓰였고 못 이은 링크 4건이 문제 목록에 있어요.

**예 2. 펼치기와 조인 뒤.** 서버 목록 2행(srv-001은 NIC 2개, srv-002는 1개)과 케이블 목록 4행을 받았어요.

| 단계 | 들어온 원본 기록 | 나간 원본 기록 | 떨어진 수와 이유 |
|---|---|---|---|
| 행으로 펼치기 | 2 | 2 (행은 3으로 늘어요) | 0 |
| 조인 (포트 키) | 2 + 4 = 6 | 2 + 3 = 5 | 1 (케이블 행의 상대 srv-009가 없어요) |

케이블 목록은 쓰임 3, 문제 1(상대가 없는 링크)로 합이 4예요. 서버 목록은 쓰임 2예요. 서버의 NIC 포트 3개가 딸린 객체가 되고, 두 소스의 기록이 한 객체로 합쳐지면 두 기록 모두 쓰임이에요.

수 맞춤이 어긋나면 어딘가에서 기록이 조용히 사라진 것이에요. 어긋남을 어떻게 다룰지는 19절에 열려 있어요.

## 14. 정의의 버전, 브랜치, 후보 실행, 병합

### 14.1 정의의 항목

정의는 낱개의 항목으로 나뉘어 있고 항목마다 버전과 주인 도메인이 있어요. 그래서 여러 조직이 동시에 고쳐도 부딪치는 곳이 항목 단위로 좁아요.

| 항목 종류 | 예 |
|---|---|
| source | 소스 하나 (비밀은 참조만) |
| dataset | 정제를 적은 데이터셋 하나 |
| mapping | 매핑 하나 |
| identity_rule | 타입의 식별 규칙과 예외 목록 |
| link_def | 링크 정의 하나 |
| guard_values | 안전장치의 값 |
| type_registry | 도메인이 더한 타입 ([ADR-0007](adr/0007-kg-model.md)) |

항목마다 item_id, kind, domain, version, content, base_version(어느 버전 위에서 고쳤나), changed_by, reviewed_by가 있어요.

### 14.2 브랜치의 상태

```
 열림 ─ 후보 실행 ─► 차이 확인 ─ 검토 요청 ─► 검토 중 ─ 승인 ─► 병합 가능 ─ 병합 직전 재실행 ─► 병합됨
  ▲                       │                     │ 반려                 │ 부딪침, 안전장치가 멈춤
  └───────── 고침 ◄────────┴─────────────────────┴──────────────────────┘
  (버리면 닫힘)
```

| 상태 | 뜻 |
|---|---|
| 열림 | 정의를 고치는 중이에요. 여럿이 동시에 열 수 있어요 |
| 차이 확인 | 후보 실행을 마쳤어요. 정의의 차이(항목 단위)와 KG의 차이를 봐요 |
| 검토 중 | 승인을 기다려요. 고친 사람은 승인하지 못해요 |
| 병합 가능 | 항목의 주인 도메인에서 다른 사람이 승인했어요 |
| 병합됨 | 정의가 새 버전으로 운영에 들어왔어요 |
| 닫힘 | 버렸어요 |

**후보 실행**은 받아 둔 원본 기록과 브랜치의 정의로 2~7단계를 돌려요(소스에 다시 가지 않아요). 후보 KG를 만들어 지금 버전과의 차이를 보여요. 차이의 예: 객체 +12 / -0 / 속성 바뀜 340, 링크 +1,180 / -8, 문제 31건 → 3건, 안 쓰임 2,360행 → 14행. 운영에는 영향이 없고, 후보 KG는 배포 하나가 운영 KG와 함께 가질 수 있어요([ADR-0009](adr/0009-kg-storage-and-versions.md)).

**병합 직전**에 운영의 최신 정의 위에서 후보 실행을 다시 하고 같은 안전장치를 거쳐요. 이 한 번이 항목 사이의 의존을 잡아요.

**부딪침**:
- 같은 항목을 두 브랜치가 고쳤으면 늦은 쪽이 멈추고, 사람이 어느 쪽을 쓸지 골라요. 글자 단위로 합치지 않아요.
- 다른 항목을 고친 두 브랜치는 항목 단위로는 부딪치지 않아요. 예: 브랜치 X가 데이터셋 `hosts_clean`의 컬럼 이름을 rack_code에서 rack으로 바꾸고, 브랜치 Y가 rack_code를 읽는 매핑을 더했어요. 둘 다 따로는 통과해요. 나중에 병합하는 쪽이 병합 직전 후보 실행에서 컬럼을 못 찾아 멈추고, 사람이 고쳐요.

**되돌리기**는 이전 정의를 새 버전으로 다시 병합하는 것이에요. 같은 검토를 거쳐요.

**정의를 파일로 내보내고 들이기**: 정의의 항목을 글로 된 형식으로, 정해진 순서(항목 이름 순, 칸 순서 고정)로 적어요. 같은 정의면 같은 글이 나와요. 비밀 값은 들어 있지 않고 참조만 있어요. 조직이 자기 저장소에서 따로 관리하고 싶을 때의 길이에요. 들인 정의는 운영을 직접 바꾸지 못하고 브랜치가 돼요(정의는 병합으로만 운영에 들어오기 때문이에요). 파일의 글 형식은 계약 단위가 정해요.

## 15. 동기화 실행 기록과 일정

### 15.1 실행 기록

동기화 한 번은 sync_run 하나예요. 기록은 추가만 해요.

| 칸 | 뜻 |
|---|---|
| run_id | 실행의 이름 |
| source_id | 어느 소스인지 |
| trigger | 일정, 손으로, 후보 실행 |
| definition_version | 쓴 정의의 버전 |
| status | 아래 상태 |
| started_at, finished_at | 시작과 끝 |
| stages | 단계마다 이름, 시작, 끝, 들어온 수, 나간 수, 떨어진 수와 이유 |
| capture_id, completeness | 쓴 수집과 온전함의 판정 |
| accounting | 13절의 넷 분류 |
| guard_results | 안전장치마다 판정과 까닭 |
| awaiting | 사람 확인을 기다리는 일과 필요한 역할 |
| kg_version_id | 만든 KG 버전. 없으면 비어 있어요 |
| error_code | 오류의 코드와 단계. 비밀 값과 행의 내용은 넣지 않아요 |

### 15.2 상태

| 상태 | 뜻 |
|---|---|
| 대기 | 일정이 되었거나 눌러서 줄에 섰어요 |
| 도는 중 | 단계를 밟고 있어요 |
| 사람 확인 기다림 | 첫 적용처럼 사람이 차이를 보고 확인해야 해서 쉬고 있어요 |
| 멈춤 | 안전장치가 멈췄어요. 마지막 정상 버전이 남아요 |
| 끝남 | 새 KG 버전을 만들었거나, "바뀐 것 없음"으로 끝났어요 |
| 실패 | 접속 실패나 시간 초과로 끝까지 못 갔어요. 다시 하기를 다 썼어요 |

```
 대기 ─► 도는 중 ─► 끝남
            │  ├──► 사람 확인 기다림 ─ 확인 ─► 도는 중
            │  │                   └ 거절 ─► 멈춤
            │  ├──► 멈춤        (안전장치)
            │  └──► 실패        (접속, 시간 초과)
```

같은 소스의 동기화는 한 번에 하나만 돌아요(같은 일정이 두 번 걸리지 않게 키로 막아요). 멈춤과 실패의 기록은 지우지 않고, 고친 뒤 새 실행을 만들어요.

### 15.3 일정

| 종류 | 칸 | 뜻 |
|---|---|---|
| manual | 없음 | 손으로만. 엑셀 올리기가 여기에 들어요 |
| interval | every | 간격마다 |
| fixed_time | times | 정해진 시각 (예: 매일 새벽 3시) |

프리셋은 기본 주기를 제안할 수 있어요. 간격의 하한은 정하지 않았어요(19절).

### 15.4 지표와 로그

지표는 흔히 쓰는 형식의 주소로 내고, 이름표는 소스까지만 붙여요. 단계마다 걸린 시간과 수, 받은 기록 수, 못 이은 링크 수, 연속 실패 수, 신선도를 내요. 로그에는 실행, 소스, 단계의 이름표와 수만 찍고 비밀 값과 행의 내용, 요청의 머리글과 본문은 찍지 않아요.

## 16. 엑셀 양식과 안전 한도

엑셀은 위치, 전원, 냉방의 주된 길이에요. 양식(위치, 전원, 냉방)을 내려받아 채우면 매핑 없이 받아요.

양식의 규칙은 조사에서 나온 제안을 따랐어요. 한 시트에 표 하나, 헤더는 한 행, 시트 이름과 양식 버전을 고정해요. 숨긴 행에 컬럼의 고정 ID를 두어서 표시 이름을 바꿔도 이어져요. 목록 형식은 한 줄에 장비 하나예요.

| rack_id | u_start | u_height | device_name | serial_number |
|---|---|---|---|---|
| R01 | 12 | 2 | srv-001 | SN-0042 |
| R01 | 14 | 1 | srv-002 | SN-0043 |

양식 밖의 모양은 읽지 않고 안내해요.

| 모양 | 하는 말 | 나가는 길 |
|---|---|---|
| 실장도(랙 그림 격자) | "이 시트는 랙 그림처럼 보여요" | 목록 양식으로 옮겨 올려요 |
| 범위를 적은 셀("A열~D열") | "이 셀은 범위예요. 하나씩 적어야 읽어요" | 구역마다 한 행인 양식 |
| 합친 셀 | 값은 왼쪽 위 셀에만 있어요 | 정제의 빈 값 채우기로 채워요 |

파일 올리기는 수동 동기화 한 번이고 파일 바이트의 해시를 남겨요. 지난 파일과의 차이를 보이고 같은 안전장치를 거쳐요. 오류는 시트, 행, 열, 규칙, 기대한 값, 받은 값으로 보여요. 치명 오류가 하나라도 있으면 전체를 거절하고 경고는 허용하는 것을 기본으로 삼아요(제안).

안전 한도는 다음과 같아요. **모두 가정**이에요.

| 한도 | 기본값 (가정) |
|---|---|
| 파일 크기 | 20MB |
| 압축 푼 크기 | 200MB |
| 압축비 | 100 대 1 |
| 시트 수 | 50 |
| 시트당 셀 수 | 1,000,000 |
| 수식 | 평가하지 않고 저장된 값으로만 읽어요 |
| 지원하지 않는 모양 | 매크로 파일(.xlsm), 옛 형식(.xls), 외부 링크와 외부 데이터 연결 |

파서는 포트 뒤에 두고 버전을 고정해요. 파서가 하는 일은 파일을 중간 표로 바꾸는 것까지로 줄여요. 압축 파일 검사(항목 수, 푼 크기, 경로)는 파서에 넘기기 전에 따로 해요. 엑셀로 되돌려 줄 일이 생기면 `=`, `+`, `-`, `@`로 시작하는 셀을 이스케이프해요.

## 17. 시험 자료

| 자료 | 뜻 | 시험 파일 |
|---|---|---|
| 지어낸 세계 생성기 | 씨앗을 고정한 난수로 설비-랙-서버-스위치와 포트-가상화-컨테이너-서비스의 정답 KG를 먼저 만들고, 같은 세계에서 엑셀, HTTP JSON(지어낸 서버의 응답), SQL 행을 뽑아내요 | 예정 |
| 흩뜨리는 장치 | 정답에서 소스의 모양을 일부러 망가뜨려요 | 예정 |
| 프리셋 견본 시험 | 프리셋마다 지어낸 입력과 기대 결과 | 예정 |
| 종단 시험 | 소스들에서 받아 만든 KG가 정답 KG와 맞는지, 같은 입력을 두 번 돌려 같은 KG 버전이 나오는지 | 예정 |

소스 사이의 키가 맞물려서 식별과 병합을 시험할 수 있고, 정답이 있어서 끝까지 맞는지 봐요. 같은 씨앗이면 같은 세계가 나와요.

| 흩뜨리는 장치 | 하는 일 | 시험하는 것 |
|---|---|---|
| 모양 바뀜 | 컬럼을 빼거나 자료형을 바꿔요 | 받은 모양 바뀜에서 멈춤 |
| 덜 받음 | 쪽을 빼거나 중간에 끊어요 | 덜 받은 수집이 뒤로 안 감 |
| 대량 사라짐 | 객체를 한꺼번에 뺀 수집을 만들어요 | 대량 사라짐에서 멈춤 |
| 합친 셀 | 엑셀의 셀을 합쳐요 | 빈 값 채우기, 양식 안내 |
| 수식 | 수식이 든 셀, `=`로 시작하는 셀을 넣어요 | 값으로만 읽기 |

조사에서 나온 제안으로 일련번호 겹침, 느린 응답과 요청 한도 응답(429, 503), 아주 작은 합성 압축 폭탄도 더해요. 식별자는 예약된 이름(`example.test` 꼴)과 문서용 주소 대역(192.0.2.0/24 꼴)만 쓰고, 일련번호와 MAC은 누가 봐도 가짜인 꼴로 만들어요. 이 관례는 널리 알려진 것인데 원문을 열어 확인하지는 않았어요. 시간과 UUID와 정렬은 고정 시계와 씨앗으로 넣어서 결정성을 시험해요. 실제 데이터는 저장소에 두지 않아요([ADR-0003](adr/0003-no-internal-facts-no-real-data-no-secrets.md)).

## 18. 알고 가는 한계와 가정

- 여러 제품의 안쪽 동작과 부하 특성은 확인하지 못했어요. 정제 연산의 수(열넷)와 안전장치의 숫자는 추정이고 견본 시험과 알파에서 고쳐요.
- 프리셋이 본뜰 소스 API의 모양은 아는 대로 적은 것이고, 실제 제품 문서와 대조한 적이 없어요.
- 선언한 요청만으로 안 되는 소스(세션과 호출 한도가 까다로운 것, 검색 작업을 걸어야 하는 것, 장비를 순회해야 하는 것)는 어댑터가 따로 필요해요. 모든 소스가 어댑터 셋으로 되지 않아요.
- 기본은 소스가 주는 전부를 받는 것이에요. 구성 데이터는 작고 "사라짐"이 중요한 신호라서요(가정). 변경분만 받는 소스도 삭제를 못 보므로 주기적으로 전부 받아야 해요.
- 실시간 상태(온도, 전력, 알람의 현재 값)와 라우팅 경로표는 받지 않아요. 구성이 아니라 상태라서요. ECMP는 장비 설정 값에서 읽어요.
- 정제에 집계와 식이 없어서, 집계가 필요한 소스는 소스 쪽 질의에서 해요. 쿼리 말 소스의 검색 문장은 소스 항목이라 버전이 있지만, 수집기를 직접 만드는 소스는 그 안의 코드가 정의 밖이에요.
- 원본 기록의 보관 기한이 지나면 그 수집으로 다시 돌릴 수 없어요. 지나간 KG 버전이 참조하는 기록을 남길지는 [ADR-0009](adr/0009-kg-storage-and-versions.md)에서 정해요(조사의 제안은 참조 고정이에요).
- 엑셀 파서 후보에는 알려진 취약점 이력이 있어요([출처 1](https://git.sheetjs.com/sheetjs/sheetjs/issues/2961), [출처 2](https://cdn.sheetjs.com/advisories/CVE-2024-22363.html)). 버전과 내려받은 파일의 해시를 고정하고, 사용자가 올린 파일을 믿을 수 없는 입력으로 다뤄야 해요. 이 파서의 선택은 구현할 때 정해요.
- 읽기 전용 계정을 확인하는 방법은 소스마다 달라서 어댑터가 확인하지 못하는 소스가 있어요. 쿼리 말 소스의 저장된 검색을 이름으로 부를 수 있는지는 확인하지 못했어요.

## 19. 아직 정하지 않은 것

1. 덜 받은 수집의 기록을 구간에 합칠지, 따로 둘지. 이 문서는 따로 두고 구간에 세지 않는 것으로 풀었어요.
2. 여러 소스가 대는 객체의 "안 보임"을 세는 단위. 소스마다인지, 대던 소스가 모두 안 보일 때인지.
3. 대량 사라짐의 분모(소스와 타입마다로 가정했어요)와 링크가 사라지는 경우에도 같은 장치를 걸지.
4. 링크 타입의 개수(1:1, 1:N, N:M)를 어긴 링크를 어떻게 다룰지. 넘겨받은 설계는 적용하지 않고 목록에 두었어요.
5. 수 맞춤이 어긋났을 때(멈추는지, 알리는지)와 분류의 순서.
6. 병합이 KG의 새 버전을 바로 만드는지, 다음 동기화를 기다리는지.
7. 멈춘 동기화를 사람이 풀 수 있는지, 푼다면 한 번만인지와 감사 기록(조사의 제안은 한 번만 풀고 기록을 남기는 것이에요).
8. 간격의 하한, 놓친 주기를 따라잡는 방식, 손으로만 하는 소스의 신선도 ([ADR-0011](adr/0011-kg-operations.md)).
9. 호스트마다 따로 묻는 식의 요청이 이어지는 소스에서, 요청 사이에 소스가 바뀌는 일.
10. 수집 봉투의 인증 방식과 크기 상한. 계약 단위와 [ADR-0012](adr/0012-domains-and-access.md)에서.
11. 다음 어댑터의 후보와 순서(검색 언어를 받는 소스, 장비 설정을 순회하는 소스).
