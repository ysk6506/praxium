# 현실 데이터 받기 설계

[ADR-0008](adr/0008-ingestion.md)의 결정을 풀어 쓴 문서예요. 구현하는 사람이 이 문서만 보고 데이터의 모양, 상태, 경계를 알 수 있게 썼어요. 표의 칸은 **스케치**이고 이름은 영어 snake_case예요. 예시의 소스, 이름, 숫자는 모두 지어낸 것이고, 숫자는 "가정"이거나 "재서 정한다"예요.

## 1. 무엇에 답하나
- 여러 소스를 읽기만 하면서, 소스마다 받는 때와 방식을 어떻게 관리하나요?
- 배치와 스트리밍을 한 정의로 받으면서 흐름에서 못 쓰는 연산이 없게 하려면요?
- 한 객체 타입에 배치로 오는 속성과 실시간으로 오는 속성이 섞이면 어떻게 짓고, 사용자는 어떻게 관리하나요?
- 같은 것(ECMP 등)을 설정에서도 표에서도 문서에서도 받으려면요?
- 소스가 틀리거나 덜 와도 KG가 망가지지 않게 하는 장치와, 제품이 모르는 소스·닿지 못하는 망의 소스를 받는 길은 무엇인가요?

이 문서가 정하지 않는 것: 정의의 버전·브랜치·제안·병합·되돌리기는 ADR-0014의 길을 타요. 관측은 ADR-0013, 권한은 ADR-0012([권한 설계](access-control.md)), 저장은 ADR-0009([저장 설계](kg-storage.md)), 모델은 ADR-0007([모델 설계](kg-model.md))이 정해요.

## 2. 한눈에
```
소스 ─수집─▶ 원본 기록의 변경 ─정제─▶ 데이터셋 ─공급(매핑)─▶ 속성 값
(읽기만)    (적용기가 ingest_seq)(닫힌 열넷)                        │
   ┌────────── 식별과 병합 ◀────────────────────────────────────┘
   └─▶ 링크와 묶음 ─▶ 차이 ─▶ 안전장치 ─▶ KG의 변경 묶음(change_seq) ─▶ 봉한 KG 버전
```
| 단계 | 하는 일 | 아는 것 | 모르는 것 |
|---|---|---|---|
| 수집 | 소스에서 받아 원본 기록으로 남겨요. 고치지 않아요 | 소스 접속, 프리셋의 요청, 가릴 필드 | 모델, 매핑 |
| 원본 기록의 변경 | 받은 것을 더함·고침·지움으로 바꾸고 번호를 매겨요 | 열쇠, 내용 해시 | 소스의 뜻, 받는 방식 |
| 정제 | 닫힌 열넷 연산으로 데이터셋을 다듬어요 | 데이터셋 | 접속, 모델, 받는 방식 |
| 공급(매핑) | 컬럼을 객체 타입의 속성과 식별 키에 이어요 | 모델 | 접속, 받는 방식 |
| 식별과 병합 | 같은 것을 알아보고 속성마다 이기는 값을 골라요 | 모델, 식별 이력 | 소스의 프로토콜 |
| 링크와 묶음 | 링크 정의로 객체를 잇고 묶음을 만들어요 | 모델, 링크 정의 | 접속 |
| 차이, 안전장치, 적용 | 지금 KG와 견주고 멈출지 보고 변경 묶음으로 적용해요 | KG, 규칙 | 소스 |

연결 점검은 단계가 아니라 필요할 때 하는 점검이에요. 연동(수집까지)과 모델 동기화(그 뒤)의 경계는 원본 기록의 변경이에요.

## 3. 소스, 어댑터, 프리셋, 데이터셋
### 3.1 칸
| 이름 | 칸 |
|---|---|
| 소스 `source` | `id`, `name`, `adapter`, `preset`(id와 판), `collector`(`in_product` / `remote` / `envelope_only`), `endpoints`(나가는 연결의 허용 목록), `credential_ref`, `contacts`(담당자), `completeness`(완전성 선언: 타입·링크 타입, 범위), `protection`(13.4), `expected_interval`, `status`(`active` / `paused` / `breaker_open`) |
| 데이터셋 `dataset` | `id`, `source_id`, `name`, `kind`(`raw` / `refined`), `request`(프리셋의 허용된 요청 이름), `receive_mode`, `schedule_id`, `natural_key`(소스가 키를 안 주면 구성 규칙), `event_time`(사건의 때 컬럼), `marker`(늘어난 것의 표시), `deletion`(`absent_in_full` / `delete_event` / `delete_flag` / `none`), `columns`(이름, 값 타입, `sensitivity`), `redact`(`drop`, `mask`), `expectations`. `refined`는 `inputs`와 `ops`를 가져요 |
| 프리셋 `preset` | `id`, `version`, `adapter`, `allowed_requests`(메서드, 경로의 틀, 본문의 모양), `pagination`, `auth_kind`, `datasets`(전부 받는 것과 이어서 받는 것의 한 벌), `default_feeds`, `default_sensitivity`, `default_schedule`, `redact`, `tests`(지어낸 견본) |

`natural_key`가 없으면 행의 순서에 기대게 되어 결과가 정해지지 않아요. 프리셋은 키 구성 규칙을 선언해야 해요. 키가 겹치면 수집을 거절하지 않고 문제 목록에 올리고, 어느 행을 쓸지는 정제의 "겹친 행 없애기"가 정해요. 소스와 데이터셋에는 담당자가 붙어요. 담당자는 연락처이고, 문제와 알림과 검토 요청이 그리로 가요. 권한은 권한 부여에서만 와요(ADR-0012).

### 3.2 어댑터의 포트
어댑터는 프로토콜 하나를 말하는 제품 안의 코드이고 소스의 뜻과 KG 모델을 몰라요. 쓰는 메서드는 없어요(구조 검사가 봐요). 어댑터는 자기가 할 줄 아는 메서드를 선언해요.

| 메서드 | 뜻 |
|---|---|
| `inspect` 들여다보기 | 무엇이 있나(표, 끝점, 컬럼)를 읽기 전용으로 줘요. 양에 상한이 있고 소스 지키기를 거쳐요. 매핑을 만들 때 써요 |
| `preview` 미리보기 | 데이터셋의 몇 줄을 줘요 |
| `fetch_all` 전부 받기 | 기록을 흘리고 온전함을 알려요(끝까지 갔나, 소스가 알린 수와 맞나) |
| `fetch_since` 늘어난 것 받기 | `marker` 뒤로 바뀐 것을 받고 다음 `marker`를 돌려줘요 |
| `follow` 이어서 받기 | 소스에서 읽은 자리(`source_cursor`)부터 사건을 흘려요. 자리가 이어지지 않으면 `resume_lost`로 알려요 |
| `check` 점검 | 닿는지, 인증, 소스 쪽 계정이 읽기 전용인지 봐요(13.1) |

`source_cursor`에 담기는 자리는 소스가 준 불투명한 표지예요. 저장하고 되돌려 보낼 뿐 크기를 비교하지 않아요(7.2).

### 3.3 첫 어댑터와 흐름의 어댑터 후보
| 어댑터 | 받는 방식 | 특징 |
|---|---|---|
| 파일(엑셀, CSV) | `snapshot` | 올린 파일 하나가 전부 받기 하나예요(16절) |
| HTTP JSON | `snapshot`, `incremental` | 세션 인증, 쪽 넘김, 선언한 요청 틀. 로그인과 검색 실행처럼 읽기인 POST는 허용 목록에 적어요 |
| 읽기 전용 SQL | `snapshot`, `incremental` | 조회만 되는 역할로 접속해요 |

흐름의 어댑터는 결정 기록과 함께 하나씩 더해요. 전달 보장과 순서는 일부만 확인했으므로 **모든 소스가 중복과 순서 어긋남을 낼 수 있다고 전제해요.**

| 후보 | 읽은 자리 | 지움이 보이는 법 | 맞추기가 필요한 까닭 |
|---|---|---|---|
| 메시지 기록 저장소의 주제 | 파티션별 위치 | 값 없는 기록이나 지움 표시 기록 | 보관 기간이 지나면 되감지 못해요 |
| 지켜보기 방식의 API | 불투명한 재개 토큰 | 지움 사건 | 이어지지 않으면(너무 늦음) 처음부터 다시 받아요 |
| 변경 데이터 잡기 | 변경 로그의 위치 | 지움 기록. DB가 로그에 안 남기는 지움은 못 잡아요 | 처음에 일관된 스냅샷, 그 뒤 로그. 적어도 한 번 전달돼요 |
| 밀어 넣기 | 없음(소스가 보내요) | 사건의 종류 | 순서 보장이 없고 소스가 재시도해요. 수집 봉투의 한 꼴이에요 |

"처음에 전부, 이어서, 이어지지 않으면 다시 전부"는 지켜보기 방식의 표준 모양이고, 어댑터 포트가 이 모양으로 일반화돼 있어요(4.2).

## 4. 받는 방식
### 4.1 넷과 고르는 기준
| 방식 | 무엇 | 지워진 것을 아는 길 | 고르는 기준 |
|---|---|---|---|
| `snapshot` | 주기마다 전부 받아요 | 온전한 수집에서 안 보임 | 구성 데이터의 기본. 작고 "사라짐"이 중요하고 전부 받아도 소스가 견뎌요 |
| `incremental` | 주기마다 지난번 뒤로 바뀐 것만 받아요 | 소스가 지움을 알리거나, 가끔 전부 받아 맞춰요 | 전부 받기가 비싸고 소스가 바뀐 것을 가려 줘요 |
| `stream` | 이어서 받아요(구독, 지켜보기, 변경 데이터 잡기, 밀어 넣기) | 지움 사건 | 몇 초 안의 반영이 필요하고 소스가 변경을 알려 줘요 |
| `stream` + 맞추기 | 처음에 전부, 이어서, 가끔 전부로 맞춰요 | 둘 다 | 지움 사건이 없거나 손실이 있는 소스. 지움을 아는 길이 약할수록 맞추기를 자주 해요 |

받는 방식은 소스가 아니라 **데이터셋**의 칸(`receive_mode`)이에요. 한 소스가 구성은 `snapshot`으로, 상태는 `stream`으로 줄 수 있어요. 어느 방식이든 받은 것은 원본 기록의 변경이 되고, 그 뒤 단계는 방식을 몰라요.

### 4.2 `stream` + 맞추기의 상태 흐름
```
paused ─(켜기)─▶ seeding(처음에 전부 받기) ─(온전히 끝)─▶ following(이어서 받기)
following ─(맞추기 주기)────────▶ reconciling(전부 받기, 차이를 변경으로) ─▶ following
following ─(follow가 resume_lost)─▶ resyncing(전부 받기, 차이를 변경으로) ─▶ following
following/seeding ─(안전장치, 기대 조건 fail)─▶ held(받기는 계속, 적용만 붙잡음)
held ─(release)─▶ 쌓인 것을 순서대로 적용 / ─(discard)─▶ 버린 뒤 전부 받아 맞춤
```
흐름의 상태는 `running` / `held` / `paused` / `failed`예요. 풀기(`release`)는 `operator`가 후보 실행으로 차이를 본 뒤에 해요. 붙잡힌 까닭이 정의 탓이면 정의를 고쳐 병합하고, 쌓인 변경이 새 정의로 적용돼요. **버리기(`discard`)는 맞추기를 할 수 있는 소스에서만 돼요.** 전부 받을 길이 없는 흐름은 버릴 수 없고 풀거나 붙잡아 둘 뿐이에요.
`incremental`도 같은 틀이에요: `fetch_since`가 `following` 자리에서 돌고, 맞추기 주기마다 전부 받아요.

### 4.3 지움을 아는 길
| 길 | 어떻게 | 원본 기록에서 |
|---|---|---|
| 온전한 전부 받기(`snapshot`, 맞추기, `resyncing`)에서 안 보임 | 바로 지우지 않고 잇달아 안 보인 번수(`missed_count`)를 세요 | 기본 3번(가정)이 되면 구간을 닫고 `deleted` |
| 소스가 알림(지움 사건, 지움 표시 컬럼) | 소스가 말한 지움이에요 | 바로 구간을 닫고 `deleted` |
| 덜 받은 수집 | 안 보임으로 세지 않아요 | 아무것도 지우지 않아요 |
| 길이 없음(`deletion: none`) | 지움을 몰라요 | 완전성 선언이 없으니 "없다"가 아니라 "모른다"예요(ADR-0007) |

원본 기록의 `deleted`가 객체를 물러나게 하는 것은 아니에요. 그 공급이 `retires_objects`일 때만 물러나요(9절). 흐름에서는 지움 사건과 맞추기만 물러나게 해요.

## 5. 일정
일정이 정의예요. 값(주기, 시간대, 맞추기 주기 등)을 고치는 것은 정의의 변경이라 ADR-0014의 길을 타요. 일시 정지와 지금 한 번은 정의를 바꾸지 않는 운영의 조작이고 `operator`가 하며 감사 기록에 남아요.

| 칸 (`schedule`) | 뜻 |
|---|---|
| `target` | 소스 하나 또는 데이터셋 하나. 데이터셋마다 다르게 둘 수 있어요 |
| `every` / `at` / `manual_only` | 간격 / 정해진 시각들(`timezone` 포함) / 손으로만. `snapshot`과 `incremental`에 써요 |
| `windows` | 받아도 되는 시간대. 밖이면 건너뛰고 기록해요 |
| `stream_enabled`, `reconcile_every` | `stream`의 켜고 끔, 맞추기의 주기. `incremental`도 `reconcile_every`를 가져요 |
| `misfire_policy` | 건너뛴 실행의 처리: `skip`(건너뛰고 기록) / `run_once`(한 번만 따라잡기). 기본 `run_once`(가정) |
| `expected_interval` | 기대하는 갱신 주기. 손으로만 받는 소스도 적어요. 낡음은 이것에 대요. 안 적으면 나이만 보이고 "기대 주기 없음"이에요 |

- **일시 정지**는 사유와 함께 멈추고 건강에 보여요. **지금 한 번**은 같은 길, 같은 소스 지키기, 같은 안전장치를 거쳐요.
- **겹침 금지**: 같은 데이터셋의 실행은 한 곳에서만 돌아요. 서버가 여럿이어도 일정의 키로 막아요(ADR-0011). 일꾼이 일을 쥘 때마다 `attempt`가 오르고 늦게 깨어난 일꾼의 쓰기는 번호로 막아요.
- **실패**: 다시 하기 3번, 잇달아 5번 실패하면 그 소스의 일정을 멈추고 알려요(가정). 운영 역할이 손으로 다시 켜요. 마지막 정상 버전은 그대로예요.
- **흐름**: 켜고 끔과 맞추기의 주기가 일정이에요. 흐름의 신선도는 밀림(마지막으로 적용한 사건의 때와 지금의 차이)과 마지막 맞추기의 때예요.

## 6. 수집 봉투와 떨어진 망의 수집기
### 6.1 수집 봉투의 칸
제품 밖의 수집기가 원본 기록을 보낼 때 쓰는 공개된 모양이에요. 형식은 계약 단위가 쥐고 버전이 있어요(ADR-0006).

| 칸 (`envelope`) | 뜻 |
|---|---|
| `envelope_version` | 봉투 형식의 버전 |
| `source_id`, `dataset_id`, `preset` | 무엇을 받았나 |
| `capture_id` | 수집 한 번의 키. 다시 보내도 한 번만 받아요(멱등) |
| `mode` | `full` / `delta` / `stream` |
| `collector_id`, `collector_version` | 누가 받았나 |
| `started_at`, `finished_at` | 언제 |
| `completeness` | 온전한가: `complete`, `expected_count`, `received_count`, `pages`, `errors`. 정직하게 적어야 해요 |
| `redaction` | 지운 규칙의 버전과 지운 필드의 경로 목록 |
| `body_hash` | 지운 뒤 내용의 해시 |
| `records` | 기록들: `kind`(`added` / `modified` / `deleted`), `natural_key`, `source_time`(선택), `position`(선택), `seq`(수집기가 매긴 차례 번호), `body` |

- 받는 쪽은 인증(토큰은 해시로만 저장하고 만료와 교체가 있어요), 크기 상한, `capture_id`와 `seq`로 겹침을 막고, 데이터셋의 `redact` 선언대로 비밀 값을 다시 지워요.
- 받은 순서는 수집기의 `seq`가 아니라 적용기가 굳히며 매기는 `ingest_seq`가 정해요. `seq`는 한 수집기 안에서 빠진 것을 찾는 데 써요.
- 소스가 더함과 고침을 가르지 못하면 둘 다 `added`로 보내도 돼요. 실행기는 열쇠 상태를 보고 정해요.

### 6.2 떨어진 망의 수집기
| | 제품이 싣는 수집기 | 담당자가 만든 수집기 |
|---|---|---|
| 무엇 | 일꾼의 수집 역할을 소스가 있는 망에 따로 띄운 것(역할 넷째) | 수집 봉투만 쓰는, 소스의 담당자가 짠 것 |
| 연결 | 밖으로 나가는 연결만 써요. 본체에 물어 일을 받고 수집 봉투로 보내요 | 같아요 |
| 읽기 전용 | 같은 어댑터가 돌아서 세 겹이 그대로 서요 | **그 소스의 담당자가 책임져요.** 문서와 API의 응답에 밝혀요(화면이 보여요) |
| 비밀 값 | 그 망의 비밀 값 제공자를 가리켜요 | 담당자의 몫이에요 |

본체가 그 망에 들어가지 않아도 돼요. 수집기는 읽은 자리(`source_cursor`)를 본체에 둬서 죽어도 다른 벌이나 새로 띄운 것이 이어받아요. 한 벌뿐이면 그동안 일이 기다리고 건강에 보이니 두 벌 이상을 권해요. 수집 봉투의 클라이언트 라이브러리는 여러 언어로 내요(Go, Python, TypeScript부터). 담당자가 익숙한 언어로 수집기를 만들어요. 수집기가 죽으면 소스의 건강에 생존 신호가 끊긴 것으로 보여요(ADR-0013). 담당자가 만든 수집기가 지켜야 할 것은 읽기 전용, 정직한 `completeness`, 비밀 값 지우기, 그리고 지어낸 견본 봉투로 시험한 것이에요.

## 7. 원본 기록
### 7.1 구간 모델과 변경으로 바꾸기
받은 모양 그대로(JSON) 기록 단위로 보관하고 고치지 않아요. 같은 기록이 다음 수집에서도 그대로면 복제하지 않고 구간만 늘려요.

| 칸 (`raw_record`) | 뜻 |
|---|---|
| `source_id`, `dataset_id`, `natural_key` | 어느 소스의 어느 기록인가 |
| `content_hash` | 비밀 값을 지운 뒤 내용의 해시 |
| `first_seq`, `last_seq`, `closed_seq` | 처음 본 `ingest_seq`, 마지막으로 본 것, 닫힌 것(비어 있으면 열려 있어요) |
| `missed_count` | 온전한 수집에서 잇달아 안 보인 번수 |
| `body`, `redaction_version` | 내용(JSON), 지운 규칙의 버전 |
| `excluded` | 이 기록은 쓰지 않는다는 예외(7.4) |

| 상황 | 구간 | 변경 |
|---|---|---|
| 새 열쇠 | 새 행이 열려요 | `added` |
| 같은 열쇠, 같은 해시 | `last_seq`만 늘어요 | 없음 |
| 같은 열쇠, 다른 해시 | 옛 구간을 닫고 새 행이 열려요 | `modified`(실행기에서 −옛 +새) |
| 온전한 전부 받기에서 안 보임 | `missed_count`가 늘고, 기본 3번이면 닫아요 | `deleted` |
| 다시 보임 | `missed_count`가 0으로 | 없음 |
| 덜 받은 수집 | 건드리지 않아요 | 없음 |

어느 `ingest_seq` N 때의 모습은 "`first_seq` ≤ N 이고 닫히지 않았거나 N < `closed_seq`"인 행으로 읽어요. 그래서 받아 둔 원본 기록만으로 뒤 단계를 언제든 다시 돌릴 수 있어요.

### 7.2 기록 둘, 읽은 자리 둘, 받은 차례의 번호
- **기록은 둘이고 섞지 않아요**(ADR-0009). 받은 변경의 기록은 소스에서 받은 변경을 적용 전에 쌓는 곳이에요. 포트이고 어댑터가 둘이며 둘 다 정식이에요(PostgreSQL은 작은 배포와 알파, 메시지 기록 저장소는 큰 조직이 이미 가진 것. 흐름이 차별점이라 받기를 넓히는 단계에서 둘 다 만들어요). KG에 적용된 변경의 기록(`change_seq`)은 언제나 PostgreSQL이에요.
- **읽은 자리도 둘이에요.** `source_cursor`는 소스에서 어디까지 읽었나예요. 받은 변경의 기록에 쓰는 것과 함께 나아가요. 기록이 PostgreSQL이면 한 트랜잭션이고, 메시지 기록 저장소면 쓴 뒤에 나아가서 겹쳐 받은 것을 (소스, 자리)로 걸러 내요. `applied_through`는 받은 변경의 기록에서 어디까지 적용했나예요. 열쇠 상태, 변경 묶음과 한 트랜잭션이라 정확히 한 번 적용돼요.
- **`ingest_seq`는 KG마다 하나뿐인 적용기가 차례를 굳히며 매겨요.** 받은 변경의 기록에서 묶음을 읽을 때 어느 기록의 어느 자리를 어떤 순서로 읽었는지를 목록으로 적고 번호를 매겨요. 다시 돌릴 때는 이 목록을 따라서 기록이 어느 어댑터든 차례가 같아요. 여러 소스의 변경이 섞이는 순서도 이 번호로 고정돼요. `change_seq`도 같은 적용기가 매기고 둘은 다른 번호예요.
- **시계도 사건**이에요. 일정한 간격(가정)의 `tick`을 사건으로 기록에 넣어 차례를 받게 해요. 시간이 드는 일(대기의 기한, 붙잡힌 시간)은 벽시계가 아니라 `tick`으로 세서 다시 돌려도 같은 결과예요.

### 7.3 비밀 값 지우기와 보관
- 프리셋과 데이터셋이 `redact`(`drop`, `mask`)를 선언해요. 받을 때 지우고, 해시는 지운 뒤 내용으로 구해서 비밀 값이 해시에 새지 않아요. 지운 규칙의 버전과 경로를 남겨요.
- 보관 기한을 둬요. 기본값은 재서 정해요. KG 버전이 쓴 기록은 기한이 지나도 참조가 고정돼요. 파티션 단위로 지워요.

낱개 예외는 둘뿐이에요: 식별의 예외(같다 / 다르다)와 원본 기록 제외(이 기록은 쓰지 않는다). 값을 낱개로 덮어쓰는 예외는 없고, 값은 소스나 규칙에서 고쳐요. 둘 다 정의라서 버전이 있어요.

## 8. 변경을 받아 변경을 내는 실행기
### 8.1 변경의 모양
변경 한 줄은 `(row_key, weight, row, ingest_seq, source_time)`이에요. 더함은 +1, 지움은 −1이고, 고침은 "−옛 +새" 한 쌍이에요. 모든 연산이 +와 −를 같은 길로 받아서 지움과 고침이 값으로 흘러요. 묶음의 크기와 간격은 너무 작으면 트랜잭션 비용이 지배하므로 적응형으로 두고 재서 정해요.

### 8.2 연산을 셋으로 가름
연산 등록부의 필수 칸 `class`예요. 늘어난 만큼만 다시 계산해요.

| 부류 | 필요한 것 | 연산 |
|---|---|---|
| 가. 기록 하나만 봐요 | 상태 없음. 변경이 그대로 흘러요 | 행으로 펼치기, 컬럼 나누기, 고르기, 빈 값 채우기, 값 바꾸기, 컬럼 고르기와 이름 바꾸기, 자료형으로 읽기, 정규식으로 뽑기, 이어 붙이기, 유니언 |
| 나. 열쇠마다의 상태 | 열쇠마다 저장소에 상태를 둬요 | 조인, 컬럼으로 모으기(피벗), 겹친 행 없애기, 표에서 찾아 바꾸기 |
| 다. 전체를 봐야 해요 | — | 열넷 가운데는 없어요 |

- **조인**: 양쪽 색인을 쥐고 Δa⋈b + a⋈Δb + Δa⋈Δb로 갱신해요. 지움(−)도 같은 식을 타서 한쪽 행이 지워지면 이어진 결과 행에 −가 나가요.
- **컬럼으로 모으기**: 열쇠마다 행의 묶음을 쥐어요. 만들 컬럼의 목록은 정의에 적어요. 목록에 없는 값이 오면 받은 모양이 바뀐 것으로 다뤄요(14절).
- **겹친 행 없애기**: 열쇠마다 후보를 **모두** 쥐어요. 남은 행이 지워지면 다음 후보가 올라와요(`−r2 +r1`). "가장 최근 값 하나만" 두면 지움에서 틀려요.
- **표에서 찾아 바꾸기**: 조회표가 조인의 한쪽 색인이에요. 조회표가 바뀌면 그 열쇠의 행을 다시 내요.
- **유니언**: 입력의 변경을 그대로 합쳐요. 입력 모양이 맞는지만 검사해요.
- **다**: 새 연산이 전체를 봐야 하면 흐름에서 도는 길(열쇠를 정해 열쇠마다 다시 계산하거나 큰 묶음에서만 돌리는 길)과 함께 결정 기록으로만 더해요. 흐름이라서 못 쓰는 연산이 없게 하려는 거예요.
- "값 바꾸기"의 함수는 제품에 든 순수 함수의 목록에서 골라요. 입력 순서에 기대지 않고 시계와 난수를 쓰지 않아요.

공급, 식별과 병합, 링크 정의의 조건도 같은 틀이에요. 링크 조건은 다듬은 열쇠의 색인 위에서 늘어난 만큼만 따져요.

### 8.3 열쇠 상태의 자리(포트)
메서드: `load(op_id, keys)`(상태 읽기), `store(op_id, changes)`(적용 트랜잭션 안에서 고치기), `scan(op_id, key_range)`(범위 훑기), `fork(base)`(후보 실행용 사본. 운영 상태에서 출발해 운영에 영향이 없고 버려져요).

기본 어댑터는 PostgreSQL이고 메모리에 쓰기 통과 캐시를 둬요. 캐시에 내용 해시를 두면 같은 사건(노옵)을 저장소에 닿기 전에 걸러요. 천만 개의 열쇠를 한 프로세스에 두는 것은 작은 시제품에서 감당됐지만(정지가 밀리초 아래) 저장소 입출력이 빠진 측정이에요.

### 8.4 늦게 오거나 순서가 바뀐 사건
- 순서의 기준은 `ingest_seq`예요. 소스의 시각이나 버전으로 정하지 않아요.
- 같은 `capture_id`, `seq`, 해시의 중복은 무시하고 세어요.
- `source_time`은 값을 가릴 때만 써요. 같은 공급이 같은 속성에 쥔 값의 때보다 이른 값은 덮지 못하고 `late_events`로 세어요(9.3).
- 시간 창이 없으니 워터마크도 없어요. 시간이 드는 일은 `tick`으로 세요(7.2).

**"한 번에 넣은 결과 = 나눠 흘린 결과"의 시험.** 속성 시험으로 건다: (1) 같은 원본 변경을 한 묶음으로 넣은 결과와 임의로 나눠 흘린 결과가 같은 KG 내용을 내요. (2) 중복을 섞어도 같아요. (3) 원본 기록에서 처음부터 다시 돌려도 내용(타입, 속성, 링크의 모양)이 같아요. ID까지 같다고는 약속하지 않아요(ADR-0007). (4) 전부 받기를 지난번과의 차이로 바꾼 것과 같은 변경을 이어서 받은 결과가 같아요. 입력은 17절의 생성기가 내요.

## 9. 공급
### 9.1 칸
공급(`feed`)은 데이터셋 하나에서 객체 타입 하나로 가는 매핑 하나예요. 공급은 자기가 매핑한 속성만 **쥐어요.**

| 칸 | 뜻 |
|---|---|
| `dataset_id`, `object_type` | 어느 데이터셋에서 어느 타입으로 |
| `attributes` | 속성의 매핑: `attribute`, `column`, `rank`(이기는 순서, 낮을수록 먼저), `history_kind`(기본은 `change_class`에서) |
| `identity` | 식별 키의 매핑: `key_name`, `columns`, `priority`. 딸린 객체는 부모의 문맥을 함께 적어요 |
| `creates_objects`, `retires_objects` | 객체를 만들 수 있나, 물러나게 할 수 있나 |
| `basis` | 근거의 종류: `configured` / `observed` / `declared` / `derived` |
| `approximate` | 어림 표시. `declared`의 기본 등급은 `fact`이고 어림이면 `assumed`예요 |
| `completeness` | 이 공급이 타입이나 링크 타입을 전부 주는가(범위를 붙일 수 있어요) |
| `wait_deadline` | 살만 붙이는 공급의 대기 기한(`tick`으로 세요) |
| `expectations`, `contacts` | 기대 조건, 담당자 |

### 9.2 속성 단위의 적용
- 객체의 값은 공급마다 낸 값을 따로 쥐고 있다가 **속성마다** 이기는 값을 골라요. 배치 공급의 전부 받기가 흐름 공급이 쥔 속성을 지우거나 덮지 않아요.
- 이기는 값: `rank`가 낮은 것. 같은 순위 안에서는 사건의 때(`source_time`)가 늦은 것. 그것도 같으면 `ingest_seq`가 늦은 것(18절에 물어요).
- 진 값은 버리지 않고 문제 목록에 소스 사이의 충돌로 보여요.
- 공급이 더는 값을 주지 않으면(컬럼이 비었거나 기록이 지워짐) 그 공급이 쥔 속성만 비워져요. 다른 공급이 있으면 그 값이 이기고, 없으면 값은 `unknown`이에요. 모르는 것을 가정으로 메우지 않아요. 기본값 규칙이 만든 값만 `assumed`예요.
- 저장은 갈라요. `versioned` 속성은 객체의 행과 이력에, `volatile`은 지금 값만 두는 따로 된 자리에 둬요(ADR-0009). 흐름이 초마다 상태를 바꿔도 객체의 행과 이력은 늘지 않고 배치의 적용과 서로 기다리지 않아요.

### 9.3 객체를 있게 하는 공급과 살만 붙이는 공급
- 객체는 `creates_objects`인 공급의 행에서 식별 키가 모두 채워졌을 때 생겨요. 내부 ID는 처음 본 식별 키에서 결정적으로 나와요(ADR-0007). 보통 구성 소스의 배치 공급이 만들고 물러나게도 해요. 상태를 주는 흐름 공급은 둘 다 못 해요.
- 살만 붙이는 공급은 자기 식별 키로 있는 객체를 찾아요(식별 규칙은 결정적이에요). 있으면 붙어요. 둘 이상이 맞으면 붙이지 않고 식별 후보로 문제 목록에 올려요.
- 없으면 객체를 지어내지 않고 **기한이 있는 대기**에 둬요. 기한 안에 객체가 생기면 붙고, 아니면 문제 목록에 "붙을 곳이 없는 값"으로 올라가요. 대기의 수는 공급의 건강에 보여요.
- `retires_objects`인 공급의 지움(4.3)만 객체를 물러나게 해요. 물러난 객체는 이력에 남고, 같은 식별 키로 다시 보이면 옛 ID로 되살아나요.

**사건의 때로 늦은 값 막기.** 공급이 속성마다 마지막으로 낸 값의 `source_time`을 쥐어요. 그보다 이른 값이 늦게 오면 덮지 않고 `late_events`로 세요. 소스가 때를 안 주면(`event_time`이 없으면) 받은 순서(`ingest_seq`)로만 가려요.

### 9.4 예: `VirtualMachine`에 세 공급이 붙을 때
지어낸 예예요. 타입 `VirtualMachine`의 속성 가운데 구성은 하루에 한 번 전부 받고, 상태는 이어서 받고, 담당 서비스는 엑셀로 받아요.

| 공급 | 데이터셋 · 받는 방식 | 만듦 / 물러남 | 쥐는 속성 (`rank`) | `basis` |
|---|---|---|---|---|
| `vm_config_daily` | `vm_inventory` · `snapshot`, 하루 한 번 새벽 | 예 / 예 | `name`, `cpu_count`, `memory_mb`, `guest_os` (1) | `observed` |
| `vm_runtime` | `vm_runtime_events` · `stream` + 맞추기(6시간마다, 가정) | 아니요 / 아니요 | `power_state`, `host_name` (1) | `observed` |
| `vm_service_sheet` | `vm_service_sheet` · 파일, `manual_only`(기대 주기 한 달, 가정) | 아니요 / 아니요 | `owner_service` (1), `memory_mb` (2, 어림) | `declared` |

식별은 `vm_config_daily`가 `instance_id`(`priority` 1)와 `name`(2)을 가져요. 시트는 `name`만 가져서 2순위 키로 붙어요.

| 속성 | `change_class` → 이력 | 쥔 공급 | 비고 |
|---|---|---|---|
| `name`, `cpu_count`, `guest_os` | `slow` → `versioned` | `vm_config_daily` | 바뀔 때마다 이력에 남아요 |
| `memory_mb` | `slow` → `versioned` | `vm_config_daily`(1), 시트(2) | 두 값이 다르면 1이 이기고 시트 값은 어긋남으로 보여요. 시트 값은 어림이라 `assumed` |
| `power_state`, `host_name` | `dynamic` → `volatile` | `vm_runtime` | 지금 값과 본 때만 둬요 |
| `owner_service` | `slow` → `versioned` | `vm_service_sheet` | 사람이 적은 것(`declared`) |

링크 `RUNS_ON`(`VirtualMachine` → `HypervisorHost`)은 링크 정의가 `host_name`과 호스트의 이름이 같다는 조건(다듬은 키가 같다)으로 만들어요. 링크는 기본 `versioned`이고 옮겨 다님이 잦으면 `volatile`로 내릴 수 있어요. 호스트 구성(배치)이나 `host_name`(흐름) 어느 쪽이 바뀌어도 실행기가 늘어난 만큼만 다시 따져서 사용자가 따로 할 일은 없어요.

1. **새벽의 전부 받기(온전)**: VM `vm-a`, `vm-b`, `vm-c`가 생겨요. `power_state`는 아직 쥔 공급의 값이 없어 `unknown`이에요.
2. **이어서 받기**: `vm-a`의 `power_state=off`가 와서 `volatile` 자리만 바뀌어요(객체의 행과 이력은 그대로). 아직 없는 `vm-z`의 상태는 객체를 지어내지 않고 기한이 있는 대기에 둬요.
3. **늦은 사건**: `vm-a`에 `source_time`이 더 이른 `power_state=on`이 늦게 오면 덮지 못하고 `late_events`가 하나 늘어요.
4. **다음 날의 전부 받기**: `vm-b`의 `guest_os` 컬럼이 비면 `vm_config_daily`가 쥔 그 속성만 비워져요. `power_state`와 `owner_service`는 그대로예요. `vm-c`가 안 보이면 `missed_count`가 1이 될 뿐 물러나지 않아요.
5. **엑셀 올리기**: `vm-a`에 `owner_service`가 붙어요. 시트에만 있는 `vm-q`의 행은 대기에 두고, 기한 안에 `vm_config_daily`가 `vm-q`를 만들지 않으면 "붙을 곳이 없는 값"이에요.

## 10. 타입의 공급 표
객체 타입마다 표 하나가 위 예시처럼 모든 것을 보여 줘요. **API가 주는 자원**이고(화면은 다른 저장소가 그것을 읽어 그려요) 명령줄 클라이언트로도 볼 수 있어요. 공급을 더하고 순서를 바꾸는 것은 정의의 변경이에요(ADR-0014의 길).

칸: `attribute`, `feeds`(어느 공급: 소스 · 데이터셋 · 컬럼), `receive_mode`와 `schedule`, `rank`, `history_kind`, `staleness`와 `expected_staleness`(속성마다. 답에는 요청한 속성마다 본 때가 붙어요), `fill_rate`(`required`가 분모), `conflicts`(어긋남).

공급마다의 건강도 같은 자리에서 보여요: 마지막 수집, 밀림, 붙잡힘(`held`), 붙을 곳 없는 값의 수. 물음에 `max_staleness`를 주면 그보다 묵은 속성이 답에서 표시돼요(ADR-0010).

**맞지 않는 매핑을 알려요(막지는 않아요. 고르는 것은 사용자예요).** 표준 모델이 속성마다 `change_class`(`static` / `slow` / `dynamic`)를 적어 두고, 그것이 이력의 종류와 기대 신선도의 기본값을 정해요(`static`·`slow`는 `versioned`, `dynamic`은 `volatile`. 숫자는 가정).

| 매핑 | 알림 |
|---|---|
| `dynamic` 속성을 하루에 한 번 받는 배치에 매핑 | "최대 하루 묵은 값이 돼요" |
| 식별 키를 살만 붙이는 흐름에만 매핑 | "객체가 만들어지지 않아요" |
| `static` 속성이 자주 바뀜 | "식별이 흔들려요" |

## 11. 식별과 병합, 링크 정의, 묶음
### 11.1 식별과 병합
순서만 적어요. 규칙은 ADR-0007이 정해요. (1) 공급이 낸 행의 식별 키를 값 타입의 다듬기로 다듬어요. (2) 우선순위대로 기존 식별자와 맞춰요(결정적 규칙만. 확률은 후보를 제안할 뿐 저절로 합치지 않아요). (3) 있으면 붙고, 없으면 `creates_objects`일 때만 만들어요. (4) 속성마다 이기는 값을 골라요(9.2). 합침과 가름은 이력에 남아요. 식별의 이력은 파생물이 아니라 진실의 일부이고 잃으면 안 돼요.

### 11.2 링크 정의
링크 타입마다 조건을 적어요. 사람이 선을 긋지 않아요. 한 정의가 여러 소스의 데이터셋을 읽으면 그 소스들을 범위에 가진 `approver`의 승인이 필요해요.

링크 정의(`link_def`)의 칸: `link_type`과 `binding`(개수는 바인딩에 붙어요), `from`과 `to`(양 끝 타입과 쓰는 속성), `condition`(아래 여섯 중 하나와 인자), `creates`(`link` 또는 `group`), `reads`(읽는 데이터셋들), `basis`(`derived`)와 `history_kind`.

| 조건 | 뜻 | 예 |
|---|---|---|
| `same_key` | 다듬은 키가 같다 | VM의 `host_name` = 호스트의 이름 |
| `in_list` | 목록에 들어 있다 | 점검 대상 목록의 장비 |
| `in_range` | 범위에 든다 | 주소가 대역에 든다 |
| `slot_matches` | 자리가 맞는다 | 랙과 칸이 맞는다 |
| `same_parent` | 부모가 같다 | 같은 섀시의 부품들 |
| `follow_link` | 다른 링크를 따라간 끝이 같다 | 자리를 따라 냉방을 물려받는다 |

### 11.3 묶음 만들기와 끌어낸 링크
끌어낸 링크와 묶음은 질의할 때 계산하지 않고 **받을 때 만들어 저장해요.**
1. 구성원 후보를 `group_by` 키로 묶어요. 묶음 객체의 내부 ID는 묶음 키에서 결정적으로 나와요.
2. 구성원은 `member_of`로 들고 무게와 역할을 매개 값으로 가질 수 있어요.
3. 문턱(`min_alive`)의 근거: 소스가 말하면 `fact`, 종류 기본값(기본값 규칙)이면 `assumed`, 기본값이 없으면 `unknown`이에요.
4. `basis`는 `derived`이고 입력의 종류를 함께 적어요. 등급은 쓰인 입력 중 가장 낮은 등급이에요. 구성에서 끌어낸 묶음은 설정을 온전히 읽었으면 `fact`예요.
5. 한쪽 설정만 있거나 맞지 않으면 묶음을 만들지 않고 문제 목록에 올려요(ADR-0007의 설계 문서 참고).

### 11.4 예: 같은 ECMP 묶음을 세 길로 받기
지어낸 스위치 `leaf-1`이에요. 모두 `EcmpGroup`을 가리키고, 길마다 같은 묶음 키 칸(장비, 라우팅 문맥)에 매핑해서 같은 묶음이 돼요.

| 길 | 데이터셋 | 받는 타입 · 속성 | `basis` |
|---|---|---|---|
| 설정 | 장비 설정(`snapshot`) | `RoutingProcess`의 `maximum_paths`, `RoutingSession`의 `multipath_eligible` → 링크 정의가 묶음과 구성원을 끌어내요 | `configured`(묶음은 `derived`) |
| 표 | 경로표, 이웃 표(`stream`이나 `snapshot`) | `RoutingSession`의 `session_state`, `EcmpGroup`의 구성원 | `observed` |
| 문서 | 설계 엑셀 | `EcmpGroup`과 구성원 | `declared` |

길이 여럿이면 종류별로 다 받아 둬요. 설정이 4개를 쓰게 돼 있는데 경로표에 둘만 보이면 버릴 충돌이 아니라 **의도와 관측의 어긋남**이에요. 문제 목록에 올라가고, 질의는 `as_designed`나 `as_observed`를 골라요(ADR-0010). KG는 구조와 상태를 받고, 수치의 시계열(온도, 전력, 사용률)은 쌓지 않고 가리키기만 해요. LACP, BGP 세션, 전원 A·B, 클러스터 구성도 같은 방식이에요.

## 12. 기대 조건
데이터셋과 공급에 붙이는 선언하는 검사예요(`expectation`: `target`, `kind`, `params`, `severity`, `contacts`). 정의라서 버전이 있어요.

종류는 닫힌 여덟이에요: `not_empty`(비어 있지 않다), `unique`(겹치지 않는다), `in_values`(값의 목록 안이다), `in_range`(범위 안이다), `matches_value_type`(값 타입에 맞다), `references`(다른 데이터셋에 있다), `row_count_range`(행 수의 범위), `shape`(컬럼과 자료형).

| | 배치 | 흐름 |
|---|---|---|
| 거는 곳 | 수집 한 번의 묶음 | 기록마다. 묶음에 걸 수밖에 없는 `row_count_range`는 맞추기의 전부 받기에 걸어요 |
| `warn` | 문제 목록에 올려요 | 어긴 기록을 떼어 두고 문제 목록에 올려요 |
| `fail` | 그 공급의 적용을 멈춰요 | 어긴 기록을 떼어 두고 그 공급의 적용을 붙잡아요(`held`) |

**떼어 둔 기록**은 까닭과 함께 보관돼요. 원본 기록에는 남아 있고 수 맞춤에서 "문제"로 분류돼요. 견본은 민감 등급과 읽기 권한을 따라 보여요. 정의의 새 판이 병합되면 붙잡힌 자리부터 다시 돌려요.

## 13. 읽기 전용, 소스 지키기, 비밀 값, 민감 등급
### 13.1 읽기 전용은 세 겹이에요
"읽기 메서드만"은 지킬 수 없어요(로그인, 검색 실행, GraphQL은 읽기인데도 POST를 써요).
| 겹 | 무엇 | 확인 |
|---|---|---|
| 첫째, 요청 허용 목록 | 프리셋의 (메서드, 경로의 틀, 본문의 모양). 목록 밖의 요청은 만들어지지 않아요 | 프리셋을 싣거나 정의를 저장할 때 정적 검사 |
| 둘째, 소스 쪽 계정이 읽기 전용 | SQL은 조회만 되는 역할. 읽기 전용 트랜잭션 설정은 경계가 아니에요 | 연결할 때 관리자가 확인하고 `check`가 가능한 소스는 권한을 점검해 건강에 보여요 |
| 셋째, 어댑터에 쓰는 길이 없음 | 포트에 쓰는 메서드가 없어요 | 구조 검사 |

### 13.2 쿼리 말을 받는 소스
검색은 관리자가 자유롭게 적어요(검색 하나가 데이터셋 하나). 저장할 때 **허용된 명령의 목록**으로 검사해요. 차단 목록이 아니에요.
- 검색을 명령으로 나눠 모든 명령이 허용 목록(프리셋이 소스 제품마다 갖고 있어요) 안에 있어야 저장돼요. 목록에 없는 명령과 해석하지 못한 검색은 거절해요. 부작용이 있는 명령(저장, 삭제, 내보내기, 실행)은 허용 목록에 넣지 않아요.
- 소스 쪽 계정이 읽기 전용이라는 둘째 겹이 본선이에요. 검사는 첫째 겹이에요.
- 검색마다 시간 범위와 행 수 한도를 둬요. 한도에 닿으면 잘린 채 적용하지 않고 덜 받은 수집으로 멈춰요. "기대하는 컬럼"은 `shape` 기대 조건으로 적어요.

### 13.3 나가는 연결의 허용 목록과 비밀 값
일꾼과 수집기가 닿을 수 있는 곳은 소스의 `endpoints`에 적은 주소뿐이고 기본은 막힘이에요(주소를 더하는 것은 정의의 변경). 소스에는 비밀 저장소의 참조(`credential_ref`)만 저장하고, 값은 비밀 값 제공자 포트 뒤에서만 읽어요. 로그와 지표에는 이름표와 수만 있어요.

### 13.4 소스를 지키는 값
소스마다 `protection`이 있고 값은 모두 **가정**이에요. 어댑터 앞단에서 강제해서 프리셋이 우회하지 못해요.

| 값 | 기본 | 비고 |
|---|---|---|
| `max_concurrency` | 1 | 소스의 세션과 작업 한도가 낮은 경우가 많아요 |
| `rate_limit` | 프리셋이 선언 | 요청 수 상한 |
| `retry` | 최대 3번, 물러났다 다시 하기 | 소스가 알려 준 대기 시간을 지켜요 |
| `breaker` | 잇달아 5번 실패하면 끊기 | 인증 실패는 바로 끊어요(계정이 잠기지 않게). 한 번의 시험 요청으로 닫아요 |
| `windows` | 받아도 되는 시간대 | 밖이면 건너뛰고 기록 |
| 예산 | 실행 하나의 요청 수·바이트·시간 상한 | 닿으면 덜 받은 수집 |

### 13.5 민감 등급이 컬럼에서 속성으로 흘러요
소스의 컬럼에 `sensitivity`(`open` / `restricted` / `confidential`)를 적어요. 프리셋이 기본값을 주고 관리자가 고쳐요. 정제를 지나며 출력 컬럼의 등급은 입력 가운데 가장 높은 것이 돼요. 속성의 등급은 매핑된 컬럼의 등급보다 낮을 수 없어요. 낮추려면 까닭을 적고 `admin`의 승인을 받아요. ADR-0012의 속성 등급과 한 체계예요. 원본 기록과 떼어 둔 기록을 읽는 것도 등급과 권한을 따라요.

## 14. 안전장치
자동으로 적용하기 전에 멈추게 하는 검사예요. 숫자는 모두 **재지 않은 가정**이에요.

### 14.1 배치
| 장치 | 무엇을 보나 | 멈추면 | 누가 무엇을 |
|---|---|---|---|
| 덜 받은 수집 | 쪽 넘김이 끝까지 갔나, 소스가 알린 수와 맞나, 지난번보다 기록 수가 크게 줄었나(30% 이상) | 뒤로 가지 않고 원본 기록에 "불완전"으로 남아요. 안 보임으로 세지 않아요 | `operator`가 원인을 보고 다시 받아요 |
| 같음 | 입력이 같은가 | 새 KG 버전을 만들지 않아요 | 없음 |
| 사람의 확인 | 처음 적용, 정의를 고친 뒤 첫 적용, 표준 모델이 오른 뒤 첫 적용, 실행기의 의미 버전이 오른 뒤 첫 적용 | 후보와 차이를 보여 주고 기다려요 | `operator`가 차이를 보고 확인 |
| 모양의 바뀜 | 컬럼과 자료형 | 멈춰요 | 정의를 고치거나 `operator`가 확인 |
| 대량 사라짐 | 객체가 10% 이상이면서 5건 이상, 또는 500건 이상 사라짐 | 멈춰요 | `operator`가 확인 후 적용하거나 버려요 |
| 안 보임 | 온전한 수집에서 잇달아 3번 | 그제야 물러남으로 표시해요 | 없음. 이력에 남아요 |
| 기대 조건 `fail` | 12절 | 그 공급의 적용을 멈춰요 | 담당자에게 알려요 |

### 14.2 흐름
흐름에는 온전한 수집이 없으니 **안 보인다고 물러나게 하지 않아요.** 지움 사건과 맞추기만 물러나게 해요.

| 장치 | 무엇을 보나 | 멈추면 | 누가 무엇을 |
|---|---|---|---|
| 붙잡기 `held`: 비율 | 짧은 시간에 너무 많이 사라지거나 바뀌었나(비율과 창은 재서 정해요) | 그 소스의 **적용**을 붙잡아요. 받기는 멈추지 않고 받은 변경의 기록에 쌓여요(잃지 않아요) | `operator`가 `release`나 `discard`(4.2) |
| 붙잡기: 모양 | 받은 모양이 바뀌었나 | 같아요 | 정의의 새 판을 병합하면 붙잡힌 자리부터 다시 돌려요 |
| 붙잡기: 기대 조건 | `fail`을 어긴 기록 | 기록을 떼어 두고 붙잡아요 | 같아요 |
| 맞추기 | 전부 받아 어긋난 것을 바로잡아요 | 지움은 14.1의 안 보임 규칙을 따라요 | 없음 |

붙잡힌 동안 쌓이는 변경은 조용히 버려지지 않아요. 쌓인 양이 보관의 한도에 가까워지면 알림이 올라가고, 한도를 넘으면 오래된 것부터 오래된 것의 자리(열 단위 파일을 객체 저장소에 내려 두는 포트)로 내려가요. 내려 둘 자리가 없으면 그 소스의 수집을 멈추고(소스가 읽은 자리부터 다시 줄 수 있을 때) 알려요. 밀림은 신선도에 보여요(ADR-0013). 정의를 고치는 것은 흐름에서도 브랜치와 후보 실행을 거쳐요. 병합되면 그 자리부터 새 정의로 흘러요.

## 15. 수 맞춤
원본 기록 하나는 끝에 넷 중 하나로 분류돼요: **쓰임**(객체나 링크 하나 이상에 기여) / **규칙이 걸러 냄**(어느 규칙인지) / **문제**(어느 문제인지) / **안 쓰임**. 넷의 합은 받은 수와 같고, 단계마다 들어온 수는 나간 수와 떨어진 수(이유와 함께)의 합이에요. 한 행이 객체도 링크도 되어도 한 번만 세요. 객체나 링크는 원본 기록의 참조와 규칙의 버전을 가져서, 값 하나의 근거는 같은 규칙을 다시 돌려 보여요(같은 입력이면 같은 결과). 값마다 출처를 저장하지는 않아요.

지어낸 예: 엑셀 120행을 받았어요. 정제(고르기: 계획 중인 장비 제외)에서 120 = 116 + 4(규칙이 걸러 냄). 공급에서 116 = 108 + 8(식별 키가 빈 6행은 문제, 매핑 안 된 2행은 안 쓰임). 끝의 분류는 쓰임 108 + 걸러 냄 4 + 문제 6 + 안 쓰임 2 = 120이에요. 맞지 않으면 그 동기화는 맞춤 실패로 문제 목록에 올라요(ADR-0013이 관측해요).

## 16. 엑셀
위치·전원·냉방의 주된 길이에요. 양식(랙 위치, 전원 계통, 냉방 계통)을 내려받아 채우면 매핑 없이 받아요. 한 줄에 장비 하나인 목록 형식을 받고, 격자 모양의 실장도는 읽지 않고 목록 양식을 안내해요.

- **양식**: 한 시트 = 한 표, 헤더 한 줄. 고정 시트 이름과 양식 버전 칸. 숨은 행에 안정 컬럼 ID를 두어 표시 이름을 바꿔도 매핑이 이어져요. 지어낸 위치 양식의 컬럼: `rack_id`, `u_start`, `u_height`, `device_name`.
- **업로드**는 `manual_only` 소스의 전부 받기 한 번이에요. 파일의 해시가 같으면 다시 올려도 한 번만 받고, 지난 파일과의 차이가 변경으로 보여요. 같은 안전장치를 거쳐요.
- **행의 문제**는 문제로 분류되고 나머지는 진행돼요(15절). 파일이 열리지 않거나 상한을 넘거나 압축 검사에 걸리면 덜 받은 수집이에요.
- **안전 한도(가정)**: 파일 20MB, 압축 푼 200MB, 압축비 100:1, 시트 50개, 시트당 셀 100만. 수식은 계산하지 않고 값으로만 읽어요. 매크로 파일과 옛 형식은 받지 않아요.
- 파서는 포트 뒤에 두고 버전을 고정해요(구현은 뒤 변경에서 고르고 라이선스를 봐요). 엑셀의 값은 `declared`이고 등급은 기본 `fact`, 어림 표시가 있으면 `assumed`예요.

## 17. 시험 자료
- **지어낸 세계 생성기**: 시드가 같으면 같은 세계가 나와요. 세계를 먼저 만들고 **정답 KG**를 갖고, 같은 세계에서 **배치의 모양**(엑셀 양식, HTTP JSON, SQL 덤프)과 **흐름의 모양**(같은 세계의 변화를 사건의 열로: 교체, 이동, 상태 바뀜)을 함께 내요. 소스 사이의 키가 맞물려 식별과 병합을 시험할 수 있어요. 시각, ID, 정렬은 주입해서 같은 입력이면 같은 결과예요.
- **흩뜨리는 장치**: 배치는 모양 바뀜, 덜 받음, 대량 사라짐, 키 중복, 합친 셀, 격자 엑셀, 수식 셀, 작은 합성 압축 폭탄, 느린 응답과 오류. 흐름은 중복 전달, 순서 뒤바뀜, 늦은 사건, 재개 실패, 지움 사건 누락, 폭주, 스트림 끊김.
- 프리셋마다 지어낸 입력 행 → 기대 객체와 링크의 견본 시험이 있어야 실려요. 이름과 주소는 예시용으로 예약된 것만 쓰고, 실제 데이터는 저장소에 두지 않아요.

## 18. 알고 가는 한계, 아직 정하지 않은 것
- 여러 제품의 안쪽 동작과 부하 특성, 흐름 소스의 전달 보장은 일부만 확인했어요. 모든 소스가 중복과 순서 어긋남을 낸다고 전제해요.
- 열네 연산의 수와 모든 숫자(안 보인 번수, 비율, 한도, 보관 기한, 상한)는 가정이에요. 견본 시험과 알파에서 고쳐요.
- 선언만으로 되는 것은 단순한 요청까지예요. 까다로운 소스는 어댑터가 따로 필요해요.
- 처리 속도는 저장소 입출력 없이 잰 작은 시제품의 값이에요. PostgreSQL에 변경 묶음을 적용하는 속도는 묶음의 크기에 따라 초당 수만~십만 행(작은 시제품)이고, 지속되는 변경이 초당 2~3만 행을 넘으면(추정) 받은 변경의 기록을 메시지 기록 저장소 어댑터로 바꾸거나 KG를 나눠요. 어디서 갈아타는지는 재서 정해요.

**아직 정하지 않은 것**
- 맞추기가 드문 소스에서 잇달아 안 보인 번수(기본 3)를 어떻게 다룰지.
- 객체를 만든 공급이 여럿일 때 객체가 물러나는 때.
- 한 기록에서 나온 행들의 분류가 갈릴 때 수 맞춤의 분류 순서.
- 같은 순위, 같은 사건의 때일 때의 이기는 규칙(`ingest_seq`로 가린다고 적었어요).
- "이어 붙이기"의 정확한 뜻(컬럼 값을 이어 한 컬럼으로 만드는 것으로 적었어요)과 모으기의 컬럼 목록을 정의에 적는 방식.
- 소스를 지키는 값을 느슨하게 할 때의 승인.
- 수집 봉투의 서명, 파일 드롭, 흐름의 안전장치의 비율과 창, `tick`의 간격, 묶음의 크기.
