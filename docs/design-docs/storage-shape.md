# 새 저장의 모양

KG를 PostgreSQL에 어떤 테이블로 저장하고, 모델이 바뀌면 그 테이블과 뷰를 어떻게 따라가고, 변경을 어떻게 적용하는지의 설계예요. 결정은 ADR-0080에 있어요. **이 문서의 저장 모양은 구현했어요(ADR-0089, ADR-0094). 변동 값을 값 열에 두는 것, `t_` 테이블의 이름 인덱스, 시각 값의 형식 검사는 ADR-0101에서 질의 스키마의 모양에 맞췄어요. 질의 스키마의 뷰와 함수, 등급마다의 스키마와 역할은 ADR-0113이 구현했어요. 질의 실행기와 그래프 함수 같은 뒤의 단계는 아직 예정이에요.** [KG의 저장과 버전](kg-storage.md)과 [KG의 적용](kg-storage-apply.md)에는 옛 테이블 설명이 남아 있고, 메모리·파일 저장소와 스냅샷을 훑는 질의 엔진도 걷어낼 때까지 코드에 있어요. 예시의 이름과 값은 지어낸 것이에요. 사용자가 보는 질의 스키마는 [질의 스키마](query-schema.md)에, 질의를 안전하게 돌리는 방법은 [질의 실행기와 읽기의 세 경로](query-execution.md)에 있어요.

## 1. 목적과 다루는 질문

- 제품이 뜻을 계산하지 않고 사용자가 SQL로 묻는다면, KG는 어떤 모양으로 저장해야 사용자가 쓰기 쉽고 빠른가.
- 표준 모델과 조직의 커스텀 속성이 바뀌어도 테이블을 다시 쓰지 않으려면 어떻게 하나.
- 한 KG에 객체와 링크가 수천만 개여도 되는 구조인가(REQ-134). 무엇을 측정했고 무엇이 추정인가.
- 작은 변경, 큰 변경, 전체 다시 만들기는 각각 어떻게 적용하고, 그동안 읽는 쪽은 무엇을 보나.

## 2. 개요

- 저장소는 PostgreSQL 하나예요(기준 버전 18. 19에만 있는 기능에 기대지 않아요). KG마다 **저장 스키마** `s_<kg_no>`를 따로 둬요.
- **타입마다 테이블 하나, 테이블 안의 진실은 속성 번호가 키인 문서(`doc jsonb`)**예요. 타입 있는 컬럼은 저장하지 않고 뷰가 문서에서 꺼내요(구성 C).
- **링크는 테이블 하나, 키는 정수**예요. 객체는 DB 전체에서 하나뿐이고 다시 쓰지 않는 번호(`obj_no`)로 가리키고, 밖에서 기억하는 참조는 지금의 해시 id(`ref`)예요.
- 모델(타입, 속성, 링크 타입)이 바뀌면 **스키마 관리기**가 DDL을 만들어 따라가요. 더하는 변경은 온라인이고 테이블을 다시 쓰지 않아요.
- 변경 번호의 순서, 확정 버전, 그래프 해시, 식별과 병합, 미리 보기의 계약은 그대로예요.
- **저장 포트**: 쓰기 쪽 계약(KG 목록, 쓰기, 변경 기록)과 적용이 쓰는 읽기(키로 읽기, 미리 보기)는 그대로 남아요. 질의 엔진이 쓰던 읽기 쪽 `Reader`(스냅샷 훑기)는 2단계에서도 남고, 5단계에서 스냅샷 엔진과 함께 걷어요(ADR-0025).
- **순서**: 1단계부터 정의, 수집 상태, 실행 기록, 식별 기록은 PostgreSQL의 표에 두고, 로컬 한 대는 제품과 PostgreSQL을 한 번에 띄우는 구성 파일로 떠요([PostgreSQL의 HA](postgres-ha.md) 9절). 지금의 파일 저장소 위의 길(`ingest run -data-dir`, `local`)은 5단계에서 걷어낼 때까지 새 기능 없이 그대로 돌아요.

```
 공용 스키마      KG 목록, 스키마 상태, 번호의 시퀀스와 함수, 저장 형식, 해시 키(ADR-0089: 머리·임대·세대 사건·확정 버전은 KG의 스키마에 있다).
                 KG의 행이 아닌 것: 정의(소스, 매핑, 조직 속성, 저장한 질의, 간선 정의), 시크릿 암호문, 동기화 실행 기록과 소스의 상태(`sync_run`, `source_state`, `source_dataset`), 감사
 s_<kg_no>       head · lease · generation_event · version · version_hash_part ·
                 object · object_state · t_<type_no> × 타입 수 · s_<type_no> × 변동 속성이 있는 타입
 (KG마다)         link · object_hist · link_hist · 변경 배치와 항목 · 가벼운 변경 · 식별자와 식별 이벤트 ·
                 수집의 순서 사건 · 모델 설명 테이블 4개 · 수집의 영구 테이블과 준비 테이블(ADR-0095)
 q_<kg_no>_<등급> 사용자가 보는 질의 스키마(뷰와 함수). 저장하지 않고 스키마 관리기가 만든다
```

## 3. 테이블

### 3.1 KG마다의 저장 스키마 `s_<kg_no>`

| 테이블 | 내용 |
|---|---|
| `object` | 등록부. `obj_no bigint`(DB 전체에서 하나뿐이고 다시 쓰지 않는 번호, 3.3절), `ref text`(지금의 해시 id. 밖에서 기억하는 참조), `type_no`, `name`, `min_grade`(속성들의 가장 약한 근거 등급), `seq_from`, `retired_seq`(물러난 변경 번호. 살아 있으면 비어 있어요), `first_key jsonb`(처음 본 키) |
| `object_state` | 모든 타입이 가진 상태 둘(`lifecycle_state`, `oper_state`)의 값 열 `a<번호>`와 관측 시각 열 `a<번호>_at`, 값마다의 등급·근거·관측 시각·출처 `prov jsonb`(값은 `prov`에 없어요). 이력 없이 제자리에서 갱신하고 채움 비율(fillfactor)은 70 |
| `t_<type_no>`(타입마다) | `obj_no`(기본키), `ref`, `name`, `min_grade`, **`doc jsonb`**, `source_refs`(행 단위의 출처), 내용 해시와 행 합(`row_hash`. 그래프 해시의 합에 드는 그 행의 항), `seq_from`. 채움 비율 85. 커스텀 속성도 `doc`에 들어가요. 인덱스는 기본키, 정확한 이름(`t_<type_no>_name`), 대소문자를 무시한 이름 접두어(`t_<type_no>_name_ci`)와 검색 집합의 식 인덱스예요. `ref` 인덱스는 없어요(`ref`로 찾는 일은 등록부 `object`가 맡아요) |
| `s_<type_no>` | 공통 둘 말고 변동(`volatile`) 속성이 있는 타입에만 둬요. 그 속성의 값 열 `a<번호>`와 관측 시각 열 `a<번호>_at`, `prov jsonb` |
| `link` | `link_no`, `ref`, `type_no smallint`, `src`, `dst`, **`grade`**, **`basis`**, `discriminator`(진짜 컬럼), `doc jsonb`(링크 속성), `source_refs`, 내용 해시와 행 합, `seq_from`. 인덱스는 `(src, type_no, dst)`와 `(dst, type_no, src)`, 그리고 id로 찾는 `ref`의 유일 인덱스 |
| `object_hist`, `link_hist` | 닫힌 행을 모든 컬럼 그대로(번호 키의 문서, `seq_from`, `seq_to`) 옮겨요. 인덱스에 `(type_no, seq_to)`를 더하고, `link_hist`에는 id로 찾는 `(ref, seq_from)`을 더해요 |
| `head`, `lease`, `generation_event`, `version`, `version_hash_part` | KG의 제어 행. `head`는 한 줄이고 변경 번호, 세대, 읽기 워터마크, 적용 중의 상태, 해시 상태, 포기와 복원의 진행 표시, 이력의 하한(`history_floor`)을 가져요. `lease`도 한 줄이에요. 둘 다 제자리 갱신이 잦아 채움 비율을 50으로 둬요 |
| `object_key` | 식별 색인. `(type_no, ctx_no, sig_hash)`가 기본키이고 `obj_no`, `bound_seq`(묶은 변경 번호)가 있어요. 한 번 묶은 키는 다른 객체로 옮기지 않아요. 포기는 그 번호의 줄을 지우고 복원은 지우지 않아요. 인덱스는 `obj_no`와 `bound_seq` |
| `model_type`, `model_attribute`, `model_link_type`, `model_link_rule` | 모델 설명 테이블 넷. 저장 스키마에 테이블로 있고 질의 스키마에는 그 읽기 전용 뷰가 있어요([질의 스키마](query-schema.md) 7절) |
| `change_batch`, `change_entry`, `light_change` | 변경 배치와 항목, 가벼운 변경(변동 속성만 바뀐 변경). 객체를 `obj_no`로 가리켜요 |
| `object_identifier`, `identity_event` | 식별자와 식별 이벤트. 객체를 `obj_no`로 가리켜요 |
| `ingest_order` | 수집의 순서 사건 |
| `raw_record`, `record_wait`, `record_ref`, `record_problem` | 수집이 남기는 영구 테이블(원본 레코드의 현재 판, 사라짐과 걸러짐의 기다림, 레코드가 낸 찾기 키, 레코드의 문제). `raw_record`는 소스마다의 파티션이에요(ADR-0095) |
| `stage_*`, `calc_*`, `ingest_diff` | 새 수집 흐름의 준비 테이블. 로그 있는 테이블이고 KG마다 이 스키마 안에 둬서 비우는 일이 다른 KG를 잠그지 않아요. 수신용(`stage_record`, `stage_key`, `stage_end`, `stage_claim`)은 소스마다의 파티션이고 나머지는 KG마다 한 벌이에요. 실행이 끝나면 `TRUNCATE`로 비워요 |

- **문서의 모양**: `{"<속성 번호>": {"v": 값, "g": 근거 등급, "b": 근거 종류, "t": 시각, "r": 소스 참조}}`. 값 `v`가 없고 근거 등급이 `unknown`인 속성은 "모른다는 것을 안다"는 뜻이라서 속성이 아예 없는 것과 달라요.
- 변동 속성은 `doc`에 넣지 않아요. 이력이 없고 행과 해시에 들지 않는 것은 지금 설계와 같아요(ADR-0025 9번).
- **변동 값의 진실은 값 열 하나예요**(ADR-0101). 값은 열 `a<번호>`에 속성의 값 형의 컬럼 형(`ColumnType`)으로 있고, 같은 값이 `prov`에 또 있지 않아요. `prov`의 항목은 `{"<속성 번호>": {"g": 등급, "b": 근거 종류, "t": 관측 시각, "r": 출처}}`이고 `t`, `r`은 문서의 항목과 같은 키예요(값이 없고 시각과 출처가 없으면 `t`, `r`은 빠져요). 열 `a<번호>_at`은 같은 입력에서 `t`를 시각으로 바꿔 함께 쓰는 질의용의 시각이에요. 값이 없는 항목(알 수 없음)은 값 열이 비어 있고 `prov`의 항목이 있어요. 값을 읽을 때 `prov`에 그 속성의 항목이 없으면 값이 없는 것이에요. 열이 가진 것은 값이지 쓴 글자가 아니에요: 수(`number`)와 수량(`quantity`)은 정수로 읽히면 정수로, 아니면 십진 글로 돌아오고, 시각은 아래의 한 형식으로 돌아와요. 값이 같은 갱신(값, 등급, 근거가 같은 것)은 열의 형으로 견줘서 쓰지 않아요.
- 타입이 부모를 가지면 부모의 속성을 자식이 모두 물려받아요. **객체는 자기 타입의 테이블에만 있어요**: 부모 타입의 테이블도 만들지만 비어 있어요(ADR-0101이 테스트로 확인했어요). 부모 타입의 뷰가 자식 뷰의 `UNION ALL`이어야 하는 이유예요. 모델 데이터에는 자식에 `parent`만 적혀 있으므로, 이 규칙은 스키마 관리기가 자식 테이블과 뷰를 만들 때 풀어 넣어요([모델](kg-model.md)에 같은 규칙을 적어요).
- 물리 테이블의 이름은 변하지 않는 번호로 짓고(`t_105`) 사람이 읽는 이름은 뷰에만 써요. 타입과 속성의 이름을 바꿔도 행은 그대로예요(REQ-233, REQ-246).
- 시각의 값(속성 값과 변동 값의 관측 시각)은 **UTC의 한 형식**으로만 써요: 끝이 `Z`이고 초의 소수점 아래는 6자리까지에 끝이 0이 아니에요(Go의 `time.RFC3339Nano`가 쓰는 형식이에요). 적용기의 값 검사(`graph`)가 쓰기 전에 검사하고, 다른 모양(오프셋, 시간대 없는 글, 7자리 이상)은 그 레코드의 문제가 되어 저장에 가지 않아요. 변동 속성의 수량은 수예요(열이 숫자 하나라서 단위가 든 맵은 받지 않아요. 단위는 모델에 있어요). 불변(IMMUTABLE) 함수 하나가 글자를 시각으로 바꾸고, 뷰와 식 인덱스가 그 함수를 써요. 문서에 쓰는 값의 형은 쓰기 전에 모델로 검사해요(지금 그대로).

```sql
-- 가상의 예. 타입 번호 105의 테이블
CREATE TABLE s_1.t_105 (
  obj_no bigint PRIMARY KEY, ref text COLLATE "C" NOT NULL, name text NOT NULL,
  min_grade smallint NOT NULL, doc jsonb NOT NULL, content_hash bytea NOT NULL,
  seq_from bigint NOT NULL
) WITH (fillfactor = 85);
```

### 3.2 공용 스키마

**행 수에 비례해 자라는 테이블(변경 배치와 항목, 가벼운 변경, 식별자, 식별 이벤트, 수집의 순서 사건)은 공용이 아니라 KG의 저장 스키마에 있어요**(3.1절). KG를 지우는 일이 스키마를 지우는 일이 되고, 한 KG의 청소가 다른 KG와 같은 테이블에 있지 않고, 키가 작아지기 때문이에요. **KG의 제어 행(머리, 리스, 세대 사건, 확정한 버전과 부분합)도 KG의 저장 스키마에 있어요**(`head`, `lease`, `generation_event`, `version`, `version_hash_part`. ADR-0089 결정 28, 구현했어요). 그래서 한 KG의 적용은 한 스키마 안에서 끝나요. 공용에는 KG 목록(`kg_catalog`), 스키마 상태(`kg_schema_state`), 번호의 시퀀스와 함수(`praxium_next_obj_nos`, `praxium_next_link_nos`), 해시 키만 남아요. 여기에 KG의 행이 아닌 정의(소스, 매핑, 조직 속성, 저장한 질의, 간선 정의), 시크릿 암호문, 수집 상태와 동기화 실행 기록, 감사가 더해져요(결정은 ADR-0080이고 구현의 순서는 ADR-0080의 결과 절에 있어요). **예정(ADR-0086)에서 바뀌어요**: 수집 상태 가운데 행 수에 비례하는 것(원본 레코드, 사라짐과 걸러짐의 기다림, 레코드 참조, 레코드의 문제)은 공용이 아니라 KG의 저장 스키마에 둬요. 공용에는 실행 기록과 소스와 데이터셋의 상태 표시가 남아요([수집의 규모 설계](ingestion-at-scale.md) 5절). 저장 스키마의 번호 `kg_no`는 시퀀스(`kg_no_seq`)에서 받고 다시 쓰지 않아요(구현했어요. ADR-0087). 해시 키는 KG마다 하나이고 마스터 키로 감싸 공용의 테이블에 둬요. 기준 KG에서 갈라 만든 KG는 기준의 키를 물려받아요. 공용의 **저장 형식 번호**(`storage_format`의 한 행, 지금 2)를 DB에 적고, 서버는 DB의 번호가 자기가 아는 것보다 크면 이유를 알리고 시작하지 않아요(구현했어요). 옛 형식(1, 알파 릴리스의 테이블)에 KG가 든 DB도 이유를 알리고 시작하지 않아요. 옮기는 길은 없고 새 DB에 소스를 다시 적재해요(ADR-0094). 시크릿의 마스터 키는 언제나 DB 밖의 파일이고 서버마다 경로를 줘요. 키 파일의 기본 자리(지금은 데이터 폴더의 식별자에 묶여 있어요)와 정의의 파일 형식(가져오기와 내보내기의 형식으로 남길지)은 1단계의 결정 기록이 정해요. 정의와 수집 상태에는 `kg_id`를 두지 않는 것과 두는 것을 지금 설계대로 따라요([정의](definitions.md), [수집 서비스](ingestion-service.md)).

### 3.3 번호 `obj_no`와 참조 `ref`

- `obj_no`는 시퀀스 하나에서 받아요. **KG마다 1부터 세지 않아요.** 다른 KG의 번호와 조용히 맞아떨어져 잘못 쓴 조인이 빈 결과가 아니라 그럴듯한 틀린 결과를 내는 일을 막으려는 거예요. KG의 시점 복구(제품의 `Restore`)는 시퀀스를 되돌리지 않으므로 복원 뒤에 생긴 객체가 옛 번호를 받는 일이 없어요. 커밋 순서와 맞을 필요가 없어서 시퀀스를 써도 돼요(변경 번호는 지금처럼 머리 행의 카운터예요).
- **다시 나타난 객체**: 물러난 객체가 같은 식별 키로 다시 나타나면 같은 객체라서 같은 `ref`와 같은 `obj_no`를 받아요. KG의 복원으로 사라졌다가 다시 나타나도 같아요. 등록부의 행은 KG를 지울 때 말고는 지우지 않아요. `(KG, ref)`의 `obj_no`와 `type_no`는 영원히 같고(타입이 다르면 저장소가 손상으로 거절해요), 살아 있음의 열(물러난 변경 번호. 살아 있으면 비어 있어요)이 있어요. 진실은 타입 테이블이고 등록부는 찾기용이에요. "다시 쓰지 않는다"는 한 번호가 **다른** 객체를 가리키게 되지 않는다는 뜻이에요.
- **DB의 시점 복구는 달라요**: 백업과 WAL로 DB 전체를 되감으면 시퀀스도 그 시점으로 돌아가서, 되감기 전에 쓰인 번호를 다시 받는 객체가 생길 수 있어요. 그래서 그런 복원 뒤에는 세대를 올려요(참조의 계약이 세대를 봐요). 밖에서 기억하는 것은 `ref`예요.
- `obj_no`는 내용 해시에 넣지 않아요. 링크의 해시는 지금처럼 양 끝의 `ref`로 만들어요. 그래서 다시 만들어도 같은 해시가 나와요.
- 사용자가 쓰는 조인 키는 `id`(= `obj_no`)이고, 에이전트가 기억하는 값은 `ref`예요([질의 스키마](query-schema.md) 3절). 폐기된 `ref`가 어느 `ref`로 이어졌는지는 식별 이벤트에 남아요(ADR-0074 5항).

### 3.4 계획이 정한 모양 (ADR-0085)

- 계획은 순수한 유닛 `adapter.pgschema`가 만들고(`Build`), 실행은 `pgstore`가 해요. 물리 이름은 번호로만 지어요(`t_105`, `s_105`, 컬럼 `a481`와 `a481_at`).
- 상태 테이블 `object_state`의 컬럼은 **모든 타입이 가진 변동 속성**이에요(표준 모델에서는 둘). 이 집합이 바뀌면 더하는 변경이 아니라서 스키마 관리기가 거절해요.
- 인덱스는 검색 집합(`SearchSet`. 처음에는 식별 키를 이루는 속성을 모델에서 계산해 내요)과 상태 컬럼과 위의 고정 인덱스뿐이에요. 목록과 맵 값에는 인덱스를 두지 않아요.
- 식 통계는 표준 속성 전부에, 한 객체에 식 여덟까지 묶어요. 둘 이상이면 가장 흔한 조합(mcv)을 함께 둬요. 속성이 더해지면 새 속성만 새 객체로 만들어서 있던 객체는 그대로예요.
- 변경 항목은 `entity_kind`(0 객체, 1 링크)와 `change_kind`(0 더함, 1 바뀜, 2 물러남)를 숫자로 두고 `entity_no`로 객체나 링크의 번호를 가리켜요.
- **매니페스트**가 저장 스키마의 요약이에요(생성기 버전, 모델·번호·검색 집합의 해시, 타입마다의 속성). 상태(`ok`, `index_pending`, `stats_pending`)는 해시에 들지 않아요. 통계를 첫 적재 뒤에 만드는 KG가 어긋난 것으로 보이지 않게 하려는 거예요. `Diff`는 두 매니페스트에서 더하는 변경의 단계를 내고, 아니면 거절해요(5절의 표).
- 수집 흐름의 테이블(위의 둘)은 계획에 들어 있어요(생성기 버전 3, ADR-0095). 생성기 버전이 2인 KG는 `Diff`가 이 테이블들을 만드는 단계를 내서 `AdjustStorageSchema`가 맞춰요(생성기 버전이 바뀌어도 고정 테이블의 더하기뿐이고 그 단계를 아는 버전이면 따라요). 소스의 파티션(`<테이블>_p<src_no>`)은 소스를 KG에 붙일 때 만들고, 매니페스트는 그 이름도 아는 이름으로 봐요. 소스를 붙이고 떼는 문장과 이름과 열은 `pgschema`가 줘요.
- 한 트랜잭션이 잡는 잠금: 표준 모델의 KG 하나를 만드는 데 2,357개, 스키마를 지우는 데 4,590개예요(기본 설정의 잠금 테이블 6,400개의 37%와 72%). 소스가 붙은 KG를 한 트랜잭션에 지우면 소스마다 약 68개가 더 들어서, 소스를 하나씩 먼저 떼고 지워야 해요(ADR-0095).

## 4. 왜 이 모양인가 — 세 구성의 견줌

같은 합성 데이터로 구성 셋을 만들어 쟀어요. 이 절의 수치는 모두 **측정**이고 조건은 이래요. 세계는 합성(생성기 `-seed 7 -scale 3300000`)으로 객체 1,166,114와 링크 2,080,287, 가장 큰 타입(가상 머신)은 127,514행이에요. PostgreSQL 19.0, CPU 2개, 메모리 8GB, `shared_buffers=1GB`, `work_mem=4MB`, `jit=off`예요. **쓰기 값은 `fsync`, `synchronous_commit`, `full_page_writes`를 끄고 `wal_level=minimal`로 쟀으므로 낙관적**이에요. 다른 작업이 같은 기계에서 가끔 돌아 1분 부하가 0.4~5.8로 흔들렸고, 값은 중앙값(3~5회)이에요. 캐시를 비운 값은 없어요. PostgreSQL 18에서는 돌리지 않았어요.

| 구성 | 요약 |
|---|---|
| A | 값을 진짜 컬럼에 두고 출처(근거 등급, 근거 종류, 시각, 소스 참조)는 따로 둔다 |
| B | 문서가 진실이고 값 컬럼은 저장 생성 컬럼(STORED generated column)이다 |
| **C** | **문서가 진실이고 값 컬럼은 뷰의 식이다. 검색 속성에만 식 인덱스와 식 통계를 둔다(고름)** |

| 항목(객체 117만) | A | B | C |
|---|---|---|---|
| 전체 크기 | 2,089MB | 2,318MB(+11%) | 2,168MB(+4%) |
| 처음 적재(COPY) / 인덱스 만들기 | 18.5초 / 6.9초 | 25.3초 / 6.4초 | 22.1초 / 9.4초 |
| 인덱스 있는 이름 검색 | 0.1ms | 0.1~0.2ms | 0.3ms |
| 7단계 패턴, 모든 랙 / 4단계 한 랙 | 532ms / 3.0ms | 544~667ms / 2.9~4.7ms | 620~689ms / 3.1~3.3ms |
| 집계(가상 머신 12.7만 행) | 30ms | 38ms | 48~58ms |
| 컬럼 11개를 모두 읽기 | 93ms | 105ms | 232ms |
| 시각 속성 범위 검색(인덱스 없음) | 7ms | 6.6ms | 66ms |
| 통계 없는 불리언 하나 조건의 행 수 추정(실제 22,315) | 22,220 | 22,517 | 63,757 |

- **A를 버린 이유**: 가장 작고 빨라요(크기 −4~11%, 적재 +17~27%). 그러나 적용, 해시, 확정, 복원, 미리 보기의 코드를 새로 써야 하고(문서와 컬럼 사이를 오가는 이력 형식이 필요해요), 속성 이름을 바꾸면 이력의 키가 깨지고, "모른다"와 "값 없음"의 구분과 쓴 값과 읽은 값의 일치를 따로 증명해야 해요.
- **B를 버린 이유**: 읽기는 A와 같지만 **컬럼을 더하는 모델 변경이 테이블을 잠그고 다시 써요.** 12.7만 행에서 1초, 읽기가 최대 0.9초 막혔어요. 3천만 객체의 가장 큰 타입(약 320만 행)에서는 약 26초로 **추정**해요(행 수에 비례, 행당 약 8μs). "테이블을 다시 쓰는 스키마 변경 금지"([PostgreSQL 운영](postgres-operations.md) 7번과 [PostgreSQL의 HA](postgres-ha.md)의 스키마 변경 규칙)에 걸려요.
- **C의 약점과 막는 법**: 컬럼을 많이 읽거나 집계하면 B의 1.3~2.2배 느려요(시각 속성은 인덱스가 없으면 10배, 66 대 6.6ms). 통계가 없는 속성은 계획이 크게 틀려요(위 표의 조인 추정 3,390만 대 실제 4.3만). 그래서 **통계는 표준 속성 전부에 기본으로 만들어요**(통계는 쓰기를 느리게 하지 않고 인덱스만 느리게 해요). 식 인덱스나 식 통계를 주면 추정 행 수가 진짜 컬럼과 같아졌어요.
- **고른 이유 하나 더**: C는 문서가 진실이고 컬럼은 읽을 때 계산해서, 포트의 계약(쓰기, 해시, 이력)이 지금 그대로 남아요. 우선 기능(소스 연결, 매핑 편집)이 지금의 저장 포트 위에서 먼저 돌 수 있는 것도 이 때문이에요.

## 5. 스키마 관리기

**스키마 관리기**는 모델(표준 모델과 조직 속성)을 받아 저장 스키마의 테이블, 인덱스, 통계와 질의 스키마의 뷰, 함수, 주석(`COMMENT`)을 만드는 코드예요. 모델을 받는 순수한 함수(`adapter.pgschema`)가 DDL 계획과 매니페스트를 내고, 실행기(`adapter.pgstore`)가 그 계획을 DB에 적용해요. 두 매니페스트의 차이에서 더하는 변경의 단계를 내는 것도 순수한 함수예요(ADR-0085). **구현한 것**(ADR-0087): 실행기가 테이블, 인덱스, 통계를 만들고 따라가요. **ADR-0113이 더한 것**: 같은 계획이 질의 스키마의 뷰와 함수와 설명(`COMMENT`)과 권한도 내고(생성기 버전 8), 실행기가 역할을 만들어요. 모델 설명 테이블 넷은 생성기 7의 고정 테이블이고 모델이 바뀔 때마다 비우고 다시 채워요. 질의 스키마는 스키마 관리기가 일을 할 때마다 통째로 지우고 다시 만들어서 만든 것과 따라간 것이 같아요. 모델이 타입 서넛짜리여도 돌아야 하므로 테스트는 작은 모델을 쓰고, 표준 모델 전체는 적합성 테스트와 스키마 테스트에서만 써요.

| 모델의 변경 | DDL | 영향 |
|---|---|---|
| 타입을 더한다 | 테이블과 인덱스를 만들고 뷰를 더해요 | 기존 테이블에 영향 없음 |
| 속성을 더한다 | **뷰를 다시 만들고**(필요하면 식 인덱스와 통계를 온라인으로 더해요) | 테이블을 다시 쓰지 않아요(C의 원형: 뷰 49ms) |
| 타입이나 속성의 이름을 바꾼다 | 뷰와 `COMMENT`만 다시 만들어요(스키마 관리기가 일을 할 때. 이름은 모델 해시에 들지 않아서 이름만 바뀐 모델에서는 아직 돌지 않아요, [질의 스키마](query-schema.md) 12절) | 행과 이력은 그대로(번호가 키) |
| 속성을 "검색에 쓴다"로 표시한다 | 식 인덱스를 `CREATE INDEX CONCURRENTLY`로 만들어요 | 읽기를 거의 안 막아요(원형: 읽기 최대 8~112ms) |
| 타입이나 속성을 없앤다 | 뷰에서 빼요. 행의 정리는 구현할 때 정해요 | 테이블을 다시 쓰지 않아요 |

- **규칙**: 새 컬럼과 새 테이블은 NULL 허용이거나 비어 있어요. 테이블을 다시 쓰는 변경은 하지 않아요. 인덱스는 항상 온라인이에요. DDL에는 짧은 잠금 시한(`lock_timeout`)과 다시 시도가 있어요.
- **한 번에 하나만**: 마이그레이션처럼 트랜잭션 범위의 어드바이저리 잠금으로 한 번에 하나만 돌아요. 서버가 여러 개이고 두 판이 함께 도는 동안에는 더하는 변경만 해요([PostgreSQL 운영](postgres-operations.md) 7번).
- **트랜잭션**: KG 하나의 DDL은 한 트랜잭션이에요(PostgreSQL의 DDL은 되돌려져요). `CREATE INDEX CONCURRENTLY`만 트랜잭션 밖의 따로 단계이고, 끝난 뒤 무효 인덱스를 찾아 정리해요.
- **실행기의 동작**(구현했어요. ADR-0087): 만들 때는 시퀀스에서 `kg_no`를 받고 계획의 문장을 쓰기 풀의 마이그레이션 역할로 한 트랜잭션에서 돌려요. 질의 스키마는 그 뒤에 이름마다 한 트랜잭션이에요(ADR-0126, 아래 "KG의 생성과 삭제"). KG마다의 어드바이저리 잠금과 `lock_timeout`으로 같은 KG의 동시 실행을 막고, 잠금을 못 얻으면 몇 번 다시 시도해요. 매니페스트(`kg_schema_state`의 행)는 마지막에 써서 도중에 죽으면 스키마도 행도 남지 않고, 다시 불러도 같은 결과예요. 맞출 때는 저장된 매니페스트와 새 매니페스트의 `Diff`에서 트랜잭션 안의 단계를 한 트랜잭션에, 트랜잭션 밖의 단계(`CREATE INDEX CONCURRENTLY`)를 하나씩 돌려요. 그 전에 무효 인덱스를 지우고, 끝난 뒤 스키마와 매니페스트를 견줘 모자란 인덱스를 만들고 매니페스트가 모르는 검색 인덱스를 지워요. 인덱스를 만드는 동안 상태는 `building`(만드는 중), 멈춰 있으면 `index_pending`이고 끝나면 `ok`예요. `building`인 채 30분이 지나면 다른 실행이 이어받아요. 더하는 변경이 아니면 아무것도 바꾸지 않고 거절해요. 모델의 해시가 저장된 것과 다르면 "스키마 어긋남"을 내는 함수(`CheckSchemaMatch`)가 있고, 적용과 질의의 길에 거는 것은 새 저장의 변경이 해요.
- **뷰 전체 다시 만들기**: 원형에서 뷰 약 300개와 함수를 한 트랜잭션으로 지우고 다시 만드는 데 0.41~0.49초였어요. 돌고 있는 질의가 뷰를 잡고 있으면 DDL이 기다리고, 기다리는 동안 그 뷰를 읽으려는 새 질의가 뒤에 줄을 서요. 시한과 다시 시도로 줄이는 것이 기본이에요. 뷰를 새 판으로 옆에 만들어 두고 한 번에 바꿔 다는 방법도 있는데, 쓸지는 구현할 때 정해요.
- **모델 버전의 기록**: 저장 스키마마다 적용한 모델의 해시를 DB에 적어요. 서버는 시작할 때와 질의 실행기가 머리 행을 읽을 때 이 해시를 서버의 모델의 해시와 견주고(견주는 것은 해시예요), 다르면 그 KG의 **적용과 질의를 모두** "스키마 어긋남"으로 거절해요. 진단 명령이 뷰, 식 인덱스, 식 통계의 차이를 보여요(예정). 버전을 올리는 동안 옛 서버가 읽기를 계속 받게 하는 길(더하기만 한 변경에서 직전 모델을 함께 받아들이기)은 2단계의 설계가 정해요(미결). 문서가 진실이어서 컬럼과 뷰는 모두 다시 만들 수 있고, 그래서 실패의 값이 작아요.
- **KG의 생성과 삭제**: 생성은 저장 스키마와 질의 스키마와 (KG, 민감 등급)마다의 역할을 만들어요. 설치 역할에 역할을 만드는 권한과 카탈로그 함수의 권한을 바꾸는 권한이 필요하고, 필요한 권한은 배포 안내서에 적어요. 저장 스키마와 질의 스키마를 한 트랜잭션에 만들면 기본 잠금 테이블의 80%를 넘어서, 생성은 저장 스키마와 만드는 중 표시(공용 `kg_making`)를 한 트랜잭션, 질의 스키마를 이름마다 한 트랜잭션으로 하고 마지막이 표시를 지워요. 질의 스키마가 실패하면 만든 것을 삭제의 단계로 지워요. 서버가 죽어 남은 표시는 기한(트랜잭션마다 늘어나요)이 지난 뒤 서버가 시작할 때나 같은 이름의 KG를 만들 때 지워요([ADR-0126](adr/0126-make-and-adjust-a-kg-in-steps-one-query-schema-to-a-transaction.md)). KG의 삭제는 스키마를 지우는 일이라 행을 지우며 테이블이 부푸는 일이 없어요. 스키마 전체를 한 트랜잭션에 지우면 잠금이 만들 때의 두 배쯤 들어서, 삭제는 여러 트랜잭션으로 나눠요: 삭제 중 표시(공용 `kg_deleting`), 소스 하나씩, 계산 테이블 몇 개씩, 질의 스키마 이름마다(역할은 마지막), 나머지 스키마와 목록의 행. 두 표시 중 하나라도 있는 KG는 읽기·쓰기·수집을 거절하고 목록에 보이지 않으며, 멈춘 삭제는 다시 부르거나 서버가 시작할 때 이어 해요([ADR-0125](adr/0125-delete-a-kg-in-steps-compute-tables-first.md)). 질의 스키마마다 만든 단계의 표시를 주석으로 남겨, 맞추기와 서버의 시작은 표시가 없거나 낡은 질의 스키마만 다시 만들어요(ADR-0126).

## 6. 자료형마다의 뷰의 식

타입 뷰의 컬럼은 문서의 `doc->'<속성 번호>'->>'v'`에서 꺼내요. 값의 형이 모델과 다르면 뷰가 오류를 내므로 쓰기 전에 모델로 검사하는 것이 필수예요(원형: 정수 컬럼에 글자 `"5.0"`이나 실수 `5.0`이 오류).

| 모델의 값 형 | 뷰의 컬럼 형 | 식(가상의 예. 속성 번호 `N`) |
|---|---|---|
| 문자열(`string`, `serial_number`, `fqdn`, `mac_address`, `ipv4_address` 등 기반 형이 문자열인 것) | `text` | `doc->'N'->>'v'` |
| 열거(`enum`), 참조(`ref`) | `text` | 같음. 열거 값의 검사는 쓰는 쪽이 해요 |
| 정수 | `bigint` | `(doc->'N'->>'v')::bigint` |
| 수량(`quantity`) | `numeric` | `::numeric`. 단위는 모델에 있고 값에는 없어요 |
| 수(`number`) | `double precision` | `::double precision` |
| 불리언 | `boolean` | `::boolean` |
| 목록, 맵 | `jsonb` | `doc->'N'->'v'` |
| 시각 | `timestamptz` | 시각 변환용 **불변 함수** 하나를 거쳐요(이름은 구현할 때 정해요) |

- **시각**: 글자에서 시각으로의 기본 변환은 불변이 아니라서 식 인덱스에 쓸 수 없어요. 그래서 형식을 UTC 한 가지(끝이 `Z`)로 고정하고 불변으로 표시한 함수 하나를 뷰와 식 인덱스가 함께 써요. 시간대 없는 글자는 세션 시간대에 기대므로 쓸 때 거절해요. **시각의 식 인덱스로 하는 범위 검색은 원형에서 재지 못했어요.** 글자 그대로 두면 26~500배 느렸어요(10절).
- 커스텀 속성도 `doc`에 있고 뷰에 타입 있는 컬럼으로 보여요. 컬럼 이름은 [질의 스키마](query-schema.md) 3절의 규칙을 따라요.
- 변동 속성은 문서가 아니라 상태 테이블(`object_state`, `s_<type_no>`)의 컬럼이에요.

## 7. 통계와 인덱스

- **통계는 표준 속성 전부에 기본으로** 만들어요. 안 쓰는 속성이어도 계획이 틀리지 않게 하려는 것이고 쓰기를 느리게 하지 않아요.
- **인덱스는 "검색에 쓴다"로 표시한 속성에만** 둬요. 표준 모델이 표시한 속성과 조직이 표시한 커스텀 속성에 식 인덱스를 온라인으로 만들어요. 인덱스 수는 쓰기 비용이에요: 12.7만 행을 적재할 때 인덱스 1개 대비 11개가 3.1~4.3배 느렸고(A 0.45초에서 1.94초, B 1.0초에서 3.2초, C 0.6초에서 2.4초), 5만 건 갱신의 WAL이 60~70MB에서 94~104MB로 49~57% 늘었어요(원형, 세 구성 모두). 안 쓰는 인덱스는 점검 명령이 보고해요([PostgreSQL의 HA](postgres-ha.md) 8절).
- **상태 테이블의 `oper_state`와 `lifecycle_state`에는 인덱스를 둬요.** "지금 내려가 있는 것 전부"가 가장 먼저 묻는 질문이라서예요(원형: 검색 16ms 대 훑기 수십 ms). 대가는 받아들여요. 값이 바뀌는 갱신은 제자리(HOT) 갱신을 못 해서 약 3배 비싸요(10만 건: 값이 바뀌면 HOT 0%, WAL 24MB, 0.95~1.2초. 시각만 바뀌면 HOT 100%, WAL 7.7MB, 0.55초). 그래서 **값이 같은 갱신은 쓰지 않아요**(스트림에서 합쳐요).
- **`t_<type_no>`에는 이름 인덱스 둘을 항상 둬요**(ADR-0101): 정확한 이름(`name`)과 대소문자를 무시한 이름 접두어(`lower(name) text_pattern_ops`. 데이터베이스의 정렬 규칙이 C가 아니어도 `LIKE 'ab%'`가 인덱스를 타게 하는 연산자 클래스예요). `ref`의 인덱스는 두지 않아요. `ref`로 찾는 일은 등록부(`object`의 `ref` 인덱스)가 맡고 타입을 알려 줘요. 타입마다 둘이라 표준 모델에서 336개이고, 비용은 쓰기 쪽이에요: 행 단위 길로 처음 적재하는 시간이 객체 598개의 세계에서 1.41초에서 1.44초(잡음 안), 객체 10,564개의 세계에서 31.1초에서 34.2초(+10%)였어요(인덱스를 지운 KG와 둔 KG에 같은 세계를 넣은 평균. 코어 2개의 기계라 잡음이 커요).
- **채움 비율**: 타입 테이블 85, 상태 테이블 70. 기본값 100에서는 제자리 갱신이 0.4~1.7%뿐이었고 85에서 약 19%, 70에서 약 45%였어요(원형, 5만 건). 대가로 테이블이 약 15% 커져요.
- 조인 순서 탐색의 한도는 PostgreSQL의 기본값을 유지해요. 올리면(16, 24) 7단계 패턴의 계획 시간이 7.9~10.7ms에서 87~125ms로 늘었어요.

## 8. 이력과 변경 기록

- 이력 테이블(`object_hist`, `link_hist`)은 번호 키의 문서에 `seq_from`, `seq_to`를 가진 지금 형식 그대로예요. 과거 시점의 읽기는 이 테이블과 지금 테이블을 합쳐요([질의 스키마](query-schema.md) 6절).
- 이력 인덱스 `(type_no, seq_to)`가 필요해요. 없으면 큰 적용 중의 이름 찾기가 100배 느렸어요(9.2절).
- 변동 속성만 바뀌는 변경은 상태 테이블의 제자리 갱신과 가벼운 변경 기록(`light_change`)으로 끝나요.
- 변경 배치와 항목, 변경 번호(머리 행의 카운터), 확정 버전은 지금과 같아요. 변경 번호를 머리 행에 두는 덕에 복제본에서도 읽혀요.

## 9. 적용

### 9.1 세 경로

| 경로 | 언제 | 방법 | 읽는 쪽이 보는 것 |
|---|---|---|---|
| **작은 적용** | 바뀌는 행이 한도(20만 행) 이하 | **한 트랜잭션**. 적용과 수집 상태의 저장을 같은 트랜잭션에 넣어요(**예정(ADR-0086)에서 바뀌어요**: 새 수집 흐름은 상태를 통째로 한 트랜잭션에 쓰지 않아요. 완료 표시는 머리 행이고 상태는 그 뒤에 멱등으로 반영해요) | 반쯤 적용된 KG를 보지 않아요 |
| **큰 적용** | 한도를 넘어요 | 청크(2천~1만 행)로 나눠 넣어요. 중단되면 이어 가거나 포기해요(지금 설계 그대로) | **읽기 워터마크(읽을 수 있는 변경 번호)까지의 모습** |
| **전체 다시 만들기** | 모델의 큰 변경 | 그림자 저장 스키마에 만들고 끝에 한 트랜잭션으로 바꿔 달아요 | 바꿔 달기 전까지 옛 스키마 |

- **포기와 KG의 복원**은 그림자 스키마를 쓰지 않아요. **변경 번호 하나씩 거꾸로, 번호마다 트랜잭션 하나로 제자리에서** 되돌려요(변경 항목으로 그 번호의 행만 찾아요). 머리 행에 진행의 표시("포기하는 중", "복원하는 중과 어디까지")가 있어서 도중에 서버가 죽으면 어느 서버든 이어서 끝내요. 포기는 읽는 쪽에 영향이 없어요(읽기 워터마크 뒤만 건드려요). 복원은 첫 트랜잭션에서 세대를 올리고, 끝날 때까지 그 KG의 읽기와 쓰기를 "복원하는 중"으로 거절해요.
- **작은 적용의 크기**: 20만 행은 약 25초, WAL 약 0.5GB로 **추정**해요(원형: 4개 타입 51k행이 5.4~6.6초, 비례로 늘린 값). 수집 설계의 "예정 상태"(적용 뒤 상태를 쓰기 전에 죽는 경우를 메우는 장치)는 같은 트랜잭션이라 필요 없어져요. 다만 저장소의 트랜잭션에 다른 단위의 쓰기를 싣는 포트를 새로 정해야 해요(구현할 때 정해요). **예정(ADR-0086)에서 바뀌어요**: 새 수집 흐름은 그 포트를 두지 않아요. 적용의 완료 표시는 머리 행이고 "예정 상태"도 쓰지 않아요.
- **큰 적용 중의 읽기**: 질의 스키마를 **두 벌** 둬요. 평소용의 얇은 뷰와, 큰 적용 중용의 번호 조건 뷰예요(지금 테이블에서 읽기 워터마크 이하인 행 + 이력에서 그 번호를 덮는 행). 질의 실행기가 질의마다 KG의 머리 행을 보고 어느 스키마를 쓸지 골라요. 질의 실행 중에는 DDL을 하지 않아요.
- **전체 다시 만들기**는 디스크를 전체 크기만큼 더 써요. 원형(117만 객체): 테이블 212개 채우기 6.8~18.7초 + 인덱스 6.1~9.3초 + 바꿔 달기 0.4~0.7초, 디스크 +1.66~1.90GB, 바꿔 달 때 읽기 최대 415~666ms(오류는 없었어요). 3천만에서는 약 25~30분, 디스크 약 46~50GB 추가로 **추정**해요.
- **긴 트랜잭션을 만들지 않아요.** 열린 트랜잭션이 청소를 막아 상태 테이블이 부풀어요(원형: 5천 행을 25초 동안 갱신하는 동안 30초짜리 읽기 트랜잭션이 열려 있으면 107MB에서 167~170MB로, 열려 있지 않으면 108MB). 트랜잭션 시한은 60초이고, 유휴 트랜잭션 시한을 모든 역할에 걸어요.

### 9.2 큰 적용 중 읽기의 비용

번호 조건 뷰는 비싸요(원형, 117만 객체, 가상 머신 12.7만 행 중 12,765행이 바뀌는 중): 이름으로 한 건 찾기 0.1ms가 8.6~10.7ms, 전체 개수 16~18ms가 52~68ms로 늘었어요. 커밋 지점 뒤에도 전체 개수가 36~55ms로 평소보다 2~3배 느렸어요(이력 가지가 남아요). 이력 인덱스 `(type_no, seq_to)`를 둔 값은 **측정하지 않았고** 구현할 때 다시 재요. 다른 길(긴 한 트랜잭션)은 옛 상태를 읽는 대신 중단 뒤 이어 가기를 잃어요(롤백, 처음부터).

### 9.3 배치와 스트림

- **배치**: 수집 → 계획(차이) → 적용. 차이는 DB 안의 묶음 연산으로 계산할 수 있어요(로그 있는 준비 테이블에 올리고 견줘요. 준비 테이블은 KG마다 저장 스키마 안에 둬서 비우는 일이 다른 KG를 잠그지 않아요. 원형: 51만 행에 1.7~3.6초, 행당 3.2~7.1μs). 3천만 행이면 약 2~3.5분으로 **추정**해요.
- **스트림**: 작은 변경을 시간이나 건수로 모아 적용해요(원형: 행 10개짜리 적용이 초당 1,500~2,450건. `fsync`를 끈 값이라 낙관적이에요). 적용마다 머리 행 잠금과 변경 번호 하나와 변경 배치 한 줄이 들어요. 변동 속성만 바뀌는 것은 상태 테이블의 제자리 갱신과 가벼운 변경 기록으로 끝나요. 큰 적용 중에도 스트림은 같은 KG의 머리 행이 줄을 세워요(기다려요).
- **같은 KG의 적용은 머리 행이 줄 세워요**(지금 그대로).
- 모음의 시간과 건수의 기본값은 구현할 때 정해요.
- **청소와 통계**: 스키마 관리기가 큰 테이블과 상태 테이블에 테이블마다 autovacuum 설정을 둬요(기본값은 죽은 행 20%라서 3천만 행에서 600만 행이 쌓여요). 큰 적용이 끝나면 청소와 통계 갱신을 해요. `link`의 순회는 `(src, type_no, dst)`와 `(dst, type_no, src)` 인덱스로 인덱스 전용 스캔이 되는데 이것은 청소에 기대요. `link`에는 쓰이지 않는 인덱스를 두지 않아요.
- **크기를 줄이는 길 셋**은 측정해서 정해요(미결). 이력 테이블의 압축, 한 곳에만 두는 저장 형식, `wal_compression`이에요.

### 9.4 구현한 쓰기 길 (ADR-0089)

새 저장(`Store`)의 쓰기 처리 경로를 구현했어요. `pgstore.Open`이 이 저장을 열고, 옛 테이블은 마이그레이션 0005가 지워요(ADR-0094). 서버는 시작할 때와 리스를 줄 때 끊긴 버리기·복원을 이어서 끝내요(`ResumeWork`).

- **한 청크 = 한 트랜잭션**: 머리 행을 잠그고, 작업·세대·리스·엔진·기대 머리를 지키고, 행을 쓰고, 머리를 옮겨요. 객체는 먼저 등록부(`object`)에 넣고(옛 번호가 있으면 같은 번호로 되살려요), 타입 테이블의 열린 행을 닫을 때 내용 해시가 같으면 이력으로 옮기지 않아요. 링크는 `(src, ref)` 순서로 번호를 받고 바뀐 링크는 번호를 지켜요.
- **상태만 바뀌면 타입 테이블은 그대로**예요. 휘발 값은 상태 테이블의 값 열에, 그 등급·근거·관측 시각·출처는 같은 행의 `prov`에 한 문장으로 써요(ADR-0101. 처음 구현은 값을 `prov`에 두고 열은 비워 뒀어요). 두 길(행 단위, 준비 테이블)이 같은 쓰기 함수를 써요.
- **버리기와 롤백(복원)**은 변경 번호마다 한 트랜잭션으로 거꾸로 가요. 진행은 머리 행(작업, 작업 번호, 바닥, 작업 머리)에 남아서 중간에 끊겨도 `ResumeWork`가 이어요. 롤백은 첫 트랜잭션에서 세대를 올리고, 끝날 때까지 읽기와 쓰기를 `CodeKGRestoring`으로 거절해요. 버리기는 `object_key`의 `bound_seq`가 그 번호인 행을 지워요.
- **리스**의 시계는 기본이 DB이고(`LeaseClockDB`), 적합성 테스트는 호출자의 시계를 써요(`LeaseClockCaller`). 커밋 결과를 모르면 머리를 다시 읽어 결과를 가려요.
- 적합성 36개(`Cases()` 31, `PreviewCases()` 5)가 새 저장에서 모두 통과해요. `adapter.pgcheck`는 지금의 수집과 질의 엔진이 새 저장과 메모리 저장에서 같은 그래프 해시와 같은 답을 내는지 봐요.

이 문서가 약속하는 것은 구조예요. 3천만의 **실제 측정은 더 큰 기계에서 같은 도구로** 해요. 합성 세계 생성, 적재, 관문 질의, 보고서를 담은 **규모 검증 도구**를 저장소에 넣어요(6단계. 예정). REQ-134는 바뀌지 않아요. 측정이 아직 못 한 것:

- 변경 배치와 항목, 식별자 등을 KG의 저장 스키마에 넣은 크기와 쓰기의 값(2단계의 관문에서 재요).
- 3천만의 실제 값, PostgreSQL 18에서의 확인, `fsync`를 켠 쓰기의 값, 캐시가 빈 상태의 값, 실제 복제본.
- 시각의 식 인덱스로 하는 범위 검색, 이력 인덱스를 둔 번호 조건 뷰의 비용.
- 구성 비교는 한 타입(12.7만 행)의 값이고, 그래프 함수와 동시 실행은 구성 B에서만 쟀어요(링크 테이블과 같은 인덱스를 쓰므로 구성에 의존하지 않을 것으로 추측해요).

## 11. 알려진 한계와 가정

- 원형은 제품 코드가 아니에요. 쓰기와 차이 계산은 SQL 수준의 흉내(COPY 대신 준비 테이블 복사)라서 파일 읽기 시간이 빠져 있어요.
- 수치는 가정이 아닌 측정이지만 부하가 흔들렸어요. 최솟값이 실제에 더 가까워요.
- 상태 테이블의 인덱스 비용, 채움 비율, 한도 값은 구현 뒤에 다시 측정해서 확정해요.

## 12. 미결 사항

- 번호 조건 뷰(큰 적용 중의 읽기)의 비용, 시각의 식 인덱스 범위 검색, 3천만의 실제 측정.
- 타입이나 속성을 없앴을 때 행을 정리하는 방법, 뷰를 판으로 바꿔 다는 방법을 쓸지.
- 적용 트랜잭션에 수집 상태의 쓰기를 싣는 포트(예정(ADR-0086): 새 수집 흐름은 두지 않아요).
- 스트림 모음의 시간과 건수.
