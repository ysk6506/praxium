# KG의 모델 설계

[ADR-0007](adr/0007-kg-model.md)의 결정을 풀어 쓴 문서예요. 데이터의 칸, 상태, 규칙, 가상의 예시를 담아요. 예시의 서버, 랙, 포트, 주소, 숫자는 모두 지어낸 것이고, 이름은 예시예요. 표준 모델의 타입 목록은 [표준 모델의 요약](standard-model.md)에 있어요.

## 1. 목적과 다루는 질문
- 타입이 열려 있어도(관리자가 더해요) 영향 범위가 뜻을 잃지 않으려면 무엇을 닫아야 하나요?
- "서버는 켜져 있는데 망에서 끊겼다"와 "서비스는 도는데 관리할 길이 끊겼다"를 어떻게 가르나요?
- 이중화(LACP, ECMP, BGP 세션, 전원 A·B)를 어떻게 적고, 모르는 구성원이 있으면 어떻게 읽나요?
- 모르는 것을 가정으로 메우지 않고, "없다"와 "모른다"를 어떻게 가르나요?
- 일련번호가 바뀌고 이름이 소스마다 달라도 같은 장비를 어떻게 알아보나요?
- 여러 조직이 타입을 더하고 고쳐도 비슷한 타입이 늘어나지 않게 하려면요?

이 문서가 정하지 않는 것: 영향 범위의 계산(결과의 종류, 고정점, 보는 기준)은 [ADR-0010](adr/0010-kg-queries-and-impact.md), 저장과 버전은 [ADR-0009](adr/0009-kg-storage-and-versions.md), 받는 단계는 [ADR-0008](adr/0008-ingestion.md), 역할과 권한은 [ADR-0012](adr/0012-access-control.md)가 정해요. 여기서는 채널과 뜻까지만 정의하고 가리켜요.

## 2. 개요
```
타입 등록부 (데이터, 열려 있음)          닫힌 것 (결정 기록으로만 바뀜)
  객체 타입 ─ 특성 ─ 속성 ─ 값 타입        링크의 뜻 열하나
  링크 타입 ─ 바인딩 여럿                  채널 여섯, 값 셋
  액션 타입 ─ 축 넷                        근거 등급 셋, 근거의 종류 넷
객체 ── 링크 ── 이중화 묶음(객체)           바뀌지 않는 ID + 식별 이력
   각 값과 링크: 등급 + 근거의 종류 + 이력의 종류
```

## 3. 타입 등록부의 칸
타입은 데이터예요. 칸의 이름은 `snake_case`예요. 모든 정의(타입, 속성, 링크 타입, 바인딩, 액션)는 `name`과 따로 바뀌지 않는 `id`를 가져서 이름을 바꿔도 이어져요. 등록부는 타입, 링크 타입, 속성마다 바뀌지 않는 작은 정수(`type_no`, `link_type_no`, `attr_no`)도 내줘요. **저장하는 행과 `attrs`의 키, 표의 나눔, 프로젝션은 이름이 아니라 이 번호를 써요.** 이름은 등록부에서 풀고, 번호는 다시 쓰지 않아요. 그래서 이름을 바꿔도 행은 그대로예요.

### 3.1 객체 타입
| 칸 | 뜻 |
|---|---|
| id, type_no, name, namespace | 바뀌지 않는 id, 행과 프로젝션이 이름 대신 쓰는 `type_no`, 이름(4절), 이름 공간(`std`, `org`, `ext`와 예약된 `sys`. 3.7) |
| layer | 표준 모델의 아홉 층과 열째 층 `system`(`sys` 타입이 놓이는 층) 가운데 하나(standard-model). 권한의 타입 범위를 층으로 줄 수 있는 것은 이 칸 때문이에요. 사용자가 더한 타입은 부모의 층을 따라요 |
| scope_keys | 이 타입에서 `scope_key: true`로 선언한 속성(3.2)의 이름. 읽기 권한의 객체 조건에 쓰고(자리, 환경, 맡은 조직 같은 것), 타입 하나에 넷까지예요. 하위 타입은 물려받아요. `versioned`이고 식별 키처럼 다뤄 함부로 바뀌지 않아요(ADR-0012, REQ-165) |
| parent | 부모 타입. 하나만 있어요 |
| traits | 특성 목록 (3.4) |
| properties | 속성 목록 (3.2) |
| identity_keys | 식별 키의 목록과 우선순위 (10절) |
| display_names, title_property | 언어별 표시 이름(비어 있어도 돼요. 이름과 식별에는 쓰지 않아요), 사람이 읽는 이름으로 쓸 속성 |
| standard_ref | 어느 표준의 무엇에서 빌렸는지. 확인한 것만 적고, 아니면 "프락시움이 정함" |
| status, superseded_by | `experimental` / `active` / `deprecated` (11절). 물러난 타입이 가리키는 후속 타입 |
| contacts | 담당자(사람이나 그룹의 목록). 연락처일 뿐 권한이 아니에요. 문제와 알림, 제안의 검토 요청이 그리로 가요([ADR-0012](adr/0012-access-control.md)) |

### 3.2 속성
| 칸 | 뜻 |
|---|---|
| name, attr_no, value_type | 이름, 바뀌지 않는 `attr_no`(`attrs`의 키), 값 타입 (3.3) |
| scope_key | `true`면 읽기 권한의 객체 조건에 쓰는 속성이에요. 값 타입은 짧은 글이나 `ref`이고 `volatile`일 수 없어요 |
| unit | 단위 (수량일 때) |
| enum_values | 고르기 값. `snake_case` |
| required | 꼭 있어야 하는 속성이에요. 품질의 채움률은 `required`인 속성을 분모로 내요 |
| change_class | 바뀌는 빠르기 `static`(식별자, 일련번호) / `slow`(구성, 자리) / `dynamic`(상태, 놓인 곳). 이력의 종류와 기대 신선도의 기본값을 정해요 |
| sensitivity | 민감 등급 `open` / `restricted` / `confidential` ([ADR-0012](adr/0012-access-control.md)). 비어 있으면 `open`이에요 |
| history_kind | 이력의 종류 `versioned` / `volatile`. 비어 있으면 `change_class`가 정해요(`static`과 `slow`는 `versioned`, `dynamic`은 `volatile`) |
| status, superseded_by | 속성도 물러나게 할 수 있어요 |

이력의 종류는 이래요. `versioned`는 바뀔 때마다 이력에 남아요(구조와 구성). `volatile`은 지금 값과 본 때만 두고, 내용 해시와 버전의 차이에 들지 않아요(올라와 있나 내려가 있나 같은 상태). 바뀌면 이력 없는 경량 변경 레코드가 적혀서 프로젝션과 충족 표시와 변경 알림이 따라와요. 영향 범위의 `as_observed`가 읽는 관측 상태는 `volatile`이어도 돼요. "그 버전 때"의 답에는 `volatile` 값이 없어요([KG에 묻기](kg-queries.md) 4절). **링크는 `volatile`이 될 수 없어요.** 자주 옮겨 다니는 `runs_on`도 보통의 변경이에요(그 쓰기의 양은 측정해서 봐요). 받는 방식과 변경 시퀀스는 [ADR-0008](adr/0008-ingestion.md)과 [ADR-0009](adr/0009-kg-storage-and-versions.md)가 정해요.

### 3.3 값 타입
속성의 자료형은 `string`, `integer`, `number`, `boolean`, `time`, `enum`, `quantity`(단위 있는 수), `ref`(다른 객체), `list`, `map` 중 하나이고, 그 위에 이름 붙은 **값 타입**을 얹어요.

| 값 타입 | 바탕 | 검사 | 다듬기 |
|---|---|---|---|
| `ipv4_address` | string | 점 넷, 각 0~255 | 앞의 0 없애기 |
| `mac_address` | string | 16진수 12자리 | 구분자 없애기, 소문자 |
| `serial_number` | string | 비어 있지 않음 | 앞뒤 공백 없애기, 대문자 |
| `fqdn` | string | 라벨 길이, 허용 글자 | 소문자, 끝의 점 없애기 |

값 타입은 검사와 다듬기를 가져요. 식별의 다듬기는 값 타입에서 와요. 규칙마다 따로 적지 않아요. 저장하는 값은 받은 그대로이고, 다듬은 값은 식별 키를 맞출 때만 써요. 
### 3.4 특성
여러 타입이 함께 갖는 성질이에요. 속성을 한 번만 적고, 기대는 채널을 선언해요(6절).

| 칸 | 뜻 |
|---|---|
| name | 특성 이름 (`Powered`, `Cooled`, `Locatable`, `NetworkAttached`, `Addressable`, `Manageable` 등) |
| properties | 이 특성이 주는 속성. 여러 타입이 함께 쓰는 속성은 여기에 한 번 적어요 |
| needs | 기대는 채널과 강도 (6절) |

관리자가 더한 타입도 특성을 달면 공통 동작(영향 범위, 공통 조회)에 들어와요.

### 3.5 링크 타입과 바인딩
링크 타입은 이름 하나에 바인딩 여럿을 가져요.

| 칸 | 어디에 | 뜻 |
|---|---|---|
| name, link_type_no, meaning, meaning_params | 링크 타입 | 이름, 바뀌지 않는 `link_type_no`, 링크 의미 하나(5절), 그 뜻의 매개 값(`strength`, `resource`, `whole_needs_part`, `failover_to`) |
| properties | 링크 타입 | 링크가 가질 속성. 링크의 이력은 언제나 `versioned`예요(3.2) |
| delay_class | 링크 타입 | `immediate` / `delayed`. 전파가 늦게 나타나면 답에 표시만 해요(14절) |
| from, to | 바인딩 | 출발과 도착. 타입이나 특성으로 적어요 |
| cardinality | 바인딩 | 개수 `1:1`, `1:N`, `N:1`, `N:M` (출발:도착) |
| param_constraints | 바인딩 | 매개 값의 제약 (예: 이 바인딩에서는 `strength`가 `hard`만) |

개수와 제약이 바인딩에 붙어서 `RUNS_ON` 같은 일반 이름이 층을 가로질러 쓰여요. 예: `RUNS_ON`은 `VirtualMachine` → `HypervisorHost`(N:1, `failover_to` 허용), `Pod` → `ClusterNode`(N:1), `OperatingSystem` → `VirtualMachine` 또는 `PhysicalServer`(N:1)를 바인딩으로 가져요.

### 3.6 액션 타입
| 칸 | 뜻 |
|---|---|
| name, applies_to | 이름(`snake_case`)과 쓰이는 타입이나 특성 |
| mutates, reversibility, disruption, physical | 위험의 축 넷 (12절) |
| declared_effects, inverse | 선언한 효과(KG에서 관측할 수 있는 조건)와 되돌리는 액션 |

지금은 목록과 뜻만 두어요. 실행과 툴 매핑은 엔드투엔드(E2E) 프로세스를 구체화할 때 정해요.

### 3.7 상태와 이름 공간
| 층 | 이름 공간 | 누가 고쳐요 | 승인 |
|---|---|---|---|
| 제품 표준 | `std` | 제품이 실어요. 배포 안에서는 고치지 않아요 | — |
| 조직 표준 | `org` | `editor`가 제안해요(제품 표준의 오버레이 포함) | `model_steward` |
| 사용자 정의 | `ext` | `editor`가 제안해요 | 그 타입을 범위에 가진 `approver`(고친 사람 말고) |
| 시스템 | `sys` | 제품이 실어요. 더하거나 고치는 경로가 없어요 | — |

사람이 고치는 층은 `std`, `org`, `ext` 셋이에요. `sys`는 예약된 넷째 이름 공간이에요. 프락시움 자신의 부품과 스스로 재는 합성 소스의 타입이고, 열째 층 `system`에 놓이며 따로 된 시스템 KG에만 담겨요([자기 관측성](self-observability.md)). 표준 모델의 데이터 파일과 따로 제품이 실어요. 표준 타입의 이름은 `std`가, `sys`의 이름은 `sys`가 예약해요. `ext` 타입은 표준 타입의 하위 타입을 만들고 속성을 더할 수 있지만 부모의 식별 키와 링크 의미는 바꾸지 못해요. `editor`와 `approver`는 제품에 들어 있는 닫힌 역할이고 범위를 가져요([ADR-0012](adr/0012-access-control.md)). 상태는 11절이에요.

## 4. 이름 규칙과 예
| 대상 | 규칙 | 예 |
|---|---|---|
| 객체 타입 | 단수 명사 `PascalCase` | `PhysicalServer`, `Interface`, `Lag` |
| 링크 타입 | 출발에서 도착으로 읽는 동사구 `UPPER_SNAKE_CASE` | `HOSTED_ON`, `MEMBER_OF`, `POWERED_BY` |
| 속성, 액션 타입, 고르기 값 | `snake_case` | `rated_power_w`, `power_off`, `rack_mount` |

- 표준 타입의 이름에 제품 이름을 넣지 않아요. 제품마다 다른 것은 속성이나 하위 타입에 둬요. 같은 뜻의 링크 이름이 층마다 생기면 바인딩으로 합쳐요.

## 5. 링크 의미 열하나 (채널로 정의)
### 5.1 채널
상태는 하나가 아니라 채널마다 있어요. 채널마다 `up` / `down` / `unknown` 세 값이에요.

| 채널 | 뜻 |
|---|---|
| `service` | 제 일을 한다 |
| `power` | 전력을 받고 있다 |
| `cooling` | 냉방을 받고 있다 |
| `network` | 망에 닿는다 |
| `storage` | 저장소를 쓸 수 있다 |
| `management` | 관리할 길이 있다 |

"서버는 켜져 있는데 망에서 끊겼다"는 `service`는 `up`이고 `network`는 `down`이에요. "서비스는 도는데 관리할 길이 끊겼다"는 `management`만 `down`이에요. 이 값을 어떻게 계산하고 답에 어떻게 싣는지는 [ADR-0010](adr/0010-kg-queries-and-impact.md)이에요.

### 5.2 열하나의 뜻
링크 의미는 "출발의 어느 채널이 도착의 어느 채널에 기대나"로 정의해요.

| 뜻 | 기대는 것 | 매개 값 |
|---|---|---|
| `runs_on` | 출발의 `service` ← 도착의 `service` | `failover_to`(묶음, 선택) |
| `requires` | 출발의 `service` ← 도착의 `service`. soft는 죽지 않고 줄어요 | `strength`: `hard` / `soft` |
| `supplied_by` | 출발의 그 채널 ← 도착의 `service` | `resource`: `power`, `cooling`, `network`, `storage` |
| `realized_by` | 위층 출발의 `service` ← 아래층 도착의 `service` | — |
| `part_of` | 부품이 전체의 일부예요. 전체의 `service`가 죽으면 부품도 죽어요 | `whole_needs_part`: `hard` / `soft` / `none`(기본 `none`) |
| `contained_in` | 자리예요(놓여 있다). 자리 단위의 사고(방 전체가 내려감)에서만 내용물로 번져요. 부품 관계에는 쓰지 않아요 | — |
| `connected_to` | 이어짐의 간선이에요. 양 끝의 객체가 살아 있을 때만 쓸 수 있어요. `network` 채널의 길을 따질 때 써요 | — |
| `member_of` | 묶음의 구성원이에요 | 무게, 역할 |
| `managed_by` | 출발의 `management` ← 도착의 `service` | — |
| `owned_by` | 번지지 않아요 | 역할 |
| `record_only` | 번지지 않아요 | — |

- `part_of`의 `whole_needs_part`가 부품 쪽 전파(부품이 죽으면 전체가 죽나)을 정해요. 쌍마다 한 방향만 켜져서 부품과 전체가 서로를 죽이는 고리가 안 생겨요. 이중화하는 부품(전원 장치, 팬)은 `none`으로 두고 묶음을 거쳐요.
- `contained_in`과 `part_of`를 합치지 않아요. 랙이 "제대로 일하지 않는" 것은 서버가 죽은 것이 아니에요.
- `runs_on`에 `failover_to`가 있으면 대상이 죽어도 선언된 넘겨받기가 있다는 뜻이에요. 처리는 ADR-0010이에요.
- 링크 의미는 결정 기록으로만 더해요. 논리 관계는 링크 타입을 더하는 것으로 채우고, 뜻은 열하나에서 골라요.

### 5.3 예: 부품과 자리
지어낸 서버 `srv-01`(랙 `R01`)에서 `srv-01` `MOUNTED_IN` `R01`은 `contained_in`이에요. `cpu-1` `PART_OF` `srv-01`(`whole_needs_part=hard`)은 CPU가 죽으면 서버가 죽고, 메모리 `dimm-3`(`soft`)이 죽으면 서버가 줄어들어요. 전원 장치 `psu-a`, `psu-b`는 `none`이고 묶음을 거쳐요(7절).

## 6. 채널과 타입이 선언하는 필요
타입은 자기 `service`가 어느 채널을 필요로 하는지를 특성으로 선언해요.

| 특성 | 필요로 하는 채널 | 기본 강도 |
|---|---|---|
| `Powered` | `power` | `hard` |
| `Cooled` | `cooling` | `hard` |
| `NetworkAttached` | `network` | `hard` |
| 스토리지를 쓰는 타입 | `storage` | `hard` |
| `Manageable` | `management` (잃어도 `service`는 살아 있어요) | — |

- 타입이 강도를 바꿀 수 있어요(예: 잠깐 냉방이 없어도 되는 장비를 `soft`로).
- 채널을 어느 링크로 채우는지는 `supplied_by`(자원마다 하나)와 `managed_by`예요. 필요를 선언했는데 채우는 링크가 없으면 그 채널은 "알 수 없음"이 돼요. "피드가 없다"로 읽히지 않아요(9.3).
- 망의 바깥이나 중심으로 선언한 객체는 특성 `NetworkAnchor`를 달아요. 길이 닿아야 하는 곳이에요. 어떻게 쓰이는지는 ADR-0010이에요.
- 관리자가 더한 타입은 특성을 다는 것으로 필요를 선언해요. 새 특성은 결정 기록으로만 더해요.

## 7. 이중화 그룹
### 7.1 묶음은 객체예요
이중화는 링크의 속성이 아니라 객체예요. 구성원이 셋 이상이거나 묶음이 겹치면 링크 속성으로는 적을 수 없어서예요.

| 칸 | 뜻 |
|---|---|
| (타입) | `RedundancyGroup` 또는 그 하위 타입 (표준 모델의 하위 타입은 standard-model의 표) |
| mode | 방식 `count` / `capacity` |
| min_alive | `count`에서 몇 개가 살아야 하나 |
| min_capacity | `capacity`에서 필요한 용량 (선택. 수요는 기대는 링크의 `demand`로 와요) |
| failover_time_s, ride_through_s | 정보용 숫자. 계산에 쓰지 않아요 |
| 근거 | `min_alive`에도 등급과 근거의 종류가 있어요 |

- 구성원은 `member_of`로 들어요(매개 값으로 무게와 역할).
- 기대는 쪽은 묶음에 `requires`나 `supplied_by`로 닿아요. 서버는 전원 묶음에 `POWERED_BY`로 닿아요.
- 묶음에는 둘이 있어요. 평가되는 `RedundancyGroup`과, 번지지 않는 `LogicalGroup`(조직, 환경, 배치 규칙)이에요. `member_of`의 도착은 둘 다 돼요.
- 엔진은 `count`를 먼저 만들고 `capacity`를 이어서 만들어요. 그 전까지 `capacity` 묶음의 답은 `unknown`이에요.

### 7.2 세 값 평가
구성원 `n`개 중 산 것 `a`, 모르는 것 `u`, 임계값 `k`(`min_alive`)예요.

| 조건 | 묶음 |
|---|---|
| `a ≥ k` | 살았다 |
| `a + u < k` | 죽었다 |
| 그 밖 | 모른다 |

모르는 구성원 때문에 "안전하다"로 읽히지 않아요. 구성원 자신이 살았는지는 구성원이 기대는 것까지 내려가서 따져서, 같은 전원 장치에 매달린 두 구성원이 함께 죽는 것도 잡혀요(계산은 ADR-0010).

### 7.3 min_alive의 근거 등급
| 상황 | 등급 |
|---|---|
| 장비의 설정이 최소 링크 수를 말해요 | `fact` (`basis=configured`) |
| 사람이나 문서가 적었어요 | `basis=declared`. 등급은 기본이 `fact`예요. 피드가 그 데이터셋을 "어림"이라고 표시하면 `assumed`예요 |
| 소스에 없고 기본값 규칙도 없어요 | `unknown` |
| 관리자가 적은 기본값 규칙이 채웠어요 | `assumed` |

`min_alive`를 모르면 가능한 값 모두에서 같은 답이 나올 때만 그 답이고, 아니면 `unknown`이에요(사실만 쓴 답에서는 `assumed`인 입력을 "알 수 없음"으로 읽어요).

### 7.4 예: 지어낸 LAG
`lag-7`(`Lag`)의 구성원은 포트 `port-1`~`port-4`예요. 장비 설정이 최소 링크 2를 말해서 `min_alive = 2`(`fact`, `configured`)예요. `port-3`, `port-4`가 죽으면 `a=2 ≥ 2`라 살았어요(여유 0). `port-2`도 죽으면 `a=1`이고, 나머지가 모두 `unknown`이면 `a+u ≥ 2`라 "모른다"예요.

## 8. 끌어낸 링크와 묶음
링크 정의는 (1) 다른 링크를 따라가 끌어낸 링크(자리를 따라 냉방을 물려받는다)와 (2) 묶음 객체(같은 서비스의 인스턴스들, 설정의 여러 경로)를 만들 수 있어요. **질의할 때 계산하지 않고 받을 때 만들어 저장해요.** 근거의 종류는 `derived`이고 등급은 쓰인 입력 중 가장 낮은 등급이에요. 어느 데이터셋에서 끌어내는지는 링크 정의가 적어요([ADR-0008](adr/0008-ingestion.md)).

### 8.1 한 가지 소스 모양에 묶지 않아요
ECMP, LACP, BGP 세션, 전원 A·B, 클러스터 구성 어느 것도 한 가지 길로만 받지 않아요. 표준 모델은 길마다 받을 타입과 속성을 가져요.

| 묶음 | 설정에서 | 표에서 | 문서에서 |
|---|---|---|---|
| ECMP | 여러 경로 설정, 이웃 | 경로표, 전달표 | 설계서 |
| LACP | 집계 소속, 최소 링크 | 장비의 집계 상태 표 | 배선 표 |
| BGP 세션 | 이웃 설정 | 이웃 표 | 피어 목록 |
| 전원 A·B | 서버가 말하는 전원 장치 목록 | 급전 상태 표 | 엑셀의 급전선 표 |

같은 것에 길이 여럿이면 종류별로 다 받아 두고, 질의는 보는 기준을 골라요(`as_designed`, `as_observed`, [ADR-0010](adr/0010-kg-queries-and-impact.md)). 설정과 관측이 어긋나는 것은 버릴 충돌이 아니라 값진 정보예요. 문제 목록에 "의도와 관측의 어긋남"으로 올라요.

### 8.2 예: 설정에서 ECMP 그룹을 끌어내기
지어낸 스위치 `leaf-1`이에요. 설정에 이렇게 있어요.

- 라우팅 프로세스 `bgp-1`: `maximum_paths = 4`.
- 세션 `s-a`~`s-d`: 모두 `multipath_eligible`, 기본 경로를 광고하는 이웃이에요.

링크 정의가 `s-a`~`s-d`를 구성원으로 하는 묶음 `ecmp-leaf1-default`(`EcmpGroup`, `mode=count`, `min_alive=1`)를 만들어요. 구성원이 `maximum_paths`를 넘으면 넘는 것은 `role=spare`로 들어요. 근거는 `derived`(입력은 `configured`)이고 설정을 온전히 읽었으면 `fact`예요. 한쪽 설정만 있거나 비대칭이면 묶음을 만들지 않고 문제 목록에 올려요.

같은 묶음을 경로표에서 받으면 구성원이 `observed`로 들어와요. 설정은 4개인데 경로표에 둘만 보이면 "의도와 관측의 어긋남"이에요. LACP 묶음과 BGP 세션도 같은 방식이에요.

**구조와 상태, 시계열.** KG는 구조와 상태(있다 없다, 어디에 놓였나, 올라와 있나 내려가 있나, 누구와 이웃인가)를 받아요. 미루는 것은 수치의 시계열(온도, 전력, 사용률)이에요. 그것은 KG에 쌓지 않고 가리키기만 해요. 상태는 `volatile` 속성이 되기 쉬워요(3.2).

## 9. 근거
### 9.1 근거 등급과 근거의 종류는 다른 축이에요
| 축 | 값 | 뜻 |
|---|---|---|
| 근거 등급 | `fact` / `assumed` / `unknown` | 얼마나 믿을 수 있나 |
| 근거의 종류(`basis`) | `configured` | 설정에서 읽음. 의도예요 |
| | `observed` | 받은 순간에 그렇게 보임. 경로표, 이웃 표, 상태 |
| | `declared` | 사람이나 문서가 적음. 엑셀, 설계서 |
| | `derived` | 규칙이 끌어냄. 입력의 종류를 물려받아요 |

모든 속성 값과 링크에 둘이 함께 붙어요. 값만 돌려주는 길은 없어요. 충돌(소스끼리 다른 값)은 등급이 아니라 문제 목록의 항목이에요.

### 9.2 가정으로 메우지 않아요, 답의 등급
소스에 없는 전원과 냉방을 지어 넣던 것은 시뮬레이터라서 있던 일이에요. 가정은 관리자가 적은 규칙(기본값 규칙)에서만 생기고 `assumed`로 표시돼요(기본값 규칙이 만든 값은 언제나 `assumed`예요). 사실로 올리려면 새 관측이나 확인이 필요해요(등급만 고치는 편집은 없어요).

답의 등급은 쓰인 입력 중 가장 낮은 등급이에요(`fact` > `assumed` > `unknown`). 사실만 쓴 답에서는 `assumed`인 입력을 "알 수 없음"으로 읽어요.

### 9.3 완전성 선언: "없다"와 "모른다"
| 칸 | 뜻 |
|---|---|
| feed, target, scope | 어느 피드(데이터셋에서 객체 타입으로 가는 매핑 하나)이 어느 객체 타입이나 링크 타입을, 선택으로 어느 범위(자리 등)에서 |
| claim | "이 피드는 이 타입을 전부 준다" |
| declared_by, declared_at | 누가 언제 선언했나 |

선언은 피드마다, 객체 타입과 링크 타입 둘 다에 할 수 있고 범위를 붙일 수 있어요. 선언이 있어야 "링크가 없다"가 "없다"로 읽혀요. 선언이 없으면 "모른다"예요. 선언한 수와 받은 수가 다르면 문제 목록에 올라요([ADR-0011](adr/0011-kg-operations.md)).

예: 엑셀 `rack-sheet`의 피드가 `Rack`을 전부 준다고 선언했어요. 서버 `srv-02`의 `MOUNTED_IN` 링크가 없고 `PhysicalServer`나 `MOUNTED_IN`을 전부 준다는 선언이 없다면, `srv-02`의 자리는 "모른다"예요.

## 10. 식별
바깥 식별자(일련번호, UUID, MAC, 관리 시스템의 ID)는 교체나 재생성 때 바뀌므로 KG의 키로 쓰지 않아요.

### 10.1 내부 ID와 식별자 표
객체마다 바뀌지 않는 내부 ID가 있어요. 처음 본 식별 키에서 결정적으로 나오고(같은 원본과 같은 규칙이면 같은 ID), 그 뒤로 고정돼요. 객체는 식별자를 여럿 가져요.

| 칸 | 뜻 |
|---|---|
| object_id | 내부 ID |
| id_kind, id_value | 식별자의 종류(`serial_number`, `mac_address`, 소스의 키 등)와 다듬은 값 |
| scope | 유효한 테두리(제조사, 관리 시스템 하나, 클러스터 하나) |
| seq_from, seq_to | 본 구간(변경 번호로 적어요, [KG 저장과 버전](kg-storage.md)). 끝을 열어 둘 수 있어요 |
| source | 어느 소스가 말했나 |

### 10.2 식별 키, 다듬기, 딸린 객체
- 타입마다 식별 키를 우선순위와 함께 선언해요. 강한 키(전 세계에서 유일한 것)와 약한 키(테두리 안에서만 유일한 것)를 가르고, 약한 키는 테두리가 맞아야 해요.
- 다듬기는 값 타입이 해요(대소문자, 공백, 구분자, 도메인 꼬리, 포트 이름의 표기).
- **딸린 객체**(포트, 부품)는 부모의 문맥 안에서 식별해요. 포트 "Eth1/1"은 스위치마다 있어서 (부모, 다듬은 포트 이름)이 식별 키예요. 키의 구성요소는 속성, 문맥(여럿 가능, 부모 링크 하나마다), **집합**(링크 타입으로 닿는 객체들의 정렬한 내부 ID, 나가는 쪽이나 들어오는 쪽, 정확한 크기 선택: MLAG 짝은 스위치 둘의 집합)이고, 링크가 1:1이면 문맥만으로도 키예요(트랜시버는 인터페이스 하나에 하나). 키가 요구하는 부모는 표준 모델의 보통 바인딩이고, 모든 표준 타입이 자기 키를 가져요(ADR-0022). 식별자를 모르는 `UnknownObject`는 단서의 해시(`is.hint_hash`)로 알아봐요.
- 동일 객체 식별은 정해진 다듬기와 결정적 규칙으로만 해요. 확률로 맞춘 것은 후보를 제안할 뿐 저절로 합치지 않아요.

### 10.3 속성마다 이기는 소스
타입과 속성마다 이기는 소스의 순서를 정해요. 진 값은 버리지 않고 충돌로 문제 목록에 보여요. 위치는 설비 쪽 소스가, 구성은 서버 쪽 소스가 이기게 하는 식이에요.

### 10.4 합치기, 분리, 물러남
- 합치기와 분리는 이력에 남아요. 합쳐서 물러난 ID는 남은 ID를 가리켜요. 링크의 ID는 끝점에서 나와서 합치면 흡수된 쪽의 링크 ID가 바뀌므로, `identity_event`에 옛 링크 ID와 새 링크 ID의 이음을 남겨요. 변경 알림과 충족률은 그것을 "물러남과 더함"이 아니라 이음으로 다뤄요.
- 소스에서 안 보이는 것과 물러난 것은 달라요. 온전한 수집에서 잇달아 안 보인 번수를 따로 세고, 기준(기본값의 가정)을 넘으면 물러난 것으로 표시해요([ADR-0008](adr/0008-ingestion.md)). 물러난 객체가 같은 식별 키로 다시 보일 때 옛 ID로 되살리는 것은 강한 키로 맞았거나 정해진 기간 안일 때만이에요. 약한 키(이름, 주소, 포트 이름)는 다른 장비에 다시 쓰이기 때문에, 아니면 새 ID를 주고 식별 후보로 올려요.
- 사람이 낱개로 정한 "같다 / 다르다"는 파이프라인 정의 안의 예외 목록(버전이 있는 데이터)으로 남아요. 값을 낱개로 덮어쓰는 예외는 없어요.

### 10.5 식별 이력은 진실의 일부예요
식별 이력은 되감지 않아요. 잘못 합쳤으면 "이 합침을 리버트"가 가르는 예외의 제안을 만들어 줘요(definitions.md, ADR-0014).
다음 상태는 (앞 상태, 받은 순서대로의 원본 레코드의 변경, 정의의 버전, 실행기의 의미 버전)의 함수예요. 같은 넷이면 같은 다음 상태가 나오고, KG 버전은 그 이어짐 위에 붙인 확정한 이름이에요. 내부 ID는 처음 본 식별 키에서 나온 뒤 고정돼서, **식별의 이력(어느 식별자가 어느 ID인지, 합치고 가른 기록, 잇달아 안 보인 번수)은 파생물이 아니라 진실의 일부이고 잃으면 안 돼요.**

- "지금의 원본 레코드만으로 처음부터 지은 KG"가 운영의 KG와 ID까지 같다고는 약속하지 않아요. 약속하면 ID가 이력에 따라 바뀌어야 하고, 바뀌지 않는 ID라는 더 중요한 약속이 깨져요. 내용(타입, 속성, 링크의 모양)은 같아야 하고 테스트가 걸어요.
- 드라이 런은 운영의 지금 버전의 식별 이력에서 출발해요. 그래서 후보와 운영의 차이가 ID로 맞물려요.
- 객체와 링크의 내용 해시에는 타입, 속성 값, 근거 등급이 들어가고 원본 레코드의 참조는 들어가지 않아요. 타입과 속성은 이름이 아니라 바뀌지 않는 번호(`type_no`, `attr_no`)로 들어가요. `confidential` 값은 KG마다의 해시 키로 만든 키 단 해시로 들어가고(ADR-0018), 암호화된 값의 엔벨로프 모양(`{"enc": ...}`)을 읽을 줄 아는 자리를 알파부터 둬요. 해시 규칙의 버전과 실행기의 의미 버전은 버전의 머리에 적혀요([KG 저장과 버전](kg-storage.md)).

### 10.6 예 하나: 메인보드를 갈아 일련번호가 바뀌어요
버전 1에서 서버의 일련번호는 `SN-1001`, 관리 주소는 `192.0.2.10`이었고 객체 `obj-A`가 생겼어요. 버전 2에서 메인보드를 갈아 일련번호가 `SN-2002`가 됐어요. 관리 주소와 랙 자리는 그대로예요. `SN-2002`로 맞는 객체는 없고 관리 주소는 약한 키라서 저절로 합치지 않고 식별 후보로 문제 목록에 올려요. 사람이 "같다"를 예외 목록에 적으면 `obj-A`가 `SN-2002`를 새 식별자로 가지고 `SN-1001`은 구간이 닫혀요. ID는 그대로라 링크와 이력이 끊기지 않아요.

### 10.7 예 둘: 같은 장비가 엑셀과 관리 API에 다른 이름으로 있어요
엑셀의 행은 `R01 / U12 / "SRV-001"`이고 관리 API의 항목은 `srv-001.example.test`예요. 두 값을 `fqdn` 값 타입으로 다듬으면(소문자, 도메인 꼬리) 같아서 하나의 내부 ID로 모여요. 속성은 이기는 소스가 골라요. 랙과 칸은 엑셀이, 호스트 이름과 펌웨어 버전은 관리 API가 이겨요. 엑셀이 `rack_unit=12`, 관리 API가 `13`이라고 하면 진 값이 충돌로 문제 목록에 보여요. 다듬어도 안 맞아 다른 객체로 남으면 후보 제안이 나오고 사람이 예외 목록으로 정해요.

## 11. 타입을 고치는 규칙
### 11.1 상태
| 상태 | 뜻 |
|---|---|
| `experimental` | 바뀔 수 있어요. 쓰는 쪽에는 경고가 붙어서 보여요. `ext` 타입은 여기서 시작해요 |
| `active` | 쓰이고 있어요(객체가 있고 매핑이 있어요) |
| `deprecated` | 물러났어요. `superseded_by`가 후속을 가리켜요 |

지우지 않아요. 표준이 오르면 타입이 물러날 수 있고, 그것을 쓰는 매핑에 알리되 저절로 고치지 않아요([ADR-0011](adr/0011-kg-operations.md)).

### 11.2 고치는 규칙
- 속성 더하기는 자유로워요.
- 타입, 링크 타입, 속성의 **이름은 바꿀 수 있어요.** 행은 바뀌지 않는 번호(`type_no`, `link_type_no`, `attr_no`)를 들고 있어서 이름을 바꿔도 행은 그대로예요. 옛 이름은 API에서 별명으로 한 메이저 버전 동안 받아요. 해시에는 번호가 아니라 바뀌지 않는 ID가 들어요. 속성의 **자료형**을 바꾸는 것은 새 속성을 더하고, 채우고, 옛 것을 물러나게 하는 순서로만 해요.
- 식별 키를 바꾸는 것은 식별 이력을 옮기는 계획과 함께 브랜치에서 드라이 런으로 확인해요.

## 12. 액션 타입의 축 넷
지금은 목록과 뜻만 두어요.

| 축 | 값 | 뜻 |
|---|---|---|
| `mutates` | 예/아니요 | 바꾸나 |
| `reversibility` | `reversible` / `irreversible` | 되돌릴 수 있나 |
| `disruption` | `none` / `service_affecting` / `data_loss` | 서비스나 데이터에 끼치는 영향 |
| `physical` | 예/아니요 | 사람 손이 필요한가 |

| 액션 | mutates | reversibility | disruption | physical |
|---|---|---|---|---|
| `extend_volume` | 예 | `irreversible` | `none` | 아니요 |
| `power_off` | 예 | `reversible` | `service_affecting` | 아니요 |
| `delete_volume` | 예 | `irreversible` | `data_loss` | 아니요 |
| `replace_component` | 예 | `irreversible` | `service_affecting` | 예 |

"되돌릴 수 없지만 안전한 것"(볼륨 늘리기)과 "되돌릴 수 있지만 서비스가 끊기는 것"(전원 끄기)이 한 등급에 섞이지 않아요. 승인 기본값을 축에 잇는 일은 E2E 프로세스를 구체화할 때 해요.

## 13. 타입을 관리한다
객체·링크·액션 타입을 API로 만들고 고치고 지울 수 있어요(화면은 다른 저장소가 만들어요). 길은 하나예요. **타입의 변경은 모두 정의의 변경**이라 브랜치의 변경이 되고, 드라이 런으로 영향을 보고, 승인을 거쳐 병합돼요([정의의 버전과 브랜치](definitions.md)). 제품은 이 흐름을 한 번에 이어 주되 작은 변경은 "제안 하나"로 보여요. 링크 의미, 값 타입, 특성, 채널은 제품의 것이라 API로도 더하지 못해요.

### 13.1 층과 승인
층은 3.7의 표를 따라요. `org`의 승인은 `model_steward`([ADR-0012](adr/0012-access-control.md))가 해요.

제품 표준 타입을 조직에 맞게 고치는 일(속성 더하기, 바인딩 더하기, 표시 이름, 쓰지 않을 타입 숨기기)은 `org` 층의 **오버레이**으로 해요. 원본을 고치지 않아서 제품이 올라도 오버레이가 남아요. 지우거나 이름을 바꾸는 것은 오버레이로 하지 못해요(숨기기와 물러나게 하기는 돼요). "표준 타입은 승인이 필요하다"는 `org` 층의 변경(조직 표준 타입의 추가·수정·삭제와 제품 표준의 오버레이)에 승인이 필요하다는 뜻이에요.

### 13.2 새 타입보다 넓히기가 먼저예요
필요의 대부분은 "속성 하나 더"예요. 제품은 이 순서로 이끌어요.

| 순서 | 길 | 언제 |
|---|---|---|
| 1 | 있는 타입에 `ext` 이름 공간의 속성 더하기 | 대부분 |
| 2 | 하위 타입 | 속성이 다른 한 갈래가 있을 때 |
| 3 | 새 타입 | 어느 타입의 갈래도 아닐 때 |

### 13.3 비슷한 타입을 막는 장치
- **비슷한 것 찾아 보이기**: 만들 때 이름(낱말, 고른 이름과 버린 이름의 표), 속성과 식별 키의 겹침, 같은 데이터셋에 매핑된 타입, 같은 표준에서 빌린 타입을 보여요. 있는데도 만들면 이유를 적고, 승인하는 사람에게 그 비교가 보여요.
- **`experimental`로 시작**: `ext` 타입은 `experimental`로 시작하고, `active`로 올리려면 쓰이고 있어야 해요(객체가 있고 매핑이 있어요).
- **올리기**: 여럿이 비슷한 `ext` 타입을 쓰면 `org`로 올리자고 제안해요. 바뀌지 않는 `id`가 이어져서 객체와 매핑이 깨지지 않아요.
- **합치기**: 타입 A를 B로 합치는 작업을 제품이 줘요. 매핑, 링크 정의, 식별 이력을 옮기고 A를 물러나게 해요. 드라이 런으로 확인해요.
- **쓰임 보이기**: 타입마다 객체 수, 매핑 수, 물음 수, 마지막으로 쓰인 때. 오래 쓰이지 않는 타입과 겹쳐 보이는 짝은 `model_steward`에게 주기로 보여요.
- **걸리는 것 보이기**: 고치기 전에 이 타입을 쓰는 매핑, 링크 정의, 저장해 둔 범위, API로 읽는 시스템을 보여요.

### 13.4 삭제
어디서도 쓰이지 않을 때만 지워요(지금의 KG에 객체가 없고 정의가 가리키지 않아요). 쓰이고 있으면 물러나게 하고 후속을 가리켜요. 지워도 지나간 버전이 가리키던 정의는 이력에 남아요.

## 14. 알려진 한계
- **시간은 따지지 않아요.** 냉방을 잃고 버티는 시간, 배터리가 버티는 시간, 넘겨받는 데 걸리는 시간은 값으로 받아 두기만 하고 계산하지 않아요. 링크의 `delay_class`로 답에 "늦게 나타남"을 표시만 해요(ADR-0010). 두 시간 축(bitemporal)은 쓰지 않아요. "그때 무엇을 왜 그렇게 봤나"는 KG 버전과 그것을 만든 원본 레코드와 규칙의 버전으로 답해요.
- **수치의 시계열은 KG에 쌓지 않아요.** 가리키기만 해요(8절).
- **구성과 관측이 다를 수 있어요.** 설정이 말하는 구성(`configured`)이 지금 그대로 도는지는 `observed`가 있을 때만 알 수 있어요. 둘을 다 받고 어긋남을 문제 목록에 올려요.
- **표준에서 빌렸다는 말은 확인한 것에만 써요.** 확인하지 못한 것은 "프락시움이 정함"이에요.

## 15. 미결 사항
1. 링크 개수를 어긴 데이터를 받을 때 멈추는지, 문제 목록에만 올리는지(수집 문서의 열린 물음과 같아요).
2. 부품 교체처럼 식별자가 바뀌는 흔한 일을 소스가 알리는 길을 식별 키 규칙에 어떻게 더하는지.
3. 근거의 종류 `configured`, `observed`, `declared`, `derived`가 같은 값에 여럿 있을 때 한 값으로 보이는 순서(보는 기준은 ADR-0010).
