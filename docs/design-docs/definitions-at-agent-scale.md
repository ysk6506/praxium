# 에이전트가 정의를 작성할 때의 버전 관리

[정의의 버전과 브랜치](definitions.md)는 사람이 작성하는 경우를 다뤄요. 에이전트가 정의 변경의 대부분을 작성하면 변경이 잦아져요. 이 문서는 그 경우를 위한 보충이에요(ADR-0014). 전제를 수정해요: "변경이 잦지 않다"를 고정하지 않아요. **구조(필드와 계약)는 알파에 넣고, 구현은 지표가 가리킬 때 확장해요.** 단계 표시는 [알파] [클로즈드 베타] [오픈 베타]예요.

## 1. 작성자 [알파: 필드와 규칙]
- 브랜치와 제안에 `authored_by`(주체와 `actor_kind`: `person` / `system_account`), `on_behalf_of`(위임한 사람), `agent_run_id`, `agent_build`를 둬요.
- "수정한 사람은 승인할 수 없다"를 **"같은 주체이거나 같은 `on_behalf_of`이면 승인할 수 없다"**로 확장해요.
- **승인은 사람만 해요.** 서비스 계정은 승인자가 될 수 없어요(ADR-0012).
- **`on_behalf_of`는 스스로 적을 수 없어요.** `admin`이 그 서비스 계정에 연결해 둔 사람 가운데서만 선택해요. 계정이 아무 사람이나 지정하면 "같은 위임자이면 승인할 수 없다"가 무의미해지기 때문이에요. 계정을 끄거나 토큰을 회수하는 것은 스토리지가 정상이면 30초 안에 전파돼요.
- **정의가 읽는 소스는 작성자의 범위 안**이어야 해요. 서비스 계정이 작성할 때도 그 계정의 범위 안이고, 승인은 읽는 소스의 범위도 확인해요(definitions.md 5절).
- **혼자 쓰는 테스트 배포**를 위한 `solo_approval`(기본 꺼짐, 켜면 감사에 표시와 헬스 상태의 경고)이 있어요(definitions.md 5절).
- 감사 로그에 주체, 위임한 사람, 에이전트 실행, 승인 경로(사람 또는 정책 판정)가 남아요(access-control.md).

## 2. 에이전트가 정의를 작성하는 경로 [알파]
서비스 계정이 REST와 명령줄로 브랜치와 초안 제안을 만들어요. 브랜치를 열어 수정하고 검토를 요청하는 작은 변경은 서버의 유스케이스 하나(`small_change_propose`)로 한 번에 제출할 수 있어요(definitions.md 14절). MCP의 정의 인터페이스는 읽기 전용이에요. 쓰기 툴을 MCP에 둘지는 클로즈드 베타에서 다시 검토해요.

## 3. 변경 사유 [알파: 필드, 클로즈드 베타: 값 채우기와 표시]
제안에 `trigger_ref`(문제, 역량 질문의 공백, 알림, 진단의 ID), `evidence`(근거가 된 KG 버전과 질의의 참조), `intent`(기대하는 효과의 구조화된 선언), `decision_log_hash`(검토한 대안과 버린 시도를 담은 불변 첨부)를 둬요. 승인자에게 **선언한 의도와 드라이 런의 실제 차이**를 나란히 보여요. 내보내기와 가져오기 목록에 이 필드들이 포함돼요.

## 4. 검증을 앞당기기 [알파: API 형태, 클로즈드 베타: 증분]
브랜치에서 큐가 실행할 것과 같은 검사와 드라이 런을 미리 실행해 볼 수 있는 경로를 둬요(같은 실행기). 주체별로 계산 예산이 적용돼요.

## 5. 병합 큐는 직렬 처리를 유지하되 한 번의 처리 비용을 낮춰요 [알파]
- 무거운 드라이 런은 큐 밖에서 실행하고 결과를 (브랜치 내용 해시, 메인 브랜치 끝 해시, 기준 KG 버전) 키로 재사용해요.
- 큐에서 처리할 때는 메인 브랜치 끝이 그대로인지 확인하고, 움직였으면 계보로 도달하는 것만 다시 평가해요.
- 병합 적용도 계보로 도달하는 피드와 타입에만 해요. 도달하지 않는 소스의 스트림은 새 배치로 그대로 이어 가고, 병합 결과는 일반 변경 배치로 프로젝션에 전달돼요. 그래서 병합이 잦아도 KG 전체가 중단되거나 프로젝션이 통째로 교체되지 않아요(definitions.md 6절).
- 지표 `merge_turn_duration_s`, `candidate_run_duration_s`, `merge_batch_size`를 추가해요(self-observability.md).
- **일괄 병합**(영향 범위가 겹치지 않는 제안끼리 묶어 한 번 검사하고 메인 브랜치 끝을 한 번 옮기되 제안별로 기록은 따로 남기고, 실패하면 분할해서 원인을 찾아요)은 [클로즈드 베타: 설계, 오픈 베타: 구현]이에요. 범위별 큐는 지표가 요구할 때까지 만들지 않아요.

## 6. 위험 등급 [알파: 등급 계산과 정책의 형태]
등급은 작성한 쪽의 주장이 아니라 **후보 차이에서 계산해요.** 다만 KG의 결과에 차이가 없어도 위험한 항목이 있어서, **항목 종류별 하한**을 둬요. 등급은 차이로 계산한 값과 하한 가운데 높은 쪽이에요.

| 등급 | 해당하는 경우 |
|---|---|
| R0 | KG 결과의 차이가 없어요(표시 이름, 설명, 일정의 주기) |
| R1 | 예외 목록 항목, 속성 오버레이 등 차이가 작은 한도 안이고 객체 증감과 식별 병합이 없어요 |
| R2 | 매핑과 피드의 변경이고 차이가 한도 안이에요 |
| R3 | 식별 규칙, 타입 폐기와 병합, 안전장치 완화, 민감 등급 하향, 호환성을 깨는 변경. **언제나 사람**이 확인해요 |

| 항목 종류의 하한 | 하한 |
|---|---|
| 소스의 `endpoints`(접속 주소) | R3 |
| 삭제(`redact`) 규칙 | R3 |
| 알림의 규칙과 목표를 완화 | R3 |
| 담당자(연락처) 변경 | R3 |
| 기대 조건의 강도를 `fail`에서 `warn`으로 | R3 |
| 시크릿이 접속하는 주소(`allowed_hosts`) | R3 |

이 항목들은 KG에 차이가 없어도 R3이라 첫 적용도 자동 병합도 사람이 확인해요(하한이 적용되는 항목이 하나라도 있으면 제안 전체가 R3).

**첫 적용의 사람 확인은 R2부터예요**(ADR-0008). R0, R1은 자동으로 적용하고 사후에 알려요 [알파부터]. 병합 큐 앞의 승인과는 별개의 단계예요.

**정책에 의한 자동 병합**(승인 없이 병합)은 R0, R1 [클로즈드 베타: 구현, 기본 꺼짐], R2와 사후 표본 검토 [오픈 베타]예요. 조건은 검사 전부 통과, 차이가 등급의 한도 안, 그 주체의 최근 리버트 비율이 기준 미만, 한도 안이에요. 기본은 **꺼짐**이고 `admin`이 켜요. 등급표와 정책은 정의의 항목이고 완화하려면 `admin`의 승인이 필요해요. 자동 병합은 "승인"이 아니라 정책이 허용한 것이라 감사에 정책 판정이 남아요.

## 7. 검토의 용량 [클로즈드 베타]
승인 대기를 등급별로 분류해 R3와 영향이 넓은 것을 위에 둬요. 같은 `trigger_ref`나 같은 에이전트 실행의 제안을 한 번에 묶어 검토해요(병합과 리버트는 따로). 승인자별 대기 건수와 대기 기간의 지표를 산출해요.

## 8. 의존하는 제안, 재정렬, 대규모 리버트, 서킷 브레이커
- **의존하는 제안** [클로즈드 베타]: 제안에 `after`(먼저 병합돼야 하는 제안)를 둬요. 먼저 병합돼야 하는 제안이 병합되면 기준이 새 끝으로 갱신되고 닫히면 알려요. 오버레이의 상속은 만들지 않아요.
- **메인 브랜치 최신화는 API 한 번** [클로즈드 베타]: 충돌이 없으면 자동으로 돼요. 나중에 온 쪽이 에이전트면 에이전트가 먼저 다시 정렬하고, 안 되면 위임한 사람에게 알려요.
- **대규모 리버트** [클로즈드 베타]: "에이전트 실행 X가 만든 병합 전부"를 의존 순서대로 하나의 리버트 제안으로 만들어요. 미리 보기와 승인을 거치고 연쇄적으로 자동 리버트하지 않아요.
- **서킷 브레이커** [오픈 베타]: 안전장치가 적용을 보류하거나 리버트 비율이 급증하면 그 주체와 등급의 자동 병합을 끄고 알려요.

## 9. 한도와 정리
주체별로 열린 브랜치 수, 대기 중인 제안 수, 하루 제안 수, 드라이 런의 계산 예산, 트라이얼 수집의 저장량이 있어요 [알파: 설정과 거절 응답]. 활동 없는 초안과 검토 중 제안의 자동 닫기, 같은 내용 해시의 열린 제안에 연결하기 [클로즈드 베타]. 아무도 참조하지 않는 버전과 닫힌 브랜치의 트라이얼 수집 스테이징 영역 정리 [오픈 베타]. 값은 [기본값 표](defaults.md) 6절에 가정으로 적어요(아직 정해지지 않았어요).

## 10. 설계 담당에게 확인할 사항
- 하한 목록(6절)에 추가할 항목 종류가 있는지.
- 9절의 한도 값(주체별 열린 브랜치 수 등)과 자동 닫기의 기한.
- 자동 병합의 "차이가 작은 한도"와 "최근 리버트 비율의 기준"의 값.

## 11. 관련
ADR-0014, ADR-0012(승인은 사람만, 범위), ADR-0018(시크릿의 접속 주소), ADR-0017(지표). 요구사항: REQ-218(주체와 승인), REQ-219(변경 사유), REQ-220(위험 등급과 자동 병합), REQ-221(병합 큐와 한도).
