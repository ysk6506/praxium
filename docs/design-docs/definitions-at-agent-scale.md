# 에이전트가 정의를 쓸 때의 버전 관리

[정의의 버전과 브랜치](definitions.md)는 사람이 쓰는 때를 그려요. 에이전트가 정의 변경의 대부분을 쓰면 변경이 잦아져요. 이 문서는 그때를 위한 덧붙임이에요(ADR-0014). 전제를 고쳐요: "변경이 잦지 않다"를 못 박지 않아요. **구조(칸과 계약)는 알파에 넣고, 구현은 지표가 가리킬 때 넓혀요.** 단계 표시는 [알파] [클베] [오베]예요.

## 1. 누가 썼나 [알파: 칸과 규칙]
- 브랜치와 제안에 `authored_by`(주체와 `actor_kind`: `person` / `system_account`), `on_behalf_of`(맡긴 사람), `agent_run_id`, `agent_build`를 둬요.
- "고친 사람은 승인 못 한다"를 **"같은 주체이거나 같은 `on_behalf_of`이면 승인 못 한다"**로 넓혀요.
- **승인은 사람만 해요.** 시스템 계정은 승인자가 못 돼요(ADR-0012).
- **`on_behalf_of`는 스스로 적지 못해요.** `admin`이 그 시스템 계정에 묶어 둔 사람 가운데서만 골라요. 계정이 아무 사람이나 대면 "같은 맡긴 사람이면 승인 못 한다"가 소용없어져서예요. 계정을 끄거나 토큰을 거두는 것은 저장소가 살아 있으면 30초 안에 퍼져요.
- **정의가 읽는 소스는 쓴 사람의 범위 안**이어야 해요. 시스템 계정이 쓸 때도 그 계정의 범위 안이고, 승인은 읽는 소스의 범위도 따져요(definitions.md 5절).
- **혼자 쓰는 시험 배포**를 위한 `solo_approval`(기본 꺼짐, 켜면 감사에 표시와 건강의 경고)이 있어요(definitions.md 5절).
- 감사 기록에 주체, 맡긴 사람, 에이전트 실행, 승인의 길(사람 또는 정책의 판)이 남아요(access-control.md).

## 2. 에이전트가 정의를 쓰는 길 [알파]
시스템 계정이 REST와 명령줄로 브랜치와 초안 제안을 만들어요. 브랜치를 열어 고치고 검토를 요청하는 작은 변경은 서버의 쓰임 하나(`small_change_propose`)로 한 번에 낼 수 있어요(definitions.md 14절). MCP의 정의 면은 읽기만이에요. 쓰는 툴을 MCP에 두는지는 클로즈 베타에서 다시 봐요.

## 3. 왜 바꿨나 [알파: 칸 자리, 클베: 채우고 보이기]
제안에 `trigger_ref`(문제, 역량 질문의 틈, 알림, 진단의 ID), `evidence`(근거가 된 KG 버전과 질의의 참조), `intent`(기대하는 효과의 구조화된 선언), `decision_log_hash`(검토한 대안과 버린 시도를 담은 바뀌지 않는 첨부)를 둬요. 승인자에게 **선언한 의도와 후보 실행의 실제 차이**를 나란히 보여요. 내보내기와 들이기의 목록에 이 칸들이 실려요.

## 4. 검증을 앞으로 [알파: API 모양, 클베: 증분]
브랜치에서 큐가 돌릴 것과 같은 검사와 후보 실행을 미리 돌려 보는 길을 둬요(같은 실행기). 주체마다 계산 예산이 걸려요.

## 5. 병합 큐는 직렬 하나를 지키되 차례 하나를 싸게 해요 [알파]
- 무거운 후보 실행은 큐 밖에서 돌리고 결과를 (브랜치 내용 해시, 본줄기 끝 해시, 기준 KG 버전) 열쇠로 재사용해요.
- 큐의 차례에서는 본줄기 끝이 그대로인지 보고, 움직였으면 계보로 닿는 것만 다시 따져요.
- 병합의 적용도 계보로 닿는 공급과 타입에만 해요. 닿지 않는 소스의 흐름은 새 묶음으로 바로 이어 가고, 병합의 결과는 보통의 변경 묶음으로 투영에 흘러요. 그래서 병합이 잦아도 KG 전체가 서거나 투영이 통째로 바뀌지 않아요(definitions.md 6절).
- 지표 `merge_turn_duration_s`, `candidate_run_duration_s`, `merge_batch_size`를 더해요(self-observability.md).
- **묶어서 병합**(영향 범위가 겹치지 않는 제안끼리 묶어 한 번 검사하고 본줄기 끝을 한 번 옮기되 제안마다 기록은 따로, 실패하면 쪼개 찾기)은 [클베: 설계, 오베: 구현]이에요. 범위별 큐는 지표가 요구할 때까지 만들지 않아요.

## 6. 위험의 등급 [알파: 등급 계산과 정책의 모양]
등급은 쓴 쪽의 주장이 아니라 **후보 차이에서 계산해요.** 다만 KG의 결과에 차이가 없어도 위험한 항목이 있어서, **항목 종류마다의 바닥**을 둬요. 등급은 차이로 계산한 값과 바닥 가운데 높은 쪽이에요.

| 등급 | 무엇 |
|---|---|
| R0 | KG 결과의 차이가 없어요(표시 이름, 설명, 일정의 주기) |
| R1 | 예외 목록 줄, 속성 덧씌움 등 차이가 작은 한도 안이고 객체 증감과 식별 합침이 없어요 |
| R2 | 매핑과 공급의 변경이고 차이가 한도 안이에요 |
| R3 | 식별 규칙, 타입 물러나기와 합치기, 안전장치 느슨하게, 민감 등급 낮추기, 깨는 변경. **언제나 사람**이에요 |

| 항목 종류의 바닥 | 바닥 |
|---|---|
| 소스의 `endpoints`(닿는 주소) | R3 |
| 가리기(`redact`) 규칙 | R3 |
| 알림의 규칙과 목표를 느슨하게 | R3 |
| 담당자(연락처) 바꾸기 | R3 |
| 기대 조건의 강도를 `fail`에서 `warn`으로 | R3 |
| 비밀 값이 닿는 주소(`allowed_hosts`) | R3 |

이 항목들은 KG에 차이가 없어도 R3이라 첫 적용도 자동 병합도 사람이 봐요(바닥에 닿는 항목이 하나라도 있으면 제안 전체가 R3).

**첫 적용의 사람 확인은 R2부터예요**(ADR-0008). R0, R1은 저절로 적용하고 사후에 알려요 [알파부터]. 병합 줄 앞의 승인과는 다른 문이에요.

**정책에 의한 자동 병합**(승인 없이 병합)은 R0, R1 [클베: 닫힌 베타에서 구현, 기본 꺼짐], R2와 사후 표본 검토 [오베]예요. 조건은 검사 전부 통과, 차이가 등급의 한도 안, 그 주체의 최근 되돌림 비율이 기준 아래, 한도 안이에요. 기본은 **꺼짐**이고 `admin`이 켜요. 등급표와 정책은 정의의 항목이고 느슨하게 하는 것은 `admin`의 승인이 들어요. 자동 병합은 "승인"이 아니라 정책이 허락한 것이라 감사에 정책의 판이 남아요.

## 7. 검토의 용량 [클베]
승인 대기를 등급으로 나눠 R3와 넓은 영향을 위에 둬요. 같은 `trigger_ref`나 같은 에이전트 실행의 제안을 한 묶음으로 검토해요(병합과 되돌리기는 따로). 승인자별 대기와 낡음의 지표를 내요.

## 8. 기대는 제안, 맞추기, 크게 되돌리기, 회로 차단
- **기대는 제안** [클베]: 제안에 `after`(먼저 병합돼야 하는 제안)를 둬요. 먼저 것이 병합되면 기준이 새 끝으로 맞춰지고 닫히면 알려요. 덧씌움의 상속은 만들지 않아요.
- **본줄기에 맞추기는 API 한 번** [클베]: 충돌이 없으면 저절로 돼요. 뒤에 온 쪽이 에이전트면 에이전트가 먼저 다시 맞추고, 안 되면 맡긴 사람을 불러요.
- **크게 되돌리기** [클베]: "에이전트 실행 X가 만든 병합 전부"를 의존 차례로 한 묶음의 되돌리기 제안으로 만들어요. 미리 보기와 승인을 거치고 줄줄이 저절로 되돌리지 않아요.
- **회로 차단** [오베]: 안전장치가 적용을 붙잡거나 되돌림 비율이 뛰면 그 주체와 등급의 자동 병합을 끄고 알려요.

## 9. 한도와 정리
주체마다 열린 브랜치 수, 줄에 선 제안 수, 하루 제안 수, 후보 실행의 계산 예산, 시험 수집의 저장량이 있어요 [알파: 설정과 거절의 답]. 활동 없는 초안과 검토 중 제안의 자동 닫기, 같은 내용 해시의 열린 제안에 잇기 [클베]. 아무도 가리키지 않는 판과 닫힌 브랜치의 시험 수집 자리의 정리 [오베]. 값은 [기본값 표](defaults.md) 6절에 가정으로 적어요(아직 정해지지 않았어요).

## 10. 설계 담당에게 묻는 것
- 바닥 목록(6절)에 더할 항목 종류가 있는지.
- 9절의 한도 값(주체마다의 열린 브랜치 수 등)과 자동 닫기의 기한.
- 자동 병합의 "차이가 작은 한도"와 "최근 되돌림 비율의 기준"의 값.

## 11. 관련
ADR-0014, ADR-0012(승인은 사람만, 범위), ADR-0018(비밀 값의 닿는 주소), ADR-0017(지표). 요구사항: REQ-218(주체와 승인), REQ-219(왜 바꿨나), REQ-220(위험의 등급과 자동 병합), REQ-221(병합 큐와 한도).
