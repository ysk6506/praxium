# 정의의 버전과 브랜치

정의(타입, 소스, 데이터셋, 정제, 공급, 식별 규칙 같은 버전이 있는 모든 설정)를 어떻게 쌓고, 고치고, 합치고, 되돌리고, 따라가는지의 설계예요. 코드는 아직 없어요. 칸의 이름은 `core.definitions`가 쓸 이름이고, 예시의 이름은 지어낸 거예요. 제품 책임자의 길잡이는 넷이에요. 파이프라인과 모델의 모든 것에 버전과 브랜치가 있다 / 큰 기술 회사들이 만든 사례를 참고한다 / 변경은 잦지 않으니 동시 수정의 충돌 풀기와 되돌리기가 잘 돼야 한다(잦은지는 쓰는 쪽에 달려서 못 박지 않아요. 에이전트가 많이 쓰는 때는 [덧붙임](definitions-at-agent-scale.md)이 다뤄요) / 데이터 계보를 관리한다.

## 1. 무엇에 답하나

- 정의는 어떤 단위로 버전을 매기고, KG 버전의 입력인 "정의의 버전"은 무엇인가요(ADR-0009의 결정성).
- 여러 사람이 동시에 고쳐도 운영이 깨지지 않으려면 무엇을 검사하고 어떻게 줄을 세우나요. 충돌은 어떻게 보이고 누가 푸나요.
- 잘못 병합됐을 때 어떻게 되돌리고, 되돌려도 KG에서 안 돌아오는 것은 무엇인가요.
- 고치기 전에 무엇이 걸리는지는 어떻게 아나요(정의의 계보).
- KG가 여럿이면 정의는 누구의 것이고, 병합은 어디까지 적용되며, 확인을 기다리는 동안 무엇이 서나요.
- 넘겨받은 것 문서의 쟁점 바(멈춰도 되는 것의 경계)와 사(이음매의 파일 형식)에 걸쳐요(ADR-0014 맥락).

## 2. 한눈에

```
 항목 ──(내용이 바뀔 때마다)──▶ 판: 내용 해시로 주소를 매긴, 바뀌지 않는 글
   │  "항목마다 어느 판인가"의 전체 목록 = 정의 묶음 (내용 해시가 KG 버전 ID의 입력)
   ▼
 본줄기:  D-139 ◀ D-140 ◀ D-141        배포에 하나. 한 줄의 이어짐. 끝은 행 하나(견줘서 바꾸기로만 옮긴다)
            ▲ 바탕
 브랜치(바뀐 항목만의 덧씌움) ─▶ 제안 P-57 ─▶ 검사 ─▶ 줄 ─▶ 병합 (트랜잭션 하나)
                                  │ 승인: 범위를 가진 approver
                                  └ 막는 까닭(충돌, 낡음, 검사, 모자란 승인)은 상태가 아니라 끌어낸 값
 병합 뒤: 계보로 닿는 공급과 타입에만 "새 정의를 적용하라"는 일이 걸린다. 닿지 않는 소스는 새 묶음으로 바로 이어 간다
         KG는 본줄기의 어느 묶음을 쓰는지 가리킬 뿐이다(KG마다 하나. 본줄기의 끝과 따로 옮겨 간다)
 되돌리기: 언제나 앞으로 나아가는 새 제안 (D-142 = D-140의 모습, 그러나 새 묶음)
```

- 판과 묶음은 고치지도 지우지도 않아요. 잘못은 새 묶음으로 바로잡아요.
- **정의의 본줄기는 배포에 하나예요.** 운영 KG, 후보 KG, 시험 KG, 시스템 KG는 같은 본줄기를 보고 각자 어느 묶음을 쓰는지 가리켜요. 정의의 표는 KG마다 있지 않아요. 시스템 KG는 `sys` 이름 공간의 항목만 써요(ADR-0007).
- 정의의 진실은 PostgreSQL에 있어요(ADR-0009). 실제 Git은 진실의 자리가 아니에요(13절).
- 정의 고치기는 "멈춰도 되는 것"이에요(ADR-0011). 저장소가 멈추면 못 고칠 뿐 KG와 묻기는 그대로예요.

## 3. 데이터의 모양

### 3-1. 정의의 항목의 종류
| `kind` | 뜻 | 자리 (access-control.md 9-1) |
|---|---|---|
| `type` | 객체·링크·액션 타입(`org`와 `ext`). 속성, 바인딩, 식별 키를 안에 가져요 | `ext`는 그 타입, `org`는 `model_steward` |
| `type_overlay` | 제품 표준(`std`) 타입의 덧씌움: 속성 더하기, 바인딩 더하기, 표시 이름, 숨기기 | `org`처럼 `model_steward` |
| `source` | 소스 설정(어댑터, 프리셋의 이름과 판, 비밀 값 참조) | 그 소스 |
| `dataset`, `refinement` | 소스 안의 표 하나 / 닫힌 연산으로 데이터셋을 다듬는 정제 | 딸린 소스 |
| `feed` | 공급: 데이터셋 하나에서 객체 타입 하나로 가는 매핑(완전성 선언 `completeness_declaration` 포함) | 소스와 타입 둘 (5절) |
| `identity_rule`, `exception_list` | 타입마다 식별 키의 우선순위와 이기는 소스의 순서 / 식별의 예외와 원본 기록 제외 | 그 객체 타입 |
| `link_definition` | 링크를 잇는 조건. 끌어낸 링크와 묶음 만들기 포함 | 출발 타입 |
| `expectation`, `schedule` | 기대 조건(ADR-0008) / 소스와 데이터셋의 일정, 받는 방식 | 딸린 소스 |
| `competency_question` | 역량 질문(ADR-0015): 대상, 필요한 것의 패턴, 목표 충족률 | 대상 객체 타입 |
| `objective` | 목표(ADR-0013) | 붙은 자원(소스나 객체 타입) |
| `alert_rule`, `guard_values` | 알림의 규칙(ADR-0013) / 안전장치의 값(문턱, 횟수) | 알림의 규칙은 붙은 자원(소스나 객체 타입), 안전장치의 값은 소스. 느슨하게는 `admin` |

모든 항목에는 **자리**가 있어요. 고치려면 그 자리를 범위에 가진 `editor`가, 승인하려면 그 자리를 범위에 가진 `approver`가 필요해요. 제품 표준(`std`) 타입과 시스템 KG의 `sys` 타입도 판이 있는 항목이고 제품의 버전이 그 판을 정해요. 제품은 이것들을 스키마 옮김의 한 걸음으로 저장소에 싣고, 실행 파일은 저장소의 것을 읽어요(실행 파일에 든 사본이 아니에요). 그래서 올리는 중에 일꾼 벌마다 본줄기의 해시가 달라지지 않아요. 값 타입, 링크의 뜻, 특성, 채널, 프리셋 데이터는 제품이 싣는 거라 항목이 아니에요. 담당자(연락처)는 각 항목의 한 칸이고 바꾸는 것은 정의의 변경이에요. 비밀 값은 참조만 담겨요.

### 3-2. 칸
정의의 표에는 `kg_id`가 없어요. 본줄기가 배포에 하나이기 때문이에요(ADR-0014). `kg_id`는 KG 쪽의 칸(KG마다 쓰는 묶음을 가리키는 `applied_set_no`)에만 있어요(kg-storage.md). 해시는 정규 바이너리 인코딩 위의 SHA-256이에요(ADR-0006).

| 표 | 칸 | 뜻 |
|---|---|---|
| `definition_item` | `item_id`, `kind`, `name`, `namespace`(`org`/`ext`/`sys`/덧씌움이면 `std`), `contacts` | `item_id`는 바뀌지 않고 이름이 바뀌어도 이어져요. 쓴 `item_id`는 다시 안 써요 |
| `definition_blob` | `content_hash`, `kind`, `schema_version`, `body` | 내용으로 주소를 매긴 글. 같은 내용은 한 번만 저장돼요 |
| `item_revision` | `item_id`, `rev_no`, `content_hash`, `first_set_no` | 항목의 판. 사용자에게는 `판 7`. 내용이 옛 판과 같아도(되돌림) `rev_no`는 새로 올라요 |
| `definition_set` | `set_no`, `content_hash`, `parent_set_no`, `origin`, `proposal_id`, `created_at` | 정의 묶음 `D-142`. `content_hash` = 정렬한 (`item_id`, 판의 `content_hash`) 목록의 해시. 부모는 안 넣어서, 되돌려 같은 내용이 되면 해시가 같아요 |
| `set_entry` | `set_no`, `item_id`, `content_hash` | 묶음의 전체 목록. 항목이 수천 개면 묶음마다 전체를 둬도 감당된다고 봐요(가정, 재서 정해요) |
| `trunk_head` | `set_no`, `head_rev` | 본줄기의 끝. 행 하나 |
| `branch` | `branch_id`, `name`, `base_set_no`, `state`(`open`/`merged`/`closed`), `origin`, `content_hash`, `created_by` | `content_hash`는 덧씌움의 내용 해시예요 |
| `branch_entry` | `branch_id`, `item_id`, `op`(`add`/`modify`/`remove`), `content_hash`, `base_content_hash` | 바뀐 항목만 있어요. `base_content_hash`는 바탕 묶음에서의 그 항목 |
| `proposal` | `proposal_id`(`P-57`), `branch_id`, `title`, `summary`, `state`, `origin`, `reverts_proposal_id`, `close_reason`, `superseded_by`, `queue_seq`, `merged_set_no`, `emergency`, `post_review_state` | 정식 객체예요 |
| 브랜치와 제안 둘 다(누가 썼나) | `authored_by`(주체), `actor_kind`(`person`/`system_account`), `on_behalf_of`(맡긴 사람), `agent_run_id`, `agent_build` | 5절과 덧붙임 1절 |
| `proposal`(왜 바꿨나) | `trigger_ref`, `evidence`, `intent`, `decision_log_hash`, `after`(클로즈 베타) | 칸 자리는 알파 |

- `origin`: `change`(보통), `revert`, `restore`, `import`, `bootstrap`(첫 묶음).
- 위험 등급(R0~R3)은 후보 차이에서 계산해 끌어내는 값이라 칸이 아니에요(덧붙임 6절).
- 브랜치와 제안은 일대일이고 브랜치를 열면 제안이 `draft`로 함께 생겨요(가정). **작은 변경은 "제안 하나"로 서버가 한 번에 만들어요**(`small_change_propose`: 브랜치 열기, 항목 고치기, 검토 요청까지). 화면 전용 길이 아니라 공개된 쓰임이고 클라이언트의 일로만 두지 않아요(ADR-0007).
- 사용자에게 보이는 번호: 묶음 `D-142`(옆에 해시 앞 8자), 제안 `P-57`, 항목의 `판 7`. KG 버전의 답에는 쓰인 `D-142`가 붙어요(`kg_version.definition_set_hash`, `versions` 답의 `definition_version`).
- 표준 모델의 버전은 정의 묶음에 들어가요(`std` 타입의 판이 제품 버전을 따라 바뀌어 묶음 해시에 반영돼요). 실행기의 의미 버전은 묶음 밖의 입력이에요. 둘이 오른 뒤 첫 적용도 6절의 첫 적용 규칙을 따라요(ADR-0008).
- 본줄기의 끝(병합된 묶음)과 **KG가 지금 쓰는 정의 묶음**(`kg_version.definition_set_hash`, KG마다)은 다를 수 있어요(6절).

### 3-3. 목록 항목
항목 종류가 "키가 있는 목록"이라고 선언한 곳은 키로 맞춰 합쳐요(7-2). 지금은 넷이에요.

| 항목 | 목록 | 열쇠 |
|---|---|---|
| `exception_list` | 줄 | (예외의 종류, 대상) |
| `type`, `type_overlay` | 속성 목록, 바인딩 목록 | 속성이나 바인딩의 `id` |
| `guard_values` | 값 | 값의 이름 |

그 밖의 항목은 통째로 하나로 봐요. 항목 안의 칸 단위 자동 병합은 하지 않아요.

## 4. 제안의 흐름

### 4-1. 상태
```
draft ─검토 요청─▶ in_review ─필요한 승인이 모두 있음─▶ approved ─줄에 넣음─▶ queued ─병합─▶ merged
  ▲                  │                                      │ ▲                 │
  └──── 내용을 고치면(승인과 검사 결과가 낡는다) ──────────────┴─┘                 └ 줄 맨 앞에서 실패하면 approved로 돌아가 막는 까닭이 붙어요
 어느 상태에서나(merged 빼고) ─▶ closed (`close_reason`: abandoned, rejected, superseded)
```

| 가는 길 | 조건 |
|---|---|
| `draft` → `in_review` | 낱개의 유효성 검사가 통과해야 해요(가정). 담당자에게 검토 요청이 가요 |
| `in_review` → `approved` | 5절의 필요한 승인이 현재 `content_hash`에 모두 있어요 |
| `approved` → `queued` | `editor`가 줄에 넣어요. 막는 까닭이 없어야 해요 |
| `queued` → `merged` | 6절의 병합이 끝났어요. 끝이에요 |
| 아무 때나 → `closed` | 고친 사람이나 `admin`이 닫아요. 지우지 않고 목록에서 숨기고 다시 열지 않아요(같은 브랜치로 새 제안을 만들어요). 대체되면 `superseded_by`가 새 제안을 가리켜요 |

내용을 고치면 `draft`로 돌아가고 승인은 무효가 돼요. 병합된 제안과 묶음은 고치지 못해요.

### 4-2. 막는 까닭
상태가 아니라 지금 값에서 끌어내요. 하나라도 있으면 줄에 못 들어가거나 병합이 안 돼요.

| `blocker` | 뜻 | 자세히 |
|---|---|---|
| `conflicts` | 충돌 상태가 남아 있어요 | 항목, 종류(7절) |
| `stale` | 바탕이 본줄기의 끝이 아니에요 | 얼마나 뒤처졌나, "본줄기에 맞추기"를 권해요 |
| `check_failed` / `check_pending` | 검사가 실패했거나 아직 안 했어요 | 어느 검사, 어느 항목, 까닭 |
| `approvals_missing` | 필요한 승인이 모자라요 | 어느 항목에 어느 범위의 승인이 없나. 거부가 있으면 그것도요 |
| `guard_stopped` | 후보 실행이 안전장치에 걸렸어요 | 자리를 범위에 가진 `operator`의 확인이 필요해요. 확인은 브랜치의 내용 해시에 묶여서 내용이 바뀌면 다시 해요. 값을 고칠 필요는 없어요 |
| `objective_missed` | 제안 때문에 지키던 목표 충족률을 못 지켜요(`competency_objective_missed`) | 어느 역량 질문, 전과 뒤, 새로 못 채운 객체 |

### 4-3. 검사
검사는 브랜치의 내용 해시에 묶여요. 내용이 바뀌면 낡은 결과가 되고 다시 해요. 편집 중에 돌리는 것과 줄 맨 앞에서 합친 결과로 다시 돌리는 것이 있어요.

| `check_kind` | 무엇을 보나 |
|---|---|
| `item_valid` | 바뀐 항목마다: 스키마, 이름 규칙, 정제 연산이 닫힌 목록 안인가, 값의 범위, 비밀 값은 참조뿐인가 |
| `merged_valid` | 합친 결과의 유효성. 가리킴, 고리, 타입 맞음, 물러난 것을 씀, 식별 키의 바뀜(7-3). 깨는 변경에 옮김이 있나(11절). 지우는 타입이 쓰이고 있지 않나 |
| `item_tests` | 정의의 시험(10절) |
| `candidate_run` | 받아 둔 원본 기록으로 만든 후보 KG와 지금 버전의 차이. 정의의 차이와 KG의 차이를 함께 보여요 |
| `guard` | 같은 안전장치(ADR-0008)를 후보에 적용해요 |
| `competency` | 역량 질문의 충족률이 어떻게 바뀌나(질문마다 전과 뒤, 새로 못 채운 객체). 목표를 지키던 질문이 못 지키게 되면 실패예요. 이미 목표 밑인 질문은 막지 않고 보여 줘요 |

- 결과의 칸: `proposal_id`, `check_kind`, `subject_hash`(검사한 내용 해시와 얹은 묶음의 해시), `inputs_digest`(후보 실행에서: 원본 기록의 묶음, 앞 KG 버전, 실행기의 의미 버전), `status`(`pending`/`passed`/`failed`/`needs_confirmation`), `detail`.
- 후보 실행은 소스에 다시 가지 않아요. 결정성(ADR-0009) 덕에 `subject_hash`와 `inputs_digest`가 같으면 결과를 다시 쓸 수 있어요.

## 5. 승인을 범위로

규칙은 access-control.md 9절이 정해요. 여기서는 제안의 흐름에서 어떻게 쓰이는지만 적어요.

- 제안이 고친 항목 하나하나에 **자리**가 있고, 그 자리를 범위에 가진 `approver`(고친 사람 말고)의 승인이 있어야 해요. 고치는 쪽도 자리를 범위에 가진 `editor`예요. 고친 사람은 이 브랜치에 판을 더한 모든 사람(가정)이고, **같은 주체이거나 같은 `on_behalf_of`이면 승인하지 못해요.** 승인은 사람만 해요(시스템 계정은 승인자가 못 돼요. ADR-0012).
- **`on_behalf_of`는 스스로 적지 못해요.** `admin`이 그 시스템 계정에 묶어 둔 사람 가운데서만 골라요(access-control.md). 계정이 자기 말로 다른 사람을 대면 "같은 맡긴 사람"의 열쇠가 의미가 없어져서예요.
- **`solo_approval`.** 처음 세울 때와 혼자 쓰는 시험 배포를 위한, 드러난 설정 하나예요. 켜면 자기가 고친 것을 자기가 승인할 수 있어요. 기본은 꺼짐이고, 켜면 모든 승인의 감사 기록에 표시가 남고 건강에 경고가 떠요. 이것이 없으면 혼자 시험하는 사람은 첫 정의를 병합할 수 없어요(`admin`도 같은 규칙이라서).
- **읽는 소스.** 정제 데이터셋과 링크 정의는 다른 소스의 데이터셋을 입력으로 읽을 수 있어요. 읽는 소스는 **쓴 사람의 범위 안**이어야 해요(`item_valid`가 막고 `:preview`도 같아요). 승인은 자리와 함께 **읽는 소스의 범위도 따져요**(어떻게 따지는지는 17절). 원본을 보는 길(미리 보기, 견본, 통계)은 그 데이터셋이 대는 타입의 읽기 권한도 요구하고 감사에 남아요.
- **공급**은 소스의 `editor`가 고쳐요. 그 공급이 객체를 만들거나 물러나게 하거나 식별 키를 매핑하면 대상 타입을 범위에 가진 `approver`의 승인도 필요해요. 아니면 타입의 담당자에게 알림만 가요.
- 검사가 "이 제안 때문에 깨진다"고 말한 항목도 고친 항목처럼 그 자리의 승인을 받아요. 가리키기만 하는 항목의 담당자에게는 알림만 가요. 후보 실행에서 객체가 바뀌는 타입의 `approver`도 승인해요.
- `org` 타입과 덧씌움은 `model_steward`(층으로 범위를 좁힐 수 있어요), 안전장치를 느슨하게 하는 것과 민감 등급을 낮추는 것은 `admin`이에요. 조이는 것은 자리를 범위에 가진 `approver`예요. KG의 결과에 차이가 없어도 위험한 항목(소스의 `endpoints`, 가리기 규칙, 알림과 목표를 느슨하게, 담당자, 기대 조건의 `fail`→`warn`, 비밀 값의 닿는 주소)은 등급이 R3예요(덧붙임 6절).
- 승인은 `content_hash`에 걸려요(`proposal_approval`: `proposal_id`, `approver`, `decision`, `content_hash`, `covers_item_ids`, `matched_grants`). 내용이 바뀌면 승인도 거부도 무효예요.

| 예(지어낸 것) | 필요한 승인 |
|---|---|
| `u-hansol`(`editor`, 소스 `rack_sheet`)이 `Rack` 객체를 만드는 공급 `rack_sheet_to_rack`을 고침(`P-31`) | 소스 `rack_sheet`와 대상 타입 `Rack`을 범위에 가진 `approver`. 한 사람이 둘 다 가지면(`u-narae`) 한 번이에요. `Rack`을 가진 사람이 없으면 다른 `approver`가 더 필요해요. `u-hansol`이 `approver`를 겸해도 못 해요 |
| 링크 정의 `server_in_rack`(읽는 소스는 `server_list`, `rack_sheet`, 출발 타입은 `PhysicalServer`)의 조건을 고침(`P-32`) | 자리는 출발 타입이에요. `PhysicalServer`를 범위에 가진 `approver`가 승인하고, 읽는 소스 둘의 범위도 따져요(17절). 읽는 소스만 가진 사람은 못 해요. 고친 사람은 두 소스를 범위에 가져야 해요. 가진 사람이 없으면 막히고 `admin`이 권한을 줘서 풀어요 |
| 조직 표준 타입 `Rack`에 속성 `max_power_kw`를 더함(`P-33`) | `model_steward`의 승인. 속성 더하기는 더하기라 옮김이 필요 없고, 그 타입에 공급을 단 항목의 담당자에게 알림이 가요 |

**승인이 무효가 되는 때.** 내용 해시가 바뀔 때예요. "본줄기에 맞추기"만으로는 덧씌움의 내용이 안 바뀌니 승인이 남아요. 다만 합친 결과에서 새로 깨지거나 새로 바뀌는 항목이 생겨 필요한 범위가 늘면 `approvals_missing`이 다시 켜져요(필요한 승인은 합친 결과로 계산해요). 충돌을 손으로 풀면 내용이 바뀌니 무효예요.

**안전장치를 느슨하게 할 때.** `guard_values`의 값이 느슨해지는 방향이면(문턱을 올리거나 횟수를 늘림) 제안의 필요한 승인에 `admin`이 들어가요. 어느 쪽이 느슨한지는 값마다 제품이 정해 둬요. 묶음이 한 제안에 둘이 섞여 있으면(하나는 조이고 하나는 느슨히) `admin`의 승인이 필요해요.

## 6. 병합의 줄과 적용

줄은 하나예요. 본줄기가 배포에 하나라 병합 잠금도 하나예요. 사람이 쓸 때는 변경이 잦지 않아 한 번에 하나씩 해도 충분하다고 보지만 못 박지는 않아요. 에이전트가 쓰면 잦아서, 무거운 일을 큐 밖에서 미리 하고 차례 하나를 싸게 해요(덧붙임 5절). 직렬화는 비용이 아니라 단순함이에요. 서로 멀쩡한 두 제안이 합쳐서 깨지는 일을 막아요.

**줄의 맨 앞에서 하는 일(차례).** 병합 잠금 하나를 잡고 해요.

1. 줄 맨 앞의 `queued` 제안을 꺼내요. 본줄기의 지금 끝(`set_no`, `head_rev`)을 읽어요.
2. 그 끝 위에 덧씌움을 얹어 합친 묶음을 만들어요(세 쪽 견주기, 7절). 충돌이면 줄에서 빠지고 `approved`로 돌아가 `conflicts`가 붙어요.
3. 합친 결과로 검사를 다시 해요: `item_valid`, `merged_valid`, `item_tests`. 필요한 승인을 합친 결과로 다시 계산해서 `content_hash`에 승인이 있는지 봐요.
4. 후보 실행과 안전장치는 **큐 밖에서 미리 돌린 결과**를 (브랜치 내용 해시, 본줄기 끝 해시, 기준 KG 버전) 열쇠로 다시 써요. 앞 버전은 지금 서빙하는 KG 버전이에요. 차례에서는 본줄기 끝이 그대로인지만 보고, 움직였으면 계보(12절)로 닿는 것만 다시 따져요. 열쇠가 맞는 결과가 없을 때만 그 자리에서 돌려요.
5. 모두 통과하면 **트랜잭션 하나**로 들여요: `definition_set`과 `set_entry`와 `item_revision` 쓰기, `trunk_head`를 `head_rev`가 기대한 값일 때만 바꾸기(견줘서 바꾸기), 제안을 `merged`로, 감사 기록. 여러 항목과 여러 범위의 것이 한꺼번에 들어가고 반쯤 들어간 병합은 없어요.
6. 견줘서 바꾸기가 안 맞으면(그사이 끝이 옮겨졌어요) 1로 돌아가요. 줄이 하나라 드물어요.

**병합과 KG에의 적용은 따로예요.** 본줄기의 끝(병합된 묶음)과 KG가 지금 쓰는 묶음이 다를 수 있어요. 병합은 정의를 한꺼번에 들이고 `definition_merged` 사건과 함께 "새 정의를 적용하라"는 일을 걸어요. **적용은 계보(12절)로 닿는 공급과 객체 타입에만 해요.** 병합이 바꾼 항목에서 계보를 따라가면 닿는 (공급, 타입)이 나와요. 일꾼은 후보 실행의 결과를 바탕으로 적용하고(그사이 흐른 변경은 새 정의로 다시 따져요), 적용이 끝나면 KG 버전을 봉하고(`seal_kind`: `merge`, ADR-0009) KG가 쓰는 묶음이 옮겨 가요.

- **닿지 않는 소스는 서지 않아요.** 그 소스의 흐름과 배치는 병합이 확정된 `change_seq`부터 새 묶음으로 바로 이어 가요(`stream`이면 그 앞은 옛 정의 몫이고 다시 쓰지 않아요). 닿지 않는 항목은 두 묶음에서 판이 같아서 결과도 같아요. 흐름에서 정의를 고치는 길도 브랜치와 후보 실행을 거쳐요.
- **첫 적용의 사람 확인은 R2부터예요**(ADR-0008). 후보 차이에서 계산한 등급이 R0, R1이면 저절로 적용하고 사후에 알려요(알파부터). R2, R3이면 사람이 차이를 봐요. 승인 없이 병합하는 **자동 병합**은 이것과 달라서 클로즈 베타이고 기본이 꺼짐이에요(덧붙임 6절).
- 확인을 기다리는 동안 서는 것은 **닿는 공급과 타입뿐**이에요.

| 확인을 기다리는 동안 | 서나, 도나 |
|---|---|
| 닿지 않는 소스의 흐름과 배치 | 돌아요. 새 묶음으로 바로 이어 가요 |
| 닿는 공급과 타입의 받기 | 돌아요. 받아서 원본 기록에 쌓기만 하고 적용을 미뤄요(붙잡아도 받기는 멈추지 않아요) |
| 닿는 공급과 타입의 적용 | 서요. 확인되면 한도가 있는 묶음으로 나눠 적용해요 |
| 닿는 타입의 지금 객체와 링크 | 앞 묶음의 결과 그대로 읽혀요 |
| 묻기, 변경 알림, 투영 | 돌아요 |
| 병합의 줄 | 돌아요(가정) |
| 사람의 확인 | R2, R3만 기다려요. R0, R1은 기다림이 없어요 |

- 적용이 안전장치에 걸려도 같아요. 걸린 것은 닿는 것뿐이고 문제와 알림이 올라가요. 어긋남(KG마다 `applied_set_no`와 `head_set_no`, 붙잡힌 항목)은 `definitions_overview`에 드러나요.
- **병합의 결과도 보통의 변경 묶음으로 투영에 흘러요.** 투영을 통째로 다시 짓는 것은 차이가 문턱을 넘을 때만이에요(문턱은 [기본값 표](defaults.md)에 가정으로 둬요). 병합마다 통째로 짓지 않아서 에이전트가 하루에 여러 건을 병합해도 감당돼요.
- 정의 묶음의 해시가 새 KG 버전 ID의 입력으로 들어가요. 같은 앞 버전, 원본 기록, 정의 묶음, 실행기의 의미 버전이면 같은 KG 버전이에요.

## 7. 충돌

### 7-1. 넷과 푸는 사람
| 종류 | 지어낸 예 | 어떻게 보이고 누가 푸나 |
|---|---|---|
| 같은 항목을 둘이 고침 | `P-31`과 `P-35`가 같은 공급 `rack_sheet_to_rack`의 컬럼 매핑을 다르게 고침 | 세 쪽 견주기. **뒤에 온 쪽**(먼저 병합된 쪽이 본줄기가 되므로 바탕이 낡아진 쪽)의 `editor`가 골라요 |
| 목록 항목의 다른 줄을 고침 | 예외 목록에 한쪽은 서버 쌍 X를 "같다", 다른 쪽은 쌍 Y를 "다르다"로 더함 | 열쇠가 다르니 저절로 합쳐요. 같은 열쇠면 위의 충돌이에요 |
| 뜻의 충돌(항목은 다름) | 한쪽이 데이터셋의 컬럼 `hostname`을 `host_name`으로 바꾸고, 다른 쪽이 옛 이름으로 공급을 더함 | 합친 결과의 검사가 잡아요. 무엇이 무엇을 깨는지가 보이고 뒤에 온 쪽이 고쳐요 |
| 결과의 충돌 | 각각은 맞는데 합치면 후보 KG에서 서버 객체가 대량으로 사라짐 | 후보 실행의 차이와 안전장치가 잡아요. `operator`가 확인하거나 정의를 고쳐요 |

### 7-2. 같은 항목: 세 쪽 견주기와 저절로 합치기
항목마다 세 쪽을 비교해요. **바탕**(브랜치를 딴 묶음의 판), **본줄기**(지금 끝의 판), **내 것**(덧씌움의 판).

| 바탕 / 본줄기 / 내 것 | 결과 |
|---|---|
| 본줄기 = 바탕 | 내 것을 써요 |
| 내 것 = 바탕 | 본줄기를 써요 |
| 본줄기 = 내 것 | 같은 변경이라 충돌이 아니에요 |
| 셋이 다름 | 충돌 `same_item`. 한쪽이 지우고 한쪽이 고쳤으면 `remove_vs_modify` |
| 목록 항목(3-3) | 열쇠마다 위 표를 따로 적용. 같은 열쇠만 `keyed_entry` 충돌 |

충돌은 막지 않고 **상태로 남아요**(`branch_conflict`: `branch_id`, `item_id`, `conflict_kind`, `base_content_hash`, `trunk_content_hash`, `mine_content_hash`, `status`, `resolution`, `resolved_content_hash`, `resolved_by`). 푸는 길은 셋이에요: 본줄기 것 / 내 것 / 손으로 합친 새 판. 손으로 합친 것은 보통의 편집이라 다시 검사하고 승인도 새로 받아요. 자동으로 합친 결과도 검사와 후보 실행을 거쳐요.

### 7-3. 뜻의 충돌을 잡는 검사
항목 병합은 겹치는지만 알고 뜻은 몰라요. 합친 결과를 아래로 검사해요(`merged_valid`). 컬럼 단위의 계보(12절)가 있어서 "이 데이터셋의 출력 컬럼"을 계산할 수 있어요.

| 검사 | 막는 것 | 보이는 말 |
|---|---|---|
| 가리킴 | 공급이 가리키는 컬럼, 데이터셋, 타입, 속성이 합친 결과에 없어요 | "`rack_sheet_to_rack`이 컬럼 `hostname`을 쓰는데 `P-35`가 이름을 바꿨어요" |
| 고리 | 링크 정의가 서로를 따라가거나, 데이터셋이 서로를 읽어요 | 고리의 길 전체 |
| 타입 맞음 | 매핑한 컬럼의 자료형과 속성의 자료형이 안 맞아요. 값 타입도요 | 컬럼과 속성과 자료형 둘 |
| 물러난 것을 씀 | 물러난 타입(`deprecated`)에 새 공급을 달아요. 운영 중의 `retired_type_in_use` 문제와 달리 병합에서는 막아요 | 물러난 타입과 `superseded_by` |
| 식별 키의 바뀜 | 한쪽이 식별 키를 바꿨는데 다른 쪽이 옛 키로 공급을 더해요. 한 속성의 이기는 소스가 둘로 정해져요 | 키와 공급 |

항목을 담당하는 쪽이 다르면 메시지에 양쪽 항목과 담당자를 적고 양쪽에 알려요. 합의가 안 되면 `admin`이 권한이나 담당자를 정리해서 풀어요.

### 7-4. 낡은 브랜치
바탕이 본줄기의 끝이 아니면 `stale`이에요. "본줄기에 맞추기"는 새 끝을 바탕으로 항목마다 세 쪽 견주기를 다시 해요. 덧씌움이라 가볍고, 충돌이 없으면 저절로 되고, 있으면 브랜치 안에 `conflicts`로 남아요. 나중에 풀어도 돼요. 충돌이 있는 제안은 줄에만 못 들어갈 뿐 편집과 검토는 계속돼요. 편집 중에는 같은 항목을 건드리는 다른 열린 브랜치가 목록에 보여서(`overlaps_with`) 충돌을 일찍 알 수 있어요.

## 8. 되돌리기

원칙: **지우거나 되감지 않아요. 언제나 앞으로 나아가는 새 제안이에요.** 되돌릴 제안은 `merged`여야 하고, 결과가 지금과 같으면(`content_hash`가 같으면) "할 일 없음"이에요.

### 8-1. 여섯 가지
항목마다 되돌릴 판을 정해요. 지금 본줄기의 판이 그 제안이 만든 판과 **같으면** 앞의 판으로(추가였으면 빼고, 뺀 것이었으면 되살려요), **다르면** 뒤의 변경이 같은 항목을 고친 거라 충돌이에요. 세 쪽 견주기와 같은 기계예요(바탕 = 그 제안의 결과, 본줄기 = 지금 끝, 내 것 = 그 제안의 앞 모습).

| # | 하는 일 | 만들어지는 것 | 거치는 것 |
|---|---|---|---|
| 1 | 병합된 제안 되돌리기 | `origin: revert`인 새 브랜치와 제안(`reverts_proposal_id`) | 보통의 검사, 승인, 줄 |
| 2 | 뒤의 변경이 걸릴 때 | 같은 항목이면 충돌. 뒤의 것이 되돌릴 것을 **가리키면** `merged_valid`가 실패해서 막혀요 | 무엇이 걸리는지(어느 제안의 어느 항목, 담당자)가 보여요. 함께 되돌릴 것을 **미리보기로 제안**해요. 저절로 줄줄이 되돌리지 않아요 |
| 3 | 일부만 | 제안이 바꾼 항목 가운데 고른 것만 담은 `revert` 제안 | 1과 같아요. 고른 항목들이 서로를 가리키면 검사가 막아요 |
| 4 | 정의 묶음 `D-N`으로 돌리기 | `origin: restore`. 고른 범위(소스, 객체 타입, 항목의 목록)의 항목을 `D-N`의 판으로 | 미리보기에 "`D-N` 뒤에 병합된 어느 제안의 어느 항목이 사라지나"가 보여요. 범위를 넘는 항목의 승인은 보통 규칙을 따라요 |
| 5 | 되돌린 것을 되돌리기 | 그냥 1이에요. 따로 만들 게 없어요 | 그 사이 항목이 또 바뀌었으면 같은 충돌 규칙. 되돌린 제안의 내용을 다시 병합해도 변경이 안 돌아오는 함정이 없어야 하고 시험이 걸어요 |
| 6 | 급할 때 | 방금 병합된 제안을 되돌리는 1에 `emergency: true`. "방금"은 병합된 지 정해진 기간(기본값(설정) 7일. 사후 검토의 기한은 3일) 안이고 그 뒤의 제안이 그것에 기대지 않을 때예요 | `admin`, 또는 그 제안이 고친 자리 전부를 범위에 가진 `approver`가 승인 없이 낼 수 있어요(`operator`는 못 해요. 정의의 변경이에요). 검사와 줄은 그대로 거쳐요. 후보 실행과 안전장치도요. 감사 기록에 `admin_override`로 따로 남고 `post_review_state: pending`이 붙어, 다른 `approver`나 `admin`의 사후 검토를 기한 안에 받아요. 기간과 기한의 기본값은 설정이고 재지 않은 가정이에요 |

기한이 지나도록 사후 검토가 없으면 알림이 계속 가요(ADR-0013). 급한 되돌리기도 줄을 그대로 거쳐요.

### 8-2. KG와의 경계
정의를 되돌려도 KG는 되감기지 않아요. 새 정의로 새 KG 버전이 생겨요.

- 되돌린 정의로 다시 돌린 KG는 예전의 KG와 같지 않을 수 있어요. 그사이 원본 기록이 바뀌었고 식별의 이력이 진실의 일부라서요. API가 코드와 값으로 준 경고를 클라이언트가 "정의를 `D-140`의 모습으로 되돌렸지만 KG는 그때로 돌아가지 않아요. 지금의 원본으로 `D-140`의 정의를 돌린 새 버전이 만들어져요"라고 알려요.
- **이미 합친 ID는 식별 규칙을 되돌려도 저절로 갈라지지 않아요.** 가르려면 예외 목록으로 가르고, 그것도 제안이에요. 가르면 남은 쪽은 ID를 그대로 갖고 흡수됐던 쪽은 옛 ID로 되살아나요(식별 이력이 옛 ID를 기억해요).
- **합침마다 "이 합침을 되돌리기"가 있어요**(`POST /v1/kgs/{kg}/identity-events/{id}:revert`). 식별의 이력은 되감지 않아요(그대로). 그 불편을 제품이 져요. 누르면 제품이 그 둘을 가르는 예외를 담은 제안을 만들어 줘요. 후보 실행으로 확인하고 승인을 거쳐요. 식별 규칙을 되돌리는 제안의 후보 실행은 "이 규칙으로 합쳐졌던 것들"의 목록을 보이고, 한꺼번에 가르는 예외를 함께 제안해요. 사람이 예외 목록을 손으로 적지 않아요(ADR-0014).
- **물러났던 객체가 옛 ID로 되살아나는 것은 강한 키로 맞았거나 정해진 기간 안일 때만이에요.** 정의 때문에 사라졌다 돌아온 객체는 ID가 새로 나지 않아요. 약한 키(이름, 주소처럼 다른 장비에 다시 쓰이는 것)로 기간이 지나서 다시 보이면 새 ID를 주고 식별 후보로 올려요.
- **합쳐질 때 흡수된 쪽의 링크**는 `identity_event`에 옛 링크 ID와 새 링크 ID의 이음을 남겨요. 변경 알림과 충족률은 그것을 "물러남과 더함"이 아니라 이음으로 다뤄요.
- **묻는 쪽을 옛 KG 버전에 고정하기.** 나쁜 데이터가 들어왔을 때 범위가 전체인 `operator`나 `admin`이 "물음은 버전 V로 답하라"고 고정할 수 있어요. 데이터를 되감지 않고 읽는 쪽만 고정해요. 칸은 `serving_pin`: `kg_version_id`, `reason`, `pinned_by`, `pinned_at`, `released_at`. 모든 답에 고정됐다는 표시가 붙어요. 고정하면 질의 엔진이 그 버전을 올리고, 다 올라올 때까지 고정은 `pending`이라 지금 것으로 답하며 그렇게 표시해요. 고정된 버전의 이력은 보관 기한이 지나도 지우지 않아요. 고정은 쓰기라 저장소가 살아 있어야 해요.

### 8-3. 지어낸 사고를 끝까지
`PhysicalServer`의 식별 키는 `asset_tag`(1순위), `serial_number`(2순위)였어요. `rack_sheet`의 서버 두 대(`srv-a`는 일련번호 `SN-001`, `srv-b`는 `SN-002`)가 둘 다 자산 번호가 비었고 임시 관리 주소 `192.0.2.9`로 적혀 있어요.

1. 제안 `P-41`이 식별 키에 3순위 `management_ip`를 더했어요. 식별 키를 바꾸는 깨는 변경이라 옮김을 적었어요(식별 이력: 옛 ID는 그대로, 새 키는 알아보는 데만 써요). 후보 차이는 "식별 합침 2건, 객체 -2"였고 문턱(10%이면서 5건 이상)에 못 미쳐 안전장치를 지났어요. 첫 적용 확인의 사람은 "중복 정리"로 읽고 확인했고 `D-141`이 병합돼 KG 버전 `V-88`이 나왔어요.
2. 알아챔. 문제 목록에 "서로 다른 일련번호 두 개" 충돌(속성 충돌)이 서버 한 대에 올라왔고 `quality`의 겹침 지표가 움직였어요. 시간줄에서 `D-141` 병합 직후예요.
3. 범위가 전체인 `operator`가 묻는 쪽을 `V-87`(합치기 전)에 고정했어요. 이제 답은 합쳐지기 전의 모습이고 "고정됨"이 붙어요.
4. `admin`이 급한 되돌리기를 냈어요(사후 검토는 다른 `approver`나 `admin`이 해요). `P-41`의 항목 `identity_rule`을 판 2로 돌리는 `P-44`(`emergency`)예요. 걸리는 것이 없어서 검사를 지나 줄을 거쳐 `D-142`로 병합됐어요. `D-142`의 해시는 `D-140`과 같아요. 사후 검토가 `pending`으로 붙었어요.
5. 그래도 KG에서는 두 서버가 합쳐진 채예요. 식별 이력이 되감기지 않아서요. `P-45`가 예외 목록에 "`SN-001`과 `SN-002`는 다르다"를 더했어요. 후보 실행의 차이에서 `srv-b`가 옛 ID로 되살아나는 것을 확인하고 승인을 받아 병합했어요.
6. `V-89`가 봉해졌고, `operator`가 고정을 풀었어요. 마지막으로 `identity_rule` 항목에 "같은 임시 주소를 쓰는 서로 다른 일련번호 두 행은 서버 둘이다"라는 시험 견본을 더해 같은 사고가 병합 검사에서 걸리게 했어요.

## 9. 새 소스를 더하는 브랜치

새 소스에는 후보 실행에 쓸 원본 기록이 없어요. 브랜치에서 **시험 수집**을 해요. 비밀 값을 푸는 일(시험 수집, 들여다보기, 점검, 미리 보기)은 본줄기의 소스 정의 그대로이면 그 소스를 범위에 가진 `editor`도 하고, 브랜치가 닿는 주소(`endpoints`)를 바꿨으면 그 소스의 `operator`여야 해요(ADR-0018). 새 소스는 브랜치에만 있으니 이 길들은 `branch_id`를 받아요. 같은 읽기 전용 세 겹과 소스 지키기(ADR-0008)를 거치고, 브랜치에 딸린 자리에 담겨요(`branch_id`가 붙은 원본 기록. 운영의 원본에는 안 섞여요). 그 브랜치의 후보 실행과 시험은 본줄기의 원본 기록과 이 시험 수집을 함께 읽어요. 병합되면 그 기록을 첫 수집으로 쓸 수 있어요. 브랜치를 닫으면 담긴 기록은 보관 기한을 따라 지워져요. 소스 설정은 정의의 항목이므로 담당자와 승인 규칙이 그대로 적용돼요.

## 10. 정의의 시험

항목에 견본을 붙여요. 견본은 항목 본문의 목록(열쇠 = 견본의 이름)이라 저절로 합쳐질 수 있어요.

| 칸 | 뜻 |
|---|---|
| `name` | 견본의 이름 |
| `input` | 지어낸 입력: 붙은 항목의 입력 데이터셋마다 행(컬럼 이름 → 값)의 목록 |
| `expect.objects` | 있어야 할 객체: 타입, 식별 키 값, 속성의 값과 근거 등급 |
| `expect.links` | 있어야 할 링크: 타입, 출발과 도착의 식별 키, 링크의 뜻 |
| `expect.absent` | 없어야 할 객체나 링크(예: 서버 둘이 하나로 합쳐지지 않는다) |
| `expect.problems` | 나와야 할 문제 목록의 종류 |
| `mode` | `contains`(기대한 것이 들어 있다) / `exact`(정확히 그것뿐) |

- **어떻게 도나.** 붙은 항목에서 시작해 아래 단계(공급이면 매핑, 식별, 링크)를 실제 실행기로 비어 있는 작은 KG에 돌려요. 후보 실행과 같은 실행기라서 뜻이 한 곳에만 있어요(ADR-0006).
- **언제 도나.** 편집 중에 원할 때, 검토 요청 때, 줄 맨 앞의 병합 검사(`item_tests`). 실패하면 `check_failed`예요.
- **프리셋.** 견본 없이는 제품에 실리지 않아요(ADR-0008). 프리셋을 고르면 그 견본이 소스 항목의 첫 견본으로 따라와요(가정).
- 견본은 지어낸 데이터만 담아요. 실제 데이터를 넣지 않아요(ADR-0003).

## 11. 깨는 변경과 옮김

저장될 때 검사가 항목의 판을 앞의 판과 견줘서 갈래를 정해요. 쓴 사람이 정하지 않아요.

| 갈래 | 예 | 옮김 | 검사와 승인 |
|---|---|---|---|
| 더하기 | 속성 더하기, 새 타입, 새 공급, 새 소스, 새 기대 조건 | 필요 없어요 | 보통 |
| 맞는 변경 | 표시 이름, 일정, 안전장치 조이기, 출력 컬럼의 이름과 자료형이 그대로인 정제 고침, 같은 속성에 다른 컬럼 매핑 | 필요 없어요 | 후보 실행의 차이로 확인해요 |
| **깨는 변경** | 속성의 이름이나 자료형을 바꿈 / 식별 키를 바꿈 / 타입을 물러나게 함 / 링크의 뜻을 바꿈 | **꼭 적어야 저장돼요** | 후보 실행으로 옮김을 확인하고, "무엇이 걸리나"(12절)가 제안에 붙어요 |

**옮김의 칸**(`migration`, 깨는 변경이 든 제안에 붙어요).

| 칸 | 뜻 |
|---|---|
| `change_kind` | `attribute_rename`, `attribute_retype`, `identity_key_change`, `type_retire`, `link_meaning_change`, `type_merge`, `type_promote` |
| `from_ref`, `to_ref` | 어느 속성이나 타입이 어느 것으로 |
| `value_rule` | 값을 옮기는 바꾸기. 제품에 든 순수 함수의 목록에서 골라요(ADR-0008) |
| `identity_plan` | 식별 이력을 어떻게 하나: `keep_ids`(옛 ID를 그대로), `carry_to_successor`(물러나는 타입의 식별 이력을 후속 타입으로) 등 |
| `phase` | `add_and_fill` / `retire_old` |
| `readers` | 그 시점의 "무엇이 걸리나" 결과 |

- 속성의 이름이나 자료형은 자리에서 못 바꿔요(ADR-0007). 새 속성을 더하고 채우고(`add_and_fill`) 옛 것을 물러나게 해요(`retire_old`). 둘은 보통 제안 둘이고, 뒤의 것에 읽는 쪽 목록이 붙어서 승인하는 사람이 봐요.
- **타입 합치기**(A를 B로): 공급과 링크 정의가 A 대신 B를 가리키게 하고, 식별 이력을 B로 옮기고, A를 `deprecated`로 해서 `superseded_by`가 B를 가리켜요. 하나의 제안이고 후보 실행으로 확인해요. 승인은 `model_steward`예요.
- **타입 올리기**(`ext` → `org`): `item_id`가 그대로여서 객체와 매핑이 안 깨져요. 깨는 변경은 아니지만 옮김의 칸으로 `keep_ids`를 적어 이력을 남겨요. 승인은 `model_steward`예요.
- 타입의 변경은 모두 정의의 변경이라 어느 클라이언트에서 만들고 고치고 지워도 브랜치와 후보 실행과 승인을 거쳐요(ADR-0007). 지우기는 어디서도 쓰이지 않을 때만이에요. 쓰이면 물러나게 하고 후속을 가리켜요.

## 12. 정의의 계보

항목 사이의 기댐을 그래프로 가지고, 컬럼과 속성 단위까지 따라가요(정제의 연산이 닫힌 목록이라 가능해요). 정의 묶음마다 하나이고 브랜치의 덧씌움 위에서도 계산해요. 자세한 노드, 간선, 읽는 쪽, "무엇이 걸리나"의 답(`depends`, `readers`, `open_proposals`, `object_count`, `unreadable`)은 [정의의 계보](definitions-lineage.md)에 있어요.

- 이 계보가 **병합의 적용 범위**를 정해요(6절). 병합이 바꾼 항목에서 `reads`, `column_from`, `maps_to`, `defines_link`를 따라가 닿는 공급과 타입만 새로 적용하고, 닿지 않는 소스는 새 묶음으로 바로 이어 가요. 검사도 계보로 닿는 것만 다시 따져요.
- **두 축.** 이 계보는 정의 쪽이에요(항목에서 항목으로). ADR-0008의 출처 따라가기는 데이터 쪽이에요(객체에서 원본 기록으로). 객체와 링크는 원본 기록의 참조와 규칙의 버전(정의 묶음)을 가지고 있어서, 값 하나에서 "어느 기록에서, 어느 규칙의 어느 판으로"를 따라가고, 거기서 이 그래프로 올라가 "그 규칙이 어디에 기대나"를 봐요.
- 제안에는 "무엇이 걸리나"가 붙고 에이전트도 읽기 전용 MCP로 물을 수 있어요(KG의 MCP는 읽기만 해요).

## 13. 내보내기와 들이기

- **내보내기.** 한 묶음(`D-N`)을 글 파일로 내보내요. 항목 하나가 파일 하나이고 정규 JSON(RFC 8785)이에요(ADR-0006). 순서와 들여쓰기가 정해져서 같은 묶음이면 같은 파일이에요. 비밀 값은 참조만 나가요.

```
manifest      묶음 번호, 묶음 해시, 항목 목록(item_id, 종류, 이름, 판의 해시)
items/<kind>/<name>   항목 파일: item_id, schema_version, body
```

- **들이기.** 언제나 새 브랜치와 제안(`origin: import`)을 만들어요. 본줄기를 덮어쓰지 않아요. manifest의 묶음 번호가 바탕이고 `item_id`로 항목을 맞춰요(파일 이름이 바뀌어도 같은 항목). 그 바탕이 이 본줄기에 없으면 본줄기의 지금 끝을 바탕으로 브랜치를 만들고(파일의 내용을 "되고 싶은 모습"으로 보고 차이를 내요) 바탕을 몰랐다고 경고해요. 그다음은 보통의 검사, 승인, 줄이에요.
- **바깥 Git은 거울이에요.** 조직이 내보낸 파일을 자기 Git에 두고 거기서 리뷰해도 돼요. 거기서 합쳐진 것은 들이기로 제안이 되고 프락시움의 검사와 승인을 다시 거쳐요. 양방향 자동 동기화는 안 해요(승인과 줄이 두 곳이 돼요).
- 내보낸 일은 감사 기록에 남아요(ADR-0012). 내보내기는 그 자리를 범위에 가진 `editor`가 자기 범위만큼 해요.

## 14. 한눈에 보이는 상태(API)

정의 쪽의 읽기와 쓰기는 쓰임의 이름으로 적어요. HTTP 길은 [REST API의 자원 목록](rest-api-resources-data.md)이 정해요. 정의(타입, 소스, 데이터셋, 공급, 브랜치, 제안)는 배포에 하나라 `/v1/...` 바로 아래이고(예: `/v1/definitions-overview`), KG에 든 것(식별의 되돌리기 등)은 `/v1/kgs/{kg}/...` 아래예요. 행위는 쌍점 하나로 적어요: `POST /v1/proposals/{id}:approve`, `POST /v1/branches/{id}:align`. 읽기는 에이전트용 MCP에도 나가요.

| 읽기 | 답 |
|---|---|
| `definitions_overview` | 본줄기(지금 `D-N`과 이어짐), KG마다 쓰는 묶음과 본줄기의 끝의 어긋남과 붙잡힌 항목, 열린 브랜치와 제안(상태, 막는 까닭, `overlaps_with`), 줄(순번과 맨 앞), 닫은 것(숨김) |
| `proposal` | 한 제안의 검사, 승인(필요한 것과 받은 것), 충돌, 정의의 차이, 후보 KG의 차이, 막는 까닭 |
| `definition_set`, `definition_diff` | 한 묶음의 항목 목록, 두 묶음 사이의 차이 |
| `definition_item` | 한 항목의 판의 이력, 어느 제안이 바꿨나 |
| `what_depends` | 계보 문서 12-4의 답 |
| `revert_preview` | 되돌리기의 결과와 걸리는 것, 함께 되돌릴 목록 |

정의의 자원은 REST 계약의 `/v1/...` 아래에 놓여요(ADR-0006). 오래 걸리는 일(후보 실행, 시험 수집, 내보내기)은 받았다고 답하고 작업 자원을 줘요. 작업의 진행은 만든 사람만이 아니라 그 작업이 속한 제안을 읽을 수 있는 사람도 봐요. 본줄기를 바로 고치는 길은 없고 모든 고치기는 브랜치 안에서 해요. 같은 항목을 동시에 고치는 것은 판의 표시로 막아요.

쓰기: `small_change_propose`(작은 변경을 제안 하나로), `branch_create`, `branch_edit`, `branch_align`(본줄기에 맞추기), `conflict_resolve`, `proposal_request_review`, `proposal_approve`, `proposal_reject`, `proposal_enqueue`, `proposal_close`, `revert_create`, `restore_create`, `trial_ingest_run`, `serving_pin`, `serving_unpin`, `definitions_export`, `definitions_import`.
모든 쓰기는 접근 제어의 판단을 한 곳에서 거쳐요. `definitions_overview`의 목적은 "한 일은 모두 기록되고 되돌릴 수 있다"가 보이게 해서 사람이 겁내지 않고 고치게 하는 거예요.

## 15. 알파의 범위

화면은 다른 저장소의 일이에요(제품 책임자의 결정). 이 저장소의 알파는 정의의 모든 기능(항목 고치기, 제안, 검사, 승인, 줄, 충돌 풀기, 되돌리기, 고정, 시험 수집, 계보, 내보내기와 들이기)이 **API와 명령줄 클라이언트로 되는 것**이에요(알파 1은 본줄기와 묶음의 한 줄을 세우고, 브랜치와 제안부터 되돌리기까지는 알파 2예요. 덧붙임의 [클베]와 [오베] 표시는 그대로예요). 화면이 필요한 보기는 API가 줘요: `definitions_overview`(한눈에), 제안의 상세, 충돌의 세 쪽 견주기, 되돌리기의 미리보기, "무엇이 걸리나". 사람에게 보일 글은 화면이 코드와 값으로 만들어요.

## 16. 알고 가는 한계

- **줄 하나의 빈도는 재지 않았어요.** 사람이 쓸 때는 잦지 않다고 보지만 못 박지 않아요(조사한 한 회사의 설정 시스템 논문은 설정이 평생 수십 번 바뀐다고 적어요. 그 회사의 규모 기준이에요). 에이전트가 쓰면 잦아서 차례 하나를 싸게 하는 것으로 줄 하나를 지키고, `merge_turn_duration_s` 같은 지표가 가리키면 묶어서 병합을 넓혀요(덧붙임 5절).
- **후보 실행은 예고지 보증이 아니에요.** 병합 뒤 실제 적용은 그사이 받은 원본 기록과 새 KG 버전 위에서 일어나서, R2부터의 첫 적용 확인이 두 번째 문으로 남아요. 이때 사람이 병합 때의 후보 차이와 지금 차이를 견줘 볼 수 있어야 해요(가정). R0, R1은 이 문 없이 사후 알림이라 안전장치와 되돌리기가 받쳐요.
- **항목이 수천 개, 수 MB**라는 규모는 재지 않은 가정이에요. 묶음마다 전체 목록을 두는 방식이 커지면 부모 대비 차이와 주기적 전체로 바꿔요.
- **되돌려도 안 돌아오는 것**이 있어요(8-2). 이미 합친 ID, 이미 물러난 객체의 지나간 모습이에요.
- 자동 병합은 열쇠가 있는 목록 넷에만 해요. 나머지 항목 안의 칸은 따로 합치지 않아요.

## 17. 아직 정하지 않은 것

- 옮김이 표준 타입과 `sys` 타입의 판을 어떤 모양으로 싣는지(항목의 `origin`과 `rev_no` 규칙)의 세부.
- 후보 실행에서 안전장치에 걸린 제안의 확인과, 적용 때 걸리는 안전장치의 확인이 같은 확인인지.
- 읽는 소스의 범위를 승인에서 어떻게 따지는지: 읽는 소스마다 그 소스의 `approver`가 승인해야 하나, 승인자가 그 소스의 범위를 보게 하는 정도인가.
- 닿는 것이 붙잡힌 동안 KG 버전의 정의 묶음 해시와 봉하기를 어떻게 적나(닿지 않는 변경은 앞 묶음의 이름으로 봉하고 판이 같아 결과가 같다고 읽었어요).
- 적용 일이 어느 KG에 걸리나(본줄기를 따라가는 KG에만인가). 후보 KG와 시험 KG가 묶음을 따로 고르는 길.
- 이 문서의 가정: 브랜치와 제안은 일대일, "고친 사람"은 브랜치에 판을 더한 모두.
