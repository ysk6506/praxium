# 정의의 버전과 브랜치

정의(타입, 소스, 데이터셋, 정제, 피드, 식별 규칙 같은 버전 관리되는 모든 구성 데이터)를 어떻게 저장하고, 수정하고, 병합하고, 리버트하고, 추적하는지의 설계예요. 코드는 아직 없어요. 필드 이름은 `core.definitions`가 사용할 이름이고, 예시의 이름은 가상의 값이에요. 제품 책임자의 지침은 네 가지예요. 파이프라인과 모델의 모든 것에 버전과 브랜치가 있다 / 큰 기술 회사들의 사례를 참고한다 / 변경은 잦지 않으니 동시 수정의 충돌 해결과 리버트가 잘 돼야 한다(변경이 잦은지는 사용 방식에 달려서 못 박지 않아요. 에이전트가 많이 사용하는 경우는 [보충 문서](definitions-at-agent-scale.md)가 다뤄요) / 데이터 계보를 관리한다.

## 1. 목적과 다루는 질문

- 정의는 어떤 단위로 버전을 매기고, KG 버전의 입력인 "정의의 버전"은 무엇인가요(ADR-0009의 결정성).
- 여러 사람이 동시에 수정해도 운영이 깨지지 않으려면 무엇을 검사하고 어떻게 순서를 정하나요. 충돌은 어떻게 보이고 누가 해결하나요.
- 잘못 병합됐을 때 어떻게 리버트하고, 리버트해도 KG에서 복원되지 않는 것은 무엇인가요.
- 수정하기 전에 무엇이 영향받는지는 어떻게 아나요(정의의 계보).
- KG가 여럿이면 정의는 누구의 것이고, 병합은 어디까지 적용되며, 확인을 기다리는 동안 무엇이 멈추나요.
- 테라리움에서 넘겨받은 것 문서의 쟁점 바(멈춰도 되는 것의 경계)와 사(경계의 파일 형식)에 걸쳐요(ADR-0014 맥락).

## 2. 개요

```
 항목 ──(내용이 바뀔 때마다)──▶ 리비전: 내용 해시를 주소로 쓰는 불변 본문
   │  "항목마다 어느 리비전인가"의 전체 목록 = 정의 세트 (내용 해시가 KG 버전 ID의 입력)
   ▼
 메인 브랜치:  D-139 ◀ D-140 ◀ D-141   배포에 하나. 단일 이력. 헤드는 행 하나(compare-and-swap으로만 옮긴다)
 　　　　　　　 ▲ 베이스
 브랜치(바뀐 항목만의 오버레이) ─▶ 제안 P-57 ─▶ 검사 ─▶ 큐 ─▶ 병합 (트랜잭션 하나)
                                  │ 승인: 범위를 가진 approver
                                  └ 차단 사유(충돌, 오래됨, 검사, 부족한 승인)는 상태가 아니라 파생 값
 병합 후: 계보로 도달하는 피드와 타입에만 "새 정의를 적용하라"는 작업이 등록된다. 도달하지 않는 소스는 새 정의 세트로 바로 이어 간다
         KG는 메인 브랜치의 어느 정의 세트를 사용하는지 가리킬 뿐이다(KG마다 하나. 메인 브랜치의 헤드와 따로 옮겨 간다)
 리버트: 언제나 앞으로 나아가는 새 제안 (D-142 = D-140과 같은 내용, 그러나 새 정의 세트)
```

- 리비전과 정의 세트는 수정하지도 삭제하지도 않아요. 잘못은 새 정의 세트로 바로잡아요.
- **정의의 메인 브랜치는 배포에 하나예요.** 운영 KG, 후보 KG, 테스트 KG, 시스템 KG는 같은 메인 브랜치를 보고 각자 어느 정의 세트를 사용하는지 가리켜요. 정의 테이블은 KG마다 있지 않아요. 시스템 KG는 `sys` 이름 공간의 항목만 사용해요(ADR-0007).
- 정의의 단일 진실 공급원은 PostgreSQL이에요(ADR-0009). 실제 Git은 단일 진실 공급원이 아니에요(13절).
- 정의 수정은 "멈춰도 되는 것"이에요(ADR-0011). 스토리지가 멈추면 수정만 못 할 뿐 KG와 질의는 그대로예요.

## 3. 데이터 구조

### 3-1. 정의 항목의 종류
| `kind` | 설명 | 소속 (access-control.md 9-1) |
|---|---|---|
| `type` | 객체·링크·액션 타입(`org`와 `ext`). 속성, 바인딩, 식별 키를 포함해요 | `ext`는 그 타입, `org`는 `model_steward` |
| `type_overlay` | 제품 표준(`std`) 타입의 오버레이: 속성 추가, 바인딩 추가, 표시 이름, 숨기기 | `org`처럼 `model_steward` |
| `source` | 소스 설정(어댑터, 프리셋의 이름과 버전, 시크릿 참조) | 그 소스 |
| `dataset`, `refinement` | 소스 안의 테이블 하나 / 고정된 연산 목록으로 데이터셋을 다듬는 정제 | 소속 소스 |
| `feed` | 피드: 데이터셋 하나에서 객체 타입 하나로의 매핑(완전성 선언 `completeness_declaration` 포함) | 소스와 타입 둘 (5절) |
| `identity_rule`, `exception_list` | 타입별 식별 키의 우선순위와 우선하는 소스의 순서 / 식별의 예외와 원본 레코드 제외 | 그 객체 타입 |
| `link_definition` | 링크를 생성하는 조건. 파생 링크와 그룹 생성 포함 | 출발 타입 |
| `expectation`, `schedule` | 기대 조건(ADR-0008) / 소스와 데이터셋의 일정, 수집 방식 | 소속 소스 |
| `competency_question` | 역량 질문(ADR-0015): 대상, 필요한 항목의 패턴, 목표 충족률 | 대상 객체 타입 |
| `objective` | 목표(ADR-0013) | 연결된 자원(소스나 객체 타입) |
| `alert_rule`, `guard_values` | 알림 규칙(ADR-0013) / 안전장치 값(임계값, 횟수) | 알림 규칙은 연결된 자원(소스나 객체 타입), 안전장치 값은 소스. 완화는 `admin` |

모든 항목에는 **소속**이 있어요. 수정하려면 그 소속을 범위에 가진 `editor`가, 승인하려면 그 소속을 범위에 가진 `approver`가 필요해요. 제품 표준(`std`) 타입과 시스템 KG의 `sys` 타입도 리비전이 있는 항목이고, 제품 버전이 그 리비전을 정해요. 제품은 이것들을 스키마 마이그레이션의 한 단계로 스토리지에 적재하고, 실행 파일은 스토리지의 것을 읽어요(실행 파일에 포함된 사본이 아니에요). 그래서 배포하는 중에 워커 인스턴스마다 메인 브랜치의 해시가 달라지지 않아요. 값 타입, 링크 의미, 특성, 채널, 프리셋 데이터는 제품에 포함된 것이라 항목이 아니에요. 담당자(연락처)는 각 항목의 필드 하나이고 이를 바꾸는 것은 정의의 변경이에요. 시크릿은 참조만 저장해요.

### 3-2. 컬럼
정의 테이블에는 `kg_id`가 없어요. 메인 브랜치가 배포에 하나이기 때문이에요(ADR-0014). `kg_id`는 KG 측 컬럼(KG마다 사용하는 정의 세트를 가리키는 `applied_set_no`)에만 있어요(kg-storage.md). 해시는 정규 바이너리 인코딩 위의 SHA-256이에요(ADR-0006).

| 테이블 | 컬럼 | 설명 |
|---|---|---|
| `definition_item` | `item_id`, `kind`, `name`, `namespace`(`org`/`ext`/`sys`/오버레이이면 `std`), `contacts` | `item_id`는 바뀌지 않고 이름이 바뀌어도 유지돼요. 사용한 `item_id`는 재사용하지 않아요 |
| `definition_blob` | `content_hash`, `kind`, `schema_version`, `body` | 내용 주소 방식으로 저장한 본문. 같은 내용은 한 번만 저장돼요 |
| `item_revision` | `item_id`, `rev_no`, `content_hash`, `first_set_no` | 항목의 리비전. 사용자에게는 `리비전 7`. 내용이 이전 리비전과 같아도(리버트) `rev_no`는 새로 올라가요 |
| `definition_set` | `set_no`, `content_hash`, `parent_set_no`, `origin`, `proposal_id`, `created_at` | 정의 세트 `D-142`. `content_hash` = 정렬한 (`item_id`, 리비전의 `content_hash`) 목록의 해시. 부모는 포함하지 않아서, 리버트로 같은 내용이 되면 해시가 같아요 |
| `set_entry` | `set_no`, `item_id`, `content_hash` | 정의 세트의 전체 항목 목록. 항목이 수천 개면 세트마다 전체를 저장해도 감당된다고 봐요(가정, 측정해서 정해요) |
| `trunk_head` | `set_no`, `head_rev` | 메인 브랜치의 헤드. 행 하나 |
| `branch` | `branch_id`, `name`, `base_set_no`, `state`(`open`/`merged`/`closed`), `origin`, `content_hash`, `created_by` | `content_hash`는 오버레이의 내용 해시예요 |
| `branch_entry` | `branch_id`, `item_id`, `op`(`add`/`modify`/`remove`), `content_hash`, `base_content_hash` | 바뀐 항목만 있어요. `base_content_hash`는 베이스 정의 세트에서의 그 항목 |
| `proposal` | `proposal_id`(`P-57`), `branch_id`, `title`, `summary`, `state`, `origin`, `reverts_proposal_id`, `close_reason`, `superseded_by`, `queue_seq`, `merged_set_no`, `emergency`, `post_review_state` | 정식 객체예요 |
| 브랜치와 제안 둘 다(작성자) | `authored_by`(주체), `actor_kind`(`person`/`system_account`), `on_behalf_of`(위임한 사람), `agent_run_id`, `agent_build` | 5절과 보충 문서 1절 |
| `proposal`(변경 이유) | `trigger_ref`, `evidence`, `intent`, `decision_log_hash`, `after`(클로즈드 베타) | 컬럼 자체는 알파에 포함 |

- `origin`: `change`(일반), `revert`, `restore`, `import`, `bootstrap`(첫 정의 세트).
- 위험 등급(R0~R3)은 후보 차이에서 계산하는 파생 값이라 컬럼이 아니에요(보충 문서 6절).
- 브랜치와 제안은 일대일이고 브랜치를 열면 제안이 `draft`로 함께 생겨요(가정). **작은 변경은 "제안 하나"로 서버가 한 번에 만들어요**(`small_change_propose`: 브랜치 열기, 항목 고치기, 검토 요청까지). 화면 전용 방법이 아니라 공개된 기능이고 클라이언트의 책임으로만 두지 않아요(ADR-0007).
- 사용자에게 보이는 번호: 정의 세트 `D-142`(옆에 해시 앞 8자), 제안 `P-57`, 항목의 `리비전 7`. KG 버전의 응답에는 사용된 `D-142`가 포함돼요(`kg_version.definition_set_hash`, `versions` 응답의 `definition_version`).
- 표준 모델의 버전은 정의 세트에 포함돼요(`std` 타입의 리비전이 제품 버전을 따라 바뀌어 정의 세트 해시에 반영돼요). 실행기의 의미 버전은 정의 세트 밖의 입력이에요. 둘이 올라간 뒤의 첫 적용도 6절의 첫 적용 규칙을 따라요(ADR-0008).
- 메인 브랜치의 헤드(병합된 정의 세트)와 **KG가 현재 사용하는 정의 세트**(`kg_version.definition_set_hash`, KG마다)는 다를 수 있어요(6절).

### 3-3. 목록 항목
항목 종류가 "키가 있는 목록"이라고 선언한 곳은 키로 매칭해 병합해요(7-2). 지금은 네 가지예요.

| 항목 | 목록 | 키 |
|---|---|---|
| `exception_list` | 행 | (예외의 종류, 대상) |
| `type`, `type_overlay` | 속성 목록, 바인딩 목록 | 속성이나 바인딩의 `id` |
| `guard_values` | 값 | 값의 이름 |

그 밖의 항목은 통째로 하나로 봐요. 항목 안의 필드 단위 자동 병합은 하지 않아요.

## 4. 제안의 진행 절차

### 4-1. 상태
```
draft ─검토 요청─▶ in_review ─필요한 승인이 모두 있음─▶ approved ─큐에 넣음─▶ queued ─병합─▶ merged
  ▲                  │                                      │ ▲                 │
  └──── 내용을 수정하면(승인과 검사 결과가 무효가 된다) ───────┴─┘                 └ 큐 맨 앞에서 실패하면 approved로 돌아가 차단 사유가 붙어요
 어느 상태에서나(merged 빼고) ─▶ closed (`close_reason`: abandoned, rejected, superseded)
```

| 전이 | 조건 |
|---|---|
| `draft` → `in_review` | 항목별 유효성 검사가 통과해야 해요(가정). 담당자에게 검토 요청이 가요 |
| `in_review` → `approved` | 5절의 필요한 승인이 현재 `content_hash`에 모두 있어요 |
| `approved` → `queued` | `editor`가 큐에 넣어요. 차단 사유가 없어야 해요 |
| `queued` → `merged` | 6절의 병합이 끝났어요. 최종 상태예요 |
| 아무 때나 → `closed` | 작성자나 `admin`이 닫아요. 삭제하지 않고 목록에서 숨기며 다시 열지 않아요(같은 브랜치로 새 제안을 만들어요). 대체되면 `superseded_by`가 새 제안을 가리켜요 |

내용을 수정하면 `draft`로 돌아가고 승인은 무효가 돼요. 병합된 제안과 정의 세트는 수정할 수 없어요.

### 4-2. 차단 사유
상태가 아니라 현재 값에서 파생해요. 하나라도 있으면 큐에 넣을 수 없거나 병합이 안 돼요.

| `blocker` | 설명 | 상세 |
|---|---|---|
| `conflicts` | 해결되지 않은 충돌이 있어요 | 항목, 종류(7절) |
| `stale` | 베이스가 메인 브랜치의 헤드가 아니에요 | 뒤처진 정도, "메인 브랜치 최신화"를 권해요 |
| `check_failed` / `check_pending` | 검사가 실패했거나 아직 실행되지 않았어요 | 어느 검사, 어느 항목, 이유 |
| `approvals_missing` | 필요한 승인이 부족해요 | 어느 항목에 어느 범위의 승인이 없는지. 거부가 있으면 그것도 표시해요 |
| `guard_stopped` | 드라이 런에서 안전장치가 작동했어요 | 소속을 범위에 가진 `operator`의 확인이 필요해요. 확인은 브랜치의 내용 해시에 연결돼서 내용이 바뀌면 다시 해야 해요. 값을 수정할 필요는 없어요 |
| `objective_missed` | 제안 때문에 달성하던 목표 충족률을 달성하지 못해요(`competency_objective_missed`) | 어느 역량 질문인지, 전과 후, 새로 충족하지 못한 객체 |

### 4-3. 검사
검사는 브랜치의 내용 해시에 연결돼요. 내용이 바뀌면 오래된 결과가 되어 다시 실행해야 해요. 편집 중에 실행하는 검사와 큐 맨 앞에서 병합한 결과로 다시 실행하는 검사가 있어요.

| `check_kind` | 검사 대상 |
|---|---|
| `item_valid` | 바뀐 항목마다: 스키마, 이름 규칙, 정제 연산이 고정 목록 안인지, 값의 범위, 시크릿이 참조뿐인지 |
| `merged_valid` | 병합 결과의 유효성. 참조 대상 존재, 순환, 타입 일치, 지원 중단 항목 사용, 식별 키 변경(7-3). 호환성을 깨는 변경에 마이그레이션이 있는지(11절). 삭제하는 타입이 사용 중이 아닌지 |
| `item_tests` | 정의의 테스트(10절) |
| `candidate_run` | 수집해 둔 원본 레코드로 만든 후보 KG와 현재 버전의 차이. 정의의 차이와 KG의 차이를 함께 보여요 |
| `guard` | 같은 안전장치(ADR-0008)를 후보에 적용해요 |
| `competency` | 역량 질문의 충족률 변화(질문마다 전과 후, 새로 충족하지 못한 객체). 목표를 달성하던 질문이 달성하지 못하게 되면 실패예요. 이미 목표 미달인 질문은 차단하지 않고 보여 줘요 |

- 결과 필드: `proposal_id`, `check_kind`, `subject_hash`(검사한 내용 해시와 적용 대상 정의 세트의 해시), `inputs_digest`(드라이 런에서: 원본 레코드의 배치, 이전 KG 버전, 실행기의 의미 버전), `status`(`pending`/`passed`/`failed`/`needs_confirmation`), `detail`.
- 드라이 런은 소스에 다시 접속하지 않아요. 결정성(ADR-0009) 덕에 `subject_hash`와 `inputs_digest`가 같으면 결과를 재사용할 수 있어요.

## 5. 범위 기반 승인

규칙은 access-control.md 9절이 정해요. 여기서는 제안의 진행 절차에서 어떻게 적용되는지만 적어요.

- 제안이 수정한 항목마다 **소속**이 있고, 그 소속을 범위에 가진 `approver`(작성자는 제외)의 승인이 있어야 해요. 수정하는 쪽도 해당 소속을 범위에 가진 `editor`예요. 작성자는 이 브랜치에 리비전을 추가한 모든 사람(가정)이고, **같은 주체이거나 같은 `on_behalf_of`이면 승인할 수 없어요.** 승인은 사람만 해요(서비스 계정은 승인자가 될 수 없어요. ADR-0012).
- **`on_behalf_of`는 스스로 지정할 수 없어요.** `admin`이 그 서비스 계정에 연결해 둔 사람 가운데서만 골라요(access-control.md). 계정이 임의로 다른 사람을 지정하면 "같은 위임자" 판정이 의미가 없어지기 때문이에요.
- **`solo_approval`.** 처음 구축할 때와 혼자 사용하는 테스트 배포를 위한 공개 설정 하나예요. 활성화하면 자기가 수정한 것을 자기가 승인할 수 있어요. 기본은 비활성이고, 활성화하면 모든 승인의 감사 로그에 표시가 남고 헬스 상태에 경고가 표시돼요. 이 설정이 없으면 혼자 테스트하는 사람은 첫 정의를 병합할 수 없어요(`admin`도 같은 규칙을 따르기 때문이에요).
- **입력 소스.** 정제 데이터셋과 링크 정의는 다른 소스의 데이터셋을 입력으로 읽을 수 있어요. 입력 소스는 **작성자의 범위 안**이어야 해요(`item_valid`가 차단하고 `:preview`도 같아요). 승인은 소속과 함께 **입력 소스의 범위도 확인해요**(확인 방법은 17절). 원본을 보는 경로(미리 보기, 샘플, 통계)는 그 데이터셋에 연결된 피드의 대상 타입의 읽기 권한도 요구하고 감사 로그에 남아요.
- **피드**는 소스의 `editor`가 수정해요. 그 피드가 객체를 생성하거나 폐기 처리하거나 식별 키를 매핑하면 대상 타입을 범위에 가진 `approver`의 승인도 필요해요. 그렇지 않으면 타입의 담당자에게 알림만 가요.
- 검사가 "이 제안 때문에 깨진다"고 판정한 항목도 수정한 항목처럼 그 소속의 승인을 받아요. 참조만 하는 항목의 담당자에게는 알림만 가요. 드라이 런에서 객체가 바뀌는 타입의 `approver`도 승인해요.
- `org` 타입과 오버레이는 `model_steward`(층으로 범위를 좁힐 수 있어요), 안전장치를 완화하는 것과 민감 등급을 낮추는 것은 `admin`이 승인해요. 강화하는 것은 소속을 범위에 가진 `approver`가 승인해요. KG 결과에 차이가 없어도 위험한 항목(소스의 `endpoints`, 마스킹 규칙, 알림과 목표 완화, 담당자, 기대 조건의 `fail`→`warn`, 시크릿이 접속하는 주소)은 등급이 R3예요(보충 문서 6절).
- 승인은 `content_hash`에 연결돼요(`proposal_approval`: `proposal_id`, `approver`, `decision`, `content_hash`, `covers_item_ids`, `matched_grants`). 내용이 바뀌면 승인도 거부도 무효예요.

| 예(가상) | 필요한 승인 |
|---|---|
| `u-hansol`(`editor`, 소스 `rack_sheet`)이 `Rack` 객체를 생성하는 피드 `rack_sheet_to_rack`을 수정(`P-31`) | 소스 `rack_sheet`와 대상 타입 `Rack`을 범위에 가진 `approver`. 한 사람이 둘 다 가지면(`u-narae`) 한 번이에요. `Rack`을 가진 사람이 없으면 다른 `approver`가 더 필요해요. `u-hansol`이 `approver`를 겸해도 승인할 수 없어요 |
| 링크 정의 `server_in_rack`(입력 소스는 `server_list`, `rack_sheet`, 출발 타입은 `PhysicalServer`)의 조건을 수정(`P-32`) | 소속은 출발 타입이에요. `PhysicalServer`를 범위에 가진 `approver`가 승인하고, 입력 소스 둘의 범위도 확인해요(17절). 입력 소스만 가진 사람은 승인할 수 없어요. 작성자는 두 소스를 범위에 가져야 해요. 해당 범위를 가진 사람이 없으면 차단되고 `admin`이 권한을 부여해 해결해요 |
| 조직 표준 타입 `Rack`에 속성 `max_power_kw`를 추가(`P-33`) | `model_steward`의 승인. 속성 추가는 호환되는 변경이라 마이그레이션이 필요 없고, 그 타입에 피드를 연결한 항목의 담당자에게 알림이 가요 |

**승인이 무효가 되는 경우.** 내용 해시가 바뀔 때예요. "메인 브랜치 최신화"만으로는 오버레이의 내용이 바뀌지 않으니 승인이 유지돼요. 다만 병합 결과에서 새로 깨지거나 새로 바뀌는 항목이 생겨 필요한 범위가 늘면 `approvals_missing`이 다시 활성화돼요(필요한 승인은 병합 결과로 계산해요). 충돌을 수동으로 해결하면 내용이 바뀌므로 무효예요.

**안전장치를 완화할 때.** `guard_values`의 값이 완화되는 방향이면(임계값을 올리거나 횟수를 늘림) 제안의 필요한 승인에 `admin`이 포함돼요. 어느 쪽이 완화인지는 값마다 제품이 정해 둬요. 한 제안에 강화와 완화가 섞여 있으면(하나는 강화하고 하나는 완화) `admin`의 승인이 필요해요.

## 6. 병합 큐와 적용

큐는 하나예요. 메인 브랜치가 배포에 하나라 병합 잠금도 하나예요. 사람이 사용할 때는 변경이 잦지 않아 한 번에 하나씩 처리해도 충분하다고 보지만 못 박지는 않아요. 에이전트가 사용하면 변경이 잦아서, 무거운 작업을 큐 밖에서 미리 하고 병합 턴 하나의 비용을 낮춰요(보충 문서 5절). 직렬화는 비용이 아니라 단순함을 위한 선택이에요. 각각은 정상인 두 제안이 합쳐서 깨지는 일을 막아요.

**큐 맨 앞에서 하는 일(병합 턴).** 병합 잠금 하나를 획득하고 진행해요.

1. 큐 맨 앞의 `queued` 제안을 가져와요. 메인 브랜치의 현재 헤드(`set_no`, `head_rev`)를 읽어요.
2. 그 헤드 위에 오버레이를 적용해 병합한 정의 세트를 만들어요(3-way 비교, 7절). 충돌이면 큐에서 제외되고 `approved`로 돌아가 `conflicts`가 붙어요.
3. 병합 결과로 검사를 다시 실행해요: `item_valid`, `merged_valid`, `item_tests`. 필요한 승인을 병합 결과로 다시 계산해서 `content_hash`에 승인이 있는지 확인해요.
4. 드라이 런과 안전장치는 **큐 밖에서 미리 실행한 결과**를 (브랜치 내용 해시, 메인 브랜치 헤드 해시, 기준 KG 버전) 키로 재사용해요. 기준 KG 버전은 현재 서빙하는 KG 버전이에요. 병합 턴에서는 메인 브랜치 헤드가 그대로인지만 확인하고, 움직였으면 계보(12절)로 도달하는 항목만 다시 평가해요. 키가 일치하는 결과가 없을 때만 그 시점에 실행해요.
5. 모두 통과하면 **트랜잭션 하나**로 반영해요: `definition_set`과 `set_entry`와 `item_revision` 기록, `trunk_head`를 `head_rev`가 기대한 값일 때만 변경하기(compare-and-swap), 제안을 `merged`로 변경, 감사 로그. 여러 항목과 여러 범위의 변경이 한꺼번에 반영되고 일부만 반영된 병합은 없어요.
6. compare-and-swap이 실패하면(그사이 헤드가 옮겨졌어요) 1로 돌아가요. 큐가 하나라 드물게 일어나요.

**병합과 KG 적용은 별개예요.** 메인 브랜치의 헤드(병합된 정의 세트)와 KG가 현재 사용하는 정의 세트는 다를 수 있어요. 병합은 정의를 한꺼번에 반영하고 `definition_merged` 이벤트와 함께 "새 정의를 적용하라"는 작업을 등록해요. **적용은 계보(12절)로 도달하는 피드와 객체 타입에만 해요.** 병합이 바꾼 항목에서 계보를 따라가면 도달하는 (피드, 타입)이 나와요. 워커는 드라이 런의 결과를 바탕으로 적용하고(그사이 들어온 변경은 새 정의로 다시 평가해요), 적용이 끝나면 KG 버전을 확정하고(`seal_kind`: `merge`, ADR-0009) KG가 사용하는 정의 세트가 옮겨 가요.

- **도달하지 않는 소스는 멈추지 않아요.** 그 소스의 스트림과 배치는 병합이 확정된 `change_seq`부터 새 정의 세트로 바로 이어 가요(`stream`이면 그 이전은 이전 정의가 담당하고 다시 처리하지 않아요). 도달하지 않는 항목은 두 정의 세트에서 리비전이 같아서 결과도 같아요. 스트림에서 정의를 수정하는 경우도 브랜치와 드라이 런을 거쳐요.
- **첫 적용의 사람 확인은 R2부터예요**(ADR-0008). 후보 차이에서 계산한 등급이 R0, R1이면 자동으로 적용하고 사후에 알려요(알파부터). R2, R3이면 사람이 차이를 확인해요. 승인 없이 병합하는 **자동 병합**은 이것과 달라서 클로즈드 베타이고 기본은 비활성이에요(보충 문서 6절).
- 확인을 기다리는 동안 멈추는 것은 **도달하는 피드와 타입뿐**이에요.

| 확인을 기다리는 동안 | 멈춤 또는 실행 |
|---|---|
| 도달하지 않는 소스의 스트림과 배치 | 실행돼요. 새 정의 세트로 바로 이어 가요 |
| 도달하는 피드와 타입의 수집 | 실행돼요. 수집해서 원본 레코드에 쌓기만 하고 적용을 미뤄요(보류해도 수집은 멈추지 않아요) |
| 도달하는 피드와 타입의 적용 | 멈춰요. 확인되면 한도가 있는 배치로 나눠 적용해요 |
| 도달하는 타입의 현재 객체와 링크 | 이전 정의 세트의 결과 그대로 읽혀요 |
| 질의, 변경 알림, 프로젝션 | 실행돼요 |
| 병합 큐 | 실행돼요(가정) |
| 사람의 확인 | R2, R3만 기다려요. R0, R1은 기다리지 않아요 |

- 적용 중 안전장치가 작동해도 같아요. 멈추는 것은 도달하는 항목뿐이고 문제 목록과 알림이 생성돼요. 불일치(KG마다 `applied_set_no`와 `head_set_no`, 보류된 항목)는 `definitions_overview`에 표시돼요.
- **병합의 결과도 일반 변경 배치로 프로젝션에 전달돼요.** 프로젝션을 통째로 다시 구축하는 것은 차이가 임계값을 넘을 때만이에요(임계값은 [기본값 표](defaults.md)에 가정으로 둬요). 병합마다 통째로 구축하지 않아서 에이전트가 하루에 여러 건을 병합해도 감당돼요.
- 정의 세트의 해시가 새 KG 버전 ID의 입력이 돼요. 이전 버전, 원본 레코드, 정의 세트, 실행기의 의미 버전이 같으면 같은 KG 버전이에요.

## 7. 충돌

### 7-1. 충돌 네 종류와 해결 담당
| 종류 | 가상의 예 | 표시 방식과 해결 담당 |
|---|---|---|
| 같은 항목을 둘이 수정 | `P-31`과 `P-35`가 같은 피드 `rack_sheet_to_rack`의 컬럼 매핑을 서로 다르게 수정 | 3-way 비교. **나중에 병합하는 제안**(먼저 병합된 제안이 메인 브랜치가 되므로 베이스가 오래된 쪽)의 `editor`가 선택해요 |
| 목록 항목의 다른 행을 수정 | 예외 목록에 한쪽은 서버 쌍 X를 "같다", 다른 쪽은 쌍 Y를 "다르다"로 추가 | 키가 다르니 자동으로 병합해요. 같은 키면 위의 충돌이에요 |
| 의미 충돌(항목은 다름) | 한쪽이 데이터셋의 컬럼 `hostname`을 `host_name`으로 바꾸고, 다른 쪽이 옛 이름으로 피드를 추가 | 병합 결과의 검사가 감지해요. 무엇이 무엇을 깨는지 표시되고 나중에 병합하는 제안이 수정해요 |
| 결과 충돌 | 각각은 맞는데 병합하면 후보 KG에서 서버 객체가 대량으로 사라짐 | 드라이 런의 차이와 안전장치가 감지해요. `operator`가 확인하거나 정의를 수정해요 |

### 7-2. 같은 항목: 3-way 비교와 자동 병합
항목마다 세 가지를 비교해요. **베이스**(브랜치를 만든 시점의 정의 세트에 있는 리비전), **메인 브랜치**(현재 헤드의 리비전), **내 변경**(오버레이의 리비전).

| 베이스 / 메인 브랜치 / 내 변경 | 결과 |
|---|---|
| 메인 브랜치 = 베이스 | 내 변경을 채택해요 |
| 내 변경 = 베이스 | 메인 브랜치를 채택해요 |
| 메인 브랜치 = 내 변경 | 같은 변경이라 충돌이 아니에요 |
| 셋이 모두 다름 | 충돌 `same_item`. 한쪽이 삭제하고 한쪽이 수정했으면 `remove_vs_modify` |
| 목록 항목(3-3) | 키마다 위 표를 따로 적용. 같은 키만 `keyed_entry` 충돌 |

충돌은 즉시 차단하지 않고 **상태로 남아요**(`branch_conflict`: `branch_id`, `item_id`, `conflict_kind`, `base_content_hash`, `trunk_content_hash`, `mine_content_hash`, `status`, `resolution`, `resolved_content_hash`, `resolved_by`). 해결 방법은 세 가지예요: 메인 브랜치 것 / 내 변경 / 수동으로 병합한 새 리비전. 수동 병합은 일반 편집이라 다시 검사하고 승인도 새로 받아요. 자동으로 병합한 결과도 검사와 드라이 런을 거쳐요.

### 7-3. 의미 충돌을 감지하는 검사
항목 병합은 겹치는지만 확인하고 의미는 알지 못해요. 병합 결과를 아래 항목으로 검사해요(`merged_valid`). 컬럼 단위의 계보(12절)가 있어서 "이 데이터셋의 출력 컬럼"을 계산할 수 있어요.

| 검사 | 차단 대상 | 표시 메시지 |
|---|---|---|
| 참조 대상 존재 | 피드가 참조하는 컬럼, 데이터셋, 타입, 속성이 병합 결과에 없어요 | "`rack_sheet_to_rack`이 컬럼 `hostname`을 쓰는데 `P-35`가 이름을 바꿨어요" |
| 순환 | 링크 정의가 서로를 참조하거나, 데이터셋이 서로를 읽어요 | 순환 경로 전체 |
| 타입 일치 | 매핑한 컬럼의 자료형과 속성의 자료형이 일치하지 않아요. 값 타입도 마찬가지예요 | 컬럼과 속성과 두 자료형 |
| 지원 중단 항목 사용 | 지원 중단된 타입(`deprecated`)에 새 피드를 연결해요. 운영 중의 `retired_type_in_use` 문제와 달리 병합에서는 차단해요 | 지원 중단된 타입과 `superseded_by` |
| 식별 키 변경 | 한쪽이 식별 키를 바꿨는데 다른 쪽이 옛 키로 피드를 추가해요. 한 속성에 우선하는 소스가 둘로 정해져요 | 키와 피드 |

항목의 담당자가 다르면 메시지에 양쪽 항목과 담당자를 표시하고 양쪽에 알려요. 합의가 안 되면 `admin`이 권한이나 담당자를 정리해서 해결해요.

### 7-4. 오래된 브랜치
베이스가 메인 브랜치의 헤드가 아니면 `stale`이에요. "메인 브랜치 최신화"는 새 헤드를 베이스로 항목마다 3-way 비교를 다시 해요. 오버레이라 가볍고, 충돌이 없으면 자동으로 처리되고, 있으면 브랜치 안에 `conflicts`로 남아요. 나중에 해결해도 돼요. 충돌이 있는 제안은 큐에 넣지 못할 뿐 편집과 검토는 계속돼요. 편집 중에는 같은 항목을 수정하는 다른 열린 브랜치가 목록에 표시돼서(`overlaps_with`) 충돌을 일찍 알 수 있어요.

## 8. 리버트

원칙: **삭제하거나 롤백하지 않아요. 언제나 앞으로 나아가는 새 제안이에요.** 리버트할 제안은 `merged`여야 하고, 결과가 현재와 같으면(`content_hash`가 같으면) "할 일 없음"이에요.

### 8-1. 여섯 가지 방식
항목마다 리버트할 리비전을 정해요. 현재 메인 브랜치의 리비전이 그 제안이 만든 리비전과 **같으면** 이전 리비전으로 되돌리고(추가였으면 제거하고, 삭제였으면 복원해요), **다르면** 이후 변경이 같은 항목을 수정한 것이라 충돌이에요. 3-way 비교와 같은 메커니즘이에요(베이스 = 그 제안의 결과, 메인 브랜치 = 현재 헤드, 내 변경 = 그 제안 이전의 상태).

| # | 동작 | 생성되는 것 | 거치는 절차 |
|---|---|---|---|
| 1 | 병합된 제안 리버트 | `origin: revert`인 새 브랜치와 제안(`reverts_proposal_id`) | 일반 검사, 승인, 큐 |
| 2 | 이후 변경이 영향받을 때 | 같은 항목이면 충돌. 이후 변경이 리버트 대상을 **참조하면** `merged_valid`가 실패해서 차단돼요 | 영향받는 항목(어느 제안의 어느 항목, 담당자)이 표시돼요. 함께 리버트할 대상을 **미리보기로 제안**해요. 연쇄적으로 자동 리버트하지 않아요 |
| 3 | 일부만 | 제안이 바꾼 항목 가운데 선택한 것만 포함한 `revert` 제안 | 1과 같아요. 선택한 항목들이 서로를 참조하면 검사가 차단해요 |
| 4 | 정의 세트 `D-N`으로 복원 | `origin: restore`. 선택한 범위(소스, 객체 타입, 항목 목록)의 항목을 `D-N`의 리비전으로 | 미리보기에 "`D-N` 이후에 병합된 어느 제안의 어느 항목이 사라지는지"가 표시돼요. 범위를 넘는 항목의 승인은 일반 규칙을 따라요 |
| 5 | 리버트를 리버트 | 그냥 1이에요. 따로 만들 것이 없어요 | 그사이 항목이 또 바뀌었으면 같은 충돌 규칙. 리버트된 제안의 내용을 다시 병합해도 변경이 반영되지 않는 문제가 없어야 하고 테스트로 검증해요 |
| 6 | 긴급 상황 | 방금 병합된 제안을 리버트하는 1에 `emergency: true`. "방금"은 병합된 지 정해진 기간(기본값(설정) 7일. 사후 검토의 기한은 3일) 안이고 이후의 제안이 그것에 의존하지 않을 때예요 | `admin`, 또는 그 제안이 수정한 소속 전부를 범위에 가진 `approver`가 승인 없이 요청할 수 있어요(`operator`는 할 수 없어요. 정의의 변경이에요). 검사와 큐는 그대로 거쳐요. 드라이 런과 안전장치도 마찬가지예요. 감사 로그에 `admin_override`로 따로 남고 `post_review_state: pending`이 붙어, 다른 `approver`나 `admin`의 사후 검토를 기한 안에 받아요. 기간과 기한의 기본값은 설정이고 측정하지 않은 가정이에요 |

기한이 지나도록 사후 검토가 없으면 알림이 계속 가요(ADR-0013). 긴급 리버트도 큐를 그대로 거쳐요.

### 8-2. KG와의 경계
정의를 리버트해도 KG는 롤백되지 않아요. 새 정의로 새 KG 버전이 생겨요.

- 리버트한 정의로 다시 실행한 KG는 이전의 KG와 같지 않을 수 있어요. 그사이 원본 레코드가 바뀌었고 식별 이력도 진실의 일부이기 때문이에요. API가 코드와 값으로 반환한 경고를 클라이언트가 "정의를 `D-140`과 같은 내용으로 리버트했지만 KG는 그 시점으로 돌아가지 않아요. 현재의 원본으로 `D-140`의 정의를 실행한 새 버전이 만들어져요"라고 안내해요.
- **이미 병합된 ID는 식별 규칙을 리버트해도 자동으로 분리되지 않아요.** 분리하려면 예외 목록으로 분리해야 하고, 이것도 제안이에요. 분리하면 남은 쪽은 ID를 그대로 유지하고 흡수됐던 쪽은 옛 ID로 복원돼요(식별 이력이 옛 ID를 보존해요).
- **병합마다 "이 병합을 리버트"가 있어요**(`POST /v1/kgs/{kg}/identity-events/{id}:revert`). 식별 이력은 롤백하지 않아요(그대로 유지). 그 불편은 제품이 감당해요. 누르면 제품이 그 둘을 분리하는 예외를 담은 제안을 만들어 줘요. 드라이 런으로 확인하고 승인을 거쳐요. 식별 규칙을 리버트하는 제안의 드라이 런은 "이 규칙으로 병합됐던 것들"의 목록을 보여 주고, 한꺼번에 분리하는 예외를 함께 제안해요. 사람이 예외 목록을 직접 작성하지 않아요(ADR-0014).
- **폐기 처리됐던 객체가 옛 ID로 복원되는 것은 강한 키로 일치했거나 정해진 기간 안일 때만이에요.** 정의 때문에 사라졌다가 돌아온 객체는 ID가 새로 발급되지 않아요. 약한 키(이름, 주소처럼 다른 장비에 재사용되는 것)로 기간이 지나서 다시 나타나면 새 ID를 부여하고 식별 후보로 등록해요.
- **병합될 때 흡수된 쪽의 링크**는 `identity_event`에 옛 링크 ID와 새 링크 ID의 대응 관계를 남겨요. 변경 알림과 충족률은 이를 "삭제와 추가"가 아니라 대응 관계로 처리해요.
- **질의를 옛 KG 버전에 고정하기.** 잘못된 데이터가 들어왔을 때 전체 범위의 `operator`나 `admin`이 "질의는 버전 V로 응답하라"고 고정할 수 있어요. 데이터를 롤백하지 않고 읽기 측만 고정해요. 필드는 `serving_pin`: `kg_version_id`, `reason`, `pinned_by`, `pinned_at`, `released_at`. 모든 응답에 고정됐다는 표시가 붙어요. 고정하면 질의 엔진이 그 버전을 로드하고, 로드가 끝날 때까지 고정은 `pending`이라 현재 버전으로 응답하며 그렇게 표시해요. 고정된 버전의 이력은 보존 기한이 지나도 삭제하지 않아요. 고정은 쓰기라 스토리지가 정상이어야 해요.

### 8-3. 가상의 인시던트를 끝까지 따라가기
`PhysicalServer`의 식별 키는 `asset_tag`(1순위), `serial_number`(2순위)였어요. `rack_sheet`의 서버 두 대(`srv-a`는 일련번호 `SN-001`, `srv-b`는 `SN-002`)가 둘 다 자산 번호가 비어 있고 임시 관리 주소 `192.0.2.9`로 적혀 있어요.

1. 제안 `P-41`이 식별 키에 3순위 `management_ip`를 추가했어요. 식별 키 변경은 호환성을 깨는 변경이라 마이그레이션을 작성했어요(식별 이력: 옛 ID는 그대로 유지하고, 새 키는 식별에만 사용해요). 후보 차이는 "식별 병합 2건, 객체 -2"였고 임계값(10%이면서 5건 이상)에 못 미쳐 안전장치를 통과했어요. 첫 적용 확인자는 "중복 정리"로 해석하고 확인했으며 `D-141`이 병합돼 KG 버전 `V-88`이 생성됐어요.
2. 발견. 문제 목록에 "서로 다른 일련번호 두 개" 충돌(속성 충돌)이 서버 한 대에 등록됐고 `quality`의 중복 지표가 변했어요. 타임라인에서 `D-141` 병합 직후예요.
3. 전체 범위의 `operator`가 질의를 `V-87`(병합 전)에 고정했어요. 이제 응답은 병합 전 상태이고 "고정됨"이 붙어요.
4. `admin`이 긴급 리버트를 요청했어요(사후 검토는 다른 `approver`나 `admin`이 해요). `P-41`의 항목 `identity_rule`을 리비전 2로 되돌리는 `P-44`(`emergency`)예요. 영향받는 항목이 없어서 검사를 통과하고 큐를 거쳐 `D-142`로 병합됐어요. `D-142`의 해시는 `D-140`과 같아요. 사후 검토가 `pending`으로 붙었어요.
5. 그래도 KG에서는 두 서버가 병합된 채예요. 식별 이력이 롤백되지 않기 때문이에요. `P-45`가 예외 목록에 "`SN-001`과 `SN-002`는 다르다"를 추가했어요. 드라이 런의 차이에서 `srv-b`가 옛 ID로 복원되는 것을 확인하고 승인을 받아 병합했어요.
6. `V-89`가 확정됐고, `operator`가 고정을 해제했어요. 마지막으로 `identity_rule` 항목에 "같은 임시 주소를 사용하는 서로 다른 일련번호 두 행은 서버 둘이다"라는 테스트 샘플을 추가해 같은 인시던트가 병합 검사에서 감지되게 했어요.

## 9. 새 소스를 추가하는 브랜치

새 소스에는 드라이 런에 사용할 원본 레코드가 없어요. 브랜치에서 **트라이얼 수집**을 해요. 시크릿을 복호화하는 작업(트라이얼 수집, 소스 탐색, 점검, 미리 보기)은 메인 브랜치의 소스 정의 그대로이면 그 소스를 범위에 가진 `editor`도 할 수 있고, 브랜치가 접속하는 주소(`endpoints`)를 바꿨으면 그 소스의 `operator`여야 해요(ADR-0018). 새 소스는 브랜치에만 있으니 이 API들은 `branch_id`를 받아요. 같은 읽기 전용 3중 보호와 소스 보호(ADR-0008)를 거치고, 브랜치 전용 영역에 저장돼요(`branch_id`가 붙은 원본 레코드. 운영의 원본에는 섞이지 않아요). 그 브랜치의 드라이 런과 테스트는 메인 브랜치의 원본 레코드와 이 트라이얼 수집 결과를 함께 읽어요. 병합되면 그 데이터를 첫 수집으로 사용할 수 있어요. 브랜치를 닫으면 저장된 데이터는 보존 기한에 따라 삭제돼요. 소스 설정은 정의의 항목이므로 담당자와 승인 규칙이 그대로 적용돼요.

## 10. 정의의 테스트

항목에 샘플을 연결해요. 샘플은 항목 본문의 목록(키 = 샘플의 이름)이라 자동으로 병합될 수 있어요.

| 필드 | 설명 |
|---|---|
| `name` | 샘플의 이름 |
| `input` | 합성 입력: 연결된 항목의 입력 데이터셋마다 행(컬럼 이름 → 값)의 목록 |
| `expect.objects` | 있어야 할 객체: 타입, 식별 키 값, 속성의 값과 근거 등급 |
| `expect.links` | 있어야 할 링크: 타입, 출발과 도착의 식별 키, 링크 의미 |
| `expect.absent` | 없어야 할 객체나 링크(예: 서버 둘이 하나로 병합되지 않는다) |
| `expect.problems` | 생성돼야 할 문제 목록의 종류 |
| `mode` | `contains`(기대한 것이 들어 있다) / `exact`(정확히 그것뿐) |

- **실행 방식.** 연결된 항목에서 시작해 이후 단계(피드이면 매핑, 식별, 링크)를 실제 실행기로 비어 있는 작은 KG에서 실행해요. 드라이 런과 같은 실행기라서 의미의 구현이 한 곳에만 있어요(ADR-0006).
- **실행 시점.** 편집 중 필요할 때, 검토 요청 시, 큐 맨 앞의 병합 검사(`item_tests`). 실패하면 `check_failed`예요.
- **프리셋.** 샘플 없이는 제품에 포함되지 않아요(ADR-0008). 프리셋을 선택하면 그 샘플이 소스 항목의 첫 샘플로 함께 들어와요(가정).
- 샘플에는 합성 데이터만 넣어요. 실제 데이터는 넣지 않아요(ADR-0003).

## 11. 호환성을 깨는 변경과 마이그레이션

저장할 때 검사가 항목의 리비전을 이전 리비전과 비교해서 분류를 정해요. 작성자가 정하지 않아요.

| 분류 | 예 | 마이그레이션 | 검사와 승인 |
|---|---|---|---|
| 추가 | 속성 추가, 새 타입, 새 피드, 새 소스, 새 기대 조건 | 필요 없어요 | 일반 |
| 호환되는 변경 | 표시 이름, 일정, 안전장치 강화, 출력 컬럼의 이름과 자료형이 그대로인 정제 수정, 같은 속성에 다른 컬럼 매핑 | 필요 없어요 | 드라이 런의 차이로 확인해요 |
| **호환성을 깨는 변경** | 속성의 이름이나 자료형을 변경 / 식별 키를 변경 / 타입을 지원 중단 / 링크 의미를 변경 | **반드시 작성해야 저장돼요** | 드라이 런으로 마이그레이션을 확인하고, "무엇이 영향받나"(12절)가 제안에 붙어요 |

**마이그레이션 필드**(`migration`, 호환성을 깨는 변경이 포함된 제안에 붙어요).

| 필드 | 설명 |
|---|---|
| `change_kind` | `attribute_rename`, `attribute_retype`, `identity_key_change`, `type_retire`, `link_meaning_change`, `type_merge`, `type_promote` |
| `from_ref`, `to_ref` | 어느 속성이나 타입에서 어느 것으로 바뀌는지 |
| `value_rule` | 값을 옮기는 변환. 제품에 포함된 순수 함수 목록에서 선택해요(ADR-0008) |
| `identity_plan` | 식별 이력의 처리 방법: `keep_ids`(옛 ID를 그대로 유지), `carry_to_successor`(지원 중단되는 타입의 식별 이력을 후속 타입으로 이전) 등 |
| `phase` | `add_and_fill` / `retire_old` |
| `readers` | 그 시점의 "무엇이 영향받나" 결과 |

- 속성의 이름이나 자료형은 제자리에서 바꿀 수 없어요(ADR-0007). 새 속성을 추가하고 값을 채운 뒤(`add_and_fill`) 옛 속성을 지원 중단 처리해요(`retire_old`). 이 둘은 보통 제안 두 개이고, 뒤의 제안에 참조하는 쪽 목록이 붙어서 승인하는 사람이 확인해요.
- **타입 병합**(A를 B로): 피드와 링크 정의가 A 대신 B를 참조하게 하고, 식별 이력을 B로 이전하고, A를 `deprecated`로 지정해서 `superseded_by`가 B를 가리켜요. 하나의 제안이고 드라이 런으로 확인해요. 승인은 `model_steward`예요.
- **타입 승격**(`ext` → `org`): `item_id`가 그대로여서 객체와 매핑이 깨지지 않아요. 호환성을 깨는 변경은 아니지만 마이그레이션 필드에 `keep_ids`를 기록해 이력을 남겨요. 승인은 `model_steward`예요.
- 타입의 변경은 모두 정의의 변경이라 어느 클라이언트에서 생성, 수정, 삭제해도 브랜치와 드라이 런과 승인을 거쳐요(ADR-0007). 삭제는 어디서도 사용되지 않을 때만 가능해요. 사용 중이면 지원 중단 처리하고 후속 타입을 지정해요.

## 12. 정의의 계보

항목 사이의 의존 관계를 그래프로 보유하고, 컬럼과 속성 단위까지 추적해요(정제의 연산이 고정 목록이라 가능해요). 정의 세트마다 하나이고 브랜치의 오버레이 위에서도 계산해요. 노드, 간선, 참조하는 쪽, "무엇이 영향받나"의 응답(`depends`, `readers`, `open_proposals`, `object_count`, `unreadable`)은 [정의의 계보](definitions-lineage.md)에 자세히 있어요.

- 이 계보가 **병합의 적용 범위**를 정해요(6절). 병합이 바꾼 항목에서 `reads`, `column_from`, `maps_to`, `defines_link`를 따라가 도달하는 피드와 타입만 새로 적용하고, 도달하지 않는 소스는 새 정의 세트로 바로 이어 가요. 검사도 계보로 도달하는 항목만 다시 평가해요.
- **두 축.** 이 계보는 정의 측이에요(항목에서 항목으로). ADR-0008의 출처 추적은 데이터 측이에요(객체에서 원본 레코드로). 객체와 링크는 원본 레코드의 참조와 규칙의 버전(정의 세트)을 가지고 있어서, 값 하나에서 "어느 레코드에서, 어느 규칙의 어느 리비전으로"를 추적하고, 거기서 이 그래프로 올라가 "그 규칙이 무엇에 의존하는지"를 확인해요.
- 제안에는 "무엇이 영향받나"가 붙고 에이전트도 읽기 전용 MCP로 조회할 수 있어요(KG의 MCP는 읽기만 해요).

## 13. 내보내기와 가져오기

- **내보내기.** 정의 세트 하나(`D-N`)를 텍스트 파일로 내보내요. 항목 하나가 파일 하나이고 정규 JSON(RFC 8785)이에요(ADR-0006). 순서와 들여쓰기가 정해져서 같은 정의 세트이면 같은 파일이에요. 시크릿은 참조만 내보내요.

```
manifest      정의 세트 번호, 정의 세트 해시, 항목 목록(item_id, 종류, 이름, 리비전의 해시)
items/<kind>/<name>   항목 파일: item_id, schema_version, body
```

- **가져오기.** 언제나 새 브랜치와 제안(`origin: import`)을 만들어요. 메인 브랜치를 덮어쓰지 않아요. manifest의 정의 세트 번호가 베이스이고 `item_id`로 항목을 매칭해요(파일 이름이 바뀌어도 같은 항목). 그 베이스가 이 메인 브랜치에 없으면 메인 브랜치의 현재 헤드를 베이스로 브랜치를 만들고(파일의 내용을 "목표 상태"로 보고 차이를 계산해요) 베이스를 알 수 없었다고 경고해요. 그다음은 일반 검사, 승인, 큐예요.
- **외부 Git은 미러예요.** 조직이 내보낸 파일을 자기 Git에 두고 거기서 리뷰해도 돼요. 거기서 병합된 것은 가져오기로 제안이 되고 프락시움의 검사와 승인을 다시 거쳐요. 양방향 자동 동기화는 하지 않아요(승인과 큐가 두 곳이 되기 때문이에요).
- 내보내기는 감사 로그에 남아요(ADR-0012). 내보내기는 해당 소속을 범위에 가진 `editor`가 자기 범위만큼 할 수 있어요.

## 14. 상태 개요(API)

정의 측의 읽기와 쓰기는 기능 이름으로 적어요. HTTP 경로는 [REST API의 자원 목록](rest-api-resources-data.md)이 정해요. 정의(타입, 소스, 데이터셋, 피드, 브랜치, 제안)는 배포에 하나라 `/v1/...` 바로 아래이고(예: `/v1/definitions-overview`), KG에 속한 것(식별의 리버트 등)은 `/v1/kgs/{kg}/...` 아래예요. 액션은 콜론 하나로 적어요: `POST /v1/proposals/{id}:approve`, `POST /v1/branches/{id}:align`. 읽기는 에이전트용 MCP로도 제공해요.

| 읽기 | 응답 |
|---|---|
| `definitions_overview` | 메인 브랜치(현재 `D-N`과 이력), KG마다 사용하는 정의 세트와 메인 브랜치 헤드의 불일치, 보류된 항목, 열린 브랜치와 제안(상태, 차단 사유, `overlaps_with`), 큐(순번과 맨 앞), 닫은 것(숨김) |
| `proposal` | 한 제안의 검사, 승인(필요한 것과 받은 것), 충돌, 정의의 차이, 후보 KG의 차이, 차단 사유 |
| `definition_set`, `definition_diff` | 한 정의 세트의 항목 목록, 두 정의 세트 사이의 차이 |
| `definition_item` | 한 항목의 리비전 이력, 어느 제안이 바꿨는지 |
| `what_depends` | 계보 문서 12-4의 답 |
| `revert_preview` | 리버트의 결과와 영향받는 항목, 함께 리버트할 목록 |

정의의 자원은 REST 계약의 `/v1/...` 아래에 있어요(ADR-0006). 오래 걸리는 작업(드라이 런, 트라이얼 수집, 내보내기)은 접수했다고 응답하고 작업 자원을 반환해요. 작업의 진행 상황은 생성한 사람만이 아니라 그 작업이 속한 제안을 읽을 수 있는 사람도 볼 수 있어요. 메인 브랜치를 직접 수정하는 경로는 없고 모든 수정은 브랜치 안에서 해요. 같은 항목의 동시 수정은 낙관적 동시성 제어로 차단해요.

쓰기: `small_change_propose`(작은 변경을 제안 하나로), `branch_create`, `branch_edit`, `branch_align`(메인 브랜치 최신화), `conflict_resolve`, `proposal_request_review`, `proposal_approve`, `proposal_reject`, `proposal_enqueue`, `proposal_close`, `revert_create`, `restore_create`, `trial_ingest_run`, `serving_pin`, `serving_unpin`, `definitions_export`, `definitions_import`.
모든 쓰기는 접근 제어의 판단을 한 곳에서 거쳐요. `definitions_overview`의 목적은 "수행한 작업은 모두 기록되고 리버트할 수 있다"가 보이게 해서 사람이 부담 없이 수정하게 하는 거예요.

## 15. 알파의 범위

화면은 다른 리포지토리의 일이에요(제품 책임자의 결정). 이 리포지토리의 알파는 정의의 모든 기능(항목 수정, 제안, 검사, 승인, 큐, 충돌 해결, 리버트, 고정, 트라이얼 수집, 계보, 내보내기와 가져오기)이 **API와 CLI로 동작하는 것**이에요(알파 1은 메인 브랜치와 정의 세트의 단일 이력을 구축하고, 브랜치와 제안부터 리버트까지는 알파 2예요. 보충 문서의 [클로즈드 베타]와 [오픈 베타] 표시는 그대로예요). 화면에 필요한 조회는 API가 제공해요: `definitions_overview`(개요), 제안의 상세, 충돌의 3-way 비교, 리버트의 미리보기, "무엇이 영향받나". 사람에게 보일 문구는 화면이 코드와 값으로 생성해요.

## 16. 알려진 한계

- **큐 하나의 처리 빈도는 측정하지 않았어요.** 사람이 사용할 때는 잦지 않다고 보지만 못 박지 않아요(조사한 한 회사의 설정 시스템 논문은 설정이 평생 수십 번 바뀐다고 적어요. 그 회사의 규모 기준이에요). 에이전트가 사용하면 잦아서 병합 턴 하나의 비용을 낮추는 것으로 큐 하나를 유지하고, `merge_turn_duration_s` 같은 지표가 필요하다고 가리키면 여러 제안을 배치로 묶어 병합하는 방식으로 넓혀요(보충 문서 5절).
- **드라이 런은 예고일 뿐 보증이 아니에요.** 병합 후 실제 적용은 그사이 수집한 원본 레코드와 새 KG 버전 위에서 이루어져서, R2부터의 첫 적용 확인이 두 번째 관문으로 남아요. 이때 사람이 병합 시점의 후보 차이와 현재 차이를 비교해 볼 수 있어야 해요(가정). R0, R1은 이 관문 없이 사후 알림이라 안전장치와 리버트가 보완해요.
- **항목이 수천 개, 수 MB**라는 규모는 측정하지 않은 가정이에요. 정의 세트마다 전체 목록을 두는 방식이 부담스러워지면 부모 대비 차이와 주기적 전체 저장 방식으로 바꿔요.
- **리버트해도 복원되지 않는 것**이 있어요(8-2). 이미 병합된 ID, 이미 폐기 처리된 객체의 과거 상태예요.
- 자동 병합은 키가 있는 목록 네 가지에만 적용해요. 나머지 항목 안의 필드는 따로 병합하지 않아요.

## 17. 미결 사항

- 마이그레이션이 표준 타입과 `sys` 타입의 리비전을 어떤 형식으로 적재하는지(항목의 `origin`과 `rev_no` 규칙)의 세부.
- 드라이 런에서 안전장치가 작동한 제안의 확인과, 적용 때 작동하는 안전장치의 확인이 같은 확인인지.
- 입력 소스의 범위를 승인에서 어떻게 확인하는지: 입력 소스마다 그 소스의 `approver`가 승인해야 하는지, 승인자가 그 소스의 범위를 볼 수 있는 정도로 충분한지.
- 도달하는 항목이 보류된 동안 KG 버전의 정의 세트 해시와 확정을 어떻게 기록하는지(도달하지 않는 변경은 이전 정의 세트의 이름으로 확정하고 리비전이 같아 결과가 같다고 해석했어요).
- 적용 작업이 어느 KG에 적용되는지(메인 브랜치를 따라가는 KG에만인지). 후보 KG와 테스트 KG가 정의 세트를 따로 선택하는 방법.
- 이 문서의 가정: 브랜치와 제안은 일대일, "작성자"는 브랜치에 리비전을 추가한 모든 사람.
