# KG의 적용

[KG의 저장과 버전](kg-storage.md)에서 테이블과 ID와 해시를 정했다면, 이 문서는 **변경 배치가 어떻게 KG에 들어가고, 누가 어떤 순서로 쓰고, 오래된 데이터가 어떻게 삭제되는지**를 정해요(ADR-0009). 테이블의 컬럼은 kg-storage.md의 3절을 가리켜요. 숫자는 가정이에요.

## 1. 목적과 다루는 질문

- 변경 배치 하나가 어떤 단계로 KG에 들어가고, 중간에 중단되면 어떻게 이어 가는가.
- 큰 적용(초기 적재, 큰 배치, 병합 뒤의 재적용)이 수천만 객체에서도 짧은 트랜잭션으로 끝나고, 읽기 측이 반쯤 반영된 배치를 보지 않으려면 어떻게 하는가.
- "빈 KG에서 같은 순서로 다시 실행하면 같은 변경 시퀀스"가 성립하려면 수집 순서에 무엇이 들어가는가.
- 적용기가 둘이 되지 않게, 그리고 의미 버전이 다른 코드가 번갈아 쓰지 않게 하는 리스(lease)는 어떤 구조인가.
- 시점 복구 뒤에 번호가 겹치는 것을 외부 소비자는 어떻게 알 수 있는가.
- 무엇을 얼마나 보존하고 무엇을 삭제하는가.

## 2. 개요

```
수집 변경 로그 ─(적용기가 읽어 순서를 확정: ingest_order, ingest_seq)─┐
                                                                          ▼
 정제·매핑·식별·링크 ─> 후보 ─1 적재─> stage_* ─2 차이 계산─> plan_change
                                                                          │
                      3 적용: 청크(chunk)마다 짧은 트랜잭션, 청크마다 change_seq 하나
                                                                          ▼
          live / hist / light_change / change_batch·change_entry / kg_head
                                                                          │
                      배치의 마지막 청크가 커밋될 때만  readable_through  가 오른다
```

| 용어 | 의미 |
|---|---|
| `applied_seq` | 적용된 마지막 `change_seq`. 큰 적용 중에는 앞서 나간다 |
| `readable_through` | 읽기 측이 볼 수 있는 마지막 번호. 배치 하나가 모두 들어갔을 때만 오른다. 작은 배치는 `applied_seq`와 같다 |
| 청크(chunk) | 큰 적용을 한도에 맞춰 자른 단위. 청크 하나가 트랜잭션 하나이고 `change_seq` 하나다 |
| 리스(lease) | KG마다 하나뿐인 적용기를 워커 하나가 보유한다는 표시. 실행기의 의미 버전이 들어간다 |
| 세대(generation) | 시점 복구를 할 때마다 오르는 번호 |

## 3. 적용의 3단계와 실패

적용마다 `apply_id`가 있고 스테이징 영역을 구분해요. 3단계 앞에 **순서 확정**이 있어요(4절).

| 단계 | 하는 일 | 사용하는 테이블 |
|---|---|---|
| 1. 적재 | 후보를 대량 복사로 스테이징 영역에 적재한다. 내용 해시는 애플리케이션이 계산해 함께 적재한다 | `stage_object`, `stage_link` |
| 2. 차이 계산 | 스테이징 영역과 `live`를 ID로 속성 단위로 비교해 `plan_change`에 쓴다. 안전장치(ADR-0008)를 여기서 확인한다. 그래프 해시를 이 차이만으로 갱신해 본다 | `plan_change` |
| 3. 적용 | 청크마다 트랜잭션 하나: 헤드 행을 잠그고 → 계획이 아직 유효한지, 리스와 `attempt`가 최신인지 확인하고 → `change_seq`를 하나 올리고 → 닫는 행을 `live`에서 `hist`로 옮기고 → 새 행을 `live`에 넣고 → `change_batch`와 `change_entry`를 쓰고 → 바뀐 `volatile` 값을 덮어쓰고 `light_change`에 행을 쓰고 → 실행기의 상태를 쓰고 → `kg_head`를 옮긴다 | `object_*`, `link_*`, `attr_volatile`, `light_change`, `change_*`, `operator_state`, `kg_head` |

차이가 없으면 3단계에 가지 않고 새 변경도 만들지 않아요. 스트림의 안전장치가 보류하면(`held`) 3단계에 가지 않지만 **수집은 멈추지 않아요**: 원본 레코드는 계속 쌓여요.

**사람의 확인은 위험 등급이 R2부터예요**(ADR-0014). R0와 R1은 자동으로 적용하고 알려요. 확인을 기다리는 동안 멈추는 것은 정의의 계보로 연결된 피드와 타입뿐이고, 연결되지 않은 소스의 스트림은 새 정의 세트로 바로 이어 가요([definitions.md](definitions.md)). 실행기의 의미 버전이 오른 뒤의 첫 적용은 정의를 수정한 것과 같이 다뤄요.

### 3.1 단계별 중단 처리

| 중단되는 시점 | 남는 것 | 재실행 방법 |
|---|---|---|
| 순서 확정 중 | `ingest_order`가 없거나 이미 기록됐다. `live`는 그대로 | 기록된 목록이 있으면 그 목록을 따라 이어 가고, 없으면 처음부터 읽는다. 같은 위치를 두 번 기록하지 않는다 |
| 1단계 중 | 반쯤 적재된 스테이징 영역 | 같은 `apply_id`의 스테이징 영역을 삭제하고 1단계부터. 원본 레코드가 있어 소스에 다시 접속하지 않는다 |
| 2단계 중 | 반쯤 쓴 `plan_change` | 계획을 삭제하고 2단계부터. 계획은 파생 데이터다 |
| 청크 커밋 전 | 트랜잭션이 통째로 취소된다 | 헤드가 그대로면 그 청크부터 다시 한다 |
| 청크 커밋 후, 워커가 알기 전 | 그 청크가 적용돼 있고 `kg_head`의 `apply_id`와 다음 청크 번호가 같은 트랜잭션으로 갱신돼 있다 | 이어받은 워커는 `kg_head`를 보고 다음 청크부터 진행한다. "정확히 한 번 적용"을 보장한다 |
| 배치의 마지막 청크 커밋 후 | `applied_through`와 `readable_through`가 같은 트랜잭션으로 올랐다 | 다시 할 것이 없다 |
| 워커 전체 중단 | 리스의 `lease_until`이 지난다 | 다른 워커가 `attempt`를 올려 리스를 획득하고 이어 간다(5절) |
| 뒤늦게 복귀한 이전 워커가 쓰려 함 | `attempt`가 낮다 | 3단계에서 거절된다 |
| 청크 사이에 다른 적용이 `kg_head`를 변경함 | 계획이 이전 `applied_seq` 기준이다 | 계획을 폐기하고 2단계부터 다시 계산한다. 한 KG의 적용기는 하나라 큰 적용 중에는 일어나지 않고, 리스가 바뀐 때만 있다 |

번호(`change_seq`, `ingest_seq`, 서로 다른 번호예요)는 **KG마다 하나뿐인 적용기**가 헤드 행의 카운터로 매겨요. 시퀀스 객체를 쓰지 않아요. 커밋 순서와 번호 순서가 같아야 읽기 측이 작은 번호를 놓치지 않아요.

리버트는 변경을 거꾸로 되감는(롤백) 것이 아니에요. 이전 정의를 새 변경으로 병합해 새 변경 배치와 새 버전이 나와요(ADR-0014). 식별 이력은 되감지 않아요.

## 4. 큰 적용과 초기 적재

**초기 적재도 큰 적용의 하나예요. 한 트랜잭션으로 하지 않아요.**

1. 초기 적재가 만드는 KG는 `kg.state = building`이에요. 읽기 경로와 변경 알림에 나타나지 않아요.
2. 계획(2단계)을 `plan_change`에 쓰며 **청크 번호를 매겨요**. 청크는 ID 순서로 한도(가정: 1만 행 또는 2초, [기본값 표](defaults.md))까지 잘라요. 청크를 자르는 방식이 결정적이라 다시 해도 같아요.
3. 청크마다 3단계를 실행해요. 청크가 커밋될 때 `kg_head`의 `apply_id`와 `next_chunk_no`가 함께 나아가요. 중단되면 다음 청크부터 이어 가요.
4. 마지막 청크가 커밋될 때만 `readable_through`가 `applied_seq`까지 올라요. 초기 적재라면 같은 트랜잭션에서 `kg.state`가 `serving`으로 한 번 바뀌어요.

`change_seq`는 청크마다 하나라서 나눠서 적용해도 `kg_version_id`는 달라지지 않아요. 버전 ID의 입력에 `change_seq`가 없기 때문이에요(kg-storage.md 7절). 청크 한도가 바뀌어도 같은 입력에서 같은 버전이 나와요.

**읽기 측이 반쯤 반영된 배치를 보지 않는 방법.** 읽기는 `S`를 `applied_seq`가 아니라 `readable_through`로 정해요. 배치가 실행되는 동안 청크들은 이미 `live`와 `hist`에 있지만 `seq_from`이 `S`보다 커서 보이지 않아요. 같은 이유로 **큰 적용 중에는 "최신 번호이면 `live`만 본다"는 지름길을 쓰지 않아요**: 청크가 닫은 이전 행은 `hist`에 있고 `S`에서는 아직 유효하기 때문이에요. 지름길은 `readable_through = applied_seq`일 때만 써요. 다음은 모두 `readable_through`까지만 봐요.

- `min_seq`(적어도 이 변경 번호까지 반영한 응답)의 충족 판단, `serving_pin`, 확정(`sealed_seq`는 `readable_through`를 넘지 않는다)
- 변경 알림, SSE의 `kg_changed`, 프로젝션으로 가는 변경, 충족 표시의 재계산
- 두 버전의 차이와 `from_change_seq`로 변경을 가져가는 소비자

**큰 적용 중 같은 KG의 다른 배치는 기다려요.** 번호 순서를 한 적용기가 지키기 때문이에요. 이 대기가 스트림의 적용 지연이므로 "큰 적용 중 스트림의 적용 지연"을 측정 목록에 넣어요(kg-storage.md 13절). 청크 한도는 이 지연을 줄이는 조절 변수예요.

보류된 스트림이 오래 쌓였다가 해제될 때도 한 번에 적용하지 않고 한도 크기의 배치로 나눠 적용해요.

**청크 자르기와 포기(ADR-0025).** 청크는 배치가 담은 객체와 링크(추가, 수정, 폐기하는 것 전부)를 종류와 ID 순으로 정렬해 한도만큼 잘라요. 차이가 없는 청크는 쓰지 않고, 같은 배치를 다시 실행해도 같은 곳에서 잘려요. `volatile` 값, 식별자와 식별 이벤트, 순서 이벤트(`ingest_order`)는 마지막 청크에 들어가요. **포기**는 아무도 읽지 못한 청크의 롤백이에요: `readable_through` 뒤의 행을 삭제하고, 그 청크가 닫은 행을 다시 열고, 헤드의 해시를 배치 시작 시점으로 되돌려요. 변경 번호는 다시 쓰여요. 리버트(3.1절)와 달리 새 변경도 새 버전도 만들지 않아요. 한 번도 읽을 수 없었던 상태이기 때문이에요.

## 5. 수집 순서: 고정 목록

> 다음 KG 버전 = f(이전 버전, `ingest_seq` 순서대로의 원본 변경, 정의 세트, 실행기의 의미 버전)

"순서"에 들어가는 것은 아래 **8종 이벤트의 고정 목록**이에요. 목록에 없는 것은 결과를 바꾸면 안 되고, 바꾼다면 목록에 추가하는 결정 기록이 있어야 해요. 모두 `ingest_order`에 `event_kind`로 기록돼요.

| `event_kind` | 내용 | 발생 주체 |
|---|---|---|
| `source_change` | 소스에서 수집한 원본 변경 배치 | 수집 |
| `clock_event` | 시계가 발행한 틱. 연속 미관측 횟수의 기준 시점, `pending_value`의 기한, 주기적 확정 요청이 이것을 기준으로 센다 | 시계 |
| `seal` | 확정이 일어난 시점 | 확정 |
| `held_release` | 보류된 스트림의 해제 | 운영 조작 |
| `held_discard` | 보류된 스트림의 폐기 | 운영 조작 |
| `guard_confirm` | 안전장치가 멈춘 것을 사람이 확인함 | 운영 조작 |
| `raw_exclude` | 원본 레코드를 리플레이에서 제외함 | 운영 조작 |
| `definition_switch` | KG가 사용하는 정의 세트가 바뀜 | 병합의 적용 |

- **보류된 변경은 해제될 때 `ingest_seq`를 받아요.** 보류되는 동안에는 순서가 없어서, 그 사이에 수집한 다른 변경이 먼저 확정돼요. 해제가 이벤트라서 다시 실행해도 같은 위치에 들어가요. 폐기하면 `held_discard`가 기록되고 그 변경은 순서를 받지 못해요.
- 목록의 이벤트는 모두 운영 액션이나 시계, 적용기가 발생시키고 감사 로그에 남아요. 원본 레코드를 **회수하는** 것(kg-storage.md 3.2절)은 이 목록에 없어요. 해시가 그대로라 다시 실행한 결과가 바뀌지 않기 때문이에요.
- 테스트(kg-storage.md 7.5절)는 이 목록을 기준으로 검증해요: 빈 KG에서 같은 `ingest_order`와 같은 정의로 반복하면 모든 `kg_version_id`가 같다.

## 6. 리스와 실행기의 의미 버전

KG마다 적용기는 하나예요. 워커가 적용기를 보유한다는 표시가 **리스**예요(`kg_apply_lease`: `kg_id`, `lease_owner`, `lease_until`, `attempt`, `semantic_version`).

- 리스를 획득할 때 `attempt`가 오르고, 작업하는 동안 `lease_until`을 연장해요. 쓰기는 `attempt`와 리스로 차단돼요(3.1).
- **리스에는 워커가 실행하는 실행기의 의미 버전이 들어가요.** KG의 `kg_head.applied_semantic_version`보다 낮은 버전의 워커는 리스를 획득할 수 없어요. 리스를 획득한 워커가 더 높은 버전이면 `applied_semantic_version`이 오르고, 그 뒤로 낮은 버전은 적용만 할 수 없고 읽기와 수집은 해요. 롤링 교체 중에 이웃한 두 버전이 함께 실행돼도 같은 KG를 번갈아 적용하지 않으니 결정성이 깨지지 않아요.
- 리스가 없는 워커도 소스에서 수집, 읽기, 드라이 런은 해요.
- **표준 모델과 `sys` 타입은 마이그레이션의 한 단계로 스토리지에 포함해요.** 실행 파일은 스토리지의 것을 읽어요. 실행 파일에 들어 있는 버전이 인스턴스마다 다르면 롤링 교체 중에 메인 브랜치의 해시가 인스턴스마다 달라지기 때문이에요.

## 7. 세대와 시점 복구

시점 복구를 하면 `applied_seq`가 뒤로 가서 같은 `change_seq`에 다른 내용이 생길 수 있어요. 엔진은 `kg_version_id`로 구분해요(kg-storage.md 10절). 외부 소비자는 그럴 수 없어서 **세대**를 둬요.

- `kg.generation`은 복구할 때마다 하나 올라요. 올린 시각과 되돌아간 `change_seq`는 `generation_event`에 남아요.
- `as_of`, 페이지네이션의 커서, 변경 알림의 이벤트 ID, `min_seq`에 세대가 포함돼요. `as_of`는 `(kg_id, generation, 변경 번호 또는 버전)`이에요.
- 요청의 세대가 KG의 세대와 다르면 `conflict.generation_changed`로 응답해요. 소비자는 새 세대에서 다시 시작해요.
- `kg_version`에도 세대를 적어요. 복구 전의 버전 40과 복구 후의 버전 40은 세대가 달라 구분돼요.

## 8. 보존과 삭제

보존 기본값은 [기본값 표](defaults.md)에 있어요(원본 레코드 90일, 과거 이력 1년, 감사 3년. 가정).

| 대상 | 규칙 |
|---|---|
| `raw_record` | **닫힌 구간에만** 적용한다. 구간이 열린 행(내용이 바뀌지 않은 채 여전히 유효한 행)은 경과 기간으로 삭제하지 않는다. 닫힌 지 기한이 지난 행만 삭제한다. 경과 기간은 닫은 `ingest_seq`의 `ordered_at`으로 센다. 삭제 방식(구간 단위 통째 삭제인지 정리 작업인지)은 측정해서 정한다 |
| `raw_log` | `volatile` 속성만 제공하는 스트림의 데이터셋은 구간이 아니라 추가 전용(append-only) 레코드다. 짧게 보존하고 `ingest_seq` 구간 단위로 통째로 삭제한다. 내용 해시와 버전의 해시에 들어가지 않으므로 삭제해도 버전은 바뀌지 않는다. 이 로그로 리플레이할 수 있는 것은 보존 기한 안뿐이다 |
| `hist`, `change_entry`, `change_batch` | `change_seq` 구간 단위로 통째로 삭제한다. 삭제한 구간은 `kg_maintenance.min_readable_seq`로 알린다 |
| `light_change` | 짧게 보존한다(가정). `change_seq` 구간 단위로 통째로 삭제한다. 뒤늦게 따라오는 소비자는 기한 안에서만 이어 가고, 넘으면 전체를 다시 동기화한다 |
| `pending_value`, `unseen_object` | 기한이 지나거나 대응하는 항목이 닫힐 때 삭제한다 |

- **고정 참조가 있는 것은 기한이 지나도 삭제하지 않아요.** 확정 버전이 사용한 원본 레코드와 고정된(`serving_pin`) 버전의 이력은 `min_readable_seq`가 건너뛰어요. 삭제해도 현재 그래프 해시는 바뀌지 않아요.
- 닫힌 구간만 삭제하므로 2년째 바뀌지 않은 배치의 행은 남아요. 그 행이 리플레이와 드라이 런과 값의 출처의 기반이에요.
- 회수한 기록(kg-storage.md 3.2절)은 보존 정책과 별개로 남아요. 해시와 위치와 이유만 있는 레코드예요.

## 9. 알려진 한계와 가정

- 큰 적용 중 같은 KG의 스트림이 대기해요. 청크 한도와 대기 시간은 가정이고 클로즈드 베타에서 측정해요.
- 청크 사이에 중단되면 이어서 진행하거나 포기해요. 포기는 읽기 측이 보지 못한 청크를 롤백해요(4절, ADR-0025).
- 세대는 소비자가 오래된 번호를 보유하고 있음을 알리는 장치예요. 복구 뒤 `ingest_order`가 다시 확정될 때 처음과 같은 순서가 된다고 약속하지는 않아요.
- 낮은 버전으로 롤백하는 배포는 리스를 획득할 수 없어요.

## 10. 미결 사항

- 낮은 버전으로 롤백할 때 `applied_semantic_version`을 내리는 운영 액션이 필요한지.
- 청크 한도의 기본값, 스트림의 적용 지연 목표.
- 짧은 보존(`light_change`, `raw_log`)의 기한 값.

## 11. 관련 결정과 요구사항

ADR-0009(이 문서가 풀어 쓴 결정), ADR-0010(`min_seq`와 프로젝션), ADR-0014(위험 등급과 병합). 요구사항: REQ-132(적용은 한순간에 공개되고 한 상태만 보기), REQ-131(같은 입력이면 같은 KG 버전), REQ-135(변경 시퀀스와 확정 버전), REQ-222(초기 적재와 `min_seq`).
