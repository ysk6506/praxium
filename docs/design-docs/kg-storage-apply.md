# KG의 적용

[KG의 저장과 버전](kg-storage.md)에서 표와 ID와 해시를 정했다면, 이 문서는 **변경 배치가 어떻게 KG에 들어가고, 누가 어떤 순서로 쓰고, 오래된 것이 어떻게 사라지는지**를 정해요(ADR-0009). 표의 칸은 kg-storage.md의 3절을 가리켜요. 숫자는 가정이에요.

## 1. 목적과 다루는 질문

- 변경 배치 하나가 어떤 걸음으로 KG에 들어가고, 중간에 죽으면 어떻게 이어 가나.
- 큰 적용(초기 적재, 큰 배치, 병합 뒤의 다시 적용)이 수천만 객체에서도 짧은 트랜잭션으로 끝나고, 읽는 쪽이 반쯤 든 배치를 보지 않으려면.
- "빈 KG에서 같은 순서로 다시 돌리면 같은 이어짐"이 서려면 수집 순서에 무엇이 드나.
- 적용기가 둘이 되지 않게, 그리고 뜻이 다른 코드가 번갈아 쓰지 않게 하는 리스(lease)는 어떤 모양인가.
- 시점 복구 뒤에 번호가 겹치는 것을 밖의 소비자는 어떻게 아나.
- 무엇을 얼마나 두고 무엇을 지우나.

## 2. 개요

```
받은 변경의 기록 ─(적용기가 읽어 차례를 굳힘: ingest_order, ingest_seq)─┐
                                                                          ▼
 정제·매핑·식별·링크 ─> 후보 ─1 싣기─> stage_* ─2 차이 내기─> plan_change
                                                                          │
                      3 적용: 쪽(chunk)마다 짧은 트랜잭션, 쪽마다 change_seq 하나
                                                                          ▼
          live / hist / light_change / change_batch·change_entry / kg_head
                                                                          │
                      배치의 마지막 쪽이 커밋될 때만  readable_through  가 오른다
```

| 말 | 뜻 |
|---|---|
| `applied_seq` | 적용된 마지막 `change_seq`. 큰 적용 중에는 앞서 나간다 |
| `readable_through` | 읽는 쪽이 볼 수 있는 맨 끝. 배치 하나가 다 들어갔을 때만 오른다. 작은 묶음은 `applied_seq`와 같다 |
| 쪽(chunk) | 큰 적용을 한도가 있게 자른 한 토막. 쪽 하나가 트랜잭션 하나이고 `change_seq` 하나다 |
| 리스(lease) | KG마다 하나뿐인 적용기가 워커 하나에 있다는 표시. 실행기의 의미 버전이 든다 |
| 세대(generation) | 시점 복구를 할 때마다 오르는 번호 |

## 3. 적용의 세 걸음과 실패

적용마다 `apply_id`가 있고 스테이징 영역을 가려요. 세 걸음 앞에 **순서 확정**가 있어요(4절).

| 걸음 | 하는 일 | 쓰는 표 |
|---|---|---|
| 1. 적재 | 후보를 대량 복사로 스테이징 영역에 싣는다. 내용 해시는 앱이 계산해 함께 싣는다 | `stage_object`, `stage_link` |
| 2. 차이 내기 | 스테이징 영역과 `live`를 ID로 속성 단위로 견줘 `plan_change`에 쓴다. 안전장치(ADR-0008)를 여기서 본다. 그래프 해시를 이 차이만으로 고쳐 본다 | `plan_change` |
| 3. 적용 | 쪽마다 트랜잭션 하나: 머리 행을 잠그고 → 계획이 아직 맞는지, 리스와 `attempt`가 최신인지 보고 → `change_seq`를 하나 올리고 → 닫는 행을 `live`에서 `hist`로 옮기고 → 새 행을 `live`에 넣고 → `change_batch`와 `change_entry`를 쓰고 → 바뀐 `volatile` 값을 덮어쓰고 `light_change`에 줄을 쓰고 → 실행기의 상태를 쓰고 → `kg_head`를 옮긴다 | `object_*`, `link_*`, `attr_volatile`, `light_change`, `change_*`, `operator_state`, `kg_head` |

차이가 없으면 3걸음에 가지 않고 새 변경도 만들지 않아요. 흐름의 안전장치가 붙잡으면(`held`) 3걸음에 가지 않지만 **받는 것은 멈추지 않아요**: 원본 레코드는 계속 쌓여요.

**사람의 확인은 위험 등급이 R2부터예요**(ADR-0014). R0와 R1은 저절로 적용하고 알려요. 확인을 기다리는 동안 서는 것은 정의의 계보로 닿는 피드와 타입뿐이고, 닿지 않는 소스의 흐름은 새 정의 세트로 바로 이어 가요([definitions.md](definitions.md)). 실행기의 의미 버전이 오른 뒤의 첫 적용은 정의를 고친 것과 같이 다뤄요.

### 3.1 걸음마다 죽으면

| 죽는 때 | 무엇이 남나 | 다시 하는 법 |
|---|---|---|
| 순서 확정 중 | `ingest_order`가 없거나 이미 적혔다. `live`는 그대로 | 적힌 목록이 있으면 그 목록을 따라 이어 가고, 없으면 처음부터 읽는다. 같은 자리를 두 번 적지 않는다 |
| 1걸음 중 | 반쯤 실린 스테이징 영역 | 같은 `apply_id`의 스테이징 영역을 지우고 1걸음부터. 원본 레코드가 있어 소스에 다시 가지 않는다 |
| 2걸음 중 | 반쯤 쓴 `plan_change` | 계획을 지우고 2걸음부터. 계획은 끌어낸 것이다 |
| 쪽의 커밋 전 | 트랜잭션이 통째로 취소된다 | 머리가 그대로면 그 쪽부터 다시 한다 |
| 쪽의 커밋 후, 워커가 알기 전 | 그 쪽이 적용돼 있고 `kg_head`의 `apply_id`와 다음 쪽 번호가 같은 트랜잭션으로 나아가 있다 | 이어받은 워커는 `kg_head`를 보고 다음 쪽부터 간다. "정확히 한 번 적용"을 만든다 |
| 배치의 마지막 쪽의 커밋 후 | `applied_through`와 `readable_through`가 같은 트랜잭션으로 올랐다 | 다시 할 것이 없다 |
| 워커가 통째로 죽음 | 리스의 `lease_until`이 지난다 | 다른 워커가 `attempt`를 올려 리스를 낚아채 이어 간다(5절) |
| 늦게 깨어난 옛 워커가 쓰려 함 | `attempt`가 낮다 | 3걸음에서 거절된다 |
| 쪽 사이에 다른 적용이 머리를 마이그레이션 | 계획이 옛 `applied_seq` 기준이다 | 계획을 버리고 2걸음부터 다시 낸다. 한 KG의 적용기는 하나라 큰 적용 중에는 일어나지 않고, 리스가 바뀐 때만 있다 |

번호(`change_seq`, `ingest_seq`, 서로 다른 번호예요)는 **KG마다 하나뿐인 적용기**가 머리 행의 셈으로 매겨요. 시퀀스를 쓰지 않아요. 커밋의 차례와 번호의 차례가 같아야 읽는 쪽이 작은 번호를 놓치지 않아요.

리버트는 변경을 거꾸로 감는 것이 아니에요. 이전 정의를 새 변경으로 병합해 새 변경 배치와 새 버전이 나와요(ADR-0014). 식별의 이력은 되감기지 않아요.

## 4. 큰 적용과 초기 적재

**초기 적재도 큰 적용의 하나예요. 한 트랜잭션으로 하지 않아요.**

1. 초기 적재가 만드는 KG는 `kg.state = building`이에요. 읽는 경로와 변경 알림에 나타나지 않아요.
2. 계획(2걸음)을 `plan_change`에 쓰며 **쪽 번호를 매겨요**. 쪽은 ID 순서로 한도(가정: 1만 행 또는 2초, [기본값 표](defaults.md))까지 잘라요. 쪽의 자르기는 정해진 순서라 다시 해도 같아요.
3. 쪽마다 3걸음을 해요. 쪽이 커밋될 때 `kg_head`의 `apply_id`와 `next_chunk_no`가 함께 나아가요. 죽으면 다음 쪽부터 이어 가요.
4. 마지막 쪽이 커밋될 때만 `readable_through`가 `applied_seq`까지 올라요. 초기 적재라면 같은 트랜잭션에서 `kg.state`가 `serving`으로 한 번 바뀌어요.

`change_seq`는 쪽마다 하나라서 쪼개 적용해도 `kg_version_id`는 달라지지 않아요. 버전 ID의 입력에 `change_seq`가 없기 때문이에요(kg-storage.md 7절). 쪽의 한도가 바뀌어도 같은 입력에서 같은 버전이 나와요.

**읽는 쪽이 반쯤 든 배치를 보지 않는 법.** 읽기는 `S`를 `applied_seq`가 아니라 `readable_through`로 정해요. 배치가 도는 동안 쪽들은 이미 `live`와 `hist`에 있지만 `seq_from`이 `S`보다 커서 보이지 않아요. 같은 이유로 **큰 적용 중에는 "맨 끝이면 `live`만 본다"는 지름길을 쓰지 않아요**: 쪽이 닫은 옛 행은 `hist`에 있고 `S`에서는 아직 유효하기 때문이에요. 지름길은 `readable_through = applied_seq`일 때만 써요. 다음은 모두 `readable_through`까지만 봐요.

- `min_seq`(적어도 이 변경 번호까지 본 답)의 충족 판단, `serving_pin`, 확정(`sealed_seq`는 `readable_through`를 넘지 않는다)
- 변경 알림, SSE의 `kg_changed`, 프로젝션으로 가는 변경, 충족 표시의 다시 따지기
- 두 버전의 차이와 `from_change_seq`로 가져가는 소비자

**큰 적용 중 같은 KG의 다른 묶음은 기다려요.** 번호의 차례를 한 적용기가 지키기 때문이에요. 이 기다림이 흐름의 적용 지연이므로 "큰 적용 중 흐름의 적용 지연"을 재는 목록에 넣어요(kg-storage.md 13절). 쪽의 한도는 이 지연을 줄이는 손잡이예요.

보류된 스트림이 오래 쌓였다 풀릴 때도 한 번에 적용하지 않고 한도가 있는 묶음으로 나눠 적용해요.

**쪽의 자르기와 포기(ADR-0025).** 쪽은 배치가 담은 객체와 링크(더하거나 고치거나 물리는 것 전부)를 종류와 ID 순으로 세워 한도만큼 잘라요. 차이가 없는 쪽은 쓰지 않고, 같은 배치를 다시 해도 같은 곳에서 잘려요. `volatile` 값, 식별자와 식별 사건, 차례의 사건(`ingest_order`)은 마지막 쪽에 들어요. **포기**는 아무도 못 본 쪽의 되감기예요: `readable_through` 뒤의 행을 지우고, 그 쪽이 닫은 행을 다시 열고, 머리의 해시를 배치 시작 때로 돌려요. 변경 번호는 다시 쓰여요. 리버트(3.1절)와 달리 새 변경도 새 버전도 만들지 않아요. 한 번도 읽을 수 없었던 상태이기 때문이에요.

## 5. 수집 순서: 고정 목록

> 다음 KG 버전 = f(앞 버전, 받은 차례(`ingest_seq`)대로의 원본 변경, 정의 묶음, 실행기의 의미 버전)

"차례"에 드는 것은 아래 **여덟 사건의 고정 목록**이에요. 목록에 없는 것은 결과를 바꾸면 안 되고, 바꾼다면 목록에 더하는 결정 기록이 있어야 해요. 모두 `ingest_order`에 `event_kind`로 적혀요.

| `event_kind` | 무엇 | 누가 낳나 |
|---|---|---|
| `source_change` | 소스에서 받은 원본 변경의 묶음 | 수집 |
| `clock_event` | 시계가 낸 틱. 안 보인 번수의 때, `pending_value`의 기한, 주기의 확정 요청이 이것을 센다 | 시계 |
| `seal` | 확정이 일어난 자리 | 확정 |
| `held_release` | 보류된 스트림의 풀기 | 운영 조작 |
| `held_discard` | 보류된 스트림의 버리기 | 운영 조작 |
| `guard_confirm` | 안전장치가 잡은 것을 사람이 확인함 | 운영 조작 |
| `raw_exclude` | 원본 레코드를 다시 돌리기에서 뺌 | 운영 조작 |
| `definition_switch` | KG가 쓰는 정의 세트가 바뀜 | 병합의 적용 |

- **붙잡힌 변경은 풀릴 때 `ingest_seq`를 받아요.** 붙잡히는 동안에는 차례가 없어서, 그 사이에 받은 다른 변경이 먼저 굳어요. 풀기가 사건이라 다시 돌려도 같은 자리에 들어가요. 버리면 `held_discard`가 적히고 그 변경은 차례를 받지 못해요.
- 목록의 사건은 모두 운영 액션나 시계, 적용기가 낳고 감사에 남아요. 원본 레코드를 **걷어 내는** 것(kg-storage.md 3.2절)은 이 목록에 없어요. 해시가 그대로라 다시 돌린 결과가 바뀌지 않기 때문이에요.
- 테스트(kg-storage.md 7.5절)은 이 목록으로 걸어요: 빈 KG에서 같은 `ingest_order`와 같은 정의로 되풀이하면 모든 `kg_version_id`가 같다.

## 6. 리스와 실행기의 의미 버전

KG마다 적용기는 하나예요. 워커가 적용기를 쥐는 표시가 **리스**예요(`kg_apply_lease`: `kg_id`, `lease_owner`, `lease_until`, `attempt`, `semantic_version`).

- 리스를 획득할 때 `attempt`가 오르고, 일하는 동안 `lease_until`을 밀어 줘요. 쓰기는 `attempt`와 리스로 막혀요(3.1).
- **리스에는 워커가 돌리는 실행기의 의미 버전이 들어가요.** KG의 `kg_head.applied_semantic_version`보다 낮은 버전의 워커는 리스를 획득할 수 없어요. 리스를 획득한 워커가 더 높은 버전이면 `applied_semantic_version`이 오르고, 그 뒤로 낮은 버전은 적용만 못 하고 읽기와 수집은 해요. 올리는 중에 이웃한 두 버전이 함께 돌아도 같은 KG를 번갈아 적용하지 않으니 결정성이 깨지지 않아요.
- 리스가 없는 워커도 소스에서 수집, 읽기, 드라이 런은 해요.
- **표준 모델과 `sys` 타입은 마이그레이션의 한 걸음으로 저장소에 실어요.** 실행 파일은 저장소의 것을 읽어요. 실행 파일에 든 판이 벌마다 다르면 올리는 중에 메인 브랜치의 해시가 벌마다 달라지기 때문이에요.

## 7. 세대와 시점 복구

시점 복구를 하면 `applied_seq`가 뒤로 가서 같은 `change_seq`에 다른 내용이 생길 수 있어요. 엔진은 `kg_version_id`로 알아봐요(kg-storage.md 10절). 밖의 소비자는 그럴 수 없어서 **세대**를 둬요.

- `kg.generation`은 복구할 때마다 하나 올라요. 올린 때와 돌아간 `change_seq`는 `generation_event`에 남아요.
- `as_of`, 페이지네이션의 커서, 변경 알림의 이벤트 ID, `min_seq`에 세대가 실려요. `as_of`는 `(kg_id, generation, 변경 번호 또는 버전)`이에요.
- 요청의 세대가 KG의 세대와 다르면 `conflict.generation_changed`로 답해요. 소비자는 새 세대에서 다시 시작해요.
- `kg_version`에도 세대를 적어요. 복구 앞의 버전 40과 뒤의 버전 40은 세대가 달라 구별돼요.

## 8. 보관과 삭제

보관의 기본값은 [기본값 표](defaults.md)에 있어요(원본 레코드 90일, 지나간 이력 1년, 감사 3년. 가정).

| 대상 | 규칙 |
|---|---|
| `raw_record` | **닫힌 구간에만** 건다. 구간이 열린 행(내용이 안 바뀐 채 여전히 유효한 행)은 나이로 지우지 않는다. 닫힌 지 기한이 지난 행만 지운다. 나이는 닫은 `ingest_seq`의 `ordered_at`으로 센다. 어떻게 지우는지(구간째 떼기인지 청소 작업인지)는 측정해서 정한다 |
| `raw_log` | `volatile` 속성만 대는 흐름의 데이터셋은 구간이 아니라 추가만 하는 줄이다. 짧게 보관하고 `ingest_seq` 구간째 떼어 지운다. 내용 해시와 버전의 해시에 들지 않으므로 지워도 버전은 안 바뀐다. 이 기록으로 다시 돌릴 수 있는 것은 보존 기한 안뿐이다 |
| `hist`, `change_entry`, `change_batch` | `change_seq` 구간째 떼어 지운다. 지운 구간은 `kg_maintenance.min_readable_seq`로 알린다 |
| `light_change` | 짧게 보관한다(가정). `change_seq` 구간째 떼어 지운다. 늦게 따라오는 소비자는 기한 안에서만 이어 가고, 넘으면 다시 맞춘다 |
| `pending_value`, `unseen_object` | 기한이나 짝이 닫힐 때 지운다 |

- **참조가 고정된 것은 기한이 지나도 지우지 않아요.** 확정 버전이 쓴 원본 레코드와 고정된(`serving_pin`) 버전의 이력은 `min_readable_seq`가 건너뛰어요. 지워도 지금 그래프 해시는 안 바뀌어요.
- 닫힌 구간만 지우므로 2년째 안 바뀐 배치의 행은 남아요. 그 행이 다시 돌리기와 드라이 런과 값의 출처의 바탕이에요.
- 걷어 낸 기록(kg-storage.md 3.2절)은 보관과 별개로 남아요. 해시와 자리와 이유만 있는 줄이에요.

## 9. 알려진 한계와 가정

- 큰 적용 중 같은 KG의 흐름이 기다려요. 쪽의 한도와 기다림의 길이는 가정이고 클로즈드 베타에서 재요.
- 쪽의 사이에 죽으면 이어서 가거나 포기해요. 포기는 읽는 쪽이 못 본 쪽을 되감아요(4절, ADR-0025).
- 세대는 소비자가 낡은 번호를 쥐었음을 알리는 장치예요. 복구 뒤 `ingest_order`가 다시 굳을 때 처음과 같은 차례가 된다고 약속하지는 않아요.
- 낮은 버전으로 되돌아가는 배포는 리스를 획득할 수 없어요.

## 10. 미결 사항

- 낮은 버전으로 되돌릴 때 `applied_semantic_version`을 내리는 운영 액션이 필요한지.
- 쪽의 한도의 기본값, 흐름의 적용 지연의 목표.
- 짧은 보관(`light_change`, `raw_log`)의 기한 값.
