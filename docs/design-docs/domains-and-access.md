# 도메인과 권한 설계

여러 조직이 한 KG를 함께 쓸 때 누가 무엇의 주인이고, 누가 무엇을 보고 고치고 승인하는지를 정해요. 구현하는 사람이 이 문서만 보고 데이터의 모양과 경계를 알 수 있게 적어요. 결정은 ADR-0012에 있어요.

## 1. 무엇에 답하나

- 층과 도메인마다 맡은 조직이 다를 때, 하나의 KG에서 누가 무엇을 고치나요?
- 다른 조직의 층에 내 장비가 기대는 것을 잇는 정의는 누구의 것인가요?
- 서로의 층을 어디까지 보여 주고, 무엇을 가려요?
- 권한의 판단이 길마다 흩어지지 않으려면 어떻게 하나요?
- 로그인은 어떻게 하고, 사람이 떠나면 무엇이 남고, 무엇을 기록하나요?

넘겨받은 것 문서 6절의 쟁점 나(권한 수준과 도메인을 조건으로 둔다) 가운데 프락시움 쪽의 몫이에요.

## 2. 한눈에

### 2-1. 도메인과 주인

도메인은 KG의 한 구역을 맡은 조직의 단위예요. 값은 `domain_id`로 가리켜요. 플랫폼은 도메인이 아니라 예약된 자리(`platform`)예요. 도메인 사이의 일의 주인이에요.

| 주인이 있는 것 | 주인 | 비고 |
|---|---|---|
| 소스 | 도메인 하나 | 소스를 이은 조직 |
| 정의의 항목 (데이터셋, 매핑, 링크 정의, 식별 규칙) | 도메인 하나 또는 플랫폼 | 항목마다 하나 |
| 관리자가 더한 타입 | 도메인 하나 | 표준 타입은 플랫폼 |
| 표준 모델 | 플랫폼 | 제품과 함께 버전이 올라요 |
| 도메인을 가로지르는 링크 정의 | 플랫폼, 또는 양쪽 도메인의 공동 승인 | 5절 |
| 속성마다 이기는 소스의 선택 | 플랫폼 | 도메인 사이의 일이에요 |
| 문제 | 그 소스나 정의의 주인 도메인 (둘에 걸치면 양쪽) | ADR-0011 |
| 객체 | 그 객체를 만든 매핑의 도메인 | 속성을 댄 도메인들의 집합이 함께 남아요 |

### 2-2. 역할 여섯

| 역할 | 한 줄 |
|---|---|
| `platform_admin` 플랫폼 관리자 | 도메인을 만들고, 표준 모델과 플랫폼의 정의를 맡아요 |
| `domain_owner` 도메인 주인 | 자기 도메인의 무리에게 역할을 줘요. 자기 도메인의 모든 역할을 가져요 |
| `editor` 편집 | 브랜치에서 자기 도메인의 정의를 고쳐요 |
| `approver` 승인 | 병합을 승인해요. 자기가 고친 것은 못 해요 |
| `operator` 운영 | 동기화를 돌리고 안전장치의 확인을 해요 |
| `viewer` 보기 | KG를 봐요 |

권한은 (역할, 도메인)의 짝이에요. 모든 역할은 보기를 포함하고, 그 밖의 역할끼리는 서로 포함하지 않아요(편집이 승인을 포함하지 않고, 승인이 편집을 포함하지 않아요). 편집·승인·운영·보기·도메인 주인은 도메인 하나에 대해 받아요. 플랫폼 관리자는 `platform`에 대해 받아요.

### 2-3. 작은 그림

```
 로그인 쪽 ──(무리)──▶ [무리와 역할의 짝] ──▶ 주체의 (역할, 도메인) 목록
                                                   │
 HTTP API / MCP / 일꾼 ──(하려는 일, 대상)──▶ [권한의 판단: 한 곳] ──▶ 허용 / 거절 + 까닭
                                                   │
                 질의 엔진의 가림 층 ◀── 보이는 범위     [감사 기록: 추가만]
```

## 3. 도메인의 칸

### 3-1. 도메인 (`domain`)

| 칸 | 뜻 |
|---|---|
| `domain_id` | 바뀌지 않는 이름. 영어 snake_case (`facility`) |
| `display_name` | 사람이 읽는 이름 (언어별, 비어 있어도 돼요) |
| `description` | 무엇을 맡은 구역인지 한 줄 |
| `status` | `active` / `retired` |
| `hidden` | 가린 도메인인가 (참/거짓). 기본은 거짓 |
| `visible_to_roles` | 가렸을 때 볼 수 있는 역할 목록 |
| `created_by`, `created_at` | 누가 언제 만들었나 |

`platform`은 예약돼 있어서 도메인으로 만들 수 없어요.
### 3-2. 주인 도메인이 붙는 것

| 대상 | 칸 | 뜻 |
|---|---|---|
| 소스 | `owner_domain_id` | 필수 |
| 정의의 항목 | `owner_domain_id` | 필수. 값은 도메인 또는 `platform` |
| 정의의 항목 | `also_approved_by` | 공동 승인이 필요한 다른 도메인 목록 (비어 있어도 돼요) |
| 관리자가 더한 타입 | `owner_domain_id` | 필수. 표준 타입은 `platform` |
| 속성 | `sensitivity` | 민감 등급. 타입 등록부의 속성 칸에 적어요 (8-2) |
| 문제 | `owner_domain_ids` | 하나 또는 둘 |

항목마다 주인이 있어서 여러 조직이 동시에 고쳐도 부딪치는 곳이 항목 단위로 좁아요(ADR-0008).

### 3-3. 객체와 속성에 남는 "어느 도메인이 댔나"

- 객체: `owner_domain_id`(그 객체를 만든 매핑의 도메인 하나)와 `contributing_domain_ids`(속성을 댄 도메인들의 집합)를 둬요.
- 속성: 값마다 "댄 도메인"을 저장하지 않아요. 값의 출처(규칙, 매핑, 주인 도메인)를 따라가서 끌어내요. 값은 원본 기록과 규칙의 버전을 가리키기 때문에(ADR-0008) 그 길로 답이 나와요. 자리는 설비 쪽, 구성은 서버 쪽에서 대면 속성마다 답이 달라요.
- 링크: 링크 정의의 주인 도메인(또는 `platform`)으로 물어요.

## 4. 지어낸 예시: 세 도메인과 플랫폼

세 도메인이 각자 자기 층을 대요. 모두 지어낸 이름이에요.

| 도메인 | 대는 것 | 타입 (이름은 예시) |
|---|---|---|
| `facility` 설비 | 랙, 전원 | `Rack`, `PowerDistributionUnit` |
| `server` 서버 | 서버 | `PhysicalServer` |
| `network` 네트워크 | 스위치, 포트 | `NetworkSwitch`, `SwitchPort` |
| `platform` | 링크 정의, 속성마다 이기는 소스 | — |

플랫폼의 링크 정의 셋이 서버를 랙·PDU·포트에 이어요.

| 링크 정의 (예시) | 링크 타입 (예시) | 링크의 뜻 | 읽는 데이터셋 |
|---|---|---|---|
| `server_in_rack` | `INSTALLED_IN` | `contained_in` | 서버의 목록 + 설비의 랙 목록 |
| `server_powered_by_pdu` | `POWERED_BY` | `supplied_by` (자원: `power`) | 서버의 목록 + 설비의 전원 목록 |
| `server_connected_to_port` | `CONNECTED_TO` | `connected_to` | 서버의 목록 + 네트워크의 포트 목록 |

서버 `srv-0042`를 보면 속성의 주인이 갈려요.

| 객체 | 속성 | 댄 도메인 | 까닭 |
|---|---|---|---|
| `srv-0042` (`owner_domain_id: server`) | `model`, `cpu_count` | `server` | 서버 소스가 대요 |
| 같은 객체 | `rack_unit` (칸 번호) | `facility` | 자리는 설비 쪽 목록에서 와요 |
| 같은 객체 | `hostname` | `platform`의 규칙으로 이긴 소스 | 두 소스가 다르게 대면 플랫폼이 정한 소스가 이기고, 진 값은 문제 목록에 보여요 |

### 누가 무엇을 고치고 누가 승인하나

예시의 항목 이름과 짝이에요. "고치는 쪽"은 (편집, 도메인), "승인하는 쪽"은 (승인, 도메인)이에요.

| 항목 | 주인 | 고치는 쪽 | 승인하는 쪽 |
|---|---|---|---|
| 서버 소스 `server_source` | `server` | `editor` + `server` | `approver` + `server` |
| 서버 매핑 `server_mapping` | `server` | `editor` + `server` | `approver` + `server` |
| 랙·전원 소스와 매핑 | `facility` | `editor` + `facility` | `approver` + `facility` |
| 스위치·포트 매핑 | `network` | `editor` + `network` | `approver` + `network` |
| 링크 정의 `server_in_rack` (플랫폼) | `platform` | `editor` + `platform` | `approver` + `platform` |
| 같은 링크 정의를 공동 승인으로 두면 | `server`, `also_approved_by: [facility]` | `editor` + `server` | `approver` + `server` 그리고 `approver` + `facility` |
| `PowerDistributionUnit`에 서버실의 관리 번호 속성을 더한 하위 타입 | `facility` | `editor` + `facility` | `approver` + `facility` |
| 속성마다 이기는 소스의 선택 | `platform` | `editor` + `platform` | `approver` + `platform` |

- 서버 도메인의 편집은 설비 도메인의 항목을 고치지 못해요. 링크 정의가 설비의 목록을 읽는다고 그 목록의 주인이 바뀌지 않아요.
- 한 브랜치가 여러 항목을 고치면, 항목마다 그 항목의 승인이 필요해요. 한 사람이 편집한 항목은 그 사람이 승인하지 못해요.

## 5. 도메인을 가로지르는 정의

도메인을 가로지르는 링크가 KG의 값이에요. 그 링크 정의는 양쪽 데이터셋을 읽어요. 두 가지 모양이 있어요.

| 모양 | 주인 | 승인 | 언제 쓰나 |
|---|---|---|---|
| 플랫폼의 정의 | `platform` | `approver` + `platform` | 여러 도메인에 걸친 표준적인 이음 (서버를 랙에 잇기) |
| 공동 승인하는 정의 | 한 도메인 | 주인 도메인과 `also_approved_by`의 도메인, 모두 | 두 도메인이 직접 정하고 싶은 이음 |

- 못 이은 링크의 문제는 양쪽 도메인에 보여요(ADR-0011). 서버 쪽 장비가 설비 쪽 랙을 가리키는데 랙이 없으면, 서버와 설비 양쪽 문제 목록에 올라요.

## 6. 역할의 권한

### 6-1. 무엇을 할 수 있나 × 역할

`●`는 할 수 있다는 뜻이에요. 도메인 주인은 자기 도메인에서, 편집·승인·운영·보기는 받은 도메인에서만이에요. 플랫폼 관리자는 모든 도메인과 `platform`에서 모든 역할을 할 수 있어요(막힌 일을 풀기 위해서예요). 그렇게 한 일은 감사 기록에 따로 표시돼요(11절). 빈 칸은 할 수 없어요.

| 하려는 일 | 플랫폼 관리자 | 도메인 주인 | 편집 | 승인 | 운영 | 보기 |
|---|---|---|---|---|---|---|
| 객체와 링크 보기 (열린 것) | ● | ● | ● | ● | ● | ● |
| `restricted` 속성의 값 보기 | ● | ● (자기 도메인) | ● (자기 도메인) | ● (자기 도메인) | ● (자기 도메인) | 허가가 있으면 |
| `confidential` 속성의 값 보기 | 허가가 있으면 | 허가가 있으면 | 허가가 있으면 | 허가가 있으면 | 허가가 있으면 | 허가가 있으면 |
| 가린 도메인 보기 | 도메인의 `visible_to_roles`에 따라 | | | | | |
| 대량으로 읽기 | 허가가 있으면 | 허가가 있으면 | 허가가 있으면 | 허가가 있으면 | 허가가 있으면 | 허가가 있으면 |
| 도메인 만들기, 도메인 주인 정하기 | ● | | | | | |
| 가린 도메인 설정 (도메인 주인의 요청으로) | ● | | | | | |
| 무리에게 역할 주기 | ● | ● | | | | |
| 민감 보기 허가·대량 읽기 허가 주기 | ● (전체) | ● (자기 도메인) | | | | |
| 시스템 계정 만들기 | ● | ● | | | | |
| 브랜치를 열고 정의 고치기 | ● | ● | ● | | | |
| 후보 실행과 차이 보기 | ● | ● | ● | ● | ● | |
| 병합 승인 (자기가 고친 것은 제외) | ● | ● | | ● | | |
| 병합 실행 (그 브랜치의 편집이나 승인) | ● | ● | ● | ● | | |
| 동기화 돌리기 | ● | ● | | | ● | |
| 안전장치의 확인 | ● | ● | | | ● | |
| 정의 내보내기 | ● | ● | ● | | | |
| 문제 목록 보기 | ● | ● | ● | ● | ● | ● |
| 표준 모델 고치기 | ● | | | | | |
| 감사 기록 읽기 | ● | ● (자기 도메인) | | | | |

- 허가(민감 보기, 대량 읽기)는 보기 역할에 더하는 따로의 권한이에요(8-2, 10-2).
- `platform`의 정의도 브랜치와 병합을 거쳐요. 같은 사람이 같은 항목을 고치고 승인하지는 못해요. 도메인 주인과 플랫폼 관리자도 마찬가지예요.
- 정의 내보내기는 "그 도메인의 편집 역할 이상"으로 읽어서 도메인 주인과 플랫폼 관리자가 들어가요.

### 6-2. 플랫폼의 것과 도메인의 것

| 종류 | 주인 | 누가 맡나 |
|---|---|---|
| 표준 모델의 타입 | 플랫폼 | `platform_admin` |
| 도메인 사이의 링크 정의 | 플랫폼 | `platform`의 편집·승인 |
| 속성마다 이기는 소스의 선택 | 플랫폼 | `platform`의 편집·승인 |
| 도메인 만들기 | 플랫폼 | `platform_admin` |
| 소스, 데이터셋, 매핑, 식별 규칙 | 도메인 | 그 도메인의 편집·승인 |
| 관리자가 더한 타입 | 도메인 | 그 도메인의 편집·승인 |
| 동기화와 안전장치의 확인 | 소스의 주인 도메인 | 그 도메인의 운영 (`platform`의 정의를 고쳐서 생긴 차이는 `platform`의 운영) |

### 6-3. 시스템 계정

사람이 아닌 시스템이 KG를 읽을 때(다른 조직의 도구, 에이전트)는 시스템 계정을 써요. 같은 역할을 받아요.

칸: `account_id`, `display_name`, `description`, `roles`((역할, 도메인)의 목록. 사람과 같은 모양), `rate_limit`(부르는 쪽마다의 한도, ADR-0010), `credential_ref`(비밀 저장소를 가리키는 참조만, 값은 저장하지 않아요), `status`(`active` / `disabled`), `created_by`, `created_at`.

시스템 계정은 도메인 주인(자기 도메인)이나 플랫폼 관리자가 만들어요. 사람에게 바로 역할을 주는 것은 시스템 계정과 비상용 계정뿐이에요. 자기가 고친 것을 자기가 승인하지 못하는 규칙은 같아요.

## 7. 권한의 판단은 한 곳에서

### 7-1. 구조

HTTP API, MCP, 일꾼, 질의 엔진의 가림 층이 모두 같은 판단을 불러요. 길마다 권한을 따로 적지 않아요. 판단은 코어의 한 단위가 맡고, 그 단위는 다른 단위를 읽지 않아요(ADR-0006).

정책은 데이터예요. 코드에 `if`로 흩어 적지 않고, 규칙의 표로 두고 한 곳에서 풀어요. 정책 데이터(어느 역할이 무엇을 할 수 있나)는 제품에 들어 있고 관리자가 고치지 못해요. 관리자가 고치는 것은 "누구(무리)에게 어느 역할을 어느 도메인에서"뿐이에요. 역할을 새로 만드는 일은 결정 기록으로만 해요.

### 7-2. 판단의 입력과 출력
| 입력 | 뜻 |
|---|---|
| `subject` | 누구인가: 사람 또는 시스템 계정. 이름과 종류 |
| `groups` | 로그인 쪽에서 온 무리의 목록 (시스템 계정은 비어 있어요) |
| `role_pairs` | 무리와 계정에 걸린 (역할, 도메인)의 목록. 무리와 역할의 짝에서 풀어요 |
| `grants` | 무리에 걸린 허가의 목록 (민감 보기, 대량 읽기) |
| `action` | 하려는 일 (6-1의 행) |
| `target_owner_domain_id` | 대상의 주인 도메인 (또는 `platform`) |
| `target_sensitivity` | 대상 속성의 민감 등급 (없으면 비어 있어요) |
| `context` | 승인이라면 고친 사람, 공동 승인이라면 아직 안 받은 도메인 |

| 출력 | 뜻 |
|---|---|
| `decision` | `allow` / `deny` |
| `reason` | 까닭. 닫힌 목록의 코드와 사람이 읽는 문장 |
| `matched_rule` | 어느 규칙이 걸렸나 |

까닭의 코드 (예시): `role_not_held_for_domain`, `self_approval_not_allowed`, `domain_hidden`, `sensitivity_grade_not_allowed`, `joint_approval_pending`, `no_rule_allows`.

규칙은 이런 모양이에요.

| 칸 | 뜻 |
|---|---|
| `action` | 어떤 일에 대한 규칙인가 |
| `required_role` | 필요한 역할 |
| `domain_scope` | 짝의 도메인이 대상의 주인 도메인과 같아야 하나, `platform`이어야 하나, 도메인을 안 따지나 |
| `conditions` | 덧붙는 조건 (`actor_is_not_editor_of_change`, `grade_allowed_for_role` 등) |

허용하는 규칙이 하나도 없으면 거절해요(`no_rule_allows`). 허용과 거절이 어긋나는 규칙은 두지 않아요.

### 7-3. 예
서버 도메인의 승인이 `server_mapping`의 변경을 승인하려고 해요.

```
subject:  user-a (무리: server-approvers)
role_pairs: [(approver, server)]
action:   approve_merge
target_owner_domain_id: server
context:  change_edited_by = user-b
→ allow   matched_rule: approve_merge.same_domain
```

같은 사람이 `server_in_rack`(주인은 `platform`)을 승인하려고 하면 `role_not_held_for_domain`으로 거절돼요. 자기가 고친 변경을 승인하려 하면 `self_approval_not_allowed`로 거절돼요.

## 8. 보기

### 8-1. 기본으로 열려 있어요
객체와 링크는 기본으로 모든 보기 역할에 보여요. 다른 조직의 층에 내가 기대는지를 보려면 그 층이 보여야 해요. 가리는 것은 둘뿐이에요.

### 8-2. 민감한 속성

속성마다 `sensitivity`(민감 등급)가 타입 등록부에 적혀 있어요. 등급이 없는 속성은 기본으로 열려 있어요.

등급은 닫힌 목록 셋이에요.

| 등급 | 뜻 | 값을 볼 수 있는 쪽 |
|---|---|---|
| `open` | 기본. 등급을 안 붙인 것 | 모든 보기 역할 |
| `restricted` | 주인 도메인 안에서 필요한 것 | 그 도메인의 편집·승인·운영·도메인 주인, 그리고 "민감 보기 허가"를 받은 무리 |
| `confidential` | 더 좁게 | "민감 보기 허가"를 받은 무리만 |

민감 보기 허가(`sensitive_view`)는 (무리, 도메인, 등급)의 짝이고 그 도메인의 도메인 주인이 줘요. `confidential`의 허가는 플랫폼 관리자의 승인도 필요해요.

가려진 속성은 없는 것처럼 빠지지 않고 "가려짐"으로 보여요. 속성이 있다는 것은 알지만 값은 모르는 모양이에요.

```
get  PhysicalServer srv-0042
  hostname:        "srv-0042"                  grade: fact
  model:           "model-x"                   grade: fact
  management_addr: { masked: true, reason: sensitivity_grade_not_allowed }
```

가려진 속성을 찾기(`find`)의 조건으로 쓰면 그 조건을 거절해요. 오류가 "이 속성은 가려져 있다"고 말해요. 조용히 걸러 주지 않아요. 있고 없음으로 값이 새기 때문이에요.

### 8-3. 가린 도메인

도메인 전체를 정해진 역할에만 보이게 할 수 있어요(`hidden`, `visible_to_roles`). 플랫폼 관리자가 도메인 주인의 요청으로 정하고, 감사 기록에 남아요. 보이지 않는 사람에게는 그 도메인이 주인인 객체의 내용이 가려져요. 영향 범위의 답에서는 "가려진 객체 몇 개"로만 드러나요.

### 8-4. 영향 범위가 가려진 객체를 지날 때

영향 범위는 정확성을 위해 전체 그래프에서 계산해요. 답을 내보낼 때 가려요(ADR-0010의 질의 엔진). 가려진 객체를 지나가면 이렇게 답해요.

```
impact  of: srv-0042-pdu
  version: kg-v0381   freshness: 2 hours ago
  affected:
    - PhysicalServer srv-0042          dies    grade: fact
    - PhysicalServer srv-0043          dies    grade: fact
  passed_through_masked: { count: 3 }
  affected_masked: { count: 1 }   # 영향받는 쪽에 가려진 객체가 있을 때
  note: "가려진 객체 3개를 지났어요. 내용은 보이지 않아요."
```

- 가려진 객체가 지나는 길에 있든 영향받는 끝에 있든 같아요. "가려진 객체 N개"로 수만 주고, 이름, 타입, 주인 도메인은 주지 않아요. 수조차 새면 안 되는 도메인은 지금 다루지 않아요(13절).

### 8-5. 투영의 가림 층
질의 엔진은 DB의 행 단위 권한을 지나쳐요. 그래서 엔진에 가림 층이 따로 있어요. 권한의 판단이 만든 호출자의 보이는 범위(주인 도메인과 민감 등급)를 받아 답을 만들 때 가려요. 질의의 자세한 것은 `kg-queries.md`에 있어요.

## 9. 브랜치와 병합에서의 권한

- **편집과 승인이 나뉘어요.** 정의를 고치는 것은 편집, 병합을 허락하는 것은 승인이에요. 고친 사람은 그 변경을 승인하지 못해요.
- **승인은 항목의 주인 도메인에서 와요.** 브랜치가 여러 도메인의 항목을 고쳤으면 도메인마다 승인이 필요해요.
- **도메인을 가로지르는 정의**는 플랫폼의 승인, 또는 5절의 공동 승인이에요.
- **병합 직전의 다시 하기.** 병합 직전에 운영의 최신 정의 위에서 후보 실행을 다시 하고 안전장치를 거쳐요(ADR-0008). 그 사이에 승인 뒤 항목이 바뀌었으면 그 항목은 다시 승인을 받아요.
- **병합의 실행**은 승인이 모두 있고 후보 실행과 안전장치를 지난 뒤에, 그 브랜치의 편집이나 승인 역할을 가진 사람이 해요.
- **안전장치의 확인**은 운영이 해요. 처음 적용과, 정의를 고친 뒤 첫 적용에 사람이 차이를 보고 확인해요. 자세한 것은 `ingestion.md`에 있어요. 소스의 주인 도메인의 운영이 확인하고, `platform`의 정의를 고쳐서 생긴 차이는 `platform`의 운영이 확인해요.
- **같은 항목을 두 브랜치가 고치면** 늦은 쪽이 멈추고 사람이 골라요.

## 10. 로그인

### 10-1. 포트 뒤에 있어요

코어는 "로그인된 주체와 그 무리"만 알아요. 로그인 방식은 포트 뒤의 어댑터가 맡아요. 어댑터는 표준 방식(OIDC)을 말해요. 특정 SSO 제품에 묶이지 않아요. 같은 포트에 다른 어댑터를 꽂을 수 있어요.

어댑터가 코어에 넘기는 것: `subject_id`(로그인 쪽이 정한, 바뀌지 않는 사람의 식별자), `display_name`, `groups`(로그인 쪽에서 온 무리의 이름 목록), `issued_at`과 `expires_at`(이 로그인이 유효한 시간).

### 10-2. 무리와 역할의 짝

프락시움은 사람의 목록을 쥐지 않아요. 무리와 역할의 짝만 가져요. 역할은 무리에 줘요. 사람에게 바로 주는 것은 시스템 계정과 비상용 계정뿐이에요.

칸: `group_name`(로그인 쪽 무리의 이름 그대로), `role`(여섯 중 하나), `scope`(`domain_id` 또는 `platform`), `granted_by`, `granted_at`.

도메인 주인이 자기 도메인의 짝을 더하고 빼요. 처음 도메인을 만들 때는 플랫폼 관리자가 도메인 주인의 짝을 정해요.

허가의 칸: `group_name`, `kind`(`sensitive_view` / `bulk_read`), `domain_id`, `grade`(`sensitive_view`일 때), `granted_by`, `approved_by`(`confidential`일 때 플랫폼 관리자), `granted_at`. 대량 읽기 허가는 도메인 주인(자기 도메인의 범위)이나 플랫폼 관리자(전체)가 주고 감사 기록에 남아요.

### 10-3. 사람이 떠났을 때

- 로그인 쪽에서 그 사람을 무리에서 빼면, 다음 로그인(또는 기존 로그인이 끝나는 때)부터 권한이 없어져요. 프락시움에는 사람 목록이 없어서 지울 것이 없어요.
- 그 사람이 남긴 감사 기록은 그대로예요. 열어 둔 브랜치도 남아요. 기존 로그인을 얼마나 일찍 끊을 수 있는지는 로그인 쪽 방식과 `expires_at`에 달렸어요.

### 10-4. 시스템 계정의 로그인

시스템 계정의 인증도 로그인 포트 뒤에 둬요. 로그인 쪽이 시스템용 자격을 주면 그것을 써요. 아니면 프락시움이 낸 토큰을 써요. 토큰은 해시로만 저장하고 만료와 교체가 있어요.

## 11. 감사 기록

### 11-1. 적는 것과 적지 않는 것

- 적는 것: 플랫폼 관리자가 제 역할 밖의 도메인에서 한 일(따로 표시) / 허가를 준 것 / 정의를 고친 것(누가, 어느 항목, 어느 브랜치) / 승인과 거절 / 병합과 되돌리기 / 정의와 KG의 범위를 내보낸 것 / 민감한 속성을 읽은 것 / 대량으로 읽기 / 역할을 주거나 뺀 것, 도메인을 만들거나 가린 것 / 안전장치의 확인.
- 거절된 시도는 고치는 일과 민감한 속성·대량 읽기에 대해서만 적어요. 보통의 보기 거절은 적지 않아요.
- 적지 않는 것: 누가 무엇을 보았는지(양이 감당되지 않아요) / 민감한 속성의 값 / 비밀 값 / 행의 내용.

### 11-2. 기록의 칸

| 칸 | 뜻 |
|---|---|
| `audit_id` | 기록 하나의 식별자 |
| `occurred_at` | 언제 |
| `actor_kind` | `person` / `system_account` |
| `actor_id` | 로그인 쪽의 `subject_id` 또는 `account_id` |
| `action` | 닫힌 목록의 일 이름 (`edit_definition`, `approve_merge`, `export_definition`, `read_sensitive`, `bulk_read` 등. 예시) |
| `target_kind`, `target_id` | 무엇에 한 일인가 |
| `target_domain_id` | 대상의 주인 도메인 |
| `role_pair_used` | 어느 (역할, 도메인)의 짝이 허락했나 |
| `outcome` | `allowed` / `denied` |
| `admin_override` | 플랫폼 관리자가 제 역할 밖에서 한 일인가 (참/거짓) |
| `branch_id`, `definition_version` | 정의를 고친 일이면 어느 브랜치, 어느 버전 |
| `detail` | 건수 같은 요약. 값은 넣지 않아요 |
| `request_id` | 한 요청의 이름표 (로그와 이어 보려는 것) |

### 11-3. 추가만 해요
기록은 더하기만 하고 고치거나 지우지 않아요(ADR-0011의 "기록은 추가만"). 보관 기한은 설정 값이고, 기본값은 가정이에요. 기록은 잃으면 안 되는 것의 등급이에요.

## 12. 알파에서의 범위

- 백엔드의 권한 모델을 다 만들어요: 도메인, 주인의 열쇠, 여섯 역할과 짝, 권한의 판단, 민감 등급과 가린 도메인, 엔진의 가림 층, 로그인 포트와 OIDC 어댑터, 시스템 계정, 감사 기록.
- 화면은 플랫폼 관리자와 보기 역할로 시험할 수 있는 만큼만 둬요. 나머지는 계약(HTTP API)으로 시험해요(ADR-0006).

## 13. 알고 가는 한계와 아직 정하지 않은 것

### 알고 가는 한계
- "가려진 객체 N개"의 수 자체가 정보일 수 있어요. 수를 주는 것이 결정이고, 수조차 새면 안 되는 도메인은 지금 다루지 않아요.
- 플랫폼의 정의는 편집과 승인을 다른 사람이 해야 하므로 플랫폼 영역에 두 사람 이상이 있어야 병합돼요.
- 누가 무엇을 보았는지를 안 적어서, 열린 값을 누가 읽었는지는 사고 뒤에도 알 수 없어요.
- 플랫폼 관리자는 모든 도메인에서 모든 역할을 할 수 있어요. 막힌 일을 풀기 위해서이고, 감사 기록의 표시로 지켜봐요.

### 아직 정하지 않은 것
- 도메인의 위아래 관계. 도메인을 다른 도메인 안에 둘 수 있는지, 있다면 권한이 아래로 내려가는지.
- 도메인이 나뉘거나 합쳐질 때. 주인이 바뀌는 객체와 정의의 항목, 이력에 남는 주인, 권한의 짝과 허가를 어떻게 옮기는지.
