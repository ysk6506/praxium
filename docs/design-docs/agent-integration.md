# 상시 가동 에이전트와 프락시움

글 "Building always-on agents"(2026-11-13, <https://claude.com/ko/resources/articles/building-always-on-agents>)가 그리는 상시 가동 에이전트가 프락시움에 붙을 때, 프락시움의 어느 부분이 어떤 계약을 지키는지를 정한 설계예요. 결정은 ADR-0074에 있어요. **이 문서는 아직 구현하지 않은 설계(예정)예요.** 이벤트 스트림, 게이트웨이, KG 읽기 MCP 툴은 코드가 없어요. 예시의 이름과 숫자는 지어낸 것이에요. 끊긴 프로세스를 이어 가는 맥락은 [끊긴 프로세스를 이어 가기](agent-resume-context.md)에 따로 있어요.

이 문서에서 글의 "run"은 **하네스 세션**(에이전트가 한 번 깨어 일하는 구간)으로 적어요. **실행**은 저장소의 뜻으로만 써요. 게이트웨이의 실행(업무 요청 하나의 계약, [게이트웨이 설계](gateway.md) 5절)과 동기화 실행(수집 한 번의 기록, [수집 서비스와 실행](ingestion-service.md) 8절)이 그 둘이에요. 글의 수신함, 타이머, 발신함, 메모리는 글의 구조를 가리킬 때만 쓰고, 프락시움의 것은 저장소의 낱말(이벤트 스트림, 알림 발송, 일정, 리스)로 적어요.

## 1. 목적과 다루는 질문

| 쟁점 | 답 |
|---|---|
| 끊긴 프로세스를 어떻게 이어 가나 | 맥락 읽기 한 번으로 이어 가요. 대장이 진실이고 에이전트의 작업 노트는 맡지 않아요(6.4절, [이어 가기](agent-resume-context.md)) |
| 프락시움이 에이전트를 실행하나 | 아니에요. 에이전트 쪽의 스토리지(수신함, 타이머, 메모리, 발신함)도 만들지 않아요(3절) |
| 글의 구조에서 프락시움은 무엇인가 | 외부 구성요소 4가지예요. 이벤트를 발행하는 쪽, 조회하는 곳, 자격 증명 프록시와 승인 대기, 프락시움이 사람과 시스템에 내보내는 것이에요(2절) |
| 에이전트가 이벤트를 어떻게 받나 | 이벤트 스트림과 `since` 조회예요. 정확성은 풀 방식에 있어요(4절) |
| 승인을 기다리는 동안 하네스 세션을 열어 둬야 하나 | 아니에요. 닫아도 되고 이벤트나 폴링으로 이어 가요(5절) |
| 에이전트는 무엇을 메모리에 두나 | 다시 찾아볼 수 없는 것만 두고 나머지는 참조를 둬요(6절, 10절) |
| 툴 정의를 왜 고정하나 | 모델의 프롬프트 캐시 때문이에요(7절) |
| 에이전트가 토큰을 만지지 않을 수 있나 | 네. 프록시가 헤더를 붙이는 배치를 막지 않아요(8절) |
| 내보내기와 일정은 | 원칙만 정하고 각 설계의 결정이 정해요(9절) |

## 2. 지도: 글의 다섯 요소와 프락시움의 구성요소

| 글의 요소 | 에이전트 쪽의 일 | 프락시움이 주는 것 | 문서 |
|---|---|---|---|
| 이벤트 수신함 | 이벤트를 내구성 있게 받아 두고, 중복을 거르고, 묶어서 하네스 세션을 연다 | 이벤트를 발행하는 쪽. 이벤트 스트림, `since` 조회, 의도와 실행과 동기화 실행의 상태 이벤트 | 이 문서 4절, [REST API](rest-api.md) 3-10 |
| 타이머 | 에이전트가 건 기한(후속 확인)과 반복 작업을 자기 스토리지에 둔다 | `poll_after_ms` 힌트. 대장에 있는 것(승인된 뒤의 유효 시간, 깨어나지 않는 에이전트)의 기한. 프락시움 안의 일정은 스케줄러 | 이 문서 5절, 9절, [KG 운영](kg-operations.md) 4.4 |
| 메모리 | 사용자 지시, 사용자 메모, 보고한 것, 진행 기록, 메모리 정리 | 조회하는 곳. KG와 실행 대장, 참조의 계약, 맥락 읽기 툴, 고정된 툴 정의 | 이 문서 6절, 7절, [게이트웨이 설계](gateway.md) 7절, [KG 읽기 MCP](kg-mcp.md) |
| 권한 | 에이전트의 실행 환경을 가두고 우회를 막는다(조직의 책임) | 자격 증명 프록시의 위치인 게이트웨이, 승인 대기와 이어받음, 서비스 계정과 토큰 | 이 문서 5절, 8절, [게이트웨이의 안전](gateway-safety.md) |
| 발신함 | 사용자에게 보내는 메시지와 속도 조절 | 프락시움 자신이 사람에게 내보내는 것(알림, 승인 요청, 변경 알림)과 호출 이력의 내보내기 | 이 문서 9절, [데이터 관측성](data-observability.md) 8.5절 |

프락시움 안의 상시 실행되는 부분(수집 서비스와 워커)도 글의 수신함과 타이머와 같은 문제를 풀어요. 실행 기록이 진실의 원천이고, 소스마다 하나만 돌고, 리스와 시도 번호로 늦게 깬 쓰기를 막고, 일정은 따로 설계하고, 그 설계가 따를 원칙은 9.2절에 있어요([KG 운영](kg-operations.md) 4.4, [수집 서비스와 실행](ingestion-service.md)).

## 3. 프락시움의 역할과 유지하는 것

### 3.1 유지하는 것과 이유

| 유지하는 것 | 글과 다른 점 | 이유 |
|---|---|---|
| 바꾸는 호출을 스스로 다시 보내지 않는다 | 글은 하네스 세션이 죽으면 새 워커가 같은 이벤트를 다시 처리해도 된다고 한다 | 다시 처리는 읽기와 멱등한 일에 맞다. 현실을 바꾸는 호출은 결과를 모르면 "모름"이고 사람에게 넘긴다. 의도마다 실행을 한 번만 내주는 대장이 겹쳐 깬 세션도 막는다 |
| 하네스의 세션 저장과 재개에 기대지 않는다 | 글은 호출을 보류하고 저장된 세션을 재개한다 | 하네스마다 다르고 재개한 호출은 한 번 이상 실행될 수 있다. 에이전트가 세션을 재개하든 새로 열든 프락시움에서는 같은 일이다(이어가기 번호와 맥락 읽기 툴) |
| 분류기에 의한 자동 승인이 없다 | 글은 분류기를 쓰는 자동 모드를 사례로 든다 | 글도 가장 중요한 결정은 사람이 본다고 한다. 결정적 조건 판단과 사람의 승인으로 한다 |
| 에이전트의 스토리지를 만들지 않는다 | 글의 다섯 요소는 거의 모두 에이전트 쪽에 있다 | 프락시움은 에이전트를 실행하지 않는다. 예외는 프락시움의 대장에 있는 것(의도, 실행)의 기한뿐이고 프락시움이 잰다 |
| 이벤트로 시작하는 실행은 읽기만 하는 프로세스에 한한다(REQ-527) | 글의 웹훅과 타이머는 권한 안에서 행동한다 | 실행의 시작이 곧 권한이다. 사람 없이 현실을 바꾸는 실행을 시작할 수 없다 |

### 3.2 새로 정하는 것

별도의 조율 서비스나 내구 실행 엔진을 들이지 않아요. 이벤트의 순번, 일정, 기한, 전달 상태는 스토리지 안의 기록과 워커의 한 부분이 처리해요(ADR-0011 결정 4의 둘째 원칙, [KG 운영](kg-operations.md) 3.4의 2번). 방향 메모는 "필요한지는 구체화할 때 측정"이라고 적었는데, 이 결정이 측정 전의 기본을 정해요. 스토리지 안의 처리로 모자라다고 측정되면 새 결정 기록으로 다시 열어요.

### 3.3 하지 않는 것

- 에이전트의 수신함, 타이머, 메모리 스토리지, 발신함, 사용자 지시, 사용자 메모, 보고한 것의 기록, 메모리 정리.
- 분류기에 의한 자동 승인, 하네스의 세션 재개에 기대기, MCP Apps의 승인 카드(5.3절), 내구 실행 엔진.
- 웹훅의 순서 보장과 정확히 한 번 전달.

## 4. 이벤트의 계약

이벤트는 알림이에요. 진실은 자원(대장, 실행 기록, 변경 시퀀스, 문제 목록)이고, 이벤트를 받은 쪽이 자원을 다시 읽어요([REST API](rest-api.md) 3-10).

### 4.1 모든 이벤트가 지키는 것

| 규칙 | 내용 |
|---|---|
| 같은 사건은 같은 `event_id` | 스트림으로 받아도 `since`로 조회해도 같아요. 받는 쪽이 중복을 거르는 키예요 |
| 목록에 정한 필드만 싣는다 | 종류마다 필드의 목록이 있어요. 정해진 값 목록의 상태, 진행률, 건수, 사람이 지은 id는 실려요. 소스에서 온 값과 자유 서식 텍스트는 싣지 않아요. 새 규칙이 아니라 [데이터 관측성](data-observability.md) 12절의 규칙이에요. 내보내는 모든 필드가 목록에 있는지를 테스트가 확인해요 |
| 인젝션의 통로를 줄인다 | 소스의 값이 이벤트로 나가지 않으므로 이벤트가 값을 퍼뜨리지 않아요. 사람이 지은 id는 실리므로 완전한 방어는 아니에요 |
| 가리키는 것은 참조다 | 이벤트는 종류 표(4.4절)가 정한 참조(작업 ID, 실행 ID, 의도 ID, 동기화 실행의 `id` 등)를 싣고, 받은 쪽이 그 참조로 프락시움에서 다시 읽어요(6절) |

### 4.2 `event_id`와 `since`

- `event_id`가 스트림의 위치예요. `since`와 `Last-Event-ID`는 `event_id`를 받아요([REST API](rest-api.md) 3-10, ADR-0016). 따로 드러내는 순번 필드는 없어요.
- 읽는 쪽에게 `event_id`는 **불투명한 값**이에요. 같은지 비교(중복 제거)와 `since`로 되돌려 주는 데만 쓰고, 크기를 비교하거나 빈틈을 판단하는 데 쓰지 않아요.
- 보장의 근거는 하나예요. 서버는 커밋된 순서까지만 내줘요. 이벤트는 여러 주체(작업, 제안, 의도, 알림, 동기화 실행)가 동시에 쓰므로 번호를 먼저 받은 쓰기가 나중에 커밋될 수 있어요. 커밋된 순서까지만 내주면 `since` 뒤를 이어 읽을 때 뒤늦게 커밋된 앞의 이벤트가 빠지지 않아요. KG의 읽기 워터마크(`readable_through`)와 같은 성질이에요. 구현은 이벤트 스트림을 만드는 변경이 정해요.
- 걸러 받는 계정에게 **가려진 이벤트의 수가 드러나지 않아야 해요.** 건수는 가려진 것을 뺀 수라는 원칙이에요(ADR-0016 결정 12). `event_id`의 값을 그렇게 만드는 방법은 구현 단계에서 정해요(11절).
- 의도와 실행의 이벤트가 KG별 순서에 드는지 배포 단위의 순서에 드는지는 정하지 않았어요. 조건은 둘이에요. 한 스트림에서 `since` 하나로 이어 받을 수 있어야 하고, 승인 이벤트가 빠지지 않아야 해요(11절). 동기화 실행의 이벤트는 그 KG의 순서에 들어요. 배포에 하나인 이벤트(작업, 제안, 정의)의 순서도 아직 정하지 않았어요(11절).
- 시점 복구로 세대가 바뀐 뒤의 `event_id`는 `conflict.generation_changed`예요.

### 4.3 보존 기한이 지났을 때

`since`가 가리키는 이벤트가 보존 기한을 넘겨 지워졌으면 `stale.since_too_old`로 답해요. 읽는 쪽은 이벤트를 이어 받지 않고 **현재 상태를 다시 읽어요**. 에이전트가 다시 읽을 상태는 자기 서비스 계정에 열린 실행과 의도의 목록(REQ-539, [이어 가기](agent-resume-context.md))과 자기가 보는 KG의 현재 값이에요. KG의 값을 읽는 방법은 질의의 설계를 따라요. 보존 기한은 승인 대기 시간과 승인된 뒤의 유효 시간의 합보다 길어요(설정을 읽을 때 검사해요). 그래야 에이전트가 잠든 동안의 승인 이벤트가 보존 기한 안에 남아요. 놓쳐도 `stale.since_too_old`로 알고 다시 읽으면 돼요. 값은 측정해서 정하는 가정이에요([기본값 표](defaults.md)에 더해요).

### 4.4 종류

지금 표([REST API](rest-api.md) 3-10)의 종류는 그대로예요. 에이전트가 기다리는 것을 더해요. 대장의 상태 가운데 기다리는 쪽이 알아야 하는 것은 모두 이벤트가 있어요. 이름은 각 구현 단계가 표에 정해요.

| 그룹 | 상태 변화 | 가리키는 것 | 만드는 단계 |
|---|---|---|---|
| 의도(게이트웨이) | 승인 대기가 됨, 승인됨, 거절됨, 만료됨, 취소됨, 끝남, 확인 결과가 나옴, 모름이 됨 | 의도 ID, 실행 ID | 게이트웨이의 구현 |
| 실행(게이트웨이) | 시작됨, 닫힘 | 실행 ID | 게이트웨이의 구현 |
| 동기화 실행(수집) | 확인 대기가 됨, 끝남, 실패 | 동기화 실행의 `id`와 상태 전이의 순번 | 이벤트 스트림을 만드는 변경 |

동기화 실행의 이벤트는 실행 기록의 상태 전이 순번을 써요. 이 순번은 ADR-0058의 설계에 이미 있어요([수집 서비스와 실행](ingestion-service.md) 8절). 화면은 이벤트가 없어도 실행 기록을 다시 읽어서 상태를 보므로, 이벤트 스트림은 지금 구현하는 경로의 선행 조건이 아니에요.

### 4.5 구독의 권한

- 이벤트는 그 계정이 읽을 수 있는 것에 관한 것만 나가요. `kg_changed`의 타입별 건수가 읽는 주체마다 다른 것과 같은 읽기 필터예요.
- 연결이 열려 있는 동안에도 계정의 상태와 토큰의 만료를 확인해요. 비활성화하거나 토큰을 회수한 계정, 토큰이 만료된 계정에는 이벤트가 나가지 않아요(스토리지가 정상이면 30초 안에 전파돼요. [권한](access-control.md) 11절).
- 이벤트 스트림의 연결은 계정마다 따로 세요. 계정마다 이벤트 스트림 연결 수의 한도가 따로 있고 넘으면 거절해요(값은 가정). 상시 가동 에이전트는 연결 하나를 계속 열어 두므로, 계정별 동시 요청의 한도([REST API](rest-api.md) 3-11)와는 따로 세요.
- 계정이 **자기 의도와 자기 실행**에 관한 이벤트를 받는 것은 역할과 범위가 아닌 소유에 따른 읽기 규칙이에요. 작업의 "생성자" 규칙이 선례예요. 권한 설계에 새 규칙으로 더해야 하므로 게이트웨이의 결정이 정해요. 이 결정은 조건만 적어요. 의도와 실행의 이벤트는 코어의 `/v1/events`로 받는데 게이트웨이는 다른 주소와 다른 인증이므로, 코어의 서비스 계정과 게이트웨이 쪽 신원이 같은 계정이라는 전제가 필요해요. 이 전제도 같은 규칙과 함께 정해요(11절).
- 이벤트는 REST로만 받아요. `/mcp`에는 SSE가 없어요([KG 읽기 MCP](kg-mcp.md) 1절). 읽기만 하는 서비스 계정(`viewer`)의 토큰으로 `/v1/events`를 읽어요.

### 4.6 웹훅은 나중이고 조건이 있다

지금은 설계하지 않아요. 풀 방식(스트림과 `since`)으로 충분하고, 에이전트 쪽에서 나가는 연결이라 내부망의 하네스도 붙어요. ADR-0010이 "푸시를 먼저"를 버렸고 변경 알림은 풀 방식을 먼저 줘요([KG 질의](kg-queries.md)의 변경 알림). 길게 떠 있는 리스너를 둘 수 없는 실행 환경에는 웹훅이 필요하지만 뒤의 일이에요. 붙인다면 변경 알림의 포트(ADR-0009 결정 11) 뒤의 어댑터 하나이고, 그때 지킬 조건은 이래요.

| 조건 | 이유 |
|---|---|
| 구독은 서비스 계정 하나에 묶고 전달할 때마다 읽기 필터와 계정 상태를 확인한다 | 등록한 사람이 읽을 수 없는 것을 받지 못하게 하고, 비활성화한 계정의 구독이 계속 나가지 않게 한다 |
| 서명에 보낸 시각과 `event_id`를 넣고, 받는 쪽이 허용 시차 밖을 거절한다. 키를 교체하는 동안 두 키가 유효하다 | 재전송 공격을 막고 키 교체로 전달이 끊기지 않게 한다 |
| 소스 읽기의 바깥 요청 묶기([소스와 어댑터](sources-and-adapters.md) 8절)보다 엄격한 주소 정책을 쓴다 | 소스 읽기의 정책은 읽기 요청이고 사설 주소와 루프백을 허용한다(POST로 읽는 데이터셋도 있다). 웹훅은 POST로 쓰기를 일으킬 수 있다 |
| 응답은 상태 코드만 보고 본문은 버린다. 등록할 때 확인 요청을 보내 응답을 받은 주소만 켠다 | 내부 주소의 내용을 빼내는 경로가 되지 않게 한다 |
| 서명 키는 제품 범위의 시크릿이라 `admin`이 등록한다 | [권한](access-control.md)과 [시크릿과 암호화](secrets-and-encryption.md)의 규칙을 따른다. 발송하는 부분이 새 복호화 주체가 된다 |
| 웹훅은 알림이고 현실을 바꾸는 호출이 아니다 | 웹훅으로 깬 에이전트가 게이트웨이 밖에서 현실을 바꾸면 우회이고 조직의 책임이다([보장 범위 안내서](../guides/what-praxium-guarantees.md)) |

## 5. 승인을 기다리는 동안 하네스 세션을 닫아도 된다

### 5.1 흐름

승인이 필요한 의도 하나의 흐름을 순서대로 적어요. 호출의 이름은 [게이트웨이 설계](gateway.md) 6절을 따르고 아직 구현하지 않았어요.

1. 에이전트가 준비를 불러 준비의 응답([게이트웨이 설계](gateway.md) 6절)을 받아요. 응답으로 승인 필요 여부를 알아요.
2. 승인 전에 에이전트가 실행을 부르면 응답은 **승인 대기와 의도 ID**예요. 오류가 아니라 정상 결과이고, MCP의 툴 결과에서는 `isError`가 아닌 구조화된 결과예요. 응답에는 다시 확인할 때의 힌트 `poll_after_ms`와 승인 대기의 만료 시각이 있어요. 어느 호출이 처음 대기를 알리는지는 게이트웨이를 구현할 때 정해요(11절).
3. 에이전트는 의도 ID와 실행 ID를 자기 진행 기록에 쓰고 **하네스 세션을 닫아도 돼요**. 프락시움은 하네스 세션이 닫혔는지 모르므로 실행은 열린 채로 남아요. 이벤트를 받을 수 없는 에이전트는 `poll_after_ms` 뒤에 폴링해요.
4. 프락시움이 승인 요청을 승인할 수 있는 사람에게 전달해요(5.4절). 승인 요청이 나가는 때(준비인가 첫 실행 호출인가)는 정하지 않았어요(11절). 의도가 잡은 대상의 잠금은 그대로 남아요.
5. 승인자가 승인 화면에서 승인이나 거절을 해요. 서비스 계정은 승인할 수 없어요.
6. 프락시움이 승인됨이나 거절됨 이벤트를 내요. 승인 대기 시간이 지나면 만료됨 이벤트를 내요. 승인된 뒤의 유효 시간이 지나도 만료됨 이벤트를 내고 잠금을 풀어요.
7. 에이전트 쪽의 수신함이 이벤트를 받아 새 하네스 세션을 열어요. 세션을 재개하든 새로 열든 같아요.
8. 새 세션이 **"이어받겠다"고 표시한** 맥락 읽기를 한 번 불러 이어가기 번호를 새로 받아요([이어 가기](agent-resume-context.md)). 실행에 묶인 서비스 계정만 이어받을 수 있고 감사에 남아요. 이벤트와 폴링이 함께 깨워 두 세션이 이어받아도 번호가 더 큰 세션이 이기고, 의도마다 실행은 한 번이에요.
9. 새 세션이 실행을 불러요. 프락시움은 조건을 다시 판단하고, 승인에 묶인 내용 해시와 조건의 증거가 승인 때와 같은지 확인해요. 같으면 한 번 실행하고, 달라졌으면 거절하고 다시 승인을 받게 해요.
10. 승인됐는데 정해진 시간 안에 실행 호출이 없으면 프락시움이 실행을 시작한 사람에게 알려요(5.2절).
11. 실행한 뒤의 확인(수집이 다시 읽기)과 결과는 맥락 읽기로 알아요.

### 5.2 프락시움이 직접 재는 기한

프락시움은 승인된 뒤에도 스스로 실행하지 않아요(ADR-0061). 에이전트가 실행을 다시 불러야 하므로, 세션을 닫아도 되면 승인과 실행 사이가 몇 시간이 될 수 있어요. 에이전트가 깨어나지 않으면 승인된 의도가 대장에 남고 대상의 잠금도 남아서, 잠든 에이전트가 다른 실행을 막아요. 그래서 대장에 있는 것의 기한은 프락시움이 재요. 기한의 이름은 둘로 갈라요. **승인 대기 시간**(REQ-456의 "승인 시간"과 같은 것이에요)과 **승인된 뒤의 유효 시간**이에요.

| 기한 | 지나면 |
|---|---|
| 승인 대기 시간(지금 설계에 있어요) | 만료로 거절해요 |
| 승인된 뒤의 유효 시간(승인부터 실행 호출까지) | 만료로 닫고 잠금을 풀고 실행을 시작한 사람에게 알려요 |
| 승인됐는데 실행 호출이 없는 시간(깨어나지 않는 에이전트의 감지) | 실행을 시작한 사람에게 알려요(REQ-544) |

감지의 시간은 승인된 뒤의 유효 시간보다 짧아요. 승인 대기의 응답에 싣는 만료 시각은 승인 대기이면 승인 대기 시간의 끝이고, 승인됨이면 유효 시간의 끝이에요. 승인과 무관한 "아직"의 응답에는 싣지 않아요(REQ-540).

에이전트가 스스로 건 기한(후속 확인)의 스토리지는 만들지 않아요. 실행의 시간 한도가 승인 대기 중에도 흐르는지는 아직 정하지 않았어요(11절).

### 5.3 승인 카드를 쓰지 않는 이유

MCP Apps의 승인 카드와 요청 도중 질의(elicitation)로 승인을 받지 않아요. ADR-0061이 질의를 기각한 이유와 같아요. 카드는 에이전트를 쓰는 사람의 화면에 뜨는데 승인자는 프락시움의 다른 사람이고, 승인은 프락시움의 인증과 감사 로그 안에서 이뤄져야 하고, 서비스 계정은 승인할 수 없어요. 더해서 이유가 둘 있어요.

- 상시 가동에서는 호스트 앞에 사람이 없을 수 있어요.
- 게이트웨이는 응답에서 리소스 링크를 지우고 KG 읽기 MCP는 자원을 내지 않아요. `ui://` 리소스는 지금 설계와 방향이 반대예요.

메신저 안의 승인 버튼도 같은 이유로 두지 않아요. 읽기 전용의 상태 카드(의도의 상태)로 쓰는 것은 막지 않지만 만들지 않아요. 승인 대기 결과에 승인 화면의 주소(고정된 문구와 의도 ID)를 실어 에이전트가 자기 경로로 사람에게 전하게 하는 것은 게이트웨이를 구현할 때 검토해요.

### 5.4 승인자에게 알리는 경로

운영 액션([자신의 관측성](self-observability.md) 10.2)과 정의 제안(제안의 검토 요청도 항목의 담당자에게 전달돼요)에는 승인 요청의 전달이 이미 있어요. 게이트웨이의 의도도 같은 경로를 써요. 메시지는 템플릿과 링크뿐이고 인자와 KG의 값을 넣지 않아요. 자유 서식 텍스트가 들어가면 승인자를 속이는 경로가 되기 때문이에요. 다만 승인 화면에는 자유 문장 인자가 그대로 보여요([게이트웨이 설계](gateway.md) 6절). 알림 메시지에는 없고 승인 화면에는 있다는 차이가 있어요. 알림 발송 포트의 입력은 알림 엔벨로프라서 승인 요청이 들어갈 곳이 없어요. 이것을 넓히는 일은 알림 발송의 설계가 정해요. 승인 화면에는 승인 대기 목록이 있어요.

### 5.5 두 가지 방식이 모두 된다

하네스가 호출을 보류했다가 세션을 재개하면 같은 실행 호출이 다시 와요. 의도마다 한 번만 내주므로 안전해요. 승인 대기가 정상 결과이면 보류 없이도 돼요. 프락시움은 두 방식 가운데 어느 쪽도 요구하지 않아요.

### 5.6 연속 거절의 한도

사람이 없는 에이전트가 거절되는 호출을 되풀이하는 것을 막는 장치가 지금은 없어요. 실행마다 호출 수의 한도는 있어요. 실행마다 연속 거절 수와 누적 거절 수의 한도를 두고, 넘으면 실행을 돌려줌으로 닫고 실행을 시작한 사람에게 알려요(REQ-546). 세는 것은 통제로 거절된 호출(권한, 허용 액션, 한도, 낡은 이어가기 번호, 형식)이에요. "아직"과 승인 대기는 성공 결과라 세지 않고, 승인자의 거절도 세지 않아요. 값은 측정할 가정이에요.

## 6. 참조의 계약

에이전트는 값을 베끼지 않고 **참조**를 메모리에 둬요. 참조의 형식은 (KG, 세대, 종류, ID, 버전)이에요. 프락시움이 무엇을 약속하고 무엇을 약속하지 않는지를 표로 적어요.

### 6.1 표

| 대상 | 약속 | 약속하지 않는 것과 읽을 때의 응답 |
|---|---|---|
| 객체 ID | 다른 객체를 가리키게 되지 않는다 | 병합되면 흡수된 쪽의 ID는 폐기돼요. 폐기된 ID가 어느 ID로 이어졌는지는 식별 이력에 남아요. 읽는 방법과 응답은 질의의 설계가 정해요 |
| 링크 ID | 다른 링크를 가리키게 되지 않는다 | 링크 ID는 끝점에서 만들어지므로 병합하면 흡수된 쪽의 링크 ID가 바뀌어요. 옛 ID와 새 ID의 대응은 식별 이벤트에 남아요 |
| KG 버전 | 버전은 가리키는 시점이 바뀌지 않는다 | 과거 버전을 읽는 방법과 응답은 질의의 설계가 정해요 |
| 세대 | 같은 세대 안에서 위의 약속이 지켜진다 | 세대가 바뀌거나 KG를 처음부터 다시 구축하면 이전 세대의 ID와 버전은 무효예요. 에이전트는 식별 키로 다시 찾아요 |
| 문제 ID(`issue_id`) | 같은 근본 원인이면 같은 ID다 | 같은 원인이 재발하면 같은 ID가 다시 열려요. 참조에는 (`issue_id`, 재발 번호)를 써요. REST와 이벤트의 알림은 `alert_id`이고 둘의 대응은 11절이에요 |
| 실행 ID, 의도 ID, 이벤트 ID, 동기화 실행의 `id` | 다시 쓰지 않는다 | 대장을 시점 복구로 되돌리면 이벤트도 되돌아가요(게이트웨이의 안전 9절의 미결) |

"ID가 영원히 같은 것을 가리킨다"고는 약속하지 않아요. 병합과 세대와 재구축에서 거짓이 되기 때문이에요. 처음 본 식별 키에서 ID를 만들어 고정하므로(KG의 저장과 버전 7.1), ID의 약속은 "다른 것을 가리키지 않는다"까지예요. 병합이 아직 없는 지금의 수집(ADR-0058)에서는 수집한 순서에 따라 같은 것이 두 객체가 될 수 있어요. 병합이 생기면 둘 가운데 하나가 폐기돼요. 에이전트가 가진 참조의 일부는 폐기된 ID가 될 수 있어요. 데이터 폴더를 지우고 다시 수집하는 `local`에서는 KG 이름과 세대가 같은데 ID가 다를 수 있고, 참조의 형식(KG, 세대, 종류, ID, 버전)으로는 이것을 알아챌 수 없어요.

이 표의 원칙을 KG를 읽는 툴과 질의의 응답으로 어떻게 나타낼지(읽기 조건 인자, `kg_version_id`의 노출, 폐기된 ID에 대한 응답, 결과의 형식)는 이 문서가 정하지 않아요. 질의의 설계가 정하고 이 표는 그 설계를 따라요(11절).

### 6.2 현실에 한 일은 대장이 진실이다

게이트웨이를 지난 호출의 상태는 대장이 진실이라 에이전트가 베껴 둘 필요가 없어요. 계획, 판단의 이유, 사용자와의 약속은 에이전트의 작업 노트에 둬요. 프락시움은 그것을 맡지 않아요. 한계는 둘이에요. 죽은 게이트웨이의 일지에만 있는 결과는 "모름"이고(REQ-463), 대장의 시점 복구는 미결이에요([게이트웨이의 안전](gateway-safety.md) 9절). 실행 ID나 `since`를 잃은 에이전트가 자기 일을 다시 찾도록, 게이트웨이의 읽기 툴에 **자기에게 열린 실행과 의도를 서비스 계정 기준의 목록으로 읽는 툴**을 둬요(REQ-539).

시작된 실행을 에이전트가 처음 아는 방법은 아직 없어요. 실행은 사람이 시작하고, 툴 목록은 토큰에 묶여요. 이 경로는 프로세스 정의의 설계가 정해요(11절).

### 6.3 KG의 값은 믿을 수 없는 입력이다

소스에서 온 문자열을 에이전트가 자기 지시 메모리에 옮겨 적으면, 한 번의 인젝션이 모든 하네스 세션에 실려요. 프락시움은 값과 자기 문장(툴 설명, 오류 문장)을 구조에서 가르고([KG 읽기 MCP](kg-mcp.md) 4.3절), 이벤트에 값을 싣지 않아요. 값의 정리가 `structuredContent`에도 걸리는지는 그 문서의 미결이에요. 에이전트가 메모리에 무엇을 쓰는지는 프락시움이 막을 수 없어서 권고로 적어요(10절). 이 권고는 글에 없고 프락시움이 더하는 것이에요.

### 6.4 끊긴 프로세스를 이어 가기

이어 가기 맥락은 [끊긴 프로세스를 이어 가기](agent-resume-context.md)로 따로 옮겼어요. 한 줄로 줄이면, 맥락 읽기는 **한 번의 호출**이고(이어 가려면 그 호출에 "이어받겠다"를 표시해요), 대장의 사실만 싣고, 요약이 먼저이고 상한이 있고, 조건을 다시 평가하지 않아 같은 상태면 같은 응답이고, 세션이 달라도 같은 맥락이에요(REQ-455, REQ-550).

## 7. 툴 정의의 고정과 테스트

### 7.1 무엇을 고정하나

고정하는 것은 게이트웨이가 내는 **툴 정의의 정규 직렬화**(이름, 설명, 입력과 출력 스키마, 순서)예요. **같은 실행(같은 서버 버전, 툴이 더해지거나 꺼지지 않은 동안)에서 두 번 읽은 정의는 바이트까지 같아요.** 예외는 둘이에요. 실행 중에 툴을 더하면(REQ-529)와 업스트림 툴의 정의가 바뀌어 끄고 다시 승인받으면(REQ-452) 그 뒤의 정의는 달라져요. 목적은 모델의 **프롬프트 캐시**예요. 툴 정의는 하네스 세션마다 컨텍스트의 앞부분에 실리는 고정 오버헤드이고, 앞부분이 한 바이트라도 다르면 캐시가 깨져요.

- 정의에 호출마다 달라지는 값(시각, 건수, KG의 값, 요청 ID)을 넣지 않아요.
- 게이트웨이의 툴 목록은 허용 액션이 실행마다 달라서 실행마다 달라요. 그래서 캐시의 단위는 실행이에요(REQ-451). 정의의 순서와 서버의 `instructions`를 어떻게 고정할지는 게이트웨이를 구현할 때 정해요.
- 고정하는 대상은 HTTP 응답 전체가 아니에요. JSON-RPC의 `id`와 판마다 다른 필드가 있어서 응답 전체는 같을 수 없어요.
- `tools/list`의 `ttlMs`와 `cacheScope`는 클라이언트가 목록을 **다시 가져오는 때**에 관한 것이고 다른 층이에요. `ttlMs`가 0이어도 가져온 정의가 같으면 프롬프트 캐시는 유지돼요. `cacheScope: private`는 "호출자마다 다를 수 있다"와 맞아요.

### 7.2 테스트

정규 직렬화가 고정됐는지 확인하는 테스트를 둬요(REQ-549). 이것은 MCP 전송의 일반 원칙이에요. KG를 읽는 툴의 정의에 같은 고정을 적용할지는 질의의 설계가 정하고(11절), 이 문서는 [KG 읽기 MCP](kg-mcp.md)를 고치지 않아요.

| 성질 | 확인하는 방법 |
|---|---|
| 같은 실행에서 두 번의 정의가 바이트까지 같다 | 같은 토큰으로 정의를 두 번 읽어 정규 직렬화를 비교한다 |
| 정의가 호출마다 달라지는 값에 기대지 않는다 | 시각을 바꾸고, KG의 내용을 바꾸고, 요청 ID를 바꾸어 읽어도 같다 |
| 같은 실행 안에서 연결마다 달라지지 않는다 | 같은 실행으로 연결 둘을 열어 비교한다 |
| 정의가 바뀌었을 때 알리는 방법 | 게이트웨이를 구현할 때 정한다. 게이트웨이의 읽기와 진단 툴의 정의는 승인한 업스트림 정의의 사본이라 저장소의 계약 파일이 없다 |

## 8. 자격 증명

### 8.1 게이트웨이는 자격 증명 프록시의 위치다

글이 말하는 자격 증명 프록시는 에이전트의 실행 환경 밖에서 에이전트가 모르는 자격 증명을 요청에 붙이고, 허용한 주소만 통과시키고, 모든 요청을 기록해요. 게이트웨이가 같은 위치에서 같은 일을 해요. 게이트웨이를 지나는 호출에서는 에이전트가 업스트림의 자격 증명을 받지 않고, 그 호출은 모두 기록돼요. 업스트림의 자격 증명은 에이전트의 환경이 아니라 게이트웨이 쪽에 있어요(보관 위치는 [게이트웨이의 안전](gateway-safety.md) 9절의 미결). 우회를 막는 일은 조직의 책임이에요. 모델 API나 임의의 HTTPS 트래픽을 가운데서 다시 쓰는 범용 프록시는 아니에요.

### 8.2 프락시움의 토큰도 프록시가 붙일 수 있게

업스트림의 자격 증명뿐 아니라 프락시움에 보내는 토큰도 에이전트의 환경 밖에서 붙일 수 있게 해요. 조직이 에이전트의 실행 환경 밖에 헤더를 붙여 주는 프록시를 두면, 에이전트는 토큰 없이 요청하고 프록시가 `Authorization` 헤더를 붙여요. 이 배치가 되도록 프락시움이 지키는 조건이에요(REQ-543).

| 조건 | 설명 |
|---|---|
| 토큰은 `Authorization` 헤더로만 받는다 | 주소, 본문, 툴 인자로 받지 않아요 |
| 요청에 실린 토큰을 그대로 내보내지 않는다 | 응답과 로그에 나오지 않아요(REQ-313). 발급 응답이 값을 한 번 보이는 것은 예외예요 |
| 에이전트가 토큰의 값을 알아야만 되는 기능을 만들지 않는다 | 본문을 토큰에서 만든 시크릿으로 서명하는 방식이 그 예예요 |
| 주소는 하나가 아니다 | 코어(REST와 `/mcp`), 게이트웨이, 쓴다면 운영 MCP가 다른 주소예요. 프록시의 허용 목록에는 주소마다 한 줄이 필요해요 |

### 8.3 두 배치

| 배치 | 내용 | 권고 |
|---|---|---|
| 환경 변수 | 하네스의 환경에 토큰을 둔다. 간단하다 | `viewer` 하나뿐인 토큰이라 피해가 읽기에 한정될 때만 쓴다. 인프라 구성 전체의 읽기는 정찰에 쓰일 수 있고 지금은 토큰 하나로 KG 전체가 읽히므로([KG 읽기 MCP](kg-mcp.md) 1절) 범위를 좁혀요 |
| 프록시 주입 | 프록시가 헤더를 붙인다. 에이전트는 토큰을 모른다 | 권장. 바꾸는 권한이 있는 토큰은 이 배치만 권한다 |

프록시를 쓰려면 다음을 알아야 해요.

- 에이전트마다 서비스 계정 하나를 두고, 프록시가 에이전트의 신원에 따라 토큰을 골라요. 토큰 하나를 여러 에이전트에 붙이면 계정별 한도, 읽기 기록, 감사가 에이전트를 구분하지 못해요.
- 에이전트 쪽의 나가는 프록시와 서버 쪽의 들어오는 프록시는 달라요. 주입 프록시는 TLS를 끝내야 헤더를 넣어요. 서버의 운영 모드는 TLS나 `-behind-proxy` 선언을 요구해요(REQ-311).
- 프록시가 허용 목록에 없는 `Origin` 헤더를 더하면 `/mcp`가 403으로 거절해요([KG 읽기 MCP](kg-mcp.md) 3절). 루프백에 묶인 서버는 루프백의 `Host`만 받으므로 `local`은 이 배치의 대상이 아니에요.
- 인증 실패의 제한은 호출자의 주소로 세요. 프록시 뒤에서는 같은 주소로 보이므로 만료된 토큰 하나가 거절을 쌓으면 그 주소의 거절된 토큰이 429로 답해요(REQ-314. 유효한 토큰은 통과해요). 원인이 401이 아니라 429로 보여서 읽기 어려워요.

### 8.4 실행 토큰을 정할 때의 조건

게이트웨이의 토큰 형식, 수명, 소지 증명은 미결이에요([게이트웨이의 안전](gateway-safety.md) 9절). 지금 설계는 하네스가 실행 토큰을 받고 툴 목록이 토큰에 묶여요(REQ-528). 헤더를 붙이는 프록시는 요청마다 어느 실행의 토큰을 붙일지 모르므로 이 배치와 부딪쳐요. REQ-528은 지금 고치지 않아요. 게이트웨이의 결정이 토큰을 정할 때 이 조건을 지켜요.

- 인증은 프록시가 붙일 수 있는 서비스 계정의 자격(헤더, 또는 상호 TLS)으로 해요.
- 어느 실행인지는 에이전트가 알아도 되는 식별자(주소의 경로나 헤더의 실행 ID)로 가리켜요. 실행 ID는 비밀이 아니므로 그 서비스 계정이 그 실행에 묶여 있는지를 검사해요. 실행 ID를 아는 것은 권한이 아니에요.
- 프록시 하나가 토큰 하나를 여러 에이전트에 붙이면 실행 단위의 분리가 계정 단위로 내려가요(8.3절 첫 항목).
- 요청마다 응용 계층에서 본문을 서명하는 것처럼 에이전트가 시크릿을 알아야 하는 소지 증명은 쓰지 않아요. 상호 TLS 결속을 먼저 봐요(ADR-0061 13항이 선택 강화로 이미 뒀어요). 프록시가 TLS를 끝내고 클라이언트 인증서를 가지면 돼요.

## 9. 원칙 둘

두 영역의 설계는 각자의 결정 기록이 정하고, 이 문서는 그 설계가 따를 원칙만 적어요.

### 9.1 내보내기

프락시움이 사람과 시스템에 내보내는 것(알림, 승인 요청, 변경 알림)에 관한 원칙이에요. 알림 발송의 설계([데이터 관측성](data-observability.md) 8.5절)가 정해요.

- **보낼 것의 사본을 따로 쓰지 않아요.** 추가 전용인 진실 기록(이벤트 로그, 문제 목록의 변화)을 발송하는 부분이 순서대로 읽고, **받는 곳마다 어디까지 전달했는지와 시도의 결과**만 따로 적어요. 쓰기가 한 번이라 파일 스토리지에서도 성립하고, 진실과 파생 데이터의 구분에도 맞아요. 일의 트랜잭션과 같은 쓰기로 보낼 것을 먼저 쓰는 방식은 파일 스토리지에서 성립하지 않아요(파일을 둘로 나누면 둘 사이에서 장애가 났을 때 어긋나요).
- 스토리지가 멈췄을 때의 알림과 하트비트, 게이트웨이의 로컬 일지는 이 경로 밖이에요. 하트비트는 속도 조절에서 빼요. 조절이 하트비트를 늦추거나 합치면 알림 시스템의 장애 감지가 깨져요([데이터 관측성](data-observability.md) 13절).
- 보내기 직전에 아직 유효한지 다시 확인해요. 멈췄다 다시 뜨면 낡은 것(만료된 승인 요청, 이미 해소된 알림)이 한꺼번에 나가지 않게 해요.
- 처음에는 조용하게 시작해요. 양의 적절함은 클로즈드 베타에서 재요([데이터 관측성](data-observability.md) 16절). 근거는 승인 피로예요([게이트웨이의 안전](gateway-safety.md) 6절).
- 이것은 별도의 서비스가 아니라 스토리지 안의 기록과 워커의 한 부분이에요(3.2절).

### 9.2 일정과 기한

프락시움 안의 일정과 기한에 관한 원칙이에요. 일정의 설계가 정해요([수집 서비스와 실행](ingestion-service.md) 12절이 비워 둔 것).

- **반복 규칙은 정의에 있어요.** 일정은 정의이고 값을 고치는 일은 ADR-0014의 절차예요. 기록에는 다음 기한만 둬요(정의가 바뀌면 다시 계산해요). 반복 규칙, 시간대, 수집해도 되는 시간대(`windows`), 놓친 일정의 처리(`misfire_policy`)는 정의에만 있어요.
- **스케줄러가 기한이 된 것을 찾아요.** 스케줄러(워커의 한 부분)가 고정된 간격으로 기한이 된 것을 찾고, 기한은 끝남으로, 일정은 다음 기한으로 갱신하고, 실행 기록에 한 줄을 넣어요. 넣는 것은 스케줄 키(소스, 시각 슬롯)로 멱등이에요([KG 운영](kg-operations.md) 4.4). 타이머는 스스로 실행을 시작하지 않아요.
- **실행 중에 새로 온 것의 처리는 누가 냈는지에 따라 정해요.**

| 요청한 주체 | 처리 |
|---|---|
| 사람이 누른 요청 | 409와 지금 도는 실행의 `id`예요(ADR-0058의 계약에 있어요). 사람은 화면에서 그 실행을 봐요 |
| 일정 | 미룸과 합침이에요. 소스마다 대기는 하나이고 쌓이지 않아요. 합침은 `misfire_policy: run_once`와 같은 뜻이고 `skip`과 `windows`를 반영해요. 미룬 것은 "기한이 됐지만 아직 넣지 않음"으로 남기고 지금 실행이 끝나면 넣어요. 소스마다 `queued` 또는 `running` 실행은 하나라는 유일 제약은 그대로예요 |
| 푸시 수집(뒤의 일) | 받아서 수집 변경 로그에 쓰고 다음 적용에 합쳐요. 받는 경로의 응답 방식은 푸시 수집의 설계가 정해요 |

중단하고 다시 시작하는 방식은 쓰지 않아요. 미완료 적용을 만들어요.
- **KG의 결과를 바꾸는 기한은 벽시계가 아니라 `tick`으로 세요.** 닫힘의 유예와 보류된 시간이 그 예예요. 같은 입력이면 같은 결과라는 성질을 지켜요(ADR-0009 결정 25, [수집 설계](ingestion.md) 7.2절). 타이머 기록에 두는 것은 결과를 바꾸지 않는 **운영의 기한**뿐이에요. 일정의 다음 기한, 알림의 에스컬레이션, 승인 대기 시간과 승인된 뒤의 유효 시간의 만료, 깨어나지 않는 에이전트의 감지 같은 것이에요. 같은 스토리지의 다른 기록이지 다른 스토리지가 아니에요.
- 리스의 만료는 타이머가 아니에요. 리스 기한은 실행 행의 `lease_until`이고 인계의 조건이에요.
- 확인 대기의 만료를 내구성 있는 기한으로 두려면 확인 대기의 레코드 배치가 먼저 내구성이 있어야 해요. 지금은 메모리에만 있고 서버가 다시 시작하면 실행은 실패로 닫혀요([수집 서비스와 실행](ingestion-service.md) 7.2절).
- 일정이 낸 실행이 안전장치에 걸려 확인을 기다리다 만료되는 일이 연속되면, 소스를 다시 읽고 다시 걸리고 버리는 일이 일정 중지 없이 이어져요. 일정의 설계에 "확인 대기가 연속으로 만료되면 그 일정을 멈추고 알린다"를 넣어요.
- 용어는 이렇게 나눠요. 정의는 **일정**, 그것을 돌리는 워커의 부분은 **스케줄러**예요.

## 10. 에이전트를 만드는 사람에게

프락시움에 붙는 상시 가동 에이전트를 만드는 사람에게 주는 권고예요. 안내서(`docs/guides/`)에는 아직 옮기지 않았어요. 연결 안내서를 고칠 때 아래를 옮겨요.

### 10.1 메모리에는 무엇을 두나

- **둘 것:** 프락시움에서 다시 찾아볼 수 없는 것. 사용자의 지시와 선호, 이미 사용자에게 보고한 것, 진행 중인 일의 의도 ID와 실행 ID.
- **참조로 둘 것:** 객체, 링크, 실행, 의도, 알림처럼 프락시움에 있는 것. 값 대신 참조(KG, 세대, 종류, ID, 버전)를 둬요(6절). 알림은 (`issue_id`, 재발 번호)예요. 이미 보고한 알림을 `issue_id`만으로 기억하면 재발한 알림을 이미 보고한 것으로 알고 넘겨요. 식별 키는 지시 메모리가 아닌 자료로 참조와 함께 둘 수 있어요.
- **옮겨 적지 말 것:** KG의 값은 지시 메모리에 옮겨 적지 말고 ID로 가리켜요. 소스의 글자가 지시처럼 읽혀 한 번의 인젝션이 모든 하네스 세션에 실려요.
- 참조는 KG와 세대 안에서만 유효해요. 참조가 폐기됐거나 세대가 바뀌었으면 식별 키로 다시 찾아요. `local`에서 데이터 폴더를 지우고 다시 수집하면 ID가 같다는 보장이 없어요.
- 게이트웨이를 지난 호출의 상태는 대장이 진실이라 진행 기록에 베끼지 않고 맥락 읽기 툴로 읽어요. 계획, 판단의 이유, 사용자와의 약속은 에이전트의 작업 노트에 둬요([이어 가기](agent-resume-context.md)).

### 10.2 수신함의 단위

글은 사용자당 수신함 하나로 시작하라고 해요. 프락시움에서 겹치지 않아야 하는 단위는 **실행**(게이트웨이의 계약)이에요. 이어가기 번호가 실행마다 있어요. 수신함은 실행 단위나 서비스 계정 단위로 두고, 이벤트는 `resource`로 실행을 걸러 받아요. 에이전트 하나에 서비스 계정 하나를 둬요.

### 10.3 멱등 키의 기억 기간

REST의 `Idempotency-Key`는 프로세스 메모리에 10분 동안 기억해요(구현의 값이고 보관 기간은 가정이에요). 에이전트가 죽은 뒤 몇 시간 만에 같은 이벤트를 다시 처리하며 REST로 쓰면(사용자 신고, 제안) 같은 쓰기가 두 번 될 수 있어요. 키의 기억 기간이 지났다고 보고 다시 보내기 전에 먼저 읽어서 확인해요. 게이트웨이의 준비는 내용으로 멱등이라 이 걱정이 없어요.

### 10.4 깨면 한 번에 가져온다

깨면 `since`로 밀린 이벤트를 한 번에 가져와 묶어 처리해요. `kg_changed`는 이미 구간으로 묶여서 와요. `since`가 낡아 `stale.since_too_old`를 받으면 현재 상태를 다시 읽어요(4.3절).

### 10.5 프락시움의 주소 목록

프록시의 허용 목록을 정확히 적을 수 있도록, 에이전트가 부르는 주소를 표로 줘요. 이벤트는 REST로만 받아요.

| 주소 | 용도 | 비고 |
|---|---|---|
| 코어의 `/mcp` | KG 읽기 툴 | 읽기만 하는 서비스 계정(`viewer`)의 토큰 |
| 코어의 `/v1/events`(스트림과 `since`) | 이벤트 | 같은 토큰 |
| 게이트웨이 | 바꾸는 툴, 읽기와 진단 툴, 맥락 읽기 | 다른 주소와 다른 인증이라 코어의 서비스 계정과 같은 계정으로 이어지는지가 전제예요(11절). 구현하면 정해요 |
| 운영 MCP | 프락시움 자신의 운영 | 쓴다면. 주소는 정해지지 않았어요 |

## 11. 미결

| 미결 | 정하는 때 |
|---|---|
| `event_id`의 값을 걸러 받는 계정에게 가려진 이벤트의 수가 드러나지 않게 만드는 방법 | 이벤트 스트림을 만드는 변경 |
| 의도와 실행의 이벤트가 KG별 순서에 드는지 배포 단위의 순서에 드는지(조건은 4.2절), 배포에 하나인 이벤트(작업, 제안, 정의)의 순서 | 이벤트 스트림을 만드는 변경 |
| 보존 기한, 승인 대기 시간, 승인된 뒤의 유효 시간, `poll_after_ms`, 연속 거절의 한도, 이벤트 스트림 연결 수 한도의 값 | 클로즈드 베타에서 측정해서 |
| 어느 호출이 처음 승인 대기를 알리는지, 승인 요청이 나가는 때(준비인가 첫 실행 호출인가) | 게이트웨이의 구현 |
| 실행의 시간 한도가 승인 대기 중에도 흐르는지 | 게이트웨이의 구현 |
| 승인 대기 결과에 승인 화면의 주소를 실을지 | 게이트웨이의 구현 |
| "증거가 달라짐"의 기준(조건: 관측 시각만 다른 것은 달라짐이 아니다. 판정이 같으면 같은 것으로 볼지 값까지 같아야 하는지), 거절된 뒤 의도가 어느 상태가 되는지 | 게이트웨이의 구현 |
| 실행에 묶인 서비스 계정을 묶는 방법, 사람이 다른 서비스 계정으로 바꿔 묶는 일(REQ-539, REQ-545) | 프로세스 정의의 설계 |
| 소유에 따른 읽기 규칙(자기 의도와 자기 실행의 이벤트), 코어의 서비스 계정과 게이트웨이 쪽 신원이 같은 계정이라는 전제 | 게이트웨이의 결정(권한 설계를 고친다) |
| 시작된 실행을 에이전트가 처음 아는 방법, 읽기 전용 실행이 낸 시작 요청을 사람이 시작으로 바꾸는 경로 | 프로세스 정의의 설계([게이트웨이의 안전](gateway-safety.md) 9절에 후보로 적었어요) |
| 토큰의 형식과 수명과 소지 증명(8.4절의 조건을 지켜서) | 게이트웨이의 결정 |
| 이벤트 종류의 이름 | 각 구현 단계 |

| 알림의 재발 번호의 이름과 형식, `alert_id`와 `issue_id`의 대응 | 알림을 구현하는 변경 |
| 이어 가기 맥락의 미결([이어 가기](agent-resume-context.md) 6절) | 게이트웨이의 구현 |
| 연결 안내서와 보장 범위 안내서에 8절과 10절을 옮기는 일 | 안내서를 고치는 변경 |

## 12. 검증

뒤의 구현이 테스트해야 하는 것이에요. 요구사항 번호는 모두 예정이에요.

| 무엇 | 확인하는 방법 | 요구사항 |
|---|---|---|
| 같은 사건은 어느 경로로 받아도 같은 `event_id` | 스트림과 `since`로 같은 사건을 받아 비교한다 | REQ-535 |
| 이벤트의 필드가 목록 안이다 | 내보내는 모든 필드가 목록에 있는지 본다. 소스의 값을 넣은 입력에서도 이벤트에 나오지 않는다 | REQ-535 |
| 건너뛴 이벤트가 없다 | 커밋 순서가 어긋나는 쓰기에서도 뒤에 커밋된 앞의 이벤트가 `since` 뒤를 이어 읽을 때 빠지지 않는다 | REQ-536 |
| 보존 기한이 지난 `since` | `stale.since_too_old`로 답한다. 세대가 바뀐 뒤는 `conflict.generation_changed`다 | REQ-536 |
| 구독의 권한 | 읽을 수 없는 것의 이벤트가 안 나가고, 비활성화한 계정의 연결에도 안 나간다. 걸러 받는 계정이 `event_id`로 가려진 이벤트의 수를 알 수 없다. 연결 수의 한도를 넘으면 거절한다 | REQ-537 |
| 동기화 실행의 이벤트 | 확인 대기가 됨, 끝남, 실패가 순번과 함께 나간다 | REQ-538 |
| 의도와 실행의 이벤트, 자기 것을 다시 찾기 | 상태 변화(취소됨과 확인 결과가 나옴 포함)마다 이벤트가 나가고, 다른 서비스 계정의 것은 목록에 없다 | REQ-539 |
| 승인 대기가 정상 결과 | `isError`가 아니고 `poll_after_ms`와 만료 시각이 있다. 연결이 끊기고 토큰이 만료된 뒤에도 조회와 맥락 읽기로 같은 의도의 상태가 읽힌다 | REQ-540 |
| 승인자에게 알림 | 승인 요청이 알림 발송의 설계가 정한 경로로 전달되고(그 설계 뒤) 메시지에 인자와 KG의 값이 없다. 승인 대기 목록이 있다 | REQ-541 |
| 승인된 뒤의 유효 시간과 증거 | 만료되면 잠금이 풀린다. 증거가 달라지면 실행이 거절된다 | REQ-542 |
| 깨어나지 않는 에이전트 | 승인된 뒤 정해진 시간 안에 실행 호출이 없으면 실행을 시작한 사람에게 알림이 나간다 | REQ-544 |
| 이어받음 | 실행에 묶인 서비스 계정만 이어받고 두 세션이 겹쳐도 실행은 한 번이다 | REQ-545 |
| 연속 거절의 한도 | 넘으면 실행이 돌려줌으로 닫히고 실행을 시작한 사람에게 알린다. "아직"과 승인 대기는 세지 않는다 | REQ-546 |
| 알림의 재발 | 같은 `issue_id`가 다시 열리고 재발 번호가 오른다 | REQ-548 |
| 게이트웨이의 툴 정의의 고정 | 7.2절의 확인 테스트 | REQ-549 |
| 이어 가기 맥락의 성질 | [이어 가기](agent-resume-context.md) 7절 | REQ-550 |
| 토큰의 헤더 규칙 | 계약에 토큰을 본문, 질의 인자, 툴 인자로 받는 경로가 없다(계약 검사) | REQ-543 |
