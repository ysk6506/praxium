# 테라리움에 남아 있던 제품 책임자의 요구

[테라리움에서 넘겨받은 것](from-terrarium.md)은 설계와 요구사항을 한 장으로 줄였어요. 이 문서는 그중 **제품 책임자가 직접 말한 요구**만 골라, 프락시움의 어느 결정과 요구사항이 받았는지 이어 줘요. KG 기반(데이터 연결부터 KG를 짓고 운영하는 것)을 설계할 때 출발 자료로 써요.

## 1. 읽는 법

- **이 문서는 출발 자료예요.** 제품 책임자의 요구는 이어받아요. 그때 설계 담당이 고른 것과 시뮬레이터라서 있던 것은 프락시움에서 다시 정했어요(4절과 5절).
- **표기.** 테라리움의 결정 기록은 T0152처럼, 요구사항은 T요구 120처럼 적어요. ADR-NNNN과 REQ-NNN은 프락시움의 것이에요.
- **인용.** 테라리움의 공개 저장소에 있던 문장만 짧게 옮겼어요. 제품 이름은 옮기지 않고 요구의 말로 바꿨어요. 어느 조직이 무엇을 쓴다는 말은 이 문서에 없어요(ADR-0003).
- **귀속.** 테라리움에서 제품 책임자는 목표와 요구사항만 정하고 설계 결정은 설계 담당에게 맡겼어요(T0138). 그래서 요구와 설계의 선택을 나눠 읽어요. 아래 표의 "받은 곳"은 프락시움의 결정 기록과 요구사항이에요.
- **E2E 프로세스 쪽 요구.** 제품 책임자는 지금 E2E 프로세스의 요구사항은 구체화하지 않기로 했어요. 그쪽 요구(운영 세계를 E2E 프로세스와 잇기, 툴은 게이트웨이로만 부르기)는 [E2E 프로세스의 방향](../design-docs/process-direction.md)에 있어요.

## 2. 이어받는 요구

### 2-1. 현실 데이터 받기

| 요구 | 테라리움의 출처 | 받은 곳 |
|---|---|---|
| 소스는 여러 개이고(HTTP API, 엑셀 등) 소스의 속성을 객체의 속성으로 정할 수 있어요 | T0144 | ADR-0008: REQ-110(소스, 어댑터, 프리셋), REQ-116(매핑) |
| 데이터 소스 연동과 모델 동기화는 나눠 설계해요 | T0144 | ADR-0008: REQ-113(수집과 그 뒤의 경계) |
| 널리 쓰이는 모니터링과 구성 관리 소스에서 읽기 전용으로 가져와요(그때 예로 든 제품이 있었지만 옮기지 않았어요) | T0149 | ADR-0008: REQ-110(프리셋), REQ-111(읽기 전용 세 겹) |
| 모든 소스는 읽기만 해요 | T0149, T0152 | ADR-0008: REQ-111 |
| 위치, 전원, 냉방은 엑셀로 받아요. 한 줄에 장비 하나인 목록 형식도 받아요 | T0152, T0164 | ADR-0008: REQ-120(엑셀 양식) |
| 쿼리 말을 받는 소스에서는 검색을 데이터를 가진 쪽이 자유롭게 적어요 | T0152 | ADR-0008: REQ-111(저장할 때 허용된 명령의 목록으로 검사) |
| 같은 장비가 여러 소스에 있으면 하나로 알아봐요 | T0152 | ADR-0007: REQ-104(식별과 병합) |
| 정제, 매핑, 링크 정의를 층으로 나눠요 | T0165 | ADR-0008: REQ-115(정제), REQ-116(매핑과 링크 정의) |
| 소스마다 동기화 주기를 정해요. 주기 동기화는 기본 관리 기능이에요 | T0151 | ADR-0008: REQ-121(일정과 실행 기록), REQ-124(받는 방식 넷과 소스·데이터셋마다의 일정) |
| 수집을 밖에서 볼 수 있어요(지표와 로그, 비밀 값과 행의 내용은 로그에 없음) | T0155 | ADR-0008: REQ-121. 넓힌 것은 ADR-0013: REQ-180(여덟 자리의 신호), REQ-188(지표의 저장과 열린 형식으로 내보내기) |
| 파이프라인에 버전과 브랜치가 있어요 | T0166 | ADR-0014: REQ-119(정의 묶음, 브랜치, 제안, 병합), REQ-128(충돌), REQ-129(되돌리기) |
| 실시간 상태(온도, 전력, 알람의 현재 값)는 미뤄요 | T0152 | ADR-0008 결정 1(지금은 구성 하나를 받아요). 미루는 것은 수치의 시계열이고 구조와 상태는 받아요(REQ-124, REQ-108) |
| 이 데이터 입력은 관리자 기능이고, 나중에 관리자가 권한을 준 사람이 해요 | T0152 | ADR-0012: REQ-161(권한 부여는 누구 × 역할 × 범위이고 관리자가 줘요) |
| 특정 SSO에 묶이지 않아요 | T0174 | ADR-0012: REQ-160(SSO 연결은 포트 뒤, 특정 제품에 묶이지 않음) |

### 2-2. 모델

| 요구 | 테라리움의 출처 | 받은 곳 |
|---|---|---|
| 모델은 플랫폼 중립이에요. 가상화 플랫폼 둘 이상, 쿠버네티스, 가상 데스크톱을 받아요 | T0157, T0164 | ADR-0007: REQ-105(표준 모델) |
| 객체와 관계의 표준 모델을 참고해요 | T0157 | ADR-0007: REQ-105(층마다 공개 표준에서 뼈대를 빌림) |
| 포트 단위까지 받아요 | T0156 | ADR-0007: REQ-105(네트워크 층의 포트, LAG, 라우팅 세션) |
| 논리 관계는 얼마든지 있어요. 링크 타입은 열려 있어요 | T0165 | ADR-0007: REQ-100(열린 타입), REQ-101(링크의 뜻은 열하나 중에서 고름) |
| 이중화(LACP, ECMP, BGP 세션, 전원 A와 B, 냉방, 주와 대기)를 몇 개가 살아야 하는지로 따져요 | T0156 | ADR-0007: REQ-102(이중화 묶음과 세 값) |
| ECMP는 경로표가 아니라 장비 설정 값에서 읽어요. 나중에 제품 책임자가 "설정에서 읽을 수도, 표로 받을 수도 있다"로 넓혔어요 | T0164 | ADR-0007 결정 9와 REQ-106(근거의 종류 넷: 같은 묶음을 설정, 표, 문서 어디서든 받고 어긋남을 문제 목록에 올림), REQ-105(표준 모델의 라우팅 세션) |

### 2-3. 규모, 성능, 가용성

| 요구 | 테라리움의 출처 | 받은 곳 |
|---|---|---|
| 객체와 링크가 수천만 개인 규모를 다뤄요 | T0154 | ADR-0009: REQ-134(재서 확인) |
| 스위치의 ECMP, BGP, LACP를 다 고려한 영향 범위를 1초 안에 계산해요 | T0156 | ADR-0010: REQ-142 |
| 설비 문제가 VM, 앱, 서비스에 미치는 범위는 수 초 안에 답해요 | T0156 | ADR-0010: REQ-142 |
| 고가용으로 돌아요. 저장소는 제품이 함께 내놓아요 | T0153 | ADR-0009: REQ-133, ADR-0011: REQ-154, ADR-0010: REQ-145(질의 엔진은 여러 벌) |

"3초"는 제품 책임자의 숫자가 아니에요. 제품 책임자는 "수 초"라고 했고 3초는 설계 담당이 구체화한 거예요. 프락시움은 제품 책임자의 숫자만 써요.

### 2-4. 말과 태도

| 요구 | 테라리움의 출처 | 받은 곳 |
|---|---|---|
| 말은 현업에서 쓰는 말을 쓰고, 한 뜻에 한 말이에요 | T0167, T0183 | 용어집(ADR-0005가 갱신), AGENTS.md의 설계할 때 절 |
| 이 세계를 "운영 세계"라고 불러요 | T0150 | 용어집의 운영 세계(ADR-0005) |
| 요구를 그것만 보고 좁게 판단하지 말고, 제품의 주인으로서 전체와 세부를 함께 설계해요 | T0170 | 제품 설계 한 장의 4절과 AGENTS.md의 설계할 때 절 |
| 내부 사실을 공개 저장소에 적지 않아요 | T0187 | ADR-0003 |
| 운영 데이터를 재활용할 걸 고려해 데이터를 설계해요 | T0088 | KG의 한 범위를 공개된 형식의 파일로 내보내기(ADR-0005, 뒤 순서) |
| 화면은 기능을 시험할 수 있는 수준만 먼저 만들고 UX와 UI는 클로즈 베타에서 설계해요 | T0152(클로즈 베타), 프락시움의 결정 | ADR-0006(알파는 백엔드부터), ADR-0016(화면은 다른 저장소. 이 저장소의 알파 기준은 API와 명령줄 클라이언트, REQ-147) |

## 3. 제품 책임자가 설계를 바로잡았던 곳과 거기서 배운 것

테라리움에서 설계 담당은 이틀 사이 결정 일곱 개를 쓰고 셋을 뒤집었어요(T0170이 스스로 적었어요). 제품 책임자의 교정은 거의 전부 **설계가 좁다, 닫혀 있다, 둘로 갈라져 있다**를 향했어요.

| 곳 | 무슨 일 | 갈래 | 프락시움에서 |
|---|---|---|---|
| 범위 | 설계 담당이 "받아서 짓고 그리기"를 한 번 가져오기로 읽었어요. 제품 책임자는 주기 동기화가 기본 관리 기능이라고 바로잡았어요(T0150, T0151) | 좁다 | 일정과 실행 기록이 처음부터 들어 있어요(REQ-121) |
| 쿼리 소스 | "정해 둔 검색만" 돌리려던 설계를 "무엇을 꺼낼지는 데이터를 가진 쪽이 안다"며 바로잡았어요(T0152) | 닫혀 있다 | 관리자가 자유롭게 적고 허용된 명령의 목록으로 검사해요(ADR-0008) |
| 층과 링크 | 정제를 매핑 안으로 접고 관계 종류를 닫았어요. 제품 책임자는 여러 번 같은 것을 요구했어요(T0165) | 닫혀 있다, 좁다 | 층이 따로 있고 링크 타입은 열려 있어요(ADR-0007, ADR-0008) |
| 현실과 실험 | 복사본에서 모르는 타입을 접거나 "시뮬레이션이 모르는 것"으로 보고만 하려던 설계를 "따로 놀면 쓸모없다"며 거절했어요(T0168). 현실 전용 타입 층도 거절했어요(T0169) | 둘로 갈라져 있다 | 모델은 프락시움의 하나예요(ADR-0007). 시뮬레이터 쪽 요구는 5절을 봐요 |
| 저장소 | "있는 DB에 잇기만" 하려던 설계를 "제품이 저장소까지 함께 내놓아야 한다"며 거절했어요(T0153) | 남에게 맡김 | 저장소는 제품이 함께 내놓아요(ADR-0009, REQ-133) |
| 용어 | 어려운 순우리말 신조어를 현업 말로 바꾸라고 했어요(T0167) | 새로 지음 | 현업의 말을 써요. 용어집에 한 뜻에 한 말로 남겨요 |
| 툴 | 툴을 흉내 내는 모의 서버 설계 셋을 거절했어요(T0190, T0191) | 흉내 | 실제 툴은 에이전트가 게이트웨이로만 불러요. E2E 프로세스의 방향에 있어요 |
| 흐름도 | 흐름도를 가운데에 둔 설계가 시나리오와 맞물리지 않아 접었어요(T0192) | 좁다 | 일을 목표, 규칙, 범위로 정해요. E2E 프로세스의 방향에 있어요 |

**배운 것.**
1. 요구를 받으면 "왜"까지 되묻고, 그 요구가 한 사례가 아니라 **일반 구조**(열린 타입, 분리된 층, 하나의 모델)로 설계돼야 하는지 먼저 봐요. 요구가 하나 더 올 때마다 기능을 덧붙이면 번복이 쌓여요.
2. 닫아 둔 목록에는 열 자리를 한 곳 남겨 둬요. 링크의 뜻은 닫힌 열하나로 두되 링크 타입은 얼마든지 더하게 한 것(ADR-0007), 소스는 어댑터 셋으로 두되 수집 봉투를 정식 확장 지점으로 둔 것(ADR-0008)이 그 예예요.
3. 같은 것이 두 곳에 있으면 한쪽으로 모아요. 모델은 하나예요.
4. 현업의 말을 써요.
5. 제품이 끝까지(저장소와 관측성 포함) 책임져요. 남이 준비되기를 기다리지 않아요.

## 4. 그때 설계 담당이 골랐고 프락시움이 다시 정한 것

제품 책임자의 요구를 만족시키려고 설계 담당이 고른 것이에요. 요구가 아니었으므로 프락시움은 다시 정했어요.

| 그때의 선택 | 프락시움의 결정 |
|---|---|
| 연결, 수집, 매핑, 적용의 네 단. 손질은 매핑의 앞걸음 | 수집, 정제, 매핑, 식별과 병합, 링크, 차이, 안전장치, 적용의 여덟 단계. 수집은 모델을 모르고, 연결 확인은 단계가 아니라 필요할 때 하는 점검이에요(ADR-0008) |
| 범용 커넥터 넷(파일, HTTP, SQL, 푸시 수집)과 프리셋 | 프로토콜을 말하는 어댑터는 소수의 코드, 프리셋은 데이터예요. 푸시 수집은 마지막 수단이 아니라 수집 봉투라는 정식 확장 지점이에요(ADR-0008) |
| 정제 여덟 연산 | 닫힌 열네 연산. 새 연산은 결정 기록으로 더해요(ADR-0008) |
| 링크를 잇는 조건 유형 다섯 | 닫힌 여섯 조건(ADR-0008) |
| 링크의 뜻 일곱. 묶음도 링크 | 링크의 뜻 열하나. 이중화 묶음은 객체예요(ADR-0007) |
| 사실, 가정, 모름. 소스에 없는 값은 기본 규칙으로 채움 | 사실, 가정, 모름은 그대로예요. 모르는 것을 가정으로 메우지 않아요. 소스의 완전성 선언으로 "없다"와 "모른다"를 가르고, 답의 등급은 쓰인 입력 중 가장 낮은 등급이에요(ADR-0007) |
| 받은 행 = 객체가 된 행 + 링크가 된 행 + 문제 + 안 쓰인 행 | 원본 기록 하나는 쓰임, 규칙이 걸러 냄, 문제, 안 쓰임 중 하나로 끝나요. 단계마다 들어온 수 = 나간 수 + 떨어진 수예요(ADR-0008, REQ-117) |
| 안전장치: 10% 넘게 사라지면 멈춤, 안 보임 세 번이면 삭제 | 비율과 건수를 함께 보고, 덜 받은 수집은 뒤로 가지 않게 막아요. 안 보이는 것은 물러난 것으로 표시하고 지우지 않아요. 숫자는 모두 재지 않은 가정이에요(ADR-0008) |
| 읽기 전용 세 겹: 허용 목록, 읽기 계정, 읽기 메서드만 | 요청 허용 목록, 소스 쪽 읽기 전용 계정, 어댑터에 쓰는 길이 없음. 읽기인데도 POST를 쓰는 소스가 있어 "읽기 메서드만"은 지킬 수 없어요(ADR-0008) |
| 쿼리 소스는 위험 명령의 차단 목록 | 허용된 명령의 목록으로 검사해요(ADR-0008) |
| 소스 역할 셋: 구성, 사건, 실측 | 구성 하나. 실시간 상태는 미뤘어요(ADR-0008) |
| 파이프라인을 통째로 버전 매김. 브랜치는 하나부터 | 정의를 낱개 항목으로 나누고, 정의 묶음, 브랜치, 제안으로 고쳐요. 병합은 한 줄로 세워 하나씩 하고, 항목마다 담당자(연락처)가 있고 승인은 범위를 가진 `approver`가 해요(ADR-0014, ADR-0012) |
| 객체 ID는 소스의 키에서 정함 | 객체마다 바뀌지 않는 내부 ID가 있고, 바깥 식별자는 여럿을 이력과 함께 가져요(ADR-0007) |
| 관계형 엔진 하나, 메모리 색인, 3대 내장 DB | 진실은 PostgreSQL에 두고 나머지는 자리에 맞게 포트 뒤에 둬요. 영향 범위는 투영과 따로 뜨는 질의 엔진이 답해요. 고가용 구성의 구체는 구현할 때 정해요(ADR-0006, ADR-0009, ADR-0010) |
| 영향 3초, 안전장치와 신선도의 숫자, 규모 어림 | 제품 책임자의 숫자(1초, 수 초)만 써요. 나머지는 가정이고 지어낸 규모로 재서 정해요(ADR-0010, ADR-0009) |
| 공개 전까지 관리자만 봄 | 권한 부여는 누구 × 역할 × 범위예요. 읽기도 권한 부여이고, 관리자가 "로그인한 모든 사람에게 `viewer`" 같은 기본 부여를 정할 수 있어요. 민감 등급이 속성을 가려요(ADR-0012) |
| 단계 A부터 D | 날짜 없는 순서의 계획이에요 |
| 정제, 매핑, 링크 정의마다 만드는 화면 | 화면은 다른 저장소이고 REST API의 계약으로만 대화해요(ADR-0016) |

## 5. 시뮬레이터라서 있었고 가져오지 않는 것

| 있던 것 | 왜 있었나 | 프락시움에서 |
|---|---|---|
| 세계 두 종류와 한 방향 복사, 범위 복사, 닫힘(전원, 냉방, 업링크), 객체 10만 한도 | 실험장이 한도 안에서 도니까 | 없어요. 복사는 6절을 봐요 |
| 소스에 없는 전원과 냉방을 지어 넣기, "구조만 있는 세계 / 실험할 수 있는 세계" | 물리가 돌아야 해서 | 지어내지 않아요. 모르는 것은 모름으로 두고 채워진 정도를 지표로 보여요(ADR-0007, ADR-0011, REQ-150) |
| 62개로 잠근 타입, 타입을 모델에 넣으면 끝나야 하는 다섯 가지 조건, 정밀과 기본 시뮬레이션 단계 | 타입에 시뮬레이터의 동작이 붙어서 | 모델은 운영 질문(영향, 소유, 변경)에서 시작해요. 시뮬레이터가 이해하는지는 내보내기 변환의 몫이에요 |
| 링크의 뜻 일곱 | 시뮬레이터의 전파 엔진이 계산할 수 있는 최소 집합 | 열하나로 늘렸어요. 소유와 관리와 안에 있음과 부품 같은 운영 질문이 들어왔어요(ADR-0007) |
| 소스의 사건 역할과 실측 역할 | 사고 재현과 물리 곡선 보정 | 가져오지 않아요 |
| 같은 버전이면 같은 점수 | 제품 목표의 셋째 기둥 | 같은 원본 기록과 같은 정의면 같은 KG 버전이 나와요(REQ-131). 점수는 없어요 |
| 현실 평면과 실험 평면, 일꾼 풀 분리 | 실험받는 에이전트가 현실에 닿지 않게 | 소비자 접근 제어(역할과 범위)와 서버 역할 넷(API, 일꾼, 질의 엔진, 수집기)으로 일반화했어요(ADR-0006, ADR-0012) |
| 3D 화면, 타일 접기, 지도 | 실험장의 보기 | 클로즈 베타에서 정해요 |
| 걸음 비용에서 나온 성능 수치 일부 | 시뮬레이터의 걸음 | 쓰지 않아요 |
| 준비와 운영의 상태 구분 | 실험장 안의 일부 세계만 운영이라서 | 처음부터 운영 KG예요. 운영에 영향 없이 고쳐 보는 곳은 브랜치와 후보 실행이에요(ADR-0014) |

## 6. 달라진 요구

아래 셋은 제품 책임자가 말한 요구예요. 하지만 **제품이 나뉘고 맡기기 전의 검증이 제품 밖으로 나가서** 프락시움에서는 해당하지 않아요.

| 그때의 요구 | 까닭 | 지금 |
|---|---|---|
| 현실 세계를 직접 실험하지 않고 복사해서 실험 환경을 만들어요(T0152) | 한 제품 안에서 실험하려던 요구였어요 | 필수에서 뺐어요. KG의 한 범위를 공개된 형식의 파일로 내보내는 일반 기능으로만 남겼고 뒤 순서예요(ADR-0005). **제품 책임자의 확인이 필요해요** |
| 모델은 하나이고 지어낸 세계와 받은 세계가 같은 타입을 써요(T0169) | 실험장과 한 모델을 쓰려던 요구였어요 | 모델은 프락시움의 하나예요. 테라리움과 같을 필요가 없어요(ADR-0005) |
| 실험과 현실이 따로 놀면 쓸모없어요(T0168) | 복사본에 모든 타입이 들어가게 하려던 요구였어요 | 프락시움은 실험장을 모르고 판정 기록도 받지 않아요(ADR-0005) |

이 요구 뒤의 뜻, 곧 사용자가 같은 모델로 현실과 실험을 오가고 싶다는 바람은 남아요. 내보내기 형식을 설계할 때 다시 물어요.

## 7. 찾지 못한 것

- **지워진 요구사항의 원문.** 테라리움이 없앤 요구사항(T요구 115, 116, 117, 120)의 요지는 [테라리움에서 넘겨받은 것](from-terrarium.md) 2절에만 남아 있어요. 저장소의 이력이 얕아서 원문을 되살리지 못했어요.
- **차수 계획의 발언.** 테라리움의 차수 계획 문서에는 현실 데이터에 대한 제품 책임자의 발언이 없고, 걷어내기를 적은 한 줄뿐이에요.
- **일부러 지워진 구체성.** 테라리움이 공개 저장소라서 내부에서 들은 사실을 요구의 말로 바꾸고 이름을 뺐어요(T0187, T0188). 그래서 요구가 어느 조직의 어떤 환경에서 나왔는지는 이 문서에서 알 수 없어요.
- **실제 제품과의 대조.** 소스의 응답 모양과 프리셋 매핑은 "설계 담당이 아는 대로" 적은 것이고 실제 제품 문서와 대조된 적이 없어요. 종이 위 검증(소스 여덟 가지)도 지어낸 견본이었어요.
- **제품 책임자의 입장 번복.** 처음에는 현실 데이터 가져오기를 지금 증명할 일이 아니라고 했다가(T0084) 며칠 뒤 요구사항으로 올렸어요(T0144). 어느 쪽이 지금의 뜻인지는 프락시움의 목표(ADR-0004)로 읽어요.
- **받는 쪽이 비어 있는 요구.** ECMP를 장비 설정에서 읽는다는 요구(2-2절)를 직접 받은 문장이 아직 없어요.
