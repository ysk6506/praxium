# 지금의 순서

날짜는 두지 않는다. 모두 되는 대로 빨리 하고, 무엇이 먼저인지만 정한다. 위에서 아래가 순서다.

| 순서 | 무엇 | 상태 |
|---|---|---|
| 1 | **구조 세우기**: 하네스, 문서 뼈대, 바탕 부품, CI (ADR-0002) | 끝 |
| 2 | **저장소 설정**(저장소 밖, 제품 책임자가 한다): main 보호와 `gate` 필수. 저장소는 공개로 둔다(ADR-0004) | 보호 설정 대기 |
| 3 | **제품 목표 굳히기** | 끝 (ADR-0004) |
| 4 | **KG 기반의 설계**: 별도 제품(ADR-0005), 언어와 구조(ADR-0006), KG의 모델(ADR-0007), 받기(ADR-0008), 저장과 버전(ADR-0009), 질의(ADR-0010), 운영(ADR-0011), 권한(ADR-0012), 데이터 관측성(ADR-0013), 정의의 버전과 브랜치(ADR-0014), 역량 질문(ADR-0015), 화면은 다른 저장소(ADR-0016), 프락시움 자신의 관측성과 운영 가능성(ADR-0017, 만드는 중). 넘겨받은 요구사항은 하나씩 다시 정해 [요구사항](../../product-specs/requirements.md)에 더했다 | 끝 (ADR-0005~0016). ADR-0017은 만드는 중 |
| 5 | **뼈대와 지어낸 세계**: Go 백엔드의 구조와 하네스의 Go용 검사(TD-0005), 타입 등록부와 표준 모델의 데이터 파일, 지어낸 세계 생성기 | 다음 |
| 6 | **계약**: OpenAPI 문서와 계약의 검사(서버와의 일치, 깨는 변경, 품질), 명령줄 클라이언트의 뼈대 | 대기 |
| 7 | **얇게 끝까지 한 줄**: 파일 소스 하나 → 수집 → 정제 → 공급 → 식별 → 링크 → 변경 묶음 → KG → `find`/`get`/`neighbors`를 API와 명령줄로 | 대기 |
| 8 | **받기를 넓힌다**: HTTP JSON과 SQL 어댑터, 이어서 받기와 메시지 기록 저장소 어댑터, 여러 공급의 병합, 안전장치, 일정 | 대기 |
| 9 | **정의의 브랜치와 제안과 되돌리기, 권한** | 대기 |
| 10 | **영향 범위**: 투영, 질의 엔진, 기준 구현과 견주는 시험. 지어낸 100만 객체로 기능과 결정성을 시험한다. 3천만 객체로 재는 일은 클로즈 베타에서 한다 | 대기 |
| 11 | **관측성과 역량 질문, 프락시움 자신의 관측성과 운영 행위**(진단, 운영 행위, 설정, 운영의 MCP 면) | 대기 |
| 12 | **알파**: 객체와 링크 100만 개 수준에서 모든 기능이 API와 명령줄 클라이언트로 돈다. 저장소는 PostgreSQL이고 메시지 주제는 이어서 받는 소스로 먼저 만든다. 배포 정의 | 대기 |
| 그 뒤 | **화면 저장소와 클로즈 베타**(수천만 개로 재기, 받은 변경의 기록의 메시지 기록 저장소 어댑터, 오래된 것의 자리, 객체 조건의 읽기 권한, 밖으로 내는 변경 알림의 메시지 주제 — 기본값은 [기본값 표](../../design-docs/defaults.md)에서 재서 고친다), **E2E 프로세스의 구체화**([방향 메모](../../design-docs/process-direction.md)). KG의 한 범위를 파일로 내보내는 일도 뒤 순서다 | |

## 차수마다 지키는 것

- 변경은 풀 리퀘스트로 올리고 `gate`가 초록일 때 합친다.
- 바뀐 코드와 관련된 시험만 로컬에서 돌린다. 전체는 CI가 돌린다.
- 화면과 UX 측정 하네스는 화면 저장소의 일이다(ADR-0016, TD-0002). 이 저장소의 알파는 모든 기능이 API와 명령줄 클라이언트로 되는 것이다.
- 첫 Go 제품 코드가 들어가는 변경에서 하네스의 Go용 검사를 함께 만든다(TD-0005). 그 전에는 Go 제품 코드를 합치지 않는다.
- 정리 작업(생성물 다시 만들기, 문서 감사, 작은 정리 하나, 테라리움 하네스의 바뀐 것 알리기)이 하루에 한 번 돈다. 풀 리퀘스트로 제안만 하고 합치지 않는다. 제목은 `cleanup:`으로 시작한다.
