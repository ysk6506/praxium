# 요구사항 — 인증, 권한, 시크릿

권한(160번대), 시크릿(210~217, 저장소의 구현 403~406), 접근 토큰과 관리 API(307~314), 운영 모드의 PostgreSQL 접속 TLS(472~473)의 요구사항이다. 목표와 REQ 번호의 규칙은 [요구사항 입구](requirements.md)에 있다. 번호는 모든 요구사항 문서에서 하나뿐이다.

| ID | 요구사항 |
|---|---|
| REQ-160 | **예정(ADR-0012)** 로그인은 표준 방식(OIDC)의 어댑터로 외부 SSO를 연동하고 특정 제품에 종속되지 않는다. 내장 인증(접근 토큰)은 REQ-307부터 REQ-314까지에서 먼저 만들었고 OIDC는 남은 몫이다(ADR-0044). 사람과 그룹은 SSO에서 오고, 서비스 계정은 프락시움이 발급한다. |
| REQ-161 | **예정(ADR-0012)** 권한 부여는 누구 × 역할 × 범위이고 관리자가 부여한다. 역할은 제품에 포함된 고정 8종이다(`ingester` 포함). 범위와 승인은 예정이고, 역할만 쓰는 최소한은 REQ-309다(ADR-0044). |
| REQ-162 | **예정(ADR-0012)** 읽기는 객체 타입과 민감 등급의 범위로 구분한다. 읽을 수 없는 것은 찾기와 이웃 조회에 나오지 않고, 영향 범위가 통과하면 마스킹된 객체의 수로만 응답한다. |
| REQ-163 | **예정(ADR-0012)** 제안은 수정한 항목의 소속을 범위로 가진 다른 사람이 승인한다. 조직 표준 타입은 모델 관리 역할이 승인한다. |
| REQ-164 | **예정(ADR-0012)** 누가 무엇을 수정하고 승인하고 내보냈는지, 권한 부여의 변경, 민감한 속성과 대량 읽기의 사용을 추가 전용으로 기록한다. |
| REQ-165 | **예정(ADR-0012)** 읽기 권한의 범위에 객체 조건을 적용할 수 있다. 타입이 선언한 범위용 속성(`scope_keys`)의 값으로 적용한다. 알파는 타입과 민감 등급까지, 객체 조건은 클로즈드 베타 이전에 구현한다. |
| REQ-210 | **예정(ADR-0018)** 시크릿은 평문으로 저장되지 않고 쓰기 전용이다. 정의, 로그, 내보낸 파일에 값이 없다. 오픈 베타까지 구현한다. |
| REQ-211 | **예정(ADR-0018)** 시크릿 제공자는 포트이고 외부 시크릿 스토리지와 제품에 포함된 엔벨로프 암호화 스토리지가 있다. 마스터 키는 스토리지 밖에 둔다. |
| REQ-212 | **예정(ADR-0018)** 시크릿을 복호화하는 역할은 소스에 접속하는 역할뿐이고 복호화 기록이 남는다. |
| REQ-213 | **예정(ADR-0018)** 시크릿에는 버전이 있고 교체(로테이션)할 수 있으며 만료를 미리 알린다. |
| REQ-214 | **예정(ADR-0018)** 분리망의 시크릿은 그 망을 벗어나지 않는다. |
| REQ-215 | **예정(ADR-0018)** 전송 구간은 암호화하고 인증서를 확인한다. 프락시움의 역할 사이는 서로를 확인하는 상호 인증 연결이다. |
| REQ-216 | **예정(ADR-0018)** 민감 등급이 `confidential`인 컬럼을 암호화하고, 저장 데이터의 암호화가 켜져 있는지 점검한다. |
| REQ-217 | **예정(ADR-0018)** 시크릿 유출이 의심되면 그 값을 쓰는 소스를 한 번에 중단하고 이전 버전으로 롤백하는 운영 액션이 있다. |
| REQ-403 | 시크릿 저장소는 값을 엔벨로프 암호화로 보관한다. 버전마다 새 데이터 키(32바이트)가 필드를 AES-256-GCM으로 한 번 암호화하고 데이터 키는 마스터 키로 감싼다. 인증 자료에 형식 이름, 방식 이름, 시크릿 id, 무작위 인스턴스 id, 버전(감싼 키는 마스터 키 id도)이 들어 있어 다른 시크릿이나 다른 버전의 암호문, 다른 감싼 키를 붙여 넣거나 한 바이트를 고치면 열기가 실패한다. 마스터 키 아래의 묶음 태그가 레코드의 상태 전체(범위, 허용 주소, 버전 목록과 암호문 전체, 폐기 여부)를 묶어, 파일에서 손으로 고치거나 옛 조각을 섞거나 폐기한 버전을 되살리면 열기가 실패한다. 쓰기는 모두 태그를 먼저 검증하고 다시 묶으며 폐기에도 마스터 키가 필요하다(삭제는 키 없이 된다). 남는 한계는 레코드나 파일 전체를 옛 사본으로 바꾸는 것이다. 저장 형식에 형식 이름, 판 번호, 감싸는 방식, 마스터 키 id(키에서 나온다)가 있고 모르는 판은 거절한다. 다른 마스터 키, 키 없음, 깨진 키 파일은 서로 다른 코드로 거절한다(ADR-0071). |
| REQ-404 | 시크릿의 값은 쓰기 전용이다. 열기가 돌려주는 값은 감싼 타입이고 fmt의 모든 동사, JSON, 텍스트 인코딩, `log/slog`로 어떻게 찍어도 값이 나오지 않으며 이름이 분명한 메서드 하나로만 꺼낸다. 마스터 키와 열린 값의 바이트도 설정, 서비스, 포트 값을 찍어도 나오지 않고, 오류는 호출자가 준 글을 안전한 글자일 때만 싣는다. 메타 포트의 어떤 응답과 저장 파일에도 값이 없다(ADR-0071). |
| REQ-405 | 열기는 쓰임(소스, 호스트와 포트, 목적)을 받아 한 곳에서 그 소스가 시크릿의 범위 안인지, 그 주소가 허용 주소 안인지 확인하고 아니면 코드가 있는 오류로 거절한다. 호스트는 대소문자, 끝의 점, IPv6 표기를 정규화해 비교한다(ADR-0071). |
| REQ-406 | 시크릿 저장소의 포트는 쓰기, 복호화(열기), 메타로 갈려 있어 역할은 필요한 포트만 받는다. 각 포트의 값은 다른 포트로 타입 단언되지 않는다. 메타 포트가 돌려주는 타입에는 값을 담을 자리가 없다(ADR-0071). |
| REQ-234 | **예정(ADR-0012)** 8번째 역할 `ingester`는 범위에 속한 소스에 푸시 수집만 하고(수집 엔벨로프 전송) 읽기 권한도 없다. 서비스 계정에 부여한다. |
| REQ-235 | **예정(ADR-0012)** 범위 한정 위임(자기 범위 안에서 `viewer`와 `editor`를 부여하고 회수하는 권한, `delegate`)을 위한 필드를 권한 부여의 스키마에 지금 둔다. `admin`만 부여하고 위임받은 쪽이 다시 위임하지 못한다. 구현은 클로즈드 베타다. |
| REQ-307 | 접근 토큰은 `pxm_` + 토큰 ID + 운영체제 엔트로피에서 만든 256비트 비밀이다. 서버는 도메인 접두어를 붙인 SHA-256만 저장하고 상수 시간으로 비교한다. 모든 토큰은 만료하고(기본 90일, 1시간~365일) 폐기할 수 있으며, 폐기·만료·비활성화는 다음 요청부터 거부한다. 비밀번호와 기본 계정은 없다(ADR-0044). |
| REQ-308 | 첫 관리자는 서버 기계에서 `praxium admin bootstrap`으로 만들고 토큰은 한 번만 출력한다. 활성 관리자가 있으면 거절하고, 동시에 둘이 성공할 수 없다. 잃은 토큰은 서버 기계의 `admin issue-token`으로 다시 받는다(ADR-0044). |
| REQ-309 | 토큰이 가진 역할은 토큰의 역할과 소유자의 현재 역할의 교집합이다. 관리 경로(`/v1/users`, `/v1/system-accounts`, 토큰 발급)는 `admin`만, 사용자는 `ingester`를 서비스 계정은 `admin`을 가질 수 없고 마지막 활성 관리자는 비활성화할 수 없다(ADR-0044). |
| REQ-310 | 인증 데이터는 KG와 다른 포트에 두고 메모리·파일(`identity.json`, 0600, 원자적 쓰기)·PostgreSQL 구현이 같은 적합성 테스트를 통과한다. 재시작해도 남는다(ADR-0044). |
| REQ-311 | `-mode production`은 스토리지가 file이나 postgres가 아니거나, 개발용 인증(`-dev-*` 플래그나 개발용 토큰 환경 변수)이 있거나, 활성 관리자가 없거나, TLS 없이 루프백이 아닌 주소에 열려 하거나(`-behind-proxy` 선언이 없는 경우), TLS 플래그가 하나뿐이면 스토어를 열기 전에 시작을 거부한다. `demo`와 `local`은 바뀌지 않는다(ADR-0044). |
| REQ-312 | 관리 REST API(`/v1/users`, `/v1/system-accounts`, `/v1/tokens`, `/v1/tokens/{token_id}`)와 CLI(`praxium whoami`, `praxium admin …`)를 제공한다. 만들고 행동하는 POST는 `Idempotency-Key`가 필수이고 발급한 토큰의 응답은 다시 재생하지 않는다(ADR-0044). |
| REQ-313 | 어떤 로그, 오류, 응답, 목록에도 토큰과 비밀과 해시가 나오지 않는다. 인증과 관리 사건은 `audit: true` 로그로 남는다(ADR-0044). |
| REQ-314 | 같은 주소에서 거절된 토큰이 쌓이면 그 주소의 거절된 토큰에 일정 시간 429와 `Retry-After`로 답하고 더 세지 않는다. 유효한 토큰은 차단 중인 주소에서도 통과하고 성공은 실패 횟수를 지우지 않는다. 인증 저장소가 응답하지 못하면 401이 아니라 503이다(ADR-0044). |
| REQ-472 | 운영 모드에서 스토리지가 PostgreSQL이고 접속 문자열의 호스트 가운데 하나라도 같은 기계가 아니면(루프백 주소, `localhost`, 유닛스 소켓이 아니면), `sslmode`가 `verify-full`이나 `verify-ca`가 아닌 한 스토어를 열기 전에 시작을 거부한다. `sslmode`가 없으면 드라이버의 기본값(`require`)으로 판단한다. URL과 `key=value` 형태를 드라이버의 파서로 읽고 접속 문자열은 메시지에 나오지 않는다. 거부 메시지는 지금 값과 두 가지 길(`sslmode=verify-full`, `-allow-unverified-db-tls`)을 말한다. 개발 모드와 다른 스토어에는 영향이 없다(ADR-0064). | ADR-0064, `backend/internal/pgstore/tlscheck_test.go`, `backend/cmd/praxium/dbtls_test.go` |
| REQ-473 | `-allow-unverified-db-tls`로 시작하면 서버는 PostgreSQL 접속이 서버 인증서를 확인하지 않는다는 경고를 시작 로그에 남긴다. 확인하는 접속이나 같은 기계의 접속, 개발 모드에는 경고가 없다(ADR-0064). | ADR-0064, `backend/cmd/praxium/dbtls_test.go` |
