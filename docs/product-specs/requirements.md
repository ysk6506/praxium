# 프락시움 요구사항

## 제품 목표 (ADR-0001, ADR-0004, ADR-0005)

**현실의 IT 인프라를 데이터로 받아 운영 세계를 짓고, 그 위에서 에이전트가 맡는 E2E 프로세스를 정하고 맡기고 재는 사내 운영 관리 플랫폼.**

제품 책임자가 확인한 목표다(ADR-0004). 설계 결정은 이 목표를 기준으로 내린다.

1. **현실을 받아 운영 세계(KG)를 짓고 운영한다.** 현실 시스템에서 구성 데이터를 읽어 모델(객체와 링크)에 맞추고, 무엇을 읽었고 무엇을 가정했는지 밝힌다. 현실 시스템에는 읽기만 한다. 모델은 프락시움이 쥔다(ADR-0005). 지금 구체화하는 것은 이 부분이다.
2. **일을 E2E 프로세스 단위로 정하고 에이전트에게 맡긴다.** 누가 무엇을 어디까지 해도 되는지, 누가 승인하는지, 무슨 일이 있었는지를 프락시움이 맡는다. 실제 툴은 에이전트가 MCP 게이트웨이를 통해서만 부르고, 그 호출의 인증과 인가는 게이트웨이가 책임진다. 프락시움은 실제 툴을 부르지 않는다. 방향만 있고 구체화는 뒤다([방향 메모](../design-docs/process-direction.md)).
3. **맡긴 뒤에 잰다.** 단계·사람·시간으로 잰다. 맡기기 전의 검증은 제품 밖에서 사용자가 한다. 프락시움은 그 검증을 하지도, 조건으로 삼지도 않는다.

이 문서는 요구사항의 단일 출처다. 모든 요구사항은 `REQ-NNN` ID를 가지며, 테스트는 제목에 `[REQ-NNN]`을 넣어 요구사항을 가리킨다. Go 시험은 함수 바로 위의 설명 줄에 `// [REQ-NNN] [REQ-MMM]`을 적는다(하위 시험 이름의 `[REQ-NNN]`도 읽는다, ADR-0023). 테스트가 없는 요구사항은 CI에서 실패한다(`TRACE001`). 결정은 났지만 아직 만들지 않은 요구사항은 본문을 `**예정(ADR-NNNN)**`으로 시작해 표시한다. 요구사항을 바꾸려면 ADR이 필요하다.

번호는 나눠 쓴다: 바탕 001~019, 프로세스(하네스) 020~029, 제품 100부터. 제품은 모델 100대 앞(100~109), 받기 110~129와 170대, 저장 130대, 질의와 API 140대, 운영 150대, 권한 160대, 관측 180대, 역량 질문 190대, 200대(200~209 프락시움 자신과 임시 콘솔, 210~217 비밀 값, 218~240 에이전트 시대의 정의 버전과 저장소 운영과 받기의 넓힘과 화면을 위한 API와 질의 엔진)다. 테라리움에서 넘겨받은 요구사항은 [넘겨받은 것](../references/from-terrarium.md) 2절에 있고, 하나씩 다시 정해 아래에 더했다. 각 결정의 설계는 [제품 설계 한 장](../design-docs/product-design.md)의 지도에 있다.

## 바탕

| ID | 요구사항 |
|---|---|
| REQ-001 | 같은 입력이면 같은 결과가 나온다. 시계와 난수는 한 곳(`kernel`)에서만 읽고, 나머지 코드는 주입받는다. ID, 해시, 난수열은 실행할 때마다 같다. 백엔드(Go)에서는 시계, 난수, 환경 변수를 읽는 파일을 구조 계약이 지정하고 검사가 막는다(ADR-0019). |
| REQ-002 | 사람에게 보이는 글은 쉬운 한국어다. 조사는 앞말에 맞게 붙고(이/가, 을/를, 영어 낱말과 따옴표 뒤 포함), 시간은 읽기 쉬운 단위로 적는다. |
| REQ-003 | 화면의 모든 글은 한 가지 뜻에 한 가지 말을 쓴다. 물러난 말이 화면에 돌아오면 검사가 쓸 말과 함께 알린다. |

REQ-002와 REQ-003은 프런트엔드 저장소의 것이 된다. 프런트엔드 저장소가 서면 그리로 옮긴다(TD-0006, ADR-0016). 그때까지 이 저장소에 남는다.

## 프로세스 (하네스)

| ID | 요구사항 |
|---|---|
| REQ-020 | 문서 품질: 문서는 최신 여부를 기계가 판정할 수 있어야 하고, 오래되거나 코드와 어긋난 문서는 CI에서 실패한다. |
| REQ-021 | 아키텍처 강제: 의존 방향, 공개 API 경계, 형제 격리, 외부 라이브러리 허용 범위를 기계가 검사한다. 결정(ADR)은 강제 장치와 연결된다. TypeScript와 Go 코드가 같은 규율을 받는다(ADR-0019). |
| REQ-022 | 기술 부채: 부채는 장부에 등록되고, 코드의 TODO는 장부를 가리켜야 하며, 기한이 지나거나 예산을 넘으면 실패한다. 복잡도·크기는 래칫으로 관리한다. 검사 끄기 주석·건너뛴 테스트·CI의 `continue-on-error`는 이유와 근거 번호가 있어야 하고 수는 늘 수 없다. Go 코드는 같은 한도와 같은 장부를 쓴다(ADR-0019). |
| REQ-023 | 테스트: 커버리지 하한을 래칫으로 관리하고, 테스트를 통과시키려고 테스트를 바꾸는 행위(삭제, 약화, 기대값 변경, skip)를 기계가 막는다. Go 코드는 단위마다 시험과 커버리지 하한을 갖고, Go 시험 함수(`Test`, `Fuzz`, `Example`)도 같은 잠금을 받는다. 지우거나 이름을 바꾸거나 본문과 그것이 기대는 도우미·표·정해진 값·`testdata` 파일을 바꾸면 결정 기록 없이는 실패한다(ADR-0023). |
| REQ-024 | 장기 유지보수: 어떤 코딩 에이전트가 이어받아도 AGENTS.md 하나로 길을 찾고 `pnpm check`만 통과시키면 안전하게 기여할 수 있다. 단위별 건강 상태는 하네스가 만드는 품질 등급표(`docs/generated/quality.md`, 등급 A~D)에서 한눈에 보인다. Go 단위도 같은 표에 같은 규칙으로 오른다(ADR-0023). |
| REQ-025 | 모든 설계 결정은 ADR에 이유와 함께 남긴다. 제품 목표와 요구사항은 제품 책임자가 정하고, 설계는 그것을 기준으로 정한다. |

## 제품

모두 결정은 났고 아직 만들지 않았다(`**예정(ADR-NNNN)**`). 숫자가 드는 요구는 재서 확인한다.

### 모델 (100대 앞)

| ID | 요구사항 |
|---|---|
| REQ-100 | 객체 타입, 링크 타입, 액션 타입을 데이터(타입 등록부)로 두고, 타입은 열려 있어 더할 수 있다. 이름은 영어이고 이름 규칙을 따른다. |
| REQ-101 | 링크는 닫힌 목록의 열한 가지 뜻 가운데 하나를 갖고, 뜻이 채널(`service`, `power`, `cooling`, `network`, `storage`, `management`)마다 번지는 방식을 정한다. 새 뜻은 결정 기록으로만 더한다. |
| REQ-102 | **예정(ADR-0007)** 이중화는 묶음 객체다. 산 구성원이 `min_alive` 이상이면 살았고, 산 것과 모르는 것을 합쳐도 모자라면 죽었고, 그 밖은 모른다의 세 값으로 따진다. |
| REQ-103 | **예정(ADR-0007)** 모든 값과 링크는 사실·가정·모름 등급을 갖는다. 모르는 것을 가정으로 메우지 않고, "없다"와 "모른다"는 완전성 선언으로 가른다. |
| REQ-104 | **예정(ADR-0007)** 객체는 바뀌지 않는 내부 ID를 갖는다. 같은 것 알아보기는 결정적인 규칙으로만 하고, 합치기와 가르기는 이력에 남는다. |
| REQ-105 | **예정(ADR-0007)** 표준 모델을 아홉 층에 걸쳐 넉넉하게 싣고 뼈대는 공개 표준에서 빌린다. 제품이 올라도 사용자가 더한 타입과 매핑을 덮어쓰지 않는다. |
| REQ-106 | **예정(ADR-0007)** 값·링크·묶음에 근거의 종류(`configured`, `observed`, `declared`, `derived`)를 붙이고 같은 것을 여러 길로 받는다. 의도와 관측이 어긋나면 문제 목록에 올린다. |
| REQ-107 | **예정(ADR-0007)** 타입은 `std`, `org`, `ext` 세 층이다. 조직 표준의 변경은 승인을 거치고, 비슷한 타입이 무분별하게 늘지 않게 막는 장치가 있다. |
| REQ-108 | **예정(ADR-0007)** 속성마다 바뀌는 빠르기와 이력의 종류(`versioned`, `volatile`)를 정하고, 신선도는 속성마다 낸다. |
| REQ-109 | **예정(ADR-0014)** 속성 이름이나 식별 키를 바꾸는 것 같은 깨는 변경은 옮김을 함께 적어야 저장되고, 옮김은 후보 실행으로 확인한다. |

| REQ-123 | **예정(ADR-0008)** 제품 밖의 수집기가 공개된 수집 봉투로 원본 기록을 보낼 수 있다. 받은 뒤는 다른 소스와 똑같이 거친다. |
| REQ-124 | **예정(ADR-0008)** 받는 방식은 소스마다 전부 받기, 늘어난 것만, 흐름, 흐름과 맞추기 넷 중에서 고르고, 소스와 데이터셋마다 일정을 관리한다. |
| REQ-125 | **예정(ADR-0008)** 정의 하나가 배치와 흐름에 똑같이 돈다. 같은 원본을 한 번에 넣은 결과와 나눠 흘린 결과가 같다. |

## 범위 밖

- 맡기기 전에 에이전트와 하네스를 검증하는 일. 사용자가 제품 밖(실험장)에서 독립적으로 한다. 프락시움은 실험장을 부르지 않고 그 결과를 조건으로 삼지 않는다(ADR-0005).
- 실제 툴을 부르는 일과 그 호출의 인증·인가. 에이전트와 MCP 게이트웨이의 일이다.
- 현실 시스템을 바꾸는 일. 프락시움은 읽기만 한다.
- 화면(UX·UI). 프런트엔드 저장소(아직 없다)의 일이고, 이 저장소의 계약은 REST API다. 클로즈 베타까지는 지울 수 있는 임시 콘솔만 둔다(ADR-0016).
- E2E 프로세스의 요구사항. 아직 정하지 않았고 방향만 [방향 메모](../design-docs/process-direction.md)에 있다.
