# 프락시움 요구사항

## 제품 목표 (ADR-0001, ADR-0004, ADR-0005)

**IT 인프라를 믿을 수 있는 지식 그래프(KG)로 만드는 오픈소스 플랫폼. 그 위에서 AI 에이전트에게 운영 업무를 위임하고 결과를 측정하는 것이 목표다.**

제품 책임자가 확인한 목표다(ADR-0004). 설계 결정은 이 목표를 기준으로 내린다.

1. **현실 시스템에서 데이터를 수집해 KG를 구축하고 운영한다.** 현실 시스템에서 구성 데이터를 읽어 모델(객체와 링크)로 변환하고, 무엇을 읽었고 무엇을 가정했는지 밝힌다. 현재 코드는 현실 시스템에 읽기만 한다. 모델은 프락시움이 소유한다(ADR-0005). 지금 구체화하는 것은 이 부분이다.
2. **업무를 엔드투엔드(E2E) 프로세스 단위로 정하고 에이전트에게 위임한다.** 누가 무엇을 어디까지 해도 되는지, 누가 승인하는지, 무슨 일이 있었는지를 프락시움이 관리한다. 실제 툴은 에이전트가 프락시움의 MCP 게이트웨이를 통해서만 호출하고, 그 호출의 판단과 집행과 기록은 프락시움의 구성요소가 맡는다. 게이트웨이를 우회하는 길을 막는 일은 조직의 책임이다. 현재 코드는 읽기만 하고 게이트웨이는 아직 구현하지 않았다(ADR-0061, [게이트웨이 설계](../design-docs/gateway.md)). E2E 프로세스의 구체화는 나중이다([방향 메모](../design-docs/process-direction.md)).
3. **위임한 뒤에 측정한다.** 단계·사람·시간으로 측정한다. 위임 전의 검증은 제품 밖에서 사용자가 한다. 프락시움은 그 검증을 하지도, 조건으로 삼지도 않는다.

이 문서와 아래 영역별 문서(`requirements-<영역>.md`)가 요구사항의 단일 출처다. 모든 요구사항은 `REQ-NNN` ID를 가지며, 테스트는 제목에 `[REQ-NNN]`을 넣어 요구사항을 가리킨다. Go 테스트는 함수 바로 위의 주석 행에 `// [REQ-NNN] [REQ-MMM]`을 적는다(하위 테스트 이름의 `[REQ-NNN]`도 읽는다, ADR-0023). 테스트가 없는 요구사항은 CI에서 실패한다(`TRACE001`). 결정은 났지만 아직 구현하지 않은 요구사항은 본문을 `**예정(ADR-NNNN)**`으로 시작해 표시한다. 요구사항을 변경하려면 ADR이 필요하다.

번호는 영역별로 나눠 쓰고 같은 번호는 모든 요구사항 문서에서 하나뿐이다(`TRACE004`). 번호의 영역은 다음과 같다: 기반 001~019, 프로세스(하네스) 020~029, 제품 100번 이후. 제품은 모델 100~109, 수집 110~129와 170번대, 저장 130번대, 질의와 API 140번대(KG의 읽기 전용 MCP 인터페이스는 500~519), 운영 150번대, 권한 160번대, 관측 180번대, 역량 질문 190번대, 200번대(200~209 프락시움 자신과 웹 화면(275~279 웹 UI), 210~217 시크릿(저장소의 구현은 403~406), 218~262 에이전트 시대의 정의 버전, 스토리지 운영, 수집 확장, 화면을 위한 API, 질의 엔진)이고, 게이트웨이는 450~469와 520~534다. 상시 가동 에이전트의 연동(ADR-0074)은 535~550(예정, 547은 쓰지 않는다)이고, 질의와 API(이벤트 스트림), 게이트웨이, 수집, 운영(알림), 권한(인증)의 영역 문서에 나뉘어 있다. 소스와 수집 서비스와 정의 쓰기의 설계(ADR-0058)는 401~402, 411~419, 438~449, 474~497(예정)이고, 400과 403~410은 다른 변경이 쓴다. ADR-0077로 삭제한 번호(350~357, 374~380)와 ADR-0078로 삭제한 번호(141, 142, 300~306, 425~430, 511)와 ADR-0079로 삭제한 번호(280, 281)는 다시 쓰지 않는다. 테라리움에서 인계받은 요구사항은 [인계받은 것](../references/from-terrarium.md) 2절에 있고, 하나씩 다시 정해 아래에 추가했다. 각 결정의 설계는 [제품 설계 개요](../design-docs/product-design.md)의 지도에 있다.

## 기반

| ID | 요구사항 |
|---|---|
| REQ-001 | 같은 입력이면 같은 결과가 나온다. 시계와 난수는 한 곳(`kernel`)에서만 읽고, 나머지 코드는 주입받는다. ID, 해시, 난수열은 실행할 때마다 같다. 백엔드(Go)에서는 시계, 난수, 환경 변수를 읽는 파일을 구조 계약이 지정하고 검사가 차단한다(ADR-0019). |
| REQ-002 | 사람에게 보이는 글은 한국의 IT 실무자가 쓰는 표준 용어와 짧은 문장으로 쓴 한국어다. 조사는 앞말에 맞게 붙고(이/가, 을/를, 영어 단어와 따옴표 뒤 포함), 시간은 읽기 쉬운 단위로 적는다. |
| REQ-003 | 화면의 모든 글은 한 가지 의미에 한 가지 용어를 쓴다. 옛 표기가 화면과 문서에 다시 나오면 검사가 표준 용어와 함께 알린다. |

REQ-002와 REQ-003은 화면의 요구이고 화면은 이 리포지토리의 `apps/web`에 있다. 한국어 부품(`core.kernel`)을 화면 쪽으로 옮기는 일은 부채로 남아 있다(TD-0006, ADR-0069).

## 프로세스 (하네스)

| ID | 요구사항 |
|---|---|
| REQ-020 | 문서 품질: 문서는 최신 여부를 기계가 판정할 수 있어야 하고, 오래되거나 코드와 어긋난 문서는 CI에서 실패한다. |
| REQ-021 | 아키텍처 강제: 의존 방향, 공개 API 경계, 형제 격리, 외부 라이브러리 허용 범위를 기계가 검사한다. 결정(ADR)은 강제 장치와 연결된다. TypeScript와 Go 코드가 같은 규율을 받는다(ADR-0019). |
| REQ-022 | 기술 부채: 부채는 대장에 등록되고, 코드의 TODO는 대장을 가리켜야 하며, 기한이 지나거나 예산을 넘으면 실패한다. 복잡도·크기는 래칫으로 관리한다. 검사 무시 주석·스킵된 테스트·CI의 `continue-on-error`는 이유와 근거 번호가 있어야 하고 수는 늘 수 없다. Go 코드는 같은 한도와 같은 대장을 쓴다(ADR-0019). |
| REQ-023 | 테스트: 커버리지 하한을 래칫으로 관리하고, 테스트를 통과시키려고 테스트를 변경하는 행위(삭제, 약화, 기대값 변경, skip)를 기계가 차단한다. Go 코드는 유닛마다 테스트와 커버리지 하한을 갖고, Go 테스트 함수(`Test`, `Fuzz`, `Example`)도 같은 잠금을 받는다. 삭제하거나 이름을 바꾸거나 본문과 그것이 의존하는 헬퍼·테이블·고정값·`testdata` 파일을 변경하면 결정 기록 없이는 실패한다(ADR-0023). |
| REQ-024 | 장기 유지보수: 어떤 코딩 에이전트가 작업을 이어받아도 AGENTS.md 하나로 방향을 파악하고 `pnpm check`만 통과시키면 안전하게 기여할 수 있다. 유닛별 헬스 상태는 하네스가 만드는 품질 등급표(`docs/generated/quality.md`, 등급 A~D)에서 바로 확인할 수 있다. Go 유닛도 같은 표에 같은 규칙으로 오른다(ADR-0023). |
| REQ-025 | 모든 설계 결정은 ADR에 이유와 함께 남긴다. 제품 목표와 요구사항은 제품 책임자가 정하고, 설계는 그것을 기준으로 정한다. |
| REQ-394 | 문서의 `follows` 항목은 다시 확인해야 하는 시점(`recheck`)을 정할 수 있다. `change`(기본값)는 대상이 바뀌면 바로 낡은 것이고, `release`는 다음 릴리스 전에 다시 확인하면 된다. 문자열 항목은 `change`이므로 기존 문서는 고치지 않아도 같은 검사를 받는다. 모르는 시점 값은 프런트매터 오류다(ADR-0056) |
| REQ-395 | `recheck: release` 관계의 확인 기록이 낡았으면 보통 검사(`pnpm check`, `pnpm check:pr`)에서는 실패가 아니라 알림(DOC103)이고, 릴리스 검사(`docs.ts --release`)에서는 실패(DOC013)다. 알림과 실패는 어느 문서가 어느 대상에 대해 낡았는지와 다시 확인하는 명령을 말한다. 최신이면 두 모드 모두 조용하다(ADR-0056) |
| REQ-396 | 릴리스 워크플로의 `plan` 단계는 태그와 릴리스를 만드는 실행(수동 릴리스, 태그 푸시)에서 릴리스 검사를 하고, 낡은 `release` 관계가 있으면 이유와 명령을 밝히고 거절한다. 스냅숏은 영향이 없다(ADR-0056) |
| REQ-397 | 요구사항은 입구 문서(`requirements.md`: 제품 목표, 기반, 프로세스, 범위 밖, 영역 목록)와 영역별 문서(`requirements-<영역>.md`)에 나뉘어 있다. 추적 검사는 모두를 읽고, 같은 REQ 번호가 두 곳에 있으면 실패한다(`TRACE004`). 제품 목표 문장의 출처는 입구 문서다(ADR-0063) |

## 제품

모두 결정은 났고 아직 구현하지 않았다(`**예정(ADR-NNNN)**`). 숫자가 포함된 요구는 측정해서 확인한다.

## 범위 밖

- 위임하기 전에 에이전트와 하네스를 검증하는 일. 사용자가 제품 밖(실험장)에서 독립적으로 한다. 프락시움은 실험장을 호출하지 않고 그 결과를 조건으로 삼지 않는다(ADR-0005).
- 에이전트와 하네스 자체, 그리고 게이트웨이를 우회하는 길을 막는 일. 에이전트와 조직의 일이다. 프락시움의 게이트웨이는 지나는 호출에만 보장한다(ADR-0061).
- 수집이 현실 시스템을 변경하는 일. 수집은 읽기만 한다. 변경은 게이트웨이를 지나는 호출로만 한다(ADR-0061).
- 화면의 UX·UI 설계. 클로즈드 베타에서 한다. 화면의 코드는 이 리포지토리의 `apps/web`에 있고(ADR-0069), 지금은 기능을 확인하는 수준이다. 백엔드와 화면의 경계는 REST API 계약이다.
- E2E 프로세스의 요구사항. 아직 정하지 않았고 방향만 [방향 메모](../design-docs/process-direction.md)에 있다.
