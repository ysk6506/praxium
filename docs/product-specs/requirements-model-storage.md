# 요구사항 — 모델과 저장

모델(100번대), 저장(130번대)과 스토리지 운영, KG의 세대와 시점 복구, 변경 시퀀스와 적용기의 요구사항이다. 목표와 REQ 번호의 규칙은 [요구사항 입구](requirements.md)에 있다. 번호는 모든 요구사항 문서에서 하나뿐이다.

| ID | 요구사항 |
|---|---|
| REQ-100 | 객체 타입, 링크 타입, 액션 타입을 데이터(타입 등록부)로 두고, 타입은 열려 있어 추가할 수 있다. 이름은 영어이고 이름 규칙을 따른다. |
| REQ-101 | 링크는 고정 목록의 11종 의미 가운데 하나를 갖고, 그 의미가 채널(`service`, `power`, `cooling`, `network`, `storage`, `management`)마다 전파되는 방식을 정한다. 새 의미는 결정 기록으로만 추가한다. |
| REQ-102 | **예정(ADR-0007)** 이중화는 그룹 객체다. 정상 구성원이 `min_alive` 이상이면 정상, 정상과 알 수 없음을 합쳐도 모자라면 장애, 그 밖은 알 수 없음의 3값으로 판정한다. |
| REQ-103 | **예정(ADR-0007)** 모든 값과 링크는 사실·가정·알 수 없음 등급을 갖는다. 모르는 것을 가정으로 메우지 않고, "없다"와 "모른다"는 완전성 선언으로 구분한다. |
| REQ-104 | **예정(ADR-0007)** 객체는 바뀌지 않는 내부 ID를 갖는다. 동일 객체 식별은 결정적인 규칙으로만 하고, 병합과 분리는 이력에 남는다. |
| REQ-105 | **예정(ADR-0007)** 표준 모델을 9개 계층에 걸쳐 충분히 담고 기본 구조는 공개 표준에서 차용한다. 제품을 업그레이드해도 사용자가 추가한 타입과 매핑을 덮어쓰지 않는다. |
| REQ-106 | **예정(ADR-0007)** 값·링크·그룹에 근거 종류(`configured`, `observed`, `declared`, `derived`)를 붙이고 같은 것을 여러 경로로 수집한다. 의도와 관측이 어긋나면 문제 목록에 올린다. |
| REQ-107 | **예정(ADR-0007)** 타입은 `std`, `org`, `ext` 3계층이다. 조직 표준의 변경은 승인을 거치고, 비슷한 타입이 무분별하게 늘어나지 않도록 막는 장치가 있다. |
| REQ-108 | **예정(ADR-0007)** 속성마다 변경 빈도와 이력의 종류(`versioned`, `volatile`)를 정하고, 신선도는 속성마다 계산한다. |
| REQ-109 | **예정(ADR-0014)** 속성 이름이나 식별 키를 바꾸는 것 같은 호환성을 깨는 변경은 마이그레이션을 함께 적어야 저장되고, 마이그레이션은 드라이 런으로 확인한다. |
| REQ-130 | **예정(ADR-0009)** KG 버전은 바뀌지 않고 두 버전의 차이를 바로 읽을 수 있다. |
| REQ-131 | **예정(ADR-0009)** 직전 상태, 수집 순서대로의 원본 레코드, 정의, 실행기의 의미 버전이 같으면 같은 KG 버전이 나온다. 변경 시퀀스 기준의 몫은 REQ-246이다. |
| REQ-132 | 적용은 한순간에 공개되고 읽기 측은 이전 상태나 새 상태 하나만 본다. 큰 적용은 읽기 워터마크(`readable_through`)를 배치가 끝날 때만 올리고, 그 전의 청크는 읽기, 변경 항목, `WaitReadable`에 나타나지 않는다(ADR-0025). |
| REQ-133 | **예정(ADR-0009)** 스토리지는 제품이 함께 제공하고, 커밋된 데이터를 잃지 않는다. |
| REQ-134 | **예정(ADR-0009)** 한 KG에 객체와 링크 수천만 개를 담고, 설계 여유는 수억까지 둔다. 알파는 100만 개 수준에서 모든 기능이 동작하고, 수천만 개는 클로즈드 베타에서 합성한 3천만 객체로 측정해서 확인한다(엔진은 1억까지 측정했고 그 위는 추정이다). 구조는 처음부터 수천만 개를 기준으로 설계한다. |
| REQ-135 | KG는 변경 시퀀스이고 버전은 그 위의 확정 버전이다. 어느 과거 변경 번호든 읽을 수 있고, 확정은 적용된 지점과 읽기 워터마크가 같을 때만 되며, 그래프 해시가 그대로면 새 버전을 만들지 않는다(ADR-0025). |
| REQ-136 | **예정(ADR-0009)** KG의 한 범위를 공개된 형식의 파일로 내보낼 수 있다. 읽기 권한의 범위 안에서만 내보내고 감사 로그에 남긴다. 우선순위는 알파 이후다. |
| REQ-222 | **예정(ADR-0009)** 질의하는 측이 `min_seq`를 주면 복제본이 그 번호에 못 미칠 때 주 스토리지로 가거나 대기하거나 거절한다. 청크 분할과 대기의 몫은 REQ-249에서, 첫 3개 질의가 `min_seq`를 받는 몫은 REQ-252에서 분리했다. |
| REQ-223 | **예정(ADR-0009)** 스토리지 신호(`storage.*`)를 자기 관측성에 발행하고, 모든 스토리지 접근은 `kg_id`로 스토리지를 찾는 계층을 거친다. |
| REQ-231 | **예정(ADR-0009)** KG는 계약의 자원이다. KG에 든 것을 다루는 모든 API 경로는 `/v1/kgs/{kg}/...` 아래이고 운영 KG는 `main`으로도 가리킨다. 정의의 메인 브랜치는 배포마다 하나이고 KG는 그 메인 브랜치의 어느 정의 세트를 쓰는지 가리킨다. 응답의 `as_of`에 KG의 ID와 세대가 실린다. |
| REQ-232 | **예정(ADR-0009)** `volatile` 속성의 변경을 프로젝션, 충족 표시, 변경 알림, SSE가 따라간다. 응답 엔벨로프에 `volatile_as_of`를 싣는다. 링크는 `volatile`이 될 수 없다. 스토리지 측의 몫(경량 변경 레코드, 과거 읽기에서의 생략)은 REQ-247에서, 첫 3개 질의의 엔벨로프 몫은 REQ-252에서 분리했다. |
| REQ-233 | 행은 타입, 링크 타입, 속성을 바뀌지 않는 작은 정수(`type_no`, `link_type_no`, `attr_no`)로 가리킨다. 이름은 바꿀 수 있다. 해시에는 번호가 아니라 바뀌지 않는 ID가 포함된다. |
| REQ-237 | **예정(ADR-0009)** 세대가 `as_of`, 커서, 이벤트 ID, `min_seq`에 실리고, 세대가 다르면 `conflict.generation_changed`로 응답한다. 세대를 KG에 두고 복구마다 올리는 것은 REQ-248에서, 큰 적용의 읽기 워터마크는 REQ-132에서 분리했다. |
| REQ-238 | **예정(ADR-0009)** 원본 레코드에 마스킹 표시(내용은 삭제하고 해시와 위치와 이유만 남김)를 처음부터 둔다. `admin`의 운영 액션이고 감사에 남는다. |
| REQ-246 | 같은 변경 시퀀스, 정의 세트, 실행기의 의미 버전이면 같은 ID, 변경 번호, 내용 해시, 그래프 해시, 버전 ID가 나온다. 청크 한도, 배치 안의 항목 순서, 타입과 속성의 이름 변경과 번호 변경은 결과를 바꾸지 않는다. REQ-131에서 분리한 요구다(ADR-0025). |
| REQ-247 | `volatile` 속성의 변경은 이력 없는 경량 변경 레코드에 한 건으로 남고 행과 그래프 해시에 포함되지 않는다. 같은 값을 다시 기록하면 변경이 아니다. 과거 변경 번호와 버전의 읽기는 `volatile` 값을 제공하지 않고(`graph_volatile_omitted`) 읽기 지점이 `omitted`임을 알린다. REQ-232에서 분리한 요구다(ADR-0025). |
| REQ-248 | KG에 세대가 있고 시점 복구(`Restore`)마다 하나 오르며 복구 이벤트가 남는다. 이전 세대를 가진 읽기 지점, 이미 확보한 스냅샷, 쓰기는 `graph_generation_changed`로 거절된다. 복구 뒤의 버전에 새 세대가 적힌다. REQ-237에서 분리한 요구다(ADR-0025). |
| REQ-249 | 큰 적용은 한 트랜잭션이 아니라 청크로 나눠 하고, 중단되면 다음 청크부터 이어서 하거나 포기해 롤백할 수 있으며 같은 적용의 재시도는 한 번만 반영된다. 초기 적재가 만드는 KG는 마지막 청크가 끝날 때까지 `building`이다. 질의하는 측이 `min_seq`를 주면 읽을 수 있을 때까지 대기하고 시간이 지나면 거절한다(`WaitReadable`). REQ-222에서 분리한 요구다(ADR-0025). |
| REQ-261 | 적용기는 링크의 차수 규칙(`1:1`, `N:1`)을 링크 타입이 아니라 링크가 놓인 바인딩마다 센다. 한 클러스터가 `1:1` 바인딩으로 컨트롤 플레인 하나와 `N:1` 바인딩으로 네임스페이스 여럿을 가질 수 있고, 같은 바인딩의 두 번째는 거절된다(ADR-0027). |
| REQ-270 | PostgreSQL 어댑터(`adapter.pgstore`)가 스토리지 포트의 네 역할을 모두 구현하고 적합성 테스트 31사례를 고치지 않고 통과한다. 쓰기는 헤드 행을 잠가 세대, 리스(lease), 엔진 의미 버전, 기대한 헤드를 차례로 확인하고 한 트랜잭션에서 행과 헤드를 함께 쓴다. 모든 기본키와 인덱스는 `kg_id`로 시작하고, 변경 번호는 헤드 행의 카운터이며, 스토리지 접근은 `kg_id`를 키로 하는 라우팅 계층을 지난다. 스키마는 내장한 SQL 파일과 직접 만든 마이그레이션 실행기로 올리고, 역할(적용, API 읽기, 대량, 드라이 런, 마이그레이션)마다 구문 실행 시간 한도와 잠금 대기 한도를 둔다. `api serve -store postgres -store-dsn-file <파일>`로 고르고(기본은 인메모리 스토리지), 연결 문자열(DSN)은 파일에서만 읽으며 인자와 로그와 오류에 나오지 않는다. 테스트는 실제 PostgreSQL에서 돌고 서버가 없으면 건너뛰지 않고 실패한다. TD-0011을 닫는 요구다(ADR-0032). |
| REQ-271 | 내장 파일 스토어: `api serve -store file -store-data-dir <폴더>`는 PostgreSQL 없이 실행 파일 하나와 데이터 폴더 하나로 KG를 영속 저장한다. 저널을 붙인 스토어는 적합성 테스트 31사례를 모두 통과하고, 닫았다가 같은 폴더로 다시 열면 그래프 해시, 변경 번호, 이력 조회가 같다. 기본 스토리지는 계속 `memory`다. 단일 프로세스, 이중화 없음, 메모리에 들어가는 규모가 한계이고 운영과 대규모는 PostgreSQL이 맡는다(ADR-0034). |
| REQ-272 | 응답을 돌려준 쓰기는 전원 차단, 쓰기가 끊긴 지점, 동기화하지 않은 바이트의 유실 뒤에도 전부 있고, 그 밖에는 응답 전 쓰기의 접두 일부만 있을 수 있다. 로그 끝의 깨진 레코드는 잘라 내고 계속하며, 쓰기에 실패한 스토어는 이후의 쓰기를 거절한다. 장애 주입 테스트가 모든 디스크 연산과 모든 바이트 위치에서 확인한다(ADR-0034). |
| REQ-273 | 파일 머리에 형식 이름과 버전이 있고 모르는 버전은 열지 않고 명확한 오류를 낸다. 로그 중간의 손상, 빠진 레코드, 번호가 맞지 않는 레코드는 조용히 건너뛰지 않고 오류로 멈춘다. 같은 데이터 폴더를 두 프로세스가 열지 못하고, 죽은 프로세스의 잠금은 운영체제가 회수한다(ADR-0034). |
| REQ-274 | 스냅샷은 임시 파일에 쓰고 동기화한 뒤 이름을 바꾸고 폴더를 동기화한다. 스냅샷도 체크섬으로 검증하고, 손상됐으면 직전 세대의 스냅샷과 그 뒤의 로그로 복구한다. 닫을 때 스냅샷을 쓰고, 스냅샷에 실패해도 로그가 온전하므로 쓰기를 계속한다(ADR-0034). |
| REQ-420 | **예정(ADR-0059)** 링크마다 `strength`와 `whole_needs_part`의 값을 직접 가질 수 있다. 값은 링크 타입이 고정한 값, 링크에 쓴 값(바인딩이 허용하는 값 안에서만), 바인딩의 기본값, 허용된 값이 하나뿐이면 그 값, 링크 의미의 기본값(`strength`는 hard, `whole_needs_part`는 none)의 순서로 정해진다. 개수(`cardinality`)는 바인딩의 속성이다. |
| REQ-421 | **예정(ADR-0059)** 맞는 바인딩이 여럿이면 정해진 우선순위(양쪽 끝이 좁은 것, 끝의 점수는 any 0, 트레이트 1, 타입 2 + 깊이이고 합이 큰 쪽, 같으면 바인딩 id 순)로 하나가 뽑히고, 같은 입력에는 언제나 같은 바인딩이 뽑힌다. 우선순위를 처음 넣는 0단계의 완료 기준은 모든 타입 쌍의 유효한 카디널리티와 인자가 전과 같은 것이다. |
| REQ-422 | **예정(ADR-0059)** 바인딩은 알려진 조합과 일반 규칙으로 나뉜다. 일반 규칙(누구나 그룹의 구성원, 그룹이 그룹의 구성원이고 순환은 금지, 구성원에게 의존할 수 있는 곳에서는 그룹에도 의존)은 알려진 조합이 하나도 맞지 않을 때만 쓴다. |
| REQ-423 | **예정(ADR-0059)** 그룹이 장비에 속하는 `PART_OF`(hard만 허용하는 바인딩 여섯)는 `whole_needs_part`의 기본값을 none으로 하고 허용 값을 hard와 none으로 한다. |
| REQ-424 | **예정(ADR-0059)** 점대점 연결의 의미는 링크 타입이 아니라 바인딩 단위로 켜고 끈다. 네트워크의 포트와 포트에만 켜고 장비와 장비의 이웃 관계와 전원에는 켜지 않는다. |
