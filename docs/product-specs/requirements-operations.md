# 요구사항 — 운영과 관측

운영(150번대), 관측(180번대), 역량 질문(190번대), 프락시움 자신의 운영 요구(200~208), 단계의 요구사항이다. 목표와 REQ 번호의 규칙은 [요구사항 입구](requirements.md)에 있다. 번호는 모든 요구사항 문서에서 하나뿐이다.

| ID | 요구사항 |
|---|---|
| REQ-150 | **예정(ADR-0013)** 품질을 수치로 보여 준다: 채워진 정도, 사실·가정·알 수 없음의 비율, 연결되지 않은 객체, 중복 객체, 소스 간 충돌, 신선도, 건수 정합성. KG 버전마다 남긴다. |
| REQ-151 | **예정(ADR-0011)** 문제 목록은 규칙으로 해결한다. 같은 이유의 문제를 그룹으로 보여 주고, 해결 방법은 규칙을 수정해 드라이 런으로 확인하는 것이다. 사용자가 신고하는 경로도 문제 목록으로 들어온다. |
| REQ-152 | **예정(ADR-0013)** 신선도를 숨기지 않는다. 소스에는 마지막으로 온전히 수집한 시각을, 응답에는 데이터가 얼마나 오래됐는지를 붙인다. |
| REQ-154 | **예정(ADR-0011)** 기능마다 가용성 등급이 있다. 질의는 중단되지 않고, 원본 레코드·정의·KG 버전과 이력·실행 이력·감사 로그는 잃지 않는다. 정의 수정은 중단돼도 된다. 스토리지 없이 응답하는 동안 권한 캐시의 경과 시간이 상한(기본값 15분)을 넘으면 기본 부여의 읽기만 응답한다. |
| REQ-180 | **예정(ADR-0013)** 실행기가 8개 영역(연결, 수집, 유효성, 파이프라인, 객체, 링크와 그룹, 변경, 사용)의 신호를 발행한다. |
| REQ-181 | **예정(ADR-0013)** 소스·데이터셋·피드·타입·속성·링크 타입·파이프라인·KG마다 헬스 상태를 계산한다. 헬스 상태는 정의의 계보를 따라 전파되고 근본 원인별로 그룹화된다. |
| REQ-182 | **예정(ADR-0013)** 피드·타입·속성에 목표(신선도, 온전함, 유효성, 수집량)를 선언하고, 지키지 못한 비율을 기록한다. |
| REQ-183 | **예정(ADR-0013)** 수집량, 변경량, 컬럼의 통계를 평소 수준과 비교한다. 같은 입력이면 같은 판정이 나오는 고정된 통계 기법으로 한다. |
| REQ-184 | **예정(ADR-0013)** 알림의 규칙은 고정된 종류이고, 같은 근본 원인의 알림은 하나로 합쳐져 담당자에게 전달된다. |
| REQ-185 | **예정(ADR-0013)** 동기화 한 번과 스트림의 한 구간마다 단계별 건수·시간·탈락한 레코드의 샘플을 확인하고, 자원별 이력을 타임라인으로 본다. |
| REQ-186 | **예정(ADR-0013)** 소스나 피드가 비정상일 때 어느 타입과 속성, 어느 파생 그룹, 어느 소비 시스템이 영향받는지 답한다. |
| REQ-187 | **예정(ADR-0013)** 사전 정의 질의 `health`와 `quality`를 API와 MCP로 제공하고, 모든 응답에 헬스 상태 힌트를 붙인다. |
| REQ-188 | **예정(ADR-0013)** 지표를 제품 안에 저장하고 널리 쓰는 열린 형식으로 내보낸다. 지표와 로그에는 행의 내용과 시크릿이 없다. |
| REQ-189 | **예정(ADR-0013)** 이중화 상태(여유가 0인 그룹)와 변동(flapping), 아무도 읽지 않는 타입·속성·피드를 보여 준다. |
| REQ-190 | **예정(ADR-0015)** 역량 질문은 정의의 항목이고 고정된 패턴으로 작성한다. 홉 수 제한 없이 연결할 수 있다. |
| REQ-191 | **예정(ADR-0015)** 충족률을 객체마다 자동으로 증분 계산하고 KG 버전마다 남긴다. |
| REQ-192 | **예정(ADR-0015)** 속성으로 필터링하고 그룹화해서 충족률을 본다. 어느 요구, 어느 홉, 어느 소스 때문에 충족하지 못하는지 세분해서 보고, 한도를 넘어 판정하지 못한 객체는 따로 센다. |
| REQ-193 | **예정(ADR-0015)** 표준 모델이 기본 질문을 포함하고, 타입 등록부(`required`, 바인딩의 최소 개수)에서 구조 질문이 자동으로 생성된다. |
| REQ-194 | **예정(ADR-0015)** 드라이 런의 검사에 충족률의 증감이 보이고 목표를 깨는 병합은 차단된다. 미충족 항목의 보고와 `competency` 질의를 제공한다. |
| REQ-195 | **예정(ADR-0015)** 예시 객체에서 역량 질문의 패턴을 만든다. 응답이 될 객체를 고르면 그 객체까지의 도달 경로를 보여 주고 선택한 경로가 패턴의 골격이 된다. |
| REQ-200 | **예정(ADR-0017)** 역할 4종(API, 워커, 질의 엔진, 수집기)이 같은 방식으로 지표·로그·추적을 열린 형식으로 발행한다. 로그의 모든 레코드에 안정된 이벤트 코드가 있고 시크릿과 행의 내용은 없다. |
| REQ-201 | **예정(ADR-0017)** 제품이 합성한 작은 소스로 수집에서 질의 응답까지 걸리는 시간을 스스로 측정한다. 그 소스의 객체는 운영 KG와 별도의 KG에 담는다. |
| REQ-202 | **예정(ADR-0017)** 프락시움의 컴포넌트마다 헬스 상태를 발행하고 `diagnose`로 비정상인 것, 이유, 근거 신호, 실행할 수 있는 운영 액션을 제공한다. 기본은 스토리지 없이 응답한다. |
| REQ-203 | **예정(ADR-0017)** 이벤트 코드와 오류 코드의 목록이 계약이다. 코드마다 의미, 심각도, 확인할 사항, 실행할 수 있는 운영 액션이 기계가 읽을 수 있는 형식으로 포함된다. |
| REQ-204 | **예정(ADR-0017)** 운영 액션은 고정된 목록이고 모두 API, 명령줄, MCP로 사용할 수 있다. 액션마다 위험의 축과 롤백 액션이 있고, 드라이 런이 있으며, 실행한 뒤에 효과가 나타났는지 확인한다. |
| REQ-205 | **예정(ADR-0017)** 운영 설정은 API로 변경하는 버전이 있는 데이터다. 변경마다 이전 값이 남고 리버트할 수 있으며 값의 범위를 검사한다. |
| REQ-206 | **예정(ADR-0017)** 운영 액션은 역할과 범위를 따르고, 액션마다 사람의 승인을 요구하도록 설정할 수 있다. 누가 무엇을 어떤 진단을 근거로 했는지 감사 로그에 남는다. |
| REQ-207 | **예정(ADR-0017)** 읽기 전용 MCP(`/mcp`)와 별도로, 다른 주소로 운영용 MCP 인터페이스를 제공한다(ADR-0062): 신호 조회, `diagnose`, 이벤트 코드 목록, 운영 액션(드라이 런 포함). |
| REQ-208 | **예정(ADR-0017)** 신호를 발행하는 경로와 알림을 전송하는 경로가 정상인지 하트비트로 외부에 알리고, 업그레이드 중의 상태와 한도에 도달할 때까지의 전망을 신호로 발행한다. |
| REQ-239 | ARCHITECTURE.md에 의존성 표(배포의 필수, 선택, 도입하는 라이브러리의 이름과 라이선스와 직접 구현하지 않는 이유와 대체 방안)를 두고, 라이브러리를 추가하는 변경은 이 표를 수정한다. 기계가 Go 모듈 파일(`go.mod`)과 표를 대조하고, 라이선스는 허용 목록 안이어야 한다(ADR-0019). |
| REQ-240 | **예정(ADR-0014)** 릴리스 단계는 알파 1(골격과 수직 슬라이스 하나, 웹 화면), 알파 2(확장), 클로즈드 베타, 오픈 베타, 정식이다. 일부 계약은 필드, 경로, 코드 목록의 자리만 알파에 두고 구현은 클로즈드 베타로 미룬다. |
